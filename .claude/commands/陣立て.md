# 陣立て（開発環境セットアップ）

> **BE 起動の正系（一本鎖）**: `start-backend.vbs` → `start-backend.ps1`（mutex 多重起動防止）→ WSL `/home/kenta/backend-loop.sh`（git pull→bootRun ループ）。
> **Windows 側で `gradlew bootRun` を直接叩かない**（0xC0000005 クラッシュの温床）。旧 `start-backend.bat` は廃止済み（2026-07-08 削除）。

以下の手順を順番に実行し、開発環境を整えてください。

## 1. Windows 側（本陣）を最新に同期

origin/main の最新コミットを本陣に取り込む。PowerShell で実行する（Bash の本陣 git ブロックを回避するため）。

```powershell
git -C "C:\Claude\mannschaft" pull --ff-only
```

## 2. WSL2 起動 & キープアライブ

WSL2 はアイドル時に自動停止するため、バックグラウンドプロセスで維持する。

```bash
wsl -d Ubuntu-24.04 -- bash -c "nohup sleep infinity </dev/null &>/dev/null & disown; echo 'WSL2 keepalive started'"
```

## 3. Docker コンテナ起動

MySQL 8.0 + Valkey 8 + Jaeger を docker compose で起動する。

**稼働中のコンテナは再作成しない**こと。`docker compose up -d` は構成差分があると稼働中コンテナを
作り直す場合があり、Valkey 上のアカウントロック / レート制限 / JTI ブラックリスト等の認証防御状態が
無用に消える。停止中のサービスだけを起動する条件付きで実行する。

```bash
wsl -d Ubuntu-24.04 -- bash -c "cd /mnt/c/Claude/mannschaft && \
  { docker compose ps --status running --format '{{.Service}}' 2>/dev/null | grep -qx mysql  || docker compose up -d mysql; } && \
  { docker compose ps --status running --format '{{.Service}}' 2>/dev/null | grep -qx valkey || docker compose up -d valkey; } && \
  docker compose --profile observability up -d jaeger"
```

> `docker compose ps --status running --format` が使えない古い compose の場合は、
> `docker compose ps | grep mannschaft-valkey | grep -q Up || docker compose up -d valkey` のように
> コンテナ名で稼働判定するフォールバックを使ってよい（意図は「稼働中は触らない・停止中のみ起動」）。

## 4. ミドルウェア接続確認

MySQL・Valkey・Jaeger が Windows 側の localhost から到達可能か確認する。
すべて `TcpTestSucceeded: True` であること。

```bash
powershell.exe -Command "
  Write-Host '=== MySQL (3306) ===' ;
  (Test-NetConnection -ComputerName localhost -Port 3306 -WarningAction SilentlyContinue).TcpTestSucceeded ;
  Write-Host '=== Valkey (6379) ===' ;
  (Test-NetConnection -ComputerName localhost -Port 6379 -WarningAction SilentlyContinue).TcpTestSucceeded ;
  Write-Host '=== Jaeger (4318) ===' ;
  (Test-NetConnection -ComputerName localhost -Port 4318 -WarningAction SilentlyContinue).TcpTestSucceeded
"
```

接続できない場合は、コンテナの状態を確認して対処すること：
```bash
wsl -d Ubuntu-24.04 -- bash -c "docker compose -f /mnt/c/Claude/mannschaft/docker-compose.yml ps"
```

## 5. backend-loop.sh を WSL へインストール

再起動ループスクリプトを WSL のホームディレクトリへコピーする（初回・更新時のみ必要）。

> **CRLF 対策（必須）**: 本陣は `core.autocrlf=true` のため `backend-loop.sh` が **CRLF 改行**でチェックアウトされる。これをそのまま WSL へ `cp` すると、bash が `$'\r': command not found` → `syntax error: unexpected end of file` で**ループ本体に到達せず即死**し、Spring Boot がいつまでも起動しない（vbs / nohup / setsid どの起動方式でも同一failで全滅するため誤診しやすい）。`cp` の直後に `sed -i 's/\r$//'` で **LF 化**してから使うこと。

```bash
wsl -d Ubuntu-24.04 -- bash -c "cp /mnt/c/Claude/mannschaft/backend-loop.sh /home/kenta/backend-loop.sh && sed -i 's/\r$//' /home/kenta/backend-loop.sh && chmod +x /home/kenta/backend-loop.sh && bash -n /home/kenta/backend-loop.sh && echo 'backend-loop.sh installed (LF normalized)'"
```

## 6. Spring Boot 起動 / 最新反映（自動再起動ループ付き）

**このステップの意図**: 陣立ての目的は「**最新コードの BE が動いている状態**」を作ること。単に 8080 が UP かどうかで判断すると、**古いコードのまま生き残った BE を素通り**してしまう（実際に根治PRマージ後、古い bootRun が残り実機検証できない事故が起きた）。したがって「**稼働中BEが origin/main 最新か**」で判定し、**古ければ止めて最新で立て直す**。

- 稼働中BEが最新 → 触らない（無用な6分ダウンを避ける）
- 稼働中BEが古い（stale）→ **bootRun サブツリーだけ止める**。`backend-loop.sh`（親）は起動時に `git pull` するので、次ループで最新を pull し直し再コンパイル＋再起動する。`backend-loop.sh` 本体は温存すること（`pkill -f` は自分のコマンドラインに一致して自滅するので使わない。PID または限定パターンで）
- 8080 が落ちている / backend-loop も死んでいる → `start-backend.vbs` で起動

> 走っている bytecode のコミット = WSL 作業ツリー `/home/kenta/mannschaft` の HEAD（backend-loop は再起動時にしか pull しないため）。これを `origin/main` と比較して stale 判定する。

### 6-1. 稼働状況と最新性の判定

```bash
wsl -d Ubuntu-24.04 -- bash -c "cd /home/kenta/mannschaft && git fetch origin --quiet 2>/dev/null; \
  echo HEAD=\$(git rev-parse --short HEAD); \
  echo ORIGIN=\$(git rev-parse --short origin/main); \
  (pgrep -f 'backend-loop.sh' >/dev/null && echo loop=alive || echo loop=dead)"
```

### 6-2. 分岐

- **HEAD == ORIGIN かつ 8080 UP** → 「最新稼働中」スキップ。
- **HEAD != ORIGIN（stale・loop=alive）** → bootRun サブツリーを止めて最新化（backend-loop が自動で pull+再コンパイル+再起動）:

```bash
wsl -d Ubuntu-24.04 -- bash -c "pgrep -f 'gradle-wrapper.jar bootRun' | xargs -r kill; sleep 2; fuser -k 8080/tcp 2>/dev/null; echo 'bootRun停止 → backend-loopが最新コードで再起動する'; pgrep -af backend-loop.sh | grep -v pgrep"
```

- **8080 ダウン、または loop=dead** → vbs で起動:

```powershell
Start-Process -FilePath "wscript.exe" -ArgumentList "C:\Claude\mannschaft\start-backend.vbs" -WindowStyle Hidden
Write-Host "start-backend.vbs を起動しました（自動再起動ループ付き）"
```

### 6-3. 起動 / 再コンパイル確認（最大 7 分）

> **健全性チェックは `Invoke-RestMethod` / `Test-NetConnection` を使わない**。WSL2 mirrored 下では健全な BE を偽タイムアウト判定する（memory `project_wsl2_mirrored_healthcheck_tool_false_negative`）。**`curl.exe --noproxy "*"`** で叩く。再起動直後は数十秒 `000` / 接続不可でも慌てない（フル再コンパイル ～6分）。この待機ループは長時間ゆえ **バックグラウンド実行**（`run_in_background`）で回し、完了通知を待つこと。

```bash
for i in $(seq 1 42); do
  code=$(curl.exe -s --noproxy "*" -o /dev/null -w "%{http_code}" http://localhost:8080/actuator/health 2>/dev/null)
  if [ "$code" = "200" ]; then echo "Spring Boot UP (HTTP 200) after ${i}0s"; break; fi
  echo "Waiting... ($i/42) http=$code"; sleep 10
done
```

### 6-4. 反映確認（stale から立て直した場合・必須）

再起動後、走っているコードが最新であることを裏取りする（HEAD 一致 + スキーマ変更PRなら migration 適用確認）:

```bash
wsl -d Ubuntu-24.04 -- bash -c "cd /home/kenta/mannschaft && echo HEAD=\$(git rev-parse --short HEAD) / ORIGIN=\$(git rev-parse --short origin/main)"
```

HEAD == ORIGIN になっていれば反映完了。ならなければ backend-loop のログ（`git pull` が openapi.json / gradlew のローカル変更で abort していないか等。memory `project_wsl_backend_update_pitfalls`）を確認する。

## 7. 結果報告

全ステップの結果を以下の形式で簡潔に報告する：

| 項目 | 状態 |
|------|------|
| Windows git pull | ✅ / ❌ |
| WSL2 | ✅ / ❌ |
| MySQL | ✅ / ❌ |
| Valkey | ✅ / ❌ |
| Jaeger | ✅ / ❌ |
| Gradle ビルド | ✅ / ❌ |
| backend-loop.sh インストール | ✅ / ❌ |
| Spring Boot (8080) | ✅ / ❌ |
| 最新反映 (HEAD == origin/main) | ✅ / ❌ |

全て ✅ なら「**陣立て完了。殿のご下命をお待ちしております。**」と報告する。
`最新反映` が ❌（稼働中BEが古いまま）の場合は、手順6の stale 分岐で bootRun を立て直してから再確認すること。
❌ がある場合は原因を調査し、自動修復を試みた上で再報告する。
