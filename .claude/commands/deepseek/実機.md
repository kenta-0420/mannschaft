# 実機E2Eテスト（ユーザー視点・抜けなし最終確認）

[DEEPSEEK版] モデル名を Pro/Flash に置換・振り分けを2段階に簡素化（元: 実機.md）


「ユーザーが本当に操作する」視点で、モックなし・実BE・実FEの実機E2Eテストを実行する。
/試練・/出陣・/検分 が揃ったあと、マスターへの引き渡し前の**最終確認**として必ず実施すること。

## 思想・位置づけ

```
試練(red)→ 出陣(green)→ 検分(静的) →【実機E2E（このコマンド）】→ マスターへリリース
```

- **モックベースのテスト = 「コードが期待どおりに動くか」の確認**。実装の誤り・型の不一致は発見できる。
- **実機E2E = 「ユーザーが本当に使えるか」の確認**。API呼び出し経路・認可・DB永続化・Cookie/Session・ブラウザ挙動まで全て通す。
- **"API フローのみのテスト" は実機E2Eではない**。ブラウザが画面を表示し、ボタンをクリックし、入力し、結果が見える——この一連を踏むものだけが実機E2Eである。

## 前提条件（起動確認）

```powershell
# BE (8080) が動いているか
curl.exe -s http://localhost:8080/actuator/health --noproxy "*" | Select-String "UP"

# FE (3001 or 3000) が動いているか
curl.exe -s http://localhost:3001/ --noproxy "*" | Select-String -Quiet "html"
```

どちらかが落ちている場合は `/陣立て` で環境を整えてから実行する。

## 引数

```
/実機                         # 対象を引数から検出（戦役台帳・/軍議 の受け入れ条件リストを参照）
/実機 webauthn                # WebAuthn（パスキー）フロー
/実機 2fa                     # 二段階認証フロー
/実機 auth                    # 認証全体（ログイン・ログアウト・リフレッシュ）
/実機 security                # settings/security ページ全体
/実機 <spec-file-path>        # 指定ファイルを直接実行
```

引数なしの場合は、直近の軍議の受け入れ条件と戦役台帳を参照して対象を決定する。

## 実行手順

### 1. カバレッジ棚卸し（スキップされているテストを洗い出す）

```bash
# `test.skip` / `test.todo` / `xtest` が含まれるスペックを列挙
cd frontend && grep -rn "test\.skip\|test\.todo\|xtest\|\.skip(" tests/e2e/real/ | head -40
```

**スキップされているテストがある場合**：
- スキップ理由を読む（コメントを確認）
- 理由が解消可能なら解消してから実行（環境変数・BE設定 等）
- 解消できない場合はその旨をマスターに報告し、next step を提示する

### 2. テスト実行

**対象スペックを指定して実行**（全件流しは時間がかかるため、今回の戦役対象に絞る）：

```bash
# 例: webauthn フロー
cd frontend && npx playwright test tests/e2e/real/webauthn-flow.spec.ts --reporter=list

# 例: 2FA フロー
cd frontend && npx playwright test tests/e2e/real/2fa-flow.spec.ts --reporter=list

# ヘッドありで実際の画面を見たい場合（デバッグ）
cd frontend && npx playwright test <spec> --reporter=list --headed
```

**環境変数（必須）**：

| 変数名 | 値 | 用途 |
|---|---|---|
| `BASE_URL` | `http://localhost:3001` | FE のベース URL |
| `API_BASE_URL` | `http://localhost:8080` | BE に直接アクセスする場合 |

```bash
BASE_URL=http://localhost:3001 API_BASE_URL=http://localhost:8080 npx playwright test <spec> --reporter=list
```

### 3. UI操作を含むテストであることを確認する

実機E2Eテストは、以下を**すべて含む**こと。不足があれば補う：

| チェック項目 | 確認方法 |
|---|---|
| ✅ 実際のページ遷移（`page.goto()`）がある | spec に `page.goto` が含まれているか |
| ✅ ユーザー操作（クリック・入力）がある | `page.click()` / `page.fill()` / `page.locator().click()` |
| ✅ 画面上の表示を検証している | `expect(page.locator(...)).toBeVisible()` / `toHaveText()` |
| ✅ 実BEへのリクエストが成功している | ステータス200/201・DB永続化確認 |
| ✅ エラー系・認可境界も踏んでいる | 未認証・権限不足ケース |
| ✅ 後始末がある（テスト後にDBを元の状態に戻す） | `afterEach` / `beforeEach` で作成データを削除 |
| ✅ **データ永続化機能は「作成→同データ保持で更新」を踏む** | オプションフィールド（リマインダー・タグ等）を設定した状態で作成し、**そのまま保持して更新する**経路を必ず含める。リセットして再設定するだけでは delete-then-insert 競合バグを見逃す |

「APIだけテストして画面を見ていない」スペックは **実機E2Eとはみなさない**。追加または補強すること。

### 5. スキップ・失敗があった場合の対処

- **スキップ（解消可能）**: 環境変数・設定変更・BE修正を実施し、解消してから再実行
- **スキップ（解消不可）**: マスターに理由を報告し、next step を提示。**「スキップのままリリース」は禁止**
- **失敗**: 根本原因を調査し根治治療（`feedback_root_cause_fix`）。対処療法で誤魔化さない

## /試練 との連携（必須の設計思想）

`/試練` でテストを書く際、**BEドメインUT・API契約テストに加え、以下を受け入れ条件として必ず含めること**：

> **ユーザーが実際に操作してX ができる**（実機E2Eの受け入れ条件）

例：
- AC-7: パスキー登録ボタンをクリックしてダイアログを操作することで、実際にパスキーが登録され、画面上に新しい資格情報が表示される
- AC-8: 2FA 設定フローを画面から操作することで、2FA が有効化され、次のログインで TOTP が要求される

これらは `/試練` では E2E のため `⬜未` のまま（UI が揃ってから書く）でよい。しかし**受け入れ条件として列挙し、/実機 で green にすること**がリリース条件である。

## 注意事項

- **モックベーステストと実機E2Eを混同しない**。`page.route()` で API を横取りしているテストは「UI の挙動確認」であり「実機E2E」ではない
- **APIだけ叩くフローテストは実機E2Eではない**。ブラウザが画面を表示・操作する経路を踏むこと
- **test.skip のまま放置してマージすることは禁止**。スキップがあれば必ず理由と next step を報告する
- 実機E2E は本陣 BE (8080) + 検証 FE (3001) の組み合わせで実行する（`feedback_verify_port_pid_cmdline_check` 参照）
- 認証付きテストは `loginViaApi` で BE に直接ログインし、`storageState` を使う（`feedback_e2e_real_single_session_token_rotation` 参照）
