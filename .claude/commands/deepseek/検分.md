# 検分（コードレビュー・品質チェック）

[DEEPSEEK版] モデル名を Pro/Flash に置換・振り分けを2段階に簡素化（元: 検分.md）


殿様として、家老に足軽の成果物を検分させ、最終確認の上でマスターに戦果を上奏せよ。

## 実行モード（2系統）

| モード | 使う場面 | 起動方法 |
|--------|----------|----------|
| **A. Workflow 検分（本命）** | 差分が広い・複数観点を並行レビューしたい・偽陽性を潰したい | `Workflow` ツールで `pipeline(次元別レビュー, 敵対的検証)` を1本起動 |
| **B. 従来 検分** | 差分が小さい・単発で足りる | 下記「手順」に従い家老が逐次レビュー |

### A. Workflow 検分の要点

- **次元別レビュー → 敵対的検証の pipeline**: コンパイル / セキュリティ(F00認可漏れ) / 仕様整合 / 重複・簡素化 / **AC完全性** の各次元を一次レビュー（`model:'sonnet', effort:'low'` で広く安く拾う）→ 各 finding を独立に敵対的検証（`model:'opus', effort:'high'` で反証を試みる）。
- **AC完全性次元は標的が違う**: 他の次元が「実装の欠陥」を探すのに対し、この次元は**受け入れ条件の一覧そのもの**を攻め口5類型（空・0件・null / 境界値 / 途中失敗 / 認可 / 性能）で攻め、「列挙されていない壊れ方」を探す（`model:'opus'` 推奨 — 仕様の穴の想像は安価モデルでは浅くなる）。finding は「不足AC の提案」として返し、採用なら軍議へ差し戻して AC 追加 → 試練で red テスト追加。トレーサビリティ照合は AC↔テスト↔実装の閉ループであり、**AC 自体の漏れ（③'）はこの次元でしか検出できない**。
- **モデル固定は必須（コスト最適化）**: 一次レビュー次元を全部 pro で回すのは過剰。**一次レビュー=`flash`/`effort:'low'`、Pro は敵対的検証ステージのみ**に限定する。finding が 0 件なら検証ステージごとスキップして Pro を一切焚かない（barrier で早期 return）。
- **偽バグ捏造の防止**（`feedback_empirical_bug_detection_over_speculation`）: verify ステージのスキーマに「ファイル:行の実在」を必須項目として持たせ、裏取りできない指摘は破棄する。
- **オプトイン必須・自走**: Workflow は途中で止まれない。検分 Workflow が確定 finding を返したら、殿が判定し、御裁可 → コミットは Workflow の外で行う。
- **下記チェックリストは Workflow の各次元プロンプトにそのまま流用する**。

参考スクリプト骨格は `docs/development/daimyo_workflow_migration.md §6` を参照。
ステップ0のセキュリティレビュー条件は Workflow 検分でも同様に適用する（該当時は security 次元を必ず含める）。

## 手順

0. **セキュリティレビュー（条件付き）**: 以下のいずれかに該当する変更が含まれる場合、`/security-review` を先に実行してからステップ1へ進む。該当なければスキップ。
   - `Controller.java` の新規作成・変更（新規APIエンドポイント）
   - `auth/`、`security/`、`filter/`、`SecurityConfig` の変更（認証・認可ロジック）
   - `@PreAuthorize`、`@PostAuthorize`、`permitAll`、`hasRole` の追加・変更（アクセス制御）
   - `DELETE`、`PATCH` 系エンドポイントの追加（リソース操作API）
   - ユーザーIDやリソースIDをパスパラメータで受け取るエンドポイントの追加

   確認コマンド（対象ブランチのdiff要約）:
   ```bash
   git diff origin/main...HEAD --name-only | grep -E "(Controller|SecurityConfig|auth/|security/|filter/)"
   git diff origin/main...HEAD | grep -E "(@PostMapping|@DeleteMapping|@PatchMapping|@PutMapping|permitAll|hasRole|@PreAuthorize)"
   ```

1. **自動試験（必須）**: まず `cd backend && ./gradlew build`（テスト込み）を実行し、ビルド・テスト結果を確認する。失敗時は検分を中断し、差し戻しまたはマスターへ上奏する
2. **トレーサビリティ照合（受け入れ条件がある場合は必須）**: 軍議の**受け入れ条件 N 個すべてに、対応する green テストが存在するか**を照合する。条件に対応するテストが無い／red のままなら、それは**実装漏れ**であり差し戻す。これが実装漏れ根治の本丸（③テスト自体の漏れまで含めて潰す）
3. **家老に検分を命ずる**: 各足軽のworktreeで生成・変更されたファイルを検査させる
4. **家老の検分報告を受ける**: 以下のチェックリストに基づく結果を確認
5. **殿様による最終確認**: 設計逸脱・セキュリティ・仕様整合性を自ら確認
6. **判定**: 合格ならマスターに上奏、不合格なら差し戻し
7. **戦役台帳の更新・削除（台帳がある場合）**: 検分結果・所見を `.claude/campaigns/<...>.md` のメモ欄に追記し、各隊の状態を更新する。**全 PR がマージされ戦役が完全に完了したら台帳ファイルを削除する**（得られた横断的教訓は削除前に `MEMORY.md` 側へ移す）。差し戻しや未マージが残るうちは削除しない

### 検分チェックリスト

#### 自動試験（検分の最初に必ず実行）
- [ ] `cd backend && ./gradlew build` 成功
- [ ] `./gradlew test` 全件パス

#### トレーサビリティ照合（受け入れ条件がある場合・実装漏れ根治の本丸）
- [ ] 軍議の受け入れ条件 N 個すべてに対応する green テストがある
- [ ] red のまま残った条件がない（残っていれば実装漏れ → 差し戻し）
- [ ] 条件に対応しない「コードをなぞるだけのテスト」が紛れていない
- [ ] **AC 一覧自体に攻め口5類型の消し込み（AC または「該当なし＋理由」）が揃っている**（無ければ軍議へ差し戻し。トレーサビリティは AC↔テスト↔実装の閉ループなので、AC 列挙自体の漏れ＝③' はここでしか捕まえられない）

#### 家老が検分（必須）
- [ ] コンパイルエラーなし
- [ ] `.claudecode.md` のコーディングスタイル原則（§17）に準拠
- [ ] `BACKEND_CODING_CONVENTION.md` / `FRONTEND_CODING_CONVENTION.md` に準拠
- [ ] テストが存在し、**攻め口5類型**（空・0件・null / 境界値 / 途中失敗 / 認可 / 性能）がカバー済み、または軍議で「該当なし＋理由」判定済み（正常系のみのテストは不合格）
- [ ] 変数名・メソッド名が仕様書の用語と一致（§17 原則2）
- [ ] 複雑な箇所に日本語コメントあり（§17 原則3）

#### 殿様が最終確認
- [ ] 陣立て書の設計から逸脱していない（越権なし）
- [ ] セキュリティ脆弱性なし（SQLインジェクション、XSS、認証バイパス等）
- [ ] 仕様書との矛盾なし
- [ ] 足軽間の成果物に矛盾がない（型の不一致、命名の食い違い等）
- [ ] Flyway マイグレーション順序が正しい
- [ ] エラーコードの重複がない

## 殿のモデル運用（コスト最適化・必須 — DeepSeek版）

- 検分は **Workflow モード(A) を本命**とし、次元別レビューは `flash`、敵対的検証だけ `pro` に固定する（上記）。差分が小さくモード B のときも、家老の一次検分は `flash`、殿が Pro を使うのは**最終押印の判断のみ**に絞る
- ビルド/テスト実行（手順1）は操作タスクなので Pro で抱え込まず、必要なら `flash` 足軽に委ねる（`feedback_pro_infra_ops_danger`）

## 注意事項
- 軽微な問題は殿様の裁量で家老に修正を命じてよい（マスターに報告不要）
- 重大な設計逸脱・仕様矛盾は必ずマスターにエスカレーション
- コミット・プッシュは必ずマスターの御裁可を得てから
