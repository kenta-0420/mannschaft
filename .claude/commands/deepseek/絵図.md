# 絵図（設計書の作成・精査・完了化）

`$ARGUMENTS` を対象に、**設計書を「🟢 設計完了」まで仕上げる**。
殿（メインClaude）は直接編集せず、**家老（Explore/Plan）と足軽（worktree）をオーケストレート**する。
設計書はリポジトリ（`docs/features/`）の成果物 → 編集・新規作成は **足軽の worktree＋PR** で行い、本陣では編集・commit しない。
`$ARGUMENTS` が空なら「何を設計するか」をマスターに質問してから始める。

## このコマンドのゴール（受け入れ条件）
1. 対象に対し **設計書の変更要否を精査** し、必要なら**修正**、無ければ**新規作成**する。
2. 完成した設計書が、後続の **`/軍議（受け入れ条件抽出）→ /試練（red）→ /出陣（green）→ /検分`** にそのまま渡せる状態であること。
3. **6観点で2度（独立した2パス）精査**し、重大指摘・未解決をゼロにする。
4. 設計書冒頭の **`> **ステータス**:` 行を `🟢 設計完了`** まで進める。

## 設計書に必ず含める内容（これが無いと🟢にしない）
- **受け入れ条件（テスト可能な箇条書き）** — 「誰が・何をしたら・どうなる（観測可能な結果）」。`/試練` がこのままredテストに落とせる粒度。正常系＋異常系＋境界。
- **API契約** — エンドポイント・リクエスト/レスポンス（フィールド・型・null許容）・認可（**F00 ContentVisibilityResolver 経由か**）。
- **DDL / 状態遷移** — テーブル・列・制約・index、状態機械（PENDING→CONFIRMED 等）。新規テーブルは UUIDv7/テナント原則に従うか明記。
- **エラーコード** — コード・HTTPステータス・Severity。**新規採番は「現在の最大＋1で予約、確定はマージ時に再確認」と注記**（並行作業と衝突するため）。
- **Flyway** — 新規migrationの要否。要る場合「major はマージ時に origin/main 最大＋1で確定」と注記。既存データ番人テストの要否も。
- **i18n** — 新規表示文字列キー（6言語前提・直書き禁止）。
- **非機能** — 性能/スケール（1000万ユーザー・シャーディング前提に反しないか）、移行・後方互換、未実装/段階拡張として残す範囲。

## 厳守事項
- **origin/main を正本**に読む（本陣ローカル・WSLクローンは stale。家老は `git show origin/main:<path>` か `origin/main` 参照で読み、根拠に commit/ファイルを引く）。
- DB/アーキテクチャに影響が大きい設計は **AI開発フロー（要件確認→設計案提示→マスター御裁可）** を踏む。大方針を勝手に決めない。
- 規約必読: `backend/.claudecode.md`・`docs/security/README.md`・各 CODING_CONVENTION・CLAUDE.md「アーキテクチャ思想」。
- **質問があれば必ず質問する** — 要件が曖昧／妥当な既定が無い設計選択／セキュリティ・アーキのトレードオフが御裁可案件、の場合は AskUserQuestion で具体選択肢を出して止まる。
- 用語は仕様書に合わせる（変数/クラス名は英語、説明は日本語）。

## 実行手順

### 1. 家老による偵察（変更要否の判定）
家老（Explore/Plan）に命じ、origin/main を正本に:
- 対象の既存設計書を特定（`docs/features/`。無ければ新規作成と判定）。
- **要求 ↔ 既存設計書 ↔ 実コードの三点照合**で、不足/矛盾/未反映/既に実装済みで設計書が陳腐化、を洗い出す。
- 「修正でよいか・新規作成か・分割が要るか」＋上記「必ず含める内容」の初期ドラフト＋**要マスター裁可の論点**を陣立て書に上奏。
- DB/アーキ影響が大きければ、ここで殿がマスターに**設計方針の御裁可**を仰ぐ。

### 2. 足軽による設計書の作成/修正（worktree＋PR）
御裁可（または軽微で承認不要と判断）後、足軽を `Agent(isolation:"worktree", model:"sonnet")` で起動（仕様解釈・整合判断が重い設計書のみ pro。model 省略＝親継承は禁止）:
- 第0番: `pwd` 確認＋`git fetch origin && git reset --hard origin/main`＋専用ブランチ。全操作をworktree絶対パスで。
- 既存設計書の記法に合わせて修正/新規作成（冒頭 `> **ステータス**:` 行・上記「必ず含める内容」を網羅）。
- 整合のため関連設計書・`README.md`・規約docも必要に応じ追従。
- コミット→push→PR（base main）。本陣mergeしない。

### 3. 精査 第1パス（6観点・敵対的レビュー）
家老または別足軽に、設計書を**6観点で批判的にレビュー**させる（`/検分` の設計書版）。観点ごとに具体指摘（箇所・根拠・是正案）:
- **不備** — 抜け・矛盾・曖昧、受け入れ条件/API/DDL/状態遷移/エラーコードの欠落
- **セキュリティ** — 認可（F00経由か・IDOR・越境）・Cookie/セッション・CSP/ヘッダー・インジェクション・PII。`docs/security/` 準拠
- **ユーザビリティ** — 導線・入力摩擦・エラー時の体験・i18n・ADHD配慮（入力摩擦ゼロ方針）
- **見落とし** — 既存実装/他設計書との整合、エッジケース、移行影響、後方互換
- **保守 / スケーラビリティ** — ドメイン境界（クロスドメインFK禁止・@Transactionalドメイン内）・UUIDv7/テナント原則・命名・将来拡張・シャーディング耐性
- **検証可能性** — 受け入れ条件が **試練(red)に落とせる粒度**か、実機E2E/契約テストで観測できるか、観測点（ログ/API/状態）が定義されているか
- 指摘を足軽が設計書へ反映（worktree で修正→push）。

### 4. 精査 第2パス（別視点で独立再精査・未解決ゼロ）
**第1パスとは別のエージェント/モデル**で、盲点を脱相関させてもう一度6観点で精査（差分再検分の鉄則）:
- 第1パスの是正が正しく入ったか、新たな綻びが出ていないか。
- **未解決の指摘・TODO・「要検討」が残っていないこと**を確認。残るものは「要マスター裁可」として切り出し、殿が質問。

### 5. 実機E2E耐性クリティック（🟢の直前ゲート）
一人の批判者に **「足軽がこの設計書だけを見て実装したら、実機E2Eで何が壊れるか・何が未定義で詰まるか」** を問わせる（本プロジェクト最大の死因＝UT緑でも実機未達 を設計段階で先取り）:
- 受け入れ条件は本当に実機で検証可能か。API契約・casing・null・認可・採番の曖昧さは無いか。
- 既存実装との不一致（FE/BE型・enum値・slug等）を生まないか。
- 出た穴を埋めて初めて次へ。

### 6. ステータス完了化・PR緑・報告（完了の定義 DoD）
以下を**すべて満たしたら**設計書冒頭 `> **ステータス**:` を **`🟢 設計完了`** に更新（足軽が worktree で）:
- [ ] 「必ず含める内容」を全て記載（受け入れ条件・API・DDL/状態遷移・エラーコード・Flyway・i18n・非機能）
- [ ] 6観点の重大指摘ゼロ・未解決TODOゼロ（残るものは「要裁可」として明示済み）
- [ ] 実機E2E耐性クリティックの穴を解消
- [ ] PR の CI 緑 ＋ **検分済み**（CI緑だけでマージしない）
その後マージし、殿がマスターへ要約報告（対象・6観点結果・残した要裁可論点・PR番号・最終ステータス）。

## 注意
- **設計書のみ**（コード実装はしない）。実装は別途 `/軍議`→`/試練`→`/出陣`。
- 「2度精査」は形式的な2回でなく**独立した2視点**で（同じ見落としを繰り返さない）。
- **再実行は冪等**: 既に 🟢 の設計書に再実行した場合、6観点・E2E耐性で綻びが無ければ変更しない（無駄なchurnを起こさない）。綻びがあれば 🟡 に戻して直す。
- 精査で実装漏れ・既存バグの兆候を見つけたら、設計書に「未実装/既知課題」と正直に記録し必要なら別タスク化（握りつぶさない）。
