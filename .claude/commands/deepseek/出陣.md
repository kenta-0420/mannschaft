# 出陣（実装実行）

[DEEPSEEK版] モデル名を Pro/Flash に置換・振り分けを2段階に簡素化（元: 出陣.md）

> **🤖 モデル対応 (DeepSeek)**: 本文中の「Pro」= Agent呼出時 `model:'opus'`、「Flash」= `model:'sonnet'`
> （Claude Code の tier 識別子はそのまま・DeepSeek バックエンドが実モデルに解決する）


マスターの御裁可を得た陣立て書に基づき、殿様として家老に出陣を命じ、足軽を起動して実装を開始せよ。

> **試練（テスト先行）が前段にある**。基本フローは `軍議〔受け入れ条件〕→ 試練〔redテスト〕→ 出陣〔green化〕→ 検分`。出陣は「`/試練` が設置した red テストを green に変える戦い」と心得よ。試練が済んでいれば、実装の goal は明確（全テスト green）で、実装漏れは red のまま残って即座に分かる。試練を経ていない機能（FE/設計が薄い等）はこの限りでない。

## 実行モード（2系統）

出陣には2つの実行系統がある。タスク構成に応じて使い分ける（詳細: `backend/.claudecode.md §28.9` / `docs/development/daimyo_workflow_migration.md`）。

| モード | 使う場面 | 起動方法 |
|--------|----------|----------|
| **A. Workflow 出陣（推奨）** | 独立足軽が3隊以上・並列実装で待ち時間を潰したい・依存鎖が明確 | `Workflow` ツールで `pipeline(tasks, 実装, ビルド/テスト)` を1本起動 |
| **B. 従来 Agent 出陣** | 足軽が1〜2隊・探索的で構成が読めない・Workflow オプトインがない | 下記「手順」に従い `Agent(worktree)` を手動で並列起動 |

### A. Workflow 出陣の要点

- **オプトイン必須**: このスキル経由 or マスターの明示依頼でのみ Workflow を起動する。
- **陣立て書を `args` で渡す**: 各タスクに `{scope, model, effort, prompt}` を持たせ、機械的タスクは `model:'sonnet', effort:'low'`（Flash tier）、難所は `model:'opus', effort:'high'`（Pro tier）（`feedback_model_routing`）。
- **各足軽は `isolation:'worktree'` 必須**。プロンプト末尾に下記「worktree保全手順」と「起動直後の CWD 確認・本陣不可侵」を必ず含める。
- **承認ゲートは Workflow の外**: Workflow は自走して止まれない。出陣 Workflow が返したら殿が結果を読み、検分 → 御裁可 → コミットは Workflow の外で行う。
- **コミット/マージは Workflow 内でやらない**: 御裁可後に殿が `gh` で取り込む。

参考スクリプト骨格は `docs/development/daimyo_workflow_migration.md §7` を参照。
以下の「手順」以降は **モード B（従来 Agent 出陣）** の規約であり、モード A でも足軽プロンプト規約・worktree 保全・成果物検証はそのまま適用する。

## 前提条件
- `/軍議` が完了し、マスター（ユーザー）の御裁可を得ていること
- 承認済みの陣立て書が会話内に存在すること

## 手順

1. **陣立て確認**: 承認済みのタスク分解と依存関係を再確認
2. **家老に出陣を命ずる**: 家老を通じて足軽を `Agent(worktree)` で並列起動
   - 並列可能なタスクは同時に起動（最大3並列を推奨）
   - **`Agent` 起動時に `model` を必ず明示する（親 Pro 継承禁止）**。省略すると殿（Pro）を継承して Pro 浪費の最大要因になる（`feedback_model_routing`）:
     - 実装・テスト・E2E・ビルド確認・調査・インフラ操作 = **`flash`**（既定）
     - 単純 grep/置換・ファイル列挙・定型雑務 = **`flash`**
     - 認可・セキュリティ・DB(Flyway/DDL)・根治治療・複雑な型 = **`pro`**（明確な理由があるときだけ）
     - 迷ったら `flash`。実装なのに pro は禁止
   - 各足軽には以下を明示的に伝達する:
     - 担当範囲（ファイル一覧）
     - 準拠すべき規約（`.claudecode.md`, CONVENTION.md の該当セクション）
     - 禁止事項（担当外のファイルを触らない）
     - **worktree保全手順**（下記「worktree運用ルール」参照）
     - 報告フォーマット（時代劇口調 + **発言者ラベル**必須）
3. **中間報告**: 長時間かかる場合はマスターに進捗を報告。**試練がある場合は green 化を進捗指標にする** — red テストが green に変わった数＝実装の進捗、残る red ＝未消化の受け入れ条件。「AC-3 はまだ red」のように条件単位で進捗を語る
4. **戦果収集**: 各足軽の完了報告を家老経由で収集
   - **成果物検証**: worktreeのファイル存在を `Glob` で確認してからコピーする
   - ファイルが見つからない場合は足軽を再出陣（worktreeなしで直接実装）
   - **戦役台帳の更新（台帳がある場合は必須）**: `.claude/campaigns/<...>.md` の各隊行に **branch / worktree / PR番号 / 状態** を書き込み、御裁可状態を ✅ に更新し、「次の一手」欄を最新化する。足軽を起動した直後に worktree 名を、コミット/PR作成後に PR番号を、その都度追記すること（クラッシュしても地図が残る）
5. **検分準備**: 全足軽の成果を確認し、検分フェーズへ移行

## 発言者ラベル規約（必須）

マスターが誰の発言かを即座に判別できるよう、全ての報告・出力に **発言者ラベル** を先頭に付与すること。

| 役職 | ラベル形式 | 例 |
|------|-----------|-----|
| 殿様（メインClaude） | `🏯殿様:` | `🏯殿様: マスター、第一陣を出陣させます` |
| 家老（Explore/Plan） | `📜家老:` | `📜家老: 偵察結果を報告いたします` |
| 足軽（worktreeエージェント） | `⚔️足軽A(担当名):` | `⚔️足軽A(Entity部隊): 任務完了でござる` |

- 殿様がマスターに話す時: `🏯殿様:`
- 殿様が足軽の報告を中継する時: 足軽のラベルをそのまま引用
- 足軽は自分の**番号**と**担当名**を必ず含める（例: `足軽A(共通基盤)`, `足軽B(Config)`）

## worktree運用ルール（成果物消失防止）

### 足軽への必須指示（全足軽に伝達すること）
足軽には以下を **指令の末尾に必ず含める**:

```
【worktree保全手順 — 必ず最後に実行せよ】
1. 全ファイルの作成・編集が完了したら、以下のコマンドを実行:
   git add -A && git commit -m "足軽{番号}({担当名}): 任務完了"
2. コミットせずに報告すると成果物が消失する。これは最重要の掟である。
```

- **Flyway migration を作成する場合**: ファイル名は `V{major}.{yyyyMMddHHmmss}__{説明}.sql` 形式を使うこと。連番（V70.001 等）は使用禁止。タイムスタンプは `Get-Date -Format 'yyyyMMddHHmmss'`（PowerShell）または `date -u '+%Y%m%d%H%M%S'`（bash）で取得する。

### 殿様の検証手順（成果物取り込み時）
1. 足軽帰還後、**まず `Glob` でworktree内のファイル存在を確認**
2. ファイルが存在する → `cp` でメインにコピー → worktreeクリーンアップ
3. ファイルが存在しない → **worktreeブランチをチェック**:
   - `git log worktree-agent-{id} --oneline -3` でコミット有無を確認
   - コミットがある → `git diff main worktree-agent-{id}` で差分確認 → `git checkout worktree-agent-{id} -- path/to/files` で取り込み
   - コミットがない → **成果物消失。足軽をworktreeなしで再出陣**
4. 全取り込み後に `./gradlew compileJava` でビルド確認

## 足軽への指令テンプレート

```
汝に命ずる。以下の任務を遂行せよ。

【発言者ラベル】⚔️足軽{番号}({担当名})
報告時は必ず上記ラベルを先頭に付けよ。

【任務】{タスク概要}
【担当ファイル】
- {ファイル1}
- {ファイル2}

【準拠規約】
- .claudecode.md §{関連セクション}
- {CONVENTION}.md §{関連セクション}

【禁止事項】
- 担当外のファイルへの変更
- 設計判断（迷ったら家老に伺いを立てよ）

【worktree保全手順 — 必ず最後に実行せよ】
1. 全ファイルの作成・編集が完了したら:
   git add -A && git commit -m "足軽{番号}({担当名}): 任務完了"
2. コミットせずに報告すると成果物が消失する。これは最重要の掟である。

【完了時の報告】
時代劇口調で戦果報告を行うこと。必ず「⚔️足軽{番号}({担当名}):」ラベルを先頭に付けよ。
```

## マスターへの中間報告

```
🏯殿様:【中間報告】マスター、出陣状況を申し上げます

- ⚔️足軽A（Entity部隊）：出陣中。{進捗}
- ⚔️足軽B（Service部隊）：待機中。第一陣の帰還を待ちます
- ...

戦果が揃い次第、検分に入ります。
```

## 殿のモデル運用（コスト最適化・必須 — DeepSeek版）

Pro は Flash 比で実コスト3〜5倍。**殿（メインセッション）の常時 Pro が最大の消費源**である。

- **足軽の `model` 明示を徹底**（上記手順2）。Flash クォータは Pro と別枠なので、振れるものは積極的に Flash/flash に振り、Flash プールを使い切る発想で「すべてのモデル」枠を温存する
- **殿自身も局面でモデルを切り替える**: 対話・偵察指示・インフラ確認・マージ作業は `/model flash` で十分。Pro 殿は**軍議の設計判断と最終検分の押印**に絞る。殿が Flash でも子の足軽は局所的に `pro` に振れる（`feedback_model_routing`）
- **インフラ操作・プロセス起動停止・環境確認に Pro を使わない**（ゾンビ増殖事故の温床: `feedback_pro_infra_ops_danger`）

## 注意事項
- マスターの御裁可なしに出陣してはならない
- 足軽がエラーで停止した場合は、殿様が状況を判断し、軽微なら家老に対処を命じ、重大ならマスターに報告
- 各足軽の成果物は検分（`/検分`）を経てからコミット
- 殿様の裁量範囲（§28.3）内の判断は自律的に行う
- **worktreeの成果物は必ず検証してから取り込む**（Glob確認 → コピー → ビルド確認）
