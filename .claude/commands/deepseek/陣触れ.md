# 陣触れ（フロントエンド起動）

> このスキルは運用作業のため `model: flash` 指定（殿のPro/Pro温存・feedback_pro_infra_ops_danger）。

Nuxt 開発サーバーを起動する。
**使い方**: `/伝令` の後に `/陣触れ` を実行。バックエンドとフロントエンドが揃い、開発環境が整う。

## 前提条件

- `/伝令` 済みであること（Spring Boot 稼働中 + swagger.json 取得済み）

## ⚠️ 最重要: ポートは必ず明示する（`PORT` 環境変数の罠）

**`npm run dev` を素で叩いてはならない。必ず `--port <ポート>` を明示すること。**

Nuxt は環境変数 `PORT` を読んでポートを決める。このマシンでは **MulmoTerminal（`http://localhost:34567/terminals`）が
自分の起動ポート `PORT=34567` を配下のシェルに継承させる**ため、素の `npm run dev` は 3000 ではなく **34567 を掴みに行き、
MulmoTerminal の縄張りを侵食する**（2026-07-28 に実際に発生。「Another Nuxt dev server is already running: URL http://0.0.0.0:34567」
という一見無関係なロックエラーで表面化した）。

対策は 2 点セットで必ず両方行う:

1. `PORT=<ポート>` を明示的に上書きして起動する（継承値を潰す）
2. `-- --port <ポート>` を CLI 引数でも渡す（二重の保険）

## ⚠️ 疎通確認・URL 案内は必ず `localhost` を使う（`127.0.0.1` は認証 Cookie を壊す）

**待機ループ・疎通確認・ユーザーへの URL 案内はすべて `http://localhost:<ポート>` を使うこと。`127.0.0.1` を使ってはならない。**

### 背景（2026-07-28 の一時対症療法と、その副作用が2026-08-04に発覚）

かつては `nuxt.config.ts` の `devServer.host: '0.0.0.0'` により Nuxt の HTTP サーバーが **IPv4 のみ**を bind し、
空いた `[::]:<ポート>`（IPv6 側）を **Vite の HMR WebSocket サーバーが掴む**という罠があった。
Windows の名前解決は `localhost` → `::1` を優先するため、`localhost:3000` を開くとアプリではなく
HMR の WebSocket サーバーに当たり、恒久的に `426 Upgrade Required` が返っていた。
このときは「疎通確認・URL 案内は `127.0.0.1` を使う」ことで回避していた。

**この回避策は 2026-08-04 に廃止された。** 根治として `nuxt.config.ts` の `vite.server.hmr.port` に専用ポート
（`24678`）を与え、HMR が `[::]:3000` を掴まないようにした。これにより `localhost:3000` は正常に 200 を返す。

### なぜ `127.0.0.1` で案内してはならないか（最重要）

BE は認証 Cookie（`access_token` / `refresh_token`）を **`SameSite=Strict`** で発行する
（`backend/src/main/java/com/mannschaft/app/auth/controller/AuthLoginController.java`）。
SameSite の同一サイト判定は**ホスト名の文字列**で行われるため、`127.0.0.1` と `localhost` は
ブラウザ上「別サイト」扱いになる。そのため `http://127.0.0.1:3000` でアプリを開くと、
`http://localhost:8080` からの `Set-Cookie` が**保存されない**。

ログイン直後はレスポンス body のトークンが in-memory に載るため一見正常に動くが、
15分弱で先回りリフレッシュ（`useApi.ts` の `armProactiveRefresh`）が発火した際、
refresh は Cookie だけが頼りのため 401（AUTH_007）→ **強制ログアウト**に落ちる。
「ログイン後15分でログアウトされる」不具合の実態はこれだった（実測で確定・再発防止テスト:
`frontend/tests/e2e/real/auth-cookie-origin.spec.ts`）。

- **アプリの URL は `http://localhost:<ポート>`**（`127.0.0.1` は SameSite=Strict Cookie が保存されず15分でログアウトする）
- 待機ループ・疎通確認も **案内する URL と揃えて** `localhost` を使うこと（どちらで叩いても 200 になるが、揃えないと事故の温床になる）

## ⚠️ SSR ワーカーの OOM 対策（`NODE_OPTIONS` 必須）

ヒープ既定値のままだと Nitro の SSR ワーカーが落ち、**全ページが HTTP 500** になる:

```
Worker terminated due to reaching memory limit: JS heap out of memory
```

起動時に必ずヒープを広げること（2026-07-28 に実機で発生・解消を確認）:

```
NODE_OPTIONS=--max-old-space-size=8192
```

## ⚠️ dev サーバーはセッションから切り離して起動する

Bash ツールの `run_in_background: true` で起動した子プロセスは、**Claude Code のセッションが再起動すると道連れで死ぬ**。
長時間使う dev サーバーは PowerShell の `Start-Process` で**セッション非依存**に起動すること（手順 4 参照）。

## 手順

### 1. 本陣を最新 main に同期（pull）

FE dev サーバーは本陣ディレクトリ（`C:\Claude\mannschaft\frontend`）をそのまま配信するため、
起動前に origin/main の最新を取り込まないと、マージ済みの修正が反映されず**古いコードのまま起動**してしまう。
PowerShell で実行する（Bash の本陣 git ブロックを回避するため。`--ff-only` なので分岐があれば安全に中断する）。

```powershell
git -C "C:\Claude\mannschaft" pull --ff-only
```

> ローカルに未コミットの変更があると pull は中断する。意図しない差分（改行コードのみ等）であれば
> `git -C "C:\Claude\mannschaft" checkout -- <該当ファイル>` で破棄してから再実行する。

### 2. 使用ポートの決定（3000 起点・埋まっていればインクリメント）

**方針**: 3000 を第一候補とする。

- 3000 を掴んでいるのが**本陣 frontend の Nuxt dev サーバー自身**なら、再起動のため停止して 3000 を再利用する
- 3000 を掴んでいるのが**それ以外のプロセス**（MulmoTerminal・別プロジェクト・E2E 用サーバー等）なら、
  **絶対に停止せず**、3001 → 3002 → … と空きが見つかるまでインクリメントする

`lsof` は Git Bash から Windows プロセスを検出できないため PowerShell を使う。
PID 0（TimeWait の残骸）は実プロセスではないので除外する:

```powershell
$port    = 3000
$maxPort = 3010
$chosen  = $null

while ($port -le $maxPort) {
    $conn = Get-NetTCPConnection -LocalPort $port -State Listen -ErrorAction SilentlyContinue |
            Where-Object { $_.OwningProcess -gt 0 } | Select-Object -First 1

    if (-not $conn) { $chosen = $port; break }

    $owner = $conn.OwningProcess
    $proc  = Get-CimInstance Win32_Process -Filter "ProcessId=$owner" -ErrorAction SilentlyContinue
    $cmd   = if ($proc) { $proc.CommandLine } else { "" }

    # 本陣 frontend の Nuxt dev サーバーだけは「再起動」とみなして停止してよい
    if ($cmd -like '*nuxi*' -and $cmd -like '*mannschaft*frontend*') {
        Write-Host "ポート $port の本陣 Nuxt (PID $owner) を再起動のため停止します"
        Stop-Process -Id $owner -Force -ErrorAction SilentlyContinue
        Start-Sleep -Seconds 3
        $still = Get-NetTCPConnection -LocalPort $port -State Listen -ErrorAction SilentlyContinue |
                 Where-Object { $_.OwningProcess -gt 0 }
        if (-not $still) { $chosen = $port; break }
    } else {
        Write-Host "ポート $port は別用途のプロセスが使用中 (PID $owner) — 停止せずインクリメントします"
    }
    $port++
}

if (-not $chosen) { Write-Host "ERROR: 3000〜$maxPort に空きポートがありません"; exit 1 }
Write-Host "採用ポート: $chosen"
```

> **他人のプロセスを殺さないこと。** 3000 が Nuxt 以外に握られていたら停止ではなくインクリメントで回避する。
> 特に MulmoTerminal（34567）や検証用 worktree の FE（3001）を巻き込むと殿の作業環境が壊れる。
> インクリメントは「空いているポートを探す」動作なので、3001 が検証用で埋まっていれば自動的に 3002 へ進む。

### 3. 依存パッケージ確認

node_modules が存在しない場合のみインストールする:

```bash
if [ ! -d "/c/Claude/mannschaft/frontend/node_modules" ]; then
  echo "node_modules が見つかりません。npm install を実行します..."
  cd /c/Claude/mannschaft/frontend && npm install
fi
```

### 4. Nuxt 開発サーバー起動

**手順 2 で決めたポートを `PORT=` と `--port` の両方に入れる**（`PORT` 継承の罠対策）。
**`Start-Process` で起動する**（Bash の `run_in_background` はセッション再起動で道連れになるため）:

```powershell
$log = "<scratchpad>\nuxt-dev-out.log"
$err = "<scratchpad>\nuxt-dev-err.log"
$env:NODE_OPTIONS = "--max-old-space-size=8192"   # SSR ワーカー OOM 対策（必須）
$env:PORT         = "<採用ポート>"                 # PORT 継承の罠対策
$p = Start-Process -FilePath "npm.cmd" `
     -ArgumentList "run","dev","--","--port","<採用ポート>" `
     -WorkingDirectory "C:\Claude\mannschaft\frontend" `
     -RedirectStandardOutput $log -RedirectStandardError $err `
     -WindowStyle Hidden -PassThru
Write-Host "起動: PID $($p.Id)（セッションから独立）"
```

起動完了を待機する。**初回ビルドは 5 分以上かかることがある**ので短く打ち切らないこと。
待機ループは `run_in_background: true` で投げ、完了通知を待つ。
**`localhost` ではなく `127.0.0.1` を叩くこと**（IPv6 の罠。`localhost` だと恒久 426 で偽 TIMEOUT になる）:

```bash
for i in $(seq 1 180); do
  code=$(curl -s -o /dev/null -w "%{http_code}" http://localhost:<採用ポート>/ 2>/dev/null)
  if [ "$code" = "200" ]; then echo "READY: HTTP 200 at $((i*2))s"; exit 0; fi
  if [ "$code" = "500" ]; then echo "ERROR 500"; curl -s http://localhost:<採用ポート>/ | head -c 400; exit 1; fi
  sleep 2
done
echo "TIMEOUT: 最終ステータス $code"; exit 1
```

**ステータスコードの読み方（localhost で叩いた場合。HMR は 24678 に分離済みなので `localhost:3000` で正常に判定できる）:**

| コード | 意味 | 対応 |
|---|---|---|
| `200` | 起動完了 | 完了報告へ |
| `426` | nuxi の親は起きているが**子の Nitro がまだビルド中** | 待つ（異常ではない） |
| `500` | **SSR ワーカーの OOM** の可能性が高い | ボディを読む。`JS heap out of memory` なら `NODE_OPTIONS=--max-old-space-size=8192` を付けて再起動 |
| `000` | まだ誰も listen していない / プロセスが死んだ | プロセス生死と `$err` ログを確認 |

> ⚠️ **Bash ツールのバックグラウンド出力は 0 バイトになることがある**（本件で実際に発生）。
> Nuxt の stdout は `Start-Process -RedirectStandardOutput` で採ったファイルを読むこと。

ビルド進行中かどうかは実プロセスで裏取りできる（CPU 時間とメモリが伸びていれば生きている）:

```powershell
Get-Process -Id <nuxi の PID> | Select-Object Id,CPU,WorkingSet64,StartTime
```

### 5. 結果報告

| 項目 | 状態 |
|------|------|
| 本陣 pull | ✅ / ❌ |
| 採用ポート | 3000 / 3001 / … |
| Nuxt 起動 | ✅ / ❌ |
| URL | http://localhost:&lt;採用ポート&gt; |

✅ なら「**陣触れ完了。フロントエンド陣営、出陣準備整いました。http://localhost:&lt;採用ポート&gt;**」と報告する。
**URL は必ず `localhost` で案内すること**（`127.0.0.1` は SameSite=Strict の認証 Cookie が保存されず、
ログイン後15分で強制ログアウトされる。「疎通確認・URL案内は必ずlocalhostを使う」節を参照）。
**3000 以外を採用した場合は、その理由（誰が 3000 を使っていたか）を必ず併記する。**
❌ の場合はバックグラウンドタスクの出力ファイル末尾を確認し、原因を提示する。

## 検証・E2E 用 worktree で起動する場合（ポート 3001）

本陣の dev サーバー（3000）と並行で、検証・E2E 用に**本陣と別 worktree** で起動するときは、衝突を避けるため **FE を 3001 固定**で起動する（BE は `/伝令` を 8081 で起動。CLAUDE.md「常駐サーバーのポート規約」参照）。ここでも `PORT` の明示は必須:

```bash
cd <worktreeのfrontend> && PORT=3001 npm run dev -- --port 3001
```

このとき API 接続先（`NUXT_PUBLIC_API_BASE` 等）が検証用 BE（8081）を指すよう環境変数も合わせること。

## 備考

- Nuxt の停止は `/撤収` に追加するか、PowerShell で対象を**コマンドラインで確認してから**停止する（ポート番号だけで `Stop-Process` すると無関係なプロセスを殺す）:

  ```powershell
  $c = Get-NetTCPConnection -LocalPort 3000 -State Listen | Where-Object { $_.OwningProcess -gt 0 } | Select-Object -First 1
  $p = Get-CimInstance Win32_Process -Filter "ProcessId=$($c.OwningProcess)"
  if ($p.CommandLine -like '*nuxi*') { Stop-Process -Id $c.OwningProcess -Force }
  ```

- `swagger.json` を更新した場合は Nuxt の型生成が自動で走る（Nuxt の設定による）
