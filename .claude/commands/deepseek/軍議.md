# 軍議（設計・タスク分解）

[DEEPSEEK版] モデル名を Pro/Flash に置換・振り分けを2段階に簡素化（元: 軍議.md）


マスターの指示を受け、殿様として家老に偵察・設計を命じ、陣立て書をまとめてマスターに上奏せよ。

## 前提
- マスター（ユーザー）から対象フェーズの指示を受けていること
- `.claudecode.md` §28（チーム運用規約）に従うこと

## 手順

1. **家老に偵察を命ずる**: 対象フェーズの仕様書（`docs/features/` 配下 + `README.md` 該当セクション）を精査させ、実装に必要な全要素を洗い出させる
2. **受け入れ条件（acceptance criteria）の列挙【必須成果物】**: 仕様書から、機能が満たすべき条件を**検証可能な粒度で N 個列挙**する。これが試練（テスト先行）と検分のトレーサビリティの土台になる（詳細は下記「受け入れ条件」節）
3. **陣立て書の作成**: 家老の報告を元に、以下の粒度でタスクを分解する
   - **Entity/Repository 部隊**: テーブル定義（Flyway）、エンティティ、リポジトリ
   - **Service/Config 部隊**: ビジネスロジック、設定クラス、イベント連携
   - **Controller/DTO 部隊**: API エンドポイント、リクエスト/レスポンス DTO、バリデーション
   - **試練（テスト先行）部隊**: 受け入れ条件から red テストを書く（`/試練`）。BEドメインUT・API契約テストが対象
4. **依存関係の整理**: どの部隊が先行すべきか、並列可能な範囲はどこかを明示。基本形は **Entity/Repo（骨格）→ 試練（red）→ 出陣（green）→ 検分 → E2E**
5. **殿様による精査**: 陣立て書と受け入れ条件の妥当性を自ら確認
6. **Codex による軍議検分【既定・必須】**: 陣立て書と受け入れ条件を Codex に独立検分させ、所見を反映してから上奏する（下記「Codex による軍議検分」節）。Codex 側が使えない場合（未ログイン・リミット停止・起動失敗）のみスキップし、上奏に「未実施＋理由」を明記する
7. **マスターへ上奏**: 陣立て書＋受け入れ条件（＋Codex 所見の反映結果）をマスターに提示し、御裁可を待つ

## 受け入れ条件（acceptance criteria）— 実装漏れ根治の本丸

実装漏れの真因は3種ある。①タスクは定義したが実装をサボった ②軍議のタスク分解から要件が漏れた ③テスト自体が要件を取りこぼした。テスト先行（試練）は①②に効くが、**③は受け入れ条件のトレーサビリティでしか潰せない**。だから軍議で受け入れ条件を明示列挙し、試練でテスト1本を対応づけ、検分で「全条件に green テストがあるか」を照合する。

- **粒度**: 「ログインできる」ではなく「未認証で保護APIを叩くと 401 が返る」のように**検証可能**な単位で書く
- **網羅 — 攻め口5類型の消し込み【必須】**: 正常系に加え、以下の5類型それぞれについて **AC を挙げるか「該当なし＋理由」を明示するまで列挙完了としない**。「該当なし」の明示により「考えた上で不要と判断した」と「考え漏れた」を区別する。AC 一覧自体の漏れ（③'）はトレーサビリティ照合では構造的に検出できず、実機 E2E まですり抜けた前科が多数ある（マッチング全域 IDOR `project_matching_authz_userid_as_teamid_idor`・プロモ撮影で発覚した BE バグ6件・ファイル共有の重大2バグ 等。いずれも検分通過後に発覚）

  | 類型 | 問いかけの例 |
  |---|---|
  | 空・0件・null | 一覧が0件・値が null・文字列が空のとき何が返るか |
  | 境界値 | 「N以上/以下/まで」の条件の**ちょうどN・N±1**でどうなるか |
  | 途中失敗（異常系） | 外部呼び出し失敗・途中例外時にデータが中途半端に残らないか |
  | 認可 | **他人の ID・別テナントの ID** を渡したら 403/404 か（IDOR） |
  | 性能 | ループ内クエリ（N+1）はないか・本番件数でも成立するか |
- **対応づけ**: 各条件には後で**テスト名と PR 番号**が紐づく（試練・出陣で台帳に記録）
- **戦役台帳と統合**: 列挙した受け入れ条件はそのまま**戦役台帳のチェックリスト**になる。実装漏れが「green テストの無い条件＝未消化の行」として構造的に可視化される

出力例:
```
■ 受け入れ条件（試練の対象）
AC-1: 未認証で GET /api/v1/foo を叩くと 401
AC-2: 他組織の foo を取得しようとすると 403（テナント分離）
AC-3: name 未指定で POST すると 400 とフィールドエラー
AC-4: 正常作成で 201 と Location ヘッダ
AC-5: foo が 0 件のとき GET は空配列と 200（500 にしない）
AC-6: 上限 100 件ちょうどの登録は成功し、101 件目は 409
...

■ 攻め口5類型の消し込み
空・0件・null = AC-5 / 境界値 = AC-6 / 途中失敗 = 該当なし（外部呼び出し・複数テーブル更新なし）
認可 = AC-1, AC-2 / 性能 = 該当なし（単票取得のみ・一覧はページング済み）
```

## Codex による軍議検分（既定）

**上奏の前に必ず Codex へ陣立て書と受け入れ条件を掛ける**（2026-09-03 マスター指示。自己精査だけでは AC の漏れが実際に多い）。狙いは実装後の検分では構造的に捕まえられない**③' — AC 一覧自体の漏れ**を、着手前に潰すことにある。

- **既定は実施**。`/軍議 codex-skip` と明示されたときのみ省く。
- **Codex 側が使えないときは行わなくてよい**（未ログイン・利用リミット停止・起動失敗・空応答）。その場合 **自己検分へ黙って読み替えず**、上奏の「Codex 軍議検分」欄に **未実施＋理由**を書く。実施の有無を偽らない。
- Codex には**読ませるだけ**とし、コード・ドキュメントを書かせない（`--sandbox read-only`）。

### 起動手順

1. 陣立て書と受け入れ条件を一時ファイルへ書き出す（会話中の案をそのまま渡す）。
2. `codex.cmd login status` で `Logged in` を確認する。未認証ならここで打ち切り、未実施として扱う。
3. Windows では PowerShell 実行ポリシー回避のため `codex` ではなく **`codex.cmd`** を使う。

```bash
GUNGI_PLAN="$(mktemp "${TMPDIR:-/tmp}/mannschaft-gungi-plan.XXXXXX.md")"   # 陣立て書＋AC を書き出す
GUNGI_REPORT="$(mktemp "${TMPDIR:-/tmp}/mannschaft-gungi-review.XXXXXX.md")"

codex.cmd exec \
  --sandbox read-only \
  --cd "$(pwd -W 2>/dev/null || pwd)" \
  --ephemeral \
  --output-last-message "$GUNGI_REPORT" \
  "$(cat <<EOF
次の軍議成果物（陣立て書＋受け入れ条件）を検分せよ。ファイルは変更しない。
対象: $GUNGI_PLAN

観点:
1. 受け入れ条件の漏れ — 攻め口5類型（空・0件・null / 境界値 / 途中失敗 / 認可(IDOR・テナント越境) / 性能(N+1)）で AC 一覧そのものを攻め、列挙されていない壊れ方を挙げよ
2. 「該当なし」判定の妥当性 — 理由が実際のコード・仕様に照らして成立するか
3. AC の粒度 — 検証可能（テスト1本に落ちる）か。曖昧な AC を指摘せよ
4. タスク分解の欠落・依存順序の誤り — 実装に必要でどの部隊にも割り当たっていない要素はないか
5. 既存実装・仕様書との矛盾（リポジトリを読んで裏取りすること）

各指摘は「不足AC の提案」または「修正提案」の形で、根拠となるファイル:行を添えて返せ。裏取りできない推測は挙げるな。
EOF
)"
GUNGI_EXIT=$?

if [ "$GUNGI_EXIT" -ne 0 ] || [ ! -s "$GUNGI_REPORT" ]; then
  echo "Codex 軍議検分は未実施（exit=$GUNGI_EXIT）。理由を上奏に明記し、自己検分で代替したと偽らない。"
else
  cat "$GUNGI_REPORT"
fi
```

4. 所見を殿が判定し、**採用した指摘は AC / 陣立て書へ反映してから**上奏する。却下した指摘は理由を添えて上奏に残す（Codex の指摘を黙って捨てない）。
5. 読み終えたら一時ファイル（`$GUNGI_PLAN` / `$GUNGI_REPORT`）を削除する。反映済みの内容は上奏・戦役台帳側に残す。
6. 最終判定とマスターへの上奏は常に殿の責務とする。Codex にコミット・push を行わせない。

## 戦役台帳の作成（クラッシュ耐性・複数隊/長時間の戦役のみ）

PC が突如落ちると会話コンテキスト（TodoList 含む）は消える。足軽の成果はコミット/push に残るが、「どの作業がどのブランチ/worktree/PR にどこまで進んだか」の**地図**が失われる。これを防ぐため、陣立て書が御裁可された直後（出陣前）に**戦役台帳**をファイルに落とす。

- **作成タイミング**: マスターの御裁可（「よきにはからえ」等）を得た直後、出陣に着手する前
- **置き場所**: `.claude/campaigns/<YYYY-MM-DD>-<機能スラッグ>.md`（`.gitignore` 済み・コミットされない）。雛形は `.claude/campaigns/_TEMPLATE.md` を複製して使う
- **中身**: Phase/隊ごとのチェックボックスに加え、**branch / worktree / PR番号 / 状態**を必ず記録（これが復旧の鍵）。「次の一手」欄を常に最新化
- **適用範囲**: 複数隊・複数 phase・長時間の戦役（軍議が必要な規模）のみ。1〜2ファイルの即時修正や対話だけのタスクでは**作らない**（オーバーヘッドが勝つ）
- **更新は `/出陣`・`/検分`**、**削除は戦役完了時**。クラッシュ＝正常終了しない＝ファイルが残る、が狙い
- **MEMORY.md と混同しない**: 台帳は1戦役内・一時的な作業地図。横断・恒久の知見は memory 側に残す

## Context7（兵糧庫）の運用
- Context7 MCP は**最新のライブラリドキュメント**を取得できる兵糧庫である
- **無料枠の制限**: 月1,000リクエスト / 時間60リクエスト。兵糧は有限なり
- **使用タイミング**: 軍議フェーズでの仕様確認・API仕様の裏取りに集中して使う
- **足軽には使わせない**: 出陣フェーズで足軽が個別に叩くと兵糧がすぐ尽きる。家老が軍議で必要な情報を事前に調達し、足軽への指令に含めて伝達すること
- **使い方**: プロンプトに `use context7` を付与する（例: 「Spring Security 6 の SecurityFilterChain use context7」）
