# 検分（コードレビュー・品質チェック）

殿様として、家老に足軽の成果物を検分させ、最終確認の上でマスターに戦果を上奏せよ。

## 検分者の選択

`$ARGUMENTS` の先頭で検分者を選べる。検分者以外の引数（PR番号、ブランチ、commit等）は対象指定として扱う。

| 指定 | 検分者 | 動作 |
|------|--------|------|
| 無指定 / `claude` | Claude Code | 従来どおり、下記の Workflow 検分または家老検分を実行 |
| `codex` | Codex | Codex CLIのreviewモードを自動承認で起動し、下記の全品質ゲートを独立検分 |
| `both` | Claude Code + Codex | 相互に所見を見せず独立検分した後、殿が指摘を照合して最終判定 |

例: `/検分 codex`、`/検分 claude PR-1234`、`/検分 both feature/example`

- 検分者の指定が無ければ後方互換のため `claude` とする。未知の指定を勝手に検分者名として解釈しない。
- `codex` / `both` でも、手順0（条件付きセキュリティレビュー）と手順1（自動試験）はClaude殿が先に実行する。Codexへビルドの成否を偽らず渡す。
- 最終判定、差し戻し、マスターへの上奏は常にClaude殿の責務とする。Codexへコミット・push・mergeを行わせない。

### Codex検分の起動手順

1. 初回または認証に不安がある場合は `codex.cmd login status` を実行し、`Logged in` を確認する。未認証ならCodexへフォールバックせず、マスターへログインが必要と報告する。
2. **対象worktreeへ移動**し、`pwd` と `git status --short` で対象を確認する。本陣から別worktreeを推測して起動しない。
3. 対象に応じて `CODEX_SCOPE` を1つだけ選ぶ。
   - 未コミット成果物: `CODEX_SCOPE=(--uncommitted)`
   - ブランチ/PR全体: `CODEX_SCOPE=(--base origin/main)`（比較元が別なら明示変更）
   - 単一commit: `CODEX_SCOPE=(--commit <SHA>)`
   - commit済み差分と未コミット差分が混在する場合は、一方を黙って捨てず2回に分けて検分する。
4. WindowsではPowerShell実行ポリシー回避のため `codex` ではなく **`codex.cmd`** を使う。以下をBashで実行する。

```bash
CODEX_REVIEW_REPORT="$(mktemp "${TMPDIR:-/tmp}/mannschaft-codex-review.XXXXXX.md")"
CODEX_SCOPE=(--base origin/main) # 上記の対象判定に合わせて置換
CODEX_STATUS_BEFORE="$(git status --porcelain=v1)"

codex.cmd exec \
  --approve-for-me \
  --cd "$(pwd -W 2>/dev/null || pwd)" \
  --ephemeral \
  --output-last-message "$CODEX_REVIEW_REPORT" \
  review "${CODEX_SCOPE[@]}" \
  "Mannschaftの独立検分を担当せよ。AGENTS.mdと.claude/commands/検分.mdを全文読み、同文書の全品質ゲートで対象差分をレビューすること。ファイルは変更しない。他のCodexを起動しない。指摘は重大度順に、実在するファイル:行、発生条件、影響、根拠を示すこと。受け入れ条件がある場合はAC・greenテスト・実装の対応と、AC一覧自体の攻め口5類型も照合すること。問題が無ければ残存リスクと未実行検証を明記すること。"
CODEX_EXIT=$?
CODEX_STATUS_AFTER="$(git status --porcelain=v1)"

if [ "$CODEX_STATUS_BEFORE" != "$CODEX_STATUS_AFTER" ]; then
  echo "Codex検分中にworktree状態が変化したため検分失敗。差分を保全し、勝手に復元せずマスターへ報告する。"
elif [ "$CODEX_EXIT" -ne 0 ] || [ ! -s "$CODEX_REVIEW_REPORT" ]; then
  echo "Codex検分失敗（exit=$CODEX_EXIT）。Claude検分へ黙って切り替えず、検分未完了として報告する。"
else
  cat "$CODEX_REVIEW_REPORT"
fi
```

- `--approve-for-me` により、Codex検分中の承認要求は自動レビューされる。現行Codex CLIでは `--approve-for-me` と `--sandbox read-only` は併用不可のため、ネイティブの `review` モード・変更禁止prompt・実行前後の `git status` 一致確認で非変更性を担保する。
- `--dangerously-bypass-approvals-and-sandbox` は使用禁止。自動承認のためにサンドボックスまで無効化しない。
- `both` ではClaude側の一次所見をCodexのpromptへ含めず、Codex報告もClaude検分が終わるまで読まない。両検分後、各findingの実在箇所と再現条件を殿が再確認し、重複・偽陽性・見解差を整理する。
- 報告を読み終えたら一時ファイルを削除する。削除前に必要な所見を戦役台帳または上奏へ反映する。

## 実行モード（2系統）

| モード | 使う場面 | 起動方法 |
|--------|----------|----------|
| **A. Workflow 検分（本命）** | 差分が広い・複数観点を並行レビューしたい・偽陽性を潰したい | `Workflow` ツールで `pipeline(次元別レビュー, 敵対的検証)` を1本起動 |
| **B. 従来 検分** | 差分が小さい・単発で足りる | 下記「手順」に従い家老が逐次レビュー |

### A. Workflow 検分の要点

- **次元別レビュー → 敵対的検証の pipeline**: コンパイル / セキュリティ(F00認可漏れ) / 仕様整合 / **贅肉（ponytail）** / **AC完全性** の各次元を一次レビュー（`model:'sonnet', effort:'low'` で広く安く拾う）→ 各 finding を独立に敵対的検証（`model:'opus', effort:'high'` で反証を試みる）。
- **贅肉（ponytail）次元**（出典: [Ponytail](https://github.com/DietrichGebert/ponytail)（MIT）の過剰実装削減基準を移植。旧「重複・簡素化」次元の上位互換）: コードを足す前に以下の**6段ラダー**を上から順に検討し、上の段で止まれるならそこで止まるのが正しい。差分の実装がどの段で止まれたはずかを問い、findingには必ず**5タグ**のいずれかを付す。
  1. そもそも必要か（投機的な要求なら作らない）
  2. 標準ライブラリで足りるか
  3. ネイティブ機能で足りるか（ブラウザ標準・CSS・DB制約）
  4. 既存依存で足りるか（新規依存追加の前に既存ツールを確認）
  5. 1行で済むか
  6. それでも無理なら、動く最小実装を書く

  5タグ: `delete`（不要な実装）/ `stdlib`（標準ライブラリで可能）/ `native`（ネイティブ機能で可能）/ `yagni`（不要な先制実装）/ `shrink`（縮小可能）

  **BE/FE でタグの当たりどころが異なる**（誤検知を減らすため、次元プロンプトに明記して当たりを絞る）:
  - **BE（Spring Boot）**: フレームワークがバリデーション・トランザクション・キャッシュ・リトライ・スケジューリングを備えるため、ラダー2段目（標準ライブラリ）・3段目（ネイティブ機能）の当たりは薄い。当たるのは「`@Cacheable` があるのに独自キャッシュ」「Bean Validation があるのに手書き検証」「Spring Retry があるのに独自リトライ」といった類。**BE の主戦場は `yagni` / `delete` / `shrink`** — 1実装しかない Service インターフェース、通り抜けるだけの Mapper 層、使われない Builder、早すぎる Registry/Strategy 化。
  - **FE（Nuxt / Vue / PrimeVue）**: **主戦場は `native` / `stdlib`** — ブラウザ標準（`<input type="date">` 等）・CSS・既存 UI ライブラリで足りるものに npm 依存を足していないか。npm audit ゲートが依存追加のたびに詰まる事情があるため、依存を増やさない圧力は実利がある。

  **【指摘禁止領域】**（ここを削るのは Ponytail ではなく手抜きである。指摘対象外）:
  - 信頼境界での入力検証
  - 認可（`@PreAuthorize` / F00 可視性 Resolver 経由の判定 / テナントスコープ絞り込み）
  - 監査ログ
  - データ損失防止のエラーハンドリング
  - アクセシビリティの基本
  - マスターが明示的に要求した事項

  **【本プロジェクト固有の例外】**（規約由来の抽象・正当な設計判断なので `yagni` 指摘の対象外）:
  - `UuidV7Entity` 継承（新規テーブルの主キー UUIDv7）
  - `AbstractTenantAwareRepository` 継承（テナントスコープ Repository）
  - モジュラーモノリスのドメイン境界に沿ったパッケージ分割（利用箇所が1つでも作るのが正しい）
  - `PageHeader` / `SectionCard` 等の共通コンポーネントへの寄せ（`/統一` スキルの方針と真逆になるため）
  - 実際に多実装が存在する Registry / Resolver（例: `ContentVisibilityChecker` は 22 個の Resolver、`GuardianshipAgePolicyRegistry`、`DisclosureAutoFillService` は 9 ソース）は正当な抽象。「1実装しかないか」を実際に数えてから `yagni` を指摘すること

  **検証は必須**: ponytail 系 finding は「消しても本当に動くのか」の裏取りが不可欠なため、他次元と同様に必ず敵対的検証ステージ（opus）を通すこと。検証を経ない ponytail finding は採用しない。
- **AC完全性次元は標的が違う**: 他の次元が「実装の欠陥」を探すのに対し、この次元は**受け入れ条件の一覧そのもの**を攻め口5類型（空・0件・null / 境界値 / 途中失敗 / 認可 / 性能）で攻め、「列挙されていない壊れ方」を探す（`model:'opus'` 推奨 — 仕様の穴の想像は安価モデルでは浅くなる）。finding は「不足AC の提案」として返し、採用なら軍議へ差し戻して AC 追加 → 試練で red テスト追加。トレーサビリティ照合は AC↔テスト↔実装の閉ループであり、**AC 自体の漏れ（③'）はこの次元でしか検出できない**。
- **モデル固定は必須（コスト最適化）**: 一次レビュー次元を全部 opus で回すのは過剰。**一次レビュー=`sonnet`/`effort:'low'`、Opus は敵対的検証ステージのみ**に限定する。finding が 0 件なら検証ステージごとスキップして Opus を一切焚かない（barrier で早期 return）。
- **偽バグ捏造の防止**（`feedback_empirical_bug_detection_over_speculation`）: verify ステージのスキーマに「ファイル:行の実在」を必須項目として持たせ、裏取りできない指摘は破棄する。
- **オプトイン必須・自走**: Workflow は途中で止まれない。検分 Workflow が確定 finding を返したら、殿が判定し、御裁可 → コミットは Workflow の外で行う。
- **下記チェックリストは Workflow の各次元プロンプトにそのまま流用する**。

参考スクリプト骨格は `docs/development/daimyo_workflow_migration.md §6` を参照。
ステップ0のセキュリティレビュー条件は Workflow 検分でも同様に適用する（該当時は security 次元を必ず含める）。

## 手順

0. **セキュリティレビュー（条件付き）**: 以下のいずれかに該当する変更が含まれる場合、`/security-review` を先に実行してからステップ1へ進む。該当なければスキップ。
   - `Controller.java` の新規作成・変更（新規APIエンドポイント）
   - `auth/`、`security/`、`filter/`、`SecurityConfig` の変更（認証・認可ロジック）
   - `@PreAuthorize`、`@PostAuthorize`、`permitAll`、`hasRole` の追加・変更（アクセス制御）
   - `DELETE`、`PATCH` 系エンドポイントの追加（リソース操作API）
   - ユーザーIDやリソースIDをパスパラメータで受け取るエンドポイントの追加

   確認コマンド（対象ブランチのdiff要約）:
   ```bash
   git diff origin/main...HEAD --name-only | grep -E "(Controller|SecurityConfig|auth/|security/|filter/)"
   git diff origin/main...HEAD | grep -E "(@PostMapping|@DeleteMapping|@PatchMapping|@PutMapping|permitAll|hasRole|@PreAuthorize)"
   ```

1. **自動試験（必須）**: まず `cd backend && ./gradlew build`（テスト込み）を実行し、ビルド・テスト結果を確認する。失敗時は検分を中断し、差し戻しまたはマスターへ上奏する
2. **トレーサビリティ照合（受け入れ条件がある場合は必須）**: 軍議の**受け入れ条件 N 個すべてに、対応する green テストが存在するか**を照合する。条件に対応するテストが無い／red のままなら、それは**実装漏れ**であり差し戻す。これが実装漏れ根治の本丸（③テスト自体の漏れまで含めて潰す）
3. **家老に検分を命ずる**: 各足軽のworktreeで生成・変更されたファイルを検査させる
4. **家老の検分報告を受ける**: 以下のチェックリストに基づく結果を確認
5. **殿様による最終確認**: 設計逸脱・セキュリティ・仕様整合性を自ら確認
6. **判定**: 合格ならマスターに上奏、不合格なら差し戻し
7. **戦役台帳の更新・削除（台帳がある場合）**: 検分結果・所見を `.claude/campaigns/<...>.md` のメモ欄に追記し、各隊の状態を更新する。**全 PR がマージされ戦役が完全に完了したら台帳ファイルを削除する**（得られた横断的教訓は削除前に `MEMORY.md` 側へ移す）。差し戻しや未マージが残るうちは削除しない

### 検分チェックリスト

#### 自動試験（検分の最初に必ず実行）
- [ ] `cd backend && ./gradlew build` 成功
- [ ] `./gradlew test` 全件パス

#### トレーサビリティ照合（受け入れ条件がある場合・実装漏れ根治の本丸）
- [ ] 軍議の受け入れ条件 N 個すべてに対応する green テストがある
- [ ] red のまま残った条件がない（残っていれば実装漏れ → 差し戻し）
- [ ] 条件に対応しない「コードをなぞるだけのテスト」が紛れていない
- [ ] **AC 一覧自体に攻め口5類型の消し込み（AC または「該当なし＋理由」）が揃っている**（無ければ軍議へ差し戻し。トレーサビリティは AC↔テスト↔実装の閉ループなので、AC 列挙自体の漏れ＝③' はここでしか捕まえられない）

#### 家老が検分（必須）
- [ ] コンパイルエラーなし
- [ ] `.claudecode.md` のコーディングスタイル原則（§17）に準拠
- [ ] `BACKEND_CODING_CONVENTION.md` / `FRONTEND_CODING_CONVENTION.md` に準拠
- [ ] テストが存在し、**攻め口5類型**（空・0件・null / 境界値 / 途中失敗 / 認可 / 性能）がカバー済み、または軍議で「該当なし＋理由」判定済み（正常系のみのテストは不合格）
- [ ] 変数名・メソッド名が仕様書の用語と一致（§17 原則2）
- [ ] 複雑な箇所に日本語コメントあり（§17 原則3）
- [ ] 新規依存の追加がある場合、stdlib / native / 既存依存で代替できない理由が示されている
- [ ] 贅肉（ponytail）次元の指摘が【指摘禁止領域】・本プロジェクト固有の例外に及んでいない（Registry/Resolver への `yagni` 指摘は実装数を数えたうえでのものか）

#### 殿様が最終確認
- [ ] 陣立て書の設計から逸脱していない（越権なし）
- [ ] セキュリティ脆弱性なし（SQLインジェクション、XSS、認証バイパス等）
- [ ] 仕様書との矛盾なし
- [ ] 足軽間の成果物に矛盾がない（型の不一致、命名の食い違い等）
- [ ] Flyway マイグレーション順序が正しい
- [ ] エラーコードの重複がない

## 殿のモデル運用（コスト最適化・必須）

- 検分は **Workflow モード(A) を本命**とし、次元別レビューは `sonnet`、敵対的検証だけ `opus` に固定する（上記）。差分が小さくモード B のときも、家老の一次検分は `sonnet`、殿が Opus を使うのは**最終押印の判断のみ**に絞る
- ビルド/テスト実行（手順1）は操作タスクなので Opus で抱え込まず、必要なら `sonnet` 足軽に委ねる（`feedback_opus_infra_ops_danger`）

## 注意事項
- 軽微な問題は殿様の裁量で家老に修正を命じてよい（マスターに報告不要）
- 重大な設計逸脱・仕様矛盾は必ずマスターにエスカレーション
- コミット・プッシュは必ずマスターの御裁可を得てから
