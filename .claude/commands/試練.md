# 試練（テスト先行・受け入れテスト作成）

マスターの御裁可を得た陣立て書と**受け入れ条件**に基づき、殿様として家老に試練の設置を命じ、足軽を起動して**実装より前に失敗するテスト（red）を書き切れ**。実装（`/出陣`）はこの試練を green に変えて乗り越える戦いとなる。

## 位置づけ — 開発フローのどこか

```
設計書 → 軍議〔分解＋受け入れ条件をN個列挙〕→ 試練〔条件1個=redテスト1本〕→ 出陣〔green化〕→ 検分〔条件↔テスト↔実装の照合〕→ E2E
```

- **試練は出陣の前段**。実装後に書くテストは「コードが何をするか」をなぞるだけで仕様の独立検査にならない。設計書から先に書けば、実装中は red のまま残り「**未実装なのに done に見える**」が構造的に消える（実装漏れの根治）。
- 純粋な micro-TDD（小刻み red-green-refactor）ではなく、**設計書と受け入れ条件から受け入れテストを書き切る spec-level test-first**。足軽が一気に書く流儀に合わせる。

## 対象と非対象

| テスト種別 | 試練で書くか |
|---|---|
| BEドメインのユニットテスト | ✅ 試練で先行（red）|
| API契約テスト（Controller/DTO・ステータス・認可） | ✅ 試練で先行（red）|
| FE コンポーネントテスト | ❌ 出陣の後（UIが無いと書けず ROI 低）|
| E2E（Playwright） | ❌ 最後（画面・API が揃ってから）|

- **前提**: 設計書が十分詳細で、軍議で**受け入れ条件が列挙済み**であること。設計が薄い機能はテストもブレるので、従来順（実装→テスト）に戻してよい（マスター判断・`feedback_test_first_be_api` のロールバック方針）。
- **コンパイル依存**: 契約・ユニットテストは Entity/Repo の骨格に依存して初めてコンパイルが通る。**進軍順序は Entity/Repo（骨格）→ 試練（red）→ 出陣（green）**。Entity/Repo が未着手ならテストはコンパイルできない点に注意。

## 前提条件
- `/軍議` が完了し、マスターの御裁可を得ていること
- 陣立て書に**受け入れ条件リスト**が含まれていること（無ければ軍議へ差し戻す）

## 手順

1. **受け入れ条件の確認**: 軍議が列挙した受け入れ条件を再確認し、**条件1個 ⇄ テスト1本**の対応表を作る。条件に漏れがあれば軍議へ差し戻す
2. **家老に試練設置を命ずる**: 家老を通じて足軽を `Agent(worktree)` で起動し、各受け入れ条件に対応する**失敗するテスト（red）**を書かせる
   - **`Agent` 起動時に `model` を必ず明示する（親 Opus 継承禁止）**:
     - **仕様解釈・エッジケース抽出・認可境界の試練設計 = `opus`**（試練の本質は仕様の独立検査。ここをケチると③テスト自体の漏れを招く・`feedback_test_first_be_api`）
     - 定型のテストスキャフォールド量産・既存テストの横展開 = **`sonnet`**
     - 迷ったら、設計判断を多く含むなら `opus`、機械的なら `sonnet`
   - 各足軽には担当する受け入れ条件・準拠規約（`TEST_CONVENTION.md`）・worktree保全手順を伝達する
3. **red の確認（必須）**: 書いたテストが**実装前なので必ず失敗する**ことを確認する。green になっているテストは「実装をなぞっただけ」か「条件を検査していない」疑いがあるので精査する
4. **戦果収集**: テスト成果物を `Glob` で検証して取り込み、**戦役台帳の受け入れ条件欄に「条件→テスト名→red確認」を記録**する
5. **出陣へ移行**: 全条件に red テストが揃ったら `/出陣` へ。実装はこの試練を green に変える戦いとなる

## red であることの検証
```bash
# 実装前なので、書いた試練（テスト）は失敗するのが正しい
cd backend && ./gradlew test --tests "対象テストクラス" || echo "red 確認（実装前ゆえ失敗が正常）"
```
全部 green で通ってしまう場合は、テストが受け入れ条件を実際に検査できていない兆候。条件との対応を見直す。

## 発言者ラベル規約（必須）
全ての報告に発言者ラベルを先頭に付与すること。
- 殿様: `🏯殿様:`
- 家老: `📜家老:`
- 足軽: `⚔️足軽{番号}({担当名}):`

## worktree運用ルール
- 足軽は `isolation:'worktree'` 必須。起動直後に CWD を確認し本陣不可侵。指令末尾に「全テスト作成後 `git add -A && git commit` を必ず実行（コミットせず報告すると成果物が消失する）」を含める（`/出陣` の worktree 保全手順に準拠）

## 殿のモデル運用（コスト最適化・必須）
- 試練は**仕様解釈が重い**ため、条件→テストの設計を担う足軽は `opus` を許容する。ただし定型のスキャフォールド量産は `sonnet` に振る
- 殿自身は試練の戦果統合・red 確認の判断に Opus を使い、それ以外（テスト実行などの操作）は `sonnet` 足軽へ委ねる（`feedback_opus_infra_ops_danger`）

## 注意事項
- マスターの御裁可なしに試練を設置してはならない
- **green で通るテストを「試練達成」と誤認しない**。実装前の試練は red が正常
- 受け入れ条件に対応しないテスト（コードをなぞるだけのテスト）は書かない
- 関連: `feedback_test_first_be_api` / `feedback_model_routing` / `TEST_CONVENTION.md`
