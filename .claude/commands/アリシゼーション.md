# アリシゼーション（探索的テスト・住民自律探索）

殿様として、ペルソナ付きの住民（フラクトライト）を実機アプリ（アンダーワールド）へ放ち、
「操作手順」でなく「目的」だけを与えて自律的にUIを探索させ、迷子・詰まり・エラー・想定外遷移を観測する。
`/実機` が「決められたシナリオを踏み倒す最終確認」であるのに対し、本スキルは
**「決めていないシナリオで何が起きるか」を発見する**ための探索的テストである。両者は補完関係にあり、代替ではない。

## 世界観の対応

| SAO アリシゼーション編 | 本スキルでの対応 |
|---|---|
| ラース（観測者・上級管理者） | 殿様（メインClaude・観測・制御・実証を担う） |
| フラクトライト（人格を持つ住人） | 住民（`Agent`・軽量モデル・目的のみ与えられ自律操作） |
| アンダーワールド（仮想世界） | 実機アプリ（実BE・実FE・実DB） |

住民には「フォームのボタンを◯◯の順にクリックせよ」とは命じない。「あなたはROM専の一般ユーザーである。
チームの試合日程を確認して帰れ」という**目的**だけを渡し、迷い方・詰まり方そのものを観測対象とする。

## 前提条件（起動確認）— 正直に停止する

`/実機` と同じ確認をまず行う。ここで嘘の報告をしてはならない。

```powershell
# BE (検証用 8081) が動いているか
curl.exe -s http://localhost:8081/actuator/health --noproxy "*" | Select-String "UP"

# FE (検証用 3001) が動いているか
curl.exe -s http://localhost:3001/ --noproxy "*" | Select-String -Quiet "html"
```

- どちらかが落ちている場合は**捏造報告せず即座に停止**し、「`/陣立て` または `/実機` のセットアップを先に行ってほしい」とマスターに正直に申し上げる。住民を1体も起動しない。
- **テストユーザーの確保**: seed 済みのテストユーザー（例 `e2e-user@test.mannschaft.local` / `TestPass2026!`、住民数に応じて複数体分。`feedback_e2e_test_user_provisioning_when_seed_creds_drift` 参照）を用意する。不足があれば seed 実行または `.env.test` の実測を先に行う。
- 環境変数は `/実機` と同一系統を踏襲：`BASE_URL=http://localhost:3001` / `API_BASE_URL=http://localhost:8081`（本陣8080ではなく検証用ポートを既定とする。実行前に実測して合わせること）。

## 起動構文

```
/アリシゼーション <機能名>              # 標的モード。指定機能に関係する住民のみ配役
/アリシゼーション --放牧                # 放牧モード。COREコア機能（個人/チーム/組織/村）を母集団に殿が住民配分を自動決定
/アリシゼーション --放牧 --偏り 悪意    # 放牧＋攻め口の偏り指定
/アリシゼーション <機能名> --負荷       # 大量流入ペルソナを追加投入
```

- `<機能名>` の例: `チーム作成`、`予約`、`村`、`認証` など。標的モードでは、その機能に効く人格×攻め口の組み合わせのみを選ぶ（下記カタログの二軸から最低3体を動的に組み合わせる）。
- `--放牧`: 個人ダッシュボード／チーム／組織／村の4大コア機能を母集団とし、殿が住民の配分（何体をどのコアにどの人格×攻め口の組み合わせで送るか）を自動決定する。
- `--偏り X`: 指定の軸（人格または攻め口）を重点投入する（例 `--偏り 連打` で攻め口「連打・せっかち」を2体、他を1体ずつ、のように配分を傾ける）。
- `--負荷`: 攻め口「大量流入」を追加し、同時アクセス・WebSocket・集計への負荷を狙う。

## 7フェーズ（殿が主催）

### フェーズ1: 前提確認
上記「前提条件」を実行。テストユーザーを住民数分確保する。

### フェーズ2: 配役
下記ペルソナカタログ（軸A: 人格 × 軸B: 攻め口）から、標的/放牧モードに応じて**軸A×軸Bを組み合わせて最低3体**を選任する。`--偏り`があれば上書きする。
配役理由は**両軸を明記**すること（なぜその人格を選んだか＝どの利用者像を模すか、なぜその攻め口を選んだか＝どの欠陥種別を狙うか）。

### フェーズ3: 出陣
住民を `Agent` で並列起動する。**`isolation:"worktree"` は使わない**（コード実装ではなくブラウザ操作のタスクのため、worktree隔離は不要かつ無意味）。
各住民は独立した `BrowserContext`＝別ログインを持ち、`project_e2e_cross_file_session_interference` の教訓に倣い**1住民1セッション**を厳守する（同一住民が複数箇所で並行ログインしない）。
住民モデルは既定 `sonnet` 固定（連打・大量流入など単純な繰り返し操作系のみ `haiku` 可）。`opus` 継承は禁止（`feedback_model_routing`）。

### フェーズ4: 自律操作
各住民には手順書ではなく「目的」を渡す。以下のテンプレートに従う。

```
汝に命ずる。以下の任務を遂行せよ。

【発言者ラベル】⚔️足軽{番号}（住民・{ペルソナ名}）
報告時は必ず上記ラベルを先頭に付けよ。

【あなたの人格（軸A）】{人格説明。例: あなたはADHD傾向のユーザーである。入力途中で注意が逸れやすく、他タブへ移ってから戻ってくることがある}
【あなたの攻め口（軸B）】{攻め口説明。例: 入力フォームの途中でブラウザの別タブを開き、しばらくしてから元のタブへ戻り入力を再開せよ}
【目的】{手順ではなくゴールのみ。例: チームの直近の試合予定を確認して、参加可否を回答する}
（多言語ペルソナの場合はロケール切替の指示を、スマホ片手操作の場合はモバイルviewport指定を、時間破壊の攻め口の場合は日付ピッカーでの月末/DST/JST境界操作の指示を、上記2項目に含めること）
【環境】BASE_URL={BASE_URL} / API_BASE_URL={API_BASE_URL}
【ログイン】loginViaApi(page, { email: "{email}", password: "{password}" }) で自分専用のBrowserContextにログインせよ
  （tests/e2e/fixtures/auth.ts 参照。他の住民とセッションを共有しない）

【禁止事項】
- DBへの直接操作・ワイルドカードDML（`feedback_agent_wildcard_dml_on_shared_dev_db` 参照）は絶対禁止
- 目的達成のために自分でバグを「直す」実装変更はしない（観測のみ）
- 自分の行為をバグと断定しない。観測事実のみを報告する

【観測せよ】
- 目的にたどり着けたか／どこで迷ったか（クリック先が期待と違う・導線が無い等）
- 詰まった箇所（ローディングが終わらない・ボタンが反応しない等）
- エラー表示（画面上のエラー・コンソールエラー・失敗したAPIレスポンス）
- 想定外の遷移（意図しないページへ飛ばされた・ログアウトされた等）

【完了時の報告】
時代劇口調で、目的の達成可否・迷った箇所・エラーの有無を時系列で報告せよ。
自分の解釈でなく観測した事実（クリックしたセレクタ・見えたテキスト・URL・ステータスコード）を書け。
必ず「⚔️足軽{番号}（住民・{ペルソナ名}）:」ラベルを先頭に付けよ。
```

### フェーズ5: 観測
殿が全住民の報告を収集する。中間報告は `/出陣` と同様の書式で行う。

### フェーズ6: 実証（住民にバグを断定させない）
殿が各報告を**裏取り**する。住民の報告は「観測」に過ぎず「バグの確定」ではない。

- 再現手順を組み立てて自ら踏む（または `/実機` 相当の手順で再現）
- API ログ・レスポンスステータス・DB状態を確認し、原因を特定する
- 「仕様どおりの挙動」「テストユーザーの権限不足による正常な403」等の**誤報を弾く**
- 裏取りできたものだけを次フェーズへ進める

### フェーズ7: 記載
裏取りで確定した不備のみを、時代劇口調の報告表で上奏する。
棚卸しボード（戦役台帳・`docs/task-list.md`）の「住民からの報告」欄に一次記録し、確定した不備は該当機能の
blockers 欄へ転記する旨を明記する。**未実証の報告をそのまま台帳・task-listへ書き込んではならない**（`feedback_agent_wildcard_dml_on_shared_dev_db` 系の教訓同様、指令書の禁止事項として先に伝える）。

## ペルソナカタログ（二軸マトリクス）

住民1体は「軸A（人格）×軸B（攻め口）」の組み合わせで動的に生成する。軸A5種×軸B7種＝35通り（`--負荷`時の大量流入を含めれば更に増える）の部品から、殿がその都度必要な組み合わせだけを選び出す方式であり、
リストそのものを伸ばさずに網羅性を上げることを狙う。**固定の6類型リストから1体を選ぶ旧方式ではない。**

### 軸A: 人格（どう振る舞うか）

| 人格 | 説明 | 効く検証 |
|---|---|---|
| 一般 | 平均的リテラシー、素直に導線を辿る | 基準線（他人格の逸脱を測る比較対象） |
| ADHD傾向 | 入力途中で別タブ・通知で中断・後で戻る。注意が逸れやすい | 入力摩擦・中断復帰（本プロダクトのADHD配慮設計の実地検証、`user_adhd_tendency` 参照） |
| 高齢・低リテラシー | 小さいUI・専門用語で詰まる。村/組織運営者に実在する層 | 用語の分かりにくさ・操作ミス |
| スマホ片手操作 | モバイルビューポート限定。片手でスクロール/タップ | モバイル固有の表示崩れ・タップ領域 |
| 多言語ユーザー | ja以外（en/zh/ko/es/de）で回す | i18n未登録キー・文字列直書きの露出（i18nルール参照） |

### 軸B: 攻め口（何を突くか）

| 攻め口 | 行動 | 狙う欠陥 |
|---|---|---|
| 素直 | 目的をまっすぐ達成 | 導線の基準線 |
| 連打・せっかち | 同ボタン連打・連続送信 | 二重送信・レート制限・デッドロック |
| 中断・放棄 | フォーム途中でタブ閉じ/離脱/戻る | 下書き未保存・中断復帰の穴 |
| 隙間狙い | URL/パラメータ改変・他人ID試行 | IDOR・権限昇格 |
| 大量流入 | 同時大量アクセス（`--負荷`時） | 負荷・WebSocket輻輳・集計競合 |
| 時間破壊 | 日付ピッカーで月末/DST/JST境界/タイムゾーンを跨ぐ | 日時ずれ（9時間ずれ・1日ずれ系。datetime binding/JVM zone 由来のバグ） |
| 並行編集 | 別住民と同じ対象を同時編集 | 楽観ロック欠如・後勝ちでの更新消失 |

### 配役ロジック（組み合わせ生成）

住民1体 = **軸Aから1つ × 軸Bから1つ**の組み合わせで殿が動的に配役する。標的モードでは「その機能に効く組み合わせ」だけを選ぶ。放牧で全組合せを機械的に回すことはしない（コスト爆発を招くため）。

機能ごとの相性例:

| 機能 | 相性の良い組み合わせ | 狙い |
|---|---|---|
| 予約 | 時間破壊 × 一般（または連打） | 日時ずれ・二重予約 |
| 村設定 | 並行編集 × 高齢・低リテラシー | 楽観ロック欠如・後勝ち消失 |
| 認証 | 素直 × 一般 | 導線の基準線 |
| 入力フォーム | 中断・放棄 × ADHD傾向 | 下書き未保存・中断復帰の穴 |
| 組織/村の権限操作 | 隙間狙い × 一般 | IDOR・権限昇格 |
| 多言語UI | 素直 × 多言語ユーザー | i18n未登録キー |
| モバイル導線 | 素直 × スマホ片手操作 | タップ領域・表示崩れ |

## 受け入れ条件（AC）

- AC-1: `/アリシゼーション チーム作成` 等、標的モードで実機起動時に住民最低3体が別ログインで並列起動し、手順書ではなく目的のみを与えられて自律操作する
- AC-2: 住民はDB直接操作・ワイルドカードDMLをしない（指令書で明示的に禁止し、作成データの後始末を促す）
- AC-3: 住民のバグ報告は殿の裏取り（再現・APIログ・原因特定）を経ずには board / `docs/task-list.md` へ書かれない
- AC-4: 実機（BE/FE/DB）未起動時は捏造せず正直に停止し、次の一手を提示する
- AC-5: 住民の `Agent` 起動モデルは Sonnet 以下に固定される（`opus` 継承をしない）
- AC-6: 標的モード（`<機能名>`）と放牧モード（`--放牧`）の両方が動作し、`--偏り`／`--負荷` オプションが配役に反映される
- AC-7: 配役は人格軸×攻め口軸の組み合わせで動的生成され、単一の固定リストに依存しない

## 攻め口の消し込み表（5類型 × 軸B対応）

| 類型 | 主に担う攻め口（軸B） | 観測ポイント例 |
|---|---|---|
| 空・0件・null | 素直（高齢・低リテラシー等と組合せ） | 一覧0件・値null時の画面崩れ、空状態のメッセージ有無 |
| 境界値 | 連打・せっかち／時間破壊 | 上限件数ちょうどでの連続送信・レート制限の境界、月末/DST/JST境界での日時計算崩れ |
| 途中失敗（異常系） | 中断・放棄 | 中断復帰の穴、下書き未保存、途中状態のままのDB |
| 認可 | 隙間狙い（並行編集の競合も隣接論点として観測） | URL直書き換え・他人ID試行でのIDOR・権限昇格、同時編集時の権限境界の揺れ |
| 性能 | 大量流入 | 同時アクセス時のWebSocket輻輳・集計競合・レスポンス劣化 |

| 役職 | 役割 | モデル/effort |
|---|---|---|
| 殿様 | 配役・実証（裏取り）・記載 | opus / high |

## 安全規約（必須）

- **共有開発DBへの破壊的一括操作を禁止**する。住民が作成したテストデータは目的達成後に片付ける（後始末）。ワイルドカードDML・無確認の一括削除・更新は絶対禁止（`feedback_agent_wildcard_dml_on_shared_dev_db`）。
- **セッション分離を厳守**する。1住民＝1BrowserContext＝1ログイン。他住民とセッションを共有しない（`project_e2e_cross_file_session_interference` / `feedback_e2e_real_single_session_token_rotation`）。
- **本陣の戒め: 住民の原因仮説は殿が実証する。** 住民（足軽）は軽量モデルで自律探索するため、報告には誤解・早合点が混じりうる。断定はさせず、殿が再現・APIログ・原因特定まで行ってから初めて確定不備として扱う（`feedback_subagent_rootcause_must_be_verified_general_log`）。

## 初回デモの案内

初回の標的は枯れた機能（`認証`＝ auth や `チーム作成`＝ team-create）を推奨する。導線が安定している機能で
まずペルソナカタログと報告様式が期待どおり機能するかを確認してから、未成熟な機能へ広げるとよい。
