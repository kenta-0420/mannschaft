# 役割分担（タスク別モデル振り分け）

> このスキル自体は参照用のため `model: haiku`（呼び出しても軽量に終わらせる）。

大名システムでモデルを使い分ける際の**振り分け基準**を定義する。Codex 側に作成済みの同名スキルと対になるもの。

**呼称の使い分け（重要）**: Claude Code 上ではモデルをそのまま **Opus / Sonnet / Haiku** と呼ぶ。Codex 側の同名スキルでは同じ対応関係を **Sola（Opus）/ Terra（Sonnet）/ Luna（Haiku）** という呼称で扱う。両者は同一の振り分け基準を指す別名であり、Claude Code のセッション内でSola/Terra/Lunaという呼称は使わない。

## 前提となるモデルと単価（2026-09-25 時点・Opus 5.5 登場時）

| モデル | 入力 / 出力（$/100万トークン） | キャッシュ読取 | 位置づけ |
|---|---|---|---|
| Opus 5.5 | $4 / $20 | $0.20（Opus 5 比 60% 引き） | 殿・難所の格上げ先。既定 effort は `medium` |
| Sonnet 5 | $2 / $10 | — | 足軽・家老の既定 |
| Haiku 4.5 | さらに安価 | — | 雑務 |
| Fable 5.1 | Opus 5.5 より約 1.7 倍高い | — | 公式に「ほとんどの作業で Opus 5.5 と同等」。**常用しない** |

- Opus 5.5 は Opus 5 より単価 20% 安く、同じ effort で出力トークンが 20〜25% 少ない。それでも Sonnet 5 の単価の 2 倍であり、過去の実測では足軽を Opus にすると消費量が 1 桁増えた（`feedback_model_routing`）。**Sonnet 既定の方針は変えない。**
- Sonnet 5.5 / Haiku 5.5 は「数週間以内にリリース」と公式発表されている。出たらこの表を見直す。

## 振り分け方針（現行・2026-09-25 更新）

**既定は Sonnet。Opus は「Sonnet で実際に詰まった／判断が割れた」場合の格上げ先とし、着手時点での予防的な格上げはしない。**

| タスクの性質 | 既定モデル / effort | 補足 |
|---|---|---|
| 絵図（設計書作成・要否精査） | Sonnet / medium → 詰まったら Opus / medium | 機械的な精査・反映は Sonnet、解釈が割れる箇所のみ Opus |
| 検分（コードレビュー） | **Codex 既定**（Claude 側で回す場合は一次レビュー Sonnet / low、敵対的検証ステージのみ Opus / medium） | 2026-09-01 御下命で Fable/Opus 検分は使わない方針 |
| 軍議（設計・タスク分解） | Sonnet / medium（偵察・列挙）／Opus / medium（設計判断・トレードオフ精査） | 家老 Plan/Explore も model 省略禁止・明示必須 |
| 試練（仕様解釈・エッジ抽出） | Opus / medium（定型量産は Sonnet / low） | 旧 `opus / high` から引き下げ。Opus 5.5 の medium で旧 high 相当の質が出る |
| コーディング・実装全般（FE/BE） | **Sonnet / medium** | 認可・DB(Flyway)・複雑な型でも着手時は Sonnet、差し戻された箇所だけ Opus |
| テスト・E2E・ビルド確認 | **Sonnet / low〜medium** | |
| インフラ操作・プロセス起動停止・環境確認 | **Sonnet / low**（Opus/Fable には絶対させない） | Opus は「まず深く理解しろ」バイアスで運用タスクを壊す実績あり |
| 単純grep/置換・ファイル列挙・定型雑務・索敵 | **Haiku / low** | |

## effort の段階（Opus 5.5 で変わった点）

- **Opus の既定は `medium`**。公式によれば Opus 5.5 は medium で他社最上位モデルの最高 effort と同等の成績を約 2 割のコストで出す。旧来「難所は opus / high」としていた箇所は、まず `opus / medium` で当てる。
- **格上げは2段**: Sonnet で詰まる → `opus / medium` → それでも詰まる → `opus / high`。`xhigh` は殿が理由を明記したときだけ使う。
- **`max` は使わない**。思考だけで出力上限（128K）を食い潰し、成果物が出ないまま終わる危険がある（1タスクで約 119K の出力を使った実例あり）。
- 実装足軽の格上げ上限は従来どおり Opus まで。Fable へは振らない。

## 殿（メインセッション）の運用

- **殿は Opus 5.5 / effort medium で起動する**（`~/.claude/settings.json` の `"model": "opus[1m]"` は Opus 5.5 に解決される）。詰まった局面だけセッション限定で `high` に上げ、終わったら戻す。
- **セッション途中でモデルを切り替えない**。切り替えると prompt cache が作り直しになり、Opus 5.5 最大の値下げ（キャッシュ読取 60% 引き）を捨てることになる。Sonnet で十分な仕事（陣立て・インフラ確認・マージ作業だけのセッション等）は、**最初から** `/model sonnet` のセッションで始める。従来の「対話中に `/model sonnet` へ切り替える」運用はこれで置き換える。
- **Fable 5.1 は常用しない**。Opus 5.5 がほぼ同等の成績を約 4 割安く出すため。Fable が要る仕事かどうかは、マスターが週単位で判断する。
- **Fast mode は使わない**。単価が 2 倍（$8 / $40）で、利用枠ではなく usage credits から別途課金される。
- 足軽を多く並べるほど殿がその報告を読むコストが増える。報告は要点のみ返させ、足軽の全文を殿の文脈に取り込まない。

## 使い方

- `Agent`/`Workflow` 呼び出し時は `model` パラメータ（`opus`/`sonnet`/`haiku`）を毎回明示すること（省略禁止）。Workflow の `agent()` では `effort` も明示する。
- 振り分け基準そのものの変更履歴・実測値（Opus乱用時のトークン消費など）は `feedback_model_routing` メモリが正本。本スキルは参照用の要約に留め、判断根拠の詳細はメモリ側を参照する。
