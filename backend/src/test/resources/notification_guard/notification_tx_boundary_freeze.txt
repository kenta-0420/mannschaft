# キーの書式（行番号は含めない。無関係な編集で削除＋追加に見えるのを防ぐため）:
#   <完全修飾クラス名>#<メソッド名> -> <種別>
#
# 種別:
#   ASYNC_SELF_INVOCATION  @Async メソッドの同一クラス内無修飾呼び出し（プロキシを経ず失効）
#   PLAIN_EVENT_LISTENER   通知を発火するリスナーが素の @EventListener（業務コミット前に走る）
#   DIRECT_RUNNER_CALL     sendOne を許可された入口以外から直接呼んでいる
#   ASYNC_WITHOUT_EXECUTOR 通知発火クラスの @Async が executor 無指定（event-pool へ載る）
#   TX_NOTIFY_IN_TRY       @Transactional 文脈で通知を発火し try で失敗を握っている
#   TX_NOTIFY_BARE         @Transactional 文脈で通知を発火している（try 無しの単発）
#   TX_NOTIFY_VIA_DELEGATE @Transactional 文脈から別 Bean へ委譲し、その先で通知が発火する（Issue #3039）
#
# 契約: 付随通知は業務TX内ではイベント発行だけを行う。実通知は明示的な AFTER_COMMIT 境界の後、
#       または項目TX完了を待つ非トランザクションのバッチオーケストレータからのみ実行する。
#       @Async / REQUIRES_NEW / NOT_SUPPORTED 単独は AFTER_COMMIT の代用とみなさない。
#
# 増加は常に CI fail。減少は該当実装差分と同じPRでのみ許可（是正したら必ずこの行を削る）。
# 最終目標は baseline ゼロ。
#

# 影響区分（任務5 / Codex 独立検分を受けた追加。エントリ行の末尾に " | <区分>" で付ける）
# ------------------------------------------------------------------------------
# ここに並ぶ違反は「原則5 に違反している」という点では一貫しているが、
# 性質の異なるものが混在しており、是正の手当ては同じとは限らない。
# ロット割り当ての前に機械可読な形で区別できるよう、区分を列として持つ。
#
#   ROLLBACK_COUPLED  (i)   通知の失敗が業務トランザクションを巻き戻す。#2990 が問題にしている本体。
#                           委譲先が無印（＝呼び出し元の TX にそのまま参加）／同一 TX 内の直接発火。
#   ORDERING_ONLY     (ii)  巻き戻しはしないが「業務コミット後」という因果順序を保証しない。
#                           委譲先が @Async の形（別スレッドなので例外が呼び出し元へ返らない）。
#                           **同期の REQUIRES_NEW / NOT_SUPPORTED / NEVER はここに入らない。**
#                           それらが切り離すのは「内側の作業」であって「例外の伝播」ではなく、
#                           握っていなければ例外は呼び出し元へ返り外側の業務TXも巻き戻る（L12 で是正）。
#                           業務側が後でロールバックしても通知だけ残る「逆向きの不整合」が通る。
#   AMBIGUOUS         (iii) 違反であることは確定しているが、巻き戻るかどうかを字句から決められない
#                           （Issue #3149）。レシーバの型が宣言から読めない／索引の外／
#                           呼び先の宣言が見つからない／候補間で結論が割れる。
#                           ORDERING_ONLY へ倒してはならない——それは「軽症」という主張であり、
#                           不明をそちらへ倒すと本物の地雷を軽症に見せる。安全側は常に
#                           「巻き戻るかもしれない」側であり、是正では ROLLBACK_COUPLED と同じ
#                           優先度で人手で1件ずつ確かめる。理由の記載を機械で強制する:
#                             # AMBIGUOUS_IMPACT: <完全修飾クラス名>#<メソッド名> -> <種別> : <理由>
#                           （下の「# AMBIGUOUS:」＝違反かどうか自体が決まらない、とは別物）
#
# 区分の無い行は「未分類」。残る未分類は PLAIN_EVENT_LISTENER 3 件であり、
# 番人は「一度付けた分類が黙って外れること」だけを機械的に止める（# CLASSIFIED_FLOOR）。
# 分類を増やしたら CLASSIFIED_FLOOR も同じPRで上げること。
#
# CLASSIFIED_FLOOR: 33
#
# 分類は綴りだけでなく「ソースの実際の注釈」と機械照合される（任務4）。
# TX_NOTIFY_VIA_DELEGATE / TX_NOTIFY_BARE / TX_NOTIFY_IN_TRY について呼び先の宣言から区分を導出し、
# 台帳の値と一致しなければ番人が落ちる。導出規則:
#   委譲先入口に @Async が付く、または @Transactional(propagation = REQUIRES_NEW / NOT_SUPPORTED / NEVER)
#     -> ORDERING_ONLY（呼び出し元のTXに参加しない＝巻き戻らないが因果順序は保証されない）
#   それ以外（無印・既定の REQUIRED ほか）
#     -> ROLLBACK_COUPLED（呼び出し元のTXに参加する＝通知の失敗で業務が巻き戻る）
# 分類を誤ると是正の手当てを誤る（「TXから切り離す」と「AFTER_COMMIT リスナーへ移す」は別物）ため、
# 人手のコメントではなく機械照合を正とする。
#
# ------------------------------------------------------------------------------
# 判定不能（曖昧）の台帳
# ------------------------------------------------------------------------------
# 型解決の候補が一意に決まらず、しかも候補ごとに判定が割れる箇所は、番人にとって
# 「違反である」とも「違反でない」とも言えない。これを violations() に入れずに放置すると、
# CI は赤いのに是正対象の一覧（このファイル）には現れず、ロット計画は実違反数を過少報告する。
# この戦役では「一覧が実態より小さい」が既に5回起きているので、曖昧性も同じ台帳に載せる。
#
# 書式: # AMBIGUOUS: <完全修飾クラス名>#<メソッド名> : <理由>
# 番人が次を機械的に検証する:
#   - 検出された判定不能はすべてこの台帳に載っていること（載っていなければ fail）
#   - 台帳の行がすべて現在も判定不能であること（解消したら行を消し CENSUS_FLOOR も下げる）
#   - 理由が10文字以上であること
#   - 総数（凍結エントリ + REMOVED + AMBIGUOUS）が CENSUS_FLOOR を下回らないこと
# 現時点の判定不能は 0 件（AMBIGUOUS 行なし）。0件でも仕組みは動いており、
# 台帳ゲートの変異テストが偽の判定不能を流して裏取りしている。
