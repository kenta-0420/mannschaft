# プロジェクト構成規約 (Spring Boot & Nuxt.js)

## 1. バックエンド (Java / Spring Boot)
src/main/java/com/mannschaft/app/ 配下は「技術レイヤー」ではなく「機能（ドメイン）」ごとにパッケージを分離すること。

### 構成イメージ
```
src/main/java/com/mannschaft/app/
├── config/                          # Spring設定クラス
│   ├── SecurityConfig.java
│   ├── WebSocketConfig.java
│   ├── RedisConfig.java
│   ├── CorsConfig.java
│   ├── SwaggerConfig.java
│   ├── AsyncConfig.java             # @EnableAsync + スレッドプール定義（§15）
│   ├── TimeZoneConfig.java          # JVM タイムゾーン設定（§20）
│   ├── RequestLoggingFilter.java    # MDC requestId/traceId 設定（§27）
│   └── SpringEventPublisher.java    # DomainEventPublisher 実装（§6）
├── common/                          # 共通部品
│   ├── ErrorCode.java               # エラーコード共通インターフェース
│   ├── BusinessException.java       # 業務例外（ErrorCode保持）
│   ├── GlobalExceptionHandler.java  # グローバル例外ハンドラー
│   ├── ApiResponse.java             # 共通レスポンスラッパー（単一用）
│   ├── PagedResponse.java           # ページネーション付きレスポンス
│   ├── ErrorResponse.java           # エラーレスポンス
│   ├── CommonErrorCode.java         # 共通エラーコード Enum
│   ├── CursorPagedResponse.java     # カーソルベースページネーションレスポンス
│   ├── CommonConstants.java         # プロジェクト横断的なシステム定数
│   ├── DomainEventPublisher.java    # イベント発行抽象インターフェース
│   └── event/                       # 共通イベント基底クラス
│       ├── DomainEvent.java         # マーカーインターフェース
│       └── BaseEvent.java
└── [feature]/                       # 例: auth, team, organization
    ├── [Feature]Controller.java     # ※役割ごとに分割可（例: AuthLoginController）
    ├── [Feature]Service.java        # ※役割ごとに分割可（例: AuthTokenService）
    ├── [Feature]Repository.java
    ├── [Feature]Entity.java
    ├── [Feature]ErrorCode.java      # 機能別エラーコード Enum
    ├── [Feature]Mapper.java         # MapStruct マッパー
    ├── [Feature]CreatedEvent.java   # 機能固有のドメインイベント
    └── dto/
        ├── [Feature]Request.java
        └── [Feature]Response.java
```

### ルール
- `com.mannschaft.app.controller` のような全機能共通のレイヤーパッケージは作成禁止。
- **パッケージ宣言:** ファイル移動・作成時は、ディレクトリ構造に合わせた `package` 宣言を正しく記述すること。
- **共通部品:** 複数機能で共有するモデルや基底クラスは `com.mannschaft.app.common` に配置すること。
- **設定クラス:** Spring の設定クラス（Security, WebSocket, Valkey/Redis, CORS, Swagger 等）は `com.mannschaft.app.config` に配置する。`common` とは分離し、アプリケーション設定専用とする。
- **依存関係:** 異なる機能間のサービスを呼び出す場合は、Repositoryを直接呼ばず、Service経由で呼び出すこと。
- **Service/Controller分割:** 機能が肥大化する場合は、役割ごとにクラスを分割すること。同一 feature パッケージ内に配置する。（例: `AuthService`, `AuthTokenService`, `AuthOAuthService`）

## 2. フロントエンド (TypeScript / Nuxt.js)

> ディレクトリ構成・命名規則・API通信・セキュリティの詳細は **`FRONTEND_CODING_CONVENTION.md`** に定義する。ここでは原則のみ記載する。

- Nuxt 3 の標準ディレクトリ構成をベースに、機能別でファイルを整理する
- **SSR と認証の制約**: JWT は `localStorage` に保存するため、SSR 時にはアクセス不可。SSR は公開ページ（SEO目的）のみ、認証ページは SPA モード
- **API通信**: フロントエンド → Spring Boot API に直接通信。BFF（`server/api/`）はAPIキー秘匿等の例外時のみ
- **自動生成型**: `types/generated/` は直接編集禁止。openapi-typescript で生成（`cd frontend && npm run generate:types`）

## 3. エラーハンドリングとAPIレスポンス設計

### 3.1 レスポンス形式
HTTPステータスコードで成功/失敗を判断する。`success` フィールドは持たない。
成功時は常に `data` フィールドでラップし、一貫性を保つ。
すべてのコントローラーは `ApiResponse<T>` または `PagedResponse<T>` を返り値とする。

**共通レスポンスクラス:**
```java
// 単一レスポンス: ApiResponse<T>
// フィールド: data (T)
ApiResponse<UserResponse> → { "data": { "id": 1, "name": "..." } }

// ページネーションレスポンス: PagedResponse<T> extends ApiResponse<List<T>>
// フィールド: data (List<T>), meta (PageMeta)
PagedResponse<UserResponse> → { "data": [...], "meta": { "total": 100, "page": 1, "size": 20, "totalPages": 5 } }

// エラーレスポンス: ErrorResponse
// フィールド: error (ErrorDetail: code, message, fieldErrors?)
ErrorResponse → { "error": { "code": "AUTH_001", "message": "...", "fieldErrors": [...] } }
```

**バリデーションエラー時の `fieldErrors`:**
```json
{
  "error": {
    "code": "COMMON_001",
    "message": "入力内容に不備があります",
    "fieldErrors": [
      { "field": "email", "message": "メールアドレスは必須です" },
      { "field": "password", "message": "8文字以上で入力してください" }
    ]
  }
}
```
バリデーションメッセージは `src/main/resources/messages.properties` に集約し、`GlobalExceptionHandler` でフィールド名＋メッセージを変換する。

### 3.2 エラーコード設計（Enum・機能別分割）
- `com.mannschaft.app.common` に共通インターフェース `ErrorCode` を配置する。
- 各機能パッケージ内に `[Feature]ErrorCode` Enum を作成し、`ErrorCode` を実装する。
- `ErrorCode` はHTTPステータスに依存しない。HTTPステータスとの紐付けは `GlobalExceptionHandler` で行う。

```java
// com.mannschaft.app.common.ErrorCode
public interface ErrorCode {
    String getCode();
    String getMessage();
    Severity getSeverity();

    enum Severity { ERROR, WARN, INFO }
}

// com.mannschaft.app.auth.AuthErrorCode
public enum AuthErrorCode implements ErrorCode {
    AUTH_001("AUTH_001", "メールアドレスまたはパスワードが正しくありません", Severity.WARN),
    AUTH_002("AUTH_002", "トークンの有効期限が切れています", Severity.WARN);
    // ...
}

// GlobalExceptionHandler 内で ErrorCode → HttpStatus のマッピングを管理
// Severity ベースのデフォルト + 個別オーバーライドの2層構造
private static final Map<ErrorCode, HttpStatus> HTTP_STATUS_MAP = Map.of(
    AuthErrorCode.AUTH_001, HttpStatus.UNAUTHORIZED,
    AuthErrorCode.AUTH_002, HttpStatus.UNAUTHORIZED
    // ... 個別マッピングが必要なもののみ登録
);

private HttpStatus resolveHttpStatus(ErrorCode errorCode) {
    // 1. 個別マッピングがあればそれを使用
    // 2. なければ Severity からデフォルト解決（ERROR→500, WARN→400, INFO→200）
    return HTTP_STATUS_MAP.getOrDefault(errorCode, defaultFromSeverity(errorCode.getSeverity()));
}
```

**設計理由:** エラー定義を特定のプロトコル（HTTP）から独立させ、バッチ処理やメッセージング処理など、非HTTPコンテキストでも再利用可能にするため。

#### 3.2.1 `Severity` の意味と `Severity.ERROR` の付与基準【必須】

`ErrorCode.Severity` の**唯一の消費者は `GlobalExceptionHandler#resolveHttpStatus`** である。ログレベルの決定には使われていない（`BusinessException` は severity に関わらず常に `log.warn`）。

したがって **`Severity.ERROR` を付けることは「既定で HTTP 500 を返す」宣言と同義**である。

| Severity | 既定 HttpStatus | 付けてよいのは |
| :--- | :--- | :--- |
| `ERROR` | **500** | **サーバ側の障害のみ**（外部連携失敗・生成/直列化失敗・データ不整合・想定外の状態） |
| `WARN` | 400 | クライアント起因（入力不備・不在・重複・状態遷移違反・所有権不一致） |
| `INFO` | 200 | 正常系扱いの通知 |

**クライアント起因のエラーに `Severity.ERROR` を付けてはならない。** 500 になると `status.is5xxServerError()` 経由で `error_reports` への記録と Slack エスカレーションまで走るため、利用者の入力ミスのたびに障害アラートが鳴る。

**是正手順（対処療法の禁止）:**

1. クライアント起因なら、まず **`Severity` を `WARN` に正す**（宣言箇所で意図が読めるようになる）。既定の 400 で妥当ならこれで足りる。
2. 既定の 400 では粗すぎる場合（不在は 404・重複や状態競合は 409・課金導線は 402 など）に限り `ERROR_CODE_STATUS_MAP` へ明示登録する。

**`Severity.ERROR` のまま `ERROR_CODE_STATUS_MAP` に 4xx を足すだけの直し方は禁止**する。定義側に誤分類を残したまま症状だけを隠すことになる。

> **既知の例外（新規に増やさないこと）:** `CHAT_015`(413) / `CHAT_019`(409) / `RECRUITMENT_204`(400) / `RECRUITMENT_207`(400) は `Severity.ERROR` のまま `ERROR_CODE_STATUS_MAP` で 4xx に上書きされている。ステータスは正しいが定義側の分類は誤ったままであり、既存テスト `GlobalExceptionHandlerTest` の `@DisplayName`（「ERROR severity だが個別マッピングで 400 になる」）がその状態を文書化している。**これらは過去の負債であって手本ではない。**

既定の 400 を上書きするときの目安:

| 状況 | ステータス |
| :--- | :--- |
| 入力不備・状態遷移違反・**件数/サイズの上限超過** | **400（既定のまま。上書き不要）** |
| 対象が存在しない（越境アクセスの存在秘匿を含む） | 404 |
| 重複（already exists）・状態遷移の競合・楽観ロック競合 | 409 |
| 支払いが必要 | 402 |
| レート制限 | 429 |

**「上限超過は 409」ではない。** 本リポジトリの「上限超過」系エラーコードは全数調査（154 件）で **400 が 113 件・409 が 21 件**であり、400 が本則である（409 側は PersonalTimetable / PointCard 等の一部ドメインに偏在する少数派）。件数上限を 409 に倒すと同一概念の兄弟コードと割れる。

#### 3.2.2 ステータスを決めるときは「同一概念の兄弟コード」を必ず確認する【必須】

ドメインをまたいで**同じ概念に別々のエラーコードが存在する**ことが多い。片方だけ触ると系統が割れる。

- 例: `ReservationErrorCode.MAX_REMINDERS_EXCEEDED`(`RESERVATION_015`) と `ScheduleErrorCode.MAX_REMINDERS_EXCEEDED`(`SCHEDULE_008`) は **enum 定数名まで同一**の「保存済みリマインダー件数上限」
- 例: `PaymentErrorCode.WEBHOOK_SIGNATURE_INVALID`(`PAYMENT_019`) と `ConnectPaymentErrorCode.WEBHOOK_SIGNATURE_INVALID`(`PAYMENT_C040`)

新規追加・ステータス変更の前に、**enum 定数名と日本語メッセージの両方で全 `*ErrorCode.java` を grep** し、同一概念のコードが別ステータスになっていないか確認すること。

回帰固定は `GlobalExceptionHandlerTest` の `ClientErrorMustNotBe500` にある。新規エラーコード追加時、クライアント起因なのに 500 を返す状態にしないこと。

### 3.3 エラーコード命名規則
`{機能プレフィックス}_{連番3桁}` の形式で命名する。

| プレフィックス | 機能 | 例 |
| :--- | :--- | :--- |
| `COMMON` | 共通（バリデーション、権限等） | `COMMON_001` |
| `AUTH` | 認証・認可 | `AUTH_001` |
| `TEAM` | チーム管理 | `TEAM_001` |
| `ORG` | 組織管理 | `ORG_001` |

新しい機能を追加する際は、対応するプレフィックスを定義してからエラーコードを作成すること。

### 3.4 メッセージのハイブリッド方式
- **バックエンド**: Enum にデフォルトメッセージを保持し、レスポンスに含めて返す。バックエンド単体でもエラー内容が完結するようにする。
- **フロントエンド**: エラーコード (`code`) をキーとして表示文言を制御できる。サーバーのメッセージをそのまま表示しても、コードに基づいて独自の文言に差し替えてもよい。
- この方式により、フロントエンドの実装が未完了でもエラー内容が把握でき、将来のi18n対応にもコードベースで移行しやすい。

### 3.5 グローバル例外ハンドラー
`com.mannschaft.app.common` に以下のクラスを配置する。

- **`BusinessException`**: `RuntimeException` を継承し、`ErrorCode` を保持する業務例外クラス。Service層からスローする。
- **`GlobalExceptionHandler`** (`@RestControllerAdvice`): 以下の例外をキャッチし、共通レスポンス形式に変換する。
    1. `BusinessException` → 保持する `ErrorCode` に基づきレスポンス生成。`ErrorCode` → `HttpStatus` のマッピングもここで管理する。
    2. `MethodArgumentNotValidException`（Bean Validation失敗） → `COMMON_001` + `fieldErrors` として変換
    3. `HttpMessageNotReadableException`（不正な JSON ボディ） → `COMMON_001`（400 Bad Request）
    4. `MethodArgumentTypeMismatchException`（パス変数やクエリパラメータの型不一致） → `COMMON_001`（400 Bad Request）
    5. `MissingServletRequestParameterException`（必須クエリパラメータの欠落） → `COMMON_001`（400 Bad Request）
    6. `ObjectOptimisticLockingFailureException`（楽観的ロック競合） → `COMMON_003`（409 Conflict、§22 参照）
    7. その他の未定義例外 → `COMMON_999`（システムエラー、500）として一律処理

### 3.6 フロントエンドのエラーハンドリング
- **`composables/useErrorHandler.ts`** を作成し、エラーコードから表示メッセージへの変換ロジックを集約する。
- **共通インターセプター**（`useApi.ts` 内）で、認証切れ（401）やシステムエラー（5xx）を自動キャッチし、トースト通知やエラーページへの遷移を行う。
- **フォームバリデーションエラー**: `fieldErrors` 配列を受け取り、各画面の VeeValidate と連携して項目別にメッセージを表示する。

## 4. APIバージョニング
- **方式**: URLパスベースのバージョニング（`/api/v1/...`）を採用する。
- **バージョンアップ基準**: 破壊的変更が必要な場合のみメジャーバージョン（v2, v3...）を上げる。フィールドの追加など後方互換のある変更は同一バージョン内で対応する。
- **並行稼働**: 新バージョンリリース後も、旧バージョンは最低3ヶ月間は並行稼働させる。

## 5. リソーススコープ（取得範囲）の命名規約
- **個人スコープ**: ログインユーザー自身のデータを取得する場合は `/resources/me`（例: `/todos/me`）というパスを使用する。
- **所属組織スコープ**: チームや組織に紐づくデータを取得する場合は、`/teams/{teamId}/resources` のように、親リソースのIDをパスに含めることを原則とする。
- **一貫性の保持**: `GET /todos` のようにスコープが曖昧なエンドポイントは避け、必ず「誰の・何の」範囲であるかをパス構造で定義する。
- **例外**: 検索APIなどで動的に範囲を切り替える場合は、`scope=mine|team|all` といったクエリパラメータを標準化して使用する。
- **README.md との関係**: README.md の API 設計セクションは機能一覧としての概要表記であり、スコープを省略した短縮形で記載されている。実装時は本規約に準拠し、すべてのエンドポイントに明示的なスコープ（`/me`, `/teams/{teamId}/...` 等）を付与すること。

## 6. イベント駆動設計
機能間の連携（例: 予約作成 → 通知送信、マッチング成立 → スケジュール登録）が多いため、Service 間の直接呼び出しによる密結合を避ける。

- **方針**: イベント発行を `DomainEventPublisher` インターフェースで抽象化し、初期実装は Spring の `ApplicationEvent` + `@TransactionalEventListener` を使用する。将来的な外部メッセージキュー（RabbitMQ/Kafka等）への移行に備える。
- **イベントクラス配置**:
    - `com.mannschaft.app.common.event/` には共通のマーカーインターフェース `DomainEvent` と基底クラス（`BaseEvent` 等）のみを配置する。
    - 各機能固有のイベントクラスは、**発行元の feature パッケージ内**に配置し、`DomainEvent` を実装する（例: `com.mannschaft.app.reservation.ReservationCreatedEvent`）。
- **適用基準**: 同一機能内の処理は Service 直接呼び出し、**異なる機能間の非同期連携**にイベントを使用する。
- **トランザクション境界**: イベントリスナーには `@TransactionalEventListener(phase = AFTER_COMMIT)` を使用し、**発行元のトランザクションが正常にコミットされた後にのみ実行**されるようにする。これにより、発行元がロールバックされたのにリスナーが動作する不整合を防止する。

```java
// com.mannschaft.app.common.event.DomainEvent（マーカーインターフェース）
public interface DomainEvent {
    LocalDateTime occurredAt();  // §20 日時統一規約に準拠（Instant は使用しない）
}

// com.mannschaft.app.common.DomainEventPublisher（抽象インターフェース）
public interface DomainEventPublisher {
    void publish(DomainEvent event);  // Object ではなく DomainEvent で型安全性を確保
}

// com.mannschaft.app.config.SpringEventPublisher（初期実装）
@Component
@RequiredArgsConstructor
public class SpringEventPublisher implements DomainEventPublisher {
    private final ApplicationEventPublisher applicationEventPublisher;
    @Override
    public void publish(DomainEvent event) {
        applicationEventPublisher.publishEvent(event);
    }
}

// 例: 予約作成時に通知を送信
// reservation パッケージ内にイベントクラスを配置
// com.mannschaft.app.reservation.ReservationCreatedEvent implements DomainEvent
domainEventPublisher.publish(new ReservationCreatedEvent(reservation));

// notification パッケージが購読（トランザクションコミット後に実行）
@TransactionalEventListener(phase = AFTER_COMMIT)
@Async
public void onReservationCreated(ReservationCreatedEvent event) {
    // プッシュ通知送信
}
```

- **非同期イベント失敗時の方針**: `@Async` リスナーで例外が発生した場合は、ログ出力（ERROR レベル）+ 監査ログ記録を必須とする。即時リトライは行わず、運用監視で検知・対応する。将来的にリトライ機構（Spring Retry / メッセージキューの DLQ 等）を導入する場合は、本セクションを更新すること。

## 7. 新モジュール追加ガイドライン
選択式モジュールを新規追加する際の手順:

1. **エラーコードプレフィックス**を定義する（例: `RESERVE`）
2. **Flyway マイグレーション**で `module_definitions` テーブルにレコード追加
3. **`module_level_availability`** でレベル別適用（組織/チーム/個人）を設定
4. **feature パッケージ**を新規作成（本ファイルの構成イメージに従う）
5. **テンプレートプリセット**への追加（必要に応じて `template_modules` を更新）
6. **ユニットテスト・統合テストの作成**
    - 新しいモジュール（Service, Controller等）を作成した際は、必ず対応するテストコードをセットで作成すること。
    - **テスト範囲**: ユニットテスト（境界値や例外系を含むビジネスロジックの検証）、統合テスト（DBアクセスや依存コンポーネントとの連携検証）。
    - **完了定義**: テストがすべてパスし、プロジェクトで規定されたカバレッジ基準を満たしていることを確認して完了とする。
7. **フロントエンド**: `pages/`, `components/`, `composables/` に対応するファイルを追加

## 8. データ保持・削除規約
- **個人情報の取り扱い**: 退会申請後 **30日間** を猶予期間（論理削除状態）とし、その後個人を特定できる情報（氏名、メールアドレス等）を物理削除する。
- **法的強制力のあるデータ**: 決済履歴や領収書データ等は、税法等の法令遵守のため、退会後も **7年間** 保持する。
- **データの匿名化**: 投稿内容や行動ログを統計的に利用する場合は、個人との紐付けを完全に遮断（アノニマイズ）した状態で保持する。
- **アカウント凍結時**: 規約違反等による凍結時は、再登録防止や法的対応のため、凍結解除または一定期間が経過するまで情報を保持し続ける。

## 9. サブスクリプション設計指針
- **DB構造の柔軟化**: `subscription_plans` テーブルに `plan_type` カラム（`FLAT` / `METERED`）を定義し、定額・従量の両方に対応可能なスキーマ設計を Phase 1 から検討する。
- **ビジネスロジックの分離**: 料金計算ロジックは将来の「従量課金」導入を見据え、特定の計算式に依存しないよう `BillingStrategy` 等で抽象化して実装する。
- **決定時期**: 具体的な課金ロジックの実装は Phase 8 までに確定させるが、DBマイグレーションのコストを最小化するため、器（テーブル構造）の準備は現段階で行う。

## 10. データベース命名規約
- **テーブル名**: 小文字の `snake_case` かつ **複数形** とする（例: `task_groups`）。
- **カラム名**: 小文字の `snake_case` とする（例: `due_date`）。
- **主キー**: 原則として `id`（Long/UUID）とする。
- **論理値 (Boolean)**: `is_` または `has_` で始める命名とする（例: `is_completed`）。
- **日時 (Timestamp)**: `created_at`, `updated_at`, `deleted_at` 等、`_at` を末尾に付与する。
- **日付 (Date)**: 日時を含まない場合は `_on` を末尾に付与する（例: `birthday_on`）。
- **外部キー**: `[相手先テーブルの単数形]_id` とする（例: `user_id`）。

## 11. エンティティ共通基底規約

### BaseEntity
すべての主要エンティティが継承する `@MappedSuperclass` を `com.mannschaft.app.common` に配置する。

```java
@MappedSuperclass
@Getter
public abstract class BaseEntity {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, updatable = false)
    private LocalDateTime createdAt;

    @Column(nullable = false)
    private LocalDateTime updatedAt;

    // 論理削除対象エンティティのみ deletedAt を追加（§14 参照）
    // BaseEntity には含めず、SoftDeletableEntity 等のサブクラスで拡張する

    @PrePersist
    protected void onCreate() {
        this.createdAt = LocalDateTime.now();
        this.updatedAt = this.createdAt;
    }

    @PreUpdate
    protected void onUpdate() {
        this.updatedAt = LocalDateTime.now();
    }
}
```

- ログ系テーブル（`audit_logs`, `notifications` 等）や中間テーブルは `BaseEntity` を継承せず、個別に定義してよい。
- 論理削除が必要なエンティティは `deletedAt` フィールドを個別に追加する（本ファイル §14 参照）。

## 12. ページネーション規約
- **標準方式**: オフセットベース。クエリパラメータは `?page=0&size=20&sort=createdAt,desc` を標準とする。
    - `page`: 0始まりのページ番号
    - `size`: 1ページあたりの件数（デフォルト20、最大100）

- **レスポンス**:
    - オフセットベース: `PagedResponse<T>` の `meta` フィールドで返す（§3.1 参照）。
    - カーソルベース: `CursorPagedResponse<T>` を使用する。

CursorPagedResponse<ChatMessageResponse> → {

    "meta": { "nextCursor": "msg_12345", "hasNext": true, "limit": 20 }
}

## 13. APIフィルタリング規約
- **基本形式**: フィルタリング条件は、対象フィールド名をそのままクエリパラメータのキーとして使用する（例: `?status=active`）。
- **範囲指定の命名**: 日付や数値の範囲検索には、フィールド名に接頭辞/接尾辞を付与する。
    - 開始: `_from` または `_min`（例: `?price_min=1000`）
    - 終了: `_to` または `_max`（例: `?price_max=5000`）
- **複数値（IN句）の指定**: 同一キーの複数指定（`?tags=java&tags=spring`）またはカンマ区切りを許容するよう実装を統一する。
- **部分一致（LIKE検索）**: 文字列検索で部分一致をサポートする場合は、パラメータ名に `_like` を付与する（例: `?title_like=keyword`）。

## 14. 論理削除規約
- **実装方式**: 論理削除が必要なテーブルには `deleted_at DATETIME NULL` カラムを追加する。`NULL` = 有効、値あり = 削除済み。`is_deleted` フラグ方式は使用しない。
- **適用テーブル**: 主要エンティティ（`users`, `teams`, `organizations`, `blog_posts`, `chat_messages` 等）に適用する。ログ系テーブル（`audit_logs`, `notifications`）や中間テーブルには原則適用しない。
- **自動フィルタリング**: Hibernate 6.4+ の `@SQLRestriction` を Entity に付与し、デフォルトクエリに `WHERE deleted_at IS NULL` を自動適用する。手動で毎クエリに条件を追加する方式は漏れやすいため禁止する:
```java
@Entity
@SQLRestriction("deleted_at IS NULL")
public class UserEntity extends BaseEntity {
    private LocalDateTime deletedAt;
    // ...
}
```
- **削除済みデータの取得**: 管理者機能で削除済みデータを含む検索が必要な場合は、`@SQLRestriction` を無効化するカスタムクエリ（ネイティブ SQL または `@Query` に `deleted_at` 条件を明示）を使用する。
- **物理削除**: 本ファイル §8「データ保持・削除規約」に定める猶予期間経過後に、バッチ処理で物理削除を実行する。

## 15. 非同期ジョブ実行規約
- **Virtual Threads（Java 21）**: Spring Boot 3.2+ の `spring.threads.virtual.enabled=true` を `application.yml` に設定し、Tomcat のリクエスト処理に Virtual Threads を使用する。これにより、大量の同時接続を少ないOSスレッドで効率的に処理できる。
- **基本方式**: `@Async` アノテーションを使用した Spring Boot 標準の非同期実行を採用する。`@EnableAsync` を `com.mannschaft.app.config.AsyncConfig` に付与してプール定義と合わせて管理する。
- **スレッドプール管理**: `ThreadPoolTaskExecutor` を適切に構成し、APIリクエスト用のスレッドを圧迫しないよう専用のプールを割り当てる。用途ごとにプールを分離し、長時間ジョブ（データエクスポート等）がイベントリスナー（通知送信等、§6 参照）を圧迫しないようにする。
    - **イベント用プール**: 軽量・短時間処理向け（例: `event-pool`）
    - **ジョブ用プール**: 重量・長時間処理向け（例: `job-pool`）
    - `@Async("event-pool")`, `@Async("job-pool")` のように明示的にプール名を指定すること。
- **状態管理**: ジョブの進捗状況（ステータス、完了率、生成ファイルURL等）は、`Valkey` または DB のジョブ管理テーブルで保持する。
- **拡張性**: 処理の肥大化や分散処理が必要になった段階で、Spring Batch や外部メッセージキュー（RabbitMQ/Kafka）への移行を検討する。

## 17. 開発フローの制約

### AI (Claude Code) 向けの制約（必須）
新しい機能の実装に取り掛かる際は、勝手にコードを書き始めず、必ず以下の手順を踏むこと：

1. **要件の確認とすり合わせ**: 実装する機能の詳細と、必要なテーブル定義（DDL）の案を提示し、ユーザーの承認を得ること。
2. **設計案の提示**: 機能パッケージ内のクラス構成や、APIのインターフェース案（エンドポイント名など）を提示すること。
3. **承認後の実装**: ユーザーから「Goサイン」が出た後に、初めて実際のコーディングを開始すること。

AIによる予期せぬ大規模な破壊的変更を防止し、設計の意図を正確に反映させるための制約。

### コーディングスタイルの原則（AI・人間共通）

本プロジェクトのコードは **実務経験3〜5年のプログラマが無理なく読めるレベル** を基準とする。
以下の原則をすべてのコーディング作業で遵守すること。

#### 原則1: 素直で標準的な書き方を選ぶ
- Java / TypeScript の **標準API・定番パターン** を優先して使う。ニッチなライブラリメソッドや最先端の言語機能よりも、広く知られた書き方を選ぶこと。
- **Stream・ラムダ式・インターフェースは積極的に使ってよい**。処理効率や可読性が向上する場面では for ループより Stream を優先する。ただし、`reduce` の多重ネストや `Collectors.teeing` のような使用頻度の低いメソッドは避け、`filter`, `map`, `collect`, `forEach` 等の定番オペレーションを中心に組み立てる。
- 例（TypeScript/Vue）: 高度な型パズル（Conditional Types のネスト、Template Literal Types の乱用）を避け、型が追いやすい素直な定義にする。
- **判断基準**: 「このコードを見た人が、ドキュメントやGitHub Copilotの補助なしで意味を理解できるか？」を常に自問する。

#### 原則2: コードで仕様の意図を語る
- 変数名・メソッド名・クラス名を **仕様書の用語と一致** させる。コードを読むだけで「この処理は仕様書のどの部分を実装しているか」が分かることを目指す。
- 略語は業界標準のもの（`id`, `url`, `dto` 等）に限定し、プロジェクト固有の略語は作らない。
- Boolean を返すメソッドは `is〜` / `has〜` / `can〜` で始め、条件の意味を名前だけで伝える。
- Enum の値名は仕様書の区分名をそのまま反映する。

#### 原則3: 複雑な箇所にはコメントを残す
以下に該当する箇所には **必ず日本語コメントを記載** すること:
- **ビジネスルールの分岐**: なぜその条件で分岐するのか（Why）を説明する。
  ```java
  // 安否確認は「全員回答済み」で自動クローズするが、
  // 24時間経過しても未回答者がいる場合は管理者にリマインド通知を送る
  if (response.allAnswered()) {
      safetyCheck.autoClose();
  } else if (safetyCheck.isOverdue()) {
      notifyAdminReminder(safetyCheck);
  }
  ```
- **複数テーブルを跨ぐクエリや集計ロジック**: 何のデータをどう結合しているかの全体像。
- **パフォーマンス上の理由で直感的でない書き方をしている箇所**: なぜこの書き方を選んだか。
- **外部サービス連携の前提条件や制約**: API仕様のバージョンや制限値。
- ただし、**コードを読めば自明なこと**にはコメントを付けない（`// ユーザーを取得する` のような無意味なコメントは禁止）。

#### 原則4: メソッドの構造を予測可能にする
- メソッドの冒頭で **バリデーション → データ取得 → ビジネスロジック → 結果返却** の流れを一貫させる。
- 1つのメソッドが1つの仕事だけをする。読み手が「このメソッドは何をするか」をメソッド名だけで理解でき、中身を読んで裏切られないこと。
- 途中で処理の目的が変わる場合はメソッドを分割する。

### 人間（開発者）向けの運用
- 軽微なバグ修正、リファクタリング、ドキュメント更新については、事前の設計承認をスキップして直接実装・コミットすることを許可する。
- 大規模な機能追加や、既存のデータスキーマ・アーキテクチャに影響を与える変更については、AI同様に設計案の合意を経てから進める。

## 18. Flyway マイグレーション SQL スタイル規約

### ファイル命名規則（全体最大 major + 1 × タイムスタンプ方式）

ファイル命名は `V{major}.{yyyyMMddHHmmss}__{説明}.sql`。

**採番ルール（正典）**:

1. **major は「origin/main 全体の最大 major + 1」を使う**（V82, V83, V84 … と実践済み）。
   - 新規ファイルがリポジトリ内のすべての既存ファイルの後にソートされることが保証され、
     `out-of-order: true` への依存をゼロにできる。
   - PR 作成前に `origin/main` の最大 major を確認し、他 PR と被る場合はリネームする。
2. **同一 major 内の並行 PR 衝突は minor（タイムスタンプ）で回避する**。
   - 同じ major を持つ 2 ファイルが同時に作られても、起動時刻が異なれば `yyyyMMddHHmmss` は衝突しない。

**形式と例**:
```
V84.20260526143022__add_user_profile.sql
```
（V84 がそのとき origin/main の最大 major であった場合）

**タイムスタンプの取得**:
```bash
# bash / WSL2
date -u '+%Y%m%d%H%M%S'

# PowerShell (Windows)
Get-Date -Format 'yyyyMMddHHmmss'
```

**⚠ よくある誤り（Flyway ソート順の罠）**:
Flyway は `V{major}.{minor}` の major と minor をそれぞれ**数値として比較**する。
`V9.20260603120000` の major は `9` であり、`V10`〜`V84` のすべてより**前**にソートされる。
「タイムスタンプ minor は連番 minor より大きいから後に実行される」という理解は
**同一 major 内でのみ正しい**。異なる major をまたぐ場合は major の大小が優先される。
→ 上記採番ルール（全体最大 major + 1）を守れば、この問題は発生しない。

**既存ファイルについて**: 既存の `V{phase}.{連番}__*.sql` ファイルは変更しない。
`out-of-order: true` は既存環境互換のため現状維持だが、上記採番を守れば新規ファイルは
out-of-order に依存しない（常に末尾に追加されるため）。

**番人テスト**: `FlywayFromScratchMigrationTest` がゼロ状態からすべての migration を順に適用し、
ソート順逆転やファイル破損を検知する。新規 migration 追加後は必ず CI で通過を確認すること。

**命名の機械的強制（2026-07-07〜）**: V137〜V143 系列で連番 minor（`.001` 等）が規約を逸脱して
積み上がり、並行 PR が同時に `V141.001` を名乗って main が起動不能になる事故（2026-07-07）が発生した。
これを受け、番人テスト `FlywayTimestampNamingGuardTest`（`common/architecture`）が、
凍結リスト（`FlywayLegacyMigrationBaseline` にハードコードされた既存 migration 全件）**外**の
新規ファイルについて連番 minor をビルドで機械的に拒否し（`V{major}.{yyyyMMddHHmmss}` 形式必須）、
あわせて全ファイルのバージョン重複（V141.001 二重と同型）も検知して fail させる。
既存ファイルはリネームせず凍結免除とする（凍結リストへの追記は禁止）。

SQL の書き方を以下に統一する。

### 基本スタイル
- **キーワードは大文字**: `CREATE TABLE`, `ALTER TABLE`, `NOT NULL`, `DEFAULT`, `FOREIGN KEY` 等
- **テーブル名・カラム名は小文字 snake_case**（§10 DB命名規約と統一）
- **1ファイル = 1つの論理的変更**: テーブル1つの作成、または関連する ALTER のまとめ

### コメント
- テーブル作成時は冒頭に作成意図のコメントを記載する:
```sql
-- 掲示板のスレッドを管理するテーブル
CREATE TABLE bulletin_threads (
    ...
);
```
- DELETE / DROP / ALTER TABLE ... DROP COLUMN を含む破壊的マイグレーションはファイル冒頭に警告を記載する:
```sql
-- ⚠ 破壊的変更: teams.organization_id を削除し team_org_memberships へ移行
ALTER TABLE teams DROP COLUMN organization_id;
```

### 制約・インデックスの命名
- **外部キー制約**: `fk_{テーブル名}_{参照先テーブル名}` 形式で明示的に名前を付ける:
```sql
CONSTRAINT fk_bulletin_threads_team
    FOREIGN KEY (team_id) REFERENCES teams(id)
```
- **インデックス**: `idx_{テーブル名}_{カラム名}` 形式:
```sql
CREATE INDEX idx_bulletin_threads_team_id_created_at
    ON bulletin_threads(team_id, created_at);
```
- **ユニーク制約**: `uq_{テーブル名}_{カラム名}` 形式

### 禁止事項
- `IF NOT EXISTS` は付けない（Flyway がバージョン管理するため二重実行は起きない。付けるとミスの検知が遅れる）
- `IF EXISTS`（DROP 時）も同様に禁止。存在しないオブジェクトの DROP はマイグレーション設計のミスであり、明示的にエラーにすべき

### Entity に列を足したら migration も必ず足す（番人あり）

テスト環境は `spring.jpa.hibernate.ddl-auto=create` + `flyway.enabled=false` で
**Entity からスキーマを生成する**ため、「Entity にフィールドを足したが migration を書き忘れた」乖離は
通常のテストでは原理的に検出できない。Flyway で構築した環境（本番・staging・新規開発環境）だけが
`Unknown column` で当該ドメインの API 全滅という形で壊れる
（実例: `queue_tickets.guest_phone` が 4 ヶ月間放置された）。

これを機械的に防ぐため、`FlywayFromScratchMigrationTest` に
**「全 Entity のマッピング列が Flyway 実スキーマに存在すること」の番人テスト**を置いている。
Hibernate 自身が構築した `Metadata`（Spring Boot と同じ命名戦略を適用した権威ある物理名）と、
Flyway 適用後の JDBC メタデータを突き合わせる。

- Flyway 実スキーマを要する番人テストは**このクラスに相乗りさせる**こと。
  新クラスを作ると MySQL コンテナが 1 個増え、CI の壁時計を直撃する。
- `KNOWN_UNPAID_DRIFT`（既知の未返済ドリフト台帳・凍結時点 38 列）は**増やしてはならない**。
  返済のたびに行を削り、最終的に空にする。
- 見落としやすい罠として、**`BaseEntity` 由来の `created_at` / `updated_at` を
  `CREATE TABLE` が作っていない**ケースが 17 件あった。新規テーブルでは必ず両方を作ること。
- 命名戦略の罠に注意: Spring の `CamelCaseToUnderscoresNamingStrategy` は
  「小文字の直後の大文字」でのみ `_` を挿入する。`s3Key` → `s3key`、`positionX` → `positionx` となり
  `s3_key` / `position_x` にはならない。この形のフィールドは `@Column(name = "...")` を明示すること。

## 19. DTO 粒度ルール

### Request（リクエスト）
- **Create と Update は原則として分ける**:
    - `Create[Feature]Request` → 作成時の必須フィールドのみ（例: email, password, name）
    - `Update[Feature]Request` → 変更可能フィールドのみ（例: name, displayName）
- **理由**: バリデーションルールが異なるため、共用すると `@NotBlank` と nullable が混在して複雑になる

### Response（レスポンス）
- **一覧用と詳細用を分ける**:
    - `[Feature]SummaryResponse` → 一覧表示に必要な最小限（id, name, avatarUrl 等）
    - `[Feature]DetailResponse` → 詳細画面用（全フィールド + リレーション情報）
    - `[Feature]Response` → 上記の区別が不要な場合（小さいエンティティ）

### 共通ルール
- DTO は feature パッケージ内の `dto/` サブパッケージに配置する
- **エンティティを直接レスポンスに返すことは禁止**（必ず DTO に変換する）
- DTO のフィールドは不変（`final` + `@Getter`、`@Setter` なし）とする（`BACKEND_CODING_CONVENTION.md` §1 Lombok 規約と統一）
- ネストが必要な場合は Inner class ではなく別ファイルに切り出す

## 20. 日時の扱い統一

### DB（MySQL 8.0）
- 日時カラムは **`DATETIME`** を使用する。`TIMESTAMP` は使わない（2038年問題 + MySQL の暗黙タイムゾーン変換を避けるため）
- 保存する値は **日本時間（JST / Asia/Tokyo）** で統一する
    - 国内向けサービスのため UTC 変換のコストを避ける
    - 将来の多国展開時は UTC 化マイグレーションを検討する
- 日付のみのカラムは `DATE` 型を使用する

### Java（Spring Boot）
- エンティティの日時フィールドは **`LocalDateTime`** を使用する（BaseEntity と統一）
- タイムゾーン変換が必要な場合のみ `ZonedDateTime` を使用する
- `Instant` は使わない（DB との変換が煩雑になるため）
- JVM のデフォルトタイムゾーンを起動時に `Asia/Tokyo` に設定する（`com.mannschaft.app.config` に配置）:
```java
@Configuration
public class TimeZoneConfig {
    @PostConstruct
    public void initTimeZone() {
        TimeZone.setDefault(TimeZone.getTimeZone("Asia/Tokyo"));
    }
}
```
- **Jackson の日時直列化**: `LocalDateTime` がデフォルトで配列（`[2026,3,18,21,0,0]`）として出力されるのを防ぐため、以下を `application.yml` に設定する:
```yaml
spring:
  jackson:
    serialization:
      write-dates-as-timestamps: false  # ISO 8601 文字列で出力
```
- または `JavaTimeModule` を明示的に登録する（Spring Boot は `jackson-datatype-jsr310` が依存にあれば自動登録するが、上記設定は必須）

### フロントエンド（TypeScript / Nuxt 3）
- API レスポンスの日時は **ISO 8601 文字列**で受け取る: `"2026-03-13T21:00:00"`（タイムゾーンオフセットなし = JST 前提）
- 表示時の日時フォーマットは **dayjs** で統一する（プロジェクト内で1つのライブラリに絞る）

## 22. 楽観的ロック（Optimistic Locking）

複数ユーザーが同時に同じデータを編集する可能性がある主要エンティティには、楽観的ロックを適用する。

### 実装方式
- JPA の `@Version` アノテーションを使用する。対象エンティティに `version` カラムを追加する:
```java
@Version
private Long version;
```
- DB 側のカラム定義:
```sql
version BIGINT NOT NULL DEFAULT 0
```

### 適用対象
以下のように「複数ユーザーが同時編集しうるデータ」に適用する:
- **適用する**: `schedules`, `bulletin_threads`, `bulletin_replies`, `blog_posts`, `teams`, `organizations`, `user_profiles`, `service_records` 等の主要業務データ
- **適用しない**: `audit_logs`, `notifications`, `login_histories` 等のログ系テーブル、`user_roles` 等の中間テーブル、カウンタ系カラム（`member_count` 等、アトミック更新で制御するもの）

### 競合時のハンドリング
- Spring Data JPA が `ObjectOptimisticLockingFailureException`（JPA の `OptimisticLockException` をラップした Spring 例外）をスローするので、`GlobalExceptionHandler` でキャッチして **409 Conflict** を返す:
```java
// GlobalExceptionHandler に追加
@ExceptionHandler(ObjectOptimisticLockingFailureException.class)
public ResponseEntity<ErrorResponse> handleOptimisticLock(ObjectOptimisticLockingFailureException ex) {
    ErrorResponse error = ErrorResponse.of(CommonErrorCode.COMMON_003);
    return ResponseEntity.status(HttpStatus.CONFLICT).body(error);
}
```
- エラーコード: `COMMON_003`（「他のユーザーがデータを更新しました。最新の内容を確認して再度お試しください」）
- フロントエンドは 409 を受け取った場合、最新データを再取得してユーザーに差分を提示する

### API での version の受け渡し
- **Response**: 全ての詳細レスポンスに `version` フィールドを含める
- **Request**: Update 系リクエストに `version` フィールドを必須とする
```java
public class UpdateBulletinThreadRequest {
    @NotNull
    private Long version;  // 取得時の version をそのまま返す
    // ... 他のフィールド
}
```

## 23. Enum の DB 保存方式

### ルール
- **`@Enumerated(EnumType.STRING)` を必須とする**。`ORDINAL`（数値保存）は禁止する
```java
@Enumerated(EnumType.STRING)
@Column(nullable = false)
private RoleType roleType;  // DB には "ADMIN", "MEMBER" 等の文字列で保存
```

### 理由
- `ORDINAL` は Enum の定義順序に依存するため、途中に値を追加すると既存データの意味が変わる致命的バグになる
- `STRING` なら Enum の順序変更・追加が安全。DB を直接見たときも値が分かりやすい

### DB 側のカラム定義
- MySQL の `ENUM` 型は使わない。**`VARCHAR`** で定義する:
```sql
role_type VARCHAR(30) NOT NULL  -- "ADMIN", "MEMBER", "GUEST" 等
```
- 理由: MySQL の `ENUM` 型は値の追加に `ALTER TABLE` が必要で、Flyway マイグレーションが煩雑になる。`VARCHAR` なら Java 側の Enum に値を追加するだけで済む

### CHECK 制約（任意）
- 値の整合性を DB 側でも担保したい場合は CHECK 制約を付与する:
```sql
role_type VARCHAR(30) NOT NULL,
CONSTRAINT chk_user_roles_role_type
    CHECK (role_type IN ('SYSTEM_ADMIN', 'ADMIN', 'DEPUTY_ADMIN', 'MEMBER', 'SUPPORTER', 'GUEST'))
```

## 24. Valkey キー命名規約・TTL 方針

### キー命名フォーマット
```
mannschaft:{用途}:{スコープ}:{識別子}
```

| 用途 | キーパターン | 例 | TTL |
|------|-------------|-----|-----|
| JWTブラックリスト | `mannschaft:auth:blacklist:{jti}` | `mannschaft:auth:blacklist:abc123` | Access Token の残存有効期限 |
| Refresh Token | `mannschaft:auth:refresh:{userId}:{deviceId}` | `mannschaft:auth:refresh:42:mobile` | 7日 |
| レートリミット | `mannschaft:rate:{endpoint}:{ip}` | `mannschaft:rate:login:192.168.1.1` | 1分 or 1日（エンドポイントによる） |
| キャッシュ（ユーザー） | `mannschaft:cache:user:{userId}` | `mannschaft:cache:user:42` | 30分 |
| キャッシュ（チーム） | `mannschaft:cache:team:{teamId}` | `mannschaft:cache:team:7` | 30分 |
| キャッシュ（モジュール定義） | `mannschaft:cache:modules` | — | 1時間（更新頻度が低い） |
| WebSocket セッション | `mannschaft:ws:session:{sessionId}` | `mannschaft:ws:session:sess_xyz` | 接続中のみ（切断時に削除） |
| 非同期ジョブ進捗 | `mannschaft:job:{jobType}:{jobId}` | `mannschaft:job:export:job_456` | 24時間 |

### ルール
- キーの区切りは **コロン（`:`）** を使う（Redis 互換の慣例、`valkey-cli` でのキースペース分析に対応）
- **全て小文字**で統一する
- TTL は必ず設定する（TTL なしのキーが蓄積するとメモリリークになる）
- キャッシュの無効化はデータ更新時に明示的に `DELETE` する（TTL 切れに頼らない）。Service の CUD メソッド内で対応するキャッシュを削除すること

### Spring Boot での設定
```java
// RedisConfig.java に TTL のデフォルト値を定義
@Bean
public RedisCacheConfiguration cacheConfiguration() {
    return RedisCacheConfiguration.defaultCacheConfig()
        .entryTtl(Duration.ofMinutes(30))  // デフォルト TTL
        .serializeValuesWith(
            SerializationPair.fromSerializer(new GenericJackson2JsonRedisSerializer())
        );
}
```

## 25. API の HTTP ステータスコード使い分け

### 成功系

| ステータス | 使用場面 | 例 |
|-----------|---------|-----|
| **200 OK** | データの取得・更新が成功 | `GET /users/me`, `PATCH /users/me` |
| **201 Created** | 新しいリソースの作成が成功 | `POST /teams` |
| **204 No Content** | 削除が成功（レスポンスボディなし） | `DELETE /teams/{id}` |

### エラー系

| ステータス | 使用場面 | エラーコード例 |
|-----------|---------|--------------|
| **400 Bad Request** | バリデーションエラー、リクエスト形式不正 | `COMMON_001` |
| **401 Unauthorized** | 認証失敗、トークン無効・期限切れ | `AUTH_001`, `AUTH_002` |
| **403 Forbidden** | 認証済みだが権限不足 | `COMMON_002` |
| **404 Not Found** | 指定リソースが存在しない | `{FEATURE}_001` 等 |
| **409 Conflict** | 楽観的ロック競合、一意制約違反 | `COMMON_003` |
| **429 Too Many Requests** | レートリミット超過 | — （`Retry-After` ヘッダーを付与） |
| **500 Internal Server Error** | 予期しないシステムエラー | `COMMON_999` |
| **503 Service Unavailable** | 未実装機能へのアクセス（フィーチャーフラグ OFF） | — |

### ルール
- **更新（PATCH/PUT）は 200** + 更新後のリソースをレスポンスボディに含める
- **作成（POST）は 201** + 作成されたリソースをレスポンスボディに含め、`Location` ヘッダーに新リソースの URI を設定する
- **削除（DELETE）は 204** + レスポンスボディは空。ただし**論理削除**の場合は **200 OK** + `deleted_at` 等の情報をレスポンスボディに含めてよい（クライアント側で削除日時の確認・表示に利用するため）
- **一覧取得で結果が0件の場合は 200** + 空配列（404 にしない）

## 26. ファイルアップロードフロー（Pre-signed URL）

フロントエンド → バックエンド → S3 の3者間のシーケンスを以下に統一する。

### アップロードフロー（3ステップ）
```
1. [Frontend] → POST /api/v1/{feature}/upload-url
   Request:  { "fileName": "report.pdf", "contentType": "application/pdf", "fileSize": 2048000 }
   Response: { "data": { "uploadUrl": "https://s3...", "fileKey": "uploads/teams/7/abc123.pdf", "expiresIn": 600 } }

2. [Frontend] → PUT {uploadUrl}  (S3に直接アップロード)
   Headers:  Content-Type: application/pdf
   Body:     <ファイルバイナリ>

3. [Frontend] → POST /api/v1/{feature}  or  PATCH /api/v1/{feature}/{id}
   Request:  { "title": "月次報告", "attachmentKey": "uploads/teams/7/abc123.pdf", ... }
   ※ バックエンドは fileKey の存在を S3 に確認してからDBに保存する
```

### バックエンド側の処理
- **ステップ1（URL発行）**:
    - `contentType` のホワイトリスト検証（許可: `image/jpeg`, `image/png`, `image/webp`, `application/pdf` 等。機能ごとに定義）
    - `fileSize` の上限チェック（機能ごとの上限。例: 掲示板添付は 6MB）
    - `fileKey` はUUIDベースで生成し、推測不可能にする: `uploads/{feature}/{scopeId}/{uuid}.{ext}`
    - Pre-signed URL の有効期限は **10分**（§ストレージ規約の5〜15分に準拠）
- **ステップ3（リソース登録）**:
    - `fileKey` が S3 に実在するかを `HeadObject` で確認する（偽のキーでの登録を防止）
    - 確認後に DB にレコードを保存する

### ダウンロードフロー
```
1. [Frontend] → GET /api/v1/{feature}/{id}/download-url
   Response: { "data": { "downloadUrl": "https://s3...", "expiresIn": 300 } }

2. [Frontend] → GET {downloadUrl}  (S3から直接ダウンロード)
```
- ダウンロード用 Pre-signed URL の有効期限は **5分**
- アクセス権限チェックはステップ1でバックエンドが行う（S3 は URL を知っていれば誰でもアクセス可能なため）

### 未使用ファイルの清掃
- ステップ1で URL を発行したがステップ3が行われなかったファイル（孤立ファイル）は、日次バッチで `uploads/` 配下を走査し、DBに紐付かないファイルを削除する
- バッチ対象: アップロードから **24時間** 経過 かつ DB 未登録のファイル

## 27. 構造化ログフォーマット

### 方針
- 本番環境では **JSON 形式** で出力する（ログ集約基盤での検索・フィルタリングに対応）
- 開発環境では **人間が読みやすいテキスト形式** で出力する

### logback-spring.xml（完全な設定例）
Logback の `logstash-logback-encoder` を使用する。appender と `<root>` を必ずセットで定義すること（appender だけでは出力されない）:
```xml
<!-- logback-spring.xml -->
<configuration>
    <springProfile name="prod">
        <appender name="JSON" class="ch.qos.logback.core.ConsoleAppender">
            <encoder class="net.logstash.logback.encoder.LogstashEncoder">
                <includeMdcKeyName>userId</includeMdcKeyName>
                <includeMdcKeyName>requestId</includeMdcKeyName>
                <includeMdcKeyName>traceId</includeMdcKeyName>
            </encoder>
        </appender>
        <root level="INFO">
            <appender-ref ref="JSON" />
        </root>
    </springProfile>

    <springProfile name="local">
        <appender name="CONSOLE" class="ch.qos.logback.core.ConsoleAppender">
            <encoder>
                <pattern>%d{HH:mm:ss.SSS} [%thread] %-5level %logger{36} - %msg%n</pattern>
            </encoder>
        </appender>
        <root level="DEBUG">
            <appender-ref ref="CONSOLE" />
        </root>
    </springProfile>

    <!-- テスト実行時にもログを出力する（@ActiveProfiles("test") 対応） -->
    <springProfile name="test">
        <appender name="CONSOLE_TEST" class="ch.qos.logback.core.ConsoleAppender">
            <encoder>
                <pattern>%d{HH:mm:ss.SSS} [%thread] %-5level %logger{36} - %msg%n</pattern>
            </encoder>
        </appender>
        <root level="WARN">
            <appender-ref ref="CONSOLE_TEST" />
        </root>
    </springProfile>
</configuration>
```

出力例（本番 JSON）:
```json
{
  "timestamp": "2026-03-13T21:00:00.123+09:00",
  "level": "INFO",
  "logger": "com.mannschaft.app.auth.AuthService",
  "message": "ユーザー認証成功 userId=42",
  "userId": "42",
  "requestId": "req_abc123",
  "traceId": "trace_xyz789"
}
```

### MDC（Mapped Diagnostic Context）の活用
全リクエストに以下の情報を MDC に設定し、ログに自動付与する:
- **`requestId`**: リクエストごとに UUID を生成（`X-Request-Id` ヘッダーがあればそれを使用）。`OncePerRequestFilter` で設定する。
- **`userId`**: 認証済みユーザーの ID（未認証時は `anonymous`）。**Spring Security の認証処理完了後**に設定するため、`RequestLoggingFilter` ではなく Spring Security フィルターチェーン内（`SecurityContextHolder` から取得）で別途設定する。
- **`traceId`**: 将来の分散トレーシング対応用（現時点では `requestId` と同値でよい）

```java
// RequestLoggingFilter.java（com.mannschaft.app.config に配置）
// requestId と traceId を設定する。userId は Spring Security 認証後に別途設定。
@Component
public class RequestLoggingFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                     HttpServletResponse response,
                                     FilterChain chain) throws ServletException, IOException {
        String requestId = Optional.ofNullable(request.getHeader("X-Request-Id"))
            .orElse(UUID.randomUUID().toString());
        MDC.put("requestId", requestId);
        MDC.put("traceId", requestId);
        try {
            chain.doFilter(request, response);
        } finally {
            MDC.clear();
        }
    }
}

// JwtAuthenticationFilter 等の認証フィルター内で userId を設定する:
// MDC.put("userId", String.valueOf(authenticatedUserId));
// 未認証の場合: MDC.put("userId", "anonymous");
```

## 28. チーム運用規約（マスター・殿様・家老・足軽モデル）

Claude Code のエージェント機能を活用し、四層ピラミッド型の自律チームで開発を進める。
報告は **時代劇口調** で統一し、楽しく状況を共有する。

### 28.1 役割定義

| 役職 | 正体 | 権限 | 禁止事項 |
|------|------|------|----------|
| **マスター（天上人）** | ユーザー（人間） | 大方針の決定、最終承認、コミット・プッシュの許可 | — |
| **殿様（PM）** | メインClaude セッション | マスターの意を汲み自律的に采配。軍議の主催、家老への指示、戦果のとりまとめ、マスターへの上奏 | マスターの承認なきコミット・プッシュ |
| **家老（リーダー）** | `Plan` / `Explore` サブエージェント | フェーズ設計、タスク分解、コードレビュー（検分）、足軽の監督 | 殿様の許可なき設計変更 |
| **足軽（コーダー）** | `Agent(worktree)` サブエージェント | 個別タスクのコーディング、テスト作成 | 設計判断、他の足軽の担当領域への変更 |

### 28.2 指揮系統

```
マスター（ユーザー / 天上人）
  │  天の声を下す（「Phase 1 を始めよ」「この方針で進めよ」）
  ▼
殿様（メインClaude / PM）
  │  マスターの御意を解釈し、自律的に采配
  │  判断に迷う事項・重大な分岐のみマスターにお伺い
  ▼
家老（Plan / Explore）
  │  軍議（設計）→ 陣立て（タスク分解）→ 殿様に上申
  │  殿様の御下知を得てから出陣
  ▼
足軽A (worktree)  足軽B (worktree)  足軽C (worktree)
  Entity/Repo       Service/Config     Controller/DTO
  │                 │                  │
  └─────── 各自の成果を家老に報告 ───────┘
                    │
              家老が検分（レビュー）→ 殿様に報告
                    │
              殿様がまとめてマスターに上奏 → 御裁可 → コミット
```

### 28.3 殿様の自律判断基準

殿様はマスターに逐一お伺いを立てず、以下の基準で自律的に判断する:

#### 殿様が独断で決めてよいこと（裁量範囲）
- 家老への軍議指示、タスク分解の承認
- 足軽の起動順序・並列度の調整
- 軽微なコーディング判断（命名のブレ、import順序等）
- 検分で見つけた軽微な問題の修正指示
- 差し戻し・再実装の指示

#### マスターにお伺いを立てるべきこと（上奏事項）
- フェーズ着手の開始承認（「Phase N に進軍してよろしいか」）
- 仕様書に矛盾・曖昧さがあり判断が分かれる場合
- 設計方針の重大な分岐（2つ以上の選択肢がありトレードオフがある場合）
- 想定外のエラーや技術的障壁で進軍不能になった場合
- 完成した成果物のコミット・プッシュ（最終御裁可）
- `.claudecode.md` や仕様書への変更が必要な場合

### 28.4 ワークフロー（御触書）

#### 第一の儀：軍議（設計フェーズ） — `/軍議`
1. 殿様がマスターから対象フェーズの指示を受ける
2. 殿様が家老に偵察・設計を命ずる
3. 家老が仕様書（`docs/features/` + `README.md`）を精査し、陣立て書を殿様に上申
4. 殿様が陣立て書を精査・調整し、マスターに上奏
5. マスターの「よきにはからえ」（御裁可）を待つ

#### 試練（テスト先行フェーズ） — `/試練`
軍議で定めた受け入れ条件から**失敗するテスト（red）を実装より先に作成**する（BEドメインUT・API契約テスト、`/試練`）。出陣はこの red を green 化する形で行う。詳細は CLAUDE.md『大名システム活用ルール』の実行フローを正とする。

#### 第二の儀：出陣（実装フェーズ） — `/出陣`
1. 殿様が家老に出陣を命ずる
2. 家老が足軽を `Agent(worktree)` で並列起動
3. 各足軽は担当範囲のみを実装（越権禁止）
4. 足軽は完了時に家老へ **戦果報告** を行う
5. 依存関係がある場合は家老が順序を制御
6. 殿様はマスターに中間報告（長時間の場合）

#### 第三の儀：検分（レビューフェーズ） — `/検分`
1. 家老が全足軽の成果物を検分し、殿様に報告
2. 殿様が検分結果を精査
3. 問題があれば殿様の判断で差し戻し（「やり直しじゃ！」）
4. 合格なら殿様がマスターに **戦果上奏** を行う
5. マスターの御裁可 → コミット

### 28.6 品質ゲート（検分基準）

家老は以下の基準で足軽の成果を検分する。殿様は家老の検分結果を最終確認する。

| 検分項目 | 基準 | 不合格時 | 判断者 |
|----------|------|----------|--------|
| コンパイル | エラーなし | 即差し戻し | 家老 |
| コーディング規約 | `.claudecode.md` + CONVENTION.md 準拠 | 修正指示 | 家老 |
| テスト | 対応するテストが存在し、全パス | テスト追加を命ずる | 家老 |
| 設計逸脱 | 家老の陣立て書どおりか | 越権部分を削除 | 殿様 |
| セキュリティ | OWASP Top 10 の穴なし | 即差し戻し | 殿様 |
| 仕様整合性 | 仕様書との矛盾なし | マスターに上奏 | 殿様 |

### 28.7 worktree 運用ルール

- 各足軽は `isolation: "worktree"` で起動し、独立したコピーで作業する
- 足軽間の依存がある場合は、家老が **順次起動**（先行足軽の完了を待って次を起動）
- 足軽の作業が完了したら、家老がdiffを確認し、問題なければ殿様に報告
- コンフリクトが発生した場合は家老が調停する（足軽同士で直接やり取りしない）
- 殿様がマスターの御裁可を得た後に、メインブランチへ取り込む

### 28.8 エスカレーション規約

| 状況 | 対応 | エスカレーション先 |
|------|------|-------------------|
| 足軽が設計判断に迷う | 家老に伺いを立てる | 家老 |
| 家老が設計の選択肢に迷う | 殿様に上申し判断を仰ぐ | 殿様 |
| 殿様が仕様の矛盾を発見 | マスターに上奏し御裁可を仰ぐ | マスター |
| 想定外のエラーで進軍不能 | 家老→殿様→マスターの順で報告 | マスター |
| 足軽のworktreeでコンフリクト | 家老が調停 | 家老 |
| `.claudecode.md` や仕様書の変更が必要 | 殿様がマスターに変更案を上奏 | マスター |

### 28.9 Dynamic Workflows 連携（出陣・検分の決定論ファンアウト）

**注**: Workflow ツールが提供されない環境・モデル世代では本節は適用せず、従来の対話フロー（§28.1〜28.4）に従う。

`/出陣`・`/検分` は **Dynamic Workflows（Workflow ツール）** で「足軽の並列起動」を決定論的に表現できる。
役割・承認ゲートは §28.1〜28.4 のまま維持し、フェーズの**中身**だけ Workflow に差し替える。

| 原則 | 内容 |
|------|------|
| **軍議は対話のまま** | Workflow は起動後に停止できず自走するため、`マスター御裁可` ゲートを内包できない。軍議・早馬は従来どおり対話で行う |
| **承認ゲートは Workflow の外** | `軍議→裁可→[出陣WF]→[検分WF]→裁可→コミット`。1本の Workflow に複数の御裁可を詰めない |
| **モデル/effort をスクリプトで固定** | 機械的な足軽は `model:'sonnet'/'haiku', effort:'low'`、難所と敵対的検証だけ `model:'opus', effort:'high'`（`feedback_model_routing`）。これは**コスト削減**であってトークン削減ではない |
| **worktree 隔離は必須のまま** | 足軽は `agent(..., {isolation:'worktree'})`。CWD 確認・本陣不可侵の掟は Workflow 化後も足軽プロンプトに明記する |
| **コミット/マージは Workflow 内禁止** | 御裁可後に殿が `gh` で行う（本陣 git 禁止フック・gh のみ運用を維持） |

設計詳細・参考スクリプト骨格: [`docs/development/daimyo_workflow_migration.md`](../docs/development/daimyo_workflow_migration.md)。
**Workflow はオプトイン機能**であり、スキル（`/出陣`・`/検分`）経由かマスターの明示依頼時のみ起動する。

## 30. アーキテクチャ番人テスト（ArchUnit FreezingArchRule）

`com.mannschaft.app.common.architecture` パッケージには、ドメイン境界・DB設計・認可の原則
（本ドキュメント冒頭のアーキテクチャ思想 / 認可根治戦役）を機械的に強制する ArchUnit テストが
配置されている。代表例:

| テスト | 検査内容 | 凍結ストア UUID |
|---|---|---|
| `AuthzControllerGuardArchTest` | 公開Controllerエンドポイントの認可シグナル有無（認可根治戦役 Wave4） | `9ed4737d-c74f-4374-923e-4663d3c9e256` |
| `CrossDomainEntityImportArchTest` | クロスドメイン Entity 直接参照禁止（D-1） | `584c3a46-b9c1-4cc2-bf74-e0a18eab1bef` |
| `CrossDomainTransactionalArchTest` | 越境 `@Transactional` 禁止（D-3） | `f14374b1-655e-4df2-8e82-2d79c8df9174` |
| `EntityUuidV7ConventionArchTest` | 新規テーブルの `UuidV7Entity` 継承（D-2b） | `2c0ba995-682e-4f80-a5a5-f68c835b720d` |
| `CrossDomainRepositoryDependencyArchTest` | 越境 Repository 依存禁止（D-5。D-3 の `@Transactional` 前提を外した一般化） | `427c445d-37ce-4d6e-b095-a1733efe209f` |
| `ControllerEntityResponseArchTest` | Controller の JPA Entity レスポンス禁止（D-6。戻り型のジェネリクス入れ子まで走査） | **ストア無し（恒久ルール・違反0件運用）** |

D-6 を除き `FreezingArchRule`（`freeze.refreeze=false`）で運用しており、既存の未解消違反は
`backend/src/test/resources/archunit_store/` 配下に凍結（免責）し、**新規に追加される違反のみ**
fail させる方式を採る。D-6 は導入時点で違反0件のため凍結を持たない素の ArchRule であり、
違反が1件でも出たら即 fail する（偽陰性ゼロ証明のメタテストは
`ControllerEntityResponseConditionTest` ＋ `fixtures/D6*`）。

### ⚠️ 凍結ストアは `--tests` 絞り込み実行で破壊される

`./gradlew test --tests "SomeOtherTest"` のようにテストクラスを絞り込んで実行すると、
対象の ArchUnit テストが走らない（または解析対象が絞られる）ため、`FreezingArchRule` が
「今回検出されなかった違反」をストアから誤って削除して書き戻してしまう事故が過去に複数回
発生した。免責リストから違反が消えるのは一見「改善」に見えるが、実態は**解消されていない
認可の穴・アーキテクチャ違反が番人の監視対象から静かに脱落する**という重大な後退である。

**対策**:
1. **ArchUnit 番人テストを含むテストクラスを `--tests` で絞り込んではならない**。動作確認が
   必要な場合は必ずフルの `./gradlew test`（時間がかかる場合は `./gradlew compileTestJava` に
   留め、実行自体は CI に委ねる）を使うこと。
2. 上記事故を機械的に検知する番人 `ArchUnitFreezeStoreIntegrityTest`
   （`common/architecture`）が、5つの凍結ストアファイルの**行数（＝凍結された違反件数）**を
   定数 `EXPECTED_LINES_*` と照合する。行数が増えた場合（新規違反の混入）は無条件で fail、
   減った場合も「意図した根治か、絞り込み実行による事故か」を人間に判断させるため一旦 fail
   させる設計。
3. **根治して凍結ストアの行数が本当に減った場合の運用手順**:
   - `git diff backend/src/test/resources/archunit_store/<UUID>` で解消された違反の内容を確認する
   - `ArchUnitFreezeStoreIntegrityTest` の対応する `EXPECTED_LINES_*` 定数を実測行数
     （`wc -l backend/src/test/resources/archunit_store/<UUID>`）に更新する
   - ストアファイルの変更と定数更新を**同一コミット**に含める
4. `.github/CODEOWNERS` で `backend/src/test/resources/archunit_store/` 配下をオーナーレビュー
   必須に設定している（意図しない変更が無レビューで混入しないための最終防衛線）。

## §XX ローカルアバター/画像保存 — MinIO（profile `storage`）

ローカル開発環境では Cloudflare R2 が使えないため、S3互換の MinIO を使ってアバター・バナー画像の
presigned URL フロー（`/api/v1/*/profile-media` EP）を動作確認できる。

### 起動手順

1. MinIO を起動（通常の `docker compose up -d` には含まれない）:
   ```bash
   docker compose --profile storage up -d
   ```
   - API ポート: `9000`
   - Console UI: http://localhost:9001（ユーザー: `minioadmin` / パスワード: `minioadmin`）
   - バケット `mannschaft-storage` は `minio-init` コンテナが自動作成する

2. `backend/src/main/resources/application-local.yml` に以下が設定されていることを確認:
   ```yaml
   mannschaft:
     storage:
       endpoint: http://localhost:9000
       access-key: minioadmin
       secret-key: minioadmin
       bucket: mannschaft-storage
   ```
   既定値として設定済みのため、環境変数の上書きなしで MinIO に接続できる。

3. Spring Boot を再起動（ローカルプロファイル）:
   ```bash
   cd backend && ./gradlew bootRun
   ```

4. `/settings/profile` でアバター画像を選択し、アップロードが成功することを確認する。

### 注意事項

- MinIO はローカル開発専用。本番は Cloudflare R2（`MANNSCHAFT_R2_*` 環境変数）を使用。
- ブラウザからの presigned PUT に必要な CORS（`http://localhost:3000`/`3001`）は
  `MINIO_API_CORS_ALLOW_ORIGIN` で許可済み。
- MinIO Console でバケット内容を確認できる（http://localhost:9001）。
