## 1. 概要

チーム/組織の ADMIN が、会費・イベント参加費等の支払いに対して**電子領収書**を発行する機能。日本のインボイス制度（適格請求書等保存方式）に対応し、登録番号・発行者情報・税率別内訳を含む法的要件を満たす領収書を PDF で生成する。

**主要ユースケース**:
- マンション管理組合: 管理費・修繕積立金の領収書発行
- スポーツチーム: 月会費・年会費・大会参加費の領収書発行
- 学校・PTA: 会議参加費・イベント費用の領収書発行
- 整骨院・美容室: 施術費用の領収書発行（サービス履歴連携）

**インボイス制度対応**:
- 適格請求書発行事業者の登録番号（T + 13桁）をチーム/組織に登録
- 登録済みの場合: 適格請求書（インボイス）形式で発行（税率別内訳・登録番号記載）
- 未登録の場合: 通常の領収書形式で発行（登録番号なし。「適格請求書発行事業者以外の者からの領収書」と明記）

**但し書きの自動取得**:
- `member_payments` が `schedules`（イベント）に紐付いている場合、スケジュール名を但し書きの初期値に自動設定
- 例: 「第12回 定例理事会 会議費として」「2026年4月度 月会費として」
- ADMIN が手動で編集可能

### 本ドキュメントのスコープ

| 機能 | 説明 |
|------|------|
| 発行者設定 | チーム/組織のインボイス登録番号・発行者名・住所・押印設定 |
| 領収書発行 | 支払い実績からの自動発行 / 手動発行。但し書き自動取得 |
| PDF 生成 | インボイス対応の領収書 PDF 生成・ダウンロード |
| 電子印鑑連携 | F05.3 の電子印鑑を領収書に押印 |
| 領収書一覧・検索 | 発行済み領収書の検索・再ダウンロード |

**スコープ外**:
- Stripe の自動発行レシート（`member_payments.stripe_receipt_url`）→ F08.2 で管理。本機能はそれとは別の「組織が発行する正式な領収書」
- 請求書（Invoice）発行 → 将来検討（FUTURE_CONSIDERATIONS 向き）
- 確定申告連携 → スコープ外

### 運営（Mannschaft 自身）が発行する領収書について — 本書の対象外

本書が扱うのは、**組織・チームがそのメンバーへ発行する領収書**のみである。運営（Mannschaft 自身）が発行する領収書は本書の対象外であり、別設計書で扱う。

- `ReceiptScopeType`（`backend/src/main/java/com/mannschaft/app/receipt/ReceiptScopeType.java`）は現在 `ORGANIZATION` / `TEAM` の 2 値のみであり、運営スコープに相当する値を持たない。`receipt_issuer_settings.scope_id` も組織 / チームの ID を指す前提である。
- 運営がユーザーから受け取る収入（広告費・通知クレジット購入・月謝サブスク等）に対する領収書は**未設計**である。発行主体・発行者設定の持ち方・番号採番の単位・インボイスの扱いのいずれも決まっていない。着手する際は別途軍議にかけること。本書の設計をそのまま流用できる保証はない。
- **`PLATFORM` を後から足す場合の拡張点**（詳細設計は別軍議に委ねるが、所在だけ記す）: (a) `receipt_issuer_settings.scope_id` は `BIGINT UNSIGNED NOT NULL` で組織/チームの実 ID を前提としており、**運営には対応する ID が存在しない**（固定値 0 を置くか、別テーブルへ分けるかの判断が要る）。(b) 一意制約 `uq_ris_scope (scope_type, scope_id)` は上記 (a) の決着に依存する。(c) 認可の `AccessControlService.checkAdminOrAbove(userId, scopeId, scopeType)` は `getRoleName` でスコープ別ロールを引く実装であり、**運営スコープを解釈できない**（`SYSTEM_ADMIN` 判定は別経路の `isSystemAdmin` にあるため、そちらへ分岐させる設計が要る）。(d) 領収書番号の採番単位（運営全体で 1 系列か、収入種別ごとか）も未決である。
- ただし「運営は現時点でインボイス登録番号を未取得であり、後日取得予定」という要件については、**現行設計が追加設計なしで移行に耐える**。`is_qualified_invoicer` の DB 既定値が `FALSE` であるため未取得の状態を素直に表現でき（`V8.022__create_receipt_issuer_settings.sql`）、取得後にフラグを `TRUE` にして登録番号を登録すれば、以後の発行分のみが適格請求書形式になる。発行時に発行者情報を `receipts` へスナップショットするため、**取得前に発行済みの領収書が遡って書き換わることはない**（§5「重要な判定ロジック」）。すなわち登録番号取得は設定変更 1 回で完結し、マイグレーションもデータ移行も不要である。

**制約・備考**
- `invoice_registration_number`: `T` + 13桁の数字（例: `T1234567890123`）。バリデーション: `/^T\d{13}$/`。`is_qualified_invoicer = TRUE` の場合は NOT NULL 制約をアプリ層で適用
- `default_seal_user_id`: 領収書に押印する ADMIN のユーザー ID。NULL の場合は押印なしで発行可能
- `next_receipt_number`: `SELECT ... FOR UPDATE` で排他制御し、発行時にインクリメント
- `fiscal_year_start_month` + `auto_reset_number`: 年度切替の自動リセット設定。日次バッチ（AM 0:00）で `auto_reset_number = TRUE` かつ今日が `fiscal_year_start_month` の1日の場合、`next_receipt_number` を 1 にリセットし、`receipt_number_prefix` の年部分を自動更新（例: `RC-2025-` → `RC-2026-`）。`auto_reset_number = FALSE` の場合は ADMIN が手動管理
- `receipt_note_template`: プレースホルダー `{item_name}`（支払い項目名）、`{schedule_name}`（イベント名）、`{period}`（対象期間）が使用可能

**制約・備考**
- 発行者情報（`issuer_name` / `issuer_address` / `invoice_registration_number`）は発行時点のスナップショットを保存。発行後に `receipt_issuer_settings` が変更されても既発行の領収書に影響しない
- 受領者情報（`recipient_name` / `recipient_address`）も発行時点のスナップショット。同上
- `member_payment_id`: 支払い実績に紐付く場合に設定。1つの `member_payments` に対して複数の領収書を発行可能（分割領収書）
- `voided_at`: 無効化された領収書は PDF に「無効」の赤スタンプをオーバーレイ。再ダウンロード時に無効化表示付きの PDF を返却
- `seal_stamp_log_id`: F05.3 の `seal_stamp_logs` に `target_type = 'RECEIPT'` で記録。NULL の場合は押印なし
- `schedule_id`: 但し書き自動取得元。イベントの `title` + 日付を但し書きの初期値に使用
- PDF 保持期間: **7年**（電子帳簿保存法の保存義務期間）。S3 の Lifecycle Policy で管理

| `description` | VARCHAR(200) | NO | — | 明細の説明（例: 「会議費」「飲食代」） |
| `amount` | DECIMAL(10,0) | NO | — | 税込金額 |
| `tax_rate` | DECIMAL(4,2) | NO | — | 適用税率（%）。10.00 or 8.00 |
| `tax_amount` | DECIMAL(10,0) | NO | — | 税額 |
| `amount_excl_tax` | DECIMAL(10,0) | NO | — | 税抜金額 |
| `sort_order` | INT | NO | 0 | 表示順（昇順） |

**インデックス**
```sql
INDEX idx_rli_receipt (receipt_id, sort_order)  -- 領収書別の明細一覧
```

**制約・備考**
- 明細行がある場合: `receipts.amount` = `SUM(receipt_line_items.amount)`、`receipts.tax_amount` = `SUM(receipt_line_items.tax_amount)` であることを Service 層でバリデーション
- 明細行がない場合（単一税率）: `receipts` テーブルの `tax_rate` / `tax_amount` / `amount_excl_tax` をそのまま使用。`receipt_line_items` は0件
- 1領収書あたり最大10明細行
- インボイス制度では税率ごとの区分記載が義務。複数税率がある場合は明細行で税率別合計を記載

#### `receipt_presets`

発行プリセット。毎月の定例料金など、同じ内容で繰り返し発行する領収書の設定を保存する。

| `id` | BIGINT UNSIGNED | NO | AUTO_INCREMENT | PK |
| `scope_type` | VARCHAR(20) | NO | — | スコープ（`TEAM` / `ORGANIZATION`） |
| `scope_id` | BIGINT UNSIGNED | NO | — | スコープ ID |
| `name` | VARCHAR(100) | NO | — | プリセット名（例: 「月会費」「管理費（月額）」） |

| `tax_rate` | DECIMAL(4,2) | NO | 10.00 | 適用税率（%） |
| `line_items_json` | JSON | YES | NULL | 複数税率の明細行定義（`receipt_line_items` と同形式の JSON 配列。NULL = 単一税率） |
| `payment_method_label` | VARCHAR(50) | YES | NULL | 支払い方法の表示名 |
| `seal_stamp` | BOOLEAN | NO | TRUE | 電子印鑑を押印するか |

| `deleted_at` | DATETIME | YES | NULL | 論理削除日時 |

**インデックス**
```sql
INDEX idx_rp_scope (scope_type, scope_id)  -- スコープ別のプリセット一覧
```

**制約・備考**
- 1スコープあたり最大 **30 プリセット**
- `description` にはテンプレートプレースホルダー（`{period}` 等）を使用可能。発行時に実値に置換
- `line_items_json`: `[{"description": "会議費", "amount": 3300, "tax_rate": 10.00}, ...]` 形式。発行時に `receipt_line_items` に展開
- プリセットの使用: `POST /admin/receipts` のリクエストに `preset_id` を指定 → プリセットの値をデフォルト値として適用（ADMIN が個別に上書き可能）

#### `receipt_queue`

発行待ちキュー。Stripe 決済完了時に自動追加され、ADMIN の承認を待つ。

| カラム名 | 型 | NULL | デフォルト | 説明 |
|---------|---|------|-----------|------|
| `id` | BIGINT UNSIGNED | NO | AUTO_INCREMENT | PK |
| `scope_type` | VARCHAR(20) | NO | — | スコープ（`TEAM` / `ORGANIZATION`） |
| `scope_id` | BIGINT UNSIGNED | NO | — | スコープ ID |
| `member_payment_id` | BIGINT UNSIGNED | NO | — | FK → member_payments。決済完了した支払い |
| `recipient_user_id` | BIGINT UNSIGNED | NO | — | FK → users。受領者 |
| `suggested_description` | VARCHAR(500) | YES | NULL | 自動生成された但し書き候補 |
| `suggested_amount` | DECIMAL(10,0) | NO | — | 支払い額（`member_payments.amount` から取得） |
| `preset_id` | BIGINT UNSIGNED | YES | NULL | FK → receipt_presets。マッチしたプリセット |
| `status` | VARCHAR(20) | NO | 'PENDING' | ステータス（`PENDING`: 承認待ち / `APPROVED`: 承認済み（発行処理中） / `SKIPPED`: スキップ） |
| `processed_receipt_id` | BIGINT UNSIGNED | YES | NULL | FK → receipts。承認後に発行された領収書 |
| `created_at` | DATETIME | NO | CURRENT_TIMESTAMP | |
| `updated_at` | DATETIME | NO | CURRENT_TIMESTAMP ON UPDATE | |

**インデックス**
```sql
INDEX idx_rq_scope_status (scope_type, scope_id, status, created_at DESC)  -- スコープ別の未処理キュー
UNIQUE KEY uq_rq_payment (member_payment_id)                                -- 同一支払いの重複キュー防止
```

**制約・備考**
- Stripe Webhook（`checkout.session.completed`）で `member_payments` が `PAID` になった時点で、`ActivityFeedEventListener` と同様のパターンで `ReceiptQueueEventListener` が非同期で INSERT
- `preset_id`: `payment_items` と `receipt_presets` の紐付けがある場合に自動設定。マッチしない場合は NULL（ADMIN が手動で但し書き・金額を入力）
- `SKIPPED`: 領収書が不要な支払い（例: 寄付金）の場合に ADMIN がスキップ
- `APPROVED` → `receipts` への INSERT + PDF 生成は `POST /admin/receipts` と同一フローを使用
- キューの保持期間: 90日。90日超の `PENDING` レコードは月次バッチで `SKIPPED` に自動遷移 + ADMIN アラート

```

  "recipient_user_id": 50,
  "recipient_name": "田中太郎",

- `preset_id`: プリセット ID（任意）。指定時はプリセットの値をデフォルト適用。リクエストで個別指定したフィールドはプリセットより優先
- `status`: `ISSUED`（デフォルト。即時発行）/ `DRAFT`（下書き。DEPUTY_ADMIN は DRAFT のみ指定可能）。DRAFT の場合は採番・PDF 生成・通知を行わない
- `member_payment_id`: 支払い実績に紐付ける場合に指定。NULL の場合は手動発行
- `recipient_user_id`: プラットフォームユーザーの場合に指定。NULL の場合は外部受領者（`recipient_name` 等を手動入力）
- `recipient_name`: 省略時は `recipient_user_id` の `display_name` or `member_payment_id` の支払者名を自動設定。外部受領者の場合は必須
- `recipient_postal_code` / `recipient_address`: 省略時は `users` テーブルから自動取得。外部受領者の場合は手動入力（省略可）
- `description`: 省略時は `receipt_note_template` + `payment_items.name` or `schedules.title` から自動生成
- `amount`: 税込合計金額。`tax_amount` / `amount_excl_tax` はバックエンドが `tax_rate` から算出
- `line_items`: 複数税率の場合に指定（任意）。指定時は `amount` = `SUM(line_items[].amount)` であること。省略時は単一税率（`tax_rate` から算出）。各明細の `tax_amount` / `amount_excl_tax` はバックエンドが算出
- `seal_stamp`: `true` の場合、`receipt_issuer_settings.default_seal_user_id` の電子印鑑を押印

- `email_delivery`: 領収書 PDF のメール送信設定（任意）。`enabled = true` の場合、PDF 生成完了後にメール送信。`email` を省略すると `recipient_user_id` の `users.email` を使用。外部受領者の場合は `email` を明示指定。`enabled = false`（デフォルト）の場合はメール送信なし

### 領収書発行フロー

```
1. ADMIN が領収書発行画面にアクセス
   a. 発行者設定が未登録の場合 → 「先に発行者設定を行ってください」案内
   b. 支払い実績一覧（member_payments）から対象を選択 or 手動入力

2. 但し書きの自動生成
   a. member_payment_id が指定された場合:
      i.  payment_items.name を取得 → 「{item_name}として」
      ii. member_payments に紐付く schedule_id があれば schedules.title を優先
          → 「{schedule_title}（{schedule_date}）{item_name}として」
   b. schedule_id が直接指定された場合:
      → 「{schedule_title}（{schedule_date}）会議費として」
   c. どちらもない場合:
      → receipt_note_template のテンプレートを適用
   d. ADMIN が手動で自由に編集可能（自動生成はあくまで初期値）

3. 受領者情報の自動取得
   a. member_payment_id から支払者の user_id を取得
   b. users テーブルから display_name / postal_code / address を取得
   c. 住所が未登録の場合: 宛名のみで発行（住所なし。法的には有効）

4. 領収書番号の採番
   a. receipt_issuer_settings の next_receipt_number を SELECT ... FOR UPDATE で排他取得
   b. receipt_number = receipt_number_prefix + zero-padded next_receipt_number
      例: "RC-2026-" + "00001" → "RC-2026-00001"
   c. next_receipt_number を +1 して UPDATE

5. 電子印鑑の押印（seal_stamp = true の場合）
   a. default_seal_user_id の electronic_seals から指定 variant の印鑑 SVG を取得
   b. seal_stamp_logs に INSERT（target_type = 'RECEIPT', target_id = receipts.id）
   c. seal_stamp_log_id を receipts に設定

6. PDF 生成（非同期）
   a. 領収書データ + 電子印鑑 SVG から PDF を生成
   b. S3 にアップロード → pdf_storage_key を設定
   c. Pre-signed URL（24時間有効）でダウンロード提供
```

### 電子帳簿保存法への対応

```

> **⚠️ 実装との乖離（2026-09-02 確認済み。推測ではない）**: **上記の承認制ワークフローは実装で機能していない。**
>
> `ReceiptService.java`:349 の `approveReceipt` は `accessControlService.checkAdminOrAbove(...)` を呼んでおり、`AccessControlService.java`:52 の `ADMIN_ROLES = Set.of("ADMIN", "DEPUTY_ADMIN")` により **DEPUTY_ADMIN がそのまま承認できる**。すなわち **DEPUTY_ADMIN が自分で DRAFT を起票し、自分で ISSUED へ承認できる**。本節が意図した**起票者と承認者の分離は成立していない**。
>
> **本書の記述（あるべき姿）は撤回しない。** 実装に合わせて設計を諦めるのではなく、**別戦役で権限分離を実装する**（マスター裁可 2026-09-02）。必要なのは (a) パーミッションキー `RECEIPT_MANAGE` の新設、(b) 承認・無効化を「ADMIN のみ」で判定する専用の認可メソッド（`checkAdminOrAbove` ではなく `isAdmin` 相当）への差し替え、(c) TEAM スコープに対応したパーミッション判定である（既存の `checkAdminOrHasPermission` は `ORGANIZATION` 専用。`AccessControlService.java`:464-479）。
>
> **本戦役（発行者設定画面）の対象外**である。発行者設定は ADMIN / DEPUTY_ADMIN のいずれも変更してよい性質のものであり、この乖離の影響を受けない。

### 重要な判定ロジック

- **発行者情報のスナップショット**: 領収書の発行者名・住所・登録番号は発行時点の値を `receipts` テーブルに複製。後から `receipt_issuer_settings` を変更しても既発行の領収書は不変（法的要件）
- **受領者情報のスナップショット**: 同上。ユーザーが住所を変更しても既発行の領収書は不変
- **領収書番号の連番保証**: `SELECT ... FOR UPDATE` による排他制御。同時発行時の番号重複を防止。一括発行（bulk）では必要件数分を一度にインクリメント（例: 5件なら `next_receipt_number += 5`）し、即座にロック解放。その後、各領収書の INSERT は採番済みの番号を使用（ロック保持時間を最小化）
- **無効化の不可逆性**: `voided_at` が設定された領収書は再有効化不可。新しい領収書を発行して対応
- **1支払い複数領収書**: `member_payment_id` に対して複数の領収書を発行可能（分割領収書。例: 会費と雑費を分けて領収）。合計金額が元の支払い額を超えるバリデーションは行わない（実務上、端数処理等で合わない場合がある）
- **手動発行**: `member_payment_id = NULL` で支払い実績に紐付かない領収書を発行可能。任意の金額・但し書きを設定
- **電子印鑑の連動**: `seal_stamp_logs.target_type = 'RECEIPT'` で F05.3 の印鑑検証（`GET /seal/stamps/{id}/verify`）が使用可能。領収書の無効化時は印鑑も自動取り消し
- **PDF 保持期間**: 7年（電子帳簿保存法）。S3 Lifecycle Policy で `Glacier Deep Archive` に移行後、7年経過で削除
- **但し書き候補の生成**: 直近30日以内の `attendance_required = TRUE` のイベント + スコープ内の `payment_items` から候補を自動生成。ADMIN が選択 or 手動入力
- **税額の計算**: `tax_amount = FLOOR(amount * tax_rate / (100 + tax_rate))`（税込→税抜の逆算。1円未満切り捨て）。`amount_excl_tax = amount - tax_amount`
- **メール送信**: `email_delivery.enabled = true` の場合、PDF 生成完了後に非同期送信。送信失敗は領収書発行の成否に影響しない。一括発行（bulk）ではメール送信を含めない（スパム判定回避）。一括発行後は `POST /admin/receipts/{id}/send-email` で個別送信
- **CSV エクスポート**: BOM 付き UTF-8 で出力（Excel の文字化け防止）。複数税率の領収書は明細行ごとに1行。最大 10,000件
- **PDF ロゴ**: `receipt_issuer_settings.logo_storage_key` に画像キーを保持。アップロード時に**長辺 200px を上限として縮小**（アスペクト比維持・拡大なし・透過は白背景に合成）。ロゴなしの場合はテキストタイトルのみ
- **PDF フッター**: `receipt_issuer_settings.custom_footer` のプレーンテキスト（最大500文字）を発行者情報の下に配置
- **論理削除の不使用**: `receipts` テーブルに `deleted_at` は設けない。領収書は法的文書のため削除不可。取り消しは `voided_at` で管理し、元データは永続保持
- **発行プリセット**: スコープ内で最大30件。但し書きテンプレート・金額・税率・明細行を保存。`POST /admin/receipts` に `preset_id` 指定でデフォルト値適用（個別上書き可能）
- **発行キュー**: Stripe 決済完了時に `ReceiptQueueEventListener` が自動投入。ADMIN がキュー一覧を確認 → 承認で発行。90日超の PENDING は自動 SKIPPED + アラート
- **承認制ワークフロー**: DEPUTY_ADMIN は `status=DRAFT` で下書き作成のみ。ADMIN が `PATCH /approve` で ISSUED に遷移（採番・PDF生成・通知はこの時点で実行）。ADMIN が直接発行する場合はデフォルト `status=ISSUED` で従来通り
- **一括無効化**: `POST /admin/receipts/bulk-void` で最大50件。ADMIN のみ。各領収書に対して個別 void と同等の処理（PDF 再生成・印鑑取り消し・通知・監査ログ）
- **ZIP 一括ダウンロード**: 非同期生成（S3 に ZIP アップロード。24時間保持で自動削除）。最大500件。`GET /download-zip/{jobId}` で進捗確認 + ダウンロード
- **年間サマリー**: `GET /my/receipts/annual-summary` で年間合計・件数・税率別合計を返却。無効化済み領収書は合計から除外
- **F08.2 連携**: `GET /members/{id}/payments` のレスポンスに `receipt_ids` 配列を追加（F08.2 側の変更。Phase 8 統合テスト時に対応）
- **無効化の権限制限**: `POST /admin/receipts/{id}/void` は ADMIN のみ実行可能とする設計。DEPUTY_ADMIN は不可。法的文書の取り消しは最高権限者に制限（電子帳簿保存法の改ざん防止の観点）
  - ⚠️ **実装との乖離（2026-09-02 確認済み）**: **この制限は実装で効いていない。** `ReceiptService.java`:277（単体無効化）と :308（一括無効化 `bulkVoidReceipts`）はいずれも `checkAdminOrAbove` を呼んでおり、`ADMIN_ROLES` に `DEPUTY_ADMIN` が含まれる（`AccessControlService.java`:52）ため、**DEPUTY_ADMIN が単独で無効化も最大50件の一括無効化も実行できる**。電子帳簿保存法の改ざん防止という本制限の目的は現状達成されていない。**あるべき姿は上記のまま維持し、権限分離の実装は別戦役とする**（§5 承認制ワークフローの乖離注記と同一の是正で解消する）
- **再発行フロー**: `POST /admin/receipts/{id}/reissue` で無効化済み領収書のデータを流用してプレビュー取得 → `POST /admin/receipts` で正式発行。元の領収書が未無効化の場合は 409 で拒否（無効化せずに再発行はできない）。再発行元の `receipt_number` はレスポンスに `reissue_source_receipt_number` として含め、トレーサビリティを確保

## 6. セキュリティ考慮事項

- **認可チェック**: `/admin/receipts/**` は ADMIN + DEPUTY_ADMIN のみ（設計上は `RECEIPT_MANAGE` 必須だが**未実装**。§2 の乖離注記）。`/my/receipts/**` は自分宛の領収書のみ。他人の領収書 PDF へのアクセスは 403
- **PDF アクセス制御**: Pre-signed URL（24時間有効）で S3 から直接ダウンロード。URL 推測によるアクセスを防止するため、`pdf_storage_key` にランダム UUID を含める
- **インボイス登録番号の検証**: 形式チェック（`/^T\d{13}$/`）のみ。国税庁 API との連携による実在性検証は行わない（API が不安定なため。ADMIN の自己申告を信頼）
- **レートリミット**: `Bucket4j` で以下の制限を適用する設計。
  > **⚠️ 未実装（2026-09-02 確認）**: `Bucket4j` はリポジトリに存在し `ActionMemoRateLimitFilter` / `AuditLogRateLimitFilter` / `AdPublicEndpointRateLimitFilter` 等で実際に使われているが、**`receipt` パッケージにはレートリミットの実装が 1 件も無い**（`backend/src/main/java/com/mannschaft/app/receipt/` 配下に `RateLimit` の出現 0 件）。以下は設計上の目標値であり、現在は一切適用されていない。実装は別戦役とする。
  - 領収書発行（`POST /admin/receipts`）: 1分間20件/ユーザー
  - 一括発行（`POST /admin/receipts/bulk`）: 1分間5件/ユーザー
  - PDF ダウンロード: 1分間30件/ユーザー
  - メール送信（`POST /admin/receipts/{id}/send-email`）: 1時間30件/ユーザー（メールスパム防止）
  - CSV エクスポート: 1分間3件/ユーザー
  - ロゴアップロード: 1分間5件/ユーザー
  - 一括無効化（`POST /admin/receipts/bulk-void`）: 1分間3件/ユーザー
  - キュー一括承認（`POST /admin/receipt-queue/bulk-approve`）: 1分間5件/ユーザー
  - ZIP ダウンロード生成: 1時間10件/ユーザー
- **監査ログ**: 以下のイベントを記録
  - `RECEIPT_ISSUED`: 領収書発行（receipt_number, amount, recipient）
  - `RECEIPT_VOIDED`: 領収書無効化（receipt_number, reason）
  - `RECEIPT_SETTINGS_UPDATED`: 発行者設定変更
  - `RECEIPT_BULK_ISSUED`: 一括発行（件数）
  - `RECEIPT_PDF_DOWNLOADED`: PDF ダウンロード（receipt_number, downloader）
  - `RECEIPT_NUMBER_RESET`: 領収書番号の年度リセット（scope, old_prefix → new_prefix）
  - `RECEIPT_EMAIL_SENT`: 領収書メール送信（receipt_number, recipient_email）
  - `RECEIPT_CSV_EXPORTED`: CSV エクスポート（scope, 件数, 期間）
  - `RECEIPT_LOGO_UPLOADED`: ロゴ画像アップロード
  - `RECEIPT_REISSUED`: 無効化後の再発行（new_receipt_number, source_receipt_number）
  - `RECEIPT_APPROVED`: 下書き承認（receipt_number, approver）
  - `RECEIPT_BULK_VOIDED`: 一括無効化（件数, reason）
  - `RECEIPT_QUEUE_APPROVED`: キューアイテム承認（receipt_number, queue_id）
  - `RECEIPT_QUEUE_BULK_APPROVED`: キュー一括承認（件数）
  - `RECEIPT_ZIP_GENERATED`: ZIP 一括ダウンロード生成（件数, 期間）
- **データ改ざん防止**: `receipts` テーブルの `description` / `amount` / `tax_rate` / `recipient_name` 等のデータ項目は発行後の UPDATE 禁止（Service 層で制約）。修正が必要な場合は無効化 + 再発行で対応（電子帳簿保存法の改ざん防止要件）
- **S3 Object Lock**: 領収書 PDF 専用バケット `mannschaft-receipts` に Compliance モード（Retention 7年）を設定。アップロード後の上書き・削除を物理的に防止

**FE の最大長ガード方式（確定）**: すべてのテキスト入力に **`maxlength` 属性を付けて入力段階で切る**。超過を許して後からエラーを出す方式は採らない。理由は (a) 入力してから怒られる摩擦を避ける（ADHD 配慮）、(b) BE の `@Size` は最後の防壁として残るので二重防御が成立する、(c) テストが「201 文字目が入力できない」という観測可能な事実に落ちる。ただし `invoiceRegistrationNumber` だけは形式検証があるため `maxlength=14` に加えて `^T\d{13}$` の検証エラーも出す。

#### 差分更新に伴う Bean Validation の是正（致命・必須）

差分更新に改める以上、**`UpdateIssuerSettingsRequest` の必須アノテーションをそのまま残すことはできない**。残すと 1 項目だけ送る差分更新が必ず 400 になり、AC-22 は永久に緑にならない。

| 対象 | 現状 | 是正 |
|---|---|---|
| `@NotBlank issuerName`（`UpdateIssuerSettingsRequest.java`:19-21） | 常に必須 | **DTO から外す**。必須性は**マージ後の状態**に対しサービス層で判定する（新規作成時は必須、既存更新時は任意＝送らなければ現在値を維持） |
| `@NotNull isQualifiedInvoicer`（同 :32-33） | 常に必須 | **DTO から外す**。同上 |
| `@Pattern(regexp = "^T\d{13}$") invoiceRegistrationNumber`（同 :35-37） | 空文字を弾く | **`@Pattern(regexp = "^(|T\d{13})$")` に変更**（マスター裁可）。これで「空文字＝明示クリア」が DTO を通過できる。`@Size(max=14)` は据え置き |

**二層構成は維持する**（サービス層への一本化はしない）: **DTO は形式のみ**（文字数・正規表現）、**サービス層は不変条件**（必須性・組み合わせの整合）を見る。

**不変条件はマージ後の状態に対して検証する（法的に最も重い箇所）**

現行の `ReceiptIssuerSettingsService.validateInvoiceRegistration()`（:164-174）は `request.getIsQualifiedInvoicer()` が `TRUE` のときだけ検証する。差分更新化するとこの値は `null` になりうるため、**DB が適格 `TRUE` のまま登録番号だけがクリアされ、「適格請求書の表記なのに登録番号が空」という法的に不正な PDF が発行されうる**。

したがって検証は、**既存エンティティの値にリクエストをマージした結果の状態**に対して行う:

```
merged.isQualifiedInvoicer = request.isQualifiedInvoicer ?? entity.isQualifiedInvoicer
merged.invoiceRegistrationNumber = (request に現れた場合はその値、そうでなければ entity の値)

if (merged.isQualifiedInvoicer == TRUE) {
    if (merged.invoiceRegistrationNumber が null または空)  -> RECEIPT_007
    if (^T\d{13}$ に一致しない)                              -> RECEIPT_006
}
if (新規作成)  { issuerName 必須（空なら 400）, isQualifiedInvoicer 必須 }
```

**波及**: 既存テスト `ReceiptIssuerSettingsServiceTest` の「登録番号未設定で例外」系ケースは、リクエスト単体ではなくマージ後の状態を期待する形に書き換わる。`/試練` はこの書き換えも red 側に含めること。

#### 更新は差分更新（PATCH セマンティクス）

**マスター裁可により、更新をフル置換から差分更新に改める**（BE 修正を本戦役に含む）。

- **HTTP メソッドは `PUT` から `PATCH` へ改める**。`backend/.claudecode.md` §25 は「更新（PATCH/PUT）は 200 + 更新後のリソースをレスポンスボディに含める」とのみ定め、どちらを使うかの規約は無い。実装上も `@PutMapping` を持つコントローラ 222 本に対し `@PatchMapping` は 209 本あり、PATCH は十分に慣用である。意味が差分更新である以上、RFC 上「完全置換」を意味する `PUT` のまま運用するのは本戦役が正そうとしている契約の嘘そのものなので、メソッドを実態に合わせる。
  - 波及: `docs/openapi.json`（現在 `/api/v1/admin/receipt-settings` は `get` / `put` を持つ）と `frontend/app/types/generated/index.ts` の再生成が必要。composable は D-1 でどのみち改修するため追加コストは小さい。
- **意味論**: リクエストに現れなかったフィールド、および `null` のフィールドは**無変更**。`entity.update(...)`（`ReceiptIssuerSettingsEntity.java`:97-116）が渡り値を無条件代入する現行実装を、フィールドごとの null チェック付き更新に改める。
- これにより「**触っていない項目が `NULL` で潰れる**」問題は消える。画面が全項目を送り返す必要も無くなる。
- **UPSERT は維持する**（D-4 対応）。設定が未作成のスコープへの `PATCH` は、必須項目（`issuerName` と `isQualifiedInvoicer`）が揃っていれば新規作成し、欠けていれば 400 を返す。
- **同時更新**: 差分更新化により「他人が編集した項目を巻き添えで潰す」事故は消えるが、**同一項目を同時に編集した場合は依然として後勝ち**である。楽観ロック（`@Version`）は本戦役では導入せず、**この後勝ちを明示的に受容する**。発行者設定は変更頻度が極めて低く、変更者が同一スコープの管理者に限られるためである。

#### インボイス対応トグルの挙動

1. `isQualifiedInvoicer` が **OFF** のとき、`invoiceRegistrationNumber` の入力欄は**無効化（disabled）**する。非表示ではなく無効化とし、「登録番号は適格請求書発行事業者の場合のみ入力します」という説明を添える（ADHD 配慮: 項目が消えると何が起きたか分からなくなるため、存在は残して理由を示す）。
2. OFF → ON に切り替えると、登録番号欄が有効化され**必須**になる。
3. ON のまま登録番号が空、または `^T\d{13}$` に一致しない場合、**保存ボタンを押しても送信せず**、入力欄直下にエラー文言を表示する。クライアント側検証は BE と同じ正規表現 `^T\d{13}$` を用いる（BE 側は `UpdateIssuerSettingsRequest` の `@Pattern` と `ReceiptIssuerSettingsService.validateInvoiceRegistration()`:164-174 の二重で守られており、FE はそのどちらにも到達させないことを狙う）。
4. BE から `INVOICE_REGISTRATION_NUMBER_REQUIRED`（`RECEIPT_007`）/ `INVALID_INVOICE_REGISTRATION_NUMBER`（`RECEIPT_006`）が返った場合も、同じ入力欄にエラーとして表示する（トーストだけで済ませない）。
5. **ON → OFF に戻したときの登録番号の残留**: 差分更新では「送らなければ無変更」なので、OFF で保存しても DB には**古い登録番号が残る**。これは危険である。後から別の管理者が ON に戻すと、古い番号のまま気づかず保存してしまい、誤った登録番号の適格請求書を発行しうる。したがって:
   - **OFF にして保存するときは、`invoiceRegistrationNumber` に明示的な空文字を送って DB からも消す**。差分更新の「null は無変更」に対し、**空文字は明示的なクリア**として扱う（この 2 値の区別を BE 仕様として定める）。
   - 画面上は、OFF に切り替えた時点で「保存すると登録番号も削除されます」と警告する。
   - 再度 ON にしたときは空欄から入力させる。古い番号を黙って再利用させない。

#### 既発行領収書への非遡及の明示

**設計判断**: 発行者設定の変更は、**すでに発行済みの領収書には一切反映されない**。`receipts` テーブルは発行時点の発行者名・住所・登録番号をスナップショットとして複製しており（§5「重要な判定ロジック」）、これは法的要件である。

この挙動はユーザーから見て直感に反する（「登録番号を入れたのに過去の領収書に載らない」）ため、画面上で能動的に説明する。

- フォーム上部に常設の注意書き:「ここで変更した内容は、**これから発行する領収書**に適用されます。すでに発行済みの領収書の内容は法令上変更できません。」
- とくに `isQualifiedInvoicer` / `invoiceRegistrationNumber` を変更して保存した直後は、保存成功トーストに続けて同趣旨を再掲する。
- 既発行分を訂正したい場合の導線として「無効化 → 再発行」（§5 再発行フロー）を案内する文言を置く。

#### ロゴのアップロード / 削除

- UI: 現在のロゴをプレビュー表示。未設定時は「ロゴ未設定」と、設定した場合の PDF 上の見え方（ヘッダー左上・タイトル中央）を説明する。
- アップロードは `POST /api/v1/admin/receipt-settings/logo`（`multipart/form-data`、フィールド名 `file`）、削除は `DELETE` 同パス。いずれも `scopeType` / `scopeId` をクエリで送る（D-1）。
- **フロント側ガード**: 形式は **PNG / JPEG のみ**（拡張子と `File.type` の両方）、サイズは **最大 1MB**。ガードに掛かった場合は送信せず、理由をその場に表示する。BE 側で長辺 200px 以内に縮小される旨を注記する。
- 削除は確認ダイアログを挟む（`DELETE` は 204 を返し、`logo_storage_key` が `NULL` になる）。
- **設定レコードが未作成の間、ロゴ UI は disabled にする**（マスター裁可）。BE の `updateLogo` は `findSettingsOrThrow`（`ReceiptIssuerSettingsService.java`:129,147,156-159）を通るため、レコードが無ければ `RECEIPT_001` になる。**`updateLogo` を UPSERT 化して BE の変更を増やすことはしない。** 画面は「先に発行者設定を保存してください」と表示し、保存が完了した時点でロゴ UI を有効化する。
- BE 側の実装は §9.1.1 の D-3 / D-8 是正方針に従う。

#### PII の扱い（判断の明文化）

- **発行者名・郵便番号・住所・電話は暗号化済みである**。`ReceiptIssuerSettingsEntity`:37-51 が `@Convert(converter = EncryptedStringConverter.class)` を付与し、`V9.053__add_encryption_to_pii_columns.sql`:38-43 が当該 4 列を `TEXT`（AES-256-GCM 暗号文）へ変更し `encryption_key_version` を追加している。V8.022 の `VARCHAR(200)` 等は V9.053 で置換済みであり、**現行スキーマは平文 VARCHAR ではない**。
- **`invoice_registration_number` は暗号化していない**（`VARCHAR(14)` 平文、エンティティ :57-58）。**これは意図的な設計判断とする**: インボイス登録番号は国税庁の適格請求書発行事業者公表サイトで誰でも検索できる**公表情報**であり、PII ではない。加えて領収書 PDF に印字されて受領者に配布されるため、DB でのみ秘匿しても意味が無い。
- 同様に `issuer_name` 等も「団体の公開情報相当」ではあるが、**既に暗号化されている実装を後退させない**（暗号化を外す変更は行わない）。
- **暗号化列に対する「明示クリア」は `NULL` を書き込む**（空文字ではない）。`postal_code` / `address` / `phone` は `EncryptedStringConverter` を通るため、空文字を送るとカラムには `NULL` ではなく**「空文字の暗号文」**が入り、`IS NULL` 判定・未設定判定が壊れる。サービス層で「空文字を受け取ったら `null` に正規化してからエンティティへ渡す」と定める。
- `invoice_registration_number` は暗号化列ではないが、上記と挙動を揃えるため**同じく空文字は `NULL` に正規化する**（§9.2 トグル挙動 5 の「明示クリア」はこの正規化を経て `NULL` になる）。
- 発行者設定の閲覧を D-6 で管理者限定に引き上げるのは、この PII を同一スコープの一般メンバーに開示しないためである。

### 9.5 非機能

- **PDF 非同期生成中の表示**: 領収書発行直後は `pdf_status` が生成中になりうる（§4）。発行者設定画面は PDF を生成しないため、本画面ではポーリング**不要**。一覧・発行画面側では `pdf_status` を表示し、生成中は「PDF を準備しています」と明示する（無言のスピナーで放置しない）。ポーリングを行う場合は指数バックオフとし、画面離脱時に必ず停止する。
- **ロゴアップロードの上限**: PNG / JPEG・業務上限 1MB。コンテナ側の `spring.servlet.multipart.max-file-size` は未設定＝既定 1MB のため、`2MB` を明示設定して業務上限より広く取る（§9.1.1 D-3）。レートリミットは 1 分間 5 件/ユーザー（§6）。上限超過時は待ち時間を文言で示す。
- **監査ログ**: `isQualifiedInvoicer` と `invoiceRegistrationNumber` の変更は、発行される法的文書の内容を左右するため**必ず監査ログに残す**。
  - 記録機構は `auth/service/AuditLogService.record(eventType, userId, targetUserId, teamId, organizationId, ip, ua, sessionHash, metadata)`（`AuditLogService.java`:51-70、`@Async` の fire-and-forget）。イベント名は `auth/AuditEventType` の enum。
  - **`AuditEventType` に `RECEIPT_*` のエントリは現在 1 件も無い**ため、`RECEIPT_SETTINGS_UPDATED` を新設する（§6 の監査ログ一覧に既に名前が挙がっているが、enum には存在しない）。
  - 旧値→新値の専用フィールドは機構側に無く、既存の呼び出し（例 `resume/service/ResumePhotoService.java`:126-132、`actionmemo/service/ActionMemoAdminService.java`:104-115）はいずれも `metadata` の JSON 文字列に手書きしている。本機能もこれに倣い、`{"scopeType":…,"scopeId":…,"isQualifiedInvoicer":{"old":…,"new":…},"invoiceRegistrationNumber":{"old":…,"new":…}}` の形で記録する。
  - **登録番号は公表情報**（§9.2 PII の扱い）なので監査ログに平文で残してよい。
- **入力摩擦の低減（ADHD 配慮）**:
  - 既定値をあらかじめ埋める（会計年度開始月 4・自動リセット ON）。空欄から始めさせない。
  - 取得済みの保存値は必ずフォームへ復元する。
  - 保存の成否を必ずトーストで返す。無反応で終わらせない。
  - 未保存の変更があるまま離脱しようとした場合に確認する。
  - エラーは「どの項目が」「なぜ」ダメかを入力欄の直下に出す。トーストだけにしない（AC-30 のとおり 500 時も入力値を失わない）。
  - 項目数が多いため、「発行者情報」「インボイス」「領収書番号」「PDF 体裁」の 4 セクションに分けて折りたたむ。
