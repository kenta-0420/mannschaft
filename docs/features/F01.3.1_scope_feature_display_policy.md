## 1. 目的と適用範囲

チーム・組織の管理者が、一般機能ごとにメンバーとサポータへ表示するかを独立して選ぶ。機能利用の認可とモジュール有効化は既存仕様を維持し、本設定は画面整理の追加条件とする。非表示でも直URL・既存APIの許可/拒否は変えず、元データ、個人のwidget表示設定・順序、既存minRole設定を削除・上書きしない。

対象はTEAM/ORGANIZATIONの所属利用者向けメニュー、ホームの一般タブ、関連widgetとその内部導線。同一機能は同じfeatureKeyを参照する。PERSONAL、公開ページ、認証済み非所属のPUBLIC閲覧、管理専用機能は対象外。お気に入り・検索・通知・直URL・個別詳細内リンクも今回の対象外。組織→配下チーム、親組織→子組織の継承はない。

## 2. 判定規則

- 保存値はmemberVisibleとsupporterVisibleの独立bool。true/true、true/false、false/true、false/falseの4通りを許容する。ロールの大小比較で代用しない。
- 未保存キーは両方trueとして既存表示を維持する。新規scopeに初期行は作らない。未保存のカタログ既知キーだけを既定trueとし、未知キーを新規作成しない。GET成功の未設定と、取得失敗は区別する。取得失敗をtrueへ黙ってフォールバックせず既存エラー表示・再試行を出す。
- 最終表示は「既存の所属・ロール・permission条件 AND 既存モジュール利用可否 AND 既存widget表示/minRole条件（widgetのみ）AND 本設定」。trueは既存認可を広げない。既存SidebarのMEMBER以上条件をSUPPORTERへ拡張する仕様ではない。
- 実MEMBERはmemberVisible、実SUPPORTERはsupporterVisibleを使用する。DEPUTY_ADMIN/ADMIN/SYSTEM_ADMINの通常管理表示は本設定をバイパスし、既存条件を維持する。管理者のメンバープレビューではmemberVisibleを適用し、実管理者バイパスを効かせない。プレビューは実API権限を変更しない。
- dashboardホームは常に残す固定アンカーで、設定対象にしない。管理レンズへの復帰、管理コンソール、機能設定への入口も既存の権限に従い維持する。全OFFでもホーム/スコープ切替と管理者の復帰が可能。
- 非表示設定を直URLで開いたページのリダイレクトや403の根拠に使わない。ページ内APIも従来認可どおり。

## 4. DB設計

新規テーブルscope_feature_display_policiesをmoduleドメインに置く。既存F01.3の古いBIGINT/FK例に倣わず、現行[ドメインDB原則](../architecture/domain_db_design_principles.md)を適用する。

| カラム | 型 | NULL | 説明 |
|---|---|---|---|
| id | BINARY(16) | NO | UuidV7EntityのUUIDv7主キー |
| scope_type | VARCHAR(20) | NO | TEAM / ORGANIZATION（STRING enum） |
| scope_id | BIGINT UNSIGNED | NO | slugを既存scope解決Serviceで解決した内部ID |
| feature_key | VARCHAR(64) | NO | カタログの安定機能キー |
| member_visible | BOOLEAN | NO | 初期値TRUE |
| supporter_visible | BOOLEAN | NO | 初期値TRUE |
| updated_by | BIGINT UNSIGNED | NO | 最終更新者の既存ユーザーID（ID参照のみ） |
| created_at | DATETIME(6) | NO | UTC、Entityで日時を保持 |
| updated_at | DATETIME(6) | NO | UTC、既存共通基底規約 |

UuidV7EntityはIDだけを保持するため、createdAt/updatedAtはEntityに明示し既存のUTC日時規約に従って設定する。PK(id)、UNIQUE(scope_type, scope_id, feature_key)。この複合uniqueの左端をscope一括読取にも使用する。scope_typeはTEAM/ORGANIZATIONのCHECKを付ける。scope_id/updated_byからteam/organization/userへのクロスドメインFK・CASCADEは作らない。既存scope削除処理・認可で削除scopeへのアクセスを拒否する。元データの移行・widget設定書換・初期seedは不要。Flyway番号は着手時の最大major+1とUTCタイムスタンプで採番し既存migrationは変更しない。

DDL案（Flywayでコメント・現行命名規約を適用）:

~~~sql
CREATE TABLE scope_feature_display_policies (
    id BINARY(16) NOT NULL,
    scope_type VARCHAR(20) NOT NULL,
    scope_id BIGINT UNSIGNED NOT NULL,
    feature_key VARCHAR(64) NOT NULL,
    member_visible BOOLEAN NOT NULL DEFAULT TRUE,
    supporter_visible BOOLEAN NOT NULL DEFAULT TRUE,
    updated_by BIGINT UNSIGNED NOT NULL,
    created_at DATETIME(6) NOT NULL,
    updated_at DATETIME(6) NOT NULL,
    PRIMARY KEY (id),
    CONSTRAINT uq_sfdp_scope_feature UNIQUE (scope_type, scope_id, feature_key),
    CONSTRAINT chk_sfdp_scope_type CHECK (scope_type IN ('TEAM', 'ORGANIZATION'))
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;
~~~

## 5. API契約

### STRING永続化enumの初回導入互換性レビュー

`FeatureDisplayScope#TEAM` / `#ORGANIZATION`の書込先は新設`scope_feature_display_policies.scope_type`だけとする。
2026-10-26の親検分で、実装`7efd0cfc6e`における本番全参照を照合し、旧`origin/main`
`6b9b426ec49465d11f019f8d01b2225e898bebbd`には`FeatureDisplayScope`と`scope_feature_display_policies`の参照・migration・APIがないことを
`git grep -n -e FeatureDisplayScope -e scope_feature_display_policies origin/main -- backend/src/main`の該当0件で確認した。
旧バイナリには新表を読む経路がなく、今回の初回新表導入で旧readerが未知定数を読むことはない、という範囲に限定して
2定数の互換性台帳登録を親が承認した。これは本番配布や旧task退場を実施した証明ではなく、コード・DB・APIの初回導入に対するレビュー判断である。

新表はmigration適用後に新APIが読み書きする。今回の導入を旧mainへrollbackする場合も表と保存行を保持し、削除・一律置換しない。
今後この表の定数を追加する場合は[永続化enumの二段階展開](../development/persisted_enum_deployment.md)に従い、
全読取taskへ定数だけを先行配布し、旧task退場の環境・version・時刻・証拠を確認後、別releaseで書込みを開始する。
その時点のrollback下限は読取り互換性を持つ第1段階とする。既存定数の改名・削除も保存済み行の意味を保つ個別の設計・承認・検証を要する。

| メソッド | パス | 認可 | 成功 |
|---|---|---|---|
| GET | /api/v1/teams/{slug}/feature-display-policies | 当該TEAM所属SUPPORTER以上、既存SYSTEM_ADMIN方針 | 200 |
| PUT | 同上 | 当該TEAM ADMIN、SYSTEM_ADMIN（既存方針） | 200 |
| GET | /api/v1/organizations/{slug}/feature-display-policies | 当該ORG所属SUPPORTER以上、既存SYSTEM_ADMIN方針 | 200 |
| PUT | 同上 | 当該ORG ADMIN、SYSTEM_ADMIN（既存方針） | 200 |

既存ApiResponseでdataを包み、GET/PUTのdataは以下。GETは当該scopeのカタログ全件へ未保存=trueを合成する。PUTは渡されたキーだけ更新（未指定キー保持）して保存後の全件を返す。更新者情報は一般レスポンスに返さない。

~~~json
{"features":[{"featureKey":"schedule","memberVisible":true,"supporterVisible":false}]}
~~~

PUTは当該scopeのカタログ件数ちょうどまでの全既知キー一括更新を許可し、件数超過は400（未知キー/重複キー検証でも保証する）。PUTのfeatures空配列は正常no-op。features欠落/null、要素null、キー欠落/空/未知/64文字超、bool欠落/null、重複キーは400。boolはDTOでnullable Booleanを受け@NotNullにより欠落を検出する。全要素を検証してから1トランザクションでUPSERTし、途中例外時は全件rollback。空配列でも先にscope認可を行う。未認証401、非所属/権限不足403、存在しない/削除scope404は既存scope解決・認可の順序/秘匿方針を踏襲する。他scopeのIDやslugで設定を取得/更新できない。

scope内全件を1クエリで取得し、機能ごと・widgetごとにDB/APIを呼ばない。PUTも既存行を一括取得しMap化して更新する。初回実装に独自分散キャッシュ・WebSocket配信は追加しない。更新後は該当scopeのFE共有状態を再取得し、別セッションは再読込で反映する。scope/ユーザー切替時は取得キーと状態を分離し、前scopeの設定や遅延応答を適用しない。同時編集は既存widget可視性設定と同じ後勝ちとする。共有キーはscopeType+slug+認証ユーザーで分離し、ログアウト/所属解除でクリアする。切替直後はloadingに戻し、旧GET/PUTの遅延応答はrequest sequence等で破棄する。レンズ変更は再取得せずreactiveに再判定する。

## 7. 受け入れ条件とテスト予定

以下は実装前の予定でありgreenの証跡ではない。試練で実テスト名とred結果を対応づけ、検分時にgreenテスト・PRを戦役台帳へ記録する。

| AC | 検証可能な条件 | テスト予定 |
|---|---|---|
| AC-1 | TEAM/ORGの各機能で4通りのboolを保存・再取得でき、MEMBER/SUPPORTERそれぞれ独立判定する | Service UT: fourCombinations、API IT: roundTrip |
| AC-2 | 未保存scope/キーのGETはtrue/true、既存利用者の表示とwidget設定/順序は維持する | API IT: defaultCompatibility、FE unit |
| AC-3 | 空featuresは認可後200 no-opでDB全列が不変、全既知キー件数ちょうどの一括更新は成功、件数超過/null/欠落/空キー/64超/未知/他scopeキー/重複は400、書込0 | API IT: invalidPayload、emptyNoOp（64文字以内の未知キーも400） |
| AC-4 | 設定OFFと既存認可/module/minRoleのANDが全導線で一致し、trueが権限やモジュールを拡張しない | FE unit: navigationMatrix、widgetMatrix、契約IT |
| AC-5 | 全OFFでもホーム/切替を維持、ADMIN等の通常表示と設定復帰を維持、memberLensだけはMEMBER設定が効く | FE component、実機E2E |
| AC-6 | 本設定PUTはADMIN/SYSTEM_ADMINのみ許可、DEPUTY_ADMIN/MEMBER/SUPPORTERは403、GETは所属SUPPORTER以上、未認証GET/PUTは401 | API ScopeContractIT: roleMatrix |
| AC-7 | 他scope slug、非所属、削除/不存在scopeを使って読取/更新できず、組織/チーム/親子間の設定は独立 | API ScopeContractIT: isolation |
| AC-8 | 複数機能更新中の例外で全件rollbackし、監査成功イベントもコミット前に確定しない | 実MySQL IT: rollbackAll |
| AC-9 | OFF→ONで元データと個人widget設定/順序が戻り、非表示化自体はそれらを書き換えない | API/DB IT、FE unit、実機E2E |
| AC-10 | ユーザー/scope切替と遅延応答で別scope設定が混入せず、取得失敗は既定trueへ黙ってfallbackせず再試行できる | FE unit: switchAndFailure |
