# F10.5: パフォーマンス監視 (Performance Monitoring)

> **ステータス**: 🟢 設計確定
> **実装フェーズ**: Phase 10（段階導入。Section 5 のサブフェーズ参照）
> **最終更新**: 2026-05-07
> **モジュール種別**: 横断インフラ（SYSTEM_ADMIN 専用）
> **関連ドキュメント**: F10.3 監査ログ（記録系の隣接機能）、F10.4 経営分析（業務指標。本機能は技術指標）、F10.6 エラー監視（同時に整備する観測系。アラート発火源として連携）、F12.5 フロントエンドエラー追跡（クライアント側エラー集約。F10.6 とともに本機能の通知対象）

---

## 1. 概要

Mannschaft 本番運用に向け、サーバ側のパフォーマンス（スロークエリ・API レスポンスタイム・キャッシュヒット率・JVM/DB プールリソース）を**継続的に観測・閾値超過で通知**する基盤を整備する。

### 解決する課題

| 課題 | 現状 | 本機能で解決 |
|------|------|------------|
| スロークエリの早期検知 | 把握する仕組みなし。障害発生後にやっと判明 | MySQL `slow_query_log` + Hibernate 統計 + アプリ層 `@Timed` で多層的に検知 |
| API レスポンス劣化の検知 | アクセスログから事後集計するしかない | リクエスト毎に `duration_ms` を MDC 出力 + Micrometer Timer で P50/P95/P99 計測 |
| キャッシュ効果の可視化 | Caffeine の hit/miss が表に出ない | `Caffeine.recordStats()` を有効化し Micrometer に登録 |
| 外部 APM への移行余地確保 | 入り口が無い | Micrometer + `/actuator/prometheus` で APM 中立。Datadog/Grafana/CloudWatch すべてに移行可能 |

### 設計方針

- **既存資産を最大活用**: logback の構造化 JSON 出力（logstash-logback-encoder 8.0）と Spring Boot Actuator は既に導入済み。本機能では Micrometer Prometheus registry を 1 つ追加するだけで PoC を始められる。
- **APM 中立**: Datadog や Grafana Cloud などの外部 APM を最初から強く前提せず、Micrometer の標準計測点を増やす方針に徹する。Prometheus 互換のスクレイプポイントを公開しておけば、後から自由に SaaS 接続できる。
- **段階導入**: Phase 10-α（測定軸の整備）→ Phase 10-β（アラート閾値の運用化）→ Phase 10-γ（外部 APM 接続）と分割する。Phase 10-α だけで「障害の事後解析が可能」状態に持っていく。
- **F10.6 エラー監視と棲み分け**: パフォーマンス指標が閾値を超えたら **F10.6 のアラート発火経路**（Slack 通知）に乗せる。同じ通知基盤を共有することで運用窓口を一本化する。

## 3. DB 設計

### 3.1 新規テーブル

**新規テーブル不要。** メトリクスは Micrometer がメモリ上で時系列保持し、永続化は外部 APM（Prometheus/Datadog/CloudWatch）へ委譲する。スロークエリログは MySQL の `slow_query_log` 機能をそのまま利用し、コンテナのファイルマウントで保管する。

### 3.2 永続化が必要になった場合の方針（Phase 10-γ 以降）

将来、自前で時系列を持つ必要が出た場合は **`/actuator/prometheus` を Prometheus 本体（あるいは Grafana Mimir / VictoriaMetrics）にスクレイプさせる**方式を採る。アプリ側で集計テーブルを持つことはしない（リテンションと集計は時系列 DB の責務）。

### 3.3 MySQL スロークエリログのファイル仕様

| 項目 | 値 |
|------|---|
| ファイルパス | `/var/lib/mysql/mannschaft-slow.log`（コンテナ内） |
| ホスト側マウント | `./logs/mysql-slow/`（docker-compose で永続化） |
| ローテーション | logrotate（毎日・7 世代保持・gzip 圧縮） |
| `long_query_time` | staging: `0.5` 秒、prod: `1.0` 秒 |
| `log_queries_not_using_indexes` | staging のみ `1`、prod は `0`（ノイズ過多回避） |
| `log_slow_admin_statements` | `1`（ALTER 等もスロークエリと見なす） |

## 4. API 設計

### 4.1 エンドポイント一覧

| メソッド | パス | 認証 | 説明 |
|---------|-----|------|------|
| GET | `/actuator/health` | 不要（既存） | ヘルスチェック。本番でも匿名公開 |
| GET | `/actuator/info` | SYSTEM_ADMIN | ビルド情報・git revision |
| GET | `/actuator/metrics` | SYSTEM_ADMIN | Micrometer メトリクス一覧 |
| GET | `/actuator/metrics/{name}` | SYSTEM_ADMIN | 個別メトリクス（タグ展開込み） |
| GET | `/actuator/prometheus` | SYSTEM_ADMIN または内部 NW | Prometheus スクレイプ用テキスト形式 |
| GET | `/actuator/caches` | SYSTEM_ADMIN | キャッシュ名一覧（hit/miss は metrics 経由） |
| GET | `/actuator/threaddump` | SYSTEM_ADMIN | 障害解析用スレッドダンプ |
| GET | `/actuator/loggers` | SYSTEM_ADMIN | 動的ログレベル変更（POST も同 path） |

> **注**: `heapdump` は通常運用では公開しない。必要時のみ kubectl exec などでコンテナ内から取得する運用とする。

### 4.2 認証・公開ポリシー

- `application.yml` で `management.endpoints.web.exposure.include` の値を環境別に制御:
  - prod: `health` のみ匿名 / `info,metrics,prometheus,caches,threaddump,loggers` は SYSTEM_ADMIN 必須
  - staging: 上記すべて SYSTEM_ADMIN 認証下で公開
  - local: すべて認証なしで公開
- Spring Security の `SecurityFilterChain` に `EndpointRequest.toAnyEndpoint().excluding(HealthEndpoint.class)` の SYSTEM_ADMIN ガードを追加する。`/health` のみ `permitAll()` を維持。
- Prometheus 本体からのスクレイプは内部 NW 限定。ALB/CDN レベルで `/actuator/prometheus` への外部 IP からのアクセスを 403 に固定。

### 4.3 メトリクス命名規則（Micrometer 標準 + アプリ独自）

| メトリクス名 | 種別 | タグ | 用途 |
|-------------|------|------|------|
| `http.server.requests` | Timer | `method`,`uri`,`status`,`outcome` | API レスポンスタイム（Spring 標準） |
| `jvm.memory.used` | Gauge | `area`,`id` | ヒープ・メタスペース使用量（Spring 標準） |
| `jvm.gc.pause` | Timer | `cause`,`action` | GC 一時停止時間（Spring 標準） |
| `hikaricp.connections.active` | Gauge | — | DB プール使用数（HikariCP 標準） |
| `hikaricp.connections.usage` | Timer | — | コネクション保持時間 |
| `cache.gets` | Counter | `cache`,`result=hit/miss` | Caffeine キャッシュ統計 |
| `cache.size` | Gauge | `cache` | エントリ数 |
| `mannschaft.slow_query.total` | Counter | `operation` | アプリ層で検知したスロークエリ件数（独自） |
| `mannschaft.business.event` | Counter | `event_type`,`outcome` | 重要ビジネスイベントの件数（独自・段階導入） |

## 5. ビジネスロジック

実装は段階的に進める。Phase 10-α 完了で「事後解析できる」、Phase 10-β 完了で「閾値超過時に通知される」状態を達成する。

### 5.1 Phase 10-α: 計測軸の整備

#### 5.1.1 Micrometer + Actuator 拡張

依存を 1 行追加（`backend/build.gradle.kts`）:

```kotlin
implementation("io.micrometer:micrometer-registry-prometheus")
```

`application.yml` 追加（共通）:

```yaml
management:
  endpoints:
    web:
      exposure:
        include: health,info,metrics,prometheus,caches,threaddump,loggers
  endpoint:
    health:
      show-details: when-authorized
      probes:
        enabled: true
  metrics:
    tags:
      application: mannschaft
    distribution:
      percentiles-histogram:
        http.server.requests: true
      percentiles:
        http.server.requests: 0.5,0.95,0.99
      slo:
        http.server.requests: 100ms,500ms,1s,2s
```

`application-prod.yml` で `exposure.include: health` に絞り、その他は内部 NW 限定で別途有効化する。

#### 5.1.2 API レスポンスタイム計測

Spring Boot Actuator の `http.server.requests` Timer が自動で `method`/`uri`/`status` をタグ付きで記録する。**新規実装は不要**。ただし URI テンプレート展開（`/api/v1/teams/{id}/todos`）でカーディナリティが爆発しないよう、以下を徹底する:

- `@RequestMapping` で URI テンプレートを必ず使う（`{id}` を経路変数として宣言）
- Spring Boot 3.x 標準の `WebMvcMetricsFilter` のデフォルト挙動で `uri` タグはテンプレート化される
- 動的 path（`/files/{uuid}`）が大量にある場合は `WebMvcTagsContributor` で `uri` を集約する

加えて、既存 `RequestLoggingFilter`（`com.mannschaft.app.config.RequestLoggingFilter`）の MDC に `duration_ms` を追加する。出力例（prod 環境の JSON ログ）:

```json
{
  "@timestamp": "2026-05-07T10:30:00.123Z",
  "level": "INFO",
  "message": "request_completed",
  "logger_name": "com.mannschaft.app.config.RequestLoggingFilter",
  "userId": "42",
  "requestId": "a1b2c3d4",
  "traceId": "a1b2c3d4-e5f6",
  "method": "GET",
  "path": "/api/v1/todos",
  "status": 200,
  "duration_ms": 42
}
```

`duration_ms` の閾値:

| 区分 | レベル | 追加処理 |
|------|--------|---------|
| 0 〜 500ms | INFO | 通常記録のみ |
| 500ms 〜 2000ms | INFO（フラグ `slow=true` 付与） | 記録のみ |
| 2000ms 〜 10000ms | WARN | F10.6 経由で Slack 通知（Phase 10-β） |
| 10000ms 超 | ERROR | F10.6 経由で Slack 通知 + `error_reports` テーブルに `severity=HIGH` で記録（自動連携、Phase 10-β） |

#### 5.1.3 スロークエリ検知

**MySQL レベル**:

`docker-compose.yml` の MySQL コンテナに `command` を追加:

```yaml
command: >
  --slow_query_log=ON
  --slow_query_log_file=/var/lib/mysql/mannschaft-slow.log
  --long_query_time=1.0
  --log_queries_not_using_indexes=0
  --log_slow_admin_statements=1
```

ログファイルはホストの `./logs/mysql-slow/` にマウントし、staging/prod では Cloudflare Workers + R2（あるいは外部 APM のログ収集）で吸い上げる。

**Hibernate レベル**（staging のみ）:

`application-staging.yml`:

```yaml
spring:
  jpa:
    properties:
      hibernate:
        generate_statistics: true
        session.events.log.LOG_QUERIES_SLOWER_THAN_MS: 500
logging:
  level:
    org.hibernate.stat.internal.StatisticsInitiator: INFO
```

**アプリ層**:

リポジトリ・Service の重要メソッドに `@Timed("mannschaft.repository.query", extraTags={"operation","TodoRepository.findByTeamId"})` を付与する。Phase 10-α では「全件付与」ではなく重い処理が判明している箇所（Todo 一覧・Schedule 展開・通知集約）から段階的に追加する。

#### 5.1.4 キャッシュヒット率

Caffeine 設定で `recordStats()` を有効化（`CacheConfig` 既存箇所を改修）:

```java
@Bean
public Caffeine<Object, Object> caffeineConfig() {
    return Caffeine.newBuilder()
        .recordStats()
        .expireAfterWrite(Duration.ofMinutes(10));
}
```

Spring の `CacheManager` に `CacheMetricsRegistrarConfiguration` を追加して `cache.gets{result=hit/miss}` を Micrometer に登録する。Spring Boot 3.x では `MeterBinder` が自動構成されるため、`recordStats()` を有効化するだけで十分。

Redis（Valkey）側は `redis-cli INFO stats` の `keyspace_hits` / `keyspace_misses` を `RedisMetricsBinder` 相当（Lettuce 統合）で吸い上げる。Phase 10-α では Caffeine のみ計測対象、Redis は Phase 10-β で追加。

### 5.2 Phase 10-β: アラート閾値の運用化

#### 5.2.1 アラート発火経路

```
[Micrometer 計測点]
    │
    ├─ 即時アラート: ResponseTimeFilter → 閾値超過 → F10.6 ErrorReportNotifier 経由で Slack
    │
    └─ 集計アラート: Prometheus + Alertmanager (外部) → Slack
                         ※Phase 10-γ で外部基盤を導入したら有効化
```

Phase 10-β の段階では **アプリ内で都度判定して通知する経路のみ実装**する。Prometheus/Alertmanager の外部基盤は Phase 10-γ。

#### 5.2.2 即時アラート判定

`ResponseTimeFilter`（`RequestLoggingFilter` を拡張）に閾値判定を加える:

```java
if (durationMs > 10_000) {
    errorReportNotifier.notifySlowRequest(method, path, durationMs, requestId);
}
```

`notifySlowRequest` は F10.6 §5.5 で定義する `ErrorReportNotifier` の新メソッド。同一 path の連続発火を抑制するため Caffeine ベースの 1 分間の集約バッファを噛ませる（同 §5.5 のクールダウンロジックを共有）。

#### 5.2.3 推奨アラート閾値

| 指標 | WARN | ERROR | 通知先 | 備考 |
|-----|------|-------|--------|------|
| API P95 (`http.server.requests`) | > 500ms | > 2000ms | Slack `#alerts-perf` | 単純平均ではなく分位数 |
| API P99 | > 2000ms | > 10000ms | 同上 | スパイク検知用 |
| 単一リクエスト duration | > 2000ms | > 10000ms | 同上 | アプリ内即時判定 |
| スロークエリ件数 | 5件/分 | 30件/分 | Slack | MySQL slow_query_log の集計 |
| キャッシュヒット率 (`cache.gets`) | < 80% | < 50% | Slack | TODO 一覧・通知集約等の典型キー |
| JVM Heap (`jvm.memory.used`) | > 70% | > 90% | Slack + PagerDuty 候補 | OOM 予防 |
| GC pause (`jvm.gc.pause` 95p) | > 200ms | > 1000ms | Slack | チューニングのトリガー |
| HikariCP 使用率 (`hikaricp.connections.active / max`) | > 80% | > 95% | Slack + PagerDuty 候補 | コネクション枯渇予防 |
| 5xx レスポンス率 (`http.server.requests{status=5xx}` の比率) | > 1% | > 5% | Slack | F10.6 と共通 |

これらの閾値は **段階的に妥当値へ調整する**前提とする。Phase 10-β 開始 1 ヶ月後にレビューし、誤検知が多ければ閾値を上方修正する。

### 5.3 Phase 10-γ: 外部 APM 接続（任意・未確定）

Prometheus + Grafana セルフホストか、Datadog / Grafana Cloud / CloudWatch のいずれかに接続する。**この段階での本設計書は「接続口の確保」までを保証**し、具体的な SaaS 選定は本機能の §9 変更履歴に追記する形で運用判断する。

選定の判断軸（参考）:

| 軸 | Prometheus セルフホスト | Datadog | Grafana Cloud | CloudWatch |
|----|---------------------|---------|--------------|------------|
| 月額コスト | 低（インフラ費のみ） | 高 | 中 | 中 |
| 運用負荷 | 高（Prometheus/Alertmanager/Grafana の運用） | 低 | 低 | 中 |
| データ越境 | なし（自社内） | あり（米国リージョン） | あり | AWS 経由 |
| 設定移行コスト | — | 中 | 中 | 中 |
| ログ統合 | Loki 別途 | 一体 | 一体 | CloudWatch Logs |

## 6. セキュリティ考慮事項

### 6.1 Actuator 公開範囲

- prod 環境では `/health` のみ匿名公開（Liveness/Readiness プローブ用）。`/health/details` は `show-details: when-authorized` で SYSTEM_ADMIN にのみ詳細を開示。
- `/info` は git commit hash を含むため SYSTEM_ADMIN 必須。攻撃者にビルド情報を渡さない。
- `/metrics` `/prometheus` `/threaddump` `/loggers` `/caches` は SYSTEM_ADMIN 認証＋内部 NW 限定の二重防御。
- `/heapdump` は通常運用では公開しない（含まれるオブジェクトに PII が混入するリスクが高いため）。

### 6.2 PII リーク防止

- スロークエリログには SQL **引数値**が含まれる可能性がある。引数に氏名・メールアドレス・パスワードハッシュ等の PII が紛れ込むケースを想定し、ログ収集時に**専用のマスキングフィルタ**を通す。
  - マスキング対象キーワード: `email`, `password`, `phone`, `birth`, `address`, `name`, `token`, `secret`
  - フィルタは Cloudflare Workers（Phase 10-γ）または fluent-bit でログ転送する際に適用する
- API レスポンスタイムログの `path` クエリ文字列は記録しない（セッショントークンや検索クエリが PII になる可能性）。`?` 以降を `RequestLoggingFilter` で除去する。

### 6.3 大量送信攻撃 / Actuator スクレイプ濫用

- `/actuator/prometheus` への外部 IP からのアクセスは ALB/CDN レベルで遮断。内部 NW でも秒間 1 回程度のスクレイプ間隔を Prometheus 側で守らせる（`scrape_interval: 30s` 推奨）。
- `/actuator/threaddump` は Bucket4j で 1 リクエスト/分のレートリミットを SYSTEM_ADMIN ユーザーごとに適用（誤操作で連打すると JVM が一時的に重くなるため）。

### 6.4 SYSTEM_ADMIN 認証

Spring Security 上の認可は以下の二段階で実施:

1. JWT アクセストークンに `roles=["SYSTEM_ADMIN"]` クレーム必須
2. `users.role = 'SYSTEM_ADMIN'` を DB で再確認（F10.3 と同じ二段階チェック方針）

トークン偽造耐性のため、JWT 単独に依存せず DB 再照合を必須とする。

### 6.5 監査ログ連携

Actuator の参照操作は **F10.3 監査ログには記録しない**（参照系のみのため。監査範囲外）。ただし `/actuator/loggers` への POST（動的ログレベル変更）は **`SYSTEM_ADMIN_LOGGER_CHANGED` イベント**として F10.3 に記録する。F10.3 §「今後追加予定」に Phase 10 で追加する旨を後続改訂で反映する（本設計書では言及にとどめる）。
