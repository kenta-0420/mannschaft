## 1. 概要

予約枠（`reservation_slots`）に**ライン軸（`line_id`）**を導入し、「どの予約対象（席・ベッド・施術台）の枠か」を枠自体が持てるようにする。あわせて、曜日別の**週間テンプレート**（`reservation_slot_templates`）から**30分セル枠を冪等に一括生成**する仕組みを設計する。一括作成の主軸は**週間テンプレート繰返し**であり、単発の bulk API・ドラッグ範囲選択は採らない（ドラッグは既存実装ゼロのため第三弾任意 — マスター御裁可）。

- **ライン上限を 5 → 20 に拡張**する（§5.6 で妥当性精査・推奨値 20 で確定）。
- 生成の入力に **`reservation_business_hours`（曜日別営業時間）** を使う（現状は宣言のみで slot 生成に未使用 — 実測確認済み。本機能で初めて生成に配線する）。
- 既存の休眠足場（`recurrence_rule` / `parent_slot_id` / `is_exception`）は**流用しない（廃止方針）**。判断根拠は §3.3。

> **過去決定の撤回**: 親 §4 の「`POST /reservation-slots/bulk` は Phase 3 スコープ外」は **2026-07-05 マスター御裁可で正式撤回**。ただし後継は単発 bulk API ではなく本テンプレート方式である。

### 実装事実の追認（設計書ドリフトの是正・実測 2026-07-05）

親 §3 の記述と main 実装に以下のドリフトがある。本枝番は**実装事実を正**として設計する:

| 親 §3 の記述 | main の実態（実測） | 本枝番の扱い |
|---|---|---|
| 「`booked_count` がチームの**有効ライン数**に達したら FULL」 | **V140** で `reservation_slots.capacity`（既定 1）が導入済み。FULL 判定・アトミック UPDATE（`incrementBookedCountIfAvailable` / `decrementBookedCountAndReopen`）は **`capacity` 基準**（有効ライン数は使わない） | capacity 基準を正とし、ライン軸枠は capacity=1 を標準とする（§3.1） |
| `uq_rv_slot_line_active`（同一枠×同一ラインの有効予約 UNIQUE） | **実 DDL に不存在**（V3.062 実測。生成カラム方式は設計のみ）。重複ガードはアプリ層 `existsByReservationSlotIdAndUserIdAndStatusIn`（同一枠×同一ユーザー）のみ | ライン軸導入後の重複制御は「ライン軸枠 capacity=1 のアトミック UPDATE」が主防御（§3.1）。UNIQUE 制約の追加是非は F03.4.3 §5 で扱う |
| 繰り返し枠（`recurrence_rule`）の展開・日次バッチ | **展開実装ゼロ**（`createSlot` が文字列を保存するのみ。バッチ・`is_exception` 更新・親子削除は全て未実装） | 休眠足場は流用せず廃止（§3.3） |

## 3. DB設計

### テーブル一覧（変更・追加）

| テーブル名 | 変更内容 | 論理削除 |
|-----------|------|---------|
| `reservation_slots` | **ALTER**: `line_id`（ライン軸・nullable）+ `template_id`（生成元・nullable）+ インデックス/UNIQUE 追加 | 既存のまま |
| `reservation_slot_templates` | **新規**: 週間テンプレート（UUIDv7） | なし（`is_active` で無効化・物理削除可） |

### 3.1 `reservation_slots` への ALTER（ライン軸＋生成元）

| カラム名 | 型 | NULL | デフォルト | 説明 |
|---------|---|------|-----------|------|
| `line_id` | BIGINT UNSIGNED | YES | NULL | **ライン軸**。FK → `reservation_lines.id` **ON DELETE RESTRICT**（同一ドメイン内FK・クロスドメインではない）。**NULL = 共通枠 = 既存互換**（従来の全枠は NULL のまま） |
| `template_id` | BINARY(16) | YES | NULL | 生成元テンプレート。FK → `reservation_slot_templates.id` **ON DELETE SET NULL**（同一ドメイン。テンプレ物理削除後も生成済み枠は独立して残す）。NULL = 手動作成枠 |

**インデックス・制約（追加）**
```sql
INDEX idx_rs_team_date_line (team_id, slot_date, line_id)          -- ライン軸グリッド・空き検索
UNIQUE KEY uq_rs_template_cell (template_id, slot_date, start_time) -- 生成冪等の最終防御（§5.3）
```

**設計判断の根拠（明記）**

1. **`line_id` は nullable・既存 slot / 既存チームの backfill はしない**。
   - 既存の全 slot は `staff_user_id` 軸（または共通枠）で運用されており、「その枠がどのラインか」を機械的に復元する情報が存在しない（予約行の `line_id` は「ユーザーが選んだライン」であって枠の帰属ではない）。誤った backfill は既存予約の表示・グリッドを壊すため、**backfill しないことを宣言**する。
   - `line_id IS NULL` の枠は従来どおり「共通枠」（予約時にユーザーがラインを選ぶ）。ライン軸枠（`line_id` 非 NULL）は「そのライン専用の枠」（予約時のライン選択は枠から自動決定）。両者は無期限に併存できる（挙動後退ゼロ）。
2. **`line_id` の FK はクロスドメインではない**。`reservation_slots` と `reservation_lines` はともに reservation ドメイン。アーキ原則1（クロスドメインFK禁止）の対象外であり、同一ドメイン内の整合は FK で守る（`reservations.line_id` → `reservation_lines` の既存 FK と同じ判断）。RESTRICT はラインの物理削除防止の番人（運用は論理削除）。
3. **capacity との関係（V140 追認）**: ライン軸枠は「1ライン=1資源」なので **capacity=1 を標準**とする（テンプレの `capacity` 既定 1）。共通枠は従来どおり任意の capacity。FULL 判定・並行制御は既存のアトミック UPDATE 2 本（`incrementBookedCountIfAvailable` / `decrementBookedCountAndReopen`・capacity 基準）を**そのまま使う**（変更しない。F03.4.3 が N 枠ループで流用する）。
4. **`staff_user_id` と `line_id` の併存**: 両軸は排他にしない（ライン軸枠に担当スタッフを併記できる: 例「席1・田中」）。機能B（予約不可枠）の STAFF 軸判定・機能C グリッドの staff 列はそのまま動く（§5.7 波及棚卸し）。

### 3.2 `reservation_slot_templates`（新規）

チームの週間パターン定義。**1行 = 1曜日 × 1連続時間帯 × 1ライン（または共通）**。「週間テンプレート」はチームのテンプレ行の集合であり、生成時に 30 分セルへ分割される（§5.2）。

**新規テーブルのため主キーは UUIDv7（アーキ原則6・`UuidV7Entity` 継承）。`team_id`/`created_by` はクロスドメイン参照のため FK なし（アーキ原則1）。**

| カラム名 | 型 | NULL | デフォルト | 説明 |
|---------|---|------|-----------|------|
| `id` | BINARY(16) | NO | UUIDv7 | PK |
| `team_id` | BIGINT | NO | — | チームID（FKなし・INDEX） |
| `name` | VARCHAR(100) | YES | NULL | テンプレ名（管理用メモ。例「平日午前・席1」）。NULL 可（曜日＋時間で自動表示） |
| `line_id` | BIGINT UNSIGNED | YES | NULL | 対象ライン。FK → `reservation_lines.id` ON DELETE RESTRICT（同一ドメイン）。**NULL = 共通枠テンプレ** |
| `day_of_week` | VARCHAR(3) | NO | — | 曜日（`MON`〜`SUN`。`reservation_business_hours.day_of_week` と同一表現） |
| `start_time` | TIME | NO | — | 帯の開始（30分単位: `:00` / `:30`） |
| `end_time` | TIME | NO | — | 帯の終了（30分単位・`start_time` より後） |
| `capacity` | INT | NO | 1 | 生成する各セル枠の定員（V140 の `capacity` へコピー）。ライン軸テンプレは 1 を標準 |
| `staff_user_id` | BIGINT | YES | NULL | 生成枠の担当スタッフ（任意・FKなし=usersドメイン参照）。NULL = 担当なし |
| `title` | VARCHAR(200) | YES | NULL | 生成枠の `title` へコピー（任意） |
| `price` | DECIMAL(10,2) | YES | NULL | 生成枠の `price` へコピー（表示用・任意） |
| `approval_mode` | VARCHAR(10) | YES | NULL | 生成枠の枠単位承認モード上書きへコピー。NULL = チーム既定（親 §3 の解決規則） |
| `is_active` | BOOLEAN | NO | TRUE | FALSE のテンプレは生成対象外（既生成枠は不変） |
| `created_by` | BIGINT | YES | NULL | 作成者（FKなし） |
| `created_at` | DATETIME(6) | NO | — | |
| `updated_at` | DATETIME(6) | NO | — | |

**インデックス**
```sql
INDEX idx_rst_team (team_id, day_of_week, start_time)   -- チーム別テンプレ一覧・生成スキャン
INDEX idx_rst_line (line_id)                              -- ライン削除時の参照チェック
```

**制約・備考**
- **上限: 1チームあたり最大 500 行**（RESERVATION_037）。試算根拠: 20ライン × 7曜日 × 帯3本/日 = 420 行 < 500（フル運用チームを包含しつつ生成暴走を防ぐ）。
- `start_time`/`end_time` は 30 分単位・`start < end`・最小 30 分（既存の枠バリデーション `INVALID_TIME_RANGE`=007 / `INVALID_SLOT_GRANULARITY`=022 を**再利用**。テンプレ専用コードは設けない）。
- **同一 (team, line_id, day_of_week) 内の時間帯重複は 400**（Service 層検証・再利用 007）。重複テンプレは同一セルを二重生成しようとして UNIQUE 制約エラーになるため入口で止める。共通枠テンプレ（line_id NULL）同士の重複は**許可**（既存の「共通枠同士の重複許可」と整合・親 §3）。
- 定休日（`reservation_business_hours.is_open=FALSE`）の曜日のテンプレ**作成は許可**する（後で営業日に変わる運用があるため）。生成時にスキップされるだけ（§5.2）。既存親設計の「定休日曜日の繰り返し作成は 400」より緩和し、**チェックは生成時の一点に集約**する（二重管理しない）。

### 3.3 休眠足場（`recurrence_rule` / `parent_slot_id` / `is_exception`）の扱い — **廃止（不流用）を確定**

**実コード確認結果（2026-07-05 実測）**:
- `recurrence_rule`: `CreateSlotRequest.recurrenceRule`（String）→ `createSlot` がエンティティへ**保存するのみ**。展開ロジック・日次バッチ・`generated_slots_count` 応答は**一切実装されていない**。FE の予約系コンポーネントから送信している箇所もない（`SlotFormDialog.vue` 等に参照なし・型定義のみ）。
- `parent_slot_id`: リポジトリに `findByParentSlotIdOrderBySlotDateAsc` が宣言されているが**呼び出し元ゼロ**。self-FK（ON DELETE RESTRICT）だけが存在。
- `is_exception`: 常に既定 FALSE で INSERT され、TRUE にする経路が存在しない。

**判断: 機能F はこの3点を流用せず、テンプレート方式（別テーブル）を正とする。**

| 観点 | 休眠足場の流用（不採用） | テンプレート方式（採用） |
|---|---|---|
| 管理 UI | ルールが slot 行の JSON に埋まり、一覧・編集・無効化の UI 操作に不向き | テンプレは独立行。一覧・編集・ON/OFF が素直な CRUD |
| ライン軸 | 親枠複製方式では「20ライン×曜日別」の帯定義が親枠の爆発になる | 1行=曜日×帯×ラインで正規化 |
| 例外編集 | `is_exception`/THIS_AND_FOLLOWING の伝播実装が丸ごと必要（実装ゼロから） | 生成後の枠は**独立した通常枠**。個別編集は既存の枠 CRUD がそのまま使える（伝播概念なし） |
| 削除連鎖 | self-FK RESTRICT で親削除が子に阻まれる運用複雑性 | `template_id` は SET NULL。テンプレ削除で枠は孤立せず残る |
| 冪等 | `uq_rs_parent_date` は未作成（実DDL不存在） | `uq_rs_template_cell` を新設（§5.3） |

**廃止の実施内容**:
1. **第一弾**: `CreateSlotRequest.recurrenceRule` を OpenAPI から削除（`@Schema(deprecated)` を経ず即削除。FE 送信箇所ゼロ・保存されても機能しない dead input のため破壊なし）。`createSlot` の `recurrenceRule` 保存行を削除。
2. **カラム自体（`recurrence_rule`/`parent_slot_id`/`is_exception`）と self-FK は残置**（DROP しない）。理由: 既存行のデータ保全・DROP は後戻り不能でリスクに見合う利益がない。将来のクリーンアップ migration（別 PR・要裁可）で DROP を検討する旨を親 §8 バックログに残す。
3. リポジトリの未使用メソッド `findByParentSlotIdOrderBySlotDateAsc` を削除。
4. 親 §3 の「繰り返しルール（recurrence_rule）」節は**将来形として据え置き**（本枝番が正であることを親の枝番一覧から辿れる）。

### 3.4 `reservation_lines` 上限 5→20

DDL 変更なし（`display_order INT` のまま・範囲制約は Service 層）。変更点:

| 箇所 | 変更 |
|---|---|
| `ReservationLineService.MAX_LINES_PER_TEAM` | `5L` → `20L`（実定数・実在確認済み） |
| `display_order` 許可範囲 | 1〜5 → **1〜20**（`MIN_DISPLAY_ORDER`/`MAX_DISPLAY_ORDER`） |
| `ReservationErrorCode.LINE_LIMIT_EXCEEDED`（024）のメッセージ | 「最大5本」→「最大20本」（コードは再利用・番号変更なし） |
| `INVALID_DISPLAY_ORDER`（025）のメッセージ | 「1〜5」→「1〜20」 |
| i18n（`reservation.*` の上限文言） | 6言語で 5→20 |
| 親 §1/§2/§3 の「最大5本」記述 | 本枝番を正とする（親は枝番一覧から参照） |

**推奨値 20 の妥当性精査（確定根拠）**:
1. **業態カバレッジ**: 飲食テーブル数（小規模店 5〜15 卓）・美容室セット面（3〜12 席）・整骨院ベッド（3〜10 台）・マンション共用施設（2〜8 室）の P90 を包含。20 超が必要な業態（大型飲食・複合施設）はチーム分割（フロア別・施設別）が運用上も自然。
2. **マトリックスUI の実用限界**: 列=時間軸の場合、縦に並ぶ「日付×予約対象」行が 7日×20ライン=140 行が描画・スクロールの実用上限（F03.4.4 §5 のモバイル横スクロール規約と両立）。
3. **生成行数**: §11 の試算どおり 20 ラインのフル運用でも horizon 内 slot 行はチームあたり約 1.3 万行で、`(team_id, slot_date)` インデックス下の日次クエリは数百行に収まる。
4. **50 や 100 にしない理由**: 上限は後から上げるのは容易だが下げるのは既存データがあると不可能。UI 実用限界と業態 P90 を満たす最小の切りの良い値として 20 で確定する。

## 5. ビジネスロジック

### 5.1 実装方針（クラス構成）

| 層 | 新規クラス | 役割 |
|---|---|---|
| Controller | `ReservationSlotTemplateController` | §4 の 5 エンドポイント |
| Service | `ReservationSlotTemplateService` | テンプレ CRUD・重複/上限検証 |
| Service | `ReservationSlotGenerationService` | **生成の単一実装**（手動 generate と日次バッチの両方が呼ぶ・別実装厳禁） |
| Batch | `ReservationSlotGenerationBatchService` | `@Scheduled(cron = "0 15 0 * * *")`（日次 AM 0:15 JST）＋ `@SchedulerLock`（多重起動防止・既存 `ReservationReminderDispatchBatchService` の写経） |
| Entity/Repo | `ReservationSlotTemplateEntity extends UuidV7Entity` / `ReservationSlotTemplateRepository` | `countByTeamId` / `findByTeamIdAndIsActiveTrue` / `findDistinctTeamIds`（バッチの対象チーム列挙） |

- 繰り返し展開の date 反復は `ScheduleRecurrenceService.expandRecurrenceSchedules` の曜日反復（WEEKLY・daysOfWeek）を**写経**する。ただし schedule の RecurrenceRule JSON は持たず、テンプレ行の `day_of_week` を直接使う（endType/endDate/count の概念は horizon に置換されるため不要）。
- 更新スコープ（THIS_ONLY/THIS_AND_FOLLOWING/ALL）は**導入しない**: 生成後の枠は独立した通常枠で、伝播概念がない（§3.3 の設計判断）。

### 5.2 生成アルゴリズム（セル分割・営業時間突合）

```
generate(teamId, weeks):
  horizon = [tomorrow, tomorrow + weeks*7 - 1]          # 当日は生成しない（当日枠は手動作成の領分）
  businessHours = getBusinessHours(teamId)               # 曜日→(is_open, open_time, close_time)
  templates = findByTeamIdAndIsActiveTrue(teamId)
  for date in horizon:
    dow = dayOfWeek(date)
    bh = businessHours[dow]
    for tpl in templates where tpl.day_of_week == dow:
      if not bh.is_open: skip（skippedClosedDayCount += cellCount）      # 定休日
      for cellStart in [tpl.start_time, tpl.end_time) step 30min:       # ★30分セル分割
        cellEnd = cellStart + 30min
        if cellStart < bh.open_time or cellEnd > bh.close_time:
          skip（skippedOutsideHoursCount++）                             # 営業時間外セル
        if exists slot(template_id=tpl.id, slot_date=date, start_time=cellStart):
          skip（skippedExistingCount++）                                 # 冪等（§5.3）
        INSERT reservation_slots(
          team_id, line_id=tpl.line_id, staff_user_id=tpl.staff_user_id,
          template_id=tpl.id, slot_date=date,
          start_time=cellStart, end_time=cellEnd,
          capacity=tpl.capacity, title=tpl.title, price=tpl.price,
          approval_mode=tpl.approval_mode, created_by=<実行者 or NULL(バッチ)>)
        generatedCount++
```

- **30分セル分割が標準**: テンプレの帯（例 10:00〜13:00）は 30 分セル 6 枠に分割して生成する。マトリックスUI（F03.4.4）と予約グループの連続確保（F03.4.3）は 30 分セルを前提とするため。手動作成の長尺枠（60分等）は従来どおり作成可能だが、メニュー連続確保の対象外（単枠予約のみ・F03.4.3 §5）。
- **予約不可枠（機能B）は生成時にチェックしない（確定方針）**: 機能B の enforcement は「runtime overlap ユーティリティ1本」（親 §5.B・別実装厳禁）。生成時にもスキップすると「ブロック解除後に枠が存在しない」穴と二重管理が生じる。枠は生成し、表示/予約時に runtime 判定で落とす（既存 3 箇所の判定がそのまま効く）。
- **営業時間の後変更**: 生成済み枠への遡及 CLOSE は行わない（既存実装も `BUSINESS_HOURS` 自動 CLOSE は未配線 — 親 §8 バックログの範疇）。生成時点の営業時間だけを入力に使う。
- **トランザクション**: 生成はチーム単位で 1 tx（最大試算 3,360 INSERT・§11）。バッチは行単位 try/catch ではなく**チーム単位** try/catch（1チームの失敗が他チームを巻き込まない・`log.error` で正直に記録）。

### 5.3 冪等性（同一テンプレ再生成で重複枠を作らない）

- **一意キー**: `UNIQUE KEY uq_rs_template_cell (template_id, slot_date, start_time)`。
  - 1テンプレ行は 1 日に同じ `start_time` のセルを 1 つしか作らないため、この 3 つ組で生成セルが一意になる。
  - `template_id IS NULL`（手動枠）は MySQL の UNIQUE 仕様（NULL は重複比較で distinct）により**制約の対象外**＝手動枠の自由度を奪わない。
- **スキップ規則（アプリ層一次判定）**: INSERT 前に `existsByTemplateIdAndSlotDateAndStartTime` で存在チェックしてスキップ。並行実行（手動 generate と日次バッチの競合）で存在チェックをすり抜けた場合は **UNIQUE 制約違反を捕捉してスキップ扱い**（DB が最終防御。`DataIntegrityViolationException` → skippedExistingCount。エラーにしない）。
- **テンプレ変更後の再生成**: テンプレの時刻・capacity を変更しても**既生成枠は更新しない**（予約が入っている可能性があり、黙って変えると予約者との合意を壊す）。変更後の初回生成から新定義が効く。既生成の未予約枠を新定義に合わせたい場合は「未来の未予約枠を削除（既存枠 DELETE・active 予約ありは既存 409=RESERVATION_020）→ 再生成」の明示 2 操作（UI にこの手順をガイド表示: i18n `reservation.template.regenerate_guide`）。
- **`slot_date`+`start_time` が同じでもテンプレが異なれば別枠**: 同一ライន同一時刻の二重定義はテンプレ作成時の重複検証（§3.2）で入口拒否するため、実運用では発生しない（共通枠テンプレ同士は許可＝意図的な並行枠）。

### 5.4 日次バッチ（horizon 延伸）

- `@Scheduled(cron = "0 15 0 * * *", zone = "Asia/Tokyo")` + `@SchedulerLock(name = "reservationSlotGeneration")`。リマインドバッチ（1分間隔）と時間帯を分離。
- 対象: `reservation_slot_templates` に active 行を持つ全チーム（`findDistinctTeamIds`）。各チームについて §5.2 を `weeks=4` で実行 → 常に「明日から28日先」までが埋まっている状態を維持（rolling horizon）。
- 冪等キーにより毎日全量走査しても新規 INSERT は「horizon の末尾 1 日分」だけになる。
- `@Scheduled`＋`@Transactional` 境界は最小 context 実起動の番人テストで恒久検証（既存 `ReservationReminderDispatchBatchServiceContextTest` の写経・親 §3 の既知地雷対策）。

### 5.5 ライン削除フローへの追記（機能E 連動）

親 §3「ライン削除: 未来の予約が存在する場合は論理削除不可（409）」に加えて:
1. **未来のライン軸枠（`line_id = 対象ライン` かつ `slot_date >= 今日` かつ active 予約なし）が存在する場合も 409**（枠が先・メッセージで「先にこのラインの枠を削除してください」を案内。SLOT_HAS_ACTIVE_RESERVATIONS=020 とは別事由のため既存 409 事由に追記）。
2. ライン論理削除の成功時、**当該ラインを参照する `reservation_menu_lines` 行をアプリ層で削除**（F03.4.1 §3 の RESTRICT 判断に対応する明示削除）。当該ラインを `line_id` に持つテンプレは `is_active=FALSE` へ自動更新（生成停止・行は残して復元可能に）。

### 5.6 既存 FULL 判定・アトミック UPDATE への波及（棚卸し）

| 既存資産 | 波及 | 対応 |

| `incrementBookedCountIfAvailable` / `decrementBookedCountAndReopen`（capacity 基準・実在確認済） | **変更なし**。ライン軸枠も capacity=1 の同一経路 | F03.4.3 が N 枠ループで呼ぶ（同一tx） |

## 6. セキュリティ考慮事項

- **認可 self-gate**: テンプレ CRUD・generate の全 5 本に `@PreAuthorize("@accessGuard.isScopeAdmin(authentication, #teamId, 'TEAM')")` を実装者が付与（親 §6 方針）。
- **IDOR**: `{templateId}` は `findByIdAndTeamId` 解決・他チームは 404（RESERVATION_036）で秘匿。
- **生成の資源保護**: generate は同期実行で最大約 3,360 INSERT/チーム（§11）。`weeks` 上限 4・テンプレ上限 500 行・チーム単位 tx で暴走を構造的に抑止。レートリミット: generate は `Bucket4j` で 1 チーム 1 分間に 2 回まで（親 §6 のレートリミット方針に追加）。
- **監査ログ**: テンプレの作成・更新・削除・generate 実行（件数付き）を `audit_logs` に記録。
- **PII**: テンプレは PII を含まない（staff_user_id は内部 ID・レスポンスの staffName は管理画面のみ）。

## 8. 受け入れ条件（テスト可能・正常/異常/境界）

- **F-1（正常・テンプレ作成）**: ADMIN が `lineId=1, dayOfWeek=MON, 10:00-13:00` で POST すると 201・`cellCount=6`。**観測点**: `reservation_slot_templates` に 1 行（BINARY(16) PK・line_id=1）。
- **F-2（境界・時刻検証）**: `10:15-11:00`（非30分グリッド）は 400=022、`10:00-10:00` は 400=007。既存コード再利用のため新コードが増えないこと。
- **F-3（境界・上限）**: テンプレ 499 行のチームで 500 行目 POST は 201、500 行のとき 501 行目は 400=RESERVATION_037。
- **F-4（異常・重複帯）**: 同一 (lineId=1, MON) に `10:00-13:00` がある状態で `12:00-14:00` POST は 400（時間帯重複）。共通枠テンプレ（lineId NULL）同士の同時間帯は 201（許可）。
- **F-5（正常・生成）**: MON `10:00-13:00`×lineId=1 のテンプレ 1 行で `generate(weeks=1)` すると、horizon 内の月曜 1 日について 30 分セル 6 枠が INSERT される。**観測点**: `reservation_slots` に `line_id=1, template_id=<tpl>, capacity=1` の 6 行、`start_time` が 10:00/10:30/11:00/11:30/12:00/12:30。
- **F-6（冪等）**: F-5 の直後にもう一度 `generate(weeks=1)` を実行しても新規 INSERT は 0 件（`skippedExistingCount=6`）。**観測点**: slot 行数不変・レスポンスのカウント。並行実行の UNIQUE 違反はエラーでなくスキップ扱い。
- **F-7（営業時間突合）**: 定休日（`is_open=FALSE`）の曜日はセルを生成しない（`skippedClosedDayCount` 加算）。営業時間 `9:00-12:00` の日にテンプレ帯 `10:00-14:00` は 10:00〜12:00 の 4 セルのみ生成し、12:00 以降は `skippedOutsideHoursCount` 加算（境界: `close_time` ちょうどで終わるセルは生成される＝半開でなく「セル全体が営業時間内」判定）。
- **F-8（遡及なし）**: テンプレの `startTime` を変更後に再生成しても、既生成枠は不変で新定義のセルだけが追加される。テンプレ DELETE 後、生成済み枠は `template_id=NULL` で残る（`orphanedSlotCount` が枠数と一致）。
- **F-9（日次バッチ）**: バッチ実行で horizon が翌日分だけ延伸される（前日実行済み環境で新規 INSERT = 1 日分のみ）。`@SchedulerLock` により多重起動しない。ApplicationContext 起動の番人テスト（`@EnableScheduling` 最小 context）が green。
- **F-10（ライン上限 5→20）**: ライン 19 本のチームで 20 本目 POST は 201、20 本のとき 21 本目は 400=024（メッセージ「最大20本」）。`display_order=20` は有効・`21` は 400=025。
- **F-11（ライン軸枠の後方互換）**: `line_id=NULL` の既存枠は従来どおり一覧・予約・グリッドに現れる（既存 E2E/UT が無修正で green）。ライン軸枠は `listAvailableSlots`/`getSlot` レスポンスに `lineId`/`lineName` が載る。
- **F-12（recurrenceRule 廃止）**: `CreateSlotRequest` に `recurrenceRule` を送っても無視される（フィールド削除・unknown property は Jackson 既定で無視）。OpenAPI から当該フィールドが消えている。
- **F-13（認可）**: テンプレ CRUD/generate は非 ADMIN で 403・未認証で 401・他チーム templateId は 404=RESERVATION_036。

## 9. エラーコード（採番仮置き）

> `ReservationErrorCode` 最大 = **RESERVATION_031**（実 enum 確認済 2026-07-05）。v2 通し採番の F03.4.2 分。**マージ直前に enum 実物で再確認**。

| コード | 定数名（案） | 用途 | HTTP | Severity |
|---|---|---|---|---|

## 11. 非機能・アーキ制約

- **生成枠数の上限見積り**: 最悪ケース = 20ライン × 12時間営業（24セル/日）× 7日 × 4週 = **13,440 slot 行/チーム（horizon 内）**。テンプレ上限 500 行 × 4 週 × 平均 6 セル/行 ≒ 同水準で頭打ち。
  - `(team_id, slot_date, line_id)` インデックス下で日次画面クエリは最大 480 行（20ライン×24セル）に収まり性能問題なし。
  - 全体規模: 1 万チームがフル運用しても 1.3 億行/28日。**予約が紐づかない過去枠の物理削除バッチ（slot_date が 90 日超過去・active/終端予約なし）を第二弾で導入**し、テーブルの無限成長を防ぐ（アーキ Phase 3 パーティショニングの前段）。予約が紐づく過去枠は履歴のため残す。
- **UUIDv7（アーキ原則6）**: `reservation_slot_templates` は UuidV7Entity。`reservation_slots` は既存 BIGINT のまま（原則6「既存テーブルの ID は変更しない」）。
- **クロスドメインFK禁止（原則1）/ CASCADE 同一ドメインのみ（原則2）**: 新規 FK（line_id/template_id）はいずれも reservation ドメイン内。CASCADE は使わず RESTRICT/SET NULL。
- **@Transactional ドメイン内（原則5）**: 生成は reservation ドメインに閉じる（business_hours も同ドメイン）。
- **シャーディング**: テンプレ・枠とも `team_id` を持ち、将来の organization_id シャードキー移行時はチーム→組織解決の一括 backfill で対応（新規表に organization_id を今持たせないのは既存 reservation 系テーブルとの整合を優先）。
- **OpenAPI**: BE 変更後に `docs/openapi.json` 再生成＋`npm run generate:types` を同一 PR で（`project_openapi_json_chronic_drift`）。
