# F10.1.1 / 05: 論点と決定

> **ステータス**: 🟢 設計確定
> **最終更新**: 2026-06-17
> **関連**: [README.md](./README.md)

設計上判断を要した論点と、その決定・根拠を記録する。宙ぶらりんの「要検討」は残さない。

## §1. 横スワイプに第4タブ『管理』を作るか、レンズ切替にするか

**決定**: レンズ切替（チーム/組織パネル内のトグル）。第4タブは作らない。

**根拠**:
- F22.1 の横スワイプの軸は「スコープ（個人/チーム/組織）」という単一の概念で確定している。ここに「管理」を第4タブとして足すと、軸が「スコープ ∪ 視点」という異種混合になり、循環スワイプ（個人→チーム→組織→個人）の意味論が壊れる。
- 「管理者表示」は**スコープ（どのチーム/組織か）を選んだ上での視点切替**であり、スコープと直交する。直交概念はタブ（同一軸の並び）ではなくトグル（軸に対する修飾）で表すのが UX 的に正しい。
- マスター御裁可（背景）でもレンズ切替方式が確定済み。

**却下案**: 第4タブ『管理』を追加 → 軸混合・循環破綻のため却下。

## §2. F10.1 を分割するか、母体に章追加するか

**決定**: F10.1 母体は維持（システム管理章を温存）し、冒頭にスコープ整理（A/B 棲み分け）を追記したうえで、チーム/組織管理コンソールの詳細は**新規ディレクトリ `F10.1.1_team_org_admin_console/`** に分割（F22.1 形式）。

**根拠**:
- F10.1 は既に 1743 行あり、通報・モデレーション・システム管理（AB）で密度が高い。ここに L1/L2/L3＋新 API を全文追記すると 2500 行超になり可読性が崩壊する。
- F22.1 が README + 01〜04 の分割で成功している前例がある。同形式に倣う。
- F10.1 母体には「本ドキュメントのスコープ」表に A=F10.1.1 への参照を1行追記するだけで、既存のシステム管理設計（実装済み Controller 群への参照含む）を壊さない。

**却下案**: F10.1 に直接全章追記 → 肥大化で却下。F10.1 を全面分割（F10.1 自体をディレクトリ化）→ 既存被リンク（多数の設計書が `F10.1_admin_dashboard.md` を参照）破壊リスクが大きく、システム管理章まで巻き込むため却下。

## §3. 承認待ち集約をメンバー向け action-required に相乗りさせるか、別 API にするか

**決定**: 別 API（`admin-action-required`）・別ファサード（`AdminActionRequiredFacade`）。

**根拠**:
- 視点が根本的に異なる（「私が回答すべき」vs「管理者が承認すべき」）。認可も MEMBER 以上 vs ADMIN/DEPUTY で異なる。
- 相乗りさせると、メンバー向け `ScopeActionRequiredFacade` に管理者専用の認可分岐が混入し、F00 の per-scope 認可（回覧の閲覧権がない人に 0 件）と管理者の承認待ち（ADMIN なら全部見える）が同一ファサードで衝突する。
- 集約元ドメインも異なる（メンバー=回覧/アンケ/出欠、管理者=予約/シフト/マッチング/支払/入会）。

**却下案**: 既存 `action-required` に `?as=admin` パラメータで分岐 → 認可・集約元の二重ロジック混入で却下。

## §4. DEPUTY の予算ゲートを ORG 専用メソッドだけで賄えるか

**決定**: ORG は既存 `checkAdminOrHasPermission`（ORGANIZATION 専用）を使う。TEAM は `isAdmin || hasPermission(... "TEAM" ...)` の明示判定で代替する。将来 `checkAdminOrHasPermission` のチーム対応一般化を候補として記録。

**根拠**:
- 偵察で `checkAdminOrHasPermission` が現状 ORGANIZATION 専用であることを確認済み。チームスコープの予算ウィジェットにも DEPUTY 細粒度ゲートが必要なため、`AccessControlService` の既存プリミティブ（`isAdmin` / `hasPermission`）を組み合わせて同等の判定を実現する。
- メソッドのチーム対応一般化は本機能のスコープ外の基盤改修になり得るため、明示判定で先行し、基盤側の一般化は別タスクで扱う（リスクを本機能に持ち込まない）。

**却下案**: 本機能で `checkAdminOrHasPermission` をチーム対応に書き換える → 認可基盤の挙動変更は影響範囲が広く、本機能の検分で安全性を保証しきれないため却下（明示判定で同等の安全性を確保できる）。

## §5. 既存 settings/member ルートを物理移設するか、リダイレクト/導線追加か

**決定**: member-*（被リンク多）はリダイレクト、settings-*（被リンク少）は導線追加。物理移設はしない。

**根拠**:
- 物理移設（ファイル階層変更）は import パス・E2E・通知ディープリンクを広範に破壊する（メモリ `project_slug_e2e_open_issues` の [id]→[slug] 移設で多層破壊が起きた前例）。
- 「散在解消」の目的は、ハブ index からのリンク集約＋旧パスからの転送で達成できる。各ページの実装を触らないため回帰リスクが最小。
- リダイレクトと導線追加は段階適用（P2 で導線、P4 でリダイレクト＋E2E）し、E2E 破壊を後段に隔離する。

## §6. 新規テーブルは必要か

**決定**: 不要。Flyway マイグレーションなし。

**根拠**:
- 承認待ちは各ドメインの既存テーブル（reservations.status 等）の集計で取れる。
- L1 レンズの状態（adminLens トグル）は `localStorage` で十分（DB 保存すると退会時 PII フローへの追加対応が発生し、得るものがない）。
- ウィジェット可視性は既存 `dashboard_widget_settings` / `dashboard_widget_role_visibility`（F02.2.1）に `ADMIN_*` キーを格納するだけで足り、テーブル変更不要。
- よって本機能は「既存 API のハブ集約＋新規読み取り集約 API＋FE 再編」に閉じ、新規テーブル原則（UuidV7Entity 等）の適用対象が発生しない。
