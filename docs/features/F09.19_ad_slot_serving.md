> **ステータス**: 🟡 設計中
> **実装フェーズ**: Phase 12（第1弾 = 運用型完成 / 第2弾 = 予約型は方針章のみ）
> **最終更新**: 2026-07-07
> **モジュール種別**: デフォルト機能（広告表示・広告主共通）
> **関連ドキュメント**: F09.7 広告表示（アフィリエイト・placement 語彙）、F09.11 広告主ダッシュボード（アカウント・課金）、F09.17 広告主ターゲット配信キャンペーン（BANNER チャネル）、F02.6 お知らせウィジェット（IN_FEED 掲載面）、F10.3 監査ログ

## 1. 概要

F09.19 は、F09.7（アフィリエイト表示）・F09.11（広告主アカウント/課金）・F09.17（メッセージ型キャンペーン）の 3 系統を**掲載面（広告枠）で束ねる横断サービング機構**の正本である。

2026-07-07 時点の実装は「広告を作る側」（広告主登録・クリエイティブ・請求・審査）が先行して完成している一方、以下の 3 つの欠落環により「出稿 → 掲載 → 計測 → 課金」のループが閉じていない。F09.19 第1弾はこの 3 点を充填する。

| # | 欠落環 | 現状（origin/main 裏取り済み） |
|---|---|---|
| 1 | **掲載面が無い** | BANNER チャネル・バナークリエイティブは作成できるが、フロントにライブ配信・表示するコンポーネントが存在しない。ダッシュボード末尾の広告タイルは楽天/Amazon リンクのハードコード（`WidgetAmazonAd.vue` / `WidgetRakutenAd.vue`） |
| 2 | **運用型キャンペーンの作成 API が無い** | `ad_campaigns`（CPM/CPC）へ INSERT するプロダクションコードがゼロ。広告主はクリエイティブ CRUD しか持たず、親キャンペーンを作る手段が無い |
| 3 | **日次集計バッチが無い** | `ad_daily_stats` を書き込むバッチが存在しない（読むバッチのみ）。月次請求 `MonthlyInvoiceBatchService` の集計元が常に空 |

### 購入モデル: ハイブリッド（マスター御裁可 2026-07-07）

| 弾 | モデル | 本書での粒度 |
|---|---|---|
| **第1弾（本設計）** | **運用型**: CPM/CPC × 日予算。placement を指定して出稿し、空き枠に都度配信される | 実装可能な詳細粒度（DDL・API 契約・画面仕様・受け入れ条件） |
| **第2弾（将来）** | **予約型**: placement × 期間の枠買い切り。在庫管理・予約カレンダー・売り切れ制御・保証インプレッション | 設計方針レベル（§13） |

### スコープ外

- **レベニューシェア（掲載面オーナーへの収益分配）** — 組織/チームページに他社広告が表示される側への分配は、出金・資金移動を伴い資金決済法の法務論点（F18 残高凍結と同系統）を含むため**今回は見送り**。プラットフォーム総取りを前提とし、将来課題として §14 に記録する
- eCPM オークション / リアルタイム入札（§14）
- 第三者アドネットワーク（AdSense 等）の組み込み

## 3. placement 統一語彙

placement は `AdPlacement` enum（`com.mannschaft.app.advertising.AdPlacement`）を全系統（`affiliate_configs.placement` / `ads.placement` / `ad_messaging_campaign_channels.placement`）の正とする。DB 格納は全テーブル VARCHAR(30) のため enum 追加に DDL 変更は不要。

| placement | 掲載面 | 掲載面の実装状態（第1弾完了時） |
|---|---|---|
| `DASHBOARD_TILE` | 個人/スコープダッシュボード末尾のウィジェットタイル（**新設**） | ✅ 実装（§8.2） |
| `IN_FEED` | お知らせフィード内のインフィードバナー | ✅ 実装（§8.3） |
| `SIDEBAR_RIGHT` | 右サイドバー | ❌ 掲載面未実装（affiliate 管理画面で選択可能だが表示側なし） |
| `BANNER_FOOTER` | フッターバナー | ❌ 掲載面未実装 |
| `BANNER_HEADER` | ヘッダーバナー | ❌ 掲載面未実装 |

- 掲載面未実装の 3 placement は、管理画面（affiliate-settings）・運用型キャンペーン作成 UI の選択肢に**表示しない**（BE バリデーションでは許容する。将来掲載面を実装した時に FE の選択肢解放のみで開放できる）
- placement のマスタテーブル化（`ad_placements`）は行わない。第2弾の在庫管理で必要になった時点で、CLAUDE.md「マスタ例外」規定に基づき再検討する（§13）

### placement の付与単位

**placement はクリエイティブ（`ads`）単位**とする。バナーサイズが placement 依存であり、同一キャンペーンで複数面に出す場合は面別にクリエイティブを作るのが自然なため。キャンペーン単位の placement は採用しない（サイズ不一致クリエイティブの混入を構造的に防げない）。

## 4. 中立命名原則（広告ブロッカー耐性）【設計原則】

### 原則

新設する**ネットワーク/DOM 露出面**（API URL・FE コンポーネント名・レンダリングされる DOM の class/id/data-testid・ウィジェットキー）から、EasyList 等の広告ブロックフィルタに掛かるトークン（`ad` / `ads` / `advert` / `banner` / `sponsor` / `promo` 等）を排除し、中立語 **`spotlight`** を用いる。

これは F09.7 §7 の既存原則「CSS クラス名は広告専用であることを直接示す名前を避ける」の拡張であり、**自社ファーストパーティ配信の表示欠損・計測欠損を防ぐ目的**である。第三者アドネットワークの検知回避を意図するものではない（本機構が配信するのは自社審査済み広告とファーストパーティ・アフィリエイトのみ）。

### 露出面と内部の境界

```
┌─ ブラウザ/ネットワークに露出する層 ──────────────── 中立命名（spotlight）─┐
│  GET  /api/v1/spotlight/content          ← サービング                    │
│  POST /api/v1/spotlight/{creativeId}/view   ← インプレッション計上        │
│  POST /api/v1/spotlight/{creativeId}/visit  ← クリック計上               │
│  SpotlightSlot.vue / WidgetSpotlightPrimary / WidgetSpotlightSecondary   │
│  DOM class: spotlight-*  / data-testid: spotlight-*                      │
│  ウィジェットキー: spotlightPrimary / spotlightSecondary                  │
├─ 露出しない内部層 ──────────────────────── 既存 advertising 命名を維持 ─┤
│  Java パッケージ com.mannschaft.app.advertising.**                       │
│  テーブル ads / ad_campaigns / ad_impressions / ...                      │
│  enum AdPlacement / AdvertisingErrorCode                                 │
│  i18n キー文字列（advertising.spotlight.* — JS 内部値で DOM に出ない）    │
└──────────────────────────────────────────────────────────────────────────┘
```

- **既存 API との関係**: 既存 `POST /api/v1/ads/{adId}/click` はネットワークフィルタ（`/ads/` パターン）でブロックされ計測欠損するため、**新掲載面では使わない**。既存呼び出し箇所（equipment 補充リンク等は該当なし・現状 FE 呼び出しゼロ）の互換のため残置し、OpenAPI 上 `deprecated: true` を付与する。`GET /api/v1/ads/active` / `/ads/targeted` も同様に残置（管理・互換用）し、表示側は `/spotlight/content` に一本化する
- **景表法「広告」ラベルとの両立**: 「広告」ラベルは**テキストとして**従来どおり必須表示する（§8.1）。コスメティックフィルタは class/id/属性セレクタで要素を隠すのであり、テキスト内容は照合しないため、中立クラス名の要素内に「広告」テキストを描画することで法令対応とブロッカー耐性は両立する
- 既存 `AdLabelBadge.vue` は `data-testid="ad-label-badge"` を持ち属性セレクタで狙われ得るため、Spotlight 掲載面では使わず、`SpotlightSlot.vue` 内部で同一視覚仕様（橙 #FF9800・ロケール別「広告」表記・`role="region"`）のラベル要素を `data-testid="spotlight-label"` で自前描画する（§8.1）

### 5.2 DDL 詳細

#### V144.001 — `ads` に placement

```sql
ALTER TABLE ads
    ADD COLUMN placement VARCHAR(30) NOT NULL DEFAULT 'DASHBOARD_TILE'
        COMMENT 'AdPlacement。クリエイティブはサイズが placement 依存のため ads 単位' AFTER destination_url;
```

- 既存行は 0 件想定（運用型キャンペーン作成 API が未実装のため）だが、テスト環境等に行があっても `DEFAULT 'DASHBOARD_TILE'` で埋まる。既存データ番人テストは不要（NOT NULL + DEFAULT のため失敗様式が存在しない）

#### V144.002 — `ad_campaigns` に単価スナップショット

```sql
ALTER TABLE ad_campaigns

```

#### V144.003 — BANNER チャネルに placement

```sql
ALTER TABLE ad_messaging_campaign_channels
    ADD COLUMN placement VARCHAR(30) NULL
        COMMENT 'AdPlacement。channel_type=BANNER 時のみ必須' AFTER banner_creative_id;
UPDATE ad_messaging_campaign_channels SET placement = 'DASHBOARD_TILE' WHERE channel_type = 'BANNER';
ALTER TABLE ad_messaging_campaign_channels
```

- **既存データ番人テスト要**: 既存 BANNER チャネル行（本番/シードに存在しうる）が UPDATE で埋まってから CHECK が追加されることを、`V144.003` 適用前データを模したテストで検証する（`feedback_flyway_existing_data_check_drop` の教訓: CHECK 追加は必ず「既存データ是正 → 制約追加」の順）

#### V144.004 — `ad_banner_deliveries` の意味論分離（予約 ≠ 表示）

```sql
ALTER TABLE ad_banner_deliveries
    MODIFY COLUMN ad_impression_id BIGINT UNSIGNED NULL
        COMMENT 'F09.7 ad_impressions.id (FKなし)。実表示（serve）時に設定。予約時 NULL',
    MODIFY COLUMN served_at DATETIME NULL
        COMMENT 'バナー実表示時刻。予約時 NULL（NULL = 未表示予約）';
CREATE INDEX idx_abd_user_pending ON ad_banner_deliveries (user_id, served_at, created_at);
```

- 現行実装は `AdBannerChannelService.deliver()` が**配信予約時点で** `ad_impressions` を記録し `served_at` を埋める（= ユーザーが見ていないのに impression 計上）。掲載面実装後は「予約時 NULL → serve 時に実表示として充足」に改める（§7.4）。**既存行は移行不要**（既に served_at が入った行は「表示済み」として整合する）
- 既存データ番人テスト不要（NOT NULL → NULL 許容の緩和方向のみ）

#### V144.005 / V144.006 — `ad_campaigns` の scope 化（Expand → Contract）

```sql
-- V144.005 (Expand): advertiser_account_id を追加し backfill
ALTER TABLE ad_campaigns
    ADD COLUMN advertiser_account_id BIGINT UNSIGNED NULL
        COMMENT 'advertiser_accounts.id（同一 advertising ドメインのため FK 可）' AFTER advertiser_organization_id;
UPDATE ad_campaigns c
    JOIN advertiser_accounts a
        ON a.scope_type = 'ORGANIZATION' AND a.scope_id = c.advertiser_organization_id AND a.deleted_at IS NULL
    SET c.advertiser_account_id = a.id;
ALTER TABLE ad_campaigns
    MODIFY COLUMN advertiser_account_id BIGINT UNSIGNED NOT NULL
        COMMENT 'advertiser_accounts.id（同一 advertising ドメインのため FK 可）',
    ADD CONSTRAINT fk_ad_campaigns_advertiser_account
        FOREIGN KEY (advertiser_account_id) REFERENCES advertiser_accounts (id);
CREATE INDEX idx_ad_campaigns_account_status ON ad_campaigns (advertiser_account_id, status);

-- V144.006 (Contract): クロスドメイン FK 遺物の撤廃
ALTER TABLE ad_campaigns
    DROP FOREIGN KEY fk_ad_campaigns_org,
    DROP INDEX idx_org_status,
    DROP COLUMN advertiser_organization_id;
```

- **背景**: `ad_campaigns.advertiser_organization_id` は `organizations(id)` へのクロスドメイン FK（V10.051）であり CLAUDE.md「DB設計の原則 1」違反の遺物。かつチーム広告主が運用型キャンペーンを構造的に持てない。`advertiser_accounts` は scope 化済み（V67.026 で Contract 完了）のため、`advertiser_account_id` 直結に付け替えることでチーム対応とドメイン境界是正を同時に達成する
- **既存データ番人テスト要**: backfill 後に `advertiser_account_id IS NULL` の行が残ると V144.005 の NOT NULL 化で失敗する。orphan 行（対応する advertiser_accounts が論理削除済み等）が存在するデータを模したテストで、マイグレーション前提条件（orphan 0 件、または orphan は事前に advertiser_accounts の復元 or キャンペーン削除で解消する運用手順）を検証する
- V144.006 は V144.005 と**別ファイル**とし、V144.005 適用 + アプリ参照切替（`MonthlyInvoiceBatchService` 等）完了後に適用する
- コード側: `MonthlyInvoiceBatchService` の `findByAdvertiserOrganizationId(account.getScopeId())`（scope_id を organization_id に流用しており TEAM アカウントで破綻する既知問題）を `findByAdvertiserAccountId(account.getId())` に置換する

#### V145.001 — 通報の運用型対応（F09.19.9 別実装弾。§12 参照）

```sql
ALTER TABLE ad_user_reports
    MODIFY COLUMN campaign_id BINARY(16) NULL
        COMMENT 'ad_messaging_campaigns.id (FK CASCADE)。運用型通報時 NULL',
    ADD COLUMN operational_campaign_id BIGINT UNSIGNED NULL
        COMMENT 'F09.7 ad_campaigns.id（同一ドメインだが将来分離に備え FK なし・INDEX のみ）' AFTER campaign_id,
    ADD CONSTRAINT chk_aur_target CHECK (
        (campaign_id IS NULL) != (operational_campaign_id IS NULL)
    );
CREATE INDEX idx_aur_operational_status ON ad_user_reports (operational_campaign_id, status);

ALTER TABLE ad_campaigns
    ADD COLUMN report_suspended_at DATETIME NULL
        COMMENT '通報 3 件による自動停止時刻。非 NULL 中は広告主の resume 不可';
```

- `chk_aur_target` は「メッセージ型 XOR 運用型のどちらか一方のみ指定」を強制する
- **既存データ番人テスト要**: 既存行は全て `campaign_id` 非 NULL のため CHECK を自然に満たすが、CHECK 追加を含むため既存データありのテストで適用可否を検証する

## 6. API 設計

### 6.1 エンドポイント一覧

**サービング・計測（受信者向け・中立命名）**

| メソッド | パス | 認可 | 説明 |

**運用型キャンペーン CRUD（広告主向け。org/team 対）**

`{scopeBase}` = `/api/v1/organizations/{organizationId}` または `/api/v1/teams/{teamId}`。認可は全て `AccessControlService.checkAdminOrAbove(userId, scopeId, scopeType)` + 広告主アカウント（当該 scope の `advertiser_accounts`）の存在・ACTIVE 検証（`TeamAdvertiserAccountController` の既存前例に整合）。

|---|---|---|
| GET | `{scopeBase}/advertiser/ad-campaigns` | 一覧（status フィルタ・ページング） |

| GET | `{scopeBase}/advertiser/ad-campaigns/{campaignId}` | 詳細 |

| POST | `{scopeBase}/advertiser/ad-campaigns/{campaignId}/end` | → ENDED（終端・不可逆） |

**運用型キャンペーン審査（SYSTEM_ADMIN 向け）**

既存 `/api/v1/system-admin/ad-campaigns/**` は F09.17 メッセージ型審査が使用済みのため、URL 衝突回避に `-operational` サフィックスで分離する。

| PATCH | `/api/v1/system-admin/ad-campaigns-operational/{id}/reject` | PENDING_REVIEW → DRAFT（差戻し。理由必須） |

### 6.2 `GET /api/v1/spotlight/content`

掲載面が表示すべき広告候補を返す。**認証必須**（FreqCap・受信設定・F09.17 予約参照に userId が必要。掲載面は全てログイン後画面）。**CSR から呼ぶ**（ダッシュボードウィジェット・フィードは CSR レンダリングであり、SSR 化は認証 Cookie 転送とキャッシュ分離を複雑化するため採らない。レイアウトシフトは §8 の描画規則で制御）。

**クエリパラメータ**

| パラメータ | 型 | 必須 | 説明 |
|---|---|---|---|
| `placement` | String (AdPlacement) | Yes | 不正値は 400 / `AD_003`（既存「無効な配置場所」を再利用） |
| `count` | Integer | No | 返却する候補数。1〜2。既定 1。範囲外は 400 / `AD_003` |
| `template` | String | No | スコープのテンプレート slug（アフィリエイトターゲティング用。例 `CLUB`） |
| `prefecture` | String | No | 都道府県コード（同上） |
| `locale` | String | No | 既定 `ja` |

**レスポンス（200 固定。候補ゼロもエラーにしない）**

```jsonc
{
  "data": {
    "items": [                          // 長さ 0〜count。0 件 = 掲載面は何も描画しない
      {
        "source": "HOUSE",              // "HOUSE" | "AFFILIATE"
        "house": {                      // source=HOUSE 時のみ非 null
          "creativeId": 123,            // Long (ads.id)。view/visit のパスパラメータに使う
          "campaignId": 45,             // Long | null（運用型のとき非 null）
          "messagingCampaignId": null,  // String(UUID) | null（F09.17 予約バナーのとき非 null）
          "deliveryId": null,           // String(UUID) | null（F09.17 予約バナーのとき ad_banner_deliveries.id）
          "advertiserAccountId": 7,     // Long（「この広告主を非表示」用）
          "advertiserName": "株式会社〇〇", // String（広告主表示名 = advertiser_accounts.company_name）
          "title": "…",
          "imageUrl": "https://…",      // String | null（NULL 時 FE はタイトルテキストのみのカード描画）
          "destinationUrl": "https://…",
          "width": 300,                 // Integer | null
          "height": 250,                // Integer | null
          "altText": "…"                // String | null
        },
        "affiliate": {                  // source=AFFILIATE 時のみ非 null
          "provider": "AMAZON",         // "AMAZON" | "RAKUTEN"
          "affiliateUrl": "https://…",  // BE が tag_id から構築（FE は tag_id を扱わない: F09.7 既存原則）
          "bannerImageUrl": null,       // String | null（NULL 時 FE はプロバイダ別デフォルト描画）
          "width": null, "height": null, "altText": null
        }
      }
    ]
  }
}
```

- `data.items` 以外のトップレベルフィールドなし。**内部 AUTO_INCREMENT id のうち露出するのは `creativeId` / `campaignId` / `advertiserAccountId` のみ**で、いずれも認証必須 API のため F09.7 `/ads/active`（認証不要）の id 非露出原則とは前提が異なる（認証済みユーザーへの露出は許容。広告主側 API で既に露出済みの id 群でもある）
- affiliate 項目には `id` を返さない（計測対象外のため不要）

**Valkey キャッシュ（ユーザー非依存の候補プールをキャッシュし、ユーザー依存フィルタは取得後にオンメモリ適用）**

| キー | 内容 | TTL |
|---|---|---|
| `mannschaft:cache:ads:serve-pool:{placement}` | 運用型候補（ACTIVE キャンペーン × ACTIVE クリエイティブ × 広告主 ACTIVE の JOIN 結果） | 60 秒 |
| `mannschaft:cache:ads:affiliate:{placement}:{template}:{prefecture}:{locale}` | アフィリエイト候補（F09.7 §5 キャッシュ戦略の実現。キー体系は本書が正） | 10 分 |
| `mannschaft:cache:ads:user-prefs:{userId}` | `user_ad_preferences`（acceptBannerAds / blockedAdvertiserAccountIds） | 5 分 |

- 無効化: `affiliate_configs` CUD 時に `affiliate:*` を削除、`ads` / `ad_campaigns` の状態変更時に `serve-pool:*` を削除、`user_ad_preferences` 更新時に当該 `user-prefs:{userId}` を削除
- グレースフルデグラデーション: Valkey 障害時は DB 直読み。DB も不可なら `items: []`（F09.7 既存方針踏襲。ページ描画をブロックしない）

### 6.3 `POST /api/v1/spotlight/{creativeId}/view`

インプレッション計上。**FE の可視判定（§8.1: 50% × 1 秒）後に 1 回だけ**呼ぶ。serve 応答時点では記録しない（配信 ≠ 表示）。

**リクエスト**

```jsonc
{
  "placement": "DASHBOARD_TILE",       // 必須
  "campaignId": 45,                    // Long | null（運用型のとき）
  "messagingCampaignId": null,         // String(UUID) | null（F09.17 のとき）
  "deliveryId": null                   // String(UUID) | null（F09.17 のとき必須。ad_banner_deliveries.id）
}
```

**レスポンス（201）**

```jsonc
{ "data": { "impressionId": 999, "duplicate": false } }
```

- **二重計上防止（サーバー側最終防衛）**: Valkey `SETNX mannschaft:ad:imp-dedupe:{userId}:{creativeId}:{placement}` TTL 600 秒。重複時は記録せず `duplicate: true` を **200** で返す（FE はエラー扱いしない）
- 記録実体は既存サービスへ委譲: 運用型は `AdImpressionService.record(...)`（`ad_impressions` INSERT）、F09.17 予約は `recordForMessagingCampaign(...)` + 当該 `ad_banner_deliveries` 行の `ad_impression_id` / `served_at` を充足（§7.4）
- `AdImpressionService#scheduleServe`（`@Deprecated`）は削除し、呼び出し元を `record` 系へ置換する
- 日予算カウンタ `mannschaft:ad:imps:{campaignId}:{yyyyMMdd}` を INCR（§7.3）
- `campaignId` / `messagingCampaignId` は排他（両方指定・両方 null は 400 / `AD_003`）。`creativeId` が当該キャンペーンに属さない場合は 400 / `AD_026`（既存）

### 6.4 `POST /api/v1/spotlight/{creativeId}/visit`

クリック計上。FE はレスポンスを待たずに `destinationUrl` / `affiliateUrl` を新規タブで開いてよい（fire-and-forget。計測欠損より UX を優先）。

**リクエスト**

```jsonc
{
  "placement": "DASHBOARD_TILE",
  "impressionId": 999,                 // Long | null（view 済みなら紐付け。未 view クリックは null 許容）
  "campaignId": 45,
  "messagingCampaignId": null,
  "deliveryId": null
}
```

**レスポンス（201）**: `{ "data": { "clickId": 555 } }`

- 記録実体: 運用型は `AdClickService`（`ad_clicks` INSERT）、F09.17 は `recordForMessagingCampaign` + `ad_banner_deliveries.clicked_at` 更新
- **不正クリック対策（IP レート制限）**: Valkey `INCR mannschaft:ad:click-rl:{ipHash}:{creativeId}` TTL 60 秒、上限 10。超過は 429 / `AD_029`。IP は `X-Forwarded-For` 先頭（未設定時 remoteAddr）を SHA-256 ハッシュ化して用い、生 IP は保存もログ出力もしない。既存 `AdClickController`（`/api/v1/ads/{adId}/click`）の TODO も同一ガード（`AdClickRateLimitGuard`）を共用して解消する
- 日予算カウンタ `mannschaft:ad:clicks:{campaignId}:{yyyyMMdd}` を INCR（§7.3）

### 6.5 運用型キャンペーン CRUD の契約

#### POST `{scopeBase}/advertiser/ad-campaigns`（作成）

```jsonc
// リクエスト
{
  "name": "夏季キャンペーン",          // 必須。1〜200 文字
  "pricingModel": "CPM",              // 必須。"CPM" | "CPC"
  "dailyBudget": 3000,                 // 必須。DECIMAL(10,2)。選択 rate_card の min_daily_budget 以上（違反 AD_028）
  "startDate": "2026-08-01",          // 必須。本日以降（違反 AD_030）
  "endDate": "2026-08-31",            // null 可（無期限）。非 null 時 startDate <= endDate（違反 AD_030）
  "rateCardId": 3                      // 必須。pricingModel が一致し申込日が effective 期間内のカード（違反 AD_031）
}
// レスポンス 201
{ "data": { "id": 45, "status": "DRAFT", "unitPriceSnapshot": 500.0000, ... } }
```

- 作成時に `unit_price_snapshot` を `ad_rate_cards.unit_price` から確定・凍結する（以降の料金改定の影響を受けない）
- `daily_impression_limit` は本 API では受け付けない（既存列は温存。第2弾の保証 imp で使用予定）

#### 状態遷移（既存 enum `DRAFT / PENDING_REVIEW / ACTIVE / PAUSED / ENDED` を変更なしで使用）

```
DRAFT ──submit──> PENDING_REVIEW ──approve──> ACTIVE ──pause──> PAUSED
  ^                    │                        ^                  │
  └────── reject ──────┘                        └──── resume ──────┘
ACTIVE / PAUSED ──end──> ENDED（終端）
```

- 遷移条件外の操作は 409 / `AD_027`。PUT（編集）は DRAFT / PAUSED のみ（違反 409 / `AD_027`）。PAUSED で編集した場合、再開（resume）に再審査は**不要**とする（審査対象はクリエイティブ本体であり、キャンペーン設定（予算・期間）の変更はリスクが低いため。クリエイティブの追加・変更は既存の `SystemAdminAdCreativeController` 審査（ads.status DRAFT → ACTIVE）が個別に掛かる）
- `report_suspended_at` 非 NULL（通報自動停止中。F09.19.9）の resume は 403 / `AD_027`。解除は SYSTEM_ADMIN の approve のみ
- 配信対象になる条件（§7.2 STEP 2）は「campaign ACTIVE **かつ** creative（ads）ACTIVE」の AND であり、キャンペーン承認とクリエイティブ承認は独立に必要

#### 審査 approve / reject

- approve: `PENDING_REVIEW → ACTIVE`。監査ログ `OPERATIONAL_CAMPAIGN_APPROVED`
- reject: `PENDING_REVIEW → DRAFT`。理由（`reason`: 必須 1〜500 文字）を返却レスポンスと監査ログ `OPERATIONAL_CAMPAIGN_REJECTED` に記録。広告主画面では一覧・詳細に差戻し理由を表示する

## 7. ビジネスロジック

### 7.1 サービング全体像

```
GET /spotlight/content(userId, placement, count, template, prefecture, locale)
  ├─ STEP 0: 受信設定フィルタ
  │    user_ad_preferences.accept_banner_ads = false → STEP 3 へ（自社広告を全てスキップ）
  ├─ STEP 1: F09.17 予約バナー（最優先。配信予約 = ユーザー確定済み在庫）
  ├─ STEP 2: F09.7 運用型（CPM/CPC）
  ├─ STEP 3: アフィリエイト fallback
  └─ STEP 4: 候補なし（items から除外）
count 分の候補が埋まるまで STEP 1→2→3 の順に詰める（§7.2 の重複回避規則に従う）
```

### 7.2 割当ロジック（決定的ルール。eCPM オークションは不採用）

順位付けは以下で**完全に一意**に定まる。eCPM ランキングは CTR 実績のない立ち上げ期に決定性を失うため第1弾では採用しない（§14）。

```
STEP 1: F09.17 予約バナー
  SELECT ad_banner_deliveries WHERE user_id = :me AND served_at IS NULL
    AND (チャネル placement = :placement) AND (キャンペーン status = 'DELIVERING')
    ORDER BY created_at ASC
  - blocked_advertiser_account_ids に該当する広告主の予約はスキップして次候補
  - FreqCap（週 3 件）は「予約時に消費済み」のため serve 時は再判定しない

STEP 2: F09.7 運用型
  候補条件（すべて AND）:
  - ads.status = 'ACTIVE' AND ads.placement = :placement
  - ad_campaigns.status = 'ACTIVE' AND 本日が [start_date, end_date] 内（end_date NULL は無期限）
  - 広告主 advertiser_accounts.status = 'ACTIVE' AND deleted_at IS NULL
  - 日予算残あり: 本日推定消化額 < daily_budget（§7.3。daily_budget は必須のため NULL 分岐なし）
  - advertiser_account_id が blocked_advertiser_account_ids に含まれない
  - 時間内キャップ未達: Valkey mannschaft:ad:serve-cap:{userId}:{campaignId} 不在
    （SETNX・TTL 3600 秒 = 同一ユーザー × 同一キャンペーンは 1 時間 1 回まで）
    ※ F09.17 の週 3 キャップ（AdFrequencyCapService）は push 型（配信予約型）チャネルの規律であり、
      pull 型サービングには適用しない（適用すると閲覧頻度の高いユーザーで枠が空転するため）。
      pull 型の露出抑制は本キャップ（1 時間 1 回）が担う
  順位付け（上から順に評価。完全一意）:
  1. 本日消化率（推定消化額 ÷ daily_budget）昇順   … ペーシング（未消化キャンペーン優先）
  2. campaign.id 昇順
  3. キャンペーン内クリエイティブ選択はラウンドロビン:
     Valkey INCR mannschaft:ad:rr:{campaignId}:{placement}（TTL 48h）の値 mod N を
     「ads.id 昇順リスト」の添字として選ぶ

STEP 3: アフィリエイト fallback
  AffiliateConfigService の既存ターゲティング取得（template / prefecture / locale）を placement で絞り、
  display_priority ASC → id ASC の先頭から採用（既存 /ads/active と同一順序）

count = 2 のときの重複回避規則（優先度順に適用し、満たせない場合のみ緩和）:
  a. 同一クリエイティブ（ads.id）は 2 枠に重複させない（絶対禁止）
  b. 同一広告主（advertiser_account_id）は 2 枠に重複させない
     → 2 位候補は「1 位と異なる広告主」の最上位。全候補が同一広告主なら b を緩和して同広告主の別クリエイティブ可
  c. AFFILIATE 2 枠になる場合は provider（AMAZON/RAKUTEN）を分ける。片方しか無ければ 1 件のみ返す
  候補が 1 件しか無ければ items は 1 件、0 件なら 0 件で返す（無理に埋めない）
```

### 7.3 日次集計バッチと日予算制御（欠落環 #3 の充填）

**新設 `AdDailyStatsAggregationBatchService`**（`com.mannschaft.app.advertising.service`。`@Transactional` は advertising ドメイン内で完結）:

- `@Scheduled(cron = "0 30 1 * * *", zone = "Asia/Tokyo")` + ShedLock。既存バッチ（02:00 analytics 日次、03:00 `AdMessagingBillingBridge`、05:00 月次請求）より前の 01:30 に配置し、**同日 03:00/05:00 のバッチが前日確定値を参照できる順序**を保証する
- 前日分の `ad_impressions` / `ad_clicks` を **`campaign_id IS NOT NULL`（= F09.7 運用型）に限定**して `(campaign_id, ad_id)` で集約し、`ad_daily_stats` へ UPSERT（既存 `uk_campaign_ad_date` により再実行冪等）
- **F09.17 分（`messaging_campaign_id` 非 NULL 行）は集計対象外**。F09.17 の課金は `AdMessagingBillingBridge` が `ad_*_deliveries` から直接積み上げる管轄であり、両バッチの課金境界は「`ad_impressions.campaign_id` の NULL/非 NULL」で排他になる（二重課金防止）
- cost 算定: `pricing_model = CPM → impressions / 1000 × unit_price` / `CPC → clicks × unit_price`。unit_price は `ad_campaigns.unit_price_snapshot`。NULL（V144.002 以前の既存行のみ理論上あり得る）なら集計日に有効な全国・全テンプレートカード（`target_prefecture IS NULL AND target_template IS NULL`）の単価で代替、それも無ければ cost = 0 + WARN ログ + メトリクス `ad_daily_stats_unpriced_rows` 出力（請求漏れ検知）

**日予算のリアルタイム制御（serve 側）**:

- view / visit 計上時に Valkey `INCR mannschaft:ad:imps:{campaignId}:{yyyyMMdd}` / `mannschaft:ad:clicks:{campaignId}:{yyyyMMdd}`（TTL 48h）
- serve 候補判定は「カウンタ × unit_price_snapshot で本日推定消化額を計算し、daily_budget 以上なら除外」
- Valkey フラッシュ・障害時は**フェイルオープン**（消化 0 扱い = 配信続行）。確定値は翌日の集計バッチで補正される。超過配信ぶんの課金は `ad_daily_stats` の実測値で行う（日予算は「目安の上限」であり厳密保証はしない、と広告主向け画面の注記に明記する）

### 7.4 F09.17 BANNER チャネルの意味論修正（予約 ≠ 表示）

- `AdBannerChannelService.deliver()` を「**予約のみ**」に変更: `ad_impressions` の記録をやめ、`ad_banner_deliveries` を `ad_impression_id = NULL, served_at = NULL` で INSERT する。FreqCap 消費は従来どおり予約時（在庫確定時）
- serve（STEP 1）が予約行を返し、FE の view 計上（§6.3）で `recordForMessagingCampaign` → 当該行の `ad_impression_id` / `served_at` を充足する
- `AdMessagingBillingBridge` の BANNER 課金は「**`served_at IS NOT NULL` の行のみ課金対象**」に条件を変更する（未表示予約は課金しない。従来設計 = 予約即課金からの最重要変更点。F09.17 §5 課金ブリッジも同旨に改訂済み）
- 予約の鮮度: `served_at IS NULL` かつ `created_at` から **14 日**経過した予約行は `AdCampaignStateTransitionScheduler` の日次処理で EXPIRED 扱い（行は残すが serve 対象外。キャンペーン COMPLETED 後の予約も同様に serve 対象外）とし、FreqCap を `releaseSlot`（§10.4）で返却する

### 7.5 広告非表示条件（F09.7 既存ルールの適用）

以下のいずれかで SpotlightSlot / ウィジェットを**描画しない**（F09.7 §5「広告非表示のトリガー」と同一判定。FE の Pinia プラン情報で判定）:

- スコープダッシュボード: 当該チーム/組織が有料プラン（`subscription_status != 'FREE'`）
- 個人ダッシュボード: 所属するチーム/組織のいずれかが有料プラン
- `FEATURE_V9_ENABLED = false`
- `/spotlight/content` が `items: []` を返した、または API エラー

### 8.1 `SpotlightSlot.vue`（新規 `frontend/app/components/spotlight/SpotlightSlot.vue`）

表示専用の末端コンポーネント。**データ取得は行わず** props で受け取る（取得は §8.2/8.3 の親が行う。2 枠が同一候補になる事故をサーバー側 count=2 の一括取得で構造的に防ぐため）。

```ts
interface Props {
```

## 11. セキュリティ考慮事項

- **認可**: サービング/計測 3 API は認証必須（`isAuthenticated()`）。運用型 CRUD は `AccessControlService.checkAdminOrAbove` + 当該 scope の広告主アカウント検証（403。他 scope のリソースは存在有無を問わず 403 = IDOR 対策、F09.11 §4 共通ルール踏襲）。`campaignId` 等のパスパラメータは必ず「当該 scope の advertiser_account に属するか」を検証する（`project_matching_authz_userid_as_teamid_idor` の教訓: getCurrentUserId や scopeId の流用を禁止）
- **計測の完全性**: view/visit は creativeId とキャンペーンの帰属検証（AD_026）+ Valkey 重複排除 + IP レート制限（§6.4）。認証必須のため匿名ボットによる水増しは構造的に不可。同一ユーザーの水増しは dedupe（600 秒）と serve-cap（1 時間 1 回）で抑止
- **XSS**: imageUrl / destinationUrl は BE がクリエイティブ入稿時に `https://` スキーム検証済み（既存 `AdCreativeService`）。FE は `<img src>` / `<a href>` にのみ使用し任意 HTML を挿入しない（F09.7 §7 踏襲）
- **PII**: IP は SHA-256 ハッシュのみ保持（§6.4）。serve レスポンスに他ユーザー情報は含まれない。`ad_impressions` / `ad_clicks` の保持・匿名化は F09.7/F09.17 の既存データ保持ポリシーに従う
- **監査ログ**: §10.5 に加え、運用型審査（approve/reject）と `affiliate_configs` 既存イベントは従来どおり

- フィルタ: `accept_banner_ads = false` → HOUSE をスキップし AFFILIATE のみ。`blocked_advertiser_account_ids` 該当広告主は候補除外。日予算消化済み（Valkey カウンタ × 単価 ≥ daily_budget）キャンペーンは除外。serve-cap 存在中（1 時間以内再訪）は同一キャンペーンを返さない
- 順位: 消化率 0% と 50% の 2 キャンペーン → 0% が返る。同率 → campaign.id 小。クリエイティブ 2 件はラウンドロビンで交互
- count=2: 異なる広告主 2 キャンペーン → items 2 件で広告主が重複しない。同一広告主のみ 2 キャンペーン → 同広告主 2 件（緩和規則 b）。候補 1 件 → items 1 件
- view: 同一 user × creative × placement を 600 秒内に 2 回 POST → 2 回目 `duplicate: true`・`ad_impressions` は 1 行。予約バナーの view → `ad_banner_deliveries.served_at` / `ad_impression_id` が充足される
- visit: `ad_clicks` 1 行 + impressionId 紐付け。同一 IP から 60 秒に 11 回 → 11 回目 429 / AD_029
- 異常: placement 不正値 → 400 / AD_003。未認証 → 401。creativeId とキャンペーン不一致 → 400 / AD_026

### F09.19.3 BE: 日次集計 + 意味論修正

- 集計: 前日 imp 2000 / click 10・CPM 単価 500 円のキャンペーン → `ad_daily_stats` に 1 行、cost = 1000.00。バッチ再実行で行数・金額不変（冪等）。CPC 単価 60 円・click 10 → cost = 600.00
- 境界: `messaging_campaign_id` 非 NULL の imp/click 行は集計対象外（`ad_daily_stats` に混入しない）
- 意味論: `AdBannerChannelService.deliver()` 後の行は `served_at IS NULL` かつ `ad_impressions` 未記録。`AdMessagingBillingBridge` は `served_at IS NULL` の予約行を課金しない（BANNER 課金額 = served 行数のみ）

## 19. 非機能（1000 万ユーザー・シャーディング耐性）

- **serve ホットパス**: Valkey プールキャッシュ命中時 DB 0 クエリ（user-prefs も 5 分キャッシュ）。プールはユーザー非依存のため全ユーザーで共有され、キャッシュヒット率はユーザー数に依存しない
- **追記専用テーブル**: `ad_impressions` / `ad_clicks` は INSERT only。第1弾で月次パーティション化はしない（F09.17 の `month_key` 方式を将来適用する前例として注記。保持期間・集約後削除は F09.7 §10 既存方針）
- **Valkey キー設計**: すべて `mannschaft:ad:` / `mannschaft:cache:ads:` プレフィクス + エンティティ ID を含み、キー単位でシャード分散可能。カウンタ喪失時はフェイルオープン（配信続行・翌日バッチ補正）
- **集計バッチ**: `(campaign_id, ad_id)` 単位の集約 SQL 1 本 + UPSERT。メモリはキャンペーン数 O(n)
- **監視**: `/spotlight/content` p95 200ms 超過 5 分継続でアラート（F09.7 §8 と同基準）。`ad_daily_stats_unpriced_rows`（§7.3）> 0 でアラート
