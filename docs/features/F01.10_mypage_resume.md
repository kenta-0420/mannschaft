## 1. 概要

### 1.1 目的

個人ユーザーが自分のプロフィール情報をベースに、**JIS 規格 履歴書** と **職務経歴書** の 2 種類の書類を作成・保存し、PDF / Excel 形式で出力できる機能を新設する。マイページ内の個人ツールとして提供し、就職活動・転職活動・各種応募の場面で利用できる。

入力摩擦を極力減らし（ADHD 傾向のユーザー配慮）、既存のプロフィール情報（氏名・カナ・生年月日・性別）を自動補完することで再入力を不要にする。複数バージョンを保存でき、応募先ごとに使い回せる。

### 1.2 スコープ

**本機能で実装する範囲**

- 履歴書バージョンの作成・編集・複製・論理削除（個人単位・複数バージョン保存可）
- 学歴・職歴・免許資格・スキルの子要素管理
- 証明写真のアップロード・削除（R2 / S3 ストレージ連携）
- JIS 履歴書 PDF / 職務経歴書 PDF の出力
- JIS 履歴書 Excel / 職務経歴書 Excel の出力
- 西暦 / 和暦の出力切替（令和・平成・昭和対応）
- GDPR データエクスポート連携・退会時の購入対象分類

**スコープ外**

- 履歴書の他者共有・公開（**本人のみ完全非公開**。共有機能は持たない）
- 添え状（送付状）の生成（将来フェーズ候補）
- AI による志望動機・自己 PR の自動生成（将来フェーズ候補）
- 第三者添削・レビュー機能（将来フェーズ候補）
- **英文レジュメ（English résumé / CV）の生成**（将来フェーズ候補）。本機能の **帳票本体（PDF / Excel の中身）は日本語のみ**とする。多言語化対象は **UI ラベル（画面の操作文言）のみ** で、i18n 6 言語（ja/en/zh/ko/es/de）にキーを追加する（§10・§11）

### 1.3 設計方針の要点

| 観点 | 方針 |
|------|------|
| 形式 | JIS 規格 履歴書 + 職務経歴書 の 2 種類 |
| スコープ | 個人単位・複数バージョン保存可（`user_id` 駆動。`organization_id` は持たない） |
| 出力形式 | PDF・Excel 両方 |
| 公開範囲 | 本人のみ完全非公開（自分以外からは 404） |
| ドメイン | 新規ドメイン `com.mannschaft.app.resume`（auth / user とは分離） |

## 2. 用語定義

| 用語 | 定義 |
|------|------|
| **履歴書バージョン（Resume）** | `resumes` テーブルの 1 レコード。1 ユーザーが複数持てる。`title` で識別する（例「標準」「○○社応募用」） |
| **JIS 履歴書（履歴書 / rirekisho）** | JIS Z 8303 系の一般的な様式に準拠した履歴書。氏名・住所・学歴職歴・免許資格・志望動機等を含む |
| **職務経歴書（職務経歴書 / shokumukeirekisho）** | 職務要約・活かせる経験/知識/技術・職務詳細（事業内容・職務内容・実績）を自由度高く記載する書類 |
| **era_format（元号フォーマット）** | 出力時に年を西暦（WESTERN）で出すか和暦（JAPANESE）で出すかの切替。履歴書バージョン単位で保持 |
| **証明写真（photo）** | 履歴書ヘッダーに貼る本人写真。R2 / S3 に `user/{userId}/resume/{resumeId}/photo.{ext}` キーで保存 |
| **一括保存（PUT /full 相当）** | ヘッダ項目 + 学歴 + 職歴 + 免許資格 + スキルをまとめて 1 リクエストで保存する操作。入力摩擦最小化のため主たる保存手段とする |
| **skills_summary（活かせる経験・知識・技術）** | `resumes` テーブルの **1 カラム**（TEXT）。職務経歴書冒頭に置く **自由記述の散文ブロック**（例「上流から運用まで一貫して担当し…」）。1 履歴書につき 1 つ |
| **resume_skills（構造化スキルリスト）** | `resume_skills` テーブルの **複数レコード**。スキル名 + 習熟度（BEGINNER〜EXPERT）+ 補足を **構造化した任意のリスト**。職務経歴書の「スキル一覧」表として箇条書き描画する。`skills_summary`（散文）とは **役割が異なり併存** する（散文＝総括文、構造化＝個別スキルの一覧。両方とも任意で、片方だけ使うことも両方使うこともできる） |

### 3.2 再利用する既存基盤

新機能では既存の共通基盤を最大限再利用し、新規実装を最小化する。

| 基盤 | パッケージ / クラス | 利用内容 |
|------|--------------------|---------|
| PDF 生成 | `com.mannschaft.app.common.pdf.PdfGeneratorService` | `generateFromTemplate(templateName, variables)` で Thymeleaf + Flying Saucer + OpenPDF により PDF を生成。日本語フォントは `PdfFontConfig`（NotoSansJP / NotoSerifJP）が起動時登録済 |

| Excel 生成 | `com.mannschaft.app.common.excel.ExcelGeneratorService` | `fillTemplate(InputStream, Map)`（既存テンプレへの `${key}` 差込）/ `generateListExcel()` / `generateMultiSheetExcel()`。Apache POI 5.2.5 ベース。**§7.4 で繰り返し行ブロック差込メソッドの追加（案 A 確定）が必要** |
| ストレージ | `com.mannschaft.app.common.storage.StorageService` | R2 / S3 への証明写真・生成物の保存・取得・presigned URL 発行 |
| UUIDv7 基底 | `com.mannschaft.app.common.entity.UuidV7Entity` | 新規テーブルの主キー基底（原則 6 準拠） |
| 暗号化 | 既存 AES-256-GCM コンバータ（`@Convert`） | 住所・連絡先等 PII カラムの暗号化保存 |
| レート制限 | Bucket4j + Caffeine（既存パターン） | export エンドポイントの回数制限 |
| 監査ログ | `AuditEventType` / `AuditLogService` | 出力イベントの記録 |

#### 氏名・カナ・生年月日・性別の扱い

氏名・カナ・生年月日・性別は既存 `com.mannschaft.app.auth.entity.UserEntity` に AES-256-GCM 暗号化済みで存在する。履歴書ヘッダーには **出力時に `UserEntity` を参照して埋め込む**（resume ドメインに重複保存しない）。

- ドメイン越境は **読み取りのみ**。`ResumeExportService` が `UserService`（または read-only クエリ）経由でプロフィールを取得する
- これにより、ユーザーがプロフィールの氏名・カナを更新すれば、再出力時に最新の値が反映される（二重管理の不整合を防ぐ）

> **注記（ドメイン越境）**: `ResumeExportService` の出力処理は resume ドメインと auth/user ドメインをまたぐ。Entity を直接参照せず、`UserService` のメソッド呼び出し（DTO）経由で取得することで原則 5（@Transactional はドメイン内に閉じる）を維持する。出力処理は読み取り専用のため `@Transactional(readOnly = true)` とする。

## 4. DB設計

### 4.1 テーブル一覧

| テーブル名 | 役割 | Flyway |
|-----------|------|--------|
| `resumes` | 履歴書バージョンコンテナ | 新規（UUIDv7・V70.001） |
| `resume_educations` | 学歴 | 新規（UUIDv7・V70.002） |
| `resume_careers` | 職歴（履歴書簡易職歴 + 職務経歴書詳細 兼用） | 新規（UUIDv7・V70.003） |
| `resume_qualifications` | 免許・資格 | 新規（UUIDv7・V70.004） |
| `resume_skills` | 活かせるスキル（職務経歴書用・任意） | 新規（UUIDv7・V70.005） |

#### 設計方針

- **全テーブル `UuidV7Entity` 継承・主キー `BINARY(16)`**（原則 6 準拠）
- **resume ドメイン内の FK は CASCADE 可**（`resumes` → 子テーブルは同一ドメイン親子のため `ON DELETE CASCADE` を許可。原則 2 準拠）
- **`users` への FK は張らない**。`user_id` は `BIGINT UNSIGNED` でインデックスのみ（原則 1 準拠。整合性はアプリ層で保証）
- charset `utf8mb4` / collation `utf8mb4_unicode_ci`
- 【暗号化】と記したカラムは AES-256-GCM コンバータ（`EncryptedStringConverter`）で暗号化保存する。**コンバータは暗号文を Base64 文字列として返すため、カラム型は `TEXT` とする**（`VARBINARY` は使わない。文字列カラムに格納するのが既存全 PII カラムの統一方針）

> **Flyway 番号注記（2 トラック併存）**: 本リポジトリの Flyway マイグレーションは **V1〜V19 系**（旧トラック）と **V60〜系**（新トラック）の **2 トラックが併存** している。本機能は **新トラック（V60+）** に属するため `V70.001`〜`V70.005` を採番する。**実装着手時に main 最新の空き番号（V60+ トラック）を再確認し、衝突する場合は連番を繰り上げること**（過去に V9.154 番号衝突事故あり）。

> **設計方針（二重入力の防止・ADHD 配慮）**: `resume_careers` は履歴書の簡易職歴と職務経歴書の詳細を **1 テーブルで兼用** する。
> - **履歴書（rirekisho）出力時**: `include_in_rirekisho = TRUE` の行のみを対象に、`entry_year` / `entry_month` + `company_name` + 入社 / 退社（`end_year` / `is_current`）から「○年○月 △△株式会社 入社」形式の簡易職歴行を描画する。
> - **職務経歴書（shokumukeirekisho）出力時**: `include_in_shokumukeireki = TRUE` の行のみを対象に、`business_summary` / `job_description` / `achievements` の詳細フィールドを使用する。
> - ユーザーは職歴を 1 度入力するだけで両書類に反映され、**二重入力が発生しない**。
> - **出し分けフラグ（`include_in_rirekisho` / `include_in_shokumukeireki`）** により、アルバイト歴は履歴書のみ・短期の単発職歴は職務経歴書では省く、といった実需に対応する。両フラグともデフォルト TRUE のため、何も設定しなければ両書類に出る。

### 5.6 PUT `/api/v1/resumes/{id}`（フル一括保存）

入力摩擦最小化のため、ヘッダ + 全子要素を 1 リクエストでまとめて保存する。これを主たる保存手段とする。

**リクエスト**
```json
{
  "title": "標準",
  "era_format": "JAPANESE",
  "current_address": "東京都...",
  "current_address_kana": "とうきょうと...",
  "contact_email": "me@example.com",
  "motivation": "...",
  "self_pr": "...",
  "personal_request": "...",
  "commute_minutes": 45,
  "dependents_count": 1,
  "has_spouse": true,
  "spouse_support": false,
  "career_summary": "...",
  "skills_summary": "...",
  "educations": [
    { "entry_year": 2018, "entry_month": 4, "description": "○○大学 経済学部 入学", "display_order": 0 }
  ],
  "careers": [
    { "entry_year": 2022, "entry_month": 4, "is_current": true, "company_name": "△△株式会社",
      "department": "開発部", "employment_type": "正社員", "job_description": "...", "display_order": 0 }
  ],
  "qualifications": [
    { "acquired_year": 2021, "acquired_month": 6, "name": "普通自動車第一種運転免許", "display_order": 0 }
  ],
  "skills": [
    { "skill_name": "Java", "level": "ADVANCED", "display_order": 0 }
  ]
}
```

**PUT のセマンティクス（宣言的置換・冪等）**

本 PUT は **「リソースの全状態を宣言的に置き換える」** 操作とする（PATCH のような部分更新ではない）。
- リクエストボディは履歴書の **あるべき完全な状態** を表す。ヘッダ項目はボディの値で全置換する。
- 子要素（educations / careers / qualifications / skills）も **送られた集合が正** であり、**リクエストに含まれなかった既存の子は論理削除** される。
- **冪等性**: 同一ボディを再送すれば結果は同一になる（リトライ安全）。

**保存方式（差分 upsert）**
- ヘッダ項目を更新
- 子要素は「`id` 付き → 更新 / `id` なし → 新規 / リクエストに含まれない既存子 → 論理削除」の差分同期方式とする（`@Transactional` で resume ドメイン内に閉じる）

**楽観ロック（同時編集の競合検知）**
- リクエストボディに `version`（取得時に GET で受け取った値）を含める。JPA `@Version` により、DB の `version` と不一致なら `OptimisticLockException` を検出する。
- 競合時は **409 Conflict / `RESUME_010`**「編集が競合しました（他で更新済み）」を返す。FE は最新を再取得して再編集を促す。

**バリデーション**
- `title`: 必須（`RESUME_002`）
- 子要素件数上限: educations ≤ 30 / careers ≤ 30 / qualifications ≤ 50 / skills ≤ 50（`RESUME_003`）
- 年月: `entry_year` / `acquired_year` は 1900〜（現在年 + 10）の範囲、`entry_month` は 1〜12（`RESUME_004`）
- `contact_email`: 入力された場合は **RFC 準拠のメール形式バリデーション**（`@Email` 相当。不正形式 → 400）
- **自由記述テキストの実効最大長**（DDL の `TEXT` 型は最大 64KB だが、固定レイアウト帳票に流すため実効上限を別途定める。超過 → 400）:

  | カラム | 実効最大長（文字） | 備考 |
  |--------|------------------|------|
  | `motivation`（志望動機） | 1,000 | 履歴書の志望動機欄 |
  | `self_pr`（自己 PR・特技・趣味） | 1,000 | 履歴書 |
  | `personal_request`（本人希望記入欄） | 500 | 履歴書 |
  | `career_summary`（職務要約） | 800 | 職務経歴書冒頭 |
  | `skills_summary`（活かせる経験・知識・技術） | 1,000 | 職務経歴書 |
  | `job_description`（職務内容） | 2,000 / 1 件 | 職務経歴書・会社ごと |
  | `achievements`（実績・成果） | 1,000 / 1 件 | 職務経歴書・会社ごと |

  > 上限を超えた場合の帳票描画時の挙動は §7.7 に定める（自動縮小 / 続紙 / 切詰め + 警告）。
- その他テキスト最大長: 各カラム DDL の長さに準拠（超過 → 400）

### 5.9 POST `/api/v1/resumes/{id}/duplicate`（複製）

指定バージョンを子要素ごと複製する。新しい `id` を採番し、`title` は「{元タイトル} (コピー)」とする。

**証明写真の複製方式（StorageService にサーバーサイドコピー API は存在しない）**
実コード確認の結果、`StorageService` は `upload` / `download` / `delete` / `deleteAll` / `generateUploadUrl` / `generateDownloadUrl` のみを提供し、**オブジェクト間のサーバーサイドコピー API は存在しない**。したがって写真は以下の手順で複製する:

1. 元の `photo_key` があれば `byte[] data = storageService.download(srcPhotoKey)` で取得
2. 新 `resumeId` のキー `user/{userId}/resume/{newResumeId}/photo.{ext}` を組み立て
3. `storageService.upload(dstPhotoKey, data, contentType)` で **新キーに独立して保存**（元キーとは共有しない。元を削除しても複製は無傷）
4. 複製の `resumes.photo_key` に新キーを設定

> 元と複製が **別オブジェクト** になるため、片方の写真削除・退会パージが他方に影響しない（IDOR・整合性の観点で安全）。

### 5.10 POST `/api/v1/resumes/{id}/photo`（証明写真アップロード）

**リクエスト**: `multipart/form-data`、フィールド名 `file`

**バリデーション**
- Content-Type: `image/jpeg` / `image/png` のみ（それ以外 → `RESUME_007` 415）
- サイズ: 最大 5MB（超過 → `RESUME_006` 413）
- 拡張子検証 + マジックバイト検証（Content-Type 偽装対策）
- 推奨アスペクト比 3:4（強制はしない。FE で案内）

**動作**
1. **画像の再エンコード（sanitize・必須）**: アップロードされた画像を **デコード → 再生成 → 再エンコード** することで、**EXIF / GPS などのメタデータを除去**する（位置情報漏洩防止）。同時に **寸法上限（例 2000 × 2000px）でリサイズ**し、デコンプレッション爆弾（小さいファイルが巨大画像に展開される攻撃）による OOM を防ぐ。
   - 既存 `com.mannschaft.app.common.storage.ImageConverter` を参照・再利用する。同クラスは `ImageIO.read()` で `BufferedImage` にデコードし、新しい `BufferedImage`（`TYPE_INT_RGB`）を生成して書き出すため、**この再生成過程で EXIF/GPS メタデータは自然に除去される**。`resize(BufferedImage, maxSize)` で寸法上限も実現できる。
   - 証明写真は WebP 変換するとプリンタ・他社サービスでの取り回しが悪いため、**JPEG / PNG のまま再エンコード**する方針とする（WebP 変換はしない）。`ImageConverter` に「再エンコードのみ（フォーマット維持・メタデータ除去・寸法上限）」のメソッドを追加するか、`resize()` + `ImageIO.write(..., "JPEG"/"PNG", ...)` を `ResumePhotoService` 内で組み合わせる（実装タスクに明記）。
2. ストレージキー `user/{userId}/resume/{resumeId}/photo.{ext}` で `StorageService.upload()` に保存
3. `resumes.photo_key` を更新
4. 監査ログ `RESUME_PHOTO_UPLOADED` を記録（§8.4）
5. presigned URL（TTL 5 分）を返却

### 5.11 DELETE `/api/v1/resumes/{id}/photo`（証明写真削除）

`StorageService` からオブジェクト削除 + `photo_key = NULL`。

### 5.12 プレビューと正式出力の分離

プレビュー（頻回・軽量）と正式出力（永続化・課金/監査計上）は **別エンドポイント** に分離する。ADHD 配慮で「ちょっと見て直してまた見る」を阻害しないよう、プレビューは R2 を経由せず軽い制限とする。

| 観点 | GET `/{id}/preview` | GET `/{id}/export` |
|------|---------------------|--------------------|
| 用途 | 編集中の見た目確認 | 完成版のダウンロード |
| R2 保存 | **しない**（生成 byte をそのままレスポンスボディにインライン返却） | **する**（`user/{userId}/resume/{resumeId}/{type}.{ext}`） |
| レスポンス | `Content-Type: application/pdf` / `...spreadsheetml.sheet`、`Content-Disposition: inline`、本体は生成バイナリ | presigned URL（JSON） |
| レート制限 | **緩い（120 回 / 時 / ユーザー）** | 30 回 / 時 / ユーザー |
| 監査ログ | 記録しない（編集中の内部操作のため） | `RESUME_EXPORTED` を記録 |

**共通クエリパラメータ**
| パラメータ | 値 | 説明 |
|-----------|-----|------|
| `type` | `rirekisho` / `shokumukeirekisho` | 出力する書類種別 |
| `format` | `pdf` / `excel` | 出力形式 |

#### 5.12.1 GET `/api/v1/resumes/{id}/preview`（プレビュー・インライン）

**動作**
1. パラメータ検証（不正値 → `RESUME_005` 400）
2. レート制限チェック（120 回 / 時 / ユーザー。超過 → `RESUME_008` 429）
3. `ResumeExportService` が履歴書データ + `UserEntity` のプロフィールを取得し、PDF / Excel を生成（§7）
4. **R2 に保存せず**、生成 byte を `ResponseEntity<byte[]>` で **インライン返却**（`Content-Disposition: inline; filename="..."`）

> FE は presigned URL を待たずに直接 iframe / 新規タブで表示できる。生成物が R2 に残らないためストレージコストもゼロ。

#### 5.12.2 GET `/api/v1/resumes/{id}/export`（正式出力・永続化）

**動作**
1. パラメータ検証（不正値 → `RESUME_005` 400）
2. レート制限チェック（30 回 / 時 / ユーザー。超過 → `RESUME_008` 429）
3. `ResumeExportService` が履歴書データ + `UserEntity` のプロフィールを取得
4. `type` / `format` に応じて PDF / Excel を生成（§7）
5. R2 / S3 に `user/{userId}/resume/{resumeId}/{type}.{ext}` で保存
6. 監査ログ `RESUME_EXPORTED` を記録（§8）
7. presigned URL（TTL 5 分）を返却

**レスポンス**
```json
{
  "data": {
    "download_url": "https://r2.example.com/...presigned...",
    "file_name": "20260525_履歴書_山田太郎.pdf",
    "expires_at": "2026-05-25T10:05:00+09:00"
  }
}
```

### 5.13 エラーレスポンス共通形式

```json
{
```

### 7.2 西暦 / 和暦 変換

`resumes.era_format` に応じて年表記を切り替える。変換は `ResumeEraFormatter`（resume ドメイン内ユーティリティ）で行い、テンプレートには変換済み文字列を渡す。

| era_format | 出力例（2018 年 4 月） |
|-----------|----------------------|
| `WESTERN` | 2018 年 4 月 |
| `JAPANESE` | 平成 30 年 4 月 |

**対応元号**: 令和（2019-05-01〜）/ 平成（1989-01-08〜2019-04-30）/ 昭和（1926-12-25〜1989-01-07）。境界年（改元年）は月日で判定する。`java.time.chrono.JapaneseDate` を利用して算出する方針とする。

**改元年で月が NULL の場合の決定的フォールバック規則（確定）**

入力は `entry_year` が必須・`entry_month` が任意（NULL 可）のため、改元年（**1989 年**＝昭和/平成 / **2019 年**＝平成/令和）で **月が NULL** だと元号が一意に決まらない。曖昧さを残さないため、以下の **決定的規則** を定める:

| 改元年 | 月 NULL のときに採用する元号 | 根拠（その年で日数が多数派の元号） |
|--------|------------------------------|-----------------------------------|
| **1989 年** | **平成** と表記（「平成元年」） | 1989 年は 1/1〜1/7 が昭和（7 日）、1/8〜12/31 が平成（358 日）。多数派の **平成** を採用 |
| **2019 年** | **令和** と表記（「令和元年」） | 2019 年は 1/1〜4/30 が平成（120 日）、5/1〜12/31 が令和（245 日）。多数派の **令和** を採用 |

- 規則: **「月 NULL の場合、その暦年で日数の多い側（多数派）の元号を決定的に採用する」**。これにより同一入力に対して常に同じ出力になる（テスト可能・UT-04 で境界を検証）。
- 月が指定されていれば月日で正確に判定する（1989-01 → 昭和、1989-02 → 平成、2019-04 → 平成、2019-05 → 令和）。

### 7.3 出力ファイル名（PDF / Excel 両対応）

| 書類 / 形式 | パターン | 例 |
|------------|---------|-----|
| 履歴書 PDF | `{作成日}_履歴書_{氏名}.pdf` | `20260525_履歴書_山田太郎.pdf` |
| 履歴書 Excel | `{作成日}_履歴書_{氏名}.xlsx` | `20260525_履歴書_山田太郎.xlsx` |
| 職務経歴書 PDF | `{作成日}_職務経歴書_{氏名}.pdf` | `20260525_職務経歴書_山田太郎.pdf` |
| 職務経歴書 Excel | `{作成日}_職務経歴書_{氏名}.xlsx` | `20260525_職務経歴書_山田太郎.xlsx` |

> **重要（実コード確認の結果）**: `PdfFileNameBuilder.build()` は **末尾の `.pdf` をハードコードしており**（`sb.append(".pdf")`）、`.xlsx` を生成できない。Excel 名の生成は以下のいずれかで対応する（**実装方針: 案 a を推奨**）:
> - **案 a（推奨）**: `PdfFileNameBuilder` を拡張し、拡張子を引数化した汎用ファイル名生成にする（例 `extension(String ext)` ビルダーメソッドを追加、デフォルトは `.pdf` で後方互換を維持）。命名規約（`{yyyyMMdd}_{文書種別}_{識別名}`・禁止文字 sanitize・最大長 100・RFC 5987 エンコード）を PDF / Excel で共通化できる。
> - **案 b**: `ResumeExportService` 内で `.xlsx` 名を独自に組み立てる（`PdfFileNameBuilder` で `.pdf` 部分を除いた本体を作り、自前で拡張子を付ける）。`PdfFileNameBuilder` を汚さない代わりに sanitize ロジックが二重化する。
>
> いずれにせよ **このファイル名生成タスクは §14 Phase 3 の成果物に明記** する（汎用化 or 独自生成のどちらを採るかは実装着手時に最終判断）。
>
> 履歴書は対外文書だが本人保管用途のため敬称（様）は付けない。氏名は出力時に `UserEntity` から取得する。

### 7.4 Excel 出力

`ExcelGeneratorService`（Apache POI 5.2.5）を利用する。書類の性質に応じて 2 方式を使い分ける。

| 書類 | 方式 | テンプレート / 生成方法 |
|------|------|----------------------|
| 履歴書（厚労省 2021 様式） | テンプレート差込 | `templates/excel/rirekisho.xlsx`（固定グリッド）+ 新規 `fillTemplateWithRows()`（§7.4 案 A）で学歴・職歴の可変行を差込。ファイル名は §7.3 のとおり `.xlsx` |
| 職務経歴書 | プログラム生成 | 自由度が高いため `generateMultiSheetExcel()` 等で POI プログラム生成 |

> **ExcelGeneratorService の繰り返し行ブロック差込メソッド追加（案 A 確定）**: 現行 `fillTemplate(InputStream, Map)` は **1 セル単位の `${key}` 単純置換のみ** で、学歴・職歴のような **可変長の繰り返し行ブロックの差込には対応していない**。JIS 履歴書 Excel は学歴職歴欄が複数行あるため拡張が必要。**本設計では案 A（汎用拡張）に確定する**:
> - **案 A（確定）**: 繰り返し行ブロック差込メソッド（例 `fillTemplateWithRows(InputStream, Map<String,Object> headerData, String blockMarker, List<Map<String,Object>> rows)`）を `ExcelGeneratorService` に追加する。`${edu[].year}` のような行マーカーを検出し、行を複製して値を流し込む。行数上限に縛られず、他機能（将来の帳票 Excel 出力）からも再利用できる汎用性が得られるため案 A を採る。
>
> （比較検討した案 B = 最大行数固定のフラットキー方式は、行数上限が固定になり拡張性に欠けるため不採用とした。）
>
> **このメソッド追加は §14 Phase 3 の成果物に明記する。** 既存メソッド（`fillTemplate` / `generateListExcel` / `generateMultiSheetExcel`）は変更せず、新規メソッドの追加のみとするため、**既存 Excel 機能への回帰影響はない**（§12 で回帰テスト範囲を担保）。

### 7.7 固定レイアウトへのテキスト流し込み（溢れ時の挙動）

履歴書 / 職務経歴書はいずれも **固定レイアウト**（履歴書 = 罫線グリッド・職務経歴書 = 段組）に自由記述テキストを流し込む。テキストが枠に収まらない場合の挙動を **カラム種別ごとに確定** する。

| カラム | 溢れ時の挙動 |
|--------|------------|
| `motivation` / `self_pr` / `personal_request`（履歴書の固定欄） | **フォントの自動縮小**（最小サイズまで縮小）→ なお収まらなければ **末尾を切り詰めて「…（以下省略）」を付し、画面に警告を表示**（編集を促す）。実効最大長（§5.6）を超えた入力はそもそも保存時に 400 で弾くため、通常は縮小で収まる |
| `career_summary` / `skills_summary` / `job_description` / `achievements`（職務経歴書） | 職務経歴書は **続紙（ページ自動追加）** を許容する。Flying Saucer の自動改ページにより、内容量に応じてページ数が伸びる（職務経歴書は枚数自由のため切り詰めない） |
| `resume_skills`（構造化スキル一覧） | 件数上限（≤ 50）内で全件描画。職務経歴書側で続紙対応 |

> 方針: **履歴書（様式が 1〜2 枚固定）= 自動縮小 + 切詰め警告**、**職務経歴書（枚数自由）= 続紙**。入力時点で実効最大長（§5.6）により上限を設けているため、極端な溢れは事前に防止される。

| 生年月日 / 年齢 | **UserEntity 参照** | 年齢は生年月日から算出 |

### 7.9 履歴書様式の現行性（JIS 様式廃止・厚労省 2021 推奨様式準拠）

> **重要（様式の現状）**: いわゆる **「JIS 規格の履歴書様式」は 2020 年 7 月に JIS Z 8303 の改正で附属書（履歴書の様式例）が削除され、規格としては廃止** されている。本機能は最新の慣行に合わせ、**厚生労働省が 2021 年 4 月に公表した「新たな履歴書様式例（厚労省 2021 推奨様式）」に準拠** する。文書名・UI ラベルでは引き続き「履歴書」と呼ぶが、内部のレイアウトは厚労省 2021 様式を基準とする。

厚労省 2021 推奨様式に伴う具体的な差分:

- **性別欄**: **任意記載**（記載は本人の判断）。テンプレートで表示 ON/OFF を選べるようにする。
- **配偶者・扶養家族欄**（`has_spouse` / `spouse_support` / `dependents_count`）: 厚労省 2021 様式では **削除（任意）**。本機能ではデータとしては保持しつつ、**履歴書ごとに表示 ON/OFF 可能・テンプレートで省略可** とする。
- **通勤時間欄**（`commute_minutes`）: 同様に **任意**。表示 ON/OFF 可能・テンプレで省略可。
- 上記「任意欄」はいずれも入力必須ではなく、未入力なら帳票上も非表示にできる（ADHD 配慮の必須最小化とも整合）。

> なお「JIS 履歴書」「rirekisho」という呼称は §2 用語・テンプレートファイル名（`resume-rirekisho.html` / `rirekisho.xlsx`）で踏襲するが、**意味する様式は厚労省 2021 推奨様式** である点に注意する。

## 8. セキュリティ設計

### 8.1 脅威と対策

| 脅威 | 対策 | 反映箇所 |
|------|------|---------|
| **IDOR**（他人の履歴書閲覧・編集・出力） | 全クエリを `user_id = 認証ユーザー` でフィルタ。不一致は 404（存在秘匿） | §5.1, §5.5 |
| **PII 漏洩**（住所・連絡先・メール） | `current_address` 系 / `contact_address` 系 / `contact_phone` / **`contact_email`** を AES-256-GCM 暗号化保存（既存コンバータ。すべて `TEXT` 型） | §4.2, §8.1.1 |
| **DoS / 出力肥大**（巨大データ生成） | 子要素件数上限（educations ≤ 30 / careers ≤ 30 / qualifications ≤ 50 / skills ≤ 50）+ 各テキスト最大長 | §5.6 |
| **CPU 負荷攻撃**（連続出力） | export を 30 回 / 時 / ユーザーにレート制限（Bucket4j + Caffeine） | §5.12, §8.2 |
| **写真悪用**（不正ファイル / 偽装） | Content-Type + 拡張子 + マジックバイト検証、サイズ上限、user 名前空間キー、presigned 短 TTL | §5.10, §7.6 |
| **直リンク漏洩**（生成物 URL の流出） | presigned URL の TTL を 5 分に最小化。長期 URL を発行しない | §7.5 |
| **生成物の横取り** | 生成物は `user/{userId}/` 名前空間に保存。キーにユーザー ID を含め推測困難な UUIDv7 resumeId を組み合わせる | §7.5 |

#### 8.1.1 PII（個人識別情報）一覧

resume ドメインが保持する PII を列挙する。暗号化対象は全て AES-256-GCM コンバータで `TEXT` 型に暗号化保存する。氏名・生年月日・性別は resume には保持せず `UserEntity` を出力時参照する（§3.2・§7.8）。

| PII | 保持場所 | 保護 |
|-----|---------|------|
| 現住所 / ふりがな | `resumes.current_address` / `current_address_kana` | 【暗号化】 |

### 8.2 レート制限

| エンドポイント | 制限 | キー | 備考 |
|--------------|------|------|------|
| GET `/{id}/export`（正式出力） | 30 回 / 時 | `user_id` | R2 永続化・監査計上のため厳しめ |
| GET `/{id}/preview`（プレビュー） | 120 回 / 時 | `user_id` | R2 非経由・軽量のため緩め（ADHD 配慮で頻回プレビュー許容） |

### 8.3 認証・認可

- `SecurityConfig` に `/api/v1/resumes/**` を `authenticated()` として追加する
- ロールによる制限はなし（個人ツールのため全認証ユーザーが自分のリソースのみ操作可能）
- IDOR 対策として全クエリで `user_id` 一致を強制し、不一致は 404 を返す（403 ではなく 404 で存在自体を秘匿）

### 8.4 監査ログ（必須）

> **重要（実コード確認の結果）**: `com.mannschaft.app.auth.AuditEventType` は **enum 各定数がコンストラクタ引数で `AuditEventCategory` を必須に取る**（例 `WITHDRAWAL_COMPLETED(AuditEventCategory.ACCOUNT)`）。新規定数を追加するには **既存の `AuditEventCategory` から適切な値を 1 つ選んで与える** 必要がある。
>
> resume は **アカウント所有者本人の個人データ操作** であり、PII を含む帳票を生成する。最も意味的に近い既存カテゴリは **`AuditEventCategory.ACCOUNT`**（`USER_REGISTERED` / `WITHDRAWAL_COMPLETED` / `EMAIL_CHANGED` 等が属する）であるため、resume 系の監査イベントはすべて **`ACCOUNT`** を採用する。

PII を含む書類の生成・写真の受領・レート逸脱は後追い調査の対象となるため、監査ログ記録を **任意 → 必須に格上げ** する。

| イベント | AuditEventType（追加定数） | カテゴリ | 記録タイミング・含める情報 |
|---------|---------------------------|---------|--------------------------|
| 履歴書/職務経歴書 正式出力 | `RESUME_EXPORTED(AuditEventCategory.ACCOUNT)` | ACCOUNT | `/export` 成功時（`type` / `format` / `resumeId`）。プレビューは記録しない |
| 証明写真アップロード | `RESUME_PHOTO_UPLOADED(AuditEventCategory.ACCOUNT)` | ACCOUNT | 写真の受領・再エンコード完了時（`resumeId`） |
| 出力レート上限到達 | `RESUME_EXPORT_RATE_LIMITED(AuditEventCategory.ACCOUNT)` | ACCOUNT | export/preview がレート超過で 429 を返したとき（`resumeId`・どちらのエンドポイントか） |

> `AuditEventType` に上記 3 定数を追加する（いずれも `AuditEventCategory.ACCOUNT` を付与）。

## 9. GDPR・退会対応

### 9.1 退会時の分類（CLAUDE.md §13.12 二段モデル準拠）

| 区分 | 対象 | タイミング | 分類根拠 |
|------|------|----------|---------|
| **猶予対象（強匿名化）** | `resumes` + 子テーブル（educations / careers / qualifications / skills）+ 証明写真 R2 オブジェクト + 生成物 R2 オブジェクト | `requestWithdrawal` 受付から最大 30 日後 `AccountPurgeService` バッチで **物理削除** | 履歴書は **復旧不可能なユーザー入力コンテンツ**。退会撤回ウィンドウ（30 日）を保持しつつ GDPR Art.17 を遵守 |

> 履歴書データは「再設定で復旧可能」ではなくユーザーが時間をかけて入力した固有コンテンツのため、即時消去（弱匿名化）ではなく **猶予対象（強匿名化）** に分類する。auth（OAuth/2FA）・social 等と同じ扱い。

### 9.2 退会パージ（イベント駆動・`AccountPurgedEvent` 購読）

> **重要（アーキテクチャの現行性）**: 旧来の「`AccountPurgeService` の **越域 DELETE リスト** に resume ドメインを追加する」方式は **廃止済み** である。現行アーキテクチャ（`docs/architecture/account_purge_cross_domain_refactor.md` §3〜§4 Phase C）では、`AccountPurgeService.purgeUser()` が **越境 DML を一切持たず**、`AccountPurgedEvent` を発火するだけで、各ドメインが **専用の `*PurgeEventListener`** で自ドメインのデータを片付ける **イベント駆動方式** に統一されている。resume も **この方式に従う**。

#### 9.2.1 新規 `ResumePurgeEventListener`（実コード `ChartPurgeEventListener` と同型）

新規に `com.mannschaft.app.resume.event.ResumePurgeEventListener` を作成し、`AccountPurgedEvent` を購読する。アノテーション構成は **実在する `ChartPurgeEventListener` をそのまま写経** する（三重防御）:

```java
package com.mannschaft.app.resume.event;

@Slf4j
@Component
@RequiredArgsConstructor
public class ResumePurgeEventListener {

    private final ResumeRepository resumeRepository;
    private final StorageService storageService;
    private final GdprS3PurgeFailureRepository gdprS3PurgeFailureRepository;
    private final AccountPurgeCompletionStatusRepository completionStatusRepository;

    /**
     * AccountPurgedEvent を購読し、resume ドメインの全レコードと R2 オブジェクトを物理削除する。
     * 三重防御:
     *   @Async("purge-pool")                          — 呼び出し元 TX とスレッド分離
     *   @TransactionalEventListener(AFTER_COMMIT)      — gdpr 側コミット成立後に実行
     *   @Transactional(REQUIRES_NEW)                   — 独立した新規 TX
     */
    @Async("purge-pool")
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void on(AccountPurgedEvent event) {
        Long userId = event.getUserId();
        boolean success = false;
        try {
            // 1) DB から確定的に R2 キーを列挙してから削除（プレフィックス一括削除 API は無い・§9.2.2）
            //    photo_key + 生成物キー {rirekisho,shokumukeirekisho}×{pdf,xlsx}
            List<String> keys = resumeRepository.collectStorageKeysByUserId(userId);
            try {
                storageService.deleteAll(keys);
            } catch (Exception e) {
                // R2 削除失敗は GdprS3PurgeFailureEntity に記録（夜次リトライ対象）
                keys.forEach(k -> {
                    GdprS3PurgeFailureEntity f = new GdprS3PurgeFailureEntity();
                    f.setUserId(userId); f.setS3Key(k);
                    f.setFailedAt(LocalDateTime.now()); f.setLastError(/* truncate */ e.getMessage());
                    gdprS3PurgeFailureRepository.save(f);
                });
            }
            // 2) DB 物理削除（user_id 全件・deleted_at 問わず）。子テーブルは resume ドメイン内 FK CASCADE で連鎖
            resumeRepository.deletePhysicallyByUserId(userId);
            success = true;
        } catch (Exception e) {
            log.warn("ユーザー退会 resume purge 失敗 userId={}, error={}", userId, e.getMessage(), e);
        }

        // 3) completion_status を SUCCESS に更新（ChartPurgeEventListener と同型）
        if (success) {
            completionStatusRepository.findByUserIdAndDomainName(userId, "resume")
                .ifPresent(s -> { s.setStatus("SUCCESS"); s.setCompletedAt(LocalDateTime.now());
                                  completionStatusRepository.save(s); });
        }
    }
}
```

#### 9.2.2 `AccountPurgeService.purgeTargetDomains` への "resume" 登録

`AccountPurgeService.purgeUser()` 内で `AccountPurgedEvent` 発火前に各ドメイン分の `AccountPurgeCompletionStatusEntity`（PENDING）を INSERT している（実コード確認済）。その登録リストに **"resume" を追加** する:

```java
// 実コード（AccountPurgeService.purgeUser 内）に "resume" を追記
List<String> purgeTargetDomains =
    List.of("role", "team", "payment", "chart", "proxy", "errorreport", "resume");
```

これにより `ResumePurgeEventListener` が処理完了時に **PENDING → SUCCESS** に更新する。2 時間後も PENDING のままなら `GdprPurgeAuditBatchService` が未処理として検出・アラートする（既存の監視機構にそのまま乗る）。

#### 9.2.3 R2 オブジェクト削除（プレフィックス一括削除 API は存在しない）

> **重要（実コード確認の結果）**: `StorageService` には **プレフィックス一括削除 API は存在しない**（`upload` / `download` / `delete` / `deleteAll(List<String>)` / `generateUploadUrl` / `generateDownloadUrl` のみ）。したがって `user/{userId}/resume/**` をワイルドカードで一括削除することはできない。

そのため、**DB から確定的にキーを列挙して `deleteAll(List<String>)` に渡す**:

- `resumes.photo_key`（NULL でない全レコード分）
- 生成物キー: `user/{userId}/resume/{resumeId}/{type}.{ext}`（`{type}` = `rirekisho` / `shokumukeirekisho`、`{ext}` = `pdf` / `xlsx`）を各 resume について網羅的に組み立てる

> 将来、ストレージ抽象に「プレフィックス削除」が要るようになった場合は **`StorageService` 拡張タスク**（`deleteByPrefix(String prefix)` 追加）として別途切り出す。本機能の範囲では確定列挙 + `deleteAll` で完結させる。

R2 削除に失敗したキーは **`GdprS3PurgeFailureEntity`**（実在・`setUserId` / `setS3Key` / `setFailedAt` / `setLastError`）に記録し、`AccountPurgeService` の `data_exports` 削除と同じパターンで **夜次補正バッチがリトライ** する。

#### 9.2.4 物理削除の範囲

- **DB**: `user_id = 退会ユーザー` の `resumes` を **deleted_at を問わず全件物理 DELETE**（論理削除済みも含めて完全消去）。resume ドメイン内 FK は `ON DELETE CASCADE` のため、`resume_educations` / `resume_careers` / `resume_qualifications` / `resume_skills` は自動連鎖削除される。
- **R2**: §9.2.3 のとおり確定列挙 → `deleteAll`。

### 9.3 F12.3 個人データエクスポートへの追加

F12.3 `PersonalDataCollector` の対象に履歴書データを追加する（こちらは退会パージ §9.2 とは別。**ユーザーが自分のデータをダウンロードするエクスポート権** の対応）。

- `ResumeEntity` および子エンティティに `@PersonalData(category = "resumes")` を付与する（`PersonalDataCoverageValidator` の起動時網羅性チェックで未登録を検出させる）

- エクスポート内容: 履歴書バージョンごとにヘッダ + 学歴 + 職歴 + 免許資格 + スキル。暗号化カラム（住所・電話・**メール**）は復号して出力。証明写真は presigned URL またはバイナリ同梱（F12.3 の写真方針に準拠）

```json
{
  "resumes": [
    {
      "id": "...",
      "title": "標準",
      "current_address": "東京都...",
      "educations": [ ... ],
      "careers": [ ... ],
      "qualifications": [ ... ],
      "skills": [ ... ]
```

## 11. UX設計

メモリ「ユーザーの ADHD 傾向と機能設計」（入力摩擦ゼロ・必須項目最小・後で整理可能なフロー）を反映する。

| 配慮 | 設計 |
|------|------|
| **必須項目を実質ゼロに** | 必須は `title` のみ。さらに **title 未指定なら「下書き YYYY-MM-DD」を自動採番**（§5.4）するため、ユーザーは何も入力せず「作成」だけで空の履歴書を作れる。他は全て任意で後から追記可能 |
| **再入力を不要に** | 氏名 / カナ / 生年月日 / 性別はプロフィールから自動補完（出力時参照）。ユーザーは再入力しない |
| **二重入力を防ぐ** | 職務経歴の詳細入力（職務経歴書）が履歴書の簡易職歴を兼ねる（§4.4）。1 度の入力で両書類に反映。出し分けは `include_in_*` フラグで制御 |
| **使い回し** | バージョン複製（duplicate）で応募先ごとに使い回せる。元を壊さず派生を作れる |
| **こまめな保存が不要 + autosave** | フル一括保存（PUT）で全項目を 1 操作で保存。さらに **FE で debounce（入力停止後一定時間）による下書き autosave** を行い、保存忘れを防ぐ。保存完了時は「保存しました」を明示フィードバックする（FE 責務。§11.1） |
| **頻回プレビュー** | プレビュー専用エンドポイント（`/preview`・§5.12）を緩いレート（120/時）で提供。R2 を経由しないインライン表示で「ちょっと見て直す」を阻害しない |
| **出力前プレビュー** | 正式出力前にプレビューで完成イメージを確認してから出力 |
| **西暦/和暦の柔軟性** | era_format で出力時に切替。入力は年数値のみで、表記は出力側が吸収。改元年で月未入力でも決定的に表記が決まる（§7.2） |
| **同時編集の事故防止** | 楽観ロック（§5.6）で別タブ・別端末の同時編集による上書き事故を検知し、409 で安全に再編集を促す |

### 11.1 autosave とフィードバック（FE 責務）

- **autosave**: エディタで入力が止まってから一定時間（例 1.5 秒）後に PUT を debounce 実行する。これにより明示保存を忘れても下書きが残る。
- **保存フィードバック**: 保存中はインジケータ、成功時は「保存しました」（i18n キー）を明示表示する。失敗時（409 楽観ロック競合・バリデーションエラー等）はエラー内容を表示し、競合時は最新の再取得を促す。
- **i18n**: 上記の文言（「保存しました」「編集が競合しました」等）は **UI ラベルとして 6 言語のロケールファイルに追加** する（帳票本体の日本語固定とは別。§1.2）。

## 13. エラーコード一覧

専用 enum `com.mannschaft.app.resume.ResumeErrorCode` に定義する（`ErrorCode` インターフェース実装）。`RESUME_001`〜のブロックを F01.10 専用として予約する。

| コード | HTTP | メッセージ | 用途 |
|--------|------|----------|------|
| `RESUME_001` | 404 | 履歴書が見つかりません | 存在しない / 他人の id（IDOR 秘匿） |
| `RESUME_002` | 400 | タイトルは必須です | title 未指定 / 空文字 |
| `RESUME_003` | 400 | 登録件数が上限を超えています | 子要素件数上限超過 |
| `RESUME_004` | 400 | 日付の形式が不正です | 年月範囲外・不正値 |
| `RESUME_005` | 400 | 出力種別または形式が不正です | type / format 不正 |
| `RESUME_006` | 413 | 写真サイズが上限を超えています | 5MB 超過 |
| `RESUME_007` | 415 | 非対応の写真形式です | JPEG/PNG 以外 |
| `RESUME_008` | 429 | 出力回数の上限に達しました | export / preview レート制限 |
| `RESUME_009` | 500 | 帳票生成に失敗しました | PDF/Excel 生成エラー |
| `RESUME_010` | 409 | 編集が競合しました（他で更新済み） | 楽観ロック競合（`@Version` 不一致・§5.6） |
