## 1. 概要

F09.17 は、外部広告主が「お知らせウィジェット / メール / プッシュ通知 / アプリ内バナー」の 4 チャネルを横断してターゲット配信できるメッセージ型キャンペーン基盤を提供する。広告主はキャンペーン単位でターゲット属性・配信日時・予算・本文を入稿し、SYSTEM_ADMIN の審査承認を経て受信者へ配信される。受信者側は開封率・既読率・タップ率・クリック率といったエンゲージメント指標で評価され、広告主にはパフォーマンスレポートが提供される。

F09.11 で構築済みの広告主アカウント・credit_limit・請求基盤・料金テーブルはそのまま温存し、F09.17 はその上に「メッセージ型キャンペーン」というレイヤを追加する位置づけである。F09.7 が担う既存バナー表示型広告とは別系統として運用される。

### F09.17 と関連機能の責任境界

| 機能 | スコープ | 配信形態 | F09.17 との関係 |
|---|---|---|---|
| **F09.17（本機能）** | 外部広告主から **他組織ユーザー** へ広告メッセージを 4 チャネル横断配信 | お知らせ + メール + プッシュ + バナー | 本ドキュメント |
| F09.11 広告主ダッシュボード | 広告主アカウント・credit_limit・請求基盤・F09.7 系既存広告のレポート | バナー（CPM/CPC） | アカウント・課金基盤として利用。`messaging_campaign_id` 列で課金行を識別 |
| F09.7 広告表示 | バナー枠・クリエイティブ管理・配信ログ | バナー（CPM/CPC） | F09.17 BANNER チャネルは F09.7 の `AdImpressionService` 経由で `serving_strategy='MESSAGING_CAMPAIGN'` で隔離抽選 |
| F09.2 プロモーション配信 | **自組織メンバー** 向けセグメント評価・プロモーション送信 | メール + アプリ内通知 | `SegmentEvaluator` を F09.17 から `AdAudienceResolver` 経由で再利用。ただし PII（user_id 個別）は漏らさない |
| F09.6 ダイレクトメール | 自組織が組織内ユーザーに送るメール本体 | メール | `DirectMailService.sendSystemMail(sender_type='SYSTEM_AD')` を F09.17 から呼び出す |
| F02.6 お知らせウィジェット | お知らせフィードの表示・既読管理 | お知らせ | `announcement_feeds.source_type='ADVERTISER_CAMPAIGN'` で広告レコードを差し込む |
| F02.8 ダッシュボードお知らせ | ダッシュボード上のお知らせウィジェット表示順制御 | お知らせ | 通常お知らせ優先・広告は 3:1 差し込み・4 位以下を表示位置上限 |
| F04.3 プッシュ通知 | プッシュ通知配信基盤 | プッシュ | `NotificationService.send(source_type='ADVERTISER_CAMPAIGN', priority='LOW')` を呼び出す |
| F10.3 監査ログ | 全機能横断の監査ログ集約 | — | F09.17 のキャンペーン状態遷移・受信設定変更を記録 |
| F08.2 会費・決済 | Stripe 連携の基盤 | — | 既存 F09.11 / F08.2 と同方針。F09.17 では追加 Webhook なし |

「F09.2 = 自組織メンバー向けプロモーション」「F09.17 = 外部広告主から他組織ユーザー向け広告」がドメイン境界の核となる。F09.2 が組織内のマーケティング、F09.17 がクロステナントの広告という棲み分けである。

### 本ドキュメントのスコープ

| 機能 | 説明 |
|---|---|
| キャンペーン CRUD | 広告主が DRAFT → REVIEW → APPROVED → DELIVERING の状態遷移でキャンペーンを管理 |
| 4 チャネル横断配信 | ANNOUNCEMENT / EMAIL / PUSH / BANNER を 1 キャンペーンで組み合わせ配信 |
| ターゲティング | 地域・年代・組織属性・興味タグなど segment 条件でユーザーを絞り込む（PII は返さない） |
| 推定リーチ取得 | 配信前に対象ユーザー数のレンジ表示（user_id は返却禁止） |
| フリークエンシーキャップ | 1 ユーザー週 3 件まで（Valkey 原子的カウンタ、ユーザー TZ で週境界判定） |
| 受信者オプトアウト | チャネル別 4 フラグ + 広告主単位ブロック（上限 100 件） |
| モデレーション | 自動 NG ワード検知 + SYSTEM_ADMIN 承認/ブロック + ユーザー通報 3 件で自動 SUSPEND |
| パフォーマンスレポート | 配信数・開封率・既読率・タップ率・クリック率を集計表示（PII なし） |
| 課金ブリッジ | 月次バッチで F09.11 `ad_invoice_items` に積上、`messaging_campaign_id` で識別 |
| 「広告」ラベル | 景品表示法対応。お知らせバッジ・メール件名 `[PR] `・プッシュ「【広告】」自動付与 |
| 多言語キャンペーン | 1 キャンペーンで言語別 body を入稿、受信時に `users.locale` で選択 |

### スコープ外

- F09.7 系既存バナー広告（CPM/CPC 単独配信）の機能拡張
- LINE / SNS 連携配信（F09.4 のスコープ）
- AI 自動入札・最適化（v2 以降）
- Stripe Webhook の新規追加（F09.11 / F08.2 の既存 Webhook を再利用）

### API プレフィックス

- 広告主向け: `/api/v1/advertiser/campaigns/messaging/**`
- 受信者向け: `/api/v1/me/ad-preferences`, `/api/v1/me/ad-deliveries`, `/api/v1/me/ad-reports`, `/api/v1/ads/unsubscribe`
- SYSTEM_ADMIN 向け: `/api/v1/system-admin/ad-campaigns/**`, `/api/v1/system-admin/ad-user-reports`

**主キー**: 全テーブル `BINARY(16) NOT NULL PRIMARY KEY`（UUIDv7、`UuidV7Entity` 継承）。
**TenantAware**: `ad_messaging_campaigns` のみ `organization_id` を保持し `AbstractTenantAwareRepository<AdMessagingCampaign, UUID>` を継承する。他テーブルは `campaign_id` 経由で間接的にテナント分離する（クロスドメイン FK は作らないが INDEX で絞り込み可能）。
**クロスドメイン FK 禁止**: `user_id` / `announcement_feed_id` / `direct_mail_recipient_id` / `notification_id` / `ad_impression_id` / `advertiser_account_id` / `organization_id` は **FK 制約なし**。INDEX のみ張り、整合性はアプリ層で保証する。
**CASCADE 制限**: F09.17 ドメイン内（`ad_messaging_campaign_channels`, `ad_audience_segments`, `ad_*_deliveries`, `ad_campaign_moderation_logs`, `ad_user_reports`）の `campaign_id` FK のみ `ON DELETE CASCADE` 可。


```json
        "consumed_budget_yen": 32400
      }
    ],
    "next_cursor": null
  }
}
```

#### `POST /api/v1/advertiser/campaigns/messaging`

**リクエスト**
```json
{
  "name": "春のキャンペーン",
  "total_budget_yen": 100000,
  "starts_at": "2026-04-01T00:00:00+09:00",
  "ends_at": "2026-04-30T23:59:59+09:00",
  "scheduled_timezone": "Asia/Tokyo",
  "frequency_cap_override": null
}
```

**バリデーション**
- `name`: 1〜120 文字、必須
- `total_budget_yen`: 1,000 以上 100,000,000 以下
- `starts_at < ends_at` かつ `starts_at >= now + 1 hour`
- `frequency_cap_override`: NULL または 1〜30

**レスポンス (201)**: 作成されたキャンペーンオブジェクト全体。

**エラー**
| ステータス | 条件 |
|---|---|
| 400 | バリデーションエラー |
| 402 | `advertiser_account.status != 'ACTIVE'` または `credit_limit` 不足 |
| 403 | `MANAGE_ADS` 権限なし |

#### `POST /api/v1/advertiser/campaigns/messaging/{id}/channels`

**リクエスト**
```json
{
  "channel_type": "EMAIL",
  "locale": "ja",
  "subject": "新サービスのご案内",
  "body_markdown": "# こんにちは\n本日…",
  "image_url": "https://cdn.mannschaft.app/ads/abc.png",

  "cta_url": "https://example.com/lp",

```

**バリデーション**
- `channel_type='BANNER'` のとき `banner_creative_id` 必須
- `cta_url` は `https://` のみ許可。許可ホストリストに照合（外部 URL 許可リスト）
- `image_url` は S3 許可ホスト限定
- `body_markdown` は最大 8,000 文字。F02.6 Markdown サニタイザを通す
- `locale` は `ja/en/zh-CN/zh-TW/ko/pt-BR` のいずれか

**レスポンス (201)**: 作成されたチャネルオブジェクト。

**エラー**
| ステータス | 条件 |
|---|---|
| 400 | バリデーションエラー |
| 409 | `(campaign_id, channel_type, locale)` 重複 |

リクエスト不要。

**レスポンス (200)**
```json
{
  "data": {
    "estimated_reach_range": "5000-10000",
    "estimated_reach_precision": "RANGE",
    "channel_breakdown": {
      "ANNOUNCEMENT": 8200,
      "EMAIL": 6900,
```

`user_id` は一切返却しない。100 人未満のセグメントは `estimated_reach_range='UNDER_100'` で個人特定リスク回避。同期 5 秒超なら 202 Accepted + WebSocket トピック `ad-preview-{campaignId}` で非同期通知。

#### `POST /api/v1/advertiser/campaigns/messaging/{id}/submit`

DRAFT → REVIEW 遷移。自動 NG ワード検知が走り、`moderation_status='AUTO_PASSED'` または `'AUTO_FLAGGED'` をセット。`AUTO_PASSED` は自動承認候補として `APPROVED` 直行候補となるが、SYSTEM_ADMIN の手動承認を必須とする運用方針（モデレーション透明性確保のため）。

**レスポンス (200)**: 更新後のキャンペーン。

**エラー**
| ステータス | 条件 |
|---|---|
| 409 | status != DRAFT、または必須項目（channels/audience）未設定 |

#### `POST /api/v1/advertiser/campaigns/messaging/{id}/launch`

APPROVED → DELIVERING 遷移。`starts_at` が現在以前なら即配信、未来なら SCHEDULED にして配信スケジューラに登録。

**エラー**
| ステータス | 条件 |
|---|---|
| 409 | status != APPROVED |
| 402 | credit_limit 不足 |

#### `POST /api/v1/advertiser/campaigns/messaging/{id}/pause`

DELIVERING / SCHEDULED → PAUSED 遷移。配信中ジョブは次バッチで停止。

未認証可。JWT 検証 → claims `{uid, token_version, channel}` → 該当チャネルを OFF にして `200 OK` 返却（HTML ページにリダイレクト）。`token_version` 不一致は `410 Gone`。

#### `POST /api/v1/me/ad-reports`

**リクエスト**
```json
{
  "campaign_id": "0190xxxx...",
  "channel_type": "EMAIL",
  "reason_code": "MISLEADING",
  "comment": "実態と異なる内容"
}
```

**レート制限**: 1 ユーザー 1 日 20 件まで。

#### `GET /api/v1/me/ad-deliveries`

自分が受信した広告一覧（過去 90 日分）。`channel_type` フィルタ可。`{data: {items: [...], next_cursor}}`。

#### `DELETE /api/v1/me/ad-deliveries`

GDPR 自己データ削除。全 `ad_*_deliveries.user_id` を NULL にセット。`campaign_id` 集計値は保持。冪等。レスポンス `204 No Content`。

#### `GET /api/v1/system-admin/ad-campaigns/review-queue`

`moderation_status IN ('PENDING','AUTO_FLAGGED','AUTO_PASSED')` を新しい順で返却。

#### `POST /api/v1/system-admin/ad-campaigns/{id}/approve`

**リクエスト**: `{"note": "問題なし"}`（任意）。

**副作用**: `moderation_status='APPROVED'`、`ad_campaign_moderation_logs` に `action='APPROVED'` 記録。広告主にメール通知。

#### `POST /api/v1/system-admin/ad-campaigns/{id}/block`

**リクエスト**: `{"reason": "景品表示法違反疑い", "refund_amount_yen": 32400}`。

**副作用**: `status='BLOCKED'`、進行中配信停止、`refund_amount_yen` を F09.11 `ad_credit_limit_requests` 経由でリファンド。広告主にメール通知 + SYSTEM_ADMIN にプッシュ通知。

#### `POST /api/v1/system-admin/ad-campaigns/{id}/unblock` (F09.17 残課題 3)

誤 BLOCK されたキャンペーンを再審査キューに戻す API。BLOCKED 状態 → REVIEW 状態 への遷移のみを許可する。
BLOCKED から直接 APPROVED に戻すのは権限濫用リスクが高いため、必ず REVIEW に戻して SYSTEM_ADMIN による再判定（`approve` または `block` 再実行）を経る運用とする。

**権限**: SYSTEM_ADMIN のみ。

**リクエスト**: `{"reason": "誤判定のため取消"}`（`reason` 必須・最大 500 文字、監査用）。

**遷移条件**: `status='BLOCKED'` のみ。それ以外は `AD_CAMPAIGN_NOT_UNBLOCKABLE` で 400 を返す。

**副作用**:
- `status='REVIEW'`, `moderation_status='PENDING'`, `blocked_reason=NULL` に更新。
- `ad_campaign_moderation_logs` に `action='UNBLOCKED'` + `reason` の行を 1 件追加。
- 監査ログイベント `CAMPAIGN_UNBLOCKED` を `AuditLogService.record` 経由で非同期発火（`metadata` に `campaign_id` と `reason` を含む）。

**レスポンス**: 204 No Content。

#### `GET /api/v1/system-admin/ad-user-reports`

`status='NEW'/'REVIEWING'` を新しい順で返却。3 件以上集まっている campaign は強調表示用フラグ `auto_suspend_candidate=true` を含める。

## 5. ビジネスロジック

### キャンペーン状態遷移マシン

```
        ┌──────────┐  submit   ┌────────┐  approve  ┌──────────┐  launch    ┌────────────┐
        │  DRAFT   ├──────────▶│ REVIEW ├──────────▶│ APPROVED ├───────────▶│ DELIVERING │
        └────┬─────┘           └───┬────┘           └────┬─────┘            └──────┬─────┘
             │                     │                     │                         │
             │ delete              │ block               │ delete? NG              │ pause
             ▼                     ▼                     │                         ▼
        (論理削除)            ┌────────┐                 │                    ┌─────────┐
                              │BLOCKED │                 │  schedule (未来)   │ PAUSED  │
                              └────────┘                 ▼                    └─────┬───┘
                                                  ┌───────────┐                     │ resume
                                                  │ SCHEDULED ├─────────────────────┘
                                                  └─────┬─────┘
                                                        │ starts_at 到達
                                                        ▼
                                                   (DELIVERING へ)

  DELIVERING ──ends_at 到達──▶ COMPLETED
  どの状態でも user 通報 3 件 → BLOCKED （自動 SUSPEND）
```

| 遷移 | 起動条件 |
|---|---|
| DRAFT→REVIEW | `submit` API、必須項目検証通過、自動 NG ワード検知実行 |
| REVIEW→APPROVED | SYSTEM_ADMIN `approve` |
| REVIEW→BLOCKED | SYSTEM_ADMIN `block` または通報 3 件 |
| BLOCKED→REVIEW | SYSTEM_ADMIN `unblock`（誤 BLOCK 取消、`moderation_status` を `PENDING` に再設定）|
| APPROVED→DELIVERING | `launch` かつ `starts_at <= now` かつ credit_limit OK |
| APPROVED→SCHEDULED | `launch` かつ `starts_at > now` |
| SCHEDULED→DELIVERING | 配信スケジューラ（5 分間隔）が `starts_at <= now` を検出 |
| DELIVERING→PAUSED | `pause` API、credit_limit 超過自動 PAUSE |
| PAUSED→DELIVERING | `launch` API（resume） |
| DELIVERING→COMPLETED | `ends_at <= now` を日次バッチで検出 |
| *→CANCELLED | 広告主が DRAFT/REVIEW のみキャンセル可（破棄相当） |

### ターゲティング評価フロー

```
1. AdAudienceResolver が ad_audience_segments を読み込む
2. INCLUDE 条件を AND で組合せ → 一次候補
3. EXCLUDE 条件を AND NOT で適用 → 最終候補
4. user_ad_preferences の各 accept_* フラグで除外
5. blocked_advertiser_account_ids でブロック広告主除外
6. user_ad_delivery_counters で週次キャップ判定（Valkey 同期）
7. 同一広告主→同一ユーザーの週次キャップ（週 1 件）判定
8. 候補ユーザー数を集計値で返却（user_id は呼出元へ漏らさない）
```

実装は `AdAudienceResolver` クラスが `SegmentEvaluator`（F09.2 から再利用）を呼び出す。`SegmentEvaluator` への入力は `segment_value` JSON、出力は `Stream<UserId>` だが、`AdAudienceResolver` 内部で消費されカウントのみ呼出元に返す。Preview API も同じ経路を通り、user_id を返さない。

### フリークエンシーキャップ判定

- **データソース**: Valkey（ホット）+ `user_ad_delivery_counters`（永続層）。
- **キー**: `ad:freq:{userId}:{weekStartDate}` （文字列カウンタ）。
- **週境界**: **ユーザー TZ で評価**。`users.timezone`（既存）の月曜 00:00 をその週の開始とする。`weekStartDate = ZonedDateTime.now(userTz).with(MONDAY).toLocalDate()`。
- **判定**: `INCR + EXPIRE`（原子的）。`INCR` の結果が `frequency_cap_override ?? 3` を超えたら配信スキップ + `DECR` でロールバック。
- **TTL**: 週末 + 1 日（次週月曜 00:00 まで保持）。
- **日次バッチ**: 02:00 に Valkey から `user_ad_delivery_counters` へ flush。Valkey 障害時のフォールバック。

### 4 チャネル委譲シーケンス

配信ワーカー `AdCampaignDeliveryWorker` が `ad_messaging_campaigns.status='DELIVERING'` を 1 分間隔でスキャンし、対象ユーザーごとに各チャネルの委譲メソッドを呼ぶ。各チャネルは F09.17 ドメインを越えるため、Service Method 呼び出し（Repository は直接触らない）で完結させ、@Transactional は F09.17 ドメイン内に閉じる。

| チャネル | 委譲先 | 呼出パラメータ |
|---|---|---|
| ANNOUNCEMENT | `AnnouncementBroadcastService.publish()` | `source_type='ADVERTISER_CAMPAIGN'`, `scope_type='ADVERTISER_AD'`, `is_advertisement=true`, `source_id=campaign_id` |
| EMAIL | `DirectMailService.sendSystemMail()` | `sender_type='SYSTEM_AD'`, `subject=[PR] <subject>`, `footer=unsubscribeJWT` |
| PUSH | `NotificationService.send()` | `source_type='ADVERTISER_CAMPAIGN'`, `priority='LOW'`, `body=【広告】<body>` |
| BANNER | `AdImpressionService.scheduleServe()` | `serving_strategy='MESSAGING_CAMPAIGN'`, `creative_id=banner_creative_id` |

> **注（F09.18 統合パス）**: EMAIL チャネルの SES 呼び出しは Phase 18-f で F09.18 outbox 経由に移行済み（2026-05-20 完了）。`ad_email_deliveries` への記録は keep（送信実績の一次データとして温存）し、`email_outbox.source_domain='advertising'`、`source_event_id=ad_email_delivery.id` で双方向トレースを担保。`ad_email_deliveries.email_outbox_id` に outbox.id を記録し逆引きも可能。課金ブリッジは `ad_email_deliveries.sent_at` / `bounce_type` を引き続き使う。詳細は F09.18 §11 移行マトリクス #15 および §12 を参照。

各委譲呼び出しは戻り値として委譲先の primary key（`announcement_feed_id` 等）を受け取り、対応する `ad_*_deliveries` レコードに保存。Valkey カウンタ INCR は配信完了時点で行う（途中失敗時のロールバックを成立させるため）。

### 開封率算出ロジック

```sql
-- ANNOUNCEMENT 既読率
SELECT
  campaign_id,
  COUNT(*) AS delivered,
  SUM(CASE WHEN read_at IS NOT NULL THEN 1 ELSE 0 END) AS read_count,
  CASE WHEN COUNT(*) = 0 THEN NULL
       ELSE SUM(CASE WHEN read_at IS NOT NULL THEN 1 ELSE 0 END) / COUNT(*)
  END AS read_rate
FROM ad_announcement_deliveries
WHERE campaign_id = ? AND month_key = ?
GROUP BY campaign_id;
```

EMAIL は `opened_at`、PUSH は `tapped_at`、BANNER は `clicked_at` を分子に同様。**ゼロ除算は NULL 返し**の共通ルール。レポート API でキャッシュ（`Cache-Control: private, max-age=60`）。

### 課金ブリッジ

月次バッチ `AdMessagingBillingBridge`（毎月 1 日 03:00 ShedLock 付き）が前月の `ad_*_deliveries` を集計し、F09.11 `ad_invoice_items` に積み上げる。`messaging_campaign_id BINARY(16) NULL` 列で識別。

| チャネル | 単価 | カウント基準 |
|---|---|---|
| ANNOUNCEMENT | ¥5 / 件 | `delivered_at IS NOT NULL` |
| EMAIL | ¥10 / 通 | `sent_at IS NOT NULL AND bounce_type IS NULL` または `bounce_type='SOFT'` |
| PUSH | ¥3 / 通 | `delivered_at IS NOT NULL AND failed_reason IS NULL` |
| BANNER | F09.7 既存 CPM/CPC | `ad_impressions` / `ad_clicks` を引き継ぎ |

**消費予算**: バッチ完了時に `ad_messaging_campaigns.consumed_budget_yen` を更新（イベント `MessagingCampaignBudgetConsumedEvent` 発行、F09.11 ダッシュボードがリアクティブ更新）。

### credit_limit 超過時の挙動

リアルタイム監視: 配信ワーカーが配信前に `advertiser_accounts.credit_used + estimated_cost > credit_limit` を判定。超過なら:

1. キャンペーン `status='PAUSED'` に遷移、`MessagingCampaignAutoPausedEvent` 発行
2. **未配信ユーザーへは送信しない**（既送信ロールバックは行わない）
3. 広告主 ADMIN にメール通知 `AD_CAMPAIGN_AUTO_PAUSED`（F09.6 経由、SYSTEM_AD ではなく SYSTEM 送信元）
4. SYSTEM_ADMIN にプッシュ通知 `AD_CAMPAIGN_AUTO_PAUSED_SYSTEM`（F04.3 経由、priority=HIGH）

`launch` API での同期判定と非同期ワーカー判定の二重に検証する。

### モデレーションロジック

#### 自動 NG ワード検知

`AdContentModerator` クラスが `submit` 時に発火。

1. キャンペーン全 channels の `subject` + `body_markdown` を結合
2. NG ワード辞書（YAML 管理、SYSTEM_ADMIN がメンテ）と照合
3. ヒットあり → `moderation_status='AUTO_FLAGGED'`、`ad_campaign_moderation_logs` に `action='AUTO_FLAGGED'` 記録
4. ヒットなし → `moderation_status='AUTO_PASSED'`、`AUTO_PASSED` 記録

#### 通報 3 件で自動 SUSPEND

`AdUserReport` 作成時、トリガーで `ad_user_reports WHERE campaign_id=? AND status IN ('NEW','REVIEWING')` の COUNT を取り、3 以上で:

1. キャンペーン `status='BLOCKED'`、`blocked_reason='USER_REPORTS_THRESHOLD'`
2. SYSTEM_ADMIN にプッシュ通知（緊急レビュー要請）
3. 当該月の配信分を `refund_amount_yen` 計算 → credit_limit にリファンド（F09.11 経由）
4. `ad_campaign_moderation_logs` に `action='BLOCKED'`、`moderator_user_id=NULL` 記録

### 多言語キャンペーンの審査

1 キャンペーンで複数 locale の `ad_messaging_campaign_channels` を持つ。SYSTEM_ADMIN は全 locale をまとめて 1 操作で承認する（個別 locale 単位の承認は採用しない。運用負荷を抑えるため）。

### 受信時 locale 選択ロジック

```
1. users.locale を取得
2. ad_messaging_campaign_channels で (campaign_id, channel_type, locale=users.locale) を検索
3. 見つからなければ locale='ja' でフォールバック
4. それも見つからなければ最初に登録された locale を使用
```

## 6. セキュリティ・コンプライアンス

### マルチテナント分離

- `AdMessagingCampaignService` の全 public メソッド入り口で `currentUser.organizationId == campaign.organizationId` を検証
- `AbstractTenantAwareRepository` を用いて Repository 層でも `organization_id` 絞り込みを強制
- SYSTEM_ADMIN のみクロステナントアクセス許可（明示の `@PreAuthorize("hasRole('SYSTEM_ADMIN')")` が付くエンドポイントに限る）

### PII 保護

- **Preview / Report / CSV すべて集計値のみ**: user_id, email, name は一切返却しない
- 100 人未満のセグメントは `estimated_reach_range='UNDER_100'` で個人特定リスク回避（F09.11 と同方針）
- 配信履歴 GET は **自分のみ**閲覧可能
- 開封ピクセル URL も JWT 認証必須（`/api/v1/ads/pixels/open?token=<JWT>`、claims `{deliveryId, type}`、HS256、exp=180d）。**user_id を URL に直書きしない**。
- CSV エクスポートは PII フリーを保証するため `AdReportCsvWriter` で固定スキーマを使用（dynamic 列禁止）

### レート制限

§4 末尾の表に準拠。Bucket4j キーは `advertiser_account_id + endpoint` または `user_id + endpoint`。超過時 `429 Too Many Requests` + `Retry-After` ヘッダ。

### 監査ログ（F10.3 連携）

| イベント | 主体 | source_type |
|---|---|---|
| `CAMPAIGN_CREATED` | 広告主 | AD_CAMPAIGN |
| `CAMPAIGN_SUBMITTED` | 広告主 | AD_CAMPAIGN |
| `CAMPAIGN_APPROVED` | SYSTEM_ADMIN | AD_CAMPAIGN |
| `CAMPAIGN_BLOCKED` | SYSTEM_ADMIN または SYSTEM（通報3件自動） | AD_CAMPAIGN |
| `CAMPAIGN_LAUNCHED` | 広告主 | AD_CAMPAIGN |
| `CAMPAIGN_PAUSED` | 広告主 / SYSTEM | AD_CAMPAIGN |
| `CAMPAIGN_COMPLETED` | SYSTEM | AD_CAMPAIGN |
| `CAMPAIGN_DELIVERED` | SYSTEM（配信ワーカー） | AD_CAMPAIGN |
| `USER_AD_PREFERENCES_UPDATED` | 受信者 | USER_AD_PREFERENCES |
| `AD_USER_REPORTED` | 受信者 | AD_USER_REPORT |
| `AD_UNSUBSCRIBED` | 受信者 / unauthenticated（JWT） | USER_AD_PREFERENCES |

### メール unsubscribe JWT

- アルゴリズム: HS256
- 有効期限: 30 日（メール内リンクの長期失効対策）
- claims: `{uid, token_version, channel}`
- 検証時に `user_ad_preferences.unsubscribe_token_version` と一致しない → 410 Gone
- `PUT /me/ad-preferences` のたびに `unsubscribe_token_version` インクリメント可能（一括失効）
- 設定 UI で「過去のメール内リンクをすべて無効化する」操作として明示

### GDPR 削除権

`DELETE /api/v1/me/ad-deliveries` 実行で:
- `ad_announcement_deliveries.user_id`, `ad_email_deliveries.user_id`, `ad_push_deliveries.user_id`, `ad_banner_deliveries.user_id` を全件 NULL に SET
- `ad_user_reports.reporter_user_id` も NULL 化
- `campaign_id` 集計値は保持（広告主の課金実績・統計を破壊しない）
- 冪等。再実行で何度実行しても結果同一

退会時匿名化フロー（CLAUDE.md 原則 4 準拠）:
1. `UserAnonymizedEvent` を購読する `AdDeliveryAnonymizationEventListener` が起動
2. 該当 user_id を持つ全 `ad_*_deliveries` を NULL 化
3. `user_ad_preferences` 行は削除（個人設定なので保持不要）
4. `user_ad_delivery_counters` 行も削除（時系列も無意味）

### モデレーション全体像

- 自動 NG ワード辞書（YAML） + SYSTEM_ADMIN 手動承認 + ユーザー通報 3 件で自動 SUSPEND + credit_limit リファンド の 4 層防御
- `ad_campaign_moderation_logs` で全イベント追跡（3 年保持）

### 「広告」ラベル必須化（景品表示法・WG 第 5 条 3 項）

| チャネル | 明示方法 |
|---|---|
| お知らせフィード | `is_advertisement=true` で「広告」バッジ表示・配色 `#FF9800` 固定・ARIA `role="region" aria-label="広告"` |
| メール | 件名 `[PR] ` プレフィックス自動付与（広告主編集不可、Service 層で強制） |
| プッシュ通知 | 本文先頭に「【広告】」自動挿入（NotificationService.send 内で強制） |
| バナー | F09.7 既存実装の「広告」ラベル（変更なし） |

i18n 別の文言は §9 を参照。

### XSS 対策

- `body_markdown` は F02.6 既存 Markdown サニタイザを通す（許可タグ・属性は F02.6 規定に従う）
- `cta_url` / `image_url` は許可スキーム + 許可ホストリストで検証（`https://` のみ、ホストは設定 YAML で管理）
- `image_url` の S3 ホストは `cdn.mannschaft.app` 限定（外部 CDN 直リンク不可）

### スパム対策

- フリークエンシーキャップ（週 3 件）
- **同一広告主 → 同一ユーザーの週次キャップ（週 1 件）**: Valkey キー `ad:freq-adv:{advertiserId}:{userId}:{weekStart}` で原子的判定
- レート制限（前掲）
- credit_limit による予算制限

### Stripe 連携

既存 F09.11 / F08.2 の Stripe Customer / Stripe Invoice 連携をそのまま使用。F09.17 では追加 Webhook なし。リファンドは F09.11 `ad_credit_limit_requests` 経由で SYSTEM_ADMIN 操作によって credit_limit を回復させる方式（既存方針踏襲）。

## 8. パフォーマンス考慮

### 配信時のバッチ分割

- Spring Batch + `StepBuilder.chunk(1000)` で 1000 ユーザー/バッチ
- パーティショニングステップで配信ワーカーを並列化（最大 4 並列。Valkey の同時接続上限を考慮）
- ジョブ失敗時は `JobRestartFailureException` でリラン可能（idempotency キー = `campaign_id + user_id + channel_type + delivery_date`）

### 配信ログのパーティショニング

- `ad_*_deliveries` は `month_key` で月次パーティション
- 6 ヶ月ホットレイヤー + 6 ヶ月〜3 年 S3 Parquet コールドレイヤー
- レポート API は過去 6 ヶ月のみホット参照、それ以前は Athena への非同期クエリで結果通知

### `ad_daily_stats` への日次集約バッチ（F09.7 拡張）

- 毎日 02:30 に日次集約バッチが `ad_*_deliveries` の前日分を `ad_daily_stats`（F09.7 既存テーブル）に集約
- `ad_daily_stats` に `messaging_campaign_id BINARY(16) NULL` 列追加で識別
- レポート API は基本このテーブルを参照することで O(1) アクセス

### Valkey カウンタ TTL

- フリークエンシーキャップ: 週末 + 1 日（次週月曜まで保持）
- 推定リーチキャッシュ: 5 分
- 同一広告主週次キャップ: 週末 + 1 日

### API レスポンスキャッシュ

| エンドポイント | Cache-Control |
|---|---|
| `GET /campaigns/messaging` | `private, max-age=60` |
| `GET /campaigns/messaging/{id}` | `private, max-age=60` |
| `GET /campaigns/messaging/{id}/report` | `private, max-age=60` |
| `POST /preview` | レスポンスに `computed_at` を含めるが Cache-Control なし。クライアント側で 5 分自前キャッシュ推奨 |
| `GET /me/ad-preferences` | `private, max-age=300` |
| `GET /me/ad-deliveries` | `private, max-age=60` |
| `GET /system-admin/ad-campaigns/review-queue` | `private, max-age=30` |
| CSV エクスポート | `no-store` |

### 推定リーチ数取得 API の非同期化

- 同期実行が 5 秒超えそうなら 202 Accepted + WebSocket トピック `ad-preview-{campaignId}` で結果通知
- 判定: 候補ユーザー数の事前推定（`AdAudienceResolver.estimateBefore()` で安価に取得）が 100,000 超なら非同期化
- 非同期結果は Valkey に 5 分 TTL で保存、WebSocket 切断時の再取得を担保

#### 3 タップオプトアウト動線

| 起点 | 1 タップ | 2 タップ | 3 タップ |
|---|---|---|---|
| メール | メール末尾 `unsubscribe` リンク | チャネル選択 OFF | 完了 |
| プッシュ | 通知長押し | 「広告受信を停止」 | 完了 |
| お知らせ | 「…」メニュー | 「設定」 | 「広告受信」OFF |

##### メール経路の SPA 実装（残課題 4 / 2026-05-17 完了）

設計書発行時の v1 実装では `GET /api/v1/ads/unsubscribe?token=...` がバックエンドから HTML を直接返却し、ワンクリックで JWT の `ch` クレーム単一チャネルを OFF にしていた（後方互換のため現在も残置）。

残課題 4 で「リンクから JWT 受領 → SPA でチャネル選択 → POST で確定 → 完了画面」の 3 ステップ UX を以下のとおり実装した。

| ステップ | 旧 v1 | 新 (残課題 4) |
|---|---|---|
| メール本文 unsubscribe リンク URL | `/api/v1/ads/unsubscribe?token=...` (BE 直接 HTML) | `/ads/unsubscribe?token=...` (Nuxt SPA) |
| 1 タップ | リンククリック | リンククリック (Nuxt SPA 起動・JWT を URL クエリで受領) |
| 2 タップ | (なし — そのまま全 OFF) | チャネル別チェックボックス選択 + 「停止する」ボタン |
| 3 タップ | 完了画面 | `POST /api/v1/ads/unsubscribe` (token + channels[]) → 完了画面 |

- 公開 POST エンドポイント: `POST /api/v1/ads/unsubscribe` (`UnsubscribeRequest{token, channels[]}` / `UnsubscribeResultResponse{disabledChannels[], remainingActiveChannels[], messageKey}`)。SecurityConfig で `permitAll`、`AdPublicEndpointRateLimitFilter` で 60/分 (IP) を GET/POST 共通で適用。
- フロントエンドページ: `frontend/app/pages/ads/unsubscribe.vue` (認証不要 / `definePageMeta({ auth: false })`)。4 チャネルチェックボックスで停止対象を選択 → POST → 完了 / エラー画面。エラーは「token 欠落」「JWT 期限切れ・無効」「レート制限 429」「その他」を区別。
- 後方互換: 旧 `GET /api/v1/ads/unsubscribe?token=...` の HTML 返却は古いメールクライアント救済のため残置。旧 URL は単一チャネル OFF、新 URL (SPA) は選択された複数チャネル OFF。
- メール本文 URL 切替: `AdEmailChannelService` の unsubscribe リンク生成を `app.base-url + /ads/unsubscribe?token=` に切替。`app.base-url` は `APP_BASE_URL` 環境変数で本番設定可能（`mannschaft.app-base-url` は廃止済み。2026-06-11 統一）。
- i18n: `advertising.unsubscribe_spa.*` ブロックを 6 言語 (ja/en/zh/ko/es/de) に追加。

#### 初回広告受信時の明示同意モーダル
