## 1. 課題・背景

### 1.1 課題 — 「行きたいね」が消えていく

現状、Mannschaft でチーム内に生まれる予定の芽は、次の2択しか行き先が無い。

| 行き先 | 何が起きるか |
|---|---|
| カレンダー（`schedules`）に登録する | 【確認済み】`start_at DATETIME NOT NULL`（`V3.040__create_schedules_table.sql`）。**日付を決めないと登録できない**。仮の日付を入れると「決まった予定」として通知・出欠・Google 同期に流れ、嘘の予定がカレンダーを汚す |
| チャット・タイムラインで話す | 流れて消える。1週間後には誰も覚えていない |

結果、「今度みんなで合宿行きたいね」「そのうち BBQ やろう」といった**日付未定のアイデアが、決まる前に死ぬ**。これは機能の欠落であって、ユーザーの怠慢ではない。

### 1.2 TimeTree 比較で採用が決まった背景【御裁可済】

競合調査（TimeTree）との比較で、Mannschaft に無く TimeTree にある強力な概念として「**キープ**」が挙がり、**採用が決定した**。

| 観点 | TimeTree の「キープ」 | 本書の設計 |
|---|---|---|
| 位置づけ | 日付未定のメモをカレンダーとは別の棚に貯める | 同じ（`schedule_keeps` テーブル） |
| 入力摩擦 | タイトルだけで置ける | 同じ（**必須はタイトル1項目のみ**・§1.3） |
| 日程確定 | キープから予定に変換できる | 同じ（**1タップで `schedules` へ落とす**・§4.5） |
| スコープ | 主に共有カレンダー単位 | **チーム／組織／個人の3スコープ**【御裁可済】（§2.3） |
| 変換後の元データ | （消える挙動） | **消さずに残し `converted_schedule_id` で紐付ける**【御裁可済】（§5.2） |

**Mannschaft 固有の勝ち筋**: チームスコープを持つことで、「行きたいね」→**チーム内で相談**→日程確定→カレンダー、という**日程化までの一連の流れがアプリ内で閉じる**。TimeTree の個人・家族用途に対し、チーム運営の意思決定導線として差別化する。

### 1.3 ADHD フレンドリー要件（CMP-005 準拠）

`memory/user_adhd_tendency.md` の3原則「**入力摩擦ゼロ・必須項目最小化・後で整理可能**」に完全準拠する。F02.5 行動メモの設計思想（【確認済み】「気分入力等の装飾的入力はオプトイン」「書かなかったことを通知で責めない」）を踏襲する。

| 原則 | 本機能での具体化 |
|---|---|
| 入力摩擦ゼロ | 作成は **タイトル1項目のみ必須**。メモ・候補日・並び順はすべて任意。1入力欄＋送信ボタンで完結 |
| 必須項目最小化 | `title` 以外に `NOT NULL`（デフォルト値なし）の入力項目を置かない |
| 後で整理可能 | メモ・候補日は後から追記できる。並び替え（`sort_order`）も後からで良い |
| 責めない・急かさない | **「キープしたまま放置している」ことを催促する通知を作らない**【既定】。滞留リマインドは実装しない（F02.5 の「メモなし週のリマインドを実装しない」判断と同思想） |
| 段階開示 | 一覧は「タイトル＋（あれば）候補日バッジ」のみ。メモ・変換操作は展開して初めて見える（F04.11 通知インボックスの段階開示に倣う） |

### 1.4 なぜ既存テーブルを流用できないか【確認済み】

| 候補 | 流用不可の理由 |
|---|---|
| `schedules` | 【確認済み】`start_at DATETIME NOT NULL`。日付未定を表現できない。NULL 許容へ緩めると、出欠生成・繰り返し展開バッチ・Google 同期・カレンダー取得クエリ（`idx_sch_team_start(team_id, start_at)` 等）**全経路が NULL を考慮する必要が生じ**、既存の稼働機能を広範囲に危険へ晒す。**新設が正当** |
| `todos`（F02.3） | TODO は「自分がやる作業」。キープは「みんなで行く予定の候補」で出席概念を持つ。役割が異なる（F02.5 の「予定=TODO／実績=行動メモ」の役割分離と同じ考え方） |
| `action_memos`（F02.5） | 個人スコープ専用・実績記録。チーム共有・日程化の導線を持たない |

## 2. スコープ

### 2.1 対象ロール

| ロール | 操作可能な範囲 |
|---|---|
| 本人（個人スコープ） | 自分のキープの作成・閲覧・編集・削除・変換 |
| チーム MEMBER 以上 | 当該チームのキープの作成・閲覧・編集・削除・変換（編集/削除は作成者本人＋チーム ADMIN。§4.6） |
| チーム SUPPORTER / GUEST | **アクセス不可**（キープはチーム内の相談段階の情報のため。§4.6） |
| 組織 MEMBER 以上 | 当該組織のキープの作成・閲覧（編集/削除は作成者本人＋組織 ADMIN） |
| 他組織・非メンバー | アクセス不可（404 で存在秘匿。§4.6） |

### 2.2 対象レベル

- [x] 組織 (Organization)
- [x] チーム (Team)
- [x] 個人 (Personal)

**主役はチームスコープ**である（§1.2）。個人スコープは「自分だけの行きたいことリスト」、組織スコープは「組織全体の年間行事候補の下書き」として提供する。

### 2.3 3スコープの排他制約【御裁可済】

`schedules` と**同じ列パターン・同じ排他方式**を採る（【確認済み】`chk_schedule_scope` の作法をそのまま踏襲）。

```sql
CONSTRAINT chk_schedule_keep_scope CHECK (
  (team_id IS NOT NULL AND organization_id IS NULL AND user_id IS NULL) OR
  (team_id IS NULL AND organization_id IS NOT NULL AND user_id IS NULL) OR
  (team_id IS NULL AND organization_id IS NULL AND user_id IS NOT NULL)
)
```

- **DB レベル CHECK ＋ アプリ層バリデーションの二重保護**（`schedules` の前例に同じ）。アプリ層は 400（`SCHEDULE_KEEP_003`）で分かりやすく返し、DB CHECK は最後の砦とする。
- **`schedules` に後から追加された `committee_id` は本書では採らない**【既定】。委員会スコープのキープ需要は現時点で無く、必要になった時点で CHECK を拡張する（`schedules` が辿った拡張経路と同じ手順が使えるため後付け可能）。

### 2.4 本書のスコープ外（明示的な後回し）

- キープへの出欠・投票（候補日の多数決）。→ 候補日は**テキスト的な候補メモに留める**（§3.3）。投票が要るなら村の寄合（`village_meetups`）または F05.4 アンケートを使う。
- キープの繰り返し設定・リマインド。→ 日付が無いものにリマインドは付かない（§1.3 の「急かさない」原則）。
- キープへのファイル・画像添付。→ Wave 3 以降の拡張候補（§12）。
- Google Calendar 同期。→ **キープは同期しない**（日付が無いので Google 側に表現できない）。変換後の `schedules` が従来どおり同期対象になる。

## 3. DB 設計

### 3.1 新規テーブル一覧

| テーブル | 種別 | ドメイン | 主キー方針 |
|---|---|---|---|
| `schedule_keeps` | 新規 | schedule | **BIGINT UNSIGNED AUTO_INCREMENT**（`BaseEntity` 継承。原則6の例外・§3.2） |

**追加テーブルは1本のみ**。候補日は JSON 列で持ち、子テーブルを作らない（§3.3）。

### 3.2 主キー方針 — なぜ `BaseEntity`（BIGINT）か【提案・原則6の例外】

CLAUDE.md 原則6は「新規テーブルは `UuidV7Entity` 継承」だが、**本テーブルは `BaseEntity`（BIGINT UNSIGNED）を採る**。

- 【確認済み】`UuidV7Entity` は本リポジトリの schedule ドメインには**存在しない**（村ドメイン等の新しい系統に存在する基底）。schedule ドメインの実体は `ScheduleEntity extends BaseEntity`（`schedule/entity/ScheduleEntity.java`）で、`id: Long`・`@GeneratedValue(IDENTITY)`。
- キープは **`schedules` と相互参照する**（`converted_schedule_id` → `schedules.id` = BIGINT）。ID 体系を混在させると、変換 API・逆参照・FE の型がすべて2体系を扱うことになり、同一ドメイン内で無用な複雑さを生む。
- よって **`schedule_keeps` は `BaseEntity` を継承し `id BIGINT UNSIGNED AUTO_INCREMENT`** とする。これは「既存ドメインの ID 体系に合わせる」ための意図的な例外であり、`docs/architecture/domain_db_design_principles.md` の例外区分（既存テーブル群との整合）に該当する。実装 PR の Javadoc に理由を明記すること。
- 【確認済み】`BaseEntity` は `id`・`createdAt`・`updatedAt` のみを持ち、**`deletedAt` は含まない**。`ScheduleEntity` と同様に **`deletedAt` フィールドを自前で持ち `@SQLRestriction("deleted_at IS NULL")` を付す**（原則3・論理削除）。

### 3.3 `schedule_keeps` DDL【提案】

| カラム名 | 型 | NULL | デフォルト | 説明 |
|---|---|---|---|---|
| `id` | BIGINT UNSIGNED | NO | AUTO_INCREMENT | PK |
| `team_id` | BIGINT UNSIGNED | YES | NULL | チームスコープ（`teams.id` を ID 参照。同一ドメイン外のため §3.5 参照） |
| `organization_id` | BIGINT UNSIGNED | YES | NULL | 組織スコープ |
| `user_id` | BIGINT UNSIGNED | YES | NULL | 個人スコープ（＝オーナー） |
| `title` | VARCHAR(200) | NO | — | **唯一の必須入力**。空文字・空白のみは 400 で拒否（§7） |
| `memo` | TEXT | YES | NULL | 任意メモ（「あそこの温泉が良いらしい」等） |
| `candidate_dates` | JSON | YES | NULL | 候補日の配列（**任意**）。形式は §3.4 |
| `status` | ENUM('KEPT','SCHEDULED','ARCHIVED') | NO | 'KEPT' | 状態（§5） |
| `converted_schedule_id` | BIGINT UNSIGNED | YES | NULL | 変換で生成した `schedules.id`。`status='SCHEDULED'` のとき非 NULL（§5.2） |
| `sort_order` | SMALLINT UNSIGNED | NO | 0 | 一覧の手動並び順（小さいほど上）。既定 0 = 未指定 |
| `created_by` | BIGINT UNSIGNED | YES | NULL | 作成者（`users.id` を ID 参照。個人スコープでは `user_id` と一致） |
| `created_at` | DATETIME | NO | CURRENT_TIMESTAMP | `BaseEntity` |
| `updated_at` | DATETIME | NO | CURRENT_TIMESTAMP ON UPDATE | `BaseEntity` |
| `deleted_at` | DATETIME | YES | NULL | 論理削除（原則3） |

```sql
CREATE TABLE schedule_keeps (
  id                    BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  team_id               BIGINT UNSIGNED NULL,
  organization_id       BIGINT UNSIGNED NULL,
  user_id               BIGINT UNSIGNED NULL,
  title                 VARCHAR(200)    NOT NULL,
  memo                  TEXT            NULL,
  candidate_dates       JSON            NULL,
  status                ENUM('KEPT','SCHEDULED','ARCHIVED') NOT NULL DEFAULT 'KEPT',
  converted_schedule_id BIGINT UNSIGNED NULL,
  sort_order            SMALLINT UNSIGNED NOT NULL DEFAULT 0,
  created_by            BIGINT UNSIGNED NULL,
  created_at            DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at            DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  deleted_at            DATETIME        NULL,
  PRIMARY KEY (id),
  CONSTRAINT chk_schedule_keep_scope CHECK (
    (team_id IS NOT NULL AND organization_id IS NULL AND user_id IS NULL) OR
    (team_id IS NULL AND organization_id IS NOT NULL AND user_id IS NULL) OR
    (team_id IS NULL AND organization_id IS NULL AND user_id IS NOT NULL)
  ),
  CONSTRAINT chk_schedule_keep_converted CHECK (
    (status = 'SCHEDULED' AND converted_schedule_id IS NOT NULL) OR
    (status <> 'SCHEDULED')
  ),
  INDEX idx_skeep_team   (team_id,         status, sort_order, id),
  INDEX idx_skeep_org    (organization_id, status, sort_order, id),
  INDEX idx_skeep_user   (user_id,         status, sort_order, id),
  INDEX idx_skeep_converted (converted_schedule_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;
```

**index の意図**:

| index | 用途 |
|---|---|
| `idx_skeep_team (team_id, status, sort_order, id)` | チームのキープ一覧（既定 `status='KEPT'` 絞り＋ `sort_order` 昇順 → `id` 降順）を index だけで解決する |
| `idx_skeep_org` / `idx_skeep_user` | 同上（組織／個人スコープ） |
| `idx_skeep_converted (converted_schedule_id)` | **逆参照**「この予定はどのキープから生まれたか」を `schedules` 側から引く（§5.2） |

**照合順序**: `utf8mb4_0900_ai_ci`（【確認済み】リポジトリ統一方針）。

### 3.4 `candidate_dates` JSON 形式【提案】

「いつがいい？」の**メモ**であり、投票機構ではない（§2.4）。

```json
["2026-09-12", "2026-09-19", "2026-10-03"]
```

| 規約 | 内容 |
|---|---|
| 型 | `String[]`（ISO-8601 の日付 `YYYY-MM-DD`。**時刻は持たない**） |
| 件数上限 | **10 件**【既定】。超過は 400（`SCHEDULE_KEEP_005`） |
| 並び | 保存時に昇順ソート・重複除去してから格納（安定した表示のため） |
| 省略 | `null` または `[]`（どちらも「候補日なし」として扱い、API は `null` を返す） |
| Java 側マッピング | 【確認済み】`ScheduleEntity.recurrenceRule` の前例に倣い **`@Column(columnDefinition = "JSON") private String candidateDates;`（String 保持）** とし、Service 層で `List<LocalDate>` へ変換する。JSON 直マッピングは既存作法から外れるため採らない |

**なぜ子テーブルにしないか**: 候補日は投票対象ではなく順序も持たない、キープに完全従属する付随データである。子テーブルにすると N+1・CASCADE・並び順管理のコストが付き、「入力摩擦ゼロ」の実装が重くなる。10 件上限の固定長配列なので JSON 列で十分（`schedules.recurrence_rule` と同じ判断）。

**⚠️ タイムゾーン**: `candidate_dates` は **日付のみ**（壁時計の日付）であり、瞬間ではない。FE で `Date` に変換して tz 投影し直すと1日ずれる（memory `project_fe_datetime_picker_instant_vs_wallclock` の既知の罠）。**文字列 `YYYY-MM-DD` のまま扱い、`localDate.ts` のユーティリティを使う**こと。

### 3.5 FK 方針とドメイン境界（原則1・2）【提案】

| 参照 | FK | 理由 |
|---|---|---|
| `team_id` → `teams.id` | **張らない** | チームは team ドメイン。**クロスドメイン FK 禁止**（原則1）。index のみ。整合はアプリ層で保証 |
| `organization_id` → `organizations.id` | **張らない** | 同上 |
| `user_id` → `users.id` | **張らない** | 同上（user ドメイン）。退会時の扱いは §3.7 |
| `created_by` → `users.id` | **張らない** | 同上 |
| `converted_schedule_id` → `schedules.id` | **張らない**【既定】 | `schedules` は**同一 schedule ドメイン**なので原則1には抵触しないが、CASCADE を張ると「予定を消したらキープごと消える」という誤った意味になる。**予定が消えてもキープは残す**（§5.4）ため FK は張らず index のみとし、アプリ層で解決する |

**`@Transactional` の閉じ方（原則5）**: キープの CRUD は schedule ドメイン内で完結する。変換（§4.5）は「キープ更新＋`schedules` 作成」の**両方が schedule ドメイン内**なので単一トランザクションで良い。通知（notification ドメインへの越境・§6）だけは分離し、**コミット後の best-effort** とする（通知失敗で変換が巻き戻らない）。

### 3.6 ER 図

```
teams (1) ──── (N) schedule_keeps          ※ team_id / organization_id / user_id は XOR（chk_schedule_keep_scope）
organizations (1) ─ (N) schedule_keeps        FK は張らない（原則1・ID 参照＋index のみ）
users (1) ──── (N) schedule_keeps

schedule_keeps (1) ──── (0..1) schedules
     converted_schedule_id ──▶ schedules.id
     （FK なし・index のみ。status='SCHEDULED' のとき非 NULL）
     ◀── 逆参照「この予定はどのキープから生まれたか」= idx_skeep_converted
```

### 3.7 退会・チーム削除時の扱い【提案】

原則3・4（論理削除・退会時匿名化）に整合させる。

| 契機 | 扱い |
|---|---|
| ユーザー退会（`UserAnonymizedEvent`） | **個人スコープ（`user_id` = 退会者）のキープは論理削除**（本人以外に価値が無い私的メモのため）。**チーム／組織スコープのキープは残置**し、`created_by` の表示解決のみ匿名化する（チームの資産であり消すと他メンバーの相談履歴が失われる）。`memo` は自由記述で PII 混入がありうるが、チームメンバーに向けて書かれた共有メモであり、`created_by` の匿名化で足りると判断する【既定】 |
| チーム削除 | チームスコープのキープは**同一トランザクション外でアプリ層が論理削除**（FK CASCADE は張らないため・原則1）。チームは論理削除が基本なので、一覧クエリがチームの `deleted_at` を見る限り実害は無いが、明示的に落とす |
| 変換先 `schedules` の削除 | キープは**残す**。`status` は `SCHEDULED` のまま・`converted_schedule_id` は保持する（§5.4） |

### 3.8 Flyway

- 新規 migration（1本）: `V{major}.{yyyyMMddHHmmss}__create_schedule_keeps.sql`
- **major はマージ時に `origin/main` 全体の最大 major +1 で確定する**（本書執筆時点の最大は **V175** → 想定 **V176**。**実装ブランチ作成時に必ず再確認**すること。memory `feedback_migration_version_collision`）。
- **minor はタイムスタンプ必須**（連番禁止・番人 `FlywayTimestampNamingGuardTest` が拒否）。`date -u '+%Y%m%d%H%M%S'` で採る。
- **rollback SQL 方針**【提案】: Flyway の undo は使わない（有償機能）。本 migration は **`CREATE TABLE` 1本のみで既存テーブルへの ALTER を含まない**ため、切り戻しは **`DROP TABLE schedule_keeps;`** で完結する。この DROP 文を migration ファイル冒頭のコメントに「-- rollback: DROP TABLE schedule_keeps;」として記載しておく（運用時に手で流せる形にする）。既存データへの破壊的変更が無いので、切り戻しによる既存機能への影響はゼロ。

### 4.5 変換 — `POST .../{keepId}/convert`【御裁可済の中核】

キープを**カレンダーの予定へ落とす**。「1タップで日程化」の実体。

**リクエスト**

```json
{
  "startAt": "2026-08-15T09:00:00",
  "endAt": "2026-08-16T17:00:00",
  "allDay": false
}
```

| フィールド | 型 | null 許容 | 必須 | 説明 |
|---|---|---|---|---|
| `startAt` | String (ISO-8601 LocalDateTime) | ✕ | ○ | 確定した開始日時。`schedules.start_at` が NOT NULL のため必須 |
| `endAt` | String | ○ | ✕ | 省略可（`schedules.end_at` は NULL 許容） |
| `allDay` | Boolean | ✕ | ✕（既定 false） | true のとき `startAt` の時刻は `00:00:00` に正規化（`schedules` の既存規約に同じ） |

- **候補日から1タップ**: FE は候補日バッジをタップすると `startAt` にその日付＋既定時刻（`allDay=true`）を載せて即 POST する。**追加入力なしで変換完了できる**こと（AC-08）。
- **サーバ側の処理**（単一トランザクション・schedule ドメイン内で完結・原則5）:
  1. キープを取得し認可（§4.6）・`status='KEPT'` を確認（他は 409 `SCHEDULE_KEEP_004`）
  2. `schedules` に新規行を作る。`title`/`description(=memo)`/スコープ列（`team_id`/`organization_id`/`user_id`）は**キープからコピー**。`event_type='OTHER'`・`status='SCHEDULED'`・`attendance_required=false`（＝出欠は作らない。日程が決まっただけの段階で出欠を強制しない＝§1.3「急かさない」）
  3. キープを `status='SCHEDULED'`・`converted_schedule_id=<新規 schedules.id>` へ更新（**元レコードは削除しない**【御裁可済】）
  4. 通知は **コミット後に best-effort** で発火（§6）

**⚠️ 日時バインド**: `startAt` はリクエストボディ経由＝Jackson 経路。クエリパラメータ経路（ConversionService）とは**独立**であり片方の修正は他方に届かない（memory `project_datetime_binding_path_asymmetry`）。本 API はボディのみなので Jackson 側の規約に従う。

**レスポンス 200**

```json
{
  "data": {
    "keep": { "id": 1234, "status": "SCHEDULED", "convertedScheduleId": 55501, "...": "..." },
    "schedule": { "id": 55501, "title": "夏合宿", "startAt": "2026-08-15T09:00:00", "...": "..." }
  }
}
```

**逆参照**: `GET /api/v1/schedules/{scheduleId}` 系のレスポンスに **`originKeepId`（Long・null 許容）** を追加する【提案】。`idx_skeep_converted` で引ける。「この予定はどのキープから生まれたか」を FE が辿れるようにする（御裁可済み方針の実体）。

### 4.6 認可【提案・F00 準拠】

**deny-by-default**（`docs/security/README.md`）。

| 判定 | 方式 |
|---|---|
| スコープ所属 | チーム／組織スコープは **リクエスト者が当該チーム／組織の MEMBER 以上**であることを検証。個人スコープは `user_id == getCurrentUserId()` |
| 可視性 | 【確認済み】schedule ドメインは `schedule/visibility/ScheduleVisibilityResolver`（`AbstractContentVisibilityResolver<ScheduleEffectiveVisibility, ScheduleVisibilityProjection>` を継承・`referenceType() = ReferenceType.SCHEDULE`）を持ち、F00 `ContentVisibilityResolver` の実装系に参加している。**キープも同じ Resolver パターンに従う**【提案】: `ScheduleKeepVisibilityResolver` を新設し `ReferenceType.SCHEDULE_KEEP`（新規 enum 値）を持たせる。**独自の可視性述語を Service に書かない**（memory `feedback_visibility_bypass_f00_audit`：独自述語は漏洩源） |
| 実効可視性 | キープは `MEMBERS_ONLY` 相当固定【既定】。`schedules` のような `min_view_role`/`visibility` 列は**持たない**（設定項目を増やさない＝入力摩擦ゼロ）。SUPPORTER/GUEST には見せない（§2.1） |
| 編集・削除・変換 | **作成者本人 ＋ 当該スコープの ADMIN** のみ。それ以外は 403（`SCHEDULE_KEEP_006`） |
| 非メンバーからのアクセス | **404**（存在秘匿。403 だと「そのチームにそのキープがある」ことが漏れる） |

**⚠️ 認可の実装上の落とし穴**（実装者向け・memory 由来）:
- `getCurrentUserId()` の戻り値を `teamId` として使い回す実装は**常に誤り**（IDOR。`project_matching_authz_userid_as_teamid_idor`）。
- 認可引数を取るが本体で使っていない「死んだ引数」は ArchUnit 番人を欺く（`feedback_dead_authz_param_deceives_guard`）。**到達を検証**すること。
- 新規エンドポイントは **ArchUnit 番人 ＋ `addFilters=false` の契約 IT** の両対応が必要（`feedback_new_authz_endpoint_archunit_and_addfilters_it`）。契約 IT には `@WithMockUser` を付す。

## 5. 状態遷移

### 5.1 遷移図

```
                 (作成)
                    │
                    ▼
              ┌──────────┐   convert（日程確定）   ┌──────────────┐
              │  KEPT    │ ─────────────────────▶ │  SCHEDULED   │
              │ 日付未定 │ ◀───────────────────── │ 予定になった  │
              └──────────┘   revert（変換の取消）  └──────────────┘
                 │    ▲                                  │
        archive  │    │ restore                          │ archive
                 ▼    │                                  ▼
              ┌───────────────────────────────────────────┐
              │                 ARCHIVED                   │
              │  やらないことにした／終わった（読み取り専用）  │
              └───────────────────────────────────────────┘
```

### 5.2 各状態の意味

| status | 意味 | `converted_schedule_id` | 編集可否 |
|---|---|---|---|
| `KEPT` | 日付未定でキープ中（既定） | NULL | 可 |
| `SCHEDULED` | 変換済み。カレンダーに実体がある | **非 NULL**（`chk_schedule_keep_converted` で DB 強制） | `memo` のみ可【既定】。`title`/`candidateDates` は変換先が正になるので不可（409 `SCHEDULE_KEEP_007`） |
| `ARCHIVED` | 見送り／完了。一覧の既定表示から外れる | 保持（変換後にアーカイブした場合） | 不可（読み取り専用） |

### 5.3 逆遷移の可否【既定】

| 遷移 | 可否 | API | 挙動 |
|---|---|---|---|
| `KEPT` → `SCHEDULED` | ○ | `POST .../convert` | §4.5 |
| `SCHEDULED` → `KEPT`（revert） | **○** | `POST .../{keepId}/revert` | **変換先 `schedules` を論理削除し**、キープを `status='KEPT'`・`converted_schedule_id=NULL` に戻す。「日程が流れた」ときの正しい戻し方。変換先の予定に**既に出欠回答が付いている場合は 409**（`SCHEDULE_KEEP_008`）で拒否し、予定側で運用させる（回答を握りつぶさない＝対処療法禁止の原則） |
| `KEPT` / `SCHEDULED` → `ARCHIVED` | ○ | `POST .../archive` | 読み取り専用化。`SCHEDULED` からのアーカイブでも**変換先 `schedules` は消さない**（予定は生きている） |
| `ARCHIVED` → `KEPT`（restore） | **○** | `POST .../{keepId}/restore` | 「やっぱりやりたい」を許す（§1.3 後で整理可能）。`converted_schedule_id` は NULL にクリアする |
| `ARCHIVED` → `SCHEDULED` | **✕** | — | 直行不可。`restore` して `KEPT` に戻してから `convert` する（遷移経路を1本に絞り、状態爆発を防ぐ） |

### 5.4 変換先 `schedules` が削除されたとき【提案】

- キープは **`status='SCHEDULED'` のまま・`converted_schedule_id` も保持**する（履歴として正しい。「一度は日程化された」事実は消さない）。
- API レスポンスは `convertedScheduleId` を返し続けるが、FE が予定を引くと 404 になる。よって **レスポンスに `convertedScheduleExists`（Boolean）を含める**【提案】。false なら FE は「予定は削除されました」と表示し、`revert` 導線を出す。
- **`chk_schedule_keep_converted` は破れない**（`converted_schedule_id` は非 NULL のままなので CHECK を満たす）。

## 6. 通知連携（F04.3）

### 6.1 通知する契機・しない契機

| 契機 | 通知 | 理由 |
|---|---|---|
| チーム／組織スコープのキープが**変換された**（日程確定） | **○** | 「行きたいねが本当に決まった」＝チーム全員に価値がある最重要イベント |
| チーム／組織スコープのキープが**作成された** | **○（既定 OFF・設定でON）**【既定】 | 相談の芽が立ったことを知りたいチームもあるが、常時 ON だと通知過多。チーム設定で opt-in |
| キープが編集された／並び替えられた | **✕** | ノイズ |
| **キープが長期間放置されている（滞留リマインド）** | **✕【重要】** | §1.3 ADHD 原則。「決められていないこと」を通知で責めない。F02.5 の「メモなし週のリマインドを実装しない」判断と同一思想。**実装してはならない** |
| 個人スコープのキープ | **✕** | 自分しかいない |

### 6.2 配線【提案】

【確認済み】既存の schedule ドメインは通知配線を持つ。それに揃える。

| 項目 | 値 |
|---|---|
| 通知種別 | **schedule ドメイン独自の文字列種別** `SCHEDULE_KEEP_CONVERTED` / `SCHEDULE_KEEP_CREATED`。**核 `NotificationType` enum は改変しない**（横断 enum への波及回避。F17.2 §3.4 の前例と同方針） |
| 宛先 | チームスコープ = 当該チームの MEMBER 以上。組織スコープ = 当該組織の MEMBER 以上。**キープを作成／変換した本人は除外**（自分の操作を自分に通知しない） |
| `actionUrl` | 変換通知は**変換先の予定**へ（`/teams/{slug}/schedules/{scheduleId}`）。作成通知はキープ一覧へ |
| トランザクション | **コミット後に best-effort**（§3.5）。`TransactionSynchronizationManager.registerSynchronization(...)` の `afterCommit()` に載せる。通知失敗で変換を巻き戻さない。**ただし失敗はログに残す**（握りつぶさない・CLAUDE.md 障害対応の原則2） |

> ⚠️ **同一トランザクション throw の罠**: `afterCommit` から呼ぶ処理を `REQUIRES_NEW` にしたい場合、同一 Bean 内の自己呼び出しでは `@Transactional` が効かない（別 Bean へ切り出すか `TransactionTemplate` を使う。memory `feedback_transactional_event_listener_requires_new`）。

| `SCHEDULE_KEEP_005` | `KEEP_TOO_MANY_CANDIDATE_DATES` | 400 | 候補日は最大10件です | `candidateDates` 11 件以上／日付形式不正 |
| `SCHEDULE_KEEP_006` | `KEEP_FORBIDDEN` | 403 | このキープを操作する権限がありません | メンバーだが作成者でも ADMIN でもない者の編集／削除／変換 |
| `SCHEDULE_KEEP_007` | `KEEP_ALREADY_SCHEDULED` | 409 | 予定になったキープのこの項目は編集できません | `SCHEDULED` 状態で `title`/`candidateDates` を PATCH |
| `SCHEDULE_KEEP_008` | `KEEP_REVERT_BLOCKED_BY_ATTENDANCE` | 409 | 出欠の回答があるため変換を取り消せません | `revert` 時に変換先 `schedules` に出欠回答が存在 |
| `SCHEDULE_KEEP_009` | `KEEP_INVALID_STATE_TRANSITION` | 409 | この状態遷移はできません | `ARCHIVED` → `SCHEDULED` の直行等（§5.3） |
| `SCHEDULE_KEEP_010` | `KEEP_LIMIT_EXCEEDED` | 409 | キープの上限に達しました | スコープあたりの件数上限超過（§10.1） |

> **注記**: `ScheduleKeepErrorCode` は**新規 enum なので 001 から採番でき、既存との衝突は原理的に無い**。ただし **`ErrorCode` 実装全体でコード文字列がユニークである前提**があるため、**確定はマージ時に `SCHEDULE_KEEP_` 接頭辞が他 enum で未使用であることを再確認**すること（採番衝突回避・memory `feedback_migration_version_collision` と同様の直前再確認）。

## 9. 受け入れ条件（AC）

実機 E2E（`/実機`）で観測可能な粒度で記述する。

### 9.1 正常系 — 作成・一覧

- **AC-01（ADHD 中核）**: チーム MEMBER が **タイトル1項目だけ**（`{"title":"夏合宿"}`）を POST して **201** が返り、一覧に現れる。**メモ・候補日を空のまま送っても 400 にならない**。
- **AC-02**: `memo` と `candidateDates`（3件）を付けて作成すると、そのまま保存され GET で同じ値が返る。`candidateDates` は**昇順ソート・重複除去**されて返る。
- **AC-03**: 一覧 GET は既定で `status='KEPT'` のみを返し、`sort_order` 昇順 →`id` 降順で並ぶ。`status=ALL` を付けると `SCHEDULED`・`ARCHIVED` も含まれる。
- **AC-04**: 個人スコープ（`/api/v1/me/schedule-keeps`）に作成したキープは、チーム一覧・組織一覧のいずれにも現れない。
- **AC-05**: `POST .../reorder` で `orderedIds` の順に並び替わり、GET の順序が変わる。リクエストに含めなかったキープの `sort_order` は変化しない。

### 9.2 正常系 — 変換・状態遷移

- **AC-06**: `KEPT` のキープに `POST .../convert`（`startAt` のみ指定）すると 200 が返り、(a) キープの `status` が `SCHEDULED`・`convertedScheduleId` が非 null になり、(b) **チームカレンダーに同じタイトルの予定が実際に現れる**。
- **AC-07（御裁可済の中核）**: 変換後も**キープのレコードは消えていない**。`status=ALL` の一覧に `SCHEDULED` として残り、`convertedScheduleId` から予定を辿れる。
- **AC-08（1タップ）**: 候補日バッジをタップして変換したとき、**追加の入力ダイアログを経ずに**変換が完了し、その候補日が予定の日付になる（`allDay=true`）。
- **AC-09（逆参照）**: 変換で生まれた予定の詳細 API が `originKeepId` を返し、FE で「このキープから作られました」表示が出る。キープ由来でない予定は `originKeepId=null`。
- **AC-10**: `POST .../archive` で `ARCHIVED` になり既定一覧から消える。`POST .../restore` で `KEPT` に戻り既定一覧に再び現れる（`convertedScheduleId` は null にクリアされる）。
- **AC-11**: `SCHEDULED` のキープに `POST .../revert` すると `KEPT` に戻り、**変換先の予定がカレンダーから消える**（論理削除）。

### 9.3 異常系

- **AC-12**: `{"title":""}` / `{"title":"   "}` は **400 `SCHEDULE_KEEP_002`**。
- **AC-13**: `candidateDates` を 11 件送ると **400 `SCHEDULE_KEEP_005`**。日付形式でない文字列（`"2026/08/15"`）も同コードで拒否。
- **AC-14（認可・IDOR）**: **別チームの** MEMBER が `/api/v1/teams/{他チームslug}/schedule-keeps/{keepId}` を GET すると **404 `SCHEDULE_KEEP_001`**（403 ではない＝存在秘匿）。
- **AC-15（認可）**: チーム MEMBER だが作成者でも ADMIN でもないユーザーが PATCH / DELETE / convert すると **403 `SCHEDULE_KEEP_006`**。**GET（閲覧）は 200** で通る。
- **AC-16（認可）**: チーム SUPPORTER / GUEST がチームキープ一覧を GET すると **404**（アクセス不可・§2.1）。未ログインは **401**。
- **AC-17**: 既に `SCHEDULED` のキープに再度 `convert` すると **409 `SCHEDULE_KEEP_004`**。
- **AC-18**: `SCHEDULED` のキープに `title` を PATCH すると **409 `SCHEDULE_KEEP_007`**。`memo` の PATCH は 200 で通る。
- **AC-19**: `ARCHIVED` のキープに直接 `convert` すると **409 `SCHEDULE_KEEP_009`**。
- **AC-20**: 変換先の予定に出欠回答が付いている状態で `revert` すると **409 `SCHEDULE_KEEP_008`**。予定は消えない。

### 9.4 境界

- **AC-21**: `title` **200 文字ちょうど**は 201、**201 文字**は 400。
- **AC-22**: `candidateDates` **10 件ちょうど**は 201、**11 件**は 400。
- **AC-23**: `candidateDates` に `[]`（空配列）を送ると保存され、GET レスポンスは **`null`**（空配列ではない・§4.2 契約）。
- **AC-24（TZ 境界）**: 候補日 `"2026-08-15"` を保存し、**ブラウザ TZ を UTC / Asia/Tokyo / America/Los_Angeles に切り替えても、表示される日付は常に 8/15**（日付は壁時計であり瞬間ではない・§3.4）。
- **AC-25（件数上限）**: スコープあたりのキープが上限（§10.1）に達した状態で作成すると **409 `SCHEDULE_KEEP_010`**。上限-1 件目までは 201。
- **AC-26（変換先削除）**: 変換先の予定を削除した後もキープは `SCHEDULED` のまま残り、レスポンスの `convertedScheduleExists` が **false** になり、FE に「元の予定は削除されました」が表示される。
- **AC-27（退会）**: ユーザー退会後、そのユーザーが作った**チームスコープ**のキープは一覧に残り `createdBy` が匿名化表示になる。**個人スコープ**のキープは一覧から消える（論理削除・§3.7）。
- **AC-28（通知しない保証）**: キープを作成して長期間放置しても、**滞留を催促する通知が一切送られない**（§6.1・ADHD 原則）。関連するバッチ・スケジューラが存在しない。

## 10. 非機能

### 10.1 件数上限【既定】

| スコープ | 上限（`status='KEPT'` の件数） | 根拠 |
|---|---|---|
| 個人 | **200 件** | 「行きたいことリスト」として現実的な上限。超えるとリスト自体が認知負荷になる（ADHD 配慮としてもむしろ上限は必要） |
| チーム | **300 件** | 数十人が数年溜めても届かない |
| 組織 | **300 件** | 同上 |

- 上限は **`status='KEPT'` のみで数える**（`ARCHIVED`・`SCHEDULED` は含めない）。「見送る」ことで枠が空くので、ユーザーは詰まったら整理すればよい。
- 超過時は 409 `SCHEDULE_KEEP_010` と、i18n メッセージで「見送りにすると枠が空きます」を案内する（**責めない文言**にする）。
- 上限はレートリミットではない（F02.5 の「摩擦ゼロ原則と矛盾しない上限」の考え方に同じ）。

### 10.2 並び順

- 既定は `sort_order` 昇順 → `id` 降順。`sort_order` の既定 0 のため、**何も並び替えていない状態では「新しい順」**になる（直近で思いついたことが上に来る＝ADHD 的に正しい）。
- `sort_order` は `SMALLINT UNSIGNED`（0〜65535）。§10.1 の上限（最大 300）に対し十分な余裕がある。
- **手動並び替えは任意機能**であり、使わなくても成立する（§1.3 後で整理可能）。

### 10.3 クエリ性能・シャーディング耐性

- 全一覧クエリは `idx_skeep_team` / `idx_skeep_org` / `idx_skeep_user`（`(scope列, status, sort_order, id)`）でカバーされ、**ファイルソートを起こさない**。実装時に `EXPLAIN` で `Using index condition` を確認すること。
- **テナント絞り込み**（原則7）: 組織スコープの Repository は **`AbstractTenantAwareRepository` を継承**する（`organization_id` を持つため）。チーム／個人スコープのクエリは対応する index で絞る。
- **シャーディング耐性**（CMP-008）: シャードキー候補は **スコープ列（`team_id` / `organization_id` / `user_id`）**。キープは**単一スコープに閉じた小さなデータ**であり、スコープをまたぐ集計・JOIN を一切行わない設計なので、スコープ列でのシャーディングに素直に耐える。
- **`converted_schedule_id` の逆参照は同一 schedule ドメイン内の参照**であり、シャード分割時も同じシャード（同一スコープ）に落ちる（キープと変換先の予定は必ず同じスコープ列の値を持つため）。**クロスシャード JOIN は発生しない**。
- N+1: 一覧の `createdBy` 表示名解決は **一括解決**（`resolveAll` 相当）で行い、行ごとにユーザーを引かない。

### 10.4 後方互換

- 新規テーブル1本＋既存 API へのフィールド追加（`originKeepId`）のみ。**既存テーブルへの ALTER も、既存 API の破壊的変更も無い**。
- `originKeepId` は **null 許容の追加フィールド**なので、既存クライアントは無視すればよい（Expand 方針）。
