## 1. 課題・背景

### 1.1 課題 — 「行きたいね」が消えていく

現状、Mannschaft でチーム内に生まれる予定の芽は、次の2択しか行き先が無い。

| 行き先 | 何が起きるか |
|---|---|
| カレンダー（`schedules`）に登録する | 【確認済み】`start_at DATETIME NOT NULL`（`V3.040__create_schedules_table.sql`）。**日付を決めないと登録できない**。仮の日付を入れると「決まった予定」として通知・出欠・Google 同期に流れ、嘘の予定がカレンダーを汚す |
| チャット・タイムラインで話す | 流れて消える。1週間後には誰も覚えていない |

結果、「今度みんなで合宿行きたいね」「そのうち BBQ やろう」といった**日付未定のアイデアが、決まる前に死ぬ**。これは機能の欠落であって、ユーザーの怠慢ではない。

### 1.2 TimeTree 比較で採用が決まった背景【御裁可済】

競合調査（TimeTree）との比較で、Mannschaft に無く TimeTree にある強力な概念として「**キープ**」が挙がり、**採用が決定した**。

| 観点 | TimeTree の「キープ」 | 本書の設計 |
|---|---|---|
| 位置づけ | 日付未定のメモをカレンダーとは別の棚に貯める | 同じ（`schedule_keeps` テーブル） |
| 入力摩擦 | タイトルだけで置ける | 同じ（**必須はタイトル1項目のみ**・§1.3） |
| 日程確定 | キープから予定に変換できる | 同じ（**2タップ以内で `schedules` へ落とす**・§4.5） |
| スコープ | 主に共有カレンダー単位 | **チーム／組織／個人の3スコープ**【御裁可済】（§2.3） |
| 変換後の元データ | （消える挙動） | **消さずに残し `converted_schedule_id` で紐付ける**【御裁可済】（§5.2） |

**Mannschaft 固有の勝ち筋**: チームスコープを持つことで、「行きたいね」→**チーム内で相談**→日程確定→カレンダー、という**日程化までの一連の流れがアプリ内で閉じる**。TimeTree の個人・家族用途に対し、チーム運営の意思決定導線として差別化する。

### 1.3 ADHD フレンドリー要件（CMP-005 準拠）

`memory/user_adhd_tendency.md` の3原則「**入力摩擦ゼロ・必須項目最小化・後で整理可能**」に完全準拠する。F02.5 行動メモの設計思想（【確認済み】「気分入力等の装飾的入力はオプトイン」「書かなかったことを通知で責めない」）を踏襲する。

| 原則 | 本機能での具体化 |
|---|---|
| 入力摩擦ゼロ | 作成は **タイトル1項目のみ必須**。メモ・候補日・並び順はすべて任意。1入力欄＋送信ボタンで完結 |
| 必須項目最小化 | `title` 以外に `NOT NULL`（デフォルト値なし）の入力項目を置かない |
| 後で整理可能 | メモ・候補日は後から追記できる。並び替え（`sort_order`）も後からで良い |
| 責めない・急かさない | **「キープしたまま放置している」ことを催促する通知を作らない**【既定】。滞留リマインドは実装しない（F02.5 の「メモなし週のリマインドを実装しない」判断と同思想）。**この不存在は ArchUnit で機械的に保証する**（§9.5・AC-28） |
| 段階開示 | 一覧は「タイトル＋（あれば）候補日バッジ」のみ。メモ・変換操作は展開して初めて見える（F04.11 通知インボックスの段階開示に倣う） |

### 1.4 なぜ既存テーブルを流用できないか【確認済み】

| 候補 | 流用不可の理由 |
|---|---|
| `schedules` | 【確認済み】`start_at DATETIME NOT NULL`。日付未定を表現できない。NULL 許容へ緩めると、出欠生成・繰り返し展開バッチ・Google 同期・カレンダー取得クエリ（`idx_sch_team_start(team_id, start_at)` 等）**全経路が NULL を考慮する必要が生じ**、既存の稼働機能を広範囲に危険へ晒す。**新設が正当** |
| `todos`（F02.3） | TODO は「自分がやる作業」。キープは「みんなで行く予定の候補」で出席概念を持つ。役割が異なる（F02.5 の「予定=TODO／実績=行動メモ」の役割分離と同じ考え方） |
| `action_memos`（F02.5） | 個人スコープ専用・実績記録。チーム共有・日程化の導線を持たない |

## 2. スコープ

### 2.1 対象ロール

| ロール | 閲覧 | 作成 | 編集・削除・revert・archive・restore | **変換（convert）** |
|---|---|---|---|---|
| 本人（個人スコープ） | ○ | ○ | ○ | ○ |
| チーム／組織 **ADMIN** | ○ | ○ | ○ | ○ |
| チーム／組織 **MEMBER** | ○ | ○ | **作成者本人のみ** | **○（全員）**【裁定・§2.1.1】 |
| チーム／組織 SUPPORTER（応援者） | **✕** | ✕ | ✕ | ✕ |
| GUEST | ✕ | ✕ | ✕ | ✕ |
| 非メンバー・他組織 | ✕（**404 で存在秘匿**） | ✕ | ✕ | ✕ |

#### 2.1.1 変換だけ MEMBER 全員に開放する理由【裁定・初版からの変更】

初版は「編集・削除・変換はすべて作成者＋ADMIN のみ」としていたが、これは**§1.2 の主目的（チーム内で相談して日程化する）と矛盾していた**。「言い出しっぺが不在・多忙でも、話がまとまったら誰かが日程を入れられる」ことが本機能の価値だからである。

- **`convert` は MEMBER 以上の全員に開放する。**
- 代わりに **変換時は作成者へ必ず通知する**（§6.1）。「自分のキープが自分の知らないうちに予定になっていた」状態を作らない。変換者＝作成者の場合は自己通知しない。
- **編集（PATCH）・削除（DELETE）・revert・archive・restore は従来どおり作成者＋ADMIN のみ。**
- **「前に進める操作は開放し、書き換え・巻き戻しは限定する」という非対称**を意図的に採る。

### 2.2 対象レベル

- [x] 組織 (Organization)
- [x] チーム (Team)
- [x] 個人 (Personal)

**主役はチームスコープ**である（§1.2）。個人スコープは「自分だけの行きたいことリスト」、組織スコープは「組織全体の年間行事候補の下書き」として提供する。

### 2.3 3スコープの排他制約【御裁可済】

【確認済み】`schedules` の現行 XOR 制約は **`ck_schedules_scope_xor`（CASE-sum 形式・4カラム）** である。`V9.086__add_committee_id_to_schedules.sql` が旧 `chk_schedule_scope`（3カラム・OR 羅列形式）を `DROP CHECK` し、置き換えた。実物（引用）:

```sql
-- 【確認済み】V9.086__add_committee_id_to_schedules.sql（既存 schedules の現行制約）
ALTER TABLE schedules
    ADD COLUMN committee_id BIGINT UNSIGNED NULL ... AFTER user_id,
    ADD CONSTRAINT fk_schedules_committee FOREIGN KEY (committee_id) REFERENCES committees (id) ON DELETE CASCADE,
    DROP CHECK chk_schedule_scope,
    ADD CONSTRAINT ck_schedules_scope_xor CHECK (
        (CASE WHEN team_id IS NOT NULL THEN 1 ELSE 0 END)
        + (CASE WHEN organization_id IS NOT NULL THEN 1 ELSE 0 END)
        + (CASE WHEN user_id IS NOT NULL THEN 1 ELSE 0 END)
        + (CASE WHEN committee_id IS NOT NULL THEN 1 ELSE 0 END)
        = 1
    );
```

**本書はこの現行形式（CASE-sum・`ck_` 接頭辞）に揃える**【提案】:

```sql
CONSTRAINT ck_schedule_keeps_scope_xor CHECK (
      (CASE WHEN team_id IS NOT NULL THEN 1 ELSE 0 END)
    + (CASE WHEN organization_id IS NOT NULL THEN 1 ELSE 0 END)
    + (CASE WHEN user_id IS NOT NULL THEN 1 ELSE 0 END)
    = 1
)
```

- **命名は `ck_schedule_keeps_scope_xor`**（`ck_` 接頭辞＋テーブル名＋用途。`ck_schedules_scope_xor` と同形）。旧 `chk_` 接頭辞は使わない。
- **CASE-sum 形式を採る理由**: OR 羅列形式はカラム N 個で N 行に膨れ、スコープ追加のたびに全行を書き直す必要がある。CASE-sum は **1行足すだけで拡張できる**（`schedules` が委員会スコープ追加時に形式ごと乗り換えたのはこのため）。同じ轍を踏まない。
- **委員会スコープ（`committee_id`）は本書では持たない**【既定】。必要になった時点で CASE を1行足すだけで拡張できる。
- **DB レベル CHECK ＋ アプリ層バリデーションの二重保護**（`schedules` の前例に同じ）。ただし到達性については §7.1 を参照（**クライアント入力からは XOR 違反に到達できない**）。

### 2.4 本書のスコープ外（明示的な後回し）

- キープへの出欠・投票（候補日の多数決）。→ 候補日は**候補メモに留める**（§3.4）。投票が要るなら村の寄合（`village_meetups`）または F05.4 アンケートを使う。
- キープの繰り返し設定・リマインド。→ 日付が無いものにリマインドは付かない（§1.3「急かさない」）。
- キープへのファイル・画像添付。→ 将来拡張（§11）。
- Google Calendar 同期。→ **キープは同期しない**（日付が無いので Google 側に表現できない）。変換後の `schedules` が従来どおり同期対象になる。
- 委員会スコープ（§2.3）。

### 3.2 主キー方針 — `UuidV7Entity`（UUIDv7・BINARY(16)）【裁定・第2版から全面変更】

> **第2版の誤り**: 第2版は「schedule ドメインの `schedules.id` が BIGINT だから ID 体系を揃える」として `BaseEntity`（BIGINT）を採り、原則6の例外として正当化していた。**この案は実装初日に機械的に止められる。**

【確認済み】**`EntityUuidV7ConventionArchTest`**（`backend/src/test/java/com/mannschaft/app/common/architecture/EntityUuidV7ConventionArchTest.java`）が **凍結方式（`FreezingArchRule.freeze`）** で次を強制している:

```java
FreezingArchRule.freeze(
    classes().that().areAnnotatedWith(Entity.class)
             .should().beAssignableTo(UuidV7Entity.class)
).as("entities should extend UuidV7Entity (D-2b)")
```

- 凍結ストア（`backend/src/test/resources/archunit_store/`）に**既存の BIGINT Entity が記録済み**であり、**新規追加の `@Entity` だけが fail する**。つまり `ScheduleKeepEntity extends BaseEntity` は **Wave 1 の初日に赤で止まる**。
- 例外は【確認済み】`VillageFestivalLivePostEntity`（複合自然キーのため）**1件のみ**登録されており、コメントに **「他 Entity へ緩めてはならない」** と明記されている。凍結ストアへの例外追加は memory `feedback_baseline_suppression_is_debt`（baseline 凍結は技術負債・免罪符化させない）にも反する。
- **したがって `schedule_keeps` は `UuidV7Entity` を継承し、主キーは UUIDv7（DDL は `BINARY(16)`）とする**（CLAUDE.md 原則6を**例外なく遵守**）。

#### 3.2.1 ID 体系の混在をどう扱うか

「`schedules` が BIGINT だから揃えたい」という第2版の動機自体は消えないが、**混在は避けられないし、避ける必要も無い**。

| 列 | 型 | 理由 |
|---|---|---|
| `schedule_keeps.id` | **BINARY(16)（UUIDv7）** | 新規テーブルの主キー。原則6 |
| `schedule_keeps.converted_schedule_id` | **BIGINT UNSIGNED** | **参照先 `schedules.id` の型に合わせる**。外部参照列の型は「自テーブルの主キー方式」ではなく**親の型**に従う（当たり前だが、UUIDv7 化に引きずられて BINARY(16) にすると参照が成立しない） |
| `schedule_keeps.team_id` / `organization_id` / `user_id` / `created_by` | **BIGINT UNSIGNED** | 同上（参照先が BIGINT のため） |

- API 上、キープの `id` は **UUID 文字列**、`convertedScheduleId` は **数値**になる。**FE の型定義でこの非対称を明示すること**（`id: string` / `convertedScheduleId: number | null`）。
- **⚠️ §4 のサンプル JSON・型表が正である**。UUIDv7 化前の版は `"id": 1234`（数値）で書かれていたが、**現行は `"id": "01920c8e-…"`（36文字の canonical UUID 文字列）**。§4.2 / §4.4.1 / §4.5 のサンプルと型表を参照すること。数値 ID を前提にしたコードを書かない。
- **DDL 前例**: 【確認済み】`V173.20260730033806__create_notification_fanout_jobs.sql`（`id BINARY(16) NOT NULL COMMENT 'UUIDv7 主キー'`・`PRIMARY KEY (id)`・`ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci`）。本書の DDL はこの様式に倣う。

#### 3.2.2 ⚠️ `UuidV7Entity` は監査カラムを持たない【確認済み・実装者向け】

【確認済み】`UuidV7Entity`（`backend/src/main/java/com/mannschaft/app/common/entity/UuidV7Entity.java`）は **`id`（`@UuidGenerator(style = TIME)`）のみ**を持ち、**`createdAt` / `updatedAt` / `deletedAt` を一切持たない**（`BaseEntity` とはここが決定的に違う）。`@SQLRestriction` も無い。

したがって `ScheduleKeepEntity` は次を**自前で宣言する**:

- `createdAt` / `updatedAt`（`@PrePersist` / `@PreUpdate` で設定）
- `deletedAt`（論理削除・原則3）
- `@SQLRestriction("deleted_at IS NULL")`

**前例**: 【確認済み】`VillageMeetupEntity`（`UuidV7Entity` を継承しつつ `createdAt`・`deletedAt` を自前で持ち `@PrePersist` で初期化）。**この構成をそのまま踏襲すること。**

- **⚠️ `@SQLRestriction` の注意**: クラス単位のアノテーションで `@MappedSuperclass` から継承されない。`ScheduleKeepEntity` 自身に明示的に付与する。また **JPQL/Criteria には効くがネイティブクエリには効かない**ため、ネイティブクエリでは `deleted_at IS NULL` を手で書く。
- **⚠️ `equals`/`hashCode`**: `UuidV7Entity` が ID ベースで実装済み。サブクラスは `@EqualsAndHashCode(callSuper = true)` を指定する（同基底の Javadoc に明記あり）。

| `created_by` | BIGINT UNSIGNED | YES | NULL | 作成者（`users.id` を ID 参照）。個人スコープでは `user_id` と一致 |
| `created_at` | DATETIME | NO | CURRENT_TIMESTAMP | **Entity 側で自前宣言**（`UuidV7Entity` は監査カラムを持たない・§3.2.2） |
| `updated_at` | DATETIME | NO | CURRENT_TIMESTAMP ON UPDATE | 同上 |
| `deleted_at` | DATETIME | YES | NULL | 論理削除（原則3） |

```sql
CREATE TABLE schedule_keeps (
  id                    BINARY(16)      NOT NULL          COMMENT 'UUIDv7 主キー',
  team_id               BIGINT UNSIGNED NULL,
  organization_id       BIGINT UNSIGNED NULL,
  user_id               BIGINT UNSIGNED NULL,
  title                 VARCHAR(200)    NOT NULL,
  memo                  TEXT            NULL,
  candidate_dates       JSON            NULL,
  status                VARCHAR(20)     NOT NULL DEFAULT 'KEPT',
  converted_schedule_id BIGINT UNSIGNED NULL,
  sort_order            INT UNSIGNED    NOT NULL DEFAULT 0,
  created_by            BIGINT UNSIGNED NULL,
  created_at            DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at            DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  deleted_at            DATETIME        NULL,
  PRIMARY KEY (id),
  CONSTRAINT ck_schedule_keeps_scope_xor CHECK (
        (CASE WHEN team_id IS NOT NULL THEN 1 ELSE 0 END)
      + (CASE WHEN organization_id IS NOT NULL THEN 1 ELSE 0 END)
      + (CASE WHEN user_id IS NOT NULL THEN 1 ELSE 0 END)
      = 1
  ),
  CONSTRAINT ck_schedule_keeps_converted CHECK (
       (status = 'KEPT'      AND converted_schedule_id IS NULL)
    OR (status = 'SCHEDULED' AND converted_schedule_id IS NOT NULL)
    OR (status = 'ARCHIVED')
  ),
  INDEX idx_skeep_team      (team_id,         status, sort_order, created_at DESC),
  INDEX idx_skeep_org       (organization_id, status, sort_order, created_at DESC),
  INDEX idx_skeep_user      (user_id,         status, sort_order, created_at DESC),
  INDEX idx_skeep_conv_team (team_id,         converted_schedule_id),
  INDEX idx_skeep_conv_org  (organization_id, converted_schedule_id),
  INDEX idx_skeep_conv_user (user_id,         converted_schedule_id)

```

#### 3.3.1 `status` は ENUM でなく VARCHAR(20)【初版からの修正】

【確認済み】`schedules` の実 DDL（`V3.040`）は **`status VARCHAR(20) NOT NULL DEFAULT 'SCHEDULED'`** であり、**MySQL の ENUM 型は使っていない**（F03.1 設計書の ENUM 表記は論理型としての表現）。

**採用理由は「schedule ドメインの作法に揃える」の一点**とする。値の妥当性は **Java enum `ScheduleKeepStatus`（`@Enumerated(EnumType.STRING)`）** で担保する。

> **第2版の理由付けを撤回**【第2パス指摘反映】: 第2版は「状態値の追加に `ALTER TABLE ... MODIFY` が要らない」を利点として挙げていたが、**自壊している**。`ck_schedule_keeps_converted` が `'KEPT'`/`'SCHEDULED'`/`'ARCHIVED'` の**リテラル3値を列挙している**以上、状態値を足すには結局この CHECK を `ALTER` する必要があり、ENUM と手間は変わらない。理由を上記1点に絞る。

#### 3.3.2 変換 CHECK — 状態と `converted_schedule_id` の対応を DB で強制【中指摘反映】

初版の CHECK は片方向（`SCHEDULED` ⇒ 非 NULL）だったため、**「`KEPT` なのに `converted_schedule_id` が残っている」不整合を DB が許していた**。これは §5.3.1 の**予定二重生成バグの温床**そのものである。

| status | `converted_schedule_id` | 理由 |
|---|---|---|
| `KEPT` | **必ず NULL** | 未変換、または `revert` 済み。**ここに値が残ると再変換で予定が二重に生まれる** |
| `SCHEDULED` | **必ず非 NULL** | 変換先が必ず存在する（レコードとしては削除済みでも ID は保持・§5.4） |
| `ARCHIVED` | **NULL / 非 NULL どちらも可** | KEPT 由来なら NULL、SCHEDULED 由来なら非 NULL。**この2由来の区別が §5.3.1 の判定に使われる** |

これにより `revert`・`restore` は **`converted_schedule_id` の NULL クリアを必ず伴う**ことが DB レベルで強制され、実装漏れが即座に制約違反として露見する。

#### 3.3.3 index の意図

| index | 用途 |
|---|---|
| `idx_skeep_team (team_id, status, sort_order, created_at DESC)` | チームのキープ一覧（既定 `status='KEPT'` 絞り＋`sort_order` 昇順 → `created_at` 降順）。**降順 index 列**により並べ替えを index の走査順で満たす（§10.3） |
| `idx_skeep_org` / `idx_skeep_user` | 同上（組織／個人スコープ） |
| `idx_skeep_conv_*` **（スコープ列が先頭）** | **逆引き**「この予定はどのキープから生まれたか」（§4.5.1）。一括逆引きは `team_id = ? AND converted_schedule_id IN (...)` の形なので**スコープ列を先頭に置く**（§10.3） |

> **⚠️ 第2版からの変更（軽微指摘反映）**: 第2版の `idx_skeep_conv_*` は `(converted_schedule_id, スコープ列)` の順で、理由を「シャード耐性」としていたが**論法が誤り**だった（シャードルーティングは index のカラム順とは無関係で、アプリがどのキーでシャードを決めるかの問題）。正しい理由は素朴に **「実際のクエリが `スコープ列 = ? AND converted_schedule_id IN (...)` の形だから、等値の絞り込みが効くスコープ列を先頭に置く」** である。順序を入れ替えた。
>
> **`deleted_at` の扱い**: 論理削除行は `@SQLRestriction` により常に `deleted_at IS NULL` が付く。上記 index に `deleted_at` は**含めない**【既定】。論理削除されたキープは全体のごく一部にとどまる想定で、index に足すと全 index が1列分太る割に選択性の改善が小さいため。削除行が積み上がって実測で問題が出たら、その時点で `deleted_at` を先頭に足した部分 index 相当を検討する。

**照合順序**: **`utf8mb4_unicode_ci`**【初版からの修正】。【確認済み】migration 配下の実出現数は `utf8mb4_unicode_ci` **546 ファイル** vs `utf8mb4_0900_ai_ci` **28 ファイル**で、`schedules` 自身（`V3.040`）も `utf8mb4_unicode_ci`。**多数派かつ隣接テーブルと一致する方**を採る（照合順序が異なると JOIN 時に暗黙変換が起き index が効かなくなる実害がある）。

### 3.4 `candidate_dates` JSON 形式【提案】

「いつがいい？」の**メモ**であり、投票機構ではない（§2.4）。

```json
["2026-09-12", "2026-09-19", "2026-10-03"]
```

| 規約 | 内容 |
|---|---|
| 型 | `String[]`（ISO-8601 の日付 `YYYY-MM-DD`。**時刻は持たない**） |
| 件数上限 | **10 件**【既定】。超過は 400（`SCHEDULE_KEEP_003`） |
| 日付形式不正 | 400（`SCHEDULE_KEEP_004`・§7 で分離） |
| 並び | 保存時に昇順ソート・重複除去してから格納 |
| **空配列の正規化** | **`[]` を受け取ったら DB には `NULL` を格納する**【軽微指摘反映】。「候補日なし」の DB 表現を **NULL 一本に固定**し、`NULL` と `[]` の2表現を混在させない（クエリ・FE 分岐を1つに保つ） |
| **過去日** | **許容する**【軽微指摘反映・既定】。「去年の今頃やった行事をまた」のようにカレンダーから拾った日付をそのまま候補にする使い方があり、弾くと入力摩擦になる（§1.3）。**過去日から変換した場合も過去日の予定として作成される**（`schedules` は過去日の予定を許容している） |
| 省略 | `null`（API レスポンスも `null`。空配列は返さない） |
| Java 側マッピング | 【確認済み】`ScheduleEntity.recurrenceRule` の前例に倣い **`@Column(columnDefinition = "JSON") private String candidateDates;`（String 保持）** とし、Service 層で `List<LocalDate>` へ変換する |

**なぜ子テーブルにしないか**: 候補日は投票対象ではなく順序も持たない、キープに完全従属する付随データである。子テーブルにすると N+1・CASCADE・並び順管理のコストが付き、「入力摩擦ゼロ」の実装が重くなる。10 件上限の固定長配列なので JSON 列で十分（`schedules.recurrence_rule` と同じ判断）。

**なぜ JSON 列に DB 側 CHECK を張らないか**【軽微指摘反映】: MySQL の `JSON_SCHEMA_VALID()` による CHECK は (a) 8.0.17+ 依存、(b) エラーが制約名しか返さず**どの要素が不正かユーザーに伝えられない**、(c) 件数・形式の検証は既にアプリ層（`SCHEDULE_KEEP_003`/`004`）が担っており二重管理になる。**検証はアプリ層に一本化**し、DB は JSON の構文妥当性（MySQL の JSON 型が自動保証）に留める。

**⚠️ タイムゾーン**: `candidate_dates` は **日付のみ**（壁時計の日付）であり瞬間ではない。FE で `Date` に変換して tz 投影し直すと1日ずれる（memory `project_fe_datetime_picker_instant_vs_wallclock`）。**文字列 `YYYY-MM-DD` のまま扱い `localDate.ts` のユーティリティを使う**こと。

### 3.5 FK 方針とドメイン境界（原則1・2）【提案】

| 参照 | FK | 理由 |
|---|---|---|
| `team_id` → `teams.id` | **張らない** | チームは team ドメイン。**クロスドメイン FK 禁止**（原則1）。index のみ・整合はアプリ層 |
| `organization_id` → `organizations.id` | **張らない** | 同上 |
| `user_id` → `users.id` | **張らない** | 同上（user ドメイン）。退会時は §3.7 |
| `created_by` → `users.id` | **張らない** | 同上 |
| `converted_schedule_id` → `schedules.id` | **張らない**【既定】 | `schedules` は**同一 schedule ドメイン**なので原則1には抵触しないが、CASCADE を張ると「予定を消したらキープごと消える」という誤った意味になる。**予定が消えてもキープは残す**（§5.4）ため FK は張らず index のみとし、アプリ層で解決する |

#### 3.5.1 ⚠️ `schedules` との FK 差分 — アプリ層の後始末が必須【重要・中指摘反映】

【確認済み】**`schedules` は本表と違って実際に FK を張っている**: `fk_sch_team`（`team_id`→`teams` **ON DELETE CASCADE**）・`fk_sch_org`（`organization_id`→`organizations` **CASCADE**）・`fk_sch_user`（`user_id`→`users` **CASCADE**）・`fk_sch_created_by`（SET NULL）・`fk_sch_parent`（RESTRICT）。

これは **`schedules` が原則1（クロスドメイン FK 禁止）確立前に作られた歴史的経緯**によるもので、**本表はこれを踏襲しない**（原則1に従い FK を張らない）。

> **⚠️ 第2版の誤りを訂正【第2パス指摘反映】**: 第2版は「チーム削除時、`schedules` は DB が CASCADE で自動削除する／`schedule_keeps` は孤児化する」と書いたが**誤り**。【確認済み】`TeamService.deleteTeam`（`backend/src/main/java/com/mannschaft/app/team/service/TeamService.java:551-559`）は **`team.softDelete()` を呼ぶだけで物理削除しない**（`restoreTeam` も存在する＝復元可能な論理削除）。【確認済み】`OrganizationService.deleteOrganization` も同じく `org.softDelete()` のみ。**行が消えない以上 FK の CASCADE は発火しない。** つまり `schedules` と `schedule_keeps` の差分は、通常運用では**顕在化しない**。

**正しい差分の整理**:

| 契機 | `schedules`（FK あり） | `schedule_keeps`（FK なし） |
|---|---|---|
| **チーム／組織の削除（通常運用）** | **CASCADE は発火しない**（`softDelete()` のみで行は残る） | 同じく何も起きない。**差は無い** |
| **チーム／組織行の物理削除**（データ整理・GDPR 対応等の例外運用） | DB が CASCADE で自動削除 | **何も起きない → 孤児化** |
| **ユーザーの物理削除** | DB が CASCADE で自動削除 | 同上 |

→ 差分が効くのは**物理削除という例外運用のときだけ**である。ただし §3.7 の後始末は、**物理削除への備えとしてではなく「論理削除された親に紐づくキープを一覧から消す」ために必要**であり、その意味では依然として必須である（AC-27b で実測する）。

### 3.7 退会・チーム／組織削除時の扱い【提案・必須】

原則3・4（論理削除・退会時匿名化）に整合させる。**§3.5.1 のとおり親の削除は論理削除であり DB は何もしてくれないため、これらはすべてアプリ層の責務である。**

**先例（そのまま踏襲する）**: 【確認済み】`MembershipEventListener`（`backend/src/main/java/com/mannschaft/app/scopefolder/listener/MembershipEventListener.java`）は **`MembershipEndedEvent` / `TeamDeletedEvent` / `OrganizationDeletedEvent` の3種を購読**し、マイスコープフォルダの dangling アイテムを後始末している。実装様式:

```java
@Transactional(propagation = Propagation.REQUIRES_NEW)
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void handleTeamDeleted(TeamDeletedEvent event) {
    try {
        folderService.handleScopeDeleted(ScopeType.TEAM, event.getTeamId());
    } catch (Exception ex) {
        log.warn("TeamDeletedEvent 処理失敗: teamId={}, error={}", event.getTeamId(), ex.getMessage(), ex);
    }
}
```

**`AFTER_COMMIT` + `REQUIRES_NEW` + try/catch で握って警告ログ**（クロスドメインのデッドロック回避）という形をそのまま採る。**例外を握るがログには必ず残す**点も踏襲する（握りつぶしではない）。

| 契機 | 扱い | 実装 |
|---|---|---|
| ユーザー退会（`UserAnonymizedEvent`） | **個人スコープ（`user_id`＝退会者）のキープは論理削除**（本人以外に価値が無い私的メモ）。**チーム／組織スコープのキープは残置**し、`created_by` の表示解決のみ匿名化する（チームの資産であり、消すと他メンバーの相談履歴が失われる）。`memo` はチームメンバーに向けて書かれた共有メモであり `created_by` の匿名化で足りると判断する【既定】 | 【確認済み】`UserAnonymizedEvent`（`backend/src/main/java/com/mannschaft/app/auth/event/UserAnonymizedEvent.java`）は実在し、**`*AnonymizationEventListener` 命名の購読リスナーが多数存在する**（`ActionMemoAnonymizationEventListener`・`InboxAnonymizationEventListener`・`ScheduleIntegrationAnonymizationEventListener` 等）。**この前例に倣い `ScheduleKeepAnonymizationEventListener` を新設**（`@TransactionalEventListener(AFTER_COMMIT)` + `@Transactional(REQUIRES_NEW)`） |

| 変換先 `schedules` の削除 | キープは**残す**（§5.4） | — |

### 4.4 更新・削除

| API | 仕様 |
|---|---|
| `PATCH .../{keepId}` | `title` / `memo` / `candidateDates` を部分更新。**未指定（キー欠落）= 変更しない、明示的 `null` = クリア** の PATCH セマンティクス（`ScheduleEntity.applyPersonalScheduleUpdate` の前例に同じ）。`status` はここで変えられない（§5 の遷移 API を使う） |
| `DELETE .../{keepId}` | 論理削除（`deleted_at` セット）。`status='SCHEDULED'` のキープを削除しても、**変換先 `schedules` は消さない**（§5.4） |

**PATCH の状態別可否**【中指摘反映】:

| status | `title` | `candidateDates` | `memo` | 拒否時のコード |
|---|---|---|---|---|
| `KEPT` | ○ | ○ | ○ | — |
| `SCHEDULED` | **✕ 409** | **✕ 409** | ○ | `SCHEDULE_KEEP_007` |
| `ARCHIVED` | **✕ 409** | **✕ 409** | **✕ 409** | `SCHEDULE_KEEP_007` |

`ARCHIVED` は**読み取り専用**であり `memo` すら書き換えられない（初版はここが未定義だった）。編集したければ `restore` する。**戻り先は由来による**（KEPT 由来 → `KEPT` で全項目編集可／SCHEDULED 由来 → `SCHEDULED` で `memo` のみ編集可。§5.3.1）。

> **⚠️ `SCHEDULED` のタイトルは「どちらが正か」**【中指摘反映】: 変換後、キープと予定の両方が `title` を持つ。**表示の正は変換先 `schedules.title`** とする（予定側で改名されたらそちらが最新だから）。キープの `title` は変換時点のスナップショットとして列に保持するが、**BE の `ScheduleKeepResponse.title` は `SCHEDULED` のとき変換先 `schedules.title` を返す**【検分是正・Wave3 で FE 責務から BE 責務へ変更】。
>
> **なぜ FE に引かせないか**: `SCHEDULED` のキープは `title` の PATCH が 409（`_007`）で塞がれている。BE が旧題目を返し続けると、予定側で改名したユーザーは**キープ側の表示を自力で直せない袋小路**に入る。しかも FE に「変換先を引き直す」責務を持たせると、キープを表示するすべての画面で同じ結線を繰り返すことになり、1 箇所忘れれば旧題目が復活する。**同じ物を指す 2 つの名前をクライアントに配らない。**
>
> **N+1 は発生しない**: 一覧は変換先の生存状態（§5.4）を解決するために `schedules` を既に一括ロードしている（`resolveConvertedSchedules`）。その結果から `title` を拾うだけなので**追加クエリはゼロ**である。
> あわせて **FE は `SCHEDULED`／`ARCHIVED` のキープで編集 UI を事前に無効化**し、`scheduleKeep.lockedHint.*` のヒントを出す。409 を「押してから知る」のは摩擦であり、押せないことを先に見せる（§1.3 段階開示）。

#### 4.4.1 `reorder` の契約【中指摘反映・初版から厳格化】

`POST .../schedule-keeps/reorder`

```json
{ "orderedIds": [12, 8, 30] }
```

| 検証 | 違反時 |
|---|---|
| すべて**同一スコープ**のキープであること（パスのスコープと一致） | **404** `SCHEDULE_KEEP_001`（他スコープの ID の存在を漏らさない・§4.6.3） |
| すべて**閲覧可能**であること（Resolver 通過） | **404** `SCHEDULE_KEEP_001` |
| すべて**非削除**（`deleted_at IS NULL`）であること | **404** `SCHEDULE_KEEP_001` |
| **ID の重複が無い**こと | **400** `SCHEDULE_KEEP_012` |
| 件数が **1件〜スコープ上限**（**個人 200 / チーム・組織 300**・§10.1 と同値）であること | **400** `SCHEDULE_KEEP_012` |
| **`ARCHIVED` のキープが混ざっていない**こと【軽微指摘反映】 | **400** `SCHEDULE_KEEP_012`（`ARCHIVED` は既定一覧に出ないので並び替え対象にならない。混入は FE のバグを示す） |

- **リクエストに含まれない同スコープのキープは `sort_order` を据え置く**【既定】（部分並び替えを許す＝摩擦を増やさない）。
- **編集権限は不要**（MEMBER 以上なら並び替え可）【既定】。並び順は「見え方の好み」であって内容の改変ではない。ただし**並び順はスコープ共有**である（ユーザーごとの並び順は持たない。持つならテーブルがもう1本要り、§3.1「追加1本のみ」を破る）。

### 4.5 変換 — `POST .../{keepId}/convert`【御裁可済の中核】

キープを**カレンダーの予定へ落とす**。「2タップ以内で日程化」の実体。

**リクエスト**

```json
{ "startAt": "2026-08-15T00:00:00", "endAt": null, "allDay": true }
```

| フィールド | 型 | null 許容 | 必須 | 説明 |
|---|---|---|---|---|
| `startAt` | String (ISO-8601 LocalDateTime) | ✕ | ○ | 確定した開始日時。`schedules.start_at` が NOT NULL のため必須 |
| `endAt` | String | ○ | ✕ | 省略可（`schedules.end_at` は NULL 許容） |
| `allDay` | Boolean | ✕ | ✕（既定 **true**） | true のとき `startAt` の時刻を `00:00:00` に正規化（`schedules` の既存規約に同じ） |

**サーバ側の処理**（単一トランザクション・schedule ドメイン内で完結・原則5）:

1. キープを取得し**スコープ一致検証**（§4.6.3）→ 認可（§4.6）→ `status='KEPT'` を確認（他は 409 `SCHEDULE_KEEP_006`）
2. `schedules` に新規行を作る（**既定値は §4.5.2 で固定**）
3. キープを `status='SCHEDULED'`・`converted_schedule_id=<新規 schedules.id>` へ更新（**元レコードは削除しない**【御裁可済】）
4. 通知は **コミット後に best-effort** で発火（§6）。**作成者への通知は必須**（§2.1.1）

**⚠️ 日時バインド**: `startAt` はリクエストボディ経由＝Jackson 経路。クエリパラメータ経路（ConversionService）とは**独立**であり片方の修正は他方に届かない（memory `project_datetime_binding_path_asymmetry`）。

#### 4.5.1 逆引き「この予定はどのキープから生まれたか」【裁定・初版から方式変更】

初版は「`schedules` に `originKeepId` 列を足す」としていたが、**裁定により列は足さない**。

- **`schedules` テーブルは一切変更しない**（§3.1）。既存の巨大テーブルに列を足すと、出欠・繰り返し・Google 同期の全経路にレスポンス差分が波及する。
- **逆引きは `schedule_keeps.converted_schedule_id` 側から引く**。`idx_skeep_conv_team` / `_org` / `_user`（**スコープ列を含む複合 index**）で解決する。
- **なぜスコープ込み複合 index か（シャード耐性）**: `converted_schedule_id` 単独 index だと、シャーディング後に「どのシャードを引けばよいか」が ID だけでは決まらず**全シャード fan-out** になる。スコープ列を含めることで、**呼び出し側が既に持っているスコープでシャードを一意に決められる**（§10.3）。
- **N+1 回避の取得方法**【中指摘反映】: 予定一覧から逆引きするときは、**`converted_schedule_id IN (:scheduleIds) AND team_id = :teamId` の1クエリで一括取得**し、`Map<Long scheduleId, ScheduleKeepRef>` に畳んでから DTO へ流し込む。**予定1件ごとに引かない**（AC-09b で実測）。
- API 形状: **専用エンドポイント `GET .../schedule-keeps/by-schedule/{scheduleId}`**（200 = 由来キープ / 404 = キープ由来でない）。既存の予定 API のレスポンスは変えない。
- **複数ヒット時の決定則**【軽微指摘反映】: `converted_schedule_id` に一意制約は張らない（`revert` → 再 `convert` の履歴で理論上は複数のキープが同じ予定 ID を指しうる）。**該当が複数ある場合は `created_at` が最新のキープ1件を返す**（`ORDER BY created_at DESC, id DESC LIMIT 1`）。「この予定を生んだ最後のキープ」が利用者の期待に最も近いため。
- **繰り返し予定の親になった場合**【中指摘反映】: 変換で作られた予定に後から繰り返しルールが設定されると `parent_schedule_id` で子が展開される。**逆引きが指すのは常に親（変換で作られた実体）のみ**とし、**展開された子には由来キープを引き継がせない**（子は親の派生であり、キープから直接生まれたわけではない）。子から辿りたい場合は FE が `parent_schedule_id` を経由する。

#### 4.5.2 変換時の `schedules` 既定値【提案・欠落AC補充】

| 列 | 値 | 理由 |
|---|---|---|
| `title` | キープの `title` をコピー | |
| `description` | キープの `memo` をコピー（null 可） | |
| `team_id`/`organization_id`/`user_id` | キープと同じスコープ列 | **スコープは変換で変わらない**（シャード耐性の前提・§10.3） |
| `start_at` / `end_at` / `all_day` | リクエスト値 | |
| `event_type` | `'OTHER'` | 種別は後から予定側で変えられる |
| `status` | `'SCHEDULED'` | |
| **`attendance_required`** | **`false`** | **日程が決まっただけの段階で出欠を強制しない**（§1.3「急かさない」）。出欠が要るなら予定側で後から有効化する |
| **`visibility`** | **`'MEMBERS_ONLY'`（固定値）** | **§4.5.2.1 参照** |
| **`min_view_role`** | **`'MEMBER_PLUS'`（固定値）** | 同上 |
| `created_by` | **変換操作者**（キープの作成者ではない） | 予定を作ったのは変換した人。キープの作成者は逆引きで辿れる |

##### 4.5.2.1 ⚠️ 可視性は固定値で書く — 「スコープ既定を継承」と書いてはいけない【第2パス指摘反映】

第2版は `visibility` / `min_view_role` を「チーム／組織の既定設定を継承」としていたが、**2つの問題がある**:

1. **その「既定を継承する実体」は変換経路には存在しない**。F03.1 の継承（`default_schedule_min_view_role`）は予定作成 API の中の話であり、キープからの変換で自動的に効くとは限らない。書いておけば効くものではない。
2. **より危険なのは、既定が緩い値だった場合**。キープは **MEMBER 限定の内輪の相談**（§4.6.2 で応援者を明示的に締め出している）。それが変換された瞬間に、スコープ既定が `SUPPORTER+` や `ANYONE` だったせいで**応援者や GUEST に見える予定になってしまう**。**可視性が変換で緩む**という、認可設計として最悪の挙動になる。

> **裁定**: 変換先の予定は **`visibility='MEMBERS_ONLY'`・`min_view_role='MEMBER_PLUS'` を固定値で設定する**（スコープ既定を参照しない）。

- これは **§4.6.2 の `MEMBERS_AND_ABOVE`（応援者・ゲスト不可視）と意味が一致する**。キープの可視性が変換後もそのまま保たれる。
- 変換後に公開範囲を広げたければ、**予定側で明示的に変更する**（人が意図して緩める分には問題ない。勝手に緩むのが問題）。
- **AC-06c でこの固定値を検証する**（§9.2）。

##### 4.5.2.1.1 ⚠️ 前提が成立していない — `min_view_role` は閲覧経路で評価されていない【Wave2 実測で判明・未解決】

> **本節の裁定（固定値を書く）は正しく実装されたが、その<b>効果</b>は現状の実装では得られない。** Wave2 の AC-06c が red のまま残っている理由である。

【確認済み・2026-08-07 実測】`min_view_role` を**評価している実装は `GoogleCalendarService.satisfiesMinViewRole`（Google カレンダー push の宛先絞り込み）だけ**である。予定の閲覧経路には評価が存在しない:

- `GET /api/v1/teams/{teamPublicId}/schedules/{scheduleId}` → `ScheduleService.getScheduleWithAccessCheck` → `ContentVisibilityChecker.canView(ReferenceType.SCHEDULE, ...)` の**F00 可視性のみ**。
- その F00 経路で `ScheduleVisibilityMapper` は **`MEMBERS_ONLY` → `SCOPE_AFFILIATED`**（＝スコープに直接所属していれば可）へ写像しており、コメントに「応援者可否は別軸 `min_view_role` が司る」と明記されている。
- しかし **`ScheduleVisibilityProjection` は `min_view_role` 列を持たない**。したがって「別軸が司る」とされた判定は**どこでも実行されていない**。

**結果**: `visibility='MEMBERS_ONLY'` かつ `min_view_role='MEMBER_PLUS'` の予定を、**そのチームの SUPPORTER（応援者）が閲覧できる**。これはキープ変換に固有の問題ではなく、**F03.1 の既存予定すべてに及ぶ認可漏れ**である。

**AC-06c への影響**: 「変換前にキープを見られなかった SUPPORTER は、変換後の予定も見られない」の後半が成立しない（キープ側は `ScheduleKeepVisibilityResolver` が `MEMBERS_AND_ABOVE` を返すため正しく 404 になり、AC-16 は緑）。**可視性は「変換で緩む」のではなく「予定側にもともと緩い穴がある」**。

**対処方針（未着手・要裁可）**: 根治は `ScheduleVisibilityProjection` に `min_view_role` を載せ、F00 の評価に合成することだが、**これは schedules の全閲覧経路の可視性意味論を変える横断変更**であり、F03.17 Wave2 の範囲を超える。CMP-017（認可漏れ全域監査）の課題として起票し、専用の PR で扱うべきである。**AC-06c は当該修正が入るまで red のまま残す**（テストを緩めて隠さない）。

#### 4.5.3 候補日が無いキープの変換 FE 導線【中指摘反映】

| キープの状態 | FE の導線 | タップ数 |
|---|---|---|

### 4.6 認可【提案・F00 準拠】

**deny-by-default**（`docs/security/README.md`）。

#### 4.6.1 判定の骨子

| 判定 | 方式 |
|---|---|
| スコープ所属 | チーム／組織スコープは **リクエスト者が当該チーム／組織の MEMBER 以上**であることを検証。個人スコープは `user_id == getCurrentUserId()` |

#### 4.6.3 IDOR 防御 — 全エンドポイントでスコープ一致を検証【裁定・重大指摘の是正】

**初版の不足**: 初版は「他チームからの GET が 404」しか書いておらず、**`convert`/`archive`/`revert`/`restore`/`reorder` といった操作系の IDOR を検証していなかった**。操作系こそ被害が大きい（他チームのキープを勝手に予定化できてしまう）。

> **全エンドポイント（GET / PATCH / DELETE / convert / revert / archive / restore / reorder / by-schedule）で、
> 「パスのスコープ」と「レコードのスコープ列」の一致を検証し、不一致なら 404 を返す。**

```
パス /teams/{teamPublicId}/schedule-keeps/{keepId}
  → teamPublicId から解決した teamId と keep.teamId が一致するか
  → 不一致（他チームのキープ / 組織キープ / 個人キープ）なら 404 SCHEDULE_KEEP_001
```

- **403 ではなく 404**。403 は「存在するが権限が無い」＝存在を漏らす。
- **`keepId` だけで検索してはならない**。`findById(keepId)` の結果に対して後からスコープを比較する実装は、**比較を忘れた瞬間に IDOR になる**。**リポジトリのクエリ自体をスコープ込みにする**（`findByIdAndTeamId(keepId, teamId)`）のが根治。**スコープを取らない単独 finder は定義しない**。
- **⚠️ 実装上の落とし穴**（memory 由来）:
  - `getCurrentUserId()` の戻り値を `teamId` として使い回す実装は**常に誤り**（`project_matching_authz_userid_as_teamid_idor`）。
  - 認可引数を取るが本体で使っていない「**死んだ引数**」は ArchUnit 番人を欺く（`feedback_dead_authz_param_deceives_guard`）。引数の存在ではなく**到達を検証**すること。
  - 共通ヘルパに一元化しても「全経路がそれを使っている」証明にはならない（`feedback_centralized_helper_not_proof_all_paths_use_it`）。**兄弟メソッドの非対称が手掛かり**。
- **AC-14a〜14f で全操作系を個別に検証する**（§9.3）。

### 5.3 状態 × 操作の全セル表【第2パス指摘反映・未定義セルを解消】

第2版は遷移を「可否リスト」で書いていたため、**組み合わせに未定義の穴が4つ**残っていた（`KEPT` への `revert`、`SCHEDULED` への `restore`、`ARCHIVED` の `DELETE`、`ARCHIVED` への `convert` のコード）。**全セルを埋めた表を正とする。**

| 現在の status | `convert` | `revert` | `archive` | `restore` | `PATCH` | `DELETE` |
|---|---|---|---|---|---|---|
| **`KEPT`** | **200** → `SCHEDULED`（§4.5） | **409 `_009`**<br>（取り消す対象が無い） | **200** → `ARCHIVED` | **200 no-op**<br>（既に KEPT） | **200**（全項目） | **200**（論理削除） |
| **`SCHEDULED`** | **409 `_006`**<br>（**二重生成はここで塞がる**） | **200** → `KEPT`<br>予定を論理削除・`conv_id` を NULL に | **200** → `ARCHIVED`<br>`conv_id` は**保持** | **200 no-op**<br>（アーカイブされていない） | **200**（`memo` のみ）<br>他は **409 `_007`** | **200**（論理削除。**予定は消さない**） |

#### 5.3.1 `restore` は「アーカイブ前の状態へ戻す」— 409 で塞ぐ裁定を撤回【第2パス裁定・第2版から変更】

> **第2版の裁定を撤回する。** 第2版は「SCHEDULED 由来の ARCHIVED からの `restore` は 409（先に `revert` せよ）」とし、専用コード `SCHEDULE_KEEP_011` まで新設していた。**この防御は不要だった。**

**第2版が恐れていた穴**:

```
KEPT → convert（予定A） → SCHEDULED → archive → ARCHIVED
     → restore（第2版初期案: KEPT に戻し conv_id を NULL クリア）
     → convert（予定B）   ← 予定A が残ったまま予定B が生まれる（二重生成）
```

**なぜ 409 が不要か**: 上の穴は **`restore` が `KEPT` へ戻し `conv_id` を NULL クリアしていたこと**が原因であって、`restore` 自体が悪かったのではない。**`restore` の戻り先を `SCHEDULED`（`conv_id` 保持）にすれば、そもそも再 `convert` は `SCHEDULED` に対する操作となり、表のとおり **409 `SCHEDULE_KEEP_006`** で既に塞がっている。**二重生成の防止機構は元から存在していた。**

**確定仕様**:

| ARCHIVED の由来 | `restore` の戻り先 | 判定 |
|---|---|---|
| `conv_id` = NULL（KEPT 由来） | **`KEPT`** | `converted_schedule_id IS NULL` |
| `conv_id` ≠ NULL（SCHEDULED 由来） | **`SCHEDULED`**（`conv_id` はそのまま保持） | `converted_schedule_id IS NOT NULL` |

- **`restore` の意味が「アーカイブする直前の状態へ戻す」で一貫する**（第2版は由来によって「戻せる／戻せない」が変わる不揃いな操作になっていた）。
- **袋小路が消える**。第2版はユーザーに「戻したいだけなのに、まず予定を消せ（revert）」と要求していた。予定を消したくない人は詰む。
- **`SCHEDULE_KEEP_011`（`KEEP_RESTORE_REQUIRES_REVERT`）は廃止**（§7）。
- **`revert` は引き続き `SCHEDULED` / `ARCHIVED`（conv_id 非 NULL）の両方から実行できる**。「予定ごと取り消したい」人はこちらを使う。**`restore`（状態を戻す）と `revert`（予定を消す）の役割分担が明確になった。**
- §3.3.2 の CHECK が `ARCHIVED` に限り `conv_id` の NULL / 非 NULL 双方を許すのは、**この由来の区別を保持するため**である（変更なし）。

### 5.4 変換先 `schedules` が消えたとき — CANCELLED と論理削除の区別【中指摘反映】

初版は「削除」しか扱っていなかったが、【確認済み】`schedules` は **`status='CANCELLED'`（キャンセル）と `deleted_at`（論理削除）の2つの「消え方」**を持つ。区別しないと FE が誤った案内を出す。

レスポンスの **`convertedScheduleState`** で表現する:

| 値 | 変換先の状態 | FE の表示・導線 |
|---|---|---|
| `NONE` | `converted_schedule_id IS NULL`（未変換） | 「予定にする」ボタン |
| `ACTIVE` | 予定が存在し `status` が `SCHEDULED`/`COMPLETED` | 予定へのリンク |
| `CANCELLED` | 予定は存在するが `status='CANCELLED'` | 「予定は中止になりました」＋`revert` 導線 |
| `DELETED` | 予定が論理削除済み（`deleted_at` 非 NULL）または存在しない | 「元の予定は削除されました」＋`revert` 導線 |

- キープ自身は **`status='SCHEDULED'` のまま残る**（履歴として正しい。「一度は日程化された」事実は消さない）。
- `CANCELLED`・`DELETED` のいずれでも **`revert` は 200 で通る**（§5.3 の冪等 revert）。
- **`convertedScheduleState` の解決は一括クエリで行う**（§4.5.1・N+1 回避）。

### 6.2 配線【提案】

| 項目 | 値 |
|---|---|
| 通知種別 | **schedule ドメイン独自の文字列種別** `SCHEDULE_KEEP_CONVERTED` / `SCHEDULE_KEEP_CREATED`。**核 `NotificationType` enum は改変しない**（横断 enum への波及回避。F17.2 §3.4 の前例と同方針）。【確認済み】`NotificationType` は `backend/src/main/java/com/mannschaft/app/notification/NotificationType.java`（**`skill` ドメインに同名 enum があるので import を取り違えないこと**・memory `feedback_spring_bean_name_collision_same_simplename`） |
| `actionUrl` | 変換通知は**変換先の予定**へ（`/teams/{slug}/schedules/{scheduleId}`）。作成通知はキープ一覧へ |
| トランザクション | **宛先判定は変換と同一トランザクション、永続化のみ `REQUIRES_NEW` の独立トランザクション**【検分是正・Wave3 で「同一TX + try/catch」から変更】。通知失敗で変換を巻き戻さない。**ただし失敗はログに残す**（握りつぶさない・CLAUDE.md 障害対応の原則2） |

> ⚠️ **`REQUIRES_NEW` の自己呼び出しの罠**: 同一 Bean 内の自己呼び出しでは `@Transactional` が効かない（別 Bean へ切り出すか `TransactionTemplate` を使う。memory `feedback_transactional_event_listener_requires_new`）。本設計は `ScheduleKeepNotificationPublisher` という**別 Bean**へ切り出すことでこれを回避する。

#### 6.2.1 通知は「判定は同一 TX・永続化は `REQUIRES_NEW`」で発行する【検分是正・Wave3】

> **Wave2 の「同一トランザクションで同期発行し、呼び出し側が try/catch + WARN で隔離する」を撤回する。** その形は **try/catch が何も守れていなかった**。

**なぜ同一 TX + try/catch が破綻するか（rollback-only の機序）**:

- `NotificationService.createNotification` は伝播指定なし＝`REQUIRED` であり、**変換と同じトランザクションに参加する**。
- この経路で最も起きやすい失敗＝通知の永続化例外は、Spring/Hibernate が**その TX を rollback-only にマークする**。
- 呼び出し側で catch して WARN に落としても**TX の汚染は消えない**。`convert()` から戻った直後のコミットが `UnexpectedRollbackException` になり **500**。すなわち**通知の失敗が変換そのものを巻き戻していた**——守ろうとしていた「変換は成立させる」がまさに壊れる。
- さらに `Exception` 全般を握るため、**レスポンス 500 とログの「変換自体は成立」が食い違う**。調査時に嘘のログだけが残る。

**是正後の形**:

1. **宛先の判定（届けてよい相手か）は外側 TX の中で行う**（`ScheduleKeepNotificationService`。`@Transactional` を付けず呼び出し側の TX に乗る）。
2. **永続化だけを `ScheduleKeepNotificationPublisher`（別 Bean・`@Transactional(REQUIRES_NEW)`）へ逃がす**。内側 TX だけが独立してロールバックするので rollback-only が外側へ伝播しない。**ここで初めて呼び出し側の try/catch が意味を持つ**。

**⚠️ `REQUIRES_NEW` の内側からは外側の未コミットデータが見えない。** よって publisher は**一切再検索をしない**——本文・遷移先・宛先はすべて呼び出し側が確定した値を引数で受け取る。同じ理由で `createNotification` 内蔵の F00 ガード（`sourceType` から予定を SQL で引く）は使えない（変換先の予定行が内側から存在しないように見え、通知が黙って捨てられる）。可視性は外側 TX で `ReferenceType.SCHEDULE_KEEP` に対して判定し（§6.2.2）、永続化は `createNotificationPreAuthorized` を使う。

**AC-15b（§9.3）の検証方法**: Wave2 は「`REQUIRES_NEW` にするとテストから通知が見えない」を撤回理由の一つに挙げていたが、これは**テスト側の書き方で解決する**問題だった。契約 IT の外側 TX は MySQL 既定の REPEATABLE READ でスナップショットが固定されているため見えないだけであり、**素の `DataSource` から新しい接続＝新しいスナップショットを取れば数えられる**（`countConvertedNotifications`）。`afterCommit` を採らない理由（テスト中にコミットが起きず永久に発火しない）は依然として有効である。

**副次的な代償**: 変換がロールバックしたのに通知だけ残る、という不整合が理論上ありうる（Wave2 が同一 TX の利点として挙げていた点）。ただし通知は変換処理の最終段にあり、その後に残る失敗要因はコミット自体しかない。**「通知が余分に1通残る」より「通知の失敗で変換が消える」ほうが遥かに重い**ため、この交換は妥当である。

#### 6.2.2 宛先判定は `ReferenceType.SCHEDULE_KEEP` で明示的に行う【検分是正・Wave3】

通知本文は**キープのタイトルを含む**。よって「キープが見えない相手には通知しない」は §6.1 の運用上の配慮ではなく、**情報漏洩の遮断**である。

- `NotificationService` 内蔵の F00 ガードに任せてはならない。`sourceType="SCHEDULE"` は `ScheduleVisibilityMapper` により `MEMBERS_ONLY -> SCOPE_AFFILIATED`（**応援者を含む直接所属軸**）へ写像されるため、**SUPPORTER へ降格した作成者がガードを通過する**。結果、キープ本体では 404 で秘匿しているタイトルが**通知経由で漏れる**（`docs/task-list.md` CMP-017b に起票済みの既存欠陥がキープへ波及したもの。CMP-017b の根治を待たずに本機能側で塞ぐ）。
- キープの正準は `ScheduleKeepVisibilityResolver`（`MEMBERS_AND_ABOVE`・§4.6.2）である。通知を作る前に `contentVisibilityChecker.canViewUuid(ReferenceType.SCHEDULE_KEEP, keepId, creatorId)` を通し、**通らなければ通知を作らない**。独自の可視性述語は書かない。

**スコープ内 MEMBER 全員への配信は CMP-017c で fan-out 基盤（CMP-001）経由で実装した**（Wave2 時点では作成者への直送のみだった）。全員配信は fan-out 基盤の担当領域であり、受信者ループを素朴に書くと同基盤が解消しようとしている N 件ループを新規に持ち込むため、次の形で配線する:

- **受信者ソース** `ScheduleKeepTeamFanoutRecipientSource`（`membership/fanout`・`scope_type="SCHEDULE_KEEP_TEAM"`）が、TEAM スコープの **MEMBER 以上（`role_kind='MEMBER'`）全員から操作者・作成者を除いた**母集団をキーセットページングで供給する。**純 SUPPORTER（`role_kind='SUPPORTER'`）と GUEST（memberships 行なし）は母集団段階で除外**し、受信者ごとの可視性再チェックをしない一括配信（`NotificationBulkFanoutService`）でもタイトルを漏らさない（§6.2.2 の SUPPORTER 素通り欠陥を母集団側で根治）。被覆索引 `idx_membership_keep_fanout (scope_type, scope_id, role_kind, left_at, user_id)`（`V179`）で index-only 走査になる。
- **操作者・作成者の除外**は `scope_ref="teamId:actorId:creatorId"` に埋め込み、受信者ソースのクエリで `user_id <> actorId AND user_id <> creatorId` として母集団から落とす。**作成者は §6.1 の「必達」の直送で受領する**ため母集団からは外し、二重送信を避ける（作成者が匿名化済み＝`created_by IS NULL` なら creator 枠は番人値 `0`）。
- **`ScheduleKeepNotificationService.notifyConverted` は、作成者直送（①・§6.2.1／§6.2.2 の可視性ガード）を先に行い、続けて TEAM の fan-out を `enqueue`（②）する**。enqueue は母集団を数えず親ジョブ 1 行を INSERT する O(1)。冪等キーはキープ ID（`source_event_uuid`）。**enqueue の失敗は変換を巻き戻さない**（best-effort。呼び出し側 `ScheduleKeepService.notifyConverted` の try/catch が握る）。作成者直送を enqueue より前に置くことで、enqueue が落ちても作成者は受領済みになる。

### 6.3 F03.18 との関係 — `SCHEDULE_CREATED` は抑止しない【裁定・第2版から変更】

**変換で作られた予定は、通常の予定作成と同じく `SCHEDULE_CREATED` の発行対象**である（キープ由来だからといって発行経路に固有の分岐を作らない。カレンダーに予定が増えたという事実は同じだから）。

> **裁定**: **`SCHEDULE_CREATED` は抑止しない。** `SCHEDULE_KEEP_CONVERTED`（§6.1）と併存させる。

第2版は「同じ出来事で2通は通知過多」として抑止する方針を書き、実装判断を F03.18 の確定待ちにしていた。**裁定によりこれを撤回する**:

- **2系統は性質が違う**。`SCHEDULE_KEEP_CONVERTED` は**通知**（プッシュされ、既読を求められる）だが、`SCHEDULE_CREATED` が流れるのは主に**フィード＝閲覧型**であり、開いた人が見るだけで「捌く対象」にならない。**通知疲れに直結するのは前者だけ**であり、後者を残しても ADHD 原則に反しない。
- 抑止の実装は既存の予定作成経路に「キープ由来なら発行しない」という分岐を差し込むことになり、**既存機能への侵襲とテスト範囲の拡大を招く**。得られるものに見合わない。
- **F03.18 の確定を待つ必要が無くなった**（本書側で判断が閉じた）。

**F03.16 / F03.18 設計書の実在についての注記**: 本書の front-matter `related` に F03.16 / F03.18 を記載しているが、【確認済み】`docs/features/` 配下に `F03.16*` および `F03.18*` のファイルは**現時点で存在しない**（実在するのは `F03.15_personal_timetable.md` まで）。【確認済み】`SCHEDULE_CREATED` は `com.mannschaft.app.notification.NotificationType` に**実在する**ので、**本節の内容は設計書の有無に依存せず成立する**（§11 再確認事項5 は「新設されたら相互参照を張る」だけの作業に縮小した）。

#### 7.2 `SCHEDULE_KEEP_011` を欠番にする理由

第2版は「SCHEDULED 由来の ARCHIVED からの `restore`」を 409 で塞ぐために `KEEP_RESTORE_REQUIRES_REVERT` を新設したが、**§5.3.1 の裁定により `restore` は `SCHEDULED` へ戻す仕様となり、このエラーが発生する経路が消滅した**。

**番号を詰めず欠番のまま残す**【既定】。実装前の設計書なので詰めても実害は無いが、**検分のログと本書の版差分を突き合わせる際に番号がずれると追跡が難しくなる**ため。実装時に `011` を新規用途で再利用してもよい（そのときは本節を更新する）。

#### 7.1 `KEEP_INVALID_SCOPE` を廃止した理由【中指摘反映・到達不能コードの削除】

初版には `KEEP_INVALID_SCOPE`（400・XOR 違反）があったが、**削除した**。

- スコープは**パスから一意に決まり、クライアントはボディでスコープを指定できない**（§4.2）。したがって**クライアント入力から XOR 違反に到達する経路が無い**。
- 到達不能なエラーコードは (a) テストで踏めない（カバレッジの嘘）、(b) 実装者に「クライアントが指定できるのか」と誤解させる、(c) 番号を無駄に消費する。
- **XOR は DB CHECK（§2.3）がサーバ側実装バグに対する最後の砦として残る**。そこに到達したら制約違反例外＝500 であり、それは**正しい**（クライアントのせいではなくサーバのバグだから、400 で「あなたの入力が悪い」と言ってはいけない）。

> **注記**: `ScheduleKeepErrorCode` は新規 enum なので 001 から採番でき、既存との衝突は原理的に無い。ただし **`ErrorCode` 実装全体でコード文字列がユニークである前提**があるため、**確定はマージ時に `SCHEDULE_KEEP_` 接頭辞が他 enum で未使用であることを再確認**すること（memory `feedback_migration_version_collision` と同様の直前再確認）。

## 10. 非機能

### 10.1 件数上限【既定】

| スコープ | 上限（`status='KEPT'` の件数） | 根拠 |
|---|---|---|
| 個人 | **200 件** | 「行きたいことリスト」として現実的な上限。超えるとリスト自体が認知負荷になる |
| チーム | **300 件** | 数十人が数年溜めても届かない |
| 組織 | **300 件** | 同上 |

- 上限は **`status='KEPT'` のみで数える**（`ARCHIVED`・`SCHEDULED` は含めない）。「見送る」ことで枠が空くので、詰まったら整理すればよい。
- 超過時は 409 `SCHEDULE_KEEP_010` と、i18n（`scheduleKeep.limit.hint`）で「見送りにすると枠が空きます」を案内する（**責めない文言**）。
- **同時作成の競合は許容する**【中指摘反映・既定】。上限チェックは `COUNT` → `INSERT` の非原子的な2ステップなので、**同時リクエストで上限を数件超えることがありうる**。防ぐには悲観ロックか一意制約が必要だが、**上限は UX 上のガードであって整合性要件ではない**（301 件になっても何も壊れない）。ロックのコストと複雑さに見合わないため**軽微な超過を許容**する。次回の作成時に上限判定が効いて止まる。

### 10.2 並び順

- **既定ソートは `sort_order` 昇順 → `created_at` 降順**【第2パス指摘反映で `id` から変更】。`sort_order` の既定 0 のため、**何も並び替えていない状態では「新しい順」**になる（直近で思いついたことが上に来る＝ADHD 的に正しい）。
- **なぜ `id` を tie-break に使わないか**: 主キーが UUIDv7 になった（§3.2）。UUIDv7 は時刻順に単調増加する設計なので `id` 降順でも実用上は「新しい順」になるが、**「ID の内部構造に順序の意味を持たせる」暗黙の依存は書かない**（ID 生成方式を変えた瞬間に並び順が壊れる）。**意味が明示されている `created_at` を使う。**
- **gap 採番を採る**【軽微指摘反映】: `reorder` 時は `0, 10, 20, 30...` と **10 刻み**で採番する。連番（0,1,2...）だと「1件だけ間に差し込む」ときに後続全件の UPDATE が必要になるが、gap があれば**間の値を1件 UPDATE するだけ**で済む。
- 型は **`INT UNSIGNED`**（初版の `SMALLINT` から変更）。gap 採番は値が飛ぶため、再採番なしの長期運用では `SMALLINT`（65535）では窮屈になりうる。`INT UNSIGNED` なら実質枯渇しない。
- **手動並び替えは任意機能**であり、使わなくても成立する（§1.3 後で整理可能）。

### 10.3 クエリ性能・シャーディング耐性

- 一覧クエリ（`スコープ列 = ? AND status = ? ORDER BY sort_order ASC, created_at DESC`）は `idx_skeep_team` / `idx_skeep_org` / `idx_skeep_user` の走査順がそのまま並び順に一致するよう、**`created_at` を降順 index 列**（MySQL 8.0 の descending index）として定義している（§3.3）。これにより**並べ替えのための追加ソートが要らない**。
  - **⚠️ 第2版の「カバリングで解決」表現は削除した**【第2パス指摘反映】。実際には `title` / `memo` / `candidate_dates` 等を SELECT するので**カバリングインデックスにはならない**（主キー経由で行を取りに行く）。index が保証するのは**絞り込みと並び順**であって、行取得までではない。
  - **降順 index 列を使わない場合**（`sort_order ASC, created_at ASC` に揃える案）でも成立するが、その場合**未整列時の一覧が「古い順」になり ADHD 上の意図（新しいものが上）が崩れる**。降順 index 列でこの矛盾を解消している。実装時に `EXPLAIN` で `Using filesort` が出ないことを確認すること。
- **テナント絞り込み**（原則7）: 組織スコープの Repository は **`AbstractTenantAwareRepository` を継承**する（`organization_id` を持つため）。
- **シャーディング耐性**（CMP-008）: シャードキー候補は **スコープ列**（`team_id` / `organization_id` / `user_id`）。キープは**単一スコープに閉じた小さなデータ**であり、スコープをまたぐ集計・JOIN を一切行わない。**キープと変換先の予定は必ず同じスコープ列の値を持つ**（§4.5.2）ため、シャード分割時も同じシャードに落ち、**クロスシャード JOIN は発生しない**。
- **⚠️ 第2版の誤った論法を訂正**【軽微指摘反映】: 第2版は「`idx_skeep_conv_*` にスコープ列を含めることでシャードを一意に決められる」と書いたが、**index のカラム構成とシャードルーティングは無関係**である（どのシャードを引くかはアプリがどのキーでルーティングするかの問題で、index の中身は関係しない）。`idx_skeep_conv_*` にスコープ列を先頭に置く理由は**単に実クエリの形（`スコープ列 = ? AND converted_schedule_id IN (...)`）に合わせるため**である（§3.3.3）。シャード耐性は上記のとおり「スコープ列でルーティングし、キープと予定が同スコープに揃う」ことで別途担保される。
- N+1: 一覧の `createdBy` 表示名解決と `convertedScheduleState` 解決は **一括解決**で行う（§4.3・§4.5.1・AC-09b）。

### 10.4 後方互換

- **新規テーブル1本のみ**。既存テーブルへの ALTER も、既存 API の破壊的変更も**無い**（初版で提案していた `schedules.origin_keep_id` 列は §4.5.1 の裁定で撤回）。
