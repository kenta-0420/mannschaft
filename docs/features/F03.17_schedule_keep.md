## 1. 課題・背景

### 1.1 課題 — 「行きたいね」が消えていく

現状、Mannschaft でチーム内に生まれる予定の芽は、次の2択しか行き先が無い。

| 行き先 | 何が起きるか |
|---|---|
| カレンダー（`schedules`）に登録する | 【確認済み】`start_at DATETIME NOT NULL`（`V3.040__create_schedules_table.sql`）。**日付を決めないと登録できない**。仮の日付を入れると「決まった予定」として通知・出欠・Google 同期に流れ、嘘の予定がカレンダーを汚す |
| チャット・タイムラインで話す | 流れて消える。1週間後には誰も覚えていない |

結果、「今度みんなで合宿行きたいね」「そのうち BBQ やろう」といった**日付未定のアイデアが、決まる前に死ぬ**。これは機能の欠落であって、ユーザーの怠慢ではない。

### 1.2 TimeTree 比較で採用が決まった背景【御裁可済】

競合調査（TimeTree）との比較で、Mannschaft に無く TimeTree にある強力な概念として「**キープ**」が挙がり、**採用が決定した**。

| 観点 | TimeTree の「キープ」 | 本書の設計 |
|---|---|---|
| 位置づけ | 日付未定のメモをカレンダーとは別の棚に貯める | 同じ（`schedule_keeps` テーブル） |
| 入力摩擦 | タイトルだけで置ける | 同じ（**必須はタイトル1項目のみ**・§1.3） |
| 日程確定 | キープから予定に変換できる | 同じ（**2タップ以内で `schedules` へ落とす**・§4.5） |
| スコープ | 主に共有カレンダー単位 | **チーム／組織／個人の3スコープ**【御裁可済】（§2.3） |
| 変換後の元データ | （消える挙動） | **消さずに残し `converted_schedule_id` で紐付ける**【御裁可済】（§5.2） |

**Mannschaft 固有の勝ち筋**: チームスコープを持つことで、「行きたいね」→**チーム内で相談**→日程確定→カレンダー、という**日程化までの一連の流れがアプリ内で閉じる**。TimeTree の個人・家族用途に対し、チーム運営の意思決定導線として差別化する。

### 1.3 ADHD フレンドリー要件（CMP-005 準拠）

`memory/user_adhd_tendency.md` の3原則「**入力摩擦ゼロ・必須項目最小化・後で整理可能**」に完全準拠する。F02.5 行動メモの設計思想（【確認済み】「気分入力等の装飾的入力はオプトイン」「書かなかったことを通知で責めない」）を踏襲する。

| 原則 | 本機能での具体化 |
|---|---|
| 入力摩擦ゼロ | 作成は **タイトル1項目のみ必須**。メモ・候補日・並び順はすべて任意。1入力欄＋送信ボタンで完結 |
| 必須項目最小化 | `title` 以外に `NOT NULL`（デフォルト値なし）の入力項目を置かない |
| 後で整理可能 | メモ・候補日は後から追記できる。並び替え（`sort_order`）も後からで良い |
| 責めない・急かさない | **「キープしたまま放置している」ことを催促する通知を作らない**【既定】。滞留リマインドは実装しない（F02.5 の「メモなし週のリマインドを実装しない」判断と同思想）。**この不存在は ArchUnit で機械的に保証する**（§9.5・AC-28） |
| 段階開示 | 一覧は「タイトル＋（あれば）候補日バッジ」のみ。メモ・変換操作は展開して初めて見える（F04.11 通知インボックスの段階開示に倣う） |

### 1.4 なぜ既存テーブルを流用できないか【確認済み】

| 候補 | 流用不可の理由 |
|---|---|
| `schedules` | 【確認済み】`start_at DATETIME NOT NULL`。日付未定を表現できない。NULL 許容へ緩めると、出欠生成・繰り返し展開バッチ・Google 同期・カレンダー取得クエリ（`idx_sch_team_start(team_id, start_at)` 等）**全経路が NULL を考慮する必要が生じ**、既存の稼働機能を広範囲に危険へ晒す。**新設が正当** |
| `todos`（F02.3） | TODO は「自分がやる作業」。キープは「みんなで行く予定の候補」で出席概念を持つ。役割が異なる（F02.5 の「予定=TODO／実績=行動メモ」の役割分離と同じ考え方） |
| `action_memos`（F02.5） | 個人スコープ専用・実績記録。チーム共有・日程化の導線を持たない |

## 2. スコープ

### 2.1 対象ロール

| ロール | 閲覧 | 作成 | 編集・削除・revert・archive・restore | **変換（convert）** |
|---|---|---|---|---|
| 本人（個人スコープ） | ○ | ○ | ○ | ○ |
| チーム／組織 **ADMIN** | ○ | ○ | ○ | ○ |
| チーム／組織 **MEMBER** | ○ | ○ | **作成者本人のみ** | **○（全員）**【裁定・§2.1.1】 |
| チーム／組織 SUPPORTER（応援者） | **✕** | ✕ | ✕ | ✕ |
| GUEST | ✕ | ✕ | ✕ | ✕ |
| 非メンバー・他組織 | ✕（**404 で存在秘匿**） | ✕ | ✕ | ✕ |

#### 2.1.1 変換だけ MEMBER 全員に開放する理由【裁定・初版からの変更】

初版は「編集・削除・変換はすべて作成者＋ADMIN のみ」としていたが、これは**§1.2 の主目的（チーム内で相談して日程化する）と矛盾していた**。「言い出しっぺが不在・多忙でも、話がまとまったら誰かが日程を入れられる」ことが本機能の価値だからである。

- **`convert` は MEMBER 以上の全員に開放する。**
- 代わりに **変換時は作成者へ必ず通知する**（§6.1）。「自分のキープが自分の知らないうちに予定になっていた」状態を作らない。変換者＝作成者の場合は自己通知しない。
- **編集（PATCH）・削除（DELETE）・revert・archive・restore は従来どおり作成者＋ADMIN のみ。**
- **「前に進める操作は開放し、書き換え・巻き戻しは限定する」という非対称**を意図的に採る。

### 2.2 対象レベル

- [x] 組織 (Organization)
- [x] チーム (Team)
- [x] 個人 (Personal)

**主役はチームスコープ**である（§1.2）。個人スコープは「自分だけの行きたいことリスト」、組織スコープは「組織全体の年間行事候補の下書き」として提供する。

### 2.3 3スコープの排他制約【御裁可済】

【確認済み】`schedules` の現行 XOR 制約は **`ck_schedules_scope_xor`（CASE-sum 形式・4カラム）** である。`V9.086__add_committee_id_to_schedules.sql` が旧 `chk_schedule_scope`（3カラム・OR 羅列形式）を `DROP CHECK` し、置き換えた。実物（引用）:

```sql
-- 【確認済み】V9.086__add_committee_id_to_schedules.sql（既存 schedules の現行制約）
ALTER TABLE schedules
    ADD COLUMN committee_id BIGINT UNSIGNED NULL ... AFTER user_id,
    ADD CONSTRAINT fk_schedules_committee FOREIGN KEY (committee_id) REFERENCES committees (id) ON DELETE CASCADE,
    DROP CHECK chk_schedule_scope,
    ADD CONSTRAINT ck_schedules_scope_xor CHECK (
        (CASE WHEN team_id IS NOT NULL THEN 1 ELSE 0 END)
        + (CASE WHEN organization_id IS NOT NULL THEN 1 ELSE 0 END)
        + (CASE WHEN user_id IS NOT NULL THEN 1 ELSE 0 END)
        + (CASE WHEN committee_id IS NOT NULL THEN 1 ELSE 0 END)
        = 1
    );
```

**本書はこの現行形式（CASE-sum・`ck_` 接頭辞）に揃える**【提案】:

```sql
CONSTRAINT ck_schedule_keeps_scope_xor CHECK (
      (CASE WHEN team_id IS NOT NULL THEN 1 ELSE 0 END)
    + (CASE WHEN organization_id IS NOT NULL THEN 1 ELSE 0 END)
    + (CASE WHEN user_id IS NOT NULL THEN 1 ELSE 0 END)
    = 1
)
```

- **命名は `ck_schedule_keeps_scope_xor`**（`ck_` 接頭辞＋テーブル名＋用途。`ck_schedules_scope_xor` と同形）。旧 `chk_` 接頭辞は使わない。
- **CASE-sum 形式を採る理由**: OR 羅列形式はカラム N 個で N 行に膨れ、スコープ追加のたびに全行を書き直す必要がある。CASE-sum は **1行足すだけで拡張できる**（`schedules` が委員会スコープ追加時に形式ごと乗り換えたのはこのため）。同じ轍を踏まない。
- **委員会スコープ（`committee_id`）は本書では持たない**【既定】。必要になった時点で CASE を1行足すだけで拡張できる。
- **DB レベル CHECK ＋ アプリ層バリデーションの二重保護**（`schedules` の前例に同じ）。ただし到達性については §7.1 を参照（**クライアント入力からは XOR 違反に到達できない**）。

### 2.4 本書のスコープ外（明示的な後回し）

- キープへの出欠・投票（候補日の多数決）。→ 候補日は**候補メモに留める**（§3.4）。投票が要るなら村の寄合（`village_meetups`）または F05.4 アンケートを使う。
- キープの繰り返し設定・リマインド。→ 日付が無いものにリマインドは付かない（§1.3「急かさない」）。
- キープへのファイル・画像添付。→ 将来拡張（§11）。
- Google Calendar 同期。→ **キープは同期しない**（日付が無いので Google 側に表現できない）。変換後の `schedules` が従来どおり同期対象になる。
- 委員会スコープ（§2.3）。

## 3. DB 設計

### 3.1 新規テーブル一覧

| テーブル | 種別 | ドメイン | 主キー方針 |
|---|---|---|---|
| `schedule_keeps` | 新規 | schedule | **BIGINT UNSIGNED AUTO_INCREMENT**（`BaseEntity` 継承。原則6の例外・§3.2） |

**追加テーブルは1本のみ**。候補日は JSON 列で持ち、子テーブルを作らない（§3.4）。**既存テーブルへの ALTER は無い**（逆引きは列を足さずに実現する・§4.5.1）。

### 3.2 主キー方針 — なぜ `BaseEntity`（BIGINT）か【提案・原則6の例外】

CLAUDE.md 原則6は「新規テーブルは `UuidV7Entity` 継承」だが、**本テーブルは `BaseEntity`（BIGINT UNSIGNED）を採る**。

- 【確認済み】`UuidV7Entity` は schedule ドメインには**存在しない**（村ドメイン等の新しい系統に存在する基底）。schedule ドメインの実体は `ScheduleEntity extends BaseEntity`（`backend/src/main/java/com/mannschaft/app/schedule/entity/ScheduleEntity.java`）で `id: Long`・`@GeneratedValue(IDENTITY)`。
- キープは **`schedules` と相互参照する**（`converted_schedule_id` → `schedules.id` = BIGINT）。ID 体系を混在させると、変換 API・逆引き・FE の型がすべて2体系を扱うことになり、同一ドメイン内で無用な複雑さを生む。
- よって **`schedule_keeps` は `BaseEntity` を継承し `id BIGINT UNSIGNED AUTO_INCREMENT`** とする。「既存ドメインの ID 体系に合わせる」ための意図的な例外であり、`docs/architecture/domain_db_design_principles.md` の例外区分に該当する。**実装 PR の Javadoc に理由を明記すること**。
- 【確認済み】`BaseEntity`（`backend/src/main/java/com/mannschaft/app/common/BaseEntity.java`）は `id`・`createdAt`・`updatedAt` のみを持ち、**`deletedAt` を含まない**。`ScheduleEntity` と同様に **`deletedAt` フィールドを自前で持つ**（原則3）。
- **⚠️ `@SQLRestriction` の注意**【軽微指摘反映】: `@SQLRestriction("deleted_at IS NULL")` は**クラス単位のアノテーションで `@MappedSuperclass` から継承されない**。`ScheduleKeepEntity` 自身に明示的に付与すること。また **JPQL/Criteria には効くがネイティブクエリには効かない**ため、ネイティブクエリでは `deleted_at IS NULL` を手で書く。

### 3.3 `schedule_keeps` DDL【提案】

| カラム名 | 型 | NULL | デフォルト | 説明 |
|---|---|---|---|---|
| `id` | BIGINT UNSIGNED | NO | AUTO_INCREMENT | PK |
| `team_id` | BIGINT UNSIGNED | YES | NULL | チームスコープ（`teams.id` を ID 参照。**FK は張らない**・§3.5） |
| `organization_id` | BIGINT UNSIGNED | YES | NULL | 組織スコープ |
| `user_id` | BIGINT UNSIGNED | YES | NULL | 個人スコープ（＝オーナー） |
| `title` | VARCHAR(200) | NO | — | **唯一の必須入力**。空文字・空白のみは 400（§7） |
| `memo` | TEXT | YES | NULL | 任意メモ |
| `candidate_dates` | JSON | YES | NULL | 候補日の配列（**任意**）。形式は §3.4 |
| `status` | **VARCHAR(20)** | NO | 'KEPT' | 状態（§5）。**ENUM ではなく VARCHAR(20)** — §3.3.1 |
| `converted_schedule_id` | BIGINT UNSIGNED | YES | NULL | 変換で生成した `schedules.id`（§3.3.2） |
| `sort_order` | INT UNSIGNED | NO | 0 | 一覧の手動並び順（小さいほど上）。gap 採番・§10.2 |
| `created_by` | BIGINT UNSIGNED | YES | NULL | 作成者（`users.id` を ID 参照）。個人スコープでは `user_id` と一致 |
| `created_at` | DATETIME | NO | CURRENT_TIMESTAMP | `BaseEntity` |
| `updated_at` | DATETIME | NO | CURRENT_TIMESTAMP ON UPDATE | `BaseEntity` |
| `deleted_at` | DATETIME | YES | NULL | 論理削除（原則3） |

```sql
CREATE TABLE schedule_keeps (
  id                    BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  team_id               BIGINT UNSIGNED NULL,
  organization_id       BIGINT UNSIGNED NULL,
  user_id               BIGINT UNSIGNED NULL,
  title                 VARCHAR(200)    NOT NULL,
  memo                  TEXT            NULL,
  candidate_dates       JSON            NULL,
  status                VARCHAR(20)     NOT NULL DEFAULT 'KEPT',
  converted_schedule_id BIGINT UNSIGNED NULL,
  sort_order            INT UNSIGNED    NOT NULL DEFAULT 0,
  created_by            BIGINT UNSIGNED NULL,
  created_at            DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at            DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  deleted_at            DATETIME        NULL,
  PRIMARY KEY (id),
  CONSTRAINT ck_schedule_keeps_scope_xor CHECK (
        (CASE WHEN team_id IS NOT NULL THEN 1 ELSE 0 END)
      + (CASE WHEN organization_id IS NOT NULL THEN 1 ELSE 0 END)
      + (CASE WHEN user_id IS NOT NULL THEN 1 ELSE 0 END)
      = 1
  ),
  CONSTRAINT ck_schedule_keeps_converted CHECK (
       (status = 'KEPT'      AND converted_schedule_id IS NULL)
    OR (status = 'SCHEDULED' AND converted_schedule_id IS NOT NULL)
    OR (status = 'ARCHIVED')
  ),
  INDEX idx_skeep_team      (team_id,         status, sort_order, id),
  INDEX idx_skeep_org       (organization_id, status, sort_order, id),
  INDEX idx_skeep_user      (user_id,         status, sort_order, id),
  INDEX idx_skeep_conv_team (converted_schedule_id, team_id),
  INDEX idx_skeep_conv_org  (converted_schedule_id, organization_id),
  INDEX idx_skeep_conv_user (converted_schedule_id, user_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

#### 3.3.1 `status` は ENUM でなく VARCHAR(20)【初版からの修正】

【確認済み】`schedules` の実 DDL（`V3.040`）は **`status VARCHAR(20) NOT NULL DEFAULT 'SCHEDULED'`** であり、**MySQL の ENUM 型は使っていない**（F03.1 設計書の ENUM 表記は論理型としての表現）。schedule ドメインの作法に揃え、`schedule_keeps.status` も **VARCHAR(20)** とする。

- 値の妥当性は **Java enum `ScheduleKeepStatus`（`@Enumerated(EnumType.STRING)`）** で担保する。
- **VARCHAR の利点**: 状態値の追加が `ALTER TABLE ... MODIFY` を伴わない（MySQL の ENUM 変更はテーブル再構築を招きうる）。

#### 3.3.2 変換 CHECK — 状態と `converted_schedule_id` の対応を DB で強制【中指摘反映】

初版の CHECK は片方向（`SCHEDULED` ⇒ 非 NULL）だったため、**「`KEPT` なのに `converted_schedule_id` が残っている」不整合を DB が許していた**。これは §5.3.1 の**予定二重生成バグの温床**そのものである。

| status | `converted_schedule_id` | 理由 |
|---|---|---|
| `KEPT` | **必ず NULL** | 未変換、または `revert` 済み。**ここに値が残ると再変換で予定が二重に生まれる** |
| `SCHEDULED` | **必ず非 NULL** | 変換先が必ず存在する（レコードとしては削除済みでも ID は保持・§5.4） |
| `ARCHIVED` | **NULL / 非 NULL どちらも可** | KEPT 由来なら NULL、SCHEDULED 由来なら非 NULL。**この2由来の区別が §5.3.1 の判定に使われる** |

これにより `revert`・`restore` は **`converted_schedule_id` の NULL クリアを必ず伴う**ことが DB レベルで強制され、実装漏れが即座に制約違反として露見する。

#### 3.3.3 index の意図

| index | 用途 |
|---|---|
| `idx_skeep_team (team_id, status, sort_order, id)` | チームのキープ一覧（既定 `status='KEPT'` 絞り＋`sort_order` 昇順 → `id` 降順）を index だけで解決する |
| `idx_skeep_org` / `idx_skeep_user` | 同上（組織／個人スコープ） |
| `idx_skeep_conv_*` **（スコープ込み複合）** | **逆引き**「この予定はどのキープから生まれたか」（§4.5.1）。**シャード耐性のためスコープ列を含める**（§10.3） |

**照合順序**: **`utf8mb4_unicode_ci`**【初版からの修正】。【確認済み】migration 配下の実出現数は `utf8mb4_unicode_ci` **546 ファイル** vs `utf8mb4_0900_ai_ci` **28 ファイル**で、`schedules` 自身（`V3.040`）も `utf8mb4_unicode_ci`。**多数派かつ隣接テーブルと一致する方**を採る（照合順序が異なると JOIN 時に暗黙変換が起き index が効かなくなる実害がある）。

### 3.4 `candidate_dates` JSON 形式【提案】

「いつがいい？」の**メモ**であり、投票機構ではない（§2.4）。

```json
["2026-09-12", "2026-09-19", "2026-10-03"]
```

| 規約 | 内容 |
|---|---|
| 型 | `String[]`（ISO-8601 の日付 `YYYY-MM-DD`。**時刻は持たない**） |
| 件数上限 | **10 件**【既定】。超過は 400（`SCHEDULE_KEEP_003`） |
| 日付形式不正 | 400（`SCHEDULE_KEEP_004`・§7 で分離） |
| 並び | 保存時に昇順ソート・重複除去してから格納 |
| **空配列の正規化** | **`[]` を受け取ったら DB には `NULL` を格納する**【軽微指摘反映】。「候補日なし」の DB 表現を **NULL 一本に固定**し、`NULL` と `[]` の2表現を混在させない（クエリ・FE 分岐を1つに保つ） |
| **過去日** | **許容する**【軽微指摘反映・既定】。「去年の今頃やった行事をまた」のようにカレンダーから拾った日付をそのまま候補にする使い方があり、弾くと入力摩擦になる（§1.3）。**過去日から変換した場合も過去日の予定として作成される**（`schedules` は過去日の予定を許容している） |
| 省略 | `null`（API レスポンスも `null`。空配列は返さない） |
| Java 側マッピング | 【確認済み】`ScheduleEntity.recurrenceRule` の前例に倣い **`@Column(columnDefinition = "JSON") private String candidateDates;`（String 保持）** とし、Service 層で `List<LocalDate>` へ変換する |

**なぜ子テーブルにしないか**: 候補日は投票対象ではなく順序も持たない、キープに完全従属する付随データである。子テーブルにすると N+1・CASCADE・並び順管理のコストが付き、「入力摩擦ゼロ」の実装が重くなる。10 件上限の固定長配列なので JSON 列で十分（`schedules.recurrence_rule` と同じ判断）。

**なぜ JSON 列に DB 側 CHECK を張らないか**【軽微指摘反映】: MySQL の `JSON_SCHEMA_VALID()` による CHECK は (a) 8.0.17+ 依存、(b) エラーが制約名しか返さず**どの要素が不正かユーザーに伝えられない**、(c) 件数・形式の検証は既にアプリ層（`SCHEDULE_KEEP_003`/`004`）が担っており二重管理になる。**検証はアプリ層に一本化**し、DB は JSON の構文妥当性（MySQL の JSON 型が自動保証）に留める。

**⚠️ タイムゾーン**: `candidate_dates` は **日付のみ**（壁時計の日付）であり瞬間ではない。FE で `Date` に変換して tz 投影し直すと1日ずれる（memory `project_fe_datetime_picker_instant_vs_wallclock`）。**文字列 `YYYY-MM-DD` のまま扱い `localDate.ts` のユーティリティを使う**こと。

### 3.5 FK 方針とドメイン境界（原則1・2）【提案】

| 参照 | FK | 理由 |
|---|---|---|
| `team_id` → `teams.id` | **張らない** | チームは team ドメイン。**クロスドメイン FK 禁止**（原則1）。index のみ・整合はアプリ層 |
| `organization_id` → `organizations.id` | **張らない** | 同上 |
| `user_id` → `users.id` | **張らない** | 同上（user ドメイン）。退会時は §3.7 |
| `created_by` → `users.id` | **張らない** | 同上 |
| `converted_schedule_id` → `schedules.id` | **張らない**【既定】 | `schedules` は**同一 schedule ドメイン**なので原則1には抵触しないが、CASCADE を張ると「予定を消したらキープごと消える」という誤った意味になる。**予定が消えてもキープは残す**（§5.4）ため FK は張らず index のみとし、アプリ層で解決する |

#### 3.5.1 ⚠️ `schedules` との FK 差分 — アプリ層の後始末が必須【重要・中指摘反映】

【確認済み】**`schedules` は本表と違って実際に FK を張っている**: `fk_sch_team`（`team_id`→`teams` **ON DELETE CASCADE**）・`fk_sch_org`（`organization_id`→`organizations` **CASCADE**）・`fk_sch_user`（`user_id`→`users` **CASCADE**）・`fk_sch_created_by`（SET NULL）・`fk_sch_parent`（RESTRICT）。

これは **`schedules` が原則1（クロスドメイン FK 禁止）確立前に作られた歴史的経緯**によるもので、**本表はこれを踏襲しない**（原則1に従い FK を張らない）。

**その結果として生じる差分を明示する（見落とすと孤児レコードが残る）**:

| | `schedules`（既存） | `schedule_keeps`（本書） |
|---|---|---|
| チーム物理削除時 | **DB が CASCADE で自動削除** | **何も起きない → アプリ層が明示的に後始末しなければ孤児化** |
| ユーザー物理削除時 | **DB が CASCADE で自動削除** | 同上 |

→ **§3.7 のアプリ層後始末は「あれば良い」ではなく必須**である。実装漏れは孤児レコードとして直接現れる（AC-27b で実測する）。

| `startAt` | String (ISO-8601 LocalDateTime) | ✕ | ○ | 確定した開始日時。`schedules.start_at` が NOT NULL のため必須 |
| `endAt` | String | ○ | ✕ | 省略可（`schedules.end_at` は NULL 許容） |
| `allDay` | Boolean | ✕ | ✕（既定 **true**） | true のとき `startAt` の時刻を `00:00:00` に正規化（`schedules` の既存規約に同じ） |

**サーバ側の処理**（単一トランザクション・schedule ドメイン内で完結・原則5）:

1. キープを取得し**スコープ一致検証**（§4.6.3）→ 認可（§4.6）→ `status='KEPT'` を確認（他は 409 `SCHEDULE_KEEP_006`）
2. `schedules` に新規行を作る（**既定値は §4.5.2 で固定**）
3. キープを `status='SCHEDULED'`・`converted_schedule_id=<新規 schedules.id>` へ更新（**元レコードは削除しない**【御裁可済】）
4. 通知は **コミット後に best-effort** で発火（§6）。**作成者への通知は必須**（§2.1.1）

**⚠️ 日時バインド**: `startAt` はリクエストボディ経由＝Jackson 経路。クエリパラメータ経路（ConversionService）とは**独立**であり片方の修正は他方に届かない（memory `project_datetime_binding_path_asymmetry`）。

#### 4.5.1 逆引き「この予定はどのキープから生まれたか」【裁定・初版から方式変更】

初版は「`schedules` に `originKeepId` 列を足す」としていたが、**裁定により列は足さない**。

- **`schedules` テーブルは一切変更しない**（§3.1）。既存の巨大テーブルに列を足すと、出欠・繰り返し・Google 同期の全経路にレスポンス差分が波及する。
- **逆引きは `schedule_keeps.converted_schedule_id` 側から引く**。`idx_skeep_conv_team` / `_org` / `_user`（**スコープ列を含む複合 index**）で解決する。
- **なぜスコープ込み複合 index か（シャード耐性）**: `converted_schedule_id` 単独 index だと、シャーディング後に「どのシャードを引けばよいか」が ID だけでは決まらず**全シャード fan-out** になる。スコープ列を含めることで、**呼び出し側が既に持っているスコープでシャードを一意に決められる**（§10.3）。
- **N+1 回避の取得方法**【中指摘反映】: 予定一覧から逆引きするときは、**`converted_schedule_id IN (:scheduleIds) AND team_id = :teamId` の1クエリで一括取得**し、`Map<Long scheduleId, ScheduleKeepRef>` に畳んでから DTO へ流し込む。**予定1件ごとに引かない**（AC-09b で実測）。
- API 形状: **専用エンドポイント `GET .../schedule-keeps/by-schedule/{scheduleId}`**（200 = 由来キープ / 404 = キープ由来でない）。既存の予定 API のレスポンスは変えない。
- **繰り返し予定の親になった場合**【中指摘反映】: 変換で作られた予定に後から繰り返しルールが設定されると `parent_schedule_id` で子が展開される。**逆引きが指すのは常に親（変換で作られた実体）のみ**とし、**展開された子には由来キープを引き継がせない**（子は親の派生であり、キープから直接生まれたわけではない）。子から辿りたい場合は FE が `parent_schedule_id` を経由する。

### 4.6 認可【提案・F00 準拠】

**deny-by-default**（`docs/security/README.md`）。

#### 4.6.1 判定の骨子

| 判定 | 方式 |
|---|---|
| スコープ所属 | チーム／組織スコープは **リクエスト者が当該チーム／組織の MEMBER 以上**であることを検証。個人スコープは `user_id == getCurrentUserId()` |

#### 4.6.2 ⚠️ SUPPORTER（応援者）の遮断 — Resolver 内でロール下限を固定合成する【裁定・重大指摘の是正】

**初版の誤り**: 初版は「キープは `MEMBERS_ONLY` 相当固定」とだけ書いていた。これは **F00 の実装上 SUPPORTER に見えてしまう**。

【確認済み】`ScheduleVisibilityResolver`（`backend/src/main/java/com/mannschaft/app/schedule/visibility/ScheduleVisibilityResolver.java`）の実装は次のとおり:

- 機能側 `ScheduleVisibility.MEMBERS_ONLY` は `ScheduleVisibilityMapper` により **`StandardVisibility.SCOPE_AFFILIATED`**（＝「そのスコープに所属している人」）へ写像される。
- **`SCOPE_AFFILIATED` は「所属者」であって「MEMBER 以上」ではない。応援者（SUPPORTER）も所属者に含まれる。**
- 同 Resolver の Javadoc は「**応援者の包含/除外は別軸の `min_view_role` が司る**」と明記しており、**Resolver は status×visibility の合成のみを担当し、ロール軸を扱っていない**。`schedules` は `min_view_role` 列を持つのでそれで応援者を除外できる。

**しかし本書のキープは `min_view_role` 列を持たない**（設定項目を増やさない＝入力摩擦ゼロ・§1.3）。したがって **`SCOPE_AFFILIATED` のままでは応援者にチームの相談内容が見えてしまう**。

**裁定による是正**:

> **`ScheduleKeepVisibilityResolver` の内部で、ロール下限「MEMBER 以上」を固定値として合成する。**

- キープは可視性設定を**持たない**（ユーザーに選ばせない）。よって Resolver は **常に「SCOPE_AFFILIATED ∧ ロール ≥ MEMBER」** を返す固定合成となる。列から読むのではなく**定数として埋め込む**。
- **`ScheduleVisibilityResolver` との差分を Javadoc に明記すること**: 「`schedules` はロール軸を `min_view_role` 列に外出ししているが、`schedule_keeps` は列を持たず MEMBER 下限を Resolver 内に固定する」。この非対称は意図的であり、レビューのたびに「なぜ schedules と違うのか」を問われないよう文書化が必須。
- **将来 `min_view_role` 相当をキープに持たせる場合**でも、固定値を列参照に差し替えるだけで済むよう**定数を1箇所に集約**して実装する。

**この遮断は Wave 1 の必須 red テストである**（§9.3 AC-16・§12）。「SUPPORTER で 404」を**実装前に落ちるテストとして先に書く**こと。認可の抜けは後から気付けない類のバグであり、テスト先行が唯一の防御になる。

#### 4.6.3 IDOR 防御 — 全エンドポイントでスコープ一致を検証【裁定・重大指摘の是正】

**初版の不足**: 初版は「他チームからの GET が 404」しか書いておらず、**`convert`/`archive`/`revert`/`restore`/`reorder` といった操作系の IDOR を検証していなかった**。操作系こそ被害が大きい（他チームのキープを勝手に予定化できてしまう）。

> **全エンドポイント（GET / PATCH / DELETE / convert / revert / archive / restore / reorder / by-schedule）で、
> 「パスのスコープ」と「レコードのスコープ列」の一致を検証し、不一致なら 404 を返す。**

```
パス /teams/{teamPublicId}/schedule-keeps/{keepId}
  → teamPublicId から解決した teamId と keep.teamId が一致するか
  → 不一致（他チームのキープ / 組織キープ / 個人キープ）なら 404 SCHEDULE_KEEP_001
```

- **403 ではなく 404**。403 は「存在するが権限が無い」＝存在を漏らす。
- **`keepId` だけで検索してはならない**。`findById(keepId)` の結果に対して後からスコープを比較する実装は、**比較を忘れた瞬間に IDOR になる**。**リポジトリのクエリ自体をスコープ込みにする**（`findByIdAndTeamId(keepId, teamId)`）のが根治。**スコープを取らない単独 finder は定義しない**。
- **⚠️ 実装上の落とし穴**（memory 由来）:
  - `getCurrentUserId()` の戻り値を `teamId` として使い回す実装は**常に誤り**（`project_matching_authz_userid_as_teamid_idor`）。
  - 認可引数を取るが本体で使っていない「**死んだ引数**」は ArchUnit 番人を欺く（`feedback_dead_authz_param_deceives_guard`）。引数の存在ではなく**到達を検証**すること。
  - 共通ヘルパに一元化しても「全経路がそれを使っている」証明にはならない（`feedback_centralized_helper_not_proof_all_paths_use_it`）。**兄弟メソッドの非対称が手掛かり**。
- **AC-14a〜14f で全操作系を個別に検証する**（§9.3）。

| `KEPT` → `SCHEDULED` | ○ | `convert` | §4.5 |
| `SCHEDULED` → `KEPT`（revert） | **○** | `revert` | **変換先 `schedules` を論理削除し**、キープを `KEPT`・`converted_schedule_id=NULL` に戻す（CHECK により NULL クリアは必須）。変換先に**出欠回答がある場合は 409**（`SCHEDULE_KEEP_008`）で拒否し、予定側で運用させる（回答を握りつぶさない＝対処療法禁止の原則） |

| **`ARCHIVED`（KEPT 由来・conv_id NULL）→ `KEPT`** | **○** | `restore` | 「やっぱりやりたい」を許す（§1.3 後で整理可能） |

#### 5.3.1 なぜ「SCHEDULED 由来の ARCHIVED からの restore」を塞ぐか【裁定・予定二重生成の根治】

初版の設計には**予定が二重に作られる穴**があった:

```
KEPT → convert（予定A 作成） → SCHEDULED → archive → ARCHIVED
     → restore（初版: status=KEPT・converted_schedule_id を NULL クリア）
     → convert（予定B 作成）   ← 予定A がカレンダーに残ったまま予定B が増える
```

初版は `restore` 時に `converted_schedule_id` を NULL クリアすると書いていたため、**予定Aへの参照が失われたまま再変換でき、同じキープから予定が2つ生まれる**。カレンダーに重複した予定が並び、どちらが正か誰にも分からなくなる。

**裁定による根治**: **SCHEDULED 由来の ARCHIVED からの `restore` は 409 で拒否し、「先に `revert` せよ」と促す。**

- 正しい順路: `ARCHIVED`（SCHEDULED 由来） → **`revert`**（予定A を論理削除し `KEPT` へ） → 必要なら再 `convert`。
- **判定は `converted_schedule_id IS NOT NULL`** で行う（`ARCHIVED` かつ非 NULL ＝ SCHEDULED 由来）。§3.3.2 の CHECK が `ARCHIVED` に限り非 NULL を許すのは、**この由来の区別を保持するため**である。
- **`revert` は `KEPT` 以外のどの状態からでも、`converted_schedule_id` が非 NULL なら受け付ける**（`SCHEDULED` / `ARCHIVED` の両方）。これがエスケープハッチになり、ユーザーが詰まない。
- エラーメッセージは**次の行動を示す**（「予定になったキープを戻すには、先に予定を取り消してください」）。単に「できません」と言わない。

### 5.4 変換先 `schedules` が消えたとき — CANCELLED と論理削除の区別【中指摘反映】

初版は「削除」しか扱っていなかったが、【確認済み】`schedules` は **`status='CANCELLED'`（キャンセル）と `deleted_at`（論理削除）の2つの「消え方」**を持つ。区別しないと FE が誤った案内を出す。

レスポンスの **`convertedScheduleState`** で表現する:

| 値 | 変換先の状態 | FE の表示・導線 |
|---|---|---|
| `NONE` | `converted_schedule_id IS NULL`（未変換） | 「予定にする」ボタン |
| `ACTIVE` | 予定が存在し `status` が `SCHEDULED`/`COMPLETED` | 予定へのリンク |
| `CANCELLED` | 予定は存在するが `status='CANCELLED'` | 「予定は中止になりました」＋`revert` 導線 |
| `DELETED` | 予定が論理削除済み（`deleted_at` 非 NULL）または存在しない | 「元の予定は削除されました」＋`revert` 導線 |

- キープ自身は **`status='SCHEDULED'` のまま残る**（履歴として正しい。「一度は日程化された」事実は消さない）。
- `CANCELLED`・`DELETED` のいずれでも **`revert` は 200 で通る**（§5.3 の冪等 revert）。
- **`convertedScheduleState` の解決は一括クエリで行う**（§4.5.1・N+1 回避）。

#### 7.1 `KEEP_INVALID_SCOPE` を廃止した理由【中指摘反映・到達不能コードの削除】

初版には `KEEP_INVALID_SCOPE`（400・XOR 違反）があったが、**削除した**。

- スコープは**パスから一意に決まり、クライアントはボディでスコープを指定できない**（§4.2）。したがって**クライアント入力から XOR 違反に到達する経路が無い**。
- 到達不能なエラーコードは (a) テストで踏めない（カバレッジの嘘）、(b) 実装者に「クライアントが指定できるのか」と誤解させる、(c) 番号を無駄に消費する。
- **XOR は DB CHECK（§2.3）がサーバ側実装バグに対する最後の砦として残る**。そこに到達したら制約違反例外＝500 であり、それは**正しい**（クライアントのせいではなくサーバのバグだから、400 で「あなたの入力が悪い」と言ってはいけない）。

> **注記**: `ScheduleKeepErrorCode` は新規 enum なので 001 から採番でき、既存との衝突は原理的に無い。ただし **`ErrorCode` 実装全体でコード文字列がユニークである前提**があるため、**確定はマージ時に `SCHEDULE_KEEP_` 接頭辞が他 enum で未使用であることを再確認**すること（memory `feedback_migration_version_collision` と同様の直前再確認）。

## 10. 非機能

### 10.1 件数上限【既定】

| スコープ | 上限（`status='KEPT'` の件数） | 根拠 |
|---|---|---|
| 個人 | **200 件** | 「行きたいことリスト」として現実的な上限。超えるとリスト自体が認知負荷になる |
| チーム | **300 件** | 数十人が数年溜めても届かない |
| 組織 | **300 件** | 同上 |

- 上限は **`status='KEPT'` のみで数える**（`ARCHIVED`・`SCHEDULED` は含めない）。「見送る」ことで枠が空くので、詰まったら整理すればよい。
- 超過時は 409 `SCHEDULE_KEEP_010` と、i18n（`scheduleKeep.limit.hint`）で「見送りにすると枠が空きます」を案内する（**責めない文言**）。
- **同時作成の競合は許容する**【中指摘反映・既定】。上限チェックは `COUNT` → `INSERT` の非原子的な2ステップなので、**同時リクエストで上限を数件超えることがありうる**。防ぐには悲観ロックか一意制約が必要だが、**上限は UX 上のガードであって整合性要件ではない**（301 件になっても何も壊れない）。ロックのコストと複雑さに見合わないため**軽微な超過を許容**する。次回の作成時に上限判定が効いて止まる。

### 10.2 並び順

- 既定は `sort_order` 昇順 → `id` 降順。`sort_order` の既定 0 のため、**何も並び替えていない状態では「新しい順」**になる（直近で思いついたことが上に来る＝ADHD 的に正しい）。
- **gap 採番を採る**【軽微指摘反映】: `reorder` 時は `0, 10, 20, 30...` と **10 刻み**で採番する。連番（0,1,2...）だと「1件だけ間に差し込む」ときに後続全件の UPDATE が必要になるが、gap があれば**間の値を1件 UPDATE するだけ**で済む。
- 型は **`INT UNSIGNED`**（初版の `SMALLINT` から変更）。gap 採番は値が飛ぶため、再採番なしの長期運用では `SMALLINT`（65535）では窮屈になりうる。`INT UNSIGNED` なら実質枯渇しない。
- **手動並び替えは任意機能**であり、使わなくても成立する（§1.3 後で整理可能）。

### 10.3 クエリ性能・シャーディング耐性

- 全一覧クエリは `idx_skeep_team` / `idx_skeep_org` / `idx_skeep_user`（`(scope列, status, sort_order, id)`）でカバーされ、**ファイルソートを起こさない**。実装時に `EXPLAIN` で確認すること。
- **テナント絞り込み**（原則7）: 組織スコープの Repository は **`AbstractTenantAwareRepository` を継承**する（`organization_id` を持つため）。
- **シャーディング耐性**（CMP-008）: シャードキー候補は **スコープ列**（`team_id` / `organization_id` / `user_id`）。キープは**単一スコープに閉じた小さなデータ**であり、スコープをまたぐ集計・JOIN を一切行わない。
- **逆引きのシャード耐性**【中指摘反映】: `converted_schedule_id` 単独 index では、シャード後に**全シャード fan-out** が必要になる。**`idx_skeep_conv_team` / `_org` / `_user` としてスコープ列を含む複合 index にする**ことで、呼び出し側が持っているスコープからシャードを一意に決められる（§4.5.1）。
- **キープと変換先の予定は必ず同じスコープ列の値を持つ**（§4.5.2）ため、シャード分割時も同じシャードに落ちる。**クロスシャード JOIN は発生しない**。
- N+1: 一覧の `createdBy` 表示名解決と `convertedScheduleState` 解決は **一括解決**で行う（§4.3・§4.5.1・AC-09b）。

### 10.4 後方互換

- **新規テーブル1本のみ**。既存テーブルへの ALTER も、既存 API の破壊的変更も**無い**（初版で提案していた `schedules.origin_keep_id` 列は §4.5.1 の裁定で撤回）。
- 新設の逆引きエンドポイント（`by-schedule`）は追加 API なので既存クライアントに影響しない。
