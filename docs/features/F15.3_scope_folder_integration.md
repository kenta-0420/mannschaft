# F15.3 マイスコープフォルダ統合UX（招待・ナビ・通知）

> **ステータス: 完了（未解決事項ゼロ）**
> 本書は F15.2 の延長フェーズとして、加入導線・ナビゲーション・ダッシュボード通知の3点を統合する設計を定義する。

---

## 1. 概要

### 1.1 機能の目的

ユーザーが多数のチーム・組織・サポータ関係に加入したとき、「どこに何があるか分からなくなる」状態を解消する。
F15.2 で完成した **マイスコープフォルダ基盤**（個人ごとに自由作成できる分類フォルダ）を、以下の3つの動線に統合することで、ユーザーが事前に作ったフォルダを軸にして加入・参照・通知をシームレスに行えるようにする。

1. **加入時フロー** — 招待リンク承諾画面でフォルダを選択（任意・未選択は「未分類」へ自動配置）
2. **ナビゲーション** — ヘッダー「チーム」「組織」をドロップダウン化し、フォルダ/個別チームへ最短2クリックで到達
3. **ダッシュボード通知** — `WidgetNotices.vue` にフォルダ別タブ + 未読件数バッジを追加

### 1.2 F15.2 との関係

| 項目 | F15.2（実装済み） | F15.3（本設計書） |
|---|---|---|
| 範囲 | バックエンド基盤・基本 CRUD | 統合 UX フェーズ（招待・ナビ・通知） |
| テーブル | `my_scope_folders` / `my_scope_folder_items` 新規 | 既存テーブルへの **カラム追加2件** のみ |
| API | フォルダ CRUD / アイテム追加削除 | 既存改修2本 + 新規4本 |
| フロント | DnD によるフォルダ管理 | ヘッダードロップダウン・タブ・招待 UI・通知ウィジェット |

F15.3 は **F15.2 の再実装ではない**。既存実装に対する増分仕様であり、F15.2 のドメインパッケージ `com.mannschaft.app.scopefolder` 内に閉じる。

### 1.3 解決する課題

- 加入後に「どのフォルダに入れるか」を後から手作業で割り振る煩雑さ（招待時に解消）
- ヘッダーから所属チームへ辿る際の階層深さ（ドロップダウンで2クリック到達）
- ダッシュボード通知が全フォルダ混在で重要通知を見落とす問題（フォルダタブで分類）

## 2. 背景・動機

### 2.1 マスター発言の要旨

> 「チーム・組織・サポータに加入しすぎると何がなんだか分からなくなる。事前に作成したフォルダで分類し、加入時に振り分け／ダッシュボード通知をフォルダ別に表示／ナビバーのチーム・組織クリック時にフォルダリストを出すと操作性・視認性が高まる」

### 2.2 ADHD 配慮の意図

本プロジェクトは ADHD 傾向ユーザーの利用を一級の前提とする（プロジェクト全体方針）。本機能は次を必須とする。

- **入力摩擦ゼロ** — 招待時のフォルダ選択は **任意**。未選択時は「未分類」フォルダへ自動配置する
- **後で整理可能** — 「とりあえず未分類に入れて後で整理する」を一級ユースケースとする
- **視覚的識別** — 色だけでなくアイコンも併用（色覚多様性対応も兼ねる）
- **2クリック以内に到達** — 認知負荷を減らすため、目的のチーム/フォルダへ最短経路で行ける

### 2.3 マスター確定事項（軍議承認済み）

| 項目 | 決定内容 |
|---|---|
| ナビ UX | **ドロップダウン**。「すべて（一覧）」項目押下で `/teams`（または `/organizations`）ハブ + タブへ遷移。フォルダ／個別チームへの直接ジャンプも同ドロップダウン内で完結 |
| 招待 UX | **任意 + 「未分類」自動配置**（ADHD 配慮で入力摩擦ゼロ） |
| 通知 UI | **既存 `WidgetNotices` 内にタブ追加 + タブ件数バッジ（吹き出し）** |

## 3. F15.2 との関係（既存実装の前提）

本節は「F15.3 で再実装しないこと」を明示する。

### 3.1 既存実装の前提（F15.2 由来）

- テーブル `my_scope_folders` / `my_scope_folder_items` は既に存在
- 1 ユーザー × 1 scope_type で最大 **20 フォルダ** の上限制約は維持
- IDOR 防止メソッド `findByIdAndUserIdAndDeletedAtIsNull` は流用
- エラーコード `ScopeFolderErrorCode` 5 種（`SCOPE_FOLDER_NOT_FOUND` / `SCOPE_FOLDER_ACCESS_DENIED` / `SCOPE_FOLDER_LIMIT_EXCEEDED` / `SCOPE_FOLDER_NAME_DUPLICATE` / `SCOPE_FOLDER_NOT_MEMBER`）は流用
- 所属確認は F15.2 が使う `UserRoleRepository.existsByUserIdAndTeamId` を踏襲（サポータ対応は §6.3 で別途扱う）

### 3.2 F01.5 `FRIEND_FOLDER` との混同回避

F01.5 「チーム間フレンド関係」には `team_friend_folders` テーブルと `FRIEND_FOLDER` 通知 scope_type が存在するが、これは **チームが他チームを分類するフォルダ（団体間）** であり、本件の「個人がスコープを分類するフォルダ」とは別概念。

- 命名: 本件は `ScopeFolder` を踏襲し、`FriendFolder` 系名称を絶対に使わない
- UI 表記: 本件のフォルダは **「マイフォルダ」** と表記（F01.5 の「フレンドフォルダ」と差別化）
- ドメイン: 本件は `scopefolder` パッケージ、F01.5 は `teamfriend` パッケージで物理的に分離済み

## 4. データモデル

### 4.1 方針

新規テーブルは作らない。F15.2 既存テーブルに **2 カラムだけ追加**し、`my_scope_folder_items` に監査用 1 カラムを追加する。

### 4.2 Flyway マイグレーション

**ファイル名（仮）**: `V11.xxx__alter_my_scope_folders_add_default_and_icon.sql`
（実装時に未使用最新版番を確認のうえ確定。現在の最新は `V9.124`）

```sql
-- マイスコープフォルダに「未分類」フラグとアイコンを追加
ALTER TABLE my_scope_folders
  ADD COLUMN is_default BOOLEAN NOT NULL DEFAULT FALSE,
  ADD COLUMN icon VARCHAR(40) NULL;

-- user_id × scope_type ごとに「未分類」は 1 行のみ。論理削除済みは対象外
CREATE UNIQUE INDEX uq_msf_user_scope_default
  ON my_scope_folders (user_id, scope_type)
  WHERE is_default = TRUE AND deleted_at IS NULL;

-- アイテムにどの経路で割り当てられたかの監査用カラム
ALTER TABLE my_scope_folder_items
  ADD COLUMN assigned_via VARCHAR(20) NOT NULL DEFAULT 'MANUAL';
```

### 4.3 カラム仕様

| カラム | 型 | 制約 | 説明 |
|---|---|---|---|
| `is_default` | BOOLEAN | NOT NULL, DEFAULT FALSE | 「未分類」フォルダフラグ。user_id × scope_type で 1 行のみ。**削除不可・改名不可・末尾固定**（API・サービス層でバリデーション） |
| `icon` | VARCHAR(40) | NULL | PrimeIcons の pi-icon 名（例: `pi-briefcase`、`pi-users`）。色 (`color`) と併用可 |
| `assigned_via` | VARCHAR(20) | NOT NULL, DEFAULT `'MANUAL'` | 監査用。値: `INVITE` / `MANUAL` / `MIGRATION` / `DEFAULT` |

### 4.4 アーキテクチャ原則との整合

| 原則 | 整合内容 |
|---|---|
| **原則 1: クロスドメインFK禁止** | `scope_id` には FK を張らない（F15.2 既存方針を踏襲）。dangling は §9.5 のイベント駆動で処理 |
| **原則 2: CASCADE は同一ドメイン内** | `my_scope_folder_items` → `my_scope_folders` のみ CASCADE（既存通り）。他ドメインとの CASCADE は無し |
| **原則 6: 新規テーブルは UUIDv7** | 本件は **既存テーブルへのカラム追加**であり新規テーブルではない。F15.2 が BIGINT のため踏襲する（既存テーブル変更は原則 6 対象外） |
| **原則 7: テナント絞り込み** | 個人スコープのため `AbstractTenantAwareRepository` 対象外（F15.2 既存方針を踏襲） |

## 5. API 設計

### 5.1 既存エンドポイントの改修

#### 5.1.1 `POST /api/v1/invite/{token}/join`（招待承諾）

リクエストボディに `folderId?` を追加。後方互換維持。

**リクエスト**:
```json
{
  "folderId": 123
}
```

| フィールド | 型 | 必須 | 説明 |
|---|---|---|---|
| `folderId` | Long | × | 配置先フォルダ ID。未指定時は `is_default=TRUE` のフォルダへ自動配置（無ければ lazy 生成） |

**振る舞い**:
1. 招待トークンを検証
2. メンバーシップを作成
3. `folderId` 指定あり → `MyScopeFolderService.addItem(folderId, scopeId, assignedVia=INVITE)` 呼び出し
4. `folderId` 未指定 → `MyScopeFolderService.findOrCreateDefault(userId, scopeType)` で未分類フォルダを取得し、そこへ addItem（`assignedVia=DEFAULT`）

**エラー**:
- 指定 `folderId` が他人所有 → `404 SCOPE_FOLDER_NOT_FOUND`
- 指定 `folderId` の scope_type が招待 scope と不一致 → `400 SCOPE_FOLDER_TYPE_MISMATCH`（新規追加が必要なら §5.4 参照）

#### 5.1.2 `GET /api/v1/me/scope-folders`（フォルダ一覧）

レスポンスに `isDefault`, `icon`, `notificationUnreadCount` を追加。

**レスポンス例**:
```json
[
  {
    "id": 1,
    "name": "部活",
    "color": "#3B82F6",
    "icon": "pi-users",
    "isDefault": false,
    "sortOrder": 0,
    "itemScopeIds": [101, 102, 103],
    "notificationUnreadCount": 5
  },
  {
    "id": 99,
    "name": "未分類",
    "color": null,
    "icon": null,
    "isDefault": true,
    "sortOrder": 9999,
    "itemScopeIds": [],
    "notificationUnreadCount": 0
  }
]
```

`notificationUnreadCount` は N+1 を避けるため Service 層で 1 クエリ集計（§6.4 参照）。

### 5.2 新規エンドポイント

| メソッド | パス | 用途 |
|---|---|---|
| `GET` | `/api/v1/me/scope-folders/default?scopeType=TEAM` | 未分類フォルダ取得（lazy 生成） |
| `POST` | `/api/v1/me/scope-folders/items/bulk-assign` | 既存所属の一括振り分け |
| `GET` | `/api/v1/me/scope-folders/notifications/summary?scopeType=TEAM` | フォルダ別未読集計（タブバッジ用） |
| `GET` | `/api/v1/notifications?folderId={id}&scopeType=TEAM` | 既存 `/notifications` の folderId フィルタ拡張 |

#### 5.2.1 `GET /api/v1/me/scope-folders/default`

**クエリ**: `scopeType=TEAM | ORGANIZATION`（必須）

**レスポンス**: `ScopeFolderResponse`（§5.1.2 と同形）

**振る舞い**:
- `is_default=TRUE` のフォルダが既に存在 → そのまま返却
- 存在しない → lazy 生成（name=`"未分類"` の i18n キー参照、`color=null`, `icon=null`, `sort_order=9999`）して返却

#### 5.2.2 `POST /api/v1/me/scope-folders/items/bulk-assign`

**リクエスト**:
```json
{
  "folderId": 123,
  "scopeIds": [101, 102, 103],
  "scopeType": "TEAM"
}
```

**振る舞い**:
1. `folderId` の所有確認（IDOR 防止）
2. 各 `scopeId` についてユーザー所属確認（サポータ含む。§6.3 参照）
3. アイテムが他フォルダにあれば移動、未配置なら新規追加
4. `assigned_via=MANUAL` を記録
5. フォルダ上限 20 超過 → `409 SCOPE_FOLDER_LIMIT_EXCEEDED`

**レスポンス**:
```json
{
  "assignedCount": 3,
  "skippedCount": 0,
  "errors": []
}
```

#### 5.2.3 `GET /api/v1/me/scope-folders/notifications/summary`

**クエリ**: `scopeType=TEAM | ORGANIZATION`（必須）

**レスポンス**:
```json
[
  { "folderId": 1, "unreadCount": 5 },
  { "folderId": 2, "unreadCount": 2 },
  { "folderId": 99, "unreadCount": 0 }
]
```

タブバッジ表示専用。総和は `WidgetNotices` の「すべて」タブ件数として再計算可能。

#### 5.2.4 `GET /api/v1/notifications?folderId={id}&scopeType=TEAM`

**既存** `/api/v1/notifications` にクエリ `folderId` と `scopeType` を追加。両方指定時のみフォルダフィルタが有効。

**フィルタロジック**:
1. `folderId` の所有確認（IDOR 防止）
2. そのフォルダの `itemScopeIds` を取得（list of team_id / org_id）
3. 通知の `scope_type` がクエリ `scopeType` と一致 かつ `scope_id` が `itemScopeIds` に含まれるものに絞る
4. ページング・既読フィルタは既存通り

`folderId` 未指定時は従来通り全件（後方互換）。

**実装上の注意（2026-07-30 障害の再発防止）**:
本フィルタはドメインをまたぐ（scopefolder の `ScopeType` → notification の `NotificationScopeType`）。
`NotificationEntity#scopeType` は `@Enumerated(EnumType.STRING)` の enum 属性であるため、
リポジトリの派生クエリへ `scopeType.name()` の **`String` を渡してはならない**（Hibernate のパラメータ束縛で
型不一致となり本エンドポイントが必ず HTTP 500 を返す）。
`NotificationService#toNotificationScopeType` で `NotificationScopeType` へ写像してから渡す。
`ScopeType`（TEAM / ORGANIZATION）は両値とも `NotificationScopeType` に同名定数が存在するため写像は全域。
写像は `switch` ではなく `==` による参照比較で書いている（enum switch が生む javac の合成クラスが
ArchUnit D-1 の新規違反として検出されるため。詳細は規約 §5 の「⚠️ 罠」を参照）。
網羅性は `NotificationScopeTypeMappingTest` が `ScopeType.values()` 全件ループで担保する。
詳細な規約は `backend/BACKEND_CODING_CONVENTION.md` §5「派生クエリの引数型は Entity 属性の型と一致させる」を参照。
実 DB 回帰は `NotificationFolderFilterContractIT` が担保する。

### 6.4 N+1 防止

`getNotificationSummary` は次の単一クエリで集計（JPQL 例、実装時に最適化）:

```sql
SELECT folder.id AS folder_id, COUNT(n.id) AS unread_count
  FROM my_scope_folders folder
  LEFT JOIN my_scope_folder_items item
    ON item.folder_id = folder.id
  LEFT JOIN notifications n
    ON n.scope_id = item.scope_id
   AND n.scope_type = folder.scope_type
   AND n.user_id = :userId
   AND n.read_at IS NULL
 WHERE folder.user_id = :userId
   AND folder.scope_type = :scopeType
   AND folder.deleted_at IS NULL
 GROUP BY folder.id
```

通知テーブル `notifications` への依存はクロスドメイン参照のため、`@Transactional` をスコープフォルダドメインに閉じ、内部では `NotificationQueryRepository` 経由で取得することを推奨（CLAUDE.md 原則 5）。

### 6.5 ドメインイベント

新規イベント（既存命名規約に従う）:

| イベント | 発火源 | リスナー処理 |
|---|---|---|
| `TeamDeletedEvent`（既存 / 新規） | Team ドメイン | 全ユーザーの `my_scope_folder_items` から該当 scope_id を物理削除 |
| `OrganizationDeletedEvent` | Organization ドメイン | 同上 |
| `MembershipEndedEvent` | F00.5 メンバーシップドメイン | 該当ユーザー × scope の `my_scope_folder_items` を物理削除 |

`MembershipEventListener` は scopefolder パッケージ内に置く（CLAUDE.md ドメイン境界原則）。
イベント側（Team / Organization / Membership ドメイン）が既存で発火していない場合は、発火点を実装時に追加する（plan §⑩、⑭参照）。

### 7.2 `ScopeNavDropdown.vue` 詳細

**Props**:
- `scopeType: 'TEAM' | 'ORGANIZATION'`（必須）
- `label: string`（i18n 済み文字列）

**内部状態**:
- `folders`: `useScopeFoldersStore` から取得
- `myScopes`: `scopeType === 'TEAM'` なら `useTeamsStore().myTeams`、ORGANIZATION なら `useOrganizationsStore().myOrganizations`
- `isOpen`: ドロップダウン開閉

**遷移先パスの決定ルール**:

`scopeType` Prop に応じてベースパス `basePath` を切り替える。`ScopeNavDropdown.vue` 内の全リンクは `basePath` を起点とする。**チームドロップダウンから組織のパスへ、組織ドロップダウンからチームのパスへ遷移することは一切ない**。

| `scopeType` | `basePath` |
|---|---|
| `TEAM` | `/teams` |
| `ORGANIZATION` | `/organizations` |

**描画構造**（plan §A の確定動線図に準拠、`basePath` プレースホルダで表記）:

```
[scopeType ▼]
  ├ 📋 すべて（一覧）                  →  {basePath}（タブ=すべて）
  ├ ────────────────
  ├ {color}{icon} フォルダ名 (件数)    →  {basePath}?folder={id}
  ├ ...
  ├ ⚪ 未分類 (件数)                   →  {basePath}?folder=default
  ├ ────────────────
  ├ 直接ジャンプリスト（個別スコープ） →  {basePath}/{id}
  ├ ＋ 新規フォルダ作成                →  モーダル
  └ ⚙ フォルダ管理                     →  {basePath}（タブ=管理タブ）
```

**具体例**:

- `scopeType="TEAM"` のドロップダウンから「すべて」→ `/teams`
- `scopeType="TEAM"` のドロップダウンから「フォルダA(id=123)」→ `/teams?folder=123`
- `scopeType="TEAM"` のドロップダウンから個別チーム(id=456) → `/teams/456`
- `scopeType="ORGANIZATION"` のドロップダウンから「すべて」→ `/organizations`
- `scopeType="ORGANIZATION"` のドロップダウンから「フォルダX(id=789)」→ `/organizations?folder=789`
- `scopeType="ORGANIZATION"` のドロップダウンから個別組織(id=321) → `/organizations/321`

**a11y**:
- `<button aria-haspopup="menu" aria-expanded="…">` でトグル
- `<ul role="menu">` 内 `<li role="menuitem">`
- 矢印キーでナビゲーション、Esc で閉じる

## 9. セキュリティ設計

### 9.1 IDOR 防止

すべての フォルダ系 API で `findByIdAndUserIdAndDeletedAtIsNull(folderId, currentUserId)` を必ず最初に呼ぶ。F15.2 既存実装を流用。
他人のフォルダ ID を指定しても `404 SCOPE_FOLDER_NOT_FOUND` を返す（403 ではない＝存在有無を漏らさない）。

### 9.2 存在漏洩防止

- 404 統一: 他人所有 / 削除済み / 不存在 は同じレスポンス
- `bulk-assign` のエラーレスポンスでも個別 scope_id ごとの存在判定結果は返さず、件数のみ

### 9.3 所属確認（サポータ含む）

§6.3 の優先順位に従い、`MembershipRepository.findByUserIdAndScope` 経由で確認。サポータ関係でも所属確認が通る実装にする。

### 9.4 GDPR・退会時

ユーザー退会時、`my_scope_folders` / `my_scope_folder_items` は **物理削除** する。これらは個人プリファレンスデータであり、統計価値も他ユーザーへの影響もないため、CLAUDE.md 原則 4 の「匿名化保持」対象外（個人設定として全消去）。

実装:
- `UserAnonymizationEventListener` に `MyScopeFolderService.deleteAllByUserId(userId)` 呼び出しを追加（既存 F09.14 等のリスナー同形）

### 9.5 チーム/組織削除時（dangling 防止）

CLAUDE.md 原則 1（クロスドメインFK禁止）に従い、`scope_id` には FK を張らない。代わりにイベント駆動で物理削除。

- `TeamDeletedEvent` → `MembershipEventListener.handleScopeDeleted(TEAM, scopeId)` → `my_scope_folder_items` から該当 scope_id を全削除
- `OrganizationDeletedEvent` → 同上

これにより、削除されたチーム/組織が誰かのフォルダに残り続けることを防ぐ。フロントは削除されたチームを `useTeamsStore` で見つけられないため、表示時に欠落チームをスキップする防御も併用する。

### 9.6 メンバーシップ終了時

`MembershipEndedEvent` → `MembershipEventListener.handleMembershipEnded(userId, scopeType, scopeId)` → 該当ユーザー × scope の items を物理削除。

サポータ関係終了時も同様（F00.5 イベントを発火源として扱う）。

### 9.7 通知フィルタの所有検証

`GET /api/v1/notifications?folderId=` 受領時、`folderId` がリクエストユーザー所有か必ず検証してからクエリ実行。他人 folderId 指定は `404 SCOPE_FOLDER_NOT_FOUND`。

### 9.8 CSRF / XSS

- フォルダ名: VARCHAR(100) + 既存サニタイザ通過 + フロント `v-text` で出力（`v-html` 禁止）
- アイコン名: VARCHAR(40)、PrimeIcons の許可リスト `^pi-[a-z0-9-]+$` で正規表現バリデーション（Service 層）
- 色: `^#[0-9A-Fa-f]{6}$` の正規表現バリデーション（F15.2 既存）
- CSRF: 全 POST / PUT / DELETE は既存の `X-CSRF-Token` ヘッダ検証に乗る

### 9.9 認可（RBAC）

全 API は **本人のみ CRUD**。RBAC 管理者は他人のマイフォルダにアクセスできない（個人設定領域のため）。
特定の例外（GDPR 削除要請・運用管理者の代理削除）が将来必要になった場合は、別エンドポイント `/api/v1/admin/users/{userId}/scope-folders` で audit log 付きで提供することを将来課題に残す（本フェーズ範囲外）。

## 12. 保守性設計

### 12.1 ドメイン境界

- 本機能の全実装は `com.mannschaft.app.scopefolder` パッケージ内に閉じる
- 外部ドメインからの参照は **`MyScopeFolderQueryService` の Public メソッド経由のみ**
- 通知ドメイン（`com.mannschaft.app.notification`）から本ドメインへの依存は片方向（読み取りのみ）。逆参照禁止
- `MembershipEventListener` はイベント受信専用。Membership / Team / Organization ドメインへ直接アクセスしない

### 12.2 `@Transactional` の閉じ込め（CLAUDE.md 原則 5）

- フォルダ系 CRUD: scopefolder ドメインに閉じる
- 通知フィルタ取得: 通知テーブルを参照するため、`@Transactional(readOnly = true)` で読み取り専用にし、書き込みは行わない
- イベントリスナー: `@TransactionalEventListener(phase = AFTER_COMMIT)` で発火元のトランザクションが完了してから処理する（クロスドメインデッドロック回避）

### 12.3 将来拡張余地

以下は将来の拡張余地を示すものであり、**本フェーズでは実装しない**。期待値管理のため明示する。

- `assigned_via` カラムにより、将来「自動振り分けルール（チーム名パターンマッチ / 組織種別自動分類）」を導入可能（現時点で実装予定なし）
- `is_default` フラグの拡張で「お気に入りフォルダ」「ピン留めフォルダ」などのメタデータを追加可能（現時点で実装予定なし）
- N+1 集計は将来的にキャッシュ層導入時にキャッシュ可能（未読件数のみ TTL 60 秒など）。**注意: Valkey 等のキャッシュ層は本プロジェクト全体でまだ導入されておらず、本機能単独で先行導入することはしない**
- フォルダ階層化（ネストフォルダ）は今フェーズ範囲外だが、`parent_folder_id` の追加で実現できる構造を維持（現時点で実装予定なし）
