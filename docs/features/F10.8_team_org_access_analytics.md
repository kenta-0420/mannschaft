## 0. 前提と本設計書の位置づけ

FE には `/teams/[slug]/analytics` と `/organizations/[slug]/analytics` のページ・型・子コンポーネントが既に存在するが、呼び先の BE API が未実装のため、PR #2185 で**チーム側サイドバー導線のみ**を非表示化している。本設計書は、その FE 契約を満たす**ページビュー（PV）計測基盤をゼロから設計する**ものである。

> **既存 FE 実態の裏取り（2026-07-08 コード確認済み・実装時の前提）**:
> - **チーム版 `/teams/[slug]/analytics.vue`** は「準備中」表示のみ（未結線）。`TeamSidebar.vue` の analytics 項目は PR #2185 でコメントアウト済み。
> - **組織版 `/organizations/[slug]/analytics.vue` は既に完全結線済みで稼働中**（`useAnalyticsApi().getAnalytics('organization', slug)` → `GET /api/v1/organizations/{slug}/analytics` を `onMounted` で呼ぶ）。`OrganizationSidebar.vue` の analytics 導線は `requiredRole: 'ADMIN'` で**表示されたまま**であり、BE 未実装のため**現状は取得失敗トーストが出る壊れた状態**である。→ 本 BE 実装完了と同時に組織側は復旧する。チーム側は導線再表示（別 PR）が必要。
> - **FE 呼び出し規約**: `useAnalyticsApi.getAnalytics(scopeType, scopeId, params)` の第 2 引数 `scopeId` には**実際には slug 文字列を渡している**（`buildBase` が `/api/v1/{teams|organizations}/${scopeId}` を組む）。よって BE のパスは §3.2/§3.3 のとおり slug で受ける（名称は `scopeId` だが値は slug）。
> - **組織版ページは表示文字列を日本語直書きしている**（「アクセス解析」「総PV」「ユニーク訪問者」「メンバー閲覧」「ゲスト閲覧」「データエクスポート」・エラートースト）。§7.4 の i18n 化は**新規キー追加だけでなく既存直書きページのリファクタも含む**（実装時に必須・CLAUDE.md i18n ルール）。
> - **エクスポート機能は本設計書の対象外（マスター御裁可 2026-07-08・§10.2-C）**: 組織版ページには `ExportDialog`（`scope-type`/`scope-id` を受け、ジョブ ID ベースのポーリングでエクスポートする既存 UI）が結線されているが、これは PV 計測とは別系統のデータエクスポート機能である。**本 F10.8 のスコープには含めず、第1弾では「データエクスポート」ボタンと `ExportDialog` を FE から非表示にする**（別途 BE エクスポート API が必要。別課題として起票・§1.5／§7.5 に反映）。

方式は「昔の HP のアクセスカウンター」に相当する**枯れた古典方式**を採用する（マスター御裁可済・変更不可）。すなわち:

1. **PV 収集 = FE ビーコン方式**（画面表示時に計測 API へ POST）
2. **ユニーク訪問者/ゲスト識別 = 匿名 cookie**（IP は保存しない・GDPR 配慮）
3. **集計 = 三層アーキ**（生ログ → 日次集計テーブル → 毎日 02:00 ShedLock バッチ → 期間集約サービスが DTO 返却。F10.4 が金型）
4. **段階リリース**: 第 1 弾 = summary + daily + monthly。**topContent（人気コンテンツランキング）は第 2 弾**（第 1 弾では空配列 `[]` を返す）

> **採番・命名の注記（マージ時に必ず再確認）**: 本書に記す Flyway major（V146 想定）・エラーコードのプレフィクスは**執筆時点の現況値**である。実装時にはマージ直前の `origin/main` を再確認し、Flyway major は「全体最大 major + 1」、minor は UTC タイムスタンプで確定すること（`FlywayTimestampNamingGuardTest` が連番採番を機械的に拒否する）。

## 1. 概要

### 1.1 目的

チーム管理者・組織管理者が「自分のチーム/組織のページやコンテンツがどれだけ閲覧されているか」を把握できるようにする。SYSTEM_ADMIN 向けの経営分析（F10.4）とは対象・データソースが完全に分離しており、本機能は**スコープ（チーム/組織）単位のアクセス解析**を提供する。

### 1.2 本ドキュメントのスコープ

| 機能 | 弾 | 説明 |
|------|----|------|
| PV 計測ビーコン受信 | 第1弾 | FE から送られる閲覧イベントを非同期で生ログに記録 |
| サマリ（summary） | 第1弾 | 総 PV / ユニーク訪問者 / メンバー閲覧 / ゲスト閲覧 |
| 日次推移（daily） | 第1弾 | 日ごとの views / uniqueVisitors |
| 月次推移（monthly） | 第1弾 | 月ごとの views / uniqueVisitors |
| 人気コンテンツランキング（topContent） | **第2弾** | コンテンツ別 PV ランキング。**第1弾では空配列 `[]` を返す** |
| 日次集計バッチ | 第1弾 | 毎日 02:00 (JST) に前日分を集計。ShedLock 排他・冪等 |
| パーティション保守バッチ | 第1弾 | 生ログテーブルの翌々月パーティションを毎月自動追加 |

### 1.3 対象ロール（ロール × 操作範囲）

集計取得 API（GET）は「そのスコープのメンバー、または当該スコープの ADMIN」のみが閲覧できる。計測ビーコン（POST）は公開ページからのゲスト計測を許容するため認可が異なる（§3.1 参照）。

| ロール | 集計取得（GET summary/daily/monthly/topContent） | 計測ビーコン（POST /page-views） |
|--------|------|------|
| SYSTEM_ADMIN | 可（全スコープ） | 可 |
| ADMIN（当該スコープ） | 可 | 可 |
| DEPUTY_ADMIN（当該スコープ） | 可 | 可 |
| MEMBER（当該スコープ） | 可 | 可（member として記録） |
| SUPPORTER（当該スコープ） | 可 | 可（member として記録） |
| GUEST（未ログイン） | **不可（401 未認証）** | 可（guest として記録。公開ページ閲覧の計測） |
| 他スコープのメンバー / 非メンバー | **不可（404 で存在秘匿。§3.3）** | 可（当該スコープが計測を受け付ける場合。§3.1） |

### 1.4 対象レベル

- [ ] プラットフォーム全体（SYSTEM_ADMIN 視点）… **F10.4 の領域。本機能では扱わない**
- [x] 組織 (Organization)
- [x] チーム (Team)
- [ ] 個人 (Personal)

### 1.5 第1弾 / 第2弾の線引き

| 項目 | 第1弾（本リリース） | 第2弾 |
|------|--------------------|-------|
| DDL | 生ログ + 日次集計テーブル（両方作成） | 追加テーブルなし（生ログを再集計で対応）またはコンテンツ別日次集計テーブルを追加 |
| API | POST /page-views、GET analytics（summary/daily/monthly 実データ、topContent は `[]`） | topContent に実データを返す |
| バッチ | 日次サマリ集計、パーティション保守 | コンテンツ別集計ステップを追加 |
| エクスポート | **対象外**。組織版ページの「データエクスポート」ボタンは**第1弾で非表示**（マスター御裁可 2026-07-08・§10.2-C）。別課題として起票 | 別 F 番の BE エクスポート API 実装後に再表示 |

> **重要（FE 型契約）**: FE 型は `topContent` を null 不可で定義しているため、第1弾でも**空配列 `[]` を必ず返す**こと（`null` は不可）。

> **エクスポートボタンの扱い（マスター御裁可 2026-07-08・§10.2-C）**: 組織版ページ `organizations/[slug]/analytics.vue` の `ExportDialog` を開く「データエクスポート」ボタン（`showExport` トリガ）は本 F10.8 のスコープ外。BE エクスポート API が未実装のため、**第1弾では当該ボタンと `ExportDialog` を FE から非表示にする**（`v-if="false"` ではなく削除もしくはコメントアウト。別課題起票後に再結線）。チーム版を組織版のミラーとして本実装する際も、エクスポートボタンは含めない。

## 2. 受け入れ条件（テスト可能）

`/試練` が red テストに落とせる粒度で列挙する。誰が・何をしたら・どうなるか。

### 2.1 計測ビーコン（POST）

- **AC-01**: 認証済みメンバーが `POST /api/v1/page-views` に有効な body（scope=TEAM, scopeId, contentType, contentId, url, title）を送ると **202 Accepted** が返り、非同期処理完了後に生ログ `page_view_logs` に 1 件（`user_id` セット・`visitor_id` は匿名 cookie 値）記録される。
- **AC-02**: 未ログインユーザーが公開ページから同 POST を送ると **202 Accepted** が返り、生ログに 1 件（`user_id = NULL`・`visitor_id` = 匿名 cookie 値）記録される（ゲスト計測）。
- **AC-03**: 匿名 cookie（`mnsft_vid`）が未発行の未ログインリクエストに対しては、レスポンスで新規 UUID を採番した cookie を Set-Cookie する（属性は §7.2 準拠）。
- **AC-04**: `scope` が `TEAM`/`ORGANIZATION` 以外、または `contentType` が許容外（`ARTICLE`/`ACTIVITY`/`PAGE`/`TEAM` 以外）の場合 **400** を返す。
- **AC-05**: `scopeId` が存在しないスコープを指すビーコンは、生ログに記録せず**握りつぶし 202 を返す**（存在秘匿。�ログ肥大攻撃を避けるため非同期側で破棄。§3.1 の設計判断参照）。
- **AC-06**: 同一 `visitor_id` から同一 `scope+contentId` へ短時間（同一日）に複数回 POST しても生ログには複数行入るが、日次集計後の `uniqueVisitors` は **1** と数える（AC-13）。
- **AC-07**: ビーコン POST がレート制限（§7.3）を超過した場合 **429** を返す（`AbstractRateLimitFilter` 標準応答。特定エラーコード body は要求しない。§6）。
- **AC-22**: `url` が絶対 URL（`http://`・`https://`・`//`・`javascript:` 等）や `/` 始まりでない値の場合 **400**（`TEAMANALYTICS_003`）。相対パス（`/teams/...`）のみ 202（§3.1 入力バリデーション）。
- **AC-23**: `title` に改行・制御文字を含む body を送っても、生ログ `title` は制御文字除去・255 文字切り詰め済みで保存される（ログ注入防止。観測点 = `page_view_logs.title`）。

### 2.2 集計取得（GET）

- **AC-08**: 当該チームのメンバーが `GET /api/v1/teams/{slug}/analytics` を叩くと **200** と `{data: AnalyticsResponse}` が返り、全フィールド（summary/daily/monthly/topContent）が**非 null**である。
- **AC-09**: 非メンバー（別チームのメンバーを含む）が他チームの `GET /api/v1/teams/{slug}/analytics` を叩くと **404**（存在秘匿。403 ではない。§3.3）。
- **AC-10**: 未ログインで `GET .../analytics` を叩くと **401**。
- **AC-11**: `dateFrom > dateTo` の場合 **400**。
- **AC-12**: `dateFrom`/`dateTo` 双方省略時は全期間集計を返す（200）。
- **AC-13**: 日次バッチ実行後、`summary.totalViews` = 期間内 `page_view_logs` の件数、`summary.uniqueVisitors` = 期間内のユニーク訪問者数（`COUNT(DISTINCT COALESCE(CONCAT('u:',user_id), CONCAT('v:',visitor_id)))`・§3.4）、`memberViews` = `user_id IS NOT NULL` の PV 数、`guestViews` = `user_id IS NULL` の PV 数、が一致する。
- **AC-14**: ゲスト（未ログイン）が同一匿名 cookie で同日に 3 回閲覧した場合、`uniqueVisitors` への寄与は **1**。
- **AC-15**: `topContent` は**第1弾では常に空配列 `[]`**（実装漏れではなく仕様）。
- **AC-16**: `daily[].date` は `YYYY-MM-DD`、`monthly[].month` は `YYYY-MM` 形式で返る。
- **AC-17**: 組織版 `GET /api/v1/organizations/{slug}/analytics` もチーム版と同一構造・同一権限規則で動作する。

### 2.3 バッチ・境界

- **AC-18**: 日次集計バッチを同一日付で 2 回実行しても結果が重複しない（冪等。`deleteByDate` → 再 INSERT）。
- **AC-19**: バックフィル用 `aggregateForDate(LocalDate)` を任意過去日付で呼ぶと、その日の日次集計行が再計算される。
- **AC-20**: 生ログに 1 件も無い日を集計しても、日次集計行は作られない（または 0 行で作られる）ため `summary` は 0 を返す（例外にしない）。
- **AC-21**: パーティション保守バッチ実行後、生ログテーブルに翌々月のパーティションが存在する（`p_future` の手前に月次パーティションが追加される）。

### 2.4 観測点（検証可能性の担保）

各 AC を実機 E2E / 契約テスト / 統合テストで観測する際の観測点を明示する（`/試練` の red テストが「どこを見れば真偽が確定するか」を定義）。

| 観測対象 | 観測手段 |
|---------|---------|
| POST の HTTP ステータス（202/400/429） | API 契約テスト（`@WebMvcTest` / `MockMvc`）・実機 curl |
| 非同期記録の結果（生ログ 1 行・`user_id`/`visitor_id`/`title`） | 統合テスト（Testcontainers MySQL）で `page_view_logs` を直接 SELECT。非同期のため `Awaitility` 等で完了待機 |
| Set-Cookie（`mnsft_vid` 新規採番） | レスポンスヘッダー検証 |
| 日次集計の正しさ（AC-13/14/18/19/20） | **`@BatchEndpoint(name="analytics-pageview-daily-aggregation")` を手動起動**（既存 F10.4 バッチと同じ手動トリガ機構）→ `page_view_daily_stats` を SELECT して期待値と照合。冪等は 2 回起動して行数不変を確認 |
| GET のステータス/ボディ（AC-08〜12/15〜17） | API 契約テスト（メンバー/非メンバー/未認証の 3 ケースを別ユーザーで）。全フィールド非 null を JSON パスで検証 |
| パーティション保守（AC-21） | `@BatchEndpoint(name="analytics-pageview-partition-maintenance")` 手動起動 → `information_schema.PARTITIONS` を SELECT して翌々月パーティション存在を確認 |

> **バッチの手動起動が試験の要**: 日次集計・パーティション保守はいずれも `@BatchEndpoint` を付与し、cron を待たずに任意タイミングで起動できる（手本 F10.4 `analytics-daily-aggregation`）。これにより E2E で「ビーコン投入 → バッチ手動起動 → GET で集計反映を確認」の一気通貫が JST 02:00 を待たずに検証できる。

> **統合テストの非同期問題（DiscardPolicy + Awaitility の落とし穴）**: `page-view-pool` は `DiscardPolicy` で飽和時にタスクを捨てる。統合テスト（`@SpringBootTest`）で `Awaitility` を使う際、タスクが Discard されても `Awaitility` はタイムアウトするまで waiting を続け最終的に`ConditionTimeoutException`を投げる（偽 red ではなくタイムアウトで失敗）一方、キューに入ったまま処理前にタイムアウトする偽成功もありうる。**テスト時は `@TestConfiguration` で `page-view-pool` Bean を `SyncTaskExecutor`（Spring `org.springframework.core.task.SyncTaskExecutor`）に差し替える**ことで `@Async` を同期実行にし、Awaitility 不要・DiscardPolicy 不要・決定論的な動作にする（既存の `@TestConfiguration` bean override パターンを踏襲）。`@WebMvcTest`（Contract テスト）では `page-view-pool` を持つ `AsyncConfig` ごとモック化するか、テスト専用の `@EnableAsync` を OFF にする。

## 3. API 契約

### 3.0 共通

- レスポンスは `ApiResponse.of(...)` により `{data: ...}` でラップする（既存規約）。
- パスは**数値 ID でなく slug（String）**。既存規約に倣い `@RequestMapping("/api/v1/teams/{slug}")` 配下で `Long teamId = teamService.resolveTeamId(slug)`（手本 `TeamController` / `TeamShiftSettingsController`）。組織版は `organizationService.resolveOrgId(slug)` を用いる（**メソッド名確定**: `resolveOrgId(String)`・コード確認済み）。
- 認可拒否は本機能では「非メンバー/存在しない slug をまとめて **404**（`TEAMANALYTICS_001`）で秘匿」する（§3.2 の EventScopeAccessGuard 差異注記・§3.3 の設計判断参照）。運用上の権限不足のみ将来 403（`TEAMANALYTICS_005`）。

### 3.1 計測ビーコン `POST /api/v1/page-views`

閲覧イベントを受信し、**非同期**で生ログに記録する。既存の非同期イベント記録基盤（`AuditLogEventListener`）の思想を踏襲するが、本 POST はトランザクション外のため **`@EventListener` + `@Async("page-view-pool")`**（PV 専用プール・§5.1）を用いる（`@TransactionalEventListener(AFTER_COMMIT)` はトランザクション境界が無いと発火しないため使わない）。

**認可**: 認証は必須としない（公開ページのゲスト計測を許可するため）。ただし濫用防止のためレート制限（§7.3）と scope 実在チェックを行う。

> **SecurityConfig への `permitAll` 登録が必須（E2E 耐性）**: 未認証を許容する POST は `SecurityConfig.java` の `http.authorizeHttpRequests` に明示的に登録しないと Spring Security がデフォルト `authenticated()` で 401 を返す。実装時に以下を追加すること（既存の `permitAll()` ブロックに倣う）:
> ```java
> .requestMatchers(HttpMethod.POST, "/api/v1/page-views").permitAll()
> ```
> これが無いと AC-02（未ログインゲスト計測が 202 になる）が実機 E2E で必ず 401 になる。チェックリストに入れること。

> **scope 実在チェックの実装可能性（敵対レビュー反映）**: 非同期リスナー内で `scope_type`/`scope_id` の実在を確認する（存在しなければ破棄。§3.1 設計判断）。実装は **軽量な存在確認**に留める — team は `TeamRepository.existsById(scopeId)`（または `deleted_at IS NULL` を含む `existsActive` 相当）、org は `OrganizationRepository` 同等。**リスナーはドメインをまたぐ read-only 確認のみで、書き込みは自ドメイン `page_view_logs` に閉じる**（CLAUDE.md 原則 5「@Transactional はドメイン内に閉じる」を維持。team/org の実在確認は「読み取り専用のクロスドメイン参照」で FK も張らないため境界違反にならない）。高頻度化した場合は実在チェック結果を短 TTL でキャッシュしてよい（実装時判断）。

**リクエストボディ**:
```json
{
  "scope": "TEAM",
  "scopeId": 123,
  "contentType": "ARTICLE",
  "contentId": 4567,
  "url": "/teams/my-team/articles/4567",
  "title": "春合宿のお知らせ"
}
```

| フィールド | 型 | 必須 | 説明 |
|-----------|----|----|------|
| `scope` | ENUM(`TEAM`,`ORGANIZATION`) | YES | 閲覧対象のスコープ種別 |
| `scopeId` | number(Long) | YES | チーム/組織の**数値 ID**（slug ではなく ID を送る。FE は `useTeamStore().currentTeam.id` 等で保持する解決済み ID を使う） |
| `contentType` | ENUM(`ARTICLE`,`ACTIVITY`,`PAGE`,`TEAM`) | YES | 閲覧対象の種類 |
| `contentId` | number(Long) | YES | 閲覧対象の ID（`PAGE` 等 ID 無し時は **0 固定**・§10.1 確定） |
| `url` | string | YES | アプリ内相対パス（最大 512 文字。topContent の NuxtLink :to に使うため**相対パス限定**） |
| `title` | string | YES | 表示タイトル（最大 255 文字） |

> **FE ビーコン実装での `scopeId`（数値 ID）取得方法（E2E 耐性）**: ビーコンの `scopeId` はスコープの**数値 ID**（`useAnalyticsApi.getAnalytics` が受け取る slug とは別物）。FE 実装時は `useTeamStore().currentTeam.id`（team の場合）・`useOrganizationStore().currentOrg.id`（org の場合）等、すでにストアに保持されている数値 ID を参照すること。slug から数値 ID を取得するために GET /api/v1/teams/{slug} を余分に叩く実装は不要（ページロード済みなら既にストアにある）。実装時に数値 ID の取得元を確認してコメントに明記すること（「どこから ID を取るか」が未定義だと足軽が詰まる箇所）。

> **入力バリデーション（ログ注入・XSS・オープンリダイレクト防止）— 敵対レビュー反映**:
> - `url` は **`/` で始まるアプリ内相対パスのみ許可**（正規表現例 `^/[A-Za-z0-9/_\-?=&.%]{0,511}$`）。`http(s)://`・`//`（プロトコル相対）・`javascript:` 等の絶対 URL/スキームは **400 で拒否**。topContent（第2弾）で `url` を NuxtLink `:to` にそのまま渡すため、外部 URL 混入はオープンリダイレクト源になる。
> - `title` は最大長で切り詰め、**制御文字・改行を除去**（ログ注入 = 生ログ SQL に `title` を混ぜて監査ログを偽装する攻撃の防止）。DB は JPA パラメータバインディングのため SQL インジェクションは起きないが、`title` は将来 topContent で FE 表示されるため**保存時に生値を保持し、表示時に FE が既存 DOMPurify/エスケープ方針で無害化**する（`docs/security/05` インジェクション横断ルール準拠）。
> - `contentType`/`scope` は enum バインドで ENUM 外は 400（`TEAMANALYTICS_003`）。`scopeId`/`contentId` は正の整数のみ。
> - **未認証エンドポイントである点の再強調**: これらのバリデーションは Controller の同期経路（202 を返す前）で行い、不正 body は非同期に回さず即 400 で弾く（非同期側に汚染データを流さない）。

**処理**:
1. Controller で **匿名 cookie（`mnsft_vid`）を解決**。未発行なら UUID を採番し Set-Cookie（属性は §7.2）。
2. リクエストは軽量 DTO に詰め、`ApplicationEventPublisher` で `PageViewRecordedEvent` を publish して即 **202 Accepted** を返す（ボディなし、または最小 ack）。
3. `@Async("page-view-pool")` のリスナー（PV 専用プール・§5.1）が受信し、scope 実在チェック（存在しなければ破棄）→ `page_view_logs` へ INSERT。SPA 遷移も毎回 POST されるので、各遷移が 1 イベント。

**レスポンス**: **202 Accepted**（ボディなし）。同期処理は cookie 解決とイベント publish のみで、DB 書き込みは非同期。

**エラー**: 400（body 不正・ENUM 不正）、429（レート制限超過）。

> **設計判断（ゲスト計測の許可方式）**: ビーコン POST を認証必須にすると公開ページ（未ログイン閲覧）を計測できず、アクセスカウンターの目的を満たせない。よって POST は**未認証を許容**する。代償として (a) scope 実在チェックで存在しない scope へのログ注入を破棄、(b) レート制限で濫用を抑止、(c) 生ログの `visitor_id` は個人特定不能な匿名 UUID のみ・IP は保存しない、で守る。集計取得（GET）側は厳格にメンバー限定とし、**書き込みは緩め・読み取りは厳格**の非対称設計とする。

> **設計判断（存在しない scope の握りつぶし）**: AC-05 は「対処療法の握りつぶし」ではなく、**未認証エンドポイントに対する意図的なログ注入防御**である。攻撃者が任意 scopeId を送ってログを膨らませる／他 scope に成りすまして計測を汚染することを防ぐため、非同期側で scope 実在を確認し、実在しないものは記録しない。クライアントには 202 を返して探索（どの scopeId が実在するか）の手がかりを与えない。

### 3.3 集計取得（組織）`GET /api/v1/organizations/{slug}/analytics`

チーム版と**同一構造・同一クエリ・同一レスポンス**。認可のみ「当該組織のメンバー/ADMIN（+ SYSTEM_ADMIN）」に読み替える。`OrganizationService.resolveOrgId(slug)` でスコープ ID を解決する（**メソッド名確定**: `resolveOrganizationId` ではなく `resolveOrgId(String slug)`。コード確認済み。チーム版は `TeamService.resolveTeamId(String slug)`）。

> **設計判断（IDOR 隠蔽は 404）**: 非メンバーが他スコープの analytics を叩いた場合、403（＝そのスコープは存在するが権限が無い、を露呈）ではなく **404** を返し、集計データの存在（＝そのスコープが計測対象として稼働している事実）を秘匿する。既存 `TEAM_001 = NOT_FOUND` 前例に一致。ただし「未認証」は横断的に 401 とする（認証すれば結果が変わるため）。
>
> **補足（スコープ実在そのものは公開情報である点の整理）**: チーム/組織の存在自体は公開ページ（`/teams/{slug}` 等）で既に露呈しており、404 秘匿の主目的は「スコープの存在」ではなく「**そのスコープの解析データにアクセスできる立場か否か**（＝メンバーシップの有無の探索）を漏らさない」ことにある。403 を返すと「実在する非メンバースコープ」と「そもそも存在しないスコープ」を攻撃者が区別できてしまうため、両者を 404 に統一して観測を潰す。

### 3.4 ユニーク訪問者/メンバー識別の規則

- **member**: `user_id IS NOT NULL`（ログイン利用者。userId 単位）。
- **guest**: `user_id IS NULL`（未ログイン。匿名 cookie `visitor_id` 単位）。
- **uniqueVisitors の重複除去キー（設計確定・§10.1 で確定）**: ログイン利用者は `user_id`、未ログインは `visitor_id`。同一ユーザーがログイン前後で別カウントにならないよう、集計時に「`user_id` があれば `user_id`、無ければ `visitor_id`」を DISTINCT キーとする。**確定 SQL 表現**: `COUNT(DISTINCT COALESCE(CONCAT('u:', user_id), CONCAT('v:', visitor_id)))`。
  - **型キャスト注意**: `user_id` は `BIGINT`、`visitor_id` は `CHAR(36)` で型が異なるため素の `COALESCE(user_id, visitor_id)` は暗黙変換の曖昧さがある。**プレフィクス付き文字列連結（`u:`/`v:`）で名前空間を分離**することで、(a) 型を明示的に文字列へ揃え、(b) 万一 `user_id` の数値と `visitor_id` の UUID が偶然一致する事故も防ぐ。この式を日次バッチの `unique_visitors` 算出と、月次/期間の生ログ直接集計（§4.3）の**両方で共通に使う**。
- **IP アドレスは一切保存しない**（GDPR 配慮）。

**主キー**: `PRIMARY KEY (id, viewed_at)`
（MySQL のレンジパーティションはパーティションキーを主キー/一意キーに含める必要があるため、`audit_logs` と同様に `(id, viewed_at)` の複合 PK とする。）

**INDEX**:
- `idx_pvl_scope_viewed (scope_type, scope_id, viewed_at)` — 日次集計バッチのスコープ×日付スキャン用
- `idx_pvl_scope_visitor (scope_type, scope_id, visitor_id)` — ユニーク訪問者集計用
- `idx_pvl_scope_content (scope_type, scope_id, content_id)` — 第2弾 topContent 集計用（先行して張っておく）

**パーティション**（月次レンジ・`audit_logs` V64.001 の書式に倣う）:
```sql
PARTITION BY RANGE (TO_DAYS(viewed_at)) (
  PARTITION p2026_07 VALUES LESS THAN (TO_DAYS('2026-08-01')),
  PARTITION p2026_08 VALUES LESS THAN (TO_DAYS('2026-09-01')),
  -- … 数年分を先行作成（実装時に audit_logs の実レンジ幅に合わせる）…
  PARTITION p_future  VALUES LESS THAN MAXVALUE
);
```

> **パーティション保守**: 翌々月分のパーティションを毎月自動追加するバッチ（§5.4）を用意する。手本は `auth-audit-log-partition-maintenance`（`AuditLogPartitionMaintenanceBatchService.addNextPartitions`、毎月 1 日 01:00 JST）。`p_future` を再オーガナイズして月次パーティションを挿入する既存ロジックを踏襲する。

> **保持・アーカイブ**: 生ログは肥大するため保持期間（例: 13 ヶ月）を設け、古いパーティションを丸ごと `DROP PARTITION` する運用（`audit_logs` のアーカイブ手本 `auth-audit-log-archive-monthly` に倣う）。日次/月次集計テーブルには恒久データが残るため、生ログ削除後も集計値は保持される。保持期間の具体値は要裁可（§9・§10 で 13 ヶ月に確定）。

**集計方針**:
- `monthly` は本テーブルを月単位で `GROUP BY YEAR(date), MONTH(date)` して集約（別テーブルを作らない。行数が小さいためアプリ層集約で十分。F10.4 の granularity 集約と同思想）。
- **月次ユニーク訪問者の算出（設計確定・§10.1 を確定）**: `unique_visitors` は日次でしか保持しないため、月次・期間サマリのユニーク訪問者を日次値の単純合算で出すと重複カウントになる。**確定方針**: 対象期間が**生ログ保持期間（13 ヶ月・§9）内**なら、その期間の `page_view_logs` から `COUNT(DISTINCT COALESCE(...))` で**直接 DISTINCT 集計して正確値**を返す。保持期間を跨ぐ/超える期間（アーカイブ済みパーティションを含む）は日次ユニークの合算（重複ありの上振れ近似）にフォールバックし、レスポンスのメタ（例 `uniqueVisitorsApproximate: true`。FE 型に無いため第1弾は内部ログのみ・FE には返さない）で扱う。第1弾の GET は全期間でも 13 ヶ月保持のため、実運用上ほぼ常に正確値になる。生ログ直接集計は `idx_pvl_scope_viewed` / `idx_pvl_scope_visitor` を使う（フルスキャンにならないようスコープ×期間で絞る）。

### 4.4 ER 図（テキスト表現）

```
page_view_logs (id, viewed_at) [月次パーティション, UuidV7]
   ↑ 毎日02:00 日次集計バッチ (scope_type, scope_id, date で GROUP BY)
page_view_daily_stats (scope_type, scope_id, date) [UNIQUE, UuidV7]
   ↑ 期間集約サービスが dateFrom〜dateTo を読み、summary/daily を構築
   ↑ monthly は date を月集約 / topContent(第2弾) は page_view_logs を content_id 集計
※ users / teams / organizations への FK は張らない（クロスドメイン FK 禁止・アプリ層保証）
```

### 4.5 UUIDv7 / テナント原則の遵守

- `page_view_logs` は `UuidV7Entity` を継承（`@UuidGenerator(style=TIME)`、`BINARY(16)`）。時刻順ソート可能でインデックス効率が高く、高頻度 INSERT でも複数ノードで独立発番できる（原則 6）。
- 集計テーブルのリポジトリは `scope_id` で絞り込むが、`organization_id` 列を直接持たないため `AbstractTenantAwareRepository` の適用は限定的。`scope_type`/`scope_id` の複合で絞り込む専用メソッドを定義する（`AbstractTenantAwareRepository` を継承するかは実装時判断。テナントスコープの手本として参照はする）。

## 5. ビジネスロジック

### 5.1 非同期ビーコン記録

```
1. POST /api/v1/page-views 受信（Controller）
2. 匿名 cookie mnsft_vid を解決（未発行なら UUID 採番 + Set-Cookie）
3. 軽量イベント PageViewRecordedEvent を ApplicationEventPublisher.publishEvent
   （手本: AuditLogEventListener の入口。ただし本 POST はトランザクション外なので
    AFTER_COMMIT ではなく即時 publish。`@Async("page-view-pool")`〔PV 専用プール・§5.1-6〕で非同期実行。
    ※ `@EventListener`〔非トランザクション〕を使う。`@TransactionalEventListener(AFTER_COMMIT)` は
    トランザクション境界が無いと発火しないため本経路では使わない点に注意）
4. 202 Accepted を即返す（DB 書き込みを待たない）
5. `@Async("page-view-pool")` リスナー:
   a. scope_type/scope_id の実在チェック（team/organization service 経由）
      → 実在しなければ破棄（ログ注入防御。§3.1）
   b. page_view_logs へ INSERT
6. Executor 飽和時の挙動（設計確定・§10.1 で確定）:
   既存 `event-pool`（`config.AsyncConfig` の `@Bean("event-pool")`・確認済み）は
   corePoolSize=2 / maxPoolSize=5 / queueCapacity=100 / RejectedExecutionHandler=**AbortPolicy（既定）**。
   このプールは監査ログ（`AuditLogEventListener` AFTER_COMMIT）と共用されており、PV バースト時に
   AbortPolicy で reject されると監査ログ記録まで巻き添えで失敗するリスクがある。
   → **PV 専用 Executor `page-view-pool` を新設する（§10.1 で (b) を確定採用）**。
     RejectedExecutionHandler は **`DiscardPolicy`**（または `DiscardOldestPolicy`）とし、飽和時は
     静かに PV を捨てる（PV は欠損許容・§7.5。監査ログの信頼性を PV バーストから隔離するのが主目的）。
     捨てた件数は Micrometer カウンタ（例 `mannschaft.pageview.discarded`）で可視化し「静かな無効化にしない」
     （レートリミット fail-open の可視化方針 `docs/security/06 §4.3.1` に倣う）。

     【実装必須】`backend/.../config/AsyncConfig.java` に `@Bean("page-view-pool")` を追加する。
     既存 `withdrawal-pool` / `purge-pool` の追加パターンをそのまま踏襲する。
     サイジング例: corePoolSize=2 / maxPoolSize=8 / queueCapacity=500 / DiscardPolicy。
     （500 キューは SPA ユーザー 500 人同時閲覧分のバースト吸収を想定。運用数値は実装時調整可）
     テスト用途では `@TestConfiguration` で `page-view-pool` を `SyncTaskExecutor`（または
     `ImmediateTaskExecutor`）に Bean 置換すること。`DiscardPolicy` + `Awaitility` の組み合わせでは
     「タスクが捨てられた」ことを `Awaitility` が区別できず偽 green になりうる（§2.4 注記参照）。
```

### 5.2 日次集計バッチ

手本は `DailyAggregationBatchService`（F10.4、`analytics-daily-aggregation`）。

```
1. @Scheduled(cron="0 0 2 * * *", zone="Asia/Tokyo") 毎日 AM 2:00 (JST)
2. @SchedulerLock(name="pageViewDailyAggregation", lockAtMostFor="30m") で ShedLock 排他
3. @BatchEndpoint(name="analytics-pageview-daily-aggregation", ...) を付与（手動起動可）
4. 対象: 前日（date = yesterday (JST)）
5. 冪等: aggregateForDate(LocalDate date) を呼ぶ
   a. deleteByDate 相当（page_view_daily_stats の当日該当行を scope 横断で削除）
   b. page_view_logs を (scope_type, scope_id) で GROUP BY し当日集計を再 INSERT:
      - total_views  = COUNT(*)
      - unique_visitors = COUNT(DISTINCT COALESCE(CONCAT('u:', user_id), CONCAT('v:', visitor_id)))
                          （§3.4 確定式。プレフィクスで型を揃え名前空間衝突を防ぐ）
      - member_views = COUNT(*) WHERE user_id IS NOT NULL
      - guest_views  = COUNT(*) WHERE user_id IS NULL
6. バックフィル: aggregateForDate(LocalDate) を public にし、任意過去日の再集計に使う（AC-19）
7. エラー時: batch_job_logs に ERROR 記録（F10.1/F10.4 と同様の運用）
```

### 5.3 期間集約サービス（GET のデータ源）

```
1. TeamService.resolveTeamId(slug) / OrganizationService.resolveOrgId(slug) で scope_id を得る
2. 認可 Guard（EventScopeAccessGuard 同型）で「スコープ帰属 + メンバーシップ」検証
   → 非メンバーは 404、未認証は 401
3. page_view_daily_stats を (scope_type, scope_id, date BETWEEN dateFrom AND dateTo) で取得
   （dateFrom/dateTo 省略時は全期間）
4. summary と monthly.uniqueVisitors の算出は下記「§5.3 uniqueVisitors 算出フロー」に従う
5. daily = 取得行をそのまま DailyPageView[] にマップ
6. monthly = daily を年月で GROUP BY 集約（views/memberViews/guestViews は日次合算で正確。
   uniqueVisitors のみ下記フローで差し替え）
7. topContent = 第1弾は空配列 []（第2弾で page_view_logs から content_id 集計）
8. ApiResponse.of(AnalyticsResponse) で返す（全フィールド非 null）
```

> **§5.3 uniqueVisitors 算出フロー（具体的実装手順・E2E 耐性）**:
>
> `summary.uniqueVisitors` と `monthly[].uniqueVisitors` は日次合算では重複カウントになる（§4.3）。
> 実装は**2 クエリ構成**とする:
>
> (a) 主クエリ: `page_view_daily_stats` で日次 daily 配列を全取得（views/member/guest は正確値）
>
> (b) unique 補正クエリ: 対象期間が生ログ保持期間内（13 ヶ月）かどうかを判定し:
>   - **保持期間内 → `page_view_logs` に追加 SELECT**:
>     ```sql
>     -- summary.uniqueVisitors（全期間 / 指定期間）
>     SELECT COUNT(DISTINCT COALESCE(CONCAT('u:', user_id), CONCAT('v:', visitor_id)))
>     FROM page_view_logs
>     WHERE scope_type = ? AND scope_id = ?
>       AND viewed_at BETWEEN ? AND ?
>     -- idx_pvl_scope_viewed を使用（scope_type, scope_id, viewed_at の複合）
>
>     -- monthly.uniqueVisitors（月ごとに GROUP BY）
>     SELECT YEAR(viewed_at), MONTH(viewed_at),
>            COUNT(DISTINCT COALESCE(CONCAT('u:', user_id), CONCAT('v:', visitor_id)))
>     FROM page_view_logs
>     WHERE scope_type = ? AND scope_id = ?
>       AND viewed_at BETWEEN ? AND ?
>     GROUP BY YEAR(viewed_at), MONTH(viewed_at)
>     ```
>   - **保持期間外（アーカイブ済み）→ 日次ユニークの合算（近似値・重複あり）**をそのまま使用。
>     第1弾の運用上、全期間指定でも 13 ヶ月以内に収まるためほぼ常に (a) ルートを通る。
>
> 足軽はこの 2 クエリ構成を Service メソッドとして実装し、Controller が組み合わせて DTO を構築する。
> `page_view_logs` が空（ビーコン未投入）の場合でも `COUNT(DISTINCT ...)` は 0 を返して例外にならない（AC-20）。

### 5.5 計測セマンティクスの確定（SPA 遷移・日付境界・二重カウント）

以下は敵対的レビューで露見した「観測の曖昧さ」を潰すための確定事項。

- **SPA ページ遷移＝1 PV（意図的仕様）**: Nuxt SPA では画面遷移ごとに FE が 1 ビーコンを送るため、1 セッションで複数ページを回ると複数 PV になる（＝従来のアクセスカウンター相当で正しい挙動）。同一ページを FE が再マウント（タブ復帰・`keep-alive` 再活性）した場合の二重送出を避けるため、**FE 側でビーコンは「ルート確定（`router.afterEach` または `onMounted`）1 回につき 1 送出」に限定**し、同一 URL への連続再送は行わない（FE 実装契約。二重カウントの主因を FE で断つ）。BE 側は受け取ったビーコンを素直に 1 行記録する（BE で重複排除はしない＝生ログは事実の記録に徹する）。`totalViews` は生ログ件数そのものなので、二重送出があれば水増しになる点を FE 契約で防ぐ。
- **日付・時間帯は JST 固定**: `viewed_at` は `DATETIME`（タイムゾーン無し）で JST の壁時計を保存する前提。日次集計バッチは前日（`yesterday` = `LocalDate.now(Asia/Tokyo).minusDays(1)`）を対象とし、`daily[].date` / `page_view_daily_stats.date` はすべて **JST の日付**で確定する（`@Scheduled(zone="Asia/Tokyo")`）。集計 SQL の日付境界も JST 前提（サーバー TZ が UTC の場合は `CONVERT_TZ` ではなく、格納時に JST で入れる方針に統一。手本 `analytics_daily_*` の日付運用に合わせる）。月次は `daily.date` を `YEAR()/MONTH()`（JST 日付）で集約するため境界も JST で一貫。
- **ダッシュボード PV ウィジェットとの連携（将来の消費者・記録）**: `TeamDashboardResponse.teamPageViews`（`Map<String,Object>`）は現在 `DashboardService` で `teamPageViews(null)` とハードコードされている（確認済み）。本機能の日次集計テーブルが埋まれば、ダッシュボードの team PV ウィジェットに要約（例: 直近 7 日の総 PV）を供給できる。**第1弾ではダッシュボード結線は行わない**（`teamPageViews(null)` のまま）が、期間集約サービスを再利用してウィジェット供給する導線を**第2弾以降の拡張点として記録**する（`project_dashboard_personal_panel_widget_wiring_parity` の結線パリティ規約に従い、供給時は KEYS/linkTo 登録の整合を取る）。

## 6. エラーコード

ドメイン別 `ErrorCode` enum（手本 `AnalyticsErrorCode`。既存プレフィクスは `ANALYTICS_001`〜`ANALYTICS_008`・確認済み）に倣い、新設 enum `TeamOrgAnalyticsErrorCode`（仮）を定義する。プレフィクスは既存 `ANALYTICS_` と衝突しない **`TEAMANALYTICS_xxx`**（仮）とする。HTTP マッピングは `GlobalExceptionHandler` の `ERROR_CODE_STATUS_MAP`（`Map.ofEntries(...)`。例 `PUBLIC_002 → 429`・`COMMON_000 → 401`・`VISIBILITY_001 → 403`・確認済み）に追記する。

> **採番はマージ時再確認**: プレフィクス・連番・Severity は執筆時点の提案。実装時に既存 `ErrorCode` 群と衝突しないか確認して確定する。

| コード（仮） | HTTP | Severity | 条件 |
|-------------|------|----------|------|
| `TEAMANALYTICS_001` | 404 | WARN | スコープが存在しない / 非メンバーによる存在秘匿（IDOR 隠蔽。GET 集計取得） |
| `TEAMANALYTICS_002` | 400 | WARN | `dateFrom > dateTo` / 日付形式不正（GET 集計取得） |
| `TEAMANALYTICS_003` | 400 | WARN | 計測ビーコンの body 不正（scope/contentType が ENUM 外・必須欠落。POST） |
| `TEAMANALYTICS_005` | 403 | WARN | （将来）スコープは特定できるが権限が明確に不足する運用上のケース |

> **429 はエラーコードで返さない（訂正）**: 計測ビーコンのレート制限は `AbstractRateLimitFilter`（Controller より前段のフィルタ層）で処理され、応答は**プロジェクト標準形**（ボディ `{"error":"Too many requests"}` + `Retry-After` + `X-RateLimit-*`）で返る（§7.3）。したがって旧案の `TEAMANALYTICS_004`（429）は**本 enum から除外**する（フィルタ層 429 は `ErrorCode`／`GlobalExceptionHandler` を経由しないため、enum に定義しても発火しない）。「レート超過」は AC-07 で「429 が返る」ことのみを検証し、特定のエラーコード body は要求しない。

※ 401（未認証）は既存の認証フィルタ層で横断的に処理されるため本 enum には含めない。

## 7. Flyway / セキュリティ / i18n / 非機能

### 7.1 Flyway マイグレーション

| ファイル名（想定） | 内容 |
|------------------|------|
| `V146.{yyyyMMddHHmmss}__create_page_view_logs.sql` | `page_view_logs`（UuidV7・複合 PK・月次パーティション・INDEX） |
| `V146.{yyyyMMddHHmmss}__create_page_view_daily_stats.sql` | `page_view_daily_stats`（UNIQUE(scope_type,scope_id,date)） |

- **major はマージ時に `origin/main` 全体の最大 major + 1 で確定**（2026-07-08 時点で最新は **V145**〔`V145.20260707153053`〕・確認済み → **V146 想定**。ただし並行 PR で major が進む可能性があるため必ず再確認。手本 `FlywayTimestampNamingGuardTest` が連番採番を拒否）。
- **minor は UTC タイムスタンプ必須**（`date -u '+%Y%m%d%H%M%S'`）。連番 `.001` は `FlywayTimestampNamingGuardTest` が機械的に拒否する。
- **パーティション DDL の罠**: レンジパーティションはパーティションキー（`viewed_at`）を PK/一意キーに含める必要がある。`PRIMARY KEY (id, viewed_at)` とすること（`audit_logs` V64.001 と同様）。UuidV7 の `id` 単独 PK にはできない点に注意。
- **既存データ番人テスト要否**: 新規テーブルのため既存データ移行は無い。ただしパーティション定義が `audit_logs` と乖離しないよう、パーティション幅・`p_future` の有無を検証するテストを推奨。

### 7.2 セキュリティ（Cookie / PII / GDPR）

`docs/security/README.md` の Cookie/セッション方針に準拠する。

- **匿名 cookie `mnsft_vid`**: ランダム UUID。個人を特定しない。発行は既存 `AuthLoginController#buildAccessTokenCookie` の `ResponseCookie.from(...)` を手本にする（`.httpOnly(true).secure(cookieSecure).path("/").sameSite("...").maxAge(...)`・確認済み）。**確定属性**:
  - `HttpOnly=true` — cookie 値は**サーバーが解決してビーコン INSERT に使うだけで、FE/SPA が JS で読む必要は無い**（FE はビーコン body を組み立て、cookie はブラウザが自動送信するのみ）。よって `HttpOnly=true` で確定してよく、§10.2-A/B の「SPA 読み取り要否」は「不要 → HttpOnly 可」で解消。
  - `Secure=cookieSecure`（`${MANNSCHAFT_COOKIE_SECURE}`。本番 true / ローカル false）— 認証 cookie と同じ環境変数に揃える。
  - `SameSite` = **`Lax`（マスター御裁可 2026-07-08 で確定・§10.2-B）**。認証 cookie の正準は `Strict`（`docs/security/02 §2`）だが、匿名計測 cookie に `Strict` を課すと、外部リンク・検索エンジン等から**別サイト経由で初回着地した公開ページ**でその閲覧に cookie が付かず（初回は必ず新規採番）ユニーク判定が水増しになる。計測 cookie は機密性が無く CSRF 経路にも使われず、万一の乗っ取り被害も小さいため `Lax` を採る（計測精度優先）。
  - `Max-Age` = 長期（例 400 日。Chrome の cookie 上限に整合）、`Path=/`。
  - **cookie 名 prefix**: 認証 cookie（`access_token`/`refresh_token`）は `__Host-` prefix を**使っていない**（コード確認済み）。よって本 cookie も prefix 無し（`mnsft_vid`）で既存規約に揃える。
- **IP アドレスは保存しない**（生ログに IP カラムを設けない）。GDPR 配慮の中核。
- **PII 非保持**: 生ログには `user_id`（内部 ID）と匿名 `visitor_id` のみ。氏名・メール等は保持しない。集計テーブルは統計値のみ。
- **cookie 同意**: **consent 不要で確定（マスター御裁可 2026-07-08・§10.2-A）**。匿名 UUID は個人特定不能・IP 非保存のため、同意バナー無しで発行してよい。将来 EU 展開等で同意基盤（F12.3 consent バナー）が導入された段階で「計測 cookie」カテゴリへ組み込む（現時点では組込対象なし）。
- **退会時**: ユーザー退会（匿名化）時、生ログの `user_id` は内部 ID のため個別消去は不要だが、CLAUDE.md の匿名化方針（統計データは残す）に沿って `user_id` はそのまま残置（統計価値を保持・個人特定不能）。

### 7.3 レートリミット

- **レートリミット基盤（手本の訂正）**: 本プロジェクトの現行レートリミットは **`ValkeyRateLimiter` + `AbstractRateLimitFilter`**（Valkey 固定ウィンドウ・Lua 原子化・fail-open）である。**Bucket4j は 2026-06-12 に全 18 フィルタから撤去済み**（`docs/security/06 §4.3.1`）。よって計測ビーコンのレートリミットは `AbstractRateLimitFilter` を継承した新規フィルタ（例 `PageViewBeaconRateLimitFilter`）で実装する。**公開エンドポイントの既存手本は `PublicApiRateLimitFilter` / `AdPublicEndpointRateLimitFilter`**（未認証・IP キー）を参照する。
- **制限主体と閾値（標準表準拠）**: `docs/security/06 §4.2` の標準閾値では「公開 API（認証不要）= **IP アドレス・60 req/分**」。計測ビーコンはこの区分に該当するため **IP キー（`AbstractRateLimitFilter` の未認証時 `ip:{ip}` 既定・X-Forwarded-For 先頭値優先）で 60 req/分**を基準とする。`visitor_id` はクライアント側 cookie で詐称容易なためレート制限のキーには使わない（IP が正）。ただし SPA のページ遷移ごとに 1 ビーコンが飛ぶため、通常閲覧で 60/分を超えないよう、必要なら本フィルタ限定で緩めの上限（例 120/分）を宣言してよい（標準表は上限目安）。
- **429 応答形式の統一（訂正）**: `AbstractRateLimitFilter` の 429 応答は**プロジェクト標準形**（ボディ `{"error":"Too many requests"}` + `Retry-After` + `X-RateLimit-*` 3 ヘッダー）で返る。フィルタ層で処理されるため、**エラーコード `TEAMANALYTICS_004`（429）はフィルタ経路では body に載らない**。§6 のエラーコード表では `TEAMANALYTICS_004` を「参考（レート超過の意味論を示すための論理コード）」に格下げし、実際の 429 応答は標準形に従うと明記する（§6 参照）。
- 集計取得 GET: メンバー限定かつ日次集計テーブル読みで軽量なため厳しめの制限は不要（標準表「認証済み READ 系 = ユーザー ID・300 req/分」に従う。専用フィルタは任意）。

### 7.5 非機能（性能・スケール・移行）

- **高頻度 INSERT 対策**: 生ログは月次パーティション + UuidV7（時刻順・独立発番）。書き込みは `@Async("page-view-pool")`（PV 専用プール・§5.1）で API レイテンシから切り離す。GET はリアルタイム生ログ集計でなく**日次集計テーブル読み**で軽量。
- **1000 万ユーザー / シャーディング原則**: 生ログは UuidV7 で複数ノード独立発番可（原則 6）。クロスドメイン FK なし（原則 1）。`scope_type/scope_id` を絞り込みキーとしテナントスコープ設計に整合（原則 7 の思想）。将来シャーディング時も既存パーティション + UUID で侵襲を最小化。
- **PV 欠損許容**: アクセスカウンターの性質上、非同期記録の取りこぼしや Executor 飽和時の Discard は許容される（正確な課金・監査データではない）。この前提を明記することで、対処療法的な同期化・リトライ地獄を避ける。
- **後方互換 / 現状の壊れ**: 新規テーブル・新規エンドポイントのみで既存 BE 機能への影響は無い。ただし **FE 組織版ページ（`organizations/[slug]/analytics.vue`）は既に稼働中で、未実装 BE を叩いて取得失敗トーストを出す壊れた状態**（§0）。本 BE 実装完了で組織側は自動復旧する。チーム版は PR #2185 で `TeamSidebar` 導線を隠しているため、実装完了後に導線再表示（別 PR）+ チーム版ページの本結線が必要。
- **エクスポート機能は別依存（本 F10.8 対象外・マスター御裁可 2026-07-08 で確定・§10.2-C）**: 組織版ページの `ExportDialog`（`scope-type`/`scope-id`・ジョブ ID ポーリング）は PV 計測とは独立したデータエクスポート機能で、別途 BE エクスポート API（ジョブ生成 + ステータスポーリング + ダウンロード）を要する。本設計書のスコープには含めない。BE 未実装のまま組織版ページのエクスポートボタンを押すと失敗するため、**第1弾では FE の「データエクスポート」ボタンと `ExportDialog` を非表示にする**（`analytics.vue` の `showExport` トリガ Button と `<ExportDialog>` を削除／コメントアウト）。別 F 番として起票し、BE エクスポート API 実装後に再結線する。
- **第2弾に残す範囲**: topContent（人気コンテンツランキング）の実データ算出。第1弾は空配列。第2弾で `page_view_logs` を `content_id` 集計（先行して `idx_pvl_scope_content` を張ってある）、必要ならコンテンツ別日次集計テーブルを追加する。加えてダッシュボード `teamPageViews` ウィジェットへの供給（§5.5）。
