## 0. 前提と本設計書の位置づけ

FE には `/teams/[slug]/analytics` と `/organizations/[slug]/analytics` のページ・型・子コンポーネントが既に存在するが、呼び先の BE API が未実装のため、PR #2185 で導線を一旦非表示化している。本設計書は、その FE 契約を満たす**ページビュー（PV）計測基盤をゼロから設計する**ものである。

方式は「昔の HP のアクセスカウンター」に相当する**枯れた古典方式**を採用する（マスター御裁可済・変更不可）。すなわち:

1. **PV 収集 = FE ビーコン方式**（画面表示時に計測 API へ POST）
2. **ユニーク訪問者/ゲスト識別 = 匿名 cookie**（IP は保存しない・GDPR 配慮）
3. **集計 = 三層アーキ**（生ログ → 日次集計テーブル → 毎日 02:00 ShedLock バッチ → 期間集約サービスが DTO 返却。F10.4 が金型）
4. **段階リリース**: 第 1 弾 = summary + daily + monthly。**topContent（人気コンテンツランキング）は第 2 弾**（第 1 弾では空配列 `[]` を返す）

> **採番・命名の注記（マージ時に必ず再確認）**: 本書に記す Flyway major（V146 想定）・エラーコードのプレフィクスは**執筆時点の現況値**である。実装時にはマージ直前の `origin/main` を再確認し、Flyway major は「全体最大 major + 1」、minor は UTC タイムスタンプで確定すること（`FlywayTimestampNamingGuardTest` が連番採番を機械的に拒否する）。

## 1. 概要

### 1.1 目的

チーム管理者・組織管理者が「自分のチーム/組織のページやコンテンツがどれだけ閲覧されているか」を把握できるようにする。SYSTEM_ADMIN 向けの経営分析（F10.4）とは対象・データソースが完全に分離しており、本機能は**スコープ（チーム/組織）単位のアクセス解析**を提供する。

### 1.2 本ドキュメントのスコープ

| 機能 | 弾 | 説明 |
|------|----|------|
| PV 計測ビーコン受信 | 第1弾 | FE から送られる閲覧イベントを非同期で生ログに記録 |
| サマリ（summary） | 第1弾 | 総 PV / ユニーク訪問者 / メンバー閲覧 / ゲスト閲覧 |
| 日次推移（daily） | 第1弾 | 日ごとの views / uniqueVisitors |
| 月次推移（monthly） | 第1弾 | 月ごとの views / uniqueVisitors |
| 人気コンテンツランキング（topContent） | **第2弾** | コンテンツ別 PV ランキング。**第1弾では空配列 `[]` を返す** |
| 日次集計バッチ | 第1弾 | 毎日 02:00 (JST) に前日分を集計。ShedLock 排他・冪等 |
| パーティション保守バッチ | 第1弾 | 生ログテーブルの翌々月パーティションを毎月自動追加 |

### 1.3 対象ロール（ロール × 操作範囲）

集計取得 API（GET）は「そのスコープのメンバー、または当該スコープの ADMIN」のみが閲覧できる。計測ビーコン（POST）は公開ページからのゲスト計測を許容するため認可が異なる（§3.1 参照）。

| ロール | 集計取得（GET summary/daily/monthly/topContent） | 計測ビーコン（POST /page-views） |
|--------|------|------|
| SYSTEM_ADMIN | 可（全スコープ） | 可 |
| ADMIN（当該スコープ） | 可 | 可 |
| DEPUTY_ADMIN（当該スコープ） | 可 | 可 |
| MEMBER（当該スコープ） | 可 | 可（member として記録） |
| SUPPORTER（当該スコープ） | 可 | 可（member として記録） |
| GUEST（未ログイン） | **不可（403）** | 可（guest として記録。公開ページ閲覧の計測） |
| 他スコープのメンバー / 非メンバー | **不可（404 で存在秘匿。§3.3）** | 可（当該スコープが計測を受け付ける場合。§3.1） |

### 1.4 対象レベル

- [ ] プラットフォーム全体（SYSTEM_ADMIN 視点）… **F10.4 の領域。本機能では扱わない**
- [x] 組織 (Organization)
- [x] チーム (Team)
- [ ] 個人 (Personal)

### 1.5 第1弾 / 第2弾の線引き

| 項目 | 第1弾（本リリース） | 第2弾 |
|------|--------------------|-------|
| DDL | 生ログ + 日次集計テーブル（両方作成） | 追加テーブルなし（生ログを再集計で対応）またはコンテンツ別日次集計テーブルを追加 |
| API | POST /page-views、GET analytics（summary/daily/monthly 実データ、topContent は `[]`） | topContent に実データを返す |
| バッチ | 日次サマリ集計、パーティション保守 | コンテンツ別集計ステップを追加 |

> **重要（FE 型契約）**: FE 型は `topContent` を null 不可で定義しているため、第1弾でも**空配列 `[]` を必ず返す**こと（`null` は不可）。

## 2. 受け入れ条件（テスト可能）

`/試練` が red テストに落とせる粒度で列挙する。誰が・何をしたら・どうなるか。

### 2.1 計測ビーコン（POST）

- **AC-01**: 認証済みメンバーが `POST /api/v1/page-views` に有効な body（scope=TEAM, scopeId, contentType, contentId, url, title）を送ると **202 Accepted** が返り、非同期処理完了後に生ログ `page_view_logs` に 1 件（`user_id` セット・`visitor_id` は匿名 cookie 値）記録される。
- **AC-02**: 未ログインユーザーが公開ページから同 POST を送ると **202 Accepted** が返り、生ログに 1 件（`user_id = NULL`・`visitor_id` = 匿名 cookie 値）記録される（ゲスト計測）。
- **AC-03**: 匿名 cookie（`mnsft_vid`）が未発行の未ログインリクエストに対しては、レスポンスで新規 UUID を採番した cookie を Set-Cookie する（属性は §7.2 準拠）。
- **AC-04**: `scope` が `TEAM`/`ORGANIZATION` 以外、または `contentType` が許容外（`ARTICLE`/`ACTIVITY`/`PAGE`/`TEAM` 以外）の場合 **400** を返す。
- **AC-05**: `scopeId` が存在しないスコープを指すビーコンは、生ログに記録せず**握りつぶし 202 を返す**（存在秘匿。�ログ肥大攻撃を避けるため非同期側で破棄。§3.1 の設計判断参照）。
- **AC-06**: 同一 `visitor_id` から同一 `scope+contentId` へ短時間（同一日）に複数回 POST しても生ログには複数行入るが、日次集計後の `uniqueVisitors` は **1** と数える（AC-13）。
- **AC-07**: ビーコン POST がレート制限（§7.3）を超過した場合 **429** を返す。

### 2.2 集計取得（GET）

- **AC-08**: 当該チームのメンバーが `GET /api/v1/teams/{slug}/analytics` を叩くと **200** と `{data: AnalyticsResponse}` が返り、全フィールド（summary/daily/monthly/topContent）が**非 null**である。
- **AC-09**: 非メンバー（別チームのメンバーを含む）が他チームの `GET /api/v1/teams/{slug}/analytics` を叩くと **404**（存在秘匿。403 ではない。§3.3）。
- **AC-10**: 未ログインで `GET .../analytics` を叩くと **401**。
- **AC-11**: `dateFrom > dateTo` の場合 **400**。
- **AC-12**: `dateFrom`/`dateTo` 双方省略時は全期間集計を返す（200）。
- **AC-13**: 日次バッチ実行後、`summary.totalViews` = 期間内 `page_view_logs` の件数、`summary.uniqueVisitors` = 期間内のユニーク `visitor_id` 数、`memberViews` = `user_id IS NOT NULL` の PV 数、`guestViews` = `user_id IS NULL` の PV 数、が一致する。
- **AC-14**: ゲスト（未ログイン）が同一匿名 cookie で同日に 3 回閲覧した場合、`uniqueVisitors` への寄与は **1**。
- **AC-15**: `topContent` は**第1弾では常に空配列 `[]`**（実装漏れではなく仕様）。
- **AC-16**: `daily[].date` は `YYYY-MM-DD`、`monthly[].month` は `YYYY-MM` 形式で返る。
- **AC-17**: 組織版 `GET /api/v1/organizations/{slug}/analytics` もチーム版と同一構造・同一権限規則で動作する。

### 2.3 バッチ・境界

- **AC-18**: 日次集計バッチを同一日付で 2 回実行しても結果が重複しない（冪等。`deleteByDate` → 再 INSERT）。
- **AC-19**: バックフィル用 `aggregateForDate(LocalDate)` を任意過去日付で呼ぶと、その日の日次集計行が再計算される。
- **AC-20**: 生ログに 1 件も無い日を集計しても、日次集計行は作られない（または 0 行で作られる）ため `summary` は 0 を返す（例外にしない）。
- **AC-21**: パーティション保守バッチ実行後、生ログテーブルに翌々月のパーティションが存在する（`p_future` の手前に月次パーティションが追加される）。

## 3. API 契約

### 3.0 共通

- レスポンスは `ApiResponse.of(...)` により `{data: ...}` でラップする（既存規約）。
- パスは**数値 ID でなく slug（String）**。既存規約に倣い `@RequestMapping("/api/v1/teams/{slug}")` 配下で `Long teamId = teamService.resolveTeamId(slug)`（手本 `TeamController` / `TeamShiftSettingsController`）。組織版は `organizationService.resolveOrganizationId(slug)` 相当を用いる（**メソッド名は実装時に `OrganizationService` の実物で確認**）。
- 認可拒否のうち「権限不足」は 403、「スコープの存在自体を秘匿すべき IDOR」は 404 とする（既存 `TEAM_001 = NOT_FOUND` 前例に倣う。§3.3）。

### 3.1 計測ビーコン `POST /api/v1/page-views`

閲覧イベントを受信し、**非同期**で生ログに記録する。既存の非同期イベント記録基盤（`AuditLogEventListener` / AFTER_COMMIT / `@Async("event-pool")`）の思想を踏襲する。

**認可**: 認証は必須としない（公開ページのゲスト計測を許可するため）。ただし濫用防止のためレート制限（§7.3）と scope 実在チェックを行う。

**リクエストボディ**:
```json
{
  "scope": "TEAM",
  "scopeId": 123,
  "contentType": "ARTICLE",
  "contentId": 4567,
  "url": "/teams/my-team/articles/4567",
  "title": "春合宿のお知らせ"
}
```

| フィールド | 型 | 必須 | 説明 |
|-----------|----|----|------|
| `scope` | ENUM(`TEAM`,`ORGANIZATION`) | YES | 閲覧対象のスコープ種別 |
| `scopeId` | number(Long) | YES | チーム/組織の数値 ID（FE が保持している解決済み ID。slug ではなく ID を送る） |
| `contentType` | ENUM(`ARTICLE`,`ACTIVITY`,`PAGE`,`TEAM`) | YES | 閲覧対象の種類 |
| `contentId` | number(Long) | YES | 閲覧対象の ID（`PAGE` のように ID が無い場合は 0 等の規約値。実装時確定・要裁可 §10） |
| `url` | string | YES | アプリ内相対パス（最大 512 文字。topContent の NuxtLink :to に使うため相対パス限定） |
| `title` | string | YES | 表示タイトル（最大 255 文字） |

**処理**:
1. Controller で **匿名 cookie（`mnsft_vid`）を解決**。未発行なら UUID を採番し Set-Cookie（属性は §7.2）。
2. リクエストは軽量 DTO に詰め、`ApplicationEventPublisher` で `PageViewRecordedEvent` を publish して即 **202 Accepted** を返す（ボディなし、または最小 ack）。
3. `@Async("event-pool")` のリスナーが受信し、scope 実在チェック（存在しなければ破棄）→ `page_view_logs` へ INSERT。SPA 遷移も毎回 POST されるので、各遷移が 1 イベント。

**レスポンス**: **202 Accepted**（ボディなし）。同期処理は cookie 解決とイベント publish のみで、DB 書き込みは非同期。

**エラー**: 400（body 不正・ENUM 不正）、429（レート制限超過）。

> **設計判断（ゲスト計測の許可方式）**: ビーコン POST を認証必須にすると公開ページ（未ログイン閲覧）を計測できず、アクセスカウンターの目的を満たせない。よって POST は**未認証を許容**する。代償として (a) scope 実在チェックで存在しない scope へのログ注入を破棄、(b) レート制限で濫用を抑止、(c) 生ログの `visitor_id` は個人特定不能な匿名 UUID のみ・IP は保存しない、で守る。集計取得（GET）側は厳格にメンバー限定とし、**書き込みは緩め・読み取りは厳格**の非対称設計とする。

> **設計判断（存在しない scope の握りつぶし）**: AC-05 は「対処療法の握りつぶし」ではなく、**未認証エンドポイントに対する意図的なログ注入防御**である。攻撃者が任意 scopeId を送ってログを膨らませる／他 scope に成りすまして計測を汚染することを防ぐため、非同期側で scope 実在を確認し、実在しないものは記録しない。クライアントには 202 を返して探索（どの scopeId が実在するか）の手がかりを与えない。

### 3.2 集計取得（チーム）`GET /api/v1/teams/{slug}/analytics`

**認可**: 当該チームのメンバー、または当該チームの ADMIN（+ SYSTEM_ADMIN）。**Controller 入口で検証**（共有メソッドに認可を埋めない。バッチ巻き添えを避ける既存戒め準拠）。直近 PR #2186 の `EventScopeAccessGuard` と同型の「スコープ帰属 + メンバーシップ検証」を踏襲する（**実装時に `EventScopeAccessGuard` の実シグネチャを確認して同型 Guard を用意**）。

**クエリパラメータ**:
| パラメータ | 型 | 必須 | 説明 |
|-----------|----|----|------|
| `dateFrom` | DATE(`YYYY-MM-DD`) | NO | 集計開始日。省略時は全期間 |
| `dateTo` | DATE(`YYYY-MM-DD`) | NO | 集計終了日。省略時は全期間 |

**レスポンス（200 OK）** — 全フィールド null 不可:

**エラー**: 400（`dateFrom > dateTo`・日付形式不正）、401（未認証）、404（非メンバー/存在しない slug — §3.3）。

### 3.3 集計取得（組織）`GET /api/v1/organizations/{slug}/analytics`

チーム版と**同一構造・同一クエリ・同一レスポンス**。認可のみ「当該組織のメンバー/ADMIN（+ SYSTEM_ADMIN）」に読み替える。`organizationService.resolveOrganizationId(slug)` でスコープ ID を解決する。

> **設計判断（IDOR 隠蔽は 404）**: 非メンバーが他スコープの analytics を叩いた場合、403（＝そのスコープは存在するが権限が無い、を露呈）ではなく **404** を返し、スコープの存在自体を秘匿する。既存 `TEAM_001 = NOT_FOUND` 前例に一致。ただし「未認証」は横断的に 401 とする（認証すれば結果が変わるため）。

### 3.4 ユニーク訪問者/メンバー識別の規則

- **member**: `user_id IS NOT NULL`（ログイン利用者。userId 単位）。
- **guest**: `user_id IS NULL`（未ログイン。匿名 cookie `visitor_id` 単位）。
- **uniqueVisitors** の重複除去キー: ログイン利用者は `user_id`、未ログインは `visitor_id`。同一ユーザーがログイン前後で別カウントにならないよう、集計時に「`user_id` があれば `user_id`、無ければ `visitor_id`」を DISTINCT キーとする（実装時に集計 SQL で `COALESCE`/`CASE` 表現。要裁可の余地 §10-3）。
- **IP アドレスは一切保存しない**（GDPR 配慮）。

## 4. DB 設計

### 4.1 テーブル一覧

| テーブル名 | 役割 | 主キー方針 | 論理削除 | パーティション |
|-----------|------|-----------|---------|--------------|
| `page_view_logs` | 生ログ（高頻度 INSERT） | **UuidV7Entity**（`BINARY(16)`） | なし | 月次レンジ（`TO_DAYS(viewed_at)`） |
| `page_view_daily_stats` | 日次集計 | BaseEntity（`BIGINT`/IDENTITY） | なし | なし |

> **原則遵守**: 生ログは高頻度 INSERT かつテナントごとに行が増えるため、CLAUDE.md 原則 6（新規テーブルは UUIDv7）に**明確に該当**するので `UuidV7Entity` を継承する。日次集計テーブルは既存 `analytics_daily_*`（F10.4）が `BaseEntity`（Long/IDENTITY）である前例に倣う。**クロスドメイン FK は張らない**（`users`/`teams`/`organizations` へ FK を張らず、参照整合性はアプリ層で保証。原則 1）。

### 4.2 `page_view_logs`（生ログ・月次パーティション）

FE ビーコンが 1 閲覧ごとに 1 行を非同期 INSERT する。高頻度書き込みのスケール手本は `audit_logs`（F10.3 / V64.001）の月次レンジパーティションに倣う。

| カラム | 型 | NULL | デフォルト | 説明 |
|--------|----|----|-----------|------|
| `id` | `BINARY(16)` | NO | （UUIDv7 アプリ生成） | PK の一部（UuidV7Entity） |
| `scope_type` | `VARCHAR(20)` | NO | — | `TEAM` / `ORGANIZATION`（`bulletin_threads` V5.002 と同方式） |
| `scope_id` | `BIGINT UNSIGNED` | NO | — | チーム/組織 ID（FK なし・アプリ層保証） |
| `content_type` | `VARCHAR(20)` | NO | — | `ARTICLE`/`ACTIVITY`/`PAGE`/`TEAM` |
| `content_id` | `BIGINT UNSIGNED` | NO | 0 | 閲覧対象 ID（PAGE 等 ID 無し時は 0。要裁可 §10-1） |
| `url` | `VARCHAR(512)` | NO | — | アプリ内相対パス |
| `title` | `VARCHAR(255)` | NO | — | 表示タイトル |
| `user_id` | `BIGINT UNSIGNED` | YES | NULL | ログイン利用者 ID。NULL = guest（FK なし） |
| `visitor_id` | `CHAR(36)` | NO | — | 匿名 cookie の UUID（個人特定不能） |
| `viewed_at` | `DATETIME` | NO | CURRENT_TIMESTAMP | 閲覧日時（パーティションキー） |
| `created_at` | `DATETIME` | NO | CURRENT_TIMESTAMP | レコード作成日時 |

**主キー**: `PRIMARY KEY (id, viewed_at)`
（MySQL のレンジパーティションはパーティションキーを主キー/一意キーに含める必要があるため、`audit_logs` と同様に `(id, viewed_at)` の複合 PK とする。）

**INDEX**:
- `idx_pvl_scope_viewed (scope_type, scope_id, viewed_at)` — 日次集計バッチのスコープ×日付スキャン用
- `idx_pvl_scope_visitor (scope_type, scope_id, visitor_id)` — ユニーク訪問者集計用
- `idx_pvl_scope_content (scope_type, scope_id, content_id)` — 第2弾 topContent 集計用（先行して張っておく）

**パーティション**（月次レンジ・`audit_logs` V64.001 の書式に倣う）:
```sql
PARTITION BY RANGE (TO_DAYS(viewed_at)) (
  PARTITION p2026_07 VALUES LESS THAN (TO_DAYS('2026-08-01')),
  PARTITION p2026_08 VALUES LESS THAN (TO_DAYS('2026-09-01')),
  -- … 数年分を先行作成（実装時に audit_logs の実レンジ幅に合わせる）…
  PARTITION p_future  VALUES LESS THAN MAXVALUE
);
```

> **パーティション保守**: 翌々月分のパーティションを毎月自動追加するバッチ（§5.4）を用意する。手本は `auth-audit-log-partition-maintenance`（`AuditLogPartitionMaintenanceBatchService.addNextPartitions`、毎月 1 日 01:00 JST）。`p_future` を再オーガナイズして月次パーティションを挿入する既存ロジックを踏襲する。

> **保持・アーカイブ**: 生ログは肥大するため保持期間（例: 13 ヶ月）を設け、古いパーティションを丸ごと `DROP PARTITION` する運用（`audit_logs` のアーカイブ手本 `auth-audit-log-archive-monthly` に倣う）。日次/月次集計テーブルには恒久データが残るため、生ログ削除後も集計値は保持される。保持期間の具体値は要裁可（§10-4）。

### 4.3 `page_view_daily_stats`（日次集計）

日次バッチが前日分を集計して 1 スコープ 1 日 1 行で upsert する。手本は `analytics_daily_users`（V10.069 の `UNIQUE KEY(date)`）を「スコープ×日付」に拡張したもの。

| カラム | 型 | NULL | デフォルト | 説明 |
|--------|----|----|-----------|------|
| `id` | `BIGINT UNSIGNED` | NO | AUTO_INCREMENT | PK |
| `scope_type` | `VARCHAR(20)` | NO | — | `TEAM` / `ORGANIZATION` |
| `scope_id` | `BIGINT UNSIGNED` | NO | — | チーム/組織 ID |
| `date` | `DATE` | NO | — | 集計対象日 |
| `total_views` | `INT UNSIGNED` | NO | 0 | 当日総 PV |
| `unique_visitors` | `INT UNSIGNED` | NO | 0 | 当日ユニーク訪問者（COALESCE(user_id, visitor_id) の DISTINCT） |
| `member_views` | `INT UNSIGNED` | NO | 0 | 当日メンバー PV（user_id IS NOT NULL） |
| `guest_views` | `INT UNSIGNED` | NO | 0 | 当日ゲスト PV（user_id IS NULL） |
| `created_at` | `DATETIME` | NO | CURRENT_TIMESTAMP | レコード作成日時 |
| `updated_at` | `DATETIME` | NO | CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP | レコード更新日時 |

**UNIQUE KEY**: `uk_pvds_scope_date (scope_type, scope_id, date)` — 1 スコープ 1 日 1 行を保証。冪等な upsert（`INSERT ... ON DUPLICATE KEY UPDATE`）と範囲検索（プレフィクス `(scope_type, scope_id)` で INDEX 利用）を兼ねる。

**集計方針**:
- `monthly` は本テーブルを月単位で `GROUP BY YEAR(date), MONTH(date)` して集約（別テーブルを作らない。行数が小さいためアプリ層集約で十分。F10.4 の granularity 集約と同思想）。
- **月次ユニーク訪問者の注意**: `unique_visitors` は日次でしか保持しないため、月次のユニーク訪問者を日次値の単純合算で出すと重複カウントになる。第1弾では月次 `uniqueVisitors` は「その月の生ログから直接 DISTINCT 集計」する（生ログ保持期間内は可能）か、または「日次ユニークの合算（近似・重複あり）」のどちらを採るか **要裁可（§10-2）**。推奨: 生ログ保持期間内は生ログ直接集計で正確値を返す。

### 4.4 ER 図（テキスト表現）

```
page_view_logs (id, viewed_at) [月次パーティション, UuidV7]
   ↑ 毎日02:00 日次集計バッチ (scope_type, scope_id, date で GROUP BY)
page_view_daily_stats (scope_type, scope_id, date) [UNIQUE, BaseEntity]
   ↑ 期間集約サービスが dateFrom〜dateTo を読み、summary/daily を構築
   ↑ monthly は date を月集約 / topContent(第2弾) は page_view_logs を content_id 集計
※ users / teams / organizations への FK は張らない（クロスドメイン FK 禁止・アプリ層保証）
```

### 4.5 UUIDv7 / テナント原則の遵守

- `page_view_logs` は `UuidV7Entity` を継承（`@UuidGenerator(style=TIME)`、`BINARY(16)`）。時刻順ソート可能でインデックス効率が高く、高頻度 INSERT でも複数ノードで独立発番できる（原則 6）。
- 集計テーブルのリポジトリは `scope_id` で絞り込むが、`organization_id` 列を直接持たないため `AbstractTenantAwareRepository` の適用は限定的。`scope_type`/`scope_id` の複合で絞り込む専用メソッドを定義する（`AbstractTenantAwareRepository` を継承するかは実装時判断。テナントスコープの手本として参照はする）。

## 5. ビジネスロジック

### 5.1 非同期ビーコン記録

```
1. POST /api/v1/page-views 受信（Controller）
2. 匿名 cookie mnsft_vid を解決（未発行なら UUID 採番 + Set-Cookie）
3. 軽量イベント PageViewRecordedEvent を ApplicationEventPublisher.publishEvent
   （手本: AuditLogEventListener の入口。ただし本 POST はトランザクション外なので
    AFTER_COMMIT ではなく即時 publish。@Async("event-pool") で非同期実行）
4. 202 Accepted を即返す（DB 書き込みを待たない）
5. @Async("event-pool") リスナー:
   a. scope_type/scope_id の実在チェック（team/organization service 経由）
      → 実在しなければ破棄（ログ注入防御。§3.1）
   b. page_view_logs へ INSERT
6. event-pool が飽和した場合は既存の Executor 設定（RejectedExecutionHandler）に従う
   （PV は欠損を許容できる性質のため、CallerRuns より Discard 系が望ましい。実装時に
    event-pool の既存設定を確認し、PV 専用 Executor を分けるか判断。要裁可 §10-5）
```

### 5.2 日次集計バッチ

手本は `DailyAggregationBatchService`（F10.4、`analytics-daily-aggregation`）。

```
1. @Scheduled(cron="0 0 2 * * *", zone="Asia/Tokyo") 毎日 AM 2:00 (JST)
2. @SchedulerLock(name="pageViewDailyAggregation", lockAtMostFor="30m") で ShedLock 排他
3. @BatchEndpoint(name="analytics-pageview-daily-aggregation", ...) を付与（手動起動可）
4. 対象: 前日（date = yesterday (JST)）
5. 冪等: aggregateForDate(LocalDate date) を呼ぶ
   a. deleteByDate 相当（page_view_daily_stats の当日該当行を scope 横断で削除）
   b. page_view_logs を (scope_type, scope_id) で GROUP BY し当日集計を再 INSERT:
      - total_views  = COUNT(*)
      - unique_visitors = COUNT(DISTINCT COALESCE(CAST(user_id AS CHAR), visitor_id))
      - member_views = COUNT(*) WHERE user_id IS NOT NULL
      - guest_views  = COUNT(*) WHERE user_id IS NULL
6. バックフィル: aggregateForDate(LocalDate) を public にし、任意過去日の再集計に使う（AC-19）
7. エラー時: batch_job_logs に ERROR 記録（F10.1/F10.4 と同様の運用）
```

### 5.3 期間集約サービス（GET のデータ源）

```
1. resolveTeamId(slug) / resolveOrganizationId(slug) で scope_id を得る
2. 認可 Guard（EventScopeAccessGuard 同型）で「スコープ帰属 + メンバーシップ」検証
   → 非メンバーは 404、未認証は 401
3. page_view_daily_stats を (scope_type, scope_id, date BETWEEN dateFrom AND dateTo) で取得
   （dateFrom/dateTo 省略時は全期間）
4. summary = 期間内 daily 行を合算（total/member/guest）+ uniqueVisitors は §5.3-注 に従う
5. daily = 取得行をそのまま DailyPageView[] にマップ
6. monthly = daily を年月で GROUP BY 集約
7. topContent = 第1弾は空配列 []（第2弾で page_view_logs から content_id 集計）
8. ApiResponse.of(AnalyticsResponse) で返す（全フィールド非 null）
```

> **注（summary.uniqueVisitors / monthly.uniqueVisitors）**: 日次集計テーブルの `unique_visitors` は日単位のため、期間サマリ・月次のユニーク訪問者を日次値の合算で出すと重複カウントになる。第1弾では**生ログ保持期間内はその期間の `page_view_logs` から DISTINCT 直接集計して正確値を返す**方針を推奨（§4.3・§10-2）。生ログ保持期間外（アーカイブ済み）の期間は日次合算の近似値にフォールバックし、その旨をレスポンスに含めるかは要裁可。

### 5.4 パーティション保守バッチ

```
1. @Scheduled(cron="0 0 1 1 * *", zone="Asia/Tokyo") 毎月 1 日 AM 1:00 (JST)
2. @SchedulerLock + @BatchEndpoint(name="analytics-pageview-partition-maintenance")
3. page_view_logs の翌々月パーティションが無ければ p_future を REORGANIZE して追加
   （手本: AuditLogPartitionMaintenanceBatchService.addNextPartitions）
4. 併せて保持期間超過の古いパーティションを DROP PARTITION（保持期間は要裁可 §10-4）
```

## 7. Flyway / セキュリティ / i18n / 非機能

### 7.1 Flyway マイグレーション

| ファイル名（想定） | 内容 |
|------------------|------|
| `V146.{yyyyMMddHHmmss}__create_page_view_logs.sql` | `page_view_logs`（UuidV7・複合 PK・月次パーティション・INDEX） |
| `V146.{yyyyMMddHHmmss}__create_page_view_daily_stats.sql` | `page_view_daily_stats`（UNIQUE(scope_type,scope_id,date)） |

- **major はマージ時に `origin/main` 全体の最大 major + 1 で確定**（執筆時点 V145 が最新 → V146 想定。ただし並行 PR で major が進む可能性があるため必ず再確認）。
- **minor は UTC タイムスタンプ必須**（`date -u '+%Y%m%d%H%M%S'`）。連番 `.001` は `FlywayTimestampNamingGuardTest` が機械的に拒否する。
- **パーティション DDL の罠**: レンジパーティションはパーティションキー（`viewed_at`）を PK/一意キーに含める必要がある。`PRIMARY KEY (id, viewed_at)` とすること（`audit_logs` V64.001 と同様）。UuidV7 の `id` 単独 PK にはできない点に注意。
- **既存データ番人テスト要否**: 新規テーブルのため既存データ移行は無い。ただしパーティション定義が `audit_logs` と乖離しないよう、パーティション幅・`p_future` の有無を検証するテストを推奨。

### 7.2 セキュリティ（Cookie / PII / GDPR）

`docs/security/README.md` の Cookie/セッション方針に準拠する。

- **匿名 cookie `mnsft_vid`**: ランダム UUID。個人を特定しない。属性は `docs/security/` の規約に厳密準拠（実装時に既存 cookie 発行実装 `ResponseCookie.from(...)` の属性設定を手本にする）。想定属性: `HttpOnly`（JS から読めなくする）※ただし SPA が自前で読む必要がある場合は要検討 §10-6、`Secure`、`SameSite=Lax`、長期 `Max-Age`（例 400 日）、`Path=/`。cookie 名の prefix（`__Host-` 等）採否は既存規約に合わせる。
- **IP アドレスは保存しない**（生ログに IP カラムを設けない）。GDPR 配慮の中核。
- **PII 非保持**: 生ログには `user_id`（内部 ID）と匿名 `visitor_id` のみ。氏名・メール等は保持しない。集計テーブルは統計値のみ。
- **cookie 同意**: 匿名 UUID は「厳密に必要な計測」に該当するか、consent 対象かを `F12.3` / `docs/security/` の consent 方針で確認（要裁可 §10-6）。個人特定しない集計目的の cookie は多くの法域で consent 不要だが、プロジェクトの consent バナー方針に合わせる。
- **退会時**: ユーザー退会（匿名化）時、生ログの `user_id` は内部 ID のため個別消去は不要だが、CLAUDE.md の匿名化方針（統計データは残す）に沿って `user_id` はそのまま残置（統計価値を保持・個人特定不能）。

### 7.3 レートリミット

- 計測ビーコン `POST /page-views`: 既存 `Bucket4j` 手本に倣い、**IP/セッション単位でなく `visitor_id` + リモート識別子**でバケットを設ける（例: 1 分 60 件程度）。超過は 429（`TEAMANALYTICS_004`）。公開エンドポイントのため濫用防止の要。
- 集計取得 GET: メンバー限定かつ日次集計テーブル読みで軽量なため厳しめの制限は不要（既存 API 共通のグローバル制限に従う）。

### 7.4 i18n（新規表示キー・6 言語前提・直書き禁止）

### 7.5 非機能（性能・スケール・移行）

- **高頻度 INSERT 対策**: 生ログは月次パーティション + UuidV7（時刻順・独立発番）。書き込みは `@Async("event-pool")` で API レイテンシから切り離す。GET はリアルタイム生ログ集計でなく**日次集計テーブル読み**で軽量。
- **1000 万ユーザー / シャーディング原則**: 生ログは UuidV7 で複数ノード独立発番可（原則 6）。クロスドメイン FK なし（原則 1）。`scope_type/scope_id` を絞り込みキーとしテナントスコープ設計に整合（原則 7 の思想）。将来シャーディング時も既存パーティション + UUID で侵襲を最小化。
- **PV 欠損許容**: アクセスカウンターの性質上、非同期記録の取りこぼしや Executor 飽和時の Discard は許容される（正確な課金・監査データではない）。この前提を明記することで、対処療法的な同期化・リトライ地獄を避ける。
- **後方互換**: 新規テーブル・新規エンドポイントのみ。既存機能への影響なし。FE は PR #2185 で導線を非表示化済みのため、BE 実装完了後に導線を再表示する（別 PR）。
- **第2弾に残す範囲**: topContent（人気コンテンツランキング）の実データ算出。第1弾は空配列。第2弾で `page_view_logs` を `content_id` 集計（先行して `idx_pvl_scope_content` を張ってある）、必要ならコンテンツ別日次集計テーブルを追加する。

| 5 | event-pool を PV 専用に分離するか | (a) 既存 event-pool 相乗り、(b) PV 専用 Executor + Discard 系拒否ハンドラ | (b) 推奨（監査ログの記録を PV バーストで詰まらせない） |
