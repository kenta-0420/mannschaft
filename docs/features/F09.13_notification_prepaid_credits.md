# F09.13 通知プリペイドクレジット機能

## 概要

告知通知の一斉送信に対して課金する、プリペイドクレジットシステム。
月間10,000通の無料枠を超えた分をクレジット残高から消費する。
クレジットは Stripe Checkout による一括購入で補充する。

---

## 仕様

### 無料枠・課金ルール

| ルール | 内容 |
|---|---|
| 月間無料枠 | 10,000通（組織単位・毎月1日リセット） |
| 無料枠アラート | 9,000通到達でADMINへ警告通知（月1回のみ） |
| 超過分 | クレジット残高から差し引き |
| 残高不足 | 72時間の猶予期間（送信可）、超過分は翌月1日に残高からマイナス相殺 |
| クレジット有効期限 | 購入から2年（失効30日前・7日前にADMINアラート） |
| 1通の定義 | 1受信者アカウント = 1通（push + email 両方届いても1通） |

### カウント対象

| 対象 | サービスクラス | 条件 |
|---|---|---|
| 一斉送信 | `NotificationHelper.notifyAll()` | `isBillable=true` のとき |
| SESメール | `DirectMailService.sendMail()` | 組織スコープのとき |
| 確認通知 | `ConfirmableNotificationService.send()` | 組織スコープのとき |

**カウント対象外**: 自動イベント通知、システム通知、1:1 DM

### プリペイドパッケージ

| パッケージ名 | 通数 | 価格 |
|---|---|---|
| スタンダード 10万通 | 100,000通 | ¥100,000 |
| スタンダード 20万通 | 200,000通 | ¥180,000 |
| スタンダード 50万通 | 500,000通 | ¥400,000 |
| スタンダード 100万通 | 1,000,000通 | ¥700,000 |

## DB 設計

### テーブル一覧

| テーブル名 | 説明 | 主キー種別 |
|---|---|---|
| `notification_credit_packages` | パッケージマスタ | BIGINT AUTO_INCREMENT（マスタ例外） |
| `notification_credit_purchases` | 購入履歴 | BIGINT AUTO_INCREMENT |
| `organization_notification_balances` | 組織別残高 | BIGINT AUTO_INCREMENT |
| `notification_monthly_usage` | 月次使用量集計 | BIGINT AUTO_INCREMENT |

**注**: `notification_credit_packages` はマスタテーブル（全テナント共通・書き込みは運用バッチのみ）のため、アーキテクチャ原則6のUUIDv7例外を適用。

### ER 図（概略）

```
notification_credit_packages 1─N notification_credit_purchases
organizations 1─1 organization_notification_balances
organizations 1─N notification_credit_purchases
organizations 1─N notification_monthly_usage
```

### 重要カラム

**`notification_credit_purchases`**
- `remaining_credits`: FIFO消費追跡用残クレジット（失効バッチで使用）
- `idempotency_key`: Webhook冪等処理用UUID（UNIQUE制約）
- `expires_at`: `paid_at + 2年`（支払い完了時に自動設定）

**`organization_notification_balances`**
- `version`: JPA楽観的ロック用
- `credit_balance`: マイナス値を許容（猶予期間の負債）
- `grace_period_start_at` + `grace_period_debt`: 残高不足猶予の追跡

## アーキテクチャ

### 消費フロー

```
送信サービス（NotificationHelper / DirectMailService / ConfirmableNotificationService）
  ↓ consume(organizationId, recipientCount, sourceType)
NotificationCreditService
  ↓ PESSIMISTIC_WRITE で残高をロック
OrganizationNotificationBalanceEntity
  ├── 無料枠 → freeUsedThisMonth += freeToUse
  ├── クレジット残高 → creditBalance -= creditNeeded
  ├── 残高不足（初回）→ gracePeriodStart, gracePeriodDebt += debt
  ├── 残高不足（猶予内）→ gracePeriodDebt += debt
  └── 残高不足（猶予超過）→ throw BusinessException(CREDIT_INSUFFICIENT)
```

**無料枠 90% 超過アラートのトランザクション境界（Issue #2990）**: 9,000 通到達時のアラートは
`consume` の業務トランザクション内では送らない。`consume` は `NotificationCreditFreeQuotaAlertEvent`
を publish するだけに留め、`notification.credit.event.NotificationCreditFreeQuotaAlertListener` が
`AFTER_COMMIT` + `@Async("event-pool")` で受け取り、受信者（組織 ADMIN）ごとに
`NotificationDeliveryRunner#sendOne`（1 件 = 1 独立トランザクション）へ委譲する。

是正前は `@Async` 付きの `sendFreeQuotaAlertAsync` を同一クラス内から無修飾で自己呼び出ししており、
Spring プロキシを経ないため `@Async` が失効し、アラート送信が `consume` のトランザクション内で
同期実行されていた。通知側の DB 例外は rollback-only を残すため、`try/catch` で握っても
**クレジット消費（無料枠消費量・月次使用量・アラート送信済フラグ）ごと巻き戻っていた**。
実害の入口は `DirectMailService#sendMail`（一斉メール送信）である。

### 購入フロー

```
フロントエンド → POST /checkout → NotificationCreditCheckoutService
  → Stripe Price遅延生成（null の場合）
  → Stripe Customer取得/生成
  → notification_credit_purchases レコード PENDING で作成
  → Stripe Checkout Session作成（metadata: notificationCreditPurchaseId）
  → checkoutUrl を返す

Stripe Webhook (checkout.session.completed)
  → StripeWebhookService.handleCheckoutCompleted()
  → notificationCreditPurchaseId が metadata にある場合
  → NotificationCreditCheckoutService.handlePurchaseCompleted()
  → purchase.markAsPaid() + creditService.addCredits()
  → 監査ログ記録（NOTIFICATION_CREDIT_PURCHASED）
```

### バッチ処理

| バッチ | スケジュール | 処理内容 |
|---|---|---|
| `NotificationCreditMonthlyResetBatch` | 毎月1日 AM 2:00 JST | 猶予負債相殺・無料枠リセット |
| `NotificationCreditExpiryBatch` | 毎日 AM 3:00 JST | 期限アラート・失効処理 |

## 既存サービスへの変更

### NotificationHelper

```java
// 新規オーバーロード（isBillable + organizationId）
public void notifyAll(..., boolean isBillable, Long organizationId)
```

既存の呼び出し元はすべて `isBillable=false` の既存シグネチャを使用するため後方互換性あり。

### StripePaymentProvider

```java
// 新規メソッド（notificationCreditPurchaseId を metadata に含める）
CheckoutSessionInfo createNotificationCreditCheckoutSession(...)

// WebhookEventInfo に新フィールド追加
record WebhookEventInfo(..., Long notificationCreditPurchaseId)
```

### StripeWebhookService

```java
// checkout.session.completed の分岐追加
if (event.notificationCreditPurchaseId() != null) {
    notificationCreditCheckoutService.handlePurchaseCompleted(event);
} else {
    // 既存の memberPayment 処理
}
```

## OQ 解決済み一覧

| 質問 | 回答 |
|---|---|
| UUIDv7 vs BIGINT | マスタテーブル（packages）と既存 Stripe 基盤整合性のため BIGINT を採用。テナントスコープの purchases は将来の UUID 移行候補 |
| クロスドメイン依存（payment → notification） | StripeWebhookService が NotificationCreditCheckoutService に依存する構造。TODO コメントで将来のイベント駆動分離を明記 |
| チームスコープの確認通知課金 | 組織IDが不明のため ORGANIZATION スコープのみ課金対象。チームスコープは現在スキップ（将来 team→org 解決を追加） |
| 猶予期間中の送信制御 | 72時間以内は送信許可、超過後は BusinessException でブロック（根治治療の原則に従い、エラー握りつぶし禁止）|
| Webhook 冪等性 | `idempotency_key` に UNIQUE 制約を付与。PAID 済み購入はスキップして二重処理を防ぐ |
