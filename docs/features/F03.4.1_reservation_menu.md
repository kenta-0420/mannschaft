## 1. 概要

チームが提供するサービスメニュー（例: 「カット 60分」「整体 90分」「テーブル利用 120分」）をマスタとして定義する。メニューは**所要時間（30分の倍数）**を持ち、会員がメニューを選ぶと F03.4.3 の予約グループが**必要枠数（30分×N）を自動確保**する起点となる。

- **料金は表示のみ**（決済しない・マスター御裁可）。F08 決済連携は本設計のスコープ外。
- **チーム共通マスタ＋予約対象（ライン）ごとの提供可否**（マスター御裁可）。例: 「カット」は席1・席2で提供、「ヘッドスパ」は席1のみ。
- 既存の枠フリーテキスト `title` は**併存**する（メニュー未使用チームの後方互換。メニューは opt-in）。

> **過去決定の撤回**: 親 §8 で「予約枠のメニュー管理は FUTURE_CONSIDERATIONS に延期（多業種対応でマスター設計が困難）」としていたが、**2026-07-05 マスター御裁可で正式に撤回**。業種別スキーマを持たない「名前＋所要時間＋表示用料金」の最小モデル＋ライン別提供可否で多業種を吸収する。

### 用語

| 用語 | 意味 |
|---|---|
| メニュー | 本機能で定義するサービス項目（名前・所要時間・表示用料金） |
| ライン（予約対象） | `reservation_lines`。席・ベッド・施術台等（親 §3）。上限は F03.4.2 で 5→20 に拡張 |
| 提供可否 | メニュー×ラインの提供関係（`reservation_menu_lines`）。**行が 0 件のメニュー=全ラインで提供可**（既定・入力摩擦ゼロ） |
| 必要枠数 | `duration_minutes / 30`（30分セル枠の個数）。消費側は F03.4.3 |

> **共通枠と予約行のラインの関係（用語の固定・F03.4.2 §3.1 と同文）**: 予約は既存仕様上 `reservations.line_id` が **NOT NULL**（V3.062 実DDL）であり、共通枠（`slot.line_id IS NULL`）の予約では**ユーザーが選択したラインが `reservations.line_id` に入る**。メニューの提供可否判定は常にこの「予約行に入るライン」に対して行う。

## 2. スコープ

### 対象ロール

| ロール | 操作可能な範囲 |
|--------|--------------|
| ADMIN / DEPUTY_ADMIN（`MANAGE_RESERVATIONS`） | メニューの CRUD・提供可否設定・表示順・有効/無効 |
| MEMBER / SUPPORTER | 有効メニューの一覧閲覧（予約時の選択） |
| 公開ユーザー（`allow_public_reservation=TRUE` のチーム） | 有効メニューの一覧閲覧（会員と同じ view ゲート） |
| GUEST | 対象外 |

### スコープ外

- メニューの決済・在庫・キャンペーン価格（料金は `DECIMAL` の**表示専用**）
- メニューの組織（Organization）レベル共有（チーム単位のみ）
- メニュー別のスタッフ指名制約（提供可否は**ライン軸のみ**。スタッフ軸は将来拡張）

## 3. DB設計

### テーブル一覧

| テーブル名 | 役割 | 論理削除 |
|-----------|------|---------|
| `reservation_menus` | メニューマスタ（チーム単位・UUIDv7） | あり（`deleted_at`） |
| `reservation_menu_lines` | メニュー×ラインの提供可否（0件=全ライン提供可） | なし（物理削除） |

### `reservation_menus`

**新規テーブルのため主キーは UUIDv7（アーキ原則6・`UuidV7Entity` 継承）。`team_id` は teams ドメインへのクロスドメイン参照のため FK なし・インデックスのみ（アーキ原則1）。**

| カラム名 | 型 | NULL | デフォルト | 説明 |
|---------|---|------|-----------|------|
| `id` | BINARY(16) | NO | UUIDv7 | PK（`UuidV7Entity` 継承） |
| `team_id` | BIGINT UNSIGNED | NO | — | チームID（クロスドメイン参照・FKなし・INDEX。既存 `reservation_lines.team_id`＝V3.060 と同型の UNSIGNED に統一） |
| `name` | VARCHAR(100) | NO | — | メニュー名（例: 「カット」「整体60分コース」） |
| `duration_minutes` | INT | NO | — | 所要時間（分）。**30の倍数・30〜480**。`CHECK (duration_minutes % 30 = 0 AND duration_minutes BETWEEN 30 AND 480)` |
| `price` | DECIMAL(10,2) | YES | NULL | 表示用料金（**決済しない**）。NULL = 料金表示なし |
| `description` | VARCHAR(500) | YES | NULL | メニュー説明（会員向け表示） |
| `display_order` | INT | NO | 1 | 表示順（1〜20。チーム内。Service 層で範囲検証） |
| `is_active` | BOOLEAN | NO | TRUE | 有効/無効。FALSE は会員向け一覧・予約起点から除外（既存予約は影響なし） |
| `created_by` | BIGINT UNSIGNED | YES | NULL | 作成者 user_id（クロスドメイン参照・FKなし。既存 `reservation_slots.created_by`＝V3.061 と同型の UNSIGNED に統一） |
| `created_at` | DATETIME(6) | NO | — | |
| `updated_at` | DATETIME(6) | NO | — | |
| `deleted_at` | DATETIME(6) | YES | NULL | 論理削除（`@SQLRestriction("deleted_at IS NULL")`） |

**インデックス**
```sql
INDEX idx_rm_team (team_id, display_order)      -- チーム別メニュー一覧（表示順）
INDEX idx_rm_team_active (team_id, is_active)   -- 有効メニュー検索
```

**制約・備考**
- **上限: 1チームあたり最大 20 件**（論理削除済みは数えない。有効・無効は問わず数える）。21件目の作成は 400（RESERVATION_033）。
  - **20 の論拠**: 予約UIのメニュー選択ダイアログで1画面スクロール内に収まる実用上限（ADHD配慮=選択肢過多の回避）。美容室・整骨院・飲食のコースメニューの実態は 5〜15 件で P90 を包含。マスタは行数が小さくシャーディング負荷ではないため上限は UX 起点で決めた。
- `duration_minutes` の上限 480（=8時間・16枠）: 営業時間（親 §3 の既定 9:00-18:00）を超えるメニューは業態上想定外。F03.4.3 のグループ最大枠数（16枠）と同値で整合。
- **CHECK 制約は DB 最終防御・Service 層が一次検証**（400 = RESERVATION_034）。MySQL 8.0.16+ で CHECK は実 enforce される。
- `name` の同一チーム内重複は**許可**（「カット（新人）」「カット（指名）」等を別行にする運用があり、UNIQUE で縛ると業務を阻害する。誤重複は UI の一覧で視認可能）。
- メニュー削除（論理削除）: 既存予約グループ（F03.4.3 `reservations.menu_id`）からの参照は残る（履歴表示用に menu 行は物理削除しない）。削除済みメニューは新規予約の起点にできないだけで、既存予約の表示は `@SQLRestriction` を迂回する専用 `findByIdIncludingDeleted` で名前解決する。

### `reservation_menu_lines`

メニュー×ライン（予約対象）の提供可否。**同一ドメイン（reservation）内の親子のため FK を張る**（アーキ原則1・2 に適合: クロスドメインではない）。

| カラム名 | 型 | NULL | デフォルト | 説明 |
|---------|---|------|-----------|------|
| `menu_id` | BINARY(16) | NO | — | FK → `reservation_menus.id` **ON DELETE CASCADE**（同一ドメイン親子。メニュー物理削除時に提供可否行も同時削除で孤児行を防ぐ） |
| `line_id` | BIGINT UNSIGNED | NO | — | FK → `reservation_lines.id` **ON DELETE RESTRICT**（同一ドメイン。ラインは論理削除運用のため実質発火しない。物理削除を試みた場合の孤児行防止の番人） |
| `created_at` | DATETIME(6) | NO | — | |

**インデックス・制約**
```sql
PRIMARY KEY (menu_id, line_id)     -- 複合PK（提供関係は1組1行）
INDEX idx_rml_line (line_id)       -- ライン起点の提供メニュー逆引き（マトリックスUIのフィルター）
```

**CASCADE 可否の判断（明記）**
- `menu_id` への `ON DELETE CASCADE`: **採用**。`reservation_menus` と `reservation_menu_lines` は同一ドメイン（reservation）内の親子（提供可否はメニューの属性）であり、アーキ原則2「CASCADE DELETE は同一ドメイン内のみ許可」に適合。メニューは論理削除運用だが、テストデータ掃除・GDPR 起点の物理削除時に孤児行を残さない。
- `line_id` への CASCADE: **不採用（RESTRICT）**。ライン削除は「未来予約が存在すれば 409」の論理削除運用（親 §3）であり、提供可否行を黙って消すとメニューの提供範囲が音もなく変わる（暗黙の全ライン化 or 提供先消失）。RESTRICT で物理削除を止め、論理削除時は**アプリ層で提供可否行を明示削除**する（F03.4.2 §5 のライン削除フローに追記）。

**提供可否のセマンティクス（確定・入力摩擦ゼロ既定）**
- あるメニューの `reservation_menu_lines` 行が **0 件 = 全ライン（active な全予約対象）で提供可**（既定。作成直後は 0 件）。
- 行が **1 件以上 = 列挙されたラインのみ提供可**。
- 「全ラインで提供不可」を表現したい場合は `is_active = FALSE` を使う（空配列に意味を持たせない）。
- ラインが後から追加された場合: 行 0 件のメニューは自動的に新ラインでも提供可（全ライン提供のまま）。行列挙型のメニューは新ラインでは提供不可のまま（明示追加が必要）— この非対称は UI 上に注記する（i18n キー `reservation.menu.line_scope_note`）。

### ER図（追加分）

```
teams (1) ──── (N) reservation_menus            [チーム共通マスタ, FKなし]         ★機能E
reservation_menus (1) ──── (N) reservation_menu_lines   [提供可否, CASCADE]        ★機能E
reservation_lines (1) ──── (N) reservation_menu_lines   [提供先ライン, RESTRICT]   ★機能E
reservation_menus (1) ──── (N) reservations     [menu_id, nullable, F03.4.3 で追加] ★機能G
```

## 4. API設計

### エンドポイント一覧

| メソッド | パス | 認証 | 説明 |
|---------|-----|------|------|
| GET | `/api/v1/teams/{teamId}/reservation-menus` | 会員/公開（view ゲート） | メニュー一覧。会員/公開ユーザーは有効メニューのみ、ADMIN+ は無効含む全件 |
| POST | `/api/v1/teams/{teamId}/reservation-menus` | ADMIN+ | メニュー作成（最大20件） |
| PATCH | `/api/v1/teams/{teamId}/reservation-menus/{menuId}` | ADMIN+ | メニュー更新（部分更新・提供可否 `lineIds` 含む） |
| DELETE | `/api/v1/teams/{teamId}/reservation-menus/{menuId}` | ADMIN+ | メニュー削除（論理削除） |

- `ADMIN+` = ADMIN または `MANAGE_RESERVATIONS` 権限を持つ DEPUTY_ADMIN。管理系 3 本は `@PreAuthorize("@accessGuard.isScopeAdmin(authentication, #teamId, 'TEAM')")`（実シグネチャ3引数・親 §2 準拠）。
- GET は `@PreAuthorize` を付けず **Service 層で `ReservationViewAccessGuard.assertCanView(teamId, userId)`**（会員 or `allow_public_reservation`。非許可は 403 = RESERVATION_021）。予約作成・グリッド（機能C）と**同一述語を共有**する（親 §4.C の方針踏襲。独自述語の新設禁止 — `feedback_visibility_bypass_f00_audit`）。
- **ADMIN 判定による無効メニュー包含**: GET は view ゲート通過後、`accessControlService.isAdminOrAbove(userId, teamId, "TEAM")` が真なら `is_active=FALSE` も含めて返す（クエリパラメータでの切替は設けない。ロールで自動決定＝パラメータ改竄面を作らない）。

### `POST /api/v1/teams/{teamId}/reservation-menus`

**リクエストボディ**
```json
{
  "name": "カット",
  "durationMinutes": 60,
  "price": 4500.00,
  "description": "シャンプー・ブロー込み",
  "displayOrder": 1,
  "lineIds": [1, 2]

```

| フィールド | 型 | 必須 | バリデーション |
|-----------|---|------|-------------|
| `name` | String | Yes | 1〜100文字 |
| `durationMinutes` | Integer | Yes | 30の倍数・30〜480。違反は 400（RESERVATION_034） |
| `price` | BigDecimal | No | 0 以上・小数2桁以内。null = 料金非表示 |
| `description` | String | No | 最大500文字 |
| `displayOrder` | Integer | No | 1〜20。省略時は **`MAX(display_order) + 1`**（未削除行の最大値+1。「既存メニュー数+1」ではない — 論理削除で歯抜けになった番号との衝突を避ける。既存 0 件なら 1。MAX が既に 20 なら 20 のまま重複許容=下記の並び順規則で安定） |
| `lineIds` | Long[] | No | 省略/null/空配列 = 全ライン提供可。指定時は各 ID が当該チームの active ライン（`deleted_at IS NULL`）であること（不正 ID は 400 = RESERVATION_035） |

> **並び順の確定規則**: `display_order` はチーム内で**一意を強制しない**（親 `reservation_lines` と同方針）。一覧の並びは **`ORDER BY display_order ASC, created_at ASC, id ASC`** の三段ソートで決定的にする（同値時の順序が呼び出しごとに揺れない。UUIDv7 の `id` は時刻順のため最終タイブレークとして安定）。

> **request DTO の Jackson 手本（親 §4.B の再発地雷回避を踏襲）**: `@Getter @RequiredArgsConstructor` ＋ 全フィールド `final` ＋ **単一コンストラクタ**。`@Builder` 併用や複数コンストラクタは `@JsonCreator` / `@JsonProperty` 必須（無いと Jackson no Creators で実 POST 500）。`lineIds` の「省略=全ライン」の既定は final DTO では表現できないため **Service 層で null→空リスト正規化**する。

### `DELETE /api/v1/teams/{teamId}/reservation-menus/{menuId}`

論理削除。`reservation_menu_lines` 行は**物理削除しない**（menu 行が論理削除で不可視になるため実害なし。物理削除時は CASCADE で追従）。

**レスポンス（200 OK）**
```json
{ "data": { "id": "0198xx...uuid", "deletedAt": "2026-07-05T12:00:00+09:00" } }
```

**エラーレスポンス**
| ステータス | 条件 |
|-----------|------|
| 401 | 未認証 |
| 403 | ADMIN+ 以外 |
| 404 | メニュー不存在（RESERVATION_032） |

> **削除時に既存予約グループは壊さない**: 未来の予約グループが当該メニューを参照していても削除は**許可**する（ラインの「未来予約あり 409」とは非対称）。メニューは表示属性であり、削除してもグループの枠・時間は既に確保済みで業務が壊れないため。予約詳細のメニュー名は削除済み行から解決する（§3 備考）。

## 5. ビジネスロジック

### 実装方針（クラス構成）

| 層 | 新規クラス | 役割 |
|---|---|---|
| Controller | `ReservationMenuController` | 上記 4 エンドポイント。管理系に `@PreAuthorize` self-gate |

## 6. セキュリティ考慮事項

- **認可 self-gate**: 管理系 3 エンドポイントは `@PreAuthorize("@accessGuard.isScopeAdmin(authentication, #teamId, 'TEAM')")` を実装者が自分で付与（既存ゲートの存在を仮定しない・親 §6 の方針踏襲）。
- **view ゲートの一元化**: 会員向け GET の閲覧可否は `ReservationViewAccessGuard.assertCanView` に集約（予約作成・グリッドと同一述語）。独自の可視性述語を新設しない。
- **IDOR**: `{menuId}` は `findByIdAndTeamId` で解決し、他チームのメニューは 404（RESERVATION_032）で存在ごと隠蔽。
- **PII**: メニューは PII を含まない（name/price/description はチームの公開情報）。監査: メニューの作成・更新・削除は `audit_logs` に記録（親 §6 の監査対象に追加）。
- **入力サニタイズ**: `name` / `description` は XSS 対策として HTML タグ除去（親 §6 のフリーテキスト方針と同じ）。

## 8. 受け入れ条件（テスト可能・正常/異常/境界）

> `/試練` はここから red テストを起こす。観測点を明記した。

- **E-1（正常・作成）**: ADMIN が `name="カット", durationMinutes=60` で POST すると 201。レスポンスに `requiredSlotCount=2`・`lineIds=[]`（全ライン提供可）が含まれる。**観測点**: `reservation_menus` に 1 行（BINARY(16) PK）、`reservation_menu_lines` は 0 行。
- **E-2（正常・提供可否）**: `lineIds=[1,2]` 指定で POST すると `reservation_menu_lines` に 2 行でき、GET の `lineIds` が `[1,2]` で返る。
- **E-3（境界・所要時間）**: `durationMinutes=30`（下限）と `480`（上限）は 201。`45`（非30倍数）・`0`・`510`（上限超）は 400 = RESERVATION_034。
- **E-4（境界・上限件数）**: メニューが 19 件のとき 20 件目 POST は 201、20 件のとき 21 件目は 400 = RESERVATION_033。論理削除済みはカウントしない（20 件中 1 件削除→新規 POST 可）。
- **E-5（異常・提供可否不正）**: 他チームのライン ID / 削除済みライン ID を `lineIds` に含む POST は 400 = RESERVATION_035。
- **E-6（正常・部分更新）**: PATCH で `lineIds=[]` を送ると提供可否行が全削除され「全ライン提供可」へ戻る。`lineIds` 未指定 PATCH は提供可否が据え置き。`clearPrice=true` で `price` が null に戻る。
- **E-7（可視性）**: `is_active=FALSE` のメニューは会員 GET に現れず、ADMIN GET には現れる。非会員かつ非公開チームの GET は 403 = RESERVATION_021、未認証は 401。管理系 POST/PATCH/DELETE は非 ADMIN で 403。
- **E-8（削除と名前解決の足場・第一弾）**: メニュー DELETE は未来参照の有無に関わらず 200（論理削除）。**観測点（第一弾で red 化可能な範囲）**: `deleted_at` セット後も専用リポジトリメソッド `findByIdIncludingDeleted(menuId)`（`@SQLRestriction` 迂回のネイティブ/`@Query`）が当該行を返し、`name` が取得できること（リポジトリ IT）。※ `reservations.menu_id` は **F03.4.3（第二弾）で追加**されるカラムのため、「予約グループ詳細でメニュー名が解決できる」一気通貫の検証は**第二弾の AC（G-14）で行う**（第一弾では red テストを書けない — 弾境界の明記）。
- **E-9（IDOR）**: 他チームの `menuId` への PATCH/DELETE は 404 = RESERVATION_032（403 ではなく存在秘匿）。

## 9. エラーコード（採番仮置き）

> 現在の `ReservationErrorCode` の最大は **RESERVATION_031**（`NOTIFY_RECIPIENT_NOT_FOUND`・実 enum 確認済 2026-07-05）。v2 の採番は枝番 4.1→4.4 の順で **032 から通し**で仮置きする。**最終採番はマージ直前に origin/main の enum 実物で再確認**すること（並行 PR 衝突回避）。

| コード | 定数名（案） | 用途 | HTTP | Severity |
|---|---|---|---|---|
| RESERVATION_032 | `MENU_NOT_FOUND` | メニュー不存在（IDOR 秘匿含む） | 404 | WARN（個別マップで 404） |
| RESERVATION_033 | `MENU_LIMIT_EXCEEDED` | メニュー上限 20 件超過 | 400 | WARN |
| RESERVATION_034 | `INVALID_MENU_DURATION` | 所要時間が 30 の倍数でない / 30〜480 範囲外 | 400 | WARN |
| RESERVATION_035 | `MENU_LINE_IDS_INVALID` | **メニュー定義時（POST/PATCH）**の lineIds 不正（不正 ID / 他チーム / 削除済みライン） | 400 | WARN |

> **035 のスコープは「メニュー定義時」に限定**する。**予約時の「提供不可ラインでの確保」は別コード RESERVATION_043**（`GROUP_MENU_LINE_NOT_OFFERED`・F03.4.3 で採番）— 管理者の定義ミスと会員の予約時競合は発生文脈・利用者・FE 導線が異なるため、コードを分けて FE が出し分けられるようにする（意味衝突の回避・精査第1パス指摘12）。

（F03.4.2 は 036〜037、F03.4.3 は 038〜**043** を使用。F03.4.4 は新規コードなし）

## 11. 非機能・アーキ制約

- **UUIDv7（アーキ原則6）**: `reservation_menus` は `UuidV7Entity` 継承。`reservation_menu_lines` は複合自然キー（menu_id×line_id で1組1行のリレーション表であり、サロゲート不要。行はメニュー上限20×ライン上限20=最大400行/チームでシャーディング負荷にならない）。
- **クロスドメインFK禁止（アーキ原則1）**: `team_id` / `created_by` は FK なし・INDEX のみ。`menu_id`/`line_id` は同一ドメイン内 FK で整合を守る。
- **@Transactional はドメイン内（アーキ原則5）**: メニュー CRUD は reservation ドメインに閉じる。view ゲートの membership 解決は既存 `ReservationViewAccessGuard` 経由（新規越境なし）。
- **性能**: メニュー一覧は「メニュー最大20件 + menu_lines 最大400行」の 2 クエリで返る（N+1 なし）。キャッシュ不要の規模。
- **OpenAPI**: 新 DTO は `@Schema(name=...)` で一意名を付け、nested schema 同名衝突を避ける（`feedback_openapi_nested_schema_name_collision`）。BE 変更後は `docs/openapi.json` 再生成＋`npm run generate:types` を同一 PR で行う（`project_openapi_json_chronic_drift`）。
