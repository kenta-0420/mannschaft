## 1. 背景・課題

組織ページに「メンバー一覧（名簿）」と「メンバー紹介」という、同じ「メンバー」を含む2つの入口が
別々に存在し、利用者が迷う（台帳 CMP-260919-1140）。本機能では、上部タブ「メンバー」の下に
サブタブ「一覧」「紹介」を設け、1画面に統合する。あわせて、各サブタブが誰に見えるかを**サブタブ単位**で
管理者が指定できるようにする（項目単位の粒度は持たない）。

本ドキュメント（Phase 1）のスコープは **設計＋バックエンド基盤** のみ。FE のタブ統合実装は Phase 2
以降で別足軽が行う。

## 2. スコープ・確定仕様

マスター裁可済みの確定仕様:

1. サブタブは「一覧（名簿）」「紹介」の2つのみ。
2. 見せる範囲は **サブタブ単位** で管理者が設定する（項目（氏名／役割等）単位の粒度は持たない）。
3. 見せる範囲の値は既存 `com.mannschaft.app.dashboard.MinRole`（`PUBLIC` / `SUPPORTER` / `MEMBER`）を
   **そのまま再利用**する（新規 enum は作らない）。
4. **一覧タブは PUBLIC を選べない**（氏名・役割等の個人情報を含むため）。紹介タブは PUBLIC も可
   （連絡先を含まないため）。
5. 一覧・紹介とも **連絡先（メール／電話／住所）は返さない**。現状の
   `role/dto/MemberResponse`（userId/displayName/avatarUrl/roleName/joinedAt/calendarColor）も
   `member/dto/MemberProfileResponse`（displayName/bio/position/photo等）も連絡先を含まないことを
   実装前に確認済み。本機能はこの制約を維持し、連絡先項目を追加しない。
6. 紹介タブは既存の紹介機能（F06.2 / `TeamPageService` 等）をそのまま活かす（FE で埋め込む）。
   紹介の中の「年度ページごとの公開（`PUBLISHED`）／下書き（`DRAFT`）」は既存の
   `PageStatus` の仕組みを流用する。
7. **合成ルール（重要）**: 紹介タブは「外側の門＝タブの見せる範囲（min_role）」と「内側の扉＝
   年度ページの公開／非公開（`PageStatus`）」の二段。**両方を通った人だけが見える。厳しい方が勝つ**。
   下書き（`DRAFT`）ページは誰にも（ADMIN 除く）見せない。公開（`PUBLISHED`）ページは外側の門を
   通った人に見せる。
8. **FE で隠すだけでなく BE でも強制する**（直近の戦役で「FE のみ隠蔽・BE 素通り」欠陥を複数潰した
   経緯があるため、この失敗を繰り返さない）。

## 3. DB設計

### `member_subtab_role_visibility`

`dashboard_widget_role_visibility`（F02.2.1）と全く同じパターン: レコードがないサブタブは
アプリ層デフォルト（`MemberSubtabDefaultMinRoleMap`、両サブタブとも `MEMBER`）が適用される
遅延作成方式。

| カラム名 | 型 | NULL | デフォルト | 説明 |
|---------|---|------|-----------|------|
| `id` | BINARY(16) | NO | — | PK（UUIDv7。DB設計原則 #6） |
| `scope_type` | VARCHAR(20) | NO | — | `TEAM` / `ORGANIZATION`（Phase 1 は ORGANIZATION のみ実配線） |
| `scope_id` | BIGINT UNSIGNED | NO | — | スコープ ID（クロスドメインFK禁止・インデックスのみ） |
| `subtab_key` | VARCHAR(30) | NO | — | `member_list` / `member_profiles` |
| `min_role` | VARCHAR(20) | NO | — | `PUBLIC` / `SUPPORTER` / `MEMBER`（既存 `MinRole` 再利用） |
| `updated_by` | BIGINT UNSIGNED | NO | — | 最終更新者（users.id、監査用。クロスドメインFK禁止のためインデックスのみ） |
| `created_at` | DATETIME(6) | NO | CURRENT_TIMESTAMP(6) | |
| `updated_at` | DATETIME(6) | NO | CURRENT_TIMESTAMP(6) ON UPDATE | |

**インデックス**

```sql
UNIQUE KEY uq_msrv_scope_subtab (scope_type, scope_id, subtab_key)
INDEX idx_msrv_scope (scope_type, scope_id)
INDEX idx_msrv_updated_by (updated_by)
```

**制約・備考**

- `subtab_key` は `member_list` / `member_profiles` の2値のみ（Service 層検証）。
- `min_role` の3値検証は `MinRole.fromString`（既存）をそのまま利用。
- `member_list` への `PUBLIC` 設定は Service 層で拒否（422、`MEMBER_016`）。
- レコードがないサブタブはアプリ層デフォルト（`MEMBER`）が適用される。

## 4. API設計（Phase 1: 組織スコープのみ）

### エンドポイント一覧

| メソッド | パス | 認証 | 認可 | 説明 |
|---------|-----|------|------|------|
| GET | `/api/v1/organizations/{slug}/member-subtab-visibility` | 必要 | 誰でも呼べる（非メンバーはデフォルト値） | サブタブ可視性設定一覧 |
| PUT | `/api/v1/organizations/{slug}/member-subtab-visibility` | 必要 | ADMIN / DEPUTY_ADMIN | サブタブ可視性設定一括更新 |

GET は F02.2.1 の `DashboardWidgetVisibilityService.getSettings` と同じ方針で、非メンバーでも
403 にはせず、DB を参照せずアプリ定義のデフォルト値を返す（可視性設定自体は機密情報ではなく、
コンソールエラー抑制を優先するため）。

### `PUT` リクエスト例

```json
{
  "subtabs": [
    { "subtabKey": "member_profiles", "minRole": "PUBLIC" },
    { "subtabKey": "member_list", "minRole": "MEMBER" }
  ]
}
```

**動作**:
- `min_role` がアプリ層デフォルト（`MEMBER`）と一致する場合、DB レコードを **DELETE**（テーブル肥大化防止）。
- 不一致の場合は UPSERT。
- `subtabKey` が未知の場合は 400（`COMMON_001`）。
- `subtabKey=member_list` に `minRole=PUBLIC` を指定した場合は **422**（`MEMBER_016`）。
- 監査ログ（`audit_logs`）に `MEMBER_SUBTAB_VISIBILITY_UPDATED` 種別で記録。

**認可**: ADMIN は無条件で可。DEPUTY_ADMIN は新規パーミッション `MEMBER_SUBTAB_VISIBILITY_MANAGE`
（scope=`ORGANIZATION`）を保有する場合のみ可（V219 で ADMIN にデフォルト付与・DEPUTY_ADMIN は天井のみ登録）。
それ以外は 403。Service 層入口で検証（Controller の `@PreAuthorize("isAuthenticated()")` は第一防御のみ）。

## 5. 既存 API への「外側の門」ゲート追加

### 5.1 名簿 `GET /api/v1/organizations/{slug}/members`

`OrganizationController#getMembers` に、既存の `contentVisibilityChecker.assertCanView(ORGANIZATION, id, viewer)`
の**後**に、`MemberSubtabVisibilityService#assertViewable(viewer, ORGANIZATION, id, MEMBER_LIST)` を追加。
非該当なら `BusinessException(COMMON_002)` → 403。

```java
contentVisibilityChecker.assertCanView(
        ReferenceType.ORGANIZATION, id, SecurityUtils.getCurrentUserIdOrNull());
// CMP-260919-1140 Phase 1: メンバー統合画面「一覧」サブタブの外側の門（管理者が設定した min_role）。
memberSubtabVisibilityService.assertViewable(
        SecurityUtils.getCurrentUserIdOrNull(), ScopeType.ORGANIZATION, id, MemberSubtabKey.MEMBER_LIST);
return ResponseEntity.ok(organizationService.getMembers(id, pageable));
```

既定値（`MEMBER`）の場合、閲覧者ロールが `MEMBER` 未満（`SUPPORTER`／`PUBLIC`）なら拒否される。これは
「メンバーのみが名簿を見られる」という現状の実運用上の想定と等価であり、テストで回帰を担保する
（`OrganizationControllerTest#getMembers_200` / `#getMembers_subtabGateDenied_throws`）。

### 5.2 紹介 `GET /api/v1/team/pages`・`GET /api/v1/team/pages/{id}`（`TeamPageService`）

`TeamPageService#listPages` と `#checkPageMembershipOrNotFound`（`getPage` から呼ばれる）を、
組織スコープ限定で「外側の門（min_role）× 内側の扉（PageStatus）」の合成判定に拡張した。

**`checkPageMembershipOrNotFound` の新ロジック**（設計書 §2 の合成ルールをそのまま反映）:

```java
void checkPageMembershipOrNotFound(Long actorUserId, TeamPageEntity page) {
    Long scopeId = resolveScopeId(page);
    String scopeType = resolveScopeType(page);

    // ADMIN/DEPUTY_ADMIN 以上は常に全ページ閲覧可（下書き含む）
    if (accessControlService.isAdminOrAbove(actorUserId, scopeId, scopeType)) {
        return;
    }

    // 内側の扉: 下書き（DRAFT）ページは ADMIN 以外の誰にも見せない
    if (page.getStatus() == PageStatus.DRAFT) {
        throw new BusinessException(MemberErrorCode.PAGE_NOT_FOUND);
    }

    // 外側の門: 組織スコープは「紹介」サブタブの min_role で判定（Phase 1 対象。チームは対象外）
    if (SCOPE_ORGANIZATION.equals(scopeType)) {
        try {
            memberSubtabVisibilityService.assertViewable(
                    actorUserId, ScopeType.ORGANIZATION, scopeId, MemberSubtabKey.MEMBER_PROFILES);
        } catch (BusinessException ex) {
            // Wave3-B2 member BOLA対策の 404 秘匿パターンを維持（403 ではなく 404 を返す）
            throw new BusinessException(MemberErrorCode.PAGE_NOT_FOUND);
        }
        return;
    }

    // TEAM スコープは Phase 1 対象外・従来どおり
    if (!accessControlService.isMember(actorUserId, scopeId, scopeType)) {
        throw new BusinessException(MemberErrorCode.PAGE_NOT_FOUND);
    }
}
```

`listPages` の組織ブランチも同様に、`checkMembership` を `assertViewable(..., MEMBER_PROFILES)` へ置き換え、
非管理者には `PageStatus.PUBLISHED` のみ返す（下書きは一覧からも除外。`TeamPageRepository` の
既存メソッド `findByOrganizationIdAndStatusOrderBySortOrder` を利用）。

### 5.3 既知の挙動変化（意図的な仕様反映であり、対処療法ではない）

- **下書きページの秘匿強化**: 従来 `checkPageMembershipOrNotFound` は `PageStatus` を一切見ておらず、
  メンバーであれば DRAFT ページも `getPage` で閲覧でき、`listPages` の一覧にも出ていた。本機能の
  合成ルール（§2 仕様7、マスター裁可済み）により、DRAFT ページは ADMIN 以外に見せない仕様へ改める。
  これは既存バグの隠蔽的な現状追認ではなく、マスター裁可済みの合成ルールをそのまま実装したもの。
- **紹介タブを PUBLIC に設定した場合の開放**: 既定値（`MEMBER`）のままなら現状と等価だが、管理者が
  `member_profiles` を `PUBLIC` に変更すると、従来 `checkMembership` で一律 403/404 だった非メンバーにも
  `PUBLISHED` ページが開放される。これは本機能の目的（紹介タブは連絡先を含まないため PUBLIC 開放可能に
  する）そのものであり、意図した挙動。

## 8. セキュリティ考慮事項

- **二重防御**: Controller の `@PreAuthorize("isAuthenticated()")` は第一防御に過ぎず、実際の可視性判定は
  すべて Service 層（`MemberSubtabVisibilityService#assertViewable` / `#checkUpdatePermission`）で行う。
  FE のタブ非表示だけに頼らない（マスター指示の絶対条件）。
- **連絡先の非露出**: 一覧・紹介とも既存 DTO（`role/dto/MemberResponse` / `member/dto/MemberProfileResponse`）
  に連絡先フィールドを追加しない。本機能はゲートのみを追加し、レスポンスの形は変更しない。
- **404秘匿パターンの維持**: 紹介ページ詳細（bare id エンドポイント）は Wave3-B2 の BOLA 対策に従い、
  権限不足時も 403 ではなく 404（`PAGE_NOT_FOUND`）で存在を秘匿する。本機能の外側の門判定も、
  例外を `MemberErrorCode.PAGE_NOT_FOUND` に変換してこのパターンを維持する。
- **監査ログ**: 可視性設定の変更は `audit_logs` に `MEMBER_SUBTAB_VISIBILITY_UPDATED` で記録（誰が・
  いつ・どのスコープの・どのサブタブを・どう変更したか）。
