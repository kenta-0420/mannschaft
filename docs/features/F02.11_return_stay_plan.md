# F02.11: 帰省・滞在予定

> **ステータス**: 🟡 設計精査中
> **対象**: 個人ダッシュボードとチームのメンバー一覧
> **関連**: [F02.2 マイダッシュボード](F02.2_dashboard.md)、[F01.2 組織・チーム・メンバー・ロール](F01.2_org_team_member_role.md)、[F00 ContentVisibilityResolver](F00_content_visibility_resolver.md)、[F09.16 居住実態管理・見守り](F09.16_residence_status_management.md)

## 1. 目的と非目的

本人が個人ダッシュボードで、帰省または滞在の予定を複数管理し、所属チームごとに明示して共有する。チームでは、未来は「帰省予定／滞在予定」、期間中は「帰省中／滞在中」をメンバー名の横の pill と詳細一覧で知ることができる。

これは本人の任意の行動予定であり、住所台帳、安否確認、推定死亡スコア、見守り同意、`expected_absence_periods`、`ResidentActivityUpdatedEvent`、F09.15/16 の封緘見守りデータとは**絶対に統合しない**。相互参照は誤利用防止の注意書きのみで、テーブル、イベント、API、権限、監査レコードを共用しない。

初回実装は国内の都道府県だけを示す。市区町村、詳細住所、座標、郵便番号、移動手段、理由、メモは保存も API 入力も禁止する。

## 2. 用語・制約

| 項目 | 定義 |
|---|---|
| 種別 | `HOMECOMING`（帰省）／`STAYING`（滞在） |
| 期間 | `startDate` と `endDate` がともに `LocalDate`、両端を含む。時刻は持たない |
| 国内地点 | `locationCountryCode='JP'` と JIS X 0401 の都道府県コード（`01`〜`47`）。表示名は i18n カタログで解決 |
| 将来の海外 | ISO 3166-1 alpha-2 の `countryCode` と任意の `regionName`（最大100文字）を追加可能な列で予約する。初回 API は `JP` 以外を拒否 |
| 表示状態 | 保存しない。本人の IANA timezone の当日と比較して `UPCOMING` / `ACTIVE` / `ENDED` を都度算出 |

- 予定は開始日順（同日なら `createdAt`、`id`）に表示し、期間の重複を許可する。
- 作成・更新時点で `startDate >= viewerToday`、`endDate >= startDate`、`endDate <= viewerToday + 365日` とする。365日は過剰な将来行動予定の露出を抑え、年次予定に十分な上限である。
- 1ユーザー最大30件（終了済みを含めず、`end_date >= viewerToday` の件数）。公開先は0チームから開始し、0件は「下書き／非公開」として本人だけに見える。
- チーム公開先はその時点で active な本人の `MEMBER` 以上のチームだけ。1予定最大20チーム。全選択／全解除は、候補（active `MEMBER` 以上）のみへ作用する。

## 3. 認可・プライバシー境界

| 操作 | 認可 | 備考 |
|---|---|---|
| 本人CRUD・公開先変更 | 認証済み本人 | self-scoped endpoint。所有者条件を Service でも必ず検証 |
| チーム一覧・pill・詳細 | 対象チームの active `MEMBER` / `DEPUTY_ADMIN` / `ADMIN` | `SUPPORTER`、`PUBLIC`、未所属者は不可。管理権限だけによる横断閲覧は不可 |
| SYSTEM_ADMIN | 原則不可 | 運用者権限はチーム可視性を迂回しない。法令対応等の緊急開示は本機能外で、別の承認・監査済み break-glass 手続を新設するまで提供しない |

可視性は予定単位ではなく `return_stay_plan_team_visibilities` の存在で決まる。予定を取得した後に権限をフィルタするのではなく、SQL の起点を閲覧者の active membership と可視性行の結合にする。予定 ID 直指定の他人／非公開／脱退済みは一律 `404` とし存在を秘匿する。

本人がチームを脱退・除名されたときは、その `team_id` の可視性行を即時物理削除する（予定本体は残す）。チーム削除時も同様に可視性行のみを削除する。閲覧クエリは active membership と `teams.deleted_at IS NULL` を必須にするため、非同期削除失敗中にも表示しない。

F00 の ContentVisibilityResolver は投稿等の汎用コンテンツ公開を扱う。本機能は team allow-list の最小可視性であり、コルクボード参照、`reference_id_uuid`、timeline、検索索引、通知、公開 API の対象外であるため、F00 の `ReferenceType` は追加しない。

## 4. データ設計

`docs/architecture/domain_db_design_principles.md` の原則6により新規 Entity は `UuidV7Entity`、主キーは `BINARY(16)` UUIDv7 とする。いずれもユーザー個人ドメインで `organization_id` を持たないため原則7の `AbstractTenantAwareRepository` は不適用とし、Repository の全メソッドに `owner_user_id` 又は閲覧者 membership の条件を必須化する。`users`／`teams`／`team_memberships` は別ドメインなので FK を張らず、BINARY(16)列 + index のみとする。

### 4.1 `return_stay_plans`

| 列 | 型 / NULL | 内容 |
|---|---|---|
| `id` | BINARY(16) / NO | UUIDv7 PK |
| `owner_user_id` | BINARY(16) / NO | 所有者。cross-domain FKなし |
| `plan_type` | VARCHAR(16) ascii_bin / NO | `HOMECOMING` / `STAYING` |
| `location_country_code` | CHAR(2) ascii_bin / NO | 初回は `JP` 固定 |
| `prefecture_code` | CHAR(2) ascii_bin / YES | 国内時必須、JIS 2桁 |
| `region_name` | VARCHAR(100) utf8mb4_0900_as_ci / YES | 将来海外のみ。初回はNULL固定 |
| `start_date`, `end_date` | DATE / NO | 両端含む |
| `created_at`, `updated_at` | DATETIME(6) / NO | UTC。`updated_at` は更新時更新 |
| `version` | BIGINT / NO | 0開始の楽観ロック |

```sql
PRIMARY KEY (id),
KEY idx_rsp_owner_active (owner_user_id, end_date, start_date, id),
KEY idx_rsp_owner_start (owner_user_id, start_date, created_at, id),
CHECK (plan_type IN ('HOMECOMING','STAYING')),
CHECK (end_date >= start_date),
CHECK (
 (location_country_code = 'JP' AND prefecture_code BETWEEN '01' AND '47' AND region_name IS NULL)
 OR (location_country_code <> 'JP' AND prefecture_code IS NULL AND region_name IS NOT NULL)
)
```

### 4.2 `return_stay_plan_team_visibilities`

| 列 | 型 / NULL | 内容 |
|---|---|---|
| `id` | BINARY(16) / NO | UUIDv7 PK |
| `plan_id` | BINARY(16) / NO | 同一ドメイン親。FK + `ON DELETE CASCADE` |
| `team_id` | BINARY(16) / NO | cross-domain FKなし |
| `created_at` | DATETIME(6) / NO | UTC |

```sql
PRIMARY KEY (id),
UNIQUE KEY uq_rsptv_plan_team (plan_id, team_id),
KEY idx_rsptv_team_plan (team_id, plan_id),
CONSTRAINT fk_rsptv_plan FOREIGN KEY (plan_id) REFERENCES return_stay_plans(id) ON DELETE CASCADE
```

全テーブルの文字列照合順序は列単位で明示し、テーブル既定は `utf8mb4_0900_as_ci`。列・index・check・unique・`version`・`created_at`・`updated_at` は Flyway 実装時に番人テスト対象と照合する。候補 migration は `V185.{UTC timestamp}__create_return_stay_plans.sql`。**major 185 は origin/main 現在値184からの仮置きであり、マージ時に origin/main 最大 major + 1 を再確認して採番する。**

## 5. API 契約（`/api/v1`、JSONは lowerCamelCase）

全日時は日付文字列 `YYYY-MM-DD`、UUIDは canonical string。リクエスト未知フィールドは400。本人 endpoint は F00 不要、チーム endpoint も F00 を使わず本機能固有の allow-list guard で判定する。

| Endpoint | request / response | 認可・ページング |
|---|---|---|
| `GET /me/return-stay-plans` | `?includeEnded=false`。`{items:[Plan], serverDate, timezone}` | 本人。件数上限30のためページングなし。`teamIds` は空配列可 |
| `POST /me/return-stay-plans` | `{planType,location:{countryCode,prefectureCode,regionName},startDate,endDate,teamIds,version?}` → `201 Plan` | 本人。`teamIds` 未指定／`[]`は0公開 |
| `PUT /me/return-stay-plans/{planId}` | POST同等の全置換 + 必須`version` → `200 Plan` | 本人のみ、競合409 |
| `DELETE /me/return-stay-plans/{planId}` | bodyなし → `204` | 本人のみ。本人以外・不在は404 |
| `GET /teams/{teamId}/members/return-stay-plans` | `?memberIds=<UUID複数>&date=YYYY-MM-DD` → `{items:[MemberPlans]}` | active MEMBER以上。memberIds最大100、対象チームのメンバーだけを1クエリ群で取得。ページングなし（メンバー一覧のバッチ補助） |
| `GET /teams/{teamId}/members/{memberId}/return-stay-plans` | `?from&to&page=0&size=20` → `Page<Plan>` | active MEMBER以上。`size` 1–50、開始日昇順。`totalElements/totalPages` は正しい count query を返す |

`Plan`: `{id, planType, location:{countryCode,prefectureCode:null|string,regionName:null|string}, startDate,endDate,displayStatus,teamIds,version,createdAt,updatedAt}`。初回国内では `countryCode='JP'`、`prefectureCode` 非null、`regionName=null`。`MemberPlans` は `{memberId, plans:[TeamPlan]}`、`TeamPlan` は公開先の teamId を返さず、`id,planType,location,startDate,endDate,displayStatus` のみを返す。0件は `items:[]`、該当 memberId がない／閲覧不可は行を返さず、エラーにより存在を示さない。

クライアントは自機の時計を信頼せず `serverDate` と保存済み timezone を使う。サーバーは `ZoneId.of(user.timezone)` で `LocalDate.now(zone)` を固定して、同一リクエスト内で状態・上限・応答を一貫算出する。timezone 未設定は既存ユーザー設定の既定 `Asia/Tokyo` を利用し、無効timezoneは400にする。

## 6. 状態遷移・整合性

```
保存（非公開 teamIds=[]） --公開先を1件以上選択--> 公開
公開 --全解除/脱退/チーム削除--> 非公開
today < startDate: UPCOMING → startDate <= today <= endDate: ACTIVE → endDate < today: ENDED（チームでは非表示）
```

`ENDED` は論理状態で、削除やバッチ更新を行わない。更新は予定行と可視性行を同一 transaction で置換し、候補チームの active membership をロックなし再検証する。途中で脱退した場合は transaction をロールバックし、`RETURN_STAY_PLAN_006` を返す。削除は親行削除により同一ドメイン子を CASCADE する。

## 7. エラー契約候補

`ReturnStayPlanErrorCode` を新設する。採番は実装開始時に既存最大値 + 1 を予約し、マージ直前にも再確認する（ここに示す suffix は仮）。HTTP map は `GlobalExceptionHandler` の明示登録と契約ITを同時に追加する。

| 仮コード | HTTP | Severity | 条件 |
|---|---:|---|---|
| `RETURN_STAY_PLAN_001` | 404 | WARN | 予定不在・他人の予定（存在秘匿） |
| `_002` | 400 | WARN | 日付、種別、国内地点、timezone、海外初回拒否の検証失敗 |
| `_003` | 409 | WARN | 30件／20チーム上限超過 |
| `_004` | 409 | WARN | optimistic lock競合 |
| `_005` | 403 | WARN | `SUPPORTER`/`PUBLIC` 等チーム閲覧不可 |
| `_006` | 409 | WARN | 公開先がactive MEMBER以上でなくなった途中失敗 |
| `_007` | 400 | WARN | memberIds 100件・page/size範囲超過 |

## 8. Backend / Frontend 構成

- Backend: `returnstayplan/` に `ReturnStayPlanEntity`, `ReturnStayPlanTeamVisibilityEntity`, 各 Repository, `ReturnStayPlanService`, `ReturnStayPlanTeamQueryService`, `ReturnStayPlanController`, DTO, mapper, error enum を置く。Controllerは `@SelfScopedEndpoint`、Serviceに `@AuthorizedInService` 相当の所有者・membership guard を置く。既存の `backend/src/main/java/com/mannschaft/app/common/entity/UuidV7Entity.java`、`common/exception/GlobalExceptionHandler.java`、F00の resolver 実装を根拠として踏襲する。
- バッチ: `findVisiblePlansForTeamAndMemberIds(teamId, memberIds, today)` は membership→visibility→plan の set-based query とし、対象ユーザーごとの query を発行しない。期間条件は `end_date >= today AND start_date <= today + 365日`、終了済みは除外する。1000万ユーザーでも shard key は `owner_user_id`、チーム読取は `team_id` index から候補 plan を引く。将来チーム規模が大きければ `team_id` を可視性行に持つ現設計のまま teamId hash shard／read model を追加可能で、予定本体の再配置を強制しない。
- Frontend: `frontend/app/composables/useReturnStayPlanApi.ts`、個人 dashboard widget `ReturnStayPlanWidget.vue`、チーム member list の `ReturnStayPlanPill.vue` と詳細 dialog を追加する。全選択／全解除には選択数と「管理者も未選択チームを閲覧できない」を表示する。自動表示は期限終了時に消え、通知・公開検索・SSRキャッシュへ混入させない。
- i18n: `frontend/app/locales/{ja,en,zh,ko,es,de}/return_stay_plan.json` を6言語同一keyで追加する。種別・状態・47都道府県・フォーム検証・空状態・公開先注意・エラーを含め、ハードコードしない。

## 9. PII・保持・監査

本データは正確な住所ではないが、行動予定に当たりセンシティブな準個人情報として最小化する。APIレスポンス、例外、監査ログ、アクセスログ、metrics、tracing に地点名・期間・teamIdsを出力しない。監査は「本人が予定を作成／更新／削除／公開先を変更した」のみで、予定内容は保存せず actor/planId/時刻/操作種別を10年保持する既存監査方針に従う。チーム閲覧は個別アクセス監査を行わず集計のみとし、閲覧行動が更なる行動履歴にならないようにする。

退会・GDPR消去では `owner_user_id` 条件で予定と可視性行を同一 purge transaction で即時物理削除し、export には本人の現存予定・終了済み保持分を含める。バックアップの保持・消去は既存GDPR運用に従う。チーム脱退／削除は前述の公開先行のみ即時削除する。

## 10. テスト可能な受入条件・試練マップ

| AC | 検証 |
|---|---|
| AC-01 正常 | 本人が国内2予定（重複可）を作成、別々の公開先を選び、未来／期間中で正しい文言になる |
| AC-02 空・0・null | `teamIds=[]` は保存可・本人だけ表示、チーム側は空配列。国内の`regionName=null`、海外列のnullable契約を確認 |
| AC-03 境界 | 当日開始・当日終了はACTIVE、前日はUPCOMING、翌日は非表示。365日ちょうど可、366日不可。30件可／31件不可、20チーム可／21件不可 |
| AC-04 入力 | end<start、都道府県外コード、JPでregionName、海外country、無効timezone、未知JSON fieldは400 |
| AC-05 途中失敗 | 更新transaction中に公開先membershipを失うと409、予定・可視性とも部分更新しない。version競合も409 |
| AC-06 認可 | 他人CRUDは404、未公開チームのADMIN・SYSTEM_ADMIN・SUPPORTER・PUBLIC・脱退者は閲覧不可。対象TEAM active MEMBER以上だけ可 |
| AC-07 自動非表示 | 脱退・チーム削除後、同期queryで即時非表示かつ可視性行削除。終了予定も非表示 |
| AC-08 性能 | 100 memberIds、各30予定で SQL回数定数（計画2〜3 query、N+1ゼロ）、p95 200ms以内をTestcontainersの explain/index確認と repository spy で検証 |
| AC-09 互換 | 既存 dashboard / member list APIのレスポンスを変更せず、新規バッチ endpoint の失敗は pill非表示＋明示エラー（黙殺しない） |
| AC-10 i18n・E2E | 6言語キー完全性、個人作成→team閲覧→公開解除→脱退→不可視をPlaywright実機で確認 |

試練では Entity/DDL番人（UUIDv7・cross-domain FKゼロ・collation・index/check/version）、Service unit（状態・上限・timezone・transaction）、Controller/Scope Contract（404秘匿・403ロール）、Repository integration（バッチ・pagination count・EXPLAIN）、OpenAPI生成型、6言語キー、Playwrightを必須とする。実機E2Eは異なるtimezoneの本人、MEMBER、SUPPORTER、TEAM ADMIN、SYSTEM_ADMIN、脱退処理を含む6アカウントで行う。
