# F02.11: 帰省・滞在予定

> **ステータス**: 🟢 設計完了
> **関連**: [F02.2](F02.2_dashboard.md) / [F01.2](F01.2_org_team_member_role.md) / [F00](F00_content_visibility_resolver.md) / [F10.X](F10.X_batch_catalog.md)

## 1. 目的と状態

本人が個人ダッシュボードで帰省・滞在予定を作成し、表示ラベルを「帰省中」(`HOMECOMING`) / 「滞在中」(`STAYING`) から選ぶ。予定は複数 TEAM に公開でき、公開したくない TEAM は個別に外せる。TEAM のメンバー一覧は、公開中の予定を pill と詳細 dialog で表示し、飲み会等の誘いを判断しやすくする。

`startDate`/`endDate` は `LocalDate`。国内新規 plan の timezone snapshot は `Asia/Tokyo`、将来の海外は明示 IANA timezone とする。状態算出は全読取・更新で `ownerToday = LocalDate.now(ZoneId.of(plan.timezone))` を用い、`UPCOMING` / `ACTIVE` / `ENDED` を決める。ACTIVE は公開ON/OFF、公開先、任意地域、終了日の当日以後への延長のみ変更可。他の日付・planType・timezone は400。

| 項目 | 制約 |
|---|---|
| `planType` | `HOMECOMING` / `STAYING` |
| 日付 | `endDate >= startDate`、開始は ownerToday 以降、終了は ownerToday+365日以内 |
| 国内場所 | `countryCode='JP'`、`prefectureCode` は `^(0[1-9]|[1-3][0-9]|4[0-7])$`、`regionName=null` |
| 将来の海外 | ISO 3166-1 alpha-2 と trim済み `regionName`（最大100）、`prefectureCode=null`。feature flag 前は400 |
| 公開 | `isPublished=true` は `teamIds` 1..20 を必須。OFF は `teamIds` を保持し、後から所属した TEAM は自動追加しない |
| 件数 | owner の ACTIVE/UPCOMING 合計30、1 plan の公開先20 TEAM |

## 2. 認可・並行性・DDL

本人 collection（一覧・作成）だけに `@SelfScopedEndpoint` を付ける。planId を受ける item は同注釈を付けず、`ReturnStayPlanAccessGuard.findByIdAndOwnerUserId` を使い、他者・存在しない item は404。team batch/detail は viewer と owner の双方について active user、`memberships.scope_type='TEAM' AND role_kind='MEMBER' AND left_at IS NULL`、未削除・未archive TEAM、`is_published=1` と allow-list を単一SQLで確認する。ADMIN/DEPUTY_ADMIN は既存 memberships では `MEMBER` として扱う。

slug 不存在、TEAM削除/archive、未所属、SUPPORTER、無所属 SYSTEM_ADMIN は team batch/detail とも一律404（存在秘匿）。所属 MEMBER のみ可。`teamIds` 保存候補が同条件を満たさない場合も404。F02.2 の一般的 SYSTEM_ADMIN 例外は本機能に適用しない。これらと owner/viewer 脱退・公開先変更競合を IT で確認する。

`return_stay_plans`: `id BINARY(16) PK`、`owner_user_id BIGINT UNSIGNED`、planType、公開フラグ、場所、`timezone VARCHAR(64)`、日付、`version BIGINT`、audit列。`idx_rsp_owner_end(owner_user_id,end_date,start_date,id)` と history index、日付・場所 CHECK を置く。`return_stay_plan_team_visibilities` は `plan_id/team_id` UNIQUE、plan FK CASCADE、team FKなし、`idx_rsptv_team_plan(team_id,plan_id)`。

users 行は lock しない。`return_stay_plan_owner_locks` は `id BINARY(16) UUIDv7 PK`、`owner_user_id BIGINT UNSIGNED UNIQUE`、audit列。create と active 件数を増やす update は、同一 transaction で insert-if-absent（UNIQUE競合時再読込）→ owner lock を `FOR UPDATE` → active件数count → 検証・保存する。Flyway は origin/main の最新 major+1 を採番し、3表・index/check/unique/collation/version/auditを同時追加する。

## 3. API と DTO 契約

全 API は `/api/v1`、lowerCamelCase。通常は `ApiResponse<T>` の `{data:T}`、ページングは `PagedResponse<T>` の `{data:[...],meta:{total,page,size,totalPages}}` であり、二重 wrapper にしない。timestamp は既存 serializer の offset ISO-8601、日付は `YYYY-MM-DD`。

| endpoint | 契約 |
|---|---|
| `GET /me/return-stay-plans` | `includeEnded=false`、`page=0`（0以上）、`size=20`（1..100）。`PagedResponse<OwnPlan>` |
| `POST /me/return-stay-plans` | Create request、201 `{data:OwnPlan}`。新規国内 timezone は `Asia/Tokyo` |
| `GET/PUT/DELETE /me/return-stay-plans/{planId}` | `{data:OwnPlan}` / Update request / 204。PUT はversion必須、競合409 |
| `GET /teams/{slug}/members/return-stay-plans` | repeated query `memberIds=1&memberIds=2`、1..400。`{data:{items:[{memberId,plans:[TeamPlan]}]}}` |
| `GET /teams/{slug}/members/{memberId}/return-stay-plans` | `{data:[TeamPlan]}`（ページ化なし、ENDEDなし） |

| DTO | 必須・null不可 | 任意/null | enum・形式 |
|---|---|---|---|
| Create/Update request | `planType`,`isPublished`,`location`,`startDate`,`endDate`,`teamIds` | `location.prefectureCode`,`location.regionName` | 上表。OFFでもteamIds配列必須（保持用） |
| `OwnPlan` | `id`,`planType`,`isPublished`,`location`,`timezone`,`startDate`,`endDate`,`teamIds`,`version`,`createdAt`,`updatedAt` | location内の非該当地域 | id UUID文字列、timestamp offset ISO |
| `TeamPlan` | `id`,`ownerDisplayName`,`planType`,`location`,`timezone`,`startDate`,`endDate`,`status` | `ownerAvatarUrl`、location内の非該当地域 | `status`: `UPCOMING`/`ACTIVE`。公開先・versionは返さない |

unknown fields は既存 Jackson unknown-property 拒否と Bean Validation で400。`RETURN_STAY_PLAN_001` を予約し、NOT_FOUND=404、INVALID_REQUEST/LIMIT/PAGING=400、VERSION_CONFLICT/MEMBERSHIP_CHANGED=409、TEAM_ACCESS=404とする。OpenAPI は `cd backend && ./gradlew.bat generateOpenApiDocs` で更新し、生成物差分なしをCI gateにする。

## 4. UI・i18n・性能

個人 widget の正式 key は `RETURN_STAY_PLAN`。登録点は `frontend/app/composables/useDashboardWidgets.ts` の `WidgetKeyMap`（`return-stay-plan`→`RETURN_STAY_PLAN`）と `ALL_WIDGETS`、`backend/src/main/java/com/mannschaft/app/dashboard/WidgetKey.java` の enum（labelは F02.2 表）、`frontend/app/components/dashboard/DashboardPersonalPanel.vue` の `PERSONAL_DATA_WIDGET_KEYS`、`WidgetReturnStayPlan` import/render、既存 `useDashboardWidgets('personal')` による既定順・設定永続化である。F02.2 の個人ウィジェット表にも同 key を載せる。

TEAM の pill は `frontend/app/components/MemberTable.vue` の team 表示だけで専用 `useReturnStayPlanTeamApi.ts` を呼ぶ。既存 `useTeamMembers.ts` とその無関係な利用者に追加fetchしない。表示 memberId を400件ずつ batch 呼出し、`memberId` でmergeし、未返却 member は `plans:[]`。scope/ページ変更・unmount は AbortControllerで取消し、世代の古い応答を捨てる。いずれかのchunk失敗時は fail-closed（全pill非表示）にして一括retryを出す。

`frontend/app/locales/{ja,en,zh,ko,es,de}/return_stay_plan.json` に同一 key `returnStayPlan.{widget,form,planType,status,location,visibility,memberPill,dialog,error,retry}` を追加し、`frontend/nuxt.config.ts` の全6 localeの `files` 配列へ登録する。AC は widget/form の loading・empty・400 validation・404・409、batch retry、dialog の mobile fullscreen・初期focus・Esc/×/backdrop close、公開先選択を含む。

## 5. 退会・purge・試験

`UserAnonymizedEvent` listener は `@Async("event-pool")` + `@TransactionalEventListener(phase = AFTER_COMMIT)` + `@Transactional(REQUIRES_NEW)`、`AccountPurgedEvent` listener は既存規約どおり `@Async("purge-pool")` + 同じ AFTER_COMMIT/REQUIRES_NEW。いずれも owner予定・可視性を冪等削除する。

`ScheduledBatchGuard` 準拠の `ReturnStayPlanPurgeBatchService#purgeExpiredPlans` は `@BatchEndpoint(name="return-stay-plan-purge-daily")`、`@Scheduled(cron="0 10 4 * * *", zone="Asia/Tokyo")`、`@SchedulerLock(name="returnStayPlanPurgeBatch", lockAtLeastFor="PT5S", lockAtMostFor="PT5M")` を併用する。戻り値は削除件数 `Integer` として metric/log に記録する。各 plan の `planToday=LocalDate.now(ZoneId.of(plan.timezone))` に対し `endDate < planToday.minusYears(1)`（ちょうど1年前は残す）を満たす500件まで抽出・削除し、timezone境界と500件上限を IT で確認する。F10.X バッチカタログへ同名・同 lock を登録する。

E2E/IT は create/update（owner lock race含む）、OFF保持、404秘匿、DTO境界、member batch の空配列・400 chunk・部分失敗、退会イベント、purge境界、OpenAPI差分gateを対象とする。
