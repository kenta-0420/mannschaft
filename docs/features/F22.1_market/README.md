## 1. 概要

「練習試合」「審判募集」「メンバー募集」「助っ人募集」など各種の**募集（札）**が、これまで各チーム/組織/村の画面に散在していた。本機能「**市（いち）**」は、それらを**地域（都道府県・市区町村）×ジャンル**で横断的に探せる**ひとつの市場（マーケット）**として束ねる。

ミクシィの「村（コミュニティ）」が内向きの居場所であるのに対し、「市」は**村の外で人やチームが出会い、募集に応じる外向きの場**である。和風メタファーで操作語彙を統一する。

| 概念 | 語彙 | 実体（既存資産へのマッピング） |
|---|---|---|
| 市（場） | 市（いち） | 地域コード × ジャンルで絞った募集の**論理ビュー**（実体テーブルなし） |
| 募集を出す | **札を立てる** | F03.11 募集の作成→公開（`DRAFT`→`OPEN`） |
| 応募する | **札に応じる** | F03.11 参加申込（`APPLIED`/`CONFIRMED`） |
| 募集を終える | **札を下げる** | F03.11 充足（`FULL`）→最終認証→`COMPLETED` / 期限切れ`AUTO_CANCELLED` / 手動`CANCELLED` |

### 本機能の設計思想 ―「束ねるハブ層」

要件の大半は**既に実装済みの資産で賄える**。したがって本機能は **ゼロから新ドメインを作らず、既存資産を“束ねて見せる”薄いハブ層**として設計する（CLAUDE.md「再利用優先・重複実装禁止」原則）。

| 要件 | 充当する既存資産 | 状態 |
|---|---|---|
| 札の作成/公開/定員/自動キャンセル/テンプレート/配信先/カテゴリ | **F03.11 募集機能** | ✅ 実装済 |
| 応募・キャンセル待ち・自動繰上げ・リマインド | **F03.11**（`recruitment_participants` / `recruitment_reminders` + バッチ） | ✅ 実装済 |
| 最終認証（札主の確認応答） | **F04.9 確認通知**（`confirmable_notifications`） | ✅ 通知基盤は実装済。ただし `source_type`/`source_id` の JPAマッピングが欠落していたため第一陣で追加（乖離A）。`MARKET_FINALIZE` 連携の発火・確認後リスナは第二陣で新規実装 |
| 懇意のチーム（フレンドチーム）宛の非公開札 | **F01.5 フレンドチーム関係**（`team_friends` / フレンドフォルダ） | 🟢 設計済 |
| 都道府県・市区町村マスタ | **既存 `prefectures` / `cities`**（全国約1,900件 seed 済、`PrefectureEntity`/`CityEntity`） | ✅ 実装済 |
| 謝礼決済（Phase 2 後半） | **F13.1 の資金フロー設計図を流用し、市が独自に Stripe Connect 決済基盤を構築**（[`payment/`](payment/README.md) サブ設計） | 🟢 設計確定（実装未着手）。※F13.1 の決済自体は **enum/コメントのみで実装ゼロ**＝設計図のみ流用。受領者は札ごとに個人/チーム/組織を選択 |

新規に作るのは「**地域×ジャンルで束ねて見せる薄い集約層（`com.mannschaft.app.market`）**」と、既存テーブルへの**最小限の拡張（地域列・visibility値・フレンド宛先テーブル）**のみ。

## 2. スコープ

### 対象ロール
| ロール | 操作可能な範囲 |
|--------|--------------|
| SYSTEM_ADMIN | 全市の閲覧・モデレーション（不適切な札の取下げ）※モデレーションは F03.11 既存に委譲 |
| ADMIN | 自 scope（チーム/組織）の札立て・札下げ・最終認証・フレンド宛先指定 |
| DEPUTY_ADMIN | `MANAGE_RECRUITMENTS` 権限保有時のみ ADMIN と同等（F03.11 §2 準拠） |
| MEMBER | 市の閲覧・札に応じる（自身が所属するチームでの応募は ADMIN 経由） |
| SUPPORTER | 市の閲覧・札に応じる（visibility に応じる） |
| GUEST（未ログイン） | **公開札の閲覧のみ**（PII 抑制 DTO）。応募はログイン誘導 |

### 対象レベル
- [x] 組織 (Organization) — 札主になれる
- [x] チーム (Team) — 札主になれる
- [ ] 個人 (Personal) — **札主にはなれない**（身元保証のためダッシュボードを持つチーム/組織のみ）。個人は「札に応じる」側として参加

### 札立ての導線制約（重要・セキュリティ）
**札を立てられるのはチーム/組織のダッシュボードからのみ**とする。市の画面から直接は立てられない。

- 理由: 「どこの誰か」が検証済みの scope（チーム/組織）に必ず紐づけ、匿名・身元不明の投稿を**deny-by-default で排除**する。
- 市画面には「札を立てるには自分のチーム/組織ダッシュボードへ」という**導線リンクのみ**を置く（UX 配慮、§03_ui_i18n）。

## 3. 市の正体 ―「論理ビュー」

市は**実体テーブルを持たない**。「市」とは `recruitment_listings` を以下で絞り込んだ**保存可能なフィルタ条件（論理ビュー）**である。

```
市 ＝ recruitment_listings
        WHERE visibility = 'PUBLIC'
          AND status IN ('OPEN','FULL')         -- 立っている札のみ
          AND (prefecture_code = :pref  OR :pref IS NULL)
          AND (city_code       = :city  OR :city IS NULL)
          AND (category_id     = :cat   OR :cat  IS NULL)
```

### 階層（県の市 ⊃ 市区町村の市）
`cities.code`（CHAR(5)）の上位2桁が `prefecture_code`（CHAR(2)）に一致する構造を利用し、**県の市は配下市区町村の札をロールアップ**して集約表示する。

```
大分県の市（pref=44）
 ├ 別府市の市（city=44202）   ← 別府市に紐づく札
 ├ 大分市の市（city=44201）
 └ …（配下市区町村）
```

- パンくず: `大分県 ＞ 別府市`
- 「地域なし」の札（地域未指定）は **"地域を問わない" 区画**に集約（§8-1）。
- 命名衝突は起きない（市は実体でなくマスタ駆動の論理ビュー。地域は `cities.code` の一意PKで識別）。「村（village）」とは UI/i18n を明確に分離する。
