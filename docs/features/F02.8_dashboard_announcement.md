## 1. 概要

チーム・組織ダッシュボードに「**チーム内告知**」「**組織内告知**」ボタンを追加し、管理者・メンバーが3ステップの告知ウィザードで「対象範囲 → チャネル選択 → コンテンツ入力」を経て、コンテンツ作成と告知フィード登録を一括実行する機能。

### 本機能が解決する課題

| 課題 | 解決策 |
|------|--------|
| 告知に2ステップ（投稿 + お知らせフラグ設定）が必要で摩擦が高い | ウィザード1回で完結 |
| 組織管理者が「特定チームだけに連絡したい」を1か所で設定できない | `target_team_ids` による告知フィルタ |
| 毎回同じ対象範囲を手動設定する煩雑さ | 範囲テンプレートで1クリック再利用 |

### 本ドキュメントのスコープ

| 機能 | 説明 |
|------|------|
| 告知ボタン | チーム・組織ダッシュボードへのエントリポイント |
| 告知ウィザード | 3ステップ（対象範囲 → チャネル → コンテンツ）の作成フロー |
| 範囲テンプレート | 対象範囲の保存・再利用 |
| 組織からのチーム絞り込み | `announcement_feeds.target_team_ids` による配信先制御 |
| チームグループ宛て（🟡 設計中） | チームグループの個別選択・並び順の範囲指定で宛先を決める。表示は閲覧時の所属で判定し（§7.1）、グループ宛てのアンケートの push は送信時の所属で宛先チームのメンバーと組織直属メンバーに限る（§7.2）|

**スコープ外**:
- お知らせウィジェットの表示・ピン留め・既読管理 → F02.6
- プッシュ通知・メール配信 → F04.3
- 確認取得（既読追跡強制型）→ F04.9
- 告知コンテンツの編集・削除 → 各チャネルの既存機能

## 2. F02.6 との分担

```
F02.8（本機能）                F02.6（お知らせウィジェット）
────────────────────────     ─────────────────────────────
告知ボタン（ダッシュボード）    announcement_feeds テーブル管理
告知ウィザード UI               ウィジェット表示・ピン留め・既読
範囲テンプレート管理             source_deleted_at / 期限切れ連動
チャネル別コンテンツ作成         IDOR対策・レートリミット
  → announcement_feeds 登録
```

告知ウィザードの「告知を送る」実行時、バックエンドの `AnnouncementBroadcastService` が：

1. チャネル別 Service を呼び出してコンテンツを作成
2. F02.6 の `AnnouncementFeedService.createFromSource()` を呼び出して `announcement_feeds` を登録

この設計により F02.8 は F02.6 の機能を壊さず、独立したエントリポイントとして機能する。

## 3. 対象ロールと権限

| ロール | 告知ボタン表示 | ウィザード実行 | テンプレート作成・編集 |
|--------|--------------|--------------|----------------------|
| SYSTEM_ADMIN | ✅ | ✅ 全チャネル・全優先度・全対象範囲 | ✅ |
| ADMIN | ✅ | ✅ 全チャネル・全優先度・全対象範囲 | ✅ |
| DEPUTY_ADMIN（MANAGE_CONTENT 権限保持） | ✅ | ✅ 全チャネル・全優先度・全対象範囲 | ✅ |
| MEMBER | ✅ | ✅ 全チャネル（優先度 NORMAL のみ、対象範囲 MEMBERS_AND_ABOVE のみ） | ❌ |
| SUPPORTER | ❌（ボタン非表示） | ❌ | ❌ |

**優先度制限の詳細**:
- ADMIN+ のみ URGENT / IMPORTANT を選択可能
- MEMBER には優先度選択 UI を表示しない（送信時にバックエンドでも URGENT/IMPORTANT は 400 拒否）

**対象範囲（target_role）制限の詳細**:
- MEMBER が実行できるのは `target_role = MEMBERS_AND_ABOVE`（内輪）のみ
- `SUPPORTERS_AND_ABOVE` / `PUBLIC` はスコープ所属者を越えて可視になり、事実上の組織／チーム公式発信として機能するため ADMIN+（ADMIN / DEPUTY_ADMIN(MANAGE_CONTENT) / SYSTEM_ADMIN）のみ選択可能
- MEMBER には「サポーター以上」「全員（公開）」の選択肢を UI 上グレーアウトする（送信時にバックエンドでも `BROADCAST_005` で 400 拒否）

## 6. チャネル設計

| チャネル | source_type | コンテンツ作成 API | 最低必要ロール |
|---------|------------|-------------------|--------------|
| 掲示板 | `BULLETIN_THREAD` | `POST /api/v1/{scopeType}/{scopeId}/bulletin/threads` | MEMBER |
| タイムライン | `TIMELINE_POST` | `POST /api/v1/timeline/posts` | MEMBER |
| ブログ | `BLOG_POST` | `POST /api/v1/blog/posts` | MEMBER（チームのブログ有効化が前提） |
| TODO | `TODO` | `POST /api/v1/teams/{teamId}/todos`（チームスコープ）/ `POST /api/v1/organizations/{orgId}/todos`（組織スコープ） | MEMBER |
| スケジュール | `SCHEDULE` | `POST /api/v1/{scopeType}/{scopeId}/schedules` | MEMBER |
| アンケート | `SURVEY` | `POST /api/v1/{scopeType}/{scopeId}/surveys` | MEMBER |

**チャネル無効化条件**（ウィザードのステップ2でグレーアウト表示）:
- そのスコープで対応するモジュールが無効化されている場合（`module_settings` テーブルによる既存制御）
- ホバー / タップで「このチームでは〇〇機能が無効です」ツールチップを表示

### TODO チャネルの動作詳細

告知ウィザードで TODO を選択した場合:

1. `TodoAnnouncementAdapter` がスコープに応じた Service を呼び出す（チームスコープ: `TeamTodoService.create()` / 組織スコープ: `OrgTodoService.create()`）
2. `assignee_ids = []`（担当者未設定。チーム/組織全体で認識するタスクとして作成）
3. TODO 作成成功後、`AnnouncementFeedService.createFromSource()` で `announcement_feeds` に登録
4. ウィジェット表示: タイトル + 期限 + 進捗率。クリックで TODO 詳細ページへ遷移

**UX 注意**: TODO ウィザード確認画面に「担当者は TODO ページで各自が名乗りを上げるか、ADMIN が割り当ください」の補足テキストを表示する。

### スケジュール・出欠イベントの扱い

`SCHEDULE` チャネルで作成されるスケジュールは、`attendance_required` フラグを ON にすることで出欠管理イベントになる（既存の F03.x スケジュール仕様に準拠）。

## 7. 対象範囲 → コンテンツ visibility マッピング

| target_role（ウィザードの選択） | コンテンツ visibility | announcement_feeds.visibility |
|-----------------------------|--------------------|-------------------------------|
| MEMBERS_ONLY | `MEMBERS_ONLY` | `MEMBERS_ONLY` |
| SUPPORTERS_AND_ABOVE | `SUPPORTERS_AND_ABOVE` | `SUPPORTERS_AND_ABOVE` |
| PUBLIC | `PUBLIC` | `PUBLIC` |

コンテンツ作成リクエストの `visibility` フィールドは `AnnouncementBroadcastService` が自動セットする（ユーザーによる上書き不可）。

### 組織告知の `target_team_ids`

| ウィザード選択 | announcement_feeds.target_team_ids |
|-------------|-------------------------------------|
| すべてのチーム | `NULL`（制限なし） |
| 特定チームを選択（例: A, B） | `[1, 3]`（team.id の JSON 配列） |

チームダッシュボード側では親組織の `announcement_feeds` を取得する際、`target_team_ids IS NULL OR JSON_CONTAINS(target_team_ids, :teamId)` でフィルタリングする（§10.3 参照）。

> **重要**: `target_team_ids` とチームグループ指定は、**告知ウィジェットへの表示（と、グループ宛てアンケートの push。§7.2・🟡 設計中）を絞り込むもの**であり、コンテンツ自体へのアクセス制御ではない。org スコープのコンテンツは `visibility` ルール（MEMBERS_ONLY 等）に従い全 org メンバーがアクセス可能。「特定チームにだけ知らせたい」という目的で使うもので、「特定チームにだけアクセスを制限したい」場合は別途 visibility 設定を使うこと（F01.2.1 §1.2）。

### 7.1 チームグループによる宛先指定（🟡 設計中・F01.2.1）

組織がチームグループ機能を有効にしている場合、ウィザードのステップ1で「チームグループで選ぶ」を選べる。定義の正本は [F01.2.1 §8](./F01.2.1_org_team_groups.md)。

| 入力（リクエスト） | 型 | 意味 |
|---|---|---|
| `target_group_ids` | UUID 文字列の配列（0〜200）| 個別にチェックしたグループ |
| `target_group_range` | `{from_group_id: UUID\|null, to_group_id: UUID\|null}` または null | 並び順（`sort_order` 昇順）の範囲。from のみ＝「以降」、to のみ＝「以前」、両方＝「A〜B」|
| `include_unassigned` | boolean（既定 false）| 未分類の加盟チームも含める |

- 対象は「個別チェックのグループ ∪ 範囲内のグループ」に所属するチーム（∪ 未分類チーム）と、**組織の直属メンバー**（どのチームにも属さない組織役員など。マスター確定）である。
- 「チームを選ぶ」（`target_team_ids`）とグループ系の項目は同じリクエストで併用できない（400 `BROADCAST_011`）。
- **保存するもの**: 範囲を送信時の並びで展開したグループ ID 集合を `announcement_feeds.target_group_ids`、未分類の有無を `include_unassigned` に保存する。`target_team_ids` は NULL のままにする。
- **表示は閲覧時に解決する（動的）**: チームダッシュボードは、閲覧中のチームがその組織に ACTIVE で加盟し、その組織での所属グループ（削除済みは未分類扱い）が `target_group_ids` に含まれるか、未分類で `include_unassigned` が真なら表示する（§10.3）。送信後にグループの割当を直せば、直した後の所属で表示が変わる。
- **push は送信時に確定する（スナップショット）**: §7.2。表示と push で解決時点が異なる理由は F01.2.1 §8.2。
- 指定内容（グループ ID・送信時の名前・範囲・未分類の有無・送信時の解決チーム数）は `announcement_feeds.target_audience`（§8.2）に記録し、送信履歴の「宛先: 平成20年度以前（送信時 12 チーム）」表示に使う。表示判定には使わない。
- 解決結果が0チームで直属メンバーもいなければ 400 `BROADCAST_009`。**グループ指定には件数上限を掛けない**（5,000件の上限は「チームを選ぶ」だけ。400 `BROADCAST_010`。上限値は未検証で、F01.2.1 §8.3 の実測で見直す）。

### 7.2 push 通知の絞り込み（🟡 設計中・F01.2.1）

正本は [F01.2.1 §8.5](./F01.2.1_org_team_groups.md)。要点（いずれもマスター確定）:

- **絞るのは、現在 push を出しているチャネルだけ**。main 時点では、アンケート公開通知（`SurveyPublishNotificationListener` の組織スコープ×ALL＝`ORGANIZATION` fan-out）だけが該当する。掲示板・タイムライン・ブログ・TODO・スケジュールは、グループで絞っても push を出さない（新設しない）。
- **グループ宛てのアンケート告知の push を出せるのは、組織 ADMIN / DEPUTY_ADMIN(MANAGE_CONTENT) / SYSTEM_ADMIN だけ**。MEMBER のグループ宛ては表示の絞り込みだけで、push は出さない。
- 出す場合は、告知ウィザードが新しい受信者ソース `ORGANIZATION_TEAMS`（`OrgTeamsFanoutRecipientSource`）の fan-out ジョブを1件だけ、**告知と同じトランザクションの中で** enqueue する（transactional outbox 相当。冪等キーはフィード ID から導出）。宛先チームは送信時の所属で確定し、`notification_fanout_job_target_teams` 子表で渡す。
- 受信者は、宛先チームの現役メンバー（配信時点でも ACTIVE 加盟のチームに限る）∪ 組織の直属メンバー。ユーザー単位で重複排除する。子組織メンバー・宛先外チームのメンバーには送らない。応援者トグルは `target_role` から決める（`MEMBERS_ONLY` → 含めない、`SUPPORTERS_AND_ABOVE` / `PUBLIC` → 含める）。
- グループ宛てのとき、アダプターが作るアンケートの公開イベントに「告知ウィザードが宛先を管理している」印を載せ、`SurveyPublishNotificationListener` の組織全体 fan-out を止める。push の文面はアンケート公開通知と同じ（既存キー `notification.fanout.survey.published.*`）。
- 「すべてのチーム」「チームを選ぶ」の告知は、表示も push も**従来どおり**（「チームを選ぶ」の push は組織全体に届く既存挙動を回帰させない。絞るかどうかは F01.2.1 §17 #19 の裁可事項）。
- 表示の絞り込みと push の絞り込みは同じリリースに入れる。

### 7.3 範囲テンプレートとチームグループ（🟡 設計中・F01.2.1）

テンプレートはチーム ID ではなく**グループの指定**（個別グループ・範囲・未分類の有無）を保存し、使うたびに**サーバーが解決する**（§8.1 の追加列）。解決手順の正本は [F01.2.1 §8.6](./F01.2.1_org_team_groups.md)。

- 個別グループのうち削除済み・他組織のものは黙って除外し、レスポンスの `warnings` に `TEMPLATE_GROUPS_REMOVED` を載せる。画面は読込時に「削除されたチームグループがテンプレートから除外されました」と表示する。
- 範囲の端のグループが削除済みなら範囲が成り立たない。画面では読込時に範囲を空にして再選択を求め、`template_id` だけを指定して API で送った場合は 400 `BROADCAST_013`。
- 範囲は**使った時点の並び**で展開する。保存後にグループを追加・並べ替えれば、展開結果もそれに従う。
- グループの削除時にテンプレートを書き換えることはしない（organization ドメインから social ドメインへ書き込みを波及させないため）。

- 組織スコープであること（TEAM スコープでグループ系の項目を指定したら 400 `BROADCAST_012`）

- テンプレートの範囲の端が削除済みでないこと（400 `BROADCAST_013`）

## 10. ビジネスロジック（バックエンド設計）

### 10.1 AnnouncementBroadcastService.broadcast()

```
1. 認可チェック
   a. 呼び出し元がスコープのメンバーであること
   b. MEMBER が priority = URGENT/IMPORTANT を指定していないこと
2. template_id 検証（指定がある場合）
   → templateRepository.findById(templateId) で取得し、scope_type / scope_id が一致することを確認
   → 不一致 または 存在しない場合は 400 Bad Request
   → 一致する場合、リクエストの target_role / target_team_ids / preferred_channel にテンプレート値を適用
      （ただしリクエストで明示的に指定された値はテンプレート値より優先）
3. target_team_ids 検証（scopeType == ORGANIZATION の場合）
   → teamRepository.findTeamIdsByOrgId(scopeId) で取得した ID セットに全て含まれるか確認
3.5 チームグループ指定の解決（🟡 設計中・F01.2.1 §8。§7.1）
   → テンプレート指定があれば F01.2.1 §8.6 の手順でサーバー側解決する
   → 組織側 Service（organization ドメイン）に宛先指定を渡し、範囲を送信時の並びでグループ ID 集合へ展開する
     （表示用に target_group_ids / include_unassigned として保存）
   → 同時に、送信時の所属から push 宛先チーム集合を確定する（ACTIVE 加盟 × group_id。削除済みグループは未分類扱い）
   → 手順5のアダプター呼び出しに BroadcastAudience（グループ宛てである印・push 可否）を渡す。
     push 可否 = チャネルが現に push を出す（現状アンケートのみ）かつ 呼び出し元が ADMIN / DEPUTY_ADMIN(MANAGE_CONTENT) / SYSTEM_ADMIN
   → 手順6のフィード登録の後、同じトランザクションの中で ORGANIZATION_TEAMS の fan-out を1件 enqueue する
     （push 可否が真のときだけ。冪等キーはフィード ID から導出。F01.2.1 §8.5.3）
4. モジュール有効チェック
   → moduleSettingsRepository.isEnabled(scopeType, scopeId, channel.getModuleKey()) で確認
5. チャネルアダプター呼び出し
   → contentId = adapterRegistry.get(channel).createContent(content, scopeType, scopeId, visibility, userId)
6. AnnouncementFeedService.createFromSource(sourceType, contentId, scopeType, scopeId, priority, expiresAt, targetTeamIds)
7. BroadcastResult(announcement_feed_id, content_id, content_url) を返却
```

全処理は `@Transactional` でラップ。4のコンテンツ作成成功後に5が失敗した場合はロールバックし、コンテンツも削除される。

### 10.3 target_team_ids フィルタリング（チームダッシュボード表示側）

`DashboardService.getTeamDashboard(teamId, userId)` 内での `announcement_feeds` 取得クエリに、親組織からの告知取得を追加する:

```sql
-- チームの告知（既存クエリ変更なし）
SELECT * FROM announcement_feeds
WHERE scope_type = 'TEAM' AND scope_id = :teamId
  AND source_deleted_at IS NULL
  AND (expires_at IS NULL OR expires_at > NOW())
  AND visibility IN (:allowedVisibilities)

UNION ALL

-- 親組織からの告知（新規追加）
SELECT * FROM announcement_feeds
WHERE scope_type = 'ORGANIZATION'
  AND scope_id IN (:orgIds)
  AND (target_team_ids IS NULL
       OR JSON_CONTAINS(target_team_ids, CAST(:teamId AS JSON)))
  AND source_deleted_at IS NULL
  AND (expires_at IS NULL OR expires_at > NOW())
  AND visibility IN (:allowedVisibilities)

ORDER BY is_pinned DESC,
         FIELD(priority, 'URGENT', 'IMPORTANT', 'NORMAL'),
         created_at DESC
LIMIT :limit
```

`:orgIds` = ユーザーの所属組織のうち、当該チームを含む組織の ID リスト（`team_memberships` から取得）

**チームグループ宛ての表示判定（🟡 設計中・F01.2.1 §8.2）**: 上の親組織クエリの `target_team_ids` 条件を、次の判定に置き換える。判定は共通の `AnnouncementAudienceMatcher` に集約し、`DashboardService` の既存の Java 側判定（`target_team_ids` の文字列照合）もこれに寄せる。

```
親組織 O の告知 f をチーム T に表示するか:
  f.target_team_ids IS NULL AND f.target_group_ids IS NULL          → 表示（すべてのチーム宛て）
  f.target_team_ids IS NOT NULL                                     → JSON_CONTAINS(f.target_team_ids, T)（従来どおり）
  f.target_group_ids IS NOT NULL                                    → 次を閲覧時に判定（動的）
      g = T の O での所属グループ（team_org_memberships ACTIVE の group_id。
          org_team_groups.deleted_at IS NULL で JOIN し、削除済み・NULL は「未分類」）
      g が未分類 → f.include_unassigned
      それ以外   → JSON_CONTAINS(f.target_group_ids, g)
```

- `:orgIds` は T が ACTIVE で加盟するすべての組織（複数あり得る。F01.2.1 §9）。所属グループは組織ごとに異なるので、`T の組織ごとの所属グループ` を1回のクエリで Map に引いてから判定する。
- 組織ダッシュボード（組織スコープ）の表示は従来どおり絞らない（直属メンバー・管理者は組織の告知をすべて見られる）。

## 11. セキュリティ考慮事項

### 11.1 IDOR 対策（target_team_ids）

組織告知で `target_team_ids` を指定する場合、各 team_id が確かにその組織の配下チームであることを二重検証:

```java
if (scopeType == ORGANIZATION && targetTeamIds != null && !targetTeamIds.isEmpty()) {
    Set<Long> orgTeamIds = teamRepository.findTeamIdsByOrgId(scopeId);
    if (!orgTeamIds.containsAll(targetTeamIds)) {
        throw new BadRequestException("target_team_ids に無効なチーム ID が含まれています");
    }
}
```

これにより他組織のチーム ID を指定して不正な配信対象を作ることを防ぐ。

> **候補集合の確定（🟡 設計中・F01.2.1 §17 #20）**: 現行実装の `validateTargetTeamIds` は、候補を `UserRoleRepository.findTeamIdsByOrganizationId`（`user_roles` の組織ロール行 ∪ ACTIVE の `team_org_memberships`）で作っている。このうち `user_roles` 由来の候補は「組織ロールを持つ人がいるチーム」であって「組織に加盟しているチーム」ではない。本書で、**候補は ACTIVE の `team_org_memberships` だけ**と確定する（`user_roles` 経由を除く）。チームグループの展開と同じ基準にそろえ、加盟していないチームを宛先に選べないようにする（F01.2.1 AC-K07）。

### 11.2 チャネル権限の二重検証

`AnnouncementChannelAdapter.createContent()` は内部で各チャネルの既存 Service を呼び出す。各 Service にはすでに独自の認可チェックが実装されているため、`AnnouncementBroadcastService` での1回目 + 各チャネル Service での2回目という二重検証になる。これはセキュリティ上の冗長性として意図的に許容する。

### 11.3 priority エスカレーション防止

MEMBER が `priority = URGENT / IMPORTANT` を指定したリクエストは 400 Bad Request で拒否する（F02.6 §6 の方針に準拠）。フロントエンドで優先度を NORMAL 固定にしていても、バックエンドでも独立して検証する。

### 11.4 テンプレートのスコープ分離

`GET /announcement-templates` は呼び出し元のスコープ内（scope_type + scope_id が一致するもの）のみを返す。他スコープのテンプレートを参照・操作することはできない。

### 11.5 コンテンツ作成の原子性

`broadcast` API はコンテンツ作成 → `announcement_feeds` 登録の2ステップを `@Transactional` で包む。`announcement_feeds` 登録に失敗した場合はコンテンツもロールバックされる（告知されないコンテンツが孤立して存在し続けることを防ぐ）。

外部イベント発行（ApplicationEvent）は `@TransactionalEventListener(phase = AFTER_COMMIT)` で行うため、ロールバック時にイベントは発行されない。

### 11.6 XSS 対策

- `announcement_range_templates.name` はユーザー入力文字列。API レスポンスでは `{{ }}` テキスト補間のみで表示（`v-html` 禁止）
- `content` フィールドの各項目（title / body / description）は既存チャネルの入力サニタイズ処理をそのまま使用

### 11.7 レートリミット（Bucket4j）

| 操作 | 制限 |
|------|------|
| `POST /{scope}/broadcast` | 5分5件 / ユーザー |
| `POST /{scope}/announcement-templates` | 1分10件 / ユーザー |
| `PUT /{scope}/announcement-templates/{id}` | 1分20件 / ユーザー |
| `DELETE /{scope}/announcement-templates/{id}` | 1分10件 / ユーザー |

**補足**: `broadcast` 実行時、内部で呼ばれる `AnnouncementFeedService.createFromSource()` には F02.6 のレートリミット（`POST /announcements`: 5分10件 / ユーザー）も適用される。

### 11.8 オフライン時の動作

F02.6 §6.9（PWA 対応）の方針に準拠し、告知ウィザードはオフライン時に実行不可。「+ チーム内告知」ボタンを `disabled` にし、ツールチップ「オフラインのため告知できません」を表示する。
