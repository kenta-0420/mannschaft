## 1. 概要

メニュー（例: カット60分）を選ぶと、**所要時間分の連続枠（30分セル×N）を1つの「予約グループ」として一括確保**する。1予約=1枠の既存モデルは維持しつつ、複数の予約行を `group_id` で束ねる（**案(b)・兄弟行方式**。案比較は §3.1）。

- **満席制御**: 既存のアトミック UPDATE（capacity 基準・実在確認済み）を **N 枠ぶん同一トランザクション内でループ**し、**1枠でも確保失敗なら全ロールバック（部分成功禁止）**。
- **自動確保＋手動調整**: メニュー選択→連続枠の自動選定（§5.3）。ユーザーは提案された枠列に対し**枠の追加（延長）**ができる。減らすことはできない（メニュー成立要件を割るため）。
- **状態遷移はグループ単位**（PENDING→CONFIRMED→…）。キャンセル期限の基準時刻は**先頭枠の開始時刻**。
- 単枠予約（既存 `POST /reservations`）は**無変更で併存**する（`group_id IS NULL` = 単枠・既存互換）。

## 2. スコープ

### 対象ロール

| ロール | 操作可能な範囲 |
|--------|--------------|
| MEMBER / SUPPORTER / 公開ユーザー（view ゲート） | グループ予約の作成・自分のグループのキャンセル・詳細閲覧 |
| ADMIN / DEPUTY_ADMIN（**role ベース・権限フラグ不問**。`isScopeAdmin` は純ロール判定で `MANAGE_RESERVATIONS` を参照しない — AccessGuard.java:46 実測。DEPUTY_ADMIN は権限有無に関わらず 200） | グループの承認・拒否相当のキャンセル・完了・ノーショー・詳細閲覧 |

### スコープ外

- グループのリスケジュール（**第二弾では非対応**。キャンセル→再予約の運用。単枠の既存 reschedule は無変更で維持）
- 複数日・複数ライン跨ぎのグループ（1グループ = 同一日・同一予約対象の連続枠のみ）
- グループの部分キャンセル（枠単位の切り離し。全枠一括キャンセルのみ）

## 3. DB設計

### 3.1 案比較（マスター指示による必須比較）— 推奨は **案(b) `group_id` 兄弟行方式**

| 比較軸 | 案(a) 親予約＋明細 junction（`reservation_groups` 親表 + `reservation_group_items`） | 案(b) `reservations.group_id`（UUIDv7 nullable）で兄弟行 ★推奨 |
|---|---|---|
| 既存の枠×予約整合資産 | 明細行は `reservations` ではないため、**枠削除ガード（`existsByReservationSlotIdAndStatusIn`=020）・予約不可枠 overlap クエリ（`findActiveReservationsOverlappingUnavailability`）・アトミック UPDATE の呼出規約が全て二重化**（明細にも同等の走査が必要） | 兄弟行は通常の `reservations` 行。**上記の既存クエリ・ガードが無修正でグループの各枠にも効く**（安全側） |
| 重複予約ガード（`existsByReservationSlotIdAndUserIdAndStatusIn`・実測） | 明細を別走査しないと同一枠の二重予約を検知できない | 兄弟行が同一ガードに自然に乗る |
| 集計・一覧 | 親行=1予約で自然。ただし枠別の稼働集計は明細 join が必要 | 行数が枠数ぶん膨らむ → **`is_group_primary` フラグで代表行に絞る**補正が必要（§3.2） |
| 状態遷移 | 親に一元化できて綺麗 | 兄弟行のステータスを揃えて更新（同一tx・全行一括） |
| 移行リスク | 新テーブル2枚＋既存 API/クエリの広範な書き換え（blast radius 大: ガード・overlap クエリ・イベント発行の全経路が明細対応を要する） | ALTER 1本＋**一覧・集計クエリ約10本の改名/条件追加**（§5.6 #4/#10 に列挙。Spring Data 派生クエリの条件追加はメソッド改名=呼出側変更を伴うため「条件を足すだけ」ではないが、対象が列挙可能な有限集合に閉じる点で案(a)より局所的） |
| 将来の部分キャンセル | 明細単位で自然に表現可 | 兄弟行単位で表現可。ただし**代表行昇格規則が必要**（代表行を含む部分キャンセル時、残存行のうち最小 `slot_date`+`start_time` の行を `is_group_primary=TRUE` へ昇格して不変条件を維持する。第二弾は全枠一括キャンセルのみのため昇格は未実装・将来要件として明記） |

**推奨根拠（確定）**: 既存実装は「予約行=枠行」の前提でガード・クエリ・イベントが組まれている（§5.6 棚卸しで実コード確認済み）。案(a) はこの前提を壊して明細への二重実装を強いる。案(b) は既存資産がそのまま各兄弟行に効き、補正が必要なのは「集計・一覧の代表行絞り」と「イベント・リマインドの代表行一本化」に限定される。**案(b) を採用する。**

### 3.2 `reservations` への ALTER

| カラム名 | 型 | NULL | デフォルト | 説明 |
|---------|---|------|-----------|------|
| `group_id` | BINARY(16) | YES | NULL | 予約グループID（**アプリ層で UUIDv7 を採番**。グループ専用テーブルは作らない=案(b)）。**NULL = 単枠予約 = 既存互換** |
| `menu_id` | BINARY(16) | YES | NULL | 選択メニュー。FK → `reservation_menus.id` **ON DELETE RESTRICT**（同一ドメイン。メニューは論理削除運用のため実質発火しない。F03.4.1 §4「参照中メニューは物理削除しない」と整合）。NULL = メニュー未使用（単枠・自由グループ） |
| `is_group_primary` | BOOLEAN | NO | TRUE | **グループ代表行フラグ**。単枠予約は常に TRUE。グループでは先頭枠（最小 `slot_date`+`start_time`）の行のみ TRUE。一覧・統計の重複計上防止（§5.6） |

**インデックス（追加）**
```sql
INDEX idx_rv_group (group_id)                          -- グループの兄弟行取得
INDEX idx_rv_user_primary (user_id, is_group_primary, status)  -- 一覧の代表行絞り
```

**制約・備考**
- 既存行は `group_id=NULL / menu_id=NULL / is_group_primary=TRUE` にフォールバック（`DEFAULT TRUE` で自動充足・挙動後退ゼロ）。**from-scratch 既存行シード番人テスト必須**（親 §7 の作法）。
- `uq_rv_slot_line_active`（同一枠×同一ラインの有効予約 UNIQUE）は**実 DDL に不存在**（実測・親設計書の記述は aspirational）。本枝番でも**追加しない**: ライン軸枠は capacity=1 のアトミック UPDATE が満席防御であり、共通枠のライン重複は既存ギャップとして据え置く（親 §8 バックログの範疇。グループ機能の前提ではない）。
- グループの兄弟行は `reservation_slot_id` が互いに異なる（連続する別セル枠）。`team_id`/`user_id`/`line_id`/`menu_id`/`group_id`/`status` は全兄弟行で同値。`user_note` は代表行のみに保存（兄弟行は NULL）。
- **不変条件（invariant・明文化）**: 同一 `group_id` を持つ行集合には **`is_group_primary=TRUE` の行がちょうど 1 行**存在する（0 行でも 2 行以上でもない）。単枠予約（`group_id IS NULL`）は常に TRUE。この不変条件は作成 tx で構造的に成立させ（§5.2）、集計・一覧の正しさ（§5.6 #4/#10）とイベント一本化（§5.5）の前提となる。将来の部分キャンセル導入時は**代表行昇格規則**（残存行のうち最小 `slot_date`+`start_time` を TRUE へ昇格）で維持する（§3.1 の案(b) 注記参照）。

### `POST .../confirm` / `POST .../complete` / `POST .../no-show`

単枠の既存遷移 API（親 §4）とそれぞれ同じ前提条件をグループ単位に適用する:

| 操作 | 前提 status（全枠） | 遷移後 | 副作用 |
|---|---|---|---|
| confirm | PENDING | CONFIRMED（全枠） | `ReservationConfirmedEvent` を**代表行についてのみ 1 回**発行（リマインド生成・§5.5） |
| complete | CONFIRMED | COMPLETED（全枠） | なし（既存単枠と同じ） |
| no-show | CONFIRMED | NO_SHOW（全枠） | なし |

前提を満たさない場合は 400=006。いずれも同一 tx で全兄弟行を更新する（部分遷移禁止）。

### 既存単票 API との関係（明確化）

- グループ所属行（`group_id IS NOT NULL`）に対する**単票の状態遷移 API**（`/reservations/{id}/cancel|confirm|complete|no-show|reschedule`）は **400 = RESERVATION_042**（「この予約はグループの一部です。グループ単位で操作してください」）。部分キャンセル・部分承認による booked_count 不整合とグループ状態の分裂を構造的に防ぐ。
- `GET /reservations/{id}`（単票詳細）は**全行で許可**（読み取りに分裂リスクなし）。
- `PUT /reservations/{id}`（メモ更新）は**代表行（`is_group_primary=TRUE`）のみ許可・非代表行は 400 = RESERVATION_042**。理由: 一覧は代表行のみを返す（§5.6 #10）ため、非代表行に書いたメモは**二度と UI に浮上せず事実上消失**する（サイレントデータロス）。代表行リダイレクト（非代表行への PUT を代表行へ透過適用）は「指定した ID と違う行が書き換わる」暗黙挙動になるため不採用とし、明示的な 400 拒否で FE に代表行操作を強制する。

## 5. ビジネスロジック

### 5.1 実装方針（クラス構成）

| 層 | 新規クラス | 役割 |
|---|---|---|
| Controller | `ReservationGroupController` | §4 の 6 エンドポイント |
| Service | `ReservationGroupService` | 作成（連続検証＋N枠アトミック確保）・グループ状態遷移・所有権/締切判定 |
| Repository | 既存 `ReservationRepository` に追加 | `findByGroupIdOrderById` / `findByGroupIdAndTeamId` / 一覧系の `is_group_primary` 対応（§5.6） |

- 単枠予約の `ReservationService.createReservation` の変更は F03.4.2 §5.6 のライン整合検証の追加のみ。ただし**既存の単票状態遷移メソッド 6 本すべてにグループ行ガード（RESERVATION_042）の挿入が必要**であり、「既存 Service 無修正」ではない（正直な棚卸し）:
  1. `cancelByUser` 2. `cancelByAdmin` 3. `confirmReservation` 4. `completeReservation` 5. `markNoShow` 6. `rescheduleReservation`
  — 各メソッド先頭で `entity.getGroupId() != null` なら 400=042 を throw（PUT メモ更新は非代表行のみ 042・§4）。**この 6 本＋PUT は回帰テストの必須対象**として `/試練` で列挙する（単枠予約〔group_id NULL〕では従来どおり通過することも対で検証）。グループ操作自体は `ReservationGroupService` に分離する。
- 満席確保のうち **increment は `ReservationSlotRepository.incrementBookedCountIfAvailable` をリポジトリ直呼び**（§5.2 の 4. 参照。既存 `ReservationSlotService.incrementAndCheckFull` は 0 行時に RESERVATION_004〔400〕を throw する void メソッドのため、グループの 409=039 契約を満たせない — 実測 `ReservationSlotService.java:302-308`）。**decrement は既存 `decrementAndReopen`（throw しない void）をそのまま流用**する。SQL 実装（アトミック UPDATE 2 本）はリポジトリ層で単一のまま共有し、**例外変換だけが呼出側で異なる**（別 SQL 実装の禁止は維持）。

### 5.2 グループ作成フロー（同一トランザクション・部分成功禁止）

```
@Transactional
createGroup(teamId, userId, request):
 1. viewAccessGuard.assertCanView(teamId, userId)                     # 単枠・グリッドと同一述語

 4. ★枠の確保（アトミック UPDATE×N・slotId 昇順・INSERT より先）:
    for slot in slots (slotId 昇順):
      int updated = slotRepository.incrementBookedCountIfAvailable(slot.getId())   # リポジトリ直呼び・戻り値で判定

    MANUAL: PENDING 維持
 8. ReservationCreatedEvent を代表行についてのみ 1 回発行
    （slotTitle には menuName（menu 指定時）または先頭枠 title を渡す。管理者通知・機能D メールが 1 回だけ飛ぶ）
```

**順序の設計意図（確保 UPDATE → INSERT・S→X ロック昇格の根絶）**: `reservations` の INSERT は FK（`reservation_slot_id` → `reservation_slots`）の親行検査で対象 slot 行に**共有(S)ロック**を取る。仮に INSERT を先に行いその後に increment（**排他(X)ロック**）を取ると、同一枠へ並行予約する複数 tx がそれぞれ S を保持したまま X を待ち合う **S→X ロック昇格デッドロック**になる — これは**同一行**上の競合であり、slotId の取得順序では防げない（順序の問題ではなく昇格の問題）。**確保（X）を先行**させれば各 tx は最初から X を取り合うだけになり、昇格経路が構造的に消える。確保に失敗（0 行更新）した tx は INSERT に到達せず、例外→ロールバックで先行確保分も巻き戻る（部分成功が存在しない）。検証（2）はロックを取らない読み取りのため最初に置く。`SELECT FOR UPDATE` は不要（単一行アトミック UPDATE の合成で N 枠も安全）。

**デッドロックの残存リスク（正直な記述）**: 上記に加えて**確保ループは常に slotId 昇順**とする（異なる枠集合を逆順に取り合う交差デッドロックの回避 — こちらは複数行間の順序の問題であり昇順が有効）。ただし 2 策を尽くしても、InnoDB のギャップロック・インデックス経路等に起因する稀なデッドロックは理論上ゼロにならない。発生時は DB が一方の tx を強制ロールバックするため、`DeadlockLoserDataAccessException` を **409（RESERVATION_039 と同じ「選び直し」契約）にマップ**し、FE の再取得フロー（§5.3・`conflict_retry`）で吸収する。BE での自動リトライは行わない（空き状況が変わった可能性があるため、ユーザー可視の再選択が正）。

### 5.3 メニュー選択→連続枠の自動選定（FE 提案・BE 検証）

- **自動選定は FE（マトリックスUI・F03.4.4）が行い、BE は §5.2 の検証で最終防御する**（責務分担の確定。理由: 選定は「ユーザーがクリックしたセルを起点に画面上の空きセルを N 個延ばす」純表示ロジックであり、BE に置くと グリッド API と二重の空き判定を持つことになる。権威判定は作成 tx の 4.〔アトミック確保〕が担う）。
- FE の選定規則: 起点セル（クリック位置）から**同一ライン・同一日で時間昇順に、state=AVAILABLE のセルを N 個連続で選ぶ**。途中に AVAILABLE でないセル（BOOKED/CLOSED/UNAVAILABLE）または枠の不存在（隙間）があれば**その起点では不成立**（グレーアウト。F03.4.4 §5）。
- **手動調整**: 提案された N 枠に対し、末尾に連続する空きセルを**追加**できる（延長。最大 16 枠）。先頭・途中の除去は不可（連続性とメニュー成立要件を守る）。メニューなし（自由グループ）は 1 枠から任意に延長。
- 同時実行で FE 提案が古くなった場合（他ユーザーが先に確保）: BE の 409=RESERVATION_039 を受けて FE はグリッドを再取得し「選び直してください」を表示（i18n `reservation.group.conflict_retry`）。

### 5.4 状態遷移（グループ単位）

```
            ┌─(AUTO 即時)──────────────┐
POST 作成 ──┤                           ▼
            └─(MANUAL)─→ PENDING ──confirm──→ CONFIRMED ──complete──→ COMPLETED
                            │                    │
                            │                    ├──no-show──→ NO_SHOW
                          cancel               cancel
                            │                    │
                            ▼                    ▼
                        CANCELLED            CANCELLED
```

- 全兄弟行は**常に同一 status**（グループ不変条件）。遷移は全行同一 tx。
- **キャンセル期限の基準時刻 = 先頭枠（最小 `slot_date`+`start_time`）の開始**。`reservation_policies.cancel_deadline_hours`（既定24・注入 Clock 基準）から `deadline = 先頭枠開始 - hours` を算出し、超過した本人キャンセルは 400=026（既存 `cancelByUser` と同じ規則をグループへ適用。ADMIN は対象外）。「後半の枠だけまだ締切前」という部分判定はしない（グループ=1来店）。
- キャンセル時の副作用: 全枠について `decrementAndReopen`（アトミック復帰）・未送信リマインド CANCELLED 化（代表行由来のリマインドのみ存在する・§5.5）・`ReservationCancelledByMemberEvent` を代表行で 1 回発行（本人キャンセル時）。

### 5.5 イベント・リマインド・通知の一本化（代表行集約）

既存リスナー群は `ReservationCreatedEvent`/`ReservationConfirmedEvent` を予約 1 行ごとに発行される前提で購読している（実測: 管理者通知・機能D メール・リマインド生成）。グループで N 回発行すると **管理者通知 N 通・宛先メール N 通・リマインド N×(24h,1h)** の洪水になるため:

- **イベントは代表行（`is_group_primary=TRUE`）についてのみ発行する**（§5.2 の 7/8）。`ReservationConfirmedEvent.slotStartAt` = 先頭枠開始 → リマインドは「来店の 24h/1h 前」1 セットだけ生成される（意味的にも正）。
- 既存リスナー（`ReservationAdminNotificationEventListener` / `ReservationRecipientEmailEventListener` / `ReservationReminderEventListener`）は**無修正**（発行側の集約で完結。受信側にグループ知識を持たせない）。
- 機能D メール本文の「日時」= 先頭枠の来店日時（親 §5.D の N-1 是正と整合）。メニュー名は `slotTitle` 経由で載る（§5.2 の 8）。

## 6. セキュリティ考慮事項

- **認可**: 作成は view ゲート（会員 or 公開）を Service 層で。**ADMIN 限定は 3 本（confirm/complete/no-show）**に `@PreAuthorize isScopeAdmin`（self-gate・role ベース＝`MANAGE_RESERVATIONS` 権限フラグは enforcement に使わない。§2 参照）。cancel/GET は「本人 or ADMIN」を Service 層で判定し、非該当は **404（RESERVATION_040）で存在秘匿**（UUID 列挙攻撃対策）。
- **レートリミット**: グループ作成は単枠予約と同じバケット（1ユーザー1分5回・親 §6）を**共有**する（別バケットにすると単枠×5＋グループ×5 の買い占めが可能になるため）。
- **買い占め防止**: 1グループ最大16枠の上限＋レートリミット共有が本枝番の実 enforce。`max_active_reservations`（親 §5 のチーム設定・同時有効予約数上限）は**現行の単枠 `createReservation` に enforcement が存在しない**（実測・既存ギャップ＝親 §8 バックログの範疇）ため、本枝番でグループ側だけ先行 enforce しない（単枠とグループで非対称な制限は買い占め防止として無意味かつ不公平）。**将来 enforcement を導入する際の規定をここで確定**する: 件数は**グループ=1件（`is_group_primary=TRUE` 基準）**で数える（枠数で数えると 60 分メニューが 2 件扱いになり不公平）。
- **PII**: グループレスポンスは本人/管理者向けのみ。マトリックスUI 側（F03.4.4）には従来どおり PII を載せない。
- **監査ログ**: グループの作成・承認・キャンセル・完了・ノーショーを `audit_logs` に記録（groupId・枠数付き）。

## 8. 受け入れ条件（テスト可能・正常/異常/境界）

### 実機E2E の前提データ手順（第二弾・/実機 用）

1. **準備順序を厳守**: チーム作成 → `PUT /reservation-settings/business-hours`（**非 NULL の実時刻**。NULL のままだと generate が全セル skip し「グループを組む枠がない」偽陰性）→ ライン作成 → メニュー作成（F03.4.1）→ テンプレ作成 → generate（F03.4.2）→ グループ予約。
2. **generate は tomorrow 以降のみ**生成する。当日枠・直近時刻のシナリオ（即時来店のグループ等）は**手動 `POST /reservation-slots`**（30分セル×連続）で用意する。
3. **時刻境界 AC（G-8 のキャンセル締切等）は固定 Clock 注入＋手動枠**で検証する（明日以降の generate 枠では「締切 24h 前を過ぎた」状態を作れない/実時刻依存で flaky になるため）。
4. 認可 E2E（G-12 等）は使い捨てチームの新規作成で行う（`feedback_authz_e2e_seed_membership_pollution`）。実機は認証付き CRUD 一気通貫（作成→一覧折りたたみ→キャンセル→booked_count 復帰）まで確認する（`feedback_e2e_real_full_crud`）。

- **G-1（正常・AUTO 確定）**: カット60分（必要枠2）を `slotIds=[10:00枠, 10:30枠], lineId=1` で POST → 201・`status=CONFIRMED`・`slotCount=2`。**観測点**: `reservations` 2 行（同一 group_id・先頭行のみ `is_group_primary=TRUE`・全行 CONFIRMED）、両 slot の `booked_count=1`（capacity=1 なら `slot_status=FULL`）。
- **G-2（満席・全ロールバック）**: 2 枠中 2 枠目が満席のとき POST は 409=RESERVATION_039。**観測点**: `reservations` に行が増えていない・**1 枠目の `booked_count` も増えていない**（部分成功禁止の核心）。
- **G-3（境界・連続性）**: `[10:00-10:30, 11:00-11:30]`（間に10:30枠を挟まない）は 400=038。`[10:00-10:30, 10:30-11:00]` は 201（隣接=連続）。別ライン混在・別日混在も 400=038。
- **G-4（境界・枠数）**: 16 枠は 201、17 枠は 400=041。メニュー必要枠数 2 に対し slotIds 1 個は 400=038、3 個（延長）は 201。
- **G-5（メニュー提供可否）**: menu_lines が `[席2]` のみのメニューを `lineId=1`（席1）で POST → 400=**043**（`GROUP_MENU_LINE_NOT_OFFERED`）。menu_lines 0 件（全ライン可）なら任意ラインで 201。
- **G-6（予約不可枠）**: グループのいずれかの枠が機能B の overlap に該当すると 400=009（行・booked_count とも不変）。
- **G-7（手動承認とグループ遷移）**: MANUAL チームで POST → 全行 PENDING。`/confirm` で全行 CONFIRMED（部分 confirm は存在しない）。グループ行への単票 `/reservations/{id}/confirm` は 400=042。
- **G-8（キャンセル締切・先頭枠基準）**: `cancel_deadline_hours=24`・先頭枠開始が 20 時間後のとき本人 cancel は 400=026。ADMIN cancel は 200。締切内の本人 cancel は 200 で**全枠** CANCELLED・全 slot の booked_count が減り FULL→AVAILABLE 復帰。**観測点**: 固定 Clock 注入で境界（deadline ちょうど）を検証。
- **G-9（通知・リマインドの一本化）**: G-1 の作成で `ReservationCreatedEvent`/`ReservationConfirmedEvent` が**各 1 回だけ**発行される。**観測点（二層）**: ①発行回数 = `ApplicationEventPublisher.publishEvent` の呼出回数がイベント型ごとに **1**（UT: モック/`@RecordApplicationEvents` で型別にカウント検証） ②副作用 = `reservation_reminders` が代表行 reservationId に対する 1 セット（24h/1h）のみ・`email_outbox` が有効宛先 × 1 通のみ（枠数を乗じない・実 DB IT）。
- **G-10（一覧の折りたたみ）**: `GET /reservations/my` にグループが **1 件**として現れ、`groupId`/`groupSize=2`/期間が 10:00〜11:00 で返る。兄弟行は現れない。チーム一覧・upcoming も同様。`getStats` の CONFIRMED 件数はグループ=1 で数えられる。
- **G-11（既存互換）**: 単枠予約（既存 `POST /reservations`）の作成・キャンセル・一覧・統計が本改修後も既存テスト green のまま（`group_id=NULL`/`is_group_primary=TRUE` 経路）。
- **G-12（IDOR）**: 他人のグループへの GET/cancel（非 ADMIN）・他チームの groupId は 404=RESERVATION_040。
- **G-13（デッドロック耐性・実 DB 並行 IT）**: **実 DB（Testcontainers MySQL）上の並行統合テスト**で担保する（純 Mockito UT では InnoDB のロック挙動を踏まないため不可）。シナリオ: capacity=1 の同一 2 枠（slotId 昇順/逆順の slotIds）を **2 スレッドから同時 POST**（`CountDownLatch` で同時開始）。**観測点**: ①一方が 201・他方が 409（039 or 013）で完了し、`DeadlockLoserDataAccessException` が未変換のまま 500 にならない ②終了後の両 slot の `booked_count` 最終値が**ちょうど 1**（二重確保も取りこぼしもない） ③敗者側の `reservations` に行が残っていない（全ロールバック）。確保ループの slotId 昇順・確保先行（UPDATE→INSERT）の実装順は同 IT ＋コードレビューで確認する。
- **G-14（メニュー名の履歴解決・F03.4.1 E-8 の第二弾側）**: メニューを参照する予約グループ作成後にメニューを論理削除しても、`GET /reservation-groups/{groupId}`・`GET /reservations/my`（代表行）の `menuName` が削除済みメニュー行から解決されて非 null で返る。**観測点**: `reservation_menus.deleted_at` セット後のレスポンス `menuName`（`findByIdIncludingDeleted` 経由）。

## 11. 非機能・アーキ制約

- **UuidV7**: `group_id`/`menu_id` は BINARY(16)。グループ ID はアプリ層 UUIDv7 採番（時刻順ソート可・シャード非依存＝アーキ原則6 の意図に適合。専用親テーブルを作らないためテーブル増ゼロ）。
- **クロスドメインFK禁止/CASCADE 制限**: 追加 FK は `menu_id`→`reservation_menus`（同一ドメイン・RESTRICT）のみ。
- **トランザクション境界**: グループ作成/遷移は reservation ドメイン内の単一 `@Transactional`（原則5）。イベント購読側は既存の AFTER_COMMIT + REQUIRES_NEW を無修正で踏襲。
- **性能**: 作成 tx は最大 16 INSERT + 16 UPDATE + 検証 SELECT 数本（全て PK/インデックスヒット）。一覧の `is_group_primary` は複合インデックス（§3.2）でカバー。
- **1000万ユーザー規模**: `reservations` の行数はグループ導入で最大16倍に増え得るが、実運用のメニューは 1〜3 枠（30〜90分）が主で平均 2 倍程度と見積もる。将来のパーティショニング（親アーキ Phase 3）は `team_id`+`slot_date` 系での分割方針に影響なし（group_id はパーティションキーにしない）。
- **OpenAPI**: 新 DTO 追加後に `generate:types` 同一 PR（`project_openapi_json_chronic_drift`）。FE は生成型優先（`feedback_fe_api_type_assertion_field_lie`）。
