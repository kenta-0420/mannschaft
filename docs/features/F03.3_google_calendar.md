# F08: 外部連携（Google Calendar / iCal 個人同期）

> **ステータス**: 🟢 設計完了（Phase 3 + Phase 4）
> **実装フェーズ**: Phase 4（Phase 3 実装済み）
> **最終更新**: 2026-06-26
> **関連ドキュメント**: スケジュール管理（共有）→ `F05_schedule_shared.md` / 個人スケジュール → `F05_schedule_personal.md`

---

## 1. 概要

外部カレンダーアプリとのスケジュール連携機能。以下2種類のアプローチを提供する。

| 方式 | 対象アプリ | 仕組み | 方向 |
|------|-----------|--------|------|
| **Google Calendar OAuth 同期（Phase 3）** | Google カレンダー | OAuth 2.0 認可 → API でイベントを push | アプリ→Google（一方向）|
| **Google Calendar 双方向同期（Phase 4）** | Google カレンダー | Push Notifications（Webhook）でリアルタイム受信 → 反映 | Google→アプリ（受信のみ追加）|
| **iCal 購読 URL** | Apple カレンダー、Google カレンダー、Outlook 等 | ユーザーが URL を登録 → 外部アプリが定期 pull | アプリ→外部（read-only）|

**Phase 4 の同期方針（マスター御裁可 2026-06-25）**:
- **同期フィールド**: タイトル・開始日時・終了日時・場所のみ（RRULE 繰り返し・添付ファイルは無視）
- **繰り返しイベント**: 一切取り込まない（`recurringEventId` が存在するイベントはスキップ）
- **競合解決**: Mannschaft が正（Mannschaft での変更は常に Google を上書きする。Google での変更は次回 Mannschaft での変更まで保持される）
- **反映ラグ**: Webhook 受信後 数秒〜数分（Google からの Push 通知受信後に Google API で最新取得し反映）

> 管理者レベルの Google カレンダー共有連携（チーム・組織のカレンダーを共有公開する機能）は F09 で別途設計する。

### テーブル定義

#### `user_google_calendar_connections`

ユーザーが個人 Google カレンダーへの自動同期を利用するために必要な OAuth 2.0 認可情報を管理するテーブル。

| カラム名 | 型 | NULL | デフォルト | 説明 |
|---------|---|------|-----------|------|
| `id` | BIGINT UNSIGNED | NO | AUTO_INCREMENT | PK |
| `user_id` | BIGINT UNSIGNED | NO | — | FK → users（ON DELETE CASCADE）|
| `google_account_email` | VARCHAR(255) | NO | — | 連携した Google アカウントのメールアドレス |
| `google_calendar_id` | VARCHAR(255) | NO | 'primary' | 同期先カレンダー ID（デフォルト: ユーザーのメインカレンダー）|
| `access_token` | TEXT | NO | — | Google Calendar API アクセストークン（AES-256-GCM 暗号化）|
| `refresh_token` | TEXT | NO | — | リフレッシュトークン（AES-256-GCM 暗号化）|
| `token_expires_at` | DATETIME | NO | — | アクセストークンの有効期限 |
| `is_active` | BOOLEAN | NO | TRUE | 連携が有効かどうか（AUTH_ERROR または手動解除で FALSE）|
| `personal_sync_enabled` | BOOLEAN | NO | FALSE | 個人スケジュール（`schedules.user_id IS NOT NULL`）を Google カレンダーへ同期するか（アプリ→Google 一方向）。`is_active = FALSE` の場合は同期されない |
| `last_sync_error_type` | ENUM('AUTH_ERROR', 'QUOTA_EXCEEDED', 'NETWORK_ERROR', 'SERVER_ERROR') | YES | NULL | 直近の同期エラー種別。同期成功時に NULL にリセット |
| `last_sync_error_message` | TEXT | YES | NULL | ユーザー向けエラー詳細（設定画面の Google 連携セクションに表示）。同期成功時に NULL にリセット |
| `last_sync_error_at` | DATETIME | YES | NULL | 最後のエラー発生日時（全リトライ失敗後に記録）。同期成功時に NULL にリセット |
| `encryption_key_version` | INT UNSIGNED | NO | 1 | トークン暗号化に使用した AES-256-GCM 鍵のバージョン。鍵ローテーション時の再暗号化管理に使用 |
| `created_at` | DATETIME | NO | CURRENT_TIMESTAMP | |
| `updated_at` | DATETIME | NO | CURRENT_TIMESTAMP ON UPDATE | |

**インデックス**
```sql
UNIQUE KEY uq_ugcc_user_id (user_id)    -- 1ユーザー1 Google アカウント連携（Phase 3 制限）
```

**制約・備考**
- `access_token` / `refresh_token` は **平文保存禁止**（AES-256-GCM で暗号化必須）。暗号鍵は環境変数またはシークレットマネージャー（AWS Secrets Manager 等）で管理し、ソースコードや設定ファイルには含めない
- **暗号鍵ローテーション**: 新しい鍵バージョンを追加した場合、新規暗号化は最新バージョンで行い `encryption_key_version` を更新する。旧バージョンのレコードはバッチ処理で順次再暗号化する（`WHERE encryption_key_version < {current_version}` で対象抽出）。復号時は `encryption_key_version` に対応する鍵を使用する。全レコードの再暗号化完了後に旧鍵を破棄する
- 1ユーザーにつき1 Google アカウント連携（複数アカウント対応は Phase 4+ で検討）
- ユーザー退会時は、退会処理サービス内でアプリ層から Google Token Revoke を実施した後、users レコードの物理削除に伴い `ON DELETE CASCADE` で本テーブルも物理削除される（CASCADE はDB操作のみのため、revoke は CASCADE 前にアプリ層で実行する）
- 個人スケジュールの同期設定は `user_calendar_sync_settings` ではなく本カラム（`personal_sync_enabled`）で管理する。チーム・組織は scope_id が必要だが個人スコープに scope_id は存在しないため

#### `user_calendar_sync_settings`

ユーザーが Google カレンダーへの自動同期を有効化したチーム・組織のリスト。

| カラム名 | 型 | NULL | デフォルト | 説明 |
|---------|---|------|-----------|------|
| `id` | BIGINT UNSIGNED | NO | AUTO_INCREMENT | PK |
| `user_id` | BIGINT UNSIGNED | NO | — | FK → users（ON DELETE CASCADE）|
| `scope_type` | ENUM('TEAM', 'ORGANIZATION') | NO | — | 同期対象の種別 |
| `scope_id` | BIGINT UNSIGNED | NO | — | 同期対象のチーム / 組織 ID |
| `is_enabled` | BOOLEAN | NO | TRUE | 同期が有効かどうか |
| `created_at` | DATETIME | NO | CURRENT_TIMESTAMP | |
| `updated_at` | DATETIME | NO | CURRENT_TIMESTAMP ON UPDATE | |

**インデックス**
```sql
UNIQUE KEY uq_ucss_user_scope (user_id, scope_type, scope_id)
INDEX idx_ucss_scope (scope_type, scope_id, is_enabled)    -- スケジュール変更時に同期対象ユーザーを検索
```

**制約・備考**
- `user_google_calendar_connections.is_active = TRUE` でないと同期は実行されない（アプリ層でチェック）
- ユーザーがチーム・組織を退会しても設定レコードは削除しない（再加入時の自動復元のため）
- スケジュール変更時の同期処理では、対象ユーザーの当該チーム/組織への所属状態を確認し、退会済みの場合は同期をスキップする（`user_calendar_sync_settings` の `is_enabled = TRUE` だけでは不十分）
- チーム/組織が物理削除された場合、`scope_id` で参照していたレコードが孤立する（FK なし）。90日バッチの物理削除時にアプリ層で当該 `scope_id` の `user_calendar_sync_settings` も併せて DELETE する

---

#### `user_schedule_google_events`

ユーザーごとの「スケジュール → Google Calendar イベント ID」マッピングテーブル。Google Calendar API の更新・削除操作に使用する。

| カラム名 | 型 | NULL | デフォルト | 説明 |
|---------|---|------|-----------|------|
| `user_id` | BIGINT UNSIGNED | NO | — | FK → users（ON DELETE CASCADE）|
| `schedule_id` | BIGINT UNSIGNED | NO | — | FK → schedules（ON DELETE CASCADE）|
| `google_event_id` | VARCHAR(255) | NO | — | Google Calendar のイベント ID |
| `last_synced_at` | DATETIME | NO | — | 最終同期日時 |

**インデックス**
```sql
UNIQUE KEY uq_usge_user_schedule (user_id, schedule_id)   -- PK 代替（AUTO_INCREMENT PK なし）
INDEX idx_usge_schedule_id (schedule_id)                  -- スケジュール更新時に全同期ユーザーを検索
```

**制約・備考**
- 同期エラー（API エラー・トークン期限切れ等）が発生した場合は最大3回まで指数バックオフで再試行（1分後→10分後→1時間後）。詳細は Section 5「Google Calendar 同期エラーハンドリングフロー」参照

#### `user_ical_tokens`

iCal 購読 URL 用のシークレットトークンを管理するテーブル。1ユーザーにつき1つのトークンのみ有効。

| カラム名 | 型 | NULL | デフォルト | 説明 |
|---------|---|------|-----------|------|
| `id` | BIGINT UNSIGNED | NO | AUTO_INCREMENT | PK |
| `user_id` | BIGINT UNSIGNED | NO | — | FK → users（ON DELETE CASCADE）|
| `token` | VARCHAR(64) | NO | — | URL-safe なランダムトークン（32 バイト = 64 hex 文字、暗号学的乱数）|
| `is_active` | BOOLEAN | NO | TRUE | FALSE にすると URL が無効化される（再生成まで購読不可）|
| `last_polled_at` | DATETIME | YES | NULL | 外部カレンダーが最後に iCal URL をポーリングした日時 |
| `created_at` | DATETIME | NO | CURRENT_TIMESTAMP | |
| `updated_at` | DATETIME | NO | CURRENT_TIMESTAMP ON UPDATE | |

**インデックス**
```sql
UNIQUE KEY uq_uit_user_id (user_id)   -- 1ユーザー1トークン保証
UNIQUE KEY uq_uit_token (token)       -- トークンからユーザーを逆引き
```

**制約・備考**
- トークンは `SecureRandom` 等の暗号学的乱数で生成する（`Math.random()` 禁止）
- トークン再生成時は同一レコードを UPDATE する（履歴は保持しない）
- ユーザー退会時は `ON DELETE CASCADE` で物理削除
- `last_polled_at` はポーリング検知・レート制限の補助情報として使用する

## 4. API設計

### エンドポイント一覧

#### Google Calendar OAuth 同期
| メソッド | パス | 認証 | 説明 | フェーズ |
|---------|------|------|------|---------|
| GET | `/api/v1/me/google-calendar/status` | 必要 | Google カレンダー連携状態確認 | Phase 3 |
| POST | `/api/v1/me/google-calendar/connect` | 必要 | Google Calendar OAuth 連携（認可コード受取）| Phase 3 |
| DELETE | `/api/v1/me/google-calendar/disconnect` | 必要 | Google Calendar 連携解除 | Phase 3 |
| GET | `/api/v1/me/calendar-sync-settings` | 必要 | チーム・組織別の同期設定一覧 | Phase 3 |
| PUT | `/api/v1/me/teams/{id}/calendar-sync` | 必要 | チームの Google カレンダー同期 ON/OFF | Phase 3 |
| PUT | `/api/v1/me/organizations/{id}/calendar-sync` | 必要 | 組織の Google カレンダー同期 ON/OFF | Phase 3 |
| PUT | `/api/v1/me/google-calendar/personal-sync` | 必要 | 個人スケジュールの Google カレンダー同期 ON/OFF | Phase 3 |
| POST | `/api/v1/me/google-calendar/sync` | 必要 | 手動再同期（未同期・失敗スケジュールを再プッシュ）| Phase 3 |
| POST | `/api/v1/webhooks/google-calendar` | **不要**（外部）| Google Calendar Push Notification 受信 | **Phase 4** |

#### iCal 購読 URL
| メソッド | パス | 認証 | 説明 |
|---------|------|------|------|
| GET | `/api/v1/me/ical/token` | 必要 | iCal 購読 URL・トークン取得（未発行なら自動生成）|
| POST | `/api/v1/me/ical/token/regenerate` | 必要 | トークン再生成（旧 URL を即時無効化）|
| DELETE | `/api/v1/me/ical/token` | 必要 | トークン削除（購読 URL を永久無効化）|
| GET | `/ical/{token}.ics` | 不要（トークンが認証を兼ねる）| iCal ファイル配信（外部カレンダーがポーリング）。スコープ別フィルタ対応 |

> `/ical/{token}.ics` は `/api/v1/` プレフィックスなしの専用ルート。外部カレンダーアプリがヘッダーなしで直接アクセスするため。
>
> **スコープ別フィルタ（クエリパラメータ方式）**:
> - `/ical/{token}.ics` — 全スケジュール（現行互換・デフォルト）
> - `/ical/{token}.ics?scope=team&id={teamId}` — 特定チームのスケジュールのみ
> - `/ical/{token}.ics?scope=organization&id={orgId}` — 特定組織のスケジュールのみ
> - `/ical/{token}.ics?scope=personal` — 個人スケジュールのみ
>
> トークンは共通（1ユーザー1トークン）。フィルタはクエリパラメータで指定する。不正な `scope` / `id`（未所属チーム等）は無視して空の VCALENDAR を返す（404 にはしない — 退会後もカレンダーアプリがポーリングを続けるため、エラーではなく空データを返す方が安全）。

### リクエスト／レスポンス仕様

#### `GET /api/v1/me/google-calendar/status`

**レスポンス（200 OK）**
```json
{
  "data": {
    "is_connected": true,
    "google_account_email": "user@gmail.com",
    "google_calendar_id": "primary",
    "is_active": true,
    "personal_sync_enabled": false,
    "last_sync_error": null
  }
}
```

> - `is_connected = false` の場合、他のフィールドは全て `null` として返す
> - `last_sync_error` はエラー発生時のみオブジェクト: `{"type": "QUOTA_EXCEEDED", "message": "...", "occurred_at": "2026-03-01T..."}`

---

#### `POST /api/v1/me/google-calendar/connect`

Google OAuth 2.0 の認可コードを受け取り、アクセストークン・リフレッシュトークンを取得して保存する。

**リクエストボディ**
```json
{
  "code": "4/P7q7W91a-oMsCeLvIaQm6bTrgtp...",
  "state": "random-csrf-token-from-session",
  "redirect_uri": "https://app.mannschaft.example.com/oauth/google-calendar/callback"
}
```

> - `state`: フロントエンドが OAuth 認可リクエスト時に生成し、セッションに保存した CSRF 防止トークン。バックエンドはセッション内の値と一致するか検証する（OAuth 2.0 仕様準拠）

**レスポンス（200 OK）**
```json
{
  "data": {
    "google_account_email": "user@gmail.com",
    "google_calendar_id": "primary",
    "is_active": true
  }
}
```

> 既に同じ Google アカウントで連携済みの場合はトークンのみ更新して 200 を返す

**エラーレスポンス**
| ステータス | 条件 |
|-----------|------|
| 400 | `code` または `redirect_uri` が不正・欠落 |
| 401 | 未認証 |
| 422 | Google Token Endpoint からのトークン取得に失敗（認可コード期限切れ・無効等）|
| 422 | `state` パラメータがセッション値と不一致（CSRF 検知）|

---

#### `DELETE /api/v1/me/google-calendar/disconnect`

Google Calendar 連携を解除する。Google 側での認可取り消し（revoke）も実施する。解除後は全チーム・組織・個人の同期が停止する（`user_google_calendar_connections.is_active = FALSE`）。

**レスポンス（204 No Content）**

> - 再連携は `POST /me/google-calendar/connect` から再実施
> - `user_calendar_sync_settings` のレコードは削除しない（再連携時に設定を復元するため）
> - `user_schedule_google_events` のレコードは全件 DELETE する（再連携時に別アカウントの `google_event_id` で操作する事故を防止。Google 側の既存イベントは残る）
> - Google 側の既存イベントは削除しない（ユーザーの過去イベント履歴を保持するため。revoke 後は API アクセス不可のため削除不能な場合もある）

#### `PUT /api/v1/me/teams/{id}/calendar-sync`

チームの Google カレンダー同期を ON/OFF 切り替える。初回 ON 時に過去の未同期スケジュール（今日以降の未来分）を一括同期する。

**リクエストボディ**
```json
{
  "is_enabled": true
}
```

**レスポンス（200 OK）**
```json
{
  "data": {
    "team_id": 1,
    "is_enabled": true,
    "backfill_count": 12
  }
}
```

> `backfill_count`: 初回 ON 時に遡り同期したスケジュール件数。既に同期済みまたは OFF 切替時は 0

**エラーレスポンス（共通）**
| ステータス | 条件 |
|-----------|------|
| 400 | バリデーションエラー |
| 401 | 未認証 |
| 403 | 当該チーム/組織に所属していない |
| 404 | チーム/組織が存在しない |
| 422 | Google Calendar 未連携のまま同期 ON を要求（`/me/google-calendar/connect` が未完了）|

---

> `backfill_count`: 初回 ON 時に遡り同期した個人スケジュール件数（今日以降の未来分）。既に同期済みまたは OFF 切替時は 0

**エラーレスポンス**
| ステータス | 条件 |
|-----------|------|
| 401 | 未認証 |
| 422 | Google Calendar 未連携（`is_active = FALSE` または未接続）|

#### `POST /api/v1/me/google-calendar/sync`

同期エラーで失敗したスケジュールを手動で再同期する。`is_active = TRUE` の場合のみ実行可能。

**レスポンス（202 Accepted）**
```json
{
  "data": {
    "backfill_count": 3,
    "message": "同期を開始しました。完了まで数分かかる場合があります。"
  }
}
```

> - `backfill_count`: 未同期スケジュール（`user_schedule_google_events` に未登録）のスケジュール数（@Async 開始前に事前算出）
> - 同期処理は @Async で非同期実行。成功後に `last_sync_error_*` をクリアする

**エラーレスポンス**
| ステータス | 条件 |
|-----------|------|
| 401 | 未認証 |
| 422 | `is_active = FALSE`（AUTH_ERROR による連携解除済み。`/me/google-calendar/connect` で再連携が必要）|

iCal 購読 URL を返す。トークン未発行の場合は自動生成して返す。

> - `webcal_url`: 技術ユーザーがカレンダーアプリに直接貼り付ける用（`webcal://` スキーム）

トークンを再生成する。旧トークンの URL は即時無効化される。

トークンを物理削除する（購読 URL を永久無効化）。Valkey キャッシュ（`ical:{token}`、`ical_ratelimit:{token}`）も同時に削除する。

**レスポンス（204 No Content）**

> 再び購読 URL が必要な場合は `GET /api/v1/me/ical/token` で新規発行する（新しいトークンが生成される）

#### `GET /ical/{token}.ics`

iCal 形式（RFC 5545 準拠）のスケジュールを返す。外部カレンダーアプリが定期的にポーリングする。

**`?action=subscribe` クエリパラメータ（カレンダー登録ショートカット）**

クエリパラメータに `action=subscribe` が含まれる場合、iCal データは返さず即座に `webcal://` スキームへリダイレクトする。フロントエンドの「カレンダーに登録」ボタンはこの URL（`subscribe_url`）を使用する。

| 項目 | 値 |
|-----|---|
| ステータス | `302 Found` |
| `Location` | `webcal://{host}/ical/{token}.ics`（`?action=subscribe` は除去） |
| `Cache-Control` | `no-store`（ブラウザにリダイレクト先をキャッシュさせない） |
| レート制限 | **スキップ**（iCal 生成・DB クエリなし）|

> - iOS / macOS: `webcal://` を検知してカレンダー.app が自動起動し「購読しますか？」ダイアログを表示
> - Android / Windows: `webcal://` の自動起動が効かない場合のため、画面に `ical_url`（`https://`）も手動コピー用として併記する
> - 外部カレンダーアプリの定期ポーリングは `webcal://` ではなく `ical_url`（`https://`）に対して行われるため、通常の iCal 配信フローに影響しない

**レスポンスヘッダー（通常リクエスト）**
```
Content-Type: text/calendar; charset=utf-8
Content-Disposition: attachment; filename="mannschaft.ics"
Cache-Control: no-cache, private
ETag: "{schedules の最終更新に基づくハッシュ}"
Last-Modified: "{最新スケジュールの updated_at}"
```

> `Cache-Control: no-cache, private` により、CDN・プロキシはキャッシュせず、クライアントは ETag/If-None-Match で毎回検証する

**レスポンスボディ例（iCalendar 形式）**
```
BEGIN:VCALENDAR
VERSION:2.0
PRODID:-//Mannschaft//Mannschaft//JA
CALNAME:Mannschaft スケジュール
X-WR-TIMEZONE:{user_timezone}
REFRESH-INTERVAL;VALUE=DURATION:PT15M
X-PUBLISHED-TTL:PT15M
BEGIN:VTIMEZONE
TZID:{user_timezone}
...
END:VTIMEZONE
BEGIN:VEVENT
UID:schedule-10@mannschaft.app
SUMMARY:[FC Tokyo Youth] 火木練習
DTSTART;TZID={user_timezone}:20260401T190000
DTEND;TZID={user_timezone}:20260401T210000
LOCATION:駒沢公園
DESCRIPTION:出欠: 未回答\nhttps://app.mannschaft.example.com/schedules/10
DTSTAMP:20260301T010000Z
LAST-MODIFIED:20260301T010000Z
STATUS:CONFIRMED
BEGIN:VALARM
TRIGGER:-PT30M
ACTION:DISPLAY
DESCRIPTION:Mannschaft スケジュールリマインダー
END:VALARM
END:VEVENT
BEGIN:VEVENT
UID:schedule-500@mannschaft.app
SUMMARY:歯医者の予約
DTSTART;TZID={user_timezone}:20260410T140000
DTEND;TZID={user_timezone}:20260410T150000
LOCATION:〇〇歯科
DESCRIPTION:https://app.mannschaft.example.com/schedules/500
DTSTAMP:20260301T010000Z
LAST-MODIFIED:20260301T010000Z

ACTION:DISPLAY

END:VALARM

```

> `{user_timezone}` は `users.timezone`（デフォルト: `Asia/Tokyo`）から取得する。Phase 1 の users テーブルに `timezone VARCHAR(50) NOT NULL DEFAULT 'Asia/Tokyo'` を追加すること。IANA タイムゾーン ID（`Asia/Tokyo`, `America/New_York` 等）を使用する

**VEVENT フィールド定義**
| フィールド | 値 | 補足 |
|-----------|---|------|
| `UID` | `schedule-{id}@mannschaft.app` | スケジュール ID が一意性を保証 |
| `SUMMARY` | チーム/組織スケジュール: `[{scope_name}] {title}` / 個人スケジュール: `{title}` | |
| `DTSTART` / `DTEND` | `all_day = TRUE` の場合は DATE 形式（`DTSTART;VALUE=DATE:`）、否の場合は TZID 付き DATETIME。TZID はユーザーの `timezone` 設定を使用 | |
| `STATUS` | `CONFIRMED`（CANCELLED スケジュールは iCal 配信対象外のため、配信されるイベントは常に CONFIRMED）| |
| `DESCRIPTION` | 構造化テキスト。①出欠ステータス（チーム/組織スケジュールのみ: `出欠: {attending/absent/undecided/未回答}`）②スケジュール `description`（あれば）③アプリ内URL `https://{host}/schedules/{id}`。各要素は `\n` 区切り。NULL の要素は省略 | |
| `LOCATION` | `location` フィールドの内容（NULL の場合は省略）| |
| `VALARM` | デフォルト30分前リマインダー（`TRIGGER:-PT30M`）。Apple Calendar / Outlook がネイティブ通知を表示する。Google Calendar は iCal の VALARM を無視し独自の通知設定を優先する | |

**配信スコープ**
- **配信期間**: `start_at >= TODAY - 2ヶ月` かつ `start_at <= TODAY + 12ヶ月`
- **配信対象（デフォルト）**: `GET /my/calendar` と同じ横断ビュー（個人 + 参加中の全チーム/組織スケジュール）
- **スコープ別フィルタ**: クエリパラメータ `scope` / `id` が指定された場合、配信対象を絞り込む
  - `?scope=team&id={teamId}` — 当該チームのスケジュールのみ
  - `?scope=organization&id={orgId}` — 当該組織のスケジュールのみ
  - `?scope=personal` — 個人スケジュール（`schedules.user_id = 本人`）のみ
  - 未所属スコープ・存在しない ID の場合は空の VCALENDAR を返す（404 にはしない）
- **CANCELLED 除外**: `status = CANCELLED` のスケジュールは iCal 配信対象外とする。iCal プロトコルではイベント削除の伝播が弱く、CANCELLED イベントが外部カレンダーに残骸として残り続けるため。キャンセル情報はアプリ内で確認する運用とする（Google Calendar 同期側では `status:cancelled` で正しく処理されるため影響なし）
- **visibility フィルタ**: ユーザーの現在ロールを動的に評価し `min_view_role` 条件を満たすスケジュールのみ配信
- **件数上限**: 最大 500件。超過した場合は未来のスケジュールを優先して返す（詳細は Section 5 参照）
- **キャッシュ**: Valkey TTL 15分。キャッシュキーは `ical:{token}:{scope}:{id}`（スコープ未指定時は `ical:{token}:all:0`）に iCal 文字列 + ETag を保存。キャッシュヒット時は DB クエリ省略。TTL 自然失効で最大15分の更新ラグが発生する（許容範囲と判断）
- **将来の拡張**: 過去遡及範囲は Phase 4+ の「プロ設定」でユーザー選択式への拡張を検討。初期リリースでは固定

**レスポンスヘッダー（通常時）**
```
Content-Type: text/calendar; charset=utf-8
ETag: "{SHA256(MAX(updated_at) | COUNT(*)) の hex 64文字}"
Last-Modified: "{対象スケジュール群の最大 updated_at (RFC 7231 形式)}"
```

> - ETag はスケジュール群の最終更新日時と件数から計算（iCal 文字列の生成前に取得可能）
> - クライアントが `If-None-Match: "{ETag}"` を送信し一致した場合 → **304 Not Modified**（ボディなし・iCal 生成なし）
> - Apple Calendar・Google Calendar・Outlook はいずれも ETag / Last-Modified を尊重し、304 受信時はデータ転送を省略する

**エラーレスポンス**
| ステータス | 条件 |
|-----------|------|
| 304 | クライアントのキャッシュが最新（`If-None-Match` が現在の ETag と一致）|
| 404 | トークンが存在しない / `is_active = FALSE` |
| 429 | レート制限超過（`Retry-After: 300` ヘッダーを返す）|

## 5. ビジネスロジック

### Google カレンダー個人同期フロー

```
[連携開始]
1. POST /api/v1/me/google-calendar/connect を受付
2. `state` パラメータをセッション値と照合（不一致は 422）
3. Google OAuth 2.0 認可コードを Google Token Endpoint に送信
4. アクセストークン・リフレッシュトークンを取得（失敗時は 422）
5. 既存レコードがある場合のアカウント変更検知:
   a. 既存の `google_account_email` と新アカウントを比較
   b. 異なる場合: `user_schedule_google_events` を全件 DELETE（旧アカウントの google_event_id 無効化）
      + `personal_sync_enabled = FALSE` にリセット
6. 両トークンを AES-256-GCM で暗号化して user_google_calendar_connections に UPSERT
   （`is_active = TRUE` を明示的に設定。再連携時にアクティブ状態を復元する）
7. 200 OK を返す

[同期有効化]
1. PUT /api/v1/me/teams/{id}/calendar-sync または PUT /api/v1/me/organizations/{id}/calendar-sync
   （is_enabled: true）を受付（以降のフローは両スコープ共通。scope_type が TEAM / ORGANIZATION で異なるのみ）
2. user_google_calendar_connections.is_active = TRUE か確認（未連携は 422）
3. user_calendar_sync_settings を UPSERT（is_enabled = true）
4. バックフィル対象件数を事前に取得（@Async 開始前・同期処理とは別に実施）:
   a. 当該チームの schedules（start_at >= NOW()、deleted_at IS NULL）を取得
   b. user_schedule_google_events に未登録のスケジュールを抽出し、件数を backfill_count として保持
5. 200 OK を返す（backfill_count を含む; バックフィル処理は @Async で非同期継続）
6. @Async: 手順 4-b の未登録スケジュールを Google Calendar にイベント作成
   → 成功したものを user_schedule_google_events に INSERT

[個人スケジュール同期設定変更]
1. PUT /api/v1/me/google-calendar/personal-sync（is_enabled: true）を受付
2. user_google_calendar_connections.is_active = TRUE か確認（未連携は 422）
3. user_google_calendar_connections.personal_sync_enabled を UPDATE
4. ON 時: 個人スケジュール（user_id = 本人、start_at >= NOW()、deleted_at IS NULL）で
   user_schedule_google_events に未登録のものを @Async でバックフィル
5. 200 OK を返す（backfill_count を含む）

[スケジュール変更時の自動同期（ApplicationEvent 受信）]
- 前提チェック: 対象ユーザーの `is_active = TRUE` かつ当該スコープの同期設定が有効かつ当該チーム/組織に所属中であることを確認（いずれか不成立なら同期スキップ）
- **GOOGLE_IMPORT スキップ（Phase 4 との無限ループ防止）**: `schedules.source = 'GOOGLE_IMPORT'` の場合は同期スキップする。Google から取り込んだスケジュールを再び Google にプッシュすると Google → Mannschaft → Google の無限ループが発生するため
- ファンアウト制御: 大規模チーム（N人同期）では1スケジュール変更で N件の Google API 呼び出しが発生する。以下の段階的制御を適用する:
  a. **即時処理（N <= 200）**: Google Calendar Batch API（最大50件/バッチリクエスト）を使用して @Async で非同期実行。メインスレッドへの影響を防ぐ
  b. **キューイング処理（N > 200）**: 先頭200件は即時 Batch 処理。残りは Valkey Stream（key: `gcal_sync_queue`）にエンキューし、バックグラウンドワーカーが 100件/分 のペースで段階処理する。超過ユーザーの同期完了まで数分〜数十分の遅延が発生する（許容範囲と判断）
  c. **日次クォータ監視**: Google API 呼び出し件数を Valkey カウンター（`gcal_api_daily:{date}`、TTL 25時間）で集計。80万件/日（デフォルト quota 100万件の80%）到達時にワーカーを一時停止し、アラートを発報する
- SCHEDULE_CREATED  → 同期設定ユーザーの Google Calendar にイベント作成 → user_schedule_google_events INSERT
- SCHEDULE_UPDATED  → ApplicationEvent に変更フィールド名リスト (`changedFields`) を含める。Google Calendar イベントに影響するフィールド（`title`, `start_at`, `end_at`, `location`, `description`, `status`, `all_day`）のいずれかが含まれる場合のみ同期を実行する。`memo` 等の内部フィールドのみの変更時は同期スキップ → user_schedule_google_events から google_event_id を取得 → Google Calendar API で UPDATE
- SCHEDULE_CANCELLED → user_schedule_google_events から google_event_id を取得 → Google Calendar API でイベントの status を "cancelled" に更新（マッピングは保持）
- SCHEDULE_REOPENED  → user_schedule_google_events にマッピングが存在する場合 → Google Calendar API でイベントの status を "confirmed" に更新して復元
- SCHEDULE_DELETED   → user_schedule_google_events から google_event_id を取得 → Google Calendar API でイベント削除
                   → user_schedule_google_events からレコードを DELETE

[連携解除（DELETE /api/v1/me/google-calendar/disconnect）]
1. Google Token Revoke Endpoint に refresh_token を送信（access_token は期限切れの可能性があるため refresh_token を優先。失敗してもベストエフォート）
2. user_schedule_google_events から当該ユーザーのレコードを全件 DELETE（再連携時の旧 google_event_id 誤操作防止）
3. user_google_calendar_connections.is_active = FALSE に UPDATE
   （レコード自体は保持。user_calendar_sync_settings も保持して再連携時に設定復元可能にする）

[トークンリフレッシュ]
- API 呼び出し前に token_expires_at を確認
- 期限切れの場合: Google Token Endpoint にリフレッシュトークンで再取得
- リフレッシュ失敗時: is_active = FALSE に設定し、ユーザーに再連携通知を送信
```

### Google Calendar 同期エラーハンドリングフロー

```
[エラー種別の判定と即時対応]
- 401 / 403（認証エラー）    → AUTH_ERROR: リトライなし。即座に失敗処理へ進む
- 429（クォータ超過）        → QUOTA_EXCEEDED: リトライ対象
- 5xx（Google サーバーエラー）→ SERVER_ERROR: リトライ対象
- タイムアウト・接続失敗      → NETWORK_ERROR: リトライ対象

[リトライ戦略（QUOTA_EXCEEDED / SERVER_ERROR / NETWORK_ERROR の場合）]
- Spring @Retryable を使用:
    maxAttempts = 4（初回1回 + 再試行3回）
    backoff = @Backoff(delay = 60_000, multiplier = 10.0, maxDelay = 3_600_000)
    → 試行タイミング: 即時 → 1分後 → 10分後 → 1時間後
- ※ @Async と @Retryable の同一メソッド適用は Spring AOP の制約により不可。
      リトライ対象の同期ロジックは別サービスクラスに切り出して @Retryable を付与する

[全リトライ失敗時 / AUTH_ERROR 時（@Recover または catch で処理）]
1. user_google_calendar_connections を UPDATE:
   - last_sync_error_type = '{エラー種別}'
   - last_sync_error_message = '{ユーザー向けメッセージ}'（例: "Google カレンダーとの同期に失敗しました。設定画面から再同期を試みてください"）
   - last_sync_error_at = NOW()
   - AUTH_ERROR の場合のみ: is_active = FALSE
2. アプリ内通知を送信（通知システムの設計は別途 Feature Doc で定義）
   - 通知内容: "{チーム名} のスケジュールが Google カレンダーに同期できませんでした"
   - AUTH_ERROR の場合: "Google カレンダーの連携が切れました。再連携してください"

[同期成功時]
- last_sync_error_type / last_sync_error_message / last_sync_error_at を NULL にリセット
  （設定画面のエラー表示をクリアするため）

[手動再同期（POST /api/v1/me/google-calendar/sync）]
1. is_active = FALSE なら 422 を返す（AUTH_ERROR のため再連携が先決）
2. 未同期スケジュールを検出（backfill ロジックと同一: schedules と user_schedule_google_events を比較）
3. backfill_count を返す（202 Accepted）
4. @Async で未同期スケジュールを Google Calendar に再プッシュ
   - リトライ戦略（上記と同様）で実行
   - 成功後: last_sync_error_* を NULL にリセット
   - 失敗後: last_sync_error_* を更新
```

### iCal ファイル生成フロー

```
[GET /ical/{token}.ics?action=subscribe 受付時（webcal:// リダイレクト）]
1. {token} をキーに user_ical_tokens を検索
   - レコードが存在しない または is_active = FALSE → 404 を返す
2. 302 Found を返す:
   - Location: webcal://{host}/ical/{token}.ics（?action=subscribe は除去、scope/id パラメータは保持）
   - Cache-Control: no-store
   ※ レート制限チェック・iCal 生成・DB 更新は一切行わない

[GET /ical/{token}.ics 受付時（通常 iCal 配信）]
1. {token} をキーに user_ical_tokens を検索
2. レコードが存在しない または is_active = FALSE → 404 を返す
3. クエリパラメータからスコープフィルタを解析:
   - `scope=team&id={N}` → チーム単体モード
   - `scope=organization&id={N}` → 組織単体モード
   - `scope=personal` → 個人スケジュールのみモード
   - パラメータなし → 全スケジュール（デフォルト）
   - 不正なパラメータ（scope だけで id なし等）→ デフォルトにフォールバック
4. Valkey レート制限チェック（key: `ical_ratelimit:{token}`、TTL: 5分）
   - key が存在する → 429 を返す（`Retry-After: 300` ヘッダー付き）
   - key が存在しない → SET（TTL 5分）して step 5 へ進む
   ※ レート制限はトークン単位（スコープ別ではない）。Nginx `limit_req_zone` による IP 単位のバースト保護と二層構成
5. Valkey キャッシュ確認（key: `ical:{token}:{scope}:{id}`）→ {icalString, etag} を取得
   - HIT:
     a. `If-None-Match` ヘッダーが stored etag と一致 → 304 Not Modified を返す（iCal 生成なし・DB クエリなし）
     b. 一致しない または `If-None-Match` なし → cached iCal 文字列を返す（step 12 へ）
   - MISS: step 6 へ進む
6. user_id からユーザーのロール情報・タイムゾーン設定を取得
7. 軽量メタデータクエリ（ETag 早期算出・iCal 生成前に実行）:
   SELECT MAX(s.updated_at), COUNT(*) FROM schedules s
   WHERE [スコープフィルタ + visibility filter + date range + status != 'CANCELLED' + deleted_at IS NULL]
   → ETag = SHA256("{max_updated_at}|{count}|{scope}:{id}") を計算
   → `If-None-Match` ヘッダーが一致する場合 → 304 Not Modified を返す（iCal 生成スキップ）
8. user_ical_tokens.last_polled_at を現在時刻に UPDATE（実際に iCal 生成が必要な場合のみ）
9. スケジュールを2段階クエリで取得（スコープフィルタ + `status != 'CANCELLED'` + `deleted_at IS NULL` + min_view_role フィルタを適用）:
   a. 未来スケジュール: start_at >= TODAY かつ start_at <= TODAY + 12ヶ月
      ORDER BY start_at ASC  LIMIT 500
   b. 過去スケジュール: start_at >= TODAY - 2ヶ月 かつ start_at < TODAY
      ORDER BY start_at DESC  LIMIT MAX(0, 500 - 手順aの件数)
   c. a + b をマージして start_at ASC で再ソート（合計最大 500件）
   d. スコープフィルタが指定されたチーム/組織にユーザーが未所属の場合 → 0件（空 VCALENDAR を返す）
10. schedules を RFC 5545 形式に変換して VCALENDAR を生成
    - X-WR-TIMEZONE / VTIMEZONE: ユーザーの `timezone` 設定から動的生成
    - VEVENT の UID: schedule-{id}@mannschaft.app
    - SUMMARY: チーム/組織は "[{scope_name}] {title}"、個人は "{title}"
    - STATUS: 常に CONFIRMED（CANCELLED は配信対象外のため）
    - DESCRIPTION: 構造化テキスト（出欠ステータス + description + アプリ内URL）
    - VALARM: TRIGGER:-PT30M のデフォルトリマインダーを付与
    - all_day = TRUE → DTSTART;VALUE=DATE:、FALSE → DTSTART;TZID={user_timezone}:
11. {icalString, etag} を Valkey にキャッシュ（key: `ical:{token}:{scope}:{id}`、TTL: 15分）
12. ETag・Last-Modified ヘッダーを付与し、Content-Type: text/calendar; charset=utf-8 で返す

[トークン再生成・削除時のキャッシュ処理]
- POST /api/v1/me/ical/token/regenerate:
  旧トークンの Valkey キャッシュを明示削除（`DEL ical:{旧token}:*` パターン削除で全スコープキャッシュを一括削除、`DEL ical_ratelimit:{旧token}`）
- DELETE /api/v1/me/ical/token: 同様に両キーを削除

[トークン生成（GET /api/v1/me/ical/token で未発行時）]
1. SecureRandom で 32 バイトのランダム値を生成（hex エンコードで 64 文字）
2. user_ical_tokens に INSERT（user_id, token, is_active = TRUE）
3. ical_url・subscribe_url・webcal_url を組み立ててレスポンスを返す
   - ical_url     = https://{host}/ical/{token}.ics
   - subscribe_url = https://{host}/ical/{token}.ics?action=subscribe
   - webcal_url   = webcal://{host}/ical/{token}.ics

[トークン再生成（POST /api/v1/me/ical/token/regenerate）]
1. 新しいトークン（32 バイト乱数）を生成
2. user_ical_tokens を UPDATE（token = 新トークン、last_polled_at = NULL、updated_at = 現在時刻）
3. 旧トークンは即時無効化（UPDATE により参照不可）
4. 新しい iCal URL をレスポンスとして返す
```

### iCal レート制限・通信最適化

```
[レート制限の二層構成]

層1 - Nginx（IP 単位のバースト保護）:
  limit_req_zone $binary_remote_addr zone=ical:10m rate=30r/m;
  → 1 IP あたり 30 リクエスト/分（同一 NAT IP の複数ユーザーを考慮した緩い上限）
  → バースト攻撃・クローラーをアプリ到達前に遮断

層2 - Valkey（トークン単位の持続レート制限）:
  key:   ical_ratelimit:{token}
  TTL:   300秒（5分）
  操作:  EXISTS → 429 の場合はここで返す / 存在しない場合は SET EX 300 して続行
  → Apple Calendar（15分間隔）/ Google Calendar・Outlook（1時間以上）の標準ポーリングに対し
     1回/5分は十分な余裕を持つ設定
  → 同一トークンからの過剰ポーリング（バグ・手動リロード連打等）を個別に制御

[ETag によるデータ転送最適化]
  ETag 値: SHA256("{MAX(visible_schedules.updated_at)}|{COUNT(visible_schedules)}") → hex 64文字
  算出タイミング: iCal 文字列の生成前（軽量 SELECT クエリ1本で取得可能）
  保存先:  Valkey（`ical:{token}` に iCal 文字列と etag をペアで保存）
  動作:
    ① キャッシュ HIT 時: stored etag と If-None-Match を比較 → 一致で 304（DB クエリなし）
    ② キャッシュ MISS 時: 軽量クエリで etag を算出 → 一致で 304（iCal 生成なし）
                          → 不一致の場合のみ iCal を生成してキャッシュに保存
  効果:
    - スケジュールが更新されない限り、ポーリングごとの iCal 生成・データ転送量ゼロ
    - キャッシュ期限切れ後も iCal 生成をスキップできる（従来は生成後に比較していた）
    - Apple Calendar は ETag を正しく処理することを確認済み（標準動作）

[標準的なカレンダーアプリとの対応表]
  アプリ            | 標準ポーリング間隔 | レート制限（5分/回）| ETag 対応 |
  ------------------|-------------------|---------------------|-----------|
  Apple Calendar    | 15分              | ◎ 問題なし           | ○        |
  Google Calendar   | 1〜24時間         | ◎ 問題なし           | ○        |
  Outlook           | 1〜3時間          | ◎ 問題なし           | ○        |
  Thunderbird       | 30分〜1時間       | ◎ 問題なし           | ○        |
```

### P4-1. DB 設計追加

#### `google_calendar_webhook_channels`（Phase 4 新規）

Google Calendar Push Notifications のチャンネル情報を管理するテーブル。1ユーザーにつき1チャンネル。チャンネルの有効期限は最大7日（Google の制限）。

| カラム名 | 型 | NULL | デフォルト | 説明 |
|---------|---|------|-----------|------|
| `id` | BIGINT UNSIGNED | NO | AUTO_INCREMENT | PK |
| `user_id` | BIGINT UNSIGNED | NO | — | FK → users（ON DELETE CASCADE）|
| `channel_id` | VARCHAR(255) | NO | — | Google に送ったチャンネルの UUID（`X-Goog-Channel-ID` ヘッダーに対応）|
| `resource_id` | VARCHAR(255) | NO | — | Google Calendar のリソース ID（`X-Goog-Resource-ID` ヘッダーに対応。チャンネル停止時に使用）|
| `channel_token` | VARCHAR(64) | NO | — | Webhook 真正性検証用トークン（SecureRandom 32 バイト hex。`X-Goog-Channel-Token` と照合）|
| `expires_at` | DATETIME | NO | — | チャンネル有効期限（Google から返却される expiration を UTC で保存）|
| `last_received_at` | DATETIME | YES | NULL | 最後に Push Notification を受信した日時。`events.list` の `updatedMin` 算出に使用（`last_received_at - 10分`）|
| `created_at` | DATETIME | NO | CURRENT_TIMESTAMP | |
| `updated_at` | DATETIME | NO | CURRENT_TIMESTAMP ON UPDATE | |

**インデックス**
```sql
UNIQUE KEY uq_gcwc_user_id (user_id)          -- 1ユーザー1チャンネル（UPSERT）
UNIQUE KEY uq_gcwc_channel_id (channel_id)    -- X-Goog-Channel-ID からユーザーを逆引き
INDEX idx_gcwc_expires_at (expires_at)        -- 期限切れチャンネルの一括更新バッチで使用
```

**制約・備考**
- `channel_token` は SecureRandom で生成し**平文保存**でよい（秘密情報ではなく HMAC 検証用の識別子）
- 有効期限は Google 側の最大値（6日23時間 = 604 800 秒）に合わせ、`expires_at = NOW() + 6日23時間` として登録する（7日に設定すると Google が拒否するため余裕を持つ）
- チャンネル更新時は既存レコードを UPSERT（停止→再登録）する。旧 `channel_id` と `resource_id` でチャンネル停止を実施してから新規登録する
- ユーザー退会時は `ON DELETE CASCADE` で物理削除。アプリ層で Google チャンネル停止（revoke）を先に実施すること

#### `user_schedule_google_events` カラム追加（Phase 4）

Phase 3 テーブルに双方向同期用の2カラムを追加する。

| 追加カラム | 型 | NULL | デフォルト | 説明 |
|----------|---|------|-----------|------|
| `sync_direction` | ENUM('PUSH_ONLY', 'BIDIRECTIONAL') | NO | 'PUSH_ONLY' | PUSH_ONLY: アプリ→Google のみ（Phase 3 互換）。BIDIRECTIONAL: Google から取り込んだイベントを含む双方向同期中 |
| `google_etag` | VARCHAR(255) | YES | NULL | Google イベントの ETag。Webhook 受信後の `events.list` 応答と比較し、変化なしならスキップして冪等性を確保 |

**制約・備考**
- `google_etag` は Google API 同期成功時（Phase 3 の push 方向・Phase 4 の受信方向 両方）に最新の ETag で更新する。Phase 3 の同期処理（SCHEDULE_UPDATED 等）でも Google API 呼び出し後に `google_etag` を更新すること（Phase 4 Webhook 受信時に「変化なし」と正しく判定するため）
- 既存レコードの `sync_direction` は全て `PUSH_ONLY` のまま維持する（ALTER TABLE でデフォルト値が自動適用）
- **Google から新規取り込みした予定は `BIDIRECTIONAL` で登録する**（P4-3 Step 6d）。`PUSH_ONLY` のままにすると Phase 5 以降のチーム双方向同期で区別できなくなるため

### P4-2. API 設計追加

#### Webhook 受信エンドポイント

| メソッド | パス | 認証 | 説明 |
|---------|------|------|------|
| POST | `/api/v1/webhooks/google-calendar` | **不要**（Google から送信）| Google Calendar Push Notification 受信 |

**セキュリティ設計**:
- Spring Security の `SecurityConfig` で `/api/v1/webhooks/google-calendar` を `permitAll()` および CSRF 除外リストに追加する
- 真正性検証は `X-Goog-Channel-Token` ヘッダーと DB の `channel_token` の一致で行う（不一致は即 403）
- `X-Goog-Channel-ID` で該当チャンネルを特定（存在しない場合は 404）

**リクエストボディ**: なし（Google は Push Notification をヘッダーのみで送信する。`@RequestBody` を定義しないこと）

**Google が送るリクエストヘッダー**
| ヘッダー | 値 | 説明 |
|---------|---|------|
| `X-Goog-Channel-ID` | `"uuid-..."` | 登録したチャンネルの UUID |
| `X-Goog-Resource-ID` | `"..."` | Google Calendar のリソース ID |
| `X-Goog-Channel-Token` | `"hex64..."` | 登録時に指定したトークン（真正性確認用）|
| `X-Goog-Resource-State` | `"sync"\|"exists"\|"updated"` | 変更種別（注: Google Calendar は `"deleted"` を直接送信しない。イベント削除は `status="cancelled"` の `"updated"` 通知として届く）|
| `X-Goog-Message-Number` | `"1"` 等 | メッセージ連番（単調増加・欠落は正常。処理順保証なし）|

**レスポンス**
| ステータス | 条件 |
|-----------|------|
| 200 | 正常受信（state に関わらず Google は 200 を期待する）|
| 403 | `X-Goog-Channel-Token` が DB の `channel_token` と不一致（CSRF防止）|
| 404 | `X-Goog-Channel-ID` が DB に存在しない（失効チャンネルからの到達等）|

> Google は 200 以外を受信した場合もリトライしない。403/404 はログに記録するが、ユーザーへのエラー通知は不要（次回チャンネル更新時に自動復旧）。

### P4-3. ビジネスロジック（Phase 4）

#### Webhook チャンネル登録フロー

```
[チャンネル登録トリガー（以下のいずれかで発火）]
  A. 個人同期 ON（PUT /me/google-calendar/personal-sync is_enabled=true）
  B. ダッシュボード表示時の自動更新（後述）
  C. 週次バッチ（後述）

[チャンネル登録手順]
1. SecureRandom で 32 バイトの channel_token（hex 64 文字）を生成
2. UUID.randomUUID() で channel_id を生成
3. Google Calendar API: Events.watch を呼び出す
   - calendarId: user_google_calendar_connections.google_calendar_id
   - type: "web_hook"
   - id: channel_id（上記で生成した UUID）
   - address: "{APP_BASE_URL}/api/v1/webhooks/google-calendar"
   - token: channel_token
   - expiration: (现在时刻 + 6日23時間のUNIX timestamp ミリ秒)
4. Google から expiration（UNIXミリ秒）と resourceId を受け取る
5. google_calendar_webhook_channels に UPSERT:
   - user_id, channel_id, resource_id, channel_token, expires_at（UTCに変換）
6. 旧チャンネルが存在した場合（UPSERT の BEFORE で旧 channel_id/resource_id を退避）:
   → 旧チャンネルを Google Calendar API: Channels.stop で停止（ベストエフォート。失敗しても継続）

[チャンネル登録エラーハンドリング]
- 401/403（OAuth エラー）: is_active = FALSE に設定。ユーザーに再連携通知
- 429（クォータ超過）: 指数バックオフでリトライ（3回）
- 5xx: 指数バックオフでリトライ（3回）
- 全失敗時: ログ記録。次回ダッシュボード表示時に再試行（致命的ではない）
```

---

#### Webhook 受信フロー（`POST /api/v1/webhooks/google-calendar`）

```
[受信処理]
1. X-Goog-Channel-ID で google_calendar_webhook_channels を検索
   - 存在しない → 404（失効チャンネル）
2. DB の channel_token と X-Goog-Channel-Token を比較
   - 不一致 → 403（CSRF 防止）
3. X-Goog-Resource-State を確認:
   - "sync"   → ノーオペレーション（チャンネル登録直後の確認通知）。200 を返す
   - "exists" → ノーオペレーション。200 を返す
   - "updated" → Step 4 へ（Google 側で変更・削除が発生）
   - その他（未知の state）→ ログ記録して 200 を返す（Google が将来新しい state を追加した場合の前向き互換）

[updated 処理（Step 4〜7）]
4. user_id から user_google_calendar_connections を取得
   - is_active = FALSE → 処理スキップ（200 を返す）
   - personal_sync_enabled = FALSE → 処理スキップ
5. `google_calendar_webhook_channels.last_received_at` を現在時刻に UPDATE
6. Google Calendar API: Events.list を呼び出し、直近の変更イベントを取得
   - showDeleted=true, orderBy=updated, maxResults=50
   - updatedMin: (last_received_at の更新前の値 - 10分)。null の場合（初回）は NOW() - 30分を使用（重複受信の吸収バッファ）
7. 取得したイベントをループ処理:
   a. recurringEventId が存在する → スキップ（繰り返しイベントは一切取り込まない）
   b. status = "cancelled" → Step 8-1（削除処理）へ
   c. user_schedule_google_events で google_event_id が登録済みか確認
      - 未登録 → Mannschaft の個人スケジュールとして新規登録（Step 7d）
      - 登録済み:
        i. google_etag が変化していない → スキップ（冪等性）
        ii. 変化あり → 既存 Mannschaft スケジュールを更新（Step 7e）
   d. 新規スケジュール登録:
      - title = Google の summary（max 255 文字にトランケート）
      - start_at / end_at:
        - `start.dateTime` が存在する → DATETIME として変換（ユーザータイムゾーン基準）、`all_day = false`
        - `start.dateTime` が null（全日予定）→ `start.date`（YYYY-MM-DD）を取得し `all_day = true`。`start_at = start.date の 00:00:00`、`end_at = end.date の 00:00:00`
      - location = Google の location（null の場合は省略）
      - user_id = 連携ユーザー ID（個人スケジュール）
      - source = 'GOOGLE_IMPORT'（Google からの取り込み識別用。schedules テーブルに source カラムを追加 ※）
      - user_schedule_google_events に INSERT（sync_direction='BIDIRECTIONAL', google_etag=最新 ETag）
   e. 既存スケジュール更新:
      - **競合解決ルール**: Mannschaft が正。次回 Mannschaft での更新時に Google の値は上書きされる。それまでの間は Google の最新値を Mannschaft に反映する
      - 更新対象フィールド: title, start_at, end_at, location のみ（all_day も start.dateTime の有無で更新）
        description, status, memo 等は変更しない（Mannschaft の値を維持）
      - user_schedule_google_events の google_etag を最新値に更新
8. 200 を返す

[削除処理（Step 8-1: status="cancelled" のイベント）]
8-1. google_event_id に対応する user_schedule_google_events を検索
   - 存在しない → 処理スキップ（Mannschaft 未取り込みのイベントの削除）
   - 存在する → schedule_id から schedules を取得し、soft delete（deleted_at = NOW()）
   - user_schedule_google_events の該当レコードを DELETE

[エラーハンドリング]
- Google API 呼び出し（Events.list）で 401/403: is_active = FALSE 設定 + 通知
- 429 / 5xx: ログ記録のみ（次回 Webhook で自然リカバリ）
- DB エラー: ログ記録のみ（200 を返し Google へのリトライを防ぐ）
```

> ※ `schedules` テーブルへの `source ENUM('MANNSCHAFT', 'GOOGLE_IMPORT') DEFAULT 'MANNSCHAFT'` カラム追加は Flyway V132.003 で実施（既存レコードは全て `MANNSCHAFT` でバックフィル）。

#### Webhook チャンネル維持フロー

Google Calendar Push Notification チャンネルは最大7日で失効する。以下の二重構成で維持する。

**ダッシュボード表示時の自動更新**

```
[トリガー: GET /api/v1/dashboard または GET /api/v1/me/google-calendar/status]
1. リクエストユーザーの google_calendar_webhook_channels を取得（存在しない場合はスキップ）
2. expires_at <= NOW() + 3日（72時間）の場合のみ更新処理を実行
   - ユーザーが毎日使えば自然に更新される設計
   - 3日前閾値を設けることで「期限切れ直前に連続アクセスしても1回だけ更新」とはならないが、
     UPSERT の結果として idempotent（channel_id が変わるため）
3. チャンネル登録フロー（P4-3 の手順）を @Async で実行（レスポンスをブロックしない）
4. 更新は1ユーザーにつき最短 3日に1回（expires_at が 3日以上残っていれば何度来ても更新しない）
```

**日次バッチ（フォールバック）**

```
[スケジュール: 毎日 02:00（Asia/Tokyo）]
理由: 週次バッチ（月曜1回）+ 3日前閾値の組み合わせでは、バッチ直後に更新されたチャンネルを
      ユーザーが7日間ダッシュボードを開かない場合に次回バッチまで検知できず、
      最大14日（バッチ間隔7日 + 有効期限7日）の同期停止が発生しうる。
      毎日実行にすることで最大漏れ期間を「有効期限7日 - 閾値3日 + 1日 = 5日」に圧縮する。

1. google_calendar_webhook_channels から expires_at <= NOW() + 3日 の全レコードを取得
2. 各ユーザーについてチャンネル登録フロー（P4-3）を並列実行（最大 10スレッド）
3. 完了件数・失敗件数をログに記録（監視ダッシュボード向け）
4. バッチ全失敗時の手動回復: `GoogleWebhookChannelRenewalBatch.runManually()` を管理者が
   アプリサーバーで直接呼び出すか、`POST /admin/google-calendar/webhook/renew-all` 管理APIを利用
   （管理APIは Phase 4 の将来拡張で追加予定。初期は手動実行で対応）

[失効チャンネルのクリーンアップ]
- 同バッチで expires_at < NOW() - 7日（すでに失効から7日以上経過）のレコードを DELETE（Google 側はすでに不活性）
```

#### 連携解除時のチャンネル停止

```
[DELETE /api/v1/me/google-calendar/disconnect に追加]
既存の Phase 3 処理（revoke, user_schedule_google_events 全件 DELETE, is_active=FALSE）に加えて:
1. google_calendar_webhook_channels を取得（存在しない場合はスキップ）
2. Google Calendar API: Channels.stop（channel_id, resource_id）をベストエフォートで呼び出す
3. google_calendar_webhook_channels のレコードを DELETE

[Google アカウント変更時（POST /api/v1/me/google-calendar/connect で別アカウント）]
Phase 3 の「既存の google_account_email と新アカウントが異なる場合」に追加:
- 旧 google_calendar_webhook_channels を取得（存在する場合）
- 旧チャンネルを Channels.stop でベストエフォート停止
- google_calendar_webhook_channels の旧レコードを DELETE
- 新アカウントで接続後、チャンネル登録フローを実行（personal_sync_enabled が TRUE の場合）

[個人同期 OFF 時のチャンネル停止（PUT /api/v1/me/google-calendar/personal-sync is_enabled=false）]
1. google_calendar_webhook_channels を取得（存在しない場合はスキップ）
2. Google Calendar API: Channels.stop（channel_id, resource_id）をベストエフォートで呼び出す
3. google_calendar_webhook_channels のレコードを DELETE（チャンネルを解放）
   ※ 再度 ON にした場合はチャンネル登録フローを実行する

[ユーザー退会時（UserWithdrawalService 経由）]
`ON DELETE CASCADE` でレコードが削除される前に:
1. google_calendar_webhook_channels を取得
2. Google Calendar API: Channels.stop（channel_id, resource_id）をベストエフォートで呼び出す
   （失敗しても最大7日で Google 側のチャンネルは自動期限切れになるため許容）
3. CASCADE で自動削除されるため DELETE 不要
```

### P4-6. セキュリティ考慮事項（Phase 4）

| 脅威 | 対策 |
|------|------|
| なりすまし Webhook（第三者が POST を送信） | `X-Goog-Channel-Token` と DB の `channel_token` を **`MessageDigest.isEqual()`** で定数時間比較（timing attack 防止。`String.equals()` は早期リターンするため使用禁止）。64 文字のランダムトークン（256 bit エントロピー）で実用上十分 |
| CSRF | Spring Security の CSRF 保護を `/api/v1/webhooks/google-calendar`（**特定パスのみ**。`/api/v1/webhooks/**` ワイルドカードは将来の誤爆リスクがあるため使用しない）で除外。代わりに channel_token 検証で代替 |
| replay 攻撃 | `X-Goog-Message-Number` は単調増加だが欠落は正常。同一 google_etag の受信は冪等に処理（変更なしとしてスキップ）|
| DDoS / 過剰リクエスト | Nginx のレート制限で先に遮断（例: `limit_req_zone $binary_remote_addr zone=webhook:10m rate=10r/s`）。channel_token 検証は Nginx 後段で実施 |
| OAuth トークン漏洩 | Phase 3 と同様に AES-256-GCM 暗号化（既存設計を踏襲）|
| Google 側 API quota 超過 | Webhook 受信時の `events.list` は1回のみ（`maxResults=50`）。日次クォータ監視は Phase 3 の既存仕組みを共用 |
| 個人情報の無制限取り込み | 対象は `personal_sync_enabled = TRUE` かつ `is_active = TRUE` のユーザーのみ。繰り返しイベントは除外 |
| 無限同期ループ | `schedules.source = 'GOOGLE_IMPORT'` のスケジュールは Phase 3 の自動同期（SCHEDULE_CREATED/UPDATED）から除外（Section 5 に追記）|

### P4-7. 受け入れ条件（Phase 4・試練の対象）

```

AC-9: ダッシュボード API 呼び出し時、チャンネル有効期限が 3 日以内なら @Async で自動更新される

AC-13: 連携解除（DELETE /me/google-calendar/disconnect）時に Webhook チャンネルも停止・レコード削除される

AC-15: Google から取り込んだスケジュール（source='GOOGLE_IMPORT'）が更新・作成された場合、Phase 3 の自動同期（Google へのプッシュ）は実行されない（無限ループ防止）

AC-18: Google アカウントを別アカウントに変更（POST /connect）した場合、旧 Webhook チャンネルが停止されて新アカウント用チャンネルが登録される
```
