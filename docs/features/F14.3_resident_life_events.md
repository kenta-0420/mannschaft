## 1. 概要

### 1.1 解決する問題

住民（区分所有者・居住者）が **逝去** または **転出** したとき、システムには次の3つの穴がある。

| # | 穴 | 実測の根拠 |
|---|---|---|
| P-1 | **札を立てる人間の操作点が存在しない** | `UserEntity#changeStatus` に `DECEASED`/`RELOCATED` を渡す呼出元がゼロ。`UserStatusChangedEvent`（`auth/event/UserStatusChangedEvent.java`）の publish 元もゼロ |
| P-2 | **受信側だけが完成していて宙吊り** | `ProxyConsentLifeEventJob`（`proxy/batch/ProxyConsentLifeEventJob.java:25-39`）は `LIFE_EVENT_STATUSES = Set.of(UserStatus.DECEASED, UserStatus.RELOCATED)` を `@EventListener` で受け、`ProxyConsentLifecycleService#revokeAllForUser` により当該ユーザの全代理入力同意書を `RevokeMethod.AUTO_BY_LIFE_EVENT` で失効させる。**発火元が無いので一度も動いたことがない** |
| P-3 | **札が立つと本人の画面が白紙になる（CMP-050 の副作用）** | CMP-050 で `UserRoleRepository` の在籍プリミティブ4本に `u.status = 'ACTIVE'` を課したため、`RELOCATED`/`DECEASED` のユーザーは在籍集合が空になる。ログインは通る（`AuthService:187-197` が拒否するのは `PENDING_VERIFICATION` と `FROZEN` のみ）のに、ログイン後に何も見えない。これが CMP-053 |

住民台帳側にも対になる穴がある。`resident_registry.death_status` は 4 値（`ALIVE`/`SUSPECTED`/`CONFIRMED`/`CANCELLED_FALSE_ALARM`、`V9.102`）まで DDL・Entity・Enum が揃っているのに、**書き手は `ResidentRegistryService#markDeathSuspected`（:244-258）の 1 箇所だけ**で、これは `DelinquencyEscalationService#advanceStage` の D+120 自動起票から `SUSPECTED` を立てるためのものである。**人が `CONFIRMED` に確定させる本番経路が無い。** F09.15 自身がこれを認めている（同書 L607-614: 手動入力 API は v2 送り）。

本設計はこの 2 つの空箱を 1 本の線で繋ぐ。

#### 1.2.1 F09.15 §9.5 との整合（衝突ではない）

F09.15 §9.5 は次のように書く。

> `death_status = CONFIRMED` への遷移単独では封緘解除されない。**独立した二者承認プロセス** が必須。これにより、死亡誤確認時に取り消し（`CANCELLED_FALSE_ALARM`）すれば封緘は無傷で守られる。

本設計はこれを **破らない**。本設計が `CONFIRMED` 遷移に自動で連動させるのは以下の 3 つだけである。

- `users.status` → `DECEASED`（可逆。§9.2 で取り消せる）
- 代理入力同意書の失効（**不可逆**。§3.1）
- 管理権限の即時停止（§3.4・A-1 方針）

**封緘（`succession_pre_registrations` / `unseal_requests`）には一切触れない。** 二者承認は F09.15 の管轄のまま残る。実装時に第4の連動を足さないことを §17.2 のテストで固定する。

## 3. 中核原則

### 3.1 自動と人の分離（本設計の中核）

```
理事の操作（1回）
        │
        ├─ 自動 ─► resident_registry の札
        ├─ 自動 ─► users.status = DECEASED / RELOCATED
        │              └─► UserStatusChangedEvent（AFTER_COMMIT）
        │                      └─► ProxyConsentLifeEventJob
        │                              └─► 代理入力同意書を全件失効（不可逆）
        ├─ 自動 ─► 管理権限の即時停止（§3.4）
        ├─ 自動 ─► 監査ログ1件（§10）
        ├─ 自動 ─► 理事へ通知1通（§11.1）
        └─ 自動 ─► 住民一覧に「要対応」バッジ（§11.2）
                        │
                        ▼
                理事が見て、判断して、明示的に
                        │
                        ▼
                  所属解除（別操作・§9.3）
```

**同意書の失効は自動、所属の解除は人（理事）が行う。** この分離が本設計の中核である。理由は非対称なリスクにある。

- 同意書が失効し続けても誰も困らない（代理入力ができなくなるだけで、再度取り直せる）。逆に、逝去した人の名義で代理入力が通り続ける方が危険である。よって **自動・即時・不可逆** にする。
- 所属を自動で終わらせると、誤登録のとき本人の予定・請求・履歴の見え方が一斉に消え、復旧が難しい。よって **人が見て判断する**。

#### 3.1.1 不可逆性

**札を取り消しても、失効した同意書は復活しない。** `ProxyConsentLifecycleService#revokeAllForUser` は失効を記録するだけで、逆操作を持たない。本設計はこれに逆操作を足さない（履歴の改竄になるため）。UI は §12.3 で明示的に警告する。

#### 3.1.2 組合をまたぐ波及を仕様として受容する（A-2）

`revokeAllForUser(userId, reason)` は **ユーザー単位**で全同意書を失効させる。したがって **A 組合の理事が立てた札が、本人の B 組合の同意書まで失効させる**。

これを **仕様として受容する**。F14.1 受信側の改造（スコープ単位失効への変更）は行わない。根拠は次の 2 点である。

1. 逝去は人に属する事実であり、A 組合で逝去した人が B 組合では生きている、ということはない。**逝去に関しては全スコープ波及が正しい**。
2. 転出については「A マンションから転出した人の B マンションの同意書」が失効するのは過剰である。しかし §4.2 R-1 により、`RELOCATED` は **当該ユーザーの全 `resident_registry` 行が転出済みになったときにのみ**立つ。B マンションに現役の居住者行が残っていれば札は立たず、波及も起きない。**R-1 を全スコープ横断で定義することで、過剰な波及は構造的に防がれる**（§4.2 中3 対応）。

ただし理事から見て予期しない挙動になりうるため、**§12.3 の確認ダイアログに「他の管理組合の同意書も失効します」を明記**し、i18n キー `proxy.lifeEvent.confirm.crossOrgWarning` を設ける。AC-215 が 2 組織にまたがるケースを固定する。

### 3.2 不変条件

> **INV-1**: ユーザーが**在籍集合**に現れてよいのは、**ログインが通り、かつログイン後のゲートで保護 API を遮断されない状態**のときに限る。

`PENDING_PARENTAL_CONSENT` は `AuthService` がログインを通す（拒否対象は `PENDING_VERIFICATION`・`FROZEN` の 2 つのみ）が、`ParentalConsentGateFilter` が許可リスト外の保護 API を **403 `AUTH_070`**（401 は絶対に返さない。FE `useApi.ts` の 401 ハンドラが無限リフレッシュを起こすため。同フィルタ javadoc :29-32）で遮断する。在籍を持たせても使えないため、在籍を持たせない。

> **INV-2**: 札は所属を終わらせない。所属の終わりは §9.3 の明示操作によってのみ表現される。

> **INV-3（Codex 中7 で弱めた）**: 札の付与・取消・所属解除のいずれも、監査ログ 1 件の記録を**試みる**。ただしこれは **best effort** であり、「必ず 1 件残る」ことは保証しない。
>
> **弱めた理由（実測）**: `AuditLogService#record`（`auth/service/AuditLogService.java:49-70`）は `@Async` で、内部で `catch (Exception e) { log.error(...) }` し **rethrow しない**（fire-and-forget）。したがって DB 障害・executor rejection・プロセス停止では監査行が残らない。初版の INV-3 は「1 件残さずに完了してはならない」と絶対条件を書いていたが、**実装がその条件を満たせない**。満たせない不変条件を掲げるのは、通常成功だけを検証する AC（AC-212/260）で「守れている」と誤認する土壌になる。
>
> **代わりに置く保証**: ①監査の配送失敗を**握りつぶさず可視化**する（§10.2 の欠落検知）②`users.status` が `DECEASED`/`RELOCATED` でありながら RESIDENT カテゴリの監査行が 1 件も無いユーザーを定期的に検出し WARN で運用へ上げる（§9.4.4 の照合バッチに相乗り）。**同期トランザクション化・outbox 化は採らない**（判断根拠は §9.4.3）。

> **INV-4**: 台帳とアカウントは 1 対 N である。伝播規則は §4.2 に定める。

> **INV-5**: **在籍を持つことと、管理権限を持つことは別の層である。** 札が立ったユーザーは在籍を保持するが、当該スコープの管理権限（ADMIN/DEPUTY_ADMIN としての操作）を**行使できない**。§3.4。

> **INV-6（A-5）**: 札が立ったユーザーは、**fan-out 配信の宛先から外れない**。組合からのお知らせ・回覧・通知は従来どおり届く。所属解除されて初めて届かなくなる。§8.7。

### 3.3 本人の画面は白紙にならない（ただし例外がある）

札が立っている間、本設計が保証するのは次の**2種類**である。

| 保証 | 内容 | 担保 |
|---|---|---|
| **自分起点の参照** | ログインでき、所属組合／チームが見え、自分の予定・請求・iCal が見える | §8.2 の在籍条件の緩和 |
| **fan-out 配信の受信** | 組合が全員に送るお知らせ・回覧・通知が届く | §8.7 の配信クエリ載せ替え（A-5・INV-6）|

初版は前者しか保証していなかった。しかし §12.3 の所属解除ダイアログは「解除すると**お知らせ**が見られなくなる」と警告している。これは**解除するまでは見られる**という約束であり、後者の保証が無ければ嘘になる。実測でも配信系クエリは `u.status = 'ACTIVE'` 固定であり、札が立った時点で宛先から外れていた（§8.7）。

**ただし、転出については例外がある。これを仕様として明記する。**

`ResidentRegistryRepository#findActiveByUserId` は `WHERE rr.userId = :userId AND rr.moveOutDate IS NULL` である（:18-19）。`move_out_date` を立てた瞬間に、resident ドメインの**自室系 API が参照不能になる**。

| 影響を受けるもの | 実測の根拠 | 転出後の挙動 |
|---|---|---|
| `GET /api/v1/users/me/dwelling-unit` | `ResidentRegistryService#getMyUnit` :181-184 が `findActiveByUserId` → `MY_UNIT_NOT_FOUND` | **404 になる** |
| `GET /api/v1/users/me/resident-info` | 同上 | **404 になる** |
| F09.16 年次居住実態申告の認可 | `isActiveResidentOfOrganization` :210-212 が `findActiveByUserIdAndOrganizationId` を使う | **false になり認可が落ちる** |

**判断: 仕様として受容する。** 「そのマンションから転出した＝もうその住戸の居住者ではない」のだから、自室情報が引けなくなるのは正しい挙動である。年次居住実態申告の対象外になるのも正しい。§3.3 が守るのは **組合員としての在籍**（予定・請求・お知らせ）であって、**居住者としての住戸情報**ではない。この 2 つの線引きを明示する。

なお **逝去（`death_status`）は `findActiveByUserId` の条件に含まれないため、自室系 API に影響しない**。影響するのは転出だけである。

### 3.4 在籍二層 — 「読めるが書けない」（A-1）

札が立ったユーザーは次の二層になる。

| 層 | 判定の入口（実測） | 札付与後 |
|---|---|---|
| **在籍層** | `AccessControlService#isMember` → `MembershipRepository#existsActiveByUserAndScope`（:40-46）、および `UserRoleRepository` の在籍プリミティブ4本 | **保持する**。ダッシュボード・予定・請求・iCal・配信の受信が従来どおり |
| **権限層** | `AccessControlService#resolveEffectiveRole`（private・:231-258）→ `isAdminOrAbove` / `isAdmin` / `checkAdminOrAbove` | **即座に失う**。他人への札付与・台帳編集・権限譲渡その他の管理操作ができなくなる |

**この2層は実装上も別の経路である**（§9.5.1 の実測）。`isMember` は `resolveEffectiveRole` を経由せず、独立した `existsActiveByUserAndScope` を引く。したがって **`resolveEffectiveRole` だけを締めれば、在籍層に一切触れずに権限層だけを落とせる。** これが §9.5 で中枢案を採れる理由である。

**なぜこの分離が必要か（本設計が初めて作り出す危険）**

実測: `AccessControlService#resolveEffectiveRole`（:231-258）は `user_roles` と `memberships.role_kind` だけを見て、**`users.status` も `deleted_at` も一切参照しない**。`isAdminOrAbove` は `ADMIN_ROLES = Set.of("ADMIN","DEPUTY_ADMIN")` に含まれるかを見るだけである（:377-380）。

従来これは到達不能だった。`DECEASED`/`RELOCATED` を立てる経路が存在しなかったからである（P-1）。**本設計が初めてこの状態を到達可能にする。** 対策を同時に入れなければ、「逝去した理事長のアカウントが理事長のまま操作できる」状態を新規に作り出すことになる。

> ⚠️ **この穴は新設 EP だけの問題ではない（第2パス R-1）。** 実測: **resident ドメインのコントローラ9本すべてに `@PreAuthorize` がゼロ**である（`OrgResidentController`・`TeamResidentController` ほか、`grep -c PreAuthorize` が全ファイル 0）。`create`/`update`/`delete`/`verify`/`move-out` はいずれも `SecurityUtils.getCurrentUserId()` を Service へ渡し、Service 内の `checkAdminForResident` だけで守られている。したがって **SpEL 層（`AccessGuard`）にどれだけ検査を足しても、既存の住民台帳の編集・削除・確認・退去処理は素通りする。** 実現手段は §9.5 で中枢案を確定する。

### 4.1 `users.status` 状態機械

現行 7 値（DB CHECK は `V18.014` + `V18.033` で 7 値済み）。

                     └───────────────► ACTIVE ◄───────────────────────┘ 自動復帰
```

#### 4.1.1 操作ごとの直接遷移をやめ、台帳の事実から**再計算**する（Codex 重大4・**全面改訂**）

**初版（0.3 まで）の欠陥**: §9.1／§9.2 は「逝去確定なら `ACTIVE` → `DECEASED`」「逝去取消なら `DECEASED` → `ACTIVE`」という **操作ごとの直接遷移**で書かれていた。逝去と転出は `death_status` と `move_out_date` という**独立した 2 列**であり §6.3.2 のとおり**同時に立ちうる**ため、この書き方は次の操作列で破綻する。

```
① 逝去確定            → users.status = DECEASED
② 全台帳行に転出日を設定 → 現 status が ACTIVE でないので伝播スキップ（DECEASED のまま）
③ 逝去札だけ取消       → 旧規則「現 status が DECEASED なら ACTIVE に戻す」に従い ACTIVE へ
```

最終状態は「死亡確認なし・全行転出済み」であり、R-1 上は **`RELOCATED` でなければならない**。旧規則では `ACTIVE` に戻るため、**転出札が残っている利用者の管理権限が §9.5.7 により復帰し**、同意書の失効条件も崩れる。逆順（転出 → 逝去確定）では現 status が `RELOCATED` なので逝去の伝播がスキップされ、§6.3.2 が定める「`DECEASED` 優先」と一致しない。

**是正: `users.status` は台帳の全事実から一意に再計算する。** 操作の種類・順序・取消順序に一切依存しない。

> **再計算規則（正本。以降すべての節はこれに従う）**
>
> 対象ユーザーに紐づく `deleted_at IS NULL` の `resident_registry` 行を**スコープを問わず全件**取り、次の順に判定する。
>
> ```
> CONFIRMED の行が 1 件以上         -> DECEASED
> それ以外で、全行が move_out_date 非 NULL  -> RELOCATED
> それ以外                          -> ACTIVE
> ```
>
> 行が 1 件も無い場合（全行が論理削除された等）は `ACTIVE` とする。

**運営 status との優先順位（Codex 重大4 で明示化）**: 上の再計算は **`users.status` が現在 `ACTIVE` / `DECEASED` / `RELOCATED` のいずれかであるときにのみ適用する**。`FROZEN` / `ARCHIVED` / `PENDING_VERIFICATION` / `PENDING_PARENTAL_CONSENT` および `deleted_at` 非 NULL のときは**再計算結果を書き込まない**（台帳のみ更新し `userStatusChanged:false`）。運営・認証フローが所有する status のほうが強い。

- これにより `DECEASED` ⇄ `RELOCATED` の**直接遷移は自然に発生しうる**（逝去札を取り消したら全行転出済みだった、等）。初版の「直接遷移禁止」は**撤回する**。禁止していたのは監査追跡のためだったが、監査ログは操作ごとに 1 件ずつ残るため追跡性は失われない。
- 再計算は**冪等**である。同じ台帳状態から何度計算しても同じ結果になるため、§9.4.4 の照合バッチがそのまま整合回復手段になる。

#### 4.1.2 遷移可否表（4.1.1 の再計算規則を表にしたもの）

| 現 `users.status` | 台帳の再計算結果 | 書き込む | 実行者 | 備考 |
|---|---|---|---|---|
| `ACTIVE` / `DECEASED` / `RELOCATED` | `ACTIVE` / `DECEASED` / `RELOCATED` | ✅ 再計算値をそのまま書く | 理事（ADMIN以上）／SYSTEM_ADMIN | §9.1・§9.2。**同意書は復活しない** |
| `FROZEN` / `ARCHIVED` / `PENDING_*` | （何であれ） | ❌ 書かない | — | 台帳の札だけを立てる（§9.1 手順6・B-6）。`userStatusChanged: false` |
| `deleted_at` 非 NULL（退会済み） | （何であれ） | ❌ 書かない | — | 同上 |
| `DECEASED`/`RELOCATED` | — | ✅（既存経路） | 運営が `FROZEN` 等へ | 本設計は妨げない。以後この利用者は上表 2 行目に落ちる |

### 4.2 `resident_registry` の遷移可否と伝播（4値 × 4値）

`resident_registry.user_id` は **NULL 可**（`V9.017`）。アカウントを持たない居住者が存在する。また 1 ユーザーが複数居室・共有持分で **複数行**を持ちうる。

#### 4.2.1 `death_status` の遷移可否表（中1 対応）

| From \ To | `ALIVE` | `SUSPECTED` | `CONFIRMED` | `CANCELLED_FALSE_ALARM` |
|---|---|---|---|---|
| **`ALIVE`** | — | ✅ バッチのみ（`markDeathSuspected`・伝播なし） | ✅ **API**（伝播あり） | ❌ `RESIDENT_012` |
| **`SUSPECTED`** | ❌ | — | ✅ **API**（伝播あり）**← 理事が確定させる典型経路** | ✅ **API**（伝播なし。疑いの取り下げ） |
| **`CONFIRMED`** | ❌ **禁止** | ❌ | ❌ `RESIDENT_012` | ✅ **API**（`DECEASED → ACTIVE` の伝播あり） |
| **`CANCELLED_FALSE_ALARM`** | ❌ | ❌ バッチは立てない（下記） | ✅ **API**（再確定。伝播あり） | — |

**設計上の要点**

- **`SUSPECTED → CONFIRMED` が理事の典型経路である。** 滞納エスカレーション D+120 が `markDeathSuspected` で `SUSPECTED` を自動起票し（:244-258）、理事がそれを見て確定させる。初版の設計書はこの経路を落としていた。
- **`CONFIRMED → ALIVE` は禁止する。** 取消は `CANCELLED_FALSE_ALARM` を経由させる。`ALIVE` に戻すと「一度も疑われなかった」ことになり、監査上の履歴が台帳から消える（軽3 の判断）。**単なる誤入力の訂正であっても `CANCELLED_FALSE_ALARM` が残る**が、これは意図した設計である。訂正の理由は `audit_logs.metadata.reason` に残る。台帳の値が「誤警報」という語感を持つ問題は、**FE 側で `CANCELLED_FALSE_ALARM` を「記録なし（訂正済み）」と表示する**ことで吸収する（i18n `lifeEvent.deathStatus.cancelled`）。
- **`CANCELLED_FALSE_ALARM → CONFIRMED`（再確定）は許可する。** 実測: `markDeathSuspected` は `deathStatus != ALIVE` なら早期 return するため（:248-252）、**一度取り消した居住者はバッチで二度と `SUSPECTED` にならない**。API による再確定を塞ぐと、誤って取り消した居住者を二度と逝去にできなくなる。
- 初版の §9.1 手順3 は「現 `death_status` が `CONFIRMED` なら 409」としか書いておらず、この表と矛盾していた。**手順3 は本表に従う**と改める。

#### 4.2.2 伝播の粒度規則

**伝播は「操作 → 遷移」ではなく「操作 → 台帳更新 → §4.1.1 の再計算 → 書き込み可否判定」の一本道である**（Codex 重大4）。

| 台帳側の操作 | 台帳の更新 | アカウント側 |
|---|---|---|
| `death_status → CONFIRMED` | 常に行う | **§4.1.1 で再計算**。`user_id IS NULL` なら何もしない |
| `death_status → CANCELLED_FALSE_ALARM` | 常に行う | 同上（**取消でも `ACTIVE` に戻るとは限らない**。他行が `CONFIRMED` なら `DECEASED` 継続、全行転出済みなら `RELOCATED`）|
| `death_status → SUSPECTED` | 常に行う（バッチのみ） | **伝播しない**（疑いは判断ではない。再計算も走らせない）|
| `move_out_date: NULL → 日付` | 常に行う | **§4.1.1 で再計算** |
| `move_out_date: 日付 → NULL` | 常に行う | 同上 |

**R-1（転出の粒度規則・全スコープ横断）**: 転出は住戸に属する事実であり、**2 号室から転出しても 5 号室に住み続けているなら転出していない**。よって `RELOCATED` は「当該ユーザーに紐づく `deleted_at IS NULL` の `resident_registry` 行が、**スコープを問わず全て** `move_out_date` 非 NULL」のときに限る。**これは §4.1.1 の再計算規則 2 行目そのものである**（独立した規則ではなく、再計算規則の一部として読むこと）。

> **スコープ横断で定義する理由**（中3 対応）: 伝播先の `users.status` はユーザー単位のグローバルな値であり、その受け手 `revokeAllForUser` もユーザー単位である。判定だけをスコープ内に閉じると、A 組合を転出しただけで B 組合の同意書が失効する。**判定・伝播・副作用の3つを同じ粒度（ユーザー単位）に揃える**ことで整合が取れる。

**R-2（逝去の取消の粒度規則）**: `DECEASED` が外れるのは、当該ユーザーに紐づくどの行も `CONFIRMED` でなくなったときに限る。**外れた先が `ACTIVE` とは限らない**（§4.1.1 の 2 行目に落ちれば `RELOCATED`）。

#### 4.2.3 同一ユーザーの複数台帳行の並行更新（Codex 重大3・**初版に欠落していた**）

**欠陥（実測で確定）**: `ResidentRegistryService#moveOut`（:158-164）は通常の読み取り→更新であり、**ロックを取得しない**。`ResidentRegistryEntity` に **`@Version` は無く**、`ResidentRegistryRepository` の `@Query` 3 本（:18 / :23 / :29）にも `@Lock` / `FOR UPDATE` は**無い**。

したがって同一ユーザーの 2 行を**同時に**転出させると、両トランザクションが R-1 の判定時に「もう一方はまだ転出していない」と読み、**双方が伝播をスキップし得る**。commit 後の台帳は全行転出済みなのに `users.status` は `ACTIVE` のまま残り、**この取りこぼしは永久に回復しない**（以後どの操作も走らないため）。2 件の `CONFIRMED` を同時に取り消した場合も同型で、確認済み行がゼロなのに `DECEASED` が残る。**逐次実行しか扱わない AC-231/232/244 ではこれを検出できない。**

**是正: 同一 `userId` に対するライフイベント更新を直列化する。**

1. **アカウント側の `users` 行を悲観ロックで先に取る。** §9.1 手順 0 として、`user_id` が非 NULL のとき `SELECT ... FOR UPDATE` 相当（`@Lock(LockModeType.PESSIMISTIC_WRITE)` の `findByIdForUpdate(userId)`）を**トランザクションの最初に**発行する。ロック対象を台帳行ではなく `users` 行にするのは、**競合するのが「同一ユーザーの複数台帳行」であり、共通の資源がアカウント側にしか無い**ためである（台帳行をそれぞれロックしても互いを排除できない）。
2. ロック取得後に台帳を更新し、**その後で** §4.1.1 の再計算を行う。ロック区間の内側で全台帳行を読み直すため、もう一方の更新は必ず見える（見えないならまだ commit していないので、こちらのロック待ちで直列化される）。
3. `user_id IS NULL` の居住者はロックを取らない（伝播が無く競合しない）。
4. **再計算が冪等である**（§4.1.1）ため、万一取りこぼしても §9.4.4 の照合バッチが自己修復する。ロックは第一防御、照合は第二防御である。

> ⚠️ **ロックは `users` 行 1 本に限ること。** 複数行をロックすると獲得順序次第でデッドロックする。また `@Transactional` の内側で最初に取り、外部呼び出し（通知・監査）より前に完了させる。ロック保持時間はトランザクション長そのものなので、§9.1 の手順9・10（監査・通知）は `@Async` のまま外へ出す。

### 4.3 `memberships` との独立性

`memberships` / `user_roles` は札を**一切参照しない**。所属が終わるのは §9.3 の明示操作のみ。

## 5. DB 設計

### 5.1 結論: 新規テーブル・新規カラムともに **不要**

| 必要な情報 | 既存の置き場所 |
|---|---|
| 逝去したか | `resident_registry.death_status`（`V9.102`）|
| いつ・誰が逝去の札を立てたか | `death_status_changed_at` / `death_status_changed_by`。`updateDeathStatus(DeathStatus, Long changedBy)` が両方を更新 |
| 転出したか・いつ | `resident_registry.move_out_date`（`V9.017`）。`moveOut(LocalDate)` |
| **なぜ**（理由）・取消の履歴 | `audit_logs`（§10） |
| 誰が所属解除したか | `memberships.left_at` / `leave_reason` + `audit_logs` |

`resident_registry` は BIGINT 主キーを維持する。`V9.102` / `V9.103` の冒頭コメントが前例として明記している。

> `-- F09.1 と同一ドメイン内の拡張であり、主キーは BIGINT を維持する（UUIDv7 化はしない）。`

CLAUDE.md「アーキテクチャ思想」6 の UUIDv7 原則は **新規テーブルを作る場合にのみ**適用される。

### 5.2 転出専用カラムは追加しない

`relocated_at` は **`move_out_date` が既にある**。しかも `PATCH /residents/{id}/move-out` という API と `ResidentRegistryService#moveOut`（:158-176）、`ALREADY_MOVED_OUT` まで実装済みで、`dwelling_units.resident_count` のデクリメントまで面倒を見ている。`relocated_reason` は `audit_logs.metadata` に載せる（自由記述であり検索・集計の要件が無い）。

### 5.3 `occupancy_status` で転出を代替できるか → できない

`occupancy_status`（`OWNER_OCCUPIED`/`RENTED_OUT`/`VACANT`/`SECONDARY_HOME`/`UNKNOWN`）は **住戸の使われ方**を表す。`RENTED_OUT` は区分所有者が住んでいないが**組合員のまま**の状態であり、転出と混同すると賃貸に出しただけの区分所有者に `RELOCATED` が立ち同意書が失効する。よって転出は `move_out_date` を正本とし、`occupancy_status` は触らない。

### 5.4 `memberships.leave_reason` の ENUM 拡張（**要 Flyway**）

`LeaveReason` は現在 `SELF`/`REMOVED`/`GDPR`/`TRANSFER`/`OTHER`。**`DECEASED` と `RELOCATED` の 2 値を追加する。**

追加しないと §9.3 の所属解除がすべて `REMOVED`（＝理事が追い出した）に畳まれ区別できなくなる。

**家老の偵察の前提を1点訂正する**: DB CHECK `chk_memberships_left_reason`（`V60.001__create_memberships_table.sql:39-42`）は値を列挙していない。実体は「`left_at` と `leave_reason` が同時に NULL か同時に非 NULL か」の対応検査のみである。

```sql
CONSTRAINT chk_memberships_left_reason CHECK (
    (left_at IS NULL AND leave_reason IS NULL)
    OR (left_at IS NOT NULL AND leave_reason IS NOT NULL)
),
```

値を列挙しているのは **カラム定義側の MySQL ENUM**（同ファイル L31）である。したがって **CHECK 制約は変更不要。`MODIFY COLUMN` で ENUM 定義だけを拡張する**（§14）。

> `revokedConsentCount` は**設けない**。同意書失効は AFTER_COMMIT の別トランザクション・別スレッドで走るため、同期レスポンスで件数を約束できない。**約束できない値のフィールドを型だけ確保するのは嘘の契約になる**ので置かない。確認手段は §17.3 に定める。

#### 6.1.1 操作系フィールドを一覧 DTO に常設しない（B-8・前回改訂の自己矛盾を是正）

前回改訂（0.2）は、`revokedConsentCount` を上記の理由で退けておきながら、**同じ性質の `userStatusChanged` / `newUserStatus` を `ResidentResponse` に常設していた**（B-4 のフィールド追加案）。一覧取得時にはこれらは意味を持たず常に `false` / `null` になるため、**自分が立てた原則を自分で破っていた**。

**是正: 操作の結果を表すフィールドは操作系 DTO に閉じる。**

| フィールド | 置き場所 |
|---|---|
| `userStatusChanged` / `newUserStatus` | **`ResidentLifeEventResponse` のみ**（`death-status` / `move-out/cancel` / 拡張後の `move-out` の戻り値）|
| `deathStatus` / `lifeEventFlag` / `membershipStillActive` | **`ResidentResponse`**（状態を表すフィールドであり、一覧でも意味を持つ）|

`membershipStillActive` を状態側に置くのは、それが「今この居住者は所属が残っているか」という**継続的な事実**であり、一覧のバッジ表示（§11.2）に必要だからである。

### 6.2 転出の札（既存 API の拡張 + 取消の新設）

```
PATCH /api/v1/organizations/{orgId}/residents/{id}/move-out          （既存を拡張）
PATCH /api/v1/organizations/{orgId}/residents/{id}/move-out/cancel   （新規）
```

**既存 `move-out` の拡張方針（B-8 により前回改訂の B-4 から変更）**

1. リクエストボディ `MoveOutRequest { moveOutDate?: string(date), reason?: string }` を **任意**で受ける（ボディ無しは従来どおり `LocalDate.now()`。後方互換）
2. **レスポンスは `ResidentLifeEventResponse` にする**（§6.1 と同型）

**なぜ破壊的変更を許容するか**: §6.1.1 のとおり、操作系フィールドを状態 DTO に常設しないという原則を優先する。破壊的変更の実害は実測でゼロである。

- `frontend/app/composables/useResidentApi.ts:99` の `moveOutResident` は **呼出元がゼロ**（定義と return 句以外にヒットなし＝現状 dead code）。**追随が必要な FE 呼出元は存在しない。**
- 生成型 `operations["moveOut"]` / `operations["moveOut_1"]`（`frontend/app/types/generated/index.ts` :131545 / :138570、200 → `ApiResponseResidentResponse`）は再生成で自動更新される。CI（`frontend-ci.yml:73-81`）が生成型のドリフトを検査するため、再生成漏れは赤くなる。

### 6.3 所属解除（新規）

```
POST /api/v1/organizations/{orgId}/residents/{id}/membership-release
```

**認可**: SYSTEM_ADMIN または **ADMIN のみ**（DEPUTY_ADMIN 不可。§7）

**Request**

| フィールド | 型 | null許容 | 説明 |
|---|---|---|---|
| `reason` | `string` | ✅ 任意 | 最大 500 文字。監査ログ metadata |
| `expectedFlag` | `string` | ❌ 必須 | `DECEASED` \| `RELOCATED`。**競合検出（optimistic check）**。§6.3.1 |

**Response 200** `{ released: boolean, leaveReason: string }`

#### 6.3.1 `expectedFlag` の位置づけ（中4 対応）

初版は `confirmToken` と呼び「誤操作防止」と説明していたが、**これは誤りである**。この値は FE が画面上の状態から自動送信するものであり、**人の誤操作は一切防がない**。防げるのは「画面を開いてから別の理事が状態を変えた」という **stale state（競合）だけ**である。名称を `expectedFlag` に改め、説明を「競合検出（optimistic check）」に改める。

**FE がこの値をどこから得るか**（D-6 対応）: §6.5 の ADMIN 向け一覧レスポンスが返す `lifeEventFlag`（`DECEASED` \| `RELOCATED` \| `null`）を**そのまま送る**。一覧の行データ以外を生成元にしてはならない。§12.2 に UI 側の受け渡し経路を明記する。

#### 6.3.2 逝去と転出が両方立っている場合の優先順位（中4 対応）

`death_status` と `move_out_date` は独立した 2 列であり、**同時に立ちうる**（典型例: 逝去の札が立った後、遺族が退去届を出す）。

- `lifeEventFlag` および `leaveReason` は **`DECEASED` を優先する**。人に属する事実の方が住戸に属する事実より強いため。**この優先順位は §4.1.1 の再計算規則（`CONFIRMED` を先に見る）と同一であり、二重定義ではなく同じ規則の別表現である**（Codex 重大4 対応で整合を明記）。
- `expectedFlag` に `RELOCATED` が送られてきて実際は両方立っている場合は **`RESIDENT_015`（競合）** を返す。一覧を再読込すれば `DECEASED` が得られる。

**前提条件**: 札が立っていること。立っていなければ `RESIDENT_012`（通常の除名は既存の membership API を使う）。

### 6.4 認可の配置と BOLA 対策（B-3 で 403 に確定）

`docs/security/03_role_authority_model.md` §3.3.3（:245）は新規 EP について「**宣言（SpEL ガード）を第一防御、Service 層明示呼出を第二防御**」とする方針を**標準とする**と定める。本設計の 4 エンドポイントはこれに従う。

| 層 | 実装 | 目的 |
|---|---|---|
| **第一防御（宣言）** | `@PreAuthorize("@accessGuard.isScopeAdmin(authentication, #orgId, 'ORGANIZATION')")`（所属解除は `isScopeStrictAdmin`）| パス変数によるスコープ内ロール判定。**SYSTEM_ADMIN 短絡もここで効く**（§7） |

> ⚠️ **初版の「404 に畳んで存在秘匿する」は事実誤認だったので撤回する。** 実測: `checkAdminForResident` → `checkAdminOrAbove`（:412-416）は非 ADMIN に `COMMON_002`（403）を投げる。既存の `verify` / `move-out` も他スコープ ID に対して 403 である。**既存 API の契約を変えないため 403 に揃える。** 存在秘匿を優先したい場合は resident ドメイン全体の方針変更が必要であり、本設計の射程外とする（§19 U-12）。

#### 6.4.1 `ParentalConsentGateFilter` の許可リスト（D-8 対応）

**新設 4 エンドポイントを許可リストに追加しない。** 許可リストは `isAllowed`（:101-140）にハードコードされており、現在通しているのは `/api/v1/parental-consent/*`・`GET|DELETE /api/v1/users/me`・`POST /api/v1/auth/logout`・`POST /api/v1/auth/refresh`・`/api/i18n/*`・`/api/v1/public/*` のみである。

### 6.5 一覧レスポンスへの札の露出（重5 対応・**初版に欠落していた**）

初版は札の記録・伝播を設計しながら、**一覧 API に札を載せる設計を持っていなかった**。実測: `ResidentResponse` に `deathStatus` フィールドは存在しない（`moveOutDate` はある）。このままでは **FE はバッジを描けない**。

さらに、初版の AC-253/254（「レスポンスに `deathStatus` が含まれない」）は**現状すでに満たされており、実装ゼロで green になる偽の受け入れ条件**であった。

**単一 DTO を維持し、非 ADMIN には機微フィールドを `null` で返す（B-7）。**

| フィールド | 型 | ADMIN / DEPUTY_ADMIN / SYSTEM_ADMIN | 一般メンバー |
|---|---|---|---|
| `deathStatus` | `string`（null許容）| `ALIVE` / `SUSPECTED` / `CONFIRMED` / `CANCELLED_FALSE_ALARM` | **常に `null`** |
| `lifeEventFlag` | `string`（null許容）| `DECEASED` / `RELOCATED` / `null` | **常に `null`** |
| `membershipStillActive` | `boolean`（null許容）| 実値 | **常に `null`** |

`ResidentRegistryService#listByUnit` は現在 `checkMembership` で一般メンバーにも通している（:43-50）。**閲覧者のロールを判定して、機微フィールドを埋めるか `null` のままにするかを切り替える。**

#### 6.5.1 ロール別 DTO に分けない理由（B-7）

ロール別に別クラス（`ResidentPublicResponse`）を返す案は**採らない**。同一エンドポイントが 2 つの戻り値型を持つと、**springdoc は片方しか OpenAPI に出力せず、生成型がその一方に固定される**。結果として `frontend/app/types/generated/index.ts` は実際のレスポンスと食い違い、**FE の型が嘘になる**。しかもこのズレは CI の生成型ドリフト検査（`frontend-ci.yml:73-81`）でも検出できない（生成物とスキーマは一致したままで、スキーマ自体が現実と違うため）。単一 DTO なら型は常に真であり、値が `null` かどうかだけが権限で変わる。

> **実測の補足**: `ResidentResponse` にも `application.yml` にも `@JsonInclude(NON_NULL)` 相当の設定は無い。よって `null` は省略されず `"deathStatus": null` として実際にシリアライズされる。AC-272 はレスポンス JSON 上で観測可能である。

#### 6.5.2 実装上の制約（MapStruct と final フィールド）

`ResidentResponse` は全フィールド `final` の `@RequiredArgsConstructor` DTO であり、`ResidentMapper`（`@Mapper(componentModel = "spring")`）が**フィールド名の自動マッピング**で生成している。ここに機微フィールドを足すと次の問題が出る。

- `deathStatus` は Entity 側に同名の `DeathStatus` enum があるため MapStruct が enum → String を自動変換できる。**しかし権限による出し分けができない**（マッパーは閲覧者を知らない）。
- `lifeEventFlag` と `membershipStillActive` は **Entity に対応するソースが無い**ため、MapStruct は未マップターゲットとしてコンパイル警告／エラーを出す。

**したがってマッパーだけでは組めない。** Service 層に組み立て役（assembler）を置き、`ResidentMapper` で基本項目を詰めた後に、閲覧者のロールと §6.5.3 の一括問い合わせ結果を使って機微フィールドを確定させる。`final` フィールドのため部分的な後付けはできず、**assembler が最終的なコンストラクタ呼び出しを行う**形にする。

#### 6.5.3 `membershipStillActive` の N+1 を避ける（M-3）

居住者ごとに membership を照会すると、住戸数 × 居住者数に比例して SQL が増える。**1000万ユーザーを見据える設計としてこれは許容しない。**

**既存の一括プリミティブを使う。** `MembershipRepository#findActiveRoleKindsByScopeAndUsers(scopeType, scopeId, userIds)`（:204-210）は `userId IN :userIds` で一括解決する投影クエリで、まさにこの用途のために追加されたものである。同メソッドの javadoc（:188-196）はこう書いている。

> 候補者ごとに `findActiveRoleKinds` を呼ぶと候補者数に比例して SQL が増える（**AC-39 が禁じる形**）。

一覧の組み立て手順は次のとおり。

1. 住戸一覧から `resident_registry` 行をまとめて引く（既存）
2. `user_id` が非 NULL のものを集めて `userIds` を作る（**空なら呼ばない**。`IN ()` は不正 SQL）
3. `findActiveRoleKindsByScopeAndUsers` を **1 回**呼び、在籍している `userId` の集合を得る
4. メモリ上で突き合わせて `membershipStillActive` を確定する

これで一覧あたりの追加 SQL は **1 本**に収まる。

#### 6.5.4 本人向け API への機微フィールド漏洩を塞ぐ（Codex 中6・**初版に欠落していた**）

**欠陥（実測で確定）**: 本設計は §6.5 で共有 DTO `ResidentResponse` に `deathStatus` 等を追加する。ところが `ResidentMapper`（`resident/mapper/ResidentMapper.java`）は

```java
@Mapper(componentModel = "spring")
public interface ResidentMapper {
    ResidentResponse toResidentResponse(ResidentRegistryEntity entity);   // :27
```

という **フィールド名の暗黙マッピングだけ**の宣言であり、`ResidentRegistryEntity` には `deathStatus` フィールドが**既に実在する**（`ResidentRegistryEntity.java:111`、`private DeathStatus deathStatus = DeathStatus.ALIVE;`）。したがって **DTO にフィールドを足した瞬間、`toResidentResponse` を呼ぶ全経路が自動的に `deathStatus` を詰める。**

そして**本人向け API がこの経路を直に踏んでいる**。

| 実測 | 内容 |
|---|---|
| `UserResidentController.java:38-40` | `GET /api/v1/users/me/resident-info` が **`ApiResponse<ResidentResponse>` を返す**（一覧 API と同一 DTO）|
| `ResidentRegistryService.java:192-196` | ロール認識 assembler を経由せず **`residentMapper.toResidentResponse(entity)` を直接呼ぶ** |

結果として **本人に `SUSPECTED` や `CANCELLED_FALSE_ALARM` まで露出する**。とりわけ `SUSPECTED`（滞納エスカレーション D+120 の自動起票）は **`users.status` に伝播しない**ため、§13.1 の「本人開示の対象は `users.status` のみ」という方針を**迂回して**本人に届く。「システムがあなたの死亡を疑っています」という、理事の判断ですらない中間状態を本人に見せることになる。

**是正: `ResidentResponse` を生成する全経路を、§6.5.2 のロール認識 assembler へ統一する。**

- `residentMapper.toResidentResponse(...)` の**直接呼出をゼロにする**。マッパーは assembler の内部からのみ呼ばれる。
- assembler は必ず「閲覧者」を引数に取る。**閲覧者が当該スコープの ADMIN / DEPUTY_ADMIN / SYSTEM_ADMIN でない限り、`deathStatus` / `lifeEventFlag` / `membershipStillActive` は `null` で固定する。**
- **本人であることは開示理由にならない。** 本人閲覧は「一般メンバーとしての閲覧」と同じ扱いにする（本人が自分の状態を知る経路は §12.4 の `users.status` バナー 1 本に絞る。これが §13.1 の方針そのものである）。
- 本人 API を別 DTO に分離する案は**採らない**。§6.5.1 の理由（同一 DTO を返す EP が複数あるとき springdoc の出力と FE 生成型がずれる／DTO を増やすほど「新しい経路から漏れる」再発面が増える）と同じで、**経路を 1 本に絞るほうが構造的に強い**。
- **AC-274 / AC-275**（§17.1）が、本人 API のレスポンス JSON に 3 フィールドが `null` で現れること、および `toResidentResponse` の直接呼出元が assembler 以外に存在しないことを固定する。

> ⚠️ **assembler への統一は「今ある呼出元を直す」だけでは守れない。** 将来だれかがマッパーを直接呼ぶ経路を足せば同じ穴が開く。ArchUnit 番人で `ResidentMapper#toResidentResponse` / `#toResidentResponseList` の呼出元を assembler クラス 1 つに限定する（AC-275）。

## 7. 権限モデル

**新しい権限名は追加しない。** 既存の `AccessGuard` で足りる。権限を足すと migration での `INSERT INTO permissions` が必須になり、番人 `PermissionNameCatalogGuardTest` と `DeadPermissionCatalogFlywayIT` の対象が増える。本設計にはロール以上の粒度を必要とする理由が無い。

**段差を付ける**（所属解除の方が強い操作である）。

| 操作 | 必要ロール | 第一防御（SpEL） | 第二防御（Service・entity由来） |
|---|---|---|---|
| 逝去／転出の札 付与・取消 | SYSTEM_ADMIN または ADMIN / DEPUTY_ADMIN | `@accessGuard.isScopeAdmin(...)` | `checkAdminForResident` 相当 |
| **所属解除** | SYSTEM_ADMIN または **ADMIN のみ** | **`@accessGuard.isScopeStrictAdmin(...)`** | `isAdmin(entity由来scopeId)` |

### 7.1 SYSTEM_ADMIN の締め出し問題は `AccessGuard` で解決する（中8 対応）

実測: `AccessControlService#checkAdminOrAbove`（:412-416）に **SYSTEM_ADMIN 短絡は無い**。`ADMIN_ROLES = Set.of("ADMIN","DEPUTY_ADMIN")` であり、`resolveEffectiveRole` はスコープ内の行のみを見るため、team/org が NULL の SYSTEM_ADMIN 行は解決されない。したがって Service 層の `checkAdminOrAbove` だけで組むと **運営（SYSTEM_ADMIN）が §6.3 を実行できない**。§4.1 の遷移可否表が「実行者: 運営」と書く行と矛盾する。

**`AccessGuard` を第一防御に採ることでこれが同時に解決する。** 実測（`common/security/AccessGuard.java`）:

```java
public boolean isScopeAdmin(Authentication authentication, Long scopeId, String scopeType) {
    Long userId = resolveUserId(authentication);
    if (userId == null) { return false; }
    if (accessControlService.isSystemAdmin(userId)) { return true; }   // ← SYSTEM_ADMIN 短絡
    return accessControlService.isAdminOrAbove(userId, scopeId, scopeType);
}
```

`isScopeStrictAdmin`（:65-74）も同型で、`isSystemAdmin` 短絡の後に `isAdmin`（ADMIN のみ・DEPUTY_ADMIN を除く）を呼ぶ。**求めていた段差がそのまま既存 Bean にある。**

> **初版の「`AccessControlService` に `checkAdmin` を1メソッド追加する」提案は撤回する。** 新規メソッドは不要である。
>
> ⚠️ ただし第二防御（Service 層・entity 由来）は SYSTEM_ADMIN 短絡を持たないため、**Service 層の検査にも `isSystemAdmin` の短絡を入れる**（`AccessGuard` と同じ順序）。片方だけに短絡があると SYSTEM_ADMIN が第一防御を抜けて第二防御で落ちる。
>
> ⚠️ **`AccessGuard` は SYSTEM_ADMIN 短絡と段差のためだけに使う。** 管理権限の即時停止（§9.5）は `AccessGuard` では閉じないため、**中枢（`resolveEffectiveRole`）で行う**。`AccessGuard` の `isScopeAdmin` / `isScopeStrictAdmin` は内部で `isAdminOrAbove` / `isAdmin` を呼ぶので、中枢を締めれば**自動的に**札付きユーザーを弾くようになる。`AccessGuard` 側に個別の検査を足す必要はない。

### 7.2 ArchUnit 認可網羅（中9 対応・クラス名を実測）

## 8. CMP-050 在籍条件の緩和

### 8.1 許容集合と各 status の根拠

現行は `u.deleted_at IS NULL AND u.status = 'ACTIVE'`。これを **許容集合方式**に変える。

```sql
u.deleted_at IS NULL AND u.status IN ('ACTIVE','RELOCATED','DECEASED')
```

| status | 在籍を持てるか | 根拠 |
|---|---|---|
| `ACTIVE` | ✅ 許容 | 自明 |
| `RELOCATED` | ✅ **許容** | ログインが通り、ゲートでも遮断されない。**CMP-053 の根治そのもの** |
| `DECEASED` | ✅ **許容** | 同上。未精算請求・遺族による確認導線のため、理事が明示的に所属解除するまで在籍は残る |
| `ARCHIVED` | ❌ 不許容 | ログイン時に自動 `ACTIVE` 復帰するため在籍を持たせなくても実害が出ない。AC-9 が名指しで守っている |
| `FROZEN` | ❌ 不許容 | `AuthService:193-196` が `AUTH_003` でログイン拒否。**CMP-050 の元凶**（凍結 ADMIN へのオーナー譲渡によるロックアウト）を直接防ぐ条件であり緩めてはならない |
| `PENDING_VERIFICATION` | ❌ 不許容 | `AuthService:188-191` が `AUTH_002` でログイン拒否 |
| `PENDING_PARENTAL_CONSENT` | ❌ 不許容 | ログインは通るが `ParentalConsentGateFilter` が 403 `AUTH_070` で遮断する。**在籍を持っても使えない**。INV-1 の精緻化はこの 1 値のために必要である |

> **INV-5 との関係**: 許容集合に `DECEASED`/`RELOCATED` を入れるのは **在籍層**の話であり、**権限層**は §9.5 が別途締める。この 2 層を混同しないこと。許容集合を狭めて権限を止めようとすると、本人の画面が白紙に戻り CMP-053 を再発させる。

**実装上の注意（軽7 訂正）**: 許容集合は 4 本のクエリ（うち各々 UNION の両枝、計 8 箇所）に散らばる。文字列リテラルを 8 回書くとドリフトする。**インタフェースのフィールドは暗黙に `public static final` であり、コンパイル時定数として `@Query` の文字列連結にそのまま使える。**

    @Query(value = "... AND u.status IN (" + MEMBERSHIP_ELIGIBLE_STATUSES + ") ...", nativeQuery = true)
    ...
}
```

#### 9.1.1 手順6 の非対称を解消した理由（B-6）

初版は手順6 で `FROZEN`/`ARCHIVED`/`PENDING_*` に対し **`RESIDENT_014` を返し手順4 もロールバックする**としていた。これは誤りだったので撤回する。

**理由**: 逝去の札が立って `users.status = DECEASED` になった後、遺族が退去届を出す場面を考える。このとき現 status は `ACTIVE` ではないので、初版の設計では **409 + 台帳ロールバックとなり、故人の住戸の退去を台帳に記録できない**。住民台帳の目的（誰がどの住戸に住んでいるかを正しく保つこと）に真っ向から反する。

**訂正後**: 台帳は常に更新し、伝播できないときは伝播だけを飛ばす。`user_id IS NULL` の場合（手順6）とまったく同じ扱いに揃える。`RESIDENT_014` は**廃止する**（§15）。

**転出（`move-out`）とその取消、逝去の取消も、手順はまったく同じである**（Codex 重大4）。手順5 で触る列が `move_out_date` か `death_status` かが違うだけで、手順7 の再計算は**操作の種類を一切参照しない**。0.3 版が操作ごとに別々の規則（「R-1 を満たせば `RELOCATED`」「現 status が `DECEASED` なら `ACTIVE` に戻す」）を書いていたのが §4.1.1 の欠陥の温床だったので、**規則を 1 本に統合する**。

#### 9.3.3 唯一の ADMIN が逝去した場合（重2 後半）

**2 つの相互作用が衝突する。**

- 通常の `MembershipService#leave` は `checkLastAdminProtectedByUserRoles`（:340-364）を呼び、`isAdmin && adminCount <= 1` のとき `MEMBERSHIP_LAST_ADMIN_BLOCKED`（409）を投げる。**唯一の理事長が逝去すると所属解除できない。**
- 一方 `removeMemberWithoutAdminCheck` はこの保護を**意図的にバイパスする**（javadoc :297「⚠️ AccountPurgeService 等の管理者操作専用。通常の API からは呼ばないこと」）。バイパスすると組合が **ADMIN 不在（ロックアウト）**になる。

**判断: バイパスはするが、その前に後任 ADMIN の存在を本設計側で要求する。**

手順5 で **「対象者が当該スコープの ADMIN である」場合に限り**、「対象者以外の ADMIN が 1 人以上在籍しているか」を検査し、いなければ **`RESIDENT_016`（後任理事の選任が必要です・409）** を返す。

> ⚠️ **検査を対象者のロールで限定するのは必須である（B-9）。** 無条件に「ADMIN が 1 人以上いること」を要求すると、**既に ADMIN 不在に陥っている組合では、一般住民の所属解除まで 409 で塞がれる**。逝去した理事の後始末をしたいのに、その理事が唯一の ADMIN だったせいで他の全住民の処理まで止まる、という最悪の詰み方をする。対象が一般住民（MEMBER / SUPPORTER）なら ADMIN の在否と無関係に通す。AC-258 / AC-259 がこの 2 ケースを分けて固定する。

- これにより `MEMBERSHIP_LAST_ADMIN_BLOCKED` には**到達しない**（先に本設計側の明示的なエラーで止まる）。理事に対して「まず後任を決めてください」という**行動可能なメッセージ**を出せる。
- `removeMemberWithoutAdminCheck` 系の窓口を使う理由は「`user_roles` を確実に消すため」であって「保護を外したいため」ではない。保護そのものは §9.3.3 の検査として本設計側に持ち直している。
- 後任の**自動**選任（夜次承継バッチ等）は既存設計書 `docs/architecture/account_purge_last_admin_succession.md` §4.1 / §6 Phase α-1 の領域であり、**本設計は後任選任を要求するだけで自動化しない**（§2.2 S-6）。

### 9.4 `UserStatusChangedEvent` の発火点と受信側の AFTER_COMMIT 化（B-1・**全面改訂**）

#### 9.4.1 発火点（**新規に作る。既存物ではない**）

前回改訂は「`auth` ドメインのユーザーステータス変更 Service 1 箇所のみ」と、あたかも既存物があるかのように書いていた。**実測ではそのような Service は存在しない**ので、明確に新規作成物として書き直す（M-8）。

実測:

- `UserEntity#changeStatus` の呼出元は `backend/src/main` に **ゼロ**（P-1）
- 既存の `freeze()` / `unfreeze()` / `archive()` / `unarchive()` は Entity のセッタを叩くだけで、**`UserStatusChangedEvent` を publish しない**
- したがって `UserStatusChangedEvent` の publish 元は現在ゼロであり、本設計が**最初の 1 つ**を作る

**設計**

- **新設**: `auth` ドメインにユーザーステータス変更 Service を 1 つ作る。`users.status` の変更と `UserStatusChangedEvent` の publish を**原子的に**行う唯一の窓口とする
- `UserEntity#changeStatus` は Entity のセッタのままにし、イベントを持たせない（Entity から飛ばすと発火点が散る）
- イベントのフィールドは既存のまま。**変更しない**

> ⚠️ **`users.status` の書き手を当該 Service に限定する ArchUnit 番人を置く（M-8）。**
>
> これが無いと、将来だれかが `changeStatus` や既存の `freeze()` 系を経由して `DECEASED` を書いた瞬間、**イベントが飛ばず同意書が失効しない穴**が静かに開く。しかもその穴は「同意書が失効していない」という**不作為**として現れるため、通常のテストでは気づけない。番人はこの一族の欠陥（既存の `freeze()` 系がイベントを出さない、という現状そのもの）が再生産されるのを防ぐ。AC-287 が対応する。

#### 9.4.2 受信側を `@TransactionalEventListener(AFTER_COMMIT)` に変更する

**現状**: `ProxyConsentLifeEventJob` は `@Async("event-pool") @EventListener`（:30-39）である。これは **publish 時点で別スレッドに渡る**ため、その後にトランザクションがロールバックしても **同意書は不可逆に失効済みになる**。

**初版の対処は誤りだった。** 初版は「publish 前に検査を済ませる設計にする」と書いていたが、これは既知の 1 経路（`RESIDENT_014` のロールバック）しか塞がない。実際には楽観ロック競合・制約違反・監査ログ以外の後続処理の失敗など**あらゆる失敗経路**が残る。CLAUDE.md「対処療法の禁止」に抵触するため撤回する。

**訂正: 受信側を三重防御に変更する。** 同リポジトリに正解の前例がある。`RolePurgeEventListener`（`role/event/RolePurgeEventListener.java:63-66）:

```java
@Async("purge-pool")
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void on(AccountPurgedEvent event) {
```

`ProxyConsentLifeEventJob` を同じ形（`@Async("event-pool")` + `@TransactionalEventListener(AFTER_COMMIT)` + `@Transactional(REQUIRES_NEW)`）に変更する。これにより **コミットが確定してからでなければ同意書は失効しない**。

**受信側の契約変更を避けたいという初版の理由は却下する。** `UserStatusChangedEvent` は publish 元がゼロで、この受信側は**一度も動いたことがない**（P-2）。契約破壊の実害はゼロである。既存の動作を壊さずに正しい配線へ直せる、またとない機会である。

> ⚠️ `@TransactionalEventListener` はトランザクション**外**で publish されたイベントを既定で**受け取らない**。運営操作など非トランザクション文脈から `changeStatus` を呼ぶ経路を将来足す場合は、必ずトランザクション内で publish すること。§17.1 AC-210 がこれを固定する。

#### 9.4.3 AFTER_COMMIT 化だけでは足りない — 配送を永続化する（Codex 重大2・**0.3 版の重大な不足**）

**0.3 版の欠陥**: §9.4.2 は「これで**コミットが確定してからでなければ同意書は失効しない**」と書いて完結していた。**これは半分しか解決していない。**

実測: `ProxyConsentLifeEventJob.java:30-32` は

```java
@EventListener
@Async("event-pool")
public void onUserStatusChanged(UserStatusChangedEvent event) {
```

すなわち **プロセス内イベント**である。AFTER_COMMIT 化は「ロールバックしたのに失効した」という**誤失効**を防ぐが、**配送そのものを永続化しない**。commit 完了後、非同期処理の開始前または完了前に

- プロセス停止（デプロイ・OOM・クラッシュ）
- executor の rejection（`event-pool` のキュー溢れ）
- consumer 内での未捕捉例外

のいずれかが起きると、**イベントは何の痕跡も残さず消える**。結果は「`users.status = DECEASED` なのに、有効な代理入力同意書がそのまま残る」である。これは本設計が §3.1 で「自動・即時・不可逆」と約束した唯一の副作用が、**静かに実行されなかった**状態であり、逝去した人の名義で代理入力が通り続けるという、本設計が防ごうとしたリスクそのものである。

**しかも AC-203 / AC-215 の通常実行＋Awaitility ではこの消失窓を一切検出できない。** 正常系では必ず届くからである。

**判断: 2 段階に分けて実装する。段階1 で消失を検知・回復できる状態にし、段階2 で消失窓そのものを閉じる。**

| 段階 | 内容 | Phase |
|---|---|---|
| **段階1（必須）** | AFTER_COMMIT 化（§9.4.2）＋ **§9.4.4 の照合バッチ**。消失窓は**残る**が、**残ることを検知でき、自動で回復できる**状態にする | Phase 2 |
| **段階2（本則）** | **transactional outbox 化**。source transaction 内で永続行を作り、冪等 consumer が失効させる。消失窓そのものを閉じる | Phase 2（下記のとおり前例があるため段階1 と同一 Phase で完遂できる） |

**段階2 を本設計の射程に含めると判断した根拠 — リポジトリに前例が 2 つ実在する（実測）**

| 前例 | 実体 |
|---|---|
| `email_outbox` | `backend/src/main/resources/db/migration/V68.001__create_email_outbox.sql`。状態 `PENDING`/`SENDING`/`SENT`/`DEAD_LETTER`/`FAILED`/`CANCELLED`、`retry_count`、`idempotency_key`、`next_attempt_at` を持つ。実装は `backend/src/main/java/com/mannschaft/app/mail/outbox/` 配下に `EmailOutboxServiceImpl` / `EmailOutboxWorker` / `EmailOutboxStuckRecoveryBatch` / `EmailOutboxAlertChecker` の**4 役が揃っている** |
| `notification_fanout_jobs` | `V173.20260730033806__create_notification_fanout_jobs.sql`。永続ジョブキュー表 |

**前例があるため、outbox は本設計にとって新機軸ではなく既存様式の適用である。** 表・ワーカー・スタック回復・アラートの 4 点セットをこの一族に倣って設計できるので、「過大だから段階分割して先送りする」理由が消えた。したがって **段階1・段階2 とも Phase 2 で実装する**。

**設計（段階2）**

1. **新規表 `user_life_event_outbox`**（`UuidV7Entity` 継承。CLAUDE.md アーキテクチャ思想 6）。列は `user_id` / `new_status` / `old_status` / `state`（`PENDING`/`PROCESSING`/`DONE`/`DEAD_LETTER`）/ `attempt_count` / `next_attempt_at` / `last_error` / `idempotency_key`。**Flyway 1 本が追加で必要**（§14 M-2）
2. **行の作成は §9.1 手順9 と同一トランザクション内**で行う。`users.status` の書き込みと outbox 行の作成が原子的であることが、この設計の全体である
3. **consumer は冪等**にする。`ProxyConsentLifecycleService#revokeAllForUser` は「既に失効済みの同意書には何もしない」性質を持つため、**同一行を 2 度処理しても結果は変わらない**（重複配送に耐える）。ここは実装時に実測で再確認すること
4. **リトライ**: 指数バックオフ、上限到達で `DEAD_LETTER` へ落とし**アラートを上げる**（`EmailOutboxAlertChecker` に倣う）。**握りつぶさない**
5. **スタック回復**: `PROCESSING` のまま一定時間動かない行を `PENDING` へ戻すバッチ（`EmailOutboxStuckRecoveryBatch` に倣う）。プロセス停止で `PROCESSING` のまま取り残された行がここで回収される
6. **`@TransactionalEventListener(AFTER_COMMIT)` は段階2 でも残す**。outbox は「遅くとも必ず届く」を保証し、イベントは「通常は即座に届く」を担う。**イベントが先に処理した行は consumer が冪等にスキップする**

#### 9.4.4 照合バッチ（reconciliation・段階1 の中核）

**目的**: 「`users.status` が `DECEASED`/`RELOCATED` なのに、有効な代理入力同意書が残っている」ユーザーを定期的に検出し、失効させる。

| 項目 | 内容 |
|---|---|
| 周期 | 日次（既存の `ProxyConsentExpiryJob` と同じ 02:00 台。ShedLock で多重実行を防ぐ — F14.1 のバッチ様式に倣う） |
| 検出条件 | `users.status IN ('DECEASED','RELOCATED')` かつ `deleted_at IS NULL` の利用者で、`revoked_at IS NULL` かつ `approved_at IS NOT NULL` の `proxy_input_consents` 行を持つもの |
| 処理 | `revokeAllForUser(userId, AUTO_BY_LIFE_EVENT)` を呼ぶ（**手動の失効と同じ窓口**）|
| 記録 | **検出件数を必ずログ・メトリクスに出す。0 件が正常であり、非 0 は配送経路の欠陥を意味する**。非 0 が続く場合はアラートを上げる |
| 相乗り | §4.1.1 の再計算と `users.status` の不整合（Codex 重大3 の取りこぼし）も同じバッチで検出・修復する。全台帳行から再計算した値と `users.status` が食い違う利用者を洗い、正しい値へ寄せる |
| 相乗り2 | INV-3 の監査欠落検知（`DECEASED`/`RELOCATED` なのに RESIDENT カテゴリの監査行がゼロ）も同バッチで WARN を出す |

> **このバッチは「あってもなくてもよい保険」ではない。** 段階1 の時点ではこれが**唯一の消失検出手段**であり、段階2 の後も outbox の `DEAD_LETTER` を取りこぼさない最終防衛線である。**段階1・段階2 のどちらの実装順序でも、このバッチを外してはならない。**

> ⚠️ **消失窓が残ることの正直な記録**: 段階1 のみの状態では、イベント消失から照合バッチの次回実行までの**最長約 24 時間**、逝去・転出した利用者の同意書が有効なまま残りうる。§19 U-19 に記録する。段階2 完了後もこの窓は **`DEAD_LETTER` 到達分についてのみ**残る（そこはアラートで人が気づく設計である）。

### 9.5 管理権限の即時停止（A-1・A-4 で中枢案に確定）

#### 9.5.1 なぜ SpEL 層（`AccessGuard`）では閉じないのか

前回改訂は案 (c)（`AccessGuard` の `isScopeAdmin` / `isScopeStrictAdmin` に検査を足す）を採り、案 (b)（`AccessControlService` 中枢）を「波及極大」として退けていた。**この判断は誤りだったので撤回する。**

実測すると、案 (c) が守れる範囲はごく一部である。

| 実測 | 値 |
|---|---|
| `@PreAuthorize("@accessGuard...")` を伴うマッピング | GET 18 / POST 42 / DELETE 16 / PATCH 15 / PUT 9 = **計 100** |
| `AccessControlService#checkAdminOrAbove` の出現 | **679 箇所 / 243 ファイル** |
| `isAdminOrAbove` | 173 箇所 / 93 ファイル |
| `isAdmin` | 35 箇所 / 22 ファイル |
| `checkPermission` | 26 箇所 / 19 ファイル |

※ 出現数には宣言・javadoc の言及を含む概数だが、桁の比較には足りる。

**案 (c) が守れるのは全体の 1/6 以下**である。決定的なのは §3.4 で示した実測で、**resident ドメインのコントローラ9本すべてに `@PreAuthorize` が無い**。つまり本設計が対象とする住民台帳の編集・削除・確認・退去処理そのものが、案 (c) の射程の外にある。マスター方針「札が立ったら即座に使えなくする」を満たせない。

#### 9.5.2 採用案: `resolveEffectiveRole` で**降格**させる

**検査を置く場所を、認可判定が必ず通る中枢に移す。**

実測により、ロール判定はすべて 1 本の私有メソッドに集約されていることが分かった。

```
isAdminOrAbove(:377)  ─┐
isAdmin(:385)         ─┼─► getRoleName(:185) ─► resolveEffectiveRoleName(:216) ─┐
checkAdminOrAbove(:412) ┘  （!isAdminOrAbove で 403 COMMON_002）                 ├─► resolveEffectiveRole(:231, private)
hasRoleOrAbove(:401) ───────────────────────────────────────────────────────────┘
```

一方、**在籍層はここを通らない**。`isMember`(:76-78) は `membershipRepository.existsActiveByUserAndScope`(:78) を直接引く独立経路である。したがって `resolveEffectiveRole` だけを触れば、**在籍層に指一本触れずに権限層を落とせる**。これが §3.4 の二層を実装上そのまま表現する。

**ただし「空にする」のではなく「降格させる」。**

`resolveEffectiveRole` は 2 段階で解決する。

| 段 | 源泉 | 返しうるロール |
|---|---|---|
| 第1段 | `user_roles` | ADMIN / DEPUTY_ADMIN ほか |
| 第2段 | `memberships.role_kind` | MEMBER / SUPPORTER |

`Optional.empty()` を返す実装にすると `hasRoleOrAbove("MEMBER")` まで false になり、在籍層が壊れる（`hasRoleOrAbove` は同じメソッドを使う）。

**よって、札が立っているときは第1段の結果から `ADMIN_ROLES`（`Set.of("ADMIN","DEPUTY_ADMIN")`、:52）を除外し、第2段の MEMBER / SUPPORTER はそのまま残す。**

```
resolveEffectiveRole(userId, scopeId, scopeType):
    第1段: user_roles 由来のロールを解決
        → 【新設】当該 userId の users.status が DECEASED / RELOCATED なら
                  ADMIN / DEPUTY_ADMIN を候補から除外する（降格）
    第2段: memberships.role_kind 由来（MEMBER / SUPPORTER）はそのまま
    → priority 最小を返す
```

これにより札付きユーザーは **MEMBER に降格**する。`isAdminOrAbove` / `isAdmin` は false、`checkAdminOrAbove` は 403 `COMMON_002`、`hasRoleOrAbove("MEMBER")` は true のまま。**在籍層（§3.4）は無傷である。**

#### 9.5.3 塞ぎ漏れる 3 経路（同時に塞ぐ）

`resolveEffectiveRole` を締めただけでは通り抜ける経路が 3 つある。実測で特定した。

| # | 経路 | なぜ抜けるか | 対処 |
|---|---|---|---|
| G-1 | **`resolveEffectiveRoleNames`（:285）/ `resolveEffectiveRoleNamesIncludingOrgDescendants`（:328）** | 候補者一括解決の**別実装**。javadoc（:267-271）は「`resolveEffectiveRoleName` と完全に同一の規則」と謳うが、コードは独立している。片方だけ直すとこの約束が破れる | **同じ降格規則を適用する**。AC-286 が両者の一致を固定する |
| G-2 | **権限ベースの判定**（`checkPermission` :507 / `checkAdminOrHasPermission` :443）| `RoleService#resolveEffectivePermissions` が源泉で、`resolveEffectiveRole` を経由しない。しかも `@Cacheable("role-permissions")` で **TTL 5 分**（`config/RedisConfig.java:133-134`）| **§9.5.3.1 で全面的に再設計した**（Codex 重大1）。0.3 版の「降格規則を `resolveEffectivePermissions` に適用し、付与・取消時に `@CacheEvict` する」は**安全性を evict の成功に依存させるため撤回** |
| G-3 | `checkAdminOrHasPermission` の第2段（`existsDeputyAdminWithPermissionInOrganization`）| `users` を結合していない専用クエリ | 同クエリに許容集合条件を足す |

##### 9.5.3.1 G-2 の再設計 — ライフイベント判定をキャッシュの**外側**へ出す（Codex 重大1）

**0.3 版の欠陥**: G-2 の対処は「降格規則を `resolveEffectivePermissions` の中に入れ、札付与・取消時に `@CacheEvict` する」だった。これは **マスター方針「札が立ったら管理権限は即座に使えなくなる」を保証できない。** 実測で 4 つの理由がある。

| # | 実測 | 帰結 |
|---|---|---|
| 1 | `RoleService.java:417-418` は `@Cacheable(value = "role-permissions", key = "#userId + ':' + #scopeType + ':' + #scopeId")` | **キャッシュヒット時は、追加した status 判定が実行されない**。判定をメソッドの中に入れる限り、キャッシュはその判定ごと結果を焼き付けている |
| 2 | `config/LoggingCacheErrorHandler.java:108` の `handleCacheEvictError` は **evict 失敗をログして握りつぶす**（rethrow しない） | evict が失敗しても業務は成功で返る。**理事の画面には「記録しました」と出るのに、権限は止まっていない** |
| 3 | 同クラス :69-71 の定数 `AUTHZ_RISK_SUFFIX` が自認している — 「キャッシュ無効化に失敗したため fail-open で業務処理を続行する。**古い値が TTL 満了まで残るため認可に影響しうる**（ロール/可視性の反映遅延）」 | この危険は既知であり、本設計はそこへ**安全性そのもの**を預けようとしていた |
| 4 | キーは `userId:scopeType:scopeId` である。ある利用者の**全スコープ**のキーを列挙する手段が要るが、0.3 版はそれを定義していなかった。**Spring の `@CacheEvict` に「userId 前方一致」は無い** | 複数組合に属する理事では、そもそも**どのキーを消せばよいか決まっていない** |

**是正: ライフイベントによる停止判定を、キャッシュされる値の外側に出す。**

```
checkPermission(userId, scopeId, scopeType, permission):
    ① 【新設・キャッシュしない】ライフイベント status ゲート
         users.status が DECEASED / RELOCATED なら —— ここで拒否（403 COMMON_002）
    ② ①を通過した場合にのみ resolveEffectivePermissions(...) を読む（従来どおりキャッシュ可）
```

| 設計上の要点 | 内容 |
|---|---|
| **キャッシュの中身を変えない** | `role-permissions` は**生の権限だけ**を保持する（ライフイベントの状態を混ぜない）。混ぜないので、古いキャッシュが残っていても**それが管理権限の復活を意味しない** |
| **evict は最適化であって安全装置ではない** | `@CacheEvict` は引き続き行ってよいが、**失敗しても安全性は損なわれない**。`LoggingCacheErrorHandler` の握りつぶしが本設計の穴にならなくなる |
| **Valkey 障害に耐える** | Valkey が一時的に落ちてキャッシュが更新できなくても、ゲート①は DB を見るため**即時に拒否する** |
| **キー列挙問題が消える** | 全スコープのキーを列挙する必要が無くなる。ゲートは userId 単位の判定であり、スコープに依存しない |
| **`resolveEffectiveRole` 側との整合** | §9.5.2 の降格は `user_roles` を引くクエリへ条件を畳み込む方式であり、**そもそもキャッシュされていない**（§9.5.6 実測: ロール判定経路にキャッシュは無い）。したがって §9.5.2 は書き直す必要が**ない**。再設計が要るのは G-2（権限経路）だけであり、両者は「キャッシュされない判定で停止させる」という点で**同じ構造に揃う** |

**性能影響の評価（L-3 との整合）**

ゲート①は `users.status` の 1 行読み取りである。素朴に実装すると認可判定のたびに発生し、§9.5.4 が禁じた形になる。**そこで次の 2 点を課す。**

1. **リクエストスコープでメモ化する。** 認可判定は 1 リクエスト内で複数回走るが、**判定対象は常に「今リクエストしている本人」1 人**である。`@RequestScope` の保持クラス（または明示的な `ThreadLocal`）に `users.status` を 1 回だけ読んで保持する。**追加読み取りは 1 リクエストあたり最大 1 本**に収まる。
2. **権限ベース経路にしか置かない。** ロール判定経路（`resolveEffectiveRole`）は §9.5.4 のとおり既存クエリへの畳み込みで**追加読み取りゼロ**を維持する。ゲート①は G-2 が扱う `checkPermission` / `checkAdminOrHasPermission` の入口にだけ置く。

> **§9.5.4 の「追加読み取りゼロ」との関係**: L-3 が禁じたのは「**認可判定のたびに**数百箇所で追加クエリが出ること」である。1 リクエスト 1 本のメモ化読み取りはこれに当たらない。**それでもゼロではない**ので、代替として「JWT に載せる」案も検討したが**採らない**。JWT は最長 15 分ステールになりうるため（§9.5.6）、「即座に停止」を満たせずゲートを置く意味が失われる。

> ⚠️ **G-3（`existsDeputyAdminWithPermissionInOrganization`）はキャッシュされないため、0.3 版どおり「クエリへ許容集合条件を畳み込む」で正しい**。変更は不要である。

#### 9.5.4 追加の DB 読み取りを発生させない（L-3）

素朴に実装すると、認可判定のたびに `users` を引く追加クエリが **数百箇所**で発生する。認可はほぼ全 API が通る経路であり、1 回の追加読み取りが全体のレイテンシに乗る。**これは許容しない。**

**対策: 既存クエリへ条件を畳み込む。** `resolveEffectiveRole` の第1段は `user_roles` を引くクエリを**すでに 1 本発行している**。ここに `users` を結合して `u.status NOT IN ('DECEASED','RELOCATED')` を課せば、**追加クエリはゼロ**で降格が実現する。第1段の源泉こそが ADMIN/DEPUTY_ADMIN の供給元なので、絞る対象としても正確である。

> ⚠️ 既存の `findByUserIdAndTeamId` / `findByUserIdAndOrganizationId` を直接書き換えないこと。これらは認可以外の用途からも呼ばれうるため、巻き添えで挙動が変わる。**認可専用の新メソッド**（例: `findAuthzRoleByUserIdAndTeamId`）を追加し、`resolveEffectiveRole` からのみ呼ぶ。G-1 / G-2 / G-3 のクエリも同様に、それぞれ既存の結合へ条件を畳み込む。

#### 9.5.5 読み取り系の管理 EP をどう扱うか（線引き）

降格により、**ADMIN 限定の読み取り EP も 403 になる**（例: 組織の分析画面、会員名簿の管理ビュー）。これを許容するかは設計判断である。

**判断: 許容する（403 にする）。**

- マスター方針が守れと定めたのは「**自分の**予定・請求の閲覧」であり、これらは `checkMembership` / `isMember` 経由なので**一切影響を受けない**（§3.4）。
- ADMIN 限定の読み取りは「他人の情報を管理者として見る」行為であり、**閲覧であっても管理操作**である。逝去・転出した理事が組合員名簿や分析を見続けられる方が不自然である。
- 読み書きで挙動を分けると、「読めるのに書けない管理画面」という中途半端な UI 状態を全管理画面に対して設計せねばならず、複雑さに見合わない。

#### 9.5.6 即時に効くこと（D-1・実測で確認）

**トークンの失効処理は不要である。** 実測で次を確認した。

- `RoleClaimResolver` が JWT に載せるのは **`MEMBER` と `SYSTEM_ADMIN` のみ**で、**per-scope の ADMIN / DEPUTY_ADMIN は JWT に載らない**。したがって「古いトークンに焼き付いた ADMIN 権限」は存在しない。
- `AccessControlService` のロール判定経路に**キャッシュは無く、毎回 DB を引く**。よって札付与は per-scope 判定に**即時反映**される。

前回改訂が案 (a)（セッション／トークン全失効）を退けた判断は、この実測により**正しかったことが裏づけられた**。§3.3 のログイン継続方針とも矛盾しない。

> ⚠️ **唯一の例外が G-2 の `role-permissions` キャッシュ（TTL 5 分）である。** ここだけは「キャッシュが無い」が成り立たない。**0.3 版はこれを `@CacheEvict` で解こうとしたが、evict 失敗時に fail-open することが実測で判明したため、§9.5.3.1 でキャッシュの外側のゲートへ再設計した。** 「認可にキャッシュは無い」を一般化してゲートを省くと、権限ベースの経路だけが最大 5 分間（evict 失敗時は TTL 満了まで）素通りする。
>
> ⚠️ SYSTEM_ADMIN は JWT 由来で最長 15 分ステールになりうるが、本設計は SYSTEM_ADMIN を降格対象から除外する（§7.1 の短絡が先に効く）ため影響しない。

#### 9.5.7 取消時の復帰

札取消で §4.1.1 の再計算結果が `ACTIVE` になれば降格条件が外れ、**管理権限は自動的に復帰する**。`user_roles` の行に触っていないため権限そのものは保持されたままである。

> ⚠️ **復帰するのは「再計算結果が `ACTIVE` になったとき」だけである**（Codex 重大4）。逝去札を取り消しても全台帳行が転出済みなら再計算値は `RELOCATED` であり、**管理権限は停止したままが正しい**。0.3 版の「`DECEASED` を `ACTIVE` に戻す」直接遷移では、この場合に権限が誤って復帰していた。
>
> ⚠️ **G-2 の復帰は `@CacheEvict` に依存しない**（§9.5.3.1）。ゲート①は `users.status` を直接見るため、キャッシュの状態と無関係に即座に復帰する。evict は「古い権限**リスト**」を新しくするための最適化として引き続き行う。

## 10. 監査ログ

書き口: `AuditLogService#record(...)`。`@Async` かつ内部で例外を握りつぶす（監査失敗が業務を壊さない）。`eventType` は `String`。

> ⚠️ **この方式は INV-3 を保証しない。** 実測（`AuditLogService.java:49-70`）: `record` は `@Async` で `catch (Exception e) { log.error(...) }` し **rethrow しない**。DB 障害・executor rejection・プロセス停止では監査行が残らない。**§3.2 の INV-3 は Codex 中7 を受けて「best effort」に弱めた。**
>
> **同期トランザクション化／監査 outbox 化を採らない理由**: ①監査は横断機構であり、本設計の 4 エンドポイントのためだけに `AuditLogService` の契約を変えると、既存 700 超の呼出元すべての失敗挙動が変わる（監査 DB の不調で業務が全面停止する方向へ倒れる）②本設計固有の「絶対に失われてはならない副作用」は同意書の失効であり、そちらは §9.4.3 で outbox 化する。**優先順位を付けた上で、監査は best effort と正直に書く**ことを選ぶ。
>
> **代わりに §10.2 の欠落検知を置く。**

RESIDENT カテゴリの既存 4 値（`auth/AuditEventType.java:138-142`、publish 元ゼロ）を使う。

```java
DEATH_STATUS_CHANGED_TO_SUSPECTED(AuditEventCategory.RESIDENT),
DEATH_STATUS_CHANGED_TO_CONFIRMED(AuditEventCategory.RESIDENT),
DEATH_STATUS_CHANGED_TO_CANCELLED(AuditEventCategory.RESIDENT),
OCCUPANCY_STATUS_CHANGED(AuditEventCategory.RESIDENT),
```

**転出用に 1 値を新規追加する（B-5）。**

```java
RESIDENT_RELOCATION_CHANGED(AuditEventCategory.RESIDENT),
```

> 初版は `OCCUPANCY_STATUS_CHANGED` の流用を「暫定」としていたが撤回する。同定数は F09.16 の居住実態区分の変更を指しており転出とは意味が違う。`name()` を文字列保存するため **Flyway 不要・コスト極小**であり、「暫定」の流用は恒久化する。

| 本設計の操作 | eventType |
|---|---|
| 逝去の札 付与 | `DEATH_STATUS_CHANGED_TO_CONFIRMED.name()` |
| 逝去の札 取消 | `DEATH_STATUS_CHANGED_TO_CANCELLED.name()` |
| （既存バッチの自動起票） | `DEATH_STATUS_CHANGED_TO_SUSPECTED.name()` — `markDeathSuspected` に監査ログを足す（現在は `log.info` のみ）。本設計のついで作業 |
| 転出の札 付与／取消 | `RESIDENT_RELOCATION_CHANGED.name()` |
| 所属解除 | **本設計では書かない。既存経路に委ねる**（§10.1）|

> `ProxyAuditEventTypes` のような定数クラスを新設して二重定義しないこと。`AuditEventType` の `.name()` を直接渡す。

### 10.1 所属解除の監査は既存経路が既に書いている（R-2）

**前回改訂の §10 の表と AC-260 は誤りだったので訂正する。**

実測: `MembershipService#leave` は `OrganizationMemberAuditEvent` / `TeamMemberAuditEvent`（`SubType.REMOVED`）を publish し、`team/event/TeamOrgAuditEventListener.java:138` がこれを `ORGANIZATION_MEMBER_REMOVED` / `TEAM_MEMBER_REMOVED` に写像して **既に `audit_logs` へ記録している**。

これがもたらしていた 2 つの問題:

1. **AC-260（「所属解除で `ORGANIZATION_MEMBER_REMOVED` が 1 件記録される」）は、本設計が何も実装しなくても green になる**偽の受け入れ条件だった。
2. §10 の表は本設計側でも書くと読めるため、素直に実装すると **2 件**記録され、AC-260 の「1 件」が逆に落ちる。

**訂正後の設計**

- **除名の事実そのものは既存経路に委ねる。本設計は `ORGANIZATION_MEMBER_REMOVED` / `TEAM_MEMBER_REMOVED` を自前で書かない。**
- ただし既存リスナーが書く行の **metadata は `null`** であり、本設計固有の文脈（なぜ解除したのか、どちらの札によるのか、理事が入力した理由）が一切残らない。**INV-3（監査を残さずに完了してはならない）を満たすには不足である。**
- よって **所属解除では、本設計固有の監査行を 1 件だけ追加で書く**。eventType は札の種別に応じて `DEATH_STATUS_CHANGED_TO_CONFIRMED` ではなく、**`RESIDENT_RELOCATION_CHANGED` / `DEATH_STATUS_CHANGED_TO_CONFIRMED` を再利用せず**、metadata の `eventKind = "MEMBERSHIP_RELEASED"` で識別する（eventType は札種別に対応する RESIDENT カテゴリ値を用いる）。

**結果として所属解除では `audit_logs` に 2 行が残る。**

| 行 | 書き手 | eventType | metadata |
|---|---|---|---|
| 1 | 既存 `TeamOrgAuditEventListener`（本設計は関与しない）| `ORGANIZATION_MEMBER_REMOVED` / `TEAM_MEMBER_REMOVED` | `null` |
| 2 | **本設計** | RESIDENT カテゴリ値 | `eventKind` / `leaveReason` / `reason` / `residentRegistryId` 入り |

2 行になることは意図した設計である。1 行目は「組合員が除名された」という membership ドメインの事実、2 行目は「住民台帳のライフイベントに起因する解除だった」という resident ドメインの文脈であり、**別ドメインの別の事実**である。

> ⚠️ **AC-260 は「本設計固有の metadata を持つ行が存在する」で書く**（§17.1）。既存経路が書く行の存在だけを検証すると、実装ゼロで green になる。

**metadata（JSON）**

```json
{
  "eventKind": "DEATH_CONFIRMED | DEATH_CANCELLED | RELOCATION_SET | RELOCATION_CANCELLED | MEMBERSHIP_RELEASED",
  "residentRegistryId": 12345,
  "oldStatus": "SUSPECTED",
  "newStatus": "CONFIRMED",
  "oldUserStatus": "ACTIVE",
  "newUserStatus": "DECEASED",
  "userStatusChanged": true,
  "reason": "理事が入力した自由記述（最大500文字）",
  "leaveReason": "DECEASED"
}
```

`oldStatus`/`newStatus` は台帳側、`oldUserStatus`/`newUserStatus` はアカウント側。両方載せることで、R-1 により台帳だけ変わってアカウントが変わらなかったケースを後から追える。`reason` は **PII を含みうる**（§13.1 で保持期間を扱う）。

### 10.2 監査の欠落検知（Codex 中7・INV-3 を best effort にした代償措置）

INV-3 を弱めた以上、**「残らなかったこと」を誰も知らないまま済ませてはならない**。次の 2 段で検知する。

| 段 | 内容 |
|---|---|
| **即時** | `AuditLogService` の握りつぶし箇所は既に `log.error` を出している。本設計は**そこに手を入れず**、代わりに **監査記録の失敗をカウンタとして可観測にする**ことを要求する（実装時に既存のメトリクス基盤へ載せる。無ければ `log.error` の監視で代替してよい）。**「握りつぶしを消して業務を落とす」方向へは倒さない**（§10 の判断） |
| **日次** | **§9.4.4 の照合バッチに相乗りさせる**。`users.status IN ('DECEASED','RELOCATED')` かつ `deleted_at IS NULL` の利用者のうち、`AuditEventCategory.RESIDENT` の監査行が **1 件も無い**ものを洗い、件数を WARN で運用へ上げる。0 件が正常である |

> ⚠️ **AC-212 / AC-260 は「通常成功時に監査行が増えること」しか検証しない。** これは INV-3（best effort 版）に対する妥当な AC だが、**「必ず残る」ことの証明ではない**。§17.1 に **AC-216**（欠落検知が実際に欠落を検出できること）を追加し、検知機構そのものを番人にする。「監査が残る」ことをテストで示せない以上、**検知が動くことを示す**のが取りうる最善である。

## 13. セキュリティ・プライバシー

### 13.1 死亡情報の開示範囲

| 相手 | 開示 | 手段 |
|---|---|---|
| 当該スコープの ADMIN / DEPUTY_ADMIN / SYSTEM_ADMIN | ✅ 可 | §6.5 の `ResidentResponse`（`deathStatus` 入り） |
| 同一スコープの一般メンバー | ❌ **不可** | §6.5 のとおり単一 DTO のまま `deathStatus` / `lifeEventFlag` を **`null`** で返す（B-7）|

| 他スコープ | ❌ | §6.4 の認可（403） |
| プッシュ通知の本文 | ❌ 氏名・事実を載せない | §11.1 |

**本人に開示する判断の根拠**: 誤って札が付いた場合に本人が気づいて訂正を申し立てられる。自分の状態を自分に隠す設計は、訂正の起点を理事だけに限定し、誤登録の是正を遅らせる。実測でも `UserProfileResponse.status` は既に存在するため、隠す方が既存 API の破壊的変更を要する。

> 初版は「本人には観測させない」としていたが撤回する。
>

**M-1 の SQL（L-4: 現行定義を丸ごと再宣言する）**

`MODIFY COLUMN` は列定義を**置き換える**。元の定義に含まれる属性を書き落とすと、その属性は消える。よって**コピー元を明示する**。

コピー元は `V60.001__create_memberships_table.sql:31`（実測・verbatim）:

```sql
    leave_reason ENUM('SELF','REMOVED','GDPR','TRANSFER','OTHER') NULL,
```

**この列には `COMMENT` も `DEFAULT` も付いていない**ため、再宣言すべき属性は `NULL` 許容のみである。したがって M-1 は次で過不足がない。

```sql
ALTER TABLE memberships
    MODIFY COLUMN leave_reason
        ENUM('SELF','REMOVED','GDPR','TRANSFER','OTHER','DECEASED','RELOCATED') NULL;
```

> ⚠️ もし実装時点で `origin/main` の当該列に `COMMENT` 等が追加されていたら、**その時点の定義をコピー元にし直すこと**。`MODIFY COLUMN` は差分適用ではない。

**採番規約と major を 1 つ消費する妥当性（軽1 対応）**

`backend/.claudecode.md` §18（:504-512）の採番ルール（正典）を実測した。

> 1. **major は「origin/main 全体の最大 major + 1」を使う**（V82, V83, V84 … と実践済み）。新規ファイルがリポジトリ内のすべての既存ファイルの後にソートされることが保証され、`out-of-order: true` への依存をゼロにできる。
> 2. **同一 major 内の並行 PR 衝突は minor（タイムスタンプ）で回避する**。

#### 非同期系 AC の観測手段（中11 対応）

本設計には `@Async` に依存する AC が複数ある（AC-203/210/213/215 の同意書失効、AC-212/260 の監査ログ）。**観測手段を決めないと `/試練` が書けないか flaky になる。**

**採用: Awaitility による bounded polling。** リポジトリに前例がある（`StandingsRecalculationAfterCommitIT:165-169`）。

```java
Awaitility.await()
        .atMost(Duration.ofSeconds(10))
        .pollInterval(Duration.ofMillis(200))
        .untilAsserted(() -> { /* 失効を検証 */ });
```

- **`SyncTaskExecutor` への差し替えを採らない理由**: 同期化すると `@TransactionalEventListener(AFTER_COMMIT)` の配線そのものが検証対象から外れ、AC-210（ロールバック時に失効しない）が意味を失う。**非同期のまま待つことが、配線を検証することそのものである。**
- 配線が壊れていればタイムアウトして赤くなるため、番人として機能する。
- ⚠️ `AuditLogService` は `@Async` かつ**内部で例外を握りつぶす**（監査失敗が業務を壊さない設計）。AC-212/260 が握りつぶしで無言の偽 green にならないよう、**監査ログの行が実際に増えたことを DB 側で検証する**（例外が飛ばないことの確認では不十分）。
