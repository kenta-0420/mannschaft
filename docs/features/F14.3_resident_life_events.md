> ## ⚠️ 版1.0 で方式そのものを変えた経緯（必ず最初に読むこと）
>
> 版 0.1〜0.5 は **「札」方式** — 逝去・転出を `users.status` に `DECEASED` / `RELOCATED` として立て、**認可層に「札が立っていたら止める」関門を置く** — で設計されていた。この方式に対し **Codex（別系統モデル）による独立検分を 3 巡**かけたが、**毎回、重大級の指摘が出て収束しなかった**。
>
> | 巡 | 見つかった迂回路・欠陥 |
> |---|---|
> | 1 巡目 | `@CacheEvict` 依存では evict 失敗時に権限が TTL 満了まで残る（`LoggingCacheErrorHandler` が失敗を握りつぶす）|
> | 2 巡目 | `RoleService#hasPermission` を**直接呼ぶ経路が 5 か所**あり `checkPermission` の関門を通らない |
> | 3 巡目 | `MembershipBatchQueryService` が `user_roles` を直接読んでロールスナップショットを作る／`PermissionGroupService#hasPermission` が `RoleService` を通らない |
>
> **原因は設計の巧拙ではない。** このシステムの認可判定は 1 か所に集約されておらず、**関門を置くたびに「そこを通らない経路」が新たに見つかる**。3 巡かけても探索が終わる見込みが立たなかった。
>
> **マスターの裁可により方式を転換した。**
>
> > 「札という概念をなくして、逝去・転居など**組合員活動へ参加できなくなった場合、アーカイブのような別タブを作ってそちらに移動**させ、**1 か月ほど通常組合員ができる操作のみできる**ようにすればいい。1 か月後は**自動で組合から外れる**」
>
> **新方式の要点は「関門を置くのをやめ、権限そのものを取り上げる」ことである。** 役職（`user_roles`）と権限グループ割当（`user_permission_groups`）を実際に削除すれば、**どの認可経路も自分から閉じる**。関門も、抜け道の棚卸しも要らなくなる。§8 がこれを経路ごとに検証する。
>
> **この記録を残す理由**: 同じ袋小路へ再突入しないため。「`users.status` に状態を足して認可層で見る」という発想は自然に見えるが、**このコードベースでは実装コストではなく検証コストが発散する**。

## 1. 概要

### 1.1 解決する問題

住民（区分所有者・居住者）が **逝去** または **転出** したとき、システムには次の穴がある。

| # | 穴 | 実測の根拠 |
|---|---|---|
| P-1 | **人が逝去・転出を確定させる操作点が存在しない** | `resident_registry.death_status` は 4 値（`ALIVE`/`SUSPECTED`/`CONFIRMED`/`CANCELLED_FALSE_ALARM`、`V9.102`）まで DDL・Entity・Enum が揃っているのに、**書き手は `ResidentRegistryService#markDeathSuspected` の 1 箇所だけ**で、これは滞納エスカレーション D+120 から `SUSPECTED` を立てるためのもの。**人が `CONFIRMED` に確定させる本番経路が無い**。F09.15 自身が「手動入力 API は v2 送り」と認めている |
| P-2 | **代理入力同意書の失効機構が宙吊り** | `ProxyConsentLifeEventJob`（`proxy/batch/ProxyConsentLifeEventJob.java`）は `UserStatusChangedEvent` を `@EventListener` で受け、`revokeAllForUser` により全同意書を `AUTO_BY_LIFE_EVENT` で失効させる。しかし **`UserStatusChangedEvent` の publish 元は `backend/src/main` にゼロ**であり、**一度も動いたことがない** |
| P-3 | **逝去・転出した組合員が組合員一覧に残り続け、理事の役職も保持したままになる** | 所属を終わらせる導線も、役職を外す導線も無い。逝去した理事長のアカウントが理事長のまま残る |

### 1.2 新方式で解く形

```
理事が住民台帳で「逝去」「転出」を記録
        │
        ├─ 自動 ─► resident_registry に記録（death_status / move_out_date）
        ├─ 自動 ─► memberships を【アーカイブ在籍】へ（archived_at を立てる）
        ├─ 自動 ─► 役職を取り上げる（user_roles 行を削除）
        ├─ 自動 ─► 権限グループ割当を取り上げる（user_permission_groups 行を削除）
        │            └─ 取り上げた内容は復元用に記録（§5.3）
        ├─ 自動 ─► 代理入力同意書を全件失効（同期・同一トランザクション）
        └─ 自動 ─► 監査ログ
                        │
                        │  アーカイブ在籍期間（既定 1 か月）
                        │  ・ログインできる／自分の予定・請求が見える／通知も届く
                        │  ・一般組合員ができる操作のみ（管理操作は不可）
                        ▼
                  日次バッチが期限到来を検出
                        │
                        └─► 自動退会（memberships.left_at 確定・事由と日時を記録）
```

**「札を立てて関門で止める」のではなく、「役職を実際に取り上げ、一般組合員として在籍させ、期限が来たら自動で外す」。** 理事の催促も棚卸しも不要になる。

### 1.3 既存機能との責務分離

| 機能 | 所有するもの | 本設計との関係 |
|---|---|---|
| **F09.1 住民台帳** | `resident_registry` 本体（`V9.017`）。`move_out_date`・`moveOut(actorUserId, id, moveOutDate)`・`ALREADY_MOVED_OUT` | **転出の記録場所はここ。新設しない** |
| **F09.15 相続支援** | `death_status` 4値 enum の**正本**。封緘（事前登録）と二者承認による解除 | **逝去の記録場所はここ。値の意味は F09.15 が正本**。本設計は F09.15 が v2 送りにした「ADMIN 手動入力 API」を実装して埋める（§1.4） |
| **F09.16 居住実態管理** | `occupancy_status` 5値（`V9.103`）、年次居住実態申告 | **転出には使わない**（§5.6） |
| **F14.1 代理入力** | `ProxyConsentLifecycleService#revokeAllForUser`、`PROXY_INPUT_EXECUTE`/`PROXY_CONSENT_APPROVE` | **失効の実行主体。本設計が同期で呼ぶ**（§9.5）|
| **F00.5 メンバーシップ基盤** | `memberships`（`V60.001`）。`joined_at`/`left_at`/`leave_reason`/`role_kind` | **アーカイブ在籍の置き場所。列を追加する**（§5.2）|
| **role ドメイン** | `user_roles`、`permission_groups` / `user_permission_groups`（`V2.007`〜`V2.009`）| **取り上げる対象**（§8・§9.3）|

#### 1.4 F09.15 §9.5 との整合（衝突ではない）

F09.15 §9.5 は「`death_status = CONFIRMED` への遷移単独では封緘解除されない。**独立した二者承認プロセス**が必須」と定める。**本設計はこれを破らない。** `CONFIRMED` 遷移に自動で連動させるのは次の 4 つだけである。

- アーカイブ在籍への移行（可逆。§9.4 で取り消せる）
- 役職・権限グループ割当の取り上げ（**可逆**。§9.4 で復元する）
- 代理入力同意書の失効（**不可逆**。§3.3）
- 期限到来後の自動退会（§9.6）

**封緘（`succession_pre_registrations` / `unseal_requests`）には一切触れない。** 二者承認は F09.15 の管轄のまま残る。第5の連動を足さないことを AC-901 で固定する。

### 1.5 用語定義

| 用語 | 意味 | 実体 |
|---|---|---|
| **ライフイベントの記録** | 「この人は逝去した／転出した」という理事の判断の記録 | `resident_registry.death_status = CONFIRMED` または `move_out_date IS NOT NULL` |
| **アーカイブ在籍** | 在籍はしているが、管理操作ができず、期限到来で自動退会する状態 | `memberships.archived_at IS NOT NULL AND left_at IS NULL` |
| **通常在籍** | 従来どおりの在籍 | `memberships.archived_at IS NULL AND left_at IS NULL` |
| **自動退会** | アーカイブ期限の到来により、バッチが所属を終了させること | `left_at` 確定 ＋ `left_trigger = AUTO_ARCHIVE_EXPIRY` |
| **取り上げ／復元** | 役職・権限グループ割当を削除する／元に戻す操作 | §9.3 / §9.4 |
| **理事** | 当該スコープの `ADMIN`（理事長）／`DEPUTY_ADMIN`（副理事長）| `AccessGuard#isScopeAdmin` / `#isScopeStrictAdmin` |

## 3. 中核原則

### 3.1 関門を置かず、権限を取り上げる（本設計の中核）

**旧方式**: `users.status` に札を立て、認可判定の要所に「札が立っていたら止める」関門を置く。
→ **関門を通らない経路を探し続ける作業になり、3 巡の検分で収束しなかった。**

**新方式**: 権限の**源泉となるデータそのもの**（`user_roles` 行と `user_permission_groups` 行）を削除する。
→ **どの認可経路も、自分が読むデータが無くなることで自動的に閉じる。** 経路の網羅は「権限の源泉が何本あるか」という**有限で列挙可能な問い**に変わる。§8 がこれを列挙し、**2 本しかない**ことを実測で示す。

> **INV-1（最重要）**: アーカイブ在籍中のユーザーは、当該スコープにおいて **`user_roles` 行も `user_permission_groups` 行も持たない**。管理権限の停止はこの一事によって成立し、**認可コードへの変更を一切必要としない**。

### 3.2 在籍は残す（本人の画面は白紙にならない）

> **INV-2**: アーカイブ在籍は `memberships.left_at IS NULL` を保つ。したがって在籍判定・在籍列挙・fan-out 配信の宛先は**従来どおり**である。

- `users.status` は **`ACTIVE` のまま変えない**。ログイン・在籍列挙・配信のいずれにも影響しない
- 本人は自分の予定・請求・iCal を従来どおり閲覧でき、組合からのお知らせ・通知も従来どおり届く
- できなくなるのは**管理操作だけ**である（役職を取り上げたため）

> **これが旧方式に対する最大の利点である。** 旧方式は `users.status` を非 ACTIVE にしたため、在籍列挙 4 本と fan-out クエリ 6 本の許容集合を書き換える必要があり（旧 §8）、その波及は 26 ファイルに及んでいた。**新方式ではそれらの変更が 1 行も要らない。**

### 3.3 同意書の失効は不可逆

`ProxyConsentLifecycleService#revokeAllForUser` は失効を記録するだけで逆操作を持たない。本設計はこれに逆操作を足さない（履歴の改竄になるため）。**記録を取り消しても、失効した同意書は復活しない。** UI は §12.4 で明示的に警告する。

### 3.4 組合をまたぐ波及を仕様として受容する（マスター裁可済み）

実測: `revokeAllForUser(userId, reason)` は `findActiveBySubjectOrProxyUserId(userId)` を引くため **ユーザー単位**で全同意書を失効させる。組織スコープ限定の失効メソッドは**存在しない**（`ProxyConsentLifecycleService` の public メソッドは `expireOutdatedConsents()` と `revokeAllForUser(...)` の 2 本のみ・実測）。

したがって **A 組合の理事が記録した逝去が、本人の B 組合の同意書まで失効させる。** これを仕様として受容する。

- 逝去は人に属する事実であり、A 組合で逝去した人が B 組合では生きている、ということはない。**全スコープ波及が正しい**
- 転出については過剰になりうるが、**アーカイブ移行と自動退会は当該スコープにしか及ばない**ため、実害は「他組合の同意書を取り直す手間」に限られる
- ただし理事から見て予期しない挙動になりうるため、**§12.4 の確認ダイアログに明記**し、i18n キー `lifeEvent.confirm.crossOrgWarning` を設ける。AC-402 が 2 組織にまたがるケースを固定する

### 3.5 記録は業務データに同期で確定させる（監査ログに依存しない）

> **INV-3**: 「いつ・なぜ・誰によって」アーカイブされ、退会したかは、**`memberships` の列に同期トランザクションで確定させる**。監査ログは**補助**であり、要件の担保をそこに依存させない。

**根拠（3 巡の検分で確認済み）**: `AuditLogService#record` は `@Async` かつメソッド本体内で `catch (Exception e) { log.error(...) }` して rethrow しない（fire-and-forget）。加えて `@Async` の既定プール `event-pool`（`AsyncConfig.java:37-48`・`@Primary`・queue capacity 100・既定 `AbortPolicy`）が**キュー溢れで投入を拒否すると本体が開始されず、その catch も log.error も動かない**。

したがって **「記録として持ちたい」というマスター要件を監査ログだけに依存させてはならない。** §5.2 で `memberships` に列を追加し、業務トランザクション内で同期に確定させる。監査ログは「誰がどの画面から操作したか」という運用文脈を補うために併記する。

## 4. 状態モデル

### 4.1 メンバーシップの状態

**`users.status` は一切変更しない。** 状態は `memberships` の 2 列の組合せで表現する。

| 状態 | `archived_at` | `left_at` | 意味 | 一覧での表示 |
|---|---|---|---|---|
| **通常在籍** | NULL | NULL | 従来どおりの組合員 | 組合員タブ |
| **アーカイブ在籍** | 非 NULL | NULL | 在籍するが管理操作不可・期限到来で自動退会 | **アーカイブタブ**（残り日数つき）|
| **退会済み** | 非 NULL または NULL | 非 NULL | 所属終了 | 一覧に出ない（履歴のみ）|

```
        ┌──────────────┐
        │   通常在籍    │
        └──────┬───────┘
               │ §9.2 理事が逝去・転出を記録
               │  ＋ 役職と権限グループ割当を取り上げ（§9.3）
               │  ＋ 同意書を失効（不可逆・§9.5）
               ▼
        ┌──────────────┐   §9.4 記録の取消（理事）
        │ アーカイブ在籍 │──────────────────────► 通常在籍
        │  （既定1か月） │      役職・権限グループを復元
        └──────┬───────┘      （同意書は復活しない）
               │ §9.6 期限到来（日次バッチ）
               ▼
        ┌──────────────┐
        │   退会済み    │  left_at / leave_reason / left_trigger / left_by を確定
        └──────────────┘
```

### 4.2 遷移規則

| From | To | 契機 | 可否 |
|---|---|---|---|
| 通常在籍 | アーカイブ在籍 | 理事が逝去（`CONFIRMED`）または転出（`move_out_date`）を記録 | ✅ §9.2 |
| アーカイブ在籍 | 通常在籍 | 理事が記録を取り消す | ✅ §9.4。役職・権限グループを復元。**同意書は復活しない** |
| アーカイブ在籍 | 退会済み | アーカイブ期限の到来（日次バッチ） | ✅ §9.6。`left_trigger = AUTO_ARCHIVE_EXPIRY` |
| アーカイブ在籍 | 退会済み | 理事が手動で退会させる（既存の除名 API）| ✅ 既存経路。`left_trigger = MANUAL` |
| 退会済み | アーカイブ在籍 | 記録の取消 | ❌ **自動では戻さない**（§9.4.2）|
| 通常在籍 | 退会済み | 既存の除名・自主退会 | ✅ 既存経路。本設計は変更しない |

> **`resident_registry` と `memberships` は 1 対 N である。** 1 ユーザーが複数住戸に行を持ちうる。アーカイブ移行の粒度規則は §9.2.2 に定める。

### 4.3 `users.status` には何も書かない

**本設計は `users.status` を読み書きしない。** `DECEASED` / `RELOCATED` という enum 値は存在し続けるが（`UserEntity.UserStatus`・`V18.014` + `V18.033` の CHECK 制約）、**本設計はそこへ書き込まない**。扱いは §19.1 に定める。

## 5. DB 設計

### 5.1 結論

| 対象 | 変更 |
|---|---|
| `resident_registry` | **変更なし**（`death_status` / `move_out_date` の既存列で足りる）|
| `memberships` | **列を 6 本追加**（§5.2）＋ `leave_reason` の ENUM 値を 2 つ追加（§5.4）|
| 復元用記録 | **新規テーブル 1 本**（§5.3）|
| `users` | **変更なし** |

### 5.2 `memberships` への列追加（アーカイブ状態と退会の記録）

**なぜ `memberships` か**: アーカイブは「所属の状態」であり、所属を表現する表は `memberships` である。`resident_registry` から導出する案は採らない — 台帳は住戸に紐づき（1 ユーザー N 行）、所属はスコープに紐づく（1 ユーザー 1 行）ため**粒度が違い**、導出のたびに §9.2.2 の集約規則を再実行することになる。**状態は状態として持つ。**

**実測した `memberships` の現状**（`MembershipEntity.java` / `V60.001__create_memberships_table.sql`）: `id`(BIGINT IDENTITY) / `user_id` / `scope_type` / `scope_id` / `role_kind` / `joined_at` / `left_at` / `leave_reason` / `invited_by` / `gdpr_masked_at` / `created_at` / `updated_at`。**`@Version` は無い。`removed_by` に相当する列も無い。**

> ⚠️ **重要な実測**: 現在 `removedBy`（操作者）は `MembershipLeaveRequest` を通じて**一時的に渡されるだけ**で、**`memberships` の行には一切永続化されていない**。用途は監査イベントの actor 決定のみである（`MembershipService#leave`）。したがってマスター要件「外れた理由・日時を記録として持ちたい」は、**既存列だけでは満たせない**。

**追加する列**

| 列 | 型 | Null | 役割 |
|---|---|---|---|
| `archived_at` | `DATETIME(3)` | ✅ | アーカイブ在籍の開始日時。NULL = 通常在籍 |
| `archive_reason` | `VARCHAR(10)` | ✅ | `DECEASED` / `RELOCATED`。アーカイブの事由 |
| `archived_by` | `BIGINT` | ✅ | **記録した理事の user_id**。SYSTEM_ADMIN 操作もここに入る |
| `archive_expires_at` | `DATETIME(3)` | ✅ | **自動退会の予定日時**。移行時に確定して書く（§5.2.1）|
| `left_trigger` | `VARCHAR(24)` | ✅ | `MANUAL` / `AUTO_ARCHIVE_EXPIRY`。**自動退会と人による退会を区別する**（§5.2.2）|
| `left_by` | `BIGINT` | ✅ | 退会させた操作者の user_id。**自動退会では NULL** |

- `archived_at` / `archive_reason` / `archived_by` / `archive_expires_at` は**同時に非 NULL または同時に NULL**（CHECK 制約 `chk_memberships_archive_consistency`）
- `left_trigger` は `left_at` と**同時に非 NULL または同時に NULL**（CHECK 制約 `chk_memberships_left_trigger`）。既存の `chk_memberships_left_reason` と同じ様式に倣う
- クロスドメイン FK は張らない（`archived_by` / `left_by` は `users` への ID 参照のみ。CLAUDE.md アーキテクチャ思想 1）

#### 5.2.1 `archive_expires_at` を移行時に確定して書く理由

「`archived_at` ＋ 設定値（1 か月）」で毎回計算する案は**採らない**。設定値を後から変えたとき、**既にアーカイブ済みの人の退会日が遡って動く**（短くすると即日退会が発生しうる）。**移行した時点の約束を行に固定する**ことで、設定変更が既存のアーカイブ在籍者に影響しない。UI の残り日数表示もこの列をそのまま使う（§12.3）。

#### 5.2.2 `left_trigger` を独立した列にする理由（マスター要件「自動か人かを区別」）

**`leave_reason` に `AUTO_...` 系の値を足す案は採れない。** 実測で 2 つの制約がある。

1. `MembershipEntity` の `leave_reason` は **`@Column(length = 10)`** である。`DECEASED`(8 文字) と `RELOCATED`(9 文字) は入るが、`AUTO_DECEASED`(13) のような合成値は**入らない**
2. そもそも「事由（なぜ）」と「主体（誰が／自動か）」は**直交する軸**である。理事が手で退会させた逝去者と、期限到来で自動退会した逝去者は、**事由が同じで主体が違う**。1 列に畳むと組合せ爆発する

**`left_by` の NULL では区別できない。** 実測: `removedBy = null` は**既に自主退会（SELF）とシステム purge の両方で使われている**（`MembershipService#leave` の javadoc が「自主退会・システム処理では null」と明記、`RoleService:332` が `null` を渡す）。**NULL は「自動退会」を意味しない。** したがって明示的な `left_trigger` 列が要る。

> **既存行の扱い**: 追加時、既存の退会済み行は `left_trigger` が NULL になる。**バックフィルしない**（過去の退会が自動か手動かを事後に判定する材料が無く、推測で埋めると記録として嘘になる）。`left_trigger IS NULL AND left_at IS NOT NULL` は「本機能導入前の退会」を意味すると定義し、CHECK 制約は**新規行にのみ効く形**にできないため、**制約は `left_at IS NULL` 側だけを縛る**（下記）。

```sql
CONSTRAINT chk_memberships_left_trigger CHECK (
    left_at IS NOT NULL OR left_trigger IS NULL
)
```

すなわち「`left_at` が NULL なら `left_trigger` も NULL」だけを保証する。逆向き（`left_at` があれば `left_trigger` も必須）は既存行のため課せない。**この非対称を AC-703 で明示的に固定する**（将来この制約を「対称にすべきでは」と誤って強化されるのを防ぐ）。

### 5.3 復元用テーブル `archived_membership_grants`（新規）

**なぜ要るか**: §9.3 で `user_roles` 行と `user_permission_groups` 行を**物理削除**する。実測で確認したとおり、`user_roles` には**ソフトデリートも履歴表も存在しない**（`UserRoleEntity` は `id`/`userId`/`roleId`/`teamId`/`organizationId`/`scopeKey`/`grantedBy`/`createdAt`/`updatedAt` のみ。`role_history` 系のテーブルは grep でゼロ件）。**削除したら何を持っていたか分からなくなる。** §9.4 の取消で復元できない。

| 列 | 型 | 役割 |
|---|---|---|
| `id` | `BINARY(16)` PK | **UUIDv7**（`UuidV7Entity` 継承。CLAUDE.md アーキテクチャ思想 6。新規テーブルのため）|
| `membership_id` | `BIGINT NOT NULL` | どのアーカイブに紐づくか（同一ドメイン内のため FK 可）|
| `grant_type` | `VARCHAR(20) NOT NULL` | `ROLE` / `PERMISSION_GROUP` |
| `grant_ref_id` | `BIGINT NOT NULL` | `grant_type=ROLE` なら `roles.id`、`PERMISSION_GROUP` なら `permission_groups.id`。**クロスドメイン FK は張らない**（ID 参照＋インデックスのみ）|
| `granted_by` | `BIGINT` | 元の付与者（`user_roles.granted_by` / `user_permission_groups.assigned_by` を退避）|
| `revoked_at` | `DATETIME(3) NOT NULL` | 取り上げた日時 |
| `restored_at` | `DATETIME(3)` | 復元した日時。NULL = 未復元 |
| `created_at` / `updated_at` | `DATETIME(3) NOT NULL` | `UuidV7Entity` は時刻列を持たないため明示定義する（3 巡目の検分で得た教訓）|

- インデックス: `idx_archived_grants_membership (membership_id, restored_at)`
- **行は削除しない。** 復元しても `restored_at` を埋めるだけにする。「いつ取り上げていつ戻したか」が履歴として残る（マスター要件「記録として持ちたい」に沿う）

### 5.4 `LeaveReason` の ENUM 拡張（**要 Flyway**）

**実測**: `LeaveReason` は `SELF` / `REMOVED` / `GDPR` / `TRANSFER` / `OTHER` の 5 値（`membership/domain/LeaveReason.java`）。

**`DECEASED` と `RELOCATED` の 2 値を追加する。** 追加しないと逝去・転出による退会がすべて `REMOVED`（＝理事が追い出した）に畳まれ、マスター要件「事由が判別できること」を満たせない。

**DDL 上の正確な状態（実測・3 巡目で確認済みの内容を再確認した）**

- `leave_reason` は **native MySQL ENUM** である（`V60.001__create_memberships_table.sql:31`）:
  ```sql
      leave_reason ENUM('SELF','REMOVED','GDPR','TRANSFER','OTHER') NULL,
  ```
- CHECK 制約 `chk_memberships_left_reason`（同 :39-42）は**値を列挙していない**。`left_at` と `leave_reason` の NULL 同期だけを検査する:
  ```sql
  CONSTRAINT chk_memberships_left_reason CHECK (
      (left_at IS NULL AND leave_reason IS NULL)
      OR (left_at IS NOT NULL AND leave_reason IS NOT NULL)
  ),
  ```
- **`leave_reason` の型を変更した後続 migration は存在しない**（`db/migration` 全走査で確認。`memberships` に触れる後続は `V60.002`（member_positions 作成）/ `V60.004`（unique + index 追加）/ `V60.005`・`V60.010`・`V60.011`・`V73.001`（データ移行・コメント）/ `V78.001` / `V174`・`V179`（索引）のみ）

**したがって CHECK 制約は変更不要。`MODIFY COLUMN` で ENUM 定義だけを拡張する**（§14 M-1）。両値とも 9 文字以下であり `@Column(length = 10)` に収まる。

### 5.5 転出専用カラムは追加しない

`relocated_at` は **`move_out_date` が既にある**。`PATCH /residents/{id}/move-out` という API と `ResidentRegistryService#moveOut`、`ALREADY_MOVED_OUT` まで実装済みで、`dwelling_units.resident_count` のデクリメントまで面倒を見ている。理由の自由記述は `audit_logs.metadata` に載せる。

### 5.6 `occupancy_status` で転出を代替できるか → できない

`occupancy_status`（`OWNER_OCCUPIED`/`RENTED_OUT`/`VACANT`/`SECONDARY_HOME`/`UNKNOWN`）は**住戸の使われ方**を表す。`RENTED_OUT` は区分所有者が住んでいないが**組合員のまま**の状態であり、転出と混同すると賃貸に出しただけの区分所有者がアーカイブされる。転出は `move_out_date` を正本とし、`occupancy_status` は触らない。

### 6.4 認可の配置と BOLA 対策

`docs/security/03_role_authority_model.md` §3.3.3 は新規 EP について「**宣言（SpEL ガード）を第一防御、Service 層明示呼出を第二防御**」を標準とする。本設計の各エンドポイントはこれに従う。

| 層 | 実装 | 目的 |
|---|---|---|
| **第一防御（宣言）** | `@PreAuthorize("@accessGuard.isScopeAdmin(authentication, #orgId, 'ORGANIZATION')")` | パス変数によるスコープ内ロール判定。**SYSTEM_ADMIN 短絡もここで効く**（§7.1）|
| **第二防御（Service）** | `ResidentRegistryService#checkAdminForResident` 相当（**entity 由来の scopeId**）| **BOLA 防止**。パスの `{orgId}` と `residentId` の実スコープが食い違うケースを塞ぐ |

**他スコープの `residentId` を指定した場合は 403 を返す**（`CommonErrorCode.COMMON_002`）。実測: `checkAdminForResident` → `checkAdminOrAbove` は非 ADMIN に `COMMON_002`（403）を投げ、既存の `verify` / `move-out` も他スコープ ID に対して 403 である。**既存 API の契約を変えないため 403 に揃える。**

#### 6.4.1 `ParentalConsentGateFilter` の許可リスト

**新設エンドポイントを許可リストに追加しない。** 保護者同意待ちの未成年が住民台帳の管理操作を行う場面は存在しないため、遮断されて正しい。遮断時の応答は **403 `AUTH_070` 固定であり 401 ではない**（同フィルタが「401 は絶対に返さない。FE `useApi.ts` の 401 ハンドラが無限リフレッシュを起こすため」と明記）。本設計は 401 を返す経路を新設しない。

### 6.5 住民一覧レスポンスへの露出

**実測**: `ResidentResponse` に `deathStatus` フィールドは存在しない（`moveOutDate` はある）。このままでは **FE は逝去の記録を描けない**。

**単一 DTO を維持し、非 ADMIN には機微フィールドを `null` で返す。**

| フィールド | 型 | ADMIN / DEPUTY_ADMIN / SYSTEM_ADMIN | 一般メンバー・**本人** |
|---|---|---|---|
| `deathStatus` | `string`（null許容）| `ALIVE` / `SUSPECTED` / `CONFIRMED` / `CANCELLED_FALSE_ALARM` | **常に `null`** |
| `archived` | `boolean`（null許容）| 実値 | **常に `null`** |

#### 6.5.1 ロール別 DTO に分けない理由

ロール別に別クラスを返す案は**採らない**。同一エンドポイントが 2 つの戻り値型を持つと、**springdoc は片方しか OpenAPI に出力せず、生成型がその一方に固定される**。結果として FE の型が嘘になり、しかもこのズレは CI の生成型ドリフト検査でも検出できない（生成物とスキーマは一致したまま、スキーマ自体が現実と違うため）。単一 DTO なら型は常に真であり、値が `null` かどうかだけが権限で変わる。

> **実測の補足**: `ResidentResponse` にも `application.yml` にも `@JsonInclude(NON_NULL)` 相当の設定は無い。よって `null` は省略されず `"deathStatus": null` として実際にシリアライズされ、AC で観測可能である。

#### 6.5.2 本人向け API への漏洩を塞ぐ（3 巡目の検分で得た知見を維持）

**実測**: `ResidentMapper`（`resident/mapper/ResidentMapper.java:27`）は

```java
ResidentResponse toResidentResponse(ResidentRegistryEntity entity);
```

という**フィールド名の暗黙マッピングだけ**の宣言であり、`ResidentRegistryEntity` には `deathStatus` フィールドが**既に実在する**。したがって **DTO にフィールドを足した瞬間、`toResidentResponse` を呼ぶ全経路が自動的に `deathStatus` を詰める。** そして本人向け API がこの経路を直に踏んでいる（`UserResidentController` の `GET /api/v1/users/me/resident-info` が同じ DTO を返し、`ResidentRegistryService` が `residentMapper.toResidentResponse(entity)` を直接呼ぶ）。

**是正: `ResidentResponse` を生成する全経路をロール認識 assembler へ統一する。**

- `residentMapper.toResidentResponse(...)` の**直接呼出をゼロにする**。マッパーは assembler の内部からのみ呼ばれる
- assembler は必ず「閲覧者」を引数に取る。**閲覧者が当該スコープの ADMIN / DEPUTY_ADMIN / SYSTEM_ADMIN でない限り機微フィールドは `null` で固定する**
- **本人であることは開示理由にならない。** とりわけ `SUSPECTED`（滞納エスカレーションの自動起票）は理事の判断ですらない中間状態であり、本人に見せてはならない
- ArchUnit 番人で `toResidentResponse` / `toResidentResponseList` の呼出元を assembler 1 クラスに限定する（AC-505）

#### 6.5.3 `archived` の N+1 を避ける

居住者ごとに membership を照会すると、住戸数 × 居住者数に比例して SQL が増える。**既存の一括プリミティブを使う。** `MembershipRepository#findActiveRoleKindsByScopeAndUsers(scopeType, scopeId, userIds)` は `userId IN :userIds` で一括解決する投影クエリであり、同 javadoc が「候補者ごとに呼ぶと候補者数に比例して SQL が増える（AC-39 が禁じる形）」と明記している。同じ様式でアーカイブ状態も一括解決する（`userIds` が空なら呼ばない。`IN ()` は不正 SQL）。一覧あたりの追加 SQL を **1 本**に収める。

### 6.6 `death_status` の遷移可否表

| From \ To | `ALIVE` | `SUSPECTED` | `CONFIRMED` | `CANCELLED_FALSE_ALARM` |
|---|---|---|---|---|
| **`ALIVE`** | — | ✅ バッチのみ（`markDeathSuspected`・アーカイブ移行なし）| ✅ **API**（アーカイブ移行あり）| ❌ `RESIDENT_012` |
| **`SUSPECTED`** | ❌ | — | ✅ **API**（移行あり）**← 理事の典型経路** | ✅ **API**（移行なし。疑いの取り下げ）|
| **`CONFIRMED`** | ❌ **禁止** | ❌ | ❌ `RESIDENT_012` | ✅ **API**（アーカイブ取消あり）|
| **`CANCELLED_FALSE_ALARM`** | ❌ | ❌ バッチは立てない（下記）| ✅ **API**（再確定。移行あり）| — |

- **`SUSPECTED → CONFIRMED` が理事の典型経路である。** 滞納エスカレーション D+120 が `markDeathSuspected` で `SUSPECTED` を自動起票し、理事がそれを見て確定させる
- **`CONFIRMED → ALIVE` は禁止する。** 取消は `CANCELLED_FALSE_ALARM` を経由させる。`ALIVE` に戻すと「一度も疑われなかった」ことになり監査上の履歴が台帳から消える。台帳の値が「誤警報」という語感を持つ問題は、**FE 側で「記録なし（訂正済み）」と表示する**ことで吸収する（i18n `lifeEvent.deathStatus.cancelled`）
- **`CANCELLED_FALSE_ALARM → CONFIRMED`（再確定）は許可する。** 実測: `markDeathSuspected` は `deathStatus != ALIVE` なら早期 return するため、**一度取り消した居住者はバッチで二度と `SUSPECTED` にならない**。API による再確定を塞ぐと、誤って取り消した居住者を二度と逝去にできなくなる

## 7. 権限モデル

**新しい権限名は追加しない。** 既存の `AccessGuard` で足りる。権限を足すと migration での `INSERT INTO permissions` が必須になり、番人 `PermissionNameCatalogGuardTest` と `DeadPermissionCatalogFlywayIT` の対象が増える。本設計にはロール以上の粒度を必要とする理由が無い。

**段差を付ける**（取消は記録より強い操作である。誤って権限を復活させうるため）。

| 操作 | 必要ロール | 第一防御（SpEL）| 第二防御（Service・entity由来）|
|---|---|---|---|
| 逝去／転出の**記録** | SYSTEM_ADMIN または ADMIN / DEPUTY_ADMIN | `@accessGuard.isScopeAdmin(...)` | `checkAdminForResident` 相当 |
| 逝去／転出の**取消**（役職の復元を伴う）| SYSTEM_ADMIN または **ADMIN のみ** | **`@accessGuard.isScopeStrictAdmin(...)`** | `isAdmin(entity由来scopeId)` |
| アーカイブ一覧の閲覧 | SYSTEM_ADMIN または ADMIN / DEPUTY_ADMIN | `@accessGuard.isScopeAdmin(...)` | — |

### 7.1 SYSTEM_ADMIN の締め出し問題は `AccessGuard` で解決する

実測: `AccessControlService#checkAdminOrAbove` に **SYSTEM_ADMIN 短絡は無い**。`ADMIN_ROLES = Set.of("ADMIN","DEPUTY_ADMIN")` であり、`resolveEffectiveRole` はスコープ内の行のみを見るため、team/org が NULL の SYSTEM_ADMIN 行は解決されない。したがって Service 層の `checkAdminOrAbove` だけで組むと**運営（SYSTEM_ADMIN）が操作できない**。

**`AccessGuard` を第一防御に採ることでこれが同時に解決する**（実測 `common/security/AccessGuard.java`）:

```java
public boolean isScopeAdmin(Authentication authentication, Long scopeId, String scopeType) {
    Long userId = resolveUserId(authentication);
    if (userId == null) { return false; }
    if (accessControlService.isSystemAdmin(userId)) { return true; }   // ← SYSTEM_ADMIN 短絡
    return accessControlService.isAdminOrAbove(userId, scopeId, scopeType);
}
```

`isScopeStrictAdmin` も同型で、`isSystemAdmin` 短絡の後に `isAdmin`（ADMIN のみ・DEPUTY_ADMIN を除く）を呼ぶ。**求めていた段差がそのまま既存 Bean にある。**

> ⚠️ 第二防御（Service 層・entity 由来）は SYSTEM_ADMIN 短絡を持たないため、**Service 層の検査にも `isSystemAdmin` の短絡を入れる**（`AccessGuard` と同じ順序）。片方だけに短絡があると SYSTEM_ADMIN が第一防御を抜けて第二防御で落ちる。

### 7.2 ArchUnit 認可網羅

新規エンドポイントは **`AuthzControllerGuardArchTest`**（`backend/src/test/java/com/mannschaft/app/common/architecture/`）の対象になる。ルール名は `public controller endpoints must have an authorization signal (Wave4)` で `FreezingArchRule.freeze(...)` である。合格するには `@PreAuthorize` / `AccessControlService`・`*AccessGuard`・`*AccessService` への直接呼出（depth ≤ 2）/ マーカー注釈のいずれかを持てばよい。

**本設計は `@PreAuthorize` を付けるため、凍結ストアへの追記は不要**（違反しないので何も凍結されない）。

> ⚠️ `./gradlew test --tests ...` の絞り込み実行は凍結ストアを破壊する既知の罠がある。実装 PR では**凍結ストアに差分が出ていないこと**を必ず確認する。

## 8. 管理権限の停止が全経路で成立することの検証 **【本設計の要】**

**旧方式が 3 巡の検分で収束しなかったのは、「関門を置く」という手段が経路の網羅を要求したからである。** 新方式は問いを変える —— **「管理権限の源泉となるデータは何本あるか」**。これは有限で列挙可能である。

### 8.1 検証の方法

3 巡の検分で発見された全 6 経路（および追加で発見した 2 経路）について、**それが最終的にどのテーブルを読むか**を実測し、`user_roles` 行と `user_permission_groups` 行の削除で閉じるかを 1 つずつ確認した。

### 8.2 検証表（実測）

| # | 経路 | 最終的に読むデータ | `user_roles` 削除だけで閉じるか | `user_permission_groups` も削除すれば閉じるか |
|---|---|---|---|---|
| 1 | `AccessControlService#resolveEffectiveRole`（private）→ `isAdmin` / `isAdminOrAbove` / `hasRoleOrAbove` / `checkAdminOrAbove` / `checkOwnerOrAdmin` | `user_roles` + `roles`（第1段）、`memberships.role_kind`（第2段）| ✅ **閉じる** | ✅ |
| 2 | `AccessControlService#checkAdminOrHasPermission` | `existsDeputyAdminWithPermissionInOrganization` の native query。**行の起点が `user_roles ur` で `r.name='DEPUTY_ADMIN'` に固定**され、権限グループの `EXISTS` はその**従属**サブクエリ | ✅ **閉じる**（起点行が消えるため権限グループ付与の有無に関係なく 0 件）| ✅ |
| 3 | **`RoleService#hasPermission` → `resolveEffectivePermissions`** | **2 系統の UNION**。①`user_roles`→`role_permissions`→`permissions` ②**`user_permission_groups`→`permission_group_permissions`→`permissions`** | ❌ **閉じない**（②が残る）| ✅ **閉じる** |
| 4 | `MembershipBatchQueryService#fetchDirectRoles` → `UserScopeRoleSnapshot`（`ContentVisibilityResolver` 系が消費）| `user_roles`（`findByUserIdAndScopes`）+ `memberships.role_kind` | ✅ **閉じる** | ✅ |
| 5 | **`PermissionGroupService#hasPermission`**（`PropertyWorkPackageMaskingService` が直接利用）| `permission_groups` / `user_permission_groups` / `permission_group_permissions` / `permissions`。**`user_roles` を一切参照しない** | ❌ **閉じない** | ✅ **閉じる** |
| 6 | `BulletinAccessGuard#requireManageContent` / `JobPolicy#canCreatePosting` / `#canDecideApplication` / `UnsealRequestService#checkUnsealPermission` | いずれも `isAdmin(...)`（=経路1）**OR** `roleService.hasPermission(...)`（=経路3）| ❌ **部分的**（OR の後段が残る）| ✅ **閉じる** |
| 7 | `AccessGuard#isScopeAdmin` / `#isScopeStrictAdmin` | 経路1 ＋ `isSystemAdmin` 短絡 | ✅ **閉じる** | ✅ |
| 7' | `AccessGuard#hasScopePermission` | 経路3 | ❌ **閉じない** | ✅ **閉じる** |
| 8 | `AdminRoleChecker#hasAnyAdminRoleInAnyTeam`（`@PreAuthorize("@adminRoleChecker...")`）| `user_roles` のみ（`findAdminAndDeputyAdminTeamIds`）| ✅ **閉じる** | ✅ |
| — | `memberships.role_kind` | enum は **`MEMBER` / `SUPPORTER` の 2 値のみ**（`RoleKind.java`）| **管理権限を与えることが原理的に不可能** | — |

### 8.3 結論 — 管理権限の源泉は **2 本**であり、両方を取り上げれば全経路が閉じる

> **`user_roles` の行を削除するだけでは不十分である。** 実測により、**`permission_groups` 機構が `user_roles` と完全に独立した第 2 の権限源泉**であることが確定した。

`PermissionGroupService` の javadoc がこれを設計意図として明言している（実測・verbatim）:

> ロール直付けの permission（`role_permissions` の `is_default=1` 等）は本メソッドでは判定しない。本メソッドは「**権限グループ経由の明示付与**」のみを対象とする。

すなわち **`user_permission_groups` は「ロールとは別に、個別ユーザーへ直接権限を与える」ための機構**である（`V2.007`〜`V2.009` で導入。`user_permission_groups` の FK は `users` と `permission_groups` のみで、**`user_roles` への参照は一切無い**）。

**したがって §9.3 の取り上げは 2 本立てにする。**

1. 当該スコープの **`user_roles` 行を削除**する
2. 当該スコープに属する `permission_groups` に対する **`user_permission_groups` 行を削除**する

**この 2 本で表中の全経路が閉じる。** そして重要なのは、**認可コードには一切手を入れていない**ことである。旧方式が 3 巡かけても閉じ切らなかった問題が、**データを消すという 1 つの操作**に還元された。

> ⚠️ **なぜこの結論を信頼してよいか（旧方式との違い）**: 旧方式は「関門を通らない経路」を探す作業であり、**探索が尽きたことを証明できなかった**（毎巡新しい経路が出た）。新方式が問うのは「権限を与えているテーブルは何か」であり、これは**スキーマから有限に列挙できる**。`permissions` テーブルを参照する経路は `role_permissions`（ロール由来）と `permission_group_permissions`（権限グループ由来）の 2 本しかなく、前者は `user_roles`、後者は `user_permission_groups` によってユーザーへ結びつく。**この 2 本以外にユーザーへ権限を結びつける表は存在しない**（`V2.007`〜`V2.009` および `role_permissions` のスキーマで確認）。
>
> ただし **「証明した」とは書かない。** 新しい権限機構が将来足される可能性はある。そこで **AC-801 の番人**（`permissions` テーブルを参照する新たな結合経路が増えたら検知する）を置く。

### 8.4 SYSTEM_ADMIN は取り上げ対象外

実測: `isSystemAdmin` は `userRoleRepository.existsSystemAdminByUserId(userId)` を引く。SYSTEM_ADMIN は**スコープを持たない大域の `user_roles` 行**であり、組合のアーカイブとは無関係である。**本設計は SYSTEM_ADMIN 行に触れない**（運営がその組合の住民でもある場合、運営権限まで奪うのは筋が違う）。§7.1 の短絡が先に効くため、SYSTEM_ADMIN はアーカイブ在籍中でも管理操作ができる。**これは意図した設計である。** AC-804 が固定する。

### 8.5 「一般組合員ができる操作のみ」が成立すること

マスター要件「1 か月ほど**通常組合員ができる操作のみ**できる」は、次の 2 点で成立する。

| | 根拠 |
|---|---|
| **できること（一般組合員の操作）** | `memberships` 行が `left_at IS NULL` のまま残るため、`isMember` / `existsActiveByUserAndScope` / 在籍列挙 4 本 / fan-out クエリのいずれも**従来どおり通る**（§3.2 INV-2）。`resolveEffectiveRole` は第2段の `memberships.role_kind` から **MEMBER** を返す |
| **できないこと（管理操作）** | §8.2 の全経路が §8.3 の 2 本の削除で閉じる |

**すなわち「MEMBER に降格した通常の組合員」そのものになる。** 旧方式が `resolveEffectiveRole` の内部に降格ロジックを注入して実現しようとしたことが、**データを消すだけで自然に達成される**。

## 9. ビジネスロジック

### 9.1 全体の配置

| 責務 | 配置先 |
|---|---|
| 台帳の記録（`death_status` / `move_out_date`）| `ResidentRegistryService`（既存）|
| アーカイブ移行・取消・自動退会 | **`MembershipArchiveService`（新設・membership ドメイン）** |
| 役職／権限グループの取り上げ・復元 | **`RoleService` に新設するメソッド**（role ドメイン。`user_roles` / `user_permission_groups` の書き手は role ドメインに閉じる）|
| 同意書の失効 | `ProxyConsentLifecycleService#revokeAllForUser`（既存・§9.5）|

> **クロスドメイン `@Transactional` について**: 本操作は resident → membership → role → proxy と推移的に 4 ドメインを跨ぐ。実測により、番人 `CrossDomainTransactionalArchTest`（D-3）は javadoc が明記するとおり **「推移呼び出し（A→B→他ドメイン repo）は追わない（直接依存のみ）」** ため、**D-3 違反は 1 件も増えない**（各 Service は自ドメインの repository しか触らない）。**しかし D-3 が緑であることは越境が無いことを意味しない。** 意図的な越境であることを設計書のこの節と実装のクラス javadoc の両方に明記し、§20.2 U-2 に技術負債として記録する。

### 9.2 逝去・転出の記録（アーカイブ移行）

**フロー（逝去・`CONFIRMED` の例。転出も §9.2.2 の粒度規則以外は同一）**

1. `residentRepository.findById(id)` → 無ければ `RESIDENT_003`
2. 第二防御: entity 由来の scopeId で ADMIN以上（＋SYSTEM_ADMIN 短絡）を検査（§6.4・§7.1）
3. **§6.6 の遷移可否表に従って検査**。不可な遷移なら `RESIDENT_012`
4. `entity.updateDeathStatus(DeathStatus.CONFIRMED, actorUserId)` → `save`
5. `user_id` が NULL なら以降をスキップし `archived:false` で 200（アカウント未紐づけの居住者）
6. **§9.2.2 の粒度規則**を判定。満たさなければアーカイブ移行をスキップし `archived:false` で 200（**台帳の更新はロールバックしない**）
7. 当該スコープの `memberships` 行を取得。**既にアーカイブ済み、または退会済みなら移行をスキップ**（冪等）
8. **役職・権限グループ割当を取り上げ、復元用に記録する**（§9.3）
9. `archived_at` / `archive_reason` / `archived_by` / `archive_expires_at` を確定して `save`
10. **代理入力同意書を同期で失効**（§9.5）
11. 監査ログ（§10）

> **通知は出さない。** 旧方式は理事に「要対応」を通知し一覧にバッジを出して所属解除を促していたが、**新方式は自動で退会するため催促が不要**である。§11 参照。

#### 9.2.1 アーカイブ移行をスキップした場合も台帳は更新する

手順6・7 でスキップする場合も**台帳の更新はロールバックしない**。住民台帳の目的（誰がどの住戸に住んでいるかを正しく保つこと）は、所属の状態と独立に達成されるべきである。レスポンスは `archived:false` で 200 を返す。

#### 9.2.2 アーカイブ移行の粒度規則

`resident_registry` は 1 ユーザーが複数行（複数住戸・共有持分）を持ちうる。**アーカイブは「その組合の組合員でなくなる」という判断**なので、粒度を揃える。

| 事由 | 移行の条件 |
|---|---|
| **逝去**（`CONFIRMED`）| **当該スコープ内**の当該ユーザーの `resident_registry` 行が**1 行でも `CONFIRMED`** になったら移行する。逝去は人に属する事実であり、1 住戸でも確定すればその人は逝去している |
| **転出**（`move_out_date`）| **当該スコープ内**の当該ユーザーの `deleted_at IS NULL` の行が**すべて** `move_out_date` 非 NULL になったときに移行する。**2 号室から転出しても 5 号室に住み続けているなら、その組合の組合員ではある** |

> **旧方式との違い（重要）**: 旧方式の R-1 は `users.status` という**ユーザー単位のグローバル値**へ伝播させるため、粒度を**全スコープ横断**で定義せざるを得なかった。新方式のアーカイブは **`memberships` というスコープ単位の行**に対する操作なので、**当該スコープ内で閉じて判定できる**。判定・作用・副作用の粒度が自然に揃い、旧方式が抱えていた「A 組合の転出で B 組合が巻き込まれる」問題が構造的に消える。
>
> **例外は同意書の失効だけ**である（`revokeAllForUser` がユーザー単位のため。§3.4 で受容済み）。

### 9.3 役職・権限グループの取り上げ

**§8.3 の結論に従い 2 本立てで行う。** 新設メソッド `RoleService#revokeGrantsForArchive(scopeId, scopeType, targetUserId, membershipId)` を置く。

```
revokeGrantsForArchive(...):
    ① user_roles の当該スコープ行を取得
         → archived_membership_grants に (ROLE, roleId, grantedBy) を記録
         → userRoleRepository.delete(...) + flush()
    ② 当該スコープに属する permission_groups に対する user_permission_groups 行を取得
         → archived_membership_grants に (PERMISSION_GROUP, groupId, assignedBy) を記録
         → userPermissionGroupRepository.deleteAll(...) + flush()
    ③ role-permissions キャッシュを当該ユーザー分 evict
```

#### 9.3.1 既存の `removeMember` 系を使わない理由

**実測**: `RoleService#removeMember` / `#removeMemberWithoutAdminCheck` は `user_roles` 行を削除した**あと `leaveMembershipForRoleRevoke(...)` を呼んで `memberships` の退会まで行う**。本設計が必要なのは「役職だけ取り上げて在籍は残す」ことなので、**これらは使えない**（使うと在籍まで終わり、アーカイブ在籍が成立しない）。

また `removeMemberWithoutAdminCheck` は **actor 引数を持たず** `LeaveReason.REMOVED` と `removedBy=null` をハードコードしている。**新設メソッドが必要である。**

#### 9.3.2 キャッシュの扱い（旧方式の教訓を活かす）

`RoleService#resolveEffectivePermissions` は `@Cacheable(value="role-permissions", key="#userId + ':' + #scopeType + ':' + #scopeId")` で **TTL 5 分**（`RedisConfig`）である。取り上げ後に `@CacheEvict` を行う。

> ⚠️ **ただし旧方式と違い、evict の失敗は権限の残存を意味するが「設計の破綻」ではない。** 旧方式は evict 失敗＝関門の無効化＝**永続的な迂回**だったが、新方式は**源泉データが既に消えている**ため、キャッシュが切れれば（最長 5 分）必ず正しい状態に収束する。`LoggingCacheErrorHandler` が evict 失敗を握りつぶしても、**最大 5 分の反映遅延**にとどまる。
>
> **とはいえ 5 分の遅延は許容しない。** キーは `userId:scopeType:scopeId` であり、**アーカイブは単一スコープの操作なのでキーが一意に定まる**（旧方式が詰まった「全スコープのキー列挙」問題は発生しない）。確実に evict できる。AC-802 が固定する。

#### 9.3.3 復元時に他者が同じ役職に就いている場合

**役職は排他ではない。** 実測: `user_roles` は `(user_id, scope, role_id)` の行であり、同一スコープに複数の ADMIN が存在できる（`checkLastAdmin` が「ADMIN が 1 人だけ」を特別扱いすることが、複数いられる証拠である）。したがって **他者が同じ役職に就いていても、復元は競合しない。** 単に両者が ADMIN になる。

> ただし**オーナー（唯一性のある概念）が絡む場合は別**である。実測の範囲では `user_roles` に「オーナー」を表す排他制約は無く、オーナー移譲は `TransferOwnershipPanel` 経由の別機構である。**本設計は役職の復元のみを行い、オーナー移譲には触れない。** 復元後に ADMIN が 2 人になることは正常である。AC-506 が固定する。

#### 9.3.4 唯一の ADMIN が逝去した場合

**アーカイブ移行そのものは阻止しない。** 逝去した理事長を理事長のままにしておくほうが危険だからである。ただし **ADMIN 不在（ロックアウト）**が発生しうる。

**判断: 移行は通し、警告を返す。**

- 手順8 で「対象者が当該スコープの ADMIN であり、かつ他に ADMIN が 1 人もいない」場合、**移行は実行したうえでレスポンスに `lastAdminWarning: true` を載せる**。FE は「後任の理事を選任してください」と表示する（i18n `lifeEvent.warning.lastAdmin`）
- **409 で阻止しない。** 阻止すると「逝去した理事長を降ろせない」状態になり、より悪い
- 後任の**自動**選任は既存設計書 `account_purge_last_admin_succession.md` の領域であり、**本設計は警告するだけで自動化しない**（§2.2 S-5）
- SYSTEM_ADMIN は §8.4 のとおり影響を受けないため、最終手段として運営が介入できる

### 9.4 記録の取消（誤記録の救済）

**フロー**

1〜3 は §9.2 と同じ（§6.6 の表に従う）。ただし第一防御は `isScopeStrictAdmin`（ADMIN のみ＋SYSTEM_ADMIN 短絡。§7）
4. `entity.updateDeathStatus(DeathStatus.CANCELLED_FALSE_ALARM, actorUserId)`（転出取消なら `move_out_date` を NULL に戻し `incrementResidentCount()`）
5. **§9.2.2 の粒度規則を再判定**し、まだ移行条件を満たすなら**アーカイブは解除しない**（例: 2 行のうち 1 行だけ逝去を取り消したが、もう 1 行が `CONFIRMED` のまま）
6. アーカイブ解除: `archived_at` / `archive_reason` / `archived_by` / `archive_expires_at` を **NULL に戻す**
7. **役職・権限グループを復元**（`archived_membership_grants` の `restored_at IS NULL` の行を読み、`user_roles` / `user_permission_groups` を再作成して `restored_at` を埋める）
8. `role-permissions` キャッシュを evict
9. **同意書は復活させない**（§3.3）
10. 監査ログ

#### 9.4.1 復元の冪等性

手順7 は `restored_at IS NULL` の行だけを対象とし、再作成前に**同じ行が既に存在しないかを確認**する（他経路で再付与されていた場合に重複行を作らない）。既に存在するなら作成をスキップして `restored_at` だけ埋める。AC-504 が固定する。

#### 9.4.2 既に自動退会済みだった場合

**アーカイブ期限が過ぎて自動退会した後に記録を取り消した場合、所属は自動では復活させない。**

**根拠**: 退会後は `memberships.left_at` が確定し、`member_positions` の終了処理も走っている（`MembershipService#leave` が行う）。これを機械的に巻き戻すと、**退会後に発生した他の変更（再加入、別の役職付与など）と競合しうる**。しかも「1 か月放置された誤記録」は稀であり、そのために復活経路を用意すると**そちらの経路のほうがバグの温床になる**。

- 台帳の記録（`death_status` / `move_out_date`）は**取り消される**（誤りは誤りとして訂正される）
- 所属は**復活しない**。レスポンスに `membershipRestored: false` と `alreadyWithdrawn: true` を載せ、FE は「所属は自動退会済みのため復活しません。再度招待してください」と案内する（i18n `lifeEvent.info.alreadyWithdrawn`）
- 役職も復元しない（`archived_membership_grants` の行は `restored_at` を埋めずに残す。**記録は残す**）
- **再加入は既存の招待フローで行う**。`memberships` は履歴を持つ設計（`uq_memberships_history (user_id, scope_type, scope_id, joined_at)`）なので、再加入は新しい行として自然に表現される

AC-503 がこの挙動を固定する。

### 9.5 代理入力同意書の失効（**同期・同一トランザクション**）

**旧方式との最大の違い。** 旧方式は `UserStatusChangedEvent` → `@Async` リスナーという**プロセス内イベント配送**に依存し、その配送保証のために outbox・照合バッチ・冪等 consumer まで設計する羽目になっていた。

**新方式は `ProxyConsentLifecycleService#revokeAllForUser` を §9.2 手順10 で同期に直接呼ぶ。**

実測により、これが成立する条件が揃っている。

```java
@Transactional
public int revokeAllForUser(Long userId, String reason) {
    List<ProxyInputConsentEntity> consents = consentRepository.findActiveBySubjectOrProxyUserId(userId);
    consents.forEach(consent -> consent.revoke(RevokeMethod.AUTO_BY_LIFE_EVENT, null, reason));
    consentRepository.saveAll(consents);
    return consents.size();
}
```

| 条件 | 実測 |
|---|---|
| `@Transactional` である | ✅ 呼出元のトランザクションに参加する（既定 `REQUIRED`）|
| **冪等である** | ✅ `findActiveBySubjectOrProxyUserId` が**有効な同意書だけ**を引くため、2 回呼んでも 2 回目は 0 件で no-op |
| 件数を返す | ✅ `int`。§6.1 の `revokedConsentCount` に載せられる |
| 失効件数が同期で確定する | ✅ **旧方式で「約束できない」として外したフィールドが、約束できるようになった** |

**ロールバック時の扱い**: 同一トランザクションなので、**アーカイブ移行が失敗すれば失効も巻き戻る**。これは正しい挙動である（旧方式が抱えていたのは逆の問題 —— コミットしていないのに失効済みになる —— であり、同期化によって両方向とも解決する）。

> ⚠️ **`UserStatusChangedEvent` は使わない。** したがって `ProxyConsentLifeEventJob` は**発火元を持たないまま残る**。扱いは §19.1 に定める。

### 9.6 自動退会バッチ

#### 9.6.1 バッチ様式（実測した規約に従う）

`docs/features/F10.X_batch_catalog.md` と番人 `ScheduledBatchGuardTest`（`common/architecture/`）が要求する形式を実測した。**すべて必須である。**

| 要件 | 内容 |
|---|---|
| `@BatchEndpoint(name=..., description=...)` | **必須**。kebab-case で `{domain}-{action}[-{cadence}]`。重複名は**起動時に fail fast**。本設計は **`membership-archive-expiry-daily`** とする |
| `@SchedulerLock(name=..., lockAtMostFor=...)` | **必須**。`lockAtMostFor` を**明示**すること（設定クラス既定の 30m に頼るのは番人が禁止）|
| `@Scheduled(cron=..., zone="Asia/Tokyo")` | 日次。既存 `ProxyConsentExpiryJob` が `0 0 2 * * *` なので**時間帯をずらして** `0 30 2 * * *` とする |
| カタログへの追記 | `docs/features/F10.X_batch_catalog.md` に 1 行追加する（**実装 PR で必須**）|
| `ShedLockConfig` の javadoc 一覧 | ロック名を追記（CI 非強制だが運用の地図）|

ShedLock は `ShedLockConfig`（`@Profile("!test & !openapi-gen & !e2e")` / `JdbcTemplateLockProvider` / `usingDbTime()`）で構成済み、ロック表は `V11.010__create_shedlock_table.sql`。**新規の基盤整備は不要。**

#### 9.6.2 処理内容

```
対象: memberships WHERE archived_at IS NOT NULL
                    AND left_at IS NULL
                    AND archive_expires_at <= NOW()

各行について（1 行 1 トランザクション）:
    left_at        = NOW()
    leave_reason   = archive_reason に対応する値（DECEASED / RELOCATED）
    left_trigger   = 'AUTO_ARCHIVE_EXPIRY'
    left_by        = NULL（自動のため。§5.2.2 のとおり left_trigger で区別する）
    → member_positions の終了処理も行う（既存 leave と同じ後始末）
    → 監査ログ（§10）
```

#### 9.6.3 冪等性・再実行安全性・失敗時の扱い

| 観点 | 設計 |
|---|---|
| **冪等性** | 抽出条件に `left_at IS NULL` が入るため、**一度処理した行は次回の対象にならない**。同じ行を 2 回退会させることは構造的に起きない |
| **再実行安全性** | 手で再実行しても、前回処理済みの行は抽出されない。**バッチ全体を何度走らせても結果は同じ** |
| **1 行 1 トランザクション** | `EmailOutboxWorker` の様式に倣う。1 行の失敗が他の行を巻き込まない |
| **失敗時** | 行ごとに try/catch し、`log.error` ＋ メトリクスカウンタを増やして**次の行へ進む**。失敗した行は `left_at` が NULL のままなので**翌日のバッチが自然に再試行する**（リトライ機構を別途作らない）|
| **多重実行** | `@SchedulerLock` が防ぐ |
| **観測** | 処理件数・失敗件数を info/error で出す。**0 件が正常な日もある**ため 0 件をアラートにしない |

> **outbox もリトライ表も要らない。** 「期限が来たら退会させる」という操作は**状態から毎回導出できる**ため、配送を永続化する必要が無い。**これは §9.5 の同期化と並んで、新方式が旧方式より単純になった要点である。**

#### 9.6.4 アーカイブ期間は設定可能にする

**固定ではなく設定可能にする。** 根拠: マスターの指示が「**1 か月ほど**」であり厳密な法的要件ではないこと、組合ごとに慣行が異なりうること、実機・E2E で 1 か月待てないこと。

実測した既存の様式に従い、`application.yml` にプロパティを置き `@Value` で注入する（既存例: `mannschaft.system-log.slow-query-cron`、`equipment.ranking.cron`）。

```yaml
mannschaft:
  membership-archive:
    retention-days: 30
```

- **移行時に `archive_expires_at` へ焼き込む**ため、設定変更は既存のアーカイブ在籍者に影響しない（§5.2.1）
- **組合ごとの可変化は行わない**（組織別設定の置き場所が無く、射程が広がる）。§20.2 U-5 に記録

## 10. 監査ログ

書き口: `AuditLogService#record(...)`。`eventType` は `String`。

> ⚠️ **§3.5（INV-3）のとおり、監査ログは補助である。** 「いつ・なぜ・誰が」というマスター要件の担保は `memberships` の列（§5.2）と `archived_membership_grants`（§5.3）が**同期トランザクションで**負う。実測どおり `AuditLogService#record` は `@Async` かつ本体内で例外を握りつぶし、さらに executor rejection ではその catch すら動かないため、**要件をここに依存させない**。

|---|---|
| 逝去の記録 | `DEATH_STATUS_CHANGED_TO_CONFIRMED` |

**metadata（JSON）**

### 10.1 既存の除名監査との重複を避ける

**実測**: `MembershipService#leave` は `OrganizationMemberAuditEvent` / `TeamMemberAuditEvent`（`SubType.REMOVED`）を publish し、`team/event/TeamOrgAuditEventListener` がこれを `ORGANIZATION_MEMBER_REMOVED` / `TEAM_MEMBER_REMOVED` に写像して**既に `audit_logs` へ記録している**。

自動退会（§9.6）は `leave` 相当の後始末を行うため、**この既存経路も発火する**。したがって自動退会では `audit_logs` に **2 行**残る。

| 行 | 書き手 | eventType | metadata |
|---|---|---|---|
| 1 | 既存 `TeamOrgAuditEventListener`（本設計は関与しない）| `ORGANIZATION_MEMBER_REMOVED` / `TEAM_MEMBER_REMOVED` | `null` |
| 2 | **本設計** | `MEMBERSHIP_AUTO_WITHDRAWN` | 上記 metadata 入り |

**2 行になることは意図した設計である。** 1 行目は「組合員が除名された」という membership ドメインの事実、2 行目は「アーカイブ期限の到来による自動退会だった」という本設計固有の文脈である。

> ⚠️ **AC は「本設計固有の metadata を持つ行が存在する」で書く**（AC-706）。既存経路が書く行の存在だけを検証すると**実装ゼロで green になる**（3 巡の検分で通算 13 件見つかった類型）。

## 11. 通知

### 11.1 理事への催促通知・バッジは**作らない**

**旧方式では必要だった**（理事が手で所属解除しない限り札が残り続けるため、通知 1 通＋一覧バッジで促していた）。**新方式では自動退会するため催促が不要である。**

- `NotificationType` への新値追加は**行わない**
- `messages.properties` 7 ファイルへの追記も**不要**
- 住民一覧の「要対応」バッジも**作らない**
- 再通知バッチも**作らない**

**代わりに、アーカイブタブに残り日数を表示する**（§12.3）。理事が見たいときに見える状態を作れば足り、通知で割り込む必要は無い。

> **これは旧方式から純粋に削れた設計である。** §11 は旧版で `NotificationType` 追加・宛先解決クエリの実測・7 言語の messages 追加・`NotificationList.vue` のアイコン対応まで抱えていたが、**すべて不要になった**。

### 11.2 本人への通知も行わない

アーカイブ移行は本人に通知しない。理由は 2 つある。

1. 逝去の場合、**本人に届く通知は遺族が見る**。「あなたは逝去として記録されました」という通知が届くのは酷である
2. 転出の場合も、本人が転出届を出した結果であることが通常であり、通知の価値が低い

**誤記録に本人が気づく手段**は §12.5 の画面表示で担保する（ログインすれば見える。プッシュしない）。

## 17. テスト方針

### 17.1 受け入れ条件

> **3 巡の検分で得た教訓を新 AC にも適用する**（§19.3）。とりわけ次の 3 点を全 AC に対して自己点検した。
> - **既存実装が既に満たしている条件を AC にしない**（実装ゼロで green）
> - **原理的に成立しない条件を書かない**
> - **状態は API を通して作る**（フィクスチャで DB を直接いじって作らない）
>
> 自己点検の結果は §17.4 に記す。

#### 管理権限の停止（§8）— **本設計の要**

> **§8.2 の各経路を個別に測る。1 本の AC に畳んではならない。** 畳むと、最も検出しやすい経路 1 本だけで green になり、`permission_groups` 経由の残存を見逃す（旧方式が 3 巡で繰り返した失敗そのもの）。

- **AC-201**: ADMIN のユーザーをアーカイブ移行させると、`AccessControlService#isAdminOrAbove` と `#isAdmin` がいずれも `false` を返し、`checkAdminOrAbove` が `COMMON_002` を投げる（経路1）
- **AC-202（最重要）**: 移行前に **`user_permission_groups` 経由で `MANAGE_CONTENT` 権限を付与**しておき、移行後に `RoleService#hasPermission(...)` が **`false` を返す**（経路3）
  - ※ **`user_roles` 行だけを削除する実装ではこの AC は red になる。** `resolveEffectivePermissions` は `user_roles`→`role_permissions` と `user_permission_groups`→`permission_group_permissions` の **UNION** であり、後者は `user_roles` を一切参照しない（§8.3）
  - ※ **この AC が新方式の生命線である。** これが green なら §8.2 の経路 3・6・7' がまとめて閉じる
- **AC-203**: 同ユーザーについて `AccessControlService#checkAdminOrHasPermission` が `COMMON_002` を投げる（経路2）
- **AC-204**: `MembershipBatchQueryService` が作る `UserScopeRoleSnapshot` に、当該スコープの ADMIN/DEPUTY_ADMIN が**現れない**（経路4）
- **AC-205（権限グループ独立経路）**: `PermissionGroupService#hasPermission(userId, scopeType, scopeId, "PROPERTY_HISTORY_MANAGE")` が移行後に **`false` を返す**（経路5）
  - ※ このメソッドは `user_roles` を一切読まない（実測）。`user_permission_groups` を消していなければ red
- **AC-206**: 移行後、**`BulletinAccessGuard#requireManageContent` が拒否する**（経路6）。権限グループ経由で `MANAGE_CONTENT` を持っていた場合も拒否されること
- **AC-207**: 移行後、**`JobPolicy#canCreatePosting` / `#canDecideApplication` が `false`**、**`UnsealRequestService#checkUnsealPermission` が拒否**（経路6）。いずれも権限グループ経由の付与がある状態で測る
- **AC-208**: 移行後、`@PreAuthorize("@accessGuard.isScopeAdmin(...)")` を持つ EP が **403**、`@accessGuard.hasScopePermission(...)` を持つ EP も **403**（経路7・7'）
- **AC-209**: 移行後、`AdminRoleChecker#hasAnyAdminRoleInAnyTeam` が **`false`**（他チームの ADMIN 行を持たない場合。経路8）

#### 一般組合員としての操作は維持される（§8.5）

- **AC-211**: 移行後も `AccessControlService#isMember` と `hasRoleOrAbove("MEMBER")` が **`true` のまま**である
  - ※ **AC-201 と対で成立して初めて番人になる。** AC-211 単独では「何も実装しない」が最良解になる
- **AC-212**: 移行後も、本人の `GET /api/v1/dashboard` が 200 かつ当該組合の内容が**空でない**
- **AC-213**: 移行後も、本人の `GET /api/v1/me/payment-requirements` と `GET /api/v1/me/payments` が 200 かつ当該組合の内容が空でない
- **AC-214**: 移行後も、本人の iCal フィード（`/ical/{token}.ics`）に**当該組合の予定が含まれる**
- **AC-215**: 移行後も、当該組合でアンケートを公開すると**そのユーザーが配信の宛先に含まれる**（`findUserIdsByScope`）
  - ※ AC-212〜215 は「`users.status` を変えない」という設計判断（§3.2）の検証である。**旧方式では在籍列挙 4 本と fan-out 6 本の改修が必要だったが、新方式では 1 行も変えずに green になるはずである。** もし red なら設計の前提（INV-2）が崩れているので、そこで止まって設計を見直すこと

#### 記録とアーカイブ移行（§9.2）

- **AC-301**: ADMIN が `PATCH /residents/{id}/death-status {deathStatus:"CONFIRMED"}` を送ると 200、`death_status='CONFIRMED'`、`death_status_changed_by` が操作者 ID、`death_status_changed_at` が非 NULL
- **AC-302**: AC-301 の後、当該ユーザーの当該スコープの `memberships` 行が **`archived_at` 非 NULL / `archive_reason='DECEASED'` / `archived_by`=操作者 / `archive_expires_at` 非 NULL** になり、**`left_at` は NULL のまま**である
- **AC-303**: `archive_expires_at` が `archived_at` ＋ 設定日数（`retention-days`）と一致する
- **AC-304**: DEPUTY_ADMIN も記録を実行できる（200）
- **AC-305**: 一般メンバーが記録を実行すると **403 `COMMON_002`**
- **AC-306**: 別スコープの ADMIN が他スコープの `residentId` を指定すると **403 `COMMON_002`**
- **AC-307**: SYSTEM_ADMIN が記録を実行できる（200）※§7.1 の短絡
- **AC-308**: `user_id` が NULL の居住者に記録すると、台帳は更新され 200、`archived:false`
- **AC-309**: `deathStatus` に `SUSPECTED` または `ALIVE` を指定すると 400
- **AC-310**: `reason` が 501 文字だと 400（境界: 500 文字はちょうど通る）
- **AC-311（冪等）**: 既にアーカイブ済みのユーザーについて、**同一スコープの別の居住者行**に逝去を記録しても、`archived_at` が**上書きされない**（最初の移行時刻が保たれる）

#### 粒度規則（§9.2.2）

- **AC-321（転出）**: 同一スコープに `resident_registry` 行を 2 つ持つユーザーの**片方だけ**を `move-out` すると、台帳は更新されるが**アーカイブ移行は起きない**（`archived_at` が NULL のまま）
- **AC-322（転出）**: AC-321 の後にもう片方も `move-out` すると**アーカイブ移行が起きる**
- **AC-323（逝去）**: 同一スコープに 2 行持つユーザーの**片方だけ**を `CONFIRMED` にすると、**アーカイブ移行が起きる**（逝去は 1 行で足りる。転出との非対称を固定する）
- **AC-324（スコープ独立）**: 2 つの組織それぞれに `resident_registry` 行を持つユーザーについて、**組織 A で転出を記録しても組織 B の `memberships` はアーカイブされない**
  - ※ 旧方式は `users.status` へ伝播させたため全スコープ横断の判定が必要だったが、新方式はスコープ内で閉じる（§9.2.2）。**この AC がその設計判断を固定する**

#### 取り上げと復元（§9.3・§9.4）

- **AC-501**: アーカイブ移行時、`archived_membership_grants` に **`grant_type='ROLE'`** の行が作られ、`grant_ref_id` が元の `roles.id`、`granted_by` が元の `user_roles.granted_by` と一致する
- **AC-502（最重要）**: 権限グループ割当を持つユーザーの移行時、`archived_membership_grants` に **`grant_type='PERMISSION_GROUP'`** の行が作られ、対応する `user_permission_groups` 行が**削除されている**
  - ※ AC-202 が「権限が閉じたこと」を測るのに対し、この AC は「**復元できる形で**閉じたこと」を測る。記録せずに削除する実装は AC-202 では green・この AC で red になる
- **AC-503**: 取消（`CANCELLED_FALSE_ALARM`）を実行すると、`user_roles` 行と `user_permission_groups` 行が**再作成され**、`archived_membership_grants` の `restored_at` が埋まり、AC-201/AC-202 の判定が **`true` に戻る**
- **AC-504（冪等）**: 取消を 2 回連続で実行しても、`user_roles` / `user_permission_groups` に**重複行ができない**
- **AC-505**: `ResidentMapper#toResidentResponse` / `#toResidentResponseList` の呼出元が **ロール認識 assembler の 1 クラスのみ**であることを ArchUnit で検証する（§6.5.2）
- **AC-506**: 他ユーザーが既に同じスコープの ADMIN である状態で復元しても、**両者が ADMIN になる**（復元が競合で失敗しない。§9.3.3）
- **AC-507**: 既に自動退会済みのユーザーについて記録を取り消すと、①台帳は訂正される ②`memberships.left_at` は**そのまま**（所属は復活しない）③レスポンスの `alreadyWithdrawn` が `true` ④`archived_membership_grants` の `restored_at` は**埋まらない**（§9.4.2）
- **AC-508**: 唯一の ADMIN をアーカイブ移行させると、**移行は成功し（200）**、レスポンスの `lastAdminWarning` が `true` になる。**409 で阻止されない**（§9.3.4）

#### 同意書の失効（§9.5）

- **AC-401**: アーカイブ移行の成功時、当該ユーザーの代理入力同意書がすべて `status="REVOKED"` かつ `revokeMethod="AUTO_BY_LIFE_EVENT"` になり、**レスポンスの `revokedConsentCount` が実際の件数と一致する**
  - ※ **同期呼出のため Awaitility は不要である。** 旧方式は `@Async` だったため bounded polling が要ったが、新方式は同一トランザクションで完結する
- **AC-402（組合またぎ）**: **2 つの組織それぞれに `resident_registry` 行を持つユーザー**について、組織 A で逝去を記録すると、**組織 B に紐づく同意書も失効する**（§3.4 の受容を固定する）
- **AC-403（ロールバック）**: アーカイブ移行のトランザクション内で**後続処理に例外を発生させる**と、①`resident_registry` が更新されていない ②`memberships.archived_at` が NULL のまま ③**同意書が失効していない** — の 3 点がすべて成り立つ
  - ※ 同期・同一トランザクションであることの検証。旧方式が outbox まで動員して解こうとした問題が、この 1 本の AC に収まった
- **AC-404**: 取消を実行しても、失効した同意書は **失効したまま**である（§3.3 の非可逆性）

#### 自動退会バッチ（§9.6）

- **AC-601**: `archive_expires_at <= NOW()` かつ `left_at IS NULL` のアーカイブ在籍行に対しバッチを実行すると、`left_at` が確定し、`leave_reason` が **`DECEASED` / `RELOCATED`**（`archive_reason` に対応）、`left_trigger='AUTO_ARCHIVE_EXPIRY'`、`left_by IS NULL` になる
  - ※ **`leave_reason='REMOVED'` を書く実装では red になる。** 既存の `leaveByUserAndScope` は `REMOVED` をハードコードしているため、そのまま流用すると green にならない（**実装ゼロで green を避けるための条件設定**）
- **AC-602（人による退会との区別・マスター要件）**: 理事が手動で退会させた行は `left_trigger='MANUAL'` かつ `left_by` が操作者 ID になり、**AC-601 の自動退会行と機械的に区別できる**
  - ※ **`left_by IS NULL` だけでは区別できない。** 実測で `removedBy=null` は自主退会（SELF）とシステム purge でも使われている（§5.2.2）。この AC は `left_trigger` 列の存在意義そのものを固定する
- **AC-603（冪等）**: バッチを 2 回連続で実行しても、2 回目の処理件数が **0 件**であり、`left_at` が上書きされない
- **AC-604**: `archive_expires_at` が未来の行は**対象にならない**
- **AC-605**: `archived_at` が NULL の通常在籍行は**対象にならない**
- **AC-606（失敗の分離）**: 対象 3 行のうち 1 行で例外が起きても、**残り 2 行は退会が確定する**（1 行 1 トランザクション）。かつ失敗した行は `left_at` が NULL のまま残り、**次回実行で再試行される**
- **AC-607**: 自動退会後、当該ユーザーは在籍列挙から**外れる**（`findTeamIdsByUserId` / `findOrganizationIdsByUserId` に当該スコープが現れない）。かつ fan-out 配信の宛先からも外れる
  - ※ AC-215（アーカイブ中は宛先に**含まれる**）と対をなす。**アーカイブ中と退会後で挙動が変わること**を固定する
- **AC-608**: バッチクラスが `@BatchEndpoint` と `@SchedulerLock`（`lockAtMostFor` 明示）を持つ（番人 `ScheduledBatchGuardTest` が緑であること）

#### 一覧・DTO（§6.3・§6.5）

- **AC-701（重要）**: アーカイブ在籍者が**通常の組合員一覧 `GET /{slug}/members` に現れない**
  - ※ **何もしなければ現れる。** `findByScopeAndActive` は `left_at IS NULL` しか見ないため（実測）、アーカイブ在籍者（`left_at` は NULL）は通過してしまう。`archived_at IS NULL` の追加が必要

- **AC-703（制約の非対称を固定）**: `left_at IS NULL AND left_trigger IS NOT NULL` の INSERT が **CHECK 制約で拒否される**。一方、**`left_at IS NOT NULL AND left_trigger IS NULL`（本機能導入前の既存行に相当）は許可される**

- **AC-705b（一般メンバー向け）**: 一般メンバーが同じ居住者一覧を取得すると、**フィールドは存在するが `deathStatus` / `archived` がすべて `null`** である
  - ※ AC-705 と AC-705b は**対で成立して初めて番人になる**（片方だけでは、両方が壊れて常に `null` を返す場合に偽 green になる）
- **AC-705c（本人向け）**: `death_status='SUSPECTED'` の居住者**本人**が `GET /api/v1/users/me/resident-info` を呼ぶと、`deathStatus` が **`null`** で返る（**`"SUSPECTED"` が返ってはならない**。§6.5.2）

#### 17.3.1 同意書失効の観測点（**FE には無い**）

**正直に記す: 代理入力同意書の失効を確認できる FE 画面は存在しない。** 実測: FE で `proxy_input_consents` を扱うのは `admin/proxy-desk.vue` → `ProxyInputDeskPanel.vue` → `ProxyConsentListItem.vue` のみで、これは「代理者である自分が使える同意書を選ぶ」ピッカーであり（`getActiveConsents()`）、**失効済みはそもそも一覧に出ない**。`useProxyInputApi.ts` の `getConsentsByOrg` / `approveConsent` / `revokeConsent` / `getRecords` は **4 本とも呼出元がゼロ**である。

```
GET /api/v1/organizations/{orgId}/proxy-input-consents   （ADMIN以上）
→ data[].status == "REVOKED" かつ data[].revokeMethod == "AUTO_BY_LIFE_EVENT"
```

### 17.4 「実装ゼロで green になる AC」の自己総ざらい

## 19. 方式転換に伴う判断

### 19.1 CMP-053 の根治は不要になった（D-1 の結論）

**結論: この欠陥は新方式では到達不能になる。**

| 判断対象 | 結論 | 根拠 |

### 19.2 outbox は不要になった（D-2 の結論）

**結論: outbox・照合バッチ・冪等 consumer のいずれも作らない。**

| 旧方式で必要だった理由 | 新方式でどう消えたか |
|---|---|
| 同意書失効が `@Async` のプロセス内イベント配送に依存し、commit 後の停止で**消失しうる**ため、配送を永続化する必要があった | **同期・同一トランザクションで呼ぶ**（§9.5）。配送という概念が無くなった。実測で `revokeAllForUser` が `@Transactional` かつ冪等であり、そのまま呼べる |
| 消失を検知するため日次の照合バッチが要った | **消失しない**ため不要 |
| 自動退会の配送保証 | **状態から毎回導出する**方式（`archive_expires_at <= NOW() AND left_at IS NULL`）にしたため、配送も永続キューも不要（§9.6.3）|

**トレードオフの明示**: 同期化により、同意書失効が**業務トランザクションを巻き込む**。すなわち `revokeAllForUser` が失敗すればアーカイブ移行も失敗する。

**これを受容する。** 根拠は 3 点。

1. **同じトランザクションで失敗するほうが正しい。** 「アーカイブしたのに同意書が失効していない」状態を作らない
2. **失効対象は当該ユーザーの同意書のみ**であり、件数は現実的に数件〜数十件である。長大なトランザクションにならない
3. 失敗すれば理事の画面にエラーが出て**再実行できる**。旧方式の「静かに失われる」より遥かに扱いやすい

### 19.3 3 巡の検分で得た知見のうち、新方式でも有効なもの（D-3 の結論）

**残した観点**（§17.1 と §17.4 に適用済み）:

| 観点 | 新方式での適用先 |
|---|---|
| **実装ゼロで green になる AC を作らない** | §17.4 で全 AC を自己点検し 4 件を書き換えた |
| **既存経路が既に満たしている条件を AC にしない** | AC-601 / AC-602 / AC-706 |
| **原理的に成立しない AC を書かない** | AC-403 の書き方を点検した |
| **対で成立して初めて番人になる AC を明示する** | AC-201↔AC-211、AC-705↔AC-705b、AC-215↔AC-607 |
| **状態はフィクスチャで直接作らず API を通して作る** | 全 AC に適用 |
| **経路ごとに AC を分け、1 本に畳まない** | AC-201〜209（§8.2 の 8 経路を個別に測る）|
| **監査ログは非同期で欠落しうるため、要件の担保をそこに依存させない** | §3.5（INV-3）・§5.2・§10 |

**不要になった知見**（旧方式固有・削除した）:

- キャッシュ evict 失敗時の fail-open 対策（`LoggingCacheErrorHandler` / `AUTHZ_RISK_SUFFIX`）→ **関門を置かないため無関係**。§9.3.2 に「evict 失敗は最大 5 分の遅延にとどまる」とだけ残した
- `users` 行の悲観ロックと locking read によるライフイベント更新の直列化 → **`users.status` を書かないため不要**
- `users.status` の再計算規則・運営 status からの戻り経路（`restoreToActive`）→ **同上**
- 非キャッシュ status ゲートと迂回路の棚卸し → **§8 の「権限の源泉を消す」に置き換わった**
