## 1. 概要

### 1.1 解決する問題

住民（区分所有者・居住者）が **逝去** または **転出** したとき、システムには次の3つの穴がある。

| # | 穴 | 実測の根拠 |
|---|---|---|
| P-1 | **札を立てる人間の操作点が存在しない** | `UserEntity#changeStatus`（`backend/src/main/java/com/mannschaft/app/auth/entity/UserEntity.java:314`）に `DECEASED`/`RELOCATED` を渡す呼出元がゼロ。`UserStatusChangedEvent`（`auth/event/UserStatusChangedEvent.java`）の publish 元もゼロ |
| P-2 | **受信側だけが完成していて宙吊り** | `ProxyConsentLifeEventJob`（`proxy/batch/ProxyConsentLifeEventJob.java:25-39`）は `LIFE_EVENT_STATUSES = Set.of(UserStatus.DECEASED, UserStatus.RELOCATED)` を `@EventListener` で受け、`ProxyConsentLifecycleService#revokeAllForUser` により当該ユーザの全代理入力同意書を `RevokeMethod.AUTO_BY_LIFE_EVENT` で失効させる。**発火元が無いので一度も動いたことがない** |
| P-3 | **札が立つと本人の画面が白紙になる（CMP-050 の副作用）** | CMP-050 で `UserRoleRepository` の在籍プリミティブ4本に `u.status = 'ACTIVE'` を課したため、`RELOCATED`/`DECEASED` のユーザーは在籍集合が空になる。ログインは通る（`AuthService:187-197` が拒否するのは `PENDING_VERIFICATION` と `FROZEN` のみ）のに、ログイン後に何も見えない。これが CMP-053 |

住民台帳側にも対になる穴がある。`resident_registry.death_status` は 4 値（`ALIVE`/`SUSPECTED`/`CONFIRMED`/`CANCELLED_FALSE_ALARM`、`V9.102`）まで DDL・Entity・Enum が揃っているのに、**書き手は `ResidentRegistryService#markDeathSuspected`（:243-258）の 1 箇所だけ**で、これは `DelinquencyEscalationService#advanceStage` の D+120 自動起票から `SUSPECTED` を立てるためのものである。**人が `CONFIRMED` に確定させる本番経路が無い。** F09.15 自身がこれを認めている（同書 L607-614: 手動入力 API は v2 送り）。

本設計はこの 2 つの空箱を 1 本の線で繋ぐ。

#### 1.2.1 F09.15 §9.5 との整合（衝突ではない）

F09.15 §9.5 は次のように書く。

> `death_status = CONFIRMED` への遷移単独では封緘解除されない。**独立した二者承認プロセス** が必須。これにより、死亡誤確認時に取り消し（`CANCELLED_FALSE_ALARM`）すれば封緘は無傷で守られる。

本設計はこれを **破らない**。本設計が `CONFIRMED` 遷移に自動で連動させるのは以下の 2 つだけである。

- `users.status` → `DECEASED`（可逆。§9.2 で取り消せる）
- 代理入力同意書の失効（**不可逆**。§3.1）

**封緘（`succession_pre_registrations` / `unseal_requests`）には一切触れない。** 二者承認は F09.15 の管轄のまま残る。設計書に「自動で連動するのはこの 2 つだけ」と明記し、実装時に第3の連動を足さないことを ArchUnit ではなく §17 のテストで固定する。

## 3. 中核原則

### 3.1 自動と人の分離（本設計の中核）

```
理事の操作（1回）
        │
        ├─── 自動 ────► users.status = DECEASED / RELOCATED
        │                       │
        │                       └─► UserStatusChangedEvent
        │                               │
        │                               └─► ProxyConsentLifeEventJob
        │                                       └─► 代理入力同意書を全件失効
        │                                            （AUTO_BY_LIFE_EVENT・不可逆）
        │
        ├─── 自動 ────► 監査ログ1件（§10）
        │
        ├─── 自動 ────► 理事へ通知1通（§11.1）
        │
        └─── 自動 ────► 住民一覧に「要対応」バッジ（§11.2）
                                │
                                ▼
                        理事が見て、判断して、明示的に
                                │
                                ▼
                          所属解除（別操作・§9.3）
```

**同意書の失効は自動、所属の解除は人（理事）が行う。** この分離が本設計の中核である。理由は非対称なリスクにある。

- 同意書が失効し続けても誰も困らない（代理入力ができなくなるだけで、再度取り直せる）。逆に、逝去した人の名義で代理入力が通り続ける方が危険である。よって **自動・即時・不可逆** にする。
- 所属を自動で終わらせると、誤登録のとき本人の予定・請求・履歴の見え方が一斉に消え、復旧が難しい。よって **人が見て判断する**。

#### 3.1.1 不可逆性（マスター方針2）

**札を取り消しても、失効した同意書は復活しない。** `ProxyConsentLifecycleService#revokeAllForUser` は失効を記録するだけで、逆操作を持たない。本設計はこれに逆操作を足さない（履歴の改竄になるため）。

したがって UI は札付与の確認ダイアログで **「この操作を取り消しても、失効した代理入力同意書は元に戻りません。再取得が必要です」** と明示する（§12.3、i18n キー `proxy.lifeEvent.confirm.irreversibleWarning`）。

### 3.2 不変条件

本設計が守る不変条件を、正確な形で述べる。CMP-050 の議論では「ログインできる ＝ 在籍を持てる」と粗く語られていたが、これでは `PENDING_PARENTAL_CONSENT` を取り逃す。

> **INV-1**: ユーザーが在籍集合（`findTeamIdsByUserId` 等）に現れてよいのは、**ログインが通り、かつログイン後のゲートで保護 API を遮断されない状態** のときに限る。

`PENDING_PARENTAL_CONSENT` は `AuthService` がログインを通す（拒否対象は `PENDING_VERIFICATION`・`FROZEN` の2つのみ、`AuthService:188-197`）が、`ParentalConsentGateFilter` が許可リスト外の保護 API を 403 `AUTH_070` で遮断する（`config/ParentalConsentGateFilter.java:27,52-68`）。在籍を持たせても使えないため、在籍を持たせない。

> **INV-2**: 札（`DECEASED`/`RELOCATED`）は所属を終わらせない。所属の終わりは `memberships.left_at` / `user_roles` の行の消滅によってのみ表現される。

> **INV-3**: 札の付与・取消・所属解除のいずれも、監査ログを 1 件残さずに完了してはならない。

> **INV-4**: 台帳（`resident_registry`）とアカウント（`users.status`）は 1 対 N である。伝播規則は §4.2 に定める。

### 3.3 本人の画面は白紙にならない（マスター方針5）

札が立っている間も、本人は

- ログインできる（`AuthService` は `DECEASED`/`RELOCATED` を拒否しない）
- 自分の所属組合／チームが見える（§8 の緩和による）
- 自分の予定・請求が見える
- ただし代理入力の同意書は失効している（§3.1）

「転出」は住所変更ではなく「そのマンションから転出した＝居住者でなくなった」の意である。区分所有者としての権利・未精算の請求・過去の議事録閲覧は転出後も続きうる。よって **所属を終わらせる意図の状態ではない**。この解釈は `docs/task-list.md` の CMP-053 の記述と一致する。

## 4. 状態モデル

### 4.1 `users.status` 状態機械

現行 7 値（`auth/entity/UserEntity.java:261-272`、DB CHECK は `V18.014` + `V18.033` で 7 値済み）。

```
                         ┌──────────────────────┐
                         │ PENDING_VERIFICATION │
                         └──────────┬───────────┘
                                    │ メール確認
              ┌─────────────────────┴──────────────────┐
              │                                        │
   ┌──────────▼───────────────┐              ┌─────────▼────────┐
   │ PENDING_PARENTAL_CONSENT │──保護者同意──►│      ACTIVE      │
   └──────────────────────────┘              └───┬───┬───┬──────┘
                                                 │   │   │
                     ┌───────────────────────────┘   │   └────────────┐
                     │ 本設計 §9.1                    │ 運営            │ 長期未ログイン
                     │ （理事の札付与）                 │                │
          ┌──────────▼──────────┐          ┌─────────▼──────┐  ┌──────▼─────┐
          │ DECEASED / RELOCATED│          │     FROZEN     │  │  ARCHIVED  │
          └──────────┬──────────┘          └────────────────┘  └──────┬─────┘
                     │ 本設計 §9.2                                     │ ログイン時
                     │ （理事の札取消・可逆）                            │ 自動復帰
                     └───────────────► ACTIVE ◄───────────────────────┘
```

**遷移可否表**（本設計が新設・許可する遷移のみ。他ドメインの既存遷移は変更しない）

| From | To | 可否 | 実行者 | 備考 |
|---|---|---|---|---|
| `ACTIVE` | `DECEASED` | ✅ | 理事（ADMIN以上） | §9.1。台帳 `death_status = CONFIRMED` に連動 |
| `ACTIVE` | `RELOCATED` | ✅ | 理事（ADMIN以上） | §9.1。台帳 `move_out_date` 設定に連動 |
| `DECEASED` | `ACTIVE` | ✅ | 理事（ADMIN以上） | §9.2。同意書は復活しない |
| `RELOCATED` | `ACTIVE` | ✅ | 理事（ADMIN以上） | §9.2。同上 |
| `DECEASED` | `RELOCATED` | ❌ | — | 直接遷移させない。いったん `ACTIVE` に戻してから付け直す（監査ログを2件残し、意図を追跡可能にするため） |
| `RELOCATED` | `DECEASED` | ❌ | — | 同上 |
| `FROZEN` | `DECEASED`/`RELOCATED` | ❌ | — | 凍結は運営の判断。理事が上書きできてはならない。`RESIDENT_014` を返す |
| `PENDING_VERIFICATION` / `PENDING_PARENTAL_CONSENT` | `DECEASED`/`RELOCATED` | ❌ | — | 未確立のアカウントに札を立てる意味がない。`RESIDENT_014` |
| `ARCHIVED` | `DECEASED`/`RELOCATED` | ❌ | — | `ARCHIVED` はログイン時に自動 `ACTIVE` 復帰するため、札を立てても次のログインで消える。`RESIDENT_014` |
| `DECEASED`/`RELOCATED` | `FROZEN` 等 | ✅（既存経路） | 運営 | 本設計は妨げない |

> ⚠️ **`users.deleted_at` が非 NULL（退会済み）のユーザーには札を立てない**。退会は §1 の匿名化フローの管轄であり、札は無意味である。`RESIDENT_013`（居住者にアカウントが紐づいていない／対象外）を返す。

### 4.2 `resident_registry` との対応表

`resident_registry.user_id` は **NULL 可**（`V9.017`）。アカウントを持たない居住者（F14.1 が対象とするオフライン住民の一部、および同居家族）が存在する。また 1 ユーザーが複数居室・共有持分で **複数行**を持ちうる（F09.15 L894 が明示）。

| 台帳側の事実 | アカウント側への伝播 | 条件 |
|---|---|---|
| `death_status: ALIVE → CONFIRMED` | `users.status → DECEASED` | `user_id IS NOT NULL` かつ `users.deleted_at IS NULL` かつ現 status が `ACTIVE` |
| `death_status: CONFIRMED → CANCELLED_FALSE_ALARM` | `users.status → ACTIVE` | 現 status が `DECEASED` のときのみ（他の理由で FROZEN 等になっていたら触らない） |
| `death_status: ALIVE → SUSPECTED`（自動起票） | **伝播しない** | 疑いは判断ではない。§9.1 の対象外 |
| `move_out_date: NULL → 日付` | `users.status → RELOCATED` | 上記に加えて、**当該ユーザーの当該スコープ内の他の `resident_registry` 行がすべて `move_out_date` 非 NULL であること**（下記 R-1） |
| `move_out_date: 日付 → NULL`（転出取消） | `users.status → ACTIVE` | 現 status が `RELOCATED` のときのみ |

**R-1（転出の粒度規則）**: 逝去は人に属する事実なので 1 行でも `CONFIRMED` なら人が逝去している。一方、転出は住戸に属する事実であり、**2 号室から転出しても 5 号室に住み続けているなら転出していない**。よって `RELOCATED` の付与は「当該ユーザーに紐づく `deleted_at IS NULL` の `resident_registry` 行がすべて `move_out_date` 非 NULL」を満たしたときに限る。満たさない場合、台帳の `move_out_date` は設定するが `users.status` は変えない（API はその旨を `userStatusChanged: false` で返す。§6.2）。

**R-2（逝去の粒度規則）**: 逆に、逝去の取消（`CANCELLED_FALSE_ALARM`）で `ACTIVE` に戻すのは、**当該ユーザーに紐づくどの行も `CONFIRMED` でなくなったとき**に限る。

### 4.3 `memberships` との独立性

`memberships` / `user_roles` は札を**一切参照しない**。所属が終わるのは §9.3 の明示操作のみ。

| 札 | 所属 | 意味 | 一覧での表示 |
|---|---|---|---|
| なし | あり | 通常の居住者 | — |
| **あり** | **あり** | **要対応**（理事の判断待ち） | 🔴 バッジ（§11.2）|
| あり | なし | 処理済み | グレー表示 |
| なし | なし | 台帳のみの記録（アカウント連携前など） | — |

## 5. DB 設計

### 5.1 結論: 新規テーブル・新規カラムともに **不要**

| 必要な情報 | 既存の置き場所 | 根拠 |
|---|---|---|
| 逝去したか | `resident_registry.death_status` | `V9.102`。Entity `ResidentRegistryEntity:108-111`、Enum `resident/entity/DeathStatus.java` |
| いつ・誰が逝去の札を立てたか | `death_status_changed_at` / `death_status_changed_by` | `V9.102`。`updateDeathStatus(DeathStatus, Long changedBy)`（Entity:155）が両方を更新 |
| 転出したか・いつ転出したか | `resident_registry.move_out_date` | `V9.017`。`moveOut(LocalDate)`（Entity:229）|
| **なぜ**（理由） | `audit_logs.metadata`（JSON） | §10 |
| 取消の履歴 | `audit_logs`（付与1件・取消1件が時系列で残る） | §10 |
| 誰が所属解除したか | `memberships.left_at` / `leave_reason` / `MembershipChangedEvent` + `audit_logs` | 既存 |

`resident_registry` は BIGINT 主キーを維持する。`V9.102` / `V9.103` の冒頭コメントが前例として明記している。

> `-- F09.1 と同一ドメイン内の拡張であり、主キーは BIGINT を維持する（UUIDv7 化はしない）。`

CLAUDE.md「アーキテクチャ思想」6 の UUIDv7 原則は **新規テーブルを作る場合にのみ**適用される。本設計は新規テーブルを作らないため、この原則に抵触しない。

### 5.2 転出専用カラム（`relocated_at` / `relocated_reason`）は追加しない

家老の偵察指示では追加要否の判断を求められたが、**追加不要**と結論する。

- `relocated_at` は **`move_out_date` が既にある**。しかも `PATCH /residents/{id}/move-out` という API と `ResidentRegistryService#moveOut(Long, Long, LocalDate)`（:158-176）、`ResidentErrorCode.ALREADY_MOVED_OUT`（`RESIDENT_008`）まで実装済みで、`dwelling_units.resident_count` のデクリメントまで面倒を見ている。ここに `users.status` 伝播を足すのが最小の改修である。
- `relocated_reason` は `audit_logs.metadata` に載せる。理由は自由記述であり、検索・集計の要件が現時点で存在しない。列にすると `death_status` 側にも対称の理由列を求められ、2 列増えて両方 NULL のまま残る公算が高い。

### 5.3 `occupancy_status` で転出を代替できるか → できない

F09.16 が所有する `occupancy_status`（`OWNER_OCCUPIED`/`RENTED_OUT`/`VACANT`/`SECONDARY_HOME`/`UNKNOWN`、`V9.103`）は **住戸の使われ方**を表す。「その住戸は今どう使われているか」であって「この人はもうここに住んでいないか」ではない。

- `RENTED_OUT` は区分所有者が住んでいないが**組合員のまま**の状態であり、F09.16 L612 が「賃貸化済み居住者の年次更新は区分所有者本人に通知」と明示している。これを転出と混同すると、賃貸に出しただけの区分所有者に `RELOCATED` が立ち、代理入力同意書が失効する。
- `VACANT` は誰も住んでいない住戸であり、人の状態ではない。

よって **転出は `move_out_date` を正本とし、`occupancy_status` は触らない**。ただし §19 U-2 に、転出処理後に住戸が空になった場合の `occupancy_status` 自動更新の要否を残す。

### 5.4 `memberships.leave_reason` の ENUM 拡張（**要 Flyway**）

`LeaveReason` は現在 `SELF`/`REMOVED`/`GDPR`/`TRANSFER`/`OTHER`（`membership/domain/LeaveReason.java`）。逝去・転出に相当する値が無い。

**結論: `DECEASED` と `RELOCATED` の 2 値を追加する。**

- 追加しないと §9.3 の所属解除がすべて `REMOVED`（＝理事が追い出した）に畳まれ、退会統計・GDPR 対応・将来の再入居導線で区別できなくなる。
- **家老の偵察の前提を1点訂正する**: DB CHECK `chk_memberships_left_reason`（`V60.001__create_memberships_table.sql:39-42`）は値を列挙していない。実体は「`left_at` と `leave_reason` が同時に NULL か同時に非 NULL か」の対応検査のみである。

```sql
CONSTRAINT chk_memberships_left_reason CHECK (
    (left_at IS NULL AND leave_reason IS NULL)
    OR (left_at IS NOT NULL AND leave_reason IS NOT NULL)
),
```

  値を列挙しているのは **カラム定義側の MySQL ENUM**（同ファイル L31）である。

```sql
leave_reason ENUM('SELF','REMOVED','GDPR','TRANSFER','OTHER') NULL,
```

  したがって **CHECK 制約は変更不要。`MODIFY COLUMN` で ENUM 定義だけを拡張する**（§14）。

存在秘匿も既存に合わせる。他スコープの `residentId` を指定した場合は 403 ではなく **`RESIDENT_003`（居住者が見つかりません・404）** に畳む。これにより「そのIDは存在するが権限が無い」という差分が観測できない。

## 8. CMP-050 在籍条件の緩和

### 8.1 許容集合と各 status の根拠

現行は `u.deleted_at IS NULL AND u.status = 'ACTIVE'`。これを **許容集合方式**に変える。

```sql
u.deleted_at IS NULL AND u.status IN ('ACTIVE','RELOCATED','DECEASED')
```

| status | 在籍を持てるか | 根拠 |
|---|---|---|
| `ACTIVE` | ✅ 許容 | 自明 |
| `RELOCATED` | ✅ **許容** | `AuthService:188-197` はログインを拒否しない。ゲートフィルタも通す。マスター方針5により所属は残る。**CMP-053 の根治そのもの** |
| `DECEASED` | ✅ **許容** | 同上。逝去直後の未精算請求・遺族による確認導線のため、理事が明示的に所属解除するまで在籍は残る |
| `ARCHIVED` | ❌ 不許容 | ログイン時に自動 `ACTIVE` 復帰するため、在籍を持たせなくても実害が出ない（次のログインで `ACTIVE` になり在籍が戻る）。ガードテスト AC-9（`ac9_ARCHIVEDユーザーも4メソッドすべて非所属`、:383）が名指しで守っている |
| `FROZEN` | ❌ 不許容 | `AuthService:193-196` が `AUTH_003` でログイン拒否。**CMP-050 の元凶**（凍結 ADMIN へのオーナー譲渡によるロックアウト）を直接防ぐ条件であり、緩めてはならない |
| `PENDING_VERIFICATION` | ❌ 不許容 | `AuthService:188-191` が `AUTH_002` でログイン拒否 |
| `PENDING_PARENTAL_CONSENT` | ❌ 不許容 | `AuthService` はログインを通すが、`ParentalConsentGateFilter` が許可リスト外の保護 API を 403 `AUTH_070` で遮断する（`ParentalConsentGateFilter.java:27,52-68`）。**在籍を持っても使えない**。INV-1 の精緻化はこの 1 値のために必要である |

**実装上の注意**: 許容集合は 4 本のクエリ（うち 2 本は UNION の両枝、計 8 箇所）に散らばる。文字列リテラルを 8 回書くとドリフトする。`UserRoleRepository` に定数として集約する（native query の文字列連結内で参照可能な `private static final String` は使えないため、インタフェースの `String` 定数 + 連結で表現するか、8 箇所を 1 つの `@Query` 断片テンプレートとして切り出す）。§17 に「8 箇所すべてが同一集合であること」を検証するテストを置く。

### 8.3 `MembershipRepository` の同時改修（2系統の食い違いを本設計の射程で潰す）

`MembershipRepository.findActiveByUserAndScopeType`（`membership/repository/MembershipRepository.java:138-143`）は JPQL で `leftAt IS NULL` のみを見ており、**`users.status` を一切見ない**。

```java
@Query("SELECT m FROM MembershipEntity m " +
        "WHERE m.userId = :userId AND m.scopeType = :scopeType AND m.leftAt IS NULL " +
        "ORDER BY m.joinedAt DESC")
```

これを `MembershipService#getActiveTeamIdsByUser`（:378）/ `#getActiveOrgIdsByUser`（:408）が使うため、同一ユーザーの在籍集合が **画面ごとに食い違う**（`UserRoleRepository` 系は ACTIVE 必須・呼出元53ファイル / `MembershipService` 系は ACTIVE 不問・呼出元13ファイル）。

**本設計はこの食い違いを、統合ではなく「同じ許容集合を両系統に課す」ことで潰す。** `MembershipEntity` は `userId` を持つだけで `UserEntity` への関連を持たないため、JPQL のままでは users に結合できない。同ファイル内の native query 化、または `EXISTS` サブクエリを持つ新メソッドを追加して `MembershipService` の 2 メソッドをそちらへ向ける。

改修後、両系統は「`FROZEN`・`PENDING_*`・`ARCHIVED`・論理削除を除外し、`ACTIVE`/`RELOCATED`/`DECEASED` を含む」で一致する。これで **RELOCATED/DECEASED に関する食い違いは解消する**。

> ⚠️ **`MembershipRepository` 側の改修は本設計で最も危険な箇所である。** これまで `users.status` を見ていなかったので、`FROZEN` ユーザーが `getActiveTeamIdsByUser` に現れていた。改修により **現れなくなる**（これは CMP-050 の意図どおりの是正だが、13 呼出元の挙動が変わる）。§16 で Phase を分け、§17 で 13 呼出元それぞれの回帰を確認する。

### 8.6 射程外: 2系統統合の段階移行（骨子のみ）

## 9. ビジネスロジック

### 9.1 札付与

配置先: `ResidentRegistryService`（住民台帳ドメイン）。ただし `users.status` の更新は **`auth` ドメインの Service 経由**で行う（CLAUDE.md「アーキテクチャ思想」5: `@Transactional` はドメイン内に閉じる。越境時はコメントで理由明記）。

**フロー（逝去・`CONFIRMED`）**

1. `residentRepository.findById(id)` → 無ければ `RESIDENT_003`
2. `checkAdminForResident(actorUserId, entity)`（entity 由来の scopeId で BOLA 対策）
3. 遷移可否検査: 現 `death_status` が `CONFIRMED` なら `RESIDENT_012`（既に札あり・409）
4. `entity.updateDeathStatus(DeathStatus.CONFIRMED, actorUserId)` → `save`
5. `user_id` が NULL なら以降をスキップ（`userStatusChanged: false` を返す）
6. `users.status` の現在値を検査。`ACTIVE` 以外なら **札は台帳にだけ立て、`users.status` は変えない**。`FROZEN`/`ARCHIVED`/`PENDING_*` の場合は `RESIDENT_014`（§4.1）を返して **手順4もロールバックする**（台帳とアカウントが乖離した状態を作らない）
7. `auth` ドメインの Service に `changeStatus(userId, DECEASED)` を依頼。この中で `UserStatusChangedEvent` を publish（§9.4）
8. 監査ログ（§10）
9. 理事へ通知1通（§11.1）

**転出（`move-out`）** は §4.2 R-1 の粒度規則が追加される点だけが異なる。手順6の前に「当該ユーザーの他の `resident_registry` 行がすべて `move_out_date` 非 NULL か」を確認し、満たさなければ手順7〜9をスキップして `userStatusChanged: false` で返す（台帳の `move_out_date` は設定する）。

> **トランザクション境界**: 手順4（台帳）と手順7（アカウント）は別ドメインである。単一トランザクションで括ると D-3 の越境トランザクション負債（凍結ストア6298件）を増やす。**同一トランザクションに括る**ことを選ぶ（台帳とアカウントが乖離した状態を残さないことを優先する）。越境理由をコード上のコメントに明記し、D-3 baseline に 1 件追加する。この判断の代替案（アカウント側を非同期にして結果整合にする）は §19 U-1 に残す。

### 9.2 札取消

1〜3 は §9.1 と同じ（現 `death_status` が `CONFIRMED` **でない**なら `RESIDENT_012`）
4. `entity.updateDeathStatus(DeathStatus.CANCELLED_FALSE_ALARM, actorUserId)`
5. §4.2 R-2 の規則で、当該ユーザーのどの行も `CONFIRMED` でなくなったかを確認
6. `users.status` が **`DECEASED` のときのみ** `ACTIVE` に戻す。それ以外（運営が別途 `FROZEN` にした等）は触らない
7. 監査ログ `DEATH_STATUS_CHANGED_TO_CANCELLED`
8. **同意書は復活させない**（§3.1.1）。通知は出さない（要対応バッジが消えるだけ）

転出取消（`move-out/cancel`）も同型。`move_out_date` を NULL に戻し、`unit.incrementResidentCount()`（`moveOut` の `decrementResidentCount` と対称）を呼ぶ。

### 9.3 所属解除

1〜2 は §9.1 と同じ。ただし認可は **ADMIN のみ**（§7）
3. 札が立っていること（`death_status = CONFIRMED` または `move_out_date` 非 NULL）を確認。立っていなければ `RESIDENT_012`
4. `confirmToken` と現在の札種別が一致することを確認。不一致なら `RESIDENT_015`（§6.3）
5. `MembershipService#leaveByUserAndScope(userId, unit.getScopeType(), unit.resolveScopeId(), leaveReason, actorUserId)` を呼ぶ
   - `leaveReason` は札の種別により `LeaveReason.DECEASED` / `LeaveReason.RELOCATED`（§5.4 で追加）
   - このメソッドが `left_at` / `leave_reason` の確定、現役役職の自動離任、`MembershipChangedEvent(REMOVED)` の発火まで担う。**本設計はここに何も足さない**
   - 戻り値 `false`（活動中の membership が無い）は正常系。`released: false` で 200 を返す
6. 監査ログ: `AuditEventType.ORGANIZATION_MEMBER_REMOVED` または `TEAM_MEMBER_REMOVED`（スコープにより選択。§10）

> **`user_roles` 行の扱い**: `leaveByUserAndScope` は membership 側を処理する。`user_roles` に残る行がある場合、§8.1 の許容集合が `DECEASED` を含むため在籍が残り続ける。`leaveByUserAndScope` が「現役役職の自動離任」を担うことは確認済みだが、それが `user_roles` 行の削除まで及ぶか、`memberships` に紐づく役職のみかは**未確認**。§19 U-5 に残し、実装時に必ず実測して確認すること。

### 9.4 `UserStatusChangedEvent` 発火点の確定

現状 publish 元ゼロ。本設計で **唯一の発火点**を決める。

- 発火するのは **`auth` ドメインのユーザーステータス変更 Service 1 箇所のみ**。`UserEntity#changeStatus(UserStatus)` は Entity のセッタであり、イベントを持たない（持たせない。Entity からイベントを飛ばすと発火点が散る）
- 呼出元は §9.1 / §9.2 の 2 経路（および将来の運営操作）
- イベントのフィールドは既存のまま `(Object source, Long userId, UserStatus oldStatus, UserStatus newStatus)`（`auth/event/UserStatusChangedEvent.java`）。**変更しない**
- `ProxyConsentLifeEventJob` は `@EventListener @Async("event-pool")` で受ける（:30-39）。`@Async` なのでトランザクションの外で走る。`revokeAllForUser(userId, reason)` の `reason` は自由文字列で、ジョブが `"ユーザーステータス変更: " + newStatus.name()` を組み立てる。**この文字列組み立てを本設計で変えない**（既存の失効記録との書式一貫性のため）

> ⚠️ **実装時の落とし穴**: `@Async` かつ非 `@TransactionalEventListener` なので、**§9.1 のトランザクションがロールバックしてもジョブが走ってしまう**可能性がある。§9.1 手順6の `RESIDENT_014` ロールバック経路が該当する。イベント publish を「ステータス変更が確定した後」に置くこと（`@TransactionalEventListener(phase = AFTER_COMMIT)` への変更は F14.1 の受信側契約を変えるため、まず **publish 側でロールバック経路に入らないよう先に検査を済ませる**設計にする。§9.1 の手順順序がそうなっている）。§17 に「ロールバック時に同意書が失効していないこと」の統合テストを置く。

## 10. 監査ログ

書き口: `AuditLogService#record(eventType, userId, targetUserId, teamId, organizationId, ipAddress, userAgent, sessionHash, metadata)`。`@Async` かつ内部で例外を握りつぶす（監査失敗が業務を壊さない）。`eventType` は `String`。

**新しい `AuditEventType` は追加しない。** RESIDENT カテゴリの 4 値が既に予約済みで publish 元ゼロである（`auth/AuditEventType.java:138-142`）。

```java
DEATH_STATUS_CHANGED_TO_SUSPECTED(AuditEventCategory.RESIDENT),
DEATH_STATUS_CHANGED_TO_CONFIRMED(AuditEventCategory.RESIDENT),
DEATH_STATUS_CHANGED_TO_CANCELLED(AuditEventCategory.RESIDENT),
OCCUPANCY_STATUS_CHANGED(AuditEventCategory.RESIDENT),
```

| 本設計の操作 | eventType | 備考 |
|---|---|---|
| 逝去の札 付与 | `AuditEventType.DEATH_STATUS_CHANGED_TO_CONFIRMED.name()` | |
| 逝去の札 取消 | `AuditEventType.DEATH_STATUS_CHANGED_TO_CANCELLED.name()` | |
| （既存バッチの自動起票） | `DEATH_STATUS_CHANGED_TO_SUSPECTED.name()` | `markDeathSuspected` に監査ログを足す（現在は `log.info` のみ）。本設計のついで作業 |
| 転出の札 付与／取消 | `OCCUPANCY_STATUS_CHANGED.name()` | ⚠️ 名前が居住実態区分を指すため意味がずれる。§19 U-6 に「転出専用の `AuditEventType` を1値追加すべきか」を残す。**暫定でこれを使い、metadata の `eventKind` で区別する** |
| 所属解除 | `ORGANIZATION_MEMBER_REMOVED.name()` / `TEAM_MEMBER_REMOVED.name()` | `auth/AuditEventType.java:89` / `:77`。スコープにより選択 |

> `ProxyAuditEventTypes` のような定数クラスを新設して二重定義しないこと。`AuditEventType` の `.name()` を直接渡す。

**metadata（JSON）**

```json
{
  "eventKind": "DEATH_CONFIRMED | DEATH_CANCELLED | RELOCATION_SET | RELOCATION_CANCELLED | MEMBERSHIP_RELEASED",
  "residentRegistryId": 12345,
  "oldStatus": "ALIVE",
  "newStatus": "CONFIRMED",
  "oldUserStatus": "ACTIVE",
  "newUserStatus": "DECEASED",
  "userStatusChanged": true,
  "reason": "理事が入力した自由記述（最大500文字）",
  "leaveReason": "DECEASED"
}
```

- `oldStatus` / `newStatus` は台帳側の値。`oldUserStatus` / `newUserStatus` はアカウント側。両方載せることで、R-1 により台帳だけ変わってアカウントが変わらなかったケースを後から追える
- `reason` は理事の自由記述であり **PII を含みうる**。F09.15 L840 が「監査ログ `DEATH_STATUS_CHANGED` は 10 年保持必須」としているため、保持期間の整合を §13.1 で扱う
- 所属解除の場合は `leaveReason` を載せる

## 13. セキュリティ・プライバシー

### 13.1 死亡情報の開示範囲

逝去の事実は最も強い区分の個人情報であり、遺族の意向にも関わる。

| 相手 | 開示 |
|---|---|
| 当該スコープの ADMIN / DEPUTY_ADMIN | ✅ 台帳上で参照可（既存の住民台帳の閲覧範囲に従う） |
| 同一スコープの一般メンバー | ❌ **不可**。住民一覧 API のレスポンスから `deathStatus` を除く（一般メンバー向けレスポンスに載せない） |
| 本人（アカウント） | ❌ 自分の `users.status` を API で観測できないようにする。`/api/v1/users/me` 系のレスポンスに `status` が含まれていないかを実装時に確認する（§19 U-8） |
| 他スコープ | ❌ §6.4 の存在秘匿により、そもそも `residentId` が観測できない |
| プッシュ通知の本文 | ❌ 氏名・事実を載せない（§11.1） |

`presumed_death_score` は F09.15 が「本人非開示」と定めている（`V9.102` のカラムコメント）。本設計はこの列に触れない。

**保持期間**: F09.15 L840 が監査ログ `DEATH_STATUS_CHANGED` の 10 年保持を要求している。本設計の監査ログはすべて同カテゴリ（`AuditEventCategory.RESIDENT`）に載るため、既存の保持ポリシーに自動的に従う。**新しい保持期間を定義しない。**

### 13.2 札付き本人のログイン継続を許す判断のリスク評価

マスター方針5により、`DECEASED`/`RELOCATED` でも本人はログインでき所属も残る。これは意図的な設計判断であり、リスクは以下のとおり評価した。

| リスク | 評価 | 緩和 |
|---|---|---|
| 逝去したはずのアカウントが使われ続ける | **受容する**。逝去の札は理事の判断であって法的確定ではない。誤登録の可能性が常にあり、誤登録でログインを止めると本人が是正を申し立てる手段まで失う | 代理入力同意書は即時失効するため、**第三者が本人名義で代理入力を通す経路は塞がっている**（§3.1） |
| 遺族が故人のアカウントで組合の情報を閲覧する | **受容する**。区分所有者の権利承継が完了するまで、未精算の請求・議事録の確認は正当な必要性がある | 所属解除（§9.3）を理事が判断して行えるため、必要なら止められる |
| 札が立ったまま長期間放置される | **バッジで継続的に促す**（§11.2） | — |
| `DECEASED` を在籍集合に含めたことで、他の認可判定が緩む | **本設計で最も注意を要する点**。在籍プリミティブ4本は 53 ファイルから呼ばれており、緩和はそのすべてに波及する | §8.4 の AC-13〜AC-17 で不許容集合を機械的に固定する。加えて §17 で「緩和前後で `FROZEN`/`PENDING_*` の挙動が変わらないこと」を全 status 総当たりで検証する |

**認可設計の原則との整合**: 本設計は認可を緩める方向の変更を含む。CMP-050 が締めた条件を一部戻す形になるため、**なぜ戻してよいのかを status ごとに §8.1 の表で明示的に根拠づけている**。表に無い status を後から足す変更は、同じ形式の根拠づけを必須とする。

## 15. エラーコード

**配置先の判断**: `AuthErrorCode`（最大 `AUTH_072`）ではなく **`ResidentErrorCode`**（`backend/src/main/java/com/mannschaft/app/resident/ResidentErrorCode.java`）に置く。

理由: 本設計の操作点はすべて住民台帳ドメインの API（`/residents/{id}/...`）であり、D-1（ドメイン境界）の観点で resident 側が自然である。`AuthErrorCode` に置くと、resident のコントローラが auth のエラーコードを投げる越境依存が生まれる。

**実測**: `ResidentErrorCode` の現在の最大は **`RESIDENT_011`**（`LISTING_NOT_EDITABLE`）。よって新規は `RESIDENT_012` から予約する。

| コード | 定数名 | メッセージ | HTTP | Severity | 用途 |
|---|---|---|---|---|---|
| `RESIDENT_012` | `LIFE_EVENT_STATE_CONFLICT` | 既にこの状態が記録されています | **409** | `WARN` | 札の二重付与／札が無い状態での取消／札が無い状態での所属解除（§9.1〜9.3）。状態競合のため 409（既存 `ALREADY_MOVED_OUT`・`ALREADY_VERIFIED` と同じ扱い） |
| `RESIDENT_013` | `RESIDENT_HAS_NO_ACCOUNT` | この居住者にはアカウントが紐づいていません | **409** | `WARN` | 所属解除の対象に `user_id` が無い／`users.deleted_at` が非 NULL（§4.1 の注記） |
| `RESIDENT_014` | `USER_STATUS_NOT_ELIGIBLE` | 現在のアカウント状態では記録できません | **409** | `WARN` | `FROZEN`/`ARCHIVED`/`PENDING_*` に札を立てようとした（§4.1 の遷移可否表） |
| `RESIDENT_015` | `LIFE_EVENT_CONFIRM_MISMATCH` | 確認内容が現在の状態と一致しません | **409** | `WARN` | `confirmToken` 不一致（§6.3）。画面を開いてから別の理事が状態を変えた場合に該当 |

権限不足は既存 `CommonErrorCode.COMMON_002`（403）。居住者不在・他スコープ越境は既存 `ResidentErrorCode.RESIDENT_003`（404、存在秘匿。§6.4）。

> ⚠️ **採番注記**: `RESIDENT_012`〜`RESIDENT_015` は現在の最大 `RESIDENT_011` + 1 からの予約であり、**確定はマージ時に `origin/main` の `ResidentErrorCode` を再確認して行うこと**（並行セッションが先に採っている可能性がある）。
>
> ⚠️ **ステータス写像**: `ErrorCode` から HTTP ステータスへの写像は `GlobalExceptionHandler` が担う。既存の `RESIDENT_008`（`ALREADY_MOVED_OUT`）が実際に 409 で出ているかを実装時に実測し、同じ経路に乗せること（`Severity.WARN` が一律 400 に落ちる写像になっていないかを確認する）。
