# F06.4.1 データ・状態・同期設計

> **ステータス**: 🟡 仕様裁可待ち（脱退時共有の扱い未確定）
> **最終更新**: 2026-11-08
> **親設計**: [個人の頑張り記録](F06.4.1_personal_effort_records.md)。以下DDLは未適用の案。

## 1. 境界

新規effortrecordドメインだけで原本・定義snapshot・共有projectionを管理する。既存activity/team/user/timelineへの参照はIDとService経由、クロスドメインFKなし。個人側のルーティングはowner_user_id、チーム側はorganization_id。現行単一DBでも両者を同じTXへ入れない。同一effortrecordドメインであっても将来異なるシャードになるため、private→team FKも作らない。

definitionは個人所有にせず、標準プリセットまたはチーム定義の不変snapshot識別用で、TEAMはorganization側、PRESETは共通参照データとして全シャードへ同じUUID/内容を配布する。原本はdefinition JSON自体を保持するため、definition側へJOINしないで本人閲覧・集計可能。snapshot revisionの作成はactivity Serviceから認可済み定義を取得し、非TX Facadeからeffort definition Serviceへ渡す。activityの更新TXを共有しない。

## 2. DDL案

全新規EntityはUuidV7Entity継承、idは真正UUIDv7/BINARY(16)。created_at/updated_at/deleted_atはUTC DATETIME(6)、新規瞬間型はInstant、recorded_onはLocalDate/DATE。@Versionと `@SQLRestriction("deleted_at IS NULL")` を主要表へ適用する。UuidV7Entityの継承フィールドが既存LocalDateTimeなら共通基底を一括変更せず、追加業務時刻はInstantとして対応を明示する。以下のNOT NULLに暗黙の空値defaultは与えない。

```sql
CREATE TABLE effort_definitions (

  KEY idx_effort_definition_team (organization_id, team_id, deleted_at),
  CHECK (source_type IN ('PRESET','TEAM')),
  CHECK (current_revision >= 1 AND version >= 0),
  CHECK ((source_type='PRESET' AND organization_id IS NULL AND team_id IS NULL AND team_template_id IS NULL)
```

source_keyはPRESETなら固定code、TEAMなら `team:{teamId}:template:{templateId}`。definition current_revisionの更新とrevision INSERTは同一definition側TXで、同一hashならrevisionを増やさない。stable field keyはrevision間で保持し、型/単位/semanticの変更は新keyであることを検証する。retired後もrevisionを物理削除しない。team template IDは既存BIGINTを参照し、UUIDへ置換しない。

原本にはUUID・revisionをFKなしで参照し、作成時に定義JSONを複写。保存後の定義JSONは変更不可。values_jsonはfieldKey→string/nullのobject、private noteは独立列。上限/必須/JSON schema/recorded_on範囲/IANA TZ/allowlist subset/hashはServiceで検証する（MySQL CHECKだけでJSON値の意味を保証しない）。team projection JSONには共有allowlistのfieldだけを置く。所有者private noteをreceiptにも残すため、receiptはprivate原本と同じowner認可・同じ消去対象であり、team mutation receiptはSharedRecordのみ。保持24時間で期限削除バッチ、個人情報の長期保管に使わない。

operation_pathにはHTTP method込みの正規化pathを入れ、route_kind=OWNERはowner user、TEAMはorganization IDでルーティングする。TEAM receiptのroute_idはorganization、query teamIdをpathに含める。Receipt確保・業務更新・応答保存は同一ルーティング先/同一ドメインTXで確定。ネットワークI/O中にTXを保持しない。未完receiptを別TXで先にcommitしないため、プロセス停止でも永久IN_PROGRESSを残さない。

削除はdeleted_atを立てる。同一原本の有効共有は原本1行のshare_idで一意に保持する。取消後別teamへ移すときは新share_idを採番しshare_versionを増加、古いshareのtombstoneはteam側に残す。再度同じteamへ共有する場合は既存source一意行のidを再利用し、本人が新previewで許可したshare_versionでだけ復帰する。share IDの変更とsource一意制約が衝突しないよう、過去teamの既存share IDをServiceから取得してpreview予約IDに使う。管理者MODERATEDはこの復帰を許可しない。

## 3. 同期と状態遷移

```text
private未共有 → preview（未永続・10分有効）
  → owner TX: PENDING + shareVersion増分 + desired_projection/対象version
  → AFTER_COMMIT event
  → 非TX coordinator → team TX: projection upsert
  → 非TX coordinator → timeline Service TX: source UUIDでupsert
  → owner TX: contentRevision/shareVersion一致ならVISIBLE（不一致なら旧ackを破棄）

PENDING → FAILED（業務原本は保存済み）→ 本人明示retry → PENDING
PENDING/VISIBLE/FAILED → 本人取消 → REVOKED
team VISIBLE/PENDING → 管理者非表示 → MODERATED（再試行では復活不可）
```

EffortShareRequestedEventは原本ID、owner ID、share ID、sourceVersion、shareVersionとrouting IDのみを持つ。非TX listener/coordinatorがowner Serviceで現在のdesired projectionを取得し、team Service→timeline Service→owner ackを順番に呼ぶ。各Serviceが自身のTXを完了してから次へ進み、@Transactionalの自己呼出しを使わない。同期失敗は非TX coordinatorがERROR＋監査を記録し、owner側FAILEDを別TXで記録する（contentRevision/shareVersion一致時のみ）。rollback-only TX内でcatchして業務成功と見せない。

AFTER_COMMITは通知規約に合わせ、通常イベントの即時自動リトライをしない。イベント消失/投入拒否/プロセス停止でPENDINGが残る場合は、監視が60秒超のpendingを検知する。本人はGET応答の状態で確認でき、60秒超PENDINGの再試行要求も、owner CASでFAILEDへ移してから同じdesired commandを再実行できる。運用者による再送は専用保守コマンドでshare UUID/versionを指定し、当該commandを再読込して実行する。勝手に古いpayloadを再送しない。イベントは配送の唯一の正本ではなく、owner行のdesired状態が正本。

team upsertはsourceVersion/shareVersionが現在許可と一致することをowner Serviceで直前確認し、古いversionを拒否。team行のMODERATEDは終端であり、owner側のVISIBLE ackが遅れても読取時にteam状態を必ず確認する。私的内容編集でcontentRevisionが増えた瞬間から旧投影はF00非表示。projection→timelineの間に停止しても、再送はshare UUIDを一意sourceにして同じタイムライン投稿を更新する。時刻/並び順createdAtは初回共有のまま、updatedAtだけ更新し新着を乱発しない。

team upsertのTXは、検証済みdesired projectionとcontentRevision/shareVersion/hashを書き込み、team行のstateを**VISIBLEにしてcommit**する（team PENDINGのまま終了しない）。続くtimeline upsertが成功してから、owner ack TXが同じcontentRevision/shareVersion/hashについてowner share_state=VISIBLEとsynced_source_versionを確定する。F00の許可にはteam VISIBLEに加えowner VISIBLEと同期版一致の両方が必要なので、team commitからowner ackまで内容は非表示のままとなる。初回だけでなく既存原本の訂正でも、ownerは先にPENDINGとなり、teamの新しいprojectionをVISIBLEでupsert→timelineの対応版更新→owner ackの同じ順序を使う。旧版team VISIBLE、更新途中の新しいteam VISIBLE、owner FAILEDはいずれも全条件を満たさず非表示。再試行はこの順序を冪等に完了し、正常時にowner/team両方がVISIBLEへ到達する。

タイムラインに新しいsource type `PERSONAL_EFFORT_SHARE` とUUID source参照を追加する。既存createSystemVillagePostのUUID経路はVILLAGE専用であり流用しない。下記のTEAM専用内部Serviceを新規追加し、BIGINT source IDへ変換しない。新規投稿にはshare_with_friends=false、forward sourceなし、外部公開不可、閲覧TEAM固定、全interaction capability=false。通常createPostのparentId、通常PUT、reaction、comment、引用/repost、フレンドチーム転送の各BE入口でsource typeを判定して禁止する。通常投稿は現行機能を維持する。

取消はowner TXでREVOKED＋shareVersion増分を先にcommitし、AFTER_COMMITでteam/timelineを非表示にする。F00はowner許可とcontentRevision/shareVersionを読むため、物理的な削除の完了を待たずstale payloadを返さない。管理者非表示はteam TXを先にcommitして即deny、その後ownerへ状態を通知する。通知が失われてもteam状態を読めば禁止は継続する。team/organizationの削除状態もF00で確認する。投稿者の退会は下記の既決保持方針に従い本文を維持し、著者表示だけ匿名化する。

F00 resolverはprivate sourceにはowner一致、shared sourceにはteam所属・team/organization有効・projection state・owner許可（退会purge後は非本文tombstone）・contentRevision/shareVersion・hash一致を確認する。team一覧のSQLで取得したprojectionを最終表示前にbatch判定する。判定は一覧・詳細・個人集約timeline・検索結果・リンク展開・通知本文preview・フレンドチーム転送・外部公開を含む全経路で同じServiceへ集約する。キャッシュへ内容を固定保存してこの判定を省略しない。個人の最近activity/監査/通知へprivate値をコピーしない。共有通知の新規配信自体は今回範囲外。

## 4. 障害・競合の検証表

| 注入点 | 必須の観測結果 |
|---|---|
| private保存commit前の例外 | 原本もreceiptも残らず、共有なし |
| private保存後、share要求前の通信切断 | 原本は取得可能。別key再作成を誘導しない |
| event publish/async拒否/停止 | 原本PENDINGが残り、監視と本人表示で検知。未共有としてteamは非表示 |
| team upsert後、timeline失敗 | 原本FAILED、team投影は存在してもowner未確定のため非表示。再試行で同じtimelineへ収束 |
| timeline成功後、owner ack失敗 | team/timelineはowner PENDINGのため非表示。再送upsertで1件に収束 |
| source v2より後にv1イベント到着 | v1はupsert/ack不可。最新値を上書きしない |
| 取消後に遅延create/update到着 | owner許可REVOKEDでdeny、shareVersionの古い作成を拒否 |
| 管理者非表示後に本人retry/編集 | team MODERATED維持。原本だけは更新可能 |
| 別team移行と旧teamイベント競合 | 原本のcurrent share ID/team/versionと不一致なら旧teamは不可視 |
| F00/owner shard/profile照会の障害 | private値を返さずエラー。認可不能を許可へ倒さない |

## 5. ライフサイクルと移行検証

既決の [退会フロー§13.13](../architecture/withdrawal_flow_immediate_anonymization_fix.md) に従う。退会申請時は本人のprivate APIアクセスを停止するが、猶予期間中の原本を不可逆消去しない。共有本文は残し、UserAnonymizedEventでは著者表示だけ「退会者」へ匿名化する。退会だけを理由に既存共有をREVOKEDにしない。AccountPurgedEvent（30日後）でprivate values/note/definition snapshot/共有mapping/receipt responseを消去する。共有許可の判定に必要なowner route/source UUID/contentRevision/shareVersion/state/hashだけを非本文tombstoneに残し、共有projectionの本文を維持する。tombstoneの値なしでF00が検証できない状態ならfail closedとする。

purgeリスナーは既存のpurge completion tracking/retry基盤へeffortrecord担当として登録し、owner消去とreceipt消去の完了を冪等に記録する。途中失敗で完了を記録せず、既存purge再試行で収束させる。ユーザーの明示した原本削除/共有取消は退会とは別で即REVOKEDを確定し、tombstoneにも反映する。退会撤回期間中の原本は復帰可能、共有を自動再投稿しない。チーム削除はprivate原本を消さず、チーム側projectionを論理削除する。脱退時の保持/解除は親設計の未決裁可事項であり、アカウント退会と混同しない。

実装時には既存activity/team/user/timelineデータを含むFlyway実MySQLで、無変更保全、同一migration再起動、全表照合順序、UUID version nibble=7、FKがeffort definition内部だけ、制約違反、indexによるEXPLAIN、非TX境界の部分失敗と順逆配送を検証する。migration majorはマージ時最大+1、minorはUTC日時で採番。設計段階では架空のFlyway番号を確定しない。Entity/migration変更時の自動ER再生成とOpenAPI生成は実装PRで行う。

## 6. 版の独立性と更新表

versionは原本行の@Version（CAS用）、contentRevisionは日付/values/private noteの内容版、shareVersionは共有許可・mapping・allowlistの版である。source_version列/API sourceVersionはcontentRevisionを指し、@Versionとは比較しない。ackの状態更新で@Versionが増えても可視性は失われない。projection hashには共有内容と共有定義revisionを含める。

| 操作 | version | contentRevision | shareVersion |
|---|---|---|---|
| 原本作成 | 0 | 1 | 0 |
| 日付/値/note内容更新 | +1 | +1 | 不変（既存mappingで新しいdesiredを作る） |
| 初回共有/再共有/allowlistやmapping変更 | +1 | 不変 | +1 |
| PENDING→VISIBLE ack / FAILED記録 | +1 | 不変 | 不変 |
| 同一desiredのretry | +1 | 不変 | 不変 |
| 本人取消/原本削除 | +1 | 削除では不変 | +1 |
| 管理者非表示 | team version+1、owner通知反映時+1 | 不変 | 不変（team MODERATEDで終端） |

API previewは@Versionで同時編集を検知し、投稿時にもversionを要求する。F00はcontentRevision/shareVersionを比較する。retry/ackで変更されたversionは次回owner GETから取得し、内容版を推測しない。purge後tombstoneでは版を固定し、共有の新規編集や再共有を許可しない。

## 7. TEAMタイムラインへの追加契約

タイムラインドメインへ次の対応表を新規追加する（この表もUuidV7Entity）。timeline_posts.idは既存BIGINTを維持する。値はtimeline_posts.contentへ複写せず、contentは固定の非個人文言キー用識別子のみとし、DTO生成時に許可済みSharedRecordをhydrateする。

```sql
CREATE TABLE timeline_effort_sources (
  id BINARY(16) NOT NULL,
  organization_id BIGINT UNSIGNED NOT NULL,
  team_id BIGINT UNSIGNED NOT NULL,
  timeline_post_id BIGINT UNSIGNED NOT NULL,
  share_uuid BINARY(16) NOT NULL,
  share_version BIGINT NOT NULL,
  content_revision BIGINT NOT NULL,
  is_revoked BOOLEAN NOT NULL DEFAULT FALSE,
  created_at DATETIME(6) NOT NULL,
  updated_at DATETIME(6) NOT NULL,
  PRIMARY KEY (id), UNIQUE KEY uq_timeline_effort_share (share_uuid),
  UNIQUE KEY uq_timeline_effort_post (timeline_post_id),
  KEY idx_timeline_effort_team (organization_id, team_id, is_revoked),
  CONSTRAINT fk_timeline_effort_post FOREIGN KEY (timeline_post_id) REFERENCES timeline_posts(id),
  CHECK (share_version >= 0 AND content_revision >= 1)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;
```

新規内部 `TimelineEffortSourceService.upsertTeamShare(organizationId,teamId,shareUuid,shareVersion,contentRevision)` は認可済みcoordinatorだけが呼ぶ（外部Controller公開なし）。team Serviceで現在の共有state/版を確認し、timeline自身のTXで投稿と対応表を原子的upsertする。同一share UUIDは投稿1件、古い版はno-op、同版再送は同一post ID、撤回済み旧版で復活不可。`revokeTeamShare(...,shareVersion)` は対応表を失効し投稿を論理削除する。将来の再共有は新しい本人許可shareVersionのときのみ復帰し、MODERATEDを解除しない。

timeline→effortの照会は非TX Facade/read hydratorから行い、timeline TX内で別ドメインRepositoryへアクセスしない。投稿本文、検索index、通知preview、forward payloadに値を保存しない。既存の全timeline取得/検索/転送/公開/親ID/反応経路は対応表存在の判定を含む共通source guardを先に通し、未対応のread pathを残した状態で導線を有効化しない。

### 7.1 purge後tombstoneの具体形

別表を増やさずeffort_records行をtombstoneとして使用する。AccountPurgedEvent処理はvalues_json={}、definition_snapshot={}、private_note=NULL、share_mapping_json=NULL、share_definition_snapshot=NULL、desired_projection=NULL、selected_field_keys=NULL、last_error_code=NULL、purged_at=現在UTCを同一owner TXで確定する。owner_user_id/id/definition_id/版/share routing ID/state/desired_hash/synced_source_versionのみ残す。purged行のcreatedAt/recordedOnは公開DTOへ返さず、個人一覧/詳細/集計はpurged_at IS NULLを必須にする。通常Entityの@SQLRestrictionはdeleted_at IS NULL AND purged_at IS NULLとする（原本表だけ）。

shared F00専用のRepository projection queryは認可済みowner routeとsource UUIDで、上記許可・版・hash列だけをSELECTする。purged_at有無を問わず読める専用native queryとし、JSON本文列をSELECTせず、deleted_atがあれば明示削除としてdenyする。これにより@SQLRestrictionでtombstoneを見失わず、一般APIからpurged行へ到達させない。共有取消のtombstoneはREVOKEDを保持し、purgeでVISIBLEへ戻さない。
