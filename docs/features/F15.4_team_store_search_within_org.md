## 1. 概要・目的・スコープ

### 1.1 目的
チェーン本部のような **組織（Organization）** 配下に多数の **チーム（店舗／支店／教室）** がぶら下がる業態で、エンドユーザーが組織ページから **都道府県・市町村・キーワード** で配下店舗を絞り込み検索できる UX を提供する。**未ログインユーザーでも利用可能** にすることで、新規ユーザーの店舗発見導線を整備する。

例: マクドナルド組織のページから「東京都・渋谷区」を選んで渋谷区内の店舗一覧を取得する。

F04.6 のグローバル横断検索とは独立し、**組織スコープ限定** の検索 UX として位置づける。

### 1.2 対象ユーザーとアクセス可否

| ロール | アクセス可否 | 可視範囲 |
|---|---|---|
| SYSTEM_ADMIN | 可 | 当該組織配下のチーム（PUBLIC + ORG_ONLY、PRIVATE は今回対象外） |
| ADMIN（当該組織所属） | 可 | 自組織配下の PUBLIC + ORGANIZATION_ONLY |
| DEPUTY_ADMIN（当該組織所属） | 可 | 同上 |
| MEMBER（当該組織所属） | 可 | 同上 |
| SUPPORTER | 可 | PUBLIC のみ（GUEST 同等） |
| GUEST（未ログイン／非組織メンバーのログイン会員） | 可 | 自組織配下の PUBLIC のみ・抑制版 DTO |

### 1.3 スコープ内
- 組織ページ配下の専用検索ページ `/organizations/{id}/teams/search`
- バックエンド検索 API `GET /api/v1/organizations/{orgId}/teams/search`
- 都道府県・市町村プルダウン連動（既存マスター API 流用）
- 未ログイン GET 許可（permitAll、レート制限あり）
- 6 言語 i18n キー追加（ja は完全、他言語は ja からのフォールバックで開始）

### 1.4 スコープ外
- 半径 X km の地理空間検索（DDL に lat/lng 未追加のため別 PR）
- 地図表示
- PRIVATE チームの公開
- 全体横断公開検索（F04.6 が担当）
- 店舗詳細ページの未ログイン公開（検索結果カードまでで止める）
- 組織階層（子組織配下店舗）の横断検索（§10 暫定決定参照）

## 2. DB 設計

### 2.1 新規テーブル
**なし**。既存 `teams` テーブルの以下カラムを利用：

| カラム | 型 | 用途 |
|---|---|---|
| `name` | VARCHAR(100) | 店舗名（部分一致対象） |
| `name_kana` | VARCHAR(100) | フリガナ（部分一致対象、ソートキー） |
| `prefecture` | VARCHAR(20) | 都道府県（完全一致） |
| `city` | VARCHAR(50) | 市町村（完全一致） |
| `visibility` | ENUM('PUBLIC','GUESTS_AND_ABOVE','SUPPORTERS_AND_ABOVE','MEMBERS_AND_ABOVE') | ロールベース公開範囲（V79.001 で旧 ORGANIZATION_ONLY / PRIVATE から移行済。旧 PRIVATE / ORGANIZATION_ONLY は GUESTS_AND_ABOVE に統合）|
| `template` | VARCHAR(30) | 業種テンプレート |
| `icon_url` | VARCHAR(500) | アイコン URL |
| `archived_at` | DATETIME | 凍結時刻（NULL のみ検索対象） |
| `deleted_at` | DATETIME | 論理削除（NULL のみ検索対象） |
| `version` | BIGINT | 楽観ロック |

組織紐付けは既存 `team_org_memberships` テーブル（`status='ACTIVE'`）を経由する。

### 2.2 既存インデックスの確認
- `teams`: `idx_teams_visibility (visibility)` のみ（`V2.004__create_teams_table.sql`）
- `team_org_memberships`: `organization_id` のインデックスが存在するか実機 EXPLAIN で確認のうえ、無ければ補強する

### 2.3 追加インデックス（Flyway: `V9.142__add_teams_search_indexes.sql`）

**設計根拠**: 組織配下の店舗数は典型的に数十〜数千件。アクセス順は
`team_org_memberships (organization_id 駆動) → teams (PK 結合) → prefecture/city フィルタ`
となるため、`teams` 側のセカンダリインデックスは「事前絞り込み後の prefecture/city/visibility 後置フィルタ」と「ソート用 name_kana」の 2 本を用意する。

```sql
-- F15.4: 組織内チーム（店舗）検索の高速化

-- 後置フィルタ高速化（archived_at IS NULL を含む）
CREATE INDEX idx_teams_pref_city_visibility
  ON teams (prefecture, city, visibility, archived_at);

-- フリガナ昇順ソート用
CREATE INDEX idx_teams_name_kana ON teams (name_kana);

-- team_org_memberships の補強（存在確認後・存在しない場合のみ追加）
-- マイグレーション実装時に INFORMATION_SCHEMA で存在確認すること
```

### 2.4 JOIN 戦略
- Specification 内で `team_org_memberships` を INNER JOIN（`status='ACTIVE'`）
- **`organizations` は JOIN しない**: コントローラ側で先に `OrganizationEntity` をロードして visibility 判定を済ませる方式に統一（重複判定を避ける）
- countQuery でも同じ JOIN を発行
- `query.distinct(true)` で重複排除

## 3. API 設計

### 3.1 エンドポイント
`GET /api/v1/organizations/{orgId}/teams/search` （**認証不要**、permitAll、レート制限あり）

### 3.2 クエリパラメータ

| 名前 | 型 | 必須 | バリデーション | 説明 |
|---|---|---|---|---|
| `keyword` | string | 任意 | 最大 100 文字 / 制御文字禁止 / LIKE エスケープ | `name` または `name_kana` の部分一致 |
| `prefecture` | string | 任意 | 最大 20 文字 / マスター存在チェック | 完全一致 |
| `city` | string | 任意 | 最大 50 文字 | 完全一致。`prefecture` 未指定時は無視（警告ログのみ、400 にしない） |
| `template` | string | 任意 | 列挙値ホワイトリスト | 完全一致 |
| `page` | int | 任意 | 0 以上 | 既定 0 |
| `size` | int | 任意 | 1〜50 | 既定 20 |
| `sort` | string | 任意 | ホワイトリスト：`nameKana,asc` / `name,asc` / `createdAt,desc` | 既定 `nameKana,asc` |

### 3.3 レスポンス DTO（2 系統）

権限判定結果に応じてサーバ側で出し分け、Swagger 上は `oneOf` で表記する。

#### `TeamPublicSummaryResponse`（GUEST／非メンバー向け抑制版）
```json
{
  "id": "mannschaft-shibuya",
  "slug": "mannschaft-shibuya",
  "name": "マクドナルド渋谷店",
  "nameKana": "マクドナルドシブヤテン",
  "prefecture": "東京都",
  "city": "渋谷区",
  "template": "STORE",
  "iconUrl": "https://.../icon.png"
}
```

> **`slug` フィールド（2026-06-14 追加）**: FE が `/teams/{slug}` ルートへのリンクを構築できるよう `slug` を独立フィールドとして追加した。`id` も後方互換のため同値を返す。

**意図的に含めないフィールド**: `memberCount` / `bannerUrl` / `homepageUrl` / `establishedDate` / `supporterEnabled` / `archivedAt` / `nickname1/2` / 連絡先 / 住所詳細番地。

#### `TeamSearchResultResponse`（組織メンバー向け詳細版）
上記に加え `memberCount` / `bannerUrl` / `homepageUrl` / `establishedDate` / `visibility` / `supporterEnabled` を含む。`slug` フィールドも同様に含まれる。

ページングは既存 `PagedResponse<T>` を使用：

```json
{
  "data": {
    "content": [...],
    "totalElements": 42,
    "totalPages": 3,
    "page": 0,
    "size": 20
  }
}
```

### 3.4 ステータスコード

| コード | 条件 |
|---|---|
| 200 | 検索成功（0 件含む） |
| 400 | バリデーション違反（size 超過 / keyword 文字数超過 / sort 値違反 等） |
| 404 | 組織が存在しない／削除済み／未ログイン者から見て visibility != PUBLIC（エニュメレーション対策で 403 ではなく 404） |
| 429 | レート制限超過 |

### 3.5 レート制限
既存の `PointCardRateLimitFilter` パターンを参考に `OrganizationTeamSearchRateLimitFilter` を新設：
- **未ログイン**: 30 req / 分 / IP
- **ログイン**: 120 req / 分 / userId

レート違反時は §6.6 のとおり監査ログを記録する。

## 4. ビジネスロジック

### 4.1 新規クラス
- `TeamSearchSpecifications`（`backend/src/main/java/com/mannschaft/app/team/service/`） — `VillageSearchSpecifications` をリファレンス
- `TeamSearchService`
- `OrganizationTeamSearchController`（既存 `TeamController` に混ぜず分離 — permitAll スコープを明確化する意図）
- `OrganizationTeamSearchRateLimitFilter`
- `TeamPublicSummaryResponse` / `TeamSearchResultResponse`

### 4.2 Specification メソッド
```java
public final class TeamSearchSpecifications {
    public static Specification<TeamEntity> notDeleted();
    public static Specification<TeamEntity> notArchived();
    public static Specification<TeamEntity> belongsToOrganization(Long orgId);  // team_org_memberships INNER JOIN, status='ACTIVE'
    public static Specification<TeamEntity> visibilityIn(Set<Visibility> allowed);
    public static Specification<TeamEntity> nameOrKanaContains(String q);       // LIKE エスケープ込み
    public static Specification<TeamEntity> prefectureEquals(String pref);
    public static Specification<TeamEntity> cityEquals(String city);
    public static Specification<TeamEntity> templateEquals(String template);
}
```

**LIKE エスケープ**: `%` `_` `\` を `\\` でエスケープし `cb.like(..., '\\')` を使用する。MySQL の `utf8mb4_0900_ai_ci` により大小文字・全半角差は吸収される。

### 4.3 権限判定フロー（コントローラ）
```
1. orgId で OrganizationEntity を取得（deleted_at IS NULL）。なければ 404
2. currentUser = SecurityContext から取得（null 可）
3. organization.visibility != PUBLIC のとき:
     - currentUser が当該組織メンバー（AccessControlService.isMember）→ 続行
     - else → 404（存在を漏らさない）
4. allowedVisibilities を決定:
     - 組織メンバー → {PUBLIC, ORGANIZATION_ONLY}
     - else（GUEST 含む）→ {PUBLIC}
5. TeamSearchService.search(orgId, criteria, allowedVisibilities, pageable)
6. allowedVisibilities が PUBLIC のみ → TeamPublicSummaryResponse へ射影
   else → TeamSearchResultResponse へ射影
```

### 4.4 ページネーション
既存 Pageable（offset-based）を使用。`sort` 値は `TeamSearchService` 入口でホワイトリストチェックを行い、許可外の列は 400。

## 6. セキュリティ

### 6.1 Spring Security 認証バイパス
```java
.requestMatchers(HttpMethod.GET, "/api/v1/organizations/*/teams/search").permitAll()
```
他のパスへの影響なし。Filter Chain 内で `OrganizationTeamSearchRateLimitFilter` を `UsernamePasswordAuthenticationFilter` の前段に挿入する。

### 6.2 エニュメレーション対策
- 組織が PRIVATE/ORGANIZATION_ONLY で未ログイン者には **404** を返す（403/401 を返さない）
- 削除済み組織も 404
- レスポンス本文は `"Organization not found"` で固定し、内部状態（PRIVATE か削除済みか）を漏らさない

### 6.3 SQL Injection
JPA Criteria API + パラメータバインディング。LIKE 句のメタ文字エスケープは §4.2 のとおり。

### 6.4 個人情報漏洩防止
- 未ログイン者向け DTO（`TeamPublicSummaryResponse`）はメンバー数・連絡先・メールアドレス・住所詳細番地を **一切含まない**
- 住所は `prefecture` + `city` まで
- サーバ側で DTO 変換を二重チェック（`TeamSearchService` と `OrganizationTeamSearchController` 両方で権限判定）

### 6.5 キャッシュ戦略
Phase 1 では未導入。Phase 3 で計測のうえ Valkey 導入を判断する。
導入時はキャッシュキーに権限スコープを含める：
```
teamsearch:{orgId}:{paramHash}:{PUBLIC_ONLY|MEMBER}
```
TTL は短め（60 秒程度）に設定。組織内チーム更新時のキャッシュ無効化方針は導入時に確定する。

### 6.6 監査ログ
未ログイン公開検索は個人情報を含まないため、**通常時は記録しない**。
ただし以下のときのみ `AuditEvent` に記録：
- レート制限違反時：カテゴリ `RATE_LIMIT_EXCEEDED`、内容に `orgId` と IP ハッシュ

### 6.7 CORS / CSRF
GET のため CSRF 対象外（`csrf.ignoringRequestMatchers` に追加）。CORS は既存設定を踏襲（許可オリジン制御）。

### 6.8 ログ出力
- 住所詳細・連絡先はログに出さない
- `keyword` パラメータは長すぎる場合 20 文字に切り詰めて記録（必要時のみ DEBUG レベル）

## 7. ユーザビリティ

- 都道府県プルダウン先頭に「指定なし」をデフォルト選択
- 市町村は都道府県未選択時に disabled + プレースホルダ「先に都道府県を選択」
- debounce 300ms で入力中も結果が自動更新
- 検索ボタンは UI 一貫性のため設置（モバイルでフォーカス外しによる確定が分かりやすい）
- 0 件のときは条件リセットボタンとヒントテキスト
- ページネーションは結果リストの上下両方に配置
- モバイル: プルダウン群を縦並びにし、検索結果は 1 カラム
- ブラウザバック・URL 共有で条件復元可能
- ローディングスケルトン表示
- SEO: 公開検索結果ページは `<meta name="robots" content="index,follow">`（公開店舗情報のため）

## 12.4 Phase 4: memberCount 事前集計

### 完了情報
- **完了日**: 2026-05-17
- **PR**: [#718](https://github.com/kenta-0420/mannschaft/pull/718)
- **マージ SHA**: `008306df0f8537906ed5b0aa13e0a590a35124dd`

### 背景
Phase 1〜3 で `TeamSearchResultResponse#memberCount` は検索結果 1 件ごとに `team_org_memberships` を COUNT する N+1 計算で算出していたため、組織配下店舗数の増加に伴いレスポンスタイムが線形劣化する懸念があった。Phase 4 では事前集計カラム化により、検索クエリから COUNT サブクエリを排除する。

### 実装概要（三段構え）

1. **事前集計カラム** — `teams.member_count`（`BIGINT NOT NULL DEFAULT 0`）を Flyway `V9.159__add_teams_member_count.sql` で追加。`idx_teams_member_count` を併設し、既存全行は `team_org_memberships` の `ACTIVE` 行数で一括バックフィルしてから NOT NULL 化。
2. **イベント駆動同期更新** — `TeamMemberCountListener` が `@TransactionalEventListener(phase = AFTER_COMMIT)` + `@Transactional(propagation = REQUIRES_NEW)` で `MembershipChangedEvent` を購読し、`TeamRepository#incrementMemberCount(teamId)` / `decrementMemberCount(teamId)` を呼び出す。AFTER_COMMIT により本トランザクションのロールバック時には副作用が発生しない。
3. **夜次バッチ補正** — `TeamMemberCountBackfillBatchService` を毎日 02:00 JST に起動（`@Scheduled` + `@SchedulerLock` で重複起動防止）。相関サブクエリ `UPDATE teams t SET member_count = (SELECT COUNT(*) FROM team_org_memberships tom WHERE tom.team_id = t.id AND tom.status='ACTIVE')` で全 team を一括補正し、イベント取りこぼし／競合・退会経路漏れを最終整合性で吸収する。

### DTO 反映
`TeamSearchResultResponse#memberCount` を新カラム `teams.member_count` 参照に置換。検索クエリから COUNT サブクエリが消え、N+1 計算が解消された。

### Flyway バージョン番号について
当初予定の `V9.154` は他フェーズの作業との衝突を避けるため、最終的に **`V9.159`** で適用した。設計書本文 §9 の `V9.142` は Phase 1 のインデックス DDL を指し、本 Phase 4 の `V9.159` とは別物である。

### 既知の制約 / Caveat
- **退会時の即時同期は行われない** — `AccountPurgeService#deleteAllByUserId(userId)` はユーザー退会処理の中で `team_org_memberships` を直接削除するが、その経路では `MembershipChangedEvent` を発火していない。そのため退会直後の検索結果は実態より +1 されたカウントを返しうる。整合性は夜次バッチで翌朝までに回復する設計とした。即時同期が必要となる UX が出現した場合は、`AccountPurgeService` 内でも `MembershipChangedEvent` を発火するよう改修する（ドメイン越境の整合性確保策として、`AuthAnonymizationEventListener` 系の購読パターン拡張も視野）。
