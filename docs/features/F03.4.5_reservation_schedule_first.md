## 1. 概要（マスターの実使用フィードバックが設計の動機）

> **マスターのフィードバック（2026-07-08・原文の意図）**:
> 「チーム側が予約枠を設定するのが使いにくい。通常の業務であれば、テンプレートを登録すれば通常時はなにもせずとも営業時間が更新されていく。編集したいのは、通常営業をクローズさせる時か、振替で営業する時。現状は営業枠を個別で作ることから始まっているので脳内摩擦が多い」

現状の管理UIは「個別枠の作成（SlotManager）」が主役で、テンプレートを保存しても**「今すぐ枠を作成」ボタンを別途押さないと枠が生まれない**（`SlotTemplateManager.vue` 実測: 保存成功 → `regenerate_guide` メッセージ → 手動 generate の 3 ステップ）。さらに**営業時間を編集する UI がチーム管理タブに存在しない**（実測: `useReservationApi.updateBusinessHours` の参照コンポーネントはゼロ。営業時間は API 直叩きでしか設定できない）。これがマスターの言う「脳内摩擦」の実体である。

本書は予約管理の管理側 UX を**「営業スケジュール中心モデル」**へ改訂する:

| 節 | 内容 | 一言で |
|---|---|---|
| §3 (A) | テンプレ保存＝即自動生成・管理タブ再編・「休業にする/臨時営業する」例外操作 | **通常時は何もしない。編集するのは例外だけ** |
| §4 (B) | 週次定期の予約不可枠（事由ラベル＋公開可否） | 「毎週火曜19-20時は研修」を1回だけ登録 |

## 3. A) 営業スケジュール中心モデル（本丸）

### 3.1 テンプレ保存＝即自動生成

#### 設計判断: 同期実行を採用（AFTER_COMMIT 非同期は不採用）

テンプレの create / update 成功時に、**該当テンプレ 1 行のみを対象に** horizon 28 日（`[tomorrow, tomorrow+27日]`）の生成を自動実行する。

| 観点 | **同期（採用）** | AFTER_COMMIT 非同期（不採用） |
|---|---|---|
| 利用者への結果提示 | 保存レスポンスに生成カウントを同梱でき、**トーストで「保存し、28日先までの枠を◯件作成しました」を即時提示**できる。「保存したのに枠がない」というマスター指摘の混乱が構造的に消える | 生成結果を返せない。失敗時はログのみ＝症状の黙殺（根治原則違反）になりやすい |
| 処理量 | **単一テンプレ scope なら最大 24セル/日 × 4回（28日中の同一曜日の出現数）= 96 INSERT**（12時間営業の帯でも。1テンプレ行は 1 曜日のみを持つため「×28日」ではない——精査2パス H 訂正。全域 13,440 = 上限500行に近い約140テンプレ × 96 と整合）。既存の日付チャンク tx（1日=1 tx・REQUIRES_NEW・`ReservationSlotGenerationService` 実装済）をそのまま流用すれば応答遅延は実用圏（1秒未満想定・AC S-2 で観測） | 96 INSERT を非同期化する利得がない |
| 追加基盤 | 不要（Service 呼び出し 1 本） | イベント＋`@TransactionalEventListener(REQUIRES_NEW)`＋番人テストが増える |
| 失敗時の挙動 | チャンク tx 失敗はテンプレ保存自体には波及させない（保存 tx は既にコミット済み後に生成を実行・下記実装順序）。生成失敗はエラートーストで正直に報告し、日次バッチの差分レンジ（F03.4.2 §5.4）が翌朝自己修復する | 同左だがユーザーに見えない |

**実装順序と tx 境界（確定・精査1パス反映）**: 生成は「保存 tx がコミットした**後**」に、**`@Transactional` サービスメソッドの外側**で実行する。具体的には `createTemplate` / `updateTemplate`（いずれも `@Transactional`・実測）を先に完了させ、**コントローラまたは非トランザクションのファサードメソッド**（既存 `generate()` の `@Transactional(propagation = Propagation.SUPPORTS, readOnly = true)`＋コントローラ呼びと**同型**・実測）から `ReservationSlotGenerationService` の**単一テンプレ版**を呼ぶ。生成が失敗しても保存は成立済みで、レスポンスは `generation.failed=true` で正直に返す（下記契約）。

> **⚠ tx 境界の罠（実装者向け・必読）**: `reservation_slots` は FK `fk_rs_template`（`template_id` → `reservation_slot_templates`・**V142.002 実DDL 根拠**）を持つ。もし生成を保存 tx の**内側**から呼ぶと、生成側の日付チャンク tx は `REQUIRES_NEW`（`TransactionTemplate`・実装済）のため**別コネクション**となり、**親 tx が未コミットのテンプレ行を FK 参照する slot INSERT が親の行ロック解放を待つ自己デッドロック → lock wait timeout** に陥る。「保存 tx コミット → 外側で生成」の順序はこの構造的デッドロックの回避条件であり、実装時に順序を崩してはならない。

#### レスポンス契約 — `SlotTemplateSaveResponse`（新設・テンプレ POST/PATCH 共通）

保存＋生成結果を 1 レスポンスに包む（AC S-1/S-3 の観測点を型で固定）:

```json
{
  "data": {
    "template": { "id": "0198...", "dayOfWeek": "MON", "startTime": "10:00", "...": "（SlotTemplateResponse と同形）" },
    "generation": {
      "generatedCount": 24,
      "skippedExistingCount": 0,
      "skippedClosedDayCount": 4,
      "skippedOutsideHoursCount": 2,
      "failed": false
    }
  }
}
```

| フィールド | 型 | null | 説明 |
|-----------|---|------|------|
| `template` | Object | 不可 | 既存 `SlotTemplateResponse` と同形（保存結果） |
| `generation` | Object | 不可 | 生成結果。カウント 4 種は既存 `GenerateSlotsResponse` と同名・同義 |
| `generation.failed` | boolean | 不可 | 生成段の失敗。TRUE のときカウント各値は**コミット済みチャンク分**（日付単位 tx のため部分実行があり得る）。翌朝の日次バッチ差分レンジが残りを自己修復する |

- テンプレ POST/PATCH の応答型が `SlotTemplateResponse` 単体から変わるため **OpenAPI 再生成＋`generate:types`＋FE 改修を同一 PR** で行う（現行の応答消費者は `SlotTemplateManager.vue` のみ・実測。破壊範囲は閉じている）。

**複数曜日ループとの集約規則（精査2パス D・W1 実装を前提）**: W1（PR #2198）の新規作成ダイアログは選択曜日ぶん `createSlotTemplate` を **N 回順次呼ぶループ**（`selectedDays`・W1 ブランチ実測）。W2 では各呼びが `SlotTemplateSaveResponse` を返すため、FE は **N 件の `generation` を合算して 1 トースト**で報告する（生成/スキップの合計件数。`reservation.template.auto_generated` の `{generated}` に合算値）。**部分失敗**（一部曜日で `failed=true` または呼び自体が 4xx/5xx）時は「**{total}曜日中{failedCount}曜日で枠の作成に失敗しました（保存済みの曜日は有効です）**」表現の警告トースト 1 本に集約する（曜日ごとに N 連トーストを出さない・§11 `auto_generated_partial`）。

- **生成 scope はチーム全テンプレではなく当該テンプレのみ**（設計判断）: チーム全域 generate（最悪 13,440 INSERT・F03.4.2 §5.2）を CRUD 応答に載せると保存が重くなる。他テンプレの horizon 延伸は日次バッチの責務のまま。
- **`update` で `isActive=FALSE` にした場合・時刻を変更した場合**: 既生成枠への遡及なし原則（F03.4.2 §5.3）は**不変**。無効化は「以後生成されない」だけ、時刻変更は「新定義セルの追加生成」だけが起きる。旧定義の未予約枠を消したい場合の 2 操作ガイド（枠削除 → 保存）は文言を改訂して残す（§11 `regenerate_guide` 改訂）。
- **自動生成はレートリミット（RESERVATION_044）の対象外**（設計判断）: 保存操作そのものが頻度の自然な上限であり、単一テンプレ scope＋冪等（INSERT IGNORE + `uq_rs_template_cell`）のため暴走リスクがない。手動 generate API に残るリミットはそのまま。

#### 「今すぐ枠を作成」ボタンと `weeks` 選択 UI の廃止（API は残置・deprecate）

| 対象 | 決定 | 根拠 |
|---|---|---|
| FE `SlotTemplateManager.vue` の「今すぐ枠を作成」ボタン＋`weeks` Select（実測: `generateNow()`／`generateWeeks` ref） | **撤去** | 保存＝反映になるため操作の存在意義が消える。残すと「押さないと反映されないのでは」という疑念（脳内摩擦）が残る |
| BE `POST /reservation-slot-templates/generate` | **残置＋`@Deprecated`（OpenAPI `deprecated: true`）** | 生成型（`generate:types`）を参照する既存クライアント・E2E・運用リカバリ（バッチ障害時の手動追い付き）用に互換維持。**削除は将来の別 PR・要裁可**（§14 要裁可論点） |
| `weeks` パラメータ | API 上残置（1〜4・既定 4）。**FE からは常に省略**（=28日） | additive 契約を壊さない |
| i18n `reservation.template.generate` / `generate_result` / `generate_rate_limited` / `generate_skipped_closed` | **キー残置・値流用**（自動生成・臨時営業の結果トーストが再利用） | 6言語の再翻訳コストを避ける |
| i18n `reservation.template.generate_weeks` ほか UI 撤去で参照ゼロになるキー | **削除/改訂**（廃止波及キーの**全数列挙は §11 の一覧表が正**・精査2パス C） | 死蔵キー化の防止（§5.4 と同方針） |

### 3.2 管理タブの再編（初期セットアップの流れ＝画面の並び）と営業時間 UI の新設

#### 実測の現状（`TeamReservationsPanel.vue` 管理タブ）

```
LineManager → MenuManager → SlotTemplateManager → SlotManager → 詳細設定Accordion
  （詳細設定 = PublicToggle / PolicySettings / UnavailabilityManager / NotifyRecipients）
※ 営業時間の編集 UI は存在しない（updateBusinessHours の参照コンポーネントゼロ・実測）
```

#### 改訂後の並び（確定）

```
① 営業時間（BusinessHoursManager.vue 新設）
② 予約対象（LineManager・呼称は §5 で動的化・並び順編集を追加 §5.4）
③ メニュー（MenuManager・既存のまま)
④ 週間スケジュール（WeeklyScheduleManager.vue = SlotTemplateManager 発展 + §4 定期予約不可枠）
⑤ 例外日カレンダー（§3.3 の「休業にする/臨時営業する」起点）
⑥ 詳細設定 Accordion（既存4種 ＋ SlotManager をここへ移設）
```

- **①〜④の並び = 初期セットアップの思考順**（場所を開ける時間 → 何を貸すか → 何を提供するか → 週の設計図）。ADHD 配慮（`user_adhd_tendency`）: ページは上から順に埋めるだけ・例外操作は⑤⑥へ段階開示。
- **`BusinessHoursManager.vue`（新設）**: 曜日 7 行 ×（営業トグル `isOpen`・開始/終了 30 分刻み Select）。取得は既存 `GET /reservation-settings/business-hours` のまま。**PUT の応答は §3.1 と同型の生成結果ラッパへ変更**する（`BusinessHoursSaveResponse { hours: BusinessHourResponse[], generation: { generatedCount, skippedExistingCount, skippedClosedDayCount, skippedOutsideHoursCount, failed } }`。保存成功時に同期 generate を実行し結果を同梱——営業時間の拡大で `skippedOutsideHoursCount` に落ちていたセルが埋まる。縮小方向は遡及 CLOSE しない=スコープ外の明記どおり）。生成の tx 境界・失敗時挙動は §3.1 と同一規約（保存 tx コミット後・外側実行・`failed=true`＋エラートーストで正直に報告・翌朝バッチが自己修復）。
  - **生成 scope は「変更のあった曜日」の差分に限定**（精査1パス反映・INSERT 量の抑制）: PUT リクエストと現行値を突合し、`isOpen`/`openTime`/`closeTime` のいずれかが変わった曜日の active テンプレのみを対象に horizon 28 日を生成する。通常の変更は 1〜2 曜日＝全テンプレ方式の約 1/7〜2/7（最悪の 7 曜日全変更でも従来案と同量 13,440 INSERT が上限）。
  - **生成中の UX（規定）**: 保存ボタンは生成完了まで loading 表示（`saving`）＋「枠を更新しています…」のインライン文言（§11 `business_hours.generating`）。完了トーストは生成カウント同梱（`business_hours.save_success`）。応答は**既定の API タイムアウト内に 200 を返すこと**を回帰 AC とする（S-6 観測点）。
  - **PUT/GET の非対称（精査2パス G）**: 応答型の変更は `updateBusinessHours`（PUT）**のみ**。`getBusinessHours`（GET）は `BusinessHourResponse[]` のまま不変であり、現行の GET 消費者 `ReservationUnavailabilityManager.vue`（テンプレ自動充填用・実測）への影響はない。
  - **営業時間の縮小・定休化時のガイド（精査2パス I）**: BusinessHoursManager は保存前に現行値と突合し、**縮小方向の変更**（`isOpen` true→false・時間帯の短縮）を検知したら「この曜日のすでに作成済みの未来の枠はそのまま残ります（遡って閉じません）。特定日を恒久的に閉じる場合は例外日カレンダーの『この日を休業にする』を使ってください」のガイドを保存確認に表示する（§11 `business_hours.shrink_note`・遡及 CLOSE しない既存方針をユーザーに正直に伝える。AC S-6⑤）。
- **営業時間未設定チームの初回体験（精査2パス E）**: `ReservationSettingsResponse.hasBusinessHours=false`（実在フィールド・実測）のとき、④週間スケジュール画面の空状態に「**先に営業時間を設定してください**」ガイド＋①営業時間セクションへのスクロール/フォーカス導線を表示する（§11 `template.need_business_hours_hint`）。また保存時自動生成の結果が **`generatedCount=0` かつ `skippedOutsideHoursCount>0`（または `skippedClosedDayCount>0`）** のときは、トーストに**原因を明示**する（「枠は作成されませんでした（営業時間外/定休日のため）。営業時間を確認してください」§11 `template.generated_zero_hint`）。「保存したのに枠が 0 件」の無言の混乱——本設計の動機そのもの——を再発させない（AC S-11）。
- **`SlotManager`（個別枠 CRUD）の格下げ**: 詳細設定 Accordion 内へ移設し、セクションラベルを「個別の枠を手動管理（例外操作）」とする（§11 i18n）。機能・API は無変更（枠 CRUD は臨時営業・当日枠・長尺枠の正規手段として残る）。
- **タブ再編は表示順の変更のみ**で、各コンポーネントの props / API 契約は不変（`SlotTemplateManager` → `WeeklyScheduleManager` は §4.4 のリネーム＋統合。`pathPrefix:false` 規約により**コンポーネント名=ファイル名**で参照されるため、参照箇所の同時改修を弾内タスクに含める — `project_nuxt_pathprefix_false_component_name_misuse`）。

### 3.3 例外操作の前面化 — 「この日を休業にする」「臨時営業する」

管理タブ⑤に**例外日カレンダー**（月表示ミニカレンダー・`ScheduleExceptionPanel.vue` 新設）を置き、日クリックで 2 択ダイアログを出す。

#### 3.3.1 「この日を休業にする」= 既存の予約不可枠（全日・TEAM軸）作成のショートカット

- **新 API なし**（設計判断）: 実体は既存 `POST /reservation-settings/blocked-times`（`blockedDate=選択日, startTime/endTime=null（全日）, resourceType=TEAM, reason=任意`）。enforcement は機能B の runtime overlap（親 §5.B）がそのまま効く。
- **既存予約がある場合の警告と一括対応導線**: ダイアログ表示時に既存 `GET /blocked-times/impact`（親 §4.B）を全日条件で呼び、`affectedCount >= 1` なら
  1. 警告カード「この日には有効な予約が {n} 件あります」＋予約一覧（impact レスポンスの氏名・時間帯）
  2. 各行に「予約一覧タブで対応」導線（予約一覧タブへ遷移し、既存の管理者キャンセル/承認 UI で振替・キャンセル）
  3. 登録ボタンは disabled（BE の 409=RESERVATION_027 が最終防御・既存挙動不変）
- **会員へ告知したい休業は既存「緊急休業」へ誘導**: ダイアログに「予約者への通知・お知らせ配信が必要な場合は緊急休業を使う」リンク（既存タブ `EmergencyClosureForm`）。**予約不可枠（受付を閉じる）と緊急休業（告知・確認フロー）は別機能のまま**とし、統合しない（設計判断: 緊急休業は確認レコード・リマインド等の重い独自フローを持ち、混ぜると両方の単純さを失う）。

#### 3.3.2 「臨時営業する」= 定休日・営業時間外への単日テンプレ適用

**設計判断（2案比較 → 単日テンプレ適用 API を採用）**:

| 案 | 内容 | 評価 |
|---|---|---|

#### `POST /api/v1/teams/{teamId}/reservation-slot-templates/generate-single-day`

| フィールド | 型 | 必須 | バリデーション |
|-----------|---|------|-------------|
| `date` | String(date) | Yes | 明日以降（当日・過去は 400=PAST_DATE_SLOT 023 再利用。生成系の「当日は手動枠の領分」原則と統一）。上限: 今日から 90 日以内（horizon 外の遠未来生成を防ぐ・汎用 400） |

**レスポンス（200 OK）**: 既存 `GenerateSlotsResponse` と同型（`generatedCount` / `skippedExistingCount`。営業時間チェックを行わないため closed/outside 系カウントは常に 0）。

**エラー**: active テンプレ 0 件（対象曜日に 1 行もない）→ 400（`BusinessException`・「この曜日のテンプレートがありません」メッセージ・generate の状態検証と同作法）／401・403（ADMIN+）。**§4 の定期予約不可枠は生成をスキップしない**（機能B と同じ「生成はする・runtime で落とす」一貫方針 §4.2）。

- **horizon 外生成とウォーターマークの扱い（精査2パス A・必読）**: 本 API は horizon（28日）の**外**（tomorrow+28〜+90日）に `template_id` 付きセルを作れる唯一の経路である。日次バッチの差分レンジが参照する `lastGeneratedDate` は **horizon 上限でクランプした導出**（`MAX(slot_date) WHERE template_id=T AND slot_date <= tomorrow+27日`・F03.4.2 §5.4 追補）であるため、horizon 外の単日生成は**ウォーターマークに影響せず**、通常の週次生成は欠落しない（AC S-8③）。クランプを実装しないまま本 API を出すことは不可（W2-1 で同時実装）。
- **同日の全日休業（機能B・全日 TEAM blocked_times）との衝突（精査2パス F・挙動を一意に定義）**: FE は「臨時営業する」ダイアログ表示時に対象日の全日 TEAM 予約不可枠の有無を検査し、**存在する場合は警告カード「この日は休業に設定されています」＋「休業を解除してから実行してください」導線（当該 blocked_time の削除ダイアログへ）を表示し、実行ボタンを disabled** にする（生成しても全セルが runtime で UNAVAILABLE になり誰も予約できない=無意味な操作を入口で止める）。**BE はブロックしない**（生成はする・runtime で落とすの一貫方針 §4.2。休業解除を後で行う前提で先に枠だけ用意する運用を API 層で禁じない）。AC S-12。
- 認可: `@PreAuthorize("@accessGuard.isScopeAdmin(authentication, #teamId, 'TEAM')")`（テンプレ系 5 本と同一）。
- レートリミット: 既存 generate と同一 zone（`reservation-template-generate`・1チーム 2回/分・RESERVATION_044 再利用）を**共有**する（同種の生成資源保護。別 zone にする理由がない）。
- 監査ログ: `audit_logs` に記録（テンプレ系と同じ作法）。
- **FE**: 例外日カレンダーの「臨時営業する」ダイアログ =「適用する曜日ダイヤ」Select（既定=当日曜日）＋実行ボタン＋結果トースト。生成後にその日のセル一覧（マトリックスの単日ビュー）へ遷移して確認できる導線。

### 3.4 既存の生成基盤との整合棚卸し

| 既存資産（F03.4.2） | 本節の変更による影響 | 対応 |
|---|---|---|
| 日次バッチ（テンプレごと差分レンジ `[max(tomorrow, lastGeneratedDate+1), tomorrow+27日]`） | **クランプ追補が必要**（精査2パス A・F03.4.2 §5.4 改訂済）: 単日テンプレ適用（§3.3.2・最大+90日）が horizon 外に `template_id` 付きセルを作ると、素の `MAX(slot_date)` ではウォーターマークが跳ねて range が恒久に空 → **当該テンプレの通常週次枠が最大 2 ヶ月未生成**になる。`lastGeneratedDate` の導出を `MAX(slot_date) WHERE template_id=T AND slot_date <= tomorrow+27日` に**クランプ**することで根治。保存時自動生成（horizon 内）はクランプ後も従来どおりウォーターマークを前進させ、バッチは末尾 1 日へ収束する | **F03.4.2 §5.4 のクランプ追補を W2-1 で実装**（AC S-4 回帰＋S-8③が番人） |
| 冪等（先読み Set＋INSERT IGNORE＋`uq_rs_template_cell`） | 自動生成・単日適用とも同一経路を流用。並行（保存直後にバッチ/手動 generate）でも二重生成なし | 変更なし |
| ライン削除フロー（テンプレ停止 → 409 ガード → 未来枠 purge の番号順・F03.4.2 §5.5） | 無変更で整合。ライン削除がテンプレを止めるため、保存時自動生成の対象からも自然に外れる | 変更なし |
| 生成時に予約不可枠をチェックしない方針 | **単日テンプレ適用・§4 の定期不可枠にも同方針を貫徹**（生成はする・runtime で落とす） | §4.2 で明文化 |
| `ReservationSlotGenerationService` の公開シグネチャ | 単一テンプレ版・単日版（営業時間チェック省略）を**同クラスに追加**（別実装厳禁の原則維持）。内部の日付ループ・チャンク tx・冪等はプライベート共通部を共有 | 実装時にリファクタ（挙動番人: 既存 F-5〜F-9 green 維持） |

## 4. B) 定期予約不可枠（週次繰り返し・事由ラベル・公開可否）

「毎週火曜 19:00-20:00 = 研修」「毎週水曜 9:00-12:00 = スクール」のような**週次繰り返しの予約不可**を 1 回の登録で恒久化する。単発の `reservation_blocked_times`（機能B）は日付ごとに行が要るため、この用途では毎週の登録作業が発生していた。

### 4.1 DB設計 — `reservation_recurring_blocked_times`（新規）

**新規テーブルのため UUIDv7（アーキ原則6・`UuidV7Entity` 継承）。`team_id`/`created_by` はクロスドメイン参照のため FK なし（原則1）。`line_id` は同一 reservation ドメイン内 FK。**

**インデックス**

**制約・備考**
- **上限: 1チームあたり 50 行**（RESERVATION_047）。試算: 20ライン × 主要曜日数本で十分・判定は毎リクエストのメモリ突合のため小さく保つ。
- 時刻検証は既存 007/022 再利用（30分単位・start < end・最小30分）。
- **同一 (team, line, 曜日) 内のルール同士の時間帯重複は許可**（設計判断: 「研修」と「清掃」が重なっても判定は any-match で正しく、入口で禁じる利益がない。テンプレの重複禁止とは目的が違う——テンプレは二重生成の物理的衝突があるが、不可ルールは論理判定のみ）。
- **ライン削除フロー（F03.4.2 §5.5）への追補**: 手順 1（テンプレ停止）の直後に「当該ラインの定期予約不可枠を `is_active=FALSE` 化」を追加する（手順 1.5）。ラインが論理削除された後に RESTRICT FK が残るのは既存テンプレと同じ扱い。

### 4.2 enforcement — **runtime overlap 統合を採用**（生成時スキップは不採用）

機能B の思想（親 §5.B「enforcement は runtime overlap ユーティリティ 1 本・blocked_times に行を書くだけ・slot は CLOSE しない」）と、週次定期の「テンプレ的」性質のどちらに寄せるかの設計判断:

| 観点 | **runtime 統合（採用）** | 生成時スキップ（不採用） |
|---|---|---|
| 効く範囲 | テンプレ生成枠・**手動枠・既存枠・単日臨時営業枠のすべて**に即効 | テンプレ生成枠にしか効かない（手動枠・既生成枠は素通り＝穴） |
| ルール解除の反映 | 即時（次のリクエストから予約可能に戻る） | 「スキップされたセルは枠が存在しない」ため、解除後に**再 generate するまで枠が無い**（機能B 設計時に退けたのと同一の穴） |
| 事由ラベル表示（is_public） | セル（=枠）が存在するから **UNAVAILABLE セルに「研修」を載せられる** | 枠が無い＝セルは「−（枠なし）」となり、**事由を表示する場所自体が消える**（マスター要件と両立しない） |
| 二重管理 | 判定 1 本（機能B と同居） | 生成時と runtime の二重判定になる |
| 機能B との整合 | 「テンプレは BE に持たず具体時刻のみ」という機能B の単発設計とは異なり週次ルールを持つが、**enforcement 経路は同じ 1 本**に統合されるため思想の核（単一判定・行を書くだけ）は維持 | — |

**結論: 生成はする・表示/予約時に runtime で落とす**。機能B の 3 箇所（`listAvailableSlots` / `createReservation`（グループ経由含む）/ `ReservationGridService`）が自動追従する形で `ReservationUnavailabilityChecker` を拡張する。

**チェッカー拡張（実装指針）**

```
// 新メソッド（既存 isBlocked と並置・別実装厳禁の原則で 3 箇所が共有）
boolean isRecurringBlocked(slotDate, slotStart, slotEnd, slotLineId, rule):
    if !rule.isActive: return false
    if to3Letter(slotDate) != rule.dayOfWeek: return false      # F03.4.2 §5.2 と同じ 3 文字正準変換
    # 対象軸マッチ
    if rule.lineId == null:            resourceMatch = true      # チーム全体（共通枠含む全 slot）
    else:                              resourceMatch = (rule.lineId == slot.lineId)
    #   ※ slot.lineId == null（共通枠）はライン指定ルールの対象外（STAFF 軸の null 非一致と同じ規則）
    if not resourceMatch: return false
    # 時間帯 overlap（半開区間・機能B と同一）
    return slotStart < rule.endTime and rule.startTime < slotEnd
```

- 既存 `isBlocked`（9引数コア）は**変更しない**（既存テスト green 維持）。呼び出し 3 箇所は「単発 blocked_times の any-match **OR** 定期ルールの any-match」で合成する集約メソッド `isBlockedByAny(slot, blocks, recurringRules)`（オーバーロード追加）を使う。
- ルールの読み込みは `findByTeamIdAndIsActiveTrue(teamId)` の全件メモリ突合（上限 50 行・単発 blocked_times の日付ロードと同じ作法・N+1 なし）。
- **実測注記**: 現行チェッカーのシグネチャに `slotLineId` は無い（LINE 軸は未 enforce・実測）。本機能でコアに `slotLineId` を渡す必要が生じるため、F03.4.2 §5.7 が予告した「機能B の LINE 軸 enforce」（`reservation_blocked_times.resource_type='LINE'`）を**同じ弾で併せて配線する**（同一の引数追加で両方が成立し、二度手間を避ける）。

### 4.3 全日型・409 ガード・impact

- **全日型（start/end NULL）の週次ルールは作らない**（設計判断）: 「毎週火曜は終日休み」は営業時間（`reservation_business_hours.is_open=FALSE`）の領分であり、二重の表現手段を作ると「どちらを直せば休みが消えるのか」が分からなくなる。ダイアログに「終日休みにしたい場合は営業時間で火曜を定休日にする」ガイドを表示（§11 i18n）。
- **作成/更新時の 409 ガード（RESERVATION_027 再利用）＋ impact**: 機能B と同じく、overlap する active 予約（PENDING/CONFIRMED）が存在すれば 409。週次ルールは将来無限に効くため、**判定対象は「今日から 90 日先までの active 予約」**とする（枠の生成 horizon は 28 日・手動枠を含めても 90 日で実用上全件。90 日超の先の予約が後から衝突した場合は runtime 判定が新規予約を止めるだけで、既存予約はそのまま有効——この限界を設計書に明記し、AC R-6 で境界を固定する）。
  - impact: `GET /reservation-recurring-blocked-times/impact?dayOfWeek=&startTime=&endTime=&lineId=`（副作用ゼロ・氏名込み一覧＋対象日付リスト。機能B impact と同じ管理画面用途）。
  - クエリ: 既存 `findActiveReservationsOverlappingUnavailability`（機能B・親 §5.B）を写経し、「日付レンジ × 曜日フィルタ（アプリ層）× 時間帯 overlap × line 軸」で新設。

### 6.1 キャンセル待ち（waitlist）

> 親 §8 解決済み事項の「キャンセル待ちは Phase 3 スコープ外」は、本設計をもって**マスター指示により再起票**する（設計まで。実装は別裁可）。

#### 通知方式の設計判断 — **全員一斉通知・早い者勝ちを採用**（先着独占ホールドは不採用）

| 観点 | **全員一斉通知（採用）** | 先着 1 名へ順番通知＋N時間独占ホールド（不採用） |
|---|---|---|
| 並行制御 | 不要の追加なし。空き枠の取り合いは**既存のアトミック UPDATE（`incrementBookedCountIfAvailable`・capacity 基準）が既に解決済み** | 「ホールド中は他者の予約を弾く」仮予約状態が capacity 機構に割り込む＝FULL 判定の二重化 |
| バッチ | 不要（通知して終わり） | ホールド失効→次順位へ通知の連鎖バッチが必須 |
| 公平性 | 通知は同時・確保は先着（透明で説明しやすい） | 登録順に厳密だが、無反応者のホールドで枠が塩漬けになる |
| ADHD 配慮 | 「通知が来たら押す」の単純動線 | 「あなたの番です・期限あり」はプレッシャー型 |

#### DB — `reservation_waitlist_entries`（新規・UUIDv7）

| カラム名 | 型 | NULL | デフォルト | 説明 |
|---------|---|------|-----------|------|
| `id` | BINARY(16) | NO | UUIDv7 | PK |
| `team_id` | BIGINT UNSIGNED | NO | — | FKなし・INDEX |
| `slot_id` | BIGINT UNSIGNED | NO | — | FK → `reservation_slots.id` **ON DELETE CASCADE**（同一ドメイン・枠が物理削除されたら待ちも消滅が正） |
| `user_id` | BIGINT UNSIGNED | NO | — | FKなし（users ドメイン） |
| `status` | VARCHAR(20) | NO | `'WAITING'` | `WAITING` / `CANCELLED`（本人取消）/ `CONVERTED`（予約成立）。「期限切れ」は行を残さず**枠開始時刻経過で導出**（クリーンアップは §6.1 バッチ節） |
| `notified_at` | DATETIME(6) | YES | NULL | 最終通知時刻（再通知間隔制御） |
| `created_at` / `updated_at` | DATETIME(6) | NO | — | |

```sql
INDEX idx_rwe_slot_status (slot_id, status)
INDEX idx_rwe_user_status (user_id, status)
```

- **重複登録ガードはアプリ層**（`existsBySlotIdAndUserIdAndStatus(WAITING)` → 409=RESERVATION_049）。DB UNIQUE は張らない（設計判断: `UNIQUE(slot_id,user_id)` は「取消→再登録」を恒久に塞ぐ。MySQL に部分 UNIQUE がなく、生成カラム方式の複雑さはこの規模のレースリスク——同一ユーザーの同時二重クリック——に見合わない）。
- 上限: 1 ユーザー同時 WAITING 10 件・1 枠あたり 50 件（RESERVATION_051）。

#### API・結線

| メソッド | パス | 認証 | 説明 |
|---------|-----|------|------|
| POST | `/api/v1/teams/{teamId}/reservation-slots/{slotId}/waitlist` | 会員/公開（view ゲート＝予約作成と同一 `ReservationViewAccessGuard`） | 登録。**枠が FULL のときのみ**（AVAILABLE 枠は 400=RESERVATION_050「空きがあるためそのまま予約してください」）・過去/CLOSED 枠は既存検証再利用 |
| DELETE | 同上 | 本人 | 自分の WAITING を CANCELLED に |
| GET | `/api/v1/users/me/reservation-waitlist` | 本人 | 自分の待ち一覧（枠情報同梱） |
| GET | `.../reservation-slots/{slotId}/waitlist/count` | ADMIN+ | 枠別の待ち人数（管理画面表示用。**会員には人数を見せない**——競争心理の煽り防止・PII なし）。チーム解決と検査順序（D 群注記・精査2パス N）: パスの `{teamId}` に対する `@PreAuthorize isScopeAdmin` が先（非 ADMIN は **403**）→ その後 `slotId` を `findByIdAndTeamId(teamId)` で解決し、他チームの slot は **404** 秘匿（403→404 の順で一意） |

- **通知トリガ**: 空き復帰点は `decrementBookedCountAndReopen`（実測: キャンセル・却下経路が呼ぶ）に集約されている。この呼び出し成功（1 行更新）後に `ReservationSlotReopenedEvent` を発行し、`@TransactionalEventListener(phase = AFTER_COMMIT)` ＋ `@Async`（親 §「ADMIN 通知フロー」と同型・REQUIRES_NEW 規約 `feedback_transactional_event_listener_requires_new`）で当該 slot の WAITING 全員へ `NotificationHelper.notify`（アプリ内＋WebPush・新 `NotificationType.RESERVATION_WAITLIST_OPENING`・HIGH・"RESERVATION" カテゴリ、`RESERVATION_REMINDER` の隣に追加）。
- **再通知の抑制**: 同一 entry への通知は `notified_at` から **60 分未満なら送らない**（キャンセル連発時の通知洪水防止）。
- **成立時の消し込み**: `createReservation` / グループ作成の成功時、同一 (slot, user) の WAITING を CONVERTED へ（同一 tx 内・reservation ドメイン内）。
- **失効クリーンアップ**: 日次バッチ（生成バッチと同じ AM 0:15 帯を避け 0:45・`@SchedulerLock`）で「slot 開始時刻を過ぎた WAITING」を物理削除（履歴価値なし）。

### 6.2 定期予約（毎週繰り返し・会員側）

会員が予約確定時に「この予約を毎週繰り返す」を選ぶと、**同一ライン・同一曜日・同一時間帯**の枠を N 週分まとめて予約する。

#### 満席週の扱い — **スキップ＋結果明細を採用**（中断は不採用)

| 観点 | **スキップ（採用）** | 満席週で中断 |
|---|---|---|
| 結果 | 「8週指定→6件成立・2件スキップ（7/21 満席・8/4 枠なし）」を**1 回の操作で確定**し明細を返す | 途中で止まり残り週の再操作が必要（ADHD 配慮に反する） |
| 整合 | 各週は独立予約（後述 series）なので歯抜けでも矛盾なし | — |

#### 設計

- **リクエスト拡張（additive）**: 単枠 `POST /reservations` とグループ `POST /reservation-groups` に `repeatWeeks: Integer`（省略/1 = 従来どおり・2〜**12** 上限。13 以上は 400=RESERVATION_052）。
- **週ごとの枠解決**: 起点予約の (lineId, dayOfWeek, startTime, endTime〔グループは構成セル列〕) を `slot_date + 7k` で検索。「枠が存在しない」「FULL」「予約不可枠 overlap」の週はスキップし、明細（`skippedWeeks[] = {date, reason: NOT_GENERATED|FULL|BLOCKED}`）で返す。horizon（28日）超の週は枠未生成のため大半 NOT_GENERATED になる——**FE は repeatWeeks の選択肢を「先の週は枠が作られ次第の手動予約」ガイド付きで 4 週までを推奨表示**し、5〜12 週は展開して選べる段階開示にする（枠生成が 28 日 rolling である限り、12 週指定の後半は構造的にスキップされる。この制約を UI で正直に伝える——症状を隠さない原則）。
- **series 表現**: `reservations` に `recurring_series_id BINARY(16) NULL` を ALTER 追加（アプリ層採番 UUIDv7・専用親テーブルなし——`group_id` 案(b) と同じ方式。`group_id`（同日連続枠の横軸）とは**独立直交**し併存可能）。INDEX `idx_rv_series (recurring_series_id)`。
- **キャンセル動線**: 予約詳細に「この回のみ / 以降すべて」の 2 択（`DELETE /reservations/{id}/cancel` に `scope: THIS_ONLY|THIS_AND_FOLLOWING` を追加・既定 THIS_ONLY。THIS_AND_FOLLOWING は series 内の当該日以降の active 予約を既存キャンセル検証（締切・権限）を**各行に適用**しながらループ）。グループ予約の series はグループ単位で同 2 択。
- **MANUAL 承認チームの負荷**: N 週分がすべて PENDING になるため、管理者の予約一覧に series まとめ承認（`scope=SERIES` の confirm）を追加。単票 confirm も従来どおり可能。
- レートリミット: §6.4 の予約作成バケットで **1 series = 1 消費**（週数ぶん消費しない。1 操作は 1 意思決定のため）。

### 6.3 仮押さえ自動失効（PENDING の期限切れ自動キャンセル）

MANUAL 承認チームで承認されないまま放置された PENDING が枠を塞ぎ続ける問題への対処。

- **チーム設定**: `reservation_policies` に ALTER 追加 `pending_expire_hours INT NULL DEFAULT 24`（**NULL = 自動失効しない／DB DEFAULT 24 で新規・既存とも既定 24 時間**——マスター確定「チーム設定・既定24h」。範囲 1〜168・更新は既存 `PATCH /reservation-settings` に additive 追加、`clearPendingExpireHours: true` で無効化——`clearApprovalMode` と同形）。
- **バッチ**: `ReservationPendingExpireBatchService`（新設・**`ReservationReminderDispatchBatchService` / `ReservationWaitlistCleanupBatchService` 写経**）。`@BatchEndpoint(name = "reservation-pending-expire")` ＋ `@Scheduled(fixedDelay = 300_000)`（5 分間隔・リマインドの 1 分と負荷帯を分離）＋ `@SchedulerLock(name = "reservationPendingExpireBatch")`。
- **失効対象（W2-6 実装時に改訂・殿の裁定 2026-07-29）**: チームの `pending_expire_hours` が有効（NULL でない）ことを前提に、以下の**いずれか**を満たす `status=PENDING`。
  - **(a)** `booked_at + pending_expire_hours <= now(注入 Clock)`
  - **(b)** **枠の終了時刻を経過している**（＝承認されないまま予約日を過ぎた仮押さえ）

  > **⚠ 初版からの変更点と理由**: 初版は (b) を「枠開始を過ぎた PENDING は既存の自動 NO_SHOW バッチの管轄」として**対象外**にしていた。しかし **予約ドメインに自動 NO_SHOW バッチは実在しない**（実測。存在するのは管理者手動の `POST /{reservationId}/no-show` のみ。`RecruitmentNoShowDetectBatch` は recruitment ドメインの別機能）。初版のままでは「承認されないまま予約日を過ぎた仮押さえ」が**永久に PENDING で残り枠を塞ぎ続ける**——本機能の目的を半分取りこぼす。よって (b) を対象に含める。
  >
  > **ポリシー行が無いチームの扱い**: `reservation_policies` は初回の設定変更で初めて行が作られるため大半のチームは行を持たない。行が無いチームは **既定 24 時間**として扱う（`COALESCE`。本節の「新規・既存とも既定 24 時間」および `getOrDefault` が GET で 24 を返すことと挙動を一致させる）。一方、行が存在して `pending_expire_hours IS NULL` のチーム（管理者が `clearPendingExpireHours` で明示的に無効化）は (a)(b) とも対象外。
- **処理**: `ReservationEntity.cancel(reason, CancelledBy.SYSTEM)`（**enum 実在・実測**）で `status=CANCELLED`・`cancelReason` に定型文 → **`ReservationSlotService.decrementAndReopen`**（設計初版の `decrementBookedCountAndReopen` は実在せず、実メソッド名は `decrementAndReopen`）で枠復帰。同メソッドは DB が実際に FULL→AVAILABLE 遷移を起こしたときのみ `ReservationSlotReopenedEvent` を発行し、§6.1 のキャンセル待ち通知が AFTER_COMMIT で連鎖発火する（**独自にイベントを撃たない**統合点）→ 申込者へ通知（新 `NotificationType.RESERVATION_PENDING_EXPIRED`・NORMAL）。
- **トランザクション境界**: 失効 1 単位（単枠 1 件 / グループ 1 組）を `REQUIRES_NEW` の独立トランザクションにし、バッチ本体には `@Transactional` を付けない。バッチ全体を 1 tx で囲むと、内側の `@Transactional` メソッドから例外が抜けた時点で participating tx が rollback-only になり、**行単位 try/catch が実質無効化**される（1 件の失敗が全件を巻き込む）ため。これにより「単位内は原子的（部分失効なし）・単位間は独立」を両立する。対象抽出は slot・policy を join した固定 3 クエリ（候補・グループ兄弟行・枠）で N+1 を出さない。注入 `Clock`・最小 context 番人テスト（写経元と同じ作法）。
- グループ予約（PENDING の series/group）: 代表行基準でグループ単位に失効（部分失効を作らない——グループの原子性維持・F03.4.3 と整合）。
- FE: 予約フォームの MANUAL チーム注意書きに「{n}時間以内に承認されない場合は自動キャンセルされます」を追加（設定値を表示・§11）。

### 6.4 予約作成の頻度レートリミット（親 §8 バックログ⑩の設計確定）

- **単枠 `POST /reservations` とグループ `POST /reservation-groups` を同一バケット**で数える（親 §6 既存記述どおり。別バケットだと 5+5 の買い占めが可能）。

## 12. 非機能・アーキ制約

- **UUIDv7（原則6）**: 新規テーブル（recurring_blocked_times / waitlist_entries）は `UuidV7Entity` 継承。既存テーブルの ALTER は ID 型不変。
- **クロスドメインFK禁止（原則1）/ CASCADE 同一ドメインのみ（原則2）**: 新規 FK は `line_id`→reservation_lines（RESTRICT）・waitlist `slot_id`→reservation_slots（CASCADE・同一ドメイン）のみ。`team_id`/`user_id`/`created_by` は FK なし。
- **@Transactional ドメイン内（原則5）**: 全処理 reservation ドメインに閉じる。通知は AFTER_COMMIT リスナー経由（既存規約）。
- **horizon 一覧（意図的な差・精査1パス反映）**: 本書に登場する期間はすべて**意図して別値**であり、統一しない:

  | 用途 | 期間 | 根拠 |
  |---|---|---|
  | テンプレ自動生成・日次バッチ | **28 日 rolling**（`tomorrow + 27日`） | F03.4.2 既定 horizon（週間テンプレの実用先読み） |
  | 単日テンプレ適用（臨時営業）の対象日上限 | **今日から 90 日以内** | 遠未来の誤生成防止。振替営業の告知実務（数週間〜2ヶ月前）を包含 |
  | 定期ルールの 409 ガード / impact | **今日から 90 日先まで** | 予約は生成 horizon（28日）＋手動枠にしか存在せず 90 日で実用上全件。無限走査の回避（§4.3） |

- **判定コスト**: 定期ルールはチームあたり最大 50 行のメモリ突合。grid レンジ呼び（最大 3,528 セル）× 50 ルールでも 18 万回の軽量比較で実用圏（既存の単発 blocked 判定と同オーダー）。クエリはチーム単位 1 本の定数（N+1 なし）。**予約作成のホットパス（`createReservation`／グループ作成）には `findByTeamIdAndIsActiveTrue` の 1 クエリが恒常追加**される（精査1パス反映・単発 blocked_times の日付ロードに並ぶ 2 本目。インデックス `idx_rrbt_team` 下の最大 50 行読みで許容。キャッシュは導入しない——鮮度優先・機能B と同方針）。
- **バッチ負荷帯の分離**: 生成 AM0:15 / waitlist クリーンアップ AM0:45 / リマインド 1 分間隔 / pending 失効 5 分間隔（`@SchedulerLock` 必須・最小 context 番人テスト各 1 本）。
- **OpenAPI**: 全 API 変更は additive（既存フィールドの型変更・削除なし。generate の `deprecated: true` 付与は非破壊）。BE 変更後 `docs/openapi.json` 再生成＋`npm run generate:types` を同一 PR（`project_openapi_json_chronic_drift`）。
- **シャーディング**: 新規表は `team_id` 保持（既存 reservation 系と同整理）。
