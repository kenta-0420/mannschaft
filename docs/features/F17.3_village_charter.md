## 1. 概要・背景

### 1.1 課題 — 「村の拠りどころ」を残す場所が無い

【確認済み】村には掲示板・タイムライン・ロビー・歳時記・お祭り・寄合・練習試合募集・ニュースレター（村だより）・村史（行事アーカイブ・F17.2）が揃った。だが、**村が「どういう約束で集う場なのか」という村自身のルール（憲章）を、明文で・構造化して残す場所が無い**。掲示板のスレッドに書いても流れてしまい、村の入口で新参者が「この村はどんな約束の場か」を一目で読めない。

## 2. マスター発案・御裁可済みの決定事項【御裁可済・変更禁止】

以下はマスターが発案し決定済みであり、本書はこれを前提に設計する。設計中に矛盾が生じても**この決定を動かさない**。

1. **条を 1 レコードとする構造化データ・条番号は保存しない**【御裁可済】
   条文は自由文の 1 本メモではなく、**1 条 = 1 レコード**の構造化データで持つ。**条番号（第一条・第二条…）は DB に保存せず、並び順（`sort_order`）から表示時に自動採番する**。途中への条挿入・条削除で番号を振り直す作業が要らないことが本旨（§6）。

2. **編集は現役の村長/長老のみ・最軽量エディタ**【御裁可済】
   編集できるのは現役の HEADMAN/ELDER のみ。UI は**1 行入力＋「＋条を追加」「＋付則を追加」の最軽量エディタ**（ADHD 入力摩擦ゼロ。CLAUDE.md「入力摩擦ゼロ・シンプル＋詳細はモーダル」）。

3. **公開範囲**【御裁可済】
   **PUBLIC 村は未参加者（ログイン済）にも憲章を公開**する（加入判断材料・相性カードと並ぶ後押し）。**UNLISTED 村の非メンバーは 404 で存在ごと秘匿**（相性 API `loadPublicVillageOrHide` と同方式）。UNLISTED 村人・SYSTEM_ADMIN は閲覧可。

4. **制定日は自動・改定日は手動**【御裁可済】
   制定日（`enacted_at`）は**初回作成時に自動セット**。改定日（`last_revised_at`）は手動「**改正を確定**」ボタンで確定し、**改定履歴（日付＋任意メモのみ・条文スナップショット無しの軽量履歴）に 1 行追記**する。

5. **策定者は村ニックネームを焼き付け、退村・退会後も残す**【御裁可済・2026-07-22 マスター裁定】
   策定者は複数可・表示順あり。制定・追加時の**村ニックネームを `nickname_snapshot` に焼き付け**、**退村しても・アカウント退会しても名前が残る**。退会時は `user_id` のみ NULL 化して個人へのリンクを切断する（原則4「投稿・履歴は保持し個人情報のみ消去」と整合。**実名は一切保存しない**＝§10 G4）。

## 3. 機能③ 公開範囲と公開ゲート

### 3.1 目的

村憲章は「この村はどういう約束の場か」を示す**加入判断材料**である。よって PUBLIC 村では**未参加者（ログイン済）にも公開**して加入の後押しにする。一方、UNLISTED 村は「そもそも見つからないべき村」なので、非メンバーには憲章の存在ごと秘匿する（存在秘匿）。

### 3.2 公開ゲートの設計【提案・確定】

公開ゲートは **F17.2 相性 API の主金型 `loadPublicVillageOrHide` を土台にしつつ、UNLISTED 時のみメンバー/SYSTEM_ADMIN バイパスを足したハイブリッド**とする。相性 API（`loadPublicVillageOrHide`）は UNLISTED を**無条件 404** にするが、憲章は「UNLISTED 村の村人・SYSTEM_ADMIN は読める」必要があるため、そこだけ掲示板閲覧認可（`checkVillageBulletinViewAccess`）の member/SYSTEM_ADMIN 分岐を移植する。

新設 `VillageCharterAccessService#loadReadableVillageOrHide(UUID villageId, Long viewerId)`【提案】の判定表:

| 村の状態 | 閲覧者 | 挙動 |
|---|---|---|
| 不存在／`deleted_at` 非 NULL／`archived_at` 非 NULL | 任意 | **404**（`VILLAGE_NOT_FOUND`・IDOR 対策で統一） |
| `visibility = PUBLIC` | ログイン済（メンバー/非メンバー問わず） | 憲章を返す |
| `visibility = UNLISTED` | 現役メンバー（`village_memberships` の USER 現役行・`left_at`／`banned_at` とも NULL） | 憲章を返す |
| `visibility = UNLISTED` | SYSTEM_ADMIN | 憲章を返す |
| `visibility = UNLISTED` | 上記以外（非メンバー） | **404**（存在秘匿・架空 ID への応答と区別を与えない） |
| 未ログイン | 任意 | **401**（Controller 入口の `SecurityUtils.getCurrentUserId()` が投げる） |

- **なぜ 404 で秘匿するか（`docs/security` 存在秘匿方針）**: UNLISTED 村に非メンバーが「403（＝存在するが権限なし）」を受け取ると、「この村は存在する」という手掛かりを与える。相性 API と同じく **404 に寄せて「架空の村 ID への応答」と区別がつかないようにする**（存在秘匿優先）。
- **`archived_at`（凍結）も read では 404 に畳む**【🟠G 精査反映】: 相性 API の `loadPublicVillageOrHide`【確認済み・`VillageAffinityService.java:125-133`】は `deleted_at` のみを弾く（`archived_at` を明示チェックしない）。一方、掲示板 read 認可 `checkVillageBulletinViewAccess` は **`villageRepository.findByIdAndDeletedAtIsNullAndArchivedAtIsNull(...)`**【確認済み・`VillageBulletinAccessService.java:73-75`】で `deleted_at`／`archived_at` の両方を弾いて `VILLAGE_NOT_FOUND`（404）にする。**憲章 read はこの掲示板側の実体（`findByIdAndDeletedAtIsNullAndArchivedAtIsNull`）に揃え、凍結村（`archived_at` 非 NULL）も 404 に畳む**（凍結村の憲章を閲覧させない・上表の「`archived_at` 非 NULL → 404」はこの実体で担保する）。
- **現役メンバー判定**は掲示板前例と同じ `village_memberships` の `subject_type=USER`＋現役（`left_at`／`banned_at` NULL）で行う（`PostingIdentityService#isUserVillageMember` 相当を流用）。
- **認可番人（`AuthzControllerGuardArchTest`・Wave4）整合**: GET 憲章はデータ依存の開放条件（非メンバーに開く）ゆえ `@PreAuthorize` で表現できない。相性 Controller と同じく **`@AuthorizedInService` マーカー**を付与し、認可の根拠（PUBLIC のみ／UNLISTED はメンバー・SYSTEM_ADMIN のみ／それ以外 404）をコメントで明示する（`VillageAffinityController` の前例に倣う）。

### 3.3 編集系は「村状態ガード → 編集権限」の2段【提案・🔴A 精査で確定】

> ⚠️ **初版の「write に公開ゲート不適用」は撤回する。** write 系は公開ゲート（PUBLIC/UNLISTED の可視性判定）とは別に、**削除済み・凍結済みの村への書き込みを拒否する村状態ガードが必須**である（凍結村に条を足せてはいけない）。祭作成の金型 `VillageFestivalService.createFestival`【確認済み・`:110-111`】が **`loadActiveVillage(villageId)` → `requireHeadmanOrElder(villageId, actorUserId)`** の順で 2 段構えなのに倣う。

- 憲章の**編集（POST/PUT/DELETE/PATCH の全 write 系）は、次の 2 段を必ずこの順で通す**:
  1. **村状態ガード** — `VillageCalendarService#loadActiveVillage` 相当【確認済み・`VillageCalendarService.java:253-263`】: 不存在／`deleted_at` 非 NULL → **404**（`VILLAGE_NOT_FOUND`）、`archived_at` 非 NULL → **`VILLAGE_ALREADY_ARCHIVED`**【確認済み・`VILLAGE_027`・`:93`】。
  2. **編集権限** — `requireHeadmanOrElder(villageId, actorUserId)`（§4.1）で現役 HEADMAN/ELDER に限定。違反は `MODERATION_FORBIDDEN`（403）。
- 公開ゲート（§3.2・PUBLIC/UNLISTED の可視性判定）は **read 専用**で write には適用しない。write は「可視性に関わらず、生きている村の現役村長/長老のみ」。
- **金型準拠**: 既存 `VillageCalendarService`／`VillageFestivalService`／`VillageMeetupService` の write メソッドはすべて `loadActiveVillage(...)` を先頭で呼ぶ。憲章 write もこれに揃え、`VillageCharterService` 内に `loadActiveVillage` 相当を持つ（共有ヘルパ化は §15.4 実装工程で検討）。

## 4. 機能① 条文管理と編集権限

### 4.1 編集権限【御裁可済・前例流用】

- 編集は**現役 HEADMAN/ELDER のみ**【御裁可済・決定2】。判定は既存 `VillageBulletinAccessService#requireHeadmanOrElder(villageId, actorUserId)`【確認済み・`:161`】を流用する。これは「現役」判定（退村 `left_at`／BAN `banned_at` を除外する `findActiveByVillageIdAndSubject`）込みで、HEADMAN/ELDER 以外は **`MODERATION_FORBIDDEN`（403）** を投げる。
- **新規エラーコードを増やさない**: 編集権限違反は既存 `MODERATION_FORBIDDEN` を流用する（掲示板ニュースレターと同じ扱い・認可述語の一元化）。
- SYSTEM_ADMIN は編集**しない**（憲章は村の自治物。運営の代理編集は本書スコープ外）。read の SYSTEM_ADMIN バイパス（§3.2）は監査目的の閲覧であって編集権限ではない。

### 4.2 最軽量エディタ（ADHD 入力摩擦ゼロ）【御裁可済】

- UI は**1 行入力＋「＋条を追加」「＋付則を追加」ボタン**。条を足す・本文を書く・付則を添える、以外の操作を最初の画面に出さない（詳細は必要時にモーダル/インライン展開・CLAUDE.md 段階開示）。
- **インライン 1 行編集＋自動保存**方式（Dialog を挟まない。募集カテゴリの Dialog 方式より軽い）。編集は各条の本文を直接クリックして書き換え、フォーカスアウト or 明示保存で `PUT .../articles/{id}` を飛ばす（§4.4）。この編集体験は村機能で**初の新規設計**（§9.3）。

### 4.3 条の構造【御裁可済・§2 決定1】

- **1 条 = 1 レコード**（`village_charter_articles`・§13）。条文 `body`（TEXT・必須）＋付則 `supplement`（TEXT・任意）。
- **条番号は保存しない**。表示採番は §6 の並び順から導出する。

### 4.4 API【提案】

すべて `/api/v1/villages/{villageId}/charter/...` 配下。read は §3.2 の公開ゲート、**write は §3.3 の 2 段（`loadActiveVillage` 村状態ガード → `requireHeadmanOrElder`）を先頭で通す**。下表「権限」列の write 系は、この 2 段通過を前提とする。

| メソッド / パス | 権限 | 用途 |
|---|---|---|
| `GET  .../charter` | §3.2 公開ゲート（非メンバー可・PUBLIC のみ・UNLISTED はメンバー/SYSTEM_ADMIN） | 憲章メタ＋条一覧（自動採番）＋策定者＋改定履歴を返す |
| `POST .../charter/articles` | §3.3 2段（村状態→現役 HEADMAN/ELDER） | 条を**末尾に追加**（自動採番。**親 charter 行の悲観ロックで直列化**・§4.5。初回はここで charter が自動生成され `enacted_at` がセット） |

| `DELETE .../charter/articles/{articleId}` | §3.3 2段 | 条を論理削除し、残る条を再連番（**親 charter 行の悲観ロックで直列化**・§6.3・version 非同送） |
| `PATCH .../charter/articles/order` | §3.3 2段 | 条の並び順を一括更新（**親 charter `@Version` 楽観ロック層2**・`charterVersion` 同送・競合 409・§7） |

| `POST .../charter/revisions` | §3.3 2段 | 「**改正を確定**」＝`last_revised_at` 更新＋改定履歴に 1 行追記（§8） |

### 4.5 憲章の自動生成（初回作成）【提案・確定】

- 憲章に「作成」専用の EP は設けない。**最初の条を `POST .../charter/articles` したときに、当該村の `village_charters` が無ければ自動生成し、`enacted_at = now` をセット**する（制定日の自動セット・§8.1）。以後の条追加では既存 charter を使う。
- **1 村 1 憲章**は `village_charters.village_id` の UNIQUE（§13）で担保。並行初回作成（2 管理者が同時に最初の条を足す）で UNIQUE 違反が出た場合は、`DataIntegrityViolationException` を捕捉して**1 回だけ再取得→既存 charter に append** にフォールバックする（F17.2 §4.4.1 の upsert 冪等リトライと同思想）。
- **並行 append の `sort_order` 直列化＋トランザクション境界【🔴B 殿裁定「方式(a)改良版」＋🟠5 精査】**: `POST articles`（および `DELETE articles/{id}` の再連番）は**クライアントに version を同送させない**。代わり、サーバ側で**親 `village_charters` 行を悲観ロック（`@Lock(LockModeType.PESSIMISTIC_WRITE)` を付けた `findById` 相当・`SELECT ... FOR UPDATE`）で取得してから `max(sort_order)+1` 採番・再連番を行う**ことで、同一 charter への並行書き込みを**行ロックで直列化**する。これにより 2 管理者が同時に条を追加しても `sort_order` は重複せず連番が保たれる（クライアントに 409 を返さず、末尾追加は常に成功させる）。悲観ロックは `charter_id` 単位（村内の 1 行）で、条本文編集（層1）とは別レーンなので他条の同時編集を妨げない。
- **トランザクション境界（🟠5 明記）**: `POST articles` は**サービスメソッド 1 本＝1 トランザクション内で「親 charter 行を FOR UPDATE 取得 → `max(sort_order)` 採番 → 条を insert → 親 charter を save（層2 `@Version` バンプ・§7）」まで完結**させる（メソッド戻り＝コミットで行ロック解放）。`DELETE articles/{id}` も同一トランザクション内で「親 FOR UPDATE → 条 soft delete → 残条 bulk UPDATE 再連番 → 親 save（層2 バンプ）」まで閉じる。ロックを跨トランザクションで持ち越さない。
- 策定者・改定履歴が空でも憲章は成立する（条が 1 本以上あれば「制定済み」）。

## 5. 機能⑤ 策定者（複数可・表示順あり）

### 5.1 目的

「誰がこの村を興し・約束を定めたか」を村の史料として残す。策定者は複数（開村メンバー）で、表示順を持つ。村ニックネームの世界に閉じ、**実名は一切保存しない**（§10 G4）。

### 5.2 村ニックネームの焼き付け【御裁可済・2026-07-22 裁定】

- 策定者を `POST .../charter/drafters`（body: `userId`）で追加するとき、サーバは**その時点の村ニックネームを解決して `nickname_snapshot`（VARCHAR(40)）に焼き付ける**。
- 解決順は既存 `resolveUserDisplayName`【確認済み・`VillageMeetupService.java:881`】と同一: **村内ニックネーム（`findByUserIdAndVillageId`）→ 全村共通ニックネーム（`findByUserIdAndVillageIdIsNull`）→ `"USER:#{userId}"`**。ただし **`resolveUserDisplayName` は `VillageMeetupService` の private メソッド**で直接呼べないため、§15.4 の準備工程で**共有ヘルパ（`VillageNicknameResolver` Bean 等）へ抽出**してから憲章サービスが呼ぶ（既存 3 サービスの複製もこれに寄せる・重複ドリフト防止）。
- **なぜスナップショットか**: ニックネームは後から変わりうるし、退村・退会で消える。憲章の策定者は「制定当時の名」を史料として固定するのが自然（F17.2 村史のスナップショット思想と同じ）。焼き付け後は、本人がニックネームを変えても・退村しても・退会しても、憲章に刻まれた名は残る。
- **`user_id` は別列で保持**（NULL 許容・FK 無し）。退会時に **`user_id` のみ NULL 化**して個人へのリンクを切り、`nickname_snapshot`（仮名文字列）は残置する（§11）。

### 5.3 表示順【提案】

- `sort_order`（0 始まり連番）で表示順を持つ。追加時は末尾（`max(sort_order)+1`）。並び替え UI は v1 スコープ外（追加順で足りる。将来拡張・§16）。DELETE 後の詰め直しは条ほど厳密でなくてよいが、条と同じく残存行を昇順に振り直す（実装簡素化のため条の再連番ロジックを共用してよい）。

### 5.4 重複防止【提案】

- 同一ユーザーを二重に策定者登録しようとした場合は **`CHARTER_DRAFTER_DUPLICATE`（409）** で拒否（冪等に握りつぶさず明示エラー・対処療法禁止）。UNIQUE `uk_vcd_charter_user (charter_id, user_id)` で DB レベルも担保（§13）。**退会後の複数 NULL は MySQL の UNIQUE が NULL を相異と扱うため共存可**（退会者の行が複数残っても UNIQUE に抵触しない）。

### 5.5 API 応答（策定者）【提案】

- `DrafterResponse`: `id`(UUID)・`displayName`(string=`nickname_snapshot`)・`sortOrder`(int)。**`user_id` は応答に載せない**【御裁可済み既定・G4】。理由: 策定者は「村ニックネームの名」で見せる史料であり、実名世界（user）への横串リンクを作らない（所属村一覧がニックネームすら返さないのと同思想・F17.2 §9.3）。

## 6. 機能② 条の並び順・自動採番

### 6.1 条番号非保存・表示時採番【御裁可済・§2 決定1】

- 条番号は `village_charter_articles` に**保存しない**。表示時に、**論理削除されていない条を `sort_order` 昇順に並べ、先頭から `index+1` を「第 N 条」として採番**する。
- API 応答 `ArticleResponse.articleNumber`(int) は**この導出値**（永続列ではない）。`sort_order` 自体は応答に露出しない（内部順序）。

### 6.2 sort_order に UNIQUE を張らない理由【提案・確定】

- `sort_order` に一意制約は**張らない**【御裁可済み既定】。連番の一意性はアプリ層で保証する。
- **理由**: (1) 並び替え・再連番の途中状態（2 条のスワップ等）で一時的に `sort_order` が重複しうるため、DB の UNIQUE があると中間状態で違反する。(2) 論理削除済み行も同じ `sort_order` 空間に残る（`deleted_at` 非 NULL の行を UNIQUE から除外する部分 UNIQUE は MySQL では書けない）。よって物理 UNIQUE は不適で、**アプリ層で「非削除条を 0,1,2,… の連番に保つ」不変条件を維持**する。
- インデックスは `idx_vca_charter_sort (charter_id, sort_order)`（採番順取得の高速化）を張る（一意ではない）。

### 6.3 再連番の仕様【提案・確定】

不変条件: **「同一 charter の `deleted_at IS NULL` の条は、`sort_order` が 0,1,2,… の隙間なし連番」**。以下の操作でこれを維持する。

**🟠 ロック順序統一の原則【第2パス精査・殿裁定・デッドロック封殺】**: **全構造変更 EP（`POST`／`DELETE`／`PATCH order`）は、まず親 `village_charters` 行を `@Lock(PESSIMISTIC_WRITE)`（`SELECT FOR UPDATE`）で先取りし、その後に条行を触る**。ロック取得順を「**親 charter 行 → 条行**」で全 EP 統一することで、`DELETE`（もし「条行→親行」の順で取ると）と `PATCH order`（「条行→親行」）が同一憲章で同時走行したときの**InnoDB ロック順序逆転デッドロック（→未ハンドリング 500）を機構的に封殺**する。`PATCH order` は親行の悲観ロック取得**後**に `charterVersion` の楽観一致検査を行い（不一致なら 409・意味論温存・下記）、`POST`／`DELETE` は親行ロック後に採番・再連番して親を save する。

| 操作 | sort_order の扱い | ロック順序（親→子で統一） | 層2 `@Version` | 競合応答 |
|---|---|---|---|---|
| 末尾追加（`POST articles`） | `max(現存)+1`（0 件なら 0） | 親 charter 行 FOR UPDATE → 条 insert | **バンプする**（親 save） | なし（悲観直列化・§4.5） |
| 論理削除（`DELETE articles/{id}`） | `deleted_at=now`→残存条を 0,1,2,… へ再連番 | 親 charter 行 FOR UPDATE → 条行 | **バンプする**（親 save） | なし（悲観直列化） |
| 並び替え（`PATCH articles/order`） | `articleIds` の順に 0,1,2,… 再付与 | 親 charter 行 FOR UPDATE → **`charterVersion` 楽観検査** → 条行 | **バンプする**（親 save） | version 不一致→409／集合不一致→400 |
| 本文/付則更新（`PUT articles/{id}`） | 変更しない | 条行のみ（親ロック不要・独立レーン） | 触らない | 条 `@Version` 不一致→409（層1） |

- **`POST`／`DELETE` は悲観直列化で 409 を返さない・`PATCH order` のみ 409【🔴B 殿裁定「方式(a)改良版」】**: 末尾追加・削除は「今の末尾に足す／今ある条を消す」操作で、**クライアントが見た構造が前提ではない**（並行で別条が増減しても意味は壊れない）。よって親行悲観ロックで直列化し、409 を返さず常に成功させる。一方 `PATCH order`（並び替え）は**クライアントが画面で見た条の並びを丸ごと再指定する操作**なので、「見た構造が古い」なら 409 が正しい意味を持つ。
- **層2 `@Version` は POST/DELETE/PATCH order の全構造変更でバンプする【🟠4 殿裁定・第2パス観点2 同時解消】**: 上表のとおり 3 EP とも親を save して層2 `@Version` を++する（親を FOR UPDATE で load→save する実装ゆえ自然にバンプ）。これにより **「並び替え中に別管理者が条を追加/削除して構造が変わった → その POST/DELETE が層2 version を上げている → 後続の `PATCH order` は手元の古い `charterVersion` で 409」** が**機構的に成立**する（§7 の物語が実装と一致）。悲観ロックはデッドロック封殺と `sort_order` 直列化を、層2 楽観検査は PATCH order の「古い構造」検知を担う（役割分担）。
- **再連番の bulk UPDATE は層1 `@Version` を触らない【🟠C 精査反映】**: `DELETE`／`PATCH order` の再連番は、**残存条の `sort_order` のみを更新する bulk UPDATE（JPQL の `UPDATE ... SET sortOrder = ...`／ネイティブ UPDATE）で行い、各条エンティティの層1 `@Version` をバンプしない**（`sort_order` は「構造＝charter の持ち物」であって「その条の本文の版」ではない）。バンプするのは**親 charter の層2 `@Version` のみ**。これにより「別条を同時編集している管理者の層1 version が、無関係な並び替え/削除で勝手に上がって 409 になる」事故を防ぎ、**§7 の『別条の同時編集は衝突しない』独立性主張を守る**。
- **`PATCH articles/order` の集合検証**: 親行ロック・`charterVersion` 検査を通過した後、リクエストの `articleIds` が**当該 charter の非削除条の id 集合とちょうど一致**するか検証する（欠落・余分・重複はすべて **400**）。**400 は「version は一致するが articleIds 集合が不正（重複・不足）」の場合に限る**（version 不一致は先に 409 で弾かれる・§17.3 AC-13 注記）。全条の順序を過不足なく指定させることで、部分並び替えによる連番の破れを防ぐ。

## 7. 同時実行制御の設計（悲観ロック直列化＋2 層楽観ロック）

村憲章は「条の本文編集（局所・高頻度）」と「条の構造変更＝追加/削除/並び替え（全体影響・低頻度）」で衝突の性質が違うため、**悲観ロック（デッドロック封殺＋直列化）と 2 層の楽観ロック（衝突検知）を組み合わせる**【提案・🔴B＋🟠4＋第2パス デッドロック裁定で確定】。

**土台となるロック順序統一の原則（§6.3）**: 全構造変更 EP（`POST`／`DELETE`／`PATCH order`）は**親 `village_charters` 行を `@Lock(PESSIMISTIC_WRITE)` で先取り → 条行**の順でロックする。この統一により `DELETE`×`PATCH order` の並行走行でも**ロック順序逆転デッドロック（未ハンドリング 500）が起きない**。

| 制御 | 対象 | 守る操作 | 競合時 |
|---|---|---|---|
| **層1（条単位・楽観）** | `village_charter_articles.version`（`@Version`） | `PUT .../articles/{id}`（本文/付則の in-place 更新のみ・親ロック不要の独立レーン） | `CHARTER_ARTICLE_VERSION_CONFLICT`（409） |
| **層2（憲章全体・楽観検査）** | `village_charters.version`（`@Version`） | **`PATCH .../articles/order`（並び替え）**で `charterVersion` を同送し、親行の悲観ロック取得**後**に楽観一致検査 | `CHARTER_ORDER_VERSION_CONFLICT`（409） |
| **悲観直列化（憲章全体・親行）** | `village_charters` 行の `SELECT FOR UPDATE`（全構造変更 EP の先頭） | `POST`／`DELETE`／`PATCH order` すべて（採番・再連番の直列化＋デッドロック封殺） | 409 を返さず行ロックで直列化（`POST`/`DELETE`）。`PATCH order` はロック後の層2 検査で 409 |

- **層2 `@Version` は 3 EP すべてでバンプ【🟠4 殿裁定】**: `POST`／`DELETE`／`PATCH order` はいずれも親行を FOR UPDATE で load→save し、層2 `@Version` を++する。したがって **「並び替え中に別管理者が条を増減 → その POST/DELETE が層2 version を上げる → 後続 `PATCH order` は手元の古い `charterVersion` で 409」** が**機構的に成立**する（並行増減 → PATCH order 409 の物語が実装と一致・第2パス観点2 の 🟡 も同時解消）。
- **なぜこの分担か**: (1) 別々の条の同時編集は層1 が条ごと独立なので衝突しない（独立性は §6.3「再連番で層1 version を触らない」で担保）。(2) 並び替えは「見た構造が前提」ゆえ、間に構造が変わったら層2 楽観検査で 409（悲観ロックはデッドロック封殺と直列化、層2 検査は「古い構造」検知、と役割分担）。(3) 末尾追加・削除は「見た構造が前提でない」ので 409 を返さず悲観ロックで直列化し常に成功。
- `PUT` 応答は更新後の条 version を返し、FE は次回編集に載せ替える。構造操作（`POST`/`DELETE`/`PATCH order`）応答は更新後の**憲章全体（charter version 込み）**を返す（§18.2）。

## 8. 機能④ 制定日・改定履歴

### 8.1 制定日（自動）【御裁可済・§2 決定4】

- **`village_charters.enacted_at` は初回作成時（最初の条追加・§4.5）に `now` で自動セット**し、**以後変化しない**。「この憲章が最初に定められた日」を表す。

### 8.2 改定日（手動「改正を確定」）【御裁可済・§2 決定4】

- **`village_charters.last_revised_at` は手動「改正を確定」ボタン（`POST .../charter/revisions`）でのみ更新**する（`now` をセット）。条を編集しただけでは動かない（下書き的な小修正で改定日が汚れないように、確定は明示操作にする）。未改正の間は NULL。
- 「改正を確定」時に、**改定履歴 `village_charter_revisions` に 1 行追記**する（`revised_at=now`・`note`=任意メモ）。
- **⚠️ 条の編集は保存時に即時公開・「改正を確定」は公開ゲートではない**【🟠D 精査で明文化】: 条の追加・本文/付則の編集・削除・並び替えは、**保存した瞬間に即時公開**される（PUBLIC 村では非メンバーにも直ちに見える。憲章 read には下書き/公開の状態列が無い）。「改正を確定」ボタンは**改定日（`last_revised_at`）と改定履歴の 1 行を刻む里程標であって、条文を公開状態へ切り替えるゲートではない**。したがって「編集したが未確定だから非公開」という状態は存在しない。編集途中の中間状態を隠したい要求（ドラフト状態）は本 v1 のスコープ外で、将来拡張として §16.3 に記録する（下書きテーブル or `status` 列の追加で対応）。

### 8.3 改定履歴は軽量（条文スナップショット無し）【御裁可済・§2 決定4】

- 改定履歴は **`revised_at`（日付）＋`note`（任意メモ・VARCHAR(200)）のみ**。**そのときの条文全文のスナップショットは持たない**（軽量履歴）。
- **なぜ条文を残さないか**: 版管理（差分・巻き戻し）は本書スコープ外。村憲章は「いつ・どんな主旨で改めたか」を軽く残せれば足りる（ADHD シンプル優先）。全文版管理が必要になったら別テーブルで拡張する（後方互換・§16）。

### 8.4 API 応答（改定履歴）【提案】

- `RevisionResponse`: `id`(UUID)・`revisedAt`(datetime)・`note`(string/null)。`archived_at` 降順ならぬ **`revised_at` 降順**（新しい改定を先頭）で返す。
- 制定（初回作成）自体は改定履歴に行を作らない（制定 ≠ 改定）。制定日は charter メタ `enactedAt` で示す。

### 9.3 インライン 1 行編集＋自動保存エディタ【提案・村機能初の新規設計】

- 募集カテゴリ（`recruit-categories`）の Dialog 方式より軽い、**インライン 1 行編集＋自動保存**のエディタを子パネル内に新設する（§4.2）。編集 UI は `perms.value.isAdmin` が true のときのみ描画。村機能で初の編集体験だが、パネル自体は `chronicles.vue` の薄い子構造を踏襲（memory `feedback_copy_working_pattern_first`）。
- **編集フロー**:
  - 「＋条を追加」→ 空の条行がインラインで生える → 1 行入力 → blur/明示保存で `POST .../articles`。
  - 各条の本文をクリック→インライン編集 → blur で `PUT .../articles/{id}`（**層1 条 version 同送**）。
  - 「＋付則を追加」→ その条に付則入力欄を展開 → `PUT` で `supplement` 更新。
  - 並び替え（ドラッグ or 上下ボタン）→ `PATCH .../articles/order`（**層2 charter version 同送**）。追加・削除は version 非同送（悲観ロック直列化・§6.3）。
  - 「改正を確定」ボタン → 任意メモ入力（インライン or 軽量モーダル）→ `POST .../charter/revisions`。
- **⚠️ 保存＝即時公開・「改正を確定」は非ゲート**【🟠D 精査で明文化】: 各条の保存（`POST`/`PUT`/`DELETE`/`PATCH order`）は**即座に公開**され、PUBLIC 村では非メンバーにも直ちに反映される。FE は「改正を確定」を押すまで編集を溜めておく下書きモードを**持たない**（下書き＝将来拡張・§8.2・§16.3）。「改正を確定」は改定日・履歴を刻むだけで、条文の公開/非公開は切り替えない。UI 文言も「確定するまで非公開」と誤解させないよう、確定ボタンの説明を「この時点を改定として記録します」等に留める。
- **409 ハンドリング**: 層1（同じ条を同時編集・`PUT`）／層2（並び替え中に構造が変わった・`PATCH order`）の version 競合は 409 を受けたらトースト＋リロード促し（対処療法で握りつぶさない）。`POST`/`DELETE` は悲観ロック直列化で 409 を返さないため、この分岐は `PUT`／`PATCH order` のみ。
- **`/統一`（PageHeader/SectionCard）適用**: 新規ページなので共通コンポーネントへ寄せる（CLAUDE.md「新規ページは/統一と/手助け」）。
- **`/手助け`（使い方モーダル）適用**: 憲章ページに使い方ガイドを付ける（村長向けに「条を足す・改正を確定する」導線を説明）。

## 10. チームとの差別化ガードレール整合【全機能に適用】

村は「役職も格式も置いてくる、ゆるい縁の場」（F17.1 §1.1）。村憲章も**村ニックネームの世界に閉じ、実名世界（チーム/組織）と混ぜない**。F17.2 §10 のガードレール G1〜G5 のうち本書に関わるものを再掲し、担保を示す。

| # | ガードレール | 本書での担保 |
|---|---|---|
| G4 | **実名世界（チーム/組織）とのリンクを作らない** | 策定者は**村ニックネームを焼き付けた `nickname_snapshot` のみ**保存。**実名は一切保存しない**。応答に `user_id` を載せない（§5.5）。退会時は `user_id` を NULL 化して個人リンクを切断し、仮名文字列だけ史料として残す（§11） |
| G5 | **参加記録は村ニックネーム世界に閉じる** | 憲章・策定者・改定履歴のすべてが村内 identity（ニックネーム）で完結し、村外（実名・他チーム）へ漏れない |
| （存在秘匿） | **UNLISTED 村の存在を非メンバーに晒さない** | UNLISTED 村の非メンバーへの GET 憲章は **404**（§3.2・`docs/security` 存在秘匿方針） |

- 憲章には出欠・皆勤・欠席率のような「序列化」要素が無いため G1〜G3（未回答者非列挙・催促しない・皆勤/欠席率を数えない）は構造的に非該当。策定者の「開村メンバー」表示も**横並びの史料**であって「早く入った人が偉い」序列にはしない（F17.2 §8.8 将来拡張と同じ線引き）。

### 10.1 「村ニックネーム＝仮名」前提の明文化【🟠E 精査で補強】

策定者の `nickname_snapshot` を退会後も残置してよい根拠（原則4「個人情報のみ消去」）は、**「村ニックネームが仮名（実名でない）である」ことを前提に成立**する。この前提を制度・実装の両面で担保する。

- **(1) 実名入力の禁止をポリシーで担保**: 村ニックネームは**仮名として扱い、実名の入力は利用規約・ヘルプ文言で禁止**する。憲章機能の実装 Wave に、村ニックネーム設定画面／憲章策定者追加まわりの**規約・ヘルプ文言整備**（「実名は入れないでください」の明示）を含める（§15.4）。仮名前提が崩れると `nickname_snapshot` 残置が PII 残置になりうるため、ポリシーで入口を締める。
- **(2) 万一の実名焼付に備えた救済経路（将来拡張）**: ポリシーに反して実名相当が `nickname_snapshot` に焼き付いた場合に備え、**SYSTEM_ADMIN による策定者表示名のリダクション（伏字化）経路**を将来拡張として §16.3 に記録する（v1 では未実装。当面は §11 の `DELETE drafters` 手動削除で対処）。
- **(3) 原則4 整合は「仮名前提つき」**: §11 の「退会時は `user_id` のみ NULL 化・`nickname_snapshot` 残置」という原則4 整合の説明は、**上記(1)の仮名前提が満たされている条件下で**成立する。仮名前提つきであることを明記し、実名混入は(1)の予防と(2)の救済で押さえる。

## 11. 退会・村BAN・村削除時の各テーブルの扱い

【確認済み】既存 `VillageUserCleanerEventListener`（`UserAnonymizedEvent` を `@TransactionalEventListener(AFTER_COMMIT)`＋`@Transactional(REQUIRES_NEW)`＋`@Async("event-pool")` で購読）は、ニックネーム物理削除・ピン物理削除・メンバーシップ匿名化マーカーを行う。本書は策定者の匿名化処理を**この前例に 1 メソッド追加する形**で実装する。

| テーブル | 退会（`UserAnonymizedEvent`） | 村BAN | 村削除（論理削除運用・下記 🟡6） |
|---|---|---|---|
| `village_charters` | 影響なし（個人 identity を持たない） | 影響なし | 村論理削除で read ゲートが 404 に畳む（残置・到達不能）。`villages→charters` は FK 非付与ゆえ物理 CASCADE なし |
| `village_charter_articles` | **残置**（条文は村の史料・作成者 identity を持たない設計） | 残置 | `charter → articles` は FK CASCADE（村憲章アグリゲート内・一方向） |
| `village_charter_drafters` | **`user_id` を NULL 化**（`nickname_snapshot` は**残置**＝仮名史料）【2026-07-22 マスター裁定】 | 残置（BAN は村での活動停止であって史料削除ではない） | `charter → drafters` は FK CASCADE |
| `village_charter_revisions` | 影響なし（`note` は改定主旨・作成者 identity を持たない設計） | 影響なし | `charter → revisions` は FK CASCADE |

### 11.1 策定者匿名化の実装【提案・確定】

- `VillageUserCleanerEventListener` に **`anonymizeCharterDrafters(Long userId)`** を 1 メソッド追加し、`handleUserAnonymized` から呼ぶ（既存 `cleanupNicknames`/`cleanupPins`/`anonymizeMemberships` の隣）。
- 処理: `village_charter_drafters` の当該 `user_id` の全行を取得し、**`user_id = NULL` に更新して `nickname_snapshot` はそのまま残す**（新規リポジトリメソッド `findByUserId(Long)` を足す）。
- **GDPR 根拠（原則4・Art.17）**: 退会時に消すのは**個人へのリンク（`user_id`）だけ**。`nickname_snapshot` は**村ニックネーム（仮名文字列）であって実名・PII ではない**ため、史料として残置してよい（原則4「投稿・履歴は保持し個人情報のみ消去」・実名は元々保存していない＝§10 G4）。これは「即時消去（弱匿名化）」でも「猶予対象（強匿名化）」でもなく、**個人リンク切断＋仮名残置**という原則4 準拠の匿名化である。
- **本文置換は不要**: 策定者テーブルには自由記述の PII 混入欄が無い（`nickname_snapshot` は仮名・`sort_order` は数値）。F17.2 の comments/logs のような本文匿名化は憲章では不要。ただし条文 `body`・付則 `supplement`・改定メモ `note` は**村長/長老が書く公的文書**であり個人の私的 UGC ではないため、退会匿名化の対象外（村の史料として残す）。
- **BAN**: データは残置。村メンバーシップ側の遮断で以後の編集を止める（BAN された元村長は §4.1 の現役判定で `MODERATION_FORBIDDEN` になる）。
- **BAN 済み開村者が策定者に残ることの製品判断【🟡K 精査で明記】**: 村を興したあとに BAN された開村者も、策定者としての `nickname_snapshot` は**残置**する。これは**「BAN は村での活動停止であって史料の削除ではない」という設計意図**であり、憲章という村の史料から「誰が興したか」を消さない（退会 NULL 化とは別問題＝退会は個人リンク切断・BAN は活動停止）。ただし、荒らし等で BAN した相手を策定者からも消したい正当な運用要求はありうる。その**スクラブ手段は、現役 HEADMAN/ELDER が `DELETE .../charter/drafters/{drafterId}` で手動削除する経路のみ**とする（自動連鎖はしない）。「BAN したら策定者からも自動で外す」自動化は本 v1 では持たない（誤 BAN の巻き添えで史料が壊れるのを避け、削除は人の明示判断に委ねる）。
- **村削除【🟡6 精査で訂正】**: 村は基本 `deleted_at`／`archived_at` の**論理削除**運用（F17.1）で、**物理削除は行われない**。`villages` → `village_charters` は **FK 非付与**（同一ドメインだが村既存作法・§13.1.1）なので、**仮に村を物理 DELETE しても DB の外部キー CASCADE で憲章 4 表が連鎖削除されることはない**（初版の「村削除→子ごと CASCADE」は誤り）。村が論理削除されると、read ゲート（§3.2 の `loadReadableVillageOrHide` / `loadActiveVillage` は `deleted_at` 非 NULL を 404 に畳む）が憲章 EP を 404 にするため、憲章データは**残置したまま到達不能**になる（論理削除運用と整合）。**DB レベルの `ON DELETE CASCADE` は `charter → articles/drafters/revisions` の一方向のみ**（村憲章アグリゲート内・§13.1）で、`villages → charters` 方向には存在しない。

## 12. 状態・整合規則

### 12.1 憲章のライフサイクル

```
[未制定]──(最初の条を POST: enacted_at 自動セット)──▶[制定済み]
                                                        │  条の編集=層1楽観 / 並び替え=層2楽観 / 追加・削除=悲観直列化（§7）
                                                        │  策定者の追加/削除
                                                        └──(改正を確定: last_revised_at 更新＋改定履歴1行)──▶[改定済み（複数回可）]
```

- 「未制定」= `village_charters` 行が無い。GET は **200 で「未制定」状態**（`hasCharter=false`・空配列）を返す（**404 にしない**・§12.2）。
- 全条を削除しても charter 行は残る（`enacted_at` は制定の史実として保持）。条 0 件の憲章は「制定されたが現在条文なし」として表示（FE は空表示）。

### 12.2 GET の「未制定」応答【提案・確定】

- 憲章未制定の村（PUBLIC or 閲覧可能な UNLISTED）で `GET .../charter` は **200＋`hasCharter=false`・`enactedAt=null`・`articles=[]`・`drafters=[]`・`revisions=[]`** を返す。
- **なぜ 404 にしないか**: 「村は閲覧可能（存在する）が憲章はまだ無い」は正常状態であり、404（不存在）と混同させない。村自体の不存在・UNLISTED 非メンバーは §3.2 の公開ゲートが先に 404 を投げる（憲章の有無より村の可視性判定が先）。

### 12.3 不変条件（実装時テストで担保）

- INV-1: 同一 charter の非削除条は `sort_order` が 0,1,2,… の隙間なし連番（§6.3）。
- INV-2: 1 村に `deleted_at IS NULL` の `village_charters` は最大 1 行（UNIQUE・§13）。
- INV-3: `enacted_at` は不変（初回セット後変わらない）。`last_revised_at ≥ enacted_at`（改定は制定以後）。
- INV-4: 策定者の `nickname_snapshot` は退会後も NOT NULL のまま残る（`user_id` のみ NULL 化）。

```sql
CREATE TABLE village_charter_revisions (
    id           BINARY(16)   NOT NULL,                    -- UUIDv7（原則6）
    charter_id   BINARY(16)   NOT NULL,                    -- → village_charters.id（同一ドメイン・FK CASCADE）
    revised_at   DATETIME     NOT NULL,                    -- 改定日時（「改正を確定」時刻・§8.2）

    CONSTRAINT fk_vcr_charter FOREIGN KEY (charter_id)
        REFERENCES village_charters(id) ON DELETE CASCADE
);
```

> **FK 方針の整合**: charter → articles/drafters/revisions の `charter_id` は**同一ドメイン内の親子アグリゲート**なので `ON DELETE CASCADE` を張る（CLAUDE.md 原則2 が明示的に許可する「同一ドメイン内 CASCADE」・chat_channel↔chat_message と同型）。一方 `village_id`（→ villages）は**同一ドメインだが村既存作法（F17.2 §13.2「既存村テーブル群に倣い FK 非付与＋index」）に合わせ FK 非付与＋UNIQUE/index** とする。`user_id`（→ users）は**別ドメイン**なので FK 非付与（原則1）。

### 13.2 原則準拠

| 原則 | 遵守内容 |
|---|---|
| 原則1（クロスドメイン FK 禁止） | `drafters.user_id`（→users・別ドメイン）に FK を張らない。`charters.village_id`（→villages）も既存村作法で FK 非付与 |
| 原則2（CASCADE は同一ドメイン内のみ） | `charter_id` の CASCADE は村憲章ドメイン内アグリゲート（親 charter ↔ 子 articles/drafters/revisions）に限る。ドメイン越境の CASCADE は無い |
| 原則3（論理削除） | `village_charters`・`village_charter_articles` に `deleted_at`。改定履歴は append-only（削除しない・軽量ログ）、策定者は物理削除（付け外し操作） |
| 原則4（退会は匿名化・削除しない） | 策定者は `user_id` を NULL 化し `nickname_snapshot`（仮名）を残置（§11.1）。実名は元々保存しない |

| 原則6（UUIDv7） | 新規 4 表すべて `UuidV7Entity` 継承・BINARY(16)。村ごとに行が増えるテーブルゆえ全表適用（自然キー例外に該当するものは無い） |
| 原則7（テナント絞り込み） | 村テーブルは `organization_id` を持たない横断ドメイン（§15.1）。`AbstractTenantAwareRepository` の対象外。村スコープは `village_id` で絞る |

## 15. 非機能・実装方針・Wave 分割

### 15.1 スケール（1000万ユーザー・シャーディング前提）

- **村テーブルは `organization_id` を持たない横断ドメイン**（村は組織・チームの垣根を越える・F17.1 §1.1）。`AbstractTenantAwareRepository`（テナント絞り込み基底）の対象外で、**村スコープは `village_id`（UUID）で絞る**。将来シャーディングするなら `village_id` がシャードキー候補（UUIDv7 は独立発番可＝原則6 の狙い）。
- 憲章 4 表は**村ごとに行が増える**が、**1 村あたりの規模は小さい**（条は数条〜数十条、策定者は数人、改定履歴は年に数回）。全表 UUIDv7 で村ローカルに完結し、シャード分割時も `village_id` で追随する。
- **GET .../charter は固定回数クエリ（N+1 なし）**: charter 1 本＋articles 1 本＋drafters 1 本＋revisions 1 本の計 4 クエリで組み立てる（条数・策定者数・履歴数に依らず一定）。条・策定者・履歴の各サブリストは**規模が小さく境界があるためページングせず一括返却**する。
- **サブリストの上限【第2パス精査で明記】**: 一括返却が暴発しないよう上限を設ける（`GET` を無制限一括にしない）。
  - **条**: 既定 **200 条**（PR レビューで変更可・`POST articles` が超過を 400 で弾く）。
  - **策定者**: 既定 **20 人**（PR レビューで変更可・`POST drafters` が超過を 400 で弾く）。開村メンバー列挙という性質上、実運用は数人〜十数人で十分。
  - **改定履歴**: **上限を設けない（append-only）**。理由: 改定は**現役 HEADMAN/ELDER のみが明示操作で刻む低頻度イベント**（信頼ロール限定・年に数回想定）で、外部入力による暴発経路が無い。追記のみで肥大が緩慢なため無制限一括で許容する（将来、極端に長寿な村で肥大したら `revised_at` 降順ページングへ後方互換移行）。

### 15.2 後方互換

- 全 migration が新規 CREATE で既存に影響なし。既存村（憲章未制定）は GET が「未制定」を返すだけ（§12.2）。

## 16. エラーコード・監査・既知の未決事項

### 16.1 エラーコード（`VillageErrorCode`）

【確認済み】現在の最大は **`VILLAGE_101 CALENDAR_LOG_FORBIDDEN`**（`village/VillageErrorCode.java:492`）。**新規は `VILLAGE_102` から予約**する。

| 予約コード（暫定） | 定数名（案） | HTTP | 用途 |
|---|---|---|---|
| `VILLAGE_102` | `CHARTER_ARTICLE_NOT_FOUND` | 404 | 当該 charter に属さない条 id を指定（**他村の articleId 食い違いも 404**＝IDOR 対策・`village_id` 冗長列で照合・§AC-08） |
| `VILLAGE_103` | `CHARTER_ARTICLE_VERSION_CONFLICT` | 409 | 条の本文/付則更新（`PUT`）で条単位 `@Version` 競合（層1・§7） |
| `VILLAGE_104` | `CHARTER_ORDER_VERSION_CONFLICT` | 409 | **並び替え（`PATCH order`）のみ**で親 charter `@Version` 競合（層2・§7）。**`POST`/`DELETE` は悲観ロック直列化で 409 を返さない**（🔴B 殿裁定・§6.3） |
| `VILLAGE_105` | `CHARTER_DRAFTER_NOT_FOUND` | 404 | 存在しない策定者 id を削除（他 charter の drafter 食い違いも 404） |
| `VILLAGE_106` | `CHARTER_DRAFTER_DUPLICATE` | 409 | 同一ユーザーの二重策定者登録（§5.4） |

- **編集権限違反**は新規コードを作らず既存 **`MODERATION_FORBIDDEN`（403）** を流用（§4.1）。**村不存在・UNLISTED 非メンバー・read の凍結村**は既存 **`VILLAGE_NOT_FOUND`（404）** を流用（§3.2・存在秘匿）。**write の凍結村**は既存 **`VILLAGE_ALREADY_ARCHIVED`（`VILLAGE_027`・409「この村は凍結されています」・確認済み `:92-93`）** を流用（§3.3 の村状態ガード）。**バリデーション**（`body` 空・`PATCH order` の集合不一致・条数上限超過）は Bean Validation の **400**（カスタムコード不要）。

> **⚠️ 採番衝突の注意（確定はマージ時に再確認）**: 上記番号は**暫定予約**。【確認済み】`VillageErrorCode` の実コードは現在 `VILLAGE_101` までだが、**F17.2 §16.1 が祭 RSVP/実況で `VILLAGE_097`・`VILLAGE_098`・`VILLAGE_102`（`FESTIVAL_LIVE_POST_DUPLICATE`）を「紙上予約」**している（F17.2 W2 の実装が未着手のため未だコード化されていない）。**本書の `VILLAGE_102`〜 は F17.2 の `VILLAGE_102` 予約と衝突しうる**。よって**確定はマージ時に `VillageErrorCode` の最大コードと F17.2 の未実装予約の両方を再確認**し、先にマージされた側を尊重して連番を採り直すこと（後発側が繰り上げる。memory `feedback_migration_version_collision` と同様の直前再確認）。

## 17. 受け入れ条件（AC）

> **BE 契約テストは MockMvc 経由必須**（`TEST_CONVENTION.md`・Bean 直呼び禁止）。**実 MySQL Testcontainers**・**日時は `LocalDateTime` を bind**（文字列リテラル禁止・TZ 境界事故回避・memory `feedback_it_fixture_datetime_tz_bind`）。各 AC は `/試練` でそのまま red に落とせる粒度（正常系＋異常系＋境界）。

### 17.1 機能③ 公開ゲート

- **AC-01**（正常・公開）: `visibility=PUBLIC` 村の**未参加ログインユーザー**が `GET .../charter` を叩くと、メタ（`enactedAt`/`lastRevisedAt`）＋条一覧（自動採番済み）＋策定者＋改定履歴が返り、`canEdit=false` である。
- **AC-02**（認可・存在秘匿・IDOR）: `visibility=UNLISTED` 村の**非メンバー**が `GET .../charter` を叩くと **404**（`VILLAGE_NOT_FOUND`）。同 UNLISTED 村の**現役メンバー**および **SYSTEM_ADMIN** は 200 で閲覧できる。**未ログインは 401**。
- **AC-03**（空）: 憲章**未制定**の閲覧可能な村で `GET .../charter` は **200＋`hasCharter=false`・`articles=[]`・`drafters=[]`・`revisions=[]`**（404 にしない・§12.2）。

### 17.2 機能① 条文管理・編集権限

- **AC-04**（正常・自動生成）: 現役 HEADMAN/ELDER が `POST .../charter/articles` すると条が**末尾**に追加され、憲章が未制定なら **charter が自動生成され `enacted_at` がセット**される。以後の追加は既存 charter に積まれる。
- **AC-05**（認可）: **一般村人・非メンバー**の `POST/PUT/DELETE .../articles`・`POST/DELETE .../drafters`・`POST .../revisions` はすべて **`MODERATION_FORBIDDEN`（403）**。退村済み/BAN 済みの元村長も現役判定で 403（`findActiveByVillageIdAndSubject` が除外）。
- **AC-05b**（🔴A 村状態ガード・write）: **削除済み村**（`deleted_at` 非 NULL）または**不存在の村**への条 write（`POST/PUT/DELETE/PATCH/POST drafters/revisions`）は **404**（`VILLAGE_NOT_FOUND`）。**凍結済み村**（`archived_at` 非 NULL）への write は **`VILLAGE_ALREADY_ARCHIVED`（`VILLAGE_027`・409）**。この村状態ガードは編集権限チェック（AC-05）より**先**に評価される（§3.3 の 2 段順序＝`loadActiveVillage` → `requireHeadmanOrElder`）。
- **AC-06**（正常・層1）: 現役村長が `PUT .../articles/{id}` で条の本文・付則を更新でき、更新後の条 version が応答に載る。
- **AC-07**（異常・層1 楽観ロック）: 古い version で `PUT .../articles/{id}` すると **`CHARTER_ARTICLE_VERSION_CONFLICT`（409）**。
- **AC-08**（異常・IDOR）: **別の村の charter に属する `articleId`** を当該村の `PUT`/`DELETE .../articles/{id}` に渡すと **`CHARTER_ARTICLE_NOT_FOUND`（404）**（`village_id` 冗長列で「この村・この charter の条か」を照合し、他村の条を触らせない）。
- **AC-08b**（境界・文字数上限・🟠3）: `POST`/`PUT .../articles` で `body` が空（`@NotBlank` 違反）または **2000 字超**、あるいは `supplement` が **2000 字超**の場合は **400**（Bean Validation）。2000 字ちょうどは通る（境界内）。

### 17.3 機能② 並び順・自動採番・再連番

- **AC-09**（正常・自動採番）: 条番号は保存されず、`GET` 応答の `articleNumber` は非削除条を `sort_order` 昇順に並べた `index+1`（第一条・第二条…）である。DB に条番号列が存在しない。
- **AC-10**（境界・再連番）: `DELETE .../articles/{id}` で対象を論理削除すると、残る条の `sort_order` が詰めて 0,1,2,… に再連番され、`GET` の `articleNumber` が繰り上がる（論理削除済み行は採番から除外）。
- **AC-11**（正常・層2）: `PATCH .../articles/order` に非削除条の完全な id 集合を並べ替えて送ると、その順に再連番され、`GET` の採番が反映される。親 charter version が++される。
- **AC-11b**（🔴B 並行 append の直列化・IT）: **2 管理者が同時に `POST .../articles` を発行**しても（並行トランザクション）、親 charter 行の悲観ロック（`SELECT FOR UPDATE`）で直列化され、**`sort_order` は重複せず 0,1,2,… の連番が保たれる**（両リクエストとも 200・409 は返らない・§4.5）。Testcontainers 上で 2 スレッド並行 POST の IT で検証する（`INV-1` を並行下でも満たす）。
- **AC-11c**（🟠C 再連番の層1 非バンプ）: `DELETE`／`PATCH order` の再連番で `sort_order` が変わっても、**編集していない他条の層1 `@Version` は増えない**（bulk UPDATE が version を触らない・§6.3）。よって、条 A を編集中の管理者が持つ条 A の version は、別管理者が条 B を削除して A の `sort_order` が繰り上がっても**古くならず、A の `PUT` は 409 にならない**。
- **AC-11d**（🟠 デッドロック封殺・IT）: **`DELETE .../articles/{id}` と `PATCH .../articles/order` を同一憲章に対し多スレッドで並行実行**しても、全構造変更 EP が「親 charter 行 FOR UPDATE → 条行」の統一ロック順を守るため、**InnoDB のデッドロック（→未ハンドリング 500）が発生しない**（両者が直列化され、片方は他方のコミット後に走る）。Testcontainers 上で並行 DELETE×PATCH order の IT を回し、500・デッドロック例外が出ないことを確認する（§6.3 ロック順序統一の原則）。
- **AC-12**（異常・層2 楽観ロック・並び替えのみ）: 古い `charterVersion` で `PATCH .../articles/order` すると **`CHARTER_ORDER_VERSION_CONFLICT`（409）**。**`POST`/`DELETE` は version 非同送・悲観ロック直列化のため 409 を返さない**（§6.3・AC-11b）。
- **AC-12b**（🟠4 層2 バンプ→PATCH order 409 の連鎖・IT）: 管理者 X が `GET` で `charterVersion=v` を得た後、管理者 Y が `POST .../articles`（または `DELETE`）で**構造を変え層2 version を v→v+1 に上げる**と、X が手元の `charterVersion=v` で `PATCH .../articles/order` すると **409（`CHARTER_ORDER_VERSION_CONFLICT`）**になる（POST/DELETE が層2 をバンプするので「並び替え中に構造が変わった」を検知できる・§7）。
- **AC-13**（境界・集合不一致・400 は version 一致時に限る）: `PATCH .../articles/order` の `articleIds` が現存条集合と**欠落/余分/重複**のいずれかで一致しない場合は **400**。ただし**この 400 は `charterVersion` が一致している場合に限る**（version 不一致は親行ロック取得後の層2 検査で**先に 409** が返るため、400 には至らない・§6.3）。

### 17.4 機能⑤ 策定者

- **AC-14**（正常・スナップショット）: `POST .../charter/drafters`（`userId`）で策定者を追加すると、その時点の**村ニックネームが `nickname_snapshot` に焼き付**き（村内→全村共通→`USER:#id` の順で解決）、`sort_order` が末尾で付与される。応答 `DrafterResponse` に **`user_id` は含まれない**。
- **AC-15**（異常・重複）: 同一ユーザーの二重策定者登録は **`CHARTER_DRAFTER_DUPLICATE`（409）**。
- **AC-16**（異常・不存在/IDOR）: 存在しない・他 charter の `drafterId` を `DELETE .../drafters/{id}` すると **`CHARTER_DRAFTER_NOT_FOUND`（404）**。
- **AC-16b**（🟡I 正常・DELETE drafters は full charter 返却＋再連番）: `DELETE .../drafters/{id}` は **articles と同じく更新後の憲章全体（`VillageCharterResponse`）を返す**。削除後、残る策定者の `sortOrder` が詰めて 0,1,2,… に再連番され、`GET`／応答の `drafters` に反映される（策定者の連番も条と同じく詰め直す・§5.3）。

### 17.5 機能④ 制定日・改定履歴

- **AC-17**（正常・改定）: 現役村長が `POST .../charter/revisions`（任意 `note`）を叩くと `last_revised_at` が更新され、改定履歴に **日付＋メモの 1 行**が追記される（**条文スナップショットは持たない**）。`GET` の `revisions` が `revised_at` 降順で返る。
- **AC-17b**（🟠D 即時公開・非ゲート性）: 条を `POST`／`PUT`／`DELETE` した**直後（＝「改正を確定」を押す前）**でも、その変更は `GET .../charter` に**即時反映**され、PUBLIC 村では非メンバーの `GET` にも見える。「改正を確定」（`POST revisions`）は `last_revised_at`・改定履歴のみを更新し、**条文の可視性は一切変えない**（下書き状態は存在しない・§8.2）。
- **AC-18**（境界・制定日不変）: 初回作成時に `enacted_at` が自動セットされ、その後の条編集・改正確定で **`enacted_at` は変化しない**（改定は `last_revised_at` のみ動く）。`last_revised_at ≥ enacted_at`。

### 17.6 横断（退会・性能）

- **AC-19**（退会匿名化・GDPR）: 策定者ユーザーが退会（`UserAnonymizedEvent`）すると、`village_charter_drafters` の当該行の **`user_id` が NULL 化**されるが、**`nickname_snapshot` は残置**し、`GET` の策定者表示名が制定当時の名のまま維持される（実名は元々保存されない・§11.1）。
- **AC-20**（性能・N+1）: `GET .../charter` は条数・策定者数・履歴数に依らず**固定回数のクエリ**（charter/articles/drafters/revisions を各 1 本＝計 4 本、N+1 なし）で組み立てる。
- **AC-20b**（性能・サブリスト上限・第2パス）: 条は**既定 200 条**超で `POST .../articles` が 400、策定者は**既定 20 人**超で `POST .../drafters` が 400。改定履歴は上限なし（append-only・信頼ロール限定・§15.1）。

## 18. API 契約（全 8 EP・req/res・型・null 許容・@Schema 指示）

すべて `/api/v1/villages/{villageId}/charter/...`。`@Schema` は各 DTO フィールドに `description` を付け、`nullable` を明示する（生成型の正確性・memory `feedback_fe_api_type_assertion_field_lie`）。

### 18.1 共通レスポンス DTO

**`VillageCharterResponse`**（`GET .../charter` の本体）:

| フィールド | 型 | null | @Schema description |
|---|---|---|---|
| `villageId` | UUID | 不可 | 村 ID |
| `hasCharter` | boolean | 不可 | 憲章が制定済みか（未制定は false・§12.2） |
| `enactedAt` | datetime | 可 | 制定日（未制定は null） |
| `lastRevisedAt` | datetime | 可 | 改定日（未改正は null） |
| `version` | long | 可 | 親 charter の楽観ロック version（層2）。**`PATCH order` にのみ `charterVersion` として同送**する（並び替えは「見た構造が前提」ゆえ楽観ロック）。**`POST`/`DELETE` には同送不要**（悲観ロック直列化・§6.3・🔴B）。未制定は null |
| `canEdit` | boolean | 不可 | 閲覧者が現役 HEADMAN/ELDER か（FE の編集 UI 出し分け） |
| `articles` | `ArticleResponse[]` | 不可（空可） | 条一覧（自動採番済み・`articleNumber` 昇順） |
| `drafters` | `DrafterResponse[]` | 不可（空可） | 策定者一覧（`sortOrder` 昇順） |
| `revisions` | `RevisionResponse[]` | 不可（空可） | 改定履歴（`revisedAt` 降順） |

**`ArticleResponse`**: `id`(UUID・不可)／`articleNumber`(int・不可・**導出値**＝第 N 条・§6.1)／`body`(string・不可)／`supplement`(string・**可**)／`version`(long・不可・層1 楽観ロック)。※`sortOrder` は内部順序ゆえ**非露出**。

**`DrafterResponse`**: `id`(UUID・不可)／`displayName`(string・不可＝`nickname_snapshot`)／`sortOrder`(int・不可)。※`userId` は**非露出**（G4・§5.5）。

**`RevisionResponse`**: `id`(UUID・不可)／`revisedAt`(datetime・不可)／`note`(string・**可**)。

すべて `ApiResponse.of(...)` で包む（既存村 API の作法）。

### 18.2 各エンドポイントの req/res

| メソッド / パス | リクエスト body | 成功応答 | 主なエラー |
|---|---|---|---|

- **version 同送は `PUT`（層1 条 version）と `PATCH order`（層2 charterVersion）のみ**【🔴B 殿裁定】。`POST`/`DELETE`（articles・drafters）は version 非同送で、サーバ側の親 charter 悲観ロックにより直列化し 409 を返さない（§6.3・§4.5）。
- **構造変更系（`POST`/`DELETE`/`PATCH order`・drafters 追加/削除・revisions）の応答は更新後の憲章全体（`VillageCharterResponse`）に統一**【🟡I 精査・J 再整理】: 構造や version・採番が動くため、単票 DTO ではなく全体を返して FE が version と採番・策定者連番を一括で載せ替えられるようにする（往復削減・整合の一発同期）。単票 DTO を返すのは `PUT articles`（`ArticleResponse`＝編集した条の新 version を返すだけで足りる）のみ。
- **文字数上限は Bean Validation で担保【🟠3 精査】**: `body` は **`@NotBlank @Size(max=2000)`**、`supplement` は **`@Size(max=2000)`**、`note`（revisions）は **`@Size(max=200)`**（DDL の VARCHAR(200) と一致）を DTO に付す。上限は**既定値でありレビューで変更可**（**憲章の条文は簡潔が本旨**なので 2000 字＝原稿用紙 5 枚相当を既定とする。長文の逐条解説を書く運用が判明したら拡張）。上限超過は Bean Validation の **400**（カスタムエラーコード不要）。DDL は `body`/`supplement` を TEXT（最大 65535 バイト）で持つが、アプリ層の `@Size(max=2000)` で先に弾く（DB 上限より手前で制限）。
- **`POST .../revisions` を未制定村に叩いた場合の 404 の意味【🟡 第2パス精査で注記】**: 憲章が無い（条 0 で charter 行も無い）状態での「改正を確定」は概念矛盾。**404 で拒否する**が、この 404 は既存 `VILLAGE_NOT_FOUND`（村不在）と**同一コードを流用**し、「村が無い」と「村はあるが憲章未制定」を**レスポンス上あえて区別しない**（相性 API・掲示板と同じ存在秘匿の作法に寄せ、憲章の有無という情報を攻撃者に与えない）。制定は「最初の条追加」（`POST articles`・§4.5）で行うのが正規経路であり、未制定村への revisions は正規 UI では発生しない（FE は憲章制定後にのみ「改正を確定」ボタンを出す）。

## 20. まとめ

村憲章は、**timeline/notification 越境を持たず村憲章ドメインに閉じる**軽量機能である。設計の要点:

1. **read 公開ゲート／write 村状態ガードの分離**（§3）= read は相性 API `loadPublicVillageOrHide`（PUBLIC 通し・UNLISTED/凍結 404 秘匿）＋掲示板 member/SYSTEM_ADMIN バイパスのハイブリッド。write は祭作成金型 `loadActiveVillage`（削除→404・凍結→`VILLAGE_ALREADY_ARCHIVED`）→ `requireHeadmanOrElder` の 2 段（🔴A）。
2. **条番号非保存・並び順自動採番**（§6）= `sort_order` 連番をアプリ層で維持し、表示時に第 N 条を導出。UNIQUE を張らず再連番の中間状態を許す。再連番の bulk UPDATE は層1 version を触らない（🟠C）。
3. **同時実行制御のハイブリッド**（§7・🔴B 殿裁定）= 条本文編集＝層1 楽観（409）、並び替え＝層2 楽観（409）、末尾追加・削除＝親 charter 悲観ロック直列化（409 なし・並行 append の sort_order 重複を構造的に閉じる）。無関係な同時編集はブロックしない。
4. **策定者スナップショット＋退会 NULL 化（仮名前提）**（§5・§10.1・§11）= 村ニックネームを焼き付け、退会時は `user_id` のみ切って仮名史料を残す（原則4・G4）。仮名前提はポリシー文言で担保し、実名混入は救済経路を将来拡張に記録（🟠E）。
5. **制定日自動・改定日手動＋軽量履歴＋即時公開**（§8）= 全文版管理はせず「いつ・どんな主旨で改めたか」だけ残す。編集は保存時に即時公開で「改正を確定」は非ゲート（🟠D）。

未決事項ゼロを目指し、将来拡張（版管理・ドラフト状態・実名リダクション・リッチテキスト・多言語・策定者並び替え）は §16.3 に明示的後回しとして記録した。実装は共有ヘルパ抽出（🟠H）→BE テスト先行→FE→ポリシー文言→実機の 1 Wave（Opus 以下）で進める。
