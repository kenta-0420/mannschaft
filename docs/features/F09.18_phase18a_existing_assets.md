## §1 EmailTemplateRenderer 既存メソッド

ファイル: `backend/src/main/java/com/mannschaft/app/common/EmailTemplateRenderer.java`

```java
@Component
public class EmailTemplateRenderer {
    private final TemplateEngine templateEngine;   // Thymeleaf
    private final MessageSource messageSource;     // i18n 解決

    // L33-L38: メール認証メール (raw token を含む URL を verifyUrl で受け取る)
    public String renderVerificationEmail(String displayName, String verifyUrl, Locale locale)

    // L47-L51: パスワードリセットメール (displayName なし)
    public String renderPasswordResetEmail(String resetUrl, Locale locale)

    // L60-L62: 任意 i18n キーの解決ヘルパ
    public String resolveMessage(String code, Locale locale)
}
```

- `templateEngine.process("email/verification", context)` で `templates/email/verification.html` を読み込む
- i18n キーは Thymeleaf テンプレ側で `#{email.verification.subject}` のように参照される
- Phase 18-b では同 Renderer に新規メソッドを追加（あるいは別 Renderer に分割）して
  残 12 種の `EmailTemplateKind` をディスパッチできるようにする想定

## §2 EmailService 既存実装

ファイル: `backend/src/main/java/com/mannschaft/app/common/EmailService.java`

```java
@Service
public class EmailService {
    @Value("${mannschaft.email.from-address:noreply@mannschaft.app}") String fromAddress;
    private final SesV2Client sesV2Client;

    // L36-L54: SES v2 SimpleEmail (HTML) を同期送信
    public void sendEmail(String recipient, String subject, String htmlBody)
}
```

- SES `SendEmailRequest` を組み立てて `sesV2Client.sendEmail()` を呼ぶ
- 失敗（任意の `Exception`）は `catch` で握り潰し `log.error()` のみ。**呼び出し元は失敗に気付けない**
  → F09.18 本書起草の主動機（raw token 喪失問題）はここに集約されている
- Phase 18-c 完了時点で本メソッドは **package-private** 化し、外部呼び出しを禁止する予定
  （設計書 §11 末尾 「EmailService の package-private 化」 参照）

## §3 Phase 18-b/c で必要となる新規テンプレ 12 種

設計書 §11 「既存 14 箇所の移行マトリクス」の以下 12 種を新規にレンダラ / HTML テンプレ / i18n キーで実装する必要がある:

- `ANALYTICS_KPI_MONTHLY`, `ANALYTICS_SUMMARY`
- `ADVERTISING_INVOICE_OVERDUE`
- `ERROR_REPORT_WEEKLY`
- `NOTIFICATION_CONFIRM` (既存 `templates/email/confirmable-notification.html` を温存利用可)
- `GDPR_EXPORT_READY`, `GDPR_EXPORT_FAILED`, `GDPR_WITHDRAWAL_REMINDER`
- `RESERVATION_EMERGENCY_CLOSURE`, `RESERVATION_EMERGENCY_REMINDER`, `RESERVATION_EMERGENCY_UNCONFIRMED`

各 caller の現状送信内容（subject / body / 含まれる動的変数）から逆生成して
`renderXxx(...)` メソッドを追加する。Phase 18-b は #1〜#3 + #12 の「最優先 4 種」のみ。

## §4 既存メール本文の所在（実調査結果）

### §4.1 HTML テンプレ

`backend/src/main/resources/templates/email/` 配下に 3 ファイル:

### §4.2 i18n プロパティ（**重複ディレクトリ存在に注意**）

```
backend/src/main/resources/email/                ← (A) 既存利用中: verification / passwordReset 系
  email.properties (default)
  email_de.properties / email_en.properties / email_es.properties
  email_ja.properties / email_ko.properties / email_zh.properties

backend/src/main/resources/i18n/email/           ← (B) 既存利用中: confirmableNotification 系
  email_de.properties / email_en.properties / email_es.properties
  email_ja.properties / email_ko.properties / email_zh.properties
```

定義済み i18n キー（`email_ja.properties` から抜粋）:

(A) `email/email_ja.properties`:
- `email.verification.subject` / `email.verification.greeting` / `email.verification.body`
  / `email.verification.button` / `email.verification.expiry` / `email.verification.ignore`
- `email.passwordReset.subject` / `email.passwordReset.body` / `email.passwordReset.button`
  / `email.passwordReset.expiry` / `email.passwordReset.ignore`
- `email.common.footer`

(B) `i18n/email/email_ja.properties`:
- `email.confirmableNotification.subject` / `email.confirmableNotification.body`
  / `email.confirmableNotification.button` / `email.confirmableNotification.expiry`
  / `email.confirmableNotification.ignore`
- `email.common.footer`（同名キーが (A) と (B) で重複定義されている → Phase 18-b で要整理）

> **注意**: (A) と (B) の二重管理は Phase 18-b で **一本化** すべき技術的負債である。
> `MessageSource` の `basename` 設定 (`application.yml` の `spring.messages.basename`) は
> `messages,ValidationMessages` のみで、現状 `email`/`i18n/email` 系は別の MessageSource Bean
> から読み込まれている可能性が高い。Phase 18-b 着手時に `EmailTemplateRenderer` の
> `messageSource` がどの Bean に解決されているかを確認すること。

### §4.3 残 11 種のテンプレは将来 Phase で新規作成

`ANALYTICS_KPI_MONTHLY` 〜 `RESERVATION_EMERGENCY_UNCONFIRMED` の 11 種（`NOTIFICATION_CONFIRM`
を除く）については **HTML テンプレも i18n キーも未整備**。Phase 18-b / 18-c で各 caller の
現状の文字列リテラルを実コード調査し、逆生成して整備する必要がある。

特に `analytics/service/MonthlyKpiSnapshotBatchService.java:136` 等は SES `sendEmail()` の
`subject` / `htmlBody` 引数に **インラインで** 文字列を組み立てて渡しているケースが多いと
予想されるため、i18n 化と Thymeleaf テンプレ化を Phase 18-c で一気に進めると工数が膨らむ
可能性がある。フェーズ分割（最優先 4 種 vs 残り）の意義はここにも効いている。
