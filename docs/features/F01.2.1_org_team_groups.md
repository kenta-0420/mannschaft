## 1. 概要

組織（連盟・協会・同窓会など）とチームの「加盟」関係を、次の3点で拡張する。

1. **加盟を双方向にする。** これまでの「組織がチームを招待し、チームが承諾する」に加えて、「チームが組織に申請し、組織が承認する」を設ける。チームからの申請は、組織が受付を許可しているときだけ行える。
2. **チームグループを導入する。** 組織は加盟チームを「チームグループ」（例: 平成20年度卒、北地区、U-12）に分けられる。1つの加盟につき所属できるグループは1つで、グループには並び順がある。
3. **お知らせをグループ単位で送れるようにする。** 送信時にグループを個別に選ぶことも、「平成20年度以前」のように並び順の範囲で選ぶこともできる。対象を絞ったお知らせは、ダッシュボードの表示と push 通知の両方が対象チームに限られる。

### 1.1 解決する課題

| 課題 | 解決策 |
|---|---|
| チームが自分から組織へ加盟したくても手段がない（招待を待つしかない） | チーム→組織の加盟申請（組織が受付を許可している場合のみ） |
| 加盟の書き込み API が設計だけあって実装されていない（参照系のみ実装） | 書き込み API 群を本書で正式に定義し直す（実装は後続の戦役） |
| 加盟チームが数百に増えると、組織が「どのチームがどの区分か」を管理できない | チームグループ（平坦・並び順付き・1加盟1グループ） |
| 「平成20年度以前の卒業生チームだけ」に連絡したい | 個別選択と並び順の範囲指定の両方で宛先を決める |
| 組織のお知らせを特定チームに絞っても push は組織全体に届く | 絞り込んだお知らせは push も対象チームのメンバーだけに届ける |

### 1.2 本書のスコープ

| 範囲 | 内容 |
|---|---|
| 対象 | 加盟の申請・招待・承認・拒否・取下げ・取消・離脱・除名、申請受付設定、再申請の抑止、チームグループの CRUD・並び替え・割当、グループ宛てお知らせ（表示・push）、範囲テンプレートのグループ対応 |
| 対象外 | **閲覧制限（アクセス制御）**。グループ宛てのお知らせでも、元になった掲示板スレッドやアンケートは、従来どおり visibility ルールに従って組織メンバー全員が開ける。本機能が絞るのは「ダッシュボードのお知らせ欄に出るか」と「push 通知が届くか」の2点だけである（F02.8 §7 の既存方針を踏襲する）|
| 対象外 | グループの階層化（親子グループ）。グループは平坦とする |
| 対象外 | 1チームが同じ組織で複数のグループに入ること |

## 2. 用語と、似た概念との違い

UI での名称は **「チームグループ」** とする。単に「グループ」と書くと、ユーザー向け権限機能の「権限グループ」（`permission_groups`）と区別できないためである。コード上の名前も `TeamGroup` / `org_team_groups` とし、`PermissionGroup` とは語を重ねない。

| 概念 | 何を分けるか | 単位・寿命 | 本機能との違い |
|---|---|---|---|
| **チームグループ**（本機能 `org_team_groups`） | 組織に加盟している**チーム**を区分する | 組織ごとに常設。加盟1件につきグループは最大1つ | — |
| 権限グループ（`permission_groups`、F01.2） | **ユーザー**の権限（RBAC）を束ねる | チーム／組織ごと。ユーザーに複数割当 | 対象がユーザーで、目的が権限。チームは区分しない |
| 大会ディビジョン（`tournament_divisions`、F08.7） | 1つの**大会**の出場チームを 1部／2部などに分ける | 大会ごと。大会が終われば意味を失う | 大会に閉じた一時的な区分。組織の常設区分ではない |
| 子組織（`organizations.parent_organization_id`） | 組織の下に別の**組織（テナント）**を作る | 子組織は独自の管理者・メンバー・設定・加盟チームを持つ | 子組織は管理権限が独立した別組織。グループは権限を持たない「ラベル」にすぎず、管理者は親組織の管理者だけ |
| 委員会（F04.10） | 組織内の**ユーザー**のサブスコープ | 組織配下 | ユーザーの集まりであり、チームの区分ではない |

判断の目安として、「区分ごとに別の管理者が要る」なら子組織を、「管理者は同じで、宛先や一覧を分けたいだけ」ならチームグループを使う。

## 4. 状態遷移

### 4.1 加盟（`team_org_memberships`）

`team_org_memberships` の行は **PENDING と ACTIVE の2状態だけ**を持つ（既存どおり）。新しく `direction` 列で「誰が起こした PENDING か」を区別する。

```
                         (組織ADMIN が招待)                     (チームADMIN が申請)
                        direction=ORG_INVITE                  direction=TEAM_APPLY
                               │                                       │
                               ▼                                       ▼
                      ┌─────────────────┐                     ┌─────────────────┐
                      │ PENDING         │                     │ PENDING         │
                      │ (ORG_INVITE)    │                     │ (TEAM_APPLY)    │
                      └─────────────────┘                     └─────────────────┘
       チームADMIN が拒否 │   │ 組織ADMIN が取消       組織ADMIN が拒否 │   │ チームADMIN が取下げ
          (DECLINED)    │   │ (CANCELLED)              (REJECTED)  │   │ (WITHDRAWN)
              ▼          ▼   │                              ▼       ▼   │
           [行を物理削除]       │ チームADMIN が承諾            [行を物理削除]  │ 組織ADMIN が承認
           ＋制限を記録          │ (ACCEPTED)                  ＋制限を記録    │ (APPROVED・グループを確定)
                               ▼                                           ▼
                      ┌──────────────────────────────────────────────────────────┐
                      │ ACTIVE（direction は成立経路の記録として保持・group_id 可変）  │
                      └──────────────────────────────────────────────────────────┘
                         │ チームADMIN が離脱 (LEFT)      │ 組織ADMIN が除名 (REMOVED)
                         ▼                               ▼
                               [行を物理削除（既存どおり）]
```

| 遷移 | 起点 | 操作者 | 結果 | 制限の記録（§5.4） | 監査ログ action |
|---|---|---|---|---|---|
| 招待 | なし | 組織 ADMIN | PENDING / ORG_INVITE | — | `TEAM_ORG_INVITE_SENT` |
| 申請 | なし | チーム ADMIN | PENDING / TEAM_APPLY | — | `TEAM_ORG_APPLICATION_SUBMITTED` |
| 承諾 | PENDING / ORG_INVITE | チーム ADMIN | ACTIVE | — | `TEAM_ORG_MEMBERSHIP_CREATED`（metadata.via=ORG_INVITE） |
| 承認 | PENDING / TEAM_APPLY | 組織 ADMIN | ACTIVE（group_id を確定） | — | `TEAM_ORG_MEMBERSHIP_CREATED`（metadata.via=TEAM_APPLY, group_id） |
| 招待の拒否 | PENDING / ORG_INVITE | チーム ADMIN | 行を削除 | ORG_INVITE 方向に30日の冷却（`block=true` なら無期限） | `TEAM_ORG_INVITE_REJECTED` |
| 招待の取消 | PENDING / ORG_INVITE | 組織 ADMIN | 行を削除 | なし | `TEAM_ORG_INVITE_CANCELLED` |
| 申請の拒否 | PENDING / TEAM_APPLY | 組織 ADMIN | 行を削除 | TEAM_APPLY 方向に30日の冷却（`block=true` なら無期限） | `TEAM_ORG_APPLICATION_REJECTED` |
| 申請の取下げ | PENDING / TEAM_APPLY | チーム ADMIN | 行を削除 | なし | `TEAM_ORG_APPLICATION_WITHDRAWN` |
| 離脱 | ACTIVE | チーム ADMIN | 行を削除 | なし | `TEAM_ORG_MEMBERSHIP_REMOVED`（reason=TEAM_LEFT） |
| 除名 | ACTIVE | 組織 ADMIN | 行を削除 | なし（除名と同時に再申請を止めるオプションは §17 の段階拡張） | `TEAM_ORG_MEMBERSHIP_REMOVED`（reason=ORG_REMOVED） |
| グループ変更 | ACTIVE | 組織 ADMIN | group_id を更新 | — | `TEAM_ORG_GROUP_CHANGED`（from, to） |

- ACTIVE 行の `direction` は「どちらの経路で成立したか」の記録であり、以後の振る舞いには影響しない。
- 状態を変える更新はすべて **条件付き UPDATE／DELETE**（`WHERE id=? AND organization_id=? AND status='PENDING' AND direction=?`）で行う。影響行数が 0 なら、既に他の操作で状態が変わったとみなして 409 `TEAM_071` を返す（承認と取下げが同時に来た場合など）。

### 4.2 物理削除を維持する判断（現行設計の見直し結果）

拒否・取消・取下げ・離脱・除名で行を**物理削除する現行方針は維持する**。そのうえで、再申請の抑止には専用の制限テーブル（§5.4）を、履歴には既存の `audit_logs` を使う。

理由は次のとおり。

1. **読み手を壊さない。** `team_org_memberships` は ScopeAncestorResolver、OrgFanoutRecipientSource、スケジュール、大会、LeagueTransfer、シフト予算など、main 時点で17ファイル・約90箇所から参照されている。REJECTED などの終端状態を行として残すと、`status='ACTIVE'` で絞っていない読み手が1つでもあれば、拒否済みのチームが加盟扱いになる。全読み手の監査と番人の追加が前提になり、加盟の書き込み実装より影響が大きい。
2. **一意制約の意味を保てる。** `UNIQUE (team_id, organization_id)` は「同じ組み合わせで生きている関係は最大1件」を DB で保証している。終端行を残すと、この制約を生成列などで作り直す必要がある。
3. **抑止に必要な情報は少ない。** 再申請やスパムの抑止に要るのは「この組み合わせは、この方向で、いつまで申請（招待）できないか」だけである。これは制限テーブル1行で表せ、解除も1行の削除で済む。
4. **履歴は監査ログで足りる。** 誰がいつ拒否したかの記録は `audit_logs` に残る。業務ルール（冷却期間）は監査ログを参照せず、制限テーブルだけで判定する。

### 4.3 申請受付を off に切り替えたときの PENDING 申請

**受付を off にしても、既に届いている PENDING 申請はそのまま残し、組織 ADMIN は引き続き承認・拒否できる。** チーム側も取下げできる。off にした時点で止まるのは新規の申請だけである。

- 理由: off は「これ以上受け付けない」という意思表示であり、届いた申請を捨てる意思とは限らない。自動で拒否すると取り消しが効かず、申請したチームにとっても不意打ちになる。
- 設定画面で off に切り替えるとき、PENDING 申請が1件以上あれば「受付済みの申請が N 件残っています。申請一覧から個別に承認・拒否してください」と確認を出す。
- 受付 off の組織でも、申請一覧（組織側）と申請中一覧（チーム側）は表示し続ける。

### 4.4 グループ機能を off にしたとき

`team_groups_enabled` を off にしても、グループと割当（`group_id`）は削除しない。off の間は次のように振る舞い、on に戻せば元の状態に戻る。

- グループ管理画面・割当 UI・お知らせのグループ選択は表示しない。グループ系の書き込み API は 409 `ORG_067` を返す。
- 申請時のグループ選択は「使わない（OFF）」として扱う（保存値の `application_group_mode` は変えない）。
- 加盟チーム一覧のグループ列は表示しない。

## 5. DB 設計

### 5.1 所属ドメインと FK 方針

| テーブル | ドメイン（パッケージ） | テナント列 | Repository |
|---|---|---|---|
| `org_team_groups`（新規） | organization（`com.mannschaft.app.organization.teamgroup`） | `organization_id` | `AbstractTenantAwareRepository<OrgTeamGroupEntity, UUID>` |
| `team_org_memberships`（既存・列追加） | team（既存 `TeamOrgMembershipEntity` の所在に合わせる） | `organization_id` | 既存 `TeamOrgMembershipRepository`（書き込み追加時に `AbstractTenantAwareRepository` 継承へ移行する） |
| `team_org_affiliation_restrictions`（新規） | team（加盟と同じドメイン） | `organization_id` | `AbstractTenantAwareRepository<TeamOrgAffiliationRestrictionEntity, UUID>` |
| `organizations`（既存・列追加） | organization | — | 既存 |
| `announcement_feeds` / `announcement_range_templates`（既存・列追加） | social | — | 既存 |
| `notification_fanout_job_target_teams`（新規） | notification | — | 新規（job 子表） |

- `team_org_memberships.group_id` は organization ドメインの `org_team_groups.id` を指すが、**クロスドメイン FK は張らない**（原則1）。インデックスだけを張り、整合性はアプリ層で保証する（グループ削除時に同一トランザクションで未分類へ戻す。§7.3）。
- 読み手は、`group_id` が削除済みグループを指していても「未分類」として扱う（`org_team_groups.deleted_at IS NULL` で結合する）。これは同一トランザクションでの付け替えが何らかの理由で漏れた場合の防御である。
- 新規テーブルは `UuidV7Entity` を継承し、主キーは `BINARY(16)`（原則6）。照合順序は `utf8mb4_0900_ai_ci`（列単位の COLLATE 上書きはしない）。

### 5.2 新規 `org_team_groups`

```sql
-- 組織に加盟するチームを区分する「チームグループ」（F01.2.1）。平坦・並び順付き・論理削除
CREATE TABLE org_team_groups (
    id              BINARY(16)       NOT NULL COMMENT 'UUIDv7',
    organization_id BIGINT UNSIGNED  NOT NULL COMMENT '組織ID（クロスドメインFKなし）',
    name            VARCHAR(50)      NOT NULL COMMENT '表示名（例: 平成20年度卒）',
    description     VARCHAR(200)     NULL     COMMENT '補足説明（申請時の選択肢にも表示）',
    sort_order      INT              NOT NULL COMMENT '並び順（昇順）。範囲指定の基準',
    created_by      BIGINT UNSIGNED  NULL,
    updated_by      BIGINT UNSIGNED  NULL,
    created_at      DATETIME         NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at      DATETIME         NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    deleted_at      DATETIME         NULL,
    -- 生存行だけで名前の重複を禁じるための生成列（削除済みは NULL になり UNIQUE の対象外）
    active_name     VARCHAR(50)      GENERATED ALWAYS AS (IF(deleted_at IS NULL, name, NULL)) STORED,
    PRIMARY KEY (id),
    UNIQUE KEY uq_org_team_groups_org_active_name (organization_id, active_name),
    INDEX idx_org_team_groups_org_sort (organization_id, deleted_at, sort_order)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci
  COMMENT='チームグループ（組織内のチーム区分）';
```

| 項目 | 仕様 |
|---|---|
| 名前 | 前後の空白を除いて 1〜50 文字（コードポイント数）。生存グループ内で重複不可（照合順序により大文字小文字・全半角の一部は同一視される）|
| 上限 | 1組織あたり生存グループ **200 件**。超えると 422 `ORG_066` |
| `sort_order` | 作成時は「現在の最大値 + 1」。並び替えは全件の順序を一括で受け取り、0 から振り直す。同じ値の重複は DB では禁じず、サービス層で並び替え時に解消する |
| 削除 | 論理削除（`deleted_at`）。削除済みグループは一覧・選択肢・範囲計算のすべてから除外する |
| 階層 | 持たない（親グループ列なし） |

### 5.3 既存 `team_org_memberships` への列追加

```sql
ALTER TABLE team_org_memberships
    ADD COLUMN direction  VARCHAR(20)  NOT NULL DEFAULT 'ORG_INVITE'
        COMMENT '起点: ORG_INVITE=組織からの招待 / TEAM_APPLY=チームからの申請',
    ADD COLUMN group_id   BINARY(16)   NULL
        COMMENT 'チームグループID（org_team_groups.id・クロスドメインFKなし）。PENDING/TEAM_APPLY では希望グループ',
    ADD COLUMN message    VARCHAR(500) NULL
        COMMENT '申請・招待時の添え書き（PENDING の間だけ意味を持つ）',
    ADD COLUMN updated_at DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    ADD CONSTRAINT chk_team_org_memberships_direction CHECK (direction IN ('ORG_INVITE','TEAM_APPLY')),
    ADD INDEX idx_team_org_memberships_org_status_dir (organization_id, status, direction, invited_at),
    ADD INDEX idx_team_org_memberships_team_status_dir (team_id, status, direction),
    ADD INDEX idx_team_org_memberships_org_group (organization_id, group_id);
```

| 列 | 既存行の値 | 備考 |
|---|---|---|
| `direction` | `ORG_INVITE`（DEFAULT で一括設定） | 既存フローは組織からの招待だけだったため |
| `group_id` | `NULL`（未分類） | 組織 ADMIN が後から割り当てる（単体・一括） |
| `message` | `NULL` | ACTIVE への遷移時に NULL へ戻す（PII を不要に残さない） |
| `updated_at` | 移行時刻 | F01.2 01_db_design は `updated_at` を記載していたが V2.011 に無かった乖離をここで解消する |

- 既存の `invited_by` / `invited_at` は「PENDING 行を作った人・時刻」として両方向で使う（TEAM_APPLY では申請したチーム ADMIN）。`responded_by` / `responded_at` は「承諾・承認した人・時刻」。
- `status` は PENDING / ACTIVE の2値のまま変えない（§4.2）。
- 既存の `idx_tom_*` 相当インデックス（V2.011 は UNIQUE のみ）に加え、上の3本を追加する。一覧（組織側の申請一覧・招待一覧）は `(organization_id, status, direction, invited_at)` で、チーム側一覧は `(team_id, status, direction)` で引く。

### 5.4 新規 `team_org_affiliation_restrictions`（再申請・再招待の抑止）

```sql
-- 加盟申請・招待の再送を抑止する制限（拒否時の冷却期間・ブロック）（F01.2.1）
CREATE TABLE team_org_affiliation_restrictions (
    id               BINARY(16)       NOT NULL COMMENT 'UUIDv7',
    organization_id  BIGINT UNSIGNED  NOT NULL COMMENT '組織ID（クロスドメインFKなし）',
    team_id          BIGINT UNSIGNED  NOT NULL COMMENT 'チームID（同一ドメイン・FKは既存方針に合わせ張らない）',
    direction        VARCHAR(20)      NOT NULL COMMENT '止める向き: TEAM_APPLY=チームからの申請 / ORG_INVITE=組織からの招待',
    kind             VARCHAR(20)      NOT NULL COMMENT 'COOLDOWN=拒否後の冷却 / BLOCK=無期限ブロック',
    restricted_until DATETIME         NULL     COMMENT 'COOLDOWN の期限（UTC）。BLOCK は NULL',
    created_by       BIGINT UNSIGNED  NULL,
    created_at       DATETIME         NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at       DATETIME         NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    UNIQUE KEY uq_toar_org_team_dir (organization_id, team_id, direction),
    INDEX idx_toar_team_dir (team_id, direction),
    CONSTRAINT chk_toar_direction CHECK (direction IN ('TEAM_APPLY','ORG_INVITE')),
    CONSTRAINT chk_toar_kind CHECK (kind IN ('COOLDOWN','BLOCK')),
    CONSTRAINT chk_toar_until CHECK ((kind = 'BLOCK' AND restricted_until IS NULL)
                                  OR (kind = 'COOLDOWN' AND restricted_until IS NOT NULL))
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci
  COMMENT='チーム加盟の申請・招待の再送制限';
```

| 仕様 | 内容 |
|---|---|
| 冷却期間 | 拒否すると、その向きについて **30日**（`mannschaft.affiliation.reject-cooldown-days`、既定30）申請・招待できない。既に行があれば期限を延長する（UPSERT） |
| ブロック | 拒否時に `block=true` を付けると、期限なしで止める。解除は止めた側の ADMIN が一覧から行う |
| 判定 | `kind='BLOCK' OR restricted_until > NOW()` の行があれば拒否（403 `TEAM_068`）。期限切れの行は判定で無視し、夜間バッチで物理削除する |
| 相手に見せる情報 | 冷却中かブロックかは相手に**区別して見せない**（どちらも「現在この組織には申請できません」）。止めた側の ADMIN だけが種別と期限を見られる |
| 除名・離脱 | 制限を自動では作らない |

## 6. 加盟のビジネスロジック

### 6.1 チームからの申請

```
POST /api/v1/teams/{teamSlug}/org-applications   body: {organization_slug, group_id?, message?}
1. チームが存在・未削除か → 無ければ 404（既存のチーム不在コード）
2. 操作者がそのチームの ADMIN か → 違えば 403
3. チーム・組織のアーカイブ確認 → アーカイブ済みなら既存のアーカイブ拒否（422）
4. 組織が存在・未削除で、操作者から visibility 上見えるか → 見えなければ 404（不在と同じコード）
5. 組織の team_application_enabled が TRUE か → FALSE なら 403 TEAM_064
6. 制限（TEAM_APPLY 方向）の有無 → あれば 403 TEAM_068
7. 同じ (team, org) の行があるか
     ACTIVE → 409 TEAM_065 / PENDING(TEAM_APPLY) → 409 TEAM_066 / PENDING(ORG_INVITE) → 409 TEAM_066（「招待が届いています」の案内付き）
8. チームの PENDING(TEAM_APPLY) 件数が 10 以上 → 422 TEAM_069
9. グループ選択の検証（実効モード）
     OFF: group_id を指定されたら 400 TEAM_072（黙って捨てない）
     OPTIONAL: 指定時のみ、その組織の生存グループか検証 → 違えば 400 TEAM_072
     REQUIRED: 未指定なら 400 TEAM_067、指定時は OPTIONAL と同じ検証
10. INSERT（status=PENDING, direction=TEAM_APPLY, group_id, message, invited_by=操作者, invited_at=NOW()）
    一意制約違反（並行申請）は 409 TEAM_066 に写像する
11. 組織の ADMIN 全員へ通知「{チーム名} から加盟申請が届きました」（リンク: 組織の加盟申請一覧）
12. audit_logs: TEAM_ORG_APPLICATION_SUBMITTED
13. 201 Created
```

### 6.2 組織による承認

```
POST /api/v1/organizations/{slug}/team-applications/{membershipId}/approve   body: {group_id?: UUID|null, keep_requested_group?: boolean}
1. 組織の存在・未削除 → 404 / 操作者が組織 ADMIN か → 403
2. 行を (id, organization_id, status=PENDING, direction=TEAM_APPLY) で取得 → 無ければ 404 TEAM_070（他組織の ID も同じ応答）
3. 確定グループを決める
     keep_requested_group=true（既定）かつ group_id 省略 → 申請時の group_id をそのまま使う（削除済みなら NULL）
     group_id を明示 → その組織の生存グループか検証（違えば 400 TEAM_072）。null の明示は「未分類で承認」
     グループ機能 off → 常に NULL
4. 条件付き UPDATE: status=ACTIVE, group_id=確定値, message=NULL, responded_by, responded_at
   影響行数 0 → 409 TEAM_071（直前に取下げられた等）
5. チームの ADMIN 全員へ通知「{組織名} への加盟が承認されました（グループ: {名前|未分類}）」
6. audit_logs: TEAM_ORG_MEMBERSHIP_CREATED（via=TEAM_APPLY, requested_group_id, group_id）
7. 200 OK（加盟1件の表現を返す）
```

- グループ選択が REQUIRED の組織でも、承認時に組織 ADMIN が「未分類で承認」を選ぶことは許す（REQUIRED は申請者への入力要求であり、管理者の判断を縛らない）。

### 6.3 組織による拒否

```
POST /api/v1/organizations/{slug}/team-applications/{membershipId}/reject   body: {reason?: string(≤500), block?: boolean}
1〜2. 承認と同じ（404 / 403 / 404 TEAM_070）
3. 条件付き DELETE（PENDING かつ TEAM_APPLY）→ 影響行数 0 なら 409 TEAM_071
4. 制限を UPSERT（direction=TEAM_APPLY, kind=block ? BLOCK : COOLDOWN, restricted_until=block ? NULL : NOW()+30日）
5. チームの ADMIN へ通知「{組織名} への加盟申請は承認されませんでした」＋ reason（指定時のみ）
6. audit_logs: TEAM_ORG_APPLICATION_REJECTED（reason, block）
7. 200 OK
```

### 6.4 チームによる取下げ

```
DELETE /api/v1/teams/{teamSlug}/org-applications/{membershipId}
1. チームの存在 → 404 / チーム ADMIN か → 403
2. 条件付き DELETE（id, team_id, PENDING, TEAM_APPLY）→ 対象無しは 404 TEAM_070、状態変化は 409 TEAM_071
3. audit_logs: TEAM_ORG_APPLICATION_WITHDRAWN
4. 204 No Content
```

### 6.5 組織からの招待・承諾・拒否・取消（既存設計の正式化）

F01.2 03_business_logic の①〜④を、次の点を改めたうえで正とする。

| 点 | 改める内容 |
|---|---|
| パス | すべて slug（`{slug}` / `{teamSlug}`）。F01.2 の `{orgId}` / `{teamId}` 表記は廃止 |
| 招待の body | `{team_slug, group_id?, message?}`。`group_id` はグループ機能 on のときだけ受け付け、承諾時にそのまま確定グループになる |
| 招待前の検証 | 制限（ORG_INVITE 方向）があれば 403 `TEAM_068`。相手チームから申請(PENDING/TEAM_APPLY)が来ていれば 409 `TEAM_066`（申請一覧から承認するよう案内） |
| 招待の拒否 | body `{block?: boolean}`。行を削除し、ORG_INVITE 方向に冷却（またはブロック）を記録する |
| 招待の取消 | `DELETE /organizations/{slug}/team-invites/{teamSlug}`。制限は作らない |
| 承諾 | 条件付き UPDATE。承諾時にグループは変えられない（グループは組織の管理事項のため）|
| チームの受付 | チーム側に「招待の受付可否」の設定は設けない。不要な招待はブロックで止める（§17 で再検討）|

### 6.6 離脱・除名

F01.2 の⑤⑥を slug パスに改めて正とする（`DELETE /teams/{teamSlug}/organizations/{orgSlug}`、`DELETE /organizations/{slug}/teams/{teamSlug}`）。行を物理削除すると `group_id` も一緒に消える。再加盟したときは未分類から始まる。

### 6.7 通知の宛先と量

加盟の通知は、相手側の **ADMIN だけ**に送る（1件の操作で数名）。ADMIN 数は少ないので同期送信で足り、fan-out ジョブは使わない。

## 7. チームグループのビジネスロジック

### 7.1 作成・変更

- 作成: 名前の正規化（前後空白除去）→ 重複（生存行）なら 409 `ORG_065` → 生存件数が 200 なら 422 `ORG_066` → `sort_order = max + 1` で INSERT。
- 変更: 名前・説明のみ。並び順は §7.2 の API だけで変える。
- 名前を変えても、送信済みお知らせの記録（`target_audience`）に残した名前は変えない（送信時点の記録のため）。

### 7.2 並び替え

`PUT /organizations/{slug}/team-groups/order` で、生存グループ全件の ID を新しい順に受け取る。受け取った集合が現在の生存グループ集合と一致しなければ 409 `ORG_068`（他の管理者が同時に追加・削除した）。一致すれば 0 から振り直す。

### 7.3 削除

```
DELETE /organizations/{slug}/team-groups/{groupId}
1. 組織 ADMIN 検証・グループ機能 on 検証
2. (id, organization_id, deleted_at IS NULL) で取得 → 無ければ 404 ORG_064
3. 同一トランザクションで
   a. org_team_groups.deleted_at = NOW()
   b. team_org_memberships SET group_id = NULL WHERE organization_id = ? AND group_id = ?（ACTIVE・PENDING とも）
      ※ team ドメインの Service 呼び出しで行う。越境の @Transactional にはその理由をコメントで明記する
        （グループを消したのに所属が残る中間状態を外に見せないため）
4. audit_logs: ORG_TEAM_GROUP_DELETED（affected_team_count）
5. 204 No Content
```

- 削除の確認ダイアログで「所属している N チームは未分類に戻ります」と件数を示す。
- 範囲テンプレートは削除時に書き換えない（social ドメインへ波及させない）。テンプレートを読むときに削除済みグループを検出して扱う（F02.8 §8.1）。

### 7.4 割当

| 操作 | API | 内容 |
|---|---|---|
| 単体 | `PUT /organizations/{slug}/teams/{teamSlug}/team-group` body `{group_id: UUID\|null}` | ACTIVE の加盟1件の group_id を変更。null で未分類 |
| 一括 | `PUT /organizations/{slug}/team-group-assignments` body `{group_id: UUID\|null, team_slugs: string[1..500]}` | 指定チームをまとめて同じグループへ（または未分類へ）。1件でもその組織の ACTIVE 加盟でないチームを含めば、**全体を** 400 `ORG_069` で拒否し、該当 slug を返す（部分成功にしない） |

- 既存加盟チームは移行時に全件が未分類（`group_id = NULL`）になる。組織 ADMIN は加盟チーム一覧で「未分類」に絞り込み、一括割当で振り分ける。
- 割当変更は送信済みのお知らせに影響しない（スナップショットのため。§8.2）。

## 8. グループ宛てお知らせ（F02.8 との接続）

### 8.1 宛先の指定方法

組織スコープの告知ウィザード（ステップ1）の「対象チーム」を、次の3つから選べるようにする。グループ機能 off の組織では、従来どおり「すべて／チームを選ぶ」の2択である。

| 選び方 | 入力 | 解決されるチーム |
|---|---|---|
| すべてのチーム | なし | 制限なし（`target_team_ids = NULL`・従来どおり） |
| チームを選ぶ | `target_team_ids` | 指定チーム（従来どおり） |
| チームグループで選ぶ | `target_group_ids`（個別チェック）、`target_group_range`（範囲）、`include_unassigned` | 個別チェックしたグループ ∪ 範囲に入るグループ に**ACTIVE で所属しているチーム**、∪（`include_unassigned` なら）未分類の ACTIVE チーム |

範囲の定義（`sort_order` の昇順＝グループ管理画面の上から下の並び）:

| UI の表示 | 送る値 | 含まれるグループ |
|---|---|---|
| 「{A} 以前」（先頭から A まで） | `{from_group_id: null, to_group_id: A}` | `sort_order <= A.sort_order` |
| 「{A} 以降」（A から末尾まで） | `{from_group_id: A, to_group_id: null}` | `sort_order >= A.sort_order` |
| 「{A} 〜 {B}」 | `{from_group_id: A, to_group_id: B}` | `A.sort_order <= sort_order <= B.sort_order`。A が B より後ろなら 400 `BROADCAST_008` |

- 「以前／以降」は**グループ管理画面の並び順で上か下か**を意味する。年度のように古い順に並べれば「平成20年度以前」がそのまま読める。画面に「並び順はチームグループ管理で変えられます」と添える。
- 個別チェックと範囲は併用でき、和集合を取る。範囲に未分類は含まれない。
- 同じ送信内で「チームを選ぶ」と「チームグループで選ぶ」は併用しない（API は両方指定を 400 `BROADCAST_006` で拒否する）。

### 8.2 スナップショット方式（配信時にチーム ID へ展開する）

**グループ指定は送信時にチーム ID の集合へ展開し、`announcement_feeds.target_team_ids` にその集合を保存する。** 送信後にグループ構成が変わっても、そのお知らせの宛先は変えない。指定内容そのもの（グループ ID・名前・範囲・未分類の有無・解決チーム数）は `target_audience` に記録し、送信履歴の表示に使う。

採用理由:

1. **表示と push を一致させられる。** push は送信時に一度だけ配る。表示だけを動的に解決すると、「通知は来なかったのに表示される」「通知は来たのに表示されない」チームが生まれる。
2. **送った時点の意味を保てる。** 「平成20年度以前へ送った」という事実は、あとでグループの並びや所属が変わっても変わるべきではない。
3. **表示時の負荷が増えない。** 既存の表示判定（`target_team_ids IS NULL OR JSON_CONTAINS(...)`、多値インデックス）をそのまま使える。動的解決にすると、全チームのダッシュボード表示のたびにグループ所属との結合が要る。
4. **グループの削除・改名に巻き込まれない。**

不利な点: 送信後にグループへ入ったチームには届かない。必要なら再送してもらう（UI の送信履歴から「同じ宛先で再送」を段階拡張で検討）。

### 8.3 上限と空集合

| 条件 | 扱い |
|---|---|
| 解決結果が 0 チーム | 400 `BROADCAST_009`（「対象になるチームがありません」）。空配列のまま送らない |
| 解決結果が 5,000 チームを超える | 400 `BROADCAST_010`。「すべてのチーム」を選ぶよう案内する（多値インデックスの1行あたりのキー数と、fan-out 子表の行数を抑えるため） |
| グループ機能 off の組織でグループ系の項目を指定 | 400 `BROADCAST_007` |
| 他組織・削除済みのグループ ID | 400 `BROADCAST_006`（存在するかどうかを区別しない） |
| TEAM スコープの告知でグループ系の項目を指定 | 400 `BROADCAST_006` |

### 8.4 送信前プレビュー

`POST /api/v1/organizations/{slug}/broadcast/audience-preview` で、宛先指定から解決されるチーム数と、先頭50件のチーム名を返す。ウィザードは入力が変わるたび（300ms デバウンス）に呼び、「該当: 12チーム」と表示する。0件のときは「次へ」を押せない。

### 8.5 push 通知の絞り込み

**宛先を絞った組織告知（`target_team_ids` が NULL でない）では、push を宛先チームのメンバーにだけ送る。宛先外の組織メンバーには1件も送らない。**

| 項目 | 設計 |
|---|---|
| 新しい受信者ソース | `OrgTeamsFanoutRecipientSource`（戦略キー `ORGANIZATION_TEAMS`、role ドメイン `com.mannschaft.app.role.fanout`。`OrgFanoutRecipientSource` と同じ理由で role ドメインに置く）|
| ジョブへの宛先の渡し方 | `scope_ref` は組織 ID。宛先チーム ID は `notification_fanout_job_target_teams` に enqueue と同じトランザクションで保存する（`enqueue` に `Collection<Long> targetTeamIds` を取る版を追加）|
| 母集団 | 宛先チームの現役メンバー（`TeamFanoutRecipientSource` と同じ条件: memberships `left_at IS NULL` ∪ user_roles、users 生存・ACTIVE、応援者トグル）を和集合で重複排除する。**配信時点でも** `team_org_memberships` が ACTIVE のチームに限る（送信後に離脱したチームには送らない）|
| 含めないもの | 組織の直属メンバー（どの宛先チームにも所属しない人）、子組織のメンバー、宛先外チームのメンバー |
| ページング | user_id のキーセット、シャード時は `MOD(user_id, shardCount)`。既存 ORG ソースと同じ形 |
| 二重配信の防止 | ウィザード経由で宛先を絞った場合、チャネル側（例: アンケート公開時の ORGANIZATION fan-out）が組織全体へ送る通知を**抑止**し、告知ウィザードが `ORGANIZATION_TEAMS` ジョブを1件だけ enqueue する。チャネルアダプターには宛先（`BroadcastAudience`）を渡し、各チャネルの通知イベントはこれを運んで、リスナーが `ORGANIZATION` の代わりに `ORGANIZATION_TEAMS` を使う |
| 宛先を絞らない場合 | 従来どおり（チャネル側の通知をそのまま使う）。後方互換のため挙動を変えない |

各チャネル（掲示板・タイムライン・ブログ・TODO・スケジュール・アンケート）が現在どの経路で通知を出しているかは本書の時点で全数を確かめていない。実装の軍議で全経路を列挙し、宛先を絞った告知で `ORGANIZATION` スコープの fan-out ジョブと、宛先外ユーザーへの個別通知が**0件**であることを IT で確かめる（AC-H07・AC-H08）。

## 9. API 契約

共通事項:

- パスの識別子はすべて slug（組織 `{slug}`、チーム `{teamSlug}`／`{orgSlug}`）。加盟行の `{membershipId}` は BIGINT、グループの `{groupId}` は UUID 文字列。
- JSON は snake_case。日時は ISO-8601（オフセット付き）。
- 一覧のページングは既存の `PaginationMeta`（`page` / `size` / `total` / `has_next`）。`size` 既定 20・上限 100。
- **越境の扱い**: 他組織・他チームの `membershipId` / `groupId` を指定したときは、存在しない場合と**同じステータス・同じエラーコード**を返す（存在オラクルを作らない）。
- 認可の順序: 認証（401）→ スコープの存在と可視性（404）→ ロール（403）→ 入力検証（400）→ 状態（409/422）。

## 15. 受け入れ条件

形式: 「誰が・何をしたら・どうなる（観測できる結果）」。ロールは次の固定人物で書く。

- 組織X の ADMIN = **XA**、組織X の MEMBER = **XM**、組織X の DEPUTY_ADMIN = **XD**
- チームT の ADMIN = **TA**（組織X には未加盟）、チームT の MEMBER = **TM**
- 組織Y（別組織）の ADMIN = **YA**、組織Y に加盟するチームU
- どこにも属さない認証済みユーザー = **N**

### A. 申請受付の設定

| ID | 条件 |
|---|---|
| AC-A01 | 新規作成した組織の設定を XA が GET すると `team_application_enabled=false`、`team_groups_enabled=false`、`application_group_mode="OFF"` が返る |
| AC-A02 | XA が受付を on にして PUT すると 200。以後 `GET /organizations/X` の `team_application.enabled` が true になる |
| AC-A03 | XD・XM・TA・YA が設定を GET/PUT すると 403 |
| AC-A04 | 未認証で設定 API を呼ぶと 401 |
| AC-A05 | グループ機能 off のまま `application_group_mode="REQUIRED"` を PUT すると 422 `ORG_070`、設定は変わらない |
| AC-A06 | グループ機能 on・生存グループ0件で REQUIRED を PUT すると 422 `ORG_070` |
| AC-A07 | PENDING 申請が2件ある状態で XA が受付を off にすると 200 で、2件はそのまま残り、XA は2件とも承認・拒否できる |
| AC-A08 | 受付 off の組織Xのページを TA が開くと「チームとして加盟を申請」ボタンが表示されない |
| AC-A09 | 受付 on の組織Xのページを、どのチームの ADMIN でもない N が開くとボタンが表示されない |
| AC-A10 | `/discover/organizations` で「チーム加盟を受付中」に絞ると、受付 on の組織だけが出て、カードに「加盟受付中」バッジが付く |

### B. チームからの申請

| ID | 条件 |
|---|---|
| AC-B01 | 受付 on の組織Xへ TA が申請すると 201 で、X の申請一覧に PENDING/TEAM_APPLY が1件増え、XA に通知が1件届く |
| AC-B02 | 受付 off の組織Xへ TA が API で直接申請すると 403 `TEAM_064` で、行は作られない |
| AC-B03 | 受付 off の組織Xの申請フォーム API を TA が直打ちすると 403 `TEAM_064` |
| AC-B04 | TM（チームの MEMBER）が申請すると 403、行は作られない |
| AC-B05 | 受付 on でも visibility 上 TA から見えない組織へ申請すると、存在しない slug と同じ 404 が返る |
| AC-B06 | 既に加盟済みのチームで申請すると 409 `TEAM_065` |
| AC-B07 | 同じ組織へ2回申請すると2回目は 409 `TEAM_066`。同時に2件送っても行は1件だけ |
| AC-B08 | 組織Xから招待が届いている状態で TA が X へ申請すると 409 `TEAM_066` |
| AC-B09 | PENDING 申請を10件持つチームが11件目を申請すると 422 `TEAM_069`。10件目までは成功する（境界）|
| AC-B10 | グループ選択 REQUIRED の組織へ group_id なしで申請すると 400 `TEAM_067`。画面では送信ボタンが押せない |
| AC-B11 | グループ選択 OFF の組織へ group_id 付きで申請すると 400 `TEAM_072` |
| AC-B12 | 組織Yのグループ ID を付けて組織Xへ申請すると 400 `TEAM_072`（削除済みグループを付けた場合と同じ応答）|
| AC-B13 | TA が申請を取り下げると 204 で行が消え、XA の申請一覧から消える。制限は作られず、すぐに再申請できる |
| AC-B14 | 取下げと承認が同時に来たとき、一方だけが成功し、もう一方は 409 `TEAM_071`（または取下げ側 404 `TEAM_070`）になる |
| AC-B15 | message に 501 文字を送ると 400、500 文字は成功する |

### C. 承認・拒否・制限

| ID | 条件 |
|---|---|
| AC-C01 | XA が group_id を省略して承認すると 200 で、加盟が ACTIVE になり、申請時の希望グループに所属する。TA に通知が1件届く |
| AC-C02 | XA が別グループを指定して承認すると、指定したグループに所属し、監査ログに希望と確定の両方が残る |
| AC-C03 | XA が `group_id: null` を明示して承認すると未分類で加盟する（REQUIRED の組織でも成功する）|
| AC-C04 | 承認後、`GET /organizations/X/teams` にチームTが出て、`GET /teams/T/organizations` に組織Xとグループ名が出る。T のメンバーの ScopeAncestorResolver 解決に X が加わる |
