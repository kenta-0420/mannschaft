## 1. 概要

組織（連盟・協会・同窓会など）とチームの「加盟」関係を、次の4点で拡張する。

1. **加盟を双方向にする。** これまでの「組織がチームを招待し、チームが承諾する」に加えて、「チームが組織に申請し、組織が承認する」を設ける。チームからの申請は、組織が受付を許可しているときだけ行える。
2. **1チームが複数の組織へ同時に加盟できることを正式に保証する。** DB（`UNIQUE (team_id, organization_id)`）は元から複数加盟を許していたが、読み手の一部が「親組織は1つ」と前提していた。これを本書の範囲で改修する（§9）。
3. **チームグループを導入する。** 組織は加盟チームを「チームグループ」（例: 平成20年度卒、北地区、U-12）に分けられる。1つの加盟につき所属できるグループは1つで、グループには並び順がある。
4. **お知らせをグループ単位で送れるようにする。** 送信時にグループを個別に選ぶことも、「平成20年度以前」のように並び順の範囲で選ぶこともできる。ダッシュボードの表示は閲覧時点の所属で判定し（動的）、push 通知は、どのチームに配るかを送信時点のグループ所属で確定し（スナップショット）、そのチームの誰に届くかは配信処理の時点の所属で決める。

### 1.1 解決する課題

| 課題 | 解決策 |
|---|---|
| チームが自分から組織へ加盟したくても手段がない（招待を待つしかない） | チーム→組織の加盟申請（組織が受付を許可している場合のみ） |
| 加盟の書き込み API が設計だけあって実装されていない（参照系のみ実装） | 書き込み API 群を本書で正式に定義し直す（実装は後続の戦役） |
| 複数の組織に加盟したチームで、可視性や行事カテゴリの親組織が1つしか解決されない | 単一親前提の読み手を洗い出し、複数親の意味論を定めて改修する（§9） |
| 加盟チームが数百に増えると、組織が「どのチームがどの区分か」を管理できない | チームグループ（平坦・並び順付き・1加盟1グループ） |
| 「平成20年度以前の卒業生チームだけ」に連絡したい | 個別選択と並び順の範囲指定の両方で宛先を決める |
| 組織のお知らせを特定チームに絞っても、アンケートの push は組織全体に届く | 宛先を絞ったアンケート告知（チームを選ぶ・チームグループ）は、push も宛先チームのメンバーと直属メンバーだけに届ける（§8.5） |

### 1.2 本書のスコープ

| 範囲 | 内容 |
|---|---|
| 対象 | 加盟の申請・招待・承認・拒否・取下げ・取消・離脱・除名、申請受付設定、再申請の抑止、PENDING の期限切れと組織・チームの削除／アーカイブ時の片付け、複数親組織の読み手改修、チームグループの CRUD・並び替え・割当、グループ宛てお知らせ（表示・push）、範囲テンプレートのグループ対応 |
| 対象外 | **閲覧制限（アクセス制御）**。グループ宛てのお知らせでも、元になった掲示板スレッドやアンケートは、従来どおり visibility ルールに従って組織メンバー全員が開ける。本機能が絞るのは「ダッシュボードのお知らせ欄に出るか」と「push 通知が届くか」の2点だけである（F02.8 §7 の既存方針を踏襲する） |
| 対象外 | 現在 push を出していないチャネル（掲示板・タイムライン・ブログ・TODO・スケジュール）に push を新設すること。グループで絞っても、これらは従来どおり push しない（§8.5） |
| 対象外 | グループの階層化（親子グループ）。グループは平坦とする |
| 対象外 | 1チームが同じ組織で複数のグループに入ること |

## 2. 用語と、似た概念との違い

UI での名称は **「チームグループ」** とする。単に「グループ」と書くと、ユーザー向け権限機能の「権限グループ」（`permission_groups`）と区別できないためである。コード上の名前も `TeamGroup` / `org_team_groups` とし、`PermissionGroup` とは語を重ねない。

| 概念 | 何を分けるか | 単位・寿命 | 本機能との違い |
|---|---|---|---|
| **チームグループ**（本機能 `org_team_groups`） | 組織に加盟している**チーム**を区分する | 組織ごとに常設。加盟1件につきグループは最大1つ | — |
| 権限グループ（`permission_groups`、F01.2） | **ユーザー**の権限（RBAC）を束ねる | チーム／組織ごと。ユーザーに複数割当 | 対象がユーザーで、目的が権限。チームは区分しない |
| 大会ディビジョン（`tournament_divisions`、F08.7） | 1つの**大会**の出場チームを 1部／2部などに分ける | 大会ごと。昇降格で毎シーズン入れ替わる | 大会の成績で決まる一時的な区分。組織が管理画面で自由に付け替える常設ラベルではない |
| リーグ移籍（LeagueTransfer、F08.7.1） | **子組織（下位リーグの組織）どうしの間**でチームを昇格・降格させる | 移籍1件ごとの「送り出し＋承認」 | 移籍は**加盟先の組織そのもの**が変わる（`team_org_memberships` の行が組織をまたいで移る）。チームグループは**同じ組織の中**でラベルを付け替えるだけで、加盟先は変わらない |
| 子組織（`organizations.parent_organization_id`） | 組織の下に別の**組織（テナント）**を作る | 子組織は独自の管理者・メンバー・設定・加盟チームを持つ | 子組織は管理権限が独立した別組織。グループは権限を持たない「ラベル」にすぎず、管理者は親組織の管理者だけ |
| 委員会（F04.10） | 組織内の**ユーザー**のサブスコープ | 組織配下 | ユーザーの集まりであり、チームの区分ではない |

使い分けの目安:

- 区分ごとに別の管理者・別の設定が要る → **子組織**
- 大会の成績で区分が決まり、区分をまたぐときに組織も変わる（1部リーグの組織から2部リーグの組織へ） → **子組織＋リーグ移籍**
- 1つの大会の中だけで 1部／2部に分けたい → **大会ディビジョン**
- 管理者は同じで、一覧・お知らせの宛先を分けたいだけ（卒業年度・地区・年代） → **チームグループ**

### 3.2 チーム側の加盟操作権限 `MANAGE_ORG_AFFILIATION`（マスター確定 M1）

| 項目 | 設計 |
|---|---|
| 権限名 | `MANAGE_ORG_AFFILIATION`（表示名「組織への加盟操作」、scope=TEAM） |
| 対象の操作 | 申請・取下げ・招待の承諾／拒否・離脱・チームが止めている招待の一覧と解除・申請フォームの取得・受付中組織での申請ボタンの表示 |
| ADMIN | **常に持つ**。`role_permissions` に ADMIN・`is_default=1` の行を置く（`checkPermission` 経路は `is_default=1` の行に依存し、暗黙の全権ではないため）|
| DEPUTY_ADMIN・MEMBER | **付与されたときだけ持つ**。付与は既存の権限グループ（`permission_groups`、`target_role` = DEPUTY_ADMIN または MEMBER）に `MANAGE_ORG_AFFILIATION` を含め、そのグループを個別のユーザーに割り当てる（`PUT /api/v1/teams/{slug}/members/{userId}/permission-groups`）。**DEPUTY_ADMIN・MEMBER の `role_permissions` 天井行は作らない**（V183 `add_manage_recruitments_permission` と同じ作法。TEAM の経路は天井行の `is_default` を絞らずに集約するため、行を作ると全 DEPUTY に黙って付与される）|
| 付与できる人（ADMIN 専用権限・自己昇格の封止） | **チーム ADMIN だけ**。main の `PermissionGroupService` は作成・更新・複製・削除・ユーザー割当の各経路で `requireMutationAuthority` を通し、既定では `checkAdminOrAbove`（DEPUTY_ADMIN も通る）で判定する。このままでは DEPUTY_ADMIN が `MANAGE_ORG_AFFILIATION` を含む権限グループを作って自分に割り当てられる（自己昇格）。そこで、既存の ADMIN 専用権限の一覧 `F0914_SENSITIVE_PERMISSIONS`（`SEND_PAID_TIMELINE` / `VIEW_TIMELINE_COST`。含まれると `checkScopeAdminOnly` に切り替わる）に `MANAGE_ORG_AFFILIATION` を加える。一覧の名前が F09.14 固有になっているため、実装時に `ADMIN_ONLY_GRANTABLE_PERMISSIONS` へ改名し、判定メソッドも `containsAdminOnlyPermission` へ改める。検査の対象は、**作成**は新しい権限集合、**更新**は変更前と変更後の和集合、**複製**は複製元の権限集合、**削除**は削除前の権限集合、**ユーザー割当**は現在の割当と新しい割当の権限の和集合である（いずれも main の `requireMutationAuthority` に渡している集合と同じ）。これにより、DEPUTY_ADMIN は自分にも他人にも割り当てられず、この権限を含む既存グループの改変・複製・削除もできない（403。AC-P10〜P12）。この権限を含まないグループの操作は、従来どおり DEPUTY_ADMIN にも許す |
| 判定 | `AccessControlService.hasPermission(userId, teamId, "TEAM", "MANAGE_ORG_AFFILIATION")`（`RoleService.resolveEffectivePermissions` 経由）。DEPUTY_ADMIN は権限グループ経由、MEMBER は target_role=MEMBER の権限グループ割当経由で真になることを IT で確かめる（AC-P03・P04）|
| 権限名の定義 | 権限名の enum は無いため、定数は加盟の Service に `static final String MANAGE_ORG_AFFILIATION = "MANAGE_ORG_AFFILIATION"` で置く。正本は Flyway の `permissions` への INSERT |
| Flyway | `INSERT INTO permissions ... WHERE NOT EXISTS`（名前・表示名・scope=TEAM）と、ADMIN の `role_permissions`（`is_default=1`）。§12 の8本目 |
| 付与の画面導線 | **チームシェルに新タブ「権限グループ」（`/teams/{slug}/permission-groups`）を追加する**（main 時点でチームの権限グループ API は `TeamController` にあるが、画面が無く `useTeamMembers.ts` の関数も未使用）。組織の `/organizations/{slug}/permission-groups`（`components/organization/OrgPermissionGroupList.vue`）をチームでも使えるよう汎用化して流用する。タブの表示はチーム ADMIN・管理レンズのみ。割当はメンバー一覧（`/teams/{slug}/members`）の各メンバーの操作メニュー「権限グループ」から行う |
| 既定権限画面（`/admin/member-permissions`）との関係 | この画面は MEMBER 既定3権限（MANAGE_SCHEDULES / FILES / POSTS）専用のため、`MANAGE_ORG_AFFILIATION` は載せない（ロール全員への一括付与は想定しない。加盟操作は指定した人だけに任せる）|

## 4. 状態遷移とライフサイクル

### 4.1 加盟（`team_org_memberships`）

`team_org_memberships` の行は **PENDING と ACTIVE の2状態だけ**を持つ（既存どおり）。新しく `direction` 列で「誰が起こした PENDING か」を区別する。

```
                         (組織ADMIN が招待)                     (チームADMIN が申請)
                        direction=ORG_INVITE                  direction=TEAM_APPLY
                               │                                       │
                               ▼                                       ▼
                      ┌─────────────────┐                     ┌─────────────────┐
                      │ PENDING         │                     │ PENDING         │
                      │ (ORG_INVITE)    │                     │ (TEAM_APPLY)    │
                      └─────────────────┘                     └─────────────────┘
   チームADMIN が拒否 │  │ 組織ADMIN が取消  │期限切れ   組織ADMIN が拒否 │  │ チームADMIN が取下げ │期限切れ
     (DECLINED)     │  │ (CANCELLED)     │(EXPIRED)   (REJECTED)   │  │ (WITHDRAWN)      │(EXPIRED)
         ▼          ▼  │                 ▼               ▼         ▼  │                  ▼
        [行を物理削除＋必要なら制限を記録]  │              [行を物理削除＋必要なら制限を記録]  │
                        │ チームADMIN が承諾                         │ 組織ADMIN が承認
                        │ (ACCEPTED)                               │ (APPROVED・グループを確定)
                        ▼                                           ▼
                      ┌──────────────────────────────────────────────────────────┐
                      │ ACTIVE（direction は成立経路の記録として保持・group_id 可変）  │
                      └──────────────────────────────────────────────────────────┘
                         │ チームADMIN が離脱 (LEFT)      │ 組織ADMIN が除名 (REMOVED)
                         ▼                               ▼
                               [行を物理削除（既存どおり）]
```

| 遷移 | 起点 | 操作者 | 結果 | 制限の記録（§5.4） | 監査ログ action |
|---|---|---|---|---|---|
| 招待 | なし | 組織 ADMIN | PENDING / ORG_INVITE | — | `TEAM_ORG_INVITE_SENT` |
| 申請 | なし | チームの加盟操作者 | PENDING / TEAM_APPLY | — | `TEAM_ORG_APPLICATION_SUBMITTED` |
| 承諾 | PENDING / ORG_INVITE | チームの加盟操作者 | ACTIVE | — | `TEAM_ORG_MEMBERSHIP_CREATED`（metadata.via=ORG_INVITE） |
| 承認 | PENDING / TEAM_APPLY | 組織 ADMIN | ACTIVE（group_id を確定） | — | `TEAM_ORG_MEMBERSHIP_CREATED`（metadata.via=TEAM_APPLY, group_id） |
| 招待の拒否 | PENDING / ORG_INVITE | チームの加盟操作者 | 行を削除 | ORG_INVITE 方向に30日（`block=true` なら無期限） | `TEAM_ORG_INVITE_REJECTED` |
| 招待の取消 | PENDING / ORG_INVITE | 組織 ADMIN | 行を削除 | ORG_INVITE 方向に24時間（通知の連打防止） | `TEAM_ORG_INVITE_CANCELLED` |
| 申請の拒否 | PENDING / TEAM_APPLY | 組織 ADMIN | 行を削除 | TEAM_APPLY 方向に30日（`block=true` なら無期限） | `TEAM_ORG_APPLICATION_REJECTED` |
| 申請の取下げ | PENDING / TEAM_APPLY | チームの加盟操作者 | 行を削除 | TEAM_APPLY 方向に24時間（通知の連打防止） | `TEAM_ORG_APPLICATION_WITHDRAWN` |
| 期限切れ | PENDING（両方向） | 夜間バッチ | 60日応答が無ければ行を削除し、起こした側へ通知 | なし | `TEAM_ORG_PENDING_EXPIRED` |
| 離脱 | ACTIVE | チームの加盟操作者 | 行を削除 | なし | `TEAM_ORG_MEMBERSHIP_LEFT` |
| 除名 | ACTIVE | 組織 ADMIN | 行を削除 | なし（除名と同時に再申請を止めるオプションは §18） | `TEAM_ORG_MEMBERSHIP_REMOVED` |
| グループ変更 | ACTIVE | 組織 ADMIN | group_id を更新 | — | `TEAM_ORG_GROUP_CHANGED`（from, to） |

- ACTIVE 行の `direction` は「どちらの経路で成立したか」の記録であり、以後の振る舞いには影響しない。
- 状態を変える更新はすべて **条件付き UPDATE／DELETE**（`WHERE id=? AND organization_id=? AND status='PENDING' AND direction=?`）で行う。影響行数 0 の扱いは §6.4 の判定表に従う。
- PENDING の期限（60日、`mannschaft.affiliation.pending-ttl-days`）を設けるのは、相手が応答しないまま PENDING が残り、チームの同時申請枠（10件）を埋め続けることを防ぐためである。

### 4.2 物理削除を維持する判断（現行設計の見直し結果）

拒否・取消・取下げ・期限切れ・離脱・除名で行を**物理削除する現行方針は維持する**。そのうえで、再申請の抑止には専用の制限テーブル（§5.4）を、履歴には既存の `audit_logs` を使う。

理由は次のとおり。

1. **読み手を壊さない。** `team_org_memberships` は ScopeAncestorResolver、OrgFanoutRecipientSource、スケジュール、大会、LeagueTransfer、シフト予算など、main 時点で17ファイル・約90箇所から参照されている。REJECTED などの終端状態を行として残すと、`status='ACTIVE'` で絞っていない読み手が1つでもあれば、拒否済みのチームが加盟扱いになる。全読み手の監査と番人の追加が前提になり、加盟の書き込み実装より影響が大きい。
2. **一意制約の意味を保てる。** `UNIQUE (team_id, organization_id)` は「同じ組み合わせで生きている関係は最大1件」を DB で保証している。終端行を残すと、この制約を生成列などで作り直す必要がある。
3. **抑止に必要な情報は少ない。** 再申請やスパムの抑止に要るのは「この組み合わせは、この方向で、いつまで申請（招待）できないか」だけである。これは制限テーブル1行で表せ、解除も1行の削除で済む。
4. **履歴は監査ログで足りる。** 誰がいつ拒否したかの記録は `audit_logs` に残る。業務ルール（冷却期間）は監査ログを参照せず、制限テーブルだけで判定する。

### 4.3 申請受付を off に切り替えたときの PENDING 申請

**受付を off にしても、既に届いている PENDING 申請はそのまま残し、組織 ADMIN は引き続き承認・拒否できる。** チーム側も取下げできる。off にした時点で止まるのは新規の申請だけである。PENDING は §4.1 の期限（60日）で自然に片付く。

- 理由: off は「これ以上受け付けない」という意思表示であり、届いた申請を捨てる意思とは限らない。自動で拒否すると取り消しが効かず、申請したチームにとっても不意打ちになる。
- 設定画面で off に切り替えるとき、PENDING 申請が1件以上あれば「受付済みの申請が N 件残っています。申請一覧から個別に承認・拒否してください」と確認を出す。
- 受付 off の組織でも、申請一覧（組織側）と申請中一覧（チーム側）は表示し続ける。

### 4.4 グループ機能を off にしたとき

`team_groups_enabled` を off にしても、グループと割当（`group_id`）は削除しない。off の間は次のように振る舞い、on に戻せば元の状態に戻る。

- グループ管理画面・割当 UI・お知らせのグループ選択は表示しない。グループ系の書き込み API は 409 `ORG_067` を返す。
- 申請時のグループ選択は「使わない（OFF）」として扱う（保存値の `application_group_mode` は変えない）。
- 加盟チーム一覧のグループ列は表示しない。
- 送信済みのグループ宛てお知らせの表示判定は、off の間も保存された条件で続ける（off は新規送信を止めるだけで、過去のお知らせの宛先を変えない）。

### 4.5 組織・チームの削除とアーカイブ時の片付け

| 契機 | PENDING 行 | ACTIVE 行 | チームグループ | 制限（§5.4） | 通知 |
|---|---|---|---|---|---|
| 組織の論理削除 | 削除（既存フロー step 5 の `DELETE WHERE organization_id=?` に含まれる） | 削除（既存どおり） | 同一トランザクションで全件を論理削除（同じ organization ドメイン） | `OrganizationDeletedEvent`（AFTER_COMMIT）で team ドメインが当該組織の行を物理削除 | PENDING の相手側 ADMIN へ「組織が削除されたため、申請（招待）は取り消されました」 |
| 組織のアーカイブ | 削除（新規。申請・招待を受け付けない状態で PENDING を残すと、チームの申請枠を埋め続けるため）。main の `OrganizationService.archiveOrganization` は `archived_at` を立てるだけでイベントを出さないので、**`OrganizationArchivedEvent` の発行を追加する**。team ドメインのリスナーがこれを AFTER_COMMIT で受けて当該組織の PENDING を削除する（組織はドメインをまたぐのでイベント方式を維持する）。`archiveOrganization` は最初に組織行を `PESSIMISTIC_WRITE` でロックしてから `archived_at` を立てるので、申請・招待の作成が取る組織行ロックと競合して直列化される（§6.9）。イベントの取りこぼしは `TeamOrgLifecycleCleanupBatch` が拾う | 既存のアーカイブ規則どおり（残す） | 残す（アーカイブ解除で元に戻る） | 残す | PENDING の相手側 ADMIN へ同上 |
| 組織のアーカイブ解除 | 復元しない | — | そのまま | そのまま | なし |
| チームの論理削除 | 削除（`TeamDeletedEvent` AFTER_COMMIT で当該チームの PENDING・ACTIVE を削除。既存のチーム削除フローに追加） | 削除 | — | 当該チームの行を物理削除 | PENDING の相手側（組織）ADMIN へ同上 |
| チームのアーカイブ | 削除（同上の理由）。team と `team_org_memberships` は同じ team ドメインなので、**`TeamService.archiveTeam` の中で同じトランザクションで削除する**（イベントは使わない。`TeamArchivedEvent` は新設しない）。`archiveTeam` は最初にチーム行を `PESSIMISTIC_WRITE` でロックし、未アーカイブを再確認してから `archived_at` を立て、当該チームの PENDING（申請・招待とも）を DELETE する。申請・招待の作成が取るチーム行ロックと競合して直列化される（§6.9） | 残す（既存規則どおり） | — | 残す | 削除した PENDING の相手側（組織）ADMIN へ同上（同じトランザクションで通知ジョブを enqueue する。§6.7） |

- 申請・招待・承認・承諾の各操作は、**実行時に組織とチームの状態を再確認する**（§6.2 step 3）。画面を開いた後に相手が削除・アーカイブされた場合、状態変更は行わず、削除済みは 404、アーカイブ済みは既存のアーカイブ拒否（422）を返す。
- 組織のアーカイブとチームの論理削除の片付けはイベント経由の非同期処理なので、ごく短い間 PENDING 行が残り得る。承認時の再確認があるため、この間に誤って ACTIVE になることはない。チームのアーカイブは同じトランザクションで削除するので、コミットの時点で PENDING は残らない。
- 組織のアーカイブ前から開いていた画面で承認・承諾した場合の応答は、片付けが済んだかどうかで分かれる（チームのアーカイブ後は常に行が無いので 404 `TEAM_070`）。**イベントの処理前**（PENDING 行がまだある）は、状態の再確認でアーカイブ済みと判定して 422（既存のアーカイブ拒否）を返し、行は PENDING のまま残る（直後にリスナーが削除する）。**削除の完了後**は行が無いので 404 `TEAM_070` を返す（AC-C13・AC-E05）。

### 4.6 時刻の扱い

- 本機能の日時は**起きた瞬間（`Instant`）**として扱う（`docs/architecture/datetime_policy_utc_instant_vs_wallclock.md`）。日時列（`team_org_memberships.invited_at` / `responded_at` / `updated_at`、`team_org_affiliation_restrictions.restricted_until` / `created_at`、`org_team_groups.deleted_at`）はすべて `DATETIME` で、**UTC の壁時計**で格納する（JPA 経路の格納基準と同じ）。新しいコードは `LocalDateTime` のフィールド・引数を持ち込まない。
- 現在時刻は **`@Primary` の `Clock`（UTC）**から `Instant.now(clock)` で取り、DATETIME の秒精度に合わせて**秒へ丸める**。ネイティブ SQL で書くときは**エポック秒**を渡して `TIMESTAMPADD(SECOND, :epochSecond, '1970-01-01 00:00:00')` で UTC 壁時計へ戻す（Java の日時型をプレースホルダへ束縛すると JDBC のタイムゾーン変換に依存するため。制限の UPSERT・承認・招待・承諾が同じ作法）。判定の現在時刻も同じ `Clock` から引数 `:now` として渡し、SQL の `NOW()`・`CURRENT_TIMESTAMP` は判定・更新の条件式に使わない（IT で `Clock` を固定 Clock に差し替えれば時間を進められるようにするため）。列の `DEFAULT CURRENT_TIMESTAMP` は、アプリが値を渡し忘れたときの保険として残してよい。
- 既存の `TeamOrgMembershipEntity` は日時列を `LocalDateTime` として読み書きする（2-B1 の申請の INSERT など）。その解釈（サーバ既定ゾーンの壁時計を瞬間へ戻す）は `TeamOrgAffiliationAssembler.AffiliationRow.from` の1か所に閉じ、応答の組み立ては `Instant` を持つ `AffiliationRow` から行う。
- 実機で時間を進めるときは、**DB の日時列を過去へずらす準備**をしたうえで、**バッチを手動起動**（`POST /api/v1/system-admin/batch/{name}/trigger?sync=true`、SYSTEM_ADMIN）する（§16.0）。テスト用の Clock 変更エンドポイントは作らない。

### 5.1 所属ドメインと Repository の方針

| テーブル | ドメイン（パッケージ） | テナント列 | Repository |

**`AbstractTenantAwareRepository` を `team_org_memberships` と `team_org_affiliation_restrictions` に適用しない理由**

1. `AbstractTenantAwareRepository` は `findByOrganizationIdAndDeletedAtIsNull` / `findByIdAndOrganizationIdAndDeletedAtIsNull` を宣言しており、`deleted_at` 列を前提にしている。両テーブルは物理削除で管理し（§4.2）、`deleted_at` 列を持たない。継承すると派生クエリの生成で起動に失敗する。
2. 両テーブルは**チーム側から組織を横断して引く**正当な読み手を持つ（チームの所属組織一覧、チームの申請中一覧、チームが止めている招待の一覧）。これらは `team_id` が起点で、1つの `organization_id` に閉じない。

代わりに、組織側から引くクエリは必ず `organization_id` を条件に含め、チーム側から引くクエリは必ず `team_id` を条件に含める。ID 指定の取得は `(id, organization_id)` または `(id, team_id)` の組でだけ行う。これを `TeamAffiliationScopeContractIT`（非メンバー 403・越境 404・正当成功）で担保する（§12）。

**クロスドメイン FK**

- `team_org_memberships.group_id` は organization ドメインの `org_team_groups.id` を指すが、**クロスドメイン FK は張らない**（原則1）。インデックスだけを張り、整合性はアプリ層で保証する（グループ削除後の非同期の付け替え。§7.3）。
- 読み手は、`group_id` が削除済みグループを指していても「未分類」として扱う（`org_team_groups.deleted_at IS NULL` で JOIN する）。付け替えが非同期なので、この防御は必須である。
- 新規テーブルは `UuidV7Entity` を継承し、主キーは `BINARY(16)`（原則6）。照合順序は `utf8mb4_0900_ai_ci`（列単位の COLLATE 上書きはしない）。

### 5.2 新規 `org_team_groups`

```sql
-- 組織に加盟するチームを区分する「チームグループ」（F01.2.1）。平坦・並び順付き・論理削除
CREATE TABLE org_team_groups (
    id              BINARY(16)       NOT NULL COMMENT 'UUIDv7',
    organization_id BIGINT UNSIGNED  NOT NULL COMMENT '組織ID（クロスドメインFKなし）',
    name            VARCHAR(50)      NOT NULL COMMENT '表示名（例: 平成20年度卒）',
    description     VARCHAR(200)     NULL     COMMENT '補足説明（申請時の選択肢にも表示）',
    sort_order      INT              NOT NULL COMMENT '並び順（昇順）。範囲指定の基準',
    created_by      BIGINT UNSIGNED  NULL,
    updated_by      BIGINT UNSIGNED  NULL,
    created_at      DATETIME         NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at      DATETIME         NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    deleted_at      DATETIME         NULL,
    -- 生存行だけで名前の重複を禁じるための生成列（削除済みは NULL になり UNIQUE の対象外）
    active_name     VARCHAR(50)      GENERATED ALWAYS AS (IF(deleted_at IS NULL, name, NULL)) STORED,
    PRIMARY KEY (id),
    UNIQUE KEY uq_org_team_groups_org_active_name (organization_id, active_name),
    INDEX idx_org_team_groups_org_sort (organization_id, deleted_at, sort_order)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci
  COMMENT='チームグループ（組織内のチーム区分）';
```

| 項目 | 仕様 |
|---|---|
| 名前 | 前後の空白を除いて 1〜50 文字（コードポイント数）。生存グループ内で重複不可（照合順序により大文字小文字・全半角の一部は同一視される）|
| 上限 | 1組織あたり生存グループ **100 件**（マスター裁定 2026-09-30。グループ指定の `target_group_ids` を常に多値インデックスの上限 148 件に収めるため）。超えると 422 `ORG_066` |
| `sort_order` | 作成時は「現在の最大値 + 1」。並び替えは全件の順序を一括で受け取り、0 から振り直す。同じ値の重複は DB では禁じず、サービス層で並び替え時に解消する |
| 削除 | 論理削除（`deleted_at`）。削除済みグループは一覧・選択肢・範囲計算・表示判定のすべてから除外する |
| 階層 | 持たない（親グループ列なし） |

### 5.4 新規 `team_org_affiliation_restrictions`（再申請・再招待の抑止）

```sql
    CONSTRAINT chk_toar_reason CHECK (reason IN ('REJECTED','DECLINED','WITHDRAWN','CANCELLED')),
    CONSTRAINT chk_toar_until CHECK ((kind = 'BLOCK' AND restricted_until IS NULL)
                                  OR (kind = 'COOLDOWN' AND restricted_until IS NOT NULL))
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci
  COMMENT='チーム加盟の申請・招待の再送制限';
```

| 仕様 | 内容 |
|---|---|
| 拒否後の冷却 | 申請の拒否（REJECTED）・招待の拒否（DECLINED）で、その向きに **30日**（`mannschaft.affiliation.reject-cooldown-days`）止める |
| 連打防止の冷却 | 申請の取下げ（WITHDRAWN）・招待の取消（CANCELLED）で、その向きに **24時間**（`mannschaft.affiliation.resend-cooldown-hours`）止める。取下げ→再申請の繰り返しで相手に通知が連打されるのを防ぐ |
| 既存行との合成 | UPSERT で1行にまとめる。BLOCK は COOLDOWN で上書きしない。COOLDOWN どうしは期限の遅いほうを残す |
| ブロック | 拒否時に `block=true` を付けると、期限なしで止める。解除は止めた側の ADMIN が一覧から行う |
| 判定 | `kind='BLOCK' OR restricted_until > :now`（`:now` は `wallClock` の現在時刻。§4.6）の行があれば拒否（403 `TEAM_068`）。期限切れの行は判定で無視し、夜間バッチで物理削除する |
| 相手に見せる情報 | 冷却中かブロックかは相手に**区別して見せない**（どちらも「現在この組織には申請できません」）。止めた側の ADMIN だけが種別・理由・期限を見られる |
| 解除一覧に出す行 | 止めた側が意思を持って作った REJECTED・DECLINED の行だけ。WITHDRAWN・CANCELLED（自分の操作で自分側が止まる24時間）は一覧に出さない |
| 除名・離脱 | 制限を自動では作らない |

> **宛先集合のキーを `scope_ref` に入れる理由（2026-09-29 の殿の判断で改めた）**: main の fan-out は、Worker が受信者ソースへ渡す `FanoutPageRequest`（`notification/fanout/FanoutPageRequest.java`）と `countRecipients(scopeRef, includeSupporters)` に `scopeRef` しか持たせておらず、ジョブ ID が無い。シャード分割（`NotificationFanoutJobService.resolveAndSplitShards`）は子シャード行を**別の ID** で作るが、**`scopeRef` は親から子へそのまま複製する**（origin/main で確認済み。兄弟シャードの検索も `scopeType`・`scopeRef`・`notificationType`・`sourceEventUuid` の一致で行う）。そこで、宛先集合のキー `audience_snapshot_id` を**ジョブ行の `scope_ref` に UUID 文字列（36文字。`scope_ref` は VARCHAR(36)）で入れる**。main の `CONFIRMABLE_TARGETS`（`ConfirmableTargetsFanoutRecipientSource`。`scopeRef` = 確認通知 ID で、宛先の表を引く）と同じ作法である。これにより `FanoutPageRequest`・`countRecipients`・`resolveAndSplitShards`・ジョブ表の変更は**要らない**（旧案の `audience_snapshot_id` 列・`FanoutCountRequest` は廃止した）。同じ組織で複数のジョブが同時に動いても、`scopeRef` が告知ごとに異なるので混ざらない。
>
> | 項目 | 設計 |
> |---|---|
> | キーの決め方 | `audience_snapshot_id = UUID.nameUUIDFromBytes(("F02.8:broadcast-audience:" + feedId).getBytes(UTF_8))`（フィード ID から決定的に導く。同じ告知の二重 enqueue でも同じ集合を指し、見出し・宛先行は主キーで1組に収束する）|
> | 親ジョブ | `scope_type = ORGANIZATION_TEAMS`、`scope_ref = audience_snapshot_id` の UUID 文字列、`organization_id` = 組織 ID で enqueue する（§8.5.3）|
> | 子シャード | `resolveAndSplitShards` が `scopeRef` を複製するので、main の変更なしに親と同じ宛先集合を参照する |
> | シャードの可否 | **シャードを許す**。`CONFIRMABLE_TARGETS` がシャードを禁止（`shard_count=1` 固定）しているのは、軍議第8版のマスター裁可「1万件超のシャード分割は最初の段階では対応しない」という**範囲の判断**であり、`scopeRef` にキーを入れる作法の技術的な制約ではない。`ORGANIZATION_TEAMS` の受信者ソースは `MOD(user_id, shardCount)` の述語を持ち（§8.5.2）、`countRecipients` も実装する |
> | 受信者ソース側の解決 | `OrgTeamsFanoutRecipientSource` は `scopeRef` を UUID として解釈し、`notification_fanout_audiences` から組織 ID を、`notification_fanout_audience_teams` から宛先チームを引く |
> | 見出しが無いとき | `scopeRef` が UUID として解釈できない、または見出し行が無い場合は、空集合を返さず例外にする（宛先ゼロとして静かに完了させない。AC-H32c）|
> | 削除 | 見出しと宛先行は同一ドメインなので CASCADE を張る。1つの集合を複数のジョブ行（親と子シャード）が参照するので、ジョブ行からの FK・CASCADE は張らない。main には完了ジョブの削除が無いので、宛先集合もジョブ行と同じく残す。将来ジョブを掃除するときは、参照するジョブが0件になった集合を同じ処理で消す |
> `target_group_ids` の多値インデックス（`CHAR(36) ARRAY`）は、UUID 文字列で保存する前提である。
>
> **多値インデックスの件数上限（部隊 1-B の実測。AC-H14a。`AnnouncementMultiValuedIndexLimitIT` が固定）**: InnoDB の多値インデックスは 1 レコードあたりのキー総バイト数に上限があり（mysql:8.0・16KB ページで 5,352 バイト）、超えると INSERT / UPDATE 自体が失敗する。1 キーは `CHAR(36) ARRAY` で 36 バイト、`UNSIGNED ARRAY` で 8 バイトなので、**`target_group_ids` は最大 148 件、`target_team_ids` は最大 669 件**（+1 件で失敗）。当初の想定「5,000 件」は成立しない。上限は、マスター裁定（2026-09-30）で「チームを選ぶ」**500 チーム**（実測 669 に収まる）、チームグループ **1 組織あたり 100 件**（`target_group_ids` は常に 148 に収まる）と確定した。超えたときは索引が拒否する前にアプリで 400（`BROADCAST_010`）・422（`ORG_066`）にすること。また索引に乗る検索は `? MEMBER OF (target_group_ids->'$[*]')` の形だけで、列名を直接渡す `MEMBER OF (col)` や `JSON_CONTAINS(col, ...)` は全走査になる（実測）。
>
> **DDL 実装時の調整（部隊 1-B）**: 原則6（新規表は UuidV7Entity 継承）のため、`announcement_feed_group_snapshots`・`notification_fanout_audience_teams` は複合主キーでなく `id BINARY(16)` 主キー + 上記の複合キーを UNIQUE（`uk_afgs_feed_group_team`・`uk_nfat_audience_team`）とした。`notification_fanout_audiences.created_at` は Instant のため `DATETIME(6)`。
> `announcement_feed_group_snapshots` は social ドメインの表で、`announcement_feeds` と同じドメインなので CASCADE を張れる（原則2）。行数は「グループ宛てお知らせ1件あたりの送信時の対象チーム数」で、件数上限は掛けない（1行が小さく、JSON の多値インデックスのような1レコードあたりの上限が無いため）。
> `announcement_feeds.id` は `BIGINT UNSIGNED`（AUTO_INCREMENT。V13.019）であり、子表の `feed_id` も `BIGINT UNSIGNED` とする。

## 6. 加盟のビジネスロジック

### 6.1 チームからの申請

```
POST /api/v1/teams/{teamSlug}/org-applications   body: {organizationSlug, groupId?, message?}
1. チームが存在・未削除か → 無ければ 404（既存のチーム不在コード）
2. 操作者がそのチームで加盟操作権限（`MANAGE_ORG_AFFILIATION`。§3.2）を持つか → 無ければ 403
3. チームのアーカイブ確認 → アーカイブ済みなら既存のアーカイブ拒否（422）
4. 組織が存在・未削除で、操作者から visibility 上見えるか → 見えなければ 404（不在と同じコード）
5. 組織のアーカイブ確認 → 既存のアーカイブ拒否（422）
6. 組織の team_application_enabled が TRUE か → FALSE なら 403 TEAM_064
7. チーム行（`teams`）→ 組織行（`organizations`）の固定順で PESSIMISTIC_WRITE ロックを取る（下記・§6.9）。ロックを保持したまま 7〜11 を行う（INSERT までロックを離さない）
   ロック取得後に状態を再確認する: チームが削除済み → 404、アーカイブ済み → 422 / 組織が削除済み → 404、アーカイブ済み → 422 / 受付が FALSE → 403 TEAM_064（step 1・3〜6 と同じ応答）
   制限（TEAM_APPLY 方向）の有無 → あれば 403 TEAM_068
8. 同じ (team, org) の行があるか
     ACTIVE → 409 TEAM_065 / PENDING(TEAM_APPLY) → 409 TEAM_066 / PENDING(ORG_INVITE) → 409 TEAM_066（「招待が届いています」の案内付き）
9. チームの PENDING(TEAM_APPLY) 件数が 10 以上 → 422 TEAM_069
10. グループ選択の検証（実効モード）
     OFF: group_id を指定されたら 400 TEAM_072（黙って捨てない）
     OPTIONAL: 指定時のみ、その組織の生存グループか検証 → 違えば 400 TEAM_072
     REQUIRED: 未指定なら 400 TEAM_067、指定時は OPTIONAL と同じ検証
11. INSERT（status=PENDING, direction=TEAM_APPLY, group_id, message, invited_by=操作者, invited_at=:now。§4.6）
    一意制約違反（並行申請）は 409 TEAM_066 に写像する
12. 組織の ADMIN 全員へ通知（`TEAM_ORG_APPLICATION_RECEIVED`。§6.7）
13. audit_logs: TEAM_ORG_APPLICATION_SUBMITTED
14. 201 Created
```

- 1チームが**複数の組織へ同時に申請・加盟してよい**（§9）。step 8 の重複判定は同じ組み合わせ（team, org）だけを見る。
- **同時申請の件数上限（step 9）の競合対策**: 件数を数えてから INSERT する間に、同じチームの別の申請が割り込むと、PENDING が9件の状態から並行した2件がともに通り11件になる。一意制約は (team, org) の組にしか掛からないので、別々の組織への並行申請は防げない。そこで、申請のトランザクションは step 7 の冒頭で**そのチームの `teams` 行を `PESSIMISTIC_WRITE`（`SELECT ... FOR UPDATE`）でロック**し、制限・既存の加盟・件数の確認と INSERT をこのロックの内側で行う。ロックの対象は、申請中に削除・作成されることがなく同じチームの申請どうしが必ず取り合う行として、チーム行を選ぶ（PENDING 行そのものは件数が0のとき存在しないためロックの対象にできない）。同じ step 7 で続けて**組織行もロック**する（チーム行 → 組織行の固定順）。チーム・組織の削除・アーカイブとの順序は、両方のロック取得後に step 1・3〜6 と同じ状態を再確認して担保する（AC-B17・AC-E07。§6.9）。

### 6.2 組織による承認

```
POST /api/v1/organizations/{slug}/team-applications/{membershipId}/approve   body: {overrideGroup: boolean, groupId?: UUID|null}
1. 組織の存在・未削除 → 404 / 操作者が組織 ADMIN か → 403
2. 行を (id, organization_id, status=PENDING, direction=TEAM_APPLY) で取得 → §6.4 の判定表
3. 状態の再確認: 組織がアーカイブ済み → 422（既存のアーカイブ拒否）。
   チームが削除済み → 404 TEAM_070（行は §4.5 の片付けで消える）、チームがアーカイブ済み → 422
4. 確定グループを決める（リクエストの overrideGroup で区別する。§10.5）
     overrideGroup=false → 申請時の group_id をそのまま使う（削除済みグループなら NULL）
     overrideGroup=true かつ groupId が UUID → その組織の生存グループか検証（違えば 400 TEAM_072）
     overrideGroup=true かつ groupId が null → 未分類で承認
     グループ機能 off → 常に NULL
5. 条件付き UPDATE: status=ACTIVE, group_id=確定値, message=NULL, responded_by, responded_at=:now
   影響行数 0 → §6.4 の判定表
6. チームの加盟操作者全員へ通知（`TEAM_ORG_APPLICATION_APPROVED`。§6.7）
7. audit_logs: TEAM_ORG_MEMBERSHIP_CREATED（via=TEAM_APPLY, requested_group_id, group_id）
8. 200 OK（加盟1件の表現を返す）
```

- グループ選択が REQUIRED の組織でも、承認時に組織 ADMIN が「未分類で承認」を選ぶことは許す（REQUIRED は申請者への入力要求であり、管理者の判断を縛らない）。
- 承諾（招待を受けたチームが承諾する）でも同じ step 3 の再確認を行う。

### 6.3 組織による拒否

```
POST /api/v1/organizations/{slug}/team-applications/{membershipId}/reject   body: {reason?: string(≤500), block?: boolean}
1〜2. 承認と同じ
3. 条件付き DELETE（PENDING かつ TEAM_APPLY）→ 影響行数 0 なら §6.4 の判定表
4. 制限を UPSERT（direction=TEAM_APPLY, reason=REJECTED, kind=block ? BLOCK : COOLDOWN, restricted_until=block ? NULL : :now+30日）
5. チームの加盟操作者全員へ通知（`TEAM_ORG_APPLICATION_REJECTED`。reason 指定時は理由入りの本文。§6.7）
6. audit_logs: TEAM_ORG_APPLICATION_REJECTED（reason, block）
7. 200 OK
```

### 6.4 チームによる取下げと、競合時の応答の判定表

```
DELETE /api/v1/teams/{teamSlug}/org-applications/{membershipId}
1. チームの存在 → 404 / 操作者がそのチームの加盟操作者か → 403
2. 条件付き DELETE（id, team_id, PENDING, TEAM_APPLY）→ 影響行数 0 なら下の判定表
3. 制限を UPSERT（direction=TEAM_APPLY, reason=WITHDRAWN, kind=COOLDOWN, restricted_until=:now+24時間）
4. audit_logs: TEAM_ORG_APPLICATION_WITHDRAWN
5. 204 No Content
```

membershipId を取る操作の応答は、**操作時点の行の状態だけ**で決まる（先にどちらが来たかで一意に決まる）。

| 操作時点の行（`id` と自スコープの組で引く） | 応答 |
|---|---|
| 行が無い（存在しない ID・他組織／他チームの ID・既に削除済み） | 404 `TEAM_070` |
| 行はあるが、状態または向きが操作の前提と違う（例: 既に ACTIVE の行を取り下げる・招待行を承認する） | 409 `TEAM_071` |
| 前提どおり | 成功 |

例（AC-B14）: 取下げ→承認の順なら、承認は 404 `TEAM_070`。承認→取下げの順なら、取下げは 409 `TEAM_071`。

### 6.5 組織からの招待・承諾・拒否・取消（既存設計の正式化）

F01.2 03_business_logic の①〜④を、次の点を改めたうえで正とする。

| 点 | 改める内容 |
|---|---|

| 承諾 | 条件付き UPDATE（チーム行 → 加盟行の順にロック。組織の状態とグループの生存はトランザクションの前に組織ドメインの読み取りで確かめる）。§6.2 step 3 と同じ状態の再確認を行う。承諾時にグループは変えられない（グループは組織の管理事項のため）。**招待で指定したグループが承諾の時点で削除済みなら、未分類（`group_id = NULL`）で加盟を成立させる**（承諾は拒否しない。承認時の §6.2 step 4 と同じ扱い。マスター裁可 2026-09-29）。グループ機能が承諾の時点で off なら `group_id = NULL` |

### 6.6 離脱・除名

F01.2 の⑤⑥を slug パスに改めて正とする（`DELETE /teams/{teamSlug}/organizations/{orgSlug}`、`DELETE /organizations/{slug}/teams/{teamSlug}`）。行を物理削除すると `group_id` も一緒に消える。再加盟したときは未分類から始まる。1チームが複数の組織に加盟している場合、離脱・除名は指定した1組織との関係だけを消し、他の組織との関係には影響しない。

**相手側への通知（マスター裁可 2026-09-29）**: 離脱・除名は、どちらも相手側へ通知する。理由欄は設けない（body なし）。

| 操作 | 受信者 | `notification_type` |
|---|---|---|
| 離脱（チーム側の操作） | 組織の ADMIN 全員 | `TEAM_ORG_MEMBERSHIP_LEFT` |
| 除名（組織側の操作） | チームの加盟操作者全員（チーム ADMIN と `MANAGE_ORG_AFFILIATION` を持つ人）| `TEAM_ORG_MEMBERSHIP_REMOVED` |

### 6.7 通知の宛先と量

加盟の通知は、組織側なら**組織 ADMIN**、チーム側なら**チームの加盟操作者**（チーム ADMIN と `MANAGE_ORG_AFFILIATION` を付与されたメンバー）に送る（1件の操作で数名）。文面キーは §14.2。

**送り方（2026-09-29 の殿の判断。旧案の `NotificationHelper.notify` による同期送信は廃止）**

- 通知は、状態を変える操作（申請・承認・拒否・招待・承諾・離脱・除名・期限切れ・システムによる取消）と**同じトランザクションの中で fan-out ジョブを1件 enqueue するだけ**にする。main に既にある `NotificationFanoutJobService.enqueueInCurrentTransaction`（`Propagation.MANDATORY`、CMP-260920-1040 で追加）を使う。
- 通知行の作成と push の配信は Worker が非同期に行う。**配信が失敗しても、申請などの操作はロールバックしない**（ジョブは Worker の再試行と既存の stuck 回復に任せる）。一方、enqueue の INSERT 自体が失敗した場合は、同じトランザクションなので操作ごとロールバックする（通知を出さずに状態だけ変わることはない）。
- **2-C（招待・承諾・辞退・取消）は、4-A の監査と同じく通知と監査をコミットの後に行う**（Codex 検分の指摘。チームの書き込みトランザクションから通知・監査ドメインの Repository に届かせない）。通知は `TeamAffiliationNotifier.enqueueAfterCommit`（`NotificationFanoutJobService.enqueueInOwnTransaction`。通知ドメインのトランザクションで、冪等キーは同じ）、監査は `TeamAffiliationAuditRecorder` を書き込みのコミット後に呼ぶ。業務と通知・監査の登録は原子的でなくなるため、どちらの失敗も操作を巻き戻さない。コミット後の順序は**監査 → 通知**とし、通知の登録が失敗（例外として呼び出し元へ伝わる）しても先に記録した監査は残る（再試行は状態判定で拒否されるため、監査を後から回復できない）。なお監査の保存失敗は、共通サービス `AuditLogService.recordSync` の既存の挙動どおり例外にならずログ（ERROR）に残るだけで呼び出し元へは伝わらない（2-C の範囲では変えない）。
- 受信者は **Worker の処理時点で解決する**。受信者ソースは次の2つを新設する（どちらも `shard_count=1` 固定。受信者が数名のため）。

| 戦略キー（`scope_type`）| `scope_ref` | 受信者 |
|---|---|---|
| `ORGANIZATION_ADMINS` | 組織 ID | 組織の ADMIN 全員（在籍中・ACTIVE のユーザー）|
| `TEAM_AFFILIATION_OPS` | チーム ID | チーム ADMIN と、権限グループで `MANAGE_ORG_AFFILIATION` を付与されたユーザー（在籍中・ACTIVE）|

> **`scope_type` は `notification_fanout_jobs.scope_type` VARCHAR(20)（Entity の `length` も20）に収める。列を広げる migration は行わない**。本書で新設する `scope_type` はいずれも main の列長制約内である。
>
> | `scope_type` | 文字数 |
> |---|---|
> | `ORGANIZATION_TEAMS` | 18 |
> | `ORGANIZATION_ADMINS` | 19 |
> | `TEAM_AFFILIATION_OPS` | 20 |

- **main の `enqueueInCurrentTransaction` の拡張が要る**: main の版は、CONFIRMABLE_TARGETS 専用に「文面行を作らない（sink が本体を読む）・`action_url` は NULL・`shard_count=1` 固定」になっている。加盟の通知（文面は `FanoutMessageKind` で6言語を描画、`action_url` あり）と §8.5.3 の告知 push（文面は `SURVEY_PUBLISHED`、シャードの自動評価が要る）はそのままでは使えない。そこで、引数を1つの record（`FanoutEnqueueCommand`。`scopeType`・`scopeRef`・`notificationType`・`idempotencyKey`・`organizationId`・`priority`・`actorId`・`sourceType`・`sourceId`・`actionUrl`・`includeSupporters`・文面（`FanoutMessageKind` と引数。任意）・シャードの扱い（`FIXED_SINGLE` / `AUTO`））にまとめた `enqueueInCurrentTransaction(FanoutEnqueueCommand)` を追加する。
- **既存の9引数版は変えない**（2026-09-29 の殿の判断）。新版へ委譲させず、重複 enqueue 時に `DataIntegrityViolationException`（`uk_fanout_idempotency`）が呼び出し元へ伝播する既存の挙動もそのまま維持する（回帰させない）。
- **新版（`FanoutEnqueueCommand`）は冪等 SQL で登録する**: ジョブ行・宛先集合行（§6.7・§8.5.3 で使う）を、MySQL の `INSERT ... ON DUPLICATE KEY UPDATE id = id`（更新結果を変えず1行として確定させるだけの no-op upsert）で INSERT する。同一 TX 内で `DataIntegrityViolationException` を捕捉しても、Spring のトランザクションはこの時点で既に rollback-only になっており（例外がいったんトランザクション同期に伝わった後）、捕捉だけでは元のトランザクション（申請・承認・告知などの本体操作）を救えない。したがって try-catch では解決せず、そもそも例外を出さない冪等 SQL で登録する。

### 6.9 アーカイブ・削除と、申請・招待の作成の直列化

「状態を確認 → 相手がアーカイブされ片付けが走る → PENDING を INSERT」の順に進むと、アーカイブ済みの相手に PENDING が残る。これを防ぐため、PENDING を作る経路と、組織・チームの状態を変える経路が**同じ行ロックを取り合う**ようにする。

| 経路 | 取るロック | 片付け |
|---|---|---|
| 申請の作成（§6.1） | チーム行 → 組織行の固定順で `PESSIMISTIC_WRITE`。取得後に両者の状態を再確認し、INSERT とコミットまで保持する | — |
| 招待の作成（§6.5。2-C） | チーム行だけを `PESSIMISTIC_WRITE`（トランザクションを team ドメインに閉じるため組織行は取らない）。組織の状態はトランザクションの前に読み、**コミット後に読み直す** | 読み直しでアーカイブ・削除を見つけたら、作った招待を取り下げる |
| チームのアーカイブ（`TeamService.archiveTeam`） | チーム行を `PESSIMISTIC_WRITE` で取ってから `archived_at` を立てる | 同じトランザクションで当該チームの PENDING を DELETE |
| 組織のアーカイブ（`OrganizationService.archiveOrganization`） | 組織行を `PESSIMISTIC_WRITE` で取ってから `archived_at` を立てる（組織行の UPDATE そのものも同じ行ロックを取る） | コミット後に `OrganizationArchivedEvent`（AFTER_COMMIT）で team ドメインが PENDING を DELETE |
| チームの論理削除 | チーム行の UPDATE（`deleted_at`）が同じ行ロックを取る | `TeamDeletedEvent`（AFTER_COMMIT） |

- **作成が先にロックを取った場合**: アーカイブ側はロック待ちになり、作成のコミット後に進む。チームのアーカイブは続く DELETE（ロック付きの読み取りなので最新のコミット済み行を見る）で、組織のアーカイブはコミット後に走るリスナーの DELETE で、いま INSERT された PENDING も消す。
- **アーカイブが先にロックを取った場合**: 作成側はロック待ちになり、アーカイブのコミット後にロックを得て状態を再確認し、アーカイブ済みとして 422 を返す（INSERT しない）。`SELECT ... FOR UPDATE` はロック付きの読み取りなので、REPEATABLE READ でもアーカイブのコミットを見る。
- **デッドロックしない理由**: 作成側は常にチーム行 → 組織行の順で取り、アーカイブ・削除の側は自分の行1つしか取らないため、循環待ちが生じない。
- **招待と組織のアーカイブ（2-C）**: 招待は組織行をロックしないので、「組織の状態を確認 → 組織がアーカイブされ片付けが走る → 招待を INSERT」の順に進みうる。そこで招待のコミットの後に組織の状態を読み直す。読み直しの時点でアーカイブがコミット済みなら、招待の側が作った PENDING を消して `ORG_003` を返す。まだコミットされていなければ、後でコミットされたアーカイブの片付け（`OrganizationArchivedEvent`）が、コミット済みの招待の行を消す。どちらの順でも PENDING は残らない（AC-E08）。チームのアーカイブとはチーム行のロックで直列化される。
- 承認・承諾（§6.2・§6.5）は PENDING 行の条件付き UPDATE で、ここでは対象外（行が消えていれば 404 `TEAM_070`）。承諾（2-C）は組織の状態をトランザクションの前に読む。承諾のコミットと組織のアーカイブが前後しても、ACTIVE はアーカイブで消えない（§4.5）ので「アーカイブの直前に承諾した」のと同じ結果になる。

## 7. チームグループのビジネスロジック

### 7.1 作成・変更

- 作成: 名前の正規化（前後空白除去）→ 重複（生存行）なら 409 `ORG_065` → 生存件数が 100 なら 422 `ORG_066` → `sort_order = max + 1` で INSERT。
- 変更: 名前・説明のみ。並び順は §7.2 の API だけで変える。
- 名前を変えても、送信済みお知らせの記録（`target_audience`）に残した名前は変えない（送信時点の記録のため）。

### 7.2 並び替え

`PUT /organizations/{slug}/team-groups/order` で、生存グループ全件の ID を新しい順に受け取る。受け取った集合が現在の生存グループ集合と一致しなければ 409 `ORG_068`（他の管理者が同時に追加・削除した）。一致すれば 0 から振り直す。

### 7.3 削除（越境トランザクションを使わない）

```
DELETE /organizations/{slug}/team-groups/{groupId}
1. 組織 ADMIN 検証・グループ機能 on 検証
2. (id, organization_id, deleted_at IS NULL) で取得 → 無ければ 404 ORG_064
3. org_team_groups.deleted_at = :now（wallClock。organization ドメインのトランザクションだけで完結）
4. OrgTeamGroupDeletedEvent(organizationId, groupId) を発行
5. audit_logs: ORG_TEAM_GROUP_DELETED
6. 204 No Content

[team ドメイン] TeamOrgGroupUnassignListener（@TransactionalEventListener(AFTER_COMMIT) + @Async）
  UPDATE team_org_memberships SET group_id = NULL
   WHERE organization_id = ? AND group_id = ?        -- ACTIVE・PENDING とも
  冪等（何度実行しても同じ結果）。失敗時はログに残し、夜間バッチ TeamOrgGroupOrphanRepairBatch
  （@BatchEndpoint name=team-org-group-orphan-repair。§6.8）が「削除済みグループを指す group_id」を拾って NULL に戻す
```

- 付け替えが非同期なので、ごく短い間 `group_id` が削除済みグループを指す。**すべての読み手は `org_team_groups.deleted_at IS NULL` で JOIN し、削除済みを指す行を「未分類」として扱う**（§5.1）。このため、付け替え前後で画面・判定の結果は変わらない。
- 削除の確認ダイアログで「所属している N チームは未分類に戻ります」と件数を示す。
- 送信済みのグループ宛てお知らせ（`target_group_ids` に削除済みグループを含むもの）は、**削除済みのグループについては送信時スナップショット（`announcement_feed_group_snapshots`）で表示を判定する**（§8.2）。そのため、削除したグループ宛ての過去のお知らせは、**送信時点でそのグループの対象だったチームに表示され続ける**（御裁可済み #6）。
- 範囲テンプレートは削除時に書き換えない（social ドメインへ波及させない）。テンプレートを使うときにサーバー側で解決する（§8.6）。

### 7.4 割当

| 操作 | API | 内容 |
|---|---|---|
| 単体 | `PUT /organizations/{slug}/teams/{teamSlug}/team-group` body `{groupId: UUID\|null}` | ACTIVE の加盟1件の group_id を変更。null で未分類 |
| 一括 | `PUT /organizations/{slug}/team-group-assignments` body `{groupId: UUID\|null, teamSlugs: string[1..500]}` | 指定チームをまとめて同じグループへ（または未分類へ）。1件でもその組織の ACTIVE 加盟でないチームを含めば、**全体を** 400 `ORG_069` で拒否し、該当 slug を返す（部分成功にしない） |

- 既存加盟チームは移行時に全件が未分類（`group_id = NULL`）になる。組織 ADMIN は加盟チーム一覧で「未分類」に絞り込み、一括割当で振り分ける。
- 監査ログ `TEAM_ORG_GROUP_CHANGED` は、4-A のグループ監査と同じく**書き込みのコミット後に**記録する（トランザクションを auth ドメインへ広げない）。一括割当は、1件でも不正なら例外で終わるため監査は1行も残らない。
- 組織が閲覧者から見えない場合は、存在しない組織と同じ 404 `ORG_001`（F00 の ORGANIZATION ラダーで判定）。SYSTEM_ADMIN は組織 ADMIN を兼ねていても 403（閲覧のみ）。
- 割当を変えると、グループ宛てお知らせの**表示**は閲覧時の所属で判定するため、変更後の所属に従う（§8.2）。送信済みの push には影響しない。

## 8. グループ宛てお知らせ（F02.8 との接続）

### 8.1 宛先の指定方法

組織スコープの告知ウィザード（ステップ1）の「対象チーム」を、次の3つから選べるようにする。グループ機能 off の組織では、従来どおり「すべて／チームを選ぶ」の2択である。

| 選び方 | 入力 | 対象 |
|---|---|---|
| すべてのチーム | なし | 制限なし（`target_team_ids = NULL`・従来どおり） |
| チームを選ぶ | `targetTeamIds`（1〜500件） | 指定チーム（従来どおり） |
| チームグループで選ぶ | `targetGroupIds`（個別チェック）、`targetGroupRange`（範囲）、`includeUnassigned` | 個別チェックしたグループ ∪ 範囲に入るグループ に所属するチーム、∪（`includeUnassigned` なら）未分類のチーム。**加えて、組織の直属メンバー**（どのチームにも属さない組織役員など）|

範囲の定義（`sort_order` の昇順＝グループ管理画面の上から下の並び）:

| UI の表示 | 送る値 | 含まれるグループ |
|---|---|---|
| 「{A} 以前」（先頭から A まで） | `{fromGroupId: null, toGroupId: A}` | `sort_order <= A.sort_order` |
| 「{A} 以降」（A から末尾まで） | `{fromGroupId: A, toGroupId: null}` | `sort_order >= A.sort_order` |
| 「{A} 〜 {B}」 | `{fromGroupId: A, toGroupId: B}` | `A.sort_order <= sort_order <= B.sort_order`。A が B より後ろなら 400 `BROADCAST_008` |

- 「以前／以降」は**グループ管理画面の並び順で上か下か**を意味する。年度のように古い順に並べれば「平成20年度以前」がそのまま読める。画面に「並び順はチームグループ管理で変えられます」と添える。
- 個別チェックと範囲は併用でき、和集合を取る。範囲に未分類は含まれない。
- 同じ送信内で「チームを選ぶ」と「チームグループで選ぶ」は併用しない（400 `BROADCAST_011`）。
- **直属メンバーを含める理由**（マスター確定）: 組織役員などチームに属さない人は、どのグループにも入れようがない。グループ宛てで彼らを外すと、組織の運営者自身にお知らせが届かなくなる。

### 8.2 表示は動的、push は「チーム集合は送信時・ユーザーは配信時」（殿の判断・以前のスナップショット推奨を上書き）

| 観点 | 解決する時点 | 保存するもの |
|---|---|---|
| **グループの集合**（範囲をどのグループに展開するか） | 送信時 | 範囲を送信時の `sort_order` で展開したグループ ID 集合を `announcement_feeds.target_group_ids` に保存。未分類の有無は `include_unassigned` |
| **表示**（どのチームのダッシュボードに出るか） | **グループが生きている間は閲覧時（動的）、グループが削除された後は送信時スナップショット** | 送信時に、展開したグループごとの所属チームを `announcement_feed_group_snapshots` に保存する（push の有無にかかわらず、グループ宛ての告知では常に保存）。判定の切替条件は下の表 |
| **push の対象チーム**（どのチームに配るか） | **送信時（固定）** | 上と同じスナップショットのチーム集合（重複排除）を、宛先集合の表 `notification_fanout_audience_teams`（キー `audience_snapshot_id`。§5.6）に写す |
| **push の受信ユーザー**（そのチームの誰に届くか） | **Worker の処理時** | 保存しない。Worker がチャンクを取るたびに、対象チームの現役メンバーと組織の直属メンバーをその時点の所属で解決する（§8.5.2 の母集団）|

**表示判定の切替条件**（`target_group_ids` の各グループ g について、閲覧時に `org_team_groups.deleted_at` を見て決める）

| g の状態（閲覧時） | 判定方法 | チームT に表示する条件 |
|---|---|---|
| 生存（`deleted_at IS NULL`） | **動的** | T がその組織に ACTIVE で加盟し、その組織での現在の所属グループが g |
| 削除済み（`deleted_at IS NOT NULL`） | **スナップショット** | `announcement_feed_group_snapshots` に (feed, g, T) の行があり、T がその組織に**今も** ACTIVE で加盟している |
| 未分類（`include_unassigned` が真） | 動的 | T の現在の所属グループが無い（NULL または削除済みを指す）|

- お知らせは、上のいずれか1つでも満たせば T に表示する（OR）。
- 切替はグループごとに独立している。同じお知らせの中で、生存グループは動的、削除済みグループはスナップショットで判定する。
- 送信後に g へ移ってきたチームは、g が生きている間は表示されるが、g の削除後は（スナップショットに無いため）表示されなくなる。送信時に g にいて後で別グループへ移ったチームは、g が生きている間は表示されず、g の削除後は表示される。これは「削除後は送信時点で対象だったチームに見せる」という御裁可の定義どおりの挙動である。

理由:

1. **表示を動的にする理由**: グループの付け忘れ・付け間違いを後から直したとき、直したチームにも過去のお知らせが見えるべきである（例: 平成18年度卒のチームを未分類のまま放置していた）。また、送信時に宛先チーム ID を展開して保存する方式は、大きな組織では1件のお知らせに数千のチーム ID を持たせることになり、多値インデックスの1行あたりのキー数の上限（実測で 669 件。§8.3）に近づく。グループ ID で保存すれば、1件あたり最大100件（グループの作成上限）で済み、多値インデックスの上限（`CHAR(36) ARRAY` で 148 件）に必ず収まるので、**グループ指定には「チームを選ぶ」の500件のような件数上限を掛けなくてよい**。
2. **グループの集合を送信時に固める理由**: 「平成20年度以前」と送った意味は、後でグループの並びを変えたりグループを追加したりしても変わるべきではない。
3. **push の対象チームを送信時に固定する理由**: push は送信時に一度だけ配るものであり、後からグループの所属が変わっても配り直せない。どのチームに配るかは送信時に確定させる。
4. **push の受信ユーザーを Worker 処理時に解決する理由**（殿の判断）: 受信ユーザー ID を送信時に全件保存すると、大きな組織では1件の告知に数万〜数十万行を書くことになり、告知のトランザクション（§8.5.3）が重くなる。また、既存の fan-out（`ORGANIZATION` / `TEAM` など）はすべて Worker がチャンクごとにその時点の所属から受信者を引く方式であり、これに揃える。この結果、enqueue から Worker 処理までの間にチームへ加入した人には届き、離脱した人には届かない。対象チームが組織から離脱していれば、そのチームのメンバーには届かない（AC-H33）。

この結果、**表示と push で解決時点が異なる**。送信後にグループの所属が変わったチームでは、「push は来なかったが表示される」「push は来たが表示されない」が起こり得る。これは上の理由による意図した挙動であり、UI の送信履歴には「表示は現在の所属で判定されます」と注記する。

- 「チームを選ぶ」（`target_team_ids`）は従来どおり送信時のチーム ID をそのまま保存し、表示もそのチーム ID で判定する（表示の挙動は変えない。push は §8.5.1 で変わる）。

### 8.3 上限と空集合

| 条件 | 扱い |
|---|---|
| 「チームを選ぶ」で500チームを超える | 400 `BROADCAST_010`。「すべてのチーム」かチームグループを使うよう案内する |
| グループ指定 | 件数上限なし（グループは1組織100件まで。作成上限により `target_group_ids` は常に多値インデックスの上限 148 件に収まる） |
| グループ指定の解決結果が0チームで、直属メンバーもいない | 400 `BROADCAST_009`（「対象になる人がいません」） |
| グループ機能 off の組織でグループ系の項目を指定 | 400 `BROADCAST_007` |
| 他組織・削除済みのグループ ID | 400 `BROADCAST_006`（存在するかどうかを区別しない） |
| TEAM スコープの告知でグループ系の項目を指定 | 400 `BROADCAST_012` |

**「チームを選ぶ」の候補の検証（Codex 軍議検分の指摘で明記）**: main の `AnnouncementBroadcastService.validateTargetTeamIds` は、候補を `UserRoleRepository.findTeamIdsByOrganizationId`（`user_roles` の組織ロール行 ∪ ACTIVE の `team_org_memberships`）で作っている。**この呼び出しを廃止し**、team ドメインに **ACTIVE の `team_org_memberships` だけを引く専用クエリ**（`TeamOrgMembershipQueryService.findActiveTeamIdsIn(organizationId, teamIds)`。`WHERE organization_id = ? AND status = 'ACTIVE' AND team_id IN (...)`）を置き、social ドメインはこの Service 経由で呼ぶ（F02.8 §11.1・§17 #20・AC-K07）。グループの展開（§8.2）も同じ「ACTIVE の加盟」基準で行う。

> **上限の根拠（実測済み・マスター裁定 2026-09-30）**: `announcement_feeds` の多値インデックスは、mysql:8.0 で 1 レコードあたりのキー総量が 5,352 バイトまで（`AnnouncementMultiValuedIndexLimitIT` が固定）。`target_team_ids`（`UNSIGNED ARRAY`・8 バイト/キー）は最大 669 件、`target_group_ids`（`CHAR(36) ARRAY`・36 バイト/キー）は最大 148 件で、当初想定の 5,000 件は成立しない。よって「チームを選ぶ」の上限は余裕を見て **500 チーム**、チームグループは **1 組織あたり 100 件**（作成上限。これでグループ指定は常に索引に収まる）と確定した。

### 8.4 送信前プレビュー

`POST /api/v1/organizations/{orgId}/broadcast/audience-preview`（告知系のため数値 `{orgId}`。§10）で、宛先指定から解決されるチーム数・直属メンバー数と、先頭50件のチーム名を返す。ウィザードは入力が変わるたび（300ms デバウンス）に呼び、「該当: 12チーム＋直属メンバー3人」と表示する。0件のときは「次へ」を押せない。

### 8.5 push 通知の絞り込み

#### 8.5.1 対象になるチャネル（マスター確定）

**push を絞るのは、現在 push を出しているチャネルだけである。** main 時点でお知らせのチャネルのうち組織スコープで push を出しているのは、アンケートの公開通知（`SurveyPublishNotificationListener`、組織スコープ×ALL は `ORGANIZATION` fan-out）だけである。掲示板・タイムライン・ブログ・TODO・スケジュールは、グループで絞っても従来どおり push を出さない（push を新設しない）。

**宛先を絞った告知（「チームを選ぶ」と「チームグループで選ぶ」）は、push も同じ規則で絞る**（御裁可済み #19。「チームを選ぶ」はグループ宛てと同じ規則に揃える）。

| 告知の宛先 | 送信者 | アンケートの push |
|---|---|---|
| すべてのチーム | 誰でも | **従来どおり**（リスナーが `ORGANIZATION` fan-out を1件） |
| チームを選ぶ（`targetTeamIds`） | 組織 ADMIN / DEPUTY_ADMIN(MANAGE_CONTENT) / SYSTEM_ADMIN | **絞る（変更）**: 告知ウィザードが `ORGANIZATION_TEAMS` fan-out を1件出す。宛先は選んだチームのメンバー＋組織の直属メンバー。リスナーの `ORGANIZATION` fan-out は出さない |
| チームを選ぶ（`targetTeamIds`） | 組織 MEMBER | **出さない（変更）**（表示の絞り込みだけ。リスナーの `ORGANIZATION` fan-out も出さない）|
| チームグループで選ぶ | 組織 ADMIN / DEPUTY_ADMIN(MANAGE_CONTENT) / SYSTEM_ADMIN | **絞る**: 告知ウィザードが `ORGANIZATION_TEAMS` fan-out を1件出し、リスナーの `ORGANIZATION` fan-out は出さない |
| チームグループで選ぶ | 組織 MEMBER | **出さない**（表示の絞り込みだけ。リスナーの `ORGANIZATION` fan-out も出さない）|

**「チームを選ぶ」の既存挙動からの変更点**（御裁可済み #19）

| 観点 | 変更前（main） | 変更後 |
|---|---|---|
| ADMIN / DEPUTY が選んだチーム宛てのアンケート | 組織全体（直属＋配下チーム全部＋子組織）に push | 選んだチームのメンバー＋組織の直属メンバーだけに push |
| MEMBER が選んだチーム宛てのアンケート | 組織全体に push | push しない |
| 表示（ダッシュボード） | 選んだチームだけ | 変更なし |
| 「すべてのチーム」 | 組織全体に push | 変更なし |
| push の無いチャネル（掲示板など） | push なし | 変更なし |
| enqueue の経路 | リスナーが AFTER_COMMIT で非同期に enqueue | 告知ウィザードが告知と同一トランザクションで enqueue（§8.5.3）|

#### 8.5.2 受信者ソース `ORGANIZATION_TEAMS`

| 項目 | 設計 |
|---|---|
| 実装 | `OrgTeamsFanoutRecipientSource`（戦略キー `ORGANIZATION_TEAMS`、role ドメイン `com.mannschaft.app.role.fanout`。`OrgFanoutRecipientSource` と同じ理由で role ドメインに置く） |
| scope_ref | `audience_snapshot_id` の UUID 文字列（§5.6。組織 ID は見出し `notification_fanout_audiences.organization_id` から引く）|
| 宛先チーム | `notification_fanout_audience_teams` を、`FanoutPageRequest.scopeRef`（= `audience_snapshot_id`）で引く。中身は「チームを選ぶ」なら選んだチーム ID、「チームグループで選ぶ」なら送信時スナップショットのチーム ID。親ジョブと子シャードは同じ集合を参照する（§5.6）|
| 母集団 | ①宛先チームの現役メンバー（`TeamFanoutRecipientSource` と同じ条件: memberships `left_at IS NULL` ∪ user_roles、users 生存・ACTIVE）のうち、**配信時点でも**そのチームが組織に ACTIVE で加盟し、かつアーカイブ済み（`teams.archived_at`）・論理削除済み（`teams.deleted_at`）でないもの（アーカイブしても ACTIVE の加盟行は残るため、加盟行の status だけでは除けない。除外の基準は §10.9 の候補・展開と同じ。送信後・配信前にアーカイブ・削除されたチームも、Worker がチャンクを取る時点で除かれる）∪ ②**組織の直属メンバー**（組織スコープの memberships・user_roles。`OrgFanoutRecipientSource` の「直属」枝と同じ条件）。ユーザー単位で重複排除 |
| 含めないもの | 宛先外チームのメンバー、子組織のメンバー |
| 応援者トグル | `include_supporters` は告知の `target_role` から決める: `MEMBERS_AND_ABOVE` → false（純 SUPPORTER を除く）、`SUPPORTERS_AND_ABOVE` / `PUBLIC` → true |
| ページング | user_id のキーセット、シャード時は `MOD(user_id, shardCount)`。既存 ORG ソースと同じ形 |

#### 8.5.3 enqueue の方式（transactional outbox 相当）

- 告知ウィザードの `broadcast()` は、コンテンツ作成・フィード登録と**同じトランザクションの中で** fan-out ジョブ1件（＋文面6行＋宛先集合の見出し `notification_fanout_audiences` と宛先チーム `notification_fanout_audience_teams`。ジョブ行の `scope_ref` に集合のキー `audience_snapshot_id` を入れる）を INSERT する。ジョブ行はコミットされて初めてワーカーから見えるので、告知がロールバックされれば push も出ない（outbox と同じ性質）。
- 既存の `NotificationFanoutJobService.enqueue` は `REQUIRES_NEW` で独立コミットするため、呼び出し側のトランザクションに参加する `enqueueInCurrentTransaction`（`Propagation.MANDATORY`）を使う。**このメソッドは main に既にある**（CMP-260920-1040 で追加。旧版の「追加する」は誤り）。ただし main の版は文面行を作らず `shard_count=1` に固定するため、§6.7 の `FanoutEnqueueCommand` 版を「文面 `SURVEY_PUBLISHED`・シャードの扱い `AUTO`（`shard_count=0` で enqueue し、Worker の `resolveAndSplitShards` に評価させる）」で呼ぶ。
- 宛先集合の登録とジョブの enqueue は、social ドメインのポート `AnnouncementPushEnqueuer`（実装 `FanoutAnnouncementPushEnqueuer`。§6.7 の `TeamAffiliationNotifier` と同じ形）を経由して呼ぶ。実装は通知ドメインの `NotificationFanoutAudienceService.registerAudience` と `NotificationFanoutJobService.enqueueInCurrentTransaction` を呼び、どちらも `Propagation.MANDATORY` で告知のトランザクションに参加する。ポートを挟むのは、告知の取引入口から通知ドメインの Repository へ推移的に届かせないため（CLAUDE.md DB 設計の原則 #5・D-3T）。
- push を出すかどうか（§8.5.1。アンケートで、送信者が push 権限を持つか）は、`BroadcastAudienceResolver.resolveForBroadcast`（チャネルも受け取る）が告知のトランザクションの外で判定し、`ResolvedBroadcastAudience.pushEnabled` として運ぶ。告知のトランザクションの中で権限を引き直すと、role ドメインの Repository に届くため（D-3T）。
- 冪等キー `source_event_uuid` = `UUID.nameUUIDFromBytes(("F02.8:broadcast:" + feedId).getBytes(UTF_8))`（フィード ID から決定的に導出。同じ告知の二重 enqueue は `uk_fanout_idempotency` で1件に収束する）。
- 通知種別 `notification_type` = `SURVEY_CREATED`、文面 `FanoutMessageKind.SURVEY_PUBLISHED`（引数はアンケート名）。**push の文面はアンケート公開通知と同じにする**（受け取る人から見れば同じ出来事であり、チャネルの既存文面を使う）。6言語のキーは既存の `notification.fanout.survey.published.title` / `.body`（`messages*.properties` に6言語とも存在）を使い、新設しない。
- リスナー側の抑止: `SurveyAnnouncementAdapter` は main 時点で `surveyService.createSurvey(...)` の直後に `surveyService.publishSurvey(scopeType, scopeId, surveyId)` を呼んで即公開している（失敗は伝播し broadcast 全体がロールバックする）。この経路に印を通すため次のようにする。
  - `SurveyService.publishSurvey` の入口を4引数版 `publishSurvey(String scopeType, Long scopeId, Long surveyId, boolean audienceControlledByBroadcast)` の1本に差し替える。他の呼び出し元（画面の公開 API・予約公開バッチ）は `false` を渡す。3引数版を残して委譲させると、`SurveyService` はクラス単位で `@Transactional` のため4引数版も別の取引入口として数えられ、公開が他ドメインの Repository へ届く既存の負債（D-3T）が入口の数だけ増える。差し替えなら凍結ストアの行は入口名の付け替えだけで済む（増分0）。
  - `SurveyPublishedEvent` に `boolean audienceControlledByBroadcast` フィールドを追加する（既存の生成箇所は `false`）。
  - `SurveyAnnouncementAdapter.createContent` は、`BroadcastAudience` が「宛先を絞った告知」なら4引数版を `true` で呼ぶ。
  - `SurveyPublishNotificationListener.onSurveyPublished` は、`event.isAudienceControlledByBroadcast()` が真なら何もしない（push は告知ウィザードの1件に一本化する）。送信者が push 権限を持たない場合（組織 MEMBER・MANAGE_CONTENT を持たない DEPUTY）も印を載せ、ウィザード側は enqueue しない（=push なし）。
- 印を載せるのは「チームを選ぶ」と「チームグループで選ぶ」の場合である。「すべてのチーム」では載せず、リスナーは従来どおり動く。


### 8.6 範囲テンプレートのサーバー側解決

テンプレートは**グループの指定**（個別グループ ID・範囲・未分類の有無）を保存し、使うたびにサーバーが解決する。

```
broadcast / audience-preview で templateId が指定されたとき
1. テンプレートを (id, scope_type, scope_id) で取得 → 不一致・不在は 400 BROADCAST_003（既存）
2. リクエストで明示された宛先項目があれば、それを優先する（既存の規則）
3. 個別グループ: テンプレートの target_group_ids から、その組織の生存グループだけを残す（削除済み・他組織は黙って除外し、
   レスポンスの warnings に TEMPLATE_GROUPS_REMOVED と除外件数を載せる）
4. 範囲: from / to の各端が生存グループか確認。どちらかが削除済みなら 400 BROADCAST_013（範囲が成り立たない）
   端が生きていれば、送信時点の sort_order で展開する
5. 3 と 4 の和集合 ＋ include_unassigned で §8.2 の保存・push 宛先を決める。0件なら §8.3 の BROADCAST_009
```

- この結果、テンプレートの保存後にグループを追加・並べ替えても、使った時点の並びで範囲が展開される（AC-J01）。
- 範囲の端が消えたテンプレートは、画面では読み込み時に範囲を空にして再選択を求め、API で `templateId` だけを送った場合は 400 `BROADCAST_013` になる（AC-J03）。

## 9. 複数組織への同時加盟（単一親前提の読み手の改修）

### 9.1 方針（マスター確定）

1チームは複数の組織へ同時に ACTIVE で加盟できる。これを本書の範囲で保証するため、「チームの親組織は1つ」と前提している読み手を改修する。改修は加盟の書き込み API の**リリースより前**（§15 の段階①に同梱）に行う。書き込み API が出るまでは複数加盟の行を作る経路が無いため、先に読み手を直しておけば、複数加盟が生じた瞬間に壊れる箇所を残さない。

意味論の原則:

| 種類 | 複数の親があるときの意味 |
|---|---|
| 可視性・権限（「親組織のメンバーなら見える」等） | **いずれかの親**で条件を満たせば真（OR）|
| 一覧・集計（親組織の一覧、配下チームの一覧、人数の集計） | **すべての親**を集合として返す。JOIN による行の重複はユーザー・チーム単位で `DISTINCT` する |
| マージ（親組織のカテゴリ・設定をチームに足し込む） | **すべての親**の分を和集合で足し込み、どの親由来かを応答に含める |
| 単一の値が要る箇所（テナントキー・課金主体など） | 呼び出し側（URL・リクエスト）に**親組織を明示させる**。明示が無い既存 API には「代表親組織」を決定的に選ぶ規則（§9.3）を使い、応答にどの組織を採ったかを含める |

> **【2026-09-30 追記・シフト予算の所有モデル変更】** マスターの新しい意図（シフトを作るのはチームだけ・シフト予算はチームが持つ）により、シフト予算の所有は組織からチームへ移る（[F08.7 改訂 v2.0](F08.7_shift_budget_team_owned.md)）。本節のうち **#11〜#16（シフト予算の組織解決・計上先・取消先）、AC-N05 のシフト予算部分・AC-N10・AC-N11・AC-N15、裁可 #24・#36 は F08.7 v2.0 の実装が入ると不要（obsolete）** になる。計上先はチーム自身の割当で一意となり、「重なる割当は 409」「`teams` 行の `PESSIMISTIC_WRITE`」「消化行への組織 ID 記録」は要らない。F08.7 v2.0 の実装より前に本節の #11〜#16 を実装する場合は、当座の安全策（曖昧な組織へは計上しない）に留め、F08.7 v2.0 の実装 PR で該当分岐とテストを削除する。裁可 #24（2026-09-26）は 2026-09-30 の新しい意図が置き換える。

### 9.3 代表親組織の規則（単一値がどうしても要る既存 API のみ）

明示の親組織を受け取れない既存 API（後方互換のため引数を増やせないもの）に限り、次の規則で1つを選ぶ。

1. `team_org_memberships.responded_at` が最も古い ACTIVE の加盟（最初に成立した加盟）
2. 同時刻なら `organization_id` が最小のもの

この規則は `TeamOrgMembershipQueryService.findPrimaryParentOrganizationId(teamId)` の1箇所にまとめ、他の箇所で `findFirst` や `LIMIT 1` を書かない。番人テスト（§12）で `team_org_memberships` に対する `findFirstBy...` / `LIMIT 1` の新規追加を禁じる。

**実装状況（部隊 3-B）**: §9.2 #7〜#10・#18 は次のとおり実装した。
- #7 `GET /me/teams`: `organizations: [{id, slug, name}]`（代表親組織が先頭・0 件は `[]`）を追加。`organizationId` は互換のため残し、値を代表親組織に固定した（非推奨）。
- #8 `ScheduleService` の予約タスクのテナントキー: 代表親組織（`COALESCE(responded_at, created_at)` 昇順 → `organization_id` 昇順）。

## 10. API 契約

共通事項:

- **JSON のフィールド名は camelCase**（Jackson の既定。`application.yml` に命名戦略の設定は無く、`BroadcastRequestDto` など既存 DTO も camelCase）。本書では、JSON のフィールドを camelCase（例 `targetGroupIds`）、DB の列を snake_case（例 `target_group_ids`）で書き分ける。新規 DTO に `@JsonProperty("snake_case")` を付けてはならない。
- パスの識別子は slug（組織 `{slug}`、チーム `{teamSlug}`／`{orgSlug}`）。加盟行の `{membershipId}` は BIGINT、グループの `{groupId}` は UUID 文字列。
- **例外: 告知系（broadcast・宛先プレビュー・範囲テンプレート）だけは数値の `{orgId}`（Long）を使う。** 既存の `AnnouncementBroadcastController`（`POST /api/v1/organizations/{orgId}/broadcast`）と `AnnouncementRangeTemplateController`（`/api/v1/organizations/{orgId}/announcement-templates`）が `@PathVariable Long orgId` であり、告知ウィザード（`useAnnouncementBroadcast.ts` / `useAnnouncementTemplates.ts`）も数値 ID で呼んでいる。同じウィザードが呼ぶ新 API だけを slug にすると、1画面で識別子が2種類混ざり、取り違えの温床になる。告知系の slug 化は告知系全体でまとめて行う別の課題とする（§18）。
- 日時は ISO-8601（オフセット付き）。
- 一覧のページングは既存の `PaginationMeta`（`page` / `size` / `total` / `hasNext`）。`size` 既定 20・上限 100。
- **越境の扱い**: 他組織・他チームの `membershipId` / `groupId` を指定したときは、存在しない場合と**同じステータス・同じエラーコード**を返す（存在オラクルを作らない）。
- 認可の順序: 認証（401）→ スコープの存在と可視性（404）→ 権限（403）→ 入力検証（400）→ 状態（409/422）。
- **「キーを送らない」と「null を送る」を区別しない。** 区別が要る箇所（承認時のグループ上書き）は、別の boolean フラグで意図を明示させる（§10.5）。`JsonNullable` は使わない。
- BE の API を変えたら、`docs/openapi.json` を更新したうえで `cd frontend && npm run generate:types` で `frontend/app/types/generated/index.ts` を再生成し、同じ PR でコミットする（手編集禁止）。

### 10.3 申請ボタンの判定と申請フォーム

**公開ページ（`/public/organizations/{slug}`）の申請ボタン**（マスター確定 M3）

1. 公開 API `GET /api/v1/public/organizations/{slug}` の応答に `acceptingTeamApplications: boolean` を加える。この API は既に公開（visibility=PUBLIC）の組織しか返さない（非公開の組織は従来どおり不在と同じ応答）。受付フラグは**既に公開されている組織にだけ**載るので、受付 off の組織・非公開の組織について新しい存在オラクルは生まれない。
2. ボタンを出すかどうかは、ログイン中のときだけ認証付きの `GET /api/v1/me/org-affiliation-eligibility?organizationSlug={slug}` で判定する。応答は `{canApply: boolean}` の1項目（他の API と同じく `{"data": {"canApply": ...}}` で包む）で、**常に 200**。`canApply` は「組織が見えて・受付中で・閲覧者が加盟操作権限を持つチームが1つ以上ある」ときだけ true。組織が存在しない・見えない・受付 off・権限のあるチームが無い、のいずれでも同じ `false` を返す（どの理由で false かを区別しない＝存在オラクルにならない）。
3. 画面は `acceptingTeamApplications && canApply` のときだけボタンを出す。未ログインではボタンを出さない（ログイン誘導も出さない）。

> **前提欠陥と直し方（2026-09-29 の殿の判断で確定）**: main 時点で、FE の `fetchPublicOrganization(orgSlug)` はルートの slug を渡しているのに、BE の `PublicOrganizationController` は `@PathVariable Long id` を要求している。本機能の公開ページ導線はこの API に依存するため、実装の段階0で先に直す。**直し方は「BE の公開組織 API を slug で受ける」に固定する**（`GET /api/v1/public/organizations/{slug}`。URL 識別子は slug に一本化するという既定の方針に合わせる）。FE で数値 ID に解決して渡す案は採らない。非公開・存在しない slug は、従来の不在応答と同じステータス・同じエラーコードを返す（AC-A13）。

### 10.6 一覧（申請・招待）

`GET .../team-applications`、`GET .../team-invites`、`GET .../org-invites`、`GET .../org-applications` は `TeamOrgAffiliationResponse` の配列＋`PaginationMeta`。並びは `requestedAt` の降順。`team-applications` はクエリ `teamGroupId` で希望グループ絞り込み可。

**招待の辞退** `POST /teams/{teamSlug}/org-invites/{membershipId}/reject`（body `{block?: boolean}`）は、申請の拒否と同じく 200 で `{restriction: {kind, restrictedUntil}}`（合成規則を適用した後の、いま有効な制限）を返す（2-C で実装）。

**制限の一覧と解除**（2-C で実装）: `GET .../team-affiliation-restrictions`（組織側）と `GET .../org-affiliation-restrictions`（チーム側）は、`{id, direction, kind, reason, restrictedUntil, team: {slug, name, iconUrl}, organization: {slug, name, iconUrl}, createdAt}` の配列＋`PaginationMeta`。並びは記録日時の降順で、いま有効な行（`kind='BLOCK' OR restricted_until > :now`）だけを出す。組織側は `TEAM_APPLY`・`REJECTED`、チーム側は `ORG_INVITE`・`DECLINED` の行だけが一覧・解除の対象で、相手側が作った行や自分の取下げ・取消による行（`WITHDRAWN`・`CANCELLED`）は解除できない（制限の迂回の封止）。解除の対象外・他組織／他チームの ID・存在しない ID は、区別せず同じ 404 `COMMON_005` を返す（§11 に制限 ID 専用のコードが無いため、汎用の「リソースが見つかりません」を使う）。

**招待の取消** `DELETE /organizations/{slug}/team-invites/{teamSlug}` は、存在しないチームの slug と招待を送っていないチームを区別せず、同じ 404 `TEAM_070` を返す（AC-G138）。

### 10.8 割当

**PUT `/api/v1/organizations/{slug}/teams/{teamSlug}/team-group`** body `{groupId: UUID|null}` → 200 で `TeamOrgAffiliationResponse`（`data` に包む。既存の申請 API と同じ）。対象チームがその組織の ACTIVE 加盟でなければ 404 `TEAM_070`。他組織・削除済みのグループなら 404 `ORG_064`。

**PUT `/api/v1/organizations/{slug}/team-group-assignments`** body `{groupId: UUID|null, teamSlugs: string[1..500]}` → 200 で `data.updatedCount`（指定した重複を除くチーム数。すでに目的のグループにいたチームも含む。監査ログは実際に変わったチームだけに残す）。不正が1件でもあれば 400 `ORG_069`（該当 slug は `error.fieldErrors[]` に `field=invalidTeamSlugs` で1件ずつ入る）、何も更新しない。グループの生存確認は組織行の `FOR UPDATE` ロックの内側で行い、並行するグループ削除とは必ず直列になる（削除が先なら 404 `ORG_064`、割当が先なら削除後のリスナーが付け替える）。`teamSlugs` が空配列（`[]`）・欠落・501件以上なら入力検証の 400（Bean Validation）で、何も更新しない（AC-G07・AC-G05）。

### 10.9 宛先プレビュー

**POST `/api/v1/organizations/{orgId}/broadcast/audience-preview`**（告知系のため数値 `{orgId}`）

リクエストは broadcast と同じ宛先項目（`targetTeamIds` / `targetGroupIds` / `targetGroupRange` / `includeUnassigned` / `templateId`）と `channel`・`targetRole`。レスポンス:

| フィールド | 型 | null |
|---|---|---|
| `resolvedTeamCount` | integer | 不可 |
| `directMemberCount` | integer | 不可（宛先を絞ったときだけ意味を持つ。それ以外は 0。**組織スコープの ACTIVE メンバーから送信者本人を除いた人数**。送信者は必ず組織メンバーなので、本人を数えると §8.3 の `BROADCAST_009` が成立しなくなるため。部隊 6-A の実装判断）|
| `sampleTeams` | `[{slug, name}]`（最大50）| 不可 |
| `groups` | `[{id, name}]`（範囲展開後のグループ）| 不可 |
| `pushEnabled` | boolean | 不可（送信者が組織 ADMIN・MANAGE_CONTENT を持つ DEPUTY・SYSTEM_ADMIN のいずれでもない場合、またはチャネルが push を出さない場合は false。UI で「push は送られません」と表示する）|
| `warnings` | `string[]` | 不可（`TEMPLATE_GROUPS_REMOVED` など）|

レートリミット 60件/分/ユーザー。

認可は既存の broadcast と同じ契約に揃える。先頭で `AccessControlService.checkMembership(userId, orgId, "ORGANIZATION")` を呼び、組織のメンバーでなければ（他組織のユーザー、存在しない `orgId` を含む）**403 `COMMON_002`** を返す（broadcast と同じ応答にし、プレビューだけ別の応答にしない）。組織の MEMBER 以上は 200。

**実装（部隊 6-A）**: 宛先の解決は `social/announcement/audience/BroadcastAudienceResolver`（トランザクションなし）が行い、broadcast とプレビューで同じ検証を通す。グループ（organization）・加盟（team）・メンバー数（membership）は別ドメインのため、告知の `@Transactional`（social）の外で各ドメインの公開 Service（`OrgTeamGroupService.findAudienceCatalog`・`TeamOrgMembershipQueryService.findActiveTeamIdsIn` / `findActiveTeamGroupAssignments`）から解決し、解決結果だけを `AnnouncementBroadcastService.broadcast` に渡して保存する。認可（403）を検証（400）より先に行い、非メンバーに他組織のグループやチームの存在を漏らさない。プレビューは検証エラー（006・007・008・011）は 400 で返すが、0 件は 400 にせず 0 を返す（画面が「次へ」を止める）。「チームを選ぶ」は 501 件以上を照合の前に 400 `BROADCAST_010` にし、重複は排除して保存する。グループの個別指定は 101 件以上を 400 `BROADCAST_006` にする（グループは 1 組織 100 件まで）。範囲の両端が null なら 400 `BROADCAST_008`。`target_audience` の JSON は `{mode: TEAMS|GROUPS, groups: [{id, name}], range: {fromGroupId, fromGroupName, toGroupId, toGroupName}|null, includeUnassigned, teamCount, directMemberCount}` で、名前は送信時の値を残す（AC-H17）。broadcast の応答にも `targetGroupIds`・`includeUnassigned`・`targetAudience` を載せる。

**閉じる側に倒した扱い（部隊 6-A・Codex 検分の反映）**:
- 明示の空配列は「すべてのチーム」に倒さない。`targetTeamIds=[]`、および範囲も未分類も無い `targetGroupIds=[]` は 400 `BROADCAST_009`（送信・プレビューとも）。`targetTeamIds=[]` とグループ項目の併用は 400 `BROADCAST_011`。
- テンプレートの宛先の解決（§8.6）は部隊 6-B の受け持ち。それが着地するまで、組織告知で宛先項目を1つも送らずに `templateId` だけを渡した送信・プレビューは 400 `COMMON_001` にする（§11 に該当する BROADCAST コードが無いため）。
- 候補・展開・プレビュー・スナップショットは、アーカイブ済み（`teams.archived_at`）・論理削除済み（`teams.deleted_at`）のチームを除く。
- `directMemberCount` は告知対象ロールに合わせて数える。`MEMBERS_AND_ABOVE`（と未指定）は純 SUPPORTER（`memberships.role_kind = SUPPORTER`）を数えず、`SUPPORTERS_AND_ABOVE`・`PUBLIC` は数える。
- チームダッシュボードの表示判定（`DashboardService.isTargetedToTeam`）は、グループ宛ての告知（`target_group_ids`・`include_unassigned`・`target_audience` を持ち `target_team_ids` が NULL）を、部隊 6-C の `AnnouncementAudienceMatcher` が着地するまでどのチームにも出さない（従来の判定は NULL を「全チーム宛て」と読み、宛先外のチームへ漏れるため）。組織側の一覧には出る。

画面の要点:

- `member-teams` の切替はクエリ `view` で行い、子ルートを作らない（永続シェル配下の兄弟ルートには親側 `<NuxtPage>` が要る既知の罠を避ける）。`/teams/{slug}/affiliations` も同様に `view=invites` 等のクエリで区画を切り替える。
- 申請ダイアログ: チーム選択（`myTeams`。`affiliationStatus` が `NONE` 以外は選べず理由を表示）→ 案内文 → グループ選択（`groupMode` が REQUIRED なら必須表示・未選択では送信ボタンが押せない、OPTIONAL なら「選ばない」を含む）→ 添え書き → 送信。
- 承認ダイアログ: 希望グループを初期選択したドロップダウン（「未分類」を含む）と「承認」ボタン。変えた場合は「希望: {A} → 承認時: {B}」と表示し、`overrideGroup=true` と選んだ `groupId`（未分類なら null）を送る。希望のままなら `overrideGroup=false` を送る。
- 拒否ダイアログ: 理由（任意）と「今後この組織（チーム）からの申請を受け付けない」チェック。
- 受付を off にする操作で PENDING が残っていれば確認ダイアログ（§4.3）。
- 告知ウィザードのステップ1（組織・グループ機能 on）:
  - 「対象チーム」: 「すべてのチーム」「チームを選ぶ」「チームグループで選ぶ」
  - 「チームグループで選ぶ」を選ぶと、グループのチェックリスト（並び順）、「範囲で選ぶ」（種類: 〜以前／〜以降／A〜B とグループのドロップダウン）、「未分類のチームを含める」、「該当: N チーム＋直属メンバー M 人」のプレビューを出す。0件なら「次へ」を押せない。
  - `pushEnabled=false`（組織 MEMBER・MANAGE_CONTENT を持たない DEPUTY、または push の無いチャネル）のときは「このお知らせの push 通知は送られません」と表示する。
  - 送信履歴には「表示は現在の所属で判定されます（削除されたグループは送信時点の対象チームで判定）」と注記する（§8.2）。
  - テンプレートを読み込んだとき、削除済みグループを除外した旨を警告表示する。範囲の端が削除済みなら範囲を空にして再選択を求める。
- お知らせ欄の送信者向け詳細（送信履歴）に `targetAudience` から「宛先: 平成20年度以前（送信時 12 チーム）」と表示する。

## 15. 非機能要件

| 観点 | 設計 |
|---|---|
| 規模の前提 | 1,000万ユーザー。1組織の加盟チームは最大で数万（大規模連盟）、グループは100件まで。1チームの加盟組織数は通常数件 |
| 申請一覧 | `(organization_id, status, direction, invited_at)` で範囲走査。PENDING は通常少数 |
| 加盟チーム一覧のグループ絞り込み・グループ所属数 | `(organization_id, group_id, status)` の索引だけで絞り込み・集計できる |
| 宛先展開（push の対象チームのスナップショット） | グループ ID 集合 → `(organization_id, group_id, status)` で ACTIVE のチームを取得。件数上限なし（宛先集合の行数＝宛先チーム数）|
| 表示判定（グループ宛て） | チームダッシュボードでは、閲覧中チームの「組織ごとの所属グループ」を `(team_id, status, direction)` 索引で1回引き、親組織の告知候補を `target_group_ids` の多値インデックスで絞る。削除済みグループの判定用に、閲覧中チームのスナップショット行を `(team_id, feed_id)` 索引で候補フィードの範囲だけ1回引く。候補の判定は共通の `AnnouncementAudienceMatcher` に集約し、`DashboardService` の既存判定（`target_team_ids`）と並べて使う |
| 表示判定（チームを選ぶ） | 既存の多値インデックス（`target_team_ids`）のまま。500件の上限は実測（669件まで）に収まる確定値（§8.3）|
| push fan-out | 1ジョブ＋宛先チーム集合（受信ユーザーは保存せず Worker 処理時に解決）。受信者数は宛先チームのメンバー＋直属メンバー（数千〜数十万）で、既存のシャード・キーセットの仕組みに乗る。enqueue は O(宛先チーム数) で、告知のトランザクション内で行う |
| 通知（加盟）| 相手側の ADMIN（チーム側は加盟操作者）のみ。操作と同じトランザクションで fan-out ジョブを enqueue し、配信は Worker が非同期に行う（配信の失敗で操作をロールバックしない。§6.7）|
| 後方互換 | 既存行は `ORG_INVITE`・未分類。グループ機能・申請受付は既定 off で、何もしなければ従来と同じ。「すべてのチーム」の告知は表示も push も従来どおり。**「チームを選ぶ」は、アンケートの push が組織全体から「選んだチーム＋直属メンバー」に変わり（MEMBER の送信は push なし）、500件の上限が新たに掛かる**（§8.5.1。表示は変わらない）。参照系 API はフィールド追加のみ。§9 の改修は、複数加盟が無いデータでは結果が変わらない |

## 16. 受け入れ条件

形式: 「誰が・何をしたら・どうなる（観測できる結果）」。ロールは次の固定人物で書く。

- 組織X の ADMIN = **XA**、組織X の MEMBER = **XM**、組織X の DEPUTY_ADMIN（MANAGE_CONTENT あり）= **XD**、組織X の DEPUTY_ADMIN（MANAGE_CONTENT なし）= **XD2**、組織X の直属メンバー（どのチームにも属さない役員）= **XO**
- チームT の ADMIN = **TA**（組織X には未加盟）、チームT の DEPUTY_ADMIN（加盟操作権限なし）= **TD**、チームT の MEMBER（加盟操作権限なし）= **TM**、チームT の MEMBER で権限グループにより `MANAGE_ORG_AFFILIATION` を付与された人 = **TG**
- 組織Y（別組織）の ADMIN = **YA**、組織Y に加盟するチームU
- どこにも属さない認証済みユーザー = **N**

### 16.0 実機E2E の共通手順

各 AC の「検証」列は、**実機**（実際に起動した BE・FE・MySQL をモックなしで操作する）か **IT 限定**（実機では状態を作れない・観測できないもの。理由を併記）のどちらかを示す。実機の AC は、この節の共通手順に従って準備→操作→観測する。

| 手順 | 方法 |
|---|---|
| 固定人物の用意 | 上の XA〜N をシードまたは API で作る。TG は、TA が `/teams/T/permission-groups` で `MANAGE_ORG_AFFILIATION` を含む権限グループ（target_role=MEMBER）を作り、メンバー一覧から TG に割り当てて作る |
| **時間を進める** | テスト用の Clock エンドポイントは作らない。**DB の日時列を過去へずらす準備**をする（例: `UPDATE team_org_affiliation_restrictions SET restricted_until = restricted_until - INTERVAL 31 DAY WHERE id = UUID_TO_BIN(?)`、`UPDATE team_org_memberships SET invited_at = invited_at - INTERVAL 61 DAY WHERE id = ?`）。判定は `wallClock` の現在時刻と比べるので、列をずらせば「時間が経った」状態になる |
| **バッチを動かす** | SYSTEM_ADMIN で `POST /api/v1/system-admin/batch/{name}/trigger?sync=true` を呼ぶ（`team-org-pending-expiry` / `team-org-group-orphan-repair` / `team-org-lifecycle-cleanup`。§6.8）。`sync=true` なので応答が返った時点で処理は終わっている |
| **push を観測する** | 受信者でログインし、通知一覧（`GET /api/v1/notifications`、画面では通知ベル）を見る。fan-out ワーカーは5秒間隔（`NotificationFanoutWorker` の `fixedDelay = 5_000`）なので、送信から**10秒以上**待ってから観測する。「届かない」ことの確認も同じ待ち時間を置く |
| ジョブの観測 | fan-out ジョブの種類・宛先は DB の `notification_fanout_jobs`（`scope_type`・`scope_ref`）と `notification_fanout_audience_teams`（ジョブ行の `scope_ref` を `UUID_TO_BIN` した `audience_snapshot_id` で引く）を SELECT して確かめる |
| URL 直打ち | ブラウザのアドレス欄に直接入力し、表示された画面と URL（追い返し先）とトーストを観測する |
