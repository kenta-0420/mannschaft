> **ステータス**: 🟢 設計確定
> **実装フェーズ**: Phase 1（auth ドメイン拡張）
> **最終更新**: 2026-05-19
> **関連ドキュメント**: F01.1_auth.md / F12.3_gdpr_personal_data.md / F03.12 ケアリンク

## 1. 概要

### 1.1 目的

個人アカウント登録時に生年月日を収集し、18歳未満ユーザーに対して保護者の同意を義務付ける機能を新設する。日本の個人情報保護法（第18条）および GDPR 第8条（子どもの個人データ処理）に基づく法的要件を満たすことが主目的である。

### 1.2 法的背景

| 根拠法 | 条項 | 内容 |
|--------|------|------|
| 個人情報保護法（日本） | 第18条 | 未成年者の個人情報収集には法定代理人の同意が必要 |
| GDPR | 第8条 | 16歳未満（加盟国により13歳まで引き下げ可）の子どものデータ処理に保護者同意が必要 |
| COPPA | § 312.5 | 13歳未満の児童のデータ収集に親の確認可能な同意が必要（参考：米国法） |

本設計では日本法を主基準とし、18歳未満全員に保護者同意を求める。GDPR より厳しい基準であり、グローバル展開時にも対応可能。

### 1.3 スコープ

**本機能で実装する範囲**

- 登録フォームへの `birth_date` フィールド追加（必須化）
- 年齢区分（AgeGroup）の計算ロジック（日本学年基準）
- 18歳未満ユーザーの `PENDING_PARENTAL_CONSENT` ステータス管理
- 保護者同意リンク（`parental_consent_links`）のライフサイクル管理
- 保護者同意フロー（招待・承認・否認・期限切れ削除）
- 保護者退会時の後継者指定ブロックフロー
- 18歳到達時の自動解放バッチ（夜次実行）
- 年齢区分設定テーブル（`age_group_settings`）のフレームワーク整備

**スコープ外**

- 年齢区分ごとの機能制限・テーマ変更（フレームワークのみ。実際の制限は別フェーズ）
- 保護者の本人確認（公的書類による確認）

### 1.4 二本立ての年齢モデル（本機能と F08.9 後見切替の違い）

Mannschaft には「年齢に基づく保護者関与」の仕組みが**目的の異なる2系統**存在する。両者は別テーブル・別エンティティ・別しきい値で独立しており、混同しないこと。

| 観点 | ① 利用開始の保護者承認（本機能・F01.9） | ② 継続的な保護者監視（F08.9 後見切替） |
|---|---|---|
| **対象年齢** | **18歳未満**（日本法基準） | **12歳未満**（小学生まで。日本既定＝満12歳に達する年度の3月末で封印。国別 `GuardianshipAgePolicy` で解決） |
| **目的** | アカウント登録時の法定代理人同意（個人情報保護法・GDPR 第8条） | 会費のまとめ支払い・所属管理補助のための保護者の代理操作（強い後見） |
| **発動タイミング** | 登録時に**一度**（`PENDING_PARENTAL_CONSENT` → 承認で `ACTIVE`）。承認が完了するまで利用不可 | 承認後も**継続的**に保護者が子アカウントへ切り替えて操作可能（`X-Proxy-For-User-Id`） |
| **中学生以降の扱い** | 対象外（18歳未満なら中学生・高校生も引き続き対象） | **自立**：切替は自動封印。プロフィール・パスワード変更等も保護者監視の対象外（本人のみ） |
| **実装エンティティ** | `parental_consent_links` / `ParentalConsentGateFilter`（本書 §7.5） | `proxy_input_consents` / `ProxyInputContext` / `GuardianshipAgePolicy` |

**要点**: 「① は 18歳未満の全員が対象だが利用開始時の一度きりのゲート」「② は 12歳未満（小学生まで）限定の継続的な代理操作」であり、**13〜17歳のユーザーは①の対象（承認待ちなら本書の制限を受ける）だが②の対象外（保護者は切替不可・自立）**という非対称な関係になる。②の詳細は [F08.9 会員決済・後見つきマルチ受益者・ペイウォール・継続課金](F08.9_membership_billing_paywall/README.md) §3.2・[03_security.md](F08.9_membership_billing_paywall/03_security.md) §3 を参照。

## 2. 用語定義

| 用語 | 定義 |
|------|------|
| **AgeGroup** | 生年月日から計算される年齢区分。6段階。DB に保存せず毎回計算する |
| **学年基準日（4月2日 cutoff）** | 日本の学校教育法施行規則に基づき、当該年度の4月1日時点で何歳かを判定する |
| **保護者同意リンク** | 子アカウントと保護者アカウントを紐づける `parental_consent_links` レコード |
| **保護者** | Mannschaft アカウントを持つ18歳以上のユーザーで、子アカウントの `parental_consent_links` に `status = APPROVED` のレコードが存在する者 |
| **唯一の承認済み保護者** | 子アカウントに対して `status = APPROVED` の `parental_consent_links` が1件しか存在しない保護者 |
| **PENDING_PARENTAL_CONSENT** | メール認証完了後、18歳未満であることが判明したユーザーが遷移するステータス。保護者の承認待ち状態。機能制限あり |
| **同意招待トークン** | 子アカウントが保護者に送る招待用トークン。SHA-256 ハッシュを DB に保存し、平文をメール本文に記載する |
| **自己申告の限界** | 保護者の正当性（実際の親権者であること）をシステムが技術的に確認する手段は現時点では持たない。§7.4 参照 |

### 3.2 `users` テーブルの変更点

#### status ENUM への `PENDING_PARENTAL_CONSENT` 追加

```sql
-- Flyway V11.166__add_pending_parental_consent_to_users_status.sql
ALTER TABLE users MODIFY COLUMN status VARCHAR(30) NOT NULL DEFAULT 'PENDING_VERIFICATION';

ALTER TABLE users DROP CONSTRAINT IF EXISTS chk_users_status;
ALTER TABLE users ADD CONSTRAINT chk_users_status CHECK (status IN (
  'PENDING_VERIFICATION',
  'PENDING_PARENTAL_CONSENT',
  'ACTIVE',
  'FROZEN',
  'ARCHIVED',
  'DECEASED',
  'RELOCATED'
));
```

#### `birth_date` の登録必須化

`users.birth_date` カラムはすでに存在（AES-256-GCM 暗号化、`VARBINARY(255) NULL`、V17.001 で追加済み）。
**カラム変更は行わない**。登録フォームの `RegisterRequest` DTO と `AuthRegistrationService` のバリデーションで必須化する。

> 理由: `birth_date` は既存のケア機能（F03.12）でも利用されており、DB レベルで `NOT NULL` に変更すると既存レコードとの互換性が失われる。

#### status 遷移図（更新版）

```
PENDING_VERIFICATION
  ├─（メール認証完了 / 18歳以上）────────────────→ ACTIVE
  ├─（メール認証完了 / 18歳未満）────────────────→ PENDING_PARENTAL_CONSENT
  │    ├─（保護者承認）──────────────────────────→ ACTIVE
  │    ├─（保護者拒否 / タイムアウト7日）──→ deleted_at 付与 ──（30日後バッチ）──→ 物理削除
  │    └─（SYSTEM_ADMIN 凍結）──→ FROZEN ──（凍結解除）──→ PENDING_PARENTAL_CONSENT ※
  └─（7日後バッチ未認証）───────────────────────→ 論理削除
ACTIVE
  ├─（SYSTEM_ADMIN 凍結）──→ FROZEN ──（凍結解除）──→ ACTIVE
  ├─（退会申請）──→ deleted_at 付与 ──（30日後バッチ）──→ 個人情報物理削除
  └─（6ヶ月非アクティブ）──→ ARCHIVED ──（ログイン）──→ ACTIVE

※ FROZEN 解除後は ACTIVE ではなく PENDING_PARENTAL_CONSENT に戻す（保護者同意スキップ防止）
  実装: 解除時に「①ユーザーが未成年（isMinor() = true）かつ ② APPROVED の parental_consent_links が0件」なら
  PENDING_PARENTAL_CONSENT に戻す。両条件を満たさない場合は ACTIVE に遷移する。
  これにより PENDING 段階で凍結されたケース・成人到達後に凍結されたケースを正しく区別できる。
  DB スキーマ変更（previous_status カラム追加）不要。
```

**各 status の意味**

| status | 意味 | ログイン可否 |
|--------|------|------------|
| `PENDING_VERIFICATION` | メール未確認 | 不可（403） |
| `PENDING_PARENTAL_CONSENT` | メール確認済み・保護者同意待ち | 不可（423） |
| `ACTIVE` | 通常利用中 | 可 |
| `FROZEN` | SYSTEM_ADMIN による凍結 | 不可（423） |
| `ARCHIVED` | 6ヶ月非アクティブ | 可（復帰後） |
| `DECEASED` | 死亡（F14.1） | 不可 |
| `RELOCATED` | 転居（F14.1） | 不可 |

### 3.3 `parental_consent_links` テーブル（新規）

#### 設計方針

- **ドメイン**: `auth` ドメインに配置（ユーザーライフサイクル管理の一部）
- **PK**: UUIDv7（`UuidV7Entity` 継承）
- **FK**: クロスドメイン FK は作らない。`parent_user_id` / `child_user_id` はインデックスのみ

#### テーブル定義

| カラム名 | 型 | NULL | デフォルト | 説明 |

| `child_user_id` | BIGINT UNSIGNED | NO | — | 子アカウントの users.id（インデックスのみ、FK なし） |
| `parent_user_id` | BIGINT UNSIGNED | YES | NULL | 保護者アカウントの users.id（承認後にセット。FK なし） |

| `status` | ENUM | NO | `PENDING` | `PENDING` / `APPROVED` / `REJECTED` / `REVOKED` |
| `expires_at` | DATETIME | NO | — | 招待有効期限（発行から7日後） |
| `approved_at` | DATETIME | YES | NULL | 保護者承認日時 |

**制約・運用ルール**

- 1人の子に対して、`status = PENDING` のリンクは最大3件まで
- `status = APPROVED` のリンクは最大5件まで
- 保護者は18歳以上であること（`AUTH_063`）
- 保護者が自分自身の子アカウントになることはできない（`AUTH_062`）
- 子本人のメールアドレスへの招待禁止（`AUTH_069`）

## 4. AgeGroup の計算ロジック

### 4.1 日本学年制度の基準

- 4月1日生まれ → 当該年度の学年（4月1日時点で満年齢に達している）
- 4月2日生まれ → 翌年度の学年（翌年4月1日時点で満年齢に達する）

### 4.2 AgeGroup enum 定義

```java
// パッケージ: com.mannschaft.app.auth
public enum AgeGroup {
    ELEMENTARY_LOWER,  // 小学校低学年（6〜7歳）
    ELEMENTARY_MIDDLE, // 小学校中学年（8〜9歳）
    ELEMENTARY_UPPER,  // 小学校高学年（10〜11歳）
    JUNIOR_HIGH,       // 中学生（12〜14歳）
    SENIOR_HIGH,       // 高校生（15〜17歳）
    ADULT              // 成人（18歳以上）
}
```

**パッケージ配置**: `com.mannschaft.app.common.util.AgeGroupCalculator`（クロスドメイン利用のため common）

### 4.3 計算アルゴリズム概要

```java
// 学年年齢（4月1日基準）でAgeGroupを計算
public static AgeGroup calculate(LocalDate birthDate, LocalDate baseDate) {
    LocalDate fiscalStart = baseDate.getMonthValue() >= 4
        ? LocalDate.of(baseDate.getYear(), 4, 1)
        : LocalDate.of(baseDate.getYear() - 1, 4, 1);
    int ageAtFiscalStart = (int) ChronoUnit.YEARS.between(birthDate, fiscalStart);
    return switch (ageAtFiscalStart) {
        case 6, 7       -> AgeGroup.ELEMENTARY_LOWER;
        case 8, 9       -> AgeGroup.ELEMENTARY_MIDDLE;
        case 10, 11     -> AgeGroup.ELEMENTARY_UPPER;
        case 12, 13, 14 -> AgeGroup.JUNIOR_HIGH;
        case 15, 16, 17 -> AgeGroup.SENIOR_HIGH;
        default -> ageAtFiscalStart >= 18 ? AgeGroup.ADULT : AgeGroup.ELEMENTARY_LOWER;
    };
}

// 18歳未満判定（保護者同意フロー起動の閾値）はカレンダー年齢で判定
public static boolean isMinor(LocalDate birthDate, LocalDate baseDate) {
    return ChronoUnit.YEARS.between(birthDate, baseDate) < 18;
}
```

| AgeGroup | 学年年齢（4月1日時点） | 学年 |
|---|---|---|
| ELEMENTARY_LOWER | 6〜7歳 | 小1・2年 |
| ELEMENTARY_MIDDLE | 8〜9歳 | 小3・4年 |
| ELEMENTARY_UPPER | 10〜11歳 | 小5・6年 |
| JUNIOR_HIGH | 12〜14歳 | 中学生 |
| SENIOR_HIGH | 15〜17歳 | 高校生 |
| ADULT | 18歳以上 | 成人 |

#### `POST /api/v1/parental-consent/invitations`

**リクエストボディ**
```json
{ "parent_email": "parent@example.com" }
```

**バリデーション**
- 呼び出し元が `PENDING_PARENTAL_CONSENT` ステータスであること
- 同一 `parent_email` への PENDING 招待が既存でないこと（AUTH_068）
- 同一子の PENDING 招待が3件未満であること（AUTH_067）
- `parent_email` が子本人のメールと一致しないこと（AUTH_069）

**レートリミット**: 同一子から 24時間 10回まで

**動作**
1. 32バイト CSPRNG トークン生成
2. SHA-256 ハッシュを `token_hash` に保存
3. 承認 URL: `https://example.com/parental-consent/approve?token=<raw_token>`
4. 保護者にメール送信

#### `POST /api/v1/parental-consent/approve`（トークン認証）

**リクエストボディ**
```json
{ "token": "<raw_token>" }
```

**動作**
1. トークン検証（`expires_at` 以内・`status = PENDING`）
2. 保護者がアカウントなし → 新規登録フローへ誘導（短命セッションでトークン保持）
3. 保護者の年齢確認（18歳以上。AUTH_063）
4. `status = APPROVED`, `approved_at = NOW()`
5. 子の `status` → `ACTIVE`
6. 子に「保護者が承認しました」通知

**レートリミット**: 同一 IP から 1時間 20回まで

**エラー統一**: 無効・期限切れ・使用済みはすべて `AUTH_060`（オラクル攻撃防止）

#### `POST /api/v1/parental-consent/reject`（トークン認証）

**動作**
1. トークン検証
2. `status = REJECTED`, `rejected_at = NOW()`
3. 他の全招待が REJECTED/REVOKED かつ APPROVED が0件の場合 → 子アカウントを削除（`anonymize()` + `softDelete()`）
4. 子のメールアドレスに通知

#### `DELETE /api/v1/parental-consent/parents/{linkId}`

**認可チェック**: リクエスト元が `child_user_id` または `parent_user_id` と一致すること（不一致は 404）

**バリデーション（子本人が実行）**: 解除後に APPROVED が0人かつ子が未成年 → 拒否（AUTH_064）

**バリデーション（保護者が実行）**: 解除後に子の APPROVED が0人かつ子が PENDING_PARENTAL_CONSENT → 拒否（AUTH_065）

## 6. フロー設計

### 6.1 未成年登録フロー

```
[子ユーザー]                                [バックエンド]
    │
    │ POST /auth/register (birth_date 含む)
    ├──────────────────────────────────────→
    │                                       │ バリデーション
    │                                       │ birth_date 暗号化保存
    │                                       │ users INSERT (status=PENDING_VERIFICATION)
    │                                       │ メール送信
    │ 201 Created                           │
    │←──────────────────────────────────── │
    │
    │ [メール内リンクをクリック]
    │
    │ POST /auth/verify-email { token }
    ├──────────────────────────────────────→
    │                                       │ トークン検証
    │                                       │ birth_date 復号 → isMinor() 判定
    │                                       │
    │                            [18歳未満の場合]
    │                                       │ status = PENDING_PARENTAL_CONSENT
    │ 200 OK                                │
    │ { requires_parental_consent: true,    │
    │   parental_consent_deadline: "..." }  │
    │←──────────────────────────────────── │
    │
    │ [FE: 保護者招待フォーム表示]
    │
    │ POST /parental-consent/invitations
    │   { parent_email: "parent@example.com" }
    ├──────────────────────────────────────→
    │                                       │ トークン生成
    │                                       │ parental_consent_links INSERT (PENDING)
    │                                       │ 保護者にメール送信
    │ 201 Created                           │
    │←──────────────────────────────────── │
    │
    │ ※ PENDING_PARENTAL_CONSENT 状態で
    │   限定ログイン可能（プロフィール編集・
    │   保護者招待操作・退会申請のみ）
```

> **注意**: `birth_date` の復号失敗時は 500 として記録する。フォールバックとして保護者同意フローを起動し、安全側に倒す。

### 6.2 保護者承認フロー

```
[保護者] メール内リンクをクリック
    → https://example.com/parental-consent/approve?token=xxx
    → [アカウントあり] ログイン後、確認画面で承認
    → [アカウントなし] 新規登録フローへ
                       登録完了後にトークンを URL パラメータ付きで渡して自動承認
    → POST /parental-consent/approve { token }
    → 子の status → ACTIVE
    → 子に承認通知
```

### 6.3 保護者退会ブロックフロー

```
保護者 → DELETE /users/me
  → ParentalConsentService.checkWithdrawalBlock(userId)
  → PENDING_PARENTAL_CONSENT の子がいて唯一の承認済み保護者
  → 409 AUTH_066
  → FE: 「別の保護者を先に設定してください」と案内
  → 保護者が別の保護者を招待・承認完了後に退会申請
  → 通過
```

### 6.4 子が18歳になった時の自動解放（`ParentalConsentReleaseBatchService`）

毎日 02:00 JST 実行。ShedLock 名: `parentalConsentReleaseBatch`。

日付の基準タイムゾーンは `@Scheduled(zone)` と同じ `Asia/Tokyo` に固定する（バッチスレッドは
`UserTimezoneFilter` を通らず `TimezoneContextHolder.get()` が UTC を返すため、JVM 既定 TZ や
リクエスト文脈に依存させると18歳到達日の判定が丸一日ずれる）。

```
1. status = 'APPROVED' かつ「成人に到達している可能性がある」リンクを
   id 昇順のキーセットページング（l.id > cursor）で 500 件ずつ取得
   （SQL で絞れるのは平文・索引付きの users.birth_year <= 今年 − 18 まで。
    閾値は AgeGroupCalculator.adultBirthDateThreshold(today) が唯一の算出元）
2. 取得した各リンクの子ユーザーについて users.birth_date を復号し、
   AgeGroupCalculator で成人判定を確定させる（境界年の未成年をここで除外）
3. 成人と確定した child_user_id ごとに:
   a. parental_consent_links の APPROVED を全件 REVOKED に更新
   b. 子に「保護者同意が自動解放されました」通知
4. カーソルを検査済みの最後の id まで必ず前進させ、取得が空になるまで 1 を繰り返す
```

> **年齢条件を SQL の WHERE 句で `users.birth_date` と比較してはならない。**
> `birth_date` は AES-256-GCM（ランダム IV）で暗号化されて格納されており、SQL 上の比較は
> 暗号文同士のバイト比較にしかならず日付順とは無関係である。SQL で使えるのは平文・索引付きの
> `users.birth_year` だけで、これは「成人を取りこぼさないが今年18歳になる年の未成年が混ざる」
> 粗い絞り込みにしかならない。確定判定は必ず復号後に `AgeGroupCalculator` で行うこと。
>
> **事後フィルタを持つ以上、ページングは必ずキーセット（`id > cursor`）にすること。**
> 先頭ページを毎回取り直すオフセットページングでは、境界年の未成年が先頭 500 件を占有した瞬間に
> 後方の成人到達者へ永久に到達できず、保護者同意が解放されないまま残る（飢餓）。
> カーソルは解放の可否にかかわらず前進させる。
>
> `birth_year` は F09.17 で後付けされた列で既存行は NULL であるため、取得クエリは
> `birth_year IS NULL` の行も候補に含める（除外すると本バッチが 1 件も拾わない無処理バッチになる）。
> 新規登録時は `AuthRegistrationService` が `birth_date` の年を `birth_year` に複写する。

### 6.5 期限切れ招待クリーンアップ（`ParentalConsentCleanupBatchService`）

毎日 03:30 JST 実行。ShedLock 名: `parentalConsentCleanupBatch`。

```
1. status = 'PENDING' かつ expires_at < NOW() のリンクを REVOKED に更新
2. child_user_id ごとに APPROVED = 0 件かつ全リンクが非PENDING の場合:
   → 子アカウントを anonymize() + softDelete()
   → 子のメールに通知
```

## 7. セキュリティ設計

### 7.1 IDOR 対策

| エンドポイント | 対策 |
|--------------|------|
| `GET /parental-consent/parents` | `child_user_id = 自分` でフィルタ。不一致は 404 |
| `DELETE /parents/{linkId}` | `child_user_id = 自分` または `parent_user_id = 自分` でなければ 404 |
| `DELETE /invitations/{linkId}` | `child_user_id = 自分` でなければ 404 |
| `GET /parental-consent/children` | `parent_user_id = 自分` でフィルタ |
| `POST /approve`, `POST /reject` | 無効・期限切れ・使用済みを `AUTH_060` で統一（オラクル攻撃防止） |

### 7.2 トークンのハッシュ化

既存の `SecureTokenGenerator` / `AuthTokenService.hashToken()` を再利用する。

- 生成: 32バイト CSPRNG
- 保存: SHA-256(raw_token) → `token_hash`
- 送信: 平文を メール URL に含める

### 7.3 レートリミット

| エンドポイント | 制限 | キー |
|--------------|------|------|
| POST `/invitations` | 24時間 10回 | `child_user_id` |
| POST `/approve` | 1時間 20回 | IP アドレス |
| POST `/reject` | 1時間 20回 | IP アドレス |

実装: 既存の Bucket4j + Caffeine パターン。

### 7.4 保護者の正当性確認（自己申告の限界と対応方針）

**現状の限界**: システムは保護者が「実際の法定代理人」であることを技術的に確認する手段を持たない。

**リスク**: 善意のない第三者が子アカウントを「承認」する可能性がある。ただし保護者がアクセスできるのは子の表示名・マスクされたメールのみ。

**現フェーズの対応方針**

1. 招待方式を子からの招待のみに限定（保護者からの一方的な紐付け不可）
2. 承認した保護者の `parent_user_id` を記録し監査ログに残す
3. SYSTEM_ADMIN が不正リンクを強制解除できる
4. 将来フェーズ: 本人確認書類のアップロードや SMS 二要素認証の義務付けを検討

### 7.5 `PENDING_PARENTAL_CONSENT` 状態での機能制限

**実装（`ParentalConsentGateFilter`・`JwtAuthenticationFilter` 直後で発火）**: サーバ側で強制する。フロント側のリダイレクトのみに頼らず、認証済み・`ppc==true`（同意待ち）のユーザーに対し、許可リスト外のリクエストを 403 `AUTH_070` で遮断する（401 は返さない。無限リフレッシュ回帰防止）。満18歳到達時は `ParentalConsentReleaseBatchService`（§6.4）が自動解放する。

**許可リスト（メソッド＋パス厳密一致）**
- `/api/v1/parental-consent/**` — 保護者同意管理 API（招待・保護者一覧・承認/否認）は丸ごと許可
- `GET /api/v1/users/me` — 本人状態確認のみ（**GET 限定**。プロフィール編集 `PUT /users/me` は許可しない）
- `DELETE /api/v1/users/me` — 退会申請。GDPR 削除権に基づき、保護者同意が完了していない本人にも退会は許可する（2026-07 マスター裁可・件1追従）
- `POST /api/v1/auth/logout` / `POST /api/v1/auth/refresh` — 認証ライフサイクルのうち同意前の未成年に必要な2経路のみ
- `/api/i18n/**`, `/api/v1/public/**` — permitAll 系プレフィックス（多重防御）

**禁止する操作（403 `AUTH_070`）**
- プロフィール編集（`PUT /users/me`）・パスワード変更（`PATCH /users/me/password`）・メール変更等の書き込み系
- チームへの参加・投稿、タイムライン投稿、チャット送信、その他の主要機能
- 2FA setup・WebAuthn register・OAuth link/confirm・セッション管理等（`/api/v1/auth/**` の一括許可は採らない。過剰許可になるため）

→ 違反時は `AUTH_070`（403）を返す。実装・テストは `backend/src/main/java/com/mannschaft/app/config/ParentalConsentGateFilter.java` / `ParentalConsentGateFilterTest.java`。

## 9. GDPR 対応

> `age_group_settings` は管理者設定マスタであり個人データを含まないため、F12.3 のデータエクスポート対象外とする。

### 9.1 `parental_consent_links` の保持・削除ルール

| 状況 | 保持ポリシー |
|------|------------|
| `status = PENDING` で期限切れ | バッチで `REVOKED` → 90日後物理削除 |
| `status = APPROVED` | 子退会後30日で物理削除（F12.3 AccountPurgeService 拡張） |
| `status = REJECTED` | 監査記録として90日保持後物理削除 |
| `status = REVOKED` | 90日保持後物理削除 |

### 9.2 データエクスポート対象

F12.3 の `PersonalDataCollector` に `parental_consent` カテゴリを追加（`parental_consent.json`）。

```json
{
  "parental_consent_links_as_child": [
    {
      "link_id": "...",
      "parent_email": "parent@example.com",
      "status": "APPROVED",
      "approved_at": "..."
    }
  ],
  "parental_consent_links_as_parent": [
    {
      "link_id": "...",
      "child_email_masked": "c***@example.com",
      "status": "APPROVED",
      "approved_at": "..."
    }
  ]
}
```

**注意**: 保護者側エクスポートでは子のメールをマスク。子の実名・電話番号等の PII は含めない。

`ParentalConsentLinkEntity` に `@PersonalData(category = "parental_consent")` を付与すること。

### 9.3 退会時のリンク処理

**子が退会する場合**
- `parental_consent_links.child_user_id = 退会ユーザー` のレコードを `REVOKED` に更新
- 各保護者に「子アカウントが退会申請しました」通知（非同期・ベストエフォート）

**保護者が退会する場合**
- §6.3 の退会ブロックフローで唯一保護者チェックを実施
- 通過後: `parent_user_id = 退会ユーザー` のレコードを `REVOKED` に更新

## 14. セキュリティ横断要件（docs/security/ との統合）

本セクションは `docs/security/` の横断設計書と F01.9 固有の実装要件を統合する。

### 14.1 未成年者アカウントへの広告配信禁止

- `users.is_minor` ≡ `AgeGroupCalculator.isMinor(birth_date, today)` が `true` の場合、F09.17 広告配信対象から除外すること
- 広告ターゲティングの `SegmentCalculationService` は年齢区分フィルタを適用する
- 未成年者を広告対象に含めてはならない（GDPR Article 8 / COPPA 準拠）

### 14.2 保護者同意メールリンクの有効期限確認

- 同意招待トークンの有効期限は **72 時間**（§3.3 の `expires_at = 発行から7日後` は運用上の最大値。72 時間未満での期限切れチェックを実装すること）

> 現状の設計では `expires_at = 発行から7日後` だが、セキュリティ観点から有効期限を 72 時間に短縮することを推奨する（§12 未解決問題 U-03 として追記を検討）。

### 14.3 GDPR Article 8: 13 歳未満の保護

- 13 歳未満（EU ユーザー対象）は保護者の同意必須（§1.2 で日本基準 18 歳未満が既にカバー）
- 日本基準 18 歳未満への保護者同意義務付けは EU 要件より厳しいため、グローバル展開でも対応済み

### 14.4 保護者同意の監査ログ

以下の操作は必ず `AuditLog` エントリを作成すること:

| 操作 | AuditEventType | 記録内容 |
|---|---|---|
| 保護者同意の承認 | `PARENTAL_CONSENT_APPROVED` | child_user_id / parent_user_id / link_id |
| 保護者同意の否認 | `PARENTAL_CONSENT_REJECTED` | child_user_id / 理由コード / link_id |
| 保護者リンクの取消（子から） | `PARENTAL_CONSENT_REVOKED_BY_CHILD` | child_user_id / link_id |
| 保護者リンクの解除（保護者から） | `PARENTAL_CONSENT_REVOKED_BY_PARENT` | parent_user_id / child_user_id / link_id |
| SYSTEM_ADMIN による強制解除 | `PARENTAL_CONSENT_ADMIN_REVOKED` | admin_user_id / child_user_id / link_id / 理由 |

> 根拠: 保護者同意は法的要件（個人情報保護法 §18 / GDPR Article 8）に基づくため、全操作を監査証跡として保持する必要がある。
