## 0. 本書の読み方 — 事実と提案の区別

TimeTree との比較検討で「誰がどの予定を追加・変更・削除・日程変更したか」を**通知（割り込み）でなくフィード（後から眺める）で追える**機能として採用が決定した。本書はその設計である。

## 1. 背景

### 1.1 課題

【確認済み】現行のスケジュール機能（`ScheduleService` ほか、`backend/src/main/java/com/mannschaft/app/schedule/`）には、予定の作成・変更・削除・日程変更を**チーム／組織のメンバーが後から一覧で追う手段が無い**。通知（F04.3/F04.11）は個々のイベントを都度プッシュするが、「今週誰が何を動かしたか」をまとめて眺める導線が欠けている。TimeTree の「アクティビティ」相当の体験差分。

### 1.2 御裁可済みの方針

1. **既存 `activity_feed` テーブルを拡張する方式を採用**【御裁可済】。`timeline_posts` へシステム投稿を作る方式（F17.2 §3.2 で村ドメインが採った方式）は本機能では**不採用**。理由: スケジュール変更は「タイムラインに流れる読み物」ではなく「ダッシュボードで後から眺める活動ログ」の性質が強く、既存の `activity_feed`（§1.3・F02.2 §該当章）が想定する用途と一致するため。
2. **可視性は参照時に `ScheduleVisibilityMapper`/`ScheduleVisibilityResolver` で絞る**【御裁可済】。作成時にスナップショットを取る方式は不採用。理由: 予定が後から非公開化・削除・出席者変更された場合でも、フィード側は常に「現在の可視性ルール」で正しく隠れる（作成時スナップショットだとタイムラグで漏洩する）。
3. **30日保持は現行を踏襲**【既定】。延長要否は将来検討（§10.1）。

## 2. スコープ

### 2.1 対象操作

| 操作 | 対応する `ActivityType`（新設） |
|---|---|
| 予定の新規作成 | `SCHEDULE_CREATED` |
| 予定の内容変更（タイトル・場所・詳細など。日時変更を除く） | `SCHEDULE_UPDATED` |
| 予定の削除・キャンセル | `SCHEDULE_CANCELLED` |
| 予定の日程変更（開始/終了日時・終日フラグの変更） | `SCHEDULE_RESCHEDULED` |

【既定・検分是正】`SCHEDULE_UPDATED` と `SCHEDULE_RESCHEDULED` の判定は、`startAt`/`endAt`/`isAllDay` の **値の等価比較（null安全）** で行う。すなわち `!Objects.equals(before.startAt, after.startAt) || !Objects.equals(before.endAt, after.endAt) || !Objects.equals(before.isAllDay, after.isAllDay)` が真であれば「日程が変わった」と判定し `SCHEDULE_RESCHEDULED` を発行する。この3項目のいずれも変わっておらず、かつ他のフィールド（タイトル・場所・詳細等）に差分があれば `SCHEDULE_UPDATED` を発行する。両方に差分がある場合は `SCHEDULE_RESCHEDULED` を優先する（日程変更の方が村人にとって重要度が高いため。その他の変更点も同一 `detail.fields` に含めて1行に畳む・§3.2）。差分が一切無い（no-op 更新）場合はイベント自体を発行しない。

### 2.2 対象外（Out of Scope）

- 個人スコープ（`ScopeType.PERSONAL`）の予定操作。既存 `ActivityFeedService.getActivityFeed` は `scopeTypes = [TEAM, ORGANIZATION]` 固定であり、本書もこれを踏襲する（個人予定は元々「他人が眺める」フィードの対象外）。
- `ScheduleAttendanceService`（出欠回答）・`ScheduleReminderService`（リマインダー）・`ScheduleMediaService`（添付ファイル）は対象外。予定本体の CRUD＋日程変更のみが対象（§5 でこの境界を明記）。
- 繰り返し予定（`ScheduleRecurrenceService`）の個別インスタンス単位のフィード化は対象外。繰り返しルール自体の変更は親予定の `SCHEDULE_UPDATED` として1件集約する【既定】。
- FE の新規画面追加は行わない。既存 dashboard ActivityFeed ウィジェットの表示分岐拡張のみ（§2.3）。

### 2.3 FE スコープ【検分是正・実ファイル名に修正】

【確認済み】既存の該当コンポーネントは以下の2ファイル（軍議時点の「dashboard ActivityFeed ウィジェット」という呼称は正式なコンポーネント名ではなかったため実名に訂正）:

- `frontend/app/components/widgets/WidgetRecentActivity.vue`: `GET /dashboard/activity`（`useDashboardApi().getActivity`）を叩き、`ActivityItem.vue` へ1件ずつ渡す親ウィジェット。現状 `targetTitle: a.summary` を渡しているのみで、**タップで対象予定へ遷移する導線は存在しない**。
- `frontend/app/components/ActivityItem.vue`: `activityConfig`（`Record<string, { icon, verb }>`）というオブジェクトに `POST_CREATED`/`EVENT_CREATED` 等7種別の**アイコンと日本語動詞がハードコードされている**（i18n 未対応。§8 で是正）。

本書で追加する作業は次の3点（いずれも新規実装。既存の仕組みを流用できる部分は無い）:
1. `activityConfig` に SCHEDULE 系4種別のエントリを追加（アイコン・i18nキー）。
2. `WidgetRecentActivity.vue` に **タップで対象予定詳細へ遷移する導線を新規実装**する（`targetType === 'SCHEDULE'` の場合 `targetId` から遷移先 URL を組み立てる。現状どの `targetType` に対しても遷移導線が無いため、本書がこの機構自体を初めて作る）。
3. `targetTitle` の組み立て元を `a.summary` から `a.detail.title` へ切り替える（§3.2・§8）。

## 3. DB設計

### 3.1 ALTER 内容【提案】

```sql
-- 【提案】activity_feed への ALTER（dashboard ドメインの変更。Flyway 版番号は下記注記のとおりマージ時に確定）
ALTER TABLE activity_feed
  ADD COLUMN detail JSON NULL;  -- 変更差分表示用。NULL=詳細なし（既存7種別は引き続きNULLのまま）
```

- 既存カラム（`scope_type`/`scope_id`/`actor_id`/`activity_type`/`target_type`/`target_id`/`summary`/`created_at`）は変更しない。
- `activity_type` の VARCHAR(30) 制約は既存のまま（`SCHEDULE_CREATED` ほか新設値も30文字以内で収まる）。
- `detail` は **JSON型・NULL許容**。既存7種別（`POST_CREATED` 等）は書き込まず `NULL` のまま（後方互換）。
- インデックスの追加は不要（`detail` は一覧クエリの絞り込み条件に使わない。読み取り時に JSON をそのまま返すのみ）。

**Flyway 採番の注記**【必須】: major は **マージ時に `origin/main` 全体の最大 major + 1 で確定**する（CLAUDE.md Git運用ルール）。2026-08-05 時点の `origin/main` 最大 major は 175 のため、本書作成時点の暫定値は 176 だが、**実装 PR のマージ直前に再取得して確定**すること（`date -u '+%Y%m%d%H%M%S'` で minor を採番）。ファイル名例（暫定）: `V176.{タイムスタンプ}__alter_activity_feed_add_detail.sql`。

### 3.2 `detail` JSON スキーマ【提案・検分是正】

変更差分表示のための構造化データ。`activity_type` ごとに任意項目を持つ薄い JSON。**表示用タイトルは `summary` ではなく `detail.title` を正本とする**（§4.1・§8 で理由を後述）。

```json
{
  "scheduleId": 12345,
  "title": "定例会議（延期）",
  "fields": [
    { "field": "startAt", "before": "2026-08-10T19:00:00", "after": "2026-08-17T19:00:00" },
    { "field": "title", "before": "定例会議", "after": "定例会議（延期）", "changed": true }
  ],
  "affectedCount": 1
}
```

| キー | 型 | 説明 |
|---|---|---|
| `scheduleId` | number | 対象予定 ID（`target_id` と同値。冗長だが JSON 単体でも自己完結させるため保持） |
| `title` | string | **予定の現在のタイトル**（作成・更新・削除いずれの操作でも常に搭載する）。FE はこれと `activityType` の i18n キーを組み合わせて表示文言を組み立てる（§4.1 理由2・§8） |
| `fields` | array | 変更されたフィールドの一覧。`SCHEDULE_CREATED`/`SCHEDULE_CANCELLED` は空配列 `[]` |
| `fields[].field` | string | 変更フィールド名（`title`/`startAt`/`endAt`/`isAllDay`/`location`/`status` のいずれか。**固定語彙・自由文字列不可。`description` は含めない**＝下記「漏洩面の是正」参照） |
| `fields[].before` | string \| null | 変更前値（作成時は存在しないため `null` は許容しない＝`SCHEDULE_CREATED` では `fields` 自体が空） |
| `fields[].after` | string \| null | 変更後値（削除・キャンセル時は `null`） |
| `fields[].changed` | boolean | `description` のように値そのものを載せられないフィールドで、「変更があった事実のみ」を示す場合に `true` を立てる（`before`/`after` は省略）。§「漏洩面の是正」参照 |
| `affectedCount` | number | `updateScope = ALL`（繰り返し予定の一括更新）で対象となった子予定の件数。単発更新時は `1`（§5.3） |

**漏洩面の是正**【検分是正・重大】: `description`（予定の詳細本文）は `fields[].before`/`after` の**語彙から除外**する。予定の詳細本文には非公開情報（個人の連絡先・機微な議題等）が含まれうるため、フィード（活動ログ）という「常時眺められる」性質の面に生の本文を転記するのはリスクが高い。`description` が変更された場合は `{ "field": "description", "changed": true }` のみを記録し、値そのものは載せない。FE は「詳細が更新されました」のような定型文言のみを表示する（値は表示しない・§4.1）。

**未知フィールド値へのフォールバック**【検分是正・中】: FE は `fields[].field` が既知の語彙（`title`/`startAt`/`endAt`/`isAllDay`/`location`/`status`）に一致しない値を受け取った場合、**その行だけをスキップせず**、フィールド名をそのまま表示するフォールバックとする（例: `field: "priority"` なら「priority: 変更前→変更後」のようにキー名をそのまま出す）。フィード全体・該当エントリ全体を握りつぶさない（CLAUDE.md「症状を隠さない」原則）。

- **before/after は生の値をそのまま文字列化**して格納する（表示用の翻訳・整形は FE 側で `activityType` + `field` を見て行う。i18n ルールに従いサーバー側で日本語文言を焼き付けない）。
- 日時は ISO-8601（`LocalDateTime.toString()` 相当）。タイムゾーン変換は行わない（既存スケジュールAPIの日時バインド方式に合わせる。memory `project_datetime_binding_path_asymmetry` の踏襲＝ボディ系は素の LocalDateTime）。
- サイズ上限: `fields` は最大10件（それ以上変更があっても先頭10件のみ記録。既存 `summary` VARCHAR(200) と同様、フィードは「概要」であって完全な監査証跡ではない＝`audit_logs` との棲み分けは F02.2 §該当章の踏襲）。

### 3.3 Entity 変更【提案】

`ActivityFeedEntity` に `detail` フィールドを追加する。

```java
@Column(columnDefinition = "JSON")
private String detail;  // JSON文字列。NULL=詳細なし
```

`ActivityEvent` にも同名フィールド（`String detail`、nullable）を追加し、`ActivityFeedEventListener.handleActivityEvent` の `ActivityFeedEntity.builder()` に `.detail(event.getDetail())` を足す。JSON のシリアライズは Service 層（§5）で `ObjectMapper` により文字列化してから `ActivityEvent` に積む。

**シリアライズ失敗時の扱い**【検分是正・中】: `ObjectMapper.writeValueAsString` が例外を投げた場合、フィードは予定 CRUD の**付帯機能**であり本体トランザクションを巻き込まない。`detail` の JSON 化に失敗しても、(1) 予定本体の作成・更新・削除処理は正常に完結させる、(2) フィード発行自体は `detail = null` にフォールバックして続行するか、あるいはフィード発行そのものをスキップし WARN ログのみ出力する（どちらでも良いが、**予定操作を失敗させることは絶対に行わない**）。既存 `ActivityFeedEventListener` の「INSERT失敗はリトライなし WARN ログのみ」という既存方針と同じ思想。

### 3.4 rollback 方針

- `detail` は NULL 許容の追加カラムのみで、既存カラムの変更・DROP・FK 変更を伴わない。**Expand のみ**（原則の「Expand → Contract」の Expand フェーズで完結。Contract 相当の作業は発生しない）。
- ロールバックが必要な場合は `ALTER TABLE activity_feed DROP COLUMN detail;` で復元可能（データ損失は `detail` 列のみ・既存7種別の運用に影響なし）。
- アプリケーションコードのロールバック（PR revert）と DB ロールバックは独立して行える（`detail` が存在しない状態でも旧コードはそのまま動作する＝後方互換）。

## 4. API契約

### 4.1 既存エンドポイントの拡張

既存 `GET /dashboard/activity`（`ActivityFeedService.getActivityFeed` が実体）のレスポンス DTO `ActivityFeedResponse`（`dashboard/dto/ActivityFeedResponse.java`）に `detail` フィールドを追加する。新規エンドポイントは作らない。**既存フィールド名 `type`（`activityType` ではない）はリネームしない**（検分是正・重大1）。

```
GET /dashboard/activity?cursor={id}&limit={n}&scopeIds={id,id,...}
```

**レスポンス拡張**:

```jsonc
{
  "id": 98765,
  "type": "SCHEDULE_RESCHEDULED",
  "actor": { "id": 501, "displayName": "田中太郎", "avatarUrl": null },
  "scopeType": "TEAM",
  "scopeId": 42,
  "scopeName": "第一営業チーム",
  "targetType": "SCHEDULE",
  "targetId": 12345,
  "summary": "予定「定例会議」の日程を変更しました",
  "detail": {
    "scheduleId": 12345,
    "title": "定例会議",
    "fields": [
      { "field": "startAt", "before": "2026-08-10T19:00:00", "after": "2026-08-17T19:00:00" }
    ],
    "affectedCount": 1
  },
  "createdAt": "2026-08-05T10:30:00"
}
```

- OpenAPI（`docs/openapi.json`）は Backend 実装 PR 側で再生成し、FE 型（`frontend/app/types/generated/index.ts`）も同一 PR で `npm run generate:types` すること（CLAUDE.md 型定義ルール）。

### 4.2 可視性フィルタリング【御裁可済の実装・検分是正で手順を書き切る】

`ActivityFeedService.getActivityFeed` の SCHEDULE 系エントリ組み立て時、対象予定（`target_id` = スケジュール ID）に対して **`ScheduleVisibilityResolver.filterAccessible(Collection<Long> scheduleIds, Long viewerUserId)`（基底 `AbstractContentVisibilityResolver` 実装）を通し、呼び出しユーザーから見えない予定のフィードは結果から除外する**。

**検分是正: 「既存の削除済みコンテンツスキップ方式」は実在しない**。F02.2 側ドキュメントの「削除済みコンテンツは `deleted_at IS NOT NULL` を検出してスキップし代替件数分を追加取得する」という記述は**現行の `ActivityFeedService.getActivityFeed` には実装されていない**（実装は Repository から `PageRequest.of(0, resolvedLimit)` で件数固定取得し、そのまま `dashboardMapper.toActivityFeedResponse` に流すのみで、可視性・削除済みのフィルタは一切無い）。本書はこの「参照時フィルタ＋不足分の追加取得」という挙動を**本書のスコープで新規に実装する**。具体的な手順は以下のとおり:

1. `resolveLimit(limit)` で確定した希望件数を `N` とする。
2. Repository から `N` 件（`PageRequest.of(0, N)`）を取得する（従来どおり）。
3. 取得結果のうち `targetType == SCHEDULE` の行について、`scheduleId` 集合を作り `ScheduleVisibilityResolver.filterAccessible(scheduleIds, userId)` に**一括**で渡す（バッチ判定・§10.3）。`targetType != SCHEDULE` の行（既存7種別）はこのフィルタを通さず、そのまま結果に含める（可視性判定の対象外）。
4. `filterAccessible` が返した `Set<Long>` に含まれない `scheduleId` を持つ行を結果から除外する。`filterAccessible` は**実存しない予定（削除済み等）の ID を fail-closed で結果セットから除外する**（`AbstractContentVisibilityResolver.loadProjections` が返さない行は自動的に不可視扱い＝§10.3）。
5. 除外後の件数が `N` 未満であれば、**直前に取得した最後の行の `id` をカーソルとして次ページを追加取得**し、3〜4を繰り返す。これを「件数が `N` に達する」か「取得したデータが尽きる（Repository が空リストを返す）」か「**追加フェッチのループ回数が上限（既定5回）に達する**」まで繰り返す。上限に達した場合は、その時点で集まった件数（`N` 未満でもよい）をそのまま返す（無限ループ防止。可視性で大半が弾かれる極端なケースでもレスポンス時間を保証する）。
6. **次カーソルの算出**: レスポンスの `nextCursor`（クライアントが次回 `cursor` に渡す値）は、**フィルタ後の最後の要素の `id` ではなく、フィルタ前に Repository から取得した最後の行の `id`** とする。理由: フィルタ後の id を使うと、次回リクエストが「除外された行を re-fetch する」区間を含んでしまい重複判定・整合性が崩れる。フィルタ前の最終 id を使えば「次はこの id より古い行から」という Repository のカーソル条件（`a.id < :cursor`）とそのまま一致し、正しく続きから取得できる。

- 予定が削除・非公開化された後に発生したフィード読み取りでも、**都度 Resolver を通すため常に最新の可視性で正しく隠れる**（作成時スナップショット方式との違い＝これが§1.2の御裁可理由そのもの）。
- **同一経路の明記**【検分是正・中】: `DashboardService.loadRecentActivity`（`DashboardService.java:262` 付近）も内部で `activityFeedService.getActivityFeed(...)` を呼ぶだけであり、`ActivityFeedService` 内に実装する可視性フィルタは**この経路にも自動的に適用される**（ダッシュボード初期表示の `recent_activity` とウィジェット単体の `GET /dashboard/activity` の両方が同一フィルタを通る）。
- 認可はここに一元化する。Controller 層・Repository 層で独自の可視性判定を追加しない（memory `feedback_visibility_bypass_f00_audit`：独自述語は漏洩源）。

### 5.2 `EVENT_CREATED` との排他ルール【検分是正・重大7】

【確認済み】`events` テーブル（`event` ドメイン、F03.8）は `schedule_id` で `schedules` テーブルの拡張情報として紐付く。`ActivityType.EVENT_CREATED` は既存の enum 値として定義済みだが、**現時点でどの Service からも発行されていない**（§1.3）。本書が `schedules` への CRUD に SCHEDULE 系イベントを結線することで、**`events.schedule_id` に紐付く予定の作成も `ScheduleService.createSchedule` を経由する限り `SCHEDULE_CREATED` の対象になる**。ここで排他ルールを明記する:

- [`F03.17`](F03.17_schedule_keep_conversion.md) のキープ変換（ユーザーの「気になる」リストから予定を作成する導線。ファイル名は暫定・別ブランチで設計中のため本書マージ時に実ファイル名を確認すること）で作られた予定も、通常の `ScheduleService.createSchedule` を経由する限り `SCHEDULE_CREATED` の発行対象である（キープ変換専用の別イベントは新設しない）。

### 5.3 `updateScope = ALL`（繰り返し予定の一括更新）時の発行件数【検分是正・中】

繰り返し予定を `updateScope: "ALL"` で一括更新した場合（親スケジュール1件の更新が複数の子スケジュールへ波及する既存フロー）、**1回の更新操作につきフィード行は1行のみ発行する**（対象の子スケジュール数だけ発行しない）。裁定: 「1操作=1行」とし、影響範囲は `detail.affectedCount`（§3.2）に件数を載せる。`target_id` は親スケジュール（更新の起点となったスケジュール）の ID を使う。

### 5.4 フィード洪水対策（同一操作の高頻度更新）【検分是正・中】

同一 `actorId` が同一 `scheduleId` に対して**直近5分以内**に複数回の更新操作（`SCHEDULE_UPDATED`/`SCHEDULE_RESCHEDULED`）を行った場合、新規 INSERT を行わず、**既存の直近1行を UPDATE してフィールド差分をマージする**（裁定）。

- 判定条件: `actorId` と `targetId`（＝ `scheduleId`）が一致し、かつ直近の同種フィード行の `createdAt` が現在時刻から5分以内。
- マージ方法: 既存行の `detail.fields` と新規差分をフィールド名でマージする（同一フィールドが再度変更された場合は `before` は既存行の `before` を維持し `after` のみ新値に差し替える＝最初の値から最新の値への差分として1行にまとめる）。`activityType` が `SCHEDULE_UPDATED` → `SCHEDULE_RESCHEDULED` に変わる場合（例: 最初はタイトルのみ変更、5分以内に日時も変更）は `activityType` を `SCHEDULE_RESCHEDULED` に昇格させる（逆方向の降格は行わない）。
- `createdAt` は UPDATE 時に更新しない（フィード上の表示順は初回操作時刻を維持。5分間の連続編集を「1つの編集セッション」として扱う）。
- 実装方針: `ActivityFeedEventListener` 側（受信時）で判定・マージするのではなく、**Service 層（§5.1 の発行ポイント）がイベント発行前に直近行の有無を確認し、マージ済みの `detail` を1回だけ発行する**か、あるいは `ActivityFeedEventListener` 側で `findRecentByActorAndTarget` 的なクエリを追加して UPDATE 分岐を行うかは実装 PR の裁量とする（いずれの方式でも「5分以内は1行に集約される」という外部から観測可能な振る舞いが一致すればよい）。

- **AC-08**（**格下げ**・検分是正）: 30日削除バッチが未実装であるため、実機E2Eでの「31日経過後に消える」検証は現実的でない。**統合テストへ格下げ**: `ActivityFeedRepository.deleteByCreatedAtBefore` を直接呼び出し、削除閾値（`threshold`）をテストコードから注入できる形（例: `LocalDateTime.now().minusDays(1)` のような短い閾値）で、閾値より古いレコードのみが物理削除され新しいレコードは残ることを確認する統合テストとする。あわせて本書で新設する `@Scheduled` バッチ（毎日 AM 3:00・30日閾値・§5.5 準拠）が正しく `deleteByCreatedAtBefore` を呼び出すことをユニットテストで確認する。
- **AC-09**（新規・検分是正）: 対象予定が物理削除・存在しない状態で当該予定のフィード行を読むと、`ScheduleVisibilityResolver.filterAccessible` が fail-closed で当該 `scheduleId` を結果から除外し、フィード一覧に表示されないことを実機確認する（§4.2・§10.3の fail-closed 挙動の裏取り）。

## 10. 非機能

### 10.1 30日保持の扱い

【既定】現行30日保持を踏襲する。延長要否は将来検討とし、本書では変更しない。理由: TimeTree 比較検討では「直近の変更を追えること」が主眼であり、長期アーカイブ用途（村史のような編纂）は要求されていない。将来、長期保持のニーズが顕在化した場合は F02.2 側の保持期間ポリシー変更として別途検討する（本書のスコープ外）。

### 10.2 インデックス

新規インデックスは追加しない（§3.1）。既存 `idx_af_scope`（`scope_type, scope_id, created_at DESC`）がそのまま SCHEDULE 系エントリの取得にも効く。`detail` は絞り込み条件に使わないため、JSON カラムへのインデックスは不要。

### 10.3 N+1 対策【検分是正で実装対象を名指し】

`ActivityFeedService.getActivityFeed` の可視性フィルタ（§4.2）は、既存クラス **`AbstractContentVisibilityResolver`（`common/visibility/AbstractContentVisibilityResolver.java`）が提供する `filterAccessible(Collection<Long> contentIds, Long viewerUserId)`** をそのまま使う。このメソッドは（1）対象 ID 集合を1SQLでまとめて実存確認込み Projection 取得し（`loadProjections`）、（2）必要なスコープ集合をバッチ集計し、（3）`MembershipBatchQueryService` でスナップショットを一括構築する、という**既存のバッチ設計そのもの**であり、1件ずつ問い合わせる実装を新たに書く必要はない。`ScheduleVisibilityResolver` はこの基底クラスのサブクラスとして実装済みのため、本書は**呼び出し側（`ActivityFeedService`）が対象 `scheduleId` 集合を1回にまとめて `filterAccessible` に渡す**ことだけを徹底すればよい（§4.2 手順3）。既存コードの `actorNames`/`teamNames`/`orgNames` のバッチ名前解決パターン（`ActivityFeedService` 内に実例あり）と同じ思想の踏襲。

### 10.4 fail-closed の挙動確認【検分是正・中】

`AbstractContentVisibilityResolver.filterAccessible` は、`loadProjections` が実存確認込みで Projection を返さない ID（削除済み・存在しない予定など）を**結果セットから自動的に除外する**（`rows == null || rows.isEmpty()` の早期リターン、および `filterAccessibleStream` の `Objects::nonNull` フィルタ）。すなわち「Projection が返らない ID は不可視」というのは本書が新設する挙動ではなく、**基底クラスの既存の fail-closed 実装がそのまま適用される**。本書はこれを AC-09 として明示的に検証する。

### 10.5 30日削除バッチの新設【検分是正・重大8・裁定】

【確認済み】`ActivityFeedRepository.deleteByCreatedAtBefore(LocalDateTime threshold)` は定義済みだが呼び出し元が無い（§1.3）。裁定: 本書のスコープで **`@Scheduled` 日次バッチを新設**する。

```java
// dashboard/service/ActivityFeedCleanupBatchService.java（新設・イメージ）
@Scheduled(cron = "0 0 3 * * *", zone = "Asia/Tokyo")
public void cleanupOldActivityFeed() {
    LocalDateTime threshold = LocalDateTime.now().minusDays(30);
    int deleted = activityFeedRepository.deleteByCreatedAtBefore(threshold);
    log.info("activity_feed 物理削除バッチ完了 deletedCount={}", deleted);
}
```

- 実行時刻: 毎日 AM 3:00 JST（F02.2 側ドキュメントに記載済みの想定時刻を踏襲）。
- 閾値: `createdAt < now - 30日`。
- 件数のログ出力のみ（アラート閾値等は本書スコープ外・既存 Micrometer カウンター `activity_feed_write_failures` とは別軸）。
- このバッチは SCHEDULE 系4種別に限らず `activity_feed` 全体（既存7種別含む）を対象とする（テーブル単位の保持ポリシーであり種別を問わない）。
