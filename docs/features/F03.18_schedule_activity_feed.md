## 0. 本書の読み方 — 事実と提案の区別

TimeTree との比較検討で「誰がどの予定を追加・変更・削除・日程変更したか」を**通知（割り込み）でなくフィード（後から眺める）で追える**機能として採用が決定した。本書はその設計である。

| 記法 | 意味 |
|---|---|
| 【確認済み】 | `origin/main` の実ファイルを開いて確認した事実。クラス名・テーブル名・enum 値は実物と一致する |
| 【提案】 | 本書で新規に提案する設計。実装は未着手 |
| 【御裁可済】 | マスターが決定済みの事項（本書では変更しない） |
| 【既定】 | 家老が既定値として置く判断。PR レビューで変更可 |

本書の目標は **未決事項ゼロ** である（§11 に残余があれば「要裁可」として明示）。

## 1. 背景

### 1.1 課題

【確認済み】現行のスケジュール機能（`ScheduleService` ほか、`backend/src/main/java/com/mannschaft/app/schedule/`）には、予定の作成・変更・削除・日程変更を**チーム／組織のメンバーが後から一覧で追う手段が無い**。通知（F04.3/F04.11）は個々のイベントを都度プッシュするが、「今週誰が何を動かしたか」をまとめて眺める導線が欠けている。TimeTree の「アクティビティ」相当の体験差分。

### 1.2 御裁可済みの方針

1. **既存 `activity_feed` テーブルを拡張する方式を採用**【御裁可済】。`timeline_posts` へシステム投稿を作る方式（F17.2 §3.2 で村ドメインが採った方式）は本機能では**不採用**。理由: スケジュール変更は「タイムラインに流れる読み物」ではなく「ダッシュボードで後から眺める活動ログ」の性質が強く、既存の `activity_feed`（§1.3・F02.2 §該当章）が想定する用途と一致するため。
2. **可視性は参照時に `ScheduleVisibilityMapper`/`ScheduleVisibilityResolver` で絞る**【御裁可済】。作成時にスナップショットを取る方式は不採用。理由: 予定が後から非公開化・削除・出席者変更された場合でも、フィード側は常に「現在の可視性ルール」で正しく隠れる（作成時スナップショットだとタイムラグで漏洩する）。
3. **30日保持は現行を踏襲**【既定】。延長要否は将来検討（§10.1）。

### 1.3 既存資産（拡張対象）

【確認済み】以下は実装済みで、本書はこの上に拡張する:

| 資産 | 実体 | 備考 |

## 2. スコープ

### 2.1 対象操作

| 操作 | 対応する `ActivityType`（新設） |
|---|---|
| 予定の新規作成 | `SCHEDULE_CREATED` |
| 予定の内容変更（タイトル・場所・詳細など。日時変更を除く） | `SCHEDULE_UPDATED` |
| 予定の削除・キャンセル | `SCHEDULE_CANCELLED` |
| 予定の日程変更（開始/終了日時の変更） | `SCHEDULE_RESCHEDULED` |

【既定】`SCHEDULE_UPDATED` と `SCHEDULE_RESCHEDULED` は Service 層で判定を分ける（§5.2）。日時が変わっていれば `SCHEDULE_RESCHEDULED`、それ以外の変更のみなら `SCHEDULE_UPDATED`。両方同時に変わった場合は `SCHEDULE_RESCHEDULED` を優先（日程変更の方が村人にとって重要度が高いため・要約文でその他の変更点も1行に畳む。§3.2）。

### 2.2 対象外（Out of Scope）

- 個人スコープ（`ScopeType.PERSONAL`）の予定操作。既存 `ActivityFeedService.getActivityFeed` は `scopeTypes = [TEAM, ORGANIZATION]` 固定であり、本書もこれを踏襲する（個人予定は元々「他人が眺める」フィードの対象外）。
- `ScheduleAttendanceService`（出欠回答）・`ScheduleReminderService`（リマインダー）・`ScheduleMediaService`（添付ファイル）は対象外。予定本体の CRUD＋日程変更のみが対象（§5 でこの境界を明記）。
- 繰り返し予定（`ScheduleRecurrenceService`）の個別インスタンス単位のフィード化は対象外。繰り返しルール自体の変更は親予定の `SCHEDULE_UPDATED` として1件集約する【既定】。
- FE の新規画面追加は行わない。既存 dashboard `ActivityFeed` ウィジェットの表示分岐拡張のみ（§2.3）。

### 2.3 FE スコープ

既存 `frontend/app/components/dashboard/` 配下の ActivityFeed ウィジェット（`GET /dashboard/activity` を叩く既存コンポーネント）に、`targetType === 'SCHEDULE'` 時のアイコン・タップ遷移先（該当予定詳細ページ）・`activityType` 別の文言分岐を追加する。新規コンポーネントは作らない。

## 3. DB設計

### 3.1 ALTER 内容【提案】

```sql
-- 【提案】activity_feed への ALTER（dashboard ドメインの変更。Flyway 版番号は下記注記のとおりマージ時に確定）
ALTER TABLE activity_feed
  ADD COLUMN detail JSON NULL;  -- 変更差分表示用。NULL=詳細なし（既存7種別は引き続きNULLのまま）
```

- 既存カラム（`scope_type`/`scope_id`/`actor_id`/`activity_type`/`target_type`/`target_id`/`summary`/`created_at`）は変更しない。
- `activity_type` の VARCHAR(30) 制約は既存のまま（`SCHEDULE_CREATED` ほか新設値も30文字以内で収まる）。
- `detail` は **JSON型・NULL許容**。既存7種別（`POST_CREATED` 等）は書き込まず `NULL` のまま（後方互換）。
- インデックスの追加は不要（`detail` は一覧クエリの絞り込み条件に使わない。読み取り時に JSON をそのまま返すのみ）。

**Flyway 採番の注記**【必須】: major は **マージ時に `origin/main` 全体の最大 major + 1 で確定**する（CLAUDE.md Git運用ルール）。2026-08-05 時点の `origin/main` 最大 major は 175 のため、本書作成時点の暫定値は 176 だが、**実装 PR のマージ直前に再取得して確定**すること（`date -u '+%Y%m%d%H%M%S'` で minor を採番）。ファイル名例（暫定）: `V176.{タイムスタンプ}__alter_activity_feed_add_detail.sql`。

### 3.2 `detail` JSON スキーマ【提案】

変更差分表示のための構造化データ。`activity_type` ごとに任意項目を持つ薄い JSON（フィード一覧で「タイトルが『定例会議』→『定例会議（延期）』に変更」のような1行要約の元データ）。

```json
{
  "scheduleId": 12345,
  "fields": [
    { "field": "startAt", "before": "2026-08-10T19:00:00", "after": "2026-08-17T19:00:00" },
    { "field": "title", "before": "定例会議", "after": "定例会議（延期）" }
  ]
}
```

| キー | 型 | 説明 |
|---|---|---|
| `scheduleId` | number | 対象予定 ID（`target_id` と同値。冗長だが JSON 単体でも自己完結させるため保持） |
| `fields` | array | 変更されたフィールドの一覧。`SCHEDULE_CREATED`/`SCHEDULE_CANCELLED` は空配列 `[]` |
| `fields[].field` | string | 変更フィールド名（`title`/`startAt`/`endAt`/`location`/`description` のいずれか。**固定語彙・自由文字列不可**） |
| `fields[].before` | string \| null | 変更前値（作成時は存在しないため `null` は許容しない＝`SCHEDULE_CREATED` では `fields` 自体が空） |
| `fields[].after` | string \| null | 変更後値（削除・キャンセル時は `null`） |

- **before/after は生の値をそのまま文字列化**して格納する（表示用の翻訳・整形は FE 側で `activityType` + `field` を見て行う。i18n ルールに従いサーバー側で日本語文言を焼き付けない）。
- 日時は ISO-8601（`LocalDateTime.toString()` 相当）。タイムゾーン変換は行わない（既存スケジュールAPIの日時バインド方式に合わせる。memory `project_datetime_binding_path_asymmetry` の踏襲＝ボディ系は素の LocalDateTime）。
- サイズ上限: `fields` は最大10件（それ以上変更があっても先頭10件のみ記録。既存 `summary` VARCHAR(200) と同様、フィードは「概要」であって完全な監査証跡ではない＝`audit_logs` との棲み分けは F02.2 §該当章の踏襲）。

### 3.3 Entity 変更【提案】

`ActivityFeedEntity` に `detail` フィールドを追加する。

```java
@Column(columnDefinition = "JSON")
private String detail;  // JSON文字列。NULL=詳細なし
```

`ActivityEvent` にも同名フィールド（`String detail`、nullable）を追加し、`ActivityFeedEventListener.handleActivityEvent` の `ActivityFeedEntity.builder()` に `.detail(event.getDetail())` を足す。JSON のシリアライズは Service 層（§5）で `ObjectMapper` により文字列化してから `ActivityEvent` に積む（Entity 側では素の JSON 文字列を保持するのみ・型安全な JSON マッピングは行わない＝既存 `ActivityFeedEntity` が Jackson の `@JdbcTypeCode` 等を使っていない現行方針に合わせる）。

### 3.4 rollback 方針

- `detail` は NULL 許容の追加カラムのみで、既存カラムの変更・DROP・FK 変更を伴わない。**Expand のみ**（原則の「Expand → Contract」の Expand フェーズで完結。Contract 相当の作業は発生しない）。
- ロールバックが必要な場合は `ALTER TABLE activity_feed DROP COLUMN detail;` で復元可能（データ損失は `detail` 列のみ・既存7種別の運用に影響なし）。
- アプリケーションコードのロールバック（PR revert）と DB ロールバックは独立して行える（`detail` が存在しない状態でも旧コードはそのまま動作する＝後方互換）。

## 4. API契約

### 4.1 既存エンドポイントの拡張

既存 `GET /dashboard/activity`（`ActivityFeedService.getActivityFeed` が実体）のレスポンス DTO `ActivityFeedResponse`（`dashboard/dto/ActivityFeedResponse.java`）に `detail` フィールドを追加する。新規エンドポイントは作らない。

```
GET /dashboard/activity?cursor={id}&limit={n}&scopeIds={id,id,...}
```

**レスポンス拡張**:

```jsonc
{
  "id": 98765,
  "scopeType": "TEAM",
  "scopeId": 42,
  "actor": { "id": 501, "displayName": "田中太郎", "avatarUrl": null },
  "scopeName": "第一営業チーム",
  "activityType": "SCHEDULE_RESCHEDULED",
  "targetType": "SCHEDULE",
  "targetId": 12345,
  "summary": "予定「定例会議」の日程を変更しました",
  "detail": {
    "scheduleId": 12345,
    "fields": [
      { "field": "startAt", "before": "2026-08-10T19:00:00", "after": "2026-08-17T19:00:00" }
    ]
  },
  "createdAt": "2026-08-05T10:30:00"
}
```

- `detail` は既存7種別では `null`。SCHEDULE 系4種別のみ非 null。
- OpenAPI（`docs/openapi.json`）は Backend 実装 PR 側で再生成し、FE 型（`frontend/app/types/generated/index.ts`）も同一 PR で `npm run generate:types` すること（CLAUDE.md 型定義ルール）。

### 4.2 可視性フィルタリング【御裁可済の実装】

`ActivityFeedService.getActivityFeed` の SCHEDULE 系エントリ組み立て時、対象予定（`target_id` = スケジュール ID）に対して **`ScheduleVisibilityResolver` を通し、呼び出しユーザーから見えない予定のフィードは結果から除外する**。

- 既存の一覧取得は `PageRequest.of(0, resolvedLimit)` で件数固定のため、可視性フィルタで除外した分は**件数が減る**（TIMELINE_POST 等の削除済みコンテンツのスキップと同様の扱い。F02.2 §該当章「削除済みコンテンツの扱い」の踏襲＝代替件数の追加取得は既存方式に合わせて行う）。
- 予定が削除・非公開化された後に発生したフィード読み取りでも、**都度 Resolver を通すため常に最新の可視性で正しく隠れる**（作成時スナップショット方式との違い＝これが§1.2の御裁可理由そのもの）。
- 認可はここに一元化する。Controller 層・Repository 層で独自の可視性判定を追加しない（memory `feedback_visibility_bypass_f00_audit`：独自述語は漏洩源）。

## 5. イベント発行ポイント一覧【提案】

| Service | メソッド | 発行契機 | `ActivityType` | `detail.fields` |
|---|---|---|---|---|
| `ScheduleService` | `createSchedule` | 予定新規作成 | `SCHEDULE_CREATED` | 空配列 `[]` |
| `ScheduleService` | `updateSchedule` | 内容変更（日時以外） | `SCHEDULE_UPDATED` | 変更されたフィールドのうち `startAt`/`endAt` を除く差分 |
| `ScheduleService` | `updateSchedule` | 日時変更を含む更新 | `SCHEDULE_RESCHEDULED` | `startAt`/`endAt` を含む全差分（§2.1 優先ルール） |
| `ScheduleService` | `deleteSchedule` | 予定削除 | `SCHEDULE_CANCELLED` | 空配列 `[]` |
| `ScheduleService` | `cancelSchedule` | 予定キャンセル | `SCHEDULE_CANCELLED` | 空配列 `[]` |

- `scopeType`/`scopeId` は既存の予定スコープ解決ロジック（`ScheduleService` が保持するチーム/組織スコープ）をそのまま使う。個人スコープ（`ScopeType.PERSONAL`）の予定は §2.2 のとおり発行対象外＝Service 側で `scopeType == PERSONAL` の場合はイベント発行自体をスキップする。
- `actorId` は操作を行ったユーザー ID（各メソッドが受け取る `userId` 引数）。
- `duplicateSchedule`（複製）は複製先が新規作成扱いのため `SCHEDULE_CREATED` を発行する【既定】。
- `ScheduleAnnualCopyService`（年次コピー）・`ScheduleRecurrenceService`（繰り返し生成）はバッチ的な一括生成であり、1件ずつのフィード化は情報過多になるため**対象外**【既定】（§2.2 と同じ理由）。
- 発行方式は既存 `ActivityEvent` をそのまま使う（`ApplicationEventPublisher.publishEvent(new ActivityEvent(...))`）。トランザクション境界は F17.2 §3.3 と同じ考え方＝`ActivityFeedEventListener` 側が `AFTER_COMMIT` で受けるため、Service 側は本体トランザクション内で発行するだけでよく、追加の `afterCommit` 同期登録は不要（既存 `ActivityFeedEventListener` の仕組みがそのまま吸収する）。

## 6. 通知との棲み分け（F04.3/F04.11）

- **通知（F04.3 個人通知／F04.11 該当範囲）**: 予定の作成・変更・削除の**都度、対象者へ割り込みで届く**。既読・未読の状態を持ち、リアルタイム性が重要な用途（例: 明日の予定が急に日程変更された、を見逃さないため）。
- **本書のフィード（`activity_feed`）**: **後から眺める活動ログ**。既読管理を持たない・リアルタイム配信もしない（ダッシュボードを開いたときに GET するのみ）。「今週チームの予定がどう動いたか」を俯瞰する用途。
- 両者は**独立して書き込まれる**（F02.2 §該当章の `audit_logs` との棲み分けと同じ考え方＝1つの操作から複数のサブシステムへ並行して書き込む）。本書の Service 発行ポイント（§5）は、通知発行ポイントとは別の `ApplicationEvent`（`ActivityEvent`）であり、通知トリガーのロジックには一切手を入れない。
- 通知が失敗してもフィードへの記録は独立して成功しうる（逆も同様）。両者間の整合性保証は行わない（既存 `ActivityFeedEventListener` の「リトライなし・WARN ログのみ」方針を踏襲＝30日で消えるログにそこまでのコストをかけない）。

## 7. エラーコード表

新設 enum **`ScheduleFeedErrorCode`**（`schedule` ドメイン配下に新設。既存の他ドメイン ErrorCode 命名規則に合わせる）。読み取り中心の機能のため少数で足りる。

| コード | 意味 | HTTP ステータス |
|---|---|---|
| `SCHEDULE_FEED_001` | フィード読み取り時、対象予定が既に削除されておりフィード表示をスキップした（エラー応答ではなく内部ログ用途。API レスポンスには現れない） | — |
| `SCHEDULE_FEED_002` | `detail` JSON のパースに失敗した（不正データ検出時。該当フィード行はレスポンスから除外し WARN ログ） | — |

**確定はマージ時に再確認すること**【必須】。上記2件は「読み取り時の内部異常系スキップ」用途であり、通常のクライアントエラー応答（4xx系）は本機能では発生しない想定（可視性フィルタは §4.2 のとおり「結果から除外」であって「エラーを返す」設計ではないため）。実装時にクライアント向けエラー応答が必要になった場合はこの表に追記する。

## 9. 受け入れ条件（AC）

- **AC-01**: チームの予定を作成すると、同チームの他メンバーのダッシュボード「最近のアクティビティ」に `SCHEDULE_CREATED` のフィード行が表示される（作成者本人には表示されない＝既存 `actor_id != userId` フィルタ）。
- **AC-02**: 予定のタイトルのみ変更すると、フィードに `SCHEDULE_UPDATED` として表示され、`detail.fields` に `title` の before/after が含まれる。
- **AC-03**: 予定の開始日時を変更すると、フィードに `SCHEDULE_RESCHEDULED` として表示され、`detail.fields` に `startAt` の before/after が含まれる。
- **AC-04**: 予定を削除すると、フィードに `SCHEDULE_CANCELLED` が表示される。
- **AC-05**: 非公開予定（`ScheduleVisibilityResolver` が不可視と判定するケース）を作成しても、可視性の無いメンバーのフィードには表示されない。
- **AC-06**: 可視だった予定が後から非公開化された場合、既存のフィード行を該当メンバーが読むと**表示されない**（作成時スナップショットでなく参照時解決であることの実機確認）。
- **AC-07**: 個人スコープ（`ScopeType.PERSONAL`）の予定操作はフィードに一切表示されない。
- **AC-08**: 作成から31日経過したスケジュールフィード行は、既存の日次物理削除バッチにより消える（新種別も既存30日保持ルールに従うことの確認）。

## 10. 非機能

### 10.1 30日保持の扱い

【既定】現行30日保持を踏襲する。延長要否は将来検討とし、本書では変更しない。理由: TimeTree 比較検討では「直近の変更を追えること」が主眼であり、長期アーカイブ用途（村史のような編纂）は要求されていない。将来、長期保持のニーズが顕在化した場合は F02.2 側の保持期間ポリシー変更として別途検討する（本書のスコープ外）。

### 10.2 インデックス

新規インデックスは追加しない（§3.1）。既存 `idx_af_scope`（`scope_type, scope_id, created_at DESC`）がそのまま SCHEDULE 系エントリの取得にも効く。`detail` は絞り込み条件に使わないため、JSON カラムへのインデックスは不要。

### 10.3 N+1 対策

`ActivityFeedService.getActivityFeed` の可視性フィルタ（§4.2）を素朴に1件ずつ `ScheduleVisibilityResolver` へ問い合わせると、フィード1ページ（既定10件・最大50件）ごとに最大 N 回の可視性判定が走る。**バッチ解決**を必須とする【提案】: `ScheduleVisibilityResolver` に対象スケジュール ID 集合をまとめて渡し、可視な ID の集合を一括取得するメソッド（既存にバッチ版が無い場合は実装 PR で追加）を使うこと。既存コードの `actorNames`/`teamNames`/`orgNames` のバッチ名前解決パターン（`ActivityFeedService` 内に実例あり）を踏襲する。
