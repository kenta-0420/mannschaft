## 1. 概要

マイ TODO 画面の「進行中にする」「完了にする」ボタンが「行先ステータス名+にする」という説明的表現で分かりにくい、という UX フィードバックを起点に、TODO のステータス操作 UX を全面的に見直す機能。以下の3機能を一体として提供する。

1. **カスタムステータスラベル**: 「未着手 / 着手中 / 完了」の SYSTEM 既定3種に加え、ユーザー / チーム / 組織がスコープ別に独自ラベル（例: 「レビュー中」「上長承認待ち」「差し戻し」）を定義できる。各ラベルは `OPEN / IN_PROGRESS / COMPLETED` の3バケットのいずれかに属し、バケット単位で集計・進捗計算される。
2. **キャッチボール**: チーム / 組織 TODO で「他のメンバーに渡す」ボタンを追加。宛先（複数可）+ 新ステータスラベル + メッセージを指定して、assignees を入れ替えつつステータスとひと言メッセージを同時に記録する。
3. **履歴タイムライン**: キャッチボール履歴を「いつ・誰から誰に・どのステータスへ・どんなメッセージで」の時系列で可視化。ボールを今誰が持っているか、なぜその状態になっているかを遡って確認できる。

### 狙う効果

- ステータス操作が **Select + 「変更」ボタン** に統一されることで「どのボタンが何をするのか」の認知負荷が消える。
- TODO の運用ルールをチームの実態に合わせやすくなる（カスタムラベル）。
- assignee = ボール保持者 が常に1点に定まり、責任の所在が明確になる（キャッチボール）。
- 履歴で経緯が追えるため、質問・追跡コストが下がる。

### 3機能の関係

カスタムステータスラベルは「ステータスの語彙」を拡張する基盤。キャッチボールはその語彙を使って `assignees + status + message` を一括更新する複合操作。履歴タイムラインはキャッチボールの結果を時系列で見せる UI。3つは独立した機能ではなく、`todo_status_labels` テーブルを共通基盤として一体で提供する。

## 2. スコープ

### 対象ロール

本マトリクスは **チーム / 組織スコープでの操作権限**を示す。個人スコープは下段「個人スコープの特例」を参照。

| ロール | チーム/組織ラベル一覧 | チーム/組織ラベル CRUD | チーム/組織 TODO のラベル選択 | キャッチボール送出 | キャッチボール履歴閲覧 |
|--------|:-:|:-:|:-:|:-:|:-:|
| SYSTEM_ADMIN | ○（全スコープ閲覧可） | ×（運用上は介入しない。緊急時の調査用途のみ別途 admin API で対応） | ○ | ○ | ○ |
| ADMIN | ○ | ○（自スコープのみ） | ○（担当者本人または ADMIN として） | ○ | ○ |
| DEPUTY_ADMIN | ○ | × | ○（担当者本人 または `MANAGE_TODO` 権限保有時） | ○（担当者本人 または `MANAGE_TODO`） | ○ |
| MEMBER | ○ | × | ○（担当者本人のみ） | ○（担当者本人のみ） | ○ |
| SUPPORTER | × | × | × | × | × |
| GUEST | × | × | × | × | × |

**個人スコープの特例**: 個人ラベル（`scope_type = 'PERSONAL'`）は本人のみが CRUD 可能（パスが `/api/v1/users/me/todo-status-labels` で実質強制）。他人の個人ラベルは閲覧・操作不可。SYSTEM_ADMIN も個人ラベルへの直接介入はしない（プライバシー観点）。

**SYSTEM ラベルの不変性**: `is_system_default = true` の SYSTEM ラベル（未着手 / 着手中 / 完了）は全員読み取り可能・編集不可・削除不可。SYSTEM_ADMIN も含む全ユーザーが書き込み禁止。Service 層で強制する。

### 対象レベル

- [x] 個人 (Personal) — `/api/v1/users/me/todo-status-labels`
- [x] チーム (Team) — `/api/v1/teams/{teamId}/todo-status-labels`
- [x] 組織 (Organization) — `/api/v1/organizations/{orgId}/todo-status-labels`
- [x] SYSTEM — 全ユーザー共通の組み込み3ラベル（読み取り専用）

### 機能対応マトリクス

| 機能 | 個人 TODO | チーム TODO | 組織 TODO |
|------|:-:|:-:|:-:|
| カスタムステータスラベル定義 | ○（本人のみ） | ○（ADMIN のみ） | ○（ADMIN のみ） |
| ラベル選択によるステータス変更 | ○ | ○ | ○ |
| キャッチボール送出 | × | ○ | ○ |
| キャッチボール履歴 | — | ○ | ○ |

個人 TODO ではキャッチボール UI を出さない（仕様）。理由: 個人 TODO に「他のメンバー」が存在しないため。

## 3. DB 設計

### テーブル一覧

| テーブル名 | 役割 | 論理削除 |
|-----------|------|---------|
| `todo_status_labels` | カスタムステータスラベル（SYSTEM/個人/チーム/組織スコープ） | あり（`deleted_at`） |
| `todo_handoffs` | キャッチボール履歴（不変ログ） | なし（TODO 物理削除時のみ CASCADE） |
| `todos`（既存テーブル拡張） | `status_label_id BIGINT NULL` カラム追加 | — |

### テーブル定義

#### `todo_status_labels`

カスタムステータスラベル本体。3バケット（`OPEN` / `IN_PROGRESS` / `COMPLETED`）のいずれかに属する。

| カラム名 | 型 | NULL | デフォルト | 説明 |
|---------|---|------|-----------|------|
| `id` | BIGINT UNSIGNED | NO | AUTO_INCREMENT | PK |
| `scope_type` | VARCHAR(20) | NO | — | `SYSTEM` / `PERSONAL` / `TEAM` / `ORGANIZATION` |
| `scope_id` | BIGINT UNSIGNED | YES | NULL | users.id / teams.id / organizations.id。`SYSTEM` のとき NULL |
| `name` | VARCHAR(50) | NO | — | ラベル表示名（例: `レビュー中`, `差し戻し`） |
| `bucket` | VARCHAR(20) | NO | — | `OPEN` / `IN_PROGRESS` / `COMPLETED` |
| `color` | VARCHAR(7) | YES | NULL | テーマカラー（HEX。例: `#FF6B6B`）。バッジ表示色 |
| `sort_order` | INT | NO | 0 | スコープ内の表示順 |
| `is_system_default` | BOOLEAN | NO | FALSE | TRUE のときは編集 / 削除不可（SYSTEM ラベル保護用） |
| `created_by` | BIGINT UNSIGNED | YES | NULL | FK → users。SYSTEM / バッチ作成は NULL（ON DELETE SET NULL） |
| `created_at` | DATETIME | NO | CURRENT_TIMESTAMP | |
| `updated_at` | DATETIME | NO | CURRENT_TIMESTAMP ON UPDATE | |
| `deleted_at` | DATETIME | YES | NULL | 論理削除日時 |

**インデックス**

```sql
INDEX idx_tsl_scope (scope_type, scope_id, sort_order)   -- スコープ別の一覧
INDEX idx_tsl_bucket (bucket)                            -- バケット集計用
INDEX idx_tsl_active (deleted_at)                        -- アクティブ抽出用
CONSTRAINT chk_tsl_bucket CHECK (bucket IN ('OPEN','IN_PROGRESS','COMPLETED'))
CONSTRAINT chk_tsl_scope_type CHECK (scope_type IN ('SYSTEM','PERSONAL','TEAM','ORGANIZATION'))
CONSTRAINT chk_tsl_scope_id_for_system CHECK (
  (scope_type = 'SYSTEM' AND scope_id IS NULL) OR
  (scope_type <> 'SYSTEM' AND scope_id IS NOT NULL)
)
```

**制約・備考**

- `(scope_type, scope_id, name)` 重複防止: MySQL は partial unique index を直接サポートしないため、Service 層で `existsActiveByScopeAndName` チェック。`deleted_at IS NULL` のレコードのみ重複扱い。
- `is_system_default = true` のレコードは Service 層で UPDATE / DELETE を拒否。
- ラベル数上限: **1スコープあたり最大 20 件（SYSTEM は除く）**。Service 層で `countActiveByScope >= 20` なら 409 `LABEL_LIMIT_EXCEEDED`。SYSTEM_ADMIN にも同じ上限を適用（暴走防止）。
- 論理削除: `deleted_at` を立てるのみ。物理削除はバッチでも行わない（履歴保全と FK ON DELETE SET NULL の挙動に依存）。

#### `todo_handoffs`

キャッチボール履歴。assignee の入れ替え + ステータス変更 + メッセージを1行に記録する不変ログ。

| カラム名 | 型 | NULL | デフォルト | 説明 |
|---------|---|------|-----------|------|
| `id` | BIGINT UNSIGNED | NO | AUTO_INCREMENT | PK |
| `todo_id` | BIGINT UNSIGNED | NO | — | FK → todos（ON DELETE CASCADE） |
| `from_user_id` | BIGINT UNSIGNED | NO | — | 操作者（FK → users。ON DELETE SET NULL は不可、ユーザー削除時は履歴削除許容のため CASCADE） |
| `from_assignee_user_ids` | JSON | NO | — | 操作前 assignees スナップショット（user_id 配列） |
| `to_assignee_user_ids` | JSON | NO | — | 操作後 assignees スナップショット（user_id 配列） |
| `previous_status` | VARCHAR(20) | NO | — | 変更前 status（`OPEN` / `IN_PROGRESS` / `COMPLETED`） |
| `previous_status_label_id` | BIGINT UNSIGNED | YES | NULL | 変更前 label_id（FK → todo_status_labels。ON DELETE SET NULL） |
| `previous_status_label_name` | VARCHAR(50) | YES | NULL | 変更前 label 名スナップショット（履歴表示でラベル削除されても壊れない） |
| `new_status` | VARCHAR(20) | NO | — | 変更後 status |
| `new_status_label_id` | BIGINT UNSIGNED | YES | NULL | 変更後 label_id（FK → todo_status_labels。ON DELETE SET NULL） |
| `new_status_label_name` | VARCHAR(50) | YES | NULL | 変更後 label 名スナップショット |
| `message` | VARCHAR(500) | YES | NULL | キャッチボールに添えるひと言（プレーンテキスト） |
| `created_at` | DATETIME | NO | CURRENT_TIMESTAMP | |

**インデックス**

```sql
INDEX idx_handoff_todo (todo_id, created_at DESC)        -- TODO 詳細のタイムライン取得
INDEX idx_handoff_from_user (from_user_id, created_at)   -- 「自分が渡した履歴」検索（将来用）
CONSTRAINT fk_handoff_todo FOREIGN KEY (todo_id) REFERENCES todos(id) ON DELETE CASCADE
CONSTRAINT fk_handoff_prev_label FOREIGN KEY (previous_status_label_id) REFERENCES todo_status_labels(id) ON DELETE SET NULL
CONSTRAINT fk_handoff_new_label FOREIGN KEY (new_status_label_id) REFERENCES todo_status_labels(id) ON DELETE SET NULL
CONSTRAINT fk_handoff_from_user FOREIGN KEY (from_user_id) REFERENCES users(id) ON DELETE CASCADE
```

**制約・備考**

- `todo_id` ON DELETE CASCADE: TODO が物理削除されたら履歴も消す（論理削除では消さない。`todos.deleted_at IS NOT NULL` でも履歴は残る）。
- ラベル名スナップショット: `previous_status_label_name` / `new_status_label_name` をリクエスト時点の `todo_status_labels.name` のコピーで保存。あとでラベルが論理削除されても履歴表示は壊れない。
- `message` は VARCHAR(500)、プレーンテキスト。HTML / Markdown 不許可（Vue デフォルトエスケープで描画）。
- `from_user_id` ON DELETE CASCADE: 退会ユーザーの履歴は連鎖削除される。これは F02.3 親設計書の `created_by ON DELETE RESTRICT`（退会前移譲必須）とは異なる扱い。**理由**: 履歴は補助情報であり、退会者の操作履歴を残す優先度は CRUD 主体の TODO 本体より低い。退会後の履歴問い合わせ要件が出た場合は将来 SET NULL + `from_user_display_name` スナップショット追加を検討。
- `from_assignee_user_ids` / `to_assignee_user_ids` の JSON は user_id の整数配列のみ（例: `[10, 12, 15]`）。ユーザー名スナップショットは保存しない（容量・整合性の観点。表示時は `users` テーブルを join し、退会ユーザーは `(退会済み)` 表示にフォールバック）。

#### `todos`（既存テーブル拡張）

```sql
ALTER TABLE todos ADD COLUMN status_label_id BIGINT UNSIGNED NULL AFTER status;
ALTER TABLE todos ADD CONSTRAINT fk_todos_status_label
  FOREIGN KEY (status_label_id) REFERENCES todo_status_labels(id) ON DELETE SET NULL;
CREATE INDEX idx_todos_status_label_id ON todos(status_label_id);
```

`status_label_id` は NULL 許容。NULL のとき: 既存 TODO は `status` enum から SYSTEM 既定ラベル（`OPEN→未着手 / IN_PROGRESS→着手中 / COMPLETED→完了`）にフロント側でフォールバック描画。マイグレーション後の一括 UPDATE は不要（後方互換）。

### ER 図（テキスト形式）

```
todo_status_labels (1) ──── (N) todos [status_label_id]                 ※ON DELETE SET NULL
todo_status_labels (1) ──── (N) todo_handoffs [previous_status_label_id] ※ON DELETE SET NULL
todo_status_labels (1) ──── (N) todo_handoffs [new_status_label_id]      ※ON DELETE SET NULL
todos (1) ──── (N) todo_handoffs                                          ※ON DELETE CASCADE
users (1) ──── (N) todo_handoffs [from_user_id]                           ※ON DELETE CASCADE
users (1) ──── (N) todo_status_labels [created_by]                        ※ON DELETE SET NULL
```

#### `POST /api/v1/teams/{teamId}/todo-status-labels`

**認可**: チーム ADMIN のみ

**リクエストボディ**

```json
{
  "name": "レビュー中",
  "bucket": "IN_PROGRESS",
  "color": "#fbbf24",
  "sort_order": 10
```

**バリデーション**

- `name`: `@NotBlank @Size(max=50)`
- `bucket`: `@NotBlank @Pattern(regexp="OPEN|IN_PROGRESS|COMPLETED")`
- `color`: `@Pattern(regexp="^#[0-9a-fA-F]{6}$")` 任意（NULL 可）
- `sort_order`: `@Min(0)` 任意（NULL → 0）

**レスポンス（201 Created）**

```json
{
  "data": {
    "id": 11,
    "scope_type": "TEAM",
    "scope_id": 100,
    "name": "レビュー中",

    "color": "#fbbf24",
    "sort_order": 10,
    "is_system_default": false,
```

## 5. ビジネスロジック

### 5.1 バケット導出ルール

```
status_label_id 指定あり
  → label.bucket に従う
  → bucket → TodoStatus へマップ
       OPEN         → TodoStatus.OPEN
       IN_PROGRESS  → TodoStatus.IN_PROGRESS
       COMPLETED    → TodoStatus.COMPLETED

status のみ指定（後方互換）
  → status をそのまま使用
  → status_label_id は更新しない（NULL のまま または既存値を保持）

両方指定
  → bucket とのマップ結果が status と一致するか検証
  → 不一致なら 400 STATUS_LABEL_BUCKET_MISMATCH
  → 一致なら両方を更新（status + status_label_id）
```

`CANCELLED` バケットは持たない（仕様）。既存のキャンセル機能は別途「キャンセル」アクション（`PATCH /todos/{id}/cancel` 等。F02.3 既存 API として維持）として継続。Kanban / リスト UI では `CANCELLED` の TODO はバッジでフィルタ表示（バケット 3 列とは別の扱い）。

### 5.2 ラベル削除時の扱い

- `DELETE /todo-status-labels/{id}` を呼ぶと、Service 層で:
  1. `is_system_default = true` なら 403 拒否
  2. `SELECT COUNT(*) FROM todos WHERE status_label_id = :id AND deleted_at IS NULL` が 0 件なら論理削除（`deleted_at = NOW()`）
  3. 1 件以上なら 409 `LABEL_IN_USE`（使用件数を返す）
- 強制削除オプションは初版では持たない（保守性重視）。クライアントは「使用中の TODO のラベルを別のものに変更してから削除」というフローを取る。
- FK は `todos.status_label_id ON DELETE SET NULL` で防御層として機能（運用上は使われないが、何らかの異常で物理削除が起きた場合の安全網）。
- `todo_handoffs.previous_status_label_id` / `new_status_label_id` は `ON DELETE SET NULL` だが、name スナップショットは残るため履歴表示は壊れない。

### 5.3 ラベル数上限

- 1スコープあたり **20 件**（`SYSTEM` を除く `PERSONAL` / `TEAM` / `ORGANIZATION` のアクティブラベル）。
- 上限は `TodoStatusLabelService` のクラス定数（後で application.yml に外出ししても良い）。
- `POST` で `countActiveByScope >= 20` なら 409 `LABEL_LIMIT_EXCEEDED`。
- `PUT` での bucket 変更や `sort_order` 変更は上限に影響しない（既存ラベル数は変わらない）。
- 削除 → 再作成のサイクルは許容（論理削除なので既存削除分がカウント対象外になる）。

### 5.4 キャッチボールトランザクション

`POST /handoff` の処理は **同一 DB トランザクション** で以下を実行:

```
1. TODO 取得 + スコープ整合チェック（IDOR 防御）
2. 操作者がスコープのメンバーか検証
3. 宛先 to_user_ids が全員スコープのアクティブメンバーか検証
4. status_label_id を validateLabelForScope で検証（label.scope_type が SYSTEM または当該スコープ）
5. F02.7 マイルストーンロックの assertNotMilestoneLocked を通す（既存ガード流用）
6. 操作前 snapshot を取得:
   - previous_assignees = SELECT user_id FROM todo_assignees WHERE todo_id = :todoId
   - previous_status / previous_status_label_id / previous_status_label_name
7. todo_assignees から既存 assignee 全削除
8. todo_assignees に新 assignees を一括 INSERT
9. todos.status / status_label_id を更新（label.bucket → status を導出）
10. todo_handoffs に1行 INSERT（snapshot 名含む）
11. プロジェクト進捗の再計算（status が COMPLETED ↔ 非COMPLETED をまたぐ場合）
12. TodoHandoffEvent 発行（@TransactionalEventListener(phase=AFTER_COMMIT) で受信）
13. TodoStatusChangedEvent も from_handoff=true で発行
```

8 と 9 の間で例外が発生した場合、トランザクションロールバックにより既存 assignees / status は元に戻る。

### 5.5 自己 handoff の扱い

- 操作者のみが `to_user_ids` に含まれる（例: `from_user_id = 5`, `to_user_ids = [5]`）ケースは **許可**。
  - 用途: メッセージ付きステータス変更として（「ここまで進めた、続きは別ステータスで」）。
  - 通知は発火しない（自分には届けない）。`TodoHandoffEvent` リスナーで `to_user_ids - from_user_id` を取り、空集合なら通知をスキップ。
- 操作者が `to_user_ids` に含まれない（自分が完全に手放す）ケースも当然許可。

### 5.6 通知発火

- `TodoHandoffEvent` 発行 → `NotificationService` が新 assignees に対して `TODO_HANDED_OFF` 通知を発行。
  - 操作者本人（`from_user_id == recipient_user_id`）は除外。
  - 通知本文: 「○○さんから『{TODO タイトル}』を渡されました（ステータス: {新ラベル名}）」
  - 詳細は F04.3 §通知種別カタログを参照。
- `TodoStatusChangedEvent` も同時に発行されるが、`from_handoff = true` のフラグで `NotificationService` 側で重複通知を抑制（status 変更通知は出さない）。
- **既存 Service の改修要点**: 既存の `TodoStatusChangedEvent` 呼び出し元（通常の `PATCH /todos/{id}/status`）には `from_handoff = false` を明示的に渡す（後方互換）。`@Builder` 採用時はデフォルト false で良い。
- **同一バケット内のラベル変更**: handoff の前後で `previous_status == new_status`（例: 着手中→レビュー中、両方 IN_PROGRESS）でも、ラベル変更があれば handoff 通知は発火する（assignee が変わったことを伝えるのが主目的）。`TodoStatusChangedEvent` は `previous_status != new_status` のときのみ発火する既存挙動を踏襲（status enum が変わらない場合、ステータス変更通知は元々発火しない）。

### 5.7 Kanban バケット間 D&D

- Kanban ビューでカードを別バケット列にドラッグ&ドロップした場合:
  - フロントエンドは `PATCH /todos/{id}/status` を呼ぶ
  - 送信ペイロードは `{ status_label_id: <移動先バケットの最初の SYSTEM 既定ラベル ID> }`
  - 例: `OPEN` 列にドロップ → `status_label_id = 1`（未着手）
- 明示的なカスタムラベル変更は **詳細ページ** で行う（D&D ではバケット切り替えのみが目的のため）。
- これにより Kanban の列移動は「ステータスを大きく変える」、詳細ページは「ラベルを細かく変える」と役割分担。
- **将来拡張の余地**: 「移動先のバケット内で `sort_order` が最も小さいラベル」を SYSTEM ラベル優先で選ぶ拡張は将来検討（チームが「未着手」より優先したい既定ラベルを持つケース）。初版は SYSTEM 固定で割り切り、`TodoStatusLabel.SYSTEM_OPEN_ID` / `SYSTEM_IN_PROGRESS_ID` / `SYSTEM_COMPLETED_ID` の定数を直接参照する。

### 5.8 既存 TODO のフォールバック

- マイグレーション直後、既存 TODO は全て `status_label_id = NULL`。
- フロント側の `TodoStatusLabelBadge` コンポーネントは `status_label_id IS NULL` のとき `status` enum を見て SYSTEM 既定ラベル（`OPEN→未着手 / IN_PROGRESS→着手中 / COMPLETED→完了`）でバッジ描画。
- API レスポンスの `status_label` フィールドも `status_label_id IS NULL` の場合、Service 側で SYSTEM 既定ラベルを埋めて返す（フロントの実装を簡略化）。
- バッチによる一括 UPDATE は実施しない。後方互換は API レイヤーで吸収。

### 5.9 N+1 対策

- `GET /todos`（一覧）レスポンスで各 TODO に `status_label` を埋める際、Service 層で一度だけ `SELECT * FROM todo_status_labels WHERE id IN (?, ?, ...)` で `Map<Long, TodoStatusLabelEntity>` を構築し、各 `TodoResponse` に挿入する。
- 同様に handoff 履歴一覧でも `to_user_ids` / `from_assignee_user_ids` の display_name 取得は一括 `SELECT id, display_name FROM users WHERE id IN (...)` で1回。

### 5.10 マイルストーンロックとの整合

- F02.7 のマイルストーンロック中の TODO は status / label 変更も禁止（423 LOCKED）。
- ラベル経由の status 変更でも同じガード（`assertNotMilestoneLocked`）を通す。
- handoff も同じガードを通す。

### 5.11 主要フロー（キャッチボール）

```
1. ユーザーが TODO 詳細で「他のメンバーに渡す」ボタン押下
2. ダイアログで宛先・新ラベル・メッセージを入力
3. 「渡す」 → 確認画面 → 「実行」
4. POST /handoff → Service が 5.4 のトランザクション処理
5. 成功 → トースト表示・詳細画面リロード（タイムラインに新行）
6. AFTER_COMMIT で TodoHandoffEvent 発火
7. NotificationService → 新 assignees に TODO_HANDED_OFF 通知
8. AuditLogService → TODO_HANDED_OFF を audit_logs に記録
```

## 6. セキュリティ考慮事項

### 6.1 IDOR（Insecure Direct Object Reference）対策

- **`validateLabelForScope(label, todo.scopeType, todo.scopeId)`**: ラベルの `scope_type / scope_id` が当該 TODO のスコープ（または SYSTEM）に一致することを Service 層で検証。他チームのラベルを別チームの TODO に張り付ける攻撃を防ぐ。
- **TODO スコープ整合チェック**: `PATCH /teams/{teamId}/todos/{id}/status` でパスの `teamId` と `todos.scope_id` が一致することを確認。`SecurityCheck` インターセプタまたは Service 入口で必ず実行。
- **handoff 宛先メンバーシップ検証**: `to_user_ids` の全員が当該スコープのアクティブメンバーであることを `MembershipService.isMemberOf(userId, scope)` で検証。退会者・他チームメンバーへの handoff を拒否。
- **ラベル ID の範囲チェック**: `GET /labels/{id}` で他人の個人ラベルにアクセスしようとした場合、Service 入口で `label.scope_type == 'PERSONAL' && label.scope_id != actorId` を 403 で拒否。

### 6.2 権限マトリクス

| 操作 | 個人 | チーム | 組織 |
|------|:-:|:-:|:-:|
| ラベル一覧取得 | 本人 | メンバー全員 | メンバー全員 |
| ラベル作成 | 本人 | ADMIN | ADMIN |
| ラベル更新 | 本人 | ADMIN | ADMIN |
| ラベル削除 | 本人 | ADMIN | ADMIN |
| ラベル選択（status 変更） | 本人 | 担当者 / ADMIN / DEPUTY_ADMIN | 担当者 / ADMIN / DEPUTY_ADMIN |
| キャッチボール送出 | — | 担当者 / ADMIN / DEPUTY_ADMIN | 担当者 / ADMIN / DEPUTY_ADMIN |
| キャッチボール履歴閲覧 | — | TODO 閲覧権を持つ全員 | TODO 閲覧権を持つ全員 |

`AccessControlService.isAdminOrAbove(actorId, scope)` を使用。組織版は `isOrgAdminOrAbove`。

### 6.3 SYSTEM ラベルの不変性

- `is_system_default = true` の ラベルは `UPDATE` / `DELETE` を Service 層で拒否（403 `SYSTEM_LABEL_IMMUTABLE`）。
- DB 側でも `BEFORE UPDATE / DELETE` トリガーで二重防御を将来検討（初版はアプリケーション層のみ）。
- SYSTEM ラベルの `id` 1, 2, 3 はマイグレーション V19.003 で固定挿入。Java 側で定数として参照可能にする（`TodoStatusLabel.SYSTEM_OPEN_ID = 1` 等）。

### 6.4 XSS 対策

- ラベル `name` および handoff `message` は **プレーンテキスト**として保存・表示。
- フロントエンド（Vue）はデフォルトで HTML エスケープして描画（`{{ label.name }}` → エスケープ済み）。`v-html` での描画は **絶対に行わない**。
- HTML / Markdown は不許可。Markdown レンダリングが必要な場面では、ラベル名は許可しない（500字メッセージは将来 Markdown 対応の余地あり、初版はプレーン）。
- バックエンドでも `Jsoup` や正規表現での厳密なサニタイズは不要（プレーンテキストとして扱うため）。ただし `name` の改行コード（`\r\n` / `\n`）は INSERT 時に除去する（表示崩れ防止）。

### 6.5 CSRF / CORS

- 既存 `SecurityConfig` の CSRF / CORS 設定を流用。新規パスは `/api/v1/...` の既存パターン下なので追加設定不要。
- JWT Bearer 認証必須。

### 6.6 大量作成攻撃

- ラベル数上限: スコープあたり **20 件**（§5.3 参照）。
- handoff 連投レートリミット（Bucket4j 適用、二段構え）:
  - TODO ごと: 1分間に **5 回**（同一 TODO への連投防止）
  - スコープごと: 1分間に **20 回**（複数 TODO 横断の分散攻撃防止）
- ラベル CRUD レートリミット: 1分間に **30 回 / ユーザー**（既存 TODO API と同等）。
- 通知の発火対象数（handoff の `to_user_ids` 数）も上限 20 で抑制（§6.8）。

### 6.7 監査ログ

以下のイベントを `AuditLogService.record()` で記録（F10.3 §イベントタイプカタログを参照）:

| event_type | metadata 例 |
|-----------|------------|
| `TODO_STATUS_LABEL_CREATED` | `{"label_id": 11, "scope_type": "TEAM", "scope_id": 100, "name": "レビュー中", "bucket": "IN_PROGRESS"}` |
| `TODO_STATUS_LABEL_UPDATED` | `{"label_id": 11, "scope_type": "TEAM", "scope_id": 100, "changed_fields": ["name", "color"]}` |
| `TODO_STATUS_LABEL_DELETED` | `{"label_id": 11, "scope_type": "TEAM", "scope_id": 100, "name_snapshot": "レビュー中"}` |
| `TODO_HANDED_OFF` | `{"todo_id": 42, "to_user_ids": [12, 15], "new_status_label_id": 11, "new_status": "IN_PROGRESS"}` |

**スコープ記録方針**: `audit_logs.team_id` / `audit_logs.organization_id` カラム（F10.3 §3 参照）には当該スコープの ID を直接記録する（チームラベル CRUD なら `team_id = scope_id`、組織ラベル CRUD なら `organization_id = scope_id`）。個人ラベル CRUD は `team_id = NULL` / `organization_id = NULL` で `user_id = scope_id`（自分のみ）。`TODO_HANDED_OFF` も同様に当該 TODO の `scope_type` / `scope_id` をカラムに記録。これにより F10.3 のスコープフィルタクエリ（ADMIN が自スコープのログのみ参照）が正しく機能する。

### 6.8 ユーザー入力サイズ制限

- `name`: 50 文字（DB VARCHAR(50) に揃える）
- `message`: 500 文字
- `to_user_ids`: 最大 20 件（一度に20人へ渡すのが現実的な上限）
- `color`: HEX 7 文字（`^#[0-9a-fA-F]{6}$`）

## 9. マイ TODO 一覧 UX 補強（運用フィードバック対応）

### 9.1 経緯

F02.3.1 リリース直後の運用フィードバックで以下3件の退行が報告された。

1. **行クリックで詳細ページへ遷移できない**: 旧クイックボタン撤去後、行のうちタイトル文字部分のみが NuxtLink になっており、それ以外（バッジ・日付・優先度）の領域をクリックしても遷移しないため「行が押せなくなった」と認識された。
2. **一覧でステータス変更ができない**: 旧クイックボタン撤去により、ステータス変更には詳細画面への遷移が必須になり、運用効率が大きく低下した（一覧でチェック → 完了の操作が消えた）。
3. **listGroups の縦並び表示が冗長**: 期限切れ / 今日 / 今週 / それ以降 / 期限なし / 完了済みの 6 グループが縦に並ぶため、ワイドモニタでは下部のグループが視野外になりやすかった。

本節で、§1 で定めた「ステータス操作 = Select + 変更ボタンに統一」という設計原則を**詳細画面のみに限定**し、一覧では運用効率を優先する旨を補強する。

### 9.2 修正方針

- **一覧の行ラッパ全体を `<NuxtLink>` で覆う**（タイトルだけでなく行のどこをクリックしても詳細へ）。
- **行頭にチェックボックス**を配置し、クリック1発で `OPEN ↔ COMPLETED` をトグル。実体は SYSTEM 既定ラベルベースで実現するため、バックエンドの `PATCH /todos/{id}/status` に `{ status: 'COMPLETED' | 'OPEN' }` を送る。チェックボックス自体は `@click.stop`/`preventDefault` で NuxtLink の遷移を抑止。
- **行末ステータスラベルバッジクリックで Popover 表示**し、現スコープの全ラベル（SYSTEM 既定 + カスタム）を一覧してそのまま選べる。Popover の各行クリックで `PATCH /todos/{id}/status` に `{ statusLabelId }` を送る。
- 個人 / チーム / 組織すべてで確認ダイアログなし（Toast 通知のみ）。詳細画面に確認 UI が残っているため、誤操作リスクは「一覧での即時操作」の利便性とトレードオフで許容する。

### 9.3 設計原則の整理

| 画面 | ステータス変更 UI | 確認 UI |
|------|---|---|
| 一覧（マイ TODO / Kanban） | チェックボックス（完了トグル）+ バッジ Popover（任意ラベル選択） | なし（即時 + Toast） |
| 詳細（個人・チーム・組織） | Select + 「変更」ボタン（既存） | あり（確認ダイアログ） |

詳細画面の「Select + 変更ボタン」UI は §1 の設計原則どおり残す。一覧は運用効率を優先し、認知負荷を増やさない範囲で操作を高速化する。

### 9.4 listGroups の grid 化

`pages/todos/index.vue` の listGroups 表示を、Tailwind の階段式 grid で `1 / 2 / 3 / 4 列` に切り替える。

```text
grid-cols-1 md:grid-cols-2 lg:grid-cols-3 xl:grid-cols-4 gap-4
```

各グループはカード（`rounded-xl border bg-surface-50`）として描画し、内部で TODO の縦リストを保つ。ワイドモニタで全グループを一望できるようになる。

### 9.5 i18n キー

`todo.list.*` 配下に新規追加（6 言語、未訳は日本語と同値で暫定登録）。

- `allDone` / `overdueSuffix`
- `toggleCompleteHint` / `toggleCompleteAria`
- `changeLabelHint` / `changeLabelAria`
- `popoverTitle` / `popoverLoading` / `popoverEmpty`

### 9.6 影響範囲（変更ファイル）

- `frontend/app/components/todo/TodoListView.vue` — 行ラッパを NuxtLink 化、チェックボックスとラベル変更 Popover を追加。
- `frontend/app/composables/useTodoList.ts` — `changeStatus` で `statusLabelId` 指定時に `load()` 再実行（statusLabel オブジェクトを楽観更新できないため）。
- `frontend/app/pages/todos/index.vue` — TodoListView に `@change-status` を渡す。
- `frontend/app/locales/{ja,en,zh,ko,es,de}/common.json` — `todo.list.*` 新設。
