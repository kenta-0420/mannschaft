## §1 概要

会議やイベントに出席できないメンバーが、代わりの人（代理人）を指定して代わりに出席させる機能。

**主要機能**:
- **代理指定**: 委任者が代理人を明示的に指名してスケジュール/イベントへの出席を委託
- **承認フロー**: 「自動承認（代理人の確認不要）」と「代理人の明示的な同意が必要」の 2 パターン
- **出欠ステータス連動**: 代理指定・承認・拒否・取り消しに応じて委任者/代理人の出欠ステータスを自動更新
- **F08.3 連携**: イベント代理出席と議決権委任（proxy_delegations）を任意でセットで委任可能
- **代理チェックイン**: REGISTRATION モードのイベントで代理人が委任者の代わりにチェックイン

**対象**:
- スケジュール出欠（F03.1）: `schedule_delegations` テーブルで管理
- イベント参加登録（F03.8）: `event_delegations` テーブルで管理

## §2 スコープ・前提条件

### 対象ロール

代理指定の権限は固定ロールではなく、**対象スケジュール/イベントの出欠回答権を持つロール**に合わせる。
すなわち F03.1 / F03.8 の `min_response_role`（出欠回答に必要な最小ロール）を満たすロールが、委任者・代理人の双方になれる。
`min_response_role` が `SUPPORTER` に設定されている場合は SUPPORTER も代理指定・代理人になれる。
（本機能を「MEMBER 固定」とは表現しない。出欠回答権を持つロールと統一する。）

| ロール | 操作可能な範囲 |
|--------|--------------|
| ADMIN | 代理一覧閲覧・管理（全件）。代理チェックイン実行 |
| DEPUTY_ADMIN | `CHECKIN_EVENTS` 権限を持つ場合: 代理チェックイン実行 |
| 出欠回答権を持つロール（`min_response_role` 以上） | 代理指定（委任者として）・代理承認/拒否（代理人として）・自分の代理状況確認。`min_response_role = SUPPORTER` の対象では SUPPORTER も含む |
| 出欠回答権を持たないロール（`min_response_role` 未満） | 対象外 |
| GUEST | 対象外（`user_id` 必須のため代理人になれない） |

> 以降の本文・API 表で `MEMBER+` と表記している箇所は、より正確には「当該スケジュール/イベントの `min_response_role` を満たすロール」を指す。設定により SUPPORTER を含みうる。

### 対象レベル
- [x] 組織 (Organization)
- [x] チーム (Team)
- [ ] 個人 (Personal)

### 前提条件・制約
- `allow_proxy_attendance = TRUE` のスケジュール/イベントのみ機能が有効
- 外部ゲスト（`guest_email` での登録者）は代理人になれない（`user_id` 必須）
- **連鎖代理禁止**: B が C の代理として `PENDING` / `ACCEPTED` 状態にある場合、B を別の委任者の代理に指定不可
- **繰り返しスケジュール**: 親スケジュール（`parent_schedule_id IS NULL` かつ `recurrence_rule IS NOT NULL`）への一括代理指定は v1 不可。各子スケジュールに個別指定

### 3.3 schedule_delegations テーブル (Flyway: 実装時採番)

スケジュールに対する代理出席委任状を管理するテーブル。

> 番号は実装時に §9 の採番方針で確定する（固定番号は割り当てない）。

```sql
CREATE TABLE schedule_delegations (
  id              BINARY(16)      NOT NULL                 COMMENT 'UUIDv7 主キー',
  schedule_id     BIGINT UNSIGNED NOT NULL                 COMMENT 'FK → schedules.id',
  delegator_id    BIGINT UNSIGNED NOT NULL                 COMMENT '委任者 user_id（クロスドメイン、FK なし）',
  delegate_id     BIGINT UNSIGNED NOT NULL                 COMMENT '代理人 user_id（クロスドメイン、FK なし）',
  organization_id BIGINT UNSIGNED NULL                     COMMENT '親スケジュールから非正規化（組織スコープ時。team_id と XOR）',
  team_id         BIGINT UNSIGNED NULL                     COMMENT '親スケジュールから非正規化（チームスコープ時。organization_id と XOR）',
  status          VARCHAR(20)     NOT NULL DEFAULT 'PENDING'
                  COMMENT 'PENDING / ACCEPTED / REJECTED / CANCELLED',
  reason          VARCHAR(500)                             COMMENT '委任理由（任意）',
  reviewed_at     DATETIME                                 COMMENT '承認/拒否/取消日時',
  created_at      DATETIME        NOT NULL,
  updated_at      DATETIME        NOT NULL,
  -- アクティブ（PENDING/ACCEPTED）な委任のみ delegator_id を保持する生成カラム。
  -- REJECTED / CANCELLED では NULL になり、NULL は UNIQUE 制約の重複対象外のため再作成可能。
  active_delegator_marker BIGINT UNSIGNED
    AS (CASE WHEN status IN ('PENDING','ACCEPTED') THEN delegator_id END) STORED
    COMMENT 'アクティブ委任の一意性を DB 強制するための生成カラム',
  PRIMARY KEY (id),
  INDEX idx_sched_deleg_schedule  (schedule_id),
  INDEX idx_sched_deleg_delegator (schedule_id, delegator_id),
  INDEX idx_sched_deleg_delegate  (schedule_id, delegate_id),
  INDEX idx_sched_deleg_status    (schedule_id, status),
  INDEX idx_sched_deleg_org       (organization_id),
  -- 「1 スケジュール × 1 委任者 につきアクティブ委任は 1 件」を DB レベルで強制。
  -- MySQL は部分ユニークインデックス非対応のため、生成カラム + UNIQUE で代替する。
  UNIQUE KEY uq_active_delegation (schedule_id, active_delegator_marker),
  CONSTRAINT fk_sched_deleg_schedule
    FOREIGN KEY (schedule_id) REFERENCES schedules(id) ON DELETE RESTRICT
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci
  COMMENT='スケジュール代理出席';
```

**設計の注記**:
- UUIDv7 主キー（CLAUDE.md 原則6: 新規テーブルは `UuidV7Entity` 継承）
- `delegator_id` / `delegate_id` はクロスドメイン参照のため FK なし、インデックスのみ（原則1）
- `organization_id` / `team_id` は親スケジュールのスコープから**非正規化して保持**する（XOR：いずれか一方が NOT NULL）。
  将来の水平シャーディングでシャードキー（`organization_id`）の一貫性を保つため（CLAUDE.md 原則7）。
  `organization_id` を持つため、対応 Repository は `AbstractTenantAwareRepository` の継承を想定する。
- **アクティブ委任の一意性は DB 制約 + アプリ層チェックの二重で保証**する。
  - DB: 生成カラム `active_delegator_marker` + `UNIQUE KEY uq_active_delegation`。`PENDING` / `ACCEPTED` の間だけ `delegator_id` を保持し、`REJECTED` / `CANCELLED` 遷移後は NULL になる（NULL は重複可のため再作成できる）。
  - アプリ層: 作成時に既存の `PENDING` / `ACCEPTED` 行を確認し、存在すれば 409（DB 制約が最後の砦、アプリ層が先に親切なエラーを返す）。

**ステータス一覧**:
| ステータス | 説明 |
|-----------|------|
| `PENDING` | 代理人の承認待ち（`is_proxy_auto_accept = FALSE` の場合のみ） |
| `ACCEPTED` | 代理確定（自動承認または代理人が承認） |
| `REJECTED` | 代理人が拒否した |
| `CANCELLED` | 委任者またはシステムが取り消した |

### 3.4 event_delegations テーブル (Flyway: 実装時採番)

イベントに対する代理出席委任状を管理するテーブル。F08.3 投票代理との任意連携カラムを含む。

> 番号は実装時に §9 の採番方針で確定する（固定番号は割り当てない）。

```sql
CREATE TABLE event_delegations (
  id                    BINARY(16)      NOT NULL           COMMENT 'UUIDv7 主キー',
  event_id              BIGINT UNSIGNED NOT NULL           COMMENT 'FK → events.id',
  delegator_id          BIGINT UNSIGNED NOT NULL           COMMENT '委任者 user_id（クロスドメイン、FK なし）',
  delegate_id           BIGINT UNSIGNED NOT NULL           COMMENT '代理人 user_id（クロスドメイン、FK なし）',
  organization_id       BIGINT UNSIGNED NULL               COMMENT '親イベントから非正規化（組織スコープ時。team_id と XOR）',
  team_id               BIGINT UNSIGNED NULL               COMMENT '親イベントから非正規化（チームスコープ時。organization_id と XOR）',
  status                VARCHAR(20)     NOT NULL DEFAULT 'PENDING'
                        COMMENT 'PENDING / ACCEPTED / REJECTED / CANCELLED',
  reason                VARCHAR(500)                       COMMENT '委任理由（任意）',
  proxy_vote_session_id BIGINT UNSIGNED                    COMMENT 'F08.3 任意連携（クロスドメイン、FK なし）',
  proxy_delegation_id   BIGINT UNSIGNED                    COMMENT 'proxy_delegations.id（連携作成後に設定）',
  reviewed_at           DATETIME                           COMMENT '承認/拒否/取消日時',
  created_at            DATETIME        NOT NULL,
  updated_at            DATETIME        NOT NULL,
  -- アクティブ（PENDING/ACCEPTED）な委任のみ delegator_id を保持する生成カラム。
  -- REJECTED / CANCELLED では NULL になり、NULL は UNIQUE 制約の重複対象外のため再作成可能。
  active_delegator_marker BIGINT UNSIGNED
    AS (CASE WHEN status IN ('PENDING','ACCEPTED') THEN delegator_id END) STORED
    COMMENT 'アクティブ委任の一意性を DB 強制するための生成カラム',
  PRIMARY KEY (id),
  INDEX idx_event_deleg_event      (event_id),
  INDEX idx_event_deleg_delegator  (event_id, delegator_id),
  INDEX idx_event_deleg_delegate   (event_id, delegate_id),
  INDEX idx_event_deleg_status     (event_id, status),
  INDEX idx_event_deleg_pv_session (proxy_vote_session_id),
  INDEX idx_event_deleg_org        (organization_id),
  -- 「1 イベント × 1 委任者 につきアクティブ委任は 1 件」を DB レベルで強制。
  -- MySQL は部分ユニークインデックス非対応のため、生成カラム + UNIQUE で代替する。
  UNIQUE KEY uq_active_delegation (event_id, active_delegator_marker),
  CONSTRAINT fk_event_deleg_event
    FOREIGN KEY (event_id) REFERENCES events(id) ON DELETE RESTRICT
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci
  COMMENT='イベント代理出席';
```

**設計の注記**:
- `proxy_vote_session_id` / `proxy_delegation_id` はクロスドメイン参照（F08.3 ドメイン）のため FK なし
- `proxy_delegation_id`: F08.3 の `proxy_delegations.id` を格納。代理出席 ACCEPTED 時に自動作成した際に設定される
- `organization_id` / `team_id` は親イベントのスコープから**非正規化して保持**する（XOR：いずれか一方が NOT NULL）。
  将来の水平シャーディングでシャードキー（`organization_id`）の一貫性を保つため（CLAUDE.md 原則7）。
  `organization_id` を持つため、対応 Repository は `AbstractTenantAwareRepository` の継承を想定する。
- **アクティブ委任の一意性は DB 制約 + アプリ層チェックの二重で保証**する（§3.3 と同方式。生成カラム `active_delegator_marker` + `UNIQUE KEY uq_active_delegation`）。
  `REJECTED` / `CANCELLED` 遷移後はマーカーが NULL になり、NULL は重複可のため別の代理人で再作成できる。

### 3.5 event_checkins テーブル追加カラム (Flyway: 実装時採番)

> `delegation_id` 追加マイグレーションの番号は実装時に §9 の採番方針で確定する（固定番号は割り当てない）。
> なお `ticket_id` の NULL 化は本機能の対象外で、PR #1022 / V70.006 で先行実施済み（後述）。

```sql
ALTER TABLE event_checkins
  ADD COLUMN delegation_id BINARY(16)
    COMMENT '代理チェックイン時の event_delegations.id（通常チェックイン時は NULL）',
  ADD INDEX idx_ec_delegation (delegation_id);
```

**`checkin_type` の追加値**:

`CheckinType` の**既存値は `STAFF_SCAN` / `SELF` / `ROLL_CALL` / `ROLL_CALL_BATCH` の 4 つ**である
（`ROLL_CALL` / `ROLL_CALL_BATCH` は F03.12 ケア対象者見守り通知で追加済み）。
代理チェックイン専用 EP 経由の場合の値として、5 つ目に **`PROXY` を追加**する。

**`ticket_id` の NULL 許可（前提作業として PR #1022 / V70.006 で先行実施済み）**:

代理チェックインは（点呼チェックイン `ROLL_CALL` と同様に）チケットを介さず、`ticket_id = NULL` で記録する。
この前提となる `event_checkins.ticket_id` の NULL 許可は、**本設計とは別に PR #1022（マイグレーション `V70.006`、
2026-05-25 main マージ済）で先行実施済み**である（実装側 `EventCheckinEntity` / `EventRollCallService` が
既に `ticketId = null` を前提にしており、現状スキーマとコードの乖離を解消するための先行修正）。
そのため本設計の代理チェックイン（§5.7）はこれを前提とし、F03.10 では `ticket_id` の NULL 化マイグレーションを
新たに発行しない（採番は PR #1022 の `V70.006` を参照）。

PR #1022（V70.006）で適用された内容は以下のとおり（参考）:

```sql
-- V70.006__alter_event_checkins_ticket_id_nullable.sql （PR #1022 / main マージ済）
ALTER TABLE event_checkins
  MODIFY COLUMN ticket_id BIGINT UNSIGNED NULL
    COMMENT 'FK → event_tickets.id（点呼・代理チェックインなどチケットを介さない場合は NULL）';
```

- 既存の `UNIQUE KEY uq_event_checkins_ticket (ticket_id)` は維持されている。MySQL では UNIQUE キー上の NULL は
  重複可のため、`ticket_id = NULL` の点呼・代理レコードが複数あっても制約に抵触しない。
- 既存 FK `fk_event_checkins_ticket (ticket_id → event_tickets.id)` は `ON DELETE CASCADE` のまま維持
  （`ticket_id` が NULL の行は FK チェック対象外）。
- `PROXY` も CHECK 制約 `chk_event_checkins_ticket_by_type`（V70.008 で前方互換的に追加済み）のチケットレス側に含まれる。
  同制約は「チケット式（`STAFF_SCAN` / `SELF`）は `ticket_id` 必須」「チケットレス
  （`ROLL_CALL` / `ROLL_CALL_BATCH` / `PROXY`）は `ticket_id = NULL`」を DB レベルで強制するため、
  代理チェックイン行（`checkin_type = 'PROXY'`, `ticket_id = NULL`）は同制約を満たす。

**二重チェックイン防止（代理）**:

- 代理チェックインの重複は `delegation_id` で判定する。`delegation_id` が **NULL でない行に対する一意性**
  （= 同一 delegation で複数回チェックインしないこと）は、DDL の部分ユニーク制約が MySQL で表現しづらいため、
  **アプリ層 + 既存チェックで保証**する：チェックイン実行前に当該 `delegation_id` の `event_checkins` 行の
  存在を確認し、既に存在すれば **409 Conflict** を返す（§4.2 の代理チェックイン 409「既にチェックイン済み」と整合）。
- `idx_ec_delegation (delegation_id)` を存在チェックのインデックスとして利用する。

## §5 ビジネスロジック

### 5.1 代理指定フロー（スケジュール・イベント共通）

```
委任者が POST /delegations
  ↓
バリデーション（§5.6 参照）
  ↓
schedule_delegations / event_delegations レコード作成
  ↓
is_proxy_auto_accept = TRUE?
  ├── YES → status = ACCEPTED に設定
  │         委任者の出欠 → ABSENT に自動更新
  │         代理人の出欠 → ATTENDING に自動更新（スケジュールの場合）
  │         代理人に「代理出席に指定されました」通知（IN_APP + PUSH）
  └── NO  → status = PENDING に設定
            委任者の出欠 → ABSENT に自動更新
            代理人に「代理出席の依頼が届いています。承認または拒否してください」通知
```

### 5.2 代理承認・拒否フロー（is_proxy_auto_accept = FALSE の場合のみ）

```
代理人が PATCH /accept
  → status = ACCEPTED
  → 代理人の出欠 → ATTENDING に自動更新（スケジュールの場合）
  → 委任者に「代理が承認されました」通知（IN_APP）
  → proxy_vote_session_id が設定されている場合: §5.5 の連携処理を実行

代理人が PATCH /reject
  → status = REJECTED
  → 委任者に「代理が拒否されました。別の代理人を指定してください」通知（IN_APP + PUSH）
  → 委任者の出欠ステータスは ABSENT のまま（ユーザーが手動再設定）
  → REJECTED 後、委任者は再度 POST /delegations で別の代理人を指定可能
```

### 5.3 代理取り消しフロー

```
委任者が DELETE /delegations/me
  → status = CANCELLED
  → 代理人の schedule_attendances を巻き戻す（スケジュールの場合）:
      ・is_proxy_input = TRUE（= この代理関係が自動投入したレコード）のみ UNDECIDED に戻す
      ・is_proxy_input = FALSE（= 代理人が自分で出した出欠）は温存する
  → 代理人に「代理出席が取り消されました」通知（IN_APP）
  → CANCELLED 後は再度 POST /delegations が可能（別の代理人でも可）

委任者が自分の出欠回答を ATTENDING に更新した場合
  → PENDING 状態の代理: status = CANCELLED に自動更新
  → ACCEPTED 状態の代理: キャンセルしない（明示的な DELETE が必要）

スケジュール/イベントが CANCELLED または COMPLETED に遷移した場合
  → 全 PENDING/ACCEPTED 代理を CANCELLED に一括更新（イベント駆動で処理）
```

**`is_proxy_input` の活用（F14.1 連携）**:
代理関係で代理人の出欠を自動投入する際は `schedule_attendances.is_proxy_input = TRUE` をセットする。
これにより「代理関係が自動で立てた出欠」と「代理人が自分の意思で出した出欠」を区別でき、
取り消し時に後者を誤って消さずに済む（上記フロー参照）。
本人が自分で上書きした場合（`is_proxy_input = FALSE` に戻る）も同様に温存される。

### 5.4 出欠ステータス連動（スケジュールの場合）

| イベント | 委任者の schedule_attendances.status | 代理人の schedule_attendances.status |
|---------|--------------------------------------|--------------------------------------|
| 代理指定（auto_accept=TRUE） | ABSENT に更新 | ATTENDING に更新（`is_proxy_input = TRUE` をセット） |
| 代理指定（auto_accept=FALSE） | ABSENT に更新 | 変化なし（代理人の承認待ち） |
| 代理承認（PENDING → ACCEPTED） | 変化なし | ATTENDING に更新（`is_proxy_input = TRUE` をセット） |
| 代理拒否（PENDING → REJECTED） | 変化なし（ユーザーが手動更新） | 変化なし |
| 代理取り消し（→ CANCELLED） | 変化なし | `is_proxy_input = TRUE` の代理由来レコードのみ UNDECIDED に戻す（本人入力は温存） |

- 代理関係が代理人の出欠を自動投入する際は **`schedule_attendances.is_proxy_input = TRUE`** をセットし、
  代理由来のレコードであることを識別できるようにする（§5.3 / F14.1 参照）。
  代理人が自分で出した出欠（`is_proxy_input = FALSE`）は代理取り消し時も温存する。

**RSVP モード（イベント）の場合**: 同様に `event_rsvp_responses` に反映。

**REGISTRATION モード（イベント）の場合**: 代理人の `event_registrations` は自動作成しない（座席二重カウント防止）。代理チェックイン専用 EP（§5.7）で対応。

### 5.5 F08.3 投票代理との任意連携（イベント駆動）

CLAUDE.md 原則5（`@Transactional` はドメイン内に閉じる）に従い、event ドメインと proxyvote ドメインを
**同期トランザクションでまたがず、イベント駆動で分離**する。event ドメインは proxy_delegations を直接作らない。

```
event_delegations が ACCEPTED に確定（自動承認 or 代理人承認）
  ↓ ［event ドメイン・同一トランザクション内］
event ドメインが EventDelegationAcceptedEvent を発火
  （proxy_delegations はこの場では作らない）
  ↓ ［AFTER_COMMIT］
proxyvote ドメインの @TransactionalEventListener(phase = AFTER_COMMIT) が受信
  ↓ ［proxyvote ドメイン・別トランザクション］
proxyVoteSessionId が指定されている場合のみ連携処理:

  proxy_vote_sessions の検証（§5.6 #9〜#11 と整合）:
    - 同スコープ（team_id / organization_id）に存在するか確認 … 不一致なら連携スキップ（warning）
    - status = OPEN であること                              … OPEN 以外なら連携スキップ（warning）
    - is_anonymous = TRUE でないこと                        … 無記名なら連携スキップ（warning）
    - 代理人がそのセッションの投票資格（MEMBER+）を満たすこと … 満たさなければ連携スキップ（warning）
    - 委任者がそのセッションに既存の proxy_delegation を持たないこと … 持つ場合は連携スキップ（warning）
  ↓
  proxy_delegations テーブルに自動作成
    { session_id: proxyVoteSessionId, delegator_id, delegate_id, is_blank: FALSE, reason: '代理出席連携' }
  ↓
  proxy_vote_sessions.is_auto_accept_delegation = TRUE?
    ├── YES → proxy_delegations.status = ACCEPTED
    └── NO  → proxy_delegations.status = SUBMITTED（別途管理者による承認が必要）
  ↓
  event_delegations.proxy_delegation_id に作成した proxy_delegations.id を設定（別トランザクションの UPDATE）
```

**設計の注記**:
- event ドメインの ACCEPTED 確定時に `EventDelegationAcceptedEvent` を発火し、proxyvote ドメインの
  `@TransactionalEventListener(phase = AFTER_COMMIT)` が受けて proxy_delegations を作成する。
  これにより 2 ドメインをまたぐ同期トランザクションを避ける（CLAUDE.md 原則5）。
- proxy_delegations 作成後、`event_delegations.proxy_delegation_id` を別トランザクションで更新する。
- **`proxyVoteSessionId` の事前バリデーション**（代理指定 POST 時に同期チェックして 422 にできるもの）と、
  **連携時（ACCEPTED 後）の再検証**を区別する。
  - 代理指定 POST 時の 422 ＝ §5.6 #9〜#11（存在・スコープ・OPEN・無記名・投票資格）。
  - **委任者がそのセッションに既存の proxy_delegation を持つ場合**は、連携をスキップするが
    **エラーにはしない（代理出席自体は成立させる）**。warning として扱い、管理者・委任者に通知ログを残す。
    既存の投票委任を上書き・破壊しないための措置。

### 5.6 バリデーション仕様（代理指定時）

| # | 条件 | 違反時のレスポンス |
|---|------|--------------------|
| 1 | schedule/event の `allow_proxy_attendance = TRUE` であること | 422 Unprocessable Entity |
| 2 | 委任者はスコープ（チーム/組織）のメンバーであること | 403 Forbidden |
| 3 | 代理人はスコープのメンバーであること（外部ゲスト不可） | 422 Unprocessable Entity |
| 4 | 委任者 ≠ 代理人（自己代理不可） | 422 Unprocessable Entity |
| 5 | 委任者の PENDING/ACCEPTED 代理が既に存在しないこと | 409 Conflict |
| 6 | 代理人が他者の代理として PENDING/ACCEPTED 状態でないこと（連鎖代理禁止） | 422 Unprocessable Entity |
| 7 | スケジュール/イベントのステータスが CANCELLED/COMPLETED でないこと | 422 Unprocessable Entity |
| 8 | 繰り返しスケジュール: `parent_schedule_id` を持つ**親**スケジュールへの直接指定は不可 | 422 Unprocessable Entity |
| 9 | `proxyVoteSessionId` 指定時: セッションが同スコープに存在し `is_anonymous = FALSE` | 422 Unprocessable Entity |
| 10 | `proxyVoteSessionId` 指定時: セッションの `status = OPEN` であること（DRAFT/CLOSED/FINALIZED は不可） | 422 Unprocessable Entity |
| 11 | `proxyVoteSessionId` 指定時: **代理人**がそのセッションの投票資格（MEMBER+）を満たすこと | 422 Unprocessable Entity |
| 12 | `proxyVoteSessionId` 指定時: **委任者**がそのセッションに既存の `proxy_delegation` を**持たない**こと。持つ場合は **エラーにせず**、投票連携のみスキップ（warning 扱い）し、代理出席自体は成立させる | エラーなし（warning） |

### 5.7 イベント REGISTRATION モードでの代理チェックイン

- 代理人は `event_registrations` に自動追加しない（定員カウントの二重計上を防ぐ）
- 代理チェックイン専用エンドポイント: `POST /api/v1/events/{eventId}/delegations/{delegationId}/checkin`
  - 実行条件: delegation の `status = ACCEPTED` かつ `delegate_id = ログインユーザー`（または ADMIN / DEPUTY_ADMIN+`CHECKIN_EVENTS`）
  - `event_checkins` にレコード作成（`delegation_id` カラムに delegation の id を設定、`ticket_id = NULL`）
  - `checkin_type = PROXY`（既存 4 値 `STAFF_SCAN` / `SELF` / `ROLL_CALL` / `ROLL_CALL_BATCH` に 5 つ目として追加）
  - **二重チェックイン防止**: 同一 `delegation_id` の `event_checkins` 行が既に存在する場合は 409 Conflict（§3.5 / §4.2 と整合。アプリ層 + 既存チェックで保証）
- チェックイン名簿（roll-call 画面）での表示: 代理人名 + 「（{委任者名} の代理）」ラベル

### 5.8 代理人または委任者のスコープ退会時の自動処理

退会するのが代理人・委任者のいずれであっても、その人物が関与する `PENDING` / `ACCEPTED` 代理は成立し得ないため自動取消する。

**代理人が退会した場合**:
- 代理人がチームを退会した際の `MembershipChangedEvent` を捕捉
- 退会した代理人が `PENDING` / `ACCEPTED` 状態の代理（代理人として）があれば `CANCELLED` に更新
- 委任者に「代理人 {名前} がメンバーを退会しました。代理を再設定してください」通知（IN_APP + PUSH）

**委任者が退会した場合**:
- 委任者がチームを退会した際の `MembershipChangedEvent` を捕捉
- その委任者が委任した `PENDING` / `ACCEPTED` 状態の代理を `CANCELLED` に更新
- 代理人に「{委任者名} さんが退会したため代理出席は取り消されました」通知（IN_APP）

**共通**:
- 定期バッチ（日次）で孤立した代理（当事者がスコープ在籍確認不可）を補完的にチェックし、取りこぼしを `CANCELLED` にする

## §6 セキュリティ考慮事項

1. **IDOR 防止**: delegation リソースへのアクセスは当事者（委任者 or 代理人）または同スコープの ADMIN のみ。`delegationId` は UUIDv7 でランダム性あり（推測困難）
2. **権限昇格防止**: 代理出席はイベント出欠の代替のみ。代理人に管理権限は付与しない。代理チェックインできるのは代理対象のイベントのみ
3. **連鎖代理悪用防止**: §5.6 バリデーション 6 番で多段委任を禁止。代理の連鎖により 1 人が多数のイベントを制御することを防ぐ
4. **なりすまし防止**: `delegate_id` はスコープ内メンバーの存在確認を実施。不正な外部 `user_id` での代理指定を防止
5. **投票操作悪用防止**: F08.3 連携時は `proxy_vote_sessions.is_anonymous = TRUE` の場合に連携を拒否。無記名投票のプライバシーを保護。同スコープのセッションかどうかも確認
6. **レートリミット**: 代理指定エンドポイントは 1 分間に 10 回/ユーザーに制限（不正なメンバー ID を試行する攻撃への対策）
7. **委任理由のプライバシー**: `reason` には健康情報（急病・通院 等）など機微情報が入りうる。UI で「この理由は管理者に共有されます」旨を注記し、`reason` は**必須にしない**（任意入力）。一覧での `reason` 表示は **ADMIN のみ**に限定し、代理人・他メンバーには表示しない

## §7 フロントエンド対応

### 7.1 スケジュール/イベント作成フォームへの追加項目

- `allow_proxy_attendance` トグル（デフォルト OFF）
- `is_proxy_auto_accept` トグル（`allow_proxy_attendance = TRUE` の場合のみ表示、デフォルト OFF）
- 両設定は PATCH API で後から変更可能

**`allow_proxy_attendance` を後から OFF にした場合の挙動**:
既存の `PENDING` / `ACCEPTED` 代理は**維持する（グランドファザリング）**し、**新規の代理指定のみブロック**する。
（既成の代理関係を一方的に無効化すると、既に代理出席を前提に予定を組んでいる現場が混乱するため。）

### 7.2 出欠回答フォームへの追加

- `allow_proxy_attendance = TRUE` かつユーザーが `ABSENT` または `UNDECIDED` を選択した場合のみ表示
- 「代理人を指定する（任意）」チェックボックス
- チェック ON: メンバー検索コンポーネント（既存 `/api/v1/teams/{id}/members` 再利用）
- 理由テキストフィールド（任意、最大 500 文字）
- イベントの場合のみ: 同スコープの投票セッションがあれば「投票も代理委任する」チェックボックス + セッション選択

## §8.1 実装メモ（第二陣 Service 層 / 2026-05-26）

§5 ビジネスロジック・§6 セキュリティ・§8 通知の Service 層実装は以下のクラス構成で行った（Controller/DTO/FE は別陣）。

| 役割 | クラス | 備考 |
|---|---|---|
| スケジュール代理 Service | `schedule.service.ScheduleDelegationService` | §5.1-5.4 / 出欠連動（同一トランザクション・原則5）|
| スケジュール代理 バリデータ | `schedule.service.ScheduleDelegationValidator` | §5.6 #1-#8 |
| スケジュール代理 通知イベント | `schedule.event.ScheduleDelegationNotificationEvent` | §8 の 7 トリガーを `Kind` で表す。業務TX内は publish のみ（Issue #2990）|
| スケジュール代理 通知配送 | `schedule.service.ScheduleDelegationNotifier` | §8 5 トリガー + 退会連動。`@TransactionalEventListener(AFTER_COMMIT)` + `@Async("event-pool")` + `NotificationDeliveryRunner#sendOne`（1件ごと REQUIRES_NEW・原則5）|
| イベント代理 Service | `event.service.EventDelegationService` | §5.4 RSVP 連動 / §5.7 代理チェックイン |
| イベント代理 バリデータ | `event.service.EventDelegationValidator` | §5.6 #1-#11（#9-#11 は proxyvote へ委譲）|
| イベント代理 通知 | `event.service.EventDelegationNotifier` | §8 |
| F08.3 連携イベント | `event.event.EventDelegationAcceptedEvent` | ACCEPTED 確定で発火（proxy_delegations は作らない）|
| F08.3 連携リスナー | `proxyvote.listener.EventDelegationAcceptedListener` | `@TransactionalEventListener(AFTER_COMMIT)` + `REQUIRES_NEW`（§5.5・原則5）|
| F08.3 連携作成 | `proxyvote.service.ProxyDelegationService#createFromEventDelegation` / `#isSessionEligibleForEventDelegation` | proxy_delegations 作成 / POST 時事前検証 |
| 退会連動リスナー | `schedule.listener.ScheduleDelegationMembershipListener` / `event.listener.EventDelegationMembershipListener` | `MembershipEndedEvent`（`MembershipService.leave` で発火確認済）受信（§5.8）|
| 補完バッチ | `schedule.batch.ProxyDelegationCleanupBatchService` | 日次 03:40 JST・`@SchedulerLock`・孤立委任クリーンアップ（§5.8）|

**設計上の補足**:
- §5.4 の「代理由来レコード識別」は `schedule_attendances.is_proxy_input = TRUE` のみで判定する（`proxy_input_record_id` は F14.1 用の BIGINT FK であり UUID の委任 ID は格納できないため、本機能では使用しない）。取消時は `is_proxy_input = TRUE` の代理人出欠のみ UNDECIDED に巻き戻し、本人入力（FALSE）は温存する。
- §8 の通知は業務トランザクションの内側では発火しない（Issue #2990 / 原則5）。`ScheduleDelegationService` は `ScheduleDelegationNotificationEvent` を publish するに留め、`ScheduleDelegationNotifier` が `AFTER_COMMIT` 後に非同期配送する。是正前は通知の DB 例外が業務トランザクションに rollback-only を残し、代理の指定・承認・拒否・取消（および日次バッチの孤立委任 CANCELLED 化、出欠回答に伴う PENDING 代理の自動取消）ごと巻き戻っていた。この是正に伴い、承認 / 取消 / 委任者退会の 3 種も Push・WebSocket で配信されるようになった（是正前は IN_APP のみ。金型に寄せた結果として意図的に受け入れた挙動変更）。
- §5.8 退会連動は `MembershipEndedEvent` リスナーを主機構とする（発火を確認済）。日次バッチはイベント取りこぼし（古いデータ・直接 DB 操作）の補完。
- §5.5 F08.3 連携の POST 時事前検証（#9-#11）は read-only クロスドメイン呼び出しとして event → proxyvote Service へ委譲し、proxy_delegations の作成自体は AFTER_COMMIT のイベント駆動で別トランザクション化（原則5 厳守）。

本改訂時点（2026-05-26）の最新マイグレーション: **V70.008**（`event_checkins.ticket_id` の CHECK 制約 / PR #1056 main マージ済）

> **前提作業**: `event_checkins.ticket_id` の NULL 許可は、本設計の代理チェックイン（§5.7）の前提として

目安として V70.009〜V70.013 が空いているが、**実装時に必ず再確認する**こと（番号は他の並行 PR がマージされた瞬間に埋まる。`feedback_migration_version_collision` の教訓 = 番号はマージ時に確定する）。
下表のファイル名は番号部分をプレースホルダ `V70.xxx__` で表記する。

| ファイル名（番号は実装時採番） | 内容 |
