# F03.10 代理出席

- **バージョン**: 1.0
- **ステータス**: 完了
- **最終更新**: 2026-05-25
- **関連機能**: F03.1, F03.8, F08.3

---

## §1 概要

会議やイベントに出席できないメンバーが、代わりの人（代理人）を指定して代わりに出席させる機能。

**主要機能**:
- **代理指定**: 委任者が代理人を明示的に指名してスケジュール/イベントへの出席を委託
- **承認フロー**: 「自動承認（代理人の確認不要）」と「代理人の明示的な同意が必要」の 2 パターン
- **出欠ステータス連動**: 代理指定・承認・拒否・取り消しに応じて委任者/代理人の出欠ステータスを自動更新
- **F08.3 連携**: イベント代理出席と議決権委任（proxy_delegations）を任意でセットで委任可能
- **代理チェックイン**: REGISTRATION モードのイベントで代理人が委任者の代わりにチェックイン

**対象**:
- スケジュール出欠（F03.1）: `schedule_delegations` テーブルで管理
- イベント参加登録（F03.8）: `event_delegations` テーブルで管理

## §2 スコープ・前提条件

### 対象ロール
| ロール | 操作可能な範囲 |
|--------|--------------|
| ADMIN | 代理一覧閲覧・管理（全件）。代理チェックイン実行 |
| DEPUTY_ADMIN | `CHECKIN_EVENTS` 権限を持つ場合: 代理チェックイン実行 |
| MEMBER | 代理指定（委任者として）・代理承認/拒否（代理人として）・自分の代理状況確認 |
| SUPPORTER | 対象外 |
| GUEST | 対象外 |

### 対象レベル
- [x] 組織 (Organization)
- [x] チーム (Team)
- [ ] 個人 (Personal)

### 前提条件・制約
- `allow_proxy_attendance = TRUE` のスケジュール/イベントのみ機能が有効
- 外部ゲスト（`guest_email` での登録者）は代理人になれない（`user_id` 必須）
- **連鎖代理禁止**: B が C の代理として `PENDING` / `ACCEPTED` 状態にある場合、B を別の委任者の代理に指定不可
- **繰り返しスケジュール**: 親スケジュール（`parent_schedule_id IS NULL` かつ `recurrence_rule IS NOT NULL`）への一括代理指定は v1 不可。各子スケジュールに個別指定

### 3.3 schedule_delegations テーブル (Flyway V70.003)

スケジュールに対する代理出席委任状を管理するテーブル。

```sql
CREATE TABLE schedule_delegations (
  id              BINARY(16)      NOT NULL                 COMMENT 'UUIDv7 主キー',
  schedule_id     BIGINT UNSIGNED NOT NULL                 COMMENT 'FK → schedules.id',
  delegator_id    BIGINT UNSIGNED NOT NULL                 COMMENT '委任者 user_id（クロスドメイン、FK なし）',
  delegate_id     BIGINT UNSIGNED NOT NULL                 COMMENT '代理人 user_id（クロスドメイン、FK なし）',
  status          VARCHAR(20)     NOT NULL DEFAULT 'PENDING'
                  COMMENT 'PENDING / ACCEPTED / REJECTED / CANCELLED',
  reason          VARCHAR(500)                             COMMENT '委任理由（任意）',
  reviewed_at     DATETIME                                 COMMENT '承認/拒否/取消日時',
  created_at      DATETIME        NOT NULL,
  updated_at      DATETIME        NOT NULL,
  PRIMARY KEY (id),
  INDEX idx_sched_deleg_schedule  (schedule_id),
  INDEX idx_sched_deleg_delegator (schedule_id, delegator_id),
  INDEX idx_sched_deleg_delegate  (schedule_id, delegate_id),
  INDEX idx_sched_deleg_status    (schedule_id, status),
  CONSTRAINT fk_sched_deleg_schedule
    FOREIGN KEY (schedule_id) REFERENCES schedules(id) ON DELETE RESTRICT
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci
  COMMENT='スケジュール代理出席';
```

**設計の注記**:
- UUIDv7 主キー（CLAUDE.md 原則6: 新規テーブルは `UuidV7Entity` 継承）
- `delegator_id` / `delegate_id` はクロスドメイン参照のため FK なし、インデックスのみ（原則1）
- ステータス別ユニーク性はアプリ層で保証（`PENDING` / `ACCEPTED` は 1 件のみ、`REJECTED` / `CANCELLED` 後は再作成可）

**ステータス一覧**:
| ステータス | 説明 |
|-----------|------|
| `PENDING` | 代理人の承認待ち（`is_proxy_auto_accept = FALSE` の場合のみ） |
| `ACCEPTED` | 代理確定（自動承認または代理人が承認） |
| `REJECTED` | 代理人が拒否した |
| `CANCELLED` | 委任者またはシステムが取り消した |

### 3.4 event_delegations テーブル (Flyway V70.004)

イベントに対する代理出席委任状を管理するテーブル。F08.3 投票代理との任意連携カラムを含む。

```sql
CREATE TABLE event_delegations (
  id                    BINARY(16)      NOT NULL           COMMENT 'UUIDv7 主キー',
  event_id              BIGINT UNSIGNED NOT NULL           COMMENT 'FK → events.id',
  delegator_id          BIGINT UNSIGNED NOT NULL           COMMENT '委任者 user_id（クロスドメイン、FK なし）',
  delegate_id           BIGINT UNSIGNED NOT NULL           COMMENT '代理人 user_id（クロスドメイン、FK なし）',
  status                VARCHAR(20)     NOT NULL DEFAULT 'PENDING'
                        COMMENT 'PENDING / ACCEPTED / REJECTED / CANCELLED',
  reason                VARCHAR(500)                       COMMENT '委任理由（任意）',
  proxy_vote_session_id BIGINT UNSIGNED                    COMMENT 'F08.3 任意連携（クロスドメイン、FK なし）',
  proxy_delegation_id   BIGINT UNSIGNED                    COMMENT 'proxy_delegations.id（連携作成後に設定）',
  reviewed_at           DATETIME                           COMMENT '承認/拒否/取消日時',
  created_at            DATETIME        NOT NULL,
  updated_at            DATETIME        NOT NULL,
  PRIMARY KEY (id),
  INDEX idx_event_deleg_event      (event_id),
  INDEX idx_event_deleg_delegator  (event_id, delegator_id),
  INDEX idx_event_deleg_delegate   (event_id, delegate_id),
  INDEX idx_event_deleg_status     (event_id, status),
  INDEX idx_event_deleg_pv_session (proxy_vote_session_id),
  CONSTRAINT fk_event_deleg_event
    FOREIGN KEY (event_id) REFERENCES events(id) ON DELETE RESTRICT
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci
  COMMENT='イベント代理出席';
```

**設計の注記**:
- `proxy_vote_session_id` / `proxy_delegation_id` はクロスドメイン参照（F08.3 ドメイン）のため FK なし
- `proxy_delegation_id`: F08.3 の `proxy_delegations.id` を格納。代理出席 ACCEPTED 時に自動作成した際に設定される

## §5 ビジネスロジック

### 5.1 代理指定フロー（スケジュール・イベント共通）

```
委任者が POST /delegations
  ↓
バリデーション（§5.6 参照）
  ↓
schedule_delegations / event_delegations レコード作成
  ↓
is_proxy_auto_accept = TRUE?
  ├── YES → status = ACCEPTED に設定
  │         委任者の出欠 → ABSENT に自動更新
  │         代理人の出欠 → ATTENDING に自動更新（スケジュールの場合）
  │         代理人に「代理出席に指定されました」通知（IN_APP + PUSH）
  └── NO  → status = PENDING に設定
            委任者の出欠 → ABSENT に自動更新
            代理人に「代理出席の依頼が届いています。承認または拒否してください」通知
```

### 5.2 代理承認・拒否フロー（is_proxy_auto_accept = FALSE の場合のみ）

```
代理人が PATCH /accept
  → status = ACCEPTED
  → 代理人の出欠 → ATTENDING に自動更新（スケジュールの場合）
  → 委任者に「代理が承認されました」通知（IN_APP）
  → proxy_vote_session_id が設定されている場合: §5.5 の連携処理を実行

代理人が PATCH /reject
  → status = REJECTED
  → 委任者に「代理が拒否されました。別の代理人を指定してください」通知（IN_APP + PUSH）
  → 委任者の出欠ステータスは ABSENT のまま（ユーザーが手動再設定）
  → REJECTED 後、委任者は再度 POST /delegations で別の代理人を指定可能
```

### 5.3 代理取り消しフロー

```
委任者が DELETE /delegations/me
  → status = CANCELLED
  → 代理人の schedule_attendances.status → UNDECIDED に戻す（スケジュールの場合）
  → 代理人に「代理出席が取り消されました」通知（IN_APP）
  → CANCELLED 後は再度 POST /delegations が可能（別の代理人でも可）

委任者が自分の出欠回答を ATTENDING に更新した場合
  → PENDING 状態の代理: status = CANCELLED に自動更新
  → ACCEPTED 状態の代理: キャンセルしない（明示的な DELETE が必要）

スケジュール/イベントが CANCELLED または COMPLETED に遷移した場合
  → 全 PENDING/ACCEPTED 代理を CANCELLED に一括更新（イベント駆動で処理）
```

### 5.4 出欠ステータス連動（スケジュールの場合）

| イベント | 委任者の schedule_attendances.status | 代理人の schedule_attendances.status |
|---------|--------------------------------------|--------------------------------------|
| 代理指定（auto_accept=TRUE） | ABSENT に更新 | ATTENDING に更新 |
| 代理指定（auto_accept=FALSE） | ABSENT に更新 | 変化なし（代理人の承認待ち） |
| 代理承認（PENDING → ACCEPTED） | 変化なし | ATTENDING に更新 |
| 代理拒否（PENDING → REJECTED） | 変化なし（ユーザーが手動更新） | 変化なし |
| 代理取り消し（→ CANCELLED） | 変化なし | UNDECIDED に戻す |

**RSVP モード（イベント）の場合**: 同様に `event_rsvp_responses` に反映。

**REGISTRATION モード（イベント）の場合**: 代理人の `event_registrations` は自動作成しない（座席二重カウント防止）。代理チェックイン専用 EP（§5.7）で対応。

### 5.5 F08.3 投票代理との任意連携

```
event_delegations 作成時に proxyVoteSessionId を指定した場合:

  ACCEPTED 時（自動 or 代理人承認）
    ↓
  proxy_vote_sessions の存在確認
    - 同スコープ（team_id / organization_id）に存在するか確認
    - is_anonymous = TRUE の場合: 422 エラー返却（無記名セッションは委任不可）
    ↓
  proxy_delegations テーブルに自動作成
    { session_id: proxyVoteSessionId, delegator_id, delegate_id, is_blank: FALSE, reason: '代理出席連携' }
    ↓
  proxy_vote_sessions.is_auto_accept_delegation = TRUE?
    ├── YES → proxy_delegations.status = ACCEPTED
    └── NO  → proxy_delegations.status = SUBMITTED（別途管理者による承認が必要）
    ↓
  event_delegations.proxy_delegation_id に作成した proxy_delegations.id を設定
```

### 5.6 バリデーション仕様（代理指定時）

| # | 条件 | 違反時のレスポンス |
|---|------|--------------------|
| 1 | schedule/event の `allow_proxy_attendance = TRUE` であること | 422 Unprocessable Entity |
| 2 | 委任者はスコープ（チーム/組織）のメンバーであること | 403 Forbidden |
| 3 | 代理人はスコープのメンバーであること（外部ゲスト不可） | 422 Unprocessable Entity |
| 4 | 委任者 ≠ 代理人（自己代理不可） | 422 Unprocessable Entity |
| 5 | 委任者の PENDING/ACCEPTED 代理が既に存在しないこと | 409 Conflict |
| 6 | 代理人が他者の代理として PENDING/ACCEPTED 状態でないこと（連鎖代理禁止） | 422 Unprocessable Entity |
| 7 | スケジュール/イベントのステータスが CANCELLED/COMPLETED でないこと | 422 Unprocessable Entity |
| 8 | 繰り返しスケジュール: `parent_schedule_id` を持つ**親**スケジュールへの直接指定は不可 | 422 Unprocessable Entity |
| 9 | `proxyVoteSessionId` 指定時: セッションが同スコープに存在し `is_anonymous = FALSE` | 422 Unprocessable Entity |

### 5.7 イベント REGISTRATION モードでの代理チェックイン

- 代理人は `event_registrations` に自動追加しない（定員カウントの二重計上を防ぐ）
- 代理チェックイン専用エンドポイント: `POST /api/v1/events/{eventId}/delegations/{delegationId}/checkin`
  - 実行条件: delegation の `status = ACCEPTED` かつ `delegate_id = ログインユーザー`（または ADMIN / DEPUTY_ADMIN+`CHECKIN_EVENTS`）
  - `event_checkins` にレコード作成（`delegation_id` カラムに delegation の id を設定）
  - `checkin_type = PROXY`（既存 `STAFF_SCAN` / `SELF` に追加）
- チェックイン名簿（roll-call 画面）での表示: 代理人名 + 「（{委任者名} の代理）」ラベル

### 5.8 代理人のスコープ退会時の自動処理

- 代理人がチームを退会した際の `MembershipChangedEvent` を捕捉
- 退会した代理人が `PENDING` / `ACCEPTED` 状態の代理があれば `CANCELLED` に更新
- 委任者に「代理人 {名前} がメンバーを退会しました。代理を再設定してください」通知（IN_APP + PUSH）
- 定期バッチ（日次）で孤立した代理（代理人がスコープ在籍確認不可）を補完的にチェック

## §6 セキュリティ考慮事項

1. **IDOR 防止**: delegation リソースへのアクセスは当事者（委任者 or 代理人）または同スコープの ADMIN のみ。`delegationId` は UUIDv7 でランダム性あり（推測困難）
2. **権限昇格防止**: 代理出席はイベント出欠の代替のみ。代理人に管理権限は付与しない。代理チェックインできるのは代理対象のイベントのみ
3. **連鎖代理悪用防止**: §5.6 バリデーション 6 番で多段委任を禁止。代理の連鎖により 1 人が多数のイベントを制御することを防ぐ
4. **なりすまし防止**: `delegate_id` はスコープ内メンバーの存在確認を実施。不正な外部 `user_id` での代理指定を防止
5. **投票操作悪用防止**: F08.3 連携時は `proxy_vote_sessions.is_anonymous = TRUE` の場合に連携を拒否。無記名投票のプライバシーを保護。同スコープのセッションかどうかも確認
6. **レートリミット**: 代理指定エンドポイントは 1 分間に 10 回/ユーザーに制限（不正なメンバー ID を試行する攻撃への対策）

## §8 通知設計

| トリガーイベント | 通知受信者 | 通知種別 | 通知本文（概要） |
|----------------|-----------|---------|----------------|
| 代理指定（is_proxy_auto_accept=FALSE → PENDING） | 代理人 | IN_APP + PUSH | 「{委任者名}さんから代理出席の依頼が届いています。承認または拒否してください。」 |

| 代理拒否（PENDING → REJECTED） | 委任者 | IN_APP + PUSH | 「{代理人名}さんが代理出席を拒否しました。別の代理人を指定してください。」 |
