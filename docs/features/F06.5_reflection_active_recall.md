## 0. 用語と前提

| 用語 | 定義 |
|---|---|
| **メインテーマ（reflection theme）** | 日々の振り返りを束ねる軽量な「器」。例: 「数学II」「○○プロジェクト」「日記」。cms ブログには載せず、公開したい時だけブログへ輸出する。既定 PRIVATE |
| **振り返り（reflection entry）** | テーマに紐づく日々の記録。アウトライン構造（メインテーマ/中見出し/小見出し/詳細/補足）の structured_content を持つ |
| **想起テスト（recall）** | 過去の振り返りをマスク（本文非表示）し、思い出して書き起こし、開示して照合する復習 |
| **間隔反復リマインダー（spaced reminder）** | 1・3・7・14 日後の固定間隔、および定期考査の 14/7/3/1 日前に送る通知 |

本機能は **reflection ドメインを新設**する（パッケージ `com.mannschaft.app.reflection`）。学生は授業ごとの振り返り、社会人は仕事の振り返り、誰でも日記として利用できる汎用機能である。

## 2. データモデル・DDL 案

### 2.0 共通方針（CLAUDE.md アーキテクチャ原則の遵守）

- **全テーブル UuidV7 主キー**（`BINARY(16)`）。Entity は `UuidV7Entity` を継承（原則 6）。
- **クロスドメイン FK 禁止**（原則 1）。`user_id`・`linked_slot_id`・`exported_blog_post_id` 等の他ドメイン参照は ID 列＋INDEX のみ。FK 制約を張らない。
- **CASCADE は同一 reflection ドメイン内のみ許可**（原則 2）。`reflection_entries.theme_id` → `reflection_themes.id`、`recall_attempts.entry_id` → `reflection_entries.id` は同一ドメインのため FK＋`ON DELETE CASCADE` 可。`reflection_spaced_reminders.entry_id` はバッチ走査性能と孤児許容のため **ID 参照（FK なし）**とする（理由は §2.5）。
- **論理削除**: theme / entry は `deleted_at` を持つ。recall_attempts / spaced_reminders は履歴・運用テーブルのため物理保持（soft delete なし）。
- **テナント**: 本機能は **個人所有（user_id）**が主であり organization_id を持たない。よって `AbstractTenantAwareRepository` は適用しない（リポジトリは `JpaRepository<T, UUID>` を継承）。組織配信は本機能のスコープ外。
- `created_at` / `updated_at` / `deleted_at` は既存 UUIDv7 テーブル（例: `incident_banners` V94）と同じく DDL に明示列で定義する。
- **可視性（MVP 確定）**: theme / entry の `visibility` は既定 `PRIVATE`、**MVP は PRIVATE 固定（CHECK で強制）**。FAMILY_SHARED（保護者による学習内容の確認）は重い設計判断を伴うため別軍議へ切り出す（§9.1）。

> **Flyway 番号は仮（プレースホルダ V900 系）**。`docs/openapi.json` や origin/main の最大 major は現状 **V119**（2026-06-20 時点）。**マージ直前に `git ls-tree origin/main backend/src/main/resources/db/migration` で最大 major を再確認し、`最大 major + 1`（並行 PR があればさらに +1）へリネームすること**（feedback_flyway_version_sort_after_global_max / feedback_migration_version_collision）。

### 2.1 `reflection_themes`（メインテーマ）

仮ファイル名: `V900.0001__create_reflection_themes.sql`

```sql
CREATE TABLE reflection_themes (
    id                   BINARY(16)   NOT NULL,
    user_id              BIGINT       NOT NULL,                      -- 所有者（users ドメイン・FK なし）
    title                VARCHAR(120) NOT NULL,
    description          VARCHAR(500) NULL,
    source_type          VARCHAR(20)  NOT NULL DEFAULT 'FREE',      -- SUBJECT/PROJECT/DIARY/FREE
    linked_slot_kind     VARCHAR(10)  NULL,                          -- TEAM/PERSONAL/NULL（時間割スロット種別）
    linked_slot_id       BIGINT       NULL,                          -- 時間割スロットID（timetable ドメイン・FK なし・論理参照）
    exam_date            DATE         NULL,                          -- 定期考査日（総まとめリマインド基準・NULL 可）
    visibility           VARCHAR(20)  NOT NULL DEFAULT 'PRIVATE',    -- MVPはPRIVATE固定（FAMILY_SHAREDは別軍議・§6.1/§9.1）
    recall_interval_days VARCHAR(50)  NOT NULL DEFAULT '1,3,7,14',   -- 想起間隔（昇順 CSV・§2.6 設計）
    created_at           DATETIME     NOT NULL,
    updated_at           DATETIME     NOT NULL,
    deleted_at           DATETIME     NULL,
    PRIMARY KEY (id),
    CONSTRAINT chk_reflection_themes_source_type
        CHECK (source_type IN ('SUBJECT','PROJECT','DIARY','FREE')),
    CONSTRAINT chk_reflection_themes_linked_slot_kind
        CHECK (linked_slot_kind IS NULL OR linked_slot_kind IN ('TEAM','PERSONAL')),
    CONSTRAINT chk_reflection_themes_visibility
        CHECK (visibility = 'PRIVATE'),  -- MVP。FAMILY_SHARED追加は別軍議で旧CHECK DROP→新CHECKのmigration
    INDEX idx_reflection_themes_user (user_id, deleted_at),
    INDEX idx_reflection_themes_user_slot (user_id, linked_slot_kind, linked_slot_id),
    INDEX idx_reflection_themes_exam (exam_date)
);
```

設計注記:
- `linked_slot_kind`/`linked_slot_id` は F03.15 と同じ表現（`TimetableSlotKind` ENUM 値・`BIGINT` 論理参照）。リンク先スロットが削除されても孤児として保持（FK なし）。
- `exam_date` は theme 単位の「次回の定期考査日」。複数考査を扱う将来拡張は別テーブル化候補（本 MVP は単一日）。

### 2.2 `reflection_entries`（日々の振り返り）

仮ファイル名: `V900.0002__create_reflection_entries.sql`

```sql
CREATE TABLE reflection_entries (
    id                  BINARY(16)   NOT NULL,
    theme_id            BINARY(16)   NOT NULL,                       -- 同一ドメイン FK 可
    user_id             BIGINT       NOT NULL,                       -- 所有者非正規化（高速絞り込み・FK なし）
    target_date         DATE         NOT NULL,                       -- 振り返り対象日
    structured_content  JSON         NOT NULL,                       -- アウトライン構造（§2.3）
    visibility          VARCHAR(20)  NOT NULL DEFAULT 'PRIVATE',     -- MVPはPRIVATE固定（§6.1/§9.1）
    version             BIGINT       NOT NULL DEFAULT 0,             -- 楽観ロック（@Version・AC-18）
    exported_blog_post_id BIGINT     NULL,                           -- 輸出先ブログ記事ID（cmsドメイン・FKなし・再輸出防止/輸出済表示・AC-20）
    created_at          DATETIME     NOT NULL,
    updated_at          DATETIME     NOT NULL,
    deleted_at          DATETIME     NULL,
    PRIMARY KEY (id),
    CONSTRAINT fk_reflection_entries_theme
        FOREIGN KEY (theme_id) REFERENCES reflection_themes(id) ON DELETE CASCADE,  -- 同一ドメイン
    CONSTRAINT chk_reflection_entries_visibility
        CHECK (visibility = 'PRIVATE'),  -- MVP。別軍議でFAMILY_SHARED追加
    CONSTRAINT uq_reflection_entries_theme_date
        UNIQUE (theme_id, target_date),                             -- (theme,target_date) 一意（AC-4）
    INDEX idx_reflection_entries_user_date (user_id, target_date),
    INDEX idx_reflection_entries_theme (theme_id, target_date)
);
```

設計注記:
- `(theme_id, target_date)` 一意制約で「1 テーマ×1 日＝1 エントリ」を保証。同日再保存は **upsert**（既存があれば UPDATE）（AC-4）。
- `deleted_at` がある行も UNIQUE に効く点に注意。論理削除済みエントリと同日同テーマで再作成する場合は、サービス層で「deleted 行を物理削除 or 復活更新」する（実装方針: 復活更新＝`deleted_at=NULL` にして上書き。一意制約衝突を避ける）。
- **復活時のリマインダー再生成（確定）**: 論理削除エントリを復活更新（`deleted_at=NULL`＋本文上書き）する際、古い `recall_attempts`／`reflection_spaced_reminders` は旧 original 基準のまま残っている。復活時はサービス層で **当該エントリ由来の PENDING リマインダーを全て CANCELLED に遷移させ、新しい本文・新しい target_date 基準で SPACED 行を再生成**する（旧予定の誤発火・旧 recall を基準にしたマスク判定の混線を防ぐ）。`recall_attempts` 履歴自体は保持するが、マスク判定（§3.1）は復活後の新 target_date を基準にやり直される。
- `user_id` は `theme.user_id` の非正規化コピー。`GET /reflections/today` 等のユーザー横断クエリを 1 SELECT で引くため。
- **【実装者向け警告】`@Builder(toBuilder=true)` + `UuidV7Entity` の id 欠落再発パターン**: `UuidV7Entity` を継承した Entity で `entity.toBuilder().build()` を更新に使うと、継承フィールドの `id` が build で落ちて id=null となり、JPA が UPDATE ではなく **INSERT** を発行してしまう（一意制約違反で 500、または制約が無い列では行重複）。これは本リポジトリで複数回再発した既知バグ（toBuilder 更新破壊キャンペーン）。**更新は managed entity を直接ミューテートすること**（`TimetableChangeEntity.applyUpdate(...)`（L81-98）/ `IncidentBannerEntity.update(...)`（L136-143）が手本＝null=現値維持セマンティクスで各フィールドを個別更新）。reflection の entry/theme 更新も `applyUpdate` 相当の直接ミューテートメソッドで実装する。version 楽観排他（@Version）と併せ、toBuilder は使わない。

### 2.3 `structured_content` JSON スキーマ

アウトラインは固定 5 階層（メインテーマ → 中見出し → 小見出し → 詳細 → 補足）。F06.4 の `field_values` 自由 JSON ではなく、**スキーマ固定**にする（想起テストでマスク対象を機械的に決めるため）。

```json
{
  "main_theme": "二次関数の最大最小",
  "sections": [
    {
      "heading": "平方完成",
      "subsections": [
        {
          "sub_heading": "基本形への変形",
          "detail": "y = a(x-p)^2 + q に変形し頂点 (p,q) を読む",
          "supplement": "a>0 で下に凸・最小値 q"
        }
      ]
    }
  ],
  "free_note": "授業後の所感や質問メモ（マスク対象外の任意欄）"
}
```

- `main_theme`（string, 必須）/ `sections`（配列）/ 各 section に `heading` + `subsections[]`、各 subsection に `sub_heading` / `detail` / `supplement`。
- `free_note` は**マスク対象外**（想起の手がかりやメタ所感を残す欄）。マスク対象は `main_theme` と `sections` 全体。
- バリデーション（確定）: JSON サイズ上限 **64KB**、`sections` 最大 **30**、各 `subsections` 最大 **30**、`main_theme`/`heading`/`sub_heading` 各 200 字、`detail`/`supplement` 各 2,000 字、`free_note` 10,000 字。サニタイズは**サービス層の専用 `ReflectionContentSanitizer`**（`<script>`・`on*` 属性・`javascript:` 除去）で保存前に正規化し、表示は出力時エスケープ（F06.1/F06.4 と同方針・XSS 二重防御）。

### 2.3.1 テンプレート（入力補助プリセット）

御要望「ノーマル／日記／仕事の振り返り／授業の振り返り」を、**`source_type` 別の入力補助プリセット**として実現する（**新テーブルを作らず** structured_content は固定 5 階層のまま）。テンプレートは「初期見出し・プレースホルダ・推奨記入欄」の違いに過ぎないため、**フロントの静的プリセット定義 + i18n** で持つ（保守性: BE スキーマを汚さず、F01.3/F06.4 のテンプレ概念と乱立させない）。

| テンプレ | source_type | 初期 main_theme / 見出しプリセット例 |
|---|---|---|
| ノーマル | FREE | 見出しなし・自由。`main_theme` のみ必須 |
| 日記 | DIARY | main_theme=「今日のできごと」、section: 出来事／感じたこと／明日に向けて |
| 仕事の振り返り | PROJECT | main_theme=案件名、section: 成果／課題／学び／次アクション（KPT 風） |
| 授業の振り返り | SUBJECT | main_theme=単元名、section: 学んだこと／つまずき／覚える要点（想起対象） |

- プリセットは `frontend/app/constants/reflectionTemplates.ts`（静的）＋ロケール 6 言語（i18n ルール遵守・直書き禁止）。テーマ作成時に選択し、エントリ作成画面の初期 structured_content を組み立てる。
- BE はテンプレートを関知しない（structured_content を受け取るのみ）。これにより入力補助の御要望を満たしつつ、テンプレ概念の乱立を回避する。

### 2.4 `recall_attempts`（想起テスト記録）

仮ファイル名: `V900.0003__create_recall_attempts.sql`

```sql
CREATE TABLE recall_attempts (
    id                BINARY(16)  NOT NULL,
    entry_id          BINARY(16)  NOT NULL,                         -- 同一ドメイン FK 可
    user_id           BIGINT      NOT NULL,                         -- 所有者非正規化（FK なし）
    recall_date       DATE        NOT NULL,                         -- 想起を行った日
    recalled_content  JSON        NOT NULL,                         -- 思い出して書いた内容（structured_content と同形 or 自由テキスト）
    self_rating       VARCHAR(12) NOT NULL,                         -- REMEMBERED/PARTIAL/FORGOT
    revealed_at       DATETIME    NULL,                             -- 開示時刻（保存＝開示で記録・AC-7）
    created_at        DATETIME    NOT NULL,
    PRIMARY KEY (id),
    CONSTRAINT fk_recall_attempts_entry
        FOREIGN KEY (entry_id) REFERENCES reflection_entries(id) ON DELETE CASCADE,  -- 同一ドメイン
    CONSTRAINT chk_recall_attempts_self_rating
        CHECK (self_rating IN ('REMEMBERED','PARTIAL','FORGOT')),
    INDEX idx_recall_attempts_entry (entry_id, recall_date),
    INDEX idx_recall_attempts_user_date (user_id, recall_date)
);
```

設計注記:
- 1 エントリにつき複数 recall（1 日後・3 日後…）が積み上がる。マスク判定は「次の想起予定日 ≤ 今日 かつ その予定日以降の recall がまだ無い」で行う（§3）。
- `revealed_at` は recall 保存処理で `NOW()` をセット（保存＝開示）。
- soft delete なし（履歴は保持）。親エントリ物理削除時は CASCADE で消える（同一ドメイン）。

### 2.5 `reflection_spaced_reminders`（間隔反復スケジュール）

仮ファイル名: `V900.0004__create_reflection_spaced_reminders.sql`

```sql
CREATE TABLE reflection_spaced_reminders (
    id            BINARY(16)  NOT NULL,
    entry_id      BINARY(16)  NULL,                                 -- 振り返りエントリID（SPACED 時必須・PRE_EXAM 時 NULL 可）
    theme_id      BINARY(16)  NULL,                                 -- テーマID（PRE_EXAM 総まとめ時に使用・FK なし）
    user_id       BIGINT      NOT NULL,                             -- 受信者（FK なし）
    remind_at     DATETIME    NOT NULL,                             -- 絶対日時（ユーザーTZでの予定時刻を JST 保存・§5.3）
    interval_days INT         NULL,                                 -- SPACED: 1/3/7/14、PRE_EXAM: 14/7/3/1（考査N日前）
    kind          VARCHAR(12) NOT NULL,                             -- SPACED/PRE_EXAM
    status        VARCHAR(12) NOT NULL DEFAULT 'PENDING',           -- PENDING/SENT/CANCELLED
    sent_at       DATETIME    NULL,
    created_at    DATETIME    NOT NULL,
    PRIMARY KEY (id),
    CONSTRAINT chk_reflection_spaced_reminders_kind
        CHECK (kind IN ('SPACED','PRE_EXAM')),
    CONSTRAINT chk_reflection_spaced_reminders_status
        CHECK (status IN ('PENDING','SENT','CANCELLED')),
    INDEX idx_reflection_spaced_reminders_due (status, remind_at),  -- バッチ走査の主キー
    INDEX idx_reflection_spaced_reminders_entry (entry_id),
    INDEX idx_reflection_spaced_reminders_theme (theme_id, kind),
    INDEX idx_reflection_spaced_reminders_user (user_id)
);
```

設計注記:
- **`entry_id`/`theme_id` を ID 参照（FK なし）とする理由**: (1) `entry_id`/`theme_id` のどちらか一方が NULL になる多態（SPACED は entry、PRE_EXAM は theme 基準）であり、両方に CASCADE FK は張れない。(2) リマインダーはバッチ走査テーブルであり、親削除時は CASCADE 連鎖よりもサービス層での明示的 CANCELLED 遷移（§5.5）が望ましい。よって同一ドメインでも FK を張らず、孤児はバッチ側で「親不在ならスキップ＆CANCELLED 化」して処理する（fail-safe）。これは原則 2（CASCADE は同一ドメインのみ「許可」＝強制ではない）に反しない。
- `remind_at` は絶対日時。`ScheduleReminderService` と同じく保存時に `Asia/Tokyo` の `LocalDateTime` へ正規化（§5.3）。`status` 遷移（PENDING→SENT）で二重送信を防止（§5）。

#### 2.5.1 リマインダー無制限生成の防止（DoS / スパム対策・確定）

1 エントリ保存で SPACED 4 行＋（exam_date 設定時）PRE_EXAM 4 行が無条件生成されるため、上限を設けないと一人のユーザーが大量のテーマ/エントリ/将来日付エントリを作って PENDING リマインダーを無制限に積めてしまう（DoS / 通知スパム）。以下の上限をサービス層で強制し、超過は **400** で拒否する（§7 のバリデーションに記載）。

| 対策 | 上限 | 検証箇所 |
|---|---|---|
| (a) ユーザーあたり PENDING リマインダー総数 | **1,000 件**（`status=PENDING` の `reflection_spaced_reminders` を `user_id` で COUNT し、新規生成で超過するなら拒否） | エントリ upsert / exam_date 設定時 |
| (b) ユーザーあたりテーマ数 | **100 テーマ**（`reflection_themes` を `user_id`＋`deleted_at IS NULL` で COUNT） | テーマ作成時 |
| (c) `target_date` 許容範囲 | **過去 365 日〜未来 30 日**（ユーザー TZ の今日基準。範囲外は 400）。1 テーマあたりのエントリ数はこの日数で実質自然制限される | エントリ upsert 時 |

- (a) は「想起予定 1/3/7/14＋FORGOT 再スケジュール＋PRE_EXAM」の合算 PENDING 数。上限到達時は新規エントリ保存自体を 400 で拒否し、既存 PENDING の消化（SENT/CANCELLED）を待たせる。
- (c) の未来 30 日上限により、遠未来日付の大量エントリで PENDING を膨らませる攻撃を遮断する。過去 365 日は「昨日までの振り返りをまとめて入力する」正当用途を許容する範囲。

### 2.6 `recall_interval_days` の保持設計

- **CSV 文字列（`VARCHAR(50)`、既定 `'1,3,7,14'`）**として `reflection_themes` に持つ。
- 採用理由: (1) 間隔は theme 単位で「1,3,7,14」固定が既定で、ユーザーが将来カスタム（例 `1,2,4,8,16`）したくなっても 1 カラムで表現できる。(2) 別テーブル化は MVP では過剰。(3) JSON 配列でなく CSV にするのは、`Integer.parseInt` で容易にパースでき MySQL 上も人間可読なため。
- アプリ層で `List<Integer>`（昇順・重複排除・正値のみ）にパースして使う。バリデーション: 1〜365 の正整数、最大 8 個、昇順。
- 本 MVP は **UI 上は固定 `1,3,7,14`**（マスター方針）。カラムはカスタム拡張の布石として持つが、API では既定値のみ受け付ける（将来開放）。

## 3. マスク（想起テスト）ロジックの厳密仕様

### 3.1 「今マスクされるべきか」の判定式

あるエントリ `e`（`target_date = D`, `recall_interval_days = [i1, i2, ...]`（昇順））と、今日 `T`（ユーザー TZ の今日）について：

0. **当日（`D == T`）は常に非マスク・編集可**（マスター御裁可 2026-06-20）。書いた当日は誤字脱字の修正・見直しを妨げないため、想起予定（最小 D+1）が未到来ゆえマスクしない。翌日以降から想起テスト対象になる。
1. **想起予定日集合** `R = { D + i_k 日 | i_k ∈ recall_interval_days }`。例: D=6/1, interval=[1,3,7,14] → R = {6/2, 6/4, 6/8, 6/15}。
2. **到来済み予定日** `R_due = { d ∈ R | d ≤ T }`。
3. `R_due` が空（まだどの想起予定も来ていない＝当日含む）→ **マスクしない（original を返す）**（AC-5）。
4. `R_due` の最大値（直近で来た想起予定日）を `d_last` とする。
5. `recall_attempts` のうち `entry_id = e.id` かつ `recall_date ≥ d_last` の**最新 recall** を取る。
   - 最新 recall が**無い** → **マスクする**（AC-6）。
   - 最新 recall の `self_rating` が **`FORGOT`** → **マスク継続（再提示）**。思い出せなかった項目は翌想起予定でまた隠して出す（マスター御裁可＝間隔反復の核心）。
   - 最新 recall の `self_rating` が **`REMEMBERED`/`PARTIAL`** → **マスクしない（開示済み）**（AC-7）。

擬似コード:

```
boolean isMasked(entry e, LocalDate today):
    if e.target_date == today: return false                  // 当日は常に非マスク・編集可（マスター御裁可）
    intervals = parse(e.theme.recall_interval_days)          // 昇順 List<Integer>
    dueDates  = intervals.map(i -> e.target_date.plusDays(i))
                         .filter(d -> !d.isAfter(today))      // d ≤ today
    if dueDates.isEmpty(): return false                       // AC-5（当日もここで非マスク）
    LocalDate dLast = max(dueDates)
    RecallAttempt latest = recallAttemptRepo
        .findTopByEntryIdAndRecallDateGreaterThanEqualOrderByRecallDateDesc(e.id, dLast)
    if latest == null:                  return true           // 未想起 → マスク（AC-6）
    if latest.self_rating == FORGOT:    return true           // 思い出せず → 再提示（マスク継続）
    return false                                              // REMEMBERED/PARTIAL → 開示（AC-7）
```

判定不能（theme 欠落で interval パース失敗、entry データ不整合など）の場合は **マスクする（fail-closed）**（AC-8）。

**FORGOT 時の再スケジュール**: recall 保存時に `self_rating == FORGOT` なら、`reflection_spaced_reminders` に**翌日（recall_date + 1）の SPACED 行を追加生成**する（PENDING）。これにより「思い出せなかった項目」が翌日また想起通知＋マスク提示される。REMEMBERED/PARTIAL なら次の固定間隔（既存予定）のまま。

**マスク中エントリの編集（AC-18 補足）**: `target_date == today` の当日エントリは非マスクゆえ `PUT` で自由に編集可（version 楽観排他のみ）。翌日以降でマスク中（isMasked=true）のエントリへの**直接 `PUT` は 409 で拒否**し、想起テスト（`POST .../recall`）で開示してからのみ編集可とする（original を見ずに上書きして学習履歴を壊す事故を防ぐ）。開示済み（revealed）エントリは編集可。

**「今日」の基準（確定）**: §3.1 の `today` および「当日」判定はすべて **ユーザー TZ 基準でサーバが算出**する（`resolveUserZone(userId)` の今日）。クライアントが日付を送る場合（例 today ビューの `?date=`）はサーバ側でフォーマット・範囲（§2.5.1 (c)）を検証し、信頼しない。クライアント時計に依存してマスク/非マスクが揺れないようにする。

### 3.2 マスク中のレスポンス分離方針（AC-8 漏洩防止）

original 本文（`structured_content`）が **マスク中はどの API 応答にも乗らない**ことを構造的に保証する。

- **レスポンス DTO を 2 種に分離**:
  - `ReflectionEntryResponse`（通常・開示時）: `structuredContent` フィールドを持つ。
  - マスク時はこの DTO の `isMasked = true` かつ `structuredContent = null`、加えて `maskedHint`（マスク中でも見せてよいメタ＝theme タイトル・target_date・想起予定日）のみ。
- **マッパーで一元化**: `ReflectionEntryResponseMapper.toResponse(entry, today, recalled)` を唯一の生成口とし、`isMasked(entry, today)==true` の分岐で `structuredContent` を**そもそも詰めない**（後段で握り潰すのではなく、ソースで null）。
- **fail-closed**: マッパーが判定例外を捕捉したら `isMasked=true`／本文 null を返す（§3.1 末尾）。
- 一覧 API（`GET /reflections/{themeId}/entries`）でも同じマッパーを通すため、一覧でもマスク中エントリの本文は出ない。
- **想起実行 API（`POST .../recall`）の応答**でのみ、recall 保存と同一トランザクションで `revealed_at` を記録した上で original を返す（AC-7）。これがマスク → 開示の唯一の遷移点。

> サーバ側でマスクするため、フロントが「本文を持っているが隠す」状態を一切作らない。これが AC-8/AC-15 の構造的担保。

## 4. 「今日の振り返りビュー」と AC-19（コマのその日限定編集）

### 4.1 既存 `TimetableChangeEntity` 機構の調査結果

`backend/.../timetable/entity/TimetableChangeEntity.java` を精査した。判明事項:

- `timetable_changes` テーブルは **TEAM 時間割（`timetable_id` → `timetables`）専用**の臨時変更（REPLACE/CANCEL/ADD/DAY_OFF）。`target_date`＋`period_number` で「特定日のコマ変更」を表現する。
- 個人時間割（`personal_timetable_slots`）には直接効かない。`PersonalTimetableDashboardService.buildPersonalItem()` は、個人スロットが `linked_timetable_id`（TEAM 時間割へのリンク）を持つ場合に限り、`TimetableChangeRepository.findByTimetableIdAndTargetDateOrderByPeriodNumber(...)`（実メソッド名・`OrderByPeriodNumber` サフィックス付き）で当日変更を**引いて表示に被せる**（マスタは書き換えない）。
- すなわち `timetable_changes` は「TEAM 時間割マスタを壊さず特定日だけ上書き表示する」既存機構として完成している。

### 4.2 流用判定: **reflection 側で日次オーバーライドを持つ案を採用**（`timetable_changes` は流用しない）

理由:
- `timetable_changes` は **TEAM 時間割の管理者が全メンバー向けに発行**する臨時変更であり、認可・通知（`notifyMembers`）・イベント（`TimetableChangeCreatedEvent`）が TEAM 文脈に固く結びついている。reflection の「今日のコマをその日限定で個人が修正/追加/削除」（AC-19）はこの文脈と異なる（個人の私的編集であり他メンバーへ波及してはならない）。
- 個人時間割スロット（`personal_timetable_slots`）に対する「その日限定編集」を `timetable_changes` に書くと TEAM 用テーブルに個人データが混入し、ドメイン境界を破る。
- 一方で **TEAM 時間割スロットの臨時変更は既に `timetable_changes` が当日表示に反映している**ため、reflection ビューはそれを**読み取って表示に反映するだけ**でよい（二重実装しない）。

**採用案**: reflection は **時間割マスタ（`personal_timetable_slots` / `timetable_slots`）を一切書き換えず**、「今日のコマ」は既存 `PersonalTimetableDashboardService.getTimetableToday(userId, today)` の出力（TEAM の `timetable_changes` 反映済み）を**そのまま流用**して縦並びに並べる。各コマに対する「その日限定の個人的修正/追加/削除」は **reflection エントリ側（`reflection_entries` の `structured_content` と、必要なら theme の当日紐付け）として保持**する。つまり：

- **修正**: コマに紐づく theme の当日エントリ（`target_date = 今日`）を upsert。コマ自体の科目名・教室を「その日だけ」見た目変更したい用途は、TEAM 由来なら既存 `timetable_changes`（管理者操作）に委ねる。個人都合の当日メモ・差し替え表現は reflection エントリ本文に書く。
- **追加（空きコマに臨時の振り返り対象を足す）**: `reflection_themes` を `linked_slot_kind=NULL` の自由テーマとして作り、当日エントリを作る（時間割マスタは無改変）。
- **削除（今日はこのコマをやらなかった）**: reflection エントリを当日分作らない／作った当日エントリを論理削除する。時間割マスタは無改変。

→ **AC-19 の「マスタを壊さない」を完全充足**。時間割の恒久構造は `personal_timetable_slots` のまま、当日の差分は reflection エントリ（と TEAM 由来の既存 `timetable_changes`）に分離される。

### 4.3 「今日の振り返りビュー」API（AC-17/AC-18）

`GET /api/v1/me/reflections/today?date=YYYY-MM-DD`（date 省略時はユーザー TZ の今日）

レスポンス: **今日の全コマ（TEAM＋PERSONAL、時刻順）＋各コマに対応する theme/当日エントリ** を縦並びで返す。

- コマ列挙は `PersonalTimetableDashboardService.getTimetableToday()` を呼ぶ（手本ではなく実呼び出し／reflection サービスから依存注入）。戻り値は `DashboardTimetableTodayResponse`（`items[]` の各 item は record `TimetableTodayItem`）。これにより TEAM の `timetable_changes`・`link_revoked` 等が既に反映される。
- 各コマ item に、`reflection_themes` の `linked_slot_kind`／`linked_slot_id` を、実レスポンス item の **`source_kind`（String "TEAM"/"PERSONAL"）＋ `slot_id`（Long）** で引き当て、その当日エントリ（`target_date=今日`）の有無・マスク状態を付与する。
  - 注: 引き当てキーは `DashboardTimetableTodayResponse.TimetableTodayItem` の実フィールド `source_kind`（String）＋`slot_id`（Long）を使う。enum `TimetableSlotKind` はサービス内部表現で API レスポンスには露出しないため、レスポンス層では String/Long で照合する。
- **空きコマ（theme 未設定）も item として返し、その場で theme 作成＋当日エントリ作成ができる**（AC-17 空コマ編集可）。
- **時間割を持たない自由テーマの導線（社会人・日記ユーザー）**: `linked_slot_kind`/`linked_slot_id` を持たない自由テーマ（`source_type` が PROJECT/DIARY/FREE）の当日エントリ／テーマも today ビューに **`slotKind=null`（コマ非依存）の item として列挙**する。時間割を持たない社会人・日記ユーザーはこれが主導線になる。したがって `ReflectionTodayResponse.items[]` には「時間割コマ由来 item」（`source_kind`/`slot_id` を持つ）と「自由テーマ由来 item」（`slotKind=null`・コマ非紐付け）の両方が混在する。FE は `slotKind` の有無で両者を描き分ける。
- **「今日」はユーザー TZ 基準でサーバが算出**する（`?date=` 省略時はサーバが `resolveUserZone(userId)` の今日を採用）。クライアントが `?date=` を送る場合はサーバ側で日付フォーマット・範囲（§2.5.1 (c)）を検証する。
- **各コマの保存は個別**（コマ単位の `PUT /reflections/entries` / upsert）。**楽観排他 409**: `reflection_entries` に楽観ロック（`updated_at` ベース or `@Version`）を持たせ、更新リクエストに `expected_updated_at`（または version）を含めて不一致なら 409（AC-18）。

> **楽観排他（確定）**: `reflection_entries` に `version BIGINT NOT NULL DEFAULT 0` 列（@Version）を持つ（§2.2 に記載済み）。PUT upsert は `expectedVersion` を受け取り、既存更新で不一致なら 409（AC-18）。`updated_at` 比較より version の方が厳密ゆえこちらを採用。新規作成時は `expectedVersion=null`。

## 5. 間隔反復バッチ・通知設計

### 5.1 手本の確認

- `ActionMemoReminderBatchService`: `@Scheduled(cron = "0 * * * * *")`（毎分）＋`@SchedulerLock(name=..., lockAtMostFor="PT50S", lockAtLeastFor="PT0S")`。`ZonedDateTime.now(UTC)` を各ユーザー TZ（`UserRepository.findTimezoneById` → `ZoneId.of`、失敗時 `Asia/Tokyo` フォールバック）に変換して分単位一致を判定。`@BatchEndpoint` 付与。
- `ScheduleReminderBatchService` → `ScheduleReminderService.processScheduledReminders()`: 絶対時刻 due 判定（`remind_at <= now`）＋未送信（`is_sent=false`）のみ対象、送信後 `markAsSent()`＋save で **status 遷移による二重送信防止**。`remind_at` は保存時 `Asia/Tokyo` の `LocalDateTime` に正規化。

### 5.2 `ReflectionSpacedReminderBatchService` 設計

reflection は **絶対日時 `remind_at` を予約行に持つ**ため、`ScheduleReminderService.processScheduledReminders()` 型（絶対時刻＋status 遷移）を主たる手本にする。ユーザー TZ は `remind_at` 生成時（§5.3）に織り込むため、バッチ本体は UTC/JST 比較のみでよい。

```java
@Slf4j @Service @RequiredArgsConstructor
public class ReflectionSpacedReminderBatchService {

    private final ReflectionSpacedReminderService reminderService;

    @BatchEndpoint(name = "reflection-spaced-reminder",
        description = "振り返りの間隔反復／考査前リマインドを1分毎に実効時刻判定して送信する")
    @Scheduled(fixedDelay = 60_000)                          // 1分間隔（ScheduleReminderBatch と同型）
    @SchedulerLock(name = "reflectionSpacedReminderBatch",
                   lockAtLeastFor = "PT50S", lockAtMostFor = "PT2M")
    public void runBatch() {
        try {
            reminderService.processDueReminders();
        } catch (Exception e) {
            log.error("振り返りリマインダーバッチ処理失敗: error={}", e.getMessage(), e);
        }
    }
}
```

`ReflectionSpacedReminderService.processDueReminders()`（`@Transactional`）:

```
now = LocalDateTime.now()                                   // JST（STORAGE_ZONE と一致）
due = reminderRepo.findByStatusAndRemindAtLessThanEqual(PENDING, now)   // idx_..._due 利用
for r in due:
    entry/theme の親存在チェック（不在 or 論理削除済み → r.status=CANCELLED; save; continue）   // 孤児 fail-safe
    notificationHelper.notify(
        r.userId, "REFLECTION_RECALL_REMINDER", title, body,
        "REFLECTION", null,                                 // sourceId は UUID 非対応のため null（単一宛 notify は filter を通らず本人配信・§5.4）
        NotificationScopeType.PERSONAL, r.userId,
        actionUrl, null)
    r.markAsSent()                                          // status=SENT, sent_at=now
    reminderRepo.save(r)                                    // status 遷移で二重送信防止（AC-10）
```

- **毎分 1 回だけ送信（AC-10）**: `status=PENDING` のみ対象＋送信直後 `SENT` 遷移。`@SchedulerLock` で複数インスタンスの重複起動を防止（AC-11）。
- **ユーザー TZ（AC-11）**: `remind_at` 生成時にユーザー TZ で「予定の日付の所定時刻（例 朝 8 時）」を算出し JST 正規化済みのため、バッチは単純な絶対時刻比較で TZ 正しく発火する。

### 5.3 `remind_at` の生成（ユーザー TZ 織り込み）

エントリ保存時（§3 の想起予定登録・AC-9）に、`recall_interval_days` の各間隔について行を作る：

```
zone = resolveUserZone(userId)                              // ActionMemo と同じ解決（失敗時 Asia/Tokyo）
remindHour = userReflectionSettingsService.remindHour(userId)   // 既定8時・ユーザー設定（§2.7）
for i in [1,3,7,14]:
    LocalDate dueDate = entry.targetDate.plusDays(i)
    ZonedDateTime zdt = dueDate.atTime(remindHour, 0).atZone(zone)
    LocalDateTime remindAtJst = zdt.withZoneSameInstant(STORAGE_ZONE).toLocalDateTime()
    create reflection_spaced_reminders(entryId=entry.id, userId, remindAt=remindAtJst,
                                       intervalDays=i, kind=SPACED, status=PENDING)
```

**`REMIND_HOUR`（確定）**: **ユーザーごとに設定可能**（§2.7 `user_reflection_settings.remind_hour`・マスター御裁可 2026-06-20＝夜学習の学生に対応）。`userReflectionSettingsService.remindHour(userId)` で解決し、**未設定ユーザーは既定 8 時（ユーザー TZ）**。既定値はアプリ定数 `ReflectionConstants.DEFAULT_REMIND_HOUR = 8` で保持。`GET/PUT /api/v1/me/reflections/settings`（§2.7）で取得・更新する。

### 5.4 通知の発火（`NotificationHelper.notify`）

```java
notificationHelper.notify(
    userId,
    "REFLECTION_RECALL_REMINDER",                           // 新規通知種別
    "振り返りの想起テスト",                                  // title（i18n: notification.reflection.recall.title）
    "○○の振り返りを思い出してみましょう",                    // body（テーマ名のみ・本文は含めない＝プライバシー）
    "REFLECTION",                                            // sourceType
    null,                                                    // sourceId（注記参照）
    NotificationScopeType.PERSONAL,
    userId,                                                  // scopeId = 本人
    "/reflections/recall?entry=" + entry.id,                // actionUrl
    null);                                                  // actorId
```

注記:
- `NotificationHelper.notify(...)` の `sourceId` は **`Long`** 型。reflection エントリは UUID 主キーのため `sourceId` には UUID を載せられない。よって `sourceId=null` とし、対象エントリは `actionUrl` のクエリ（`entry={uuid}`）で運ぶ。
- **【事実訂正】単一宛 `notify` は recipient filter を通らない**: `filterAccessibleRecipients`（F00 委譲フィルタ）を経由するのは `notifyAll` 系（複数受信者宛）のみであり、本機能が使う**単一ユーザー宛 `notify(...)` はそもそも recipient filter を通らず、本人宛に無条件配信される**（`NotificationHelper.notify` → `createNotification` → `dispatch` の直線経路）。したがって `sourceId=null` でも配信に影響はない。「filter が `sourceId==null` で素通しする」という挙動は `notifyAll` 系の話であって、本機能の単一宛配信には**無関係**である。リマインダーは本人（受信者＝発火対象本人）宛 PERSONAL 通知なので、可視性漏洩の懸念もない。
- 通知 body には**振り返り本文を含めない**（テーマ名のみ）。行動メモリマインドの「メモ内容を含めない」方針に倣う（プライバシー）。
- PRE_EXAM（総まとめ）も同じ `notify` で title/body/actionUrl を考査向けに差し替えて送る。

### 5.5 考査前リマインド（AC-12）と二重送信・キャンセル

- `reflection_themes.exam_date` を設定すると、その theme について `PRE_EXAM` 行を **14/7/3/1 日前**に 4 件生成（`interval_days` に負号でなく「考査N日前」の N を入れ、`remind_at = exam_date.minusDays(N) の所定時刻`）。
- **過去日ガード（確定）**: 各 PRE_EXAM 行は `remind_at` が**現在時刻より過去になる場合は生成しない**（スキップ）。とくに `exam_date` 自体が過去日の場合は 4 行すべてが過去になり生成 0 件となる。これにより「過去日の考査を設定した瞬間に 4 件が即 due 発火する」スパムを防ぐ。`exam_date` を過去日で設定すること自体は許容するが、その場合 PRE_EXAM リマインダーは作られない（UI は「過去日のためリマインドは生成されません」を表示する想定）。
- `exam_date` 変更時は **既存 PENDING の PRE_EXAM 行を CANCELLED にして作り直す**（再生成）。送信済み（SENT）は残す。
- theme/entry 削除時は関連 PENDING 行を `CANCELLED` 遷移（§2.5 の孤児 fail-safe と二重防御）。
- **同日複数想起の通知集約（任意改善）**: 同一ユーザーに同じ日・同じ時刻帯で複数の想起通知が due になる場合、1 件にまとめて「N 件の振り返りが想起待ちです」と集約配信する余地がある。**MVP は個別通知**（1 リマインダー＝1 通知）とし、集約は後続フェーズの任意改善とする（§9.1）。

## 6. F00 可視性・カレンダー連携・ブログ輸出

### 6.1 F00 可視性（`ReflectionEntryVisibilityResolver`）

- `ReferenceType` に **`REFLECTION_ENTRY` を追加**。reflection_entries は **UUIDv7 主キー**のため `idKind()` は `UUID_V7` 経路（`MATCH` と同様に `idKind()` の switch に追加）。Resolver は `canViewUuid` / `filterAccessibleUuid` を**自前実装**する。
  - 注: 既存 `corkboard_cards.reference_id_uuid` 経路（F00-A 案）に整合。コルクボード引用が不要なら `canViewUuid` 経路のみ実装（`MATCH` と同様）。
- **【実装方式の訂正】`AbstractContentVisibilityResolver` は継承しない**。`AbstractContentVisibilityResolver` の `canView`/`decide`/`filterAccessible` は **`final`** で **Long 経路（`contentId` が `Long`）専用**に固定されており、テンプレートメソッド（`loadProjections`/`toStandard`）も Long contentId を前提とする。UUID 主キーの reflection_entries では機能しない。実在の UUID 経路 Resolver **`MatchVisibilityResolver`（`backend/.../match/visibility/MatchVisibilityResolver.java`）を手本**にし、`ReflectionEntryVisibilityResolver implements ContentVisibilityResolver<Enum<?>>` として **`canViewUuid` / `filterAccessibleUuid` を自前実装**する（Long 経路 `canView`/`filterAccessible` は `MatchVisibilityResolver` 同様 **fail-closed**＝`false`／`Collections.emptySet()` を返す）。
  - `canViewUuid` 内で entry の `user_id`・`visibility`・親 theme の `visibility` を引き、reflection visibility（PRIVATE/将来 FAMILY_SHARED）で判定する。**MVP は PRIVATE 固定**ゆえ「viewer == 所有者（`entry.user_id == viewerId`）」判定で十分（本人のみ可視）。`filterAccessibleUuid` は所有エントリ UUID 群のみ通す。
  - reflection visibility → `StandardVisibility` マッピング（将来 FAMILY_SHARED 追加時の拡張点）：

  | reflection visibility | StandardVisibility | 意味 |
  |---|---|---|
  | `PRIVATE` | `PRIVATE` | 作成者本人のみ（**MVP は PRIVATE 固定**・AC-13） |

  **FAMILY_SHARED（保護者による学習内容の確認）は別軍議で詰める**（マスター御諚 2026-06-20・§9.1）。保護者が子の振り返りを閲覧するニーズは正当だが、家族共有先テーブル（F03.15 `personal_timetable_share_targets` 相当）・未成年/保護者同意・閲覧範囲（保護者にマスク中 original を見せるか等）の判断が重く、独立フィーチャーとして切り出す。本 MVP は visibility 列を持つが値は `PRIVATE` 固定（CHECK で強制）。

- **fail-closed**: viewer 不明・データ不整合・entry/theme 欠落は deny（`MatchVisibilityResolver` の UUID 経路と同方針＝`canViewUuid` は false、`filterAccessibleUuid` は空集合を返す）。
- **マスク × 可視性は直交**: 可視性で「閲覧してよい人か」を判定し、閲覧可の人にも §3 のマスクが効く（自分の過去エントリを想起テストするため）。MVP は PRIVATE 固定ゆえ閲覧者＝本人のみだが、マスク判定（§3.1）は閲覧者に依らずエントリ単位で決まり、本文は §3.2 でソースから null になる。よって**将来 FAMILY_SHARED を別軍議で追加しても、マスク中は保護者にも original が漏れない（AC-15 の構造担保が先行して効く）**。Resolver は MVP から設置し、カレンダー印を F00 経由でフィルタする（AC-14 の保険・将来の家族閲覧の土台）。

### 6.2 カレンダー連携（独立 enrich パス・F00 UUID 経路・AC-14）

横断カレンダー `GET /api/v1/my/calendar` の実体は **`ScheduleQueryService.getMyCalendar(userId, from, to)`**（`ScheduleService` は委譲。`ScheduleCommonController` 入口）。既存の合流ロジックは `ContentVisibilityChecker.filterAccessible(ReferenceType.SCHEDULE, List<Long>, userId)` の **Long 経路に固定**で `ScheduleEntity`（Long PK）に密結合しており、reflection の UUID 主キーをそのまま既存パスに載せられない（`CalendarEntryResponse.id` も `Long` 型）。

**設計（確定）— 既存 schedule 合流とは別の独立 enrich パスで合流する**:

- reflection 印（reflection エントリ＝target_date／想起予定＝remind_at の日付）は、**既存 schedule 合流ロジックを一切改変せず**、`getMyCalendar` の **return 直前に別途 enrich する独立パス**で追加する。具体的には reflection 側で対象 UUID 群を集め、`ContentVisibilityChecker.canViewUuid(REFLECTION_ENTRY, entryUuid, viewerId)` ／ `filterAccessibleUuid(REFLECTION_ENTRY, uuids, viewerId)`（§6.1 の UUID 経路 Resolver 経由）でフィルタしてから `CalendarEntryResponse` に変換し、既存リストへ `add` する。Long 経路（SCHEDULE）と UUID 経路（REFLECTION_ENTRY）が混ざらないため型破綻しない。
- **`CalendarEntryResponse.id` は reflection 行では `null`**。reflection 行の識別は `content.referenceUuid`（string）＋`content.referenceKind`（例 `REFLECTION_ENTRY`／`REFLECTION_RECALL`）で行い、**FE は `referenceUuid` を一意キーに使う**（id ではなく）。
- **後方互換の要確認事項（実装時）**: `CalendarEntryResponse.id` を null 許容にする変更が、**既存 FE が `id` を非 null 前提（一意キー・v-for key 等）にしていないか**を実装時に必ず確認する。既存 schedule 行は従来どおり `id`（Long）非 null、reflection 行のみ `id=null` で `referenceUuid` 非 null になる。既存 FE が壊れる場合は、reflection 行に「`id` を使わせない」描画分岐を FE 側に入れる（`referenceUuid` 有無で分岐）。
- **F00 漏洩防止**: 本人のカレンダーなので基本は全件可視だが、上記 UUID 経路フィルタを必ず通す（家族カレンダー（将来 FAMILY_SHARED・§9.1）でも F00 が漏洩を止める保険）。
- カレンダー表示内容:
  - `content.title` = theme タイトル（**マスク中でも theme タイトルは出してよい**＝§3.2 の maskedHint と同基準。本文 structured_content はカレンダーに載せない）。
  - `content.eventType` = `"REFLECTION_ENTRY"` または `"REFLECTION_RECALL"`（想起予定）。
  - `time.allDay = true`（日付ベース）。`scope.scopeType="PERSONAL"`。
- **A3 — `CalendarContentDto` は record（ソース変更を伴う）**: `CalendarEntryResponse.content` の型 `CalendarContentDto` は **record**（正準コンストラクタ `(String title, String eventType, String status)`）。`referenceUuid`／`referenceKind` を足すと **正準コンストラクタの変更**を伴い、既存の構築側（`ScheduleQueryService` の `CalendarContentDto` 生成箇所）も新引数に追従する必要がある。**API レスポンス JSON は後方互換**（新フィールドが増えるだけ）だが、**Java ソース上は record 変更ゆえ全構築箇所のコンパイル追従が必須**である点を実装時に留意する。

### 6.3 ブログ輸出（AC-20）

- `POST /api/v1/me/reflections/entries/{entryId}/export-to-blog` で、entry の `structured_content` を Markdown/HTML 本文へ整形し、`BlogPostService.createPost(userId, CreateBlogPostRequest)`（個人ブログ）を呼ぶ。
- **【訂正】visibility は `PRIVATE` を必ず明示設定する**: `BlogPostService.createPost` は `CreateBlogPostRequest.visibility` が未指定（null）のとき既定で **`MEMBERS_ONLY`**（BlogPostService.java:182-183）になり、reflection の PRIVATE 前提に反して意図せずメンバー公開されてしまう。よって輸出時は **`CreateBlogPostRequest.visibility = "PRIVATE"` を必ず明示設定**する（未指定にしない）。その後ユーザーが公開したい時に blog 側で publish する。
- **輸出後も元 reflection エントリは残す**（AC-20）。輸出済みを示すため `reflection_entries.exported_blog_post_id BIGINT NULL`（blog ドメイン ID・FK なし）を持つ（§2.2 記載済み・確定）。同列が非 NULL なら再輸出を 409 でブロック（MVP は再輸出ブロック、更新輸出は後続）。元エントリの削除は輸出と独立。
- **輸出は時点の静的コピー（同期しない）**: 輸出はその時点の本文を blog 記事へコピーするだけで、**輸出後にエントリを編集してもブログ記事は自動同期しない**（更新輸出は後続フェーズ・§9.1）。FE は「輸出後に編集済み」バッジ等の表示を検討する（判定可能条件＝`exported_blog_post_id` 非 NULL かつ `entry.updated_at > 輸出時刻`。輸出時刻は blog 記事の `created_at` で代用可）。
- 共有は `BlogPostService.sharePost(postId, userId, SharePostRequest)` を流用（個人ブログをチーム/組織へ共有する既存導線）。

## 11. Phase 2: 科目紐づけ拡張

> Phase 2 ステータス: 🟢 設計完了（マスター御裁可 2026-06-22 / 案B確定・残論点ゼロ・実装着手可）

### §11.0 概要・前提

#### 目的

Phase 1 では「時間割の特定スロット（linked_slot_id）」にテーマを紐づける設計を確立した。しかしこの設計では**今日ビューの空きコマからしか科目紐づけができない** UX 欠落がある。例えば「数学が月・水の2コマあるが、テーマ設定ダイアログから科目「数学」全体に一括紐づけしたい」という用途に対応できない。

Phase 2 ではテーマを**「時間割の科目（subject_name）」単位で紐づける**機能を追加し、今日ビューでその科目の**当日全コマ**に振り返り導線を出す。

#### 軽量方針

- **科目マスタ（subjects テーブル）は新設しない**。timetable ドメインの DDL は一切変更しない。
- reflection 側で時間割スロットを科目名（＋履修番号 course_code）で重複排除して選択肢化する（既存スロットの論理表現を再利用）。
- 「数学が週2コマでも候補は1つ（重複排除）」「数学1と数学Aは別候補」を満たす。

#### 後方互換

既存テーマは新カラム NULL → 従来の `linked_slot_id` 経路で当該スロットに表示（Phase 1 動作を完全維持）。

---

### §11.1 紐づけ方式（案B 確定）

#### reflection_themes への新カラム追加

`reflection_themes` に以下の2列を追加する:

| カラム | 型 | 説明 |
|---|---|---|
| `linked_subject_name` | `VARCHAR(200) NULL` | 科目名で紐づける場合に設定。`personal_timetable_slots.subject_name` と合わせる |
| `linked_course_code` | `VARCHAR(50) NULL` | 履修番号で紐づける場合に補完設定。`personal_timetable_slots.course_code` と合わせる（TEAM コマは常に NULL） |

どちらも NULL 可。`linked_slot_id` との共存を許容する（後述の照合ロジック参照）。

#### 今日ビュー照合ロジックの拡張

`ReflectionTodayService`（今日ビューの突き合わせ）のテーマ→コマ照合条件を以下に拡張する:

```
theme と slot の照合条件（OR で評価）:
  A: linked_slot_kind == slot.source_kind AND linked_slot_id == slot.slot_id
     （Phase 1 従来経路・後方互換）
  B: linked_slot_kind == slot.source_kind
     AND linked_subject_name == slot.subjectName
     AND (linked_slot_kind == "TEAM" OR linked_course_code == slot.courseCode)
     （Phase 2 科目名経路）
```

- 条件 A または条件 B が真のとき、当該コマにテーマを表示する。
- **効果**: 科目「数学」に紐づけた1テーマが、週内の全数学コマのうち当日該当分すべてに表示される。1日に同科目2コマあれば2枚表示される（御裁可済＝授業ごとの振り返りに直結）。

#### TEAM コマの注意事項

`timetable_slots`（チーム時間割）には `course_code` 列が存在しない。したがって **kind=TEAM の照合は `subject_name` のみ**とし、`course_code` は PERSONAL 専用の細粒度識別として使う。同名異科目の誤マッチ余地は許容（御裁可済・§11.8 に明記）。

#### 実装注意（toBuilder 禁止）

`ReflectionThemeEntity.applyUpdate` は `toBuilder()` 禁止（UuidV7Entity 継承の既知バグ・§2.2 の警告参照）。新カラム `linked_subject_name`/`linked_course_code` の更新も**直接ミューテートのセッター追加**で揃える。

手本: 既存 `applyUpdate`（`TimetableChangeEntity` L81-98 / `IncidentBannerEntity.update` L136-143）。null ＝ 現値維持セマンティクスを使い、null 渡しで「解除」したい場合は `clearLinkedSubject()` 相当のメソッドを別途用意する。

#### TEAM コマの subject_name 照合の誤マッチ許容

TEAM スロット（`timetable_slots`）には `course_code` 列が存在しないため、kind=TEAM の照合は `subject_name` のみとなる。同一チームで異なる内容だが同名の科目（例: 「体育」が2種）は誤マッチの余地がある。これは御裁可済みの許容仕様（§11.1）。将来 TEAM スロットに `course_code` 相当列が追加された場合は照合条件 B を拡張可能。
