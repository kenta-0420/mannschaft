## 0. 用語と前提

| 用語 | 定義 |
|---|---|
| **メインテーマ（reflection theme）** | 日々の振り返りを束ねる軽量な「器」。例: 「数学II」「○○プロジェクト」「日記」。cms ブログには載せず、公開したい時だけブログへ輸出する。既定 PRIVATE |
| **振り返り（reflection entry）** | テーマに紐づく日々の記録。アウトライン構造（メインテーマ/中見出し/小見出し/詳細/補足）の structured_content を持つ |
| **想起テスト（recall）** | 過去の振り返りをマスク（本文非表示）し、思い出して書き起こし、開示して照合する復習 |
| **間隔反復リマインダー（spaced reminder）** | 1・3・7・14 日後の固定間隔、および定期考査の 14/7/3/1 日前に送る通知 |

本機能は **reflection ドメインを新設**する（パッケージ `com.mannschaft.app.reflection`）。学生は授業ごとの振り返り、社会人は仕事の振り返り、誰でも日記として利用できる汎用機能である。

## 2. データモデル・DDL 案

### 2.0 共通方針（CLAUDE.md アーキテクチャ原則の遵守）

- **全テーブル UuidV7 主キー**（`BINARY(16)`）。Entity は `UuidV7Entity` を継承（原則 6）。
- **クロスドメイン FK 禁止**（原則 1）。`user_id`・`linked_slot_id`・`exported_blog_post_id` 等の他ドメイン参照は ID 列＋INDEX のみ。FK 制約を張らない。
- **CASCADE は同一 reflection ドメイン内のみ許可**（原則 2）。`reflection_entries.theme_id` → `reflection_themes.id`、`recall_attempts.entry_id` → `reflection_entries.id` は同一ドメインのため FK＋`ON DELETE CASCADE` 可。`reflection_spaced_reminders.entry_id` はバッチ走査性能と孤児許容のため **ID 参照（FK なし）**とする（理由は §2.5）。
- **論理削除**: theme / entry は `deleted_at` を持つ。recall_attempts / spaced_reminders は履歴・運用テーブルのため物理保持（soft delete なし）。
- **テナント**: 本機能は **個人所有（user_id）**が主であり organization_id を持たない。よって `AbstractTenantAwareRepository` は適用しない（リポジトリは `JpaRepository<T, UUID>` を継承）。組織配信は本機能のスコープ外。
- `created_at` / `updated_at` / `deleted_at` は既存 UUIDv7 テーブル（例: `incident_banners` V94）と同じく DDL に明示列で定義する。
- **可視性（MVP 確定）**: theme / entry の `visibility` は既定 `PRIVATE`、**MVP は PRIVATE 固定（CHECK で強制）**。FAMILY_SHARED（保護者による学習内容の確認）は重い設計判断を伴うため別軍議へ切り出す（§9.1）。

> **Flyway 番号は仮（プレースホルダ V900 系）**。`docs/openapi.json` や origin/main の最大 major は現状 **V119**（2026-06-20 時点）。**マージ直前に `git ls-tree origin/main backend/src/main/resources/db/migration` で最大 major を再確認し、`最大 major + 1`（並行 PR があればさらに +1）へリネームすること**（feedback_flyway_version_sort_after_global_max / feedback_migration_version_collision）。

### 2.1 `reflection_themes`（メインテーマ）

仮ファイル名: `V900.0001__create_reflection_themes.sql`

```sql
CREATE TABLE reflection_themes (
    id                   BINARY(16)   NOT NULL,
    user_id              BIGINT       NOT NULL,                      -- 所有者（users ドメイン・FK なし）
    title                VARCHAR(120) NOT NULL,
    description          VARCHAR(500) NULL,
    source_type          VARCHAR(20)  NOT NULL DEFAULT 'FREE',      -- SUBJECT/PROJECT/DIARY/FREE
    linked_slot_kind     VARCHAR(10)  NULL,                          -- TEAM/PERSONAL/NULL（時間割スロット種別）
    linked_slot_id       BIGINT       NULL,                          -- 時間割スロットID（timetable ドメイン・FK なし・論理参照）
    exam_date            DATE         NULL,                          -- 定期考査日（総まとめリマインド基準・NULL 可）
    visibility           VARCHAR(20)  NOT NULL DEFAULT 'PRIVATE',    -- MVPはPRIVATE固定（FAMILY_SHAREDは別軍議・§6.1/§9.1）
    recall_interval_days VARCHAR(50)  NOT NULL DEFAULT '1,3,7,14',   -- 想起間隔（昇順 CSV・§2.6 設計）
    created_at           DATETIME     NOT NULL,
    updated_at           DATETIME     NOT NULL,
    deleted_at           DATETIME     NULL,
    PRIMARY KEY (id),
    CONSTRAINT chk_reflection_themes_source_type
        CHECK (source_type IN ('SUBJECT','PROJECT','DIARY','FREE')),
    CONSTRAINT chk_reflection_themes_linked_slot_kind
        CHECK (linked_slot_kind IS NULL OR linked_slot_kind IN ('TEAM','PERSONAL')),
    CONSTRAINT chk_reflection_themes_visibility
        CHECK (visibility = 'PRIVATE'),  -- MVP。FAMILY_SHARED追加は別軍議で旧CHECK DROP→新CHECKのmigration
    INDEX idx_reflection_themes_user (user_id, deleted_at),
    INDEX idx_reflection_themes_user_slot (user_id, linked_slot_kind, linked_slot_id),
    INDEX idx_reflection_themes_exam (exam_date)
);
```

設計注記:
- `linked_slot_kind`/`linked_slot_id` は F03.15 と同じ表現（`TimetableSlotKind` ENUM 値・`BIGINT` 論理参照）。リンク先スロットが削除されても孤児として保持（FK なし）。
- `exam_date` は theme 単位の「次回の定期考査日」。複数考査を扱う将来拡張は別テーブル化候補（本 MVP は単一日）。

### 2.2 `reflection_entries`（日々の振り返り）

仮ファイル名: `V900.0002__create_reflection_entries.sql`

```sql
CREATE TABLE reflection_entries (
    id                  BINARY(16)   NOT NULL,
    theme_id            BINARY(16)   NOT NULL,                       -- 同一ドメイン FK 可
    user_id             BIGINT       NOT NULL,                       -- 所有者非正規化（高速絞り込み・FK なし）
    target_date         DATE         NOT NULL,                       -- 振り返り対象日
    structured_content  JSON         NOT NULL,                       -- アウトライン構造（§2.3）
    visibility          VARCHAR(20)  NOT NULL DEFAULT 'PRIVATE',     -- MVPはPRIVATE固定（§6.1/§9.1）
    version             BIGINT       NOT NULL DEFAULT 0,             -- 楽観ロック（@Version・AC-18）
    exported_blog_post_id BIGINT     NULL,                           -- 輸出先ブログ記事ID（cmsドメイン・FKなし・再輸出防止/輸出済表示・AC-20）
    created_at          DATETIME     NOT NULL,
    updated_at          DATETIME     NOT NULL,
    deleted_at          DATETIME     NULL,
    PRIMARY KEY (id),
    CONSTRAINT fk_reflection_entries_theme
        FOREIGN KEY (theme_id) REFERENCES reflection_themes(id) ON DELETE CASCADE,  -- 同一ドメイン
    CONSTRAINT chk_reflection_entries_visibility
        CHECK (visibility = 'PRIVATE'),  -- MVP。別軍議でFAMILY_SHARED追加
    CONSTRAINT uq_reflection_entries_theme_date
        UNIQUE (theme_id, target_date),                             -- (theme,target_date) 一意（AC-4）
    INDEX idx_reflection_entries_user_date (user_id, target_date),
    INDEX idx_reflection_entries_theme (theme_id, target_date)
);
```

設計注記:
- `(theme_id, target_date)` 一意制約で「1 テーマ×1 日＝1 エントリ」を保証。同日再保存は **upsert**（既存があれば UPDATE）（AC-4）。
- `deleted_at` がある行も UNIQUE に効く点に注意。論理削除済みエントリと同日同テーマで再作成する場合は、サービス層で「deleted 行を物理削除 or 復活更新」する（実装方針: 復活更新＝`deleted_at=NULL` にして上書き。一意制約衝突を避ける）。
- **復活時のリマインダー再生成（確定）**: 論理削除エントリを復活更新（`deleted_at=NULL`＋本文上書き）する際、古い `recall_attempts`／`reflection_spaced_reminders` は旧 original 基準のまま残っている。復活時はサービス層で **当該エントリ由来の PENDING リマインダーを全て CANCELLED に遷移させ、新しい本文・新しい target_date 基準で SPACED 行を再生成**する（旧予定の誤発火・旧 recall を基準にしたマスク判定の混線を防ぐ）。`recall_attempts` 履歴自体は保持するが、マスク判定（§3.1）は復活後の新 target_date を基準にやり直される。
- `user_id` は `theme.user_id` の非正規化コピー。`GET /reflections/today` 等のユーザー横断クエリを 1 SELECT で引くため。
- **【実装者向け警告】`@Builder(toBuilder=true)` + `UuidV7Entity` の id 欠落再発パターン**: `UuidV7Entity` を継承した Entity で `entity.toBuilder().build()` を更新に使うと、継承フィールドの `id` が build で落ちて id=null となり、JPA が UPDATE ではなく **INSERT** を発行してしまう（一意制約違反で 500、または制約が無い列では行重複）。これは本リポジトリで複数回再発した既知バグ（toBuilder 更新破壊キャンペーン）。**更新は managed entity を直接ミューテートすること**（`TimetableChangeEntity.applyUpdate(...)`（L81-98）/ `IncidentBannerEntity.update(...)`（L136-143）が手本＝null=現値維持セマンティクスで各フィールドを個別更新）。reflection の entry/theme 更新も `applyUpdate` 相当の直接ミューテートメソッドで実装する。version 楽観排他（@Version）と併せ、toBuilder は使わない。

### 2.3 `structured_content` JSON スキーマ

アウトラインは固定 5 階層（メインテーマ → 中見出し → 小見出し → 詳細 → 補足）。F06.4 の `field_values` 自由 JSON ではなく、**スキーマ固定**にする（想起テストでマスク対象を機械的に決めるため）。

```json
{
  "main_theme": "二次関数の最大最小",
  "sections": [
    {
      "heading": "平方完成",
      "subsections": [
        {
          "sub_heading": "基本形への変形",
          "detail": "y = a(x-p)^2 + q に変形し頂点 (p,q) を読む",
          "supplement": "a>0 で下に凸・最小値 q"
        }
      ]
    }
  ],
  "free_note": "授業後の所感や質問メモ（マスク対象外の任意欄）"
}
```

> **Phase 4 拡張**: 各 section に任意フィールド `type`（`"OUTLINE"` 既定 / `"TERM_CARD"` 暗記カード）と、TERM_CARD 時の `cards[]`（`term`/`meaning`）を**後方互換で追加**する。`type` 欠落＝OUTLINE とみなし既存データ・既存挙動は無改変。本体仕様は **§13-A** を正準とする（ここでは二重管理を避け参照のみ）。

- `main_theme`（string, 必須）/ `sections`（配列）/ 各 section に `heading` + `subsections[]`、各 subsection に `sub_heading` / `detail` / `supplement`。
- `free_note` は**マスク対象外**（想起の手がかりやメタ所感を残す欄）。マスク対象は `main_theme` と `sections` 全体。
- バリデーション（確定）: JSON サイズ上限 **64KB**、`sections` 最大 **30**、各 `subsections` 最大 **30**、`main_theme`/`heading`/`sub_heading` 各 200 字、`detail`/`supplement` 各 2,000 字、`free_note` 10,000 字。サニタイズは**サービス層の専用 `ReflectionContentSanitizer`**（`<script>`・`on*` 属性・`javascript:` 除去）で保存前に正規化し、表示は出力時エスケープ（F06.1/F06.4 と同方針・XSS 二重防御）。

### 2.3.1 テンプレート（入力補助プリセット）

御要望「ノーマル／日記／仕事の振り返り／授業の振り返り」を、**`source_type` 別の入力補助プリセット**として実現する（**新テーブルを作らず** structured_content は固定 5 階層のまま）。テンプレートは「初期見出し・プレースホルダ・推奨記入欄」の違いに過ぎないため、**フロントの静的プリセット定義 + i18n** で持つ（保守性: BE スキーマを汚さず、F01.3/F06.4 のテンプレ概念と乱立させない）。

| テンプレ | source_type | 初期 main_theme / 見出しプリセット例 |
|---|---|---|
| ノーマル | FREE | 見出しなし・自由。`main_theme` のみ必須 |
| 日記 | DIARY | main_theme=「今日のできごと」、section: 出来事／感じたこと／明日に向けて |
| 仕事の振り返り | PROJECT | main_theme=案件名、section: 成果／課題／学び／次アクション（KPT 風） |
| 授業の振り返り | SUBJECT | main_theme=単元名、section: 学んだこと／つまずき／覚える要点（想起対象） |

- プリセットは `frontend/app/constants/reflectionTemplates.ts`（静的）＋ロケール 6 言語（i18n ルール遵守・直書き禁止）。テーマ作成時に選択し、エントリ作成画面の初期 structured_content を組み立てる。
- BE はテンプレートを関知しない（structured_content を受け取るのみ）。これにより入力補助の御要望を満たしつつ、テンプレ概念の乱立を回避する。

### 2.4 `recall_attempts`（想起テスト記録）

仮ファイル名: `V900.0003__create_recall_attempts.sql`

```sql
CREATE TABLE recall_attempts (
    id                BINARY(16)  NOT NULL,
    entry_id          BINARY(16)  NOT NULL,                         -- 同一ドメイン FK 可
    user_id           BIGINT      NOT NULL,                         -- 所有者非正規化（FK なし）
    recall_date       DATE        NOT NULL,                         -- 想起を行った日
    recalled_content  JSON        NOT NULL,                         -- 思い出して書いた内容（structured_content と同形 or 自由テキスト）
    self_rating       VARCHAR(12) NOT NULL,                         -- REMEMBERED/PARTIAL/FORGOT
    revealed_at       DATETIME    NULL,                             -- 開示時刻（保存＝開示で記録・AC-7）
    created_at        DATETIME    NOT NULL,
    PRIMARY KEY (id),
    CONSTRAINT fk_recall_attempts_entry
        FOREIGN KEY (entry_id) REFERENCES reflection_entries(id) ON DELETE CASCADE,  -- 同一ドメイン
    CONSTRAINT chk_recall_attempts_self_rating
        CHECK (self_rating IN ('REMEMBERED','PARTIAL','FORGOT')),
    INDEX idx_recall_attempts_entry (entry_id, recall_date),
    INDEX idx_recall_attempts_user_date (user_id, recall_date)
);
```

設計注記:
- 1 エントリにつき複数 recall（1 日後・3 日後…）が積み上がる。マスク判定は「次の想起予定日 ≤ 今日 かつ その予定日以降の recall がまだ無い」で行う（§3）。
- `revealed_at` は recall 保存処理で `NOW()` をセット（保存＝開示）。
- soft delete なし（履歴は保持）。親エントリ物理削除時は CASCADE で消える（同一ドメイン）。

### 2.5 `reflection_spaced_reminders`（間隔反復スケジュール）

仮ファイル名: `V900.0004__create_reflection_spaced_reminders.sql`

```sql
CREATE TABLE reflection_spaced_reminders (
    id            BINARY(16)  NOT NULL,
    entry_id      BINARY(16)  NULL,                                 -- 振り返りエントリID（SPACED 時必須・PRE_EXAM 時 NULL 可）
    theme_id      BINARY(16)  NULL,                                 -- テーマID（PRE_EXAM 総まとめ時に使用・FK なし）
    user_id       BIGINT      NOT NULL,                             -- 受信者（FK なし）
    remind_at     DATETIME    NOT NULL,                             -- 絶対日時（ユーザーTZでの予定時刻を JST 保存・§5.3）
    interval_days INT         NULL,                                 -- SPACED: 1/3/7/14、PRE_EXAM: 14/7/3/1（考査N日前）
    kind          VARCHAR(12) NOT NULL,                             -- SPACED/PRE_EXAM
    status        VARCHAR(12) NOT NULL DEFAULT 'PENDING',           -- PENDING/SENT/CANCELLED
    sent_at       DATETIME    NULL,
    created_at    DATETIME    NOT NULL,
    PRIMARY KEY (id),
    CONSTRAINT chk_reflection_spaced_reminders_kind
        CHECK (kind IN ('SPACED','PRE_EXAM')),
    CONSTRAINT chk_reflection_spaced_reminders_status
        CHECK (status IN ('PENDING','SENT','CANCELLED')),
    INDEX idx_reflection_spaced_reminders_due (status, remind_at),  -- バッチ走査の主キー
    INDEX idx_reflection_spaced_reminders_entry (entry_id),
    INDEX idx_reflection_spaced_reminders_theme (theme_id, kind),
    INDEX idx_reflection_spaced_reminders_user (user_id)
);
```

設計注記:
- **`entry_id`/`theme_id` を ID 参照（FK なし）とする理由**: (1) `entry_id`/`theme_id` のどちらか一方が NULL になる多態（SPACED は entry、PRE_EXAM は theme 基準）であり、両方に CASCADE FK は張れない。(2) リマインダーはバッチ走査テーブルであり、親削除時は CASCADE 連鎖よりもサービス層での明示的 CANCELLED 遷移（§5.5）が望ましい。よって同一ドメインでも FK を張らず、孤児はバッチ側で「親不在ならスキップ＆CANCELLED 化」して処理する（fail-safe）。これは原則 2（CASCADE は同一ドメインのみ「許可」＝強制ではない）に反しない。
- `remind_at` は絶対日時。`ScheduleReminderService` と同じく保存時に `Asia/Tokyo` の `LocalDateTime` へ正規化（§5.3）。`status` 遷移（PENDING→SENT）で二重送信を防止（§5）。

#### 2.5.1 リマインダー無制限生成の防止（DoS / スパム対策・確定）

1 エントリ保存で SPACED 4 行＋（exam_date 設定時）PRE_EXAM 4 行が無条件生成されるため、上限を設けないと一人のユーザーが大量のテーマ/エントリ/将来日付エントリを作って PENDING リマインダーを無制限に積めてしまう（DoS / 通知スパム）。以下の上限をサービス層で強制し、超過は **400** で拒否する（§7 のバリデーションに記載）。

| 対策 | 上限 | 検証箇所 |
|---|---|---|
| (a) ユーザーあたり PENDING リマインダー総数 | **1,000 件**（`status=PENDING` の `reflection_spaced_reminders` を `user_id` で COUNT し、新規生成で超過するなら拒否） | エントリ upsert / exam_date 設定時 |
| (b) ユーザーあたりテーマ数 | **100 テーマ**（`reflection_themes` を `user_id`＋`deleted_at IS NULL` で COUNT） | テーマ作成時 |
| (c) `target_date` 許容範囲 | **過去 365 日〜未来 30 日**（ユーザー TZ の今日基準。範囲外は 400）。1 テーマあたりのエントリ数はこの日数で実質自然制限される | エントリ upsert 時 |

- (a) は「想起予定 1/3/7/14＋FORGOT 再スケジュール＋PRE_EXAM」の合算 PENDING 数。上限到達時は新規エントリ保存自体を 400 で拒否し、既存 PENDING の消化（SENT/CANCELLED）を待たせる。
- (c) の未来 30 日上限により、遠未来日付の大量エントリで PENDING を膨らませる攻撃を遮断する。過去 365 日は「昨日までの振り返りをまとめて入力する」正当用途を許容する範囲。

### 2.6 `recall_interval_days` の保持設計

- **CSV 文字列（`VARCHAR(50)`、既定 `'1,3,7,14'`）**として `reflection_themes` に持つ。
- 採用理由: (1) 間隔は theme 単位で「1,3,7,14」固定が既定で、ユーザーが将来カスタム（例 `1,2,4,8,16`）したくなっても 1 カラムで表現できる。(2) 別テーブル化は MVP では過剰。(3) JSON 配列でなく CSV にするのは、`Integer.parseInt` で容易にパースでき MySQL 上も人間可読なため。
- アプリ層で `List<Integer>`（昇順・重複排除・正値のみ）にパースして使う。バリデーション: 1〜365 の正整数、最大 8 個、昇順。
- 本 MVP は **UI 上は固定 `1,3,7,14`**（マスター方針）。カラムはカスタム拡張の布石として持つが、API では既定値のみ受け付ける（将来開放）。

## 3. マスク（想起テスト）ロジックの厳密仕様

### 3.1 「今マスクされるべきか」の判定式

あるエントリ `e`（`target_date = D`, `recall_interval_days = [i1, i2, ...]`（昇順））と、今日 `T`（ユーザー TZ の今日）について：

0. **当日（`D == T`）は常に非マスク・編集可**（マスター御裁可 2026-06-20）。書いた当日は誤字脱字の修正・見直しを妨げないため、想起予定（最小 D+1）が未到来ゆえマスクしない。翌日以降から想起テスト対象になる。
1. **想起予定日集合** `R = { D + i_k 日 | i_k ∈ recall_interval_days }`。例: D=6/1, interval=[1,3,7,14] → R = {6/2, 6/4, 6/8, 6/15}。
2. **到来済み予定日** `R_due = { d ∈ R | d ≤ T }`。
3. `R_due` が空（まだどの想起予定も来ていない＝当日含む）→ **マスクしない（original を返す）**（AC-5）。
4. `R_due` の最大値（直近で来た想起予定日）を `d_last` とする。
5. `recall_attempts` のうち `entry_id = e.id` かつ `recall_date ≥ d_last` の**最新 recall** を取る。
   - 最新 recall が**無い** → **マスクする**（AC-6）。
   - 最新 recall の `self_rating` が **`FORGOT`** → **マスク継続（再提示）**。思い出せなかった項目は翌想起予定でまた隠して出す（マスター御裁可＝間隔反復の核心）。
   - 最新 recall の `self_rating` が **`REMEMBERED`/`PARTIAL`** → **マスクしない（開示済み）**（AC-7）。

擬似コード:

```
boolean isMasked(entry e, LocalDate today):
    if e.target_date == today: return false                  // 当日は常に非マスク・編集可（マスター御裁可）
    intervals = parse(e.theme.recall_interval_days)          // 昇順 List<Integer>
    dueDates  = intervals.map(i -> e.target_date.plusDays(i))
                         .filter(d -> !d.isAfter(today))      // d ≤ today
    if dueDates.isEmpty(): return false                       // AC-5（当日もここで非マスク）
    LocalDate dLast = max(dueDates)
    RecallAttempt latest = recallAttemptRepo
        .findTopByEntryIdAndRecallDateGreaterThanEqualOrderByRecallDateDesc(e.id, dLast)
    if latest == null:                  return true           // 未想起 → マスク（AC-6）
    if latest.self_rating == FORGOT:    return true           // 思い出せず → 再提示（マスク継続）
    return false                                              // REMEMBERED/PARTIAL → 開示（AC-7）
```

判定不能（theme 欠落で interval パース失敗、entry データ不整合など）の場合は **マスクする（fail-closed）**（AC-8）。

**FORGOT 時の再スケジュール**: recall 保存時に `self_rating == FORGOT` なら、`reflection_spaced_reminders` に**翌日（recall_date + 1）の SPACED 行を追加生成**する（PENDING）。これにより「思い出せなかった項目」が翌日また想起通知＋マスク提示される。REMEMBERED/PARTIAL なら次の固定間隔（既存予定）のまま。

**マスク中エントリの編集（AC-18 補足）**: `target_date == today` の当日エントリは非マスクゆえ `PUT` で自由に編集可（version 楽観排他のみ）。翌日以降でマスク中（isMasked=true）のエントリへの**直接 `PUT` は 409 で拒否**し、想起テスト（`POST .../recall`）で開示してからのみ編集可とする（original を見ずに上書きして学習履歴を壊す事故を防ぐ）。開示済み（revealed）エントリは編集可。

**「今日」の基準（確定）**: §3.1 の `today` および「当日」判定はすべて **ユーザー TZ 基準でサーバが算出**する（`resolveUserZone(userId)` の今日）。クライアントが日付を送る場合（例 today ビューの `?date=`）はサーバ側でフォーマット・範囲（§2.5.1 (c)）を検証し、信頼しない。クライアント時計に依存してマスク/非マスクが揺れないようにする。

### 3.2 マスク中のレスポンス分離方針（AC-8 漏洩防止）

original 本文（`structured_content`）が **マスク中はどの API 応答にも乗らない**ことを構造的に保証する。

- **レスポンス DTO を 2 種に分離**:
  - `ReflectionEntryResponse`（通常・開示時）: `structuredContent` フィールドを持つ。
  - マスク時はこの DTO の `isMasked = true` かつ `structuredContent = null`、加えて `maskedHint`（マスク中でも見せてよいメタ＝theme タイトル・target_date・想起予定日）のみ。
- **マッパーで一元化**: `ReflectionEntryResponseMapper.toResponse(entry, today, recalled)` を唯一の生成口とし、`isMasked(entry, today)==true` の分岐で `structuredContent` を**そもそも詰めない**（後段で握り潰すのではなく、ソースで null）。
- **fail-closed**: マッパーが判定例外を捕捉したら `isMasked=true`／本文 null を返す（§3.1 末尾）。
- 一覧 API（`GET /reflections/{themeId}/entries`）でも同じマッパーを通すため、一覧でもマスク中エントリの本文は出ない。
- **想起実行 API（`POST .../recall`）の応答**でのみ、recall 保存と同一トランザクションで `revealed_at` を記録した上で original を返す（AC-7）。これがマスク → 開示の唯一の遷移点。

> サーバ側でマスクするため、フロントが「本文を持っているが隠す」状態を一切作らない。これが AC-8/AC-15 の構造的担保。

## 4. 「今日の振り返りビュー」と AC-19（コマのその日限定編集）

### 4.1 既存 `TimetableChangeEntity` 機構の調査結果

`backend/.../timetable/entity/TimetableChangeEntity.java` を精査した。判明事項:

- `timetable_changes` テーブルは **TEAM 時間割（`timetable_id` → `timetables`）専用**の臨時変更（REPLACE/CANCEL/ADD/DAY_OFF）。`target_date`＋`period_number` で「特定日のコマ変更」を表現する。
- 個人時間割（`personal_timetable_slots`）には直接効かない。`PersonalTimetableDashboardService.buildPersonalItem()` は、個人スロットが `linked_timetable_id`（TEAM 時間割へのリンク）を持つ場合に限り、`TimetableChangeRepository.findByTimetableIdAndTargetDateOrderByPeriodNumber(...)`（実メソッド名・`OrderByPeriodNumber` サフィックス付き）で当日変更を**引いて表示に被せる**（マスタは書き換えない）。
- すなわち `timetable_changes` は「TEAM 時間割マスタを壊さず特定日だけ上書き表示する」既存機構として完成している。

### 4.2 流用判定: **reflection 側で日次オーバーライドを持つ案を採用**（`timetable_changes` は流用しない）

理由:
- `timetable_changes` は **TEAM 時間割の管理者が全メンバー向けに発行**する臨時変更であり、認可・通知（`notifyMembers`）・イベント（`TimetableChangeCreatedEvent`）が TEAM 文脈に固く結びついている。reflection の「今日のコマをその日限定で個人が修正/追加/削除」（AC-19）はこの文脈と異なる（個人の私的編集であり他メンバーへ波及してはならない）。
- 個人時間割スロット（`personal_timetable_slots`）に対する「その日限定編集」を `timetable_changes` に書くと TEAM 用テーブルに個人データが混入し、ドメイン境界を破る。
- 一方で **TEAM 時間割スロットの臨時変更は既に `timetable_changes` が当日表示に反映している**ため、reflection ビューはそれを**読み取って表示に反映するだけ**でよい（二重実装しない）。

**採用案**: reflection は **時間割マスタ（`personal_timetable_slots` / `timetable_slots`）を一切書き換えず**、「今日のコマ」は既存 `PersonalTimetableDashboardService.getTimetableToday(userId, today)` の出力（TEAM の `timetable_changes` 反映済み）を**そのまま流用**して縦並びに並べる。各コマに対する「その日限定の個人的修正/追加/削除」は **reflection エントリ側（`reflection_entries` の `structured_content` と、必要なら theme の当日紐付け）として保持**する。つまり：

- **修正**: コマに紐づく theme の当日エントリ（`target_date = 今日`）を upsert。コマ自体の科目名・教室を「その日だけ」見た目変更したい用途は、TEAM 由来なら既存 `timetable_changes`（管理者操作）に委ねる。個人都合の当日メモ・差し替え表現は reflection エントリ本文に書く。
- **追加（空きコマに臨時の振り返り対象を足す）**: `reflection_themes` を `linked_slot_kind=NULL` の自由テーマとして作り、当日エントリを作る（時間割マスタは無改変）。
- **削除（今日はこのコマをやらなかった）**: reflection エントリを当日分作らない／作った当日エントリを論理削除する。時間割マスタは無改変。

→ **AC-19 の「マスタを壊さない」を完全充足**。時間割の恒久構造は `personal_timetable_slots` のまま、当日の差分は reflection エントリ（と TEAM 由来の既存 `timetable_changes`）に分離される。

### 4.3 「今日の振り返りビュー」API（AC-17/AC-18）

`GET /api/v1/me/reflections/today?date=YYYY-MM-DD`（date 省略時はユーザー TZ の今日）

レスポンス: **今日の全コマ（TEAM＋PERSONAL、時刻順）＋各コマに対応する theme/当日エントリ** を縦並びで返す。

- コマ列挙は `PersonalTimetableDashboardService.getTimetableToday()` を呼ぶ（手本ではなく実呼び出し／reflection サービスから依存注入）。戻り値は `DashboardTimetableTodayResponse`（`items[]` の各 item は record `TimetableTodayItem`）。これにより TEAM の `timetable_changes`・`link_revoked` 等が既に反映される。
- 各コマ item に、`reflection_themes` の `linked_slot_kind`／`linked_slot_id` を、実レスポンス item の **`source_kind`（String "TEAM"/"PERSONAL"）＋ `slot_id`（Long）** で引き当て、その当日エントリ（`target_date=今日`）の有無・マスク状態を付与する。
  - 注: 引き当てキーは `DashboardTimetableTodayResponse.TimetableTodayItem` の実フィールド `source_kind`（String）＋`slot_id`（Long）を使う。enum `TimetableSlotKind` はサービス内部表現で API レスポンスには露出しないため、レスポンス層では String/Long で照合する。
- **空きコマ（theme 未設定）も item として返し、その場で theme 作成＋当日エントリ作成ができる**（AC-17 空コマ編集可）。
- **時間割を持たない自由テーマの導線（社会人・日記ユーザー）**: `linked_slot_kind`/`linked_slot_id` を持たない自由テーマ（`source_type` が PROJECT/DIARY/FREE）の当日エントリ／テーマも today ビューに **`slotKind=null`（コマ非依存）の item として列挙**する。時間割を持たない社会人・日記ユーザーはこれが主導線になる。したがって `ReflectionTodayResponse.items[]` には「時間割コマ由来 item」（`source_kind`/`slot_id` を持つ）と「自由テーマ由来 item」（`slotKind=null`・コマ非紐付け）の両方が混在する。FE は `slotKind` の有無で両者を描き分ける。
- **「今日」はユーザー TZ 基準でサーバが算出**する（`?date=` 省略時はサーバが `resolveUserZone(userId)` の今日を採用）。クライアントが `?date=` を送る場合はサーバ側で日付フォーマット・範囲（§2.5.1 (c)）を検証する。
- **各コマの保存は個別**（コマ単位の `PUT /reflections/entries` / upsert）。**楽観排他 409**: `reflection_entries` に楽観ロック（`updated_at` ベース or `@Version`）を持たせ、更新リクエストに `expected_updated_at`（または version）を含めて不一致なら 409（AC-18）。

> **楽観排他（確定）**: `reflection_entries` に `version BIGINT NOT NULL DEFAULT 0` 列（@Version）を持つ（§2.2 に記載済み）。PUT upsert は `expectedVersion` を受け取り、既存更新で不一致なら 409（AC-18）。`updated_at` 比較より version の方が厳密ゆえこちらを採用。新規作成時は `expectedVersion=null`。

## 5. 間隔反復バッチ・通知設計

### 5.1 手本の確認

- `ActionMemoReminderBatchService`: `@Scheduled(cron = "0 * * * * *")`（毎分）＋`@SchedulerLock(name=..., lockAtMostFor="PT50S", lockAtLeastFor="PT0S")`。`ZonedDateTime.now(UTC)` を各ユーザー TZ（`UserRepository.findTimezoneById` → `ZoneId.of`、失敗時 `Asia/Tokyo` フォールバック）に変換して分単位一致を判定。`@BatchEndpoint` 付与。
- `ScheduleReminderBatchService` → `ScheduleReminderService.processScheduledReminders()`: 絶対時刻 due 判定（`remind_at <= now`）＋未送信（`is_sent=false`）のみ対象、送信後 `markAsSent()`＋save で **status 遷移による二重送信防止**。`remind_at` は保存時 `Asia/Tokyo` の `LocalDateTime` に正規化。

### 5.2 `ReflectionSpacedReminderBatchService` 設計

reflection は **絶対日時 `remind_at` を予約行に持つ**ため、`ScheduleReminderService.processScheduledReminders()` 型（絶対時刻＋status 遷移）を主たる手本にする。ユーザー TZ は `remind_at` 生成時（§5.3）に織り込むため、バッチ本体は UTC/JST 比較のみでよい。

```java
@Slf4j @Service @RequiredArgsConstructor
public class ReflectionSpacedReminderBatchService {

    private final ReflectionSpacedReminderService reminderService;

    @BatchEndpoint(name = "reflection-spaced-reminder",
        description = "振り返りの間隔反復／考査前リマインドを1分毎に実効時刻判定して送信する")
    @Scheduled(fixedDelay = 60_000)                          // 1分間隔（ScheduleReminderBatch と同型）
    @SchedulerLock(name = "reflectionSpacedReminderBatch",
                   lockAtLeastFor = "PT50S", lockAtMostFor = "PT2M")
    public void runBatch() {
        try {
            reminderService.processDueReminders();
        } catch (Exception e) {
            log.error("振り返りリマインダーバッチ処理失敗: error={}", e.getMessage(), e);
        }
    }
}
```

`ReflectionSpacedReminderService.processDueReminders()`（`@Transactional`）:

```
now = LocalDateTime.now()                                   // JST（STORAGE_ZONE と一致）
due = reminderRepo.findByStatusAndRemindAtLessThanEqual(PENDING, now)   // idx_..._due 利用
for r in due:
    entry/theme の親存在チェック（不在 or 論理削除済み → r.status=CANCELLED; save; continue）   // 孤児 fail-safe
    notificationHelper.notify(
        r.userId, "REFLECTION_RECALL_REMINDER", title, body,
        "REFLECTION", null,                                 // sourceId は UUID 非対応のため null（単一宛 notify は filter を通らず本人配信・§5.4）
        NotificationScopeType.PERSONAL, r.userId,
        actionUrl, null)
    r.markAsSent()                                          // status=SENT, sent_at=now
    reminderRepo.save(r)                                    // status 遷移で二重送信防止（AC-10）
```

- **毎分 1 回だけ送信（AC-10）**: `status=PENDING` のみ対象＋送信直後 `SENT` 遷移。`@SchedulerLock` で複数インスタンスの重複起動を防止（AC-11）。
- **ユーザー TZ（AC-11）**: `remind_at` 生成時にユーザー TZ で「予定の日付の所定時刻（例 朝 8 時）」を算出し JST 正規化済みのため、バッチは単純な絶対時刻比較で TZ 正しく発火する。

### 5.3 `remind_at` の生成（ユーザー TZ 織り込み）

エントリ保存時（§3 の想起予定登録・AC-9）に、`recall_interval_days` の各間隔について行を作る：

```
zone = resolveUserZone(userId)                              // ActionMemo と同じ解決（失敗時 Asia/Tokyo）
remindHour = userReflectionSettingsService.remindHour(userId)   // 既定8時・ユーザー設定（§2.7）
for i in [1,3,7,14]:
    LocalDate dueDate = entry.targetDate.plusDays(i)
    ZonedDateTime zdt = dueDate.atTime(remindHour, 0).atZone(zone)
    LocalDateTime remindAtJst = zdt.withZoneSameInstant(STORAGE_ZONE).toLocalDateTime()
    create reflection_spaced_reminders(entryId=entry.id, userId, remindAt=remindAtJst,
                                       intervalDays=i, kind=SPACED, status=PENDING)
```

**`REMIND_HOUR`（確定）**: **ユーザーごとに設定可能**（§2.7 `user_reflection_settings.remind_hour`・マスター御裁可 2026-06-20＝夜学習の学生に対応）。`userReflectionSettingsService.remindHour(userId)` で解決し、**未設定ユーザーは既定 8 時（ユーザー TZ）**。既定値はアプリ定数 `ReflectionConstants.DEFAULT_REMIND_HOUR = 8` で保持。`GET/PUT /api/v1/me/reflections/settings`（§2.7）で取得・更新する。

### 5.4 通知の発火（`NotificationHelper.notify`）

```java
notificationHelper.notify(
    userId,
    "REFLECTION_RECALL_REMINDER",                           // 新規通知種別
    "振り返りの想起テスト",                                  // title（i18n: notification.reflection.recall.title）
    "○○の振り返りを思い出してみましょう",                    // body（テーマ名のみ・本文は含めない＝プライバシー）
    "REFLECTION",                                            // sourceType
    null,                                                    // sourceId（注記参照）
    NotificationScopeType.PERSONAL,
    userId,                                                  // scopeId = 本人
    "/reflections/recall?entry=" + entry.id,                // actionUrl
    null);                                                  // actorId
```

注記:
- `NotificationHelper.notify(...)` の `sourceId` は **`Long`** 型。reflection エントリは UUID 主キーのため `sourceId` には UUID を載せられない。よって `sourceId=null` とし、対象エントリは `actionUrl` のクエリ（`entry={uuid}`）で運ぶ。
- **【事実訂正】単一宛 `notify` は recipient filter を通らない**: `filterAccessibleRecipients`（F00 委譲フィルタ）を経由するのは `notifyAll` 系（複数受信者宛）のみであり、本機能が使う**単一ユーザー宛 `notify(...)` はそもそも recipient filter を通らず、本人宛に無条件配信される**（`NotificationHelper.notify` → `createNotification` → `dispatch` の直線経路）。したがって `sourceId=null` でも配信に影響はない。「filter が `sourceId==null` で素通しする」という挙動は `notifyAll` 系の話であって、本機能の単一宛配信には**無関係**である。リマインダーは本人（受信者＝発火対象本人）宛 PERSONAL 通知なので、可視性漏洩の懸念もない。
- 通知 body には**振り返り本文を含めない**（テーマ名のみ）。行動メモリマインドの「メモ内容を含めない」方針に倣う（プライバシー）。
- PRE_EXAM（総まとめ）も同じ `notify` で title/body/actionUrl を考査向けに差し替えて送る。

### 5.5 考査前リマインド（AC-12）と二重送信・キャンセル

- `reflection_themes.exam_date` を設定すると、その theme について `PRE_EXAM` 行を **14/7/3/1 日前**に 4 件生成（`interval_days` に負号でなく「考査N日前」の N を入れ、`remind_at = exam_date.minusDays(N) の所定時刻`）。
- **過去日ガード（確定）**: 各 PRE_EXAM 行は `remind_at` が**現在時刻より過去になる場合は生成しない**（スキップ）。とくに `exam_date` 自体が過去日の場合は 4 行すべてが過去になり生成 0 件となる。これにより「過去日の考査を設定した瞬間に 4 件が即 due 発火する」スパムを防ぐ。`exam_date` を過去日で設定すること自体は許容するが、その場合 PRE_EXAM リマインダーは作られない（UI は「過去日のためリマインドは生成されません」を表示する想定）。
- `exam_date` 変更時は **既存 PENDING の PRE_EXAM 行を CANCELLED にして作り直す**（再生成）。送信済み（SENT）は残す。
- theme/entry 削除時は関連 PENDING 行を `CANCELLED` 遷移（§2.5 の孤児 fail-safe と二重防御）。
- **同日複数想起の通知集約（任意改善）**: 同一ユーザーに同じ日・同じ時刻帯で複数の想起通知が due になる場合、1 件にまとめて「N 件の振り返りが想起待ちです」と集約配信する余地がある。**MVP は個別通知**（1 リマインダー＝1 通知）とし、集約は後続フェーズの任意改善とする（§9.1）。

## 6. F00 可視性・カレンダー連携・ブログ輸出

### 6.1 F00 可視性（`ReflectionEntryVisibilityResolver`）

- `ReferenceType` に **`REFLECTION_ENTRY` を追加**。reflection_entries は **UUIDv7 主キー**のため `idKind()` は `UUID_V7` 経路（`MATCH` と同様に `idKind()` の switch に追加）。Resolver は `canViewUuid` / `filterAccessibleUuid` を**自前実装**する。
  - 注: 既存 `corkboard_cards.reference_id_uuid` 経路（F00-A 案）に整合。コルクボード引用が不要なら `canViewUuid` 経路のみ実装（`MATCH` と同様）。
- **【実装方式の訂正】`AbstractContentVisibilityResolver` は継承しない**。`AbstractContentVisibilityResolver` の `canView`/`decide`/`filterAccessible` は **`final`** で **Long 経路（`contentId` が `Long`）専用**に固定されており、テンプレートメソッド（`loadProjections`/`toStandard`）も Long contentId を前提とする。UUID 主キーの reflection_entries では機能しない。実在の UUID 経路 Resolver **`MatchVisibilityResolver`（`backend/.../match/visibility/MatchVisibilityResolver.java`）を手本**にし、`ReflectionEntryVisibilityResolver implements ContentVisibilityResolver<Enum<?>>` として **`canViewUuid` / `filterAccessibleUuid` を自前実装**する（Long 経路 `canView`/`filterAccessible` は `MatchVisibilityResolver` 同様 **fail-closed**＝`false`／`Collections.emptySet()` を返す）。
  - `canViewUuid` 内で entry の `user_id`・`visibility`・親 theme の `visibility` を引き、reflection visibility（PRIVATE/将来 FAMILY_SHARED）で判定する。**MVP は PRIVATE 固定**ゆえ「viewer == 所有者（`entry.user_id == viewerId`）」判定で十分（本人のみ可視）。`filterAccessibleUuid` は所有エントリ UUID 群のみ通す。
  - reflection visibility → `StandardVisibility` マッピング（将来 FAMILY_SHARED 追加時の拡張点）：

  | reflection visibility | StandardVisibility | 意味 |
  |---|---|---|
  | `PRIVATE` | `PRIVATE` | 作成者本人のみ（**MVP は PRIVATE 固定**・AC-13） |

  **FAMILY_SHARED（保護者による学習内容の確認）は別軍議で詰める**（マスター御諚 2026-06-20・§9.1）。保護者が子の振り返りを閲覧するニーズは正当だが、家族共有先テーブル（F03.15 `personal_timetable_share_targets` 相当）・未成年/保護者同意・閲覧範囲（保護者にマスク中 original を見せるか等）の判断が重く、独立フィーチャーとして切り出す。本 MVP は visibility 列を持つが値は `PRIVATE` 固定（CHECK で強制）。

- **fail-closed**: viewer 不明・データ不整合・entry/theme 欠落は deny（`MatchVisibilityResolver` の UUID 経路と同方針＝`canViewUuid` は false、`filterAccessibleUuid` は空集合を返す）。
- **マスク × 可視性は直交**: 可視性で「閲覧してよい人か」を判定し、閲覧可の人にも §3 のマスクが効く（自分の過去エントリを想起テストするため）。MVP は PRIVATE 固定ゆえ閲覧者＝本人のみだが、マスク判定（§3.1）は閲覧者に依らずエントリ単位で決まり、本文は §3.2 でソースから null になる。よって**将来 FAMILY_SHARED を別軍議で追加しても、マスク中は保護者にも original が漏れない（AC-15 の構造担保が先行して効く）**。Resolver は MVP から設置し、カレンダー印を F00 経由でフィルタする（AC-14 の保険・将来の家族閲覧の土台）。

### 6.2 カレンダー連携（独立 enrich パス・F00 UUID 経路・AC-14）

横断カレンダー `GET /api/v1/my/calendar` の実体は **`ScheduleQueryService.getMyCalendar(userId, from, to)`**（`ScheduleService` は委譲。`ScheduleCommonController` 入口）。既存の合流ロジックは `ContentVisibilityChecker.filterAccessible(ReferenceType.SCHEDULE, List<Long>, userId)` の **Long 経路に固定**で `ScheduleEntity`（Long PK）に密結合しており、reflection の UUID 主キーをそのまま既存パスに載せられない（`CalendarEntryResponse.id` も `Long` 型）。

**設計（確定）— 既存 schedule 合流とは別の独立 enrich パスで合流する**:

- reflection 印（reflection エントリ＝target_date／想起予定＝remind_at の日付）は、**既存 schedule 合流ロジックを一切改変せず**、`getMyCalendar` の **return 直前に別途 enrich する独立パス**で追加する。具体的には reflection 側で対象 UUID 群を集め、`ContentVisibilityChecker.canViewUuid(REFLECTION_ENTRY, entryUuid, viewerId)` ／ `filterAccessibleUuid(REFLECTION_ENTRY, uuids, viewerId)`（§6.1 の UUID 経路 Resolver 経由）でフィルタしてから `CalendarEntryResponse` に変換し、既存リストへ `add` する。Long 経路（SCHEDULE）と UUID 経路（REFLECTION_ENTRY）が混ざらないため型破綻しない。
- **`CalendarEntryResponse.id` は reflection 行では `null`**。reflection 行の識別は `content.referenceUuid`（string）＋`content.referenceKind`（例 `REFLECTION_ENTRY`／`REFLECTION_RECALL`／`REFLECTION_PRE_EXAM`）で行い、**FE は `referenceUuid` を一意キーに使う**（id ではなく）。
- **後方互換の要確認事項（実装時）**: `CalendarEntryResponse.id` を null 許容にする変更が、**既存 FE が `id` を非 null 前提（一意キー・v-for key 等）にしていないか**を実装時に必ず確認する。既存 schedule 行は従来どおり `id`（Long）非 null、reflection 行のみ `id=null` で `referenceUuid` 非 null になる。既存 FE が壊れる場合は、reflection 行に「`id` を使わせない」描画分岐を FE 側に入れる（`referenceUuid` 有無で分岐）。
- **F00 漏洩防止**: 本人のカレンダーなので基本は全件可視だが、上記 UUID 経路フィルタを必ず通す（家族カレンダー（将来 FAMILY_SHARED・§9.1）でも F00 が漏洩を止める保険）。
- カレンダー表示内容:
  - `content.title` = theme タイトル（**マスク中でも theme タイトルは出してよい**＝§3.2 の maskedHint と同基準。本文 structured_content はカレンダーに載せない）。
  - `content.eventType` = `"REFLECTION_ENTRY"`（振り返りエントリ）・`"REFLECTION_RECALL"`（SPACED 間隔反復の想起予定）・`"REFLECTION_PRE_EXAM"`（考査前総まとめの想起予定）のいずれか。FE はこの値でクリック時の遷移先を切り替える（`REFLECTION_RECALL`→recall 画面 `?entry={referenceUuid}`、`REFLECTION_PRE_EXAM`→テーマ詳細 `/reflections/themes/{referenceUuid}`、その他→エントリ詳細 `/reflections/entries/{referenceUuid}`）。
  - `time.allDay = true`（日付ベース）。`scope.scopeType="PERSONAL"`。
- **A3 — `CalendarContentDto` は record（ソース変更を伴う）**: `CalendarEntryResponse.content` の型 `CalendarContentDto` は **record**（正準コンストラクタ `(String title, String eventType, String status)`）。`referenceUuid`／`referenceKind` を足すと **正準コンストラクタの変更**を伴い、既存の構築側（`ScheduleQueryService` の `CalendarContentDto` 生成箇所）も新引数に追従する必要がある。**API レスポンス JSON は後方互換**（新フィールドが増えるだけ）だが、**Java ソース上は record 変更ゆえ全構築箇所のコンパイル追従が必須**である点を実装時に留意する。

### 6.3 ブログ輸出（AC-20）

- `POST /api/v1/me/reflections/entries/{entryId}/export-to-blog` で、entry の `structured_content` を Markdown/HTML 本文へ整形し、`BlogPostService.createPost(userId, CreateBlogPostRequest)`（個人ブログ）を呼ぶ。
- **【訂正】visibility は `PRIVATE` を必ず明示設定する**: `BlogPostService.createPost` は `CreateBlogPostRequest.visibility` が未指定（null）のとき既定で **`MEMBERS_ONLY`**（BlogPostService.java:182-183）になり、reflection の PRIVATE 前提に反して意図せずメンバー公開されてしまう。よって輸出時は **`CreateBlogPostRequest.visibility = "PRIVATE"` を必ず明示設定**する（未指定にしない）。その後ユーザーが公開したい時に blog 側で publish する。
- **輸出後も元 reflection エントリは残す**（AC-20）。輸出済みを示すため `reflection_entries.exported_blog_post_id BIGINT NULL`（blog ドメイン ID・FK なし）を持つ（§2.2 記載済み・確定）。同列が非 NULL なら再輸出を 409 でブロック（MVP は再輸出ブロック、更新輸出は後続）。元エントリの削除は輸出と独立。
- **輸出は時点の静的コピー（同期しない）**: 輸出はその時点の本文を blog 記事へコピーするだけで、**輸出後にエントリを編集してもブログ記事は自動同期しない**（更新輸出は後続フェーズ・§9.1）。FE は「輸出後に編集済み」バッジ等の表示を検討する（判定可能条件＝`exported_blog_post_id` 非 NULL かつ `entry.updated_at > 輸出時刻`。輸出時刻は blog 記事の `created_at` で代用可）。
- 共有は `BlogPostService.sharePost(postId, userId, SharePostRequest)` を流用（個人ブログをチーム/組織へ共有する既存導線）。

## 11. Phase 2: 科目紐づけ拡張

> Phase 2 ステータス: 🟢 設計完了（マスター御裁可 2026-06-22 / 案B確定・残論点ゼロ・実装着手可）

### §11.0 概要・前提

#### 目的

Phase 1 では「時間割の特定スロット（linked_slot_id）」にテーマを紐づける設計を確立した。しかしこの設計では**今日ビューの空きコマからしか科目紐づけができない** UX 欠落がある。例えば「数学が月・水の2コマあるが、テーマ設定ダイアログから科目「数学」全体に一括紐づけしたい」という用途に対応できない。

Phase 2 ではテーマを**「時間割の科目（subject_name）」単位で紐づける**機能を追加し、今日ビューでその科目の**当日全コマ**に振り返り導線を出す。

#### 軽量方針

- **科目マスタ（subjects テーブル）は新設しない**。timetable ドメインの DDL は一切変更しない。
- reflection 側で時間割スロットを科目名（＋履修番号 course_code）で重複排除して選択肢化する（既存スロットの論理表現を再利用）。
- 「数学が週2コマでも候補は1つ（重複排除）」「数学1と数学Aは別候補」を満たす。

#### 後方互換

既存テーマは新カラム NULL → 従来の `linked_slot_id` 経路で当該スロットに表示（Phase 1 動作を完全維持）。

---

### §11.1 紐づけ方式（案B 確定）

#### reflection_themes への新カラム追加

`reflection_themes` に以下の2列を追加する:

| カラム | 型 | 説明 |
|---|---|---|
| `linked_subject_name` | `VARCHAR(200) NULL` | 科目名で紐づける場合に設定。`personal_timetable_slots.subject_name` と合わせる |
| `linked_course_code` | `VARCHAR(50) NULL` | 履修番号で紐づける場合に補完設定。`personal_timetable_slots.course_code` と合わせる（TEAM コマは常に NULL） |

どちらも NULL 可。`linked_slot_id` との共存を許容する（後述の照合ロジック参照）。

#### 今日ビュー照合ロジックの作り替え（2系統 Map 構造）

> **照合対象は当日コマのみ**（`getTimetableToday(userId, today)` が返すコマ）。週全体スロットは `linkable-slots` EP の候補選択専用であり、今日ビューの照合には使わない。

`ReflectionTodayService` が保持する照合用 Map を以下の **2系統** に作り替える（現行の1系統 `Map<String,Theme>` は廃止）:

```
【ステップ1: Map の構築】
ユーザーのテーマ一覧を読み込み、2つの Map に振り分ける:

  bySlotKey   : Map<String, Theme>         キー = "kind:slotId"
                linked_slot_id を持つテーマを登録（条件A用・既存）

  bySubjectKey: Map<String, List<Theme>>   キー =
                  PERSONAL → "PERSONAL:subjectName:courseCode"
                  TEAM     → "TEAM:subjectName"
                linked_subject_name を持ち linked_slot_id を持たないテーマを登録
                （条件B用）

  両方持つテーマ（linked_slot_id も linked_subject_name も非NULL）は
  bySlotKey にのみ登録する（条件A優先・条件Bには落とさない）。

【ステップ2: 当日コマへの照合】
getTimetableToday(userId, today) が返す各コマを順番に処理する:

  consumedThemeIds: Set<ThemeId>（今日ビューで既にコマ表示済みのテーマ）

  各コマ slot に対して:
    1) bySlotKey.get("kind:slotId") がヒットする場合
       → そのテーマで item 化し consumedThemeIds に add（条件A優先）
       → このコマには条件Bを適用しない（A/Bの重複表示を防ぐ）

    2) ヒットしない場合
       → キーを組み立てる（PERSONAL→"PERSONAL:subjectName:courseCode"、TEAM→"TEAM:subjectName"）
       → bySubjectKey.get(キー) の全テーマを item 化
         （同科目複数テーマ存在時は複数 item・将来拡張として許容）
       → 各 themeId を consumedThemeIds に add

【ステップ3: 自由テーマの列挙】
全テーマのうち consumedThemeIds に含まれないものを自由テーマ枠に列挙する。
条件Bでコマに乗ったテーマは consumedThemeIds に含まれるため
自由テーマ枠には出ない（二重列挙の回避）。
```

**同一コマに条件A・条件B両方がマッチする場合、条件A（特定スロット）を優先し、条件Bは条件Aで claimされなかったコマにのみ適用する。**

#### subjectName の表示方法（条件A vs 条件B で異なる）

| 条件 | コマの subjectName 表示 |
|---|---|
| **条件A**（特定スロット紐づけ） | **テーマ名で上書き**（Phase 1 動作を後方互換維持）|
| **条件B**（科目名紐づけ） | **コマの科目名をそのまま表示**（上書きしない）。テーマ情報は Phase 1 で追加した `themeTitle` メタフィールドで表示する |

条件Bでコマに乗るテーマは「この科目全体に紐づく」という性質のため、コマの科目名を上書きすると UX 上の混乱を招く。`themeTitle` に振り返りのタイトルを持たせ、コマ科目名と共存して表示する。

#### TEAM コマの注意事項

`timetable_slots`（チーム時間割）には `course_code` 列が存在しない。したがって **kind=TEAM の照合は `subject_name` のみ**とし、`course_code` は PERSONAL 専用の細粒度識別として使う。同名異科目の誤マッチ余地は許容（御裁可済・§11.8 に明記）。

#### 実装注意（toBuilder 禁止）

`ReflectionThemeEntity.applyUpdate` は `toBuilder()` 禁止（UuidV7Entity 継承の既知バグ・§2.2 の警告参照）。新カラム `linked_subject_name`/`linked_course_code` の更新も**直接ミューテートのセッター追加**で揃える。

手本: 既存 `applyUpdate`（`TimetableChangeEntity` L81-98 / `IncidentBannerEntity.update` L136-143）。null ＝ 現値維持セマンティクスを使い、null 渡しで「解除」したい場合は `clearLinkedSubject()` 相当のメソッドを別途用意する。

#### セキュリティ注記

`linkable-slots` と今日ビュー照合の双方で `SecurityUtils.getCurrentUserId()` によるユーザースコープが保証される。他ユーザーのスロット・テーマを誤って照合する経路はない。

### §12.1 学年・学期モデル

#### 方式（御裁可: 実値保持＋個人時間割から自動提案）

`reflection_themes` に以下の2列を追加する:

| カラム | 型 | 説明 |
|---|---|---|
| `academic_year` | `SMALLINT NULL` | 学年度（例: 2026）。自由数値で年度体系を問わない |
| `term_label` | `VARCHAR(50) NULL` | 学期ラベル（例: 「1学期」「前期」「Q1」）。自由文字列（enum 化しない） |

**実値保持**: カラムには入力時の実際の値を保存する。進級・時間割変更後もテーマの学年・学期値は不変（記録当時の情報を正確に保持）。

**term_label を自由文字列にする理由**: 3学期制（1学期/2学期/3学期）・2学期制（前期/後期）・クォーター制（Q1/Q2/Q3/Q4）等、学校・組織によって体系が異なる。既存の `timetable_terms.name`・`PersonalTimetableEntity.termLabel` も自由文字列（VARCHAR）を採用しており、本フィールドはこれと同じ表記形式で統一する。

#### 自動提案（テーマ作成/編集 UI）— 専用 EP 方式

テーマ作成/編集時、`academic_year`・`term_label` の初期値をサーバが自動提案する仕組みを設ける。

**専用 EP**: `GET /api/v1/me/reflections/term-suggestion?baseDate=YYYY-MM-DD`

| 項目 | 内容 |
|---|---|
| **メソッド** | GET |
| **パス** | `/api/v1/me/reflections/term-suggestion` |
| **クエリパラメータ** | `baseDate` (String `YYYY-MM-DD`、任意。省略時は今日（ユーザー TZ・§3.1 と同基準）を使用) |
| **認可** | 認証必須・本人スコープ |
| **200 レスポンス** | `{ "academicYear": Integer \| null, "termLabel": String \| null }` |
| **主なエラー** | 401 |

FE はダイアログ open 時、および examDate 変更時に本 EP を呼び出す。作成前でも examDate 未保存をクエリパラメータで渡せるため「作成前か保存後か」の曖昧さがない。

```
基準日 = baseDate クエリパラメータ（指定なしは今日・ユーザー TZ・§3.1 と同基準）

本人の personal_timetables のうち
  status = ACTIVE（PersonalTimetableStatus.ACTIVE）かつ
  effectiveFrom <= 基準日 <= effectiveUntil（effectiveUntil IS NULL は今後有効とみなす）
に該当するエントリの academicYear / termLabel を初期値として提案。

DRAFT・ARCHIVED の時間割は提案に含めない（term-suggestion の目的は「現在有効な」時間割からの提案であるため）。

該当が複数ある場合は effectiveFrom が最も近い（遅い＝最新）ものを採用。
該当が1件もない場合は { academicYear: null, termLabel: null } を返す（FE は空表示）。
```

**timetable ドメイン Service メソッド**（D-1 越境依存禁止・Service 経由）:

`PersonalTimetableService`（または `DashboardService`）に以下のメソッドを新設する:

```java
/**
 * 指定日時点で有効な個人時間割（status = ACTIVE のみ）を返す。
 * DRAFT・ARCHIVED は除外する（提案に混入しないよう）。
 * 複数該当時は effectiveFrom が最新のものを採用。
 * 該当なしは Optional.empty()。
 */
Optional<PersonalTimetableSummary> findEffectiveAt(Long userId, LocalDate date);
// 実装条件: status = PersonalTimetableStatus.ACTIVE
//           AND effectiveFrom <= date
//           AND (effectiveUntil IS NULL OR effectiveUntil >= date)
```

`PersonalTimetableSummary` は `academicYear`（Integer）と `termLabel`（String）を持つ値オブジェクト（DTO または record）。

データソースは Phase 2 の `linkable-slots` と同じ `personal_timetables` テーブル（`PersonalTimetableEntity.academicYear`・`termLabel`・`effectiveFrom`・`effectiveUntil`）。reflection ドメインから timetable ドメインの Repository/Entity へ直接アクセスしない（D-1 ArchUnit 越境依存禁止）。

**academicYear の型統一（🟠 Y）**: 源泉 `PersonalTimetableEntity.academicYear` は **Java フィールド型 `Integer`**（DB 列は `SMALLINT` だが Hibernate マッピングは `Integer`）。`PersonalTimetableSummary`・EP #22 レスポンス・reflection 側の全 DTO（`ReflectionThemeResponse`・`CreateReflectionThemeRequest`・`UpdateReflectionThemeRequest`・`ArchiveFolderResponse`・`BulkArchiveRequest`）において `academicYear` の Java/DTO/API 型を **`Integer`** に統一する（`Short` は使用しない）。DB 列は引き続き `SMALLINT`（年値は範囲十分）であるが、`@Column(columnDefinition = "SMALLINT")` でフィールド型は `Integer` にマッピングする。これにより源泉との型不一致と OpenAPI 生成型での `number` ブレを回避する。

ユーザーは提案値を確認・上書き可能。自動提案はあくまで入力補助であり、保存値は提案値ではなくユーザーが確定した値とする（AC-38）。

- `ReflectionSpacedReminderBatchService` の親テーマ存在チェック（アーカイブ済みテーマのリマインダーは CANCELLED に遷移）

**テーマ単位**でアーカイブする（`reflection_themes.archived_at` のみ更新）。配下の `reflection_entries` は `theme_id` FK の CASCADE 設計のため、テーマがアーカイブされても entry は物理的に存在し続ける。アーカイブ状態は theme.archived_at で一元管理し、entry 個別の archived_at は設けない（シンプルさ優先）。

「フォルダ（学年×学期×教科グループ）を一括アーカイブ」は `bulk-archive` API（§12.4）で実現する。DB 上は対象条件に合致するテーマ群それぞれの `archived_at` を同時にセットするだけであり、スキーマは変わらない。

#### リマインダー停止（御裁可: アーカイブ時に PENDING を CANCELLED）

アーカイブ操作時（`archived_at = now()`）に、当該テーマ配下のエントリに紐づく PENDING 状態のリマインダーを**スペースド・PRE_EXAM の両方とも CANCELLED に遷移**する。これにより過去学年の振り返りへの想起通知と考査前通知が止まる。

アーカイブ時にリマインダーを停止しなかった場合、**アーカイブ済みテーマの考査前通知（PRE_EXAM）が鳴り続ける**。この停止は既存の `deleteTheme` の完成パターンを踏襲する。

```
アーカイブ処理（ReflectionThemeService.archiveTheme）:
  1. theme.archived_at = now() セット
  2. テーマ配下の全 entry_id を取得
  3. SPACED リマインダー停止:
     ReflectionSpacedReminderService.cancelPendingForEntry(entryId)
     → 各 entryId について PENDING の reflection_spaced_reminders を CANCELLED に遷移
  4. PRE_EXAM リマインダー停止:
     ReflectionSpacedReminderService.cancelPendingPreExamForTheme(themeId)
     → UPDATE reflection_spaced_reminders
        SET status = 'CANCELLED'
        WHERE theme_id = :themeId AND type = 'PRE_EXAM' AND status = 'PENDING'
       （theme 由来の exam_date リマインダーをまとめて CANCELLED）
  5. theme 保存（@Transactional 内）
```

`status` の enum 値は実コードの `PENDING` / `SENT` / `CANCELLED` を使用する（他の値は存在しない）。

**復元時（archived_at = null）は CANCELLED リマインダーを自動再生成しない**。復元後に新規エントリを保存した際の通常フロー（§5.3）で新しいリマインダーが生成される。この仕様は AC-41 に明記する。

#### アーカイブ中 entry の GET 扱い

アーカイブはテーマの**分類操作**であり、アクセス制限ではない。テーマがアーカイブ済みであっても、配下 entry の GET（recall 詳細・entry 詳細）は引き続き可能とする（アーカイブ済みの記録を見返すことが本機能の目的であるため）。entry 系 API（`/entries/{id}` 等）には `archived_at` による除外を入れない。

### §12.3 単元階層（parent_theme_id）

#### 追加カラム

`reflection_themes` に以下の1列を追加する:

| カラム | 型 | 説明 |
|---|---|---|
| `parent_theme_id` | `BINARY(16) NULL` | 親テーマの ID（NULL＝トップレベル）。自己参照 FK |

#### 自己参照 FK の適法性（原則1への適合）

`parent_theme_id` は **`reflection_themes` テーブルへの自己参照**であり、クロスドメイン FK（原則1禁止）には該当しない。同一ドメイン内の自己参照 FK であるため設置可（原則2: CASCADE は同一ドメイン内のみ許可、に適合）。

削除時の挙動: `ON DELETE SET NULL`（親テーマ削除時、子テーマの `parent_theme_id` が NULL に更新されトップレベルへ昇格）。記録・entry は保持される（AC-44）。

#### 階層制約（2階層固定）

| 制約 | 内容 | バリデーション |
|---|---|---|
| 2階層固定（親の親禁止） | 親に指定するテーマ自身が `parent_theme_id` を持つ場合は 400 | サービス層で親の `parent_theme_id` を確認 |
| 自己ループ禁止 | 自分自身を親に指定すると 400 | `themeId == parentThemeId` で 400 |
| 他人テーマ親指定禁止 | 他ユーザーのテーマを親に指定すると 404（IDOR 非秘匿・§7 方針） | 親テーマの `user_id == currentUserId` を確認 |
| archived/deleted テーマへの子設定 | アーカイブ済みまたは削除済みテーマを親に指定すると 400 | 親テーマの `archived_at IS NULL AND deleted_at IS NULL` を確認 |

#### フォルダ表示（動的生成）

`(academic_year, term_label, linked_subject_name)` の GROUP BY で動的なフォルダ階層を生成する。 `parent_theme_id` は「教科テーマ（親）＞単元テーマ（子）」という明示的な親子関係を表現するための機能であり、フォルダ表示はスキーマ上の親子構造と直交して `(academic_year, term_label, linked_subject_name)` 集計で行う。

taxonomy 別テーブル（分類専用テーブル）は作らない。

#### parent_theme_id と今日ビュー分類の非干渉

`ReflectionTodayService` による今日ビューの分類（bySlotKey / bySubjectKey / freeThemes への振り分け）は `linkedSlotKind`・`linkedSubjectName` のみを判定基準とし、`parent_theme_id` は参照しない。`parent_theme_id` の設定有無は今日ビュー照合ロジックに一切影響しない。

#### EP #18: GET `/api/v1/me/reflections/archive/search`

| 項目 | 内容 |
|---|---|
| **メソッド** | GET |
| **パス** | `/api/v1/me/reflections/archive/search` |
| **概要** | アーカイブ済みテーマを 学年/学期/教科/キーワード の AND 条件で検索する |

### §12.9 非機能・後方互換・御裁可済み事項・残課題

#### 非機能

- **本人スコープ・PRIVATE 固定（Phase 1 方針を継続）**: F00 可視性対象外（自分の記録を自分が管理する）。アーカイブ済みテーマの閲覧も本人のみ。
- **UUIDv7・テナント方針継続**: `reflection_themes` の既存 `user_id BIGINT` 直持ち（`AbstractTenantAwareRepository` 非適用）の既存設計を踏襲。`parent_theme_id` の自己参照 FK も同一テーブル内であり新テーブルは不要。
- **パラメータ上限（DoS 対策）**: `GET /archive/search` の `size` 上限を 50 件とし、超過は 400。`POST /bulk-archive` は全件パラメータなし指定を 400 で拒否（§12.4）。
- **インデックス効率**: 複合インデックス `(user_id, academic_year, term_label, linked_subject_name, archived_at)` により、フォルダ集計・検索は `user_id` でインデックスシーク後に残列でフィルタ。自己参照 FK 用インデックス `(parent_theme_id)` で SET NULL 更新を高速化。

#### 後方互換

- 新列はすべて NULL デフォルト。既存テーマは新列 NULL のままで従来動作を完全維持（AC-45）。
- `archived_at IS NULL` 条件は `deleted_at IS NULL` と同様の追加フィルタであり、NULL が「アクティブ」を意味する既存 soft delete 方針と整合。
- Phase 1・Phase 2 の既存 EP・DTO・挙動はすべて変更なし。

#### 御裁可済み事項（マスター 2026-06-23）

| 番号 | 内容 |
|---|---|
| ① | 学年/学期＝実値保持＋個人時間割からの自動提案。`term_label` は自由文字列（enum 化しない） |
| ② | アーカイブは `archived_at` カラム・テーマ単位・`deleted_at` と独立。アーカイブ時に PENDING リマインダーを CANCELLED にし、復元時は自動再生成しない |
| ③ | 横断検索は `title`/`description` への LIKE（JSON 本文の全文検索は後続フェーズ） |
| ④ | 単元階層は `parent_theme_id` 自己参照・2階層固定。taxonomy 別テーブル不採用 |

#### 残課題（正直に明記）

- **JSON 本文（`structured_content`）の全文検索**: MVP では `title`/`description` への LIKE 検索のみ。本文内のキーワード横断検索は**後続フェーズ**で実装予定（生成列＋MySQL FULLTEXT または Elasticsearch 等の検討が必要。御裁可済み・スコープ外）。
- **学年/学期の入力 UI 詳細**: 年度の数値入力 vs 選択肢（既存時間割の `academicYear` 値から動的生成）の UX はフロントエンド設計フェーズで詳細化する。
- **`parent_theme_id` の FE 木構造 UI**: 2階層ツリー表示（教科＞単元の折りたたみ）の具体的な FE 実装は出陣フェーズで詳細化する。テーマ一覧 EP への `parentThemeId` フィルタパラメータ追加が必要になる見込み。

## 13. Phase 4: 暗記カード・テンプレート刷新・中見出し折りたたみ・期間横断単語帳

> Phase 4 ステータス: 🟡 設計レビュー中（マスター方針御裁可済み 2026-06-25 / 精査 2 パス＋実機 E2E 耐性クリティック前）

### §13.0 背景・課題と方針サマリ

**ユーザーの実感した課題（3 点）:**

1. **テンプレが「どれも同じ」に見える**: 既存テンプレ（NORMAL/DIARY/WORK/CLASS）は全 section が「アウトライン型（見出し→小見出し→詳細→補足）」で**構造が同一**。学習モードが根本的に変わるテンプレが無いため違いを感じにくい。
2. **中見出しが常時全展開で脳内摩擦が大きい**: `ReflectionStructuredEditor.vue` が `v-for` で全 section を常時展開しており、長い振り返りで一覧性が悪い（ADHD 配慮で初期摩擦を下げたい）。
3. **暗記カード（単語帳）的な学習がしたい**: 「最初は訳のみ表示で単語を入力、その次は逆」という方向交互の暗記学習を、既存の想起スケジュールに乗せたい。さらに**試験前に期間を指定して全エントリの暗記カードを横断的に通し学習**したい。

**マスター御裁可済みの方針（この通りに設計する・勝手に変えない）:**

| # | 方針 |
|---|---|
| 1 | **暗記カードの出題タイミング = 振り返りの想起スケジュールに相乗り**（新テーブル/SRS アルゴリズムを作らない）。エントリがマスク対象のときカードも一緒に出題。Anki 式の per-card 習熟度は別軍議へ（§13-I） |
| 2 | **答え合わせ = 自己採点**（REMEMBERED/PARTIAL/FORGOT・**エントリ単位**の既存方式を流用）。文字一致の自動採点はしない |
| 3 | **構造 = 中見出し（section）ごとに型を選べる**。型は `OUTLINE`（既存・既定）と `TERM_CARD`（暗記カード）。1 つの振り返りに文章 section と暗記カード section を混在可 |
| 4 | **テンプレート刷新**: 暗記カード型 section を初期生成する「単語帳（VOCAB）」テンプレを追加。これにより学習モードが根本的に異なるテンプレが揃い「どれも同じ」を解消 |
| 5 | **期間横断 単語帳ビュー（追加要望）**: 期間（from/to）を指定して全エントリの暗記カードを横断抽出し、独自単語帳として閲覧＋自己クイズできる。アプリ層抽出（新テーブル不要・`idx_reflection_entries_user_date` 利用）。**この自己クイズは `recall_attempts` を書き込まない**（スケジュール想起とは独立の学習補助）。方向はユーザーがトグル |

### §13-A. データモデル（`structured_content` JSON 拡張・DDL/Flyway 変更なし）

**新規 migration は不要**。`reflection_entries.structured_content` は JSON 列でスキーマレス（BE はテンプレ無関心）であるため、section に任意フィールドを足すだけで実現する。

#### A-1. section への型フィールド追加（後方互換）

- section に任意フィールド `type: "OUTLINE" | "TERM_CARD"` を追加する。
- **`type` 欠落時は `OUTLINE` とみなす**（後方互換・既存データ無改変）。既存エントリ・既存テンプレ・既存マスク挙動を一切壊さない（AC-50）。
- `TERM_CARD` の section は `cards: [ { "term": string, "meaning": string } ]` を持つ。`term`＝語句/表、`meaning`＝意味/裏。`subsections` は空配列でよい（TERM_CARD では `subsections` を使わない）。
- 逆に `OUTLINE` section は従来どおり `subsections[]` を持ち `cards` を持たない（または空配列）。

#### A-2. 拡張後 JSON スキーマ例（§2.3 と整合）

```json
{
  "main_theme": "英単語 Unit 5",
  "sections": [
    {
      "type": "OUTLINE",
      "heading": "今日のポイント",
      "subsections": [
        { "sub_heading": "語法", "detail": "look forward to -ing", "supplement": "to は前置詞" }
      ],
      "cards": []
    },
    {
      "type": "TERM_CARD",
      "heading": "今日の単語",
      "subsections": [],
      "cards": [
        { "term": "abandon", "meaning": "見捨てる、放棄する" },
        { "term": "ambiguous", "meaning": "曖昧な" }
      ]
    }
  ],
  "free_note": "綴りに注意"
}
```

- `type` 省略・`cards` 省略の旧形（§2.3 のスキーマそのまま）も**有効**として受理し、読取時に OUTLINE / `cards=[]` として正規化する。

#### A-3. 上限（DoS / JSON 肥大化防止・既存上限と整合）

§2.3 の既存上限（JSON 64KB、`sections` 最大 30、`main_theme`/`heading` 各 200 字 等）を踏襲しつつ、暗記カード用に以下を追加する。超過は **既存 `REFLECTION_CONTENT_INVALID = REFLECTION_007`（400）** で拒否（**新規エラーコード採番は不要**）。

| 項目 | 上限 | 備考 |
|---|---|---|
| section 最大数 | **30**（既存踏襲） | OUTLINE/TERM_CARD 合算 |
| 1 section あたり `cards` 枚数 | **50 枚** | 超過で 400（REFLECTION_007） |
| `card.term` 文字数 | **200 字**（既存 `heading` と同水準） | 超過で 400 |
| `card.meaning` 文字数 | **200 字** | 超過で 400 |
| JSON 全体サイズ | **64KB**（既存踏襲） | section/cards 合算後も適用 |
| `section.type` の値 | `OUTLINE` / `TERM_CARD` のみ | それ以外は 400（不正値） |

- **検証・サニタイズ拡張点（実メソッド名で精緻化）**: §2.3 で定義済みのサービス層 `ReflectionContentSanitizer`（origin/main）は public 入口 `sanitizeAndSerialize(JsonNode)` → 各 section を private `sanitizeSection(JsonNode)` で処理し、文字列は private `sanitize(String, int maxLength)`（内部で `HtmlSanitizer.sanitizePlainText` を呼び**全 HTML を純テキスト化**）に通す構造。これを以下のように拡張する。
  - `sanitizeSection` に **`type` 値の許可リスト検証**（`OUTLINE`/`TERM_CARD` 以外は `REFLECTION_CONTENT_INVALID`=400）を追加。
  - `sanitizeSection` に **TERM_CARD の `cards[]` 枚数（≤50）・各 `term`/`meaning` の文字数（≤200）検証**を追加。
  - **`cards[]` の各 `term`/`meaning` を既存 private `sanitize(String, maxLength)`（=`HtmlSanitizer.sanitizePlainText` 全 HTML 平文化）に通す**（`detail`/`supplement`/`heading` と完全に同経路）。選択的タグ除去ではなく全 HTML 平文化の既存実装に揃える。
  - 旧形（`type`/`cards` 欠落）の正規化（読取時に `type=OUTLINE`・`cards=[]` とみなす。なお BE 保存側 `sanitizeSection` は欠落フィールドを書き足さず素通ししてよい＝読取側 §13-A-1 の「欠落=OUTLINE」解釈で吸収）。
- **JSON はスキーマレスのまま**: BE Entity 側に新カラムを足さない。型・上限の保証はサニタイザ＝サービス層に閉じる（既存方針踏襲）。

#### A-4. FE 往復コンバータの必須改修（H-1・ロッシー問題の根治）

> **【必須・実コード裏取り済み】**: 現状 `frontend/app/composables/useReflectionStructuredContent.ts`（origin/main）の `toStructured()` / `toJsonNode()` / `normalizeSection()` は section を **`{ heading, subsections }` のみで再構築し `type`/`cards` を黙って捨てる**。`frontend/app/types/reflection.ts` の `ReflectionSection`/`ReflectionSubsection` にも `type`/`cards` フィールドが無い。このまま実装すると**暗記カードは保存も読取も消滅する**（サイレントデータ喪失）。以下を必須改修とする:

1. **型拡張**（`types/reflection.ts`）:
   - `ReflectionSection` に `type: 'OUTLINE' | 'TERM_CARD'`（必須・既定 OUTLINE）と `cards?: { term: string; meaning: string }[]` を追加。
   - カード行型 `ReflectionCard { term: string; meaning: string }` を新設（再利用）。
2. **往復コンバータ拡張**（`useReflectionStructuredContent.ts`）:
   - `toStructured`/`normalizeSection`: 受信 JSON の `type`（欠落時 `'OUTLINE'`）・`cards`（配列なら各 `{term, meaning}` に正規化、欠落時 `[]`）を**往復で保持**する。

### §13-B. 出題方向（交互）ロジック ※決定論（recall_attempts に非依存）

カードの出題方向は **「到来済み想起予定日（`≤ today` に絞った dueDates）の個数 `k`」のパリティ（偶奇）で決定論的に算出**する（ユーザー要望「最初は訳のみ表示で単語を入力、その次は逆」を厳密化）。

> **【決定論化の理由・最重要】**: 当初は `recall_attempts` 件数（`COUNT(*)`）のパリティ案だったが、実装 `RecallService.recordRecall` は **due ガード無しで何度でも保存でき（同日重複・非 due でも可）**、一方 §3.1 のマスク判定は `dLast` 以降の**最新 1 件**しか見ないため、`COUNT` は「到来済み想起回数」と乖離し**方向が非決定的**になる（同じ画面を開くたびに向きが変わりうる）。これを避けるため、方向を **`recall_attempts` 件数に依存させず**、§3.1 のマスク判定と**同一の真実源（`≤ today` 絞り込み後の dueDates）**だけで算出する（真実源メソッドの是正は §13-B-1 の callout 参照）。

#### B-1. 算出式（theme intervals + target_date + today のみで定まる・完全決定論）

`k` は **§3.1 の `isMasked` 内で算出している「到来済み想起予定日（`≤ today` に絞った dueDates）」の個数**である。

> **【真実源の是正・必須】**: 既存の公開メソッド `ReflectionMaskEvaluator.dueRecallDates(entry, theme, today)`（origin/main）は **`today` でフィルタせず全予定日（例 1,3,7,14 なら 4 件）を返す**（maskedHint 表示用）。これをそのまま `.size()` すると **`k` が定数化（常に 4）して方向が交互しなくなる（AC-52 破綻）**。よって**このメソッドを `k` の算出に流用してはならない**。`isMasked` のローカルにある `≤ today` フィルタ済み集合（`ReflectionMaskEvaluator.java` の `for (int i : intervals) { LocalDate d = target.plusDays(i); if (!d.isAfter(today)) dueDates.add(d); }`）を、**新規共通メソッド `arrivedDueDates(entry, theme, today)`（`≤ today` 絞り込み後の集合を返す）として切り出し**、`isMasked` と方向算出の両方がこれを使う（単一真実源）。`dueRecallDates`（全件返す・maskedHint 表示専用）は残置し用途を分ける。

```
arrivedDueDates = theme.recall_interval_days(例 1,3,7,14) を entry.target_date に加算し、
                  today 以下に絞った集合       // ★ ≤ today フィルタ必須（§3.1 の isMasked と同一計算）
k = |arrivedDueDates|                   // 到来済み想起予定日の個数（k ≥ 1 のときのみカード出題＝マスク中）
n = k - 1                               // 0 始まりのスロット番号
direction =  n が偶数 → MEANING_TO_TERM // 意味を表示し語句を入力（初回 n=0）
             n が奇数 → TERM_TO_MEANING // 語句を表示し意味を入力（次の予定日で逆）
```

- これは **`theme.recall_interval_days` + `entry.target_date` + `today` のみ**で定まり、**`recall_attempts` に一切依存しない**＝完全決定論。同じ日に何度開いても同じ向き。
- **`today` が進むと `k` が 1,2,3,4 と増える**（1 日後到来→k=1→MEANING_TO_TERM、3 日後到来→k=2→TERM_TO_MEANING …）ため方向が交互する。`≤ today` フィルタを欠くと `k` が定数化して交互しない点が本項の肝。
- §3.1 のマスク判定（同じ `arrivedDueDates` を使う）と**同一の真実源**を使うため、マスク中（k ≥ 1）のときだけカード出題され、方向も矛盾なく定まる。

#### B-2. 方向の単位・配信

- **方向の単位は section 全体**: その回は当該カード section の**全カードが同じ向き**（予測可能・混乱しない）。カードごとに向きが変わると学習者が混乱するため section 一括とする。
- **方向は BE が算出して返す**（FE に秘匿ロジックを置かない・漏洩経路を作らない）。`ReflectionEntryResponse.maskedHint` に `recallDirection: "MEANING_TO_TERM" | "TERM_TO_MEANING"` を追加する。
- **FORGOT 再提示との関係（正しい定義）**: FORGOT で翌日 SPACED 再生成（既存 AC-22）しても、再提示が**同一の due slot 内**（同じ `dLast`・`k` が変わらない）であれば **`k` は不変ゆえ同じ向きで再テスト**される。**方向が変わるのは次の想起予定日が到来し `k` が +1 されたとき**（例 1 日後スロット → 3 日後スロットへ進んだとき）。つまり「同一 due slot の再提示は同方向（同じ向きで覚え直し）／次の予定日で逆向き」となる。これは間隔反復として妥当（同一スロットは同条件で覚え直し、次スロットで角度を変える）。

### §13-C. マスク時のカード表示（セキュリティ核心・fail-closed）

§3.2 の「マスク中は original をどの応答にも乗せない」原則を暗記カードへ拡張する。**`ReflectionEntryResponseMapper` がこの分離の唯一の生成口**である（既存方針踏襲）。

`isMasked == true` のとき:

| section 型 | マスク中の挙動 |
|---|---|
| **OUTLINE** | 従来どおり**完全非表示**（`structuredContent = null`。記憶から想起→ recall で開示）。回帰なし（AC-56） |
| **TERM_CARD** | 出題方向の **cue 側（表示側）だけ**を返す。**答え側はレスポンスに一切含めない**（null を入れるのではなく**フィールド自体を載せない**＝fail-closed・漏洩ゼロ） |

- マスク中の TERM_CARD は `structuredContent`（original 全文）には**含めず**、`maskedHint` 内の新フィールドにだけ cue を載せる。提案する形:

```json
"maskedHint": {
  "themeTitle": "英単語 Unit 5",
  "targetDate": "2026-06-20",
  "dueRecallDates": ["2026-06-21"],
  "cardQuiz": [
    {
      "heading": "今日の単語",
      "direction": "MEANING_TO_TERM",
      "prompts": [
        { "promptSide": "MEANING", "promptText": "見捨てる、放棄する" },
        { "promptSide": "MEANING", "promptText": "曖昧な" }
      ]
    }
  ]
}
```

- `maskedHint.dueRecallDates` は既存 DTO のフィールド名（`ReflectionEntryResponse.maskedHint().dueRecallDates()`）。Phase 4 で新規に増やすのは `recallDirection` と `cardQuiz` のみ。`dueRecallDates` は **maskedHint 表示用の全予定日**（既存 `dueRecallDates` メソッドの全件返却・§13-B-1 で `k` 算出に使う新 `arrivedDueDates`（≤today 絞り込み）とは別物。表示は全予定でよい）。
- `direction == MEANING_TO_TERM` のとき `promptSide="MEANING"`・`promptText` に `meaning` のみ。**`term`（答え）は一切載らない**。
- `direction == TERM_TO_MEANING` のとき `promptSide="TERM"`・`promptText` に `term` のみ。**`meaning`（答え）は一切載らない**。
- **答えの開示は POST recall（`toRevealedResponse`）でのみ**行う（§3.2 の「マスク → 開示の唯一の遷移点」を踏襲）。`recall` 応答では original 全文（両側 `term`/`meaning`）を返す。

#### C-1. マスク経路で structured_content を parse して cue を抽出（M-3・実コード裏取り済み）

> **【必須】**: 現状 `ReflectionEntryResponseMapper.maskedResponse()`（origin/main）は **structured_content を一切 parse しない**（`structuredContent(null)` と `maskedHint`＝themeTitle/targetDate/dueRecallDates のみを詰める）。cue 生成のため、**masked 経路でも structured_content を parse し、TERM_CARD section から cue 側（direction に応じた片側）だけを抽出する新規ロジックを `maskedResponse` 内に追加**する。

- `maskedResponse(entry, theme, today)` で `contentSanitizer.parse(entry.getStructuredContent())` を呼び、各 TERM_CARD section について `recallDirection`（§13-B の `k` から算出）に従い **cue 側のみ**を `cardQuiz[].prompts[]` に詰める。OUTLINE section は無視（cue も出さない）。
- **fail-closed 経路（`today == null`）の扱い**: `maskedResponse` は (a) `revealedResponse` の parse 失敗時 `maskedResponse(entry, theme, null)` で呼ばれ、(b) 通常マスク時 `maskedResponse(entry, theme, today)` で呼ばれる。**`today == null` のときは `k` が算出できない**ため、**`cardQuiz = 空配列`・`recallDirection = null`**（cue を一切出さない＝最も安全）とする。`today != null` のときのみ cue を抽出する。
- **cue 抽出中に例外**（parse 失敗・型不整合）が出た場合も **`cardQuiz = 空・recallDirection = null`** にフォールバック（fail-closed）。answer 側を絶対に載せない。
- **fail-closed の一貫性**: マッパーが型解釈・方向算出で例外を捕捉したら、TERM_CARD も含め `isMasked=true`／本文 null／`cardQuiz=空`／`recallDirection=null` を返す（§3.1 末尾の fail-closed と一貫）。

#### C-2. cardQuiz の nested record 名前衝突回避（L-6）

`cardQuiz` 要素・`prompts` 要素は**汎用名 nested record にしない**。springdoc は別 DTO の同名 nested record を単一スキーマに畳み込み、後発 PR の再生成で生成型を壊す（`feedback_openapi_nested_schema_name_collision`）。**`@Schema(name = "ReflectionMaskedCardQuiz")`・`@Schema(name = "ReflectionMaskedCardPrompt")` 等で一意名を明示**する（`recallDirection` の enum も `@Schema` で一意名化を推奨）。

#### C-3. AC 担保（観測点）

- マスク中の漏洩観測は **`GET /entries`（一覧）と `GET /entries/{id}`（詳細）**のマスク応答に限定する。**today ビュー（`ReflectionTodayResponse`）はカード本文を運ばない**（`entryId` 等のメタのみで `structuredContent`/`cardQuiz` を含まない）ため観測対象外。ペイロード文字列に**答え側の語が出現しない**ことを契約テスト＋E2E で機械的に検証する（AC-51）。
- **cue/answer 取り違えの静的漏洩に注意（M-4）**: cue 抽出を旧形（`type` 欠落=OUTLINE）・`cards` 欠落・空 `meaning` 等で取り違えると、**答えが `promptText` に乗り、例外を投げないため fail-closed が効かず静かに漏洩**する。cue/answer マッピングのユニットテストで**両 direction × 旧形/欠落カード**を網羅すること（AC-51 のテストに追加・§13-K）。

### §13-D. 想起保存（recall）とカード

- **既存 EP を流用**: `POST /me/reflections/entries/{entryId}/recall`（§7 #10）をそのまま使う。暗記カード専用 EP は作らない。
- `CreateRecallAttemptRequest.recalledContent`（JSON）にユーザーのカード回答＋自由想起を格納する。提案する形（既存の JSON 許容方針＝`recalled_content JSON` 列と整合）:

```json
{
  "cardAnswers": [
    { "heading": "今日の単語", "index": 0, "answer": "abandon" },
    { "heading": "今日の単語", "index": 1, "answer": "ambiguous" }
  ],
  "freeRecall": "OUTLINE section の自由想起テキスト"
}
```

- `heading`＋`index` でどのカードへの回答かを識別する（カード本文は recalled 側に持たせない＝ original 改竄を避ける）。形は提案であり、FE/BE 配線時に微調整してよい（JSON スキーマレス方針ゆえ BE は received JSON を保存するのみ）。
- **自己評価は従来どおりエントリ単位 1 つ**（`selfRating: REMEMBERED/PARTIAL/FORGOT`）。**カード個別採点は別軍議**（§13-I）。MVP は「そのエントリ全体（OUTLINE＋カード）を 1 評価」とする（相乗り案）。
- **FORGOT で翌日再提示**（既存 AC-22）。**方向は §13-B のとおり「到来済み想起予定日の個数 `k`」で決まり `recall_attempts` 件数には依存しない**ため、FORGOT による翌日再提示が**同一 due slot 内（`k` 不変）であれば同方向で再テスト**される（同じ向きで覚え直し）。方向が逆になるのは次の想起予定日が到来して `k` が +1 されたときのみ（§13-B-2）。
- recall 保存で **両側開示**（`toRevealedResponse` が original 全文を返し、カードは `term`/`meaning` 両方が見える。AC-53）。

#### D-1. FE 必須作業: recall.vue にカード回答 UI を新設（H-3・実コード裏取り済み）

- これらは設計記述のみ。実装は出陣フェーズ（AC-53 の E2E で cue 表示→回答→開示の一気通貫を検証）。

### §13-E. 中見出し折りたたみ（純 FE・BE/DDL 変更なし）

`ReflectionStructuredEditor.vue`（編集）／ `ReflectionStructuredView.vue`（表示）に、section ごとの折りたたみを追加する。**BE/DDL 変更は一切なし**。

- **状態はコンポーネントローカル・ephemeral**（`ref<boolean[]>` 等）。section ごとに `collapsed` を保持する。
- **ごみ箱（`pi pi-trash`）は従来どおり横に残す**（既存 `removeSection(idx)` を維持）。その横に**伸縮トグル**を追加する（折りたたみ時 `pi pi-plus`＝展開する／展開時 `pi pi-minus`＝折りたたむ、等）。
- **初期状態は文脈別**: 編集（`ReflectionStructuredEditor.vue`）は **`collapsed=true`（全折りたたみ）で初期摩擦ゼロ**。一方、開示済み／recall 後の閲覧（`ReflectionStructuredView.vue`）は**展開状態で表示**する（読むためのビューゆえ畳む必要がない）。
- **展開状態の永続化はしない**（毎回エディタは閉じた状態で開く）。永続化（最後に開いていた section を覚える等）は**別軍議**（§13-I）。MVP は初期摩擦ゼロを優先。
- 折りたたみ時も「heading（見出し）＋型バッジ（OUTLINE/暗記カード）＋件数（小見出し n／カード n 枚）」のサマリ行は見せ、ワンタップで開ける。
- **aria-label / i18n**: 「展開する」「折りたたむ」を 6 言語で用意（直書き禁止・§13 末尾の i18n 表）。トグルボタンに `:aria-label` を付与（アクセシビリティ・折りたたみ挙動は AC-46・i18n キー網羅は AC-55）。

### §13-F. 期間横断 単語帳ビュー（独自単語帳・試験対策）

期間を指定して全エントリの暗記カードを横断抽出し、独自単語帳として閲覧＋自己クイズできるビューを新設する。**新テーブル不要・アプリ層抽出**。

#### F-1. 新 EP #23

```
GET /api/v1/me/reflections/cards
    ?from=YYYY-MM-DD          (必須)
    &to=YYYY-MM-DD            (必須)
    &themeId={uuid}           (任意・特定テーマに絞り込み)
    &sourceType={SUBJECT|PROJECT|DIARY|FREE}  (任意)
    &subject={string}         (任意・Phase 2 の linked_subject_name で絞り込み)
```

- **認可**: **認証必須＋本人スコープ（自分のカードのみ）**。F00 可視性は reflection では PRIVATE 固定（§2.0/§6.1）なので、**本人所有検証（`entry.user_id == currentUserId`）で十分**であり、他人のデータは一切返さない（既存 reflection 方針と整合）。`from`/`to` は必須・`themeId`/`sourceType`/`subject` は null 許容。
- **動作**:
  1. 期間内の自分のエントリを **`idx_reflection_entries_user_date (user_id, target_date)`** で取得（`user_id = currentUserId AND target_date BETWEEN from AND to AND deleted_at IS NULL`。Phase 3 アーカイブが入っていれば既定で archived テーマも含めてよい＝自分の学習資産。要否は FE フィルタで制御）。
  2. 各エントリの `structured_content` を読み、**TERM_CARD type の section から `cards[]` をアプリ層で抽出**する（OUTLINE section は無視）。
  3. 出典メタ（`themeTitle` / `themeId` / `targetDate` / section `heading`）を各カードに付与して返す。
- **期間上限（DoS）**: `from`〜`to` の差は**最大 366 日**。超過は **400**。エラーコードは**新規採番 `REFLECTION_DATE_RANGE_INVALID = "REFLECTION_015"（400）`**を使う。
  - **【採番根拠・必須】**: 既存 `REFLECTION_004 = REFLECTION_TARGET_DATE_OUT_OF_RANGE` は**単一 `target_date` の許容範囲（過去365〜未来30日）専用**であり、意味も名前も期間幅(from/to)用ではない（流用不可）。`backend/.../reflection/ReflectionErrorCode.java`（origin/main）の現在の最大は **`REFLECTION_014`（`REFLECTION_PARENT_INVALID_STATE`）**。よって期間幅超過用に「最大+1」＝**`REFLECTION_015`** を予約する。**番号は現在の最大+1（=015）で予約、確定はマージ時に `git show origin/main:backend/.../reflection/ReflectionErrorCode.java` で最大番号を再確認**してリネームすること（並行 PR で 015 が先に使われていたら +1）。
  - **【status map 登録・必須（M-2）】**: `ReflectionErrorCode` に enum を足すだけでは 400 にならない。`GlobalExceptionHandler.ERROR_CODE_STATUS_MAP`（origin/main・`Map.ofEntries(...)` の**明示列挙**で、未登録コードは 500 系へフォールバック）に **`Map.entry("REFLECTION_015", HttpStatus.BAD_REQUEST)`** を追加すること（既存 `REFLECTION_001〜014` の隣に並べる）。
- **パラメータ契約（M-5）**: `from`/`to` 欠落は **400**。`from > to`・不正日付フォーマット（`YYYY-MM-DD` 以外）は **400**（`REFLECTION_TARGET_DATE_OUT_OF_RANGE`=REFLECTION_004 ではなく、本 EP の期間検証として `REFLECTION_015` または Bean Validation の 400 を返す。フォーマット不正は Spring の型変換 400 でよい）。不正 `sourceType`（enum 外）は **400**（無視せず弾く）。`themeId` が他人所有/不正 UUID は **空結果**（本人スコープで自然に 0 件・存在秘匿）。
- **`recall_attempts` を書き込まない**: このビューの抽出・自己クイズは**スケジュール想起と完全に独立**であり、`recall_attempts` への INSERT・マスク状態の変更を一切行わない（AC-59）。マスク状態に関係なく、ユーザー自身の単語帳として閲覧できる（自分のデータ・PRIVATE ゆえ漏洩なし）。
- **ページング**: カード総数はユーザーのエントリ数に有界だが、試験期は数百枚になりうる。`page`/`size`（既定 `size=200`・上限 500）のページングを設ける。`from`/`to`＋上限 366 日で母集合自体も自然に有界化される。

### §13-G. テンプレート刷新

#### G-1. `reflectionTemplates.ts` の型付き section プリセット化（後方互換）

現状 `ReflectionTemplateDef.sectionHeadingKeys: string[]` は「見出し i18n キーの配列」のみで**型情報を持てない**。これを**型付き section プリセット**へ拡張する（後方互換を保つ案）:

```ts
// 提案: 既存 sectionHeadingKeys を残しつつ、型付きプリセットを追加するハイブリッド案
export type ReflectionSectionType = 'OUTLINE' | 'TERM_CARD'

export interface ReflectionTemplateSectionPreset {
  type: ReflectionSectionType
  /** OUTLINE の見出し i18n キー（TERM_CARD では見出し i18n キーをそのまま流用） */
  headingKey: string
}

export interface ReflectionTemplateDef {
  key: ReflectionTemplateKey
  labelKey: string
  descKey: string
  sourceType: ReflectionSourceType
  /** 既存（後方互換・OUTLINE のみのテンプレ用） */
  sectionHeadingKeys: string[]
  /** Phase 4 追加（型付きプリセット。指定時はこちらを優先して初期 section を生成） */
  sectionPresets?: ReflectionTemplateSectionPreset[]
}
```

- **後方互換**: 既存 NORMAL/DIARY/WORK/CLASS は `sectionPresets` 未指定のまま `sectionHeadingKeys`（全 OUTLINE）で従来どおり生成（据え置き・無改変）。
- **生成ロジック**: テーマ作成時に `sectionPresets` があればそれを使い `type` 付き section を初期生成。無ければ `sectionHeadingKeys`（全 OUTLINE）で従来生成。
- **単一ユーティリティ関数へ集約**: この初期 section 生成（`sectionPresets` あれば型付き section／無ければ `OUTLINE`＋`sectionHeadingKeys`）は**単一のユーティリティ関数**（例 `buildInitialSections(template)` を `reflectionTemplates.ts` か近接モジュールに 1 つ）に集約し、テーマ作成ダイアログ・テンプレ切替の両経路から同じ関数を呼ぶ（分岐の二重実装・乖離を防ぐ）。
- 代替案として `sectionHeadingKeys` を `sectionPresets` へ完全移行する手もあるが、**4 テンプレ全書き換え＝既存テストへの影響が大きい**ため、MVP は**追加フィールド方式（ハイブリッド）**を推奨する。

#### G-1-1. `applyTemplate` の置換（H-2・実コード裏取り済み）

### §14-A. 複数教科シャッフル（EP #23 のクエリ拡張・DDL 変更なし）

期間横断 単語帳ビュー（§13-F の EP #23 `GET /me/reflections/cards`）に、**複数教科の横断抽出**と**シャッフル**を追加する。**新 EP は発番せず、既存 EP #23 のクエリパラメータを後方互換で拡張する**のみ。

#### A-1. クエリパラメータの拡張（後方互換）

| パラメータ | 型 | 必須 | §13 からの差分 | 説明 |
|---|---|---|---|---|
| `from` / `to` | date | 必須 | 変更なし | 期間（最大 366 日・§13-F-1 のまま） |
| `themeId` | uuid | 任意 | 変更なし | 特定テーマに絞り込み |
| `subject` | string | 任意 | **維持（後方互換）** | 単一教科フィルタ（Phase 2 `linked_subject_name`）。`subjects` 未指定時のみ有効 |
| `subjects` | string[] | 任意 | **★ 新規** | **複数教科**フィルタ（**繰り返しパラメータのみ**＝`subjects=英語&subjects=理科`。CSV 単一値は非対応・A-1 注記）。指定時は `subject` より優先 |
| `sourceType` | enum | 任意 | **維持（後方互換）** | 単一 sourceType フィルタ。`sourceTypes` 未指定時のみ有効 |
| `sourceTypes` | enum[] | 任意 | **★ 新規** | **複数** sourceType フィルタ。指定時は `sourceType` より優先 |
| `shuffle` | boolean | 任意 | **★ 新規** | **既定 `false`**。`true` で順不同・上限まで一括返却（A-3） |
| `page` / `size` | int | 任意 | 変更なし（`shuffle=false` 時のみ有効） | §13-F-1 のページング |

- **後方互換**: 単一 `subject` / `sourceType` も**そのまま維持**する。`subjects` が指定されたら `subject` を無視、`sourceTypes` が指定されたら `sourceType` を無視（複数版優先）。既存 FE 呼び出し（単一値）は無改変で動く。
- **`subjects` の受理形式（繰り返しパラメータ一本に確定・M-1/H-2）**: **繰り返しパラメータのみ**を正準とする（`subjects=英語&subjects=理科&subjects=社会`）。**CSV 単一値（`subjects=英語,理科`）は非対応**。理由＝教科名は自由入力 VARCHAR200（Phase 2 `linked_subject_name`）であり「**簿記2級,3級**」「**英語I,II**」のようにカンマを含む値が正当に存在しうる。CSV 分割を許すと「カンマを含む 1 教科名」と「カンマ区切りの複数教科」が区別できず結果が割れる（同じ文字列が分割の有無で別物になる）。よって:
  - **BE**: `@RequestParam(required = false) List<String> subjects` で**繰り返しパラメータを正準受理**する。Spring の CSV 自動分割に依存しない（`@RequestParam List<String>` は繰り返しパラメータを素直に束ねる。混乱を避けるため設計上 CSV は使わせない）。`sourceTypes` も同様に `List<ReflectionSourceType>` で繰り返し受理。
  - **FE**: `URLSearchParams.append` の反復で複数値を載せる（A-5）。教科名は URL エンコードして送る（日本語・カンマを含む値の往復を保証）。
- **フィルタ意味論**: `subjects` は **OR（いずれかの教科に一致）**、`sourceTypes` も OR。両方指定時は `subjects` 条件 AND `sourceTypes` 条件（異種フィルタ間は AND）。`themeId` も指定されれば AND（既存どおり）。
- **抽出はアプリ層 in 判定**: §13-F-1 の母集合取得（`idx_reflection_entries_user_date` で `user_id` ＋ `target_date BETWEEN from AND to` ＋ `deleted_at IS NULL`）は不変。`subjects`/`sourceTypes` は取得後にアプリ層の集合 in 判定で絞る（新 index/新 FK 不要）。母集合は from/to 上限 366 日 ＋ size 上限で**有界**。

#### A-2. シャッフルのセマンティクス（教科を混ぜる・固めない）

- **シャッフル = 選んだ教科の全カードを 1 つのプールに混ぜて順不同で返す**。教科ごとに固めない（例「英語＋理科＋社会」を選んだら 3 教科のカードが交ざった 1 列で返る）。これにより試験前の「教科を忘れて反射的に答える」通し学習ができる。
- **`shuffle=false`（既定）は安定順**（既存 §13-F の自然順＝母集合の `target_date` 昇順 → section heading → カード index 等の決定的順）。後方互換で既存の閲覧モードはそのまま。
- **シャッフルのアルゴリズム**: サーバ側で抽出後のカードプールに対し均一シャッフル（Fisher–Yates 相当）。**シード固定はしない**（毎回異なる順＝学習効果のため）。FE 側の再シャッフルは UI トグルで別途行ってよいが、本 EP の `shuffle=true` はサーバ返却順を順不同にする。

#### A-3. シャッフル時のページング無効化（クイズ用・一貫性のため）

- **`shuffle=true` のときはページングを使わず `size` 上限（500）まで一括返却**する。理由: シャッフルは「全プールを 1 列に混ぜる」ものであり、ページ跨ぎで順序やプール内容が割れると通し学習の一貫性が崩れる（ページ 1 とページ 2 で混ざり方が変わる/重複・欠落が起きる）。
- **`shuffle=false` のときは既存 `page`/`size` を踏襲**（§13-F-1 の `size=200` 既定・上限 500）。
- 一括返却の上限超過（プールが 500 枚を超える）対策: **`from`/`to` 上限 366 日 ＋ 教科フィルタ**で母集合を絞る前提とし、`shuffle=true` で 500 枚を超えた場合は **先頭 500 枚（シャッフル後）まで返し `totalCards` に真の総数を載せる**（FE は「期間/教科を絞ってください」を案内）。新エラーコードは増やさない（既存の上限超過は §13-F の挙動に倣う）。

#### A-4. レスポンス DTO は不変（§13-F-2）

### §14-B. 教科分類のデータ構造（`linked_subject_name` 流用・新列なし・DDL 変更ゼロ）

教科の二系統を **「同一列 `linked_subject_name` ＋ `linkedSlotKind` の有無」** で区別する。**新列は作らない**。

#### B-1. 二系統の定義

| 系統 | `linkedSlotKind` | `linkedSubjectName` | 由来 | 今日ビューでの扱い |
|---|---|---|---|---|
| **時間割連携教科** | `!= NULL` | あり（Phase 2 既存・linkable-slots EP #16 から自動導出） | 時間割コマと紐づく既存の科目連携（§11） | 条件 B でコマ照合される（既存動作・無改変） |
| **資格カテゴリ** | **`= NULL`** | あり（**自由入力**カテゴリ。例 「TOEIC」「簿記2級」） | ユーザーが自由入力した学習カテゴリ | **freeThemes 行き＝今日ビューに誤マッチしない**（B-2 で構造的に保証） |

- API 上はどちらも既存 DTO の `linkedSubjectName` / `linkedCourseCode` / `clearLinkedSubject`（origin/main 既存）を流用する。**API 差分ゼロ・新 source_type を増やさない**（§2.1 の `source_type` CHECK 制約を変えない）。
  - **【実コード裏取り（M-3）】**: `CreateReflectionThemeRequest`（origin/main）は `linkedSlotKind` / `linkedSlotId` を**持つ**（作成時のみ系統指定可）。一方 `UpdateReflectionThemeRequest`（origin/main）は `linkedSubjectName` / `linkedCourseCode` / `clearLinkedSubject` のみで **`linkedSlotKind` / `linkedSlotId` を持たない**。よって**系統（時間割連携↔資格カテゴリ）の相互変換は更新経路では構造的に不可能**（B-3 末尾参照）。
- 資格カテゴリは `linkedCourseCode` を持たなくてよい（持っても害はないが、コマ照合に使われない＝B-2）。

#### B-2. 資格カテゴリが今日ビューに誤マッチしない構造的根拠（最重要）

> **【構造的保証・実コード裏取り済み（origin/main `ReflectionTodayService.getToday`）】**

`ReflectionTodayService.getToday()` のテーマ分類ループ（origin/main）は次の三分岐である:

```
if      (linkedSlotKind != null && linkedSlotId      != null) → bySlotKey    （条件A: コマ ID 照合）
else if (linkedSlotKind != null && linkedSubjectName != null) → bySubjectKey （条件B: 時間割コマの科目名照合）
else                                                          → freeThemes   （照合されない＝今日ビューに「自由テーマ」として出るのみ）
```

- 資格カテゴリは **`linkedSlotKind = NULL`** であるため、**第 1・第 2 分岐の `linkedSlotKind != null` を両方満たさず、必ず最後の `else` ＝ `freeThemes` に落ちる**。`linkedSubjectName` に何を入れても（「TOEIC」等）、`bySlotKey`/`bySubjectKey` に登録されないため、**時間割コマとの照合対象に一切ならない（誤マッチ構造的ゼロ）**。
- freeThemes は今日ビューに「自由テーマ由来 item（§4.3）」として列挙されるが、これは**コマへの割り当てではなく**、時間割非依存ユーザー向けの主導線であり、資格カテゴリのテーマがここに並ぶのは設計意図どおり（学習対象として今日の一覧に出てよい・ただしコマ枠を占有しない）。
- つまり「資格カテゴリを単語帳の教科軸に使いたいが、時間割コマには割り当てたくない」という要望が、**既存ゲートの分岐構造だけで満たされる**（新ロジック不要）。これが本 §14-B が新列を作らずに済む根拠である（AC-64）。

#### B-3. 必須ガード（自由入力時に時間割種別を混ぜない・実装は新規作業）

> **【実コード裏取り（M-2/H-5）】**: 現状 `ReflectionThemeService.createTheme`（origin/main）は `request.linkedSlotKind()` を**無ガードでビルダーに流す**（`.linkedSlotKind(request.linkedSlotKind())` をそのまま `.build()`）。「既存ロジックで塞がれている」は**誤り**で、ガードは**新規追加が必要**。FE 側も `ReflectionThemeDialog.vue`（origin/main）は linkable-slots からの `Select` のみで**自由入力欄が存在しない**（資格カテゴリ UI は新規作業）。

- **作成経路の事故シナリオ（唯一の事故経路）**: 条件 B は `linkedSlotKind != null && linkedSubjectName != null` で発火する。資格カテゴリ（自由入力 `linkedSubjectName`）作成時に `linkedSlotKind` を非 null で送られると、`linkedSlotId == null` でも**条件 B に乗って時間割コマと誤照合する**。この一点を塞ぐ。
- **BE 新規ガード（`ReflectionThemeService.createTheme` に追加）**: `linkedSubjectName != null && linkedSlotId == null`（＝自由入力カテゴリで slot 由来でない）のとき、**`linkedSlotKind` を強制 NULL 化**してからビルダーに渡す。あるいは厳格にするなら **`linkedSlotKind != null && linkedSlotId == null` を 400 で弾く**（不整合入力の拒否）。本設計は **「強制 NULL 化（防御的正規化）」を既定**とし、入口バリデで弾く案は実装時にチーム判断で選択可（どちらでも条件 B に乗らない結果は同一）。
- **FE 新規作業（`ReflectionThemeDialog.vue` に資格カテゴリ自由入力 UI を新設）**: 現状の linkable-slots `Select` に加え、**「資格・自主学習カテゴリ（自由入力）」モードを新規追加**する。両モードを UI で排他にし、(i) 時間割連携モード＝linkable-slots から選択し `linkedSlotKind`/`linkedSubjectName`/`linkedCourseCode` を slot から載せる、(ii) 資格カテゴリモード＝自由入力 `linkedSubjectName` のみを載せ **`linkedSlotKind` は送らない（明示 undefined/null）**。これは既存 UI 流用ではなく新規実装。
- **更新経路は系統変換不可（M-3・構造的安全）**: `UpdateReflectionThemeRequest`（origin/main）は `linkedSlotKind`/`linkedSlotId` を**保持しない**ため、**更新では系統（時間割連携↔資格カテゴリ）の相互変換ができない**＝二系統相互変換は本 Phase スコープ外。これにより「資格カテゴリが後から条件 B に化ける事故は**更新経路では構造的にゼロ**」（更新で `linkedSlotKind` を非 null に変える術が API に存在しない）。系統変更を要件化するなら `UpdateRequest` 拡張が必要だが**別軍議**（§14-H 別軍議切り出し）。
- **後方互換**: 既存テーマ（`linked_subject_name` NULL）は無改変。`visibility` は PRIVATE 固定（§2.0/§6.1）のまま不変。

#### B-4. 単語帳フィルタでの混在（§14-A との接続）

- §14-A の `subjects` フィルタは **`linked_subject_name` 値で一致**を取る（時間割連携教科・資格カテゴリの区別なく同一列のため、両方が同じ `subjects` 配列で並べて選べる）。
- これにより「時間割の英語」＋「資格カテゴリの TOEIC」を同時に選んでシャッフル通し学習できる（AC-65）。`linkedSlotKind` の有無は単語帳抽出には影響しない（抽出母集合は `target_date` ＋ TERM_CARD section の有無で決まり、教科フィルタは `linked_subject_name` 値の in 判定のみ）。

#### B-5. 将来拡張（別軍議）

- 「資格カテゴリを **別軸で今日ビューにも出したい**（例: 今日の資格学習枠）」という要件が将来出たら、`linked_subject_name` 流用ではなく **`category` 新列を別軍議で検討**する。本 §14 では新列を作らない（今日ビューへの資格カテゴリ表示はスコープ外）。
