# F02.9 個人ダッシュボード お気に入りウィジェット

> **ステータス**: 🟢 設計確定（軍議完了・2度精査完了・Open Questions 全 8 件決着）
> **実装フェーズ**: Phase 1〜3 着手可
> **最終更新**: 2026-05-15

---

## 1. 概要・コンセプト

### 1.1 背景・目的

よく使うチーム・組織・村など、特定のエンティティへ毎回ナビゲーションを辿る摩擦を解消する。
ユーザーが任意のエンティティをお気に入り登録し、個人ダッシュボードから **1クリックで開く・クイック編集する** ことを目的とする。

### 1.2 コンセプト

> 「毎日使う場所・気になる著者・よく編集するページ — すべてをダッシュボードの手前に」

- **横断的ショートカット**: チーム・組織・KBページ・ブログ著者・村を種別問わず一箇所に集約
- **表示は最大10件、残りは折りたたみ**: 視認性を保ちつつ最大20件まで登録可能
- **クイック編集**: 小窓（モーダル）で簡易編集（権限ある場合のみ表示）
- **どのページからでも ⭐ で登録**: 各エンティティページのヘッダーにスターボタンを常設

## 2. スコープ

### 2.1 対象ロール

| ロール | 利用可否 |
|---|---|
| SYSTEM_ADMIN | ✅ |
| ADMIN | ✅ |
| DEPUTY_ADMIN | ✅ |
| MEMBER | ✅ |
| SUPPORTER | ✅ |
| PUBLIC（未認証） | ❌（認証済みユーザーのみ） |

### 2.2 対象エンティティ種別

| entity_type | 説明 | entityId の実体型 | クイック編集内容 |
|---|---|---|---|
| `TEAM` | チーム | BIGINT | name, description, icon |
| `ORGANIZATION` | 組織 | BIGINT | name, description |
| `KB_PAGE` | ナレッジベースページ（F06.5） | BIGINT | 編集モードで開く（小窓なし） |
| `BLOG_AUTHOR` | ブログ著者（F06.1 / ユーザー） | BIGINT (user_id) | 自分のみ: display_name, bio（他者は編集不可） |
| `VILLAGE` | 村コミュニティ（F17.1） | UUID (BINARY16) | name, description, icon |

### 2.3 スコープ外

- チーム・組織ダッシュボードへのお気に入りウィジェット表示（個人ダッシュボードのみ）
- KBページ内ブックマーク一覧（F06.5 の `kb_page_favorites` は別機能として共存）
- お気に入りの共有・公開
- お気に入り更新時のプッシュ通知
- フォルダ分類
- ポイントカードの `is_favorite` フラグ（F18）との統合

### 2.4 F17.1「お気に入り村フィード」との関係

F17.1 の関連機能表に「個人ダッシュボードに『お気に入り村フィード』ウィジェット導入」と記載があるが、これは **F02.9 の村ショートカットとは異なる概念**である。

| 機能 | 目的 | 内容 |
|---|---|---|
| **F02.9 村ショートカット** | ナビゲーション高速化 | 「よく使う村」へ 1 クリックで飛べるカード |
| **F17.1 村フィード（別ウィジェット）** | コンテンツ購読 | フォローした村の最新投稿・お知らせをまとめて表示 |

両者は別ウィジェットとして並立させる。村フィードウィジェットの詳細設計は F17.1 に委ねる。  
なお、F02.9 の村 ⭐ 登録（ショートカット）と F17.1 の村フォロー（購読）を 1 つの操作に統合するか別操作にするかは F17.1 実装時に最終決定すること。

## 3. DB 設計

### 3.1 設計原則への準拠

| 原則 | 準拠内容 |
|---|---|
| 原則1: クロスドメイン FK 禁止 | `user_id`, `entity_id` の FK 制約なし。整合性はアプリ層で保証 |
| 原則2: CASCADE 禁止（クロスドメイン） | FK なし、よってカスケード削除なし |
| 原則3: コアエンティティは論理削除 | `user_favorites` 自体は物理削除（お気に入りは意図的に削除するもの） |
| 原則6: 新規テーブルは UUIDv7 PK | `id BINARY(16)` UUIDv7 |
| 原則7: テナントスコープ Repository | お気に入りは個人スコープ（organization_id なし）。`AbstractTenantAwareRepository` 対象外 |

### 3.2 テーブル定義: `user_favorites`

```sql
CREATE TABLE user_favorites (
    id              BINARY(16)          NOT NULL                COMMENT 'UUIDv7 PK',
    user_id         BIGINT UNSIGNED     NOT NULL                COMMENT 'お気に入り登録者（FK 張らない / 退会時バッチ削除）',
    entity_type     VARCHAR(50)         NOT NULL                COMMENT 'TEAM | ORGANIZATION | KB_PAGE | BLOG_AUTHOR | VILLAGE',
    entity_id       VARCHAR(36)         NOT NULL                COMMENT 'エンティティID（BIGINT は十進数文字列 "123"、UUID は36文字ハイフン付き "018f-..."）',
    display_order   SMALLINT UNSIGNED   NOT NULL DEFAULT 0      COMMENT '表示順（低い値が先頭）',
    created_at      DATETIME            NOT NULL DEFAULT CURRENT_TIMESTAMP,

    PRIMARY KEY (id),
    UNIQUE  KEY uq_uf_user_entity  (user_id, entity_type, entity_id)  COMMENT '同一エンティティの重複登録防止',
    KEY     idx_uf_user_order      (user_id, display_order)           COMMENT 'ユーザー別一覧取得（表示順）',
    KEY     idx_uf_entity          (entity_type, entity_id)           COMMENT 'エンティティ削除時のバッチ逆引き'
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci
  COMMENT='ユーザー横断お気に入り（ダッシュボードショートカット）';
```

### 3.3 entity_id の型変換ルール（アプリ層）

| entity_type | 実体の PK 型 | entity_id に格納する値 | アプリ層での逆変換 |
|---|---|---|---|
| TEAM | BIGINT | `"123"` | Long.parseLong() |
| ORGANIZATION | BIGINT | `"456"` | Long.parseLong() |
| KB_PAGE | BIGINT | `"789"` | Long.parseLong() |
| BLOG_AUTHOR | BIGINT (user_id) | `"101"` | Long.parseLong() |
| VILLAGE | BINARY(16) UUIDv7 | `"018f2b3c-..."` | UUID.fromString() |

### 3.4 上限制約

- 1ユーザーあたり最大 **20件** まで登録可能
- `@Transactional` 内で `countByUserId(userId)` を取得し、20 件に達していれば例外をスロー
- DB に CHECK 制約は設けない（一括削除等の運用に対応するため）
- UNIQUE 制約の競合（FAV_001）と 20件上限（FAV_002）の判定を必ず区別してエラーコードを返す

### 3.5 ウィジェット設定への組み込み

F02.2 の `dashboard_widget_settings` が参照する widget_key リストに `'FAVORITES'` を追加する。  
デフォルト: **個人ダッシュボードのみ表示 ON**（チーム・組織ダッシュボードには表示しない）。  
既存の widget_key 列挙に `FAVORITES` を加えるマイグレーションが必要。

### 3.6 既存テーブルとの共存

| テーブル | 関係 |
|---|---|
| `kb_page_favorites` (F06.5) | **共存**。KBブックマーク（KB機能内一覧）とダッシュボードショートカットは意味が異なる。統合しない |
| `user_point_cards.is_favorite` (F18) | **共存**。ポイントカードウォレット内の優先表示フラグ。UIコンテキストが全く異なる |

### 3.7 退会時の後処理

ユーザー退会（匿名化・論理削除）フローに `DELETE FROM user_favorites WHERE user_id = ?` を追加する。  
FK 制約がないためバッチ側での明示的削除が必須。

**実装場所**: `com.mannschaft.app.user.service.UserService` の退会処理メソッド内、または `UserDeletedEvent` を受け取るイベントハンドラ（既存の退会フローに合わせること）。

## 4. API 設計

すべてのエンドポイントは認証済みユーザーのみアクセス可能。`user_id` は JWT から取得し、リクエストボディに含めない。

### 4.1 お気に入り一覧取得

```
GET /api/v1/me/favorites
```

**レスポンス (200 OK)**:

```json
{
  "items": [
    {
      "favoriteId": "018f2b3c-1234-7000-8000-000000000001",
      "entityType": "TEAM",
      "entityId": "123",
      "displayOrder": 0,
      "createdAt": "2026-05-15T10:00:00Z",
      "entity": {
        "name": "東京チーム",
        "description": "東京エリアの運営チーム",
        "iconUrl": "https://...",
        "pageUrl": "/teams/123",
        "status": "AVAILABLE",
        "canEdit": true,
        "editableFields": ["name", "description", "icon"]
      }
    },
    {
      "favoriteId": "018f2b3d-...",
      "entityType": "VILLAGE",
      "entityId": "018f2b3c-abcd-7000-8000-000000000002",
      "displayOrder": 1,
      "createdAt": "2026-05-15T09:00:00Z",
      "entity": {
        "name": "整骨院村",
        "description": "全国の整骨院スタッフが集まる村",
        "iconUrl": null,
        "pageUrl": "/villages/018f2b3c-abcd-7000-8000-000000000002",
        "status": "AVAILABLE",
        "canEdit": false,
        "editableFields": []
      }
    }
  ],
  "totalCount": 2,
  "maxCount": 20
}
```

**`entity.status` の値**:

| 値 | 説明 |
|---|---|
| `AVAILABLE` | 正常にアクセス可能 |
| `UNAVAILABLE` | エンティティが削除済み / アクセス権喪失 |

**`AVAILABLE` 判定の正準（認可根治戦役 第1波）**: `TEAM` / `ORGANIZATION` は F00 共通可視性ラダー
（`ContentVisibilityChecker#filterAccessible` / `#canView`）で**閲覧できると判定された対象のみ** `AVAILABLE` とする
（判定基準は `GET /api/v1/teams/{slug}` と同一）。`KB_PAGE` はページの `access_level` × スコープロールで判定する。
お気に入り登録（`POST /api/v1/me/favorites`）でも同じラダーを**件数上限・重複などの業務検証より前**に評価し、
閲覧できない対象は `FAV_003`（404・存在秘匿）で拒否する。

UNAVAILABLE の場合: `name` を `"（利用不可のアイテム）"`、`description` / `iconUrl` を `null`、`pageUrl` を `""` として返す（個人情報・内部情報の漏洩防止）。

**`entity.canEdit` のサーバーサイド判定ルール**:

| entity_type | canEdit = true の条件 |
|---|---|
| TEAM | 現ユーザーが当該チームの ADMIN または DEPUTY_ADMIN |
| ORGANIZATION | 現ユーザーが当該組織の ADMIN |
| KB_PAGE | 現ユーザーが当該ページへの write 権限を保有 |
| BLOG_AUTHOR | `entityId` (user_id) == 現ユーザーの user_id（自分のみ） |
| VILLAGE | 現ユーザーが村の OWNER または ADMIN ロール |

`canEdit` はサーバーサイドのみで算出する。クライアントからの入力値は一切信頼しない。

### 4.2 お気に入り追加

```
POST /api/v1/me/favorites
```

**リクエストボディ**:

```json
{
  "entityType": "TEAM",
  "entityId": "123"
}
```

**レスポンス (201 Created)**:

```json
{
  "favoriteId": "018f2b3c-1234-7000-8000-000000000001"
}
```

新規登録は **先頭（display_order = 0）** に挿入し、既存アイテムの display_order を全て +1 シフト（同一 `@Transactional` 内で実行）。

**バリデーション**（順序どおりに評価）:

1. `entityType` が許可リスト（TEAM / ORGANIZATION / KB_PAGE / BLOG_AUTHOR / VILLAGE）に含まれること → 外れれば FAV_005
2. `entityId` が対応する型として有効であること（BIGINT エンティティは正の整数文字列、VILLAGE は UUID 形式） → 不正なら FAV_006
3. エンティティが存在すること + 現ユーザーがアクセス権を持つこと → なければ FAV_003
4. 上限 20 件に達していないこと → 達していれば FAV_002（**カウントチェックは INSERT より前に実施すること**）
5. INSERT を実行し、UNIQUE 制約違反（DataIntegrityViolationException）を catch して FAV_001 として返す

### 4.3 お気に入り削除

```
DELETE /api/v1/me/favorites/{favoriteId}
```

- `favoriteId`: UUIDv7 形式（URL パスパラメータ）
- WHERE 句に `id = ? AND user_id = ?` を必ず付けることで他ユーザーのお気に入りへの IDOR を防止
- 他ユーザーの favoriteId を指定した場合は `403 Forbidden` (FAV_004)
- 物理削除
- **レスポンス**: `204 No Content`

### 4.4 並び替え更新

```
PATCH /api/v1/me/favorites/reorder
```

**リクエストボディ**:

```json
{
  "orderedIds": [
    "018f2b3c-...",
    "018f2b3d-...",
    "018f2b3e-..."
  ]
}
```

- `orderedIds` に **現ユーザーの全お気に入り ID** を順番に並べる（部分更新は不可、全件必須）
- サーバーサイドで `orderedIds` の各 ID が現ユーザーのものであることを確認
- 他ユーザーの ID が混入している、または現ユーザーのお気に入り件数と一致しない場合は `400 Bad Request`
- **レスポンス**: `204 No Content`

### 4.5 お気に入り存在チェック（⭐ ボタンの初期表示用）

```
GET /api/v1/me/favorites/check?entityType=TEAM&entityId=123
```

**レスポンス (200 OK)**:

```json
{
  "isFavorited": true,
  "favoriteId": "018f2b3c-..."
}
```

未登録の場合: `isFavorited: false, favoriteId: null`

### 4.6 クイック編集 API（既存 API への委譲）

クイック編集専用の新規 API は設けない。フロントエンドが各エンティティの既存 API を直接呼ぶ。

| entity_type | 委譲先 API |
|---|---|
| TEAM | `PATCH /api/v1/teams/{id}` |
| ORGANIZATION | `PATCH /api/v1/organizations/{id}` |
| KB_PAGE | 「編集モードで開く」ボタンとして表示 → `/teams/{teamId}/knowledge-base/{slug}?mode=edit` へ遷移 |
| BLOG_AUTHOR | 🔵 `PATCH /api/v1/me/profile`（自分のみ・未実装）— ブログ著者プロフィール編集 API は別 Phase で実装予定。当面は BLOG_AUTHOR のクイック編集ボタンを非表示とする |
| VILLAGE | `PATCH /api/v1/villages/{id}`（F17.1 実装後） |

権限チェックは各エンティティの API が担保するため、お気に入り API 側での二重チェックは不要。

### 4.7 エラーコード一覧

| コード | HTTP | 説明 |
|---|---|---|
| FAV_001 | 409 | 既に登録済み（重複） |
| FAV_002 | 422 | 上限 20 件超過 |
| FAV_003 | 404 | エンティティが存在しない / アクセス権なし |
| FAV_004 | 403 | 他ユーザーのお気に入りへのアクセス試行 |
| FAV_005 | 400 | entity_type が許可リスト外 |
| FAV_006 | 400 | entity_id の形式不正 |

### 5.2 ダッシュボードウィジェット（FavoritesWidget.vue）

**表示仕様**:

| 状態 | 表示 |
|---|---|
| ローディング中 | スケルトンカード 3 枚 |
| 0 件 | `FavoritesWidgetEmpty.vue`（空状態 CTA） |
| 1〜10 件 | カード全件表示 |
| 11〜20 件 | 先頭 10 件表示 + 「さらに N 件表示」折りたたみボタン |

**カード UI イメージ（FavoritesWidgetCard.vue）**:

```
┌─────────────────────────────────────────────────┐
│ [アイコン]  東京チーム         [チーム バッジ]  │
│             東京エリアの運営チーム               │
│                             [✏ 編集] [開く →] │
└─────────────────────────────────────────────────┘
```

各カードの構成要素:
- エンティティアイコン（画像または絵文字/カラーアイコン）
- 名前（太字、最大1行・overflow-ellipsis）
- entity_type バッジ（「チーム」「組織」「KB」「著者」「村」）
- 説明文（最大1行・overflow-ellipsis）
- 「開く」ボタン → `entity.pageUrl` に遷移
- 「✏ 編集」ボタン（`canEdit = true` の場合のみ表示） → クイック編集ダイアログを開く
- コンテキストメニュー（長押し / 右クリック）で「お気に入りから削除」

**UNAVAILABLE 状態のカード**:
- グレーアウト表示
- 「このアイテムは利用できなくなりました」テキスト
- 「削除」ボタンのみ表示（「開く」「編集」は非表示）

**ドラッグ & ドロップ並び替え**:
- `vue-draggable-next` 等のライブラリを使用
- 並び替え完了後に `PATCH /api/v1/me/favorites/reorder` をデバウンス 500ms で呼ぶ

**アクセシビリティ**:
- 「開く」ボタン: `aria-label="{{name}} を開く"`
- 「✏ 編集」ボタン: `aria-label="{{name}} を編集"`
- スター: `aria-pressed="true/false"`, `aria-label="{{name}} をお気に入りに追加"`

**モバイル対応**:
- カードは縦積みリスト表示（グリッドではなく単一カラム）
- ドラッグ & ドロップはタッチ操作に対応

### 5.3 クイック編集ダイアログ（FavoriteQuickEditDialog.vue）

entity_type 別のフォーム内容:

| entity_type | フォームフィールド | 保存時の挙動 |
|---|---|---|
| TEAM | name（必須）・description・icon（カラー/絵文字ピッカー） | `PATCH /api/v1/teams/{id}` → 成功後ダイアログを閉じカードを更新 |
| ORGANIZATION | name（必須）・description | `PATCH /api/v1/organizations/{id}` → 同上 |
| KB_PAGE | ダイアログを開かず、そのまま編集モードへ遷移 | `pageUrl?mode=edit` へナビゲート |
| BLOG_AUTHOR | display_name（必須）・bio | 🔵 `PATCH /api/v1/me/profile`（未実装。別 Phase 実装後に有効化） |
| VILLAGE | name（必須）・description・icon | `PATCH /api/v1/villages/{id}` → 同上 |

- 保存中: ボタンをスピナーに置換し、ダブルクリック防止
- バリデーションエラー: フィールド直下にエラーメッセージ（インライン）
- 保存成功後: `useFavoritesApi` のキャッシュ状態を更新（再フェッチ不要）
- API エラー（4xx / 5xx）: ダイアログ上部にエラーバナーを表示し、ダイアログは閉じない。ユーザーが再試行またはキャンセルできる状態を維持する

### 5.4 スターボタン（FavoriteToggleButton.vue）

マウント時: `GET /api/v1/me/favorites/check?entityType=X&entityId=Y` で初期 ON/OFF を設定。

| 状態 | 表示 |
|---|---|
| チェック中 | スピナー |
| 未登録 | ☆（空スター）|
| 登録済み | ★（塗りつぶし）|
| 上限超過かつ未登録 | ☆（disabled）。ホバーで「上限 20 件に達しています」ツールチップ |
| トグル処理中 | スピナー |

登録追加時にトースト:「お気に入りに追加しました」

## 6. セキュリティ

### 6.1 認可制御

| 脅威 | 対策 |
|---|---|
| IDOR — 他ユーザーのお気に入り削除 | `DELETE` の WHERE に `user_id = currentUserId` を必ず含め、不一致は 403 (FAV_004) |
| IDOR — 並び替え混入 | `PATCH /order` で `orderedIds` の各 ID が currentUserId のものか検証 |
| 存在しないエンティティを登録 | `POST` 時にエンティティ存在確認 + アクセス権確認をエンティティサービスに委譲 |
| entity_type インジェクション | 許可リスト（enum）でバリデーション。許可外は 400 (FAV_005) |
| canEdit 偽装 | `canEdit` はサーバーサイドのみで算出。クライアントから受け付けない |
| クイック編集の権限昇格 | 編集は各エンティティの既存 API に完全委譲。権限チェックはエンティティ API 側で保証 |
| UNAVAILABLE エンティティからの情報漏洩 | name / description / iconUrl を返さず `"（利用不可のアイテム）"` / null に置換 |
| 上限チェックの競合 | `@Transactional` 内でカウント取得 → INSERT を実行。UNIQUE 制約が最終的な重複防止を保証 |

### 6.2 レート制限

`RateLimitFilter` に追加:

| エンドポイント | 制限 |
|---|---|
| `POST /api/v1/me/favorites` | 30 req / min / user |
| `DELETE /api/v1/me/favorites/{id}` | 30 req / min / user |
| `PATCH /api/v1/me/favorites/reorder` | 10 req / min / user |
| `GET /api/v1/me/favorites` | 制限なし（読み取り専用） |
| `GET /api/v1/me/favorites/check` | 60 req / min / user |

### 7.2 FavoriteResolverService の責務

`FavoriteResolverService` は entity_type に応じた Resolver を選択し、エンティティのメタデータ（name, description, iconUrl, pageUrl, status, canEdit）を解決する。

クロスドメインデータ取得は各ドメインの Service メソッドを呼ぶ（直接 Repository を叩かない）。

```java
// 呼び出しイメージ
FavoriteEntityMetaDto meta = resolverService.resolve(
    entity_type, entity_id, currentUser
);
// 内部: teamService.getTeamMeta(id) 等に委譲
```

**N+1 問題の対策（バッチ解決）**:

`GET /api/v1/me/favorites` で最大 20 件のお気に入りを返す際、entity_type ごとにまとめて取得する（1アイテムずつ resolve を呼ばない）。

```java
// 例: entity_type = TEAM の全 ID を一括取得
List<Long> teamIds = favorites.stream()
    .filter(f -> f.getEntityType() == TEAM)
    .map(f -> Long.parseLong(f.getEntityId()))
    .toList();
Map<Long, FavoriteEntityMetaDto> teamMetas = teamResolver.resolveAll(teamIds, currentUser);
```

Resolver インターフェースには `resolveAll(List<ID>, User)` を必ず定義し、単件 `resolve` は内部から一覧呼び出しでブリッジする。

**KB_PAGE の pageUrl 構築における注意事項**:

`entity_id` は KB ページの ID のみを保持するが、`pageUrl` の構築には `teamId` と `slug` が必要（例: `/teams/{teamId}/knowledge-base/{slug}`）。`KbPageFavoriteResolver` は KB ページ情報を取得する際に所属チームの ID と slug を一緒にフェッチし、pageUrl を構築すること。

### 7.3 エンティティ種別の拡張方法

新しい entity_type を追加する場合の手順:
1. `FavoriteEntityType` enum に値を追加
2. 対応する `*FavoriteResolver` クラスを作成
3. `FavoriteResolverService` の resolver マップに登録
4. フロント: `FavoriteToggleButton` の設置、型定義・i18n 追加

## 9. Open Questions（全 8 件決着）

| # | 問い | 決定 | 根拠 |
|---|---|---|---|
| OQ-1 | KB_PAGE のクイック編集はインラインか編集モード遷移か | **編集モードで開く** | KBエディタは専用ツールとして完成度が高く、小窓に落とし込むと機能欠損が発生する |
| OQ-2 | `entity_id` の型は BIGINT か VARCHAR か | **VARCHAR(36)** | VILLAGE が UUIDv7 (BINARY16) を採用しており、全型を文字列化が最もコスト低い。単一カラムで全型を統一 |
| OQ-3 | `kb_page_favorites` と `user_favorites` を統合するか | **共存（統合しない）** | KBブックマーク（KB内一覧）とダッシュボードショートカットは意味が異なる。統合するとUXが複雑化する |
| OQ-4 | 並び替えは drag & drop 必須か | **Phase 1 スコープ内で実装** | 最大 20 件の小リストであり drag & drop の実装コストが許容範囲内 |
| OQ-5 | BLOG_AUTHOR の「編集」は何を指すか | **自分のプロフィールのみ編集可・他者は「開く」のみ** | ブログ著者の編集権限は本人限定。他者著者ページはリードオンリーショートカット |
| OQ-6 | UNAVAILABLE エンティティの auto-cleanup は即時か batch か | **即時に UNAVAILABLE 表示 + ユーザーが手動削除または 30 日後バッチ削除（Phase 2 以降）** | 即時削除では「なぜ消えたか」がユーザーに伝わらず体験が悪い |
| OQ-7 | 新規お気に入りの挿入位置は先頭か末尾か | **先頭（display_order = 0、既存を +1 シフト）** | 追加直後にすぐ見える位置に来るべき |
| OQ-8 | Village ページの ⭐ ボタンを Phase 1 から実装するか | **バックエンドは Phase 1 から VILLAGE を受け付ける。フロント ⭐ ボタンは F17.1 実装後に Phase 3 で追加** | F17.1 の村ページ実装に依存するため、バックエンドのみ先行対応 |
