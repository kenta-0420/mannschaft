## 1. 概要

1対1チャット（DM）を交わしている相手を、その場から自分が管理するチーム/組織へ **招待** する機能。従来の招待は「共有リンク/QR を渡して相手にクリックしてもらう」プル型だったが、本機能は **DM 相手を名指しで招待し、相手がチャット内カードで承諾して初めてメンバー化する** 承諾型（オファー型）とする。

**承諾型オファーの共通思想**（F01.2 team-invites / org-invites の PENDING→ACTIVE、F04.9 確認通知、および本機能と同時整備する「オーナー委譲の承諾型化」で一貫させる）:

```
PENDING ──承諾──▶ ACCEPTED（効果発生）
   │
   ├──辞退──▶ DECLINED
   ├──期限──▶ EXPIRED
   └──取消──▶ CANCELLED（発行者が取消）
```

相手の能動的な承諾（accept）があって初めて効果（メンバー化）が発生する点が、旧来の共有リンク型（クリックした人が誰でも参加できる）と根本的に異なる。指名相手だけが承諾できる **宛先照合** を核心の認可要件とし、IDOR（他人宛ての招待を第三者が承諾する）を構造的に封じる。

### 決定事項

| 論点 | 決定 |
|---|---|
| 招待の型 | **承諾型**（宛先を名指し・相手の accept で発効）。旧共有リンク型は併存（撤去しない） |
| 入口 | **1対1チャット（DM チャンネル）の相手** に限定。グループチャンネルからの一括招待は本設計のスコープ外 |
| 承諾 UI | **チャット内カード方式**（別画面遷移を強制しない。DM のメッセージストリームに招待カードを差し込む） |
| 招待できるスコープ | 発行者が **ADMIN または DEPUTY_ADMIN** として管理するチーム/組織のみ |
| 付与ロール | 招待時に選択（既定は当該スコープの MEMBER ロール）。ADMIN 昇格の招待は本機能の対象外 |

## 2. スコープ

### 対象ロール
| ロール | 操作可能な範囲 |
|--------|--------------|
| SYSTEM_ADMIN | 全招待の参照・強制取消（モデレーション） |
| ADMIN | 自分が ADMIN のチーム/組織へ DM 相手を招待・取消 |
| DEPUTY_ADMIN | `INVITE_MEMBERS` 権限を持つ場合: 自分が DEPUTY_ADMIN のチーム/組織へ DM 相手を招待・取消 |
| MEMBER | 招待の発行不可。自分宛て招待カードの承諾/辞退のみ |
| SUPPORTER | 招待の発行不可。自分宛て招待カードの承諾/辞退のみ |
| GUEST | 対象外 |

> 招待を「受ける」側はロール不問（DM の相手であれば誰でも受信できる）。招待を「出す」側にのみ ADMIN/DEPUTY_ADMIN のスコープ権限を要求する。

### 対象レベル
- [x] 組織 (Organization) — DM 相手を組織へ招待
- [x] チーム (Team) — DM 相手をチームへ招待
- [x] 個人 (Personal) — DM（1対1チャンネル）が入口

## 3. DB設計

本機能は **新規テーブルを作らず、既存2テーブルへのカラム追加のみ** で実現する。招待の本体は F01.2 の `invite_tokens` を「宛先付き」に拡張して再利用し、チャット上の表示は `chat_messages` に「招待カード種別」を追加して表現する。

> **原則6（新規テーブル UUIDv7）は非該当**: 新規テーブルを追加しないため、既存 `invite_tokens`（BIGINT PK）・`chat_messages`（BIGINT PK）の採番方式をそのまま踏襲する。UUIDv7 化は既存テーブルの ID 変更を伴い超侵襲的であるため行わない（CLAUDE.md アーキテクチャ思想 原則6「既存テーブルの BIGINT ID は変更しない」に従う）。

### 変更① `chat_messages`（chat ドメイン）

招待カードをメッセージストリーム上で表現するため、2カラムを追加する。

| カラム名 | 型 | NULL | デフォルト | 説明 |
|---------|---|------|-----------|------|
| `message_type` | VARCHAR(20) | NO | `'TEXT'` | メッセージ種別。`TEXT`（通常本文） / `INVITE_CARD`（チーム/組織への招待カード）。将来 `SYSTEM_EVENT` 等の拡張余地を残すため **VARCHAR + アプリ層検証**（ENUM にしない） |
| `invite_token_id` | BIGINT UNSIGNED | YES | NULL | `message_type = 'INVITE_CARD'` のとき、参照する招待トークン（`invite_tokens.id`）。**クロスドメイン FK は張らずインデックスのみ**（後述）。通常メッセージは NULL |

**インデックス（追加）**
```sql
INDEX idx_chat_messages_invite_token (invite_token_id)   -- 招待カードの逆引き（トークン失効時にカード状態を再解決）
```

**制約・備考**
- **`message_type` を VARCHAR にする理由**: 種別は将来増える見込み（招待カード・システムイベント・投票カード等）。MySQL の `ENUM` は値追加のたびに `ALTER TABLE`（メタデータロック）を要し、アプリ層 enum との二重管理になる。よって **VARCHAR + アプリ層 enum バリデーション**（`MessageType` enum の `valueOf` で検証、未知値は 400）で運用する。F04.2 の `chat_channels.channel_type` / `source_type` と同一の設計ポリシー。
- **`is_system` との役割分担**: 既存 `is_system`（BOOLEAN）は「メンバー参加/退出/チャンネル名変更等の、送信者を持たない告知（`sender_id = NULL`）」を表す既存の関心事。招待カードは **送信者（招待の発行者）を持つ実メッセージ** であり `sender_id` が非 NULL のため、`is_system = FALSE` のまま `message_type = 'INVITE_CARD'` で表現する。両者は直交する（`is_system` は「誰の発言でもないシステム告知か」、`message_type` は「本文の描画種別」）。招待カードは `is_system` を立てない。
- **クロスドメイン FK を張らない理由（原則1）**: `chat_messages` は chat ドメイン、`invite_tokens` は role ドメインに属する別ドメイン。異なるドメインのテーブル間に FK 制約を張らない（参照整合性はアプリ層 Service で保証）。インデックスのみ張り、トークン削除連鎖（CASCADE）も設定しない。
- **既存メッセージへの後方互換**: 既存行はマイグレーションで `message_type = 'TEXT'`（DEFAULT）が入る。`invite_token_id` は NULL。プレビュー生成（`last_message_preview`）は招待カードを「◯◯さんを招待しました」等の要約文に置換し、本文 TEXT と同様に扱う。

### 変更② `invite_tokens`（role ドメイン）

宛先を名指しする承諾型招待を表現するため、1カラムを追加する。

| カラム名 | 型 | NULL | デフォルト | 説明 |
|---------|---|------|-----------|------|
| `target_user_id` | BIGINT UNSIGNED | YES | NULL | 承諾型招待の宛先ユーザー（`users.id`）。**NULL = 従来の共有リンク型（誰でも参加可）** / **非 NULL = 宛先付き承諾型（この user のみ承諾可）**。**クロスドメイン FK は張らずインデックスのみ**（users は user ドメイン） |

**インデックス（追加）**
```sql
INDEX idx_it_target_user (target_user_id)   -- 宛先ユーザー宛ての PENDING 招待一覧
```

**制約・備考**
- **併存設計（NULL / 非 NULL の二態）**: 既存の共有リンク型招待（`target_user_id IS NULL`）と、本機能の宛先付き承諾型招待（`target_user_id IS NOT NULL`）を **同一テーブルで併存** させる。既存の発行 API・参加フローは NULL のまま影響を受けない。承諾時の宛先照合は「`target_user_id` が非 NULL のときのみ実行」する条件付き分岐で追加する。
- **宛先付きトークンの推奨既定値**: 承諾型は特定個人宛のため `max_uses = 1`（1回で消費）・`expires_at = 発行から7日` を既定とする。ただしカラムの制約ではなくアプリ層の既定値。
- **`target_user_id` に FK を張らない理由（原則1）**: users は別ドメイン。宛先ユーザーが退会（匿名化）した場合でもトークン行は残す（`SET NULL` の連鎖削除を設定しない）。退会ユーザー宛ての PENDING 招待は承諾されないまま `expires_at` で自然に EXPIRED になる。
- **`chk_it_scope`（既存 XOR CHECK）への影響なし**: `team_id`/`organization_id` の XOR 制約は不変。`target_user_id` は直交する軸（「どのスコープへ」×「誰を宛先に」）であり、既存制約に触れない。

### ドメイン越境の俯瞰

```
chat_messages (chat ドメイン)                invite_tokens (role ドメイン)
  message_type = 'INVITE_CARD'                  target_user_id = 宛先 users.id (user ドメイン)
  invite_token_id ──(FKなし・INDEX)──▶ id
                                                team_id/organization_id (team/org ドメイン)
```

いずれの参照もドメインをまたぐため **FK を張らずアプリ層で整合性を保証**（原則1）。

## 4. API設計

### エンドポイント一覧

| メソッド | パス | 認可 | 説明 |
|---|---|---|---|
| POST | `/api/v1/chat/channels/{channelId}/membership-invite` | 必要（対象スコープの ADMIN/DEPUTY_ADMIN）| DM 相手を指定スコープへ招待（宛先付きトークン発行＋招待カード投稿） |
| GET | `/api/v1/me/invitable-scopes` | 必要（認証）| 自分が招待発行できる（ADMIN/DEPUTY_ADMIN の）スコープ一覧を返す（招待モーダルの選択肢） |
| POST | `/api/v1/invite/{token}/join` | 必要（認証）| **既存 API を流用**。宛先照合込みで承諾（PENDING→参加） |
| DELETE | `/api/v1/chat/channels/{channelId}/membership-invite/{tokenId}` | 必要（発行者 or 対象スコープ ADMIN）| 招待の取消（CANCELLED。トークン失効＋カードを取消済み表示に更新） |

### `POST /api/v1/chat/channels/{channelId}/membership-invite`

DM チャンネルの相手を、指定したチーム/組織へ招待する。宛先付きトークンを発行し、当該 DM チャンネルへ招待カード（`message_type = 'INVITE_CARD'`）を投稿する。

**パスパラメータ**
- `channelId`（BIGINT）: DM チャンネル ID。`channel_type = 'DIRECT'` であること。

**リクエストボディ**
```json
{
  "scopeType": "TEAM",
  "scopeId": 12,
  "roleId": null,
  "expiresInDays": 7
}
```
| フィールド | 型 | NULL | 説明 |
|---|---|---|---|
| `scopeType` | string | 不可 | `TEAM` / `ORGANIZATION` |
| `scopeId` | number | 不可 | 招待先チーム/組織の ID |
| `roleId` | number | 可（null 時は当該スコープの MEMBER ロール）| 参加時に付与するロール |
| `expiresInDays` | number | 可（null 時は 7）| 有効期限（1/7/30/90、または無期限は非対応=承諾型は必ず期限あり）|

**レスポンス（201 Created）**
```json
{
  "data": {
    "tokenId": 3001,
    "token": "b2f7c0e2-1a3d-4c5e-8f9a-0b1c2d3e4f50",
    "targetUserId": 88,
    "scopeType": "TEAM",
    "scopeId": 12,
    "scopeName": "北陽SC ジュニア",
    "status": "PENDING",
    "expiresAt": "2026-07-25T09:00:00Z",
    "cardMessageId": 990012
  }
}
```
| フィールド | 型 | NULL | 説明 |
|---|---|---|---|
| `tokenId` | number | 不可 | 発行された `invite_tokens.id` |
| `token` | string | 不可 | 承諾 API に渡す UUID |
| `targetUserId` | number | 不可 | 宛先（DM 相手）の user ID |
| `scopeName` | string | 不可 | 招待先の表示名（カード描画用） |
| `status` | string | 不可 | 常に `PENDING` |
| `expiresAt` | string(ISO8601) | 不可 | 有効期限 |
| `cardMessageId` | number | 不可 | 投稿された招待カード `chat_messages.id` |

**認可（public 入口でガード）**:
- 実行ユーザーが `scopeType`/`scopeId` の **ADMIN または DEPUTY_ADMIN（`INVITE_MEMBERS` 権限保有）** であること（F00 認可基盤の scope 権限解決を経由。共有メソッド任せにせず本エンドポイントでガード）。
- 実行ユーザーが `channelId`（DIRECT チャンネル）のメンバーであり、宛先はその DM の相手であること。

**エラーレスポンス**
| ステータス | エラーコード | 条件 |
|---|---|---|
| 401 | — | 未認証 |
| 403 | TEAM_048 / — | 実行ユーザーが対象スコープの ADMIN/DEPUTY_ADMIN でない、または DM チャンネルの当事者でない |
| 404 | TEAM_001 / ORG_001 | スコープが存在しない/論理削除済み、またはチャンネルが存在しない |
| 409 | TEAM_003 | 宛先がすでに当該スコープのメンバー（招待不可） |
| 422 | TEAM_002 | 招待先がアーカイブ済み |

### `POST /api/v1/invite/{token}/join`（既存流用・宛先照合追加）

承諾（PENDING→参加）。**既存の共有リンク参加 API をそのまま流用** し、宛先照合ロジックのみ条件付きで追加する。

**承諾時の追加判定（既存フローへの差分）**:
1. トークン取得。`revoked_at IS NULL` かつ未期限（`expires_at > NOW()`）でなければ **ROLE_002**（無効/期限切れ）。
2. `used_count >= max_uses` なら **ROLE_003**（使用回数上限）。
3. **`target_user_id` が非 NULL の場合**（＝承諾型）: `target_user_id == 実行ユーザー ID` を照合。不一致なら **403 ROLE_009**（宛先不一致）。`target_user_id` が NULL の場合（共有リンク型）はこの照合をスキップ（既存挙動を維持）。
4. すでに当該スコープのメンバーなら **409 TEAM_003**（冪等: 二重承諾防止）。
5. メンバー化（`user_roles` / `memberships` へ INSERT）＋`used_count` インクリメント＋トークンを消費済みに。
6. 対応する招待カードの表示状態を「参加済み（JOINED）」へ更新。

**レスポンス（200 OK）**: 参加したスコープのサマリーを返す（既存レスポンス構造を踏襲）。

### `GET /api/v1/me/invitable-scopes`

招待モーダルの選択肢。自分が ADMIN/DEPUTY_ADMIN（`INVITE_MEMBERS` 権限）として招待発行できるスコープの一覧。

**レスポンス（200 OK）**
```json
{
  "data": {
    "teams": [{ "scopeId": 12, "name": "北陽SC ジュニア", "role": "ADMIN" }],
    "organizations": []
  }
}
```
- 管理スコープが **0 件でもエラーにせず空配列を返す**（200）。FE は空なら「招待できるチーム/組織がありません」を表示。

## 5. ビジネスロジック

### 招待発行フロー（越境トランザクション方針 = 原則5）

招待発行は **role ドメイン（トークン発行）を主トランザクション** とし、chat ドメイン（カード投稿）は主 tx の外で **明示的な Service 呼び出し** として連結する。単一の `@Transactional` で role と chat の Repository を同時にまたがない。

```
1. POST /chat/channels/{channelId}/membership-invite を受付
2. 【認可】実行ユーザーが scope の ADMIN/DEPUTY_ADMIN(INVITE_MEMBERS) か検証 → 否なら 403
3. 【当事者】channelId が DIRECT で実行ユーザーが当事者、宛先=相手 か検証 → 否なら 403
4. 【既メンバー】宛先が既に scope メンバーか検証 → Yes なら 409 TEAM_003
5. 【role ドメイン @Transactional】invite_tokens に INSERT
   （target_user_id=相手, team_id/organization_id=scope, role_id, max_uses=1, expires_at）
   → tokenId 確定・コミット
6. 【chat ドメイン Service 呼び出し（別 tx）】DM チャンネルへ INVITE_CARD メッセージを投稿
   （sender_id=発行者, message_type='INVITE_CARD', invite_token_id=tokenId, is_system=FALSE）
7. 【補償】6 が失敗した場合、5 のトークンを revoked_at=NOW() で失効させる（中途半端な PENDING を残さない）
8. 【到達通知】F04.9/F04.3 基盤で宛先へ「招待が届きました」通知（confirmable ではなく通常通知でよい）
9. 201 Created を返す
```

> **TODO（原則5・将来のイベント駆動化候補）**: 手順 5→6 は role ドメインと chat ドメインをまたぐ。現状は「トークン発行 tx コミット後に chat Service を明示呼び出し、失敗時はトークン失効で補償」する **Saga 風の補償トランザクション** とする。将来は `MembershipInviteIssuedEvent`（role ドメイン発火）を chat ドメインが購読してカード投稿する **イベント駆動** へ移行する。この越境は設計書間で追跡（本節と F04.2 の source_type 連携方針を将来統合）。

### 招待カードの状態遷移（表示状態）

招待カードは `invite_tokens` の状態から **導出**（カード自体は状態を持たず、参照先トークン＋メンバーシップから解決）する。

| 表示状態 | 導出条件 | カード上の主 UI |
|---|---|---|
| **PENDING** | トークン有効（`revoked_at IS NULL` かつ未期限）かつ宛先が未参加 | 「参加する」ボタン（宛先本人にのみ活性）|
| **JOINED** | 宛先が当該スコープのメンバー（承諾済み）| 「参加済み」バッジ（ボタン非活性）|
| **EXPIRED** | `expires_at <= NOW()` かつ未参加 | 「期限切れ」表示（ボタン非活性）|
| **REVOKED** | `revoked_at IS NOT NULL` かつ未参加（発行者取消 or 補償失効）| 「取消済み」表示（ボタン非活性）|

- カードは宛先本人と発行者の双方に見える（DM の 2 者）。「参加する」ボタンは **宛先本人にのみ活性**（発行者側では「相手の承諾待ち」表示）。
- 第三者はそもそも DM チャンネル非メンバーなのでカードを取得できない（チャンネル ACL が一次防壁、宛先照合が二次防壁）。

### 状態機械（オファー）

```
        発行(POST membership-invite)
              │
              ▼
          [PENDING]
          /   │   \
   accept  decline  expire/cancel
      │       │        │
      ▼       ▼        ▼
  [ACCEPTED][DECLINED][EXPIRED/CANCELLED]
  = メンバー化   = トークン失効（未参加のまま）
```
- 本機能では **DECLINED は「辞退」= トークンを消費せず宛先が明示的に断る**（`revoked_at` を立てず、カードを閉じる軽量な扱い / MVP ではボタン非表示にするだけでも可）。監査上の必須要件ではないため MVP では EXPIRED/CANCELLED を主経路とし、DECLINED は将来拡張として設計に残す。

## 6. エラーコード

| 事象 | HTTP | コード | 出所 |
|---|---|---|---|
| 宛先不一致（他人宛て招待を第三者が承諾）| 403 | **ROLE_009（新規採番）** | role（新規）|
| 対象スコープの ADMIN/DEPUTY_ADMIN でない | 403 | TEAM_048 | team（既存）|
| 招待トークンが無効/期限切れ | 400 | ROLE_002 | role（既存）|
| 使用回数上限に達している | 400 | ROLE_003 | role（既存）|
| 宛先がすでにメンバー | 409 | TEAM_003 | team（既存）|
| スコープ/チャンネルが存在しない | 404 | TEAM_001 / ORG_001 | team/org（既存）|
| 招待先がアーカイブ済み | 422 | TEAM_002 | team（既存）|

> **ROLE_009 の採番について**: 現状 `RoleErrorCode` の最大は **ROLE_008**（QRコードサイズ）であるため、宛先不一致用に **ROLE_009 を予約** する。ただし本設計はマージまでに他ブランチで ROLE_009 が先に確定する可能性があるため、**コードの確定値はマージ時に origin/main の `RoleErrorCode` を再確認して採番する**（連番衝突を避ける）。メッセージ案: 「この招待はあなた宛てではありません」。

## 7. Flyway マイグレーション

| 版 | 対象 | 内容 |
|---|---|---|
| `V{major}.{yyyyMMddHHmmss}`（見込み V157 相当）| `chat_messages` | `message_type VARCHAR(20) NOT NULL DEFAULT 'TEXT'` 追加、`invite_token_id BIGINT UNSIGNED NULL` 追加、`idx_chat_messages_invite_token` 追加 |
| `V{major}.{yyyyMMddHHmmss}`（見込み V158 相当）| `invite_tokens` | `target_user_id BIGINT UNSIGNED NULL` 追加、`idx_it_target_user` 追加 |

- 2 テーブルへの変更だが、ドメインが異なる（chat / role）ため **別ファイル 2 本** を推奨（ドメイン境界を Flyway ファイルでも維持）。1 本集約も技術上は可能だが非推奨。
- **採番規約（CLAUDE.md / backend/.claudecode.md §18）**: `major` は「origin/main 全体の最大 major + 1」で **マージ時に確定**（本設計の V157/V158 はあくまで見込み）。`minor` は **タイムスタンプ必須**（`date -u '+%Y%m%d%H%M%S'`。連番 `.001` は番人テスト `FlywayTimestampNamingGuardTest` が機械的に拒否）。
- **既存データ番人テストの要否**: 両変更とも **NULL 許容カラム追加 or DEFAULT 付き NOT NULL カラム追加** のみで、既存行に矛盾を生じない（CHECK 制約の後付けや既存値の書き換えを伴わない）。よって `feedback_flyway_existing_data_check_drop` のような「DROP→UPDATE 順序」番人テストは不要。ただし `chat_messages.message_type` の DEFAULT が全既存行に `'TEXT'` を埋めることをマイグレーションテストで確認する。

## 8. 再利用資産の配線

- **`GET /api/v1/me/teams` 系 + 新設 getter `adminOrDeputyTeams`**: 招待可能スコープの解決は、既存のメンバーシップ/ロール解決（`memberships` + `user_roles` 統合。`feedback_role_resolution_memberships_gap`）を経由する。**既存 `adminTeams` getter は触らず**、DEPUTY_ADMIN（`INVITE_MEMBERS` 権限保有）を含む `adminOrDeputyTeams`（および組織版）を **新設** して `GET /me/invitable-scopes` の実装に用いる。
- **招待トークン基盤（F01.2 `invite_tokens`）**: 発行・失効・`used_count` のアトミック消費（`SELECT ... FOR UPDATE`）・チーム/組織論理削除時の一括失効は既存ロジックをそのまま流用。`target_user_id` の照合分岐のみ追加。
- **参加時の重複防止（TEAM_003）**: `joinByInvite` 既存フローの「すでにメンバーなら弾く」処理を流用（冪等・二重承諾防止）。
- **到達通知（F04.9 / F04.3）**: 招待到達を宛先へ通知する。確認取得（confirm）まで求める F04.9 confirmable は本機能では過剰なため、**通常のアプリ内通知＋任意プッシュ** を用いる（confirmable 基盤は参照モデルであり、承諾自体はカードの「参加する」で行う）。
- **チャットカード描画（F04.2）**: `source_data` 拡張と同様に、`GET /chat/channels/{id}/messages` のレスポンスで `message_type = 'INVITE_CARD'` の行に招待サマリー（`inviteData`: スコープ名・状態・宛先か否か）を付与して返す。

## 9. 受け入れ条件

### 正常系
- [ ] ADMIN/DEPUTY_ADMIN が招待ボタンを押すと、自分が管理するスコープのみが選択肢に出る（`GET /me/invitable-scopes`）。**管理スコープ 0 件でもエラーにせず空を返す**。
- [ ] 招待発行で「宛先＝DM 相手を指定したトークン（`target_user_id` 非 NULL）」が生成され、当該 DM に招待カード（`message_type='INVITE_CARD'`, `invite_token_id` セット）が投稿される。
- [ ] 宛先本人が「参加する」を押すとメンバー化され、カードが「参加済み（JOINED）」表示に変わる。
- [ ] 招待発行者側では「参加する」ボタンが非活性で「承諾待ち」表示になる。

### 異常系（認可 / IDOR = 核心）
- [ ] **第三者が他人宛て招待トークンを `POST /invite/{token}/join` で叩くと 403 ROLE_009**（宛先照合で弾く）。
- [ ] ADMIN/DEPUTY_ADMIN でないユーザーが `POST /chat/channels/{id}/membership-invite` を直叩きすると 403（public 入口でガード）。
- [ ] DM の当事者でないユーザーが当該チャンネルからの招待発行を試みると 403。

### 境界
- [ ] **期限ちょうど**（`expires_at == NOW()`）の承諾は EXPIRED 扱いで弾かれ、カードが「期限切れ」表示になる。
- [ ] 失効済み（発行者取消 REVOKED）トークンの承諾は弾かれ、カードが「取消済み」表示になる。
- [ ] **既メンバー境界**: 宛先がすでにメンバーの場合、招待発行は 409 TEAM_003 で弾かれる。発行後に別経路で参加した後の二重承諾も TEAM_003 で冪等に弾く。

### 途中失敗（Saga 補償）
- [ ] トークン発行は成功したがカード投稿が失敗した場合、**トークンが失効（REVOKED）され、宙に浮いた PENDING が残らない**。
- [ ] 逆に、承諾処理の途中失敗でメンバー化とトークン消費が **部分適用されない**（`join` は単一 tx）。

### 攻め口5類型の消し込み
| 類型 | 消し込み |
|---|---|
| 空/0件/null | 管理スコープ 0 件で `GET /me/invitable-scopes` が 200 空配列（500 でない）。`target_user_id` NULL の既存共有リンク型は宛先照合をスキップして従来どおり動く |
| 境界 | 期限ちょうど・既メンバー境界・`max_uses=1` 消費境界 |
| 途中失敗 | 発行 2 段（トークン＋カード）の Saga 補償で中途半端を残さない |
| **認可（IDOR）** | **宛先照合（ROLE_009）＋スコープ権限ガード（TEAM_048/403）＋チャンネル ACL の三重防壁**。本機能の核心 |
| 性能 | `GET /me/invitable-scopes` は N+1 を避け一括クエリ。招待一覧・カード解決は `idx_it_target_user` / `idx_chat_messages_invite_token` を使用 |

### 横断要件
- [ ] UI 文字列は i18n 6 言語（ja/en/zh/ko/es/de）にキー追加（直書き禁止）。
- [ ] 新規モーダル/カードに `/統一`（共通コンポーネント）・`/手助け`（使い方ガイド）を適用。

## 11. 非機能

- **シャーディング整合性**: 新規テーブルを追加せず既存テーブルへのカラム追加のみのため、UUIDv7 方針（原則6）・テナントスコープ Repository 方針（原則7）に新たな違反を持ち込まない。`invite_tokens` は `team_id`/`organization_id` を持つが、宛先照合は user 単位のため organization_id シャードキーに直接は乗らない（承諾は宛先ユーザーの文脈で実行）。1000万ユーザー規模でも招待トークンは短命（`max_uses=1`・7日期限）で肥大化しにくい。
- **レートリミット**: 招待発行 `POST /chat/channels/{id}/membership-invite` は既存の招待発行レートリミット（`POST /teams|organizations/{id}/invite-tokens` の 10 req/hour per user）に準じて制限し、DM を悪用した招待スパムを防止する。
- **プライバシー**: 招待カードは DM の 2 者にのみ見える（チャンネル ACL）。宛先の user ID・表示名以外の個人情報はカードに載せない。

## 12. 判断保留（後続の6観点精査で詰める）

- **DECLINED（辞退）の永続化要否**: MVP では EXPIRED/CANCELLED を主経路とし辞退はカードを閉じる軽量扱いにしたが、辞退を監査ログに残すか（再招待の抑制・ハラスメント対策）は精査で確定する。
- **`roleId` の指定可否**: 本設計は既定 MEMBER。ADMIN/DEPUTY_ADMIN ロールを招待段階で指名させるかは、ADMIN 昇格に 2FA 必須（F01.2 transfer-ownership 参照）との整合を含め精査で確定。
- **招待の一意性制約**: 同一 DM で同一スコープ宛ての PENDING 招待を重複発行できるか（UNIQUE 制約 or アプリ層で 1 件に制限するか）は未確定。
- **Flyway 集約 vs 分割**: chat/role の 2 ドメインを別ファイルにするか 1 本に集約するかは、番人テスト・レビュー方針を踏まえ最終決定。
