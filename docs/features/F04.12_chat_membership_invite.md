## 1. 概要

1対1チャット（DM）を交わしている相手を、その場から自分が管理するチーム/組織へ **招待** する機能。従来の招待は「共有リンク/QR を渡して相手にクリックしてもらう」プル型だったが、本機能は **DM 相手を名指しで招待し、相手がチャット内カードで承諾して初めてメンバー化する** 承諾型（オファー型）とする。

**承諾型オファーの共通思想**（F01.2 team-invites / org-invites の PENDING→ACTIVE、F04.9 確認通知、および本機能と同時整備する「オーナー委譲の承諾型化」で一貫させる）:

```
PENDING ──承諾──▶ ACCEPTED（効果発生）
   │
   ├──辞退──▶ DECLINED
   ├──期限──▶ EXPIRED
   └──取消──▶ CANCELLED（発行者が取消）
```

相手の能動的な承諾（accept）があって初めて効果（メンバー化）が発生する点が、旧来の共有リンク型（クリックした人が誰でも参加できる）と根本的に異なる。指名相手だけが承諾できる **宛先照合** を核心の認可要件とし、IDOR（他人宛ての招待を第三者が承諾する）を構造的に封じる。

### 決定事項

| 論点 | 決定 |
|---|---|
| 招待の型 | **承諾型**（宛先を名指し・相手の accept で発効）。旧共有リンク型は併存（撤去しない） |
| 入口 | **1対1チャット（`DM` チャンネル）の相手** に限定。**`GROUP_DM`（複数人）は本設計のスコープ外**（発行 API 入口で 422 拒否） |
| 承諾 UI | **チャット内カード方式**（別画面遷移を強制しない。DM のメッセージストリームに招待カードを差し込む） |
| 招待できるスコープ | 発行者が **ADMIN または DEPUTY_ADMIN（`INVITE_MEMBERS` 権限）** として管理するチーム/組織のみ |
| 付与ロール | **非特権ロールのみ**（MEMBER/SUPPORTER 等）。**ADMIN/DEPUTY_ADMIN の指定は発行入口で 422 拒否**（権限昇格の抜け穴を塞ぐ。§6・C-1 参照）|
| 辞退 | **永続化する**（`revoked_at` を立てカードを REVOKED 表示。再取得で PENDING 復活・二重 accept を防ぐ）|

## 2. スコープ

### 対象ロール
| ロール | 操作可能な範囲 |
|--------|--------------|
| SYSTEM_ADMIN | 全招待の参照・強制取消（モデレーション） |
| ADMIN | 自分が ADMIN のチーム/組織へ DM 相手を招待・取消 |
| DEPUTY_ADMIN | `INVITE_MEMBERS` 権限を持つ場合: 自分が DEPUTY_ADMIN のチーム/組織へ DM 相手を招待・取消 |
| MEMBER | 招待の発行不可。自分宛て招待カードの承諾/辞退のみ |
| SUPPORTER | 招待の発行不可。自分宛て招待カードの承諾/辞退のみ |
| GUEST | 対象外 |

> 招待を「受ける」側はロール不問（DM の相手であれば誰でも受信できる）。招待を「出す」側にのみ ADMIN/DEPUTY_ADMIN のスコープ権限を要求する。

### 対象レベル
- [x] 組織 (Organization) — DM 相手を組織へ招待
- [x] チーム (Team) — DM 相手をチームへ招待
- [x] 個人 (Personal) — DM（`channel_type = 'DM'` の1対1チャンネル）が入口

## 3. DB設計

本機能は **新規テーブルを作らず、既存2テーブルへのカラム追加のみ** で実現する。招待の本体は F01.2 の `invite_tokens` を「宛先付き」に拡張して再利用し、チャット上の表示は `chat_messages` に「招待カード種別」を追加して表現する。

> **原則6（新規テーブル UUIDv7）は非該当**: 新規テーブルを追加しないため、既存 `invite_tokens`（BIGINT PK）・`chat_messages`（BIGINT PK）の採番方式をそのまま踏襲する。UUIDv7 化は既存テーブルの ID 変更を伴い超侵襲的であるため行わない（CLAUDE.md アーキテクチャ思想 原則6「既存テーブルの BIGINT ID は変更しない」に従う）。

### 変更① `chat_messages`（chat ドメイン）

招待カードをメッセージストリーム上で表現するため、2カラムを追加する。

| カラム名 | 型 | NULL | デフォルト | 説明 |
|---------|---|------|-----------|------|
| `message_type` | VARCHAR(20) | NO | `'TEXT'` | メッセージ種別。`TEXT`（通常本文） / `INVITE_CARD`（チーム/組織への招待カード）。将来 `SYSTEM_EVENT` 等の拡張余地を残すため **VARCHAR + アプリ層検証**（ENUM にしない） |
| `invite_token_id` | BIGINT UNSIGNED | YES | NULL | `message_type = 'INVITE_CARD'` のとき、参照する招待トークン（`invite_tokens.id`）。**クロスドメイン FK は張らずインデックスのみ**（後述）。通常メッセージは NULL |

**インデックス（追加）**
```sql
INDEX idx_chat_messages_invite_token (invite_token_id)   -- 招待カードの逆引き（トークン失効時にカード状態を再解決）
```

**制約・備考**
- **`message_type` を VARCHAR にする理由**: 種別は将来増える見込み（招待カード・システムイベント・投票カード等）。MySQL の `ENUM` は値追加のたびに `ALTER TABLE`（メタデータロック）を要し、アプリ層 enum との二重管理になる。よって **VARCHAR + アプリ層 enum バリデーション**（`MessageType` enum の `valueOf` で検証、未知値は 400）で運用する。F04.2 の `chat_channels.channel_type` / `source_type` と同一の設計ポリシー。
- **`is_system` との役割分担**: 既存 `is_system`（BOOLEAN）は「メンバー参加/退出/チャンネル名変更等の、送信者を持たない告知（`sender_id = NULL`）」を表す既存の関心事。招待カードは **送信者（招待の発行者）を持つ実メッセージ** であり `sender_id` が非 NULL のため、`is_system = FALSE` のまま `message_type = 'INVITE_CARD'` で表現する。両者は直交する。招待カードは `is_system` を立てない。
- **`body` の格納値（M-2）**: `chat_messages.body` は **NOT NULL**（TEXT）。`INVITE_CARD` の描画は後述 `inviteData`（`invite_tokens` から導出）で行うため body は表示に使わないが、NOT NULL 制約を満たすため **i18n 非依存の固定要約文字列**（例: `"[招待カード]"`。内部マーカー）を格納する。`body` を NULL 化する列変更は既存メッセージ全体に波及し影響が大きいため採らない。UI 表示・多言語文言は body ではなく `inviteData` + i18n キー（§10）で構築する。
- **`last_message_preview` への反映（D-14）**: 招待カードのプレビューは **i18n キー参照ではなく、投稿時点のロケールで生成した実文字列**（例: 「北陽SC ジュニア への招待を送りました」）を `last_message_preview`（既存 denormalize 列）に格納する。プレビュー列は全チャンネル一覧の高速表示用 denormalize であり、多言語再解決コストを避けるため既存メッセージ同様に実文字列で持つ（F04.2 の `last_message_preview` 方針を踏襲）。カード本体（メッセージストリーム内）の文言は `inviteData` + i18n で都度描画する。
- **クロスドメイン FK を張らない理由（原則1）**: `chat_messages` は chat ドメイン、`invite_tokens` は role ドメインに属する別ドメイン。異なるドメインのテーブル間に FK 制約を張らない（参照整合性はアプリ層 Service で保証）。インデックスのみ張り、トークン削除連鎖（CASCADE）も設定しない。
- **既存メッセージへの後方互換**: 既存行はマイグレーションで `message_type = 'TEXT'`（DEFAULT）が入る。`invite_token_id` は NULL。

### 変更② `invite_tokens`（role ドメイン）

宛先を名指しする承諾型招待を表現するため、1カラムを追加する。

| カラム名 | 型 | NULL | デフォルト | 説明 |
|---------|---|------|-----------|------|
| `target_user_id` | BIGINT UNSIGNED | YES | NULL | 承諾型招待の宛先ユーザー（`users.id`）。**NULL = 従来の共有リンク型（誰でも参加可）** / **非 NULL = 宛先付き承諾型（この user のみ承諾可）**。**クロスドメイン FK は張らずインデックスのみ**（users は user ドメイン） |

**インデックス（追加）**
```sql
INDEX idx_it_target_user (target_user_id)   -- 宛先ユーザー宛ての PENDING 招待一覧
```

**制約・備考**
- **併存設計（NULL / 非 NULL の二態）**: 既存の共有リンク型招待（`target_user_id IS NULL`）と、本機能の宛先付き承諾型招待（`target_user_id IS NOT NULL`）を **同一テーブルで併存** させる。既存の発行 API・参加フローは NULL のまま影響を受けない。承諾時の宛先照合は「`target_user_id` が非 NULL のときのみ実行」する条件付き分岐で追加する。
- **宛先付きトークンの推奨既定値**: 承諾型は特定個人宛のため `max_uses = 1`（1回で消費）・`expires_at = 発行から7日` を既定とする（カラム制約ではなくアプリ層の既定値）。
- **辞退（DECLINED）の永続化（①）**: 辞退は `revoked_at = NOW()` を立てて表現する（`invite_tokens` に status 列は追加しない）。これにより再取得しても `isValid()=false` となり PENDING に復活せず、二重 accept を構造的に防ぐ。辞退・取消・補償失効はいずれも `revoked_at` で一元表現し、区別は audit_logs の理由（DECLINED / CANCELLED / COMPENSATED）で保持する。
- **`target_user_id` に FK を張らない理由（原則1）**: users は別ドメイン。宛先ユーザーが退会（匿名化）した場合でもトークン行は残す（連鎖削除しない）。退会ユーザー宛ての PENDING は承諾されないまま `expires_at` で自然に EXPIRED になる。
- **`chk_it_scope`（既存 XOR CHECK）への影響なし**: `team_id`/`organization_id` の XOR 制約は不変。`target_user_id` は直交する軸であり既存制約に触れない。

### ドメイン越境の俯瞰

```
chat_messages (chat ドメイン)                invite_tokens (role ドメイン)
  message_type = 'INVITE_CARD'                  target_user_id = 宛先 users.id (user ドメイン)
  invite_token_id ──(FKなし・INDEX)──▶ id
                                                team_id/organization_id (team/org ドメイン)
```

いずれの参照もドメインをまたぐため **FK を張らずアプリ層で整合性を保証**（原則1）。

## 4. API設計

### エンドポイント一覧

| メソッド | パス | 認可 | 説明 |
|---|---|---|---|
| POST | `/api/v1/chat/channels/{channelId}/membership-invite` | 必要（対象スコープの ADMIN/DEPUTY_ADMIN）| DM 相手を指定スコープへ招待（宛先付きトークン発行＋招待カード投稿） |
| GET | `/api/v1/me/invitable-scopes` | 必要（認証）| 自分が招待発行できる（ADMIN/DEPUTY_ADMIN の）スコープ一覧を返す（招待モーダルの選択肢） |
| POST | `/api/v1/invite/{token}/join` | 必要（認証）| **既存 API を流用**。宛先照合＋特権ロール拒否の保険を追加して承諾（PENDING→参加） |
| POST | `/api/v1/invite/{token}/decline` | 必要（宛先本人）| **辞退**（`revoked_at` を立てカードを REVOKED 表示・audit に DECLINED 記録）|
| DELETE | `/api/v1/chat/channels/{channelId}/membership-invite/{tokenId}` | 必要（発行者 or 対象スコープ ADMIN）| 招待の取消（`revoked_at`＋カードを取消済み表示・audit に CANCELLED 記録） |

### `POST /api/v1/chat/channels/{channelId}/membership-invite`

DM チャンネルの相手を、指定したチーム/組織へ招待する。宛先付きトークンを発行し、当該 DM チャンネルへ招待カード（`message_type = 'INVITE_CARD'`）を投稿する。

**パスパラメータ**
- `channelId`（BIGINT）: DM チャンネル ID。`channel_type = 'DM'` であること（`GROUP_DM` は 422）。

**リクエストボディ（camelCase）**
```json
{
  "scopeType": "TEAM",
  "scopeId": 12,
  "roleId": null,
  "expiresInDays": 7
}
```
| フィールド | 型 | NULL | 説明 |
|---|---|---|---|
| `scopeType` | string | 不可 | `TEAM` / `ORGANIZATION` |
| `scopeId` | number | 不可 | 招待先チーム/組織の ID |
| `roleId` | number | 可（null 時は当該スコープの MEMBER ロール）| 参加時に付与するロール。**非特権ロール（MEMBER/SUPPORTER 等）のみ許可。ADMIN/DEPUTY_ADMIN を指定すると 422**（§6・C-1）|
| `expiresInDays` | number | 可（null 時は 7）| 有効期限日数。**許容値は 1 / 7 / 30 / 90 のみ**（それ以外は 422）。**無期限は非対応**（承諾型は必ず期限あり）。BE 側の既存 `InviteService.resolveExpiresAt` は `"1d"/"7d"/"30d"/"90d"` の**文字列**を受けるため、**発行 Service で `expiresInDays`(number) → `"{n}d"`(string) へ変換**してから既存経路に渡す（B-8）|

**レスポンス（201 Created・camelCase）**
```json
{
  "data": {
    "tokenId": 3001,
    "token": "b2f7c0e2-1a3d-4c5e-8f9a-0b1c2d3e4f50",
    "targetUserId": 88,
    "scopeType": "TEAM",
    "scopeId": 12,
    "scopeName": "北陽SC ジュニア",
    "status": "PENDING",
    "expiresAt": "2026-07-25T09:00:00Z",
    "cardMessageId": 990012
  }
}
```

**認可（public 入口でガード）**:
- 実行ユーザーが `scopeType`/`scopeId` の **ADMIN または DEPUTY_ADMIN（`INVITE_MEMBERS` 権限保有）** であること（F00 認可基盤の scope 権限解決を経由。共有メソッド任せにせず本エンドポイントでガード）。
- 実行ユーザーが `channelId`（`DM` チャンネル）のメンバーであり、宛先はその DM の相手であること。

**宛先ユーザーの導出（B-9）**:
- `channelId` から宛先（`targetUserId`）は **`chat_channel_members` のうち実行ユーザー以外の1名** として導出する（DM は2レコード固定・F04.2）。
- **`channel_type` が `DM` でない**（`GROUP_DM` 等）場合は 422。`chat_channel_members` が実行ユーザー含め2名でない場合も 422（DM 2名前提ガード）。
- 相手が **退会済み（匿名化）** の場合は 422（招待先を持てない）。

**エラーレスポンス**
| ステータス | エラーコード | 条件 |
|---|---|---|
| 401 | — | 未認証 |
| 403 | TEAM_048 / ORG_048 | 実行ユーザーが対象スコープの ADMIN/DEPUTY_ADMIN でない |
| 403 | — | DM チャンネルの当事者でない |
| 404 | TEAM_001 / ORG_001 | スコープが存在しない/論理削除済み、またはチャンネルが存在しない |
| 409 | TEAM_003 / ORG_007 | 宛先がすでに当該スコープのメンバー（招待不可） |
| 409 | ROLE_003 | 同一 DM × 同一スコープ宛ての **PENDING 招待が既存**（重複発行防止・③）|
| 422 | ROLE_009（発行時 422 として流用）| **`roleId` が特権ロール（ADMIN/DEPUTY_ADMIN）**（C-1）|
| 422 | TEAM_002 / ORG_003 | 招待先がアーカイブ済み |
| 422 | — | `channelId` が `DM` でない / DM が2名でない / 相手が退会済み / `expiresInDays` が許容値外 |

> **③ 重複 PENDING の 1 件制限**: 同一 DM × 同一スコープ宛ての PENDING（`target_user_id` + scope + `revoked_at IS NULL` + 未期限）が既存の場合は 409（`ownership_transfer_offers` の1件制約と設計を揃える）。アプリ層チェックを一次とする。

### `POST /api/v1/invite/{token}/join`（既存流用・宛先照合＋特権拒否を追加）

承諾（PENDING→参加）。**既存の共有リンク参加 API（`InviteService.joinByInvite`）を流用** し、以下の差分を条件付きで追加する。

**承諾時の追加判定（既存フローへの差分）**:
1. トークン取得（`findByTokenForUpdate`。`isValid()` が false なら既存どおり `ROLE_003`(回数上限) / `ROLE_002`(無効/期限切れ・失効)）。
2. **宛先照合（IDOR 防止）**: `target_user_id` が非 NULL の場合、`target_user_id == 実行ユーザー ID` を照合。不一致なら **403 ROLE_009**。NULL（共有リンク型）はスキップ（既存挙動維持）。
3. **特権ロール付与の保険ガード（C-1）**: `token.roleId` が ADMIN/DEPUTY_ADMIN ロールなら **拒否**（発行入口で弾いているが、既存 `joinByInvite` は `token.roleId` を無検証で `user_roles` に INSERT し 2FA チェックも無いため、**join 側にも特権ロール付与拒否の保険**を置く）。
4. 既存の重複参加チェック（すでにメンバーなら **409 TEAM_003 / ORG_007**・冪等）。
5. メンバー化（`user_roles` + `memberships` へ INSERT）＋`used_count` インクリメント（既存ロジック）。
6. **カード状態更新（JOINED）** を連結（後述 §5「承諾後のカード更新経路」）。

**レスポンス（200 OK・camelCase）**: カードのローカル差し替えに必要な情報を含めて返す（§5 A-2 で確定）:
```json
{
  "data": {
    "joinedScope": { "scopeType": "TEAM", "scopeId": 12, "name": "北陽SC ジュニア" },
    "cardMessageId": 990012
  }
}
```

### `POST /api/v1/invite/{token}/decline`（辞退・新設）

宛先本人のみ。`revoked_at = NOW()` を立て（カードは REVOKED 表示に導出）、audit_logs に理由 `DECLINED` を記録する。宛先不一致は 403 ROLE_009。既に失効/期限切れなら 409/410。ロール変化なし。

### `GET /api/v1/me/invitable-scopes`

招待モーダルの選択肢。自分が ADMIN/DEPUTY_ADMIN（`INVITE_MEMBERS` 権限）として招待発行できるスコープの一覧。

**レスポンス（200 OK）**
```json
{
  "data": {
    "teams": [{ "scopeId": 12, "name": "北陽SC ジュニア", "role": "ADMIN" }],
    "organizations": []
  }
}
```
- 管理スコープが **0 件でもエラーにせず空配列を返す**（200）。FE は空なら「招待できるチーム/組織がありません」を表示。
- **認可の真実源は BE**（B-6）: 発行可否は BE が `INVITE_MEMBERS` 権限解決で判定して返す。FE はこのレスポンスを表示に使うだけで、独自の権限判定はしない。

## 5. ビジネスロジック

### 招待発行フロー（越境トランザクション方針 = 原則5）

招待発行は **role ドメイン（トークン発行）を主トランザクション** とし、chat ドメイン（カード投稿）は主 tx の外で **明示的な Service 呼び出し** として連結する。単一の `@Transactional` で role と chat の Repository を同時にまたがない。

```
1. POST /chat/channels/{channelId}/membership-invite を受付
2. 【入力検証】channelId が DM か・2名か・相手が未退会か（B-9）→ 否なら 422
   roleId が特権ロールでないか（C-1）→ 特権なら 422 / expiresInDays が {1,7,30,90} か → 否なら 422
3. 【認可】実行ユーザーが scope の ADMIN/DEPUTY_ADMIN(INVITE_MEMBERS) か検証 → 否なら 403（TEAM_048/ORG_048）
4. 【当事者】実行ユーザーが channelId の当事者、宛先=相手 か検証 → 否なら 403
5. 【既メンバー】宛先が既に scope メンバーか → Yes なら 409（TEAM_003/ORG_007）
6. 【重複 PENDING】同一 DM×同一スコープ宛ての有効 PENDING が既存か → Yes なら 409（ROLE_003・③）
7. 【role ドメイン @Transactional】invite_tokens に INSERT
   （target_user_id=相手, team_id/organization_id=scope, role_id=非特権ロール, max_uses=1,
    expires_at = resolveExpiresAt("{expiresInDays}d")）→ tokenId 確定・コミット
8. 【chat ドメイン Service 呼び出し（別 tx）】DM チャンネルへ INVITE_CARD メッセージを投稿
   （sender_id=発行者, message_type='INVITE_CARD', invite_token_id=tokenId, is_system=FALSE,
    body='[招待カード]', last_message_preview=ロケール実文字列）
9. 【補償】8 が失敗した場合、7 のトークンを revoked_at=NOW()（理由 COMPENSATED）で失効（宙に浮く PENDING を残さない）
10. 【到達通知】F04.9/F04.3 基盤で宛先へ「招待が届きました」通常通知
11. 201 Created を返す
```

### 承諾後のカード更新経路（A-2・確定）

**確定方針: WebSocket ではなく join レスポンス起点の FE ローカル差し替えを一次とする。**

- 既存 `useChatWebSocket.ts` は **`MESSAGE_CREATED` のみ** を処理し `MESSAGE_UPDATED` 系ハンドラを持たない（実コード確認済み）。カード状態遷移のためだけに WS 更新経路を新設するのは影響が大きい。
- よって承諾（`POST /invite/{token}/join`）の **レスポンスに `joinedScope` と `cardMessageId` を載せ**、FE は当該 `cardMessageId` のカードを **ローカルで JOINED 状態へ差し替える**（追加の再フェッチ不要）。
- **代替（採る場合の必須条件）**: リアルタイムで双方（発行者側の DM ペイン）にも即時反映したい場合は、`useChatWebSocket.ts` に **`MESSAGE_UPDATED` ハンドラ追加が必須**（EventBus は任意 type を emit するが、購読側コンポーネントが `MESSAGE_UPDATED` を解釈してストア差し替えする実装が無い）。本設計の既定は「発行者側は次回フェッチ時に最新状態へ解決（`inviteData` は毎回 `invite_tokens` から導出）」とし、リアルタイム WS 反映は将来拡張とする（§12）。

### 承諾（join）→ カード JOINED 更新の越境（B-5・原則5）

- 承諾は **role ドメイン @Transactional**（`joinByInvite`：メンバー化＋`used_count`）を主とする。**実装主体は role ドメイン Service**。
- カードの JOINED 表示は **状態を持たず `invite_tokens` + membership から都度導出**するため、chat 側への物理更新（`chat_messages` の書き換え）は不要。よって発行フローのような chat 書き込み越境は承諾側には発生せず、**tx は role ドメインに閉じる**（発行フローとは非対称でよい）。
- FE 差し替えは join レスポンス（`cardMessageId`）で行う。失敗しても次回のメッセージ取得時に `inviteData.status` が JOINED に解決されるため、**表示の最終整合は保たれる（補償不要）**。

### 招待カードの状態遷移（表示状態）

招待カードは `invite_tokens` の状態から **導出**（カード自体は状態を持たず、参照先トークン＋メンバーシップから解決）する。

| 表示状態 | 導出条件 | カード上の主 UI |
|---|---|---|
| **PENDING** | `isValid()`（`revoked_at IS NULL` かつ `expires_at` 未到来 かつ `used_count < max_uses`）かつ宛先が未参加 | 「参加する」/「辞退」ボタン（宛先本人にのみ活性）|
| **JOINED** | 宛先が当該スコープのメンバー（承諾済み）| 「参加済み」バッジ |
| **EXPIRED** | `expires_at < NOW()` かつ未参加（後述の境界に注意）| 「期限切れ」表示 |
| **REVOKED** | `revoked_at IS NOT NULL` かつ未参加（辞退 DECLINED / 発行者取消 CANCELLED / 補償 COMPENSATED）| 辞退なら「辞退済み」、取消なら「取消済み」表示（audit の理由で区別）|

- カードは宛先本人と発行者の双方に見える（DM の 2 者）。「参加する」「辞退」ボタンは **宛先本人にのみ活性**。発行者側は「相手の承諾待ち」表示。
- 宛先本人か否かは、カード契約の **`inviteData.isTarget`（boolean）** で判定する。これが無いと「宛先のみ活性／発行者は待ち表示」が実装不能（A-4）。
- 第三者はそもそも DM チャンネル非メンバーなのでカードを取得できない（チャンネル ACL が一次防壁、宛先照合が二次防壁）。

> **期限境界（M-1）**: 既存 `InviteTokenEntity.isValid()` は `expiresAt.isBefore(now)` で判定するため **`expires_at == NOW()` は「有効」**。よって EXPIRED は **`expires_at < NOW()`** で成立し、**ちょうど（==）は PENDING（有効）** とする。受け入れ条件・試練も既存 `isValid()` に合わせる（独自の `<=` 判定を新設しない）。

### `inviteData`（カード描画契約・A-4 / 完全定義）

`GET /chat/channels/{id}/messages` 等のメッセージ取得レスポンスで、`messageType = 'INVITE_CARD'` の行にのみ付与する。BE ネスト `MessageResponse` に **`inviteData` ブロックを追加**、FE フラット `ChatMessageResponse` に **`messageType` と `inviteData` を追加**する（下記「FE 改修対象」）。

```json
{
  "messageType": "INVITE_CARD",
  "inviteData": {
    "tokenId": 3001,
    "token": "b2f7c0e2-...-4f50",
    "scopeType": "TEAM",
    "scopeId": 12,
    "scopeName": "北陽SC ジュニア",
    "status": "PENDING",
    "isTarget": true,
    "expiresAt": "2026-07-25T09:00:00Z"
  }
}
```
| フィールド | 型 | NULL | 説明 |
|---|---|---|---|
| `messageType` | `'TEXT' \| 'INVITE_CARD'` | 不可 | メッセージ種別（全メッセージに付与。既定 `'TEXT'`）|
| `inviteData` | object \| null | 可（`TEXT` 時は null）| 招待カードのペイロード |
| `inviteData.tokenId` | number | 不可 | 招待トークン ID |
| `inviteData.token` | string | 不可 | 承諾/辞退 API に渡す UUID |
| `inviteData.scopeType` | `'TEAM' \| 'ORGANIZATION'` | 不可 | 招待先種別 |
| `inviteData.scopeId` | number | 不可 | 招待先 ID |
| `inviteData.scopeName` | string | 不可 | 招待先の表示名 |
| `inviteData.status` | `'PENDING' \| 'JOINED' \| 'EXPIRED' \| 'REVOKED'` | 不可 | 導出済みの表示状態（BE が算出して返す）|
| `inviteData.isTarget` | boolean | 不可 | **呼出ユーザーが宛先本人か**（true=参加/辞退ボタン活性、false=承諾待ち表示）|
| `inviteData.expiresAt` | string(ISO8601) | 不可 | 有効期限 |

**FE 改修対象（D-13・A-4 一体）**:
- `frontend/app/types/chat.ts` の `ChatMessageResponse` に **`messageType`（`'TEXT' \| 'INVITE_CARD'`）と `inviteData`（上記型 or null）を新設**（現状 `messageType` フィールドが存在しない）。
- `frontend/app/composables/chat/chatMessageMapper.ts` の `BeMessageResponse` に BE ネスト `inviteData` を追加し、`mapBeMessage` で `messageType`/`inviteData` をフラット展開する（全取得経路の唯一の通過点）。

### 状態機械（オファー）

```
        発行(POST membership-invite)
              │
              ▼
          [PENDING]
          /   │   \    \
   accept  decline  expire  cancel
      │       │        │       │
      ▼       ▼        ▼       ▼
  [ACCEPTED][DECLINED][EXPIRED][CANCELLED]
  =メンバー化  =revoked_at    =期限     =revoked_at
             (理由DECLINED)         (理由CANCELLED)
```
- **DECLINED は永続化する（①）**: `POST /invite/{token}/decline` で `revoked_at` を立て、カードは REVOKED（辞退済み）表示。ボタン非表示だけの扱いは不採用（再取得で PENDING 復活・二重 accept を招くため）。

## 7. Flyway マイグレーション

本機能は **chat ドメインと role ドメインをまたぐため 2 本に分割**する（④の3本分割方針のうち F04.12 が2本・F01.2 のオーナー委譲が1本）。

| 版 | 対象 | 内容 |
|---|---|---|
| `V{major}.{yyyyMMddHHmmss}`（chat）| `chat_messages` | `message_type VARCHAR(20) NOT NULL DEFAULT 'TEXT'` 追加、`invite_token_id BIGINT UNSIGNED NULL` 追加、`idx_chat_messages_invite_token` 追加 |
| `V{major}.{yyyyMMddHHmmss}`（role）| `invite_tokens` | `target_user_id BIGINT UNSIGNED NULL` 追加、`idx_it_target_user` 追加 |

- **1本集約は不採用**（ドメイン境界を Flyway ファイルでも維持）。
- **採番規約**: `major` は「origin/main 全体の最大 major + 1」で**マージ時に確定**（見込み値は書かない）。`minor` は **タイムスタンプ必須**（`date -u '+%Y%m%d%H%M%S'`。連番 `.001` は番人テスト `FlywayTimestampNamingGuardTest` が拒否）。
- **既存データ番人テストの要否**: 両変更とも NULL 許容カラム追加 or DEFAULT 付き NOT NULL カラム追加のみで既存行に矛盾を生じない（CHECK 後付けや既存値書き換えなし）。よって「DROP→UPDATE 順序」型番人テストは不要。ただし `message_type` DEFAULT が全既存行に `'TEXT'` を埋めることをマイグレーションテストで確認する。
- **INVITE_MEMBERS の組織スコープ（B-7）**: 既存 `V2.015__seed_permissions.sql` は `INVITE_MEMBERS` を **`scope='TEAM'` のみ**でシードしている。組織スコープの招待発行で権限判定に用いる場合、**組織スコープの `INVITE_MEMBERS` 権限（または組織 ADMIN による包摂）を確認**し、無ければ **本機能の Flyway で組織スコープの `INVITE_MEMBERS` を seed 追加**する。※ADMIN はロール直下で招待可・DEPUTY_ADMIN の組織招待に本権限が必要なため、実装時に権限解決の実挙動（`resolveEffectivePermissions`）で組織 DEPUTY_ADMIN の判定可否を検証してから seed 要否を確定する（判断保留 §12）。

## 8. 再利用資産の配線

- **招待可能スコープの解決（`GET /me/invitable-scopes`）**: **BE を認可の真実源**とする（B-6）。BE が `memberships` + `user_roles` 統合（`feedback_role_resolution_memberships_gap`）と `INVITE_MEMBERS` 権限解決で「発行可能スコープ」を算出して返す。**FE に `adminOrDeputyTeams` getter を新設する設計は撤回**（FE の `MyTeamResponse` は `role` のみ保持し permission 非保持のため DEPUTY_ADMIN の `INVITE_MEMBERS` 判定不能）。FE は本 API の結果を表示に使うのみ（粗いフィルタは可だが認可判断はしない）。
- **招待トークン基盤（F01.2 `invite_tokens` / `InviteService`）**: 発行・失効・`used_count` のアトミック消費（`findByTokenForUpdate` + `isValid()`）・論理削除時の一括失効は既存流用。`target_user_id` 照合・特権ロール拒否・`expiresInDays→"{n}d"` 変換のみ追加。
- **参加時の重複防止**: `joinByInvite` 既存の「すでにメンバーなら弾く」（TEAM_003 / ORG_007 相当）を流用（冪等・二重承諾防止）。
- **到達通知（F04.9 / F04.3）**: 招待到達を宛先へ通常通知（confirm まで求める F04.9 は過剰なため通常のアプリ内通知＋任意プッシュ）。
- **チャットカード描画（F04.2）**: `source_data` 拡張と同様に、メッセージ取得レスポンスへ `messageType`/`inviteData` を付与（§5 スキーマ）。
- **カードの可視性（S4）**: `INVITE_CARD` の可視性は **既存のチャットメッセージ可視性判定（チャンネルメンバーシップ）と同一経路**で解決し、独自の可視性述語を新設しない（`feedback_visibility_bypass_f00_audit` に準拠）。

## 9. 受け入れ条件

### 正常系
- [ ] ADMIN/DEPUTY_ADMIN が招待ボタンを押すと、自分が管理するスコープのみが選択肢に出る（`GET /me/invitable-scopes`・**BE が真実源**）。**管理スコープ 0 件でもエラーにせず空を返す**。
- [ ] 招待発行で「宛先＝DM 相手を指定したトークン（`target_user_id` 非 NULL）」が生成され、当該 DM に招待カード（`messageType='INVITE_CARD'`, `invite_token_id` セット, `inviteData` 付き）が投稿される。
- [ ] 宛先本人が「参加する」を押すとメンバー化され、join レスポンスの `cardMessageId` でカードが「参加済み（JOINED）」表示に差し替わる。
- [ ] 招待発行者側では `inviteData.isTarget=false` により「参加する」ボタンが非活性で「承諾待ち」表示になる。

### 異常系（認可 / IDOR = 核心）
- [ ] **第三者が他人宛て招待トークンを `join`/`decline` で叩くと 403 ROLE_009**（宛先照合）。
- [ ] ADMIN/DEPUTY_ADMIN でないユーザーが発行 API を直叩きすると 403（TEAM_048/ORG_048）。
- [ ] DM の当事者でないユーザーの発行は 403。
- [ ] **`roleId=ADMIN`（または DEPUTY_ADMIN）指定の発行が 422 で拒否される**（C-1・権限昇格の抜け穴封じ）。加えて、万一そのようなトークンが存在しても `join` 側の保険ガードで特権ロール付与が拒否される。

### 境界
- [ ] **期限ちょうど**（`expires_at == NOW()`）は **有効（PENDING）**、`expires_at < NOW()` で EXPIRED（既存 `isValid()` 準拠・M-1）。
- [ ] 辞退（DECLINED）・取消（CANCELLED）済みトークンの承諾は弾かれ、カードが「辞退済み/取消済み（REVOKED）」表示になる。**辞退後に再取得しても PENDING に戻らず二重 accept できない**（①）。
- [ ] **既メンバー境界**: 宛先が既メンバーなら発行は 409（TEAM_003/ORG_007）。発行後に別経路で参加後の二重承諾も冪等に弾く。
- [ ] **重複 PENDING**: 同一 DM×同一スコープ宛ての PENDING が既存なら発行は 409（③）。
- [ ] `GROUP_DM`・非 DM チャンネルからの発行、DM が2名でない、相手退会済みは 422（B-9）。

### 途中失敗（Saga 補償）
- [ ] トークン発行成功後にカード投稿が失敗した場合、**トークンが失効（理由 COMPENSATED）され、宙に浮いた PENDING が残らない**。
- [ ] 承諾処理の途中失敗でメンバー化とトークン消費が **部分適用されない**（`join` は role ドメイン単一 tx）。

### 攻め口5類型の消し込み
| 類型 | 消し込み |
|---|---|
| 空/0件/null | 管理スコープ 0 件で 200 空配列。共有リンク型（`target_user_id` NULL）は宛先照合スキップで従来どおり動く |
| 境界 | 期限ちょうど==有効（M-1）・既メンバー・重複 PENDING・`max_uses=1` 消費境界 |
| 途中失敗 | 発行2段（トークン＋カード）の Saga 補償で中途半端を残さない |
| **認可（IDOR）** | **宛先照合（ROLE_009）＋スコープ権限ガード（TEAM_048/ORG_048）＋特権ロール拒否（C-1）＋チャンネル ACL の四重防壁**。本機能の核心 |
| 性能 | `GET /me/invitable-scopes` は N+1 回避の一括クエリ。カード解決は `idx_it_target_user` / `idx_chat_messages_invite_token` を使用 |

### 横断要件
- [ ] UI 文字列は i18n 6 言語（ja/en/zh/ko/es/de）にキー追加（直書き禁止）。
- [ ] 新規モーダル/カードに `/統一`・`/手助け` を適用。

| `chat.invite.card.revoked` | 取消済み | REVOKED（理由 CANCELLED）|

## 11. 非機能

- **シャーディング整合性**: 新規テーブルを追加せずカラム追加のみのため UUIDv7（原則6）・テナント Repository（原則7）に新たな違反を持ち込まない。承諾型トークンは短命（`max_uses=1`・7日）で肥大化しにくい。
- **レートリミット**: 発行 API は既存の招待発行レートリミット（`POST /teams|organizations/{slug}/invite-tokens` の 10 req/hour per user）に準じ、DM 悪用の招待スパムを防止。
- **プライバシー**: 招待カードは DM の 2 者のみ可視（チャンネル ACL）。カードに宛先 user ID・表示名以外の個人情報を載せない。
- **宙に浮く PENDING の掃除（S3）**: 発行2段のプロセスクラッシュ等で補償が走らず PENDING トークンが残った場合に備え、`expires_at` 経過分は自然失効するが、**発行元カードが存在しない孤児トークンを検出して失効させる掃除バッチ**（低頻度・日次）を運用に置く。
- **番人テスト（L-2）**: `ROLE_009` 採番衝突を機械検知するため、`RoleErrorCode` の連番/重複を検査する番人テスト（既存があれば拡張・無ければ新設）への追加を検討。

## 12. 判断保留（実装時に確定する軽微論点）

- **組織スコープ `INVITE_MEMBERS` の seed 要否（B-7）**: 組織 DEPUTY_ADMIN の招待判定が既存権限解決で満たせるか実挙動を確認し、不足なら Flyway で組織スコープ seed を追加する（§7）。
- **特権ロール拒否の専用エラーコード**: 本設計は 422 として ROLE_009 を流用。実装時に専用コード（ROLE_010 等）の起票も可（§6）。
- **リアルタイム WS 反映**: 発行者側 DM への即時 JOINED 反映は将来拡張（`useChatWebSocket.ts` への `MESSAGE_UPDATED` 追加が前提・§5 A-2）。
