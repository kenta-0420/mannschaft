## 1. 目的・確定要件・設計の境界

個人は一つの共通会員QRを提示し、店舗等の各チームのスタッフが読み取って、そのチームだけに有効なポイントを付与する。チームAの20ポイントとチームBの20ポイントは独立し、横断合算しない。同じ個人が受付に置かれたチームQRを自分で読んだ場合も、同じチーム・本人の残高に加算する。

確定している要件は次のとおり。

- 個人サイドバーに独立した「会員QR」を置く。直接開くと共通QRを表示し、チーム選択を求めない。
- ウォレットにも同じQRへの入口、チーム別残高、加算・交換履歴、複数特典への進捗を置く。
- チームは付与対象を「全認証済みのactive個人（非所属を含む）」「サポーター以上」「メンバー以上」から選ぶ。
- チームごとに「来店1回で1ポイント」等の加算基準と、「20ポイントで1回無料」等の特典を複数設定する。
- スタッフ読取と本人による受付QR読取の双方を設計対象に含める。本人読取で他人のuserIdを指定できない。

以下は本書の**設計提案**であり、実装開始前の設計裁可に含める。特典は閾値到達だけで自動消費せず、スタッフが内容を確認して交換を確定する。20ポイント特典なら20を消費し、残高25から交換後は5を保持する。複数特典は同じ残高を共有し、同時に複数の権利を確保した扱いにはしない。脱退・対象条件の変更後も既存残高・履歴の本人閲覧と既得ポイントの特典交換は認め、追加付与だけを現在の条件で止める。無断失効は導入しない。

金銭購入・チャージ・送金・換金・返金・外部ポイント連携・複数ポイント通貨・汎用ルールDSLは対象外。F18の`SELF_ISSUED_BALANCE`凍結を解除せず、既存プリペイド表・Service・機能フラグを流用しない。法的分類を本書で断定するものではない。

### 1.1 裁可済み：固定受付QRの2モード

2026-10-16の「よきにはからえ」により、チームごとに固定掲示QRの自動加算／スタッフ承認を選ぶ方式を採用する。`selfAwardMode=STAFF_APPROVAL`を初期値とし、当該TEAM ADMINだけが`AUTO`へ変更できる。AUTO選択時は「固定QRの撮影・遠隔再利用は防げず、同日1回の制限でも来店そのものは証明できない」と設定画面と確認ダイアログへ明示する。短期更新QR・受付専用端末・位置情報認証は今回のスコープ外として確定する。

| モード | 本人の確定POST後 | 残高に反映する時点 |
|---|---|---|
| `AUTO` | 日次枠を確認して即時加算 | 本人POSTのcommit時 |
| `STAFF_APPROVAL` | 最長30分（JST日末まで）のPENDING申請を作成し、本人に照合コードと期限を表示 | 当該TEAM ADMIN／明示委任DEPUTYが現物確認して承認したcommit時 |

双方ともサーバーJST日次1回で、スタッフによる共通会員QR加算も同じ日次枠を使う。申請作成だけでは口座・残高・加算枠を作成/消費しない。承認者が申請者本人ならADMINでも承認不可。モード変更はprogram版を増やし、旧版PENDINGを自動加算しない。申請の期限・日跨ぎ・取消・却下・競合は§5.1/§8で定義する。
## 2. 現状との三点照合・変更要否

F02.1は本人認証・チェックインの仕様、F18は外部カード再描画および組織発行カードの仕様である。要求するチーム別残高・対象条件・来店ルール・特典交換台帳は既存設計の追記だけでは境界が曖昧になるため、本書を新設し、両書には参照のみを追記する。

| 現在の事実（コード根拠） | 本設計の対応 |
|---|---|
| `membership/entity/MemberCardEntity`のscopeはPLATFORM/TEAM/ORGANIZATION。既存主キーはLong | 個人共通QRはPLATFORMカードを利用。旧TEAM/ORGANIZATIONカードは維持 |
| `membership/controller/MemberCardController`は`GET /member-cards/my`と`GET /member-cards/{id}/qr`。PLATFORM専用確保APIは無い | 明示的な本人PLATFORM確保POSTを追加。自動発行が既に保証されるとは扱わない |
| `membership/service/MemberCardService#getQrToken`のDTOは`memberCardId, qrToken, expiresIn, cardNumber, displayName, scopeType, scopeName` | 共通QR画面とウォレットで同じ表示部品・同じAPIを使う |
| `QrTokenService`はHMAC-SHA256・300秒の会員QRを発行 | 署名・時刻・状態検証だけを公開Service契約にし、ポイントから呼ぶ |
| 既存verifyはカード由来scopeの管理権限を確認し、チェックインを更新する | ポイントからverify/checkin更新を呼ばない。操作チームはURLで確定し、そのチームのスタッフ権限を別確認 |
| `CheckinLocationService`の拠点QRは固定署名。既存selfCheckinはscopeカードが必要 | 非所属を許す受付ポイント専用経路を追加し、membership登録やチェックイン成功を前提にしない |
| `team/entity/TeamEntity`にorganizationIdは無く、`team_org_memberships`で組織と多対多 | ポイントの所有境界はteamId。任意の所属組織IDをコピーして所有者にしない |
| `team_feature_settings`という既存表は無い | 本書のprogram設定表を新設し、架空の既存表を前提にしない |
| F18は外部カードの規約同意・個人opt-inで入口を制御 | チームポイント区画・共通会員QRをそのopt-inで遮断しない。外部カード側の同意制御は維持 |

## 3. 画面・導線・状態表示

| 画面 | 導線・表示・操作 |
|---|---|
| 個人 `/my/member-qr` | サイドバー「会員QR」→即PLATFORM QR。残り有効時間、更新、カメラに見せやすい大きさ。チーム一覧を経由しない |
| 既存ウォレット `/wallet` | 共通QRボタンと「チームポイント」区画を上部に表示。外部カード未同意でもこの区画は使用可 |
| 個人 `/my/team-points/{teamId}` | 自分の残高、累計獲得、加算・交換履歴、全active特典と必要ポイント・あと何ポイント。読取許可がある初回残高0は0、履歴0件は空状態。非所属の初回受付はbootstrap応答で確認し、URL直打ちではチーム情報を開示しない |
| チーム `/teams/{slug}/loyalty` | スタッフ用。操作カタログを取得→チーム名を固定表示→QR読取→対象本人の最小表示名、付与ルールと加算数を確認→確定。自由額入力は設けない。交換も特典と消費数を確認して確定 |
| チーム `/teams/{slug}/settings/loyalty` | ADMINが有効化、対象条件、ルール、複数特典を設定。固定受付のSTAFF_APPROVAL/AUTOを選択。初期値は承認、AUTOには遠隔再利用の制約を明示 |
| 受付QR発行・印刷（チーム設定内） | ADMINが「ポイント受付QR」→当該TEAMの拠点選択/作成→QRプレビュー→印刷→受付に掲示。停止は同じ画面から拠点無効化またはprogram停止。モバイルでもプレビュー・共有/印刷に到達できる。掲示には現在の自動／承認モードと、承認の場合は本人画面をスタッフに見せる手順を表示 |
| 本人 `/my/team-point-requests` | サイドバー/ウォレット「受付申請」から口座未作成でも本人申請一覧・詳細へ。申請の状態・照合コード・期限・取消を表示し、再ログイン後も確認可能 |
| スタッフ承認一覧（`/teams/{slug}/loyalty`内） | ADMIN／委任DEPUTYがPENDING／全状態の一覧切替→申請者の表示名と本人画面の照合コードを比較→承認/却下。自分の申請の承認はdisabledかつAPIも403 |
| 受付QRリンク `/my/team-points/receive` | QRを読取→ログインが必要ならログイン→対象チーム・加算内容・日次制限を確認→本人がPOST確定。AUTOなら加算、承認なら申請を作成。GET表示・ログイン復帰だけで加算/申請しない |

既存のTEAM拠点API `GET/POST /teams/{teamId}/checkin-locations`、`PUT /teams/{teamId}/checkin-locations/{locationId}`、`GET /teams/{teamId}/checkin-locations/{locationId}/qr`を、既存の認可と当該TEAM一致確認を維持して発行/一覧/停止に利用する。`LocationQrResponse`の正確なフィールドは`{locationId: Long, name: string, qrToken: string, scopeName: string, printInstructions: string}`。FEは固定署名qrTokenを使い、専用の`/my/team-points/receive#locationToken={URL-encoded token}`を生成してQR化する。既存チェックイン用URLやprintInstructionsをそのまま印刷せず、チーム名・ポイント受付・読取後の確認手順・裁可された再利用制限をi18nで表示する。既存拠点の無効化はチェックイン利用にも影響するため、同じ拠点を共有している旨を停止確認に表示する。program停止ならポイントだけを停止できる。本人がこの専用リンクを使った場合は既存selfCheckinを呼ばず、チェックイン記録・予約autoCompleteの副作用を発火させない。短期QR発行機能は追加しない。
チーム画面のslugは既存team詳細APIでnumericIdへ解決し、そのLong値をloyalty APIのteamIdに渡す。TeamDetail.id（slug）を代入したり独自のslug-ID表を作らない。本人専用QR取得/再生成を他会員へ呼ばない（F02.1の現行管理画面契約と同じ）。

共通QRは有効なactive個人が開いた時にPLATFORMカードを確保して表示する。再表示で別カードを増やさない。SUSPENDED/REVOKEDカードは勝手に再発行・有効化しない。初回作成失敗は再試行可能なエラーを表示する。期限到達・背景復帰時は古いQRを隠して再取得し、通信失敗のQRを有効と見せない。カメラ拒否時は権限の説明と再試行を表示し、職員によるuserId直入力を抜け道にしない。

全画面でloading/error/empty/loadedを区別し、取得失敗を残高0・履歴0件と表示しない。確定中は連打を抑止し、タイムアウト時は「未確定」と表示して同じIdempotency-Keyで再送する。成功後は残高・履歴・進捗を同じ取得関数で再取得する。共通UI部品・useApi/useErrorHandler/useNotificationを利用し、44pxタップ領域、390px幅、スクリーンリーダー、キーボード操作を担保する。モバイルでは折りたたみサイドバーから会員QRへ一操作、ウォレットのチームポイント区画から詳細へ一操作、チームメニューから設定・スタッフ受付へ到達できる。設定の特典編集は縦積み、受付確認ボタンはQRや数値を隠さず画面内に表示する。

## 4. 権限・対象資格・F00の適用

全APIは認証必須。activeな個人アカウントに限定し、無効化・削除・退会中は拒否する。チームの論理削除後は新規加算・交換を拒否し、本人履歴ではteamNameを「利用終了したチーム」に置換できる。プログラム停止は新規加算・新規交換を止めるが、閲覧と履歴を残す。

| 操作 | 認可 |
|---|---|
| 設定・ルール・特典の変更 | 当該TEAMのADMINのみ。組織ADMINというだけでは不可 |
| スタッフの操作カタログ取得・読取確認・付与・交換・申請一覧/詳細・承認/却下 | 当該TEAM ADMIN、または`TEAM_LOYALTY_OPERATE`をpermission_groupsで明示委任された当該TEAM DEPUTY_ADMIN |
| 個人の残高・履歴 | 認証主体のuserIdで必ず検索。URLやbodyのuserIdを受けない。本人の既存口座所有者、または当該TEAMのactive所属者のみ読取可。未関係のteamId直打ちは404。既存口座所有者の現所属は不要 |
| 本人申請一覧・詳細・取消 | 本人口座/所属は不要、認証主体userIdで申請を束縛。申請UUIDを推測しても他人の申請は404。申請があってもチーム情報GETの読取権を追加しない |
| 受付QRの確認・本人付与/申請 | userIdは認証主体固定。署名由来のTEAMとURLのteamIdの一致、拠点active、プログラム有効、ルールの本人読取許可、現在の対象資格をすべて検証 |

`TEAM_LOYALTY_OPERATE`は**新規権限**として同一実装PRのFlywayでpermissions(scope=TEAM)へ登録する。ADMINのデフォルトのみ登録し、DEPUTY_ADMINの恒常付与・is_default=1登録はしない。組織用`POINT_CARD_STAMP_ISSUE`は実在するが本機能へ転用しない。SYSTEM_ADMINも当該TEAMでの明示的なロール・委任無しに営業操作を行えない。

対象資格は加算時にサーバーで判定する。スタッフ本人の資格ではなく、読み取った個人の資格を評価する。

| targetAudience（保存値） | 判定 |
|---|---|
| `ALL_AUTHENTICATED` | active個人。チーム非所属・そのチームのGUESTも対象。所属を自動作成しない |
| `SUPPORTERS_AND_ABOVE` | `AccessControlService.isMember(userId, teamId, "TEAM")`相当のactive所属（SUPPORTERを含む） |
| `MEMBERS_AND_ABOVE` | `AccessControlService.isRegularMemberOrAbove(...)`相当（SUPPORTER/GUESTを除くactive所属） |

`hasRoleOrAbove`単独はSYSTEM_ADMINの全体昇格があるため資格判定に使わない。非所属SYSTEM_ADMINは後二条件に不適格。所属の保留・停止・削除も不適格。対象資格変更は既存残高を消去しない。

未作成口座GETの仮想0応答は当該TEAMのactive所属者（SUPPORTERを含む。GUESTのみは在籍なしで不可。付与資格は別判定）にだけ返す。非所属ALL対象者の初回表示は、有効受付QRを検証する副作用なしbootstrapが返すAccountDetailに限定する。bootstrapは恒久的なGET閲覧権を発行せず、初回加算が成功して口座を所有した後に通常GETへ移る。口座未作成かつ非所属のtransactions GETも404で、teamName/rewards/空配列を漏らさない。既存口座への本人読取はprogram停止・脱退後も維持する。

F00対象外は非公開TEAMの情報を公開してよいという意味ではない。F00はポイントの更新権限を付与する基盤ではない。本人残高・履歴・共通QRは認証主体へ束縛された私有情報のためF00 Resolver対象外。チームスタッフ用情報はLoyaltyAccessPolicy→AccessControlServiceで操作認可し、他人の残高が一般チーム一覧・検索・公開ページ・通知に流れないようにする。外部からteamIdを受ける個人EPには安易に`@SelfScopedEndpoint`を付けず、`@AuthorizedInService`とScopeContractITで境界を固定する。将来一般コンテンツとして露出する場合はF00のTEAM可視性を別途通すが、今回の会員専用情報の公開条件を増やさない。

## 5. ドメイン・サービス契約・更新順序

新規`com.mannschaft.app.loyalty`にController、LoyaltyFacade（TXなし）、LoyaltyAccessPolicy、LoyaltyQueryService、LoyaltyPointsWriter（書込TX）、Repository、DTO/Mapperを置く。Facadeがteam/個人active状態・権限・対象資格とQRを既存ドメインの公開Serviceで検証する。他ドメインRepository/Entityを参照しない。WriterのTX内ではloyalty表だけを変更する。

Writerの書込TXはREAD_COMMITTEDとし、設定版はprogram/rule/reward共有ロック、更新対象はrequest/account排他ロック、日次・receipt・PENDINGの一意性はDB UNIQUEで守る。空候補のgapやRR snapshotに依存せず、既知のunique競合・deadlockだけを失敗TX終了後にreceipt照合から安全に再試行し、未知の整合性例外は競合へ一括変換しない。

membershipへ追加する公開契約は以下。検証だけのメソッドからチェックイン・ポイント・会員所属を更新しない。

- `ensureMyPlatformCard(actorUserId)`：既存active論理行を返すか、未発行時だけ作成。停止・無効化カードを復活させない。scopeIdはNULL。
- `verifyPlatformQr(qrToken)`：形式/UUID/時刻/署名/PLATFORM/カードactive/論理削除無しを確認し、`VerifiedPlatformCard(userId: Long, memberCardId: Long, expiresAtEpoch: long)`を返す。userIdはtokenから直接信用せずDBで解決。300秒TTL、未来issuedAt、expiresAt<issuedAt、TTL改ざんを拒否し、`now > expiresAt`で期限切れ（既存境界維持）。Clockを注入してテスト可能にする。
- `resolveTeamLocationQr(locationToken)`：署名を検証し、activeなTEAM拠点から`VerifiedTeamLocation(locationId: Long, teamId: Long)`を返す。ORGANIZATION拠点は受けない。bootstrapはこの結果からteamを確定し、他の操作ではURLのexpectedTeamIdとの一致を追加検証する。クライアント指定teamIdで署名確認を省略しない。固定署名の再利用限界は§1.1のとおりで、承認時には保存locationIdを再検証する。

スタッフも本人読取も同じ`award` Writerに到達し、経路ごとに残高計算や日次判定を複製しない。Writer入口の検証済みコマンドはサーバー内部型で、HTTPリクエストからactor/recipient/pointsを直接組み立てない。

1. Facadeでactor本人の認証・active状態、スタッフ経路なら現在の当該TEAM操作権限を確認する。権限喪失は403。この段階ではrecipientのQR期限・所属・program/rule/reward状態を再評価しない。
2. `(team_id,actor_user_id,request_operation,request_key)`で成功receipt（確定済みtransaction）を照合する。同一raw requestから計算したcanonical payloadHashが一致すれば、QR期限切れ・対象者脱退・program停止・条件変更後でも元TransactionResponseを200で返す。raw tokenを解析・再検証せず、同じhashで足りる。別内容は409。成功receiptが無い要求だけを新規処理へ進める。
3. 新規処理ではTEAM境界・teamの存在/状態・QR署名/期限/失効・recipient active状態・対象資格をすべて検証する。再送照合との間に並行処理が成功した場合に備え、検証失敗時も同じactor権限の下でreceiptを再照合し、存在しhashが一致すれば元結果を返す。存在しなければ元の検証エラーを返す。
4. WriterのTXでprogram、rule（交換ならreward）を共有ロックで読み、active/有効/expectedVersionを再確認。設定変更は同じ行を排他ロックしversionを増やす。ロック順はprogram→rule/reward→同日PENDING request（存在時、id順）→accountとする。
5. accountを`(team_id,user_id)`で作成または取得し、`PESSIMISTIC_WRITE`。初回同時作成はunique衝突したTXをロールバック後、外側からreceiptを先に照合して再実行する。同じ失敗TXで握りつぶして続行しない。ロック後も成功receiptを再照合する。
6. 加算はruleのサーバー値だけを使用。日次制限なら`(team_id,user_id,rule_id,award_on)`のDB UNIQUEで重複を防ぐ。staff/self・拠点・ルール版に関係なく同じ日次枠。idempotency unique競合も失敗TXを終了してからreceipt照合へ戻る。
7. staff/AUTOで日次加算が先に成功した場合、同じ本人・ルール・awardOnのPENDING申請を同一TXでSUPERSEDED（reason=DAILY_AWARDED）へ終端化し、後から承認しても加算しない。
8. 交換は確認したrewardVersionのrequiredPointsを使用し、残高不足を拒否。成功時だけ負deltaの台帳行と残高を同一TXで保存。
9. transaction/accountの一方でも保存に失敗すれば両方ロールバック。成功後に監査イベントをAFTER_COMMITで記録。通知失敗を理由にポイントを巻き戻さない。

来店日はサーバーClockの瞬間を`Asia/Tokyo`暦日へ明示変換して計算し、クライアント入力を受けない。新loyaltyの瞬間型はJavaの`Instant`とし、DB日時はUTC、API日時は標準ISO8601の`Z`表記とする。DATETIME(0)に合わせて現在時刻の秒未満を切り捨てる。日付awardOnはJSTの`YYYY-MM-DD`。海外表示TZ・端末時計・版更新で来店日を動かさない。

ロール/所属/カード状態の越境読取はFacadeで行い、その判定時点を各操作の資格評価時点とする。認可取消と既に進行中の操作の完全な直列化を装わず、取消後の新規HTTP要求は拒否する。TX内で他ドメインをロックして巻き込まない。スタッフ画面のpreviewは確定権ではなく、新規POST時に認可・token・資格を再評価する。確定済みreceiptの回収だけは上記の先行照合を使う。

### 5.1 固定受付・申請・承認の更新手順

`POST self-awards`は共通の本人確定入口とし、bodyのexpectedProgramVersionに対応する現在のselfAwardModeで分岐する。AUTOは既存award Writer、STAFF_APPROVALは同じloyalty Writerの申請作成処理へ渡す。requestにbodyからuserId/points/modeを受けず、本人・加算数・モードはサーバーで確定する。

- 作成: actor認証→SELF_SUBMITの成功receipt照合（AUTOのtransaction、または申請行のsubmitKey）→新規のみtoken/拠点/team/資格/版/自己付与許可を確認。program/rule共有ロック下でモードを再確認する。同日加算済みは409。並行STAFF/AUTOと申請insertが入れ違ってPENDINGの保存行が一時的に残っても、daily台帳によるeffective SUPERSEDEDと承認時のuniqueが二重加算を防ぐ。PENDINGはpoints・ルール名・拠点名・program/rule版・locationId・awardOn・expiresAt=min(createdAt+30分,次のJST日0時)を保存し、[A-Z2-7]の8文字照合コードを生成する。日次枠を消費せず、accountを作らない。
- 同日PENDINGはチーム・本人・rule・awardOnにつき1件。期限は保存・表示とも`min(createdAt+30分,次のJST日0時)`とし、`now >= expiresAt`で失効する。JST日付不一致を先に判定してDAY_CHANGED、同日で30分到達ならTTL_EXPIREDとする。23:50申請の表示/保存期限は00:00であり00:20とは表示しない。旧PENDINGの期限/版/日次加算をロック下で確認し、EXPIRED/INVALIDATED/SUPERSEDEDへの更新と新規作成を同一TXで行う。有効PENDINGがあれば別キーの再申請は409で既存本人申請への案内を出す。生成式にNOW()を使わない。
- 承認: actor認証・現在のTEAM操作権限→APPROVE receipt照合を先に行い、成功済みなら元取引を返す。新規だけ申請TEAM・自己承認禁止・expectedRequestVersion・照合コード一致を確認し、team/program/拠点active・本人active・現在の対象資格・自己付与許可・STAFF_APPROVALモード・保存program/rule版・保存加算数と現在値の一致を確認する。本人画面と同じ表示名・コード・申請時刻・受付名をスタッフが比較してから確定POSTする。共通個人QRを再提示させず、この画面だけで本人照合から承認まで到達できる。
- 承認TX: program→rule→request→accountの順にロックする。requestを排他ロックしてPENDING/期限/同じJST日/版を再確認し、保存awardOnと同じ共通日次uniqueで加算する。`APPROVED + transaction + account`を同一TXでcommitし、台帳channel=SELF_APPROVED、actor=承認スタッフ、userId=申請者、sourceLocationId=保存拠点とする。daily uniqueはSTAFF/SELF_AUTO/SELF_APPROVED共通。二重承認は元receiptまたは状態競合となり取引は1件。
- 取消/却下: 本人は自分のPENDINGだけ取消可、現在のTEAM操作スタッフはPENDINGだけ却下可。bodyはexpectedRequestVersion、スタッフ承認だけ照合コードを追加必須とする。自由文の却下理由は集めず固定reason=STAFF_REJECTED。取消/却下/承認/失効の競合は同じrequest排他ロックで一方だけ成功させる。全終端は不可逆。
- 設定版・ルール版・modeが変わっていたらINVALIDATED、拠点停止/team停止/資格喪失もINVALIDATEDとしてreasonを返し、承認要求は409を返す。値を自動置換して承認しない。同じ日次加算が先行ならSUPERSEDED、期限/日跨ぎならEXPIREDで409。再申請は本人が現在内容を再確認して新キーで行い、停止中・資格外は新規申請不可。program/ruleの設定変更は既存PENDINGを一括加算せず、旧版の承認を必ず拒否する。
- エラーを伴う終端化はWriterが`RequestActionOutcome(response, errorCode?)`を返して**まずcommit**し、その後TX外Facadeが409へ変換する。TX内throwでINVALIDATED/EXPIRED化を巻き戻さない。純粋な権限/自己承認/照合コード/expectedVersion不一致は状態不変で403/409。保存途中のDB障害は全rollbackし、PENDINGのまま再試行可能。

§5手順7のstaff/AUTO日次加算成功に伴う副作用は、保存状態がPENDINGの申請だけを同一TXでSUPERSEDED/DAILY_AWARDEDへ閉じる固有ルールとし、申請自体へのapprove/cancel/reject/再申請の終端化には以下の優先順を使う。GETの仮投影がEXPIRED等でも未保存PENDINGはこの日次加算でSUPERSEDEDになり得るが、保存済み終端は上書きせず、PENDINGへの復活や二重加算は生じない。

GETはDBを更新しない。保存PENDINGについて、(1) JST日付不一致→EXPIRED/DAY_CHANGED、(2) now>=expiresAt→EXPIRED/TTL_EXPIRED、(3) program/rule版またはmode/有効状態不一致→INVALIDATED/VERSION_CHANGED、(4) team削除/停止→TEAM_INACTIVE、拠点停止/削除/TEAM不一致→LOCATION_INACTIVE、本人停止/退会→USER_INACTIVE、現在資格外→INELIGIBLEの順でINVALIDATED、(5) 同日日次取引あり→SUPERSEDED/DAILY_AWARDED、(6) 残高上限超過→INVALIDATED/POINT_LIMITの順にeffective status/reasonを投影する。この順をPOSTの新規承認/終端化でも使う。終端不可逆は保存済み終端に適用し、終端保存行は変更しない。closedAt=nullの拠点状態・本人資格等によるGET投影は現在snapshotの仮判定で、状態復旧時にPENDINGへ戻り得る。期限・日跨ぎ・既確定日次取引・単調増加する設定版は戻らない事実であり、modeを元に戻しても版不一致の旧申請は復活しない。canApprove/canCancelは投影結果がPENDINGであることを必須とし、現状態を無視して承認/取消可能と表示しない。外部状態は照会時点のsnapshotで、確定POSTでは再検証する。

照会Facadeは候補ページ内で重複排除したteamId/locationId/userId/(teamId,userId)を使い、既存ドメインの公開Serviceへ次の**追加バッチ契約**を各1回だけ呼ぶ: `TeamService.getActiveStates(teamIds)`→teamIdごとのactive/表示名、membershipの`getTeamLocationStates(locationIds)`→locationIdごとのactive/teamId/拠点名、userの`getActiveDisplayStates(userIds)`→userIdごとのactive/最小表示名、`AccessControlService.getTeamMembershipStates(teamUserKeys)`→組ごとのactive所属/regularMemberOrAbove。ALLの資格はactive個人、後二条件はこの所属snapshotで判定する。Mapに無いIDはinactive/資格無しとしてfail-closed。削除/匿名化で必須stringの表示名を得られなければ、既存共通キーの非PIIな訳文「利用終了したチーム」「退会済み利用者」「利用終了した受付」を使う（既存キーが無い語だけloyalty.requests.deletedUser/closedLocationを追加）。元PIIを復元せず、null不整合を500にしない。公開Service自体の障害は5xxでエラー表示しPENDINGへフォールバックしない。API DTOへ他人userIdや全所属情報は返さず、各公開Serviceが自ドメインRepositoryで集合照会する。loyalty側が外部Repository/SQLを直接読む・1件ずつServiceを呼ぶことは禁止。自ドメインのprogram/rule/日次台帳/残高も候補IDの集合で読む。個人一覧/詳細・スタッフ一覧/詳細・申請送信receiptの再表示で同じ投影関数を使う。

保存状態との違いでGETを500にせず、永続終端化は次のPOST時にロック下で行う。期限判定はバッチ実行に依存しない。表示名は上記バッチから現在の最小表示名だけを解決し、申請表へPIIスナップショットを保存しない。

未作成settingsは`id=null,version=null,isEnabled=false,targetAudience=MEMBERS_AND_ABOVE,selfAwardMode=STAFF_APPROVAL,rules=[],rewards=[]`。特典なしはrewards=[]、remainingPointsはmax(requiredPoints-balance,0)。canRedeemはprogram有効・reward active・残高充足をすべて満たすときtrue。口座未作成はlifetimeEarned=0。取引labelはその時点のルール/特典名のスナップショット、AWARDはruleIdのみ、REDEEMはrewardIdのみ。本人履歴にはactorUserId、カード番号、他人userId、QRを含めない。スタッフpreviewにも実名・メール・電話・他チーム残高を追加しない。

SelfAwardResultはAWARDEDならtransactionのみNOT NULL、SUBMITTEDならrequestのみNOT NULL。SUBMITTEDの再送は同じ申請idと現在のeffective statusを返し、承認済み・取消済み・失効済みでも新規申請を作らない。申請のcanApproveは現在のスタッフ権限・本人との不一致・effective PENDING・有効期限内・同日・版一致を満たすときtrue、canCancelは本人かつ有効PENDING時だけtrue。GETで投影した終端状態は既に永続化されていればclosedAtを返し、未永続化ならnullを返す。APPROVEDのみtransactionId NOT NULL、PENDING/APPROVEDはreason=null。本人名は最小表示名だけで実名/メール/電話を含めない。

申請があるだけではprivate TEAMのaccount GETを許可しない。本人申請一覧/詳細は本人IDで束縛された申請スナップショットを返し、再訪時にコード・状態を確認できる。staff申請一覧は検索対象TEAMを必ず限定し、未関係者へ件数・コード・存在を漏らさない。スタッフのstatus=PENDINGでは、program/ruleの現在版・当日・期限をSQLで絞った有限候補を先に取得し、上記の公開Serviceバッチ投影でeffective PENDINGだけを返す。検索契約は`team_id=:team AND status='PENDING' AND program_version=:currentProgramVersion AND rule_version=:currentRuleVersion AND award_on=:today AND expires_at>:now`、cursorがあれば`(expires_at,id)>(:cursorExpiresAt,:cursorId)`を加え、`ORDER BY expires_at ASC,id ASC LIMIT :candidateLimit`。期限の早い順で、候補上限は`candidateLimit=2*limit+1`（最大201）、1 HTTP要求につき候補SQL1回・外部各バッチ1回だけとする。新しい複合索引`idx_tlar_pending_current(team_id,status,program_version,rule_version,award_on,expires_at,id)`を必須にし、旧版10万件が残っていても現版・当日のrangeを直接読む。日次加算・外部状態による除外をSQLだけで完全判定したと主張しない。

候補の先頭から最大2*limit件を調べ、返却dataは最大limit件。次cursorは**実際に調べた最後の候補**を指す（先読み未返却の有効行を飛ばさない）。limit件返せた時点で候補が残る、または上限の先の1候補が存在すればhasNext=true。それ以外はfalse。全候補が外部状態で除外されれば`data=[]/hasNext=true/nextCursor!=null`を返し得る。FEはこの場合「該当申請なし」の最終空状態にせず「この範囲に有効申請なし・続きを確認」ボタンで次ページを明示取得し、全件まで自動ループしない。data=[]かつhasNext=falseで初めて最終空状態を表示する。mode/版更新後の一覧は先頭から更新可能とし、ページングを一貫snapshotとは扱わない。

status=ALLと本人申請一覧は終端を含めid DESCでlimit+1の通常seek paginationとし、除外せず投影した状態を返す。cursorは本人またはTEAM/スタッフactor・filter・並び順へ束縛し、並びが異なるcursorは400。正確な全件COUNTは返さない。

Idempotency-Keyは必須のUUID形式、不正は400。スコープを`(team,actor,operation,key)`とし、operationは`STAFF_AWARD / SELF_SUBMIT / REDEEM / APPROVE / CANCEL / REJECT`。同じoperationで別申請へキーを使い回すと409、別operationは独立。payloadHashは操作種別・正規化したteam/申請パス・bodyの各型付きフィールド（rule/reward/expectedVersion/照合コード）・入力tokenのSHA-256から決定的に計算し、JSONの空白/キー順には依存しない。対象本人を再送hashのためにtokenから解析し直さない。

actor認証/現在の操作権限を先に確認し、**成功receipt照合は新規token/資格/状態/TTL/版検証より先**。AUTOはtransactions、承認申請の送信はrequest.submitKey、承認成功はtransactions、取消/却下成功はrequest.actionKeyをreceiptとする。同内容なら元取引または同じ申請を200、別内容は409。モード変更後の同じSELF_SUBMITキーも両保存先を先に照合する。program共有ロック下で再照合してから分岐するため、mode更新との競合で同じSELF_SUBMITにAUTO台帳と申請が両方できない。終端化を伴う409は状態をcommitし、同じ要求の再送も該当終端の409を返す。actorの権限喪失は元結果回収も403。成功receiptは保持中消さず、再送TTL経過で重複作成可能にしない。raw tokenはメモリ以外に保存せず、台帳/ログへ記録しない。

同一ドメインFKはrequests(team_id,rule_id)→rules(team_id,id)、requests(team_id,transaction_id)→transactions(team_id,id)をRESTRICTで追加し、transactionsにもUNIQUE(team_id,id)を追加する。source_location_id/user_id/terminal_actor_user_idは他ドメインFKを作らない。requestと対応transactionのteam/user/rule/拠点/points/awardOn一致はWriterと実MySQL ITで固定し、transaction_idが別申請へ重複参照されないことはUNIQUEで守る。申請は物理削除しない。申請者の表示名・QR秘密を保存せず、ルール名/拠点名と数値の業務スナップショットだけを持つ。

transactionのCHECKは以下すべてを要求する。

- balance_after>=0、kind IN('AWARD','REDEEM')、channel IN('STAFF','SELF_AUTO','SELF_APPROVED')。
- AWARDはdelta>0/rule_id NOT NULL/reward_id NULL。REDEEMはdelta<0/rule_id NULL/reward_id NOT NULL/award_on NULL/channel='STAFF'/source_location_id NULL。

- rule_or_reward_version/program_version>=0。日次AWARDのaward_onはNOT NULL、都度AWARDはNULL（frequencyとの整合はWriterで検証）。NULLを含むuniqueが都度加算を誤って禁止しない。

同一ドメインの参照はtransactions(team_id,account_id)→accounts(team_id,id)、transactions(team_id,rule_id)→rules(team_id,id)、transactions(team_id,reward_id)→rewards(team_id,id)の複合FK（RESTRICT）とする。これにより別チームの口座・ルール・特典を結び付けられない。program/rule/reward/accountは物理削除せず、台帳は追記専用。台帳・残高・daily unique・idempotencyは同じDBシャード/同じTXに保つ。

account.user_idとtransaction.user_idの一致はWriterで検証し契約ITで固定する（複合FKだけで本人一致を保証したと誤記しない）。残高更新はaccountロック下で行い、overflow・残高不足・lifetime_earnedのLong overflowも事前検証する。名称/説明の空白・件数制限・日付算出はアプリ層で担う。

### 7.1 PLATFORMカードの一意性と既存データ

既存member_cardsの`(user_id,scope_type,scope_id,active_unique_key)`はPLATFORMのscope_id=NULLに対して重複を防げない。明示確保POSTの導入時に、既存表へ次の生成列とuniqueを追加する。

```sql
active_platform_user_id BIGINT UNSIGNED GENERATED ALWAYS AS
  (CASE WHEN scope_type = 'PLATFORM' AND deleted_at IS NULL THEN user_id ELSE NULL END) VIRTUAL
UNIQUE KEY uq_member_cards_active_platform_user_id (active_platform_user_id)
```

ここでactiveは「非論理削除」を意味し、SUSPENDED/REVOKEDも一意枠を占める。カード再作成で停止を回避しない。新規未発行時だけ安全なcard_code/qr_secretと個人内で安定した表示番号を生成し、並行作成はunique衝突後に別TXで既存行を返す。グローバルcount+1連番を使わない。既存member_cardsのLong主キーと旧カードのQR内容は変更しない。

migration前に非論理削除PLATFORMのuser_id別重複を検査し、あれば**適用を停止**する。行や履歴を無断で削除・統合しない。個々の状態・チェックイン参照を調べ、正準カードの選択と参照付替え・監査の別データ是正案を裁可してから再開する。検査結果へQR秘密・PIIを含めない。既存重複が無いDBでは加法的変更だけで移行できる。

## 8. 状態遷移・競合

| 対象 | 遷移・効果 |
|---|---|
| program | 未作成→DISABLED→ENABLED↔DISABLED。停止しても残高・履歴を保存。対象条件更新はversion+1、新規加算のみに適用 |
| rule | ACTIVE↔INACTIVE。更新ごとversion+1。同じidを維持し日次枠は消さない。初回取引/申請後のfrequency変更は禁止 |
| reward | ACTIVE↔INACTIVE。内容・必要数変更はversion+1。preview後の変更は409で再確認を要求し、古い同意で別の数を消費しない |
| account | 未作成→0→加算/交換。下限0、上限INT_MAX。所属喪失では消去・凍結しない |
| transaction | 成功時だけ確定行を1つ追記。AWARD/REDEEMの後更新・削除・取り消しは初期対象外 |
| 受付AUTO | 読取→本人確認画面→本人POST→即時AWARD。日次枠の残高/台帳を原子的に変更 |
| 受付承認 | 読取→本人確認画面→本人POST→PENDING（残高不変）→スタッフ承認→APPROVED+AWARD |
| 申請その他 | PENDING→CANCELLED（本人取消）、REJECTED（スタッフ却下）、EXPIRED（30分/日跨ぎ）、INVALIDATED（版・対象・状態変更）、SUPERSEDED（同日日次加算先行）。終端からの復帰なし |

設定画面のversion不一致はCOMMON_003(409)。操作時expectedVersion不一致はLOYALTY_007(409)。同時付与は加算合計が欠落しない。同時交換はロック下で片方の残高が不足した時点で拒否する。日次unique競合はLOYALTY_005に変換し、他のDB例外を同じエラーへ握りつぶさない。初回取引/申請後のfrequency変更はLOYALTY_009(400)。mode変更は必ずversion+1とし、旧版申請を継承/自動承認しない。承認時の残高INT上限到達はINVALIDATED(reason=POINT_LIMIT)をcommit後409として返す。

## 10. セキュリティ・性能・移行

QR/tokenはHTTP bodyで送信し、ブラウザ永続ストレージ・台帳・アクセスログ・監査ログ・エラー報告・分析イベントへ記録しない。受付URLの固定署名は、そのリンク自体が再利用可能な秘密である限界を表示し、URL queryをログ/Refererへ流さずfragment受け渡し→メモリ保持→history.replaceStateで除去する。ログイン復帰はtokenをURLへ埋め直さず、失われた場合は再読取を求める。GET/リンクpreview/crawlerは加算を発火させない。既存認証/Refresh/CSP/Cookie設定は変更しない。

レート制限は既存Valkey基盤を利用し、previewと書込をactor単位それぞれ60回/分、チーム単位1000回/分とする。超過429、Valkey障害でもDB日次unique/idempotency/accountロックが整合性を守る。QRはTTL中に再利用可能であるため「QR単回消費」にはせず、日次枠または明示スタッフ確認で業務の重複を止める。レート制限を来店証明とみなさない。

1000万ユーザーを先行で全チームへ展開しない。program/rule/rewardは設定時、accountは初回成功加算時にだけ作る。個人チーム一覧はINDEX(user_id,id)でlimit+1、履歴は(team_id,user_id,id DESC)のseek paginationで読み、全件COUNT/全台帳SUM/深いoffsetを避ける。カーソルは認証主体・team・並び順へ束縛し、他主体のカーソルは400。チーム名は1ページをまとめて既存公開Serviceで解決し、1件ずつ越境Serviceを呼ばない。残高とlifetimeEarnedはaccountからO(1)、全active特典は最大20件で算出する。

初期性能受け入れ目標は本番相当MySQL・1000万accounts・1億transactions、同一TEAM200人並列の異なる本人に対し、主要GETと付与/交換のp95<=500ms（HTTP、DB待ち含む、外部カメラ読取除外）。履歴1ページのloyalty SQL<=3、個人一覧はloyalty SQL<=2＋チーム名バッチ1回、EXPLAINで上記複合索引のrange/refを確認する。同一accountへの競合は直列化するが、program/ruleの共有ロックで全TEAM書込を排他直列化しない。UUIDv7/team境界で将来シャードを分け、跨いだ残高の分散TXを要求しない。実測値・データ件数・並列数・実行計画を後続実装の証拠に残す。
