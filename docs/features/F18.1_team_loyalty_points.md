## 1. 目的・確定要件・設計の境界

個人は一つの共通会員QRを提示し、店舗等の各チームのスタッフが読み取って、そのチームだけに有効なポイントを付与する。チームAの20ポイントとチームBの20ポイントは独立し、横断合算しない。同じ個人が受付に置かれたチームQRを自分で読んだ場合も、同じチーム・本人の残高に加算する。

確定している要件は次のとおり。

- 個人サイドバーに独立した「会員QR」を置く。直接開くと共通QRを表示し、チーム選択を求めない。
- ウォレットにも同じQRへの入口、チーム別残高、加算・交換履歴、複数特典への進捗を置く。
- チームは付与対象を「全認証済みのactive個人（非所属を含む）」「サポーター以上」「メンバー以上」から選ぶ。
- チームごとに「来店1回で1ポイント」等の加算基準と、「20ポイントで1回無料」等の特典を複数設定する。
- スタッフ読取と本人による受付QR読取の双方を設計対象に含める。本人読取で他人のuserIdを指定できない。

以下は本書の**設計提案**であり、実装開始前の設計裁可に含める。特典は閾値到達だけで自動消費せず、スタッフが内容を確認して交換を確定する。20ポイント特典なら20を消費し、残高25から交換後は5を保持する。複数特典は同じ残高を共有し、同時に複数の権利を確保した扱いにはしない。脱退・対象条件の変更後も既存残高・履歴の本人閲覧と既得ポイントの特典交換は認め、追加付与だけを現在の条件で止める。無断失効は導入しない。

金銭購入・チャージ・送金・換金・返金・外部ポイント連携・複数ポイント通貨・汎用ルールDSLは対象外。F18の`SELF_ISSUED_BALANCE`凍結を解除せず、既存プリペイド表・Service・機能フラグを流用しない。法的分類を本書で断定するものではない。

### 1.1 裁可待ち：受付QRの運用方式

固定QRは撮影した画像の遠隔再利用を技術的に排除できない。現在の`locationCode.signature`も期限・nonceを持たず、既存チェックインの5分重複判定はポイントの不正防止には足りない。次のどれを採るかはユーザー回答待ちで、未確定のまま実装・🟢化・マージしない。

| 選択肢 | 受付での挙動と限界 |
|---|---|
| チームごとに固定QRの自動加算／スタッフ承認を選択 | 自動は遠隔再利用の限界を受容。承認は本人申請後、スタッフ確認まで残高に反映しない |
| 固定QR・自動加算・日次上限で運用 | 同じチーム・本人・来店ルールで日次1回。遠隔からの日次1回は防げない |
| 受付端末で短期更新QRを表示 | 有効期限内の読取に限定。表示端末が必要で、期限内の中継までは防げない |

以下の受付APIは共通部分と「自動加算を選んだ場合」の契約案である。承認方式が選ばれた場合は申請のTTL、承認者、却下・取消・競合の状態機械およびDDL/API/ACを追記する。短期更新方式なら発行権限、TTL、nonceのDB一意消費、失効・再発行を追記する。これら未選択分の表やAPIを先行実装しない。

## 2. 現状との三点照合・変更要否

F02.1は本人認証・チェックインの仕様、F18は外部カード再描画および組織発行カードの仕様である。要求するチーム別残高・対象条件・来店ルール・特典交換台帳は既存設計の追記だけでは境界が曖昧になるため、本書を新設し、両書には参照のみを追記する。

| 現在の事実（コード根拠） | 本設計の対応 |
|---|---|
| `membership/entity/MemberCardEntity`のscopeはPLATFORM/TEAM/ORGANIZATION。既存主キーはLong | 個人共通QRはPLATFORMカードを利用。旧TEAM/ORGANIZATIONカードは維持 |
| `membership/controller/MemberCardController`は`GET /member-cards/my`と`GET /member-cards/{id}/qr`。PLATFORM専用確保APIは無い | 明示的な本人PLATFORM確保POSTを追加。自動発行が既に保証されるとは扱わない |
| `membership/service/MemberCardService#getQrToken`のDTOは`memberCardId, qrToken, expiresIn, cardNumber, displayName, scopeType, scopeName` | 共通QR画面とウォレットで同じ表示部品・同じAPIを使う |
| `QrTokenService`はHMAC-SHA256・300秒の会員QRを発行 | 署名・時刻・状態検証だけを公開Service契約にし、ポイントから呼ぶ |
| 既存verifyはカード由来scopeの管理権限を確認し、チェックインを更新する | ポイントからverify/checkin更新を呼ばない。操作チームはURLで確定し、そのチームのスタッフ権限を別確認 |
| `CheckinLocationService`の拠点QRは固定署名。既存selfCheckinはscopeカードが必要 | 非所属を許す受付ポイント専用経路を追加し、membership登録やチェックイン成功を前提にしない |
| `team/entity/TeamEntity`にorganizationIdは無く、`team_org_memberships`で組織と多対多 | ポイントの所有境界はteamId。任意の所属組織IDをコピーして所有者にしない |
| `team_feature_settings`という既存表は無い | 本書のprogram設定表を新設し、架空の既存表を前提にしない |
| F18は外部カードの規約同意・個人opt-inで入口を制御 | チームポイント区画・共通会員QRをそのopt-inで遮断しない。外部カード側の同意制御は維持 |

## 3. 画面・導線・状態表示

| 画面 | 導線・表示・操作 |
|---|---|
| 個人 `/my/member-qr` | サイドバー「会員QR」→即PLATFORM QR。残り有効時間、更新、カメラに見せやすい大きさ。チーム一覧を経由しない |
| 既存ウォレット `/wallet` | 共通QRボタンと「チームポイント」区画を上部に表示。外部カード未同意でもこの区画は使用可 |
| 個人 `/my/team-points/{teamId}` | 自分の残高、累計獲得、加算・交換履歴、全active特典と必要ポイント・あと何ポイント。読取許可がある初回残高0は0、履歴0件は空状態。非所属の初回受付はbootstrap応答で確認し、URL直打ちではチーム情報を開示しない |
| チーム `/teams/{slug}/loyalty` | スタッフ用。操作カタログを取得→チーム名を固定表示→QR読取→対象本人の最小表示名、付与ルールと加算数を確認→確定。自由額入力は設けない。交換も特典と消費数を確認して確定 |
| チーム `/teams/{slug}/settings/loyalty` | ADMINが有効化、対象条件、ルール、複数特典を設定。受付QRの方式欄は裁可確定後に定義 |
| 受付QR発行・印刷（チーム設定内） | ADMINが「ポイント受付QR」→当該TEAMの拠点選択/作成→QRプレビュー→印刷→受付に掲示。停止は同じ画面から拠点無効化またはprogram停止。モバイルでもプレビュー・共有/印刷に到達できる。方式確定前は固定QR掲示を確定仕様にしない |
| 受付QRリンク `/my/team-points/receive` | QRを読取→ログインが必要ならログイン→対象チーム・加算内容・日次制限を確認→本人がPOST確定。GET表示・ログイン復帰だけで加算しない |

既存のTEAM拠点API `GET/POST /teams/{teamId}/checkin-locations`、`PUT /teams/{teamId}/checkin-locations/{locationId}`、`GET /teams/{teamId}/checkin-locations/{locationId}/qr`を、既存の認可と当該TEAM一致確認を維持して発行/一覧/停止に利用する。`LocationQrResponse`の正確なフィールドは`{locationId: Long, name: string, qrToken: string, scopeName: string, printInstructions: string}`。固定署名方式を採る場合、FEはqrTokenを使い、専用の`/my/team-points/receive#locationToken={URL-encoded token}`を生成してQR化する。既存チェックイン用URLやprintInstructionsをそのまま印刷せず、チーム名・ポイント受付・読取後の確認手順・裁可された再利用制限をi18nで表示する。既存拠点の無効化はチェックイン利用にも影響するため、同じ拠点を共有している旨を停止確認に表示する。program停止ならポイントだけを停止できる。本人がこの専用リンクを使った場合は既存selfCheckinを呼ばず、チェックイン記録・予約autoCompleteの副作用を発火させない。受付端末の短期QR方式が選ばれた場合は発行画面をその方式へ差し替える。
共通QRは有効なactive個人が開いた時にPLATFORMカードを確保して表示する。再表示で別カードを増やさない。SUSPENDED/REVOKEDカードは勝手に再発行・有効化しない。初回作成失敗は再試行可能なエラーを表示する。期限到達・背景復帰時は古いQRを隠して再取得し、通信失敗のQRを有効と見せない。カメラ拒否時は権限の説明と再試行を表示し、職員によるuserId直入力を抜け道にしない。

全画面でloading/error/empty/loadedを区別し、取得失敗を残高0・履歴0件と表示しない。確定中は連打を抑止し、タイムアウト時は「未確定」と表示して同じIdempotency-Keyで再送する。成功後は残高・履歴・進捗を同じ取得関数で再取得する。共通UI部品・useApi/useErrorHandler/useNotificationを利用し、44pxタップ領域、390px幅、スクリーンリーダー、キーボード操作を担保する。モバイルでは折りたたみサイドバーから会員QRへ一操作、ウォレットのチームポイント区画から詳細へ一操作、チームメニューから設定・スタッフ受付へ到達できる。設定の特典編集は縦積み、受付確認ボタンはQRや数値を隠さず画面内に表示する。

## 4. 権限・対象資格・F00の適用

全APIは認証必須。activeな個人アカウントに限定し、無効化・削除・退会中は拒否する。チームの論理削除後は新規加算・交換を拒否し、本人履歴ではteamNameを「利用終了したチーム」に置換できる。プログラム停止は新規加算・新規交換を止めるが、閲覧と履歴を残す。

| 操作 | 認可 |
|---|---|
| 設定・ルール・特典の変更 | 当該TEAMのADMINのみ。組織ADMINというだけでは不可 |
| スタッフの操作カタログ取得・読取確認・付与・交換 | 当該TEAM ADMIN、または`TEAM_LOYALTY_OPERATE`をpermission_groupsで明示委任された当該TEAM DEPUTY_ADMIN |
| 個人の残高・履歴 | 認証主体のuserIdで必ず検索。URLやbodyのuserIdを受けない。本人の既存口座所有者、または当該TEAMのactive所属者のみ読取可。未関係のteamId直打ちは404。既存口座所有者の現所属は不要 |
| 受付QRの確認・本人付与 | userIdは認証主体固定。署名由来のTEAMとURLのteamIdの一致、拠点active、プログラム有効、ルールの本人読取許可、現在の対象資格をすべて検証 |

`TEAM_LOYALTY_OPERATE`は**新規権限**として同一実装PRのFlywayでpermissions(scope=TEAM)へ登録する。ADMINのデフォルトのみ登録し、DEPUTY_ADMINの恒常付与・is_default=1登録はしない。組織用`POINT_CARD_STAMP_ISSUE`は実在するが本機能へ転用しない。SYSTEM_ADMINも当該TEAMでの明示的なロール・委任無しに営業操作を行えない。

対象資格は加算時にサーバーで判定する。スタッフ本人の資格ではなく、読み取った個人の資格を評価する。

| targetAudience（保存値） | 判定 |
|---|---|
| `ALL_AUTHENTICATED` | active個人。チーム非所属・そのチームのGUESTも対象。所属を自動作成しない |
| `SUPPORTERS_AND_ABOVE` | `AccessControlService.isMember(userId, teamId, "TEAM")`相当のactive所属（SUPPORTERを含む） |
| `MEMBERS_AND_ABOVE` | `AccessControlService.isRegularMemberOrAbove(...)`相当（SUPPORTER/GUESTを除くactive所属） |

`hasRoleOrAbove`単独はSYSTEM_ADMINの全体昇格があるため資格判定に使わない。非所属SYSTEM_ADMINは後二条件に不適格。所属の保留・停止・削除も不適格。対象資格変更は既存残高を消去しない。

未作成口座GETの仮想0応答は当該TEAMのactive所属者（SUPPORTERを含む。GUESTのみは在籍なしで不可。付与資格は別判定）にだけ返す。非所属ALL対象者の初回表示は、有効受付QRを検証する副作用なしbootstrapが返すAccountDetailに限定する。bootstrapは恒久的なGET閲覧権を発行せず、初回加算が成功して口座を所有した後に通常GETへ移る。口座未作成かつ非所属のtransactions GETも404で、teamName/rewards/空配列を漏らさない。既存口座への本人読取はprogram停止・脱退後も維持する。

F00対象外は非公開TEAMの情報を公開してよいという意味ではない。F00はポイントの更新権限を付与する基盤ではない。本人残高・履歴・共通QRは認証主体へ束縛された私有情報のためF00 Resolver対象外。チームスタッフ用情報はLoyaltyAccessPolicy→AccessControlServiceで操作認可し、他人の残高が一般チーム一覧・検索・公開ページ・通知に流れないようにする。外部からteamIdを受ける個人EPには安易に`@SelfScopedEndpoint`を付けず、`@AuthorizedInService`とScopeContractITで境界を固定する。将来一般コンテンツとして露出する場合はF00のTEAM可視性を別途通すが、今回の会員専用情報の公開条件を増やさない。

## 5. ドメイン・サービス契約・更新順序

新規`com.mannschaft.app.loyalty`にController、LoyaltyFacade（TXなし）、LoyaltyAccessPolicy、LoyaltyQueryService、LoyaltyPointsWriter（書込TX）、Repository、DTO/Mapperを置く。Facadeがteam/個人active状態・権限・対象資格とQRを既存ドメインの公開Serviceで検証する。他ドメインRepository/Entityを参照しない。WriterのTX内ではloyalty表だけを変更する。

membershipへ追加する公開契約は以下。検証だけのメソッドからチェックイン・ポイント・会員所属を更新しない。

- `ensureMyPlatformCard(actorUserId)`：既存active論理行を返すか、未発行時だけ作成。停止・無効化カードを復活させない。scopeIdはNULL。
- `verifyPlatformQr(qrToken)`：形式/UUID/時刻/署名/PLATFORM/カードactive/論理削除無しを確認し、`VerifiedPlatformCard(userId: Long, memberCardId: Long, expiresAtEpoch: long)`を返す。userIdはtokenから直接信用せずDBで解決。300秒TTL、未来issuedAt、expiresAt<issuedAt、TTL改ざんを拒否し、`now > expiresAt`で期限切れ（既存境界維持）。Clockを注入してテスト可能にする。
- `resolveTeamLocationQr(locationToken)`：署名を検証し、activeなTEAM拠点から`VerifiedTeamLocation(locationId: Long, teamId: Long)`を返す。ORGANIZATION拠点は受けない。bootstrapはこの結果からteamを確定し、他の操作ではURLのexpectedTeamIdとの一致を追加検証する。クライアント指定teamIdで署名確認を省略しない。受付方式に応じた追加検証は§1.1確定後。

スタッフも本人読取も同じ`award` Writerに到達し、経路ごとに残高計算や日次判定を複製しない。Writer入口の検証済みコマンドはサーバー内部型で、HTTPリクエストからactor/recipient/pointsを直接組み立てない。

1. Facadeでactor本人の認証・active状態、スタッフ経路なら現在の当該TEAM操作権限を確認する。権限喪失は403。この段階ではrecipientのQR期限・所属・program/rule/reward状態を再評価しない。
2. `(team_id,actor_user_id,request_key)`で成功receipt（確定済みtransaction）を照合する。同一raw requestから計算したcanonical payloadHashが一致すれば、QR期限切れ・対象者脱退・program停止・条件変更後でも元TransactionResponseを200で返す。raw tokenを解析・再検証せず、同じhashで足りる。別内容は409。成功receiptが無い要求だけを新規処理へ進める。
3. 新規処理ではTEAM境界・teamの存在/状態・QR署名/期限/失効・recipient active状態・対象資格をすべて検証する。再送照合との間に並行処理が成功した場合に備え、検証失敗時も同じactor権限の下でreceiptを再照合し、存在しhashが一致すれば元結果を返す。存在しなければ元の検証エラーを返す。
4. WriterのTXでprogram、rule（交換ならreward）を共有ロックで読み、active/有効/expectedVersionを再確認。設定変更は同じ行を排他ロックしversionを増やす。ロック順はprogram→rule/reward→accountとする。
5. accountを`(team_id,user_id)`で作成または取得し、`PESSIMISTIC_WRITE`。初回同時作成はunique衝突したTXをロールバック後、外側からreceiptを先に照合して再実行する。同じ失敗TXで握りつぶして続行しない。ロック後も成功receiptを再照合する。
6. 加算はruleのサーバー値だけを使用。日次制限なら`(team_id,user_id,rule_id,award_on)`のDB UNIQUEで重複を防ぐ。staff/self・拠点・ルール版に関係なく同じ日次枠。idempotency unique競合も失敗TXを終了してからreceipt照合へ戻る。
7. 交換は確認したrewardVersionのrequiredPointsを使用し、残高不足を拒否。成功時だけ負deltaの台帳行と残高を同一TXで保存。
8. transaction/accountの一方でも保存に失敗すれば両方ロールバック。成功後に監査イベントをAFTER_COMMITで記録。通知失敗を理由にポイントを巻き戻さない。

来店日はサーバーClockの`Asia/Tokyo`暦日で計算し、クライアント入力を受けない。DB日時はUTC壁時計、JavaはLocalDateTime、API日時は既存serializerのoffset付きISO8601に従う。日付awardOnはJSTの`YYYY-MM-DD`。海外表示TZ・端末時計・版更新で来店日を動かさない。

ロール/所属/カード状態の越境読取はFacadeで行い、その判定時点を各操作の資格評価時点とする。認可取消と既に進行中の操作の完全な直列化を装わず、取消後の新規HTTP要求は拒否する。TX内で他ドメインをロックして巻き込まない。スタッフ画面のpreviewは確定権ではなく、新規POST時に認可・token・資格を再評価する。確定済みreceiptの回収だけは上記の先行照合を使う。

## 6. API契約

以下はすべて`/api/v1`配下、JSONはcamelCase。成功は`ApiResponse<T>={data:T}`、エラーは既存`{error:{code,message,fieldErrors?}}`。`?`表記は省略可、`| null`は明示NULL可、これ以外は必須・NULL不可。未知enumは400。Longは既存APIと同じinteger(int64)、新規UUIDはハイフン付きstring(uuid)、ポイントはinteger(int32)。pointsの上限は2,147,483,647とし、加算前にlongで計算して超過を400で拒否する。本文最大4KB、token最大512文字、名称はtrim後1〜100文字、説明は0〜500文字（空文字はNULLへ正規化）。

| HTTP・パス | Request | Response・認可 |
|---|---|---|
| POST `/member-cards/platform/me` | body無し | 200 `PlatformCardResponse`。本人active。未発行なら作成、既存なら同じid。QRを返さず、既存GET QRへ接続 |

## 7. DDL・不変条件

以下はmigrationの実行コードではなく設計契約。新規5表はすべてloyaltyドメイン、`id BINARY(16)`のUUIDv7、`created_at/updated_at DATETIME NOT NULL`、`ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci`を共通としEntityはUuidV7Entityを継承。teamId/userId/actorUserId/locationIdは既存Longと同じBIGINT UNSIGNED、他ドメインFKを作らない。新規表のorganization_idは持たない。teamをシャードルーティング境界にし、組織APIは新設しないためAbstractTenantAwareRepositoryのorganization絞込対象ではない。将来organization所有機能を追加する際は同基底を適用する別設計が必要。

| 表 | 固有列（記載なしはNOT NULL） | 制約・索引 |
|---|---|---|
| `team_loyalty_programs` | team_id; is_enabled BOOLEAN DEFAULT FALSE; target_audience VARCHAR(30); version BIGINT DEFAULT 0 | PK(id); UNIQUE(team_id); CHECK audience IN上記3値; CHECK(version>=0) |
| `team_loyalty_rules` | team_id; name VARCHAR(100); points INT; frequency VARCHAR(30); is_self_award_enabled BOOLEAN DEFAULT FALSE; is_active BOOLEAN DEFAULT TRUE; version BIGINT DEFAULT 0 | PK(id); UNIQUE(team_id)（来店基準は1つ）; UNIQUE(team_id,id); CHECK points BETWEEN 1 AND 10000; CHECK frequency IN上記2値; CHECK(NOT is_self_award_enabled OR frequency='ONCE_PER_JST_DAY'); CHECK(version>=0) |
| `team_loyalty_rewards` | team_id; name VARCHAR(100); description VARCHAR(500) NULL; required_points INT; is_active BOOLEAN DEFAULT TRUE; version BIGINT DEFAULT 0 | PK(id); UNIQUE(team_id,id); INDEX(team_id,is_active,id); CHECK required_points BETWEEN 1 AND 1000000; CHECK(version>=0) |
| `team_loyalty_accounts` | team_id; user_id; balance INT DEFAULT 0; lifetime_earned BIGINT DEFAULT 0 | PK(id); UNIQUE(team_id,user_id); UNIQUE(team_id,id); INDEX(user_id,id); CHECK balance>=0; CHECK lifetime_earned>=0 |
| `team_loyalty_transactions` | team_id; account_id BINARY(16); user_id; actor_user_id; kind VARCHAR(10); channel VARCHAR(10); delta INT; balance_after INT; rule_id BINARY(16) NULL; reward_id BINARY(16) NULL; source_location_id BIGINT UNSIGNED NULL; award_on DATE NULL; label VARCHAR(100); rule_or_reward_version BIGINT; program_version BIGINT; request_key BINARY(16); payload_hash BINARY(32) | PK(id); UNIQUE(team_id,actor_user_id,request_key); UNIQUE(team_id,user_id,rule_id,award_on); INDEX(team_id,user_id,id DESC); INDEX(team_id,account_id,id DESC) |

transactionのCHECKは以下すべてを要求する。

- balance_after>=0、kind IN('AWARD','REDEEM')、channel IN('STAFF','SELF')。
- AWARDはdelta>0/rule_id NOT NULL/reward_id NULL。REDEEMはdelta<0/rule_id NULL/reward_id NOT NULL/award_on NULL/channel='STAFF'/source_location_id NULL。
- SELFはkind='AWARD'、actor_user_id=user_id、source_location_id NOT NULL、award_on NOT NULL。STAFFのAWARDはsource_location_id NULL。
- rule_or_reward_version/program_version>=0。日次AWARDのaward_onはNOT NULL、都度AWARDはNULL（frequencyとの整合はWriterで検証）。NULLを含むuniqueが都度加算を誤って禁止しない。

同一ドメインの参照はtransactions(team_id,account_id)→accounts(team_id,id)、transactions(team_id,rule_id)→rules(team_id,id)、transactions(team_id,reward_id)→rewards(team_id,id)の複合FK（RESTRICT）とする。これにより別チームの口座・ルール・特典を結び付けられない。program/rule/reward/accountは物理削除せず、台帳は追記専用。台帳・残高・daily unique・idempotencyは同じDBシャード/同じTXに保つ。

account.user_idとtransaction.user_idの一致はWriterで検証し契約ITで固定する（複合FKだけで本人一致を保証したと誤記しない）。残高更新はaccountロック下で行い、overflow・残高不足・lifetime_earnedのLong overflowも事前検証する。名称/説明の空白・件数制限・日付算出はアプリ層で担う。

### 7.1 PLATFORMカードの一意性と既存データ

既存member_cardsの`(user_id,scope_type,scope_id,active_unique_key)`はPLATFORMのscope_id=NULLに対して重複を防げない。明示確保POSTの導入時に、既存表へ次の生成列とuniqueを追加する。

```sql
active_platform_user_id BIGINT UNSIGNED GENERATED ALWAYS AS
  (CASE WHEN scope_type = 'PLATFORM' AND deleted_at IS NULL THEN user_id ELSE NULL END) VIRTUAL
UNIQUE KEY uq_member_cards_active_platform_user_id (active_platform_user_id)
```

ここでactiveは「非論理削除」を意味し、SUSPENDED/REVOKEDも一意枠を占める。カード再作成で停止を回避しない。新規未発行時だけ安全なcard_code/qr_secretと個人内で安定した表示番号を生成し、並行作成はunique衝突後に別TXで既存行を返す。グローバルcount+1連番を使わない。既存member_cardsのLong主キーと旧カードのQR内容は変更しない。

migration前に非論理削除PLATFORMのuser_id別重複を検査し、あれば**適用を停止**する。行や履歴を無断で削除・統合しない。個々の状態・チェックイン参照を調べ、正準カードの選択と参照付替え・監査の別データ是正案を裁可してから再開する。検査結果へQR秘密・PIIを含めない。既存重複が無いDBでは加法的変更だけで移行できる。

## 8. 状態遷移・競合

| 対象 | 遷移・効果 |
|---|---|
| program | 未作成→DISABLED→ENABLED↔DISABLED。停止しても残高・履歴を保存。対象条件更新はversion+1、新規加算のみに適用 |
| rule | ACTIVE↔INACTIVE。更新ごとversion+1。同じidを維持し日次枠は消さない。日次から都度へ変更しても本人加算は許さない |
| reward | ACTIVE↔INACTIVE。内容・必要数変更はversion+1。preview後の変更は409で再確認を要求し、古い同意で別の数を消費しない |
| account | 未作成→0→加算/交換。下限0、上限INT_MAX。所属喪失では消去・凍結しない |
| transaction | 成功時だけ確定行を1つ追記。AWARD/REDEEMの後更新・削除・取り消しは初期対象外 |
| 受付（方式未確定） | 読取→本人確認画面→本人POST。自動方式なら原子的加算。承認方式の申請状態は裁可後に確定 |

設定画面のversion不一致はCOMMON_003(409)。操作時expectedVersion不一致はLOYALTY_007(409)。同時付与は加算合計が欠落しない。同時交換はロック下で片方の残高が不足した時点で拒否する。日次unique競合はLOYALTY_005に変換し、他のDB例外を同じエラーへ握りつぶさない。ルールのfrequencyを同日途中で変更しても、本人自動加算の一日一回枠は残る。

## 9. エラーコード予約

base上で`POINT_CARD`の最大は024、`MEMBERSHIP`も024。新loyaltyドメインの`LOYALTY_*`はコード・機能書に未使用で最大000として、**現在最大+1の001から予約**する。採番確定はマージ時に最新origin/main全体を再検索し、衝突時は後着側を改番する。既存コードを再利用できる認証401/形式COMMON_001/設定楽観競合COMMON_003は増やさない。全クライアント起因はSeverity.WARN、既定400以外はGlobalExceptionHandlerへ明示登録する。

| 予約コード | 条件 | HTTP | Severity |
|---|---|---|---|
| LOYALTY_001 | TEAM/本人口座対象/ルール/特典が無い・別TEAM（存在秘匿） | 404 | WARN |
| LOYALTY_002 | 当該TEAMの操作・管理権限無し | 403 | WARN |
| LOYALTY_003 | 現在の付与対象資格外 | 403 | WARN |
| LOYALTY_004 | program/rule/reward停止・本人加算不許可 | 400 | WARN |
| LOYALTY_005 | 同じ日次来店枠の加算済み | 409 | WARN |
| LOYALTY_006 | 同じIdempotency-Keyの内容相違 | 409 | WARN |
| LOYALTY_007 | 確認後にルール/特典/program変更 | 409 | WARN |
| LOYALTY_008 | 特典交換の残高不足（同義POINT_CARD_017に合わせる） | 400 | WARN |
| LOYALTY_009 | ポイント上限・件数上限・組合せ不正 | 400 | WARN |

## 10. セキュリティ・性能・移行

QR/tokenはHTTP bodyで送信し、ブラウザ永続ストレージ・台帳・アクセスログ・監査ログ・エラー報告・分析イベントへ記録しない。受付URLに固定署名を載せる方式を採る場合、そのリンク自体が再利用可能な秘密である限界を表示し、URL queryをログ/Refererへ流さずfragment受け渡し→メモリ保持→history.replaceStateで除去する。ログイン復帰はtokenをURLへ埋め直さず、失われた場合は再読取を求める。GET/リンクpreview/crawlerは加算を発火させない。既存認証/Refresh/CSP/Cookie設定は変更しない。

レート制限は既存Valkey基盤を利用し、previewと書込をactor単位それぞれ60回/分、チーム単位1000回/分とする。超過429、Valkey障害でもDB日次unique/idempotency/accountロックが整合性を守る。QRはTTL中に再利用可能であるため「QR単回消費」にはせず、日次枠または明示スタッフ確認で業務の重複を止める。レート制限を来店証明とみなさない。

1000万ユーザーを先行で全チームへ展開しない。program/rule/rewardは設定時、accountは初回成功加算時にだけ作る。個人チーム一覧はINDEX(user_id,id)でlimit+1、履歴は(team_id,user_id,id DESC)のseek paginationで読み、全件COUNT/全台帳SUM/深いoffsetを避ける。カーソルは認証主体・team・並び順へ束縛し、他主体のカーソルは400。チーム名は1ページをまとめて既存公開Serviceで解決し、1件ずつ越境Serviceを呼ばない。残高とlifetimeEarnedはaccountからO(1)、全active特典は最大20件で算出する。

初期性能受け入れ目標は本番相当MySQL・1000万accounts・1億transactions、同一TEAM200人並列の異なる本人に対し、主要GETと付与/交換のp95<=500ms（HTTP、DB待ち含む、外部カメラ読取除外）。履歴1ページのloyalty SQL<=3、個人一覧はloyalty SQL<=2＋チーム名バッチ1回、EXPLAINで上記複合索引のrange/refを確認する。同一accountへの競合は直列化するが、program/ruleの共有ロックで全TEAM書込を排他直列化しない。UUIDv7/team境界で将来シャードを分け、跨いだ残高の分散TXを要求しない。実測値・データ件数・並列数・実行計画を後続実装の証拠に残す。

Flywayは必要。新規5表、TEAM権限カタログ、PLATFORM生成列uniqueの3論理変更に分け、`V{major}.{UTC yyyyMMddHHmmss}__...sql`を追加する。base最大major=242だが、**majorはマージ時のorigin/main全体最大+1で確定**し、実装PR前にも再確認する。本書だけのPRにはmigrationを入れない。既存migrationを編集しない。新旧アプリの併存中は旧API・旧DTO・旧enumへ変更を加えず、新ルート/新表は追加のみ。受付方式や新永続enumは確定後にreader→writerの二段展開要否を確認する。

既存データ番人は必要。FlywayFromScratchMigrationTestへ表/列/複合unique/FK/CHECK/collation検証を相乗りさせ、既存F18カード・残高・会員QR・チェックイン行が不変であるmigration fixtureを追加する。PLATFORM重複無しはunique適用・旧行保持、重複有りは適用停止・旧行保持を確認する。退会時は既存GDPR匿名化方針に従い、表示名等のPIIを台帳へ保存しない（labelはチーム設定名のみ）。user_idはNULLにせず履歴を保持し、退会アカウントからのAPI到達を拒否する。
