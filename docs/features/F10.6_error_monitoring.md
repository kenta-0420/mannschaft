# F10.6: エラー監視 (Error Monitoring)

> **ステータス**: 🟢 設計確定
> **実装フェーズ**: Phase 10（段階導入。Section 5 のサブフェーズ参照）
> **最終更新**: 2026-05-07
> **モジュール種別**: 横断インフラ（SYSTEM_ADMIN 専用）
> **関連ドキュメント**: F10.3 監査ログ（記録系）、F10.4 経営分析（業務指標）、F10.5 パフォーマンス監視（性能指標。本機能と同時整備で通知経路を共有）、**F12.5 フロントエンドエラー追跡（既存実装。本機能は F12.5 を中核インフラとして引用し、運用・分類・通知の側面を整備する）**

---

## 1. 概要

サーバ・クライアント双方で発生するエラーを **検知 → 集約 → 分類 → 通知 → 改修トラッキング** まで一貫して観測できる基盤を整備する。

### 既存資産との関係（重要）

本設計書を起こす前提として、**`error_reports` テーブルおよび `useErrorReport` 経由のフロントエンド送信機構は F12.5（フロントエンドエラー追跡）で既に完全実装済み**である:

- `error_reports`（V12.006）: エラー本体（集約レコード。`error_hash` で重複集約）
- `error_reports` 拡張（V12.013）: `workflow_stage` / `assignee_id` / `github_issue_url` 等の運用カラム
- `error_report_occurrences`（V12.014）: 個別発生ログ（タイムライン用）
- `error_report_ai_analyses`（V12.015）: AI 分析履歴
- `error_report_activities`（V12.016）: 操作・コメント履歴
- `useErrorReport` composable: `POST /api/v1/error-reports` への自動送信（クールダウン 60 秒）
- `ErrorReportService` / `ErrorReportNotifier` / `ErrorReportRateLimitFilter`: バックエンド受信・通知・レート制限

**F10.6（本設計書）の責務**は F12.5 と重複しない。具体的には:

| 責務 | 担当 |
|-----|------|
| フロントから送信された個別エラーの保存・集約・閲覧 UI | F12.5（既存）|
| 個別エラーのワークフロー（NEW → IN_REVIEW → RESOLVED）と AI 分析 | F12.5（既存）|
| **バックエンド側の例外を `error_reports` に流し込む経路（`recordBackendException`）** | **F10.6（本設計書）** |
| **エラー分類ポリシー（バリデーション=記録しない / Business=WARN / 想定外=ERROR）** | **F10.6（本設計書）** |
| **アラート条件（Slack / Email / PagerDuty）と閾値** | **F10.6（本設計書）** |
| **F10.5 パフォーマンス監視と統合した通知経路** | **F10.6（本設計書）** |
| **インフラ障害（DB 接続喪失 / Redis 接続失敗）の検知と通知** | **F10.6（本設計書）** |
| **将来の外部基盤（Sentry / Loki）への移行計画** | **F10.6（本設計書）** |

### 解決する課題

| 課題 | 現状 | 本機能で解決 |
|------|------|-----------|
| バックエンド例外が `error_reports` に集約されない | `GlobalExceptionHandler` がログ出力するだけで永続化なし | `ErrorReportService.recordBackendException(exception, request, severity)` を例外ハンドラから呼ぶ |
| バリデーションエラーで `error_reports` が膨れ上がる懸念 | 既存実装は記録しない方針だが明文化されていない | §5.2 の「エラー分類基準」で正式に方針を確定 |
| アラート閾値が運用任せで一貫していない | Slack 通知は実装あり、閾値は設定値ベース | §5.5 で WARN/ERROR の数値基準を確定 |
| インフラ障害（Valkey 切断・MySQL 接続喪失）の即時検知 | ログから事後判明 | Spring Boot Health Indicator + `ErrorReportNotifier` で即時通知 |

### 設計方針

- **F12.5 既存スキーマを尊重する**: 新規テーブル追加は行わない。バックエンド例外を流し込む経路を整えるのみ。
- **対処療法禁止**: `try-catch` で例外を握りつぶしている箇所を本機能で根治する。`GlobalExceptionHandler` の各 `@ExceptionHandler` から `ErrorReportService.recordBackendException()` を呼ぶ形に統一する。
- **F10.5 パフォーマンス監視と通知経路を共有**: `ErrorReportNotifier` を共通の Slack 通知経路として、性能劣化（API > 10 秒など）も同じ口で通知する。
- **段階導入**: Phase 10-α（バックエンド例外の流し込み）→ Phase 10-β（アラート閾値の運用化）→ Phase 10-γ（外部基盤検討）。

### 3.2 集約キー（`error_hash`）の生成ルール

F12.5 の既存ロジックを踏襲しつつ、バックエンド由来の場合は以下のルールを適用:

```
error_hash = SHA-256(
    source        // "BACKEND" 固定（フロント由来は "FRONTEND"）
    + ":" + className   // 例外クラスの完全修飾名
    + ":" + method      // HTTP メソッド
    + ":" + uriTemplate // パステンプレート（{id} などプレースホルダ展開後）
    + ":" + topStackFrame // 例外の最上段スタックフレーム（行番号除く）
)
```

これにより同種のエラーが同 `error_hash` に集約される。フロント由来 (`useErrorReport` のロジック) と衝突しないよう **先頭の `source` 文字列で前置き分離する**。

### 4.2 バックエンド由来エラーの内部記録メソッド（追加）

```java
public interface ErrorReportService {
    // 既存（F12.5）
    ErrorReport create(ErrorReportCreateRequest request);

    // 本機能で追加
    void recordBackendException(
        Throwable exception,
        HttpServletRequest request,
        Severity severity
    );
}
```

呼び出し元（本機能で追加）:

- `GlobalExceptionHandler.handleGenericException(Exception ex, HttpServletRequest req)`: `severity=HIGH` で記録
- `GlobalExceptionHandler.handleBusinessException(BusinessException ex, ...)`: `severity=MEDIUM` で記録（**ただし `ErrorCode.severity` が WARN かつ HTTP 5xx ではない場合は記録しない** — §5.2 参照）
- `GlobalExceptionHandler.handleDataAccessException(DataAccessException ex, ...)`: `severity=CRITICAL` で記録（インフラ障害扱い）
- F10.5 §5.2.2 から `notifySlowRequest(...)` 経由: `severity=HIGH` で記録（10 秒超のリクエスト）
- Spring Boot Health Indicator が DOWN を返した時: `severity=CRITICAL` で記録（§5.4）

## 5. ビジネスロジック

### 5.1 全体フロー

```
[フロント発生]
useErrorReport.capture(error)
    └─ POST /api/v1/error-reports → ErrorReportService.create()
                                        ├─ error_reports に集約 INSERT
                                        ├─ error_report_occurrences に追記
                                        └─ ErrorReportNotifier.notify() ────┐
                                                                              ▼
[バックエンド発生]                                                  Slack Webhook (#alerts-error)
GlobalExceptionHandler.handle*()                                    SYSTEM_ADMIN プッシュ通知 (CRITICAL のみ)
    └─ ErrorReportService.recordBackendException()                  Email (CRITICAL のみ・Phase 10-β)
                ├─ error_reports に集約 INSERT/UPDATE
                ├─ error_report_occurrences に追記
                └─ ErrorReportNotifier.notify() ────────────────────┘

[F10.5 から呼ばれる場合]
ResponseTimeFilter (duration > 10s)
    └─ ErrorReportNotifier.notifySlowRequest() → 同上経路
```

### 5.2 エラー分類基準（**最重要**）

| 種別 | 例 | HTTP ステータス | logback レベル | `error_reports` 記録 | `severity` |
|-----|-----|--------------|---------------|------------------|----------|
| **バリデーションエラー** | `MethodArgumentNotValidException` / `ConstraintViolationException` / `HttpMessageNotReadableException` | 400 | INFO | **記録しない**（過剰になるため） | — |
| **ビジネスエラー (4xx)** | `BusinessException`（NotFound・Forbidden・Conflict 等の `Severity=WARN`） | 400/401/403/404/409 | WARN | **記録しない**（業務上想定内のため） | — |
| **ビジネスエラー (5xx)** | `BusinessException` のうち `Severity=ERROR` で 5xx を返すもの | 500 | ERROR | 記録する | MEDIUM |
| **想定外実行時例外** | `RuntimeException` / `NullPointerException` / `IllegalStateException` 等 | 500 | ERROR | 記録する | HIGH |
| **インフラ障害** | `DataAccessException` / `RedisConnectionFailureException` / `MailSendException` | 500 | ERROR | 記録する + ヘルスチェック連動通知 | CRITICAL |
| **遅延リクエスト** | F10.5 から通知される 10 秒超のリクエスト | — | WARN | 記録する | HIGH |
| **Health Indicator 異常** | `/actuator/health` の DB / Redis コンポーネントが DOWN | — | ERROR | 記録する（重複抑制あり） | CRITICAL |

> **記録しない理由（バリデーション・ビジネス 4xx）**: これらは「ユーザー操作の誤り」「業務ルールに沿った正しい拒否」であり、開発チームが調査すべきエラーではない。記録対象を絞らないと `error_reports` テーブルが日常的なリクエスト失敗で埋まり、本当に深刻な問題が埋もれる。これは F12.5 でも暗黙に採用されていた方針を本設計書で **正式に明文化**する。

### 5.3 `GlobalExceptionHandler` への組み込み方針

既存ハンドラを以下のように改修する（実装は Phase 10-α で行う）:

```java
@ExceptionHandler(Exception.class)
public ResponseEntity<ErrorResponse> handleGenericException(
        Exception ex, HttpServletRequest request) {
    // 1. 既存のログ出力（維持）
    log.error("Unhandled exception", ex);

    // 2. 本機能で追加: error_reports に記録
    errorReportService.recordBackendException(ex, request, Severity.HIGH);

    // 3. 既存のレスポンス変換（維持）
    return ResponseEntity.status(500).body(ErrorResponse.of("INTERNAL_ERROR"));
}
```

**重要**: 既存の `BusinessException` ハンドラには **ErrorCode の `severity` フィールドを参照する分岐**を入れる。`severity=WARN` かつ HTTP 4xx の場合は `recordBackendException` を呼ばない。

### 5.4 Health Indicator 連携（インフラ障害の検知）

Spring Boot Actuator の `HealthIndicator` を活用し、DB / Redis / 外部 API の DOWN を検知したら `error_reports` に記録する:

- 既存: `DataSourceHealthIndicator`（HikariCP 経由）/ `RedisHealthIndicator`（Lettuce 経由）が自動構成済み
- 本機能で追加: `HealthStatusListener`（仮称）が `HealthEndpoint` を 30 秒毎に polling し、`UP → DOWN` 遷移を検知したら `recordBackendException()` を呼ぶ。`DOWN → UP` 復旧時は `error_report_activities` に `RECOVERY` を追記
- 同じインフラの DOWN が連続発生する場合は `error_hash` で集約され `occurrence_count` が増えるのみ（テーブル汚染なし）

> **Phase 10-β-1 実装範囲（2026-05-08）**: `ErrorReportNotifier.notifyHealthDown(component, detail)` メソッドの追加と、Caffeine ベースの 5 分クールダウン抑制までを実装。**`HealthStatusListener` による `HealthEndpoint` の 30 秒 polling 実装は Phase 10-β-2 で対応予定**。Phase 10-β-1 段階では、外部監視 (Kubernetes liveness/readiness probe / 外部 SaaS) 経由で DOWN を検知した運用者が手動で `notifyHealthDown` 経路を叩ける状態にとどまる。
>
> **Phase 10-β-2 実装完了（2026-05-08）**: `com.mannschaft.app.health.HealthStatusListener` を実装し `HealthEndpoint` の 30 秒 polling を有効化。UP → DOWN 遷移検知時に `notifyHealthDown` を自動発火する。初回ポーリングは状態記録のみで通知せず、起動直後の誤検知を防ぐ。DOWN → UP 復旧通知は本フェーズではログのみ（`error_report_activities` への RECOVERY 追記は Phase 10-γ で対応予定）。設定は `mannschaft.error-monitoring.health-polling.{enabled,interval-ms}` で上書き可能。

### 5.5 アラート通知経路（`ErrorReportNotifier`）

F12.5 で既に存在する `ErrorReportNotifier` を本機能で **以下の通知メソッドを追加**して拡張する:

```java
public interface ErrorReportNotifier {
    // 既存（F12.5）: フロント由来の error_reports 受信時に呼ばれる
    void notify(ErrorReport report, NotifyContext context);

    // 本機能で追加: F10.5 からの遅延リクエスト通知
    void notifySlowRequest(String method, String path, long durationMs, String requestId);

    // 本機能で追加: Health Indicator 異常通知
    void notifyHealthDown(String component, String detail);
}
```

通知先設定（`application.yml` で構成）:

```yaml
mannschaft:
  error-monitoring:
    slack:
      webhook-url: ${MANNSCHAFT_SLACK_ERROR_WEBHOOK:}
      channel-warn: "#alerts-error"
      channel-critical: "#alerts-critical"
    email:
      enabled: false  # Phase 10-β で有効化
      recipients: ${MANNSCHAFT_ERROR_EMAIL_RECIPIENTS:}
    push:
      enabled: true   # SYSTEM_ADMIN への WebPush（既存 F04.3 通知基盤を流用）
      severities: [CRITICAL]
```

### 5.6 重複アラート抑制

同一の `error_hash` が短時間に大量発生してもアラートを連続送信しない:

- **Slack 通知**: 同一 `error_hash` あたり 1 分間で 1 通まで。2 通目以降は集約バッファに蓄積し、5 分後に「直近 5 分で N 件発生」と 1 通にまとめて送信
- **Email 通知**: 同一 `error_hash` あたり 1 時間で 1 通まで（CRITICAL のみ）
- **WebPush 通知**: 同一 `error_hash` あたり 10 分で 1 通まで（CRITICAL のみ）
- 抑制状態は Caffeine キャッシュ（メモリ）で管理。アプリ再起動でリセットされるが、再起動直後の異常検知優先のため許容

> **Phase 10-β-1 実装範囲（2026-05-08）**: 単純な重複抑制（1 分以内の同一キー早期 return）のみを Caffeine ベースで実装。**2 通目以降を集約バッファに溜めて 5 分後に「直近 5 分で N 件発生」とまとめて送信する集約サマリ送信は Phase 10-γ で対応予定**。Phase 10-β-1 段階では、現状仕様（1 分間 1 通＋以降の発生は無通知だが `error_reports.occurrence_count` は確実にインクリメント）でも、ダッシュボードの数値で発生頻度が確認できるため運用上の支障はない。
>
> **集約バッファ実装完了（2026-05-08、Phase 10-β-2 と統合 PR）**: `com.mannschaft.app.errorreport.service.ErrorReportAggregator`（Caffeine ベース、`expireAfterWrite=5min` / `maximumSize=1000` / 1 entry あたりの最大 occurrences=100）と `com.mannschaft.app.errorreport.batch.ErrorAggregationFlushBatch`（5 分毎の `@Scheduled` バッチ）を新設。`ErrorReportAsyncExecutor` でバックエンド由来例外を記録する経路から `aggregator.addOccurrence(errorHash, message, severity)` を呼び、戻り値が `FIRST_OCCURRENCE` のときのみ Slack 即時通知、`BUFFERED` のときは抑制し 5 分後の集約サマリへ流す。`BUFFER_FULL`（同一 hash で 100 件超過）は OOM 防止のため追加無視＋ log warn のみ。SYSTEM_ADMIN プッシュ通知は埋没防止のため抑制対象から外す。`ErrorReportNotifier.notifyAggregatedSummary(Map<String, AggregatedEntry>)` を新設し「直近 5 分で N 種のエラーが計 M 回発生」と 1 通の Slack メッセージ（詳細は最大 10 件まで）に集約送信する。設定は `mannschaft.error-monitoring.aggregation.{enabled,flush-interval-ms,max-occurrences-per-hash}` で上書き可能。

### 5.8 フロントエンド（Nuxt 3）エラー補足の整理

F12.5 で既に整備済みの仕組みを本設計書で改めて整理:

| 機構 | 用途 | 既存/新規 | 担当設計書 |
|------|------|----------|----------|
| `useErrorReport.capture(error)` | モーダル + サーバ送信 | 既存 | F12.5 |
| `useErrorReport.captureQuiet(error)` | サイレント送信（ウィジェット用） | 既存 | F12.5 |
| `errorHandler.client.ts`（Nuxt plugin） | Vue errorHandler / unhandledrejection | 既存 | F12.5 |
| `useError()` / `createError()` | SSR + クライアント | 既存 | Nuxt 標準 |
| `onErrorCaptured` | コンポーネント単位のキャッチ | 既存 | Nuxt 標準 |

**SSR vs CSR の扱い**: `useErrorReport.captureQuiet` は `import.meta.server` で早期 return しており、SSR 中のエラーはサーバ送信しない（既存実装）。SSR エラーは Nuxt のサーバログ側で発生し、本機能の `GlobalExceptionHandler` 経路には乗らない（Nuxt と Spring は別プロセス）。SSR エラーの集約は **Nuxt サーバログを Cloudflare Workers 等で R2 に転送し、F10.5 のスロークエリログ収集経路と統合する**運用とする（Phase 10-γ で確定）。

### 5.9 PII redact

フロントから送信される `errorMessage` / `stackTrace` / `userComment` には PII（メールアドレス・電話番号・氏名）が紛れ込む可能性がある:

- **送信前 redact（フロント）**: `useErrorReport.capture()` 内に `redact(text: string): string` 関数を新設し、以下のパターンをマスキング
  - メールアドレス: `[\w.-]+@[\w.-]+\.\w+` → `***@***`
  - 電話番号: `\d{2,4}-?\d{2,4}-?\d{4}` → `***-***-****`
  - クレジットカード様番号: `\d{4}[\s-]?\d{4}[\s-]?\d{4}[\s-]?\d{4}` → `****-****-****-****`
- **受信時 redact（バックエンド）**: 二重防御として `ErrorReportService.create()` 内で同パターンを再適用
- **`stackTrace` 内のユーザー入力**: 通常の Java スタックトレースには引数値は含まれないが、Spring の `MethodArgumentNotValidException` メッセージにはフォームの値が含まれることがある。本機能では §5.2 で「バリデーションエラーは記録しない」方針なので影響を受けない

### 5.10 外部基盤の選定方針（Phase 10-γ・参考情報）

| 候補 | 採用判断 | 理由 |
|-----|---------|------|
| Sentry（クラウド） | **保留** | 月額コスト・データ越境（米国リージョン）の懸念。導入時は ToS 確認 |
| Sentry（セルフホスト） | **保留** | 運用負荷高。インフラが固まる Phase 10 後半で再評価 |
| Grafana Loki + Promtail | **保留** | F10.5 で Grafana 採用なら一括導入が望ましい |
| GlitchTip（OSS Sentry 互換） | **保留** | セルフホスト負荷は低めだが知見不足 |
| **既存 `error_reports` + Slack 通知** | ✅ **採用（最低限の代替・現行）** | 追加インフラ不要。エラー件数が増えてから外部基盤に移行可能 |

## 6. セキュリティ考慮事項

### 6.1 IDOR 対策

- `GET /api/v1/system-admin/error-reports/{id}` は SYSTEM_ADMIN ロールのみアクセス可（F12.5 既定）
- ADMIN・MEMBER 等が他人の `error_reports` を覗くことはできない（自組織配下のエラーであっても）
- フロントの `error_reports` 送信エンドポイントは匿名でも受け付けるが、`user_id` はサーバ側で JWT から再注入する（リクエストボディの `userId` は信用しない・既存 `ErrorReportService.create()` で実装済み）

### 6.2 XSS 対策

- 管理画面（F12.5 既存）で `error_message` / `stack_trace` / `user_comment` を表示する際は **必ず Vue の `{{ }}`（HTML エスケープあり）を使用**し、`v-html` は禁止
- `stack_trace` には `<script>` タグなどの文字列が紛れる可能性がある（攻撃者が意図的に投げ込めるため）
- F12.5 既存の管理画面が v-html を使っていないことを **F10.6 設計確定の precondition** として確認済み（FRONTEND_CODING_CONVENTION.md §13 で禁止明記）

### 6.3 大量送信攻撃対策

- `POST /api/v1/error-reports` は **既存の `ErrorReportRateLimitFilter`**（F12.5 / Bucket4j）で IP 単位 10 req/分にレート制限
- 認証済みユーザーは別途 30 req/分まで許容（合法的に大量エラーを踏むケースのため）
- レート制限超過時は 429 を返し、本機能の経路には記録しない（無限ループ防止）

### 6.4 PII リーク対策

- §5.9 で定義した redact を **送信前（フロント）+ 受信時（バックエンド）の二重適用**
- `error_reports.user_comment` はユーザー自由記述なので PII が含まれる前提で扱う。SYSTEM_ADMIN 閲覧時に「個人情報を含む可能性があります」のラベル表示を管理画面 UI に追加する（F12.5 後続改訂で対応）
- スタックトレースに含まれる SQL 引数の PII は §6.4 のマスキング対象キーワード（F10.5 §6.2 と同等）でマスキング

### 6.5 SYSTEM_ADMIN 認証

F10.5 §6.4 と同じ二段階認証ポリシー:

1. JWT アクセストークンに `roles=["SYSTEM_ADMIN"]` クレーム必須
2. `users.role = 'SYSTEM_ADMIN'` を DB で再確認

### 6.6 アラート通知への偽装防止

Slack Webhook URL は環境変数で管理。リポジトリにコミットしない。Webhook 経由で送信されるメッセージは Mannschaft 側で生成するため、外部からの偽装通知混入リスクはない（Slack Webhook の片方向性）。

### 6.7 Actuator の自己参照禁止

`/actuator/health` の継続的 polling（§5.4）の結果自体は **`error_reports` に書かない**（無限ループ・ノイズ過多防止）。あくまで「DOWN を検知した時のみ書く」。
