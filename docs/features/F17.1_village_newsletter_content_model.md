## 1. 背景と課題

### 1.1 「入れ物だけ・中身が未定義」

村だより（旧・村ニュースレター）は **配信の器（設定・opt-out・配信履歴・配信バッチの骨格）は既に存在するが、「何を配信するか（本文＝内容モデル）」が一切定義されていない。** マスターが実機で「村だよりをオンにしても中身が飛んでこない」ことを発見したのが本戦役の発端である。

【確認済み】現状の内容モデルの欠落を示す実コード:

- `VillageNewsletterEntity`（`backend/.../village/entity/VillageNewsletterEntity.java`）は **`village_id` / `frequency` / `is_enabled` / `last_sent_at` / `next_scheduled_at` / 論理削除・監査カラムのみ**。本文・ダイジェスト・コメントに相当するカラムは無い。
- `VillageNewsletterDispatchBatchService.deliverToUser`（同 `batch/VillageNewsletterDispatchBatchService.java:190-193`）は **`log.debug` のプレースホルダ**。実際には何も配信していない:

  ```java
  private void deliverToUser(VillageNewsletterEntity newsletter, Long userId) {
      log.debug("[NEWSLETTER PLACEHOLDER] villageId={} userId={} freq={} (実配信は後続フェーズで NotificationDispatch 連携予定)",
              newsletter.getVillageId(), userId, newsletter.getFrequency());
  }
  ```

- 配信の集計対象・凍結・コメントを保持する「号（issue）」テーブルは存在しない。`village_newsletter_send_logs` は **1 配信バッチ実行あたり 1 行の集計値（recipient/success/failure count）のみ** で、配信本文は残らない。

【確認済み】以下は稼働済みで、本戦役はこの上に「内容モデル」を積む:

## 2. マスター確定仕様

> 本章はマスターが確定させた要件そのものである。以降の設計（§4〜§10）はこれを満たすためのもの。

### 2.1 五本柱

1. **改ざん不可の自動ダイジェスト** — **集計日**にシステムが村の活動を集計し、ダイジェストを **確定・凍結** する。以後書き換え不可（＝村人が受け取る集計値は常に事実）。
2. **別欄の村長コメント（ラグ猶予）** — **集計日〜配信日の間にラグ（猶予期間）** があり、村長/長老は **ダイジェスト本体とは別の自由記述欄** にコメントを書ける。ダイジェストを引用してよいが本体は編集不可。
3. **コメント無ければ自動配信** — **配信日** に「凍結ダイジェスト＋（あれば）コメント」を組み立てて配信。**コメントが無ければダイジェスト単体を自動配信**（村長が何もしなくても飛ぶ＝手間ゼロが既定）。
4. **集計日・配信日は村ごとに設定可能** — 現状の週次=金曜／月次=月末ハードコードを **設定制** にする。
5. **号外** — ダイジェストを外し、純粋な自由記述のみを任意タイミングで即配信（定期便とは別経路）。

### 2.2 ライフサイクル図（定期便）

```
     集計日                        ラグ（猶予期間）                       配信日
       │                                                                    │
       ▼                                                                    ▼
  ┌─────────┐   凍結    ┌──────────────────────────────┐  自動組立  ┌──────────┐
  │ 活動を集計 │ ───────▶ │  号(issue) = FROZEN            │ ────────▶ │ 配信      │
  │（期間内）  │          │  ・凍結ダイジェスト（編集不可）    │           │ 凍結値+   │
  └─────────┘          │  ・村長コメント欄（任意・編集可）   │           │ コメント   │
                        └──────────────────────────────┘           └──────────┘
                            村長/長老がこの間にコメントを書ける             コメント無し
                            （書かなくてもよい）                          →ダイジェスト単体
```

### 2.3 週次と月次の「集計日/配信日」

| 頻度 | 集計日の型 | 配信日の型 | 例 |
|---|---|---|---|
| **WEEKLY** | 曜日（DayOfWeek） | 曜日（DayOfWeek） | 集計=月曜 / 配信=金曜 |
| **MONTHLY** | 日付（1〜28 or 月末） | 日付（1〜28 or 月末） | 集計=25日 / 配信=翌1日 |

> 週次は曜日で自然、月次は「日付」で一般化する（現行の月末ハードコードは月末=特別値として表現）。詳細は §4.3。

## 3A. アーキテクチャ決定 — 案Y 確定（案X / 案Z は不採用）

> マスターが「村史は集計をためるだけ。ならば **ニュースレターをブログ形式でためて・タグ付けして・ブログの公開設定で他の人のブログ一覧にも出せる** のでは？」という統合案を提起した。これを受け内容モデルの実現アーキテクチャを3案で比較した結果、**マスターは案Y を御裁可した（2026-07-17「案Yで可。よきにはからえ」）。** 本節は決定の根拠と、案X/案Z を退けた理由を記録する。**中核仕様〔§2〕はどの案でも守る前提で、案Y で表現する。**

### 3A.1 「push（配信）」と「pull（アーカイブ）」は別概念 — 二層で整理する

マスターの要望は2つの異なる軸に分解できる:

| 層 | 概念 | 既存の相当機能 | 性質 |
|---|---|---|---|
| **push（届ける）** | 配信・通知 | 通知基盤（`NotificationHelper`） | その時に飛ばす。改ざん不可の凍結ダイジェストを送る |
| **pull（ためて見る）** | アーカイブ・公開一覧 | 既存の月次統計（`VillageChronicle`・村内 pull）／**ブログ（ためる＋公開）** | 後から一覧・タグ・公開範囲で参照 |

> **整理**: 既存の月次統計（`VillageChronicle`）＝ためる/pull（村内・統計のみ）、村だより＝**push（配信）＋ pull（号アーカイブ）の両方**、ブログ＝ためる＋公開一覧。マスターは「村だよりの成果物を **ブログのようにためて公開一覧に出す**」ことを望んでいる。この pull 層に **「村史」「村だより広場」** の名が付いた（§3B で確定）。
> **本設計の背骨**: **push 層は通知基盤に必ず載せる**（案問わず）。争点は **pull 層（号アーカイブ・タグ・公開一覧）を「ブログ本体に相乗り（案X）」か「村ドメインに独立（案Y）」か「作らない（案Z）」か**。

### 3A.2 ブログ機能の実コード確認【確認済み】

CMS ブログは成熟した本格 CMS である（`backend/src/main/java/com/mannschaft/app/cms/`）:

| 資産 | 実体 | 村転用の可否 |
|---|---|---|
| 本文モデル | `BlogPostEntity`（`title`/`body` TEXT/`excerpt`/`coverImageUrl`/`slug`） | 本文あり（村史との決定的差） |
| タグ | `BlogTagEntity` + `BlogPostTagEntity`（中間表） | ○ 概念は流用したい |
| シリーズ | `BlogPostSeriesEntity` | 村には過剰 |
| 版管理 | `BlogPostRevisionEntity` | 改ざん監査に転用余地 |
| リアクション | `BlogPostReactionEntity` | 村には任意 |
| 公開範囲 | `Visibility` enum（**`PUBLIC` あり** ＋ ラダー`SUPPORTERS_AND_ABOVE`/`MEMBERS_AND_ABOVE`/…/`CUSTOM`ペイウォール） | ○ `PUBLIC` で公開一覧に出せる |
| 下書きWF | `PostStatus`（`DRAFT`→`PENDING_SELF_REVIEW`→`PUBLISHED`/`REJECTED`） | ラグ/凍結WFと概念が近い |
| 公開一覧 | `public_visible` フラグ（F19.1）＋ RSS/Atom フィード（`BlogFeedService`） | ○ 公開一覧の実績あり |
| 可視性判定 | `BlogPostVisibilityResolver`（F00 基盤・ペイウォール連結） | △ Long 密結合（下記） |

### 3A.3 🔴 決定的な壁 — ブログは Long スコープ、村は UUID【確認済み】

案X（ブログ流用）の最大の障害。**通知基盤で発覚したのと同じ UUID/Long の壁がブログにも存在する。**

- **`BlogPostEntity` は `BaseEntity` 継承＝主キー `Long`**（`UuidV7Entity` ではない。`BlogPostEntity.java:32`）。スコープ列は **`teamId`/`organizationId`/`userId`/`socialProfileId`/`authorId` すべて `Long`**（同 :34-42）。**`villageId` が無い。** 村ID は **UUID（BINARY(16)）**。
- **`PostType` は `BLOG` / `ANNOUNCEMENT` のみ**（`PostType.java:6-9`）。VILLAGE 系の種別が無い。
- **タグ中間表は Long キー**: `BlogPostTagEntity` は `blogPostId`/`blogTagId` が **`Long` 複合主キー**（`BlogPostTagEntity.java:28-33`）。`BlogTagEntity` も `teamId`/`organizationId` が `Long`（`BlogTagEntity.java:23-25`）。UUID キーの村号をこの中間表に join させるには **PK 型 surgery** が要る。
- **F00 可視性基盤は BlogPost を Long content-id で解決**: `BlogPostVisibilityResolver.loadProjections(Collection<Long> ids)`（`BlogPostVisibilityResolver.java:69`）・`ReferenceType.BLOG_POST`。可視性・ペイウォール（`Visibility.CUSTOM`→`PaymentGateService`）が Long 前提で密結合。
- **公開フィード/リンクは team/org のみで routing**: `BlogFeedService.buildPostLink`/`buildFeedLink` は `teamId`/`organizationId` からしか URL を組まない（`BlogFeedService.java:113-134`）。村ルーティングは無い。

> つまり案X は「Long スコープ前提の成熟機能に UUID の村軸を1本通す」手術になり、可視性・タグ・フィード・多数の scope 契約 IT（`CmsBlogPostWriteScopeContractIT`/`CmsSeriesTagScopeContractIT` 等）へ波及する。

### 3A.4 改ざん不可 vs ブログ本文の自由編集【確認済み】

- 【確認済み】`BlogPostEntity.update(title, slug, body, ...)`（`BlogPostEntity.java:155-166`）は **本文 `body` を自由に上書き** する。ブログは「編集し続ける記事」モデル。
- マスター中核仕様①「凍結ダイジェスト＝以後書き換え不可」と **本文自由編集は対立**。案X で号をブログ投稿として持つ場合、**「本文の一部（ダイジェスト）は編集不可、別部（コメント）は編集可」という二領域を、単一の自由編集 `body` にどう表現するか** が課題になる。
  - 対処案: ダイジェストを別カラム（`frozen_digest_json` 等）でブログに増設し、`body`＝コメント領域のみ自由編集、表示時に結合。→ **ブログエンティティに村専用カラムを足す侵襲**。あるいは `BlogPostRevisionEntity`（版管理）で凍結版を封じる案もあるが、版管理は「編集を許した上で履歴を残す」思想で「編集を禁じる」要件と噛み合わない。

### 3A.5 三案の比較（決定の根拠）

| 軸 | 案X（ブログ本体に相乗り）**［不採用］** | 案Y（ブログを金型に村ドメインへ独立）**★確定** | 案Z（当初モデル・push のみ）**［不採用］** |
|---|---|---|---|
| 概要 | 号を `BlogPostEntity` として持つ。`villageId`(BINARY16)＋VILLAGE系 PostType/導線をブログに通す | 村ドメインに号テーブル（`title`/`body`/`tags`/`visibility`/`status`・UUIDv7）を**ブログを参考に**新設。ブログ本体は不変 | 凍結ダイジェスト＋コメントを通知配信するだけ。ためない・公開一覧なし |
| **マスター要望（ためる/タグ/公開一覧）** | ◎ 満たす（機能そのもの流用） | ○ 満たす（村ドメイン内にタグ・PUBLIC 公開一覧を持つ） | ✗ **満たさない** |
| 実装コスト | **大**（Long→UUID 軸追加の手術＋回帰） | 中（号テーブル＋村内タグ/可視性/公開一覧の新規。ただし村ドメインに閉じ設計が単純） | 小 |
| 既存ブログへの影響/リスク | **高**（可視性・ペイウォール・タグ・フィード・多数の scope IT に波及。成熟＆課金連結の security-sensitive 機能を改造） | **無**（ブログ不変） | 無 |
| UUID/Long 壁の越え方 | 壁を**越える必要**（BlogPost に BINARY(16) 村軸・タグ中間表の PK・可視性 Resolver の村分岐） | 壁を**越えない**（最初から UUIDv7 ネイティブ） | 越えない（push は actionUrl 方式・§7.2） |
| 村史との関係 | 村史は別物のまま。ブログと村史が二重の「ためる」箱に | 村史＝統計 pull、号＝配信＋アーカイブ pull と役割分担が明確 | 村史はそのまま。号は残らない |
| 改ざん不可の整合 | **課題**（本文自由編集と対立・§3A.4） | ○ 容易（`digest_*` snapshot 列を FROZEN 後 setter 無しで封じる・§4.2） | ○ 容易（凍結 snapshot） |
| ADHD-UX | 高機能ゆえ設定過多になりやすい（シリーズ/リアクション等が露出） | 村向けに必要機能だけ（タグ＋公開トグル）に絞れる＝シンプル | 最小だが「ためて見返す」体験が無い |
| 保守面積 | 機能**肥大**（村の都合がブログ本体に恒久的に混入） | 機能**重複**（タグ/可視性を村にも持つ。ただし村ドメインに局所化） | 最小 |

### 3A.6 決定 — 案Y 確定（マスター御裁可 2026-07-17）

**確定: 案Y（ブログを金型に、pull 層＝号アーカイブを村ドメインへ独立実装。push 層は通知基盤〔§7〕）。**

採用理由:
1. マスターの要望（ためる・タグ・公開一覧）を **満たしつつ**、UUID/Long の壁を **越えずに済む**（案X の最大リスクを回避）。
2. ブログは可視性・ペイウォール・課金連結を持つ **security-sensitive な成熟機能**。ここへ村軸を通す手術は回帰リスクが高く、本戦役のスコープを大きく超える（memory `feedback_openapi_nested_schema_name_collision`／scope 契約 IT 群）。
3. 改ざん不可要件が **snapshot 列で素直に満たせる**（案X は本文自由編集と衝突・§3A.4）。
4. §3A.1 の二層整理（push=通知／pull=アーカイブ）に最も自然に写像する。§4 以降の号テーブルは、案Y に `title`/`body(=コメント)`/`tags`/`visibility(PUBLIC含む)`/`status` を足したものになる（§4.2）。

**別件 ID 監査による裏付け（2026-07-17・家老の分析と一致）:**
- UUID 方針は **「新規テーブルのみ UUIDv7・既存 BIGINT は互換維持で据え置き」＝全統一ではない**（CLAUDE.md 原則6・「既存テーブルの BIGINT ID は変更しない」）。

- ブログに村（UUID）を通すのは **可視性基盤・タグ複合 PK・複数ドメインの Long 参照へ波及する中〜大規模の別軍議相当** と監査が確認。→ **案X はコスト過大、案Y が現実的** と裏付けられた。

**不採用理由:**

| 案 | 不採用理由 |
|---|---|
| **案X（ブログ本体に相乗り）** | ①ブログ 9 テーブルは BIGINT 据え置き対象の既存資産で、村（UUID）を通すには可視性基盤・タグ複合 PK・複数ドメインの Long 参照を UUID 対応する **別軍議相当の大手術**（§3A.3・監査裏付け）。②ブログ本文は自由編集で、**改ざん不可の凍結ダイジェスト要件と衝突**する（§3A.4）。③成熟＆課金連結の security-sensitive 機能への回帰リスクが本戦役スコープを大きく超える。 |

## 4. DB 設計

### 4.1 村史（`village_chronicles`）を凍結ダイジェストの保存場所に流用できるか — 結論: 流用しない

【確認済み】`VillageChronicleEntity` の性質:

- キーは **`(village_id, year_month)` の月次 UNIQUE**。`year_month` は月初日（`LocalDate`）。
- `generateForVillage` は **UPSERT**（`findByVillageIdAndYearMonth(...).orElseGet(...)` → 同一行を上書き。`VillageChronicleService.java:124-136`）。月次バッチは毎月再生成しうる。
- 保持項目は **月次の post_count / new_member_count / topic_1〜3**。**コメント欄・凍結フラグ・配信状態・ラグ・週次対応行は無い**。

**流用しない理由（改ざん不可要件との矛盾）:**

1. **改ざん不可 vs UPSERT** — 村史は設計上「再生成で上書きされる可変レコード」。マスター要件①「凍結＝以後書き換え不可」と真っ向から対立する。村史をダイジェスト保存に使うと、翌月バッチや再生成で**配信済みの値が変わりうる**（＝改ざん防止が破れる）。
2. **週次に対応行が無い** — 村史は月次のみ。週次ダイジェストの置き場が存在しない。
3. **1号＝1ライフサイクル（集計→凍結→ラグ→配信）を持てない** — 村史は状態機械を持たない。

> **したがって**: **凍結ダイジェストは新規「号（issue）テーブル」に snapshot として保存する**（§4.2）。**ただし集計ロジックは村史のものを流用する**（§5）。村史エンティティ自体は本戦役で変更しない（月次サマリの参照 UI として存続）。

### 4.2 号テーブル `village_newsletter_issues`【案Y 確定】

「集計→凍結→ラグ→配信」を **1つの号** として持つ。**新規テーブルは `UuidV7Entity` 継承・論理削除・クロスドメインFK禁止（CLAUDE.md 原則6・3・1）**。案Y の pull 層（ためる/公開一覧）として、ブログを金型に **`title` / `visibility`** を持たせる（タグは別表 §4.7）。

```sql
-- 【案Y 確定】DDL 概形（Flyway 版番号は実装時に採る。§13）
CREATE TABLE village_newsletter_issues (
    id                  BINARY(16)   NOT NULL,               -- UUIDv7（原則6）
    village_id          BINARY(16)   NOT NULL,               -- FK張らない・同一ドメインだがアプリ整合（原則1/2）
    newsletter_id       BINARY(16)   NULL,                   -- どの設定に紐づく号か（village_newsletters.id）。号外は NULL
    frequency           VARCHAR(20)  NULL,                   -- WEEKLY / MONTHLY（既存 enum を流用。EXTRA では NULL）
    issue_type          VARCHAR(20)  NOT NULL,               -- REGULAR / EXTRA（号外の判別はこちら。frequency enum は拡張しない）
    status              VARCHAR(20)  NOT NULL,               -- AGGREGATED→FROZEN→PUBLISHED→CANCELED
    -- ▼ pull 層（案Y・ためる/公開一覧）
    title               VARCHAR(200) NOT NULL,               -- 号のタイトル（既定は「YYYY年MM月 村だより」等の自動生成。村長が編集可）
    visibility          VARCHAR(30)  NOT NULL DEFAULT 'VILLAGE_MEMBERS',  -- 村内公開ラダー（§4.7.2）。VILLAGE_MEMBERS / PUBLIC
    -- 集計対象期間（凍結時に確定）
    period_start        DATETIME     NOT NULL,

    scheduled_publish_at DATETIME    NULL,                   -- 配信予定（ラグの終端）
    published_at        DATETIME     NULL,                   -- 実配信時刻

    digest_post_count       INT      NOT NULL DEFAULT 0,
    digest_new_member_count INT      NOT NULL DEFAULT 0,
    digest_festival_count   INT      NOT NULL DEFAULT 0,     -- §5.3（採否は §14 Q1）

    digest_topic_2_count INT         NOT NULL DEFAULT 0,
    digest_topic_3_name  VARCHAR(100) NULL,
    digest_topic_3_count INT         NOT NULL DEFAULT 0,
    -- ▼ 村長コメント（ダイジェストとは別欄・凍結後も編集可・楽観ロック §4.4）。号外では本文本体。
    headman_comment      TEXT        NULL,
    comment_updated_by   BIGINT      NULL,                   -- user_id（FK張らない・原則1）
    comment_updated_at   DATETIME    NULL,
    -- ▼ 閲覧数（ビューランキングの前提・§4.8）。原子的 UPDATE でインクリメント（@Version 非経由）
```

**snapshot 方式が改ざん不可を保証する仕組み【提案】:**

- 集計・凍結時に **その時点の集計値を `digest_*` カラムへ複写** する（村史や元テーブルを後から読み直さない）。
- Service 層で **`status = FROZEN` 以降 `digest_*` への setter 経路を設けない**。凍結後に集計値を更新しようとする操作は `BusinessException`（新エラーコード `NEWSLETTER_ISSUE_ALREADY_FROZEN`）で拒否する。
- コメント欄（`headman_comment`）は凍結後も編集可（要件②）だが、これは **ダイジェスト本体とは別カラム** なので snapshot の不変性を侵さない。

> **snapshot（denormalize）を選ぶ理由**: 元テーブル（投稿・メンバー・祭）は後から追加・論理削除されうるため、「配信時に再集計」すると値がぶれる＝改ざん防止が破れる。列に焼き付ければ、元データが動いても配信済みの号は永久に同じ値を返す。JSON 1 カラムでなく個別カラムにするのは、UI での参照と番人テストの検証を容易にするため（村史と同じ設計思想）。

### 4.3 集計日・配信日の持ち方【提案】

現行の週次=金曜/月次=月末ハードコード（`VillageNewsletterDispatchBatchService.java:65,82-89`）を設定制へ。**`VillageNewsletterEntity` にカラムを追加**する（新テーブルにしない — frequency×村で1行という既存モデルにそのまま乗る）。

```sql
-- 【提案】village_newsletters への ALTER（Expand。既存行は移行時にデフォルト充填）
ALTER TABLE village_newsletters
  ADD COLUMN aggregate_day  TINYINT UNSIGNED NULL,   -- WEEKLY:1-7(月=1)  MONTHLY:1-28, 0=月末
  ADD COLUMN dispatch_day   TINYINT UNSIGNED NULL,   -- 同上
  ADD COLUMN dispatch_hour  TINYINT UNSIGNED NOT NULL DEFAULT 18;  -- 配信時刻（UTC時, 0-23）
```

**型設計の要点:**

- **frequency が weekly/monthly を判別する** ため、`aggregate_day` / `dispatch_day` の意味は frequency により解釈する（曜日 or 日付）。専用カラムを頻度別に分けない（列数を抑え、frequency 切替時も同じ列を再利用）。
- **月末** は月ごとに日数が違う（28〜31）ため固定日で表せない。**`0` を「月末」の番兵値** とする（`CHECK` は MySQL 8 で有効。`aggregate_day BETWEEN 0 AND 31`）。実行時に `today.lengthOfMonth()` で解決する（既存の月末判定ロジック `today.getDayOfMonth() != today.lengthOfMonth()` と同じ考え方）。
- **月次で 29〜31 を選ばせない**（2月に飛ばない事故を防ぐ）。UI では月次の集計/配信日を **1〜28 + 「月末」** に限定する（§9）。
- **デフォルト値（移行時）**: 既存挙動を保存するため WEEKLY は `dispatch_day=5`（金）、MONTHLY は `dispatch_day=0`（月末）。集計日デフォルトは §14 Q3 でラグ既定を確定後に決める（暫定案: WEEKLY 集計=月曜、MONTHLY 集計=月末の数日前 or 月末同日）。

> **代替案（不採用）**: `aggregate_day_of_week` / `aggregate_day_of_month` を別カラムで持つ案。frequency で常に一方が NULL になり冗長。番兵値 `0=月末` の方が列数が少なく整合が取りやすい。ただし「番兵値はマジックナンバー」という批判はあるため、Java 側は `DispatchDay` 値オブジェクト or ヘルパで `0→月末` 解決を一元化する。

### 4.4 コメントの同時編集 — 楽観ロック【提案】

村長と長老が同時にコメントを編集しうる。`village_newsletter_issues.version`（`@Version`）で楽観ロックし、**衝突時は 409 Conflict**（`NEWSLETTER_ISSUE_VERSION_CONFLICT`）。FE はリロードを促す。

> 既存 `VillageChronicleEntity` / `VillageNewsletterEntity` も `@Version` を持つ（`VillageChronicleEntity.java:82-84` 等）ので、同じ作法を踏襲する。

### 4.5 送信ログの拡張【提案】

【確認済み】`VillageNewsletterSendLogEntity` は集計値のみで **どの号を配信したかの参照が無い**。号モデル導入に合わせ **`issue_id BINARY(16) NULL`** を追加（Expand、既存行は NULL 可）。これで「号→配信結果」を辿れる。**per-user の配信ログは作らない**（大規模時に行が爆発するため。成否は集計カウントのみ。既存方針を踏襲）。

| 原則2（CASCADE同一ドメイン内のみ） | `village_id`/`newsletter_id` は同一 village ドメイン。DDL では FK を張らずインデックスのみ（既存村テーブル群と同じ作法。`VillageMatchRecruitRepository` コメント参照） |
| 原則3（論理削除） | `village_newsletter_issues.deleted_at` |
| 原則5（@Transactional はドメイン内） | 集計・凍結・コメント保存は village ドメイン内で完結。配信（notification 越境）は §7 の方式で分離 |
| 原則6（UUIDv7） | 新規 `village_newsletter_issues` は `UuidV7Entity` 継承・`BINARY(16)` |

### 4.7 タグ（案Y の pull 層・村ドメイン内・UUIDv7）【案Y 確定】

マスターの「タグ付けして見やすく」を、**ブログのタグを金型に村ドメイン内で新規に持つ**（ブログの `blog_tags`/`blog_post_tags` は Long キーで流用不可＝§3A.3。よって村専用の UUIDv7 テーブルを新設）。

#### 4.7.1 タグ2テーブル【案Y 確定】

```sql
-- 村ごとのタグマスタ（村内で定義。ブログの BlogTagEntity を金型に UUIDv7 で新設）
CREATE TABLE village_newsletter_tags (
    id           BINARY(16)  NOT NULL,                        -- UUIDv7（原則6）
    village_id   BINARY(16)  NOT NULL,                        -- 村スコープ（FK張らない・原則1）
    name         VARCHAR(50) NOT NULL,
    color        VARCHAR(7)  NOT NULL DEFAULT '#6B7280',      -- #RRGGBB（ブログ既定色に倣う）
    sort_order   INT         NOT NULL DEFAULT 0,
    deleted_at   DATETIME    NULL,
    created_at   DATETIME    NOT NULL,
    updated_at   DATETIME    NOT NULL,
    version      BIGINT      NOT NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uk_vnt_village_name (village_id, name),        -- 村内でタグ名一意
    KEY idx_vnt_village (village_id, sort_order)
);

-- 号×タグの中間表（両側 UUIDv7＝Long 壁なし。ブログの blog_post_tags と違い村ドメイン内で完結）
CREATE TABLE village_newsletter_issue_tags (
    issue_id     BINARY(16)  NOT NULL,                        -- → village_newsletter_issues.id（同一ドメイン）
    tag_id       BINARY(16)  NOT NULL,                        -- → village_newsletter_tags.id（同一ドメイン）
    created_at   DATETIME    NOT NULL,

    KEY idx_vnit_tag (tag_id)                                 -- タグ→号の逆引き（公開一覧のタグ絞り込み）

```

- **Long 壁を越えない**: 両表とも UUIDv7・村ドメイン内で完結。ブログの可視性 Resolver・課金連結には一切触れない（案X との決定的な差）。
- **タグ CRUD** は HEADMAN / ELDER（既存 `requireHeadmanOrElder` 流用）。号へのタグ付けはコメント編集と同じ権限。
- 中間表は同一ドメイン CASCADE 可（`issue_id`/`tag_id` とも village ドメイン。原則2）。実 DDL では既存村テーブル群に倣い FK 非付与＋インデックスでアプリ整合とする（`VillageMatchRecruitRepository` コメントの作法）。

#### 4.7.2 公開ラダー `visibility`【案Y 確定】

号の公開範囲は **村ドメイン内の最小ラダー**（ブログの多段ラダー＋ペイウォールは持ち込まない＝ADHD-UX でシンプルに）:

| 値 | 意味 | 閲覧可能者 |
|---|---|---|
| `VILLAGE_MEMBERS`（既定） | 村内限定 | 村メンバー（＋掲示板可視性に従う。§8） |
| `PUBLIC` | 一般公開 | ログイン済みなら誰でも（全村横断の公開一覧に出る。§8・§14 Q6） |

> **enum を独自に持つ理由**: ブログの `Visibility`（`cms` パッケージ・Long 前提・ペイウォール連結）を村が import すると案X 相当の結合が生じる。村ドメイン専用の `VillageNewsletterVisibility{ VILLAGE_MEMBERS, PUBLIC }` を新設し、cms とは疎結合に保つ。将来 SUPPORTERS 等へ広げる余地は残すが MVP は2値。

### 4.8 閲覧数の記録（ビューランキングの前提）— F10.8 PV基盤の流用可否【案Y 確定】

Q6 の「ビューランキング」には各号の閲覧数が要る。既存の **F10.8 ページビュー解析基盤**（PVビーコン→`page_view_logs`→`page_view_daily_stats`）を流用できるか実コードで精査した。

#### 4.8.1 結論: F10.8 は流用しない（§3A と同じ UUID/Long 壁＋目的不一致）【確認済み】

| 障害 | 実コード根拠 |
|---|---|
| **content_id が Long** | `PageViewLogEntity.contentId` は `Long`（`page_view_logs.content_id BIGINT UNSIGNED`・`PageViewLogEntity.java:58-59`）。ビーコン DTO `PageViewBeaconRequest.contentId` も `Long`（`PageViewBeaconRequest.java:45-46`）。集計インデックス `idx_pvl_scope_content(scope_type, scope_id, content_id)` と `PageViewLogRepository.findTopContent` の projection `long getContentId()` も Long。**号 ID は UUID(BINARY16) なので格納できない**（案X・通知基盤と同じ壁）。 |
| **scope に VILLAGE 無し** | `PageViewScopeType` は `TEAM` / `ORGANIZATION` の2値のみ（`PageViewScopeType.java:16-21`）。`scopeId` も Long。村（UUID）スコープに対応するには scope 種別・認可述語（`AccessControlService.isMember`）の拡張が要る。 |
| **目的不一致（認可）** | `PageViewAnalyticsAccessGuard.requireScopeMember` は閲覧数の**読み取りをスコープメンバー／SYSTEM_ADMIN に限定**し、非メンバーは 404 秘匿（`PageViewAnalyticsAccessGuard.java:52-60`）。これは team/org 運営者向けの解析。**Q6 は「一般ユーザーが公開号のランキングを見る」公開ディスカバリ**で、対象読者が真逆。 |
| **読み取り API 粒度不足** | 単一コンテンツの view 数をピンポイント取得する API は無く、常に「スコープ全体 analytics の topContent 上位10件」としてのみ返る（`TeamAnalyticsController` / `PageViewAnalyticsService.buildTopContent`）。号単位ランキングには不足。 |

> content_id を BINARY(16) に拡張する案は、パーティション済み高書き込みテーブル＋日次集計＋ネイティブクエリ＋インデックス＋projection の全経路改修になり、**案X と同格の別軍議相当**。Q6 のためだけに負う価値はない。

#### 4.8.2 採用: ブログ自身の `viewCount` 前例に倣う最小計測【案Y 確定】

【確認済み】ブログは PV基盤とは別に、記事エンティティに **単純な閲覧カウンタ** を持つ（`BlogPostEntity.viewCount` Integer・`incrementViewCount()`）。号もこれに倣い、**`village_newsletter_issues.view_count` 列（§4.2）を公開詳細表示時にインクリメント**する。

- **UUID ネイティブ・村ドメイン内で完結**（PV基盤の Long/scope 壁を一切踏まない）。
- **ランキング** = `WHERE visibility='PUBLIC' AND status='PUBLISHED' ORDER BY view_count DESC`（`idx_vni_public_ranking` 使用）。
- **インクリメントは原子的 UPDATE**（`UPDATE village_newsletter_issues SET view_count = view_count + 1 WHERE id = ?`）で行い、**`@Version` 楽観ロックを経由しない**。理由: エンティティ read-modify-write にすると、村長のコメント/タグ編集（`version` を上げる）と閲覧カウントが衝突して lost update / 不要な 409 を生む。カウンタは別 UPDATE 文で version を触らず加算する（ブログの `incrementViewCount()` は entity 経由だが、公開閲覧は高頻度なので号では原子 UPDATE を推奨）。
- **重複除外は MVP では行わない**（ランキングは相対順位なので素の総閲覧数で十分）。将来、匿名 cookie `mnsft_vid`（F10.8 が既に発行・permitAll）で unique 化する余地は残す（§14 参考）。
- 閲覧計測の入口は **公開号詳細 API**（`GET /api/v1/newsletter/public/{issueId}`・§8.2）。`VILLAGE_MEMBERS` 号の村内閲覧はカウントしない（公開ランキングの母数は公開閲覧のみ）。【要確認】村内一覧の閲覧をカウントに含めるかは実装時に確認（推奨: 公開閲覧のみ計上でランキングの公平性を保つ）。

## 5. 集計ロジック（村史との共通化・期間可変）

### 5.1 現行集計の実体【確認済み】

`VillageChronicleService.generateForVillage`（`VillageChronicleService.java:101-151`）は月次固定で4項目を集計:

| 項目 | 集計元 | メソッド |
|---|---|---|
| 投稿数 | 掲示板＋タイムライン | `bulletinThreadRepository.countByVillageIdAndCreatedAtBetween` + `timelinePostRepository.countByVillageIdAndCreatedAtBetween` |
| 新メンバー数 | 村メンバーシップ | `membershipRepository.countByVillageIdAndJoinedAtBetween` |
| TOP3 トピック | 掲示板スレタイトル | `bulletinThreadRepository.findTitlesByVillageIdAndCreatedAtBetween` → `extractTop3Topics`（package-private・再利用可） |

期間は `from = monthFirstDay.atStartOfDay()` / `to = monthFirstDay.plusMonths(1).atStartOfDay()` の **`[from, to)` 半開区間**。

### 5.2 期間可変への共通化【提案】

村史の月次固定を、**任意の `[periodStart, periodEnd)` を受け取る集計器** に一般化する。

```java
// 【提案】共通集計器（village ドメイン内）
public record NewsletterDigestSnapshot(
    int postCount, int newMemberCount,
    int festivalCount, int meetupCount, int recruitCount,   // §5.3（採否 §14 Q1）
    List<TopicCount> top3Topics) {}

// VillageChronicleService の集計本体を period 引数化して切り出す（または新 DigestAggregator に集約）
NewsletterDigestSnapshot aggregate(UUID villageId, LocalDateTime periodStart, LocalDateTime periodEnd);
```

**方針:**

- `extractTop3Topics` は既に純関数（package-private）。**そのまま流用** する（重複実装しない。CLAUDE.md「動くものと同じパターン適用」）。
- 村史の月次生成は `aggregate(villageId, 月初, 翌月初)` を呼ぶ薄いラッパへ寄せられる（**任意**。村史をリファクタするかは §14 Q4 の恒久保存方針とセットで判断。最小変更なら村史はそのまま残し、集計器のみ新設して両者が同じ private ロジックを呼ぶ）。
- 週次の期間は **前号の `period_end` 〜 今回の集計時刻**（初回は集計日から遡って7日）。号テーブルに `period_start/period_end` を持つ理由（§4.2）。

### 5.3 集計対象に お祭り/寄合/募集 を含めるか【提案・要マスター判断 §14 Q1】

マスターは「活動全部」を希望。【確認済み】対象エンティティと期間集計の可否:

| 活動 | エンティティ | 期間キー候補 | 現状の count メソッド |
|---|---|---|---|
| お祭り | `VillageFestivalEntity`（`starts_at`/`ends_at`/`created_at`/`deleted_at`） | 開催期間 or 作成 | **無し（新設要）** |
| 寄合 | `VillageMeetupEntity`（`created_at`/`confirmed_date`/`deleted_at`） | 作成 | **無し（新設要）** |
| 募集 | `VillageMatchRecruitEntity`（`created_at`/`match_date`/`deleted_at`） | 作成 | **無し（新設要）**（`countByVillageIdAndCategoryIdAndDeletedAtIsNull` はあるが期間版は無い） |

**提案:** 各リポジトリに `countByVillageIdAndCreatedAtBetweenAndDeletedAtIsNull(...)` を新設し、**期間内に新規作成された件数** を集計する（「その週/月に立った祭・寄合・募集の数」＝活動の活発さの指標）。開催日基準（`starts_at`/`match_date`）にすると未来日イベントの扱いが複雑になるため、**MVP は作成日基準** を推奨。

> **要マスター判断（§14 Q1）**: 3種を集計に含めるか。含める場合、指標は「作成件数」でよいか（開催件数ではなく）。**推奨: 含める・作成件数基準**。

## 6. ライフサイクル／バッチ設計【提案】

現行の「配信バッチ1本（FRI/月末ハードコード）」を、**集計・凍結バッチ** と **配信バッチ** の2本に分離する。両者とも **毎日1回定時起動し、各村の設定日と今日を突き合わせて対象を選ぶ**（曜日/日付の設定制化のため）。

### 6.1 集計・凍結バッチ（新設）

```
毎日 定時（例 03:00 UTC）:
  for 各 enabled な newsletter 設定:
     if 今日が aggregate_day（曜日 or 日付, 月末番兵0 は lengthOfMonth で解決）:
        period = [前号 period_end もしくは規定の遡り, 今]
        snapshot = aggregate(villageId, period)         # §5
        issue = new Issue(status=FROZEN, digest_*=snapshot, scheduled_publish_at=次の dispatch_day)
        save(issue)                                     # 以後 digest_* は不変
        audit(VILLAGE_NEWSLETTER_ISSUE_FROZEN)          # 新イベント §7.4
```

- **冪等性**: 同一村×頻度×period_start は UNIQUE（§4.2）。二重起動でも1号（既存なら skip）。ShedLock 併用（既存バッチと同じ `@SchedulerLock`）。
- 1村失敗しても次村へ（既存 `dispatchByFrequency` の try/catch パターン踏襲。`VillageNewsletterDispatchBatchService.java:106-114`）。

### 6.2 配信バッチ（既存を改修）

```
毎日 定時（例 18:00 UTC・dispatch_hour 尊重）:
  for status=FROZEN かつ 今日が dispatch_day の issue:
     受信者 = membership.findActiveUserSubjectIdsByVillageId(villageId) − opt-out    # 既存ロジック流用
     body = 凍結ダイジェスト + (headman_comment があれば追記)                          # 手間ゼロ既定
     NotificationHelper.notifyAllPreAuthorized(受信者, ..., actionUrl=/villages/{uuid}/newsletter/issues/{issueId}, ...)  # §7
     issue.status = PUBLISHED; issue.published_at = now
     sendLog.save(issue_id=issue.id, recipient/success/failure)   # §4.5
     newsletter.last_sent_at = now
     audit(VILLAGE_NEWSLETTER_SENT)                                # 既存イベント流用
```

- **手間ゼロ既定（要件③）**: コメントの有無で分岐せず、**FROZEN 号は配信日に必ず飛ぶ**。コメントがあれば連結、無ければダイジェスト単体。村長の操作は不要。
- 既存 `dispatchSingleNewsletter` の「受信者抽出→opt-out除外→送信ログ→監査」骨格を **そのまま活かし**、`deliverToUser` を §7 の実配信へ差し替える。

> **現行コードとの重要な差分（食い違い記録・§15）**: 既存の月次配信は「月末18:00」ハードコードだが、既存の **村史生成は「翌月1日03:00 JST」**（`VillageChronicleBatchService.java:47`）。つまり現状は「月末に配信しようとしても、その月の村史はまだ生成されていない」時系列矛盾がある。本設計の集計・凍結バッチ分離はこの矛盾も解消する（配信日より前に必ず集計・凍結する）。

## 7. 配信設計（NotificationHelper 接続・型の壁の回避）

### 7.1 接続点【確認済み】

`NotificationHelper.notifyAllPreAuthorized`（`NotificationHelper.java:235-271`）を使う。**理由**: 受信者は「村メンバー − opt-out」で **呼び出し側で確定済み（事前認可済み）** なので、`canView` 可視性フィルタを通さない版が適切（`notifyAll` は `filterAccessibleRecipients` で村外可視性を誤判定しうる）。ループ内 try/catch で **1件失敗しても全体継続**（`NotificationHelper.java:244-253`）＝マスター要件「1件失敗で全体停止しない」を満たす。

### 7.2 型の壁と回避策【確認済み → 提案】

【確認済み】型の不一致:

- `NotificationEntity.sourceId` = **`Long`**（`NotificationEntity.java:60`）／`scopeId` = **`Long`**（同 :66）。だが **村ID は `UUID`**。→ Long に UUID を入れられない。
- `NotificationScopeType`（`NotificationScopeType.java:6-17`）は **TEAM / ORGANIZATION / PERSONAL / SYSTEM / FRIEND_TEAM / FRIEND_FOLDER / COMMITTEE**。**VILLAGE が無い。**
- 村ドメインは現状 `NotificationHelper` を **一切使っていない**【確認済み（village 配下に import 無し）】。つまり村通知の routing 前例がゼロ＝グリーンフィールド。

【提案】**回避策（enum を弄らずに配線する）:**

| 通知フィールド | 設定値 | 理由 |
|---|---|---|
| `notificationType` | `"VILLAGE_NEWSLETTER"`（String） | 種別は文字列なので自由 |
| `sourceType` | `"VILLAGE_NEWSLETTER"`（String） | 同上。`NotificationSourceTypeMapper` に未登録なので可視性 fail-soft 通過（が、そもそも PreAuthorized 版はフィルタを通さない） |
| `sourceId` | **`null`** | UUID を Long に載せられない。`notifyAllPreAuthorized` は sourceId を絞り込みに使わないので null で問題なし |
| `scopeType` | **`SYSTEM`**（または `PERSONAL`） | VILLAGE が無いため。号の帰属は actionUrl で表現 |
| `scopeId` | **`null`** | 同上 |
| `actionUrl` | **`"/villages/{villageUuid}/newsletter/issues/{issueUuid}"`** | 村UUID・号UUIDはここに載せる（String 500 まで。`NotificationEntity.java:68-69`）。タップで号詳細へ遷移 |
| `title` / `body` | ダイジェスト要約（200/1000 上限） | `NotificationEntity` の title=200・body=1000 制限に収める。全文は actionUrl 先で表示 |
| `actorId` | 配信は system → `null`、号外は投稿村長 user_id | — |

> **enum に VILLAGE を足さない理由**: `NotificationScopeType` は横断 enum で、`@Enumerated(STRING)` の DB 値・可視性 Resolver・FE 表示など波及が広い（memory `feedback_openapi_nested_schema_name_collision` 系のリスク）。本戦役のスコープを膨らませないため、**actionUrl 方式で回避** し、VILLAGE scope の正式追加は将来課題として起票する（§14 参考）。

### 7.3 チャネル方針【提案】

- **アプリ内通知＋PWA Push のみ**（`NotificationHelper`→`NotificationDispatchService` の稼働済み経路）。
- **メールは初手で入れない**（別系統で重い）。将来 `VillageNewsletterSendRequestedEvent` を発行してメール展開する余地は残す（既存 TODO コメント `deliverToUser` の方針と一致。`VillageNewsletterDispatchBatchService.java:183-188`）。

### 7.4 監査ログ・送信ログ【提案】

- 既存 `VILLAGE_NEWSLETTER_SENT` を配信時に記録（既存流用）。
- **新イベント追加**【提案】: `VILLAGE_NEWSLETTER_ISSUE_FROZEN`（凍結時）・`VILLAGE_NEWSLETTER_COMMENT_SAVED`（コメント保存時）・`VILLAGE_NEWSLETTER_EXTRA_SENT`（号外配信時）を `AuditEventType`（`AuditEventCategory.VILLAGE`）へ追加。【確認済み】現行は `VILLAGE_NEWSLETTER_SENT` / `VILLAGE_NEWSLETTER_OPT_OUT` / `VILLAGE_CHRONICLE_GENERATED` のみ（`AuditEventType.java:265-273`）。
- 送信ログは §4.5 の `issue_id` 付きで号単位に紐づく。

### 7.5 越境（原則5）の扱い【提案】

village バッチが notification ドメインの `NotificationHelper` を呼ぶのは **クロスドメイン**。既存 `deliverToUser` の TODO は「イベント駆動が理想」とするが、**MVP は `NotificationHelper` を直接注入**（他ドメインでも一括通知は Helper 直呼びが定着している前例に倣う）。`@Transactional` は **village 側の DB 更新（issue.status/send_log）と notification 呼び出しを分離** し、通知失敗が village トランザクションを巻き込まないようにする（通知は best-effort、号の PUBLISHED 化は確定）。将来のイベント駆動化を TODO として明記する。

| `PUT  /newsletter/issues/{issueId}/visibility` | HEADMAN / ELDER | 号の公開範囲切替（`VILLAGE_MEMBERS`↔`PUBLIC`。§4.7.2） |

### 8.2 村だより広場（村横断・公開の発見面・`/villages`）【Q6 確定】

Q6 の御裁可により、公開号（`visibility=PUBLIC` かつ `status=PUBLISHED`）を **村の検索画面 `/villages` の「村だより広場」セクション** に集め、**「新着」「ビューランキング」の2軸** で発見できる場にする。

| メソッド / パス | 権限 | 用途 |
|---|---|---|
| `GET /api/v1/newsletter/public?sort=latest` | ログイン済み（村メンバーでなくてよい） | 公開号を **published_at 降順**（新着）で一覧（`idx_vni_public_latest` 使用） |
| `GET /api/v1/newsletter/public?sort=views` | 同上 | 公開号を **view_count 降順**（ビューランキング）で一覧（`idx_vni_public_ranking` 使用） |
| `GET /api/v1/newsletter/public/{issueId}` | 同上 | 公開号の詳細。表示時に `view_count` を原子インクリメント（§4.8）。PUBLIC 以外は 404 秘匿 |

- 一覧はページング（`Paginator` 前提・§9.4）。`sort` は enum `latest` / `views`（既定 `latest`）。
- **認可の要点**: 村内の号一覧/詳細（§8.1・「村史」面）は **掲示板と同じ**（`VillageBulletinAccessService.checkVillageBulletinViewAccess`。ダイジェストは掲示板由来トピックを含むため掲示板可視性に従う。`VillageChronicleService.java:164-165` の作法）。**村だより広場は `visibility=PUBLIC` の号のみ** を返し、`VILLAGE_MEMBERS` の号は絶対に混ぜない（漏洩防止）。PUBLIC 以外への直アクセスは **404 で存在秘匿**（IDOR 対策・募集と同じ作法）。
- **閲覧数の計上は公開号詳細の表示時のみ**（§4.8）。村内閲覧はランキング母数に含めない（公平性）。
- コメント・タグ・公開範囲の編集は `requireHeadmanOrElder`（既存 `VillageNewsletterService.java:205-212` を流用。BAN/退村を除く現役判定込み）。
- OpenAPI 型再生成（`npm run generate:types`）を同一 PR で行う（CLAUDE.md 型管理）。

## 10. 号外の設計【提案】

**定期便とは別経路**。ダイジェストを **持たない** 号（`issue_type=EXTRA`）。

- `POST /newsletter/extra`（HEADMAN/ELDER）: body = 自由記述テキスト。

- `digest_*` は全て0/NULL、`headman_comment` に本文を格納（または専用 `extra_body` を使わず headman_comment を再利用）。

- 監査 `VILLAGE_NEWSLETTER_EXTRA_SENT`。
- **MVP に含めるかは §14 Q5**（推奨: 定期便を先行し、号外は第2弾でも可）。

## 11. 受け入れ条件（AC）

> **BE契約テストは MockMvc 経由必須**（`TEST_CONVENTION.md §3.1.1`・Bean直呼び禁止）。**実 MySQL Testcontainers**・**日時は `LocalDateTime` を bind**（文字列リテラル禁止・TZ境界事故回避。memory `feedback_it_fixture_datetime_tz_bind`）。各 AC は試練で red に落とせる粒度。

### 11.1 集計・凍結

- **AC-01**: 集計・凍結バッチ実行後、対象村に `status=FROZEN` の号が1件生成され、`digest_post_count` が期間内の掲示板＋タイムライン投稿数と一致する（Testcontainers に投稿を LocalDateTime bind で仕込み検証）。
- **AC-02**: 凍結済み号の `digest_*` を更新しようとする操作が `NEWSLETTER_ISSUE_ALREADY_FROZEN`（あるいは更新経路が存在しない）で拒否される＝**改ざん不可**。
- **AC-03**: 同一村×頻度×期間で集計バッチを二度走らせても号は1件（冪等・UNIQUE）。
- **AC-04**: TOP3 トピックが `extractTop3Topics` と同じ結果（既存ロジック流用の回帰）。
- **AC-05**（§14 Q1 が「含める」の場合）: 期間内に作成した祭/寄合/募集の件数が `digest_festival_count`/`digest_meetup_count`/`digest_recruit_count` に反映される。

### 11.2 コメント

- **AC-06**: HEADMAN がコメントを保存でき、`headman_comment`/`comment_updated_by`/`comment_updated_at` が更新される（MockMvc `PUT .../comment`）。
- **AC-07**: 一般村人のコメント保存は 403（`MODERATION_FORBIDDEN`）。
- **AC-08**: 古い version でのコメント保存は 409（`NEWSLETTER_ISSUE_VERSION_CONFLICT`・楽観ロック）。
- **AC-09**: 凍結後もコメントは編集できる（コメントは snapshot 不変性の対象外）。

### 11.3 配信（手間ゼロ既定・fault isolation）

- **AC-10**: コメント **無し** で配信日を迎えた FROZEN 号が **ダイジェスト単体で自動配信** され、`status=PUBLISHED`・send_log が1件・`issue_id` が紐づく（村長操作ゼロ）。
- **AC-11**: コメント **有り** の号は「ダイジェスト＋コメント」を本文に含めて配信。
- **AC-12**: 配信対象から opt-out 済みユーザーが除外される（既存 opt-out 流用の回帰）。
- **AC-13**: 受信者1名への配信が例外を投げても、他受信者への配信と号の PUBLISHED 化は継続する（`notifyAllPreAuthorized` の継続性・failure_count 加算）。
- **AC-14**: 配信通知の `scopeType` が既存 enum 値（SYSTEM 等）で、`actionUrl` に村UUID・号UUIDが載る（型の壁回避の契約テスト）。

### 11.4 タグ・公開一覧（案Y の pull 層）

- **AC-15**: HEADMAN がタグを作成・号にタグ付けでき、`GET /newsletter/issues?tagId=` でタグ絞り込み一覧が返る（村ドメイン UUIDv7・Long 壁なしの回帰）。
- **AC-16**: 号の `visibility` を `PUBLIC` に切り替えた PUBLISHED 号のみが `GET /api/v1/newsletter/public` に現れ、`VILLAGE_MEMBERS` の号は **絶対に混ざらない**（漏洩防止・MockMvc）。
- **AC-17**: 村だより広場・公開詳細は村メンバーでないログインユーザーからも見えるが、`VILLAGE_MEMBERS` 号の直 ID アクセスは 404 秘匿（IDOR）。
- **AC-20**: 公開号詳細 `GET /api/v1/newsletter/public/{issueId}` 表示で `view_count` が原子インクリメントされ、`?sort=views` の一覧が view_count 降順、`?sort=latest` が published_at 降順で並ぶ（Testcontainers・ランキング回帰）。村内閲覧（§8.1）では view_count が増えない。

### 11.5 号外（§14 Q5 が「MVP に含む」の場合）

- **AC-18**: HEADMAN の `POST /newsletter/extra` が EXTRA 号を作成し即時配信する。ダイジェストは空（`digest_*`=0）・本文は `headman_comment`。
- **AC-19**: 一般村人の号外投稿は 403。

## 15. 設計書と実コードの食い違い（記録）

実コード確認で判明した、現状の不整合・注意点:

1. **【重大】配信タイミングと集計タイミングの時系列矛盾**: 既存の月次配信は **月末18:00 UTC**（`VillageNewsletterDispatchBatchService.java:82-89`）だが、既存の月次統計（`VillageChronicle`・本節での「旧・村史」）生成は **翌月1日03:00 JST**（`VillageChronicleBatchService.java:47`）。つまり「月末に配信しようとしても、その月の統計はまだ無い」。現状 `deliverToUser` がプレースホルダなので表面化していないが、統計を配信本文に使う前提だと破綻していた。**本設計の集計・凍結バッチ分離（§6）がこの矛盾を根治する。**
2. **配信は現状ノーオペ**: `deliverToUser` は `log.debug` のみ（§1.1）。ニュースレターは「オンにしても何も飛ばない」状態。マスターの実機発見と一致。
3. **`NotificationScopeType` に VILLAGE 無し・`sourceId`/`scopeId` は Long**: 村ID（UUID）を通知に直接載せられない（§7.2）。村ドメインは通知基盤を未使用のため前例ゼロ。
4. **村史はコメント欄・凍結・週次対応・状態機械を持たない**（§4.1）。改ざん不可要件と UPSERT 性が矛盾するため、凍結ダイジェストの保存には流用不可。集計ロジックのみ流用する。
5. **送信ログに号参照が無い**（`VillageNewsletterSendLogEntity` は集計値のみ。§4.5）。号モデル導入時に `issue_id` を足す必要がある。
6. **既に opt-out / send_log / 監査イベントは実装済み**（タスク記述の「内容テーブル無し」は正しいが、opt-out・送信ログ・監査は既存）。②はこれらを流用でき、新規実装は「号・コメント・集計日設定・実配信配線」に集中できる。
7. **ブログ（CMS）は成熟機能だが Long スコープ・村軸なし**（§3A.3）: `BlogPostEntity` は `BaseEntity` 継承の Long 主キー、スコープ列は全て Long、`villageId` も VILLAGE 系 `PostType` も無い。タグ中間表は Long 複合 PK、F00 可視性 Resolver は Long content-id、公開フィードは team/org routing のみ。→ 村（UUID）をブログ本体に通すのは通知基盤と同種の UUID/Long 壁を越える手術になる。`Visibility` に `PUBLIC` は存在するため「公開一覧に出す」こと自体は概念的に可能。
8. **ブログ本文は自由編集**（`BlogPostEntity.update` が `body` を上書き・§3A.4）。改ざん不可の凍結ダイジェスト要件と対立するため、案X ではダイジェストを別領域に隔離する追加設計が要る。案Y（snapshot 列）なら衝突しない。
