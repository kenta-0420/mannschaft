## 1. 概要・背景

【確認済み】村の行事3機能は、いずれも「予定を立てて表示する」までは実装済みだが、**立てた後に村人が集い・語らい・記録を残す導線が無い**。

## 3. 機能① 行事→村フィード自動還流＋通知

### 3.1 目的

行事が「立った／近づいた／確定した／始まった」タイミングで、村のタイムラインに**システム名義の投稿**を自動生成し、村人へ通知する。村人はタイムラインを見るだけで村の行事の動きを把握でき、タップで各行事へ遷移できる。

### 3.2 システム名義投稿の表現【提案・要 Flyway ALTER】

【確認済み】`TimelinePostEntity` の投稿者構造は次のとおりで、**システム投稿を表す仕組みが無い**:

- 投稿者は `Long userId`（`@Column(nullable=false)`・列名 `userId`）。`author_user_id` という列は**存在しない**。
- 投稿主体は `PostedAsType postedAsType`（USER/TEAM/ORGANIZATION のみ・**SYSTEM 無し**）＋ `Long postedAsId`。
- `String authorRealNameSnapshot`（`@Column(name="author_real_name_snapshot", length=100)`・**NULL 許容**）。
- システム投稿フラグ（`isSystem` 等）は**存在しない**。

**採用案: `timeline_posts` に「システム投稿種別」列を1本足し、`user_id` を NULL 許容へ緩める**【提案】。

```sql
-- 【提案】timeline_posts への ALTER（timeline ドメインの変更。Flyway 版番号は §13 で確定）
ALTER TABLE timeline_posts
  MODIFY COLUMN userId BIGINT NULL,                         -- システム投稿は投稿者ユーザー無し
  ADD COLUMN system_post_type VARCHAR(40) NULL;            -- NULL=通常投稿 / 非NULL=システム自動投稿の種別
```

- `system_post_type` が非 NULL の行が**システム自動投稿**。値は村ドメイン enum `VillageEventNotificationType`（§3.4）の `.name()` を格納する（`EVENT_CREATED` 等）。
- システム投稿では `userId = NULL`・`postedAsType = NULL`・`authorRealNameSnapshot = NULL`。**表示名は i18n キー `village.systemPost.authorName`（「村の行事案内」）** を FE で解決して出す（実名スナップショットに日本語を焼き付けない＝多言語対応）。
- `scope_type = VILLAGE`・`scope_village_id = 当該村UUID`・`scope_id = 0`（既存 VILLAGE 投稿の作法）。
- **なぜ `user_id` を緩めるか（根治治療）**: システム投稿に架空のユーザー ID を割り当てると、その ID がユーザー一覧・メンション・監査で「幽霊ユーザー」として振る舞い、退会匿名化（原則4）の対象からも漏れる。列を NULL 許容にして「投稿者不在＝システム」を素直に表現するのが根治。既存行はすべて `userId` 非 NULL のままなので後方互換（§13 の Expand 方針）。
- **表示・一覧クエリへの影響**: `userId NULL` を許すことで、投稿者を JOIN 前提にしている一覧・DTO 組立が NPE を起こさないよう、システム投稿は**投稿者解決をスキップ**する分岐を timeline 側に入れる（`system_post_type != null` なら i18n 表示名を使う）。この分岐の実装は timeline ドメイン側で行う（§15 Wave 分割）。

> **代替案（不採用）**: `PostedAsType` に `SYSTEM` を足す案。`PostedAsType` は投稿主体（USER/TEAM/ORG）の enum で、既存の可視性・フォワード・friend 系ロジックが3値前提。ここへ SYSTEM を混ぜると各分岐へ波及する（memory `feedback_openapi_nested_schema_name_collision` 系リスク）。専用の `system_post_type` 列で局所化する方が波及が小さい。

### 3.3 ドメイン越境の作法（原則1・5準拠）【提案】

- 自動投稿は **village ドメイン → timeline ドメインへの越境**。**FK は張らない**（原則1）。`timeline_posts.scope_village_id` は村 UUID を保持するがアプリ層で整合を保証する（既存 VILLAGE 投稿と同じ）。
- village 側は **timeline ドメインの Service メソッドを呼び出す**（Entity を直接 new しない・原則の「ドメイン間はメソッド呼び出し」）。timeline 側に **`createSystemVillagePost(UUID villageId, VillageEventNotificationType type, String title, String body, String actionUrl)`** 相当のメソッドを新設する【提案】。
- `@Transactional` の越境（原則5）: 行事の状態更新（village トランザクション）と自動投稿・通知（timeline/notification 越境）は**分離**する。自動投稿・通知は best-effort とし、失敗しても行事の状態遷移は確定させる（通知失敗で行事作成が巻き戻らない）。将来のイベント駆動化（`VillageEventOccurredEvent`）を TODO として記録する。

### 3.4 発火タイミングと通知種別【提案】

村ドメイン独自 enum **`VillageEventNotificationType`** を新設し、**核 `NotificationType` は改変しない**（横断 enum への波及回避。ニュースレター §7 の前例と同方針）。

| enum 値 | 発火契機 | 注入点（実装済みコードへの結線先） | 自動投稿 | 通知 |
|---|---|---|---|---|
| `EVENT_CREATED` | 歳時記／祭／寄合を**作成**したとき | 各 `Village*Service` の create メソッド末尾 | ○ | ○ |
| `EVENT_UPCOMING` | 行事の**開催前日**（接近） | 新設の接近通知バッチ（§3.5） | ○ | ○ |
| `MEETUP_CONFIRMED` | 寄合が **CONFIRMED** に遷移したとき | `VillageMeetupService` の日程確定メソッド | ○ | ○ |
| `FESTIVAL_STARTED` | 祭が **SCHEDULED→ACTIVE** に遷移したとき | `VillageFestivalStateTransitionBatchService.transitionToActive`【確認済み・注入点】 | ○ | ○ |

【確認済み】`VillageFestivalStateTransitionBatchService`（15分ごと・`transitionToActive`/`transitionToEnded` が `entity.setStatus(...)+save`）は現状**監査ログのみで通知・イベント発行が無い**。ここが `FESTIVAL_STARTED`（§3）・`FESTIVAL_ENDED`（③の村史編纂・§5.5）の自然な注入点。

### 3.5 接近通知（EVENT_UPCOMING）は前日1回のみ【既定・PR レビューで変更可】

- **開催前日に1回だけ**通知する。開催当日・数日前など複数回は送らない。
- **新設バッチ**: 毎日定時（例 09:00 JST）に、翌日開催の歳時記／祭／寄合を走査し、**まだ EVENT_UPCOMING 通知を送っていない行事**にのみ自動投稿＋通知する。二重送信防止のため送信済みを記録する（§3.7）。
- **ガードレール整合の根拠**（§9）: 接近通知は**村全体への案内**であって、特定個人への出欠催促ではない。前日1回に絞ることで「個人を追い立てる催促」化を構造的に防ぐ。頻度を上げると「まだ出欠を答えていない人へのリマインド」に接近し、チームとの差別化ガードレール（未回答者を追わない）を侵すため、**前日1回**を既定とする。

### 3.6 通知の配線【提案】

ニュースレター §7 の前例（`notifyPreAuthorized` をループ・文字列種別・`scopeType=SYSTEM`・`sourceId=null`・村 UUID は actionUrl）を踏襲する。

| 通知フィールド | 設定値 | 理由 |
|---|---|---|
| `notificationType` | `VillageEventNotificationType.XXX.name()`（String） | 種別は文字列保存。核 enum を触らない |
| `sourceType` | `"VILLAGE_EVENT"`（String） | 可視性フィルタは PreAuthorized 版で通さない |
| `sourceId` | **`null`** | 行事 UUID を Long `sourceId` に載せられない（型の壁） |
| `scopeType` | **`NotificationScopeType.SYSTEM`** | `NotificationScopeType` に VILLAGE が無い。帰属は actionUrl で表現 |
| `scopeId` | **`null`** | 同上 |
| `actionUrl` | `"/villages/{villageUuid}/{calendar|festival|meetup}/{eventUuid}"` | 村・行事の UUID をここに載せる。タップで各行事へ遷移 |
| `title`/`body` | i18n 由来の要約（200/1000 上限） | `NotificationEntity` の上限に収める |
| `actorId` | **`null`**（システム発火） | — |

- 受信者は **`membershipRepository.findActiveUserSubjectIdsByVillageId(villageId)`**（村の現役 USER メンバー）。opt-out は本書スコープ外（行事通知の opt-out は将来課題・§16 参考）。
- `notifyAllPreAuthorized`（一括版・§NotificationHelper）を使い、1件失敗しても全体継続（ループ内 try/catch）。

### 3.7 二重送信防止・冪等性【提案】

`EVENT_CREATED`/`MEETUP_CONFIRMED`/`FESTIVAL_STARTED` は状態遷移の一度きりの契機なので、遷移メソッド内で1回だけ発火すれば冪等（バッチ再実行でも状態は既に遷移済み）。`EVENT_UPCOMING` はバッチが毎日走るため、**「行事×UPCOMING 送信済み」を記録する軽量テーブル**を設けるか、自動投稿の存在（`system_post_type='EVENT_UPCOMING'` かつ当該行事 actionUrl の投稿が既にある）で判定する。**採用: 軽量な送信済みマーカーを持たず、`timeline_posts` に既に当該行事×UPCOMING のシステム投稿があるかで冪等判定**（テーブル追加を避ける）。詳細は §12 状態遷移で規定。

### 3.8 ニュースレター行事欄との整合【提案・実体は §5.3 側】

ニュースレター設計書 §5.3 は、月次/週次ダイジェストに**祭/寄合/募集の「作成件数」**を含める方針（`digest_festival_count`/`digest_meetup_count`/`digest_recruit_count`・§14 Q1 推奨=含める・作成件数基準）。本書①の自動投稿はこれと**二重計上しない**: 自動投稿は「その時に流れる案内」、ニュースレター行事欄は「期間の作成件数サマリ」で層が異なる（push vs pull）。本書は**集計基準をニュースレター §5.3 の作成件数基準に合わせる**とだけ規定し、**行事欄の集計実体はニュースレター設計書側に置く**（本書では新設しない）。

## 4. 機能② 寄合の後半戦（出欠・コメント・決まったこと・宿題）

### 4.1 目的

【確認済み】寄合は `PLANNING`（候補日投票）→ `CONFIRMED`（`confirmed_date`/`confirmed_time` 確定）→ `CANCELLED` の3状態。CONFIRMED で止まっており、**確定後の「誰が来る・何を話す・何が決まった・誰が何を持ってくる」を管理できない**。ここを埋める。

### 4.2 新規テーブル【提案・すべて UuidV7Entity・BINARY(16)】

#### 4.2.1 出欠 `village_meetup_attendances`

```sql
CREATE TABLE village_meetup_attendances (
    id          BINARY(16)  NOT NULL,                    -- UUIDv7（原則6）
    meetup_id   BINARY(16)  NOT NULL,                    -- → village_meetups.id（同一ドメイン・FK非付与/index）
    user_id     BIGINT      NOT NULL,                    -- 出欠を答えた村人（FK非付与・原則1）
    status      VARCHAR(20) NOT NULL,                    -- GOING / MAYBE / ABSENT
    created_at  DATETIME    NOT NULL,
    updated_at  DATETIME    NOT NULL,
    version     BIGINT      NOT NULL,                    -- @Version
    PRIMARY KEY (id),
    UNIQUE KEY uk_vma_meetup_user (meetup_id, user_id),  -- 1寄合×1村人=1行（upsert）
    KEY idx_vma_meetup (meetup_id)
);
```

- enum `VillageMeetupAttendanceStatus { GOING, MAYBE, ABSENT }`【提案】。
- 出欠は upsert（同一村人の再回答は UPDATE）。**CONFIRMED 状態のみ**受付（§12・PLANNING は候補日投票と住み分け）。

#### 4.2.4 「決まったこと」の持ち方 — 親テーブルに列追加【提案・比較の結論】

「決まったこと」は寄合1件につき1本の自由記述メモで足りる（複数の決議を構造化する要求は無い）。**別テーブルより親 `village_meetups` に `decisions_note TEXT NULL` を1列足す方が軽い**。

```sql
ALTER TABLE village_meetups
  ADD COLUMN decisions_note TEXT NULL;                  -- 決まったこと（幹事が記す自由記述・楽観ロックは既存 version）
```

> **比較（採用＝親列追加）**: 別テーブル `village_meetup_decisions` 案は、決議を複数行で持てる柔軟さがあるが、UI も DB も重くなる（一覧・並び替え・削除の CRUD 一式が増える）。決まったことは「議事メモ1枚」の粒度で十分というのが村の実態（ADHD-UX の入力摩擦ゼロ・シンプル優先）。**親列 `decisions_note` を採用**し、将来「複数決議を構造化したい」需要が出たら別テーブルへ切り出す（後方互換な拡張）。

### 4.3 宿題 TODO の操作権限【御裁可済み既定の明文化】

| 操作 | 誰ができるか | エラー時 |
|---|---|---|
| TODO 作成 | 幹事（`organizer_user_id`）＋村長/長老 | 権限外は `MODERATION_FORBIDDEN` 相当 |
| **手挙げ（claim）** | 村人本人（未割当 TODO を自分に割り当てる） | 既に割当済みは `MEETUP_TODO_ALREADY_CLAIMED`（新規） |

| **手放し（release・未割当へ戻す）** | **本人のみ**（割当済み TODO を自分が手放す） | 他人は拒否 |

- **手挙げ者本人＋幹事のみ完了可**【御裁可済】。割当済み TODO の手放しは**本人のみ**【御裁可済】。
- 幹事は割当・完了を管理できるが、**他人の割当を勝手に手放すことはできない**（手放しは本人の自発的行為に限る）。
- 権限判定は既存 `requireOrganizer(entity, actorUserId)`（幹事）と `requireVillager(villageId, actorUserId)`（村人）を流用し、TODO 単位で assignee 一致を追加チェックする。

## 5. 機能③ お祭りの参加レイヤー（RSVP・実況・村史編纂）

### 5.1 目的

【確認済み】祭は `SCHEDULED → ACTIVE → ENDED`（＋`CANCELLED`）を15分バッチで自動遷移し、`banner_r2_key`（VARCHAR(255)）・`theme_color_hex` を持つ。ここに**参加表明・当日の実況・終了後の記録**を足す。

### 5.2 参加表明 `village_festival_rsvps`【提案・UuidV7Entity】

```sql
CREATE TABLE village_festival_rsvps (
    id           BINARY(16)  NOT NULL,                   -- UUIDv7
    festival_id  BINARY(16)  NOT NULL,                   -- → village_festivals.id（同一ドメイン）
    user_id      BIGINT      NOT NULL,                   -- FK非付与
    status       VARCHAR(20) NOT NULL,                   -- GOING / MAYBE （ABSENT は持たない）
    role_label   VARCHAR(60) NULL,                       -- 役割の自由記述ラベル（例「出店係」「受付」）。NULL=役割なし
    created_at   DATETIME    NOT NULL,
    updated_at   DATETIME    NOT NULL,
    version      BIGINT      NOT NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uk_vfr_festival_user (festival_id, user_id),  -- 1祭×1村人=1行（upsert）
    KEY idx_vfr_festival (festival_id)
);
```

- enum `VillageFestivalRsvpStatus { GOING, MAYBE }`【提案】。**ABSENT は持たない**【御裁可済み既定】。
- **不参加は「無回答」と同じ扱い**（RSVP レコードが無い＝答えていない）。これは §9 ガードレール（欠席率を数えない・未回答者を追わない）を **DB レベルで担保** する設計。ABSENT を保存できないので「欠席者一覧」も「欠席率」も構造的に作れない。

### 5.3 役割分担は v1 自由記述ラベル【御裁可済み既定】

- `role_label` は **VARCHAR(60) の自由記述**。役割マスタ（プルダウン固定値）は持たない。
- **役割マスタは将来拡張として記録**【提案・§16 参考】: 村ごとに「受付／設営／出店」等のマスタを定義してプルダウン化する案は、村の運用が固まってから。v1 は自由入力で摩擦ゼロ。

### 5.4 ACTIVE 中の実況 — 祭タグ選択方式を採用【提案・比較の結論】

開催中（ACTIVE）に村人が投稿した内容を祭に紐付けて「実況」として見せたい。2案を比較する。

| 案 | 概要 | トレードオフ |
|---|---|---|
| **案A（不採用）: `timeline_posts` に `festival_id` 参照列** | 投稿テーブルに祭 UUID 列を足し、祭に紐付く投稿を DB で束ねる | timeline ドメインに村固有の外部参照列が恒久的に混入。同一村ドメイン内でも timeline は別ドメイン（BIGINT・BaseEntity）で、①で既に `system_post_type` を足す上にさらに列追加は timeline を村都合で肥大させる。実況の母数が少ない祭でも全投稿テーブルに列が乗る |
| **案B（採用）: 投稿画面から祭タグを選ぶ→村ドメイン側で紐付けを持つ** | 開催中の祭がある村では投稿 UI に「この祭の実況として投稿」トグルを出し、選ばれた投稿の ID を**村ドメインの中間テーブル `village_festival_live_posts`** に記録する | timeline 本体は無改造。紐付けは村ドメインに閉じる（原則1・越境は ID 参照のみ）。実況が無い祭では中間表に行が増えない |

**採用＝案B**。理由: timeline を村都合で改造しない（①の `system_post_type` 追加で既に最小限の timeline 変更を負っており、これ以上は増やさない）。実況紐付けを村ドメインに閉じることで、将来 timeline をマイクロサービス分割しても村側だけで完結する。

```sql
-- 【提案】祭の実況投稿の紐付け（村ドメイン内・timeline_posts.id を ID 参照で持つ・FK非付与）
CREATE TABLE village_festival_live_posts (
    festival_id      BINARY(16) NOT NULL,                -- → village_festivals.id（同一ドメイン）
    timeline_post_id BIGINT     NOT NULL,                -- → timeline_posts.id（別ドメイン・ID参照のみ・FK非付与・原則1）
    created_at       DATETIME   NOT NULL,
    PRIMARY KEY (festival_id, timeline_post_id),
    KEY idx_vflp_festival (festival_id)
);
```

- 投稿本体は既存 VILLAGE タイムライン投稿（`scope_type=VILLAGE`）。祭タグを付けた投稿だけが `village_festival_live_posts` に登録される。
- 紐付け登録は **ACTIVE 期間中のみ**受け付ける（SCHEDULED/ENDED では実況タグ不可）。
- `timeline_post_id` が BIGINT なのは timeline が BaseEntity（BIGINT）だから【確認済み】。村側 PK は複合自然キー（`festival_id`+`timeline_post_id`）で、行は「祭×投稿」ごとに増えるが**シャーディング対象の村ドメイン内テーブル**なので UUID 化の要否を検討 → **本表は自然キー（両参照 ID の複合）で可**。理由: 独立発番の主キーを必要とせず、参照2本の組が一意。原則6の例外（自然キーが妥当なケース）に該当。§13 で明記。

### 5.5 ENDED 時の村史自動編纂【提案】

【確認済み】`VillageFestivalStateTransitionBatchService.transitionToEnded` が `ACTIVE→ENDED` を実施（現状は監査ログのみ）。ここに**村史（行事アーカイブ）への編纂呼び出しを注入**する。

- 編纂内容 = **祭の基本情報**（title・期間・banner）＋**RSVP 集計**（GOING/MAYBE 各人数・役割ラベルの列挙）＋**紐付き実況投稿の集約**（`village_festival_live_posts` の件数・代表投稿）。
- 編纂先 = §7 の村史（行事アーカイブ）テーブル `village_event_archives` に `source_type=FESTIVAL` の1行を追加。
- 冪等: 同一祭の ENDED 編纂は1回のみ（`village_event_archives` の `(source_type, source_id)` UNIQUE で二重編纂を防ぐ・§7.2）。バッチ再実行でも既存なら skip。
- 越境（原則5）: 編纂は village ドメイン内で完結（RSVP・live_posts の件数集計は村ドメイン。timeline 本文の取得は ID 参照で最小限）。ENDED 遷移トランザクションと編纂を分離し、編纂失敗が状態遷移を巻き戻さない。

## 7. 村史（行事アーカイブ）の新設と定義整理

### 7.1 村史の定義整理【御裁可済＋ニュースレター整合】

「村史」という表示名の指す先を、以下のとおり整理する（ニュースレター §3B との矛盾を防ぐ）。

| 時期 | 「村史」表示名が指すもの | 実体 |
|---|---|---|
| 現状（F17.1） | 月次統計タブ | `VillageChronicleEntity`（`village_chronicles`・投稿数/新メンバー/TOP3） |
| ニュースレター §3B 統合後 | 村だより（号）の村内アーカイブ | `village_newsletter_issues` の号一覧（既存月次統計は「月次村だより」の digest に統合） |
| **本書 F17.2 で追加** | **行事アーカイブ** | **`village_event_archives`（祭/歳時記/寄合の記録）** |

**整理の結論**【御裁可済 決定2】:
- 既存 `VillageChronicle`（月次統計）は、ニュースレター §3B の「村だより」統合で**統計タブとして退場する流れ**にある（月次村だよりの digest に吸収）。
- **本書の行事アーカイブ（`village_event_archives`）が「村史」の表示名とタブを引き継ぐ。** ニュースレターの号アーカイブ（村だより広場）とは**役割分担**する:
  - **村史（本書・行事アーカイブ）** = 祭・歳時記・寄合という**行事の記録**（誰が集い何をしたか）。
  - **村だより／村だより広場（ニュースレター）** = 村長からの**定期便（お知らせ）の積み重ね**。
- 両者は「村の歴史をためる pull 面」という点で近縁だが、**行事の記録** と **便りの記録** で層が異なるため**別テーブル・別タブ**とする。村史タブ（行事アーカイブ）とニュースレターの村だより広場は、村ページ内で並立する。

> **矛盾回避メモ**: ニュースレター §3B は「『村史』の表示名の主は号アーカイブへ移る」と書いている。本書は §3B の「既存月次統計は退場」という方向を尊重しつつ、**空席になる『村史』タブの実体を本書の行事アーカイブが埋める**。すなわち「村史 = 行事の記録」・「村だより広場 = 公開された便りの記録」と役割を分け、両設計書が同じ『村史』名を奪い合わない形に確定する。実装時、村史タブの中身を行事アーカイブにするか号アーカイブにするかは**両戦役の実装順で調整**（先行実装側が村史タブを取り、後発は自分の名で並立タブを足す）。この最終調整は §16 の「要調整」に1点残す。

### 7.2 村史テーブル — 集約テーブル方式を採用【提案・比較の結論】

村史（行事アーカイブ）の持ち方を2案で比較する。

| 案 | 概要 | トレードオフ |
|---|---|---|
| **案I（採用）: 集約テーブル `village_event_archives`** | 祭/歳時記/寄合の記録を、`source_type`＋`source_id`＋`title`＋`summary`＋`archived_at` の**共通形に正規化した1テーブル**へ編纂時に書き込む | 村史タブは1テーブルを新しい順に読むだけ（read が単純・高速）。source ごとの元テーブルが論理削除されても村史は残る（記録の永続性）。編纂時に summary を焼き付けるので元データが動いても村史はぶれない |
| **案II（不採用）: 村史タブが各機能テーブルを read 集約** | 村史タブ表示時に `village_festivals`/`village_calendar_event_logs`/`village_meetups` を横断クエリして時系列マージ | read のたびに3テーブルを UNION・ソートするコストが恒常的にかかる。元行事が論理削除されると村史からも消える（「歴史」なのに消えるのは村史の意味に反する）。祭の RSVP 集約など「編纂時点のスナップショット」を持てない |

**採用＝案I（集約テーブル）**。理由: 村史は「**その時こういう行事があった**」という**確定した記録（スナップショット）**であるべきで、元行事の後日の削除・変更で揺れてはいけない（③の祭編纂が RSVP 集計を焼き付けるのと同じ思想）。read も単純化する。

```sql
CREATE TABLE village_event_archives (
    id           BINARY(16)   NOT NULL,                  -- UUIDv7（原則6）
    village_id   BINARY(16)   NOT NULL,                  -- 村スコープ（FK非付与・原則1）
    source_type  VARCHAR(20)  NOT NULL,                  -- FESTIVAL / CALENDAR_EVENT / MEETUP
    source_id    BINARY(16)   NOT NULL,                  -- 元行事の UUID（ID参照のみ・FK非付与）
    title        VARCHAR(200) NOT NULL,                  -- 編纂時に焼き付けた表題
    summary      TEXT         NULL,                      -- 編纂サマリ（RSVP集計・実況件数等をテキスト化）
    thumbnail_r2_key VARCHAR(255) NULL,                  -- 代表画像（祭バナー等の複写・任意）
    archived_at  DATETIME     NOT NULL,                  -- 編纂時刻
    deleted_at   DATETIME     NULL,                      -- 論理削除（原則3）
    created_at   DATETIME     NOT NULL,
    updated_at   DATETIME     NOT NULL,
    version      BIGINT       NOT NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uk_vea_source (source_type, source_id),   -- 1行事=1村史エントリ（冪等・二重編纂防止）
    KEY idx_vea_village_archived (village_id, archived_at) -- 村史タブ（新しい順）
);
```

### 7.3 編纂の契機【提案】

| source_type | 編纂契機 | 注入点 |
|---|---|---|
| `FESTIVAL` | 祭が ENDED に遷移したとき（自動・§5.5） | `VillageFestivalStateTransitionBatchService.transitionToEnded` |
| `CALENDAR_EVENT` | 年輪（log）が初めて追加されたとき、または年次で（下記） | §6 の log 追加時に「その年の記録あり」を村史へ反映（初回のみ UNIQUE で1行） |
| `MEETUP` | 寄合が CONFIRMED で開催日を過ぎ、決まったこと/コメントが残ったとき（自動・軽量バッチ or 手動編纂） | §12 状態遷移で規定 |

- **祭は自動編纂で確定**（③の主眼）。歳時記・寄合の編纂契機は MVP では**祭を優先**し、歳時記・寄合の村史化は Wave 2 で足してよい（§15）。ただしテーブルは `source_type` で3種を受けられる形で最初から作る（後方互換）。

### 7.4 API【提案】

| メソッド / パス | 権限 | 用途 |
|---|---|---|
| `GET /api/v1/villages/{villageId}/event-archives` | 村人（閲覧・掲示板と同一の閲覧認可） | 村史一覧（`archived_at` 降順・`?sourceType=` 絞り込み可・ページング） |
| `GET /api/v1/villages/{villageId}/event-archives/{archiveId}` | 同上 | 村史エントリ詳細 |

- 村史は**編纂（write）が自動**なので、村人向けは read のみ。運営による訂正・非表示は将来課題（§16 参考）。

## 8. 機能⑤ ご縁スコア表示の廃止＋加入前相性表示

### 8.1 目的

【確認済み】現状の `VillageSerendipityController` は `/serendipity-scores/me`・`/serendipity-scores/ranking` を提供し、村内の「ご縁スコア」を**ランキング表示**する。これは「相性度」を名乗りながら実態は村内交流の累積カウント（`encounter_count`/`interaction_score`）で、**優劣を可視化するゲーミフィケーション**に寄っている。これを廃止し、**加入前の非メンバーが「この村は自分と合いそうか」を掴む「相性のヒント」** に置き換える。

### 8.2 ご縁スコア ランキング表示の廃止【提案】

- **`GET /serendipity-scores/ranking` とランキングウィジェットを廃止**する。
  - 手順: まず **deprecate**（FE からの参照を外し、API に `@Deprecated`／OpenAPI で deprecated 明示）→ 次リリースで**撤去**。段階撤去で既存クライアントの 404 事故を避ける。
- **集計バッチ（`VillageSerendipityBatchService`）・エンティティ（`VillageSerendipityScoreEntity`）は存置**する。理由: これらは**推薦（巡礼・おすすめ村）の内部信号**として価値がある。表示（ランキング）だけをやめ、内部の交流累積は推薦ロジックの材料として生かす。
- `GET /serendipity-scores/me`（自分のスコア）は、相性表示 API（§8.3）へ役割を統合するか、内部用途に限定する（表示からは外す）。

### 8.3 加入前相性表示 API【提案】

```
GET /api/v1/villages/{villageId}/affinity/me
```

- **非メンバーもアクセス可**・**要ログイン**。村への加入を検討している人が「自分と合いそうか」を見るための API。
- **レスポンス（フィールド・型・null 許容）**:

| フィールド | 型 | null | 説明 |
|---|---|---|---|
| `categoryMatch` | boolean | 不可 | 自分の関心カテゴリと村カテゴリが一致するか |
| `sharedVillagerCount` | integer | 不可 | 自分と同じ他村に居る村人の重なり人数。**3人未満は 0 を返す**（§8.4） |
| `sharedVillagersHidden` | boolean | 不可 | 重なりが 3人未満で秘匿された場合 true（FE は「まだ表示できません」を出す） |
| `reasonKeys` | string[] | 不可（空配列可） | 根拠一言の **i18n キー配列**（FE で翻訳。§8.5） |
| `pioneerAppeal` | boolean | 不可 | 小規模村の「先住民アピール」を出すか（総メンバー10人以下・§8.8） |
| `memberCount` | integer | 不可 | 村の総メンバー数（アピール判定の根拠・FE 表示にも流用可） |

- **活動時間帯の重なりは v1 スコープ外**【提案・§16 参考】: 「同じ時間帯に活動している村人が多い」という相性軸は、新規の時間帯集計基盤（各人の投稿・アクセス時刻分布）が必要で本書スコープを超える。将来拡張として記録。

### 8.4 匿名村人重なりは3人未満非表示【御裁可済み既定】

- `sharedVillagerCount` は**3人以上のときのみ実数を返す**。**3人未満は 0＋`sharedVillagersHidden=true`**。
- **理由（プライバシー・§9 ガードレール・`docs/security` 整合）**: 重なりが1〜2人だと「あの村の誰と誰が同じ」と個人特定に接近する。**k-匿名性（k=3）の考え方**で、3人未満は集計値を出さない。誰が重なっているか（村人の identity）は**一切返さない**（人数のみ）。

### 8.5 根拠一言（reasonKeys）と巡礼推薦の共通化【提案】

- 相性の根拠は **文言を焼き付けず i18n キーで返す**（多言語対応・`village.affinity.reason.*`）。例: `village.affinity.reason.categoryMatch`（「あなたの関心と近い村です」）、`village.affinity.reason.sharedVillagers`（「あなたと縁のある村人がいます」）。
- 【確認済み】巡礼推薦 `VillagePilgrimageRecommendationEntity.reason`（VARCHAR(100)）は「推薦理由（カテゴリ一致など）」を持つ。**相性表示の根拠一言と巡礼推薦の理由を同じ i18n キー体系に寄せる**（`village.affinity.reason.*` を両者で共有）。現状 `reason` に文言を直接格納しているなら、**キーを格納して FE で翻訳**する形へ揃える（巡礼側の改修は任意・§15 Wave 2）。

### 8.6 i18n 是正（相性度→村内交流の蓄積）【提案・6ロケール】

【確認済み】`frontend/app/locales/*/village.json` の `village.serendipity.subtitle` は「あなたとの相性度」。実態（村内交流の蓄積・出会いの累積）に合う文言へ**6ロケールすべて**で変更する。

- `village.serendipity.title`「ご縁スコア」→ 表示廃止に伴い、相性表示側の新キー `village.affinity.*` へ移設（`serendipity.*` は内部用途に縮小 or 削除）。
- `village.serendipity.subtitle`「あなたとの相性度」→「村での出会いの積み重ね」等、優劣ではなく交流の蓄積を表す語へ（6ロケール）。
- 新規 `village.affinity.*`（相性表示 UI・根拠一言）を6ロケールに追加（§14）。

### 8.7 認可設計【提案・重要】

- `GET .../affinity/me` は**非メンバーに開く**唯一の村内 API になるため、認可を厳密に設計する:
  - **要ログイン**（匿名は 401）。
  - **村が PUBLIC（誰でも参加可・検索可）のときのみ相性を返す**。承認制／UNLISTED（非公開）村では、非メンバーに村内情報の手掛かりを与えない（404 で存在秘匿 or 相性は返さず「参加後に表示」）。村の公開種別は既存 `VillageEntity` の visibility/type で判定。
  - 返すのは**集計値と i18n キーのみ**。村人の identity・ニックネーム・投稿は一切含めない（§8.4）。
- 実装は既存 `loadActiveVillage` に「PUBLIC 判定」を足したガードを新設（`requireVillager` は非メンバーを弾くので使えない）。

### 8.8 小規模村の「先住民アピール」【マスター発案・採用決定】

小さな村では匿名村人の重なり（§8.4）がそもそも出ない（母数が少ない）。その空白を、**「今なら草創メンバーとして入れる」という誘い文句**で埋める。加入の後押しになるうえ、小規模村への新規流入を促す。

**挙動:**

- **対象**: 閲覧者が**未参加**の村で、村の**総メンバー数が 10人以下**の場合。
- **表示**: 相性表示の枠に「（例）先住民になれます！」のような誘い文句を出す（草創メンバーとして入れることを売りにする）。API は `pioneerAppeal=true`＋`memberCount` を返し、FE が i18n 文言で描画する。
- **プライバシー閾値との関係（併用・置き換えではない）**: 匿名村人重なりの **「3人未満非表示」閾値（§8.4）はそのまま維持**する。小規模村では重なり表示がどのみち出ない（`sharedVillagersHidden=true`）ため、**その空白をこのアピールが補完**する関係である（G4 プライバシーを一切緩めない。人数もカウントも identity も新たに晒さない。出すのは「メンバーが少ない」という事実と誘い文句のみ）。

**しきい値・文言【既定・PR レビューで変更可】:**

- **しきい値 10人**は既定値。PR レビューで変更可（村の規模感に応じて調整）。
- **文言は i18n キー化（6ロケール・§14）**。日本語の文言候補:
  - **既定（採用）**: 「**村の草分けになれます！**」
  - 代替候補: 「開拓者になれます！」／「先住民になれます！」
  - **注記**: マスター発案の原案は「先住民になれます！」だが、「先住民」は**民族的語義（indigenous peoples）に読まれうる**懸念があるため、既定は中立的な **「村の草分けになれます！」** を採用し、代替候補を併記してレビューで最終決定する。
- 認可: `pioneerAppeal` の判定は `GET .../affinity/me` の中で行い、§8.7 の認可（未ログイン 401・PUBLIC 村限定）に従う。参加済みユーザーには出さない（未参加者向けの誘い文句なので、メンバーには `pioneerAppeal=false`）。

**将来拡張（v1 スコープ外・記録のみ）:**

- 草創期に加入したメンバーへの「**草分け**」的な軽い名鑑表示（例: 「開村メンバー」バッジ）。ただし**チーム差別化ガードレール（序列化しない・G3）に抵触しない範囲に留める**: 「早く入った人が偉い」序列や皆勤的な優劣にしない。あくまで「この村を一緒に始めた仲間」という**横並びの記録**に限る。実装するかは別途裁可。

## 9. 機能⑥ 村人ミニプロフィールの所属村一覧

### 9.1 目的

村のメンバー一覧から村人のミニプロフィールを開き、**その村人が（公開設定している範囲で）他にどんな村に居るか**を辿り、村トップへ遷移できるようにする。村人同士の「縁」をたどる導線。

### 9.2 公開トグル列の追加【提案・要 Flyway ALTER＋backfill】

【確認済み】`VillageMembershipEntity`（`village_memberships`）は `subject_type`＋`subject_id` で参加主体を表し（**`user_id` 列は無い**）、公開設定カラムを持たない。ここに公開トグルを足す。

```sql
-- 【提案】village_memberships への ALTER（村ドメイン内）
ALTER TABLE village_memberships
  ADD COLUMN profile_public BOOLEAN NOT NULL DEFAULT FALSE;  -- この村への所属を所属村一覧に公開してよいか
```

**backfill（既存行の初期値）**【提案】:
- 村が **PUBLIC（公開・検索可）** の所属 → `profile_public = TRUE`（既に公開の場に居る所属は公開既定）。
- 村が **承認制／UNLISTED（非公開）** の所属 → `profile_public = FALSE`（非公開の場の所属は既定で伏せる）。
- backfill は Flyway 内で村種別を JOIN して UPDATE（村種別は `villages` テーブルの type/visibility）。**クロスドメインではない**（villages と village_memberships は同一 village ドメイン）。

### 9.3 API【提案】

| メソッド / パス | 権限 | 用途 |
|---|---|---|
| `PATCH /api/v1/villages/{villageId}/memberships/me/profile-visibility` | 村人本人 | 自分のその村所属の公開トグル切替（body: `profilePublic` boolean） |
| `GET  /api/v1/users/{userId}/villages` | 要ログイン＋**閲覧者と対象者が同じ村に所属**（§9.4） | 対象村人の所属村一覧（公開トグル ON かつ村が PUBLIC のもののみ） |

- `GET /users/{userId}/villages` のレスポンス（1件あたり）: `villageId`(UUID)・`villageName`(string)・`villageMonshoUrl`(string/null・村紋の署名URL)・`category`(string/null)。**相手のニックネームは返さない**【御裁可済み既定】。
  - ニックネームを返さない理由: 所属村一覧は「どんな村に居るか」を見せる導線であり、村ごとのニックネーム（村内 identity）を横串で晒すと村の匿名世界が破れる（§9 ガードレール）。村名・村紋・カテゴリ・村ID までに留める。

### 9.4 閲覧権限 — 同じ村の同居者のみ【御裁可済み既定】

- `GET /users/{userId}/villages` は、**閲覧者と対象者が「どこか同じ村」に共に所属している場合のみ**返す（完全公開にしない）。
- 判定: 閲覧者の所属村集合 ∩ 対象者の所属村集合 ≠ ∅ なら許可。空なら 403（or 404 秘匿）。
- 返す村は、そのうえで**対象者が `profile_public=TRUE` に設定 かつ 村が PUBLIC** のものだけ（二重フィルタ）。
- **理由**: 見ず知らずの他人の所属村を誰でも辿れると、村をまたいだ個人追跡（ストーキング）の道具になる。「同じ村で既に縁のある者同士」に閲覧を限定し、`docs/security` の IDOR／プライバシー方針に整合させる。

### 9.5 FE 導線と設定 UI の置き場所【提案・調査済み】

- **導線**: メンバー一覧 `frontend/app/components/villages/members/VillageMembersTable.vue`（起点）→ 村人ミニプロフィール → 所属村一覧 → 村トップ遷移。
- **設定 UI の置き場所**: 【確認済み】既存の類似設定の置き場所を調査した結果:
  - 村内ニックネーム（全村共通）は **`frontend/app/pages/me/village-nickname.vue`**（マイページ配下）。
  - **村ごとの設定**は **`frontend/app/pages/villages/[id]/newsletter-settings.vue`** のように**村ページ配下**にある。
  - 本機能の公開トグルは **`village_memberships`（村ごと）** に紐づく per-village 設定なので、**村ページ配下（村メンバー設定 or 村人ミニプロフィールの自分表示内）に置く**のが既存パターンに整合する。マイページの `village-nickname.vue`（全村共通）とは粒度が異なるため、そこには置かない。
  - 具体的には、村ページのメンバー一覧から開く**自分のミニプロフィールに「この村での所属を公開する」トグル**を配置する（per-village・`PATCH .../memberships/me/profile-visibility` を叩く）。
- `/統一`（PageHeader/SectionCard）・`/手助け`（使い方モーダル）を新規画面に適用（CLAUDE.md「新規ページは/統一と/手助け」）。

## 10. チームとの差別化ガードレール【独立節・全機能に適用】

村は「役職も格式も置いてくる、ゆるい縁の場」（F17.1 §1.1）である。チーム／組織（実名・所属実態・出欠管理の世界）とは**構造的に別物**でなければならない。本書の全機能は以下のガードレールを守る。これは設計原則であり、各機能の DDL・API・UX がこれを侵さないことを §11 受け入れ条件で検証する。

| # | ガードレール | 本書での担保 |
|---|---|---|
| G1 | **未回答者の一覧を出さない** | 出欠・RSVP は「答えた人」しか返さない。誰が答えていないかを列挙する API・画面を作らない |
| G2 | **催促通知をしない** | 接近通知は**村全体への案内・前日1回のみ**（§3.5）。「あなたはまだ出欠を答えていません」型の個人宛リマインドを作らない |
| G3 | **皆勤・欠席率を数えない** | 祭 RSVP は **ABSENT を保存できない**（§5.2）ので欠席率が構造的に作れない。出欠の集計は「来る人数」のみ。皆勤バッジ・出席率ランキングを作らない |
| G4 | **実名世界（チーム/組織）とのリンクを作らない** | 表示は**村ニックネーム**で解決（§4.4/§5.6）。所属村一覧はニックネームすら返さない（§9.3）。timeline 自動投稿は実名スナップショットを焼かない（§3.2） |
| G5 | **参加記録は村ニックネーム世界に閉じる** | 出欠・コメント・TODO・RSVP・年輪・村史のすべてが村内 identity（ニックネーム）で完結し、村外（実名・他チーム）へ漏れない。所属村一覧の横串も「同じ村の同居者のみ・ニックネーム非返却」（§9.4/§9.3） |

- ⑤の相性表示も、**匿名重なりは3人未満非表示・identity 非返却**（§8.4）でこのガードレールに従う。
- ①の自動投稿も**システム名義**（個人を主語にしない）で、特定村人の行動を晒さない。

## 11. 受け入れ条件（AC）

> **BE 契約テストは MockMvc 経由必須**（`TEST_CONVENTION.md`・Bean 直呼び禁止）。**実 MySQL Testcontainers**・**日時は `LocalDateTime` を bind**（文字列リテラル禁止・TZ 境界事故回避。memory `feedback_it_fixture_datetime_tz_bind`）。各 AC は `/試練` でそのまま red に落とせる粒度（正常系＋異常系＋境界）。

### 11.1 機能① 自動還流・通知

- **AC-01**: 歳時記/祭/寄合を作成すると、当該村の `timeline_posts` に `system_post_type='EVENT_CREATED'`・`user_id IS NULL`・`scope_type='VILLAGE'`・`scope_village_id=村UUID` の行が1件生成される。
- **AC-02**: システム投稿の行は `user_id IS NULL` で保存でき、投稿者解決をスキップして i18n 表示名で描画できる（NPE を起こさない）。
- **AC-03**: 祭が `SCHEDULED→ACTIVE` に遷移すると `FESTIVAL_STARTED` の自動投稿＋通知が1回発火する（バッチ再実行で二重発火しない＝状態が既に ACTIVE）。
- **AC-04**: 寄合が `CONFIRMED` に遷移すると `MEETUP_CONFIRMED` の自動投稿＋通知が発火する。
- **AC-05**（境界）: 接近通知バッチは、翌日開催の行事に `EVENT_UPCOMING` を**1回だけ**送る。同日中にバッチが再走しても、既に UPCOMING システム投稿がある行事へは再送しない。
- **AC-06**（異常系）: 通知配線が失敗しても、行事の作成・状態遷移は確定する（通知 best-effort・行事がロールバックされない）。

### 11.2 機能② 寄合の後半戦

- **AC-07**: CONFIRMED 寄合で村人が `PUT .../attendance` を送ると出欠が upsert され、再送で UPDATE される（`(meetup_id,user_id)` UNIQUE）。
- **AC-08**（異常系）: PLANNING 状態で `PUT .../attendance` は `MEETUP_NOT_CONFIRMED` で拒否される。
- **AC-09**: 村人がコメントを投稿でき、一覧が作成日昇順で返る。投稿者本人＋村長/長老のみ削除できる。
- **AC-10**: 未割当 TODO を村人本人が `claim` で自分に割り当てられる。既に割当済みの TODO への claim は `MEETUP_TODO_ALREADY_CLAIMED` で拒否。
- **AC-11**（境界・権限）: TODO の `complete` は**手挙げ者本人＋幹事のみ**成功し、無関係な村人は拒否される。
- **AC-12**（権限）: 割当済み TODO の `release` は**本人のみ**成功し、幹事や他村人は拒否される。
- **AC-13**: 幹事＋村長/長老が `decisions_note` を更新でき、非幹事の一般村人は拒否される。

### 11.3 機能③ お祭りの参加レイヤー

- **AC-14**: 村人が `PUT .../rsvp` で GOING/MAYBE と役割ラベルを登録でき、再送で upsert される。
- **AC-15**（ガードレール G3）: RSVP に ABSENT を送ることはできない（enum に無く 400）。「欠席者一覧」を返す API が存在しない。
- **AC-16**: ACTIVE 中のみ `POST .../live-posts` で実況投稿を紐付けでき、SCHEDULED/ENDED では拒否される。
- **AC-17**: 祭が `ACTIVE→ENDED` に遷移すると `village_event_archives` に `source_type='FESTIVAL'` の村史エントリが1件編纂され、RSVP 集計（GOING/MAYBE 人数）が summary に含まれる。二重編纂されない（`(source_type,source_id)` UNIQUE）。

### 11.4 機能④ 年輪

- **AC-18**: 村人が歳時記に `POST .../logs`（year・photoR2Key・note）を追加でき、同一 year に複数件登録できる。
- **AC-19**: 年輪一覧が year 降順で返り、`photo_r2_key` は署名 URL に解決される（一覧は resolveAll で N+1 なし）。

### 11.5 機能⑤ 相性表示

- **AC-20**: 非メンバーのログインユーザーが PUBLIC 村の `GET .../affinity/me` を叩くと、`categoryMatch`・`sharedVillagerCount`・`reasonKeys` が返る。

- **AC-22**（異常系・認可）: 承認制／非公開村の `GET .../affinity/me` は非メンバーに相性を返さない（404 秘匿 or 「参加後に表示」）。未ログインは 401。
- **AC-23**: `GET .../serendipity-scores/ranking` は deprecated 表明され、FE のランキングウィジェットが撤去されている（集計バッチ・エンティティは存置）。
- **AC-24a**（先住民アピール・§8.8）: 未参加ユーザーが**総メンバー数10人以下**の PUBLIC 村の `GET .../affinity/me` を叩くと `pioneerAppeal=true`＋`memberCount` が返る。
- **AC-24b**（境界）: 総メンバー数が**11人以上**の村では `pioneerAppeal=false`。
- **AC-24c**（境界・対象外）: **参加済み**ユーザーが同じ小規模村を開いても `pioneerAppeal=false`（未参加者向けの誘い文句のため）。
- **AC-24d**（プライバシー併用）: 小規模村でも §8.4 の匿名重なり閾値は維持され、重なり2人以下なら `sharedVillagersHidden=true` のまま（アピールはそれを緩めない）。

### 11.6 機能⑥ 所属村一覧

- **AC-24**: 村人本人が `PATCH .../memberships/me/profile-visibility` で公開トグルを切り替えられる。

## 12. 状態遷移

### 12.1 寄合（meetup）

```
PLANNING ──(候補日確定: confirmed_date セット)──▶ CONFIRMED ──(開催後・記録あり)──▶ [村史編纂: 任意/Wave2]
   │  候補日投票のみ有効                              │  出欠・コメント・決まったこと・宿題が有効
   │  出欠API=MEETUP_NOT_CONFIRMED で拒否              │  候補日投票は締切
   └──────────────(取消)──────────────▶ CANCELLED（全書き込み不可・読み取りのみ）
```

- CONFIRMED 遷移時に `MEETUP_CONFIRMED` 自動投稿＋通知（§3.4）。
- 出欠受付は CONFIRMED 中のみ（§4.5）。

### 12.2 祭（festival）と RSVP の関係

```
SCHEDULED ──(starts_at<=now: 15分バッチ)──▶ ACTIVE ──(ends_at<=now: 15分バッチ)──▶ ENDED
   │ RSVP受付可（事前の参加表明）              │ RSVP受付可＋実況(live-posts)受付可      │ 村史自動編纂（§5.5）
   │ 自動投稿=なし                              │ FESTIVAL_STARTED 自動投稿＋通知(§3.4)   │ RSVP/実況は読み取りのみ
   └──────────────(取消)──────────────▶ CANCELLED（RSVP/実況 締切・編纂しない）
```

- **RSVP は SCHEDULED/ACTIVE で受付**（事前～当日の参加表明）。ENDED/CANCELLED は締切。
- **実況（live-posts）は ACTIVE のみ**受付。
- RSVP は status（GOING/MAYBE）を持つが、**祭の status（SCHEDULED/ACTIVE/ENDED）とは独立**（RSVP status は「参加意思」、祭 status は「開催段階」）。

### 12.3 接近通知（EVENT_UPCOMING）冪等

- 毎日バッチが「翌日開催 かつ 当該行事×UPCOMING のシステム投稿が未存在」の行事にのみ送信（§3.7）。送信＝システム投稿生成が冪等マーカーを兼ねる。

## 15. 非機能・実装方針・Wave 分割

### 15.1 スケール（1000万ユーザー・シャーディング前提）

- **村テーブルは `organization_id` を持たない横断ドメイン**である（村は組織・チームの垣根を越える。F17.1 §1.1）。よって `AbstractTenantAwareRepository`（テナント絞り込み基底）の対象外で、**村スコープは `village_id`（UUID）で絞る**。将来シャーディングするなら `village_id` がシャードキー候補（UUIDv7 は独立発番可＝原則6の狙い）。
- 出欠・RSVP・年輪・実況・村史は**村ごとに行が増える**テーブルなので原則6を適用（UUIDv7）。唯一 `village_festival_live_posts` のみ参照2本の複合自然キー（§5.4・原則6例外）。
- `timeline_posts` は既存 BIGINT（BaseEntity）で据え置き（既存テーブルの ID は変更しない・原則6）。①の ALTER は列追加＋NULL 緩和のみで ID 方式は触らない。

### 15.2 後方互換

- 全 ALTER は Expand（列追加・NULL 化）で既存行・既存クライアントを壊さない。
- ⑤のランキング廃止は deprecate→撤去の2段で既存クライアントの 404 を避ける（§8.2）。

### 15.3 実装方針（モデル）【御裁可済 決定3】

- 本書に基づく実装（`/試練`・`/出陣`）は **Opus 以下のモデルで行う。Fable は使わない。** 認可・越境・改ざん不可（村史 snapshot）の難所は Opus、機械的な CRUD・テーブル追加は Sonnet で可（コスト最適化。CLAUDE.md Dynamic Workflows 方針）。

### 15.4 段階実装（Wave 分割案）【提案】

| Wave | 内容 | 依存 |
|---|---|---|
| **Wave 1** | ②寄合後半戦（出欠・コメント・決まったこと・宿題）＋④年輪。**timeline を触らない純・村ドメイン**で先行（リスク最小・試練が書きやすい） | なし |
| **Wave 2** | ①自動還流（timeline ALTER＋システム投稿＋通知）＋③祭 RSVP・実況・村史編纂＋⑦村史テーブル。**timeline 越境**を含むためガードを厚く | Wave 1（村史テーブルは③が使う） |
| **Wave 3** | ⑤相性表示（ランキング廃止＋affinity API＋i18n是正）＋⑥所属村一覧（membership ALTER＋公開トグル＋FE 導線） | なし（独立・Wave 1/2 と並行可） |

- FE（村史タブ・相性 UI・所属村一覧・出欠/RSVP 画面）は各 Wave の BE 契約確定（`generate:types`）後に着手（memory `feedback_fe_be_parallel_api_boundary_after_generated_types`）。
