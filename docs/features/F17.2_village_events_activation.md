## 3. 機能① 行事→村フィード自動還流＋通知

### 3.1 目的

行事が「立った／近づいた／確定した／始まった」タイミングで、村のタイムラインに**システム名義の投稿**を自動生成し、村人へ通知する。村人はタイムラインを見るだけで村の行事の動きを把握でき、タップで各行事へ遷移できる（遷移先の行事は §3.2 で追加する `source_event_uuid` 列から解決する。actionUrl と冗長だが、DB 側の行事別集約・冪等判定にも同列を使う）。

### 3.2 システム名義投稿の表現【提案・要 Flyway ALTER】

【確認済み】`timeline_posts` の実 DDL（`V4.001__create_timeline_posts_table.sql`）と投稿者構造は次のとおりで、**システム投稿を表す仕組みが無い**:

- 投稿者列は **`user_id BIGINT UNSIGNED NOT NULL`**（同 `:6`。JPA 上は `Long userId`・snake_case 列 `user_id`）。`author_user_id` という列は**存在しない**。
- **既存 FK `fk_timeline_posts_user`**（`user_id` → `users(id)` **ON DELETE CASCADE**・同 `:25`）が張られている。
- 投稿主体は `posted_as_type VARCHAR(20) NOT NULL DEFAULT 'USER'`（同 `:8`。`PostedAsType` = USER/TEAM/ORGANIZATION のみ・**SYSTEM 無し**）＋ `posted_as_id`。
- `String authorRealNameSnapshot`（NULL 許容）。
- システム投稿フラグ（`isSystem` 等）は**存在しない**。

**採用案: `timeline_posts` に「システム投稿種別」列を1本足し、`user_id` を NULL 許容へ緩める**【提案】。

```sql
-- 【提案】timeline_posts への ALTER（timeline ドメインの変更。Flyway 版番号は §13 で確定）
ALTER TABLE timeline_posts
  MODIFY COLUMN user_id BIGINT UNSIGNED NULL,               -- 実列は user_id BIGINT UNSIGNED（userId ではない）。システム投稿は投稿者ユーザー無し
  ADD COLUMN system_post_type   VARCHAR(40) NULL,           -- NULL=通常投稿 / 非NULL=システム自動投稿の種別
  ADD COLUMN source_event_uuid  BINARY(16)  NULL,           -- システム投稿の対象行事UUID（歳時記/祭/寄合のid）。通常投稿はNULL
  ADD INDEX  idx_timeline_posts_sys (scope_village_id, system_post_type, source_event_uuid);  -- UPCOMING冪等判定・行事別集約
```

- **既存 FK `fk_timeline_posts_user`（ON DELETE CASCADE）はそのまま残す**。MySQL の FK は**参照列が NULL の行を制約対象外にする**ため、`user_id` を NULL 許容へ緩めても FK は「NULL 許容 FK」として有効に残る（システム投稿は `user_id IS NULL` なので FK に抵触しない。通常投稿は従来どおり `users(id)` を参照し CASCADE も維持）。FK の張り替え・DROP は不要。
- `system_post_type` が非 NULL の行が**システム自動投稿**。値は村ドメイン enum `VillageEventNotificationType`（§3.4）の `.name()` を格納する（`EVENT_CREATED` 等）。
- **`source_event_uuid` が対象行事の UUID を保持する**【🟠 精査2で追加】: `scope_id` は BIGINT で 0 固定・`content` は自由文なので、**行事 UUID を機械的に読み出せる列が従来無かった**（§3.7 の冪等判定・§3.1 のタップ遷移が読む列が不在だった）。専用列 `source_event_uuid BINARY(16) NULL` を足し、システム投稿はここに対象行事（`village_calendar_events`/`village_festivals`/`village_meetups` の `id`）を格納する。これにより (1) §3.7 の EVENT_UPCOMING 冪等判定が `(scope_village_id, system_post_type, source_event_uuid)` の存在チェックで機械的に行える、(2) §3.1 の「タップで各行事へ遷移」も `source_event_uuid` から遷移先を決められる（actionUrl と冗長だが、DB 検索は列で行う）。**クロスドメインではない**（対象行事は同一 village ドメイン。FK は張らず ID 参照のみ・原則1）。通常投稿は NULL。
- **`posted_as_type` は `NOT NULL DEFAULT 'USER'` のまま維持する**【方針(b)採用】。この列を NULL にする案は実 DDL（`NOT NULL DEFAULT 'USER'`）と矛盾するため採らない。**システム投稿の判定は `system_post_type IS NOT NULL` の一本槍**とし、システム投稿における `posted_as_type` の値（既定 `'USER'` が入る）は**無意味＝読まない**。「投稿主体が誰か」はシステム投稿では概念的に存在しないので、判定・表示ロジックはいずれも `posted_as_type` を参照しない。
- システム投稿では `user_id = NULL`・`authorRealNameSnapshot = NULL`（`posted_as_type` は既定値のまま・無視）。**表示名は i18n キー `village.systemPost.authorName`（「村の行事案内」）** を FE で解決して出す（実名スナップショットに日本語を焼き付けない＝多言語対応）。
- `scope_type = VILLAGE`・`scope_village_id = 当該村UUID`・`scope_id = 0`（既存 VILLAGE 投稿の作法）。
- **なぜ `user_id` を緩めるか（根治治療）**: システム投稿に架空のユーザー ID を割り当てると、その ID がユーザー一覧・メンション・監査で「幽霊ユーザー」として振る舞い、退会匿名化（原則4）の対象からも漏れる。列を NULL 許容にして「投稿者不在＝システム」を素直に表現するのが根治。既存行はすべて `user_id` 非 NULL のままなので後方互換（§13 の Expand 方針）。
- **⚠️ JPA 注釈も対で緩める**【🟠 精査で追加】: 【確認済み】`TimelinePostEntity`（`timeline/entity/TimelinePostEntity.java:52-53`）は `@Column(nullable = false) private Long userId;`。DB 列だけ NULL 許容にして注釈を残すと**宣言と実 DDL が不整合**（`ddl-auto` 検証・スキーマ生成で齟齬、可読性も誤解を招く）。ALTER と同一 PR で **`@Column(nullable = false)` を除去**（`@Column` 属性が他に無ければアノテーションごと削除可）し、`Long userId` を NULL 許容宣言に揃える。**あわせて `systemPostType`（enum）・`sourceEventUuid`（`UUID`・`@Column(columnDefinition="BINARY(16)")` 相当）フィールドを追加**する。
- **表示・一覧クエリへの影響**: `user_id NULL` を許すことで、投稿者を JOIN 前提にしている一覧・DTO 組立が NPE を起こさないよう、システム投稿は**投稿者解決をスキップ**する分岐を timeline 側に入れる（`system_post_type IS NOT NULL` なら i18n 表示名を使う）。この分岐の実装は timeline ドメイン側で行う（§15 Wave 分割）。

> **代替案（不採用）**: `PostedAsType` に `SYSTEM` を足す案。`PostedAsType` は投稿主体（USER/TEAM/ORG）の enum で、`posted_as_type NOT NULL DEFAULT 'USER'` の既存列制約・可視性・フォワード・friend 系ロジックが3値前提。ここへ SYSTEM を混ぜると各分岐へ波及する（memory `feedback_openapi_nested_schema_name_collision` 系リスク）。専用の `system_post_type` 列で局所化する方が波及が小さい。

### 3.3 ドメイン越境の作法（原則1・5準拠）【提案】

- 自動投稿は **village ドメイン → timeline ドメインへの越境**。**FK は張らない**（原則1）。`timeline_posts.scope_village_id` は村 UUID を保持するがアプリ層で整合を保証する（既存 VILLAGE 投稿と同じ）。
- village 側は **timeline ドメインの Service メソッドを呼び出す**（Entity を直接 new しない・原則の「ドメイン間はメソッド呼び出し」）。timeline 側に **`createSystemVillagePost(UUID villageId, VillageEventNotificationType type, String title, String body, String actionUrl)`** 相当のメソッドを新設する【提案】。
- `@Transactional` の越境（原則5）: 行事の状態更新（village トランザクション）と自動投稿・通知（timeline/notification 越境）は**分離**する。自動投稿・通知は best-effort とし、失敗しても行事の状態遷移は確定させる（通知失敗で行事作成が巻き戻らない）。将来のイベント駆動化（`VillageEventOccurredEvent`）を TODO として記録する。

#### 3.3.1 分離の実装方式 — 状態遷移トランザクションの「外」で発火【提案・確定】

> ⚠️ **注入点を誤ると分離が成立しない**。【確認済み】祭の状態遷移は `VillageFestivalStateTransitionBatchService.transitionToActive`/`transitionToEnded`（`:106-127`）が**メソッドレベル `@Transactional`** で、非トランザクションの `runBatch()` ループ本体（`:60-101`）から try/catch 付きで1件ずつ呼ばれる。もし自動投稿・通知・村史編纂をこの `@Transactional` メソッドの**内側**に注入すると、通知/編纂の例外が**行事の状態更新まで巻き戻す**（同一トランザクション）ため、「best-effort 分離」が成立しない。

**確定方針: 自動投稿・通知・村史編纂は `@Transactional` メソッドの外（バッチループ本体側）で、状態遷移のコミット後に発火する。**

- **祭（バッチ経由）**: `runBatch()` のループ内で `transitionToActive(f)`／`transitionToEnded(f)` が**戻った後**（＝そのトランザクションがコミット済みの後）に、続けて自動投稿・通知（③は村史編纂も）を呼ぶ。副作用側の呼び出しも try/catch で囲み、失敗しても次の村・次の祭へ継続する（既存 `runBatch` の1件失敗継続パターンを踏襲）。状態は既にコミット済みなので巻き戻らない。
- **サービス経由の同期発火（`EVENT_CREATED`／`MEETUP_CONFIRMED`）**: 行事の作成・確定は各 `Village*Service` の `@Transactional` メソッド内で行われる。ここでの副作用は **`TransactionSynchronizationManager.registerSynchronization(...)` の `afterCommit()`** に載せて、コミット後に発火する（既存 `VillageUserCleanerEventListener` が `@TransactionalEventListener(AFTER_COMMIT)` + `REQUIRES_NEW` を使う社内前例と同思想）。これにより本体トランザクションのコミット前に副作用が走らず、副作用の失敗が本体を巻き戻さない。
- **2方式の使い分けの理由**: バッチ（祭遷移）は「非トランザクションのループが小トランザクションのメソッドを呼ぶ」構造なので、ループ本体で戻り後に呼ぶのが最も素直（余計な同期登録が不要）。サービス経由（作成・確定）は呼び出し元が `@Transactional` の内側なので、`afterCommit` 同期に載せる。**どちらも「本体コミット後に副作用」という同一原則の実装差**であり、best-effort 分離を保証する。
- **⚠️ 自己呼び出しプロキシの注意**【実装者向け】: 【確認済み】現行 `runBatch()`→`transitionToActive/Ended` は**同一 Bean 内の自己呼び出し**で、Spring AOP プロキシを経由しない。よって `transitionToActive/Ended` のメソッドレベル `@Transactional` は**実質 no-op**（実際のコミット境界は `festivalRepository.save()` 自身のトランザクション）。本設計の結論（「戻り後に発火＝コミット後＝best-effort 分離」）は**この事実の下でも成立する**（save のトランザクションは戻り時点で確定済み）。ただし**副作用側を独立トランザクション（REQUIRES_NEW）にしたい場合、自己呼び出しでは `@Transactional` が効かない**。その場合は (1) 副作用を**別 Bean のメソッドに切り出してプロキシ経由で呼ぶ**、または (2) `TransactionTemplate`（`PROPAGATION_REQUIRES_NEW`）で明示的にトランザクション境界を作る、のいずれかを採ること（同一 Bean 内 `@Transactional` メソッドを自己呼び出しして REQUIRES_NEW を期待する実装は禁止）。

### 3.4 発火タイミングと通知種別【提案】

村ドメイン独自 enum **`VillageEventNotificationType`** を新設し、**核 `NotificationType` は改変しない**（横断 enum への波及回避。ニュースレター §7 の前例と同方針）。

| enum 値 | 発火契機 | 注入点（実装済みコードへの結線先） | 自動投稿 | 通知 |
|---|---|---|---|---|
| `EVENT_CREATED` | 歳時記／祭／寄合を**作成**したとき | 各 `Village*Service` の create メソッド末尾 | ○ | ○ |
| `EVENT_UPCOMING` | 行事の**開催前日**（接近） | 新設の接近通知バッチ（§3.5） | ○ | ○ |
| `MEETUP_CONFIRMED` | 寄合が **CONFIRMED** に遷移したとき | `VillageMeetupService` の日程確定メソッド | ○ | ○ |
| `FESTIVAL_STARTED` | 祭が **SCHEDULED→ACTIVE** に遷移したとき | `VillageFestivalStateTransitionBatchService.transitionToActive`【確認済み・注入点】 | ○ | ○ |

【確認済み】`VillageFestivalStateTransitionBatchService`（15分ごと・`transitionToActive`/`transitionToEnded` が `entity.setStatus(...)+save`）は現状**監査ログのみで通知・イベント発行が無い**。ここが `FESTIVAL_STARTED`（§3）・`FESTIVAL_ENDED`（③の村史編纂・§5.5）の自然な注入点。

### 3.5 接近通知（EVENT_UPCOMING）は前日1回のみ【既定・PR レビューで変更可】

- **開催前日に1回だけ**通知する。開催当日・数日前など複数回は送らない。
- **新設バッチ**: 毎日定時（例 09:00 JST）に、翌日開催の歳時記／祭／寄合を走査し、**まだ EVENT_UPCOMING 通知を送っていない行事**にのみ自動投稿＋通知する。二重送信防止のため送信済みを記録する（§3.7）。
- **`@BatchEndpoint` 付与（E2E 再現手段）**【🟠 精査で追加】: 【確認済み】既存 `VillageFestivalStateTransitionBatchService.runBatch` は `@BatchEndpoint(name="village-festival-state-transition", ...)` を持ち、`BatchEndpointRegistry` 経由で `POST /api/v1/system-admin/batch/{name}/trigger?sync=true`（SYSTEM_ADMIN）から手動キックできる。**本接近通知バッチにも `@BatchEndpoint(name="village-event-upcoming-notice", description="...")` を付与**し、E2E から手動発火できるようにする（前例踏襲・引数なしメソッドで登録可）。
- **ガードレール整合の根拠**（§10）: 接近通知は**村全体への案内**であって、特定個人への出欠催促ではない。前日1回に絞ることで「個人を追い立てる催促」化を構造的に防ぐ。頻度を上げると「まだ出欠を答えていない人へのリマインド」に接近し、チームとの差別化ガードレール（未回答者を追わない）を侵すため、**前日1回**を既定とする。

### 3.6 通知の配線【提案】

ニュースレター §7 の前例（`notifyPreAuthorized` をループ・文字列種別・`scopeType=SYSTEM`・`sourceId=null`・村 UUID は actionUrl）を踏襲する。

### 3.7 二重送信防止・冪等性【提案】

`EVENT_CREATED`/`MEETUP_CONFIRMED`/`FESTIVAL_STARTED` は状態遷移の一度きりの契機なので、遷移メソッド内で1回だけ発火すれば冪等（バッチ再実行でも状態は既に遷移済み）。`EVENT_UPCOMING` はバッチが毎日走るため、**「行事×UPCOMING 送信済み」を記録する軽量テーブル**を設けるか、自動投稿の存在で判定する。**採用: 軽量な送信済みマーカーを持たず、`timeline_posts` に既に当該行事×UPCOMING のシステム投稿があるかで冪等判定**（テーブル追加を避ける）。判定は §3.2 で追加する **`source_event_uuid` 列を使い、`WHERE scope_village_id=? AND system_post_type='EVENT_UPCOMING' AND source_event_uuid=?` の存在チェック**で機械的に行う（§3.2 の `idx_timeline_posts_sys` 複合 index を使用）。**actionUrl 文字列の部分一致に頼らず、専用列で正確に判定できる**（🟠 精査2で `source_event_uuid` を追加した根拠）。詳細は §12 状態遷移で規定。

### 3.8 ニュースレター行事欄との整合【提案・実体は §5.3 側】

ニュースレター設計書 §5.3 は、月次/週次ダイジェストに**祭/寄合/募集の「作成件数」**を含める方針（`digest_festival_count`/`digest_meetup_count`/`digest_recruit_count`・§14 Q1 推奨=含める・作成件数基準）。本書①の自動投稿はこれと**二重計上しない**: 自動投稿は「その時に流れる案内」、ニュースレター行事欄は「期間の作成件数サマリ」で層が異なる（push vs pull）。本書は**集計基準をニュースレター §5.3 の作成件数基準に合わせる**とだけ規定し、**行事欄の集計実体はニュースレター設計書側に置く**（本書では新設しない）。

### 3.9 システム投稿の FE 表示契約【🔴 精査で追加・実機E2E必須】

#### 4.4.1 出欠 upsert の実装方式【提案・確定】

`PUT .../attendance`（および §5.6 の `PUT .../rsvp`）の upsert は以下で確定する:

1. `findByMeetupIdAndUserId(meetupId, userId)`（RSVP は `findByFestivalIdAndUserId`）で既存レコードを検索。
2. **在れば** `status` を更新（`@Version` 楽観ロックで衝突検知）。**不在なら** insert。
3. **並行 insert 競合**（同一村人が二重タップ等で同時に2リクエスト）で UNIQUE 制約（`uk_vma_meetup_user`／`uk_vfr_festival_user`）違反が出た場合は、**`DataIntegrityViolationException` を捕捉して1回だけ再検索→更新にフォールバック**する（冪等リトライ）。結果は 200（新規作成でも既存更新でも「あなたの出欠はこうなった」を返すべき操作なので、201 と 200 を区別せず 200 で統一）。
4. UNIQUE により「1村人×1寄合＝1行」は DB レベルで保証。楽観ロック衝突（別リクエストが先に version を上げた）は稀だが、その場合はリトライで最新 version に載せ直す（ユーザーには最終状態が 200 で返る）。

> upsert を「常に 200・冪等」にするのは、出欠/RSVP が「今の意思を上書きする」性質でリトライ安全なため。作成/更新の区別をクライアントに握らせない（ADHD-UX の摩擦ゼロ）。

### 4.5 PLANNING と CONFIRMED の住み分け【提案】

- `PLANNING`: 既存の**候補日投票**（`village_meetup_votes`）のみ有効。出欠 API は `MEETUP_NOT_CONFIRMED`（新規）で拒否。
- `CONFIRMED`: 出欠・コメント・決まったこと・宿題が有効。候補日投票は締切（既存挙動を維持）。
- `CANCELLED`: すべて読み取りのみ（新規書き込み不可）。

- **役割マスタは将来拡張として記録**【提案・§16 参考】: 村ごとに「受付／設営／出店」等のマスタを定義してプルダウン化する案は、村の運用が固まってから。v1 は自由入力で摩擦ゼロ。

### 5.4 ACTIVE 中の実況 — 祭タグ選択方式を採用【提案・比較の結論】

開催中（ACTIVE）に村人が投稿した内容を祭に紐付けて「実況」として見せたい。2案を比較する。

| 案 | 概要 | トレードオフ |
|---|---|---|
| **案A（不採用）: `timeline_posts` に `festival_id` 参照列** | 投稿テーブルに祭 UUID 列を足し、祭に紐付く投稿を DB で束ねる | timeline ドメインに村固有の外部参照列が恒久的に混入。同一村ドメイン内でも timeline は別ドメイン（BIGINT・BaseEntity）で、①で既に `system_post_type` を足す上にさらに列追加は timeline を村都合で肥大させる。実況の母数が少ない祭でも全投稿テーブルに列が乗る |
| **案B（採用）: 投稿画面から祭タグを選ぶ→村ドメイン側で紐付けを持つ** | 開催中の祭がある村では投稿 UI に「この祭の実況として投稿」トグルを出し、選ばれた投稿の ID を**村ドメインの中間テーブル `village_festival_live_posts`** に記録する | timeline 本体は無改造。紐付けは村ドメインに閉じる（原則1・越境は ID 参照のみ）。実況が無い祭では中間表に行が増えない |

**採用＝案B**。理由: timeline を村都合で改造しない（①の `system_post_type` 追加で既に最小限の timeline 変更を負っており、これ以上は増やさない）。実況紐付けを村ドメインに閉じることで、将来 timeline をマイクロサービス分割しても村側だけで完結する。

```sql
-- 【提案】祭の実況投稿の紐付け（村ドメイン内・timeline_posts.id を ID 参照で持つ・FK非付与）
CREATE TABLE village_festival_live_posts (
    festival_id      BINARY(16) NOT NULL,                -- → village_festivals.id（同一ドメイン）
    timeline_post_id BIGINT     NOT NULL,                -- → timeline_posts.id（別ドメイン・ID参照のみ・FK非付与・原則1）
    created_at       DATETIME   NOT NULL,
    PRIMARY KEY (festival_id, timeline_post_id),
    KEY idx_vflp_festival (festival_id)
);
```

- 投稿本体は既存 VILLAGE タイムライン投稿（`scope_type=VILLAGE`）。祭タグを付けた投稿だけが `village_festival_live_posts` に登録される。
- 紐付け登録は **ACTIVE 期間中のみ**受け付ける（SCHEDULED/ENDED では実況タグ不可）。
- `timeline_post_id` が BIGINT なのは timeline が BaseEntity（BIGINT）だから【確認済み】。村側 PK は複合自然キー（`festival_id`+`timeline_post_id`）で、行は「祭×投稿」ごとに増えるが**シャーディング対象の村ドメイン内テーブル**なので UUID 化の要否を検討 → **本表は自然キー（両参照 ID の複合）で可**。理由: 独立発番の主キーを必要とせず、参照2本の組が一意。原則6の例外（自然キーが妥当なケース）に該当。§13 で明記。

### 5.5 ENDED 時の村史自動編纂【提案】

【確認済み】`VillageFestivalStateTransitionBatchService.transitionToEnded`（`:124-127`・**メソッドレベル `@Transactional`**）が `ACTIVE→ENDED` を実施（現状は監査ログのみ）。ここに**村史（行事アーカイブ）への編纂呼び出しを注入**する。

- 編纂内容 = **祭の基本情報**（title・期間・banner）＋**RSVP 集計**（GOING/MAYBE 各人数・役割ラベルの列挙）＋**紐付き実況投稿の集約**（`village_festival_live_posts` の件数・代表投稿。timeline 側 `deleted_at` 済み投稿は除外・§5.4）。
- 編纂先 = §7 の村史（行事アーカイブ）テーブル `village_event_archives` に `source_type=FESTIVAL` の1行を追加。
- 冪等: 同一祭の ENDED 編纂は1回のみ（`village_event_archives` の `(source_type, source_id)` UNIQUE で二重編纂を防ぐ・§7.2）。バッチ再実行でも既存なら skip。
- **越境（原則5）・注入点**: 編纂は village ドメイン内で完結（RSVP・live_posts の件数集計は村ドメイン。timeline 本文の取得は ID 参照で最小限）。**編纂呼び出しは `transitionToEnded` の `@Transactional` の内側に入れてはならない**（編纂失敗が ENDED 遷移を巻き戻す）。**§3.3.1 の確定方針どおり、`runBatch()` のループ本体で `transitionToEnded(f)` が戻った後（コミット後）に編纂を呼び、編纂側も try/catch で囲んで失敗しても次の祭へ継続する**（状態は既にコミット済みで巻き戻らない）。

### 5.6 API【提案】

`/api/v1/villages/{villageId}/festivals/{festivalId}/...` 配下。

| メソッド / パス | 権限 | 用途 |
|---|---|---|
| `PUT  .../rsvp` | 村人（SCHEDULED/ACTIVE のみ） | 自分の参加表明を upsert（body: `status`, 任意 `roleLabel`）。upsert 方式は §4.4.1 と同じ（冪等・200） |
| `GET  .../rsvps` | 村人（閲覧） | 参加者一覧（村ニックネーム・GOING/MAYBE 別・役割ラベル） |
| `DELETE .../rsvp` | 村人本人（**SCHEDULED/ACTIVE のみ**） | 参加表明の取り消し（レコード削除＝無回答へ戻す）。**ENDED 後は不可**（§12.2） |
| `POST .../live-posts` | 村人（ACTIVE 中のみ） | 実況タグ付き投稿の紐付け登録（body: `timelinePostId`。timeline 側 `deleted_at` 済みは登録不可） |
| `GET  .../live-posts` | 村人（閲覧） | 実況投稿一覧（timeline 側 `deleted_at IS NOT NULL` は除外・§5.5） |

- **`POST .../live-posts` の二重タグ付け**: 同一投稿を同じ祭に二度紐付けようとした場合、`village_festival_live_posts` の PK（`festival_id`+`timeline_post_id`）違反になる。**409 Conflict＋`VILLAGE_102`（`FESTIVAL_LIVE_POST_DUPLICATE`）** を返す（冪等に握りつぶさず、二重登録を明示エラーにする＝対処療法禁止の原則）。

- **`DELETE .../rsvp` が ENDED 後不可な理由**: ENDED 遷移時に村史（`village_event_archives`）へ RSVP 集計を**スナップショット確定**（§5.5）する。確定後に RSVP を消せると、村史の集計値と RSVP テーブルの実数が乖離する（村史は編纂時点の焼き付けなので変わらないが、利用者に「村史では10人なのに今は9人」という不整合を見せうる）。ENDED 後の RSVP は読み取り専用にして、村史スナップショットとの一貫性を保つ。

## 6. 機能④ 歳時記×村史の年輪（去年の様子）

### 6.1 目的

歳時記（年中行事）に、**その年ごとの「様子」（写真・一言メモ）** を積み、詳細画面で「去年の様子」「一昨年の様子」を年降順で振り返れるようにする（年輪＝年ごとの記録の積み重ね）。

### 6.2 新規テーブル `village_calendar_event_logs`【提案・UuidV7Entity】

```sql
CREATE TABLE village_calendar_event_logs (
    id                  BINARY(16)   NOT NULL,           -- UUIDv7（原則6）
    calendar_event_id   BINARY(16)   NOT NULL,           -- → village_calendar_events.id（同一ドメイン）
    year                SMALLINT     NOT NULL,           -- 記録対象の西暦年（例 2026）
    photo_r2_key        VARCHAR(255) NULL,               -- 写真（R2キー・MediaUrlResolver で署名URL化）
    note                VARCHAR(300) NULL,               -- 一言メモ
    created_by_user_id  BIGINT       NOT NULL,           -- FK非付与
    deleted_at          DATETIME     NULL,               -- 論理削除
    created_at          DATETIME     NOT NULL,
    updated_at          DATETIME     NOT NULL,
    version             BIGINT       NOT NULL,
    PRIMARY KEY (id),
    KEY idx_vcel_event_year (calendar_event_id, year)    -- 年降順取得・年絞り込み
);
```

### 6.3 1年1件か複数件か — 複数件を採用【提案・設計判断】

- **1歳時記×1年に複数件を許す**（`(calendar_event_id, year)` に UNIQUE を張らない）。
- **理由**: 「去年の夏祭りの様子」を村人が思い思いに写真＋一言で残せる方が村の実態に合う（1人1枚制限は入力摩擦を生む）。年降順の一覧で「その年の様子（複数枚）」を束ねて見せる。
- 写真は既存の **R2/MediaUrlResolver 方式**【確認済み】に従う（`photo_r2_key` VARCHAR(255)・アップロードは村の紋章／祭バナーと同じ presign 導線・`resolve`/`resolveAll` で署名 URL 化）。一覧は N+1 回避のため `resolveAll` を使う。

### 6.4 API【提案】

`/api/v1/villages/{villageId}/calendar-events/{eventId}/...` 配下。

| メソッド / パス | 権限 | 用途 |
|---|---|---|
| `GET  .../logs` | 村人（閲覧） | 年輪一覧（`?year=` 絞り込み可・既定は year 降順→作成日降順・ページング §13.5） |
| `POST .../logs` | 村人 | 年輪を追加（body: `year`, 任意 `photoR2Key`, 任意 `note`） |
| `DELETE .../logs/{logId}` | 投稿者本人＋村長/長老 | 年輪の論理削除（違反は `VILLAGE_101` `CALENDAR_LOG_FORBIDDEN`） |

- 歳時記詳細に「去年の様子（year 降順）」セクションを追加（FE は歳時記詳細画面に組み込む）。
- **応答フィールド契約（`CalendarEventLogResponse`・2026-07-21 マスター裁定で確定）**: `id` / `calendarEventId` / `year` / **`photoUrl`**（`photo_r2_key` を `MediaUrlResolver` で解決した署名付き GET URL・未設定/解決失敗は `null`・一覧は `resolveAll` で N+1 回避）/ `note` / `createdByUserId` / `createdByDisplayName`（村ニックネーム・実名スナップショット禁止）/ `createdAt`。**生の `photoR2Key` は応答に載せない**（村ドメインの `bannerUrl`/`monshoUrl` と同じ `xxxUrl` 規約・#2355 の r2PublicUrl 根絶方針に準拠）。

## 7. 村史（行事アーカイブ）の新設と定義整理

### 7.1 村史の定義整理【マスター裁定確定 2026-07-21】

「村史」という表示名の帰属は、**2026-07-21 のマスター裁定により確定した**。以下のとおり整理する。

| 時期 | 「村史」表示名が指すもの | 実体 |
|---|---|---|
| 現状（F17.1） | 月次統計タブ | `VillageChronicleEntity`（`village_chronicles`・投稿数/新メンバー/TOP3） |
| **確定（2026-07-21 裁定後）** | **行事アーカイブ** | **`village_event_archives`（祭/歳時記/寄合の記録）** |

**確定の経緯【マスター裁定 2026-07-21】:**
- ニュースレター設計書 §3B（2026-07-17 御裁可）では、「村史」タブを**号アーカイブ（村だより）に差し替える**計画だった。
- しかし **2026-07-21 のマスター裁定により、`§3B の帰属を上書き`し、「村史」の名前とタブは本書の行事アーカイブ（`village_event_archives`）が引き継ぐことに確定した**（本書の決定2を維持・§2 決定2）。
- **号アーカイブ（ニュースレターの号一覧）は「村だより」タブとして提供する**（「村史」の名は使わない）。

**確定した役割分担:**
- **村史（本書・行事アーカイブ・`village_event_archives`）** = 祭・歳時記・寄合という**行事の記録**（誰が集い何をしたか）。**「村史」タブはこれ。**
- **村だより（ニュースレター・`village_newsletter_issues` の号一覧）** = 村長からの**定期便（お知らせ）の積み重ね**。**「村だより」タブとして提供**（村横断の公開発見面は「村だより広場」）。
- 既存 `VillageChronicle`（月次統計）は、ニュースレター §3B の方針どおり月次村だよりの digest に統合されて統計タブとしては退場する（この点は §3B のまま変更なし）。
- 両タブ（村史・村だより）は村ページ内で並立する。**帰属は裁定済みで、実装順による調整は不要**（下記）。

> **裁定により未決は解消**: 従前このセクションには「村史タブの中身を行事アーカイブにするか号アーカイブにするかは実装順で調整」という残置があったが、**2026-07-21 のマスター裁定で「村史＝行事アーカイブ」に確定**したため、その運用調整は不要になった（§16.3 からも削除）。ニュースレター設計書 §3B も本裁定に追従して改訂した（`F17.1_village_newsletter_content_model.md` §3B）。

### 7.2 村史テーブル — 集約テーブル方式を採用【提案・比較の結論】

村史（行事アーカイブ）の持ち方を2案で比較する。

| 案 | 概要 | トレードオフ |
|---|---|---|
| **案I（採用）: 集約テーブル `village_event_archives`** | 祭/歳時記/寄合の記録を、`source_type`＋`source_id`＋`title`＋`summary`＋`archived_at` の**共通形に正規化した1テーブル**へ編纂時に書き込む | 村史タブは1テーブルを新しい順に読むだけ（read が単純・高速）。source ごとの元テーブルが論理削除されても村史は残る（記録の永続性）。編纂時に summary を焼き付けるので元データが動いても村史はぶれない |
| **案II（不採用）: 村史タブが各機能テーブルを read 集約** | 村史タブ表示時に `village_festivals`/`village_calendar_event_logs`/`village_meetups` を横断クエリして時系列マージ | read のたびに3テーブルを UNION・ソートするコストが恒常的にかかる。元行事が論理削除されると村史からも消える（「歴史」なのに消えるのは村史の意味に反する）。祭の RSVP 集約など「編纂時点のスナップショット」を持てない |

**採用＝案I（集約テーブル）**。理由: 村史は「**その時こういう行事があった**」という**確定した記録（スナップショット）**であるべきで、元行事の後日の削除・変更で揺れてはいけない（③の祭編纂が RSVP 集計を焼き付けるのと同じ思想）。read も単純化する。

```sql
CREATE TABLE village_event_archives (
    id           BINARY(16)   NOT NULL,                  -- UUIDv7（原則6）
    village_id   BINARY(16)   NOT NULL,                  -- 村スコープ（FK非付与・原則1）
    source_type  VARCHAR(20)  NOT NULL,                  -- FESTIVAL / CALENDAR_EVENT / MEETUP
    source_id    BINARY(16)   NOT NULL,                  -- 元行事の UUID（ID参照のみ・FK非付与）
    title        VARCHAR(200) NOT NULL,                  -- 編纂時に焼き付けた表題
    summary      TEXT         NULL,                      -- 編纂サマリ（RSVP集計・実況件数等をテキスト化）
    thumbnail_r2_key VARCHAR(255) NULL,                  -- 代表画像（祭バナー等の複写・任意）
    archived_at  DATETIME     NOT NULL,                  -- 編纂時刻
    deleted_at   DATETIME     NULL,                      -- 論理削除（原則3）
    created_at   DATETIME     NOT NULL,
    updated_at   DATETIME     NOT NULL,
    version      BIGINT       NOT NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uk_vea_source (source_type, source_id),   -- 1行事=1村史エントリ（冪等・二重編纂防止）
    KEY idx_vea_village_archived (village_id, archived_at) -- 村史タブ（新しい順）
);
```

### 7.3 編纂の契機【提案】

| source_type | 編纂契機 | 注入点 |
|---|---|---|
| `FESTIVAL` | 祭が ENDED に遷移したとき（自動・§5.5） | `VillageFestivalStateTransitionBatchService.transitionToEnded` |
| `CALENDAR_EVENT` | 年輪（log）が初めて追加されたとき、または年次で（下記） | §6 の log 追加時に「その年の記録あり」を村史へ反映（初回のみ UNIQUE で1行） |
| `MEETUP` | 寄合が CONFIRMED で開催日を過ぎ、決まったこと/コメントが残ったとき（自動・軽量バッチ or 手動編纂） | §12 状態遷移で規定 |

- **祭は自動編纂で確定**（③の主眼）。歳時記・寄合の編纂契機は MVP では**祭を優先**し、歳時記・寄合の村史化は Wave 2 で足してよい（§15）。ただしテーブルは `source_type` で3種を受けられる形で最初から作る（後方互換）。

> **⚠️ CALENDAR_EVENT 粒度の再検討（Wave2 前に確定）**: 現行の `village_event_archives` の UNIQUE は `(source_type, source_id)` で、`source_id` に `calendar_event_id` を入れると **1歳時記につき村史1件**になる。しかし歳時記は毎年繰り返す行事（§6 の年輪は年ごと）なので、村史も**年ごとに1件（「2025年の夏祭り」「2026年の夏祭り」）が自然**。よって CALENDAR_EVENT の村史化を実装する Wave2 の前に、**UNIQUE を `(source_type, source_id, year)` 相当へ拡張**（`village_event_archives` に `source_year SMALLINT NULL` を足し、FESTIVAL/MEETUP は NULL・CALENDAR_EVENT は year を入れる）**を確定する**。FESTIVAL 先行実装時点では `source_year=NULL` で `(source_type, source_id)` 実質一意なので、この拡張は後方互換な ALTER で足せる。**FESTIVAL のみの Wave2 初弾では現行 UNIQUE のままで良く、CALENDAR_EVENT 着手時にこの拡張を行う**（§15 Wave 分割）。

### 7.4 API【提案】

| メソッド / パス | 権限 | 用途 |
|---|---|---|
| `GET /api/v1/villages/{villageId}/event-archives` | 村人（閲覧・掲示板と同一の閲覧認可） | 村史一覧（`archived_at` 降順・`?sourceType=` 絞り込み可・ページング） |
| `GET /api/v1/villages/{villageId}/event-archives/{archiveId}` | 同上 | 村史エントリ詳細 |

- 村史は**編纂（write）が自動**なので、村人向けは read のみ。運営による訂正・非表示は将来課題（§16 参考）。

## 8. 機能⑤ ご縁スコア表示の廃止＋加入前相性表示

### 8.1 目的

【確認済み】現状の `VillageSerendipityController` は `/serendipity-scores/me`・`/serendipity-scores/ranking` を提供し、村内の「ご縁スコア」を**ランキング表示**する。これは「相性度」を名乗りながら実態は村内交流の累積カウント（`encounter_count`/`interaction_score`）で、**優劣を可視化するゲーミフィケーション**に寄っている。これを廃止し、**加入前の非メンバーが「この村は自分と合いそうか」を掴む「相性のヒント」** に置き換える。

### 8.2 ご縁スコア ランキング表示の廃止【提案】

- **`GET /serendipity-scores/ranking` とランキングウィジェットを廃止**する。

### 8.4 匿名村人重なりは3人未満非表示＋バケット化（差分攻撃対策）【御裁可済み既定＋精査反映】

**基本方針（御裁可済み既定）**: 匿名村人の重なりは **3人未満は非表示**。誰が重なっているか（村人の identity）は**一切返さない**（k-匿名性 k=3 の考え方）。

**🔴 差分攻撃（differential attack）の脅威と緩和【精査で追加】:**

- **脅威**: 正確な人数（旧設計の `sharedVillagerCount`）を返すと、攻撃者が**自分の所属村集合を1村ずつ変えて再クエリ**し、返る人数の差分から「どの村の重なりが誰か」を個人へ到達させうる。k=3 の下限だけでは、境界（2→3人）を跨ぐ操作の繰り返しで特定に近づける。
- **緩和1: 正確な人数を返さずバケット化**（採用）: 応答は enum `sharedVillagerBucket` のみ:

  | バケット | 条件（実数 n） | FE 表示（i18n） |
  |---|---|---|
  | `HIDDEN` | n < 3 | 「まだ表示できません」 |
  | `FEW` | 3 ≤ n ≤ 9 | 「数人」 |
  | `MANY` | n ≥ 10 | 「10人以上」 |

  バケット化により、差分クエリで得られる情報が「バケット境界（3・10）をまたいだか」だけになり、個人到達の解像度が大幅に落ちる。
- **緩和2: レート制限**【実装要件・接続点確定】: `GET .../affinity/me` に**レート制限**を課す。【確認済み】既存 Valkey 基盤は認証済み EP 向けに userId キーの前例がある（`AbstractRateLimitFilter.resolveClientKey` が認証時 `"u:{userId}"` を返す。`ScheduleDelegationRateLimitFilter` 等が金型）。これに倣い **`VillageAffinityRateLimitFilter extends AbstractRateLimitFilter`** を新設する:
  - **キー**: `userId + villageId`（`resolveRule`/`shouldNotFilter` で対象パスを `/api/v1/villages/*/affinity/me` に限定し、userId 単独でなく村ごとにカウントして「所属村集合を変えながら同一村を叩く」差分攻撃を村単位で捕捉）。
  - **SecurityConfig 登録**: `FilterRegistrationBean` でサーブレット自動登録を無効化し、**`.addFilterAfter(villageAffinityRateLimitFilter, JwtAuthenticationFilter.class)`** で JWT 認証の後段に差し込む（SecurityContext に userId が入った後・既存の認証済みフィルタ群と同位置）。
  - **既定レート**: **30回/分**（既定・PR レビューで変更可）。通常の閲覧（村を見て相性を確認）には十分で、数百回の差分クエリは弾ける水準。
  - **超過時**: `429 Too Many Requests`（既存フィルタの応答に同じ）。
- **緩和3: 監査ログ**【実装要件】: 相性クエリを**監査記録**する（`AuditEventType.VILLAGE_AFFINITY_QUERIED`・§16.2）。所属村集合を頻繁に変えながら同一村の相性を何度も引く異常パターンを事後検知できるようにする。
- **理由（プライバシー・§10 ガードレール G4・`docs/security` 整合）**: 重なりが1〜2人だと「あの村の誰と誰が同じ」と個人特定に接近する。バケット化＋レート制限＋監査の3層で、k=3 の名目だけでなく**差分攻撃に対する実効的な緩和**を担保する。

### 8.5 根拠一言（reasonKeys）と巡礼推薦の共通化【提案】

- 相性の根拠は **文言を焼き付けず i18n キーで返す**（多言語対応・`village.affinity.reason.*`）。例: `village.affinity.reason.categoryMatch`（「あなたの関心と近い村です」）、`village.affinity.reason.sharedVillagers`（「あなたと縁のある村人がいます」）。
- 【確認済み】巡礼推薦 `VillagePilgrimageRecommendationEntity.reason`（VARCHAR(100)）は「推薦理由（カテゴリ一致など）」を持つ。**相性表示の根拠一言と巡礼推薦の理由を同じ i18n キー体系に寄せる**（`village.affinity.reason.*` を両者で共有）。現状 `reason` に文言を直接格納しているなら、**キーを格納して FE で翻訳**する形へ揃える（巡礼側の改修は任意・§15 Wave 2）。

**`reasonKeys` 付与条件の真理値表【提案・確定】:**

| categoryMatch | sharedVillagerBucket | pioneerAppeal | 付与される reasonKeys |
|---|---|---|---|
| true | 任意 | 任意 | `reason.categoryMatch` を含む |
| 任意 | `FEW` または `MANY` | 任意 | `reason.sharedVillagers` を含む |
| 任意 | 任意 | true | `reason.pioneer` を含む |
| false | `HIDDEN` | false | **空配列 `[]`**（根拠なし。FE は根拠セクションを描画しない） |

- 各行は独立に評価し**和集合**を取る（例: categoryMatch=true かつ bucket=MANY なら `[reason.categoryMatch, reason.sharedVillagers]`）。

### 8.7 認可設計【提案・重要】

`GET .../affinity/me` は**非メンバーに開く**唯一の村内 API になるため、認可を厳密に設計する。開放条件を**実3軸で確定**する【確認済み・既定/PRレビューで変更可】。

【確認済み】`VillageEntity` の関連軸は3つ:
- `visibility`（`VillageVisibility { PUBLIC, UNLISTED }`・検索可否。PUBLIC=検索結果に出る / UNLISTED=検索非表示・URL 直アクセスのみ）
- `join_policy`（`VillageJoinPolicy { FREE, APPROVAL }`・参加方式。FREE=即時参加 / APPROVAL=申請承認制）
- `bulletin_visibility`（`VillageBulletinVisibility { PUBLIC, MEMBERS_ONLY }`・掲示板可視性。相性 API の開放判定には使わない）

**開放条件の確定【既定・PR レビューで変更可】:**

| 条件 | 挙動 |
|---|---|
| `visibility = PUBLIC`（`join_policy` は不問＝FREE でも APPROVAL でも開放） | 相性を返す |
| `visibility = UNLISTED` | **常に 404 で存在秘匿**（非メンバーに村の存在の手掛かりを与えない） |
| 未ログイン | 401 |

- **`join_policy` を不問にする理由**: 承認制（APPROVAL）の村でも、検索に出る（PUBLIC）以上「申請して入るか」を検討する非メンバーは正当に存在する。相性表示は**その申請動機付け**に有効なので、APPROVAL でも開放する。一方 **UNLISTED は「そもそも見つからないべき村」**なので、非メンバーには存在ごと秘匿する（404）。
- 返すのは**バケット化した集計値と i18n キーのみ**（§8.4）。村人の identity・ニックネーム・投稿は一切含めない。
- 実装は既存 `loadActiveVillage` に「`visibility=PUBLIC` 判定」を足したガードを新設（`requireVillager` は非メンバーを弾くので使えない）。UNLISTED は `VILLAGE_099`（`AFFINITY_NOT_PUBLIC_VILLAGE`）ではなく **404 応答**で秘匿する（存在秘匿を優先）。

### 8.8 小規模村の「先住民アピール」【マスター発案・採用決定】

小さな村では匿名村人の重なり（§8.4）がそもそも出ない（母数が少ない）。その空白を、**「今なら草創メンバーとして入れる」という誘い文句**で埋める。加入の後押しになるうえ、小規模村への新規流入を促す。

**挙動:**

- **対象**: 閲覧者が**未参加**の村で、村の**総メンバー数が 10人以下**の場合。
- **表示**: 相性表示の枠に「（例）先住民になれます！」のような誘い文句を出す（草創メンバーとして入れることを売りにする）。API は `pioneerAppeal=true`＋`memberCount` を返し、FE が i18n 文言で描画する。
- **プライバシー閾値との関係（併用・置き換えではない）**: 匿名村人重なりの **「3人未満非表示」＋バケット化（§8.4）はそのまま維持**する。小規模村では重なり表示がどのみち出ない（`sharedVillagerBucket=HIDDEN`）ため、**その空白をこのアピールが補完**する関係である（G4 プライバシーを一切緩めない。人数もバケットも identity も新たに晒さない。出すのは「メンバーが少ない」という村の規模＝公開情報と誘い文句のみ）。

**しきい値・文言【既定・PR レビューで変更可】:**

- **しきい値 10人**は既定値。PR レビューで変更可（村の規模感に応じて調整）。
- **文言は i18n キー化（6ロケール・§14）**。日本語の文言候補:
  - **既定（採用）**: 「**村の草分けになれます！**」
  - 代替候補: 「開拓者になれます！」／「先住民になれます！」
  - **注記**: マスター発案の原案は「先住民になれます！」だが、「先住民」は**民族的語義（indigenous peoples）に読まれうる**懸念があるため、既定は中立的な **「村の草分けになれます！」** を採用し、代替候補を併記してレビューで最終決定する。
- 認可: `pioneerAppeal` の判定は `GET .../affinity/me` の中で行い、§8.7 の認可（未ログイン 401・PUBLIC 村限定）に従う。参加済みユーザーには出さない（未参加者向けの誘い文句なので、メンバーには `pioneerAppeal=false`）。

**将来拡張（v1 スコープ外・記録のみ）:**

- 草創期に加入したメンバーへの「**草分け**」的な軽い名鑑表示（例: 「開村メンバー」バッジ）。ただし**チーム差別化ガードレール（序列化しない・G3）に抵触しない範囲に留める**: 「早く入った人が偉い」序列や皆勤的な優劣にしない。あくまで「この村を一緒に始めた仲間」という**横並びの記録**に限る。実装するかは別途裁可。

## 9. 機能⑥ 村人ミニプロフィールの所属村一覧

### 9.1 目的

村のメンバー一覧から村人のミニプロフィールを開き、**その村人が（公開設定している範囲で）他にどんな村に居るか**を辿り、村トップへ遷移できるようにする。村人同士の「縁」をたどる導線。

### 9.2 公開トグル列の追加【提案・要 Flyway ALTER＋backfill】

【確認済み】`VillageMembershipEntity`（`village_memberships`）は `subject_type`＋`subject_id` で参加主体を表し（**`user_id` 列は無い**）、公開設定カラムを持たない。ここに公開トグルを足す。

```sql
-- 【提案】village_memberships への ALTER（村ドメイン内）
ALTER TABLE village_memberships
  ADD COLUMN profile_public BOOLEAN NOT NULL DEFAULT FALSE;  -- この村への所属を所属村一覧に公開してよいか
```

**backfill（既存行の初期値）— 実3軸で確定【精査反映】**:

【確認済み】`villages` の軸は `visibility`（PUBLIC/UNLISTED）と `join_policy`（FREE/APPROVAL）。backfill 条件を両軸で確定する:

- **`visibility=PUBLIC AND join_policy=FREE` の村の所属 → `profile_public = TRUE`**（「誰でも見つけて即入れる」最も開かれた村の所属だけを既定 ON）。
- **それ以外（`visibility=UNLISTED` または `join_policy=APPROVAL`）→ `profile_public = FALSE`**（非公開村・承認制村の所属は、既存の慎重さを尊重し既定 OFF。本人が能動的にトグル ON にしたときだけ公開）。
- backfill は Flyway 内で `villages` を JOIN して UPDATE（`WHERE v.visibility='PUBLIC' AND v.join_policy='FREE'` を TRUE、他を DEFAULT FALSE のまま）。**クロスドメインではない**（villages と village_memberships は同一 village ドメイン）。

> **なぜ `join_policy=FREE` まで絞るか**: `visibility=PUBLIC` だけを条件にすると承認制（APPROVAL）の村の所属も既定公開になる。承認制の村は「入るのに審査が要る＝所属自体がある程度センシティブ」なので、backfill の既定 ON は「誰でも即入れる FREE 村」に限定し、それ以外は本人の明示操作に委ねる（既定は伏せる側に倒す＝プライバシー保守的）。

### 9.3 API【提案】

| メソッド / パス | 権限 | 用途 |
|---|---|---|
| `PATCH /api/v1/villages/{villageId}/memberships/me/profile-visibility` | 村人本人 | 自分のその村所属の公開トグル切替（body: `profilePublic` boolean） |
| `GET  /api/v1/users/{userId}/villages` | 要ログイン＋**閲覧者と対象者が同じ村に所属**（§9.4） | 対象村人の所属村一覧（公開トグル ON かつ村が `visibility=PUBLIC` のもののみ） |

- `GET /users/{userId}/villages` のレスポンス（1件あたり）: `villageId`(UUID)・`villageName`(string)・`villageMonshoUrl`(string/null・村紋の署名URL)・`category`(string/null)。**相手のニックネームは返さない**【御裁可済み既定】。
  - ニックネームを返さない理由: 所属村一覧は「どんな村に居るか」を見せる導線であり、村ごとのニックネーム（村内 identity）を横串で晒すと村の匿名世界が破れる（§10 ガードレール）。村名・村紋・カテゴリ・村ID までに留める。

### 9.4 閲覧権限 — 同じ村の同居者のみ＋0件は一律403【御裁可済み既定＋精査反映】

- `GET /users/{userId}/villages` は、**閲覧者と対象者が「どこか同じ村」に共に所属している場合のみ**返す（完全公開にしない）。
- 判定: 閲覧者の所属村集合 ∩ 対象者の所属村集合 ≠ ∅ なら許可の第一関門。
- 返す村は、そのうえで**対象者が `profile_public=TRUE` かつ 村が `visibility=PUBLIC`** のものだけ（二重フィルタ）。
- **🔴 0件時は一律 403（200 空配列を返さない）【精査で確定】**: 二重フィルタの結果**返せる村が0件になる場合、共通村があるか否かに関わらず一律 403 を返す**。理由: 「共通村なし→403／共通村あるが公開村0件→200 空配列」と応答を分けると、**空配列が返ること自体が「この2人は同じ村に居る」という同居関係の存在を漏らす**（サイドチャネル）。同居関係の有無もプライバシー情報なので、**0件はすべて 403 に統一**して同居関係の有無を秘匿する。
- **理由**: 見ず知らずの他人の所属村を誰でも辿れると、村をまたいだ個人追跡（ストーキング）の道具になる。「同じ村で既に縁のある者同士」に閲覧を限定し、`docs/security` の IDOR／プライバシー方針に整合させる。

### 9.5 FE 導線と設定 UI — ミニプロフィール Dialog は新規作成【🟠 精査で明確化・調査済み】

## 10. チームとの差別化ガードレール【独立節・全機能に適用】

村は「役職も格式も置いてくる、ゆるい縁の場」（F17.1 §1.1）である。チーム／組織（実名・所属実態・出欠管理の世界）とは**構造的に別物**でなければならない。本書の全機能は以下のガードレールを守る。これは設計原則であり、各機能の DDL・API・UX がこれを侵さないことを §11 受け入れ条件で検証する。

| # | ガードレール | 本書での担保 |
|---|---|---|
| G1 | **未回答者の一覧を出さない** | 出欠・RSVP は「答えた人」しか返さない。誰が答えていないかを列挙する API・画面を作らない |
| G2 | **催促通知をしない** | 接近通知は**村全体への案内・前日1回のみ**（§3.5）。「あなたはまだ出欠を答えていません」型の個人宛リマインドを作らない |
| G3 | **皆勤・欠席率を数えない** | 祭 RSVP は **ABSENT を保存できない**（§5.2）ので欠席率が構造的に作れない。寄合出欠は ABSENT を持つが**当該寄合の調整目的のみ・村横断の欠席集計 API は作らない**（非対称の正当化は §10.1）。皆勤バッジ・出席率ランキングを作らない |
| G4 | **実名世界（チーム/組織）とのリンクを作らない** | 表示は**村ニックネーム**で解決（§4.4/§5.6）。所属村一覧はニックネームすら返さない（§9.3）。timeline 自動投稿は実名スナップショットを焼かない（§3.2） |
| G5 | **参加記録は村ニックネーム世界に閉じる** | 出欠・コメント・TODO・RSVP・年輪・村史のすべてが村内 identity（ニックネーム）で完結し、村外（実名・他チーム）へ漏れない。所属村一覧の横串も「同じ村の同居者のみ・ニックネーム非返却」（§9.4/§9.3） |

- ⑤の相性表示も、**匿名重なりは3人未満非表示・identity 非返却**（§8.4）でこのガードレールに従う。
- ①の自動投稿も**システム名義**（個人を主語にしない）で、特定村人の行動を晒さない。

### 10.1 寄合出欠の ABSENT を許す理由（祭 RSVP との非対称の正当化）

**寄合出欠は GOING/MAYBE/ABSENT の3値を持つ（§4.2.1）が、祭 RSVP は GOING/MAYBE のみで ABSENT を持たない（§5.2）。** この非対称は意図的であり、G1/G3 と矛盾しない。正当化を明記する。

- **寄合は「実務調整（意思決定）」機能**である。日程・場所・持ち物を詰めるオフ会調整で、幹事は「何人分の席・資料を用意するか」を把握する必要がある。明示的な「行けない（ABSENT）」は、**既に実装済みの候補日投票が3値（○/△/×相当）を持つのと同じ文化**であり、寄合という機能の性質上、decline（欠席表明）に実務価値がある。
- **祭は「自由参加のお祭り」**である。来たい人が来る場で、「行かない」を宣言する実務価値が無い（席割りや資料配布のような調整が発生しない）。よって祭 RSVP は「行く／たぶん行く」だけを持ち、不参加は無回答と同じ扱いにする（§5.2）。
- **G1/G3 との整合の担保**:
  - **未回答者は列挙不可能**（G1）: ABSENT は「本人が能動的に×を選んだ」レコードのみ。**答えていない村人はレコード自体が存在しない**ため、「未回答者一覧」は寄合でも構造的に作れない。ABSENT の存在は「未回答者を追う」こととは別物。
  - **横断集計を作らない**（G3）: ABSENT は**当該寄合の調整目的でのみ表示**する。**村人ごとの「寄合欠席率」「皆勤」を村横断で集計する API・画面は作らない**（AC-32b で検証）。1つの寄合の中で「今回×の人」を幹事が見るのは調整、村をまたいで「あの人はいつも欠席」と数えるのは序列化＝禁止、という線引き。
- この非対称により、G3 の表現「祭 RSVP は ABSENT を保存できない」は**祭に限った担保**であり、寄合の ABSENT は上記の横断非集計で G3 を担保する（担保手段が機能ごとに異なるだけで、いずれも「優劣を数えない」原則に収束する）。

## 11. 受け入れ条件（AC）

> **BE 契約テストは MockMvc 経由必須**（`TEST_CONVENTION.md`・Bean 直呼び禁止）。**実 MySQL Testcontainers**・**日時は `LocalDateTime` を bind**（文字列リテラル禁止・TZ 境界事故回避。memory `feedback_it_fixture_datetime_tz_bind`）。各 AC は `/試練` でそのまま red に落とせる粒度（正常系＋異常系＋境界）。

### 11.1 機能① 自動還流・通知

- **AC-01**: 歳時記/祭/寄合を作成すると、当該村の `timeline_posts` に `system_post_type='EVENT_CREATED'`・`user_id IS NULL`・`scope_type='VILLAGE'`・`scope_village_id=村UUID`・`source_event_uuid=作成した行事のUUID` の行が1件生成される。
- **AC-02**: システム投稿の行は `user_id IS NULL`（`posted_as_type` は既定 `'USER'` のまま・読まれない）で保存でき、投稿者解決を `system_post_type IS NOT NULL` 判定でスキップして i18n 表示名で描画できる（NPE を起こさない）。
- **AC-02b**（FE 表示契約・実機E2E観測）: 村タイムラインを開くと、システム投稿カードが **投稿者名「村の行事案内」（`village.systemPost.authorName`）＋システムアイコン** で表示される（空カード・空アバターにならない）。`PostResponse.systemPostType` が非 null で応答に含まれ、`TimelinePostCard.vue` が分岐して描画する。実機で「作成→村フィードにシステム投稿が名前付きで出る」を目視確認する。
- **AC-03**: 祭が `SCHEDULED→ACTIVE` に遷移すると `FESTIVAL_STARTED` の自動投稿＋通知が1回発火する（バッチ再実行で二重発火しない＝状態が既に ACTIVE）。
- **AC-04**: 寄合が `CONFIRMED` に遷移すると `MEETUP_CONFIRMED` の自動投稿＋通知が発火する。
- **AC-05**（境界）: 接近通知バッチは、翌日開催の行事に `EVENT_UPCOMING` を**1回だけ**送る（`source_event_uuid=行事UUID` のシステム投稿が1件だけ生成される）。同日中にバッチが再走しても、`(scope_village_id, system_post_type='EVENT_UPCOMING', source_event_uuid)` の存在チェックで既存を検知し、同一行事へは再送しない（timeline_posts の当該行事×UPCOMING 行が2件にならない）。
- **AC-05b**（実機E2E再現手段）: 行事の開催日を翌日に設定 → `POST /api/v1/system-admin/batch/village-event-upcoming-notice/trigger?sync=true`（SYSTEM_ADMIN）で接近通知バッチを手動発火 → 村タイムラインに `EVENT_UPCOMING` システム投稿が出現し、村メンバーに通知が届くことを観測できる（`@BatchEndpoint` 付与・§3.5）。再度 trigger しても投稿・通知は増えない（冪等）。
- **AC-06**（異常系・失敗注入）: timeline/通知の Service 呼び出しを**例外を投げるようスタブ化**した状態で祭を `SCHEDULED→ACTIVE` 遷移させると、**祭の `status` は `ACTIVE` に遷移済み**（コミットされている）である一方、**当該村・当該行事の `timeline_posts` は0件**（副作用が本体を巻き戻していない＝§3.3.1 の分離が機能）。バッチは次の祭へ継続する。

### 11.2 機能② 寄合の後半戦

- **AC-07**: CONFIRMED 寄合で村人が `PUT .../attendance` を送ると出欠が upsert され、再送で UPDATE される（`(meetup_id,user_id)` UNIQUE）。
- **AC-08**（異常系）: PLANNING 状態で `PUT .../attendance` は `MEETUP_NOT_CONFIRMED` で拒否される。
- **AC-09**: 村人がコメントを投稿でき、一覧が作成日昇順で返る。投稿者本人＋村長/長老のみ削除できる。
- **AC-10**: 未割当 TODO を村人本人が `claim` で自分に割り当てられる。既に割当済みの TODO への claim は `MEETUP_TODO_ALREADY_CLAIMED` で拒否。
- **AC-11**（境界・権限）: TODO の `complete` は**手挙げ者本人＋幹事のみ**成功し、無関係な村人は拒否される。
- **AC-12**（権限）: 割当済み TODO の `release` は**本人のみ**成功し、幹事や他村人は拒否される。
- **AC-13**: 幹事＋村長/長老が `decisions_note` を更新でき、非幹事の一般村人は拒否される。

### 11.3 機能③ お祭りの参加レイヤー

- **AC-14**: 村人が `PUT .../rsvp` で GOING/MAYBE と役割ラベルを登録でき、再送で upsert される。
- **AC-14b**（境界・ページング・§13.5）: `GET .../rsvps` は size 上限付きページングで返し、全件一括返却しない（祭 RSVP は数百人規模になりうるため必ずページングする・G3「全員の出欠を舐めて集計する」実装の構造的抑止）。

## 12. 状態遷移

### 12.1 寄合（meetup）

```
PLANNING ──(候補日確定: confirmed_date セット)──▶ CONFIRMED ──(開催後・記録あり)──▶ [村史編纂: 任意/Wave2]
   │  候補日投票のみ有効                              │  出欠・コメント・決まったこと・宿題が有効
   │  出欠API=MEETUP_NOT_CONFIRMED で拒否              │  候補日投票は締切
   └──────────────(取消)──────────────▶ CANCELLED（全書き込み不可・読み取りのみ）
```

- CONFIRMED 遷移時に `MEETUP_CONFIRMED` 自動投稿＋通知（§3.4）。
- 出欠受付は CONFIRMED 中のみ（§4.5）。

### 12.2 祭（festival）と RSVP の関係

```
SCHEDULED ──(starts_at<=now: 15分バッチ)──▶ ACTIVE ──(ends_at<=now: 15分バッチ)──▶ ENDED
   │ RSVP受付可（事前の参加表明）              │ RSVP受付可＋実況(live-posts)受付可      │ 村史自動編纂（§5.5）
   │ 自動投稿=なし                              │ FESTIVAL_STARTED 自動投稿＋通知(§3.4)   │ RSVP/実況は読み取りのみ
   └──────────────(取消)──────────────▶ CANCELLED（RSVP/実況 締切・編纂しない）
```

- **RSVP は SCHEDULED/ACTIVE で受付**（事前～当日の参加表明）。ENDED/CANCELLED は締切。
- **実況（live-posts）は ACTIVE のみ**受付。
- RSVP は status（GOING/MAYBE）を持つが、**祭の status（SCHEDULED/ACTIVE/ENDED）とは独立**（RSVP status は「参加意思」、祭 status は「開催段階」）。

### 12.3 接近通知（EVENT_UPCOMING）冪等

- 毎日バッチが「翌日開催 かつ 当該行事×UPCOMING のシステム投稿が未存在」の行事にのみ送信（§3.7）。送信＝システム投稿生成が冪等マーカーを兼ねる。
- 「未存在」判定は `timeline_posts` を **`scope_village_id=村UUID AND system_post_type='EVENT_UPCOMING' AND source_event_uuid=行事UUID`** で検索し0件かで行う（§3.2 の `source_event_uuid` 列・`idx_timeline_posts_sys` index）。

### 13.4 退会・村BAN・村削除時の各新規テーブルの扱い【精査で追加】

【確認済み】既存の村ドメイン前例 `VillageUserCleanerEventListener`（`UserAnonymizedEvent` を `@TransactionalEventListener(AFTER_COMMIT)` + `@Transactional(REQUIRES_NEW)` + `@Async` で購読）は次の方針を採る:
- ニックネーム（`user_village_nicknames`）: **物理削除**、ピン（`user_village_pins`）: **物理削除**、メンバーシップ（`village_memberships`）: **匿名化マーカー**（`leftAt=now`・`bannedReason="ANONYMIZED"`）で**投稿・UGC は保持**。
- `bulletin_posts`/`timeline_posts`/`chat_messages` 等の UGC は「各機能ドメインの匿名化リスナーが担当」（本体は残し、表示解決が匿名化される）。

本書の新規テーブルもこの前例に揃える（原則3・4）:

| テーブル | 退会（`UserAnonymizedEvent`） | 村BAN | 村削除（村ドメイン内） |
|---|---|---|---|
| `village_meetup_attendances` | **残置**（user_id 保持・表示解決が匿名化。出欠は「元村人A」で残る。集計の歴史価値を保持） | 残置（membership 側で以後の書き込みを遮断） | 村と同一ドメイン → **CASCADE 可**（村の物理削除は稀。基本は村の論理削除で親が消える） |
| `village_meetup_comments` | **本文匿名化の対象**（body に PII が混入しうる → 退会時に**本文を匿名化プレースホルダへ置換**するか、user_id 表示解決の匿名化に委ねる。方針は下記） | 残置 | CASCADE 可 |
| `village_meetup_todos` | 残置（title は行事の持ち物等・PII 性低。assignee/created_by の表示解決を匿名化） | 残置 | CASCADE 可 |
| `village_festival_rsvps` | **残置**（役割ラベルは PII 性低・表示解決匿名化） | 残置 | CASCADE 可 |
| `village_festival_live_posts` | 残置（紐付けは timeline_post_id の参照のみ。本文は timeline 側の匿名化に従う） | 残置 | CASCADE 可 |

| `village_event_archives` | **残置**（村史は編纂スナップショット＝村の歴史。個人 identity を含まない集計テキストなので匿名化不要。created_by 相当は持たない設計） | 残置 | CASCADE 可 |

**退会時の PII 匿名化範囲の明記**【提案・確定】:
- **自由記述本文（`village_meetup_comments.body`・`village_calendar_event_logs.note`）は退会時匿名化の対象に含める**。既存の UGC 方針（本体保持・表示解決匿名化）に加え、**自由記述テキストは本人が書いた内容に実名・連絡先等の PII が混入しうる**ため、退会時に当該ユーザーが書いた comments/logs の本文を**匿名化プレースホルダ（「（退会した村人の投稿）」等）へ置換**する。これは既存 `VillageUserCleanerEventListener` に comments/logs のクリーン処理を1メソッドずつ追加する形で実装（本前例と同じ `AFTER_COMMIT`+`REQUIRES_NEW`）。
- **本文置換 vs 表示解決匿名化の使い分け**: ニックネーム表示は「投稿者の名前」の匿名化で足りるが、**本文そのものに書かれた PII は表示解決では消えない**ため、自由記述本文は物理的に置換する（GDPR Art.17・CLAUDE.md 原則4「個人情報のみ消去」に整合）。写真（`photo_r2_key`）は R2 オブジェクトの削除要否を実装時に判断（村史編纂に取り込まれた代表画像を除き、退会者の写真は削除候補）。
- **BAN**: データは残置し、`village_memberships` 側の遮断で以後の書き込み・閲覧を止める（既存 BAN 前例に同じ）。BAN は「その村での活動停止」であって「投稿の削除」ではない。
- **村削除**: 新規テーブルはすべて village ドメイン内なので **CASCADE 可**（原則2）。ただし村は基本 `deleted_at` の論理削除（F17.1 原則3）で、物理削除は稀。DDL では既存村テーブルに倣い FK 非付与＋アプリ層で親削除時に子を処理する（`VillageMatchRecruitRepository` の作法）。

### 13.5 一覧 GET のページング・ソート規約【🟠 精査で追加・既存村API前例に整合】

【確認済み】既存の村一覧 GET（`VillageMeetupController.list`）は **`@RequestParam page`（既定 0）／`size`（既定 `DEFAULT_PAGE_SIZE=20`）→ `PageRequest.of(max(page,0), size<=0?20:size, Sort.by(DESC,"createdAt"))`** で `Pageable` を組み、`List<Response>` を `ApiResponse.of(...)` で包む方式。本書の新規一覧 GET もこれに揃える。

| API | 既定ソート | ページング | 根拠 |
|---|---|---|---|
| `GET .../attendances` | `createdAt` ASC（出欠は付いた順に見せる） | `page`/`size`（既定20） | 出欠は数人〜数十人が通常だが、上限のため必ずページング |
| `GET .../rsvps` | `createdAt` ASC | `page`/`size`（既定20・**必須**） | **祭 RSVP は数百人規模になりうる**ため全件返しは禁止・必ずページング |
| `GET .../comments` | `createdAt` ASC（会話は古い順） | `page`/`size`（既定20） | 掲示板コメントの前例に同じ |
| `GET .../todos` | `createdAt` ASC | `page`/`size`（既定20） | — |
| `GET .../logs`（年輪） | `year` DESC → `createdAt` DESC | `page`/`size`（既定20） | 「去年の様子」を先頭に |
| `GET .../event-archives`（村史） | `archived_at` DESC | `page`/`size`（既定20） | 新しい行事を先頭に |
| `GET .../live-posts` | `created_at` ASC（実況は時系列） | `page`/`size`（既定20） | — |

- すべて `VillageMeetupController` と同じ `PageRequest.of(...)＋Sort.by(...)` の作法で実装し、`ApiResponse.of(List)` で返す（`Page` エンベロープは既存村APIに倣い使わない）。
- **RSVP のページング必須は G3 とも整合**: 全 RSVP を一括で返さないことで「全員の出欠を舐めて集計する」クライアント実装を構造的に抑止（数百人規模の一覧を意図的にページ分割する）。

## 15. 非機能・実装方針・Wave 分割

### 15.1 スケール（1000万ユーザー・シャーディング前提）

- **村テーブルは `organization_id` を持たない横断ドメイン**である（村は組織・チームの垣根を越える。F17.1 §1.1）。よって `AbstractTenantAwareRepository`（テナント絞り込み基底）の対象外で、**村スコープは `village_id`（UUID）で絞る**。将来シャーディングするなら `village_id` がシャードキー候補（UUIDv7 は独立発番可＝原則6の狙い）。
- 出欠・RSVP・年輪・実況・村史は**村ごとに行が増える**テーブルなので原則6を適用（UUIDv7）。唯一 `village_festival_live_posts` のみ参照2本の複合自然キー（§5.4・原則6例外）。
- `timeline_posts` は既存 BIGINT（BaseEntity）で据え置き（既存テーブルの ID は変更しない・原則6）。①の ALTER は列追加＋NULL 緩和のみで ID 方式は触らない。

### 15.2 後方互換

- 全 ALTER は Expand（列追加・NULL 化）で既存行・既存クライアントを壊さない。
- ⑤のランキング廃止は deprecate→撤去の2段で既存クライアントの 404 を避ける（§8.2）。

### 15.3 実装方針（モデル）【御裁可済 決定3】

- 本書に基づく実装（`/試練`・`/出陣`）は **Opus 以下のモデルで行う。Fable は使わない。** 認可・越境・改ざん不可（村史 snapshot）の難所は Opus、機械的な CRUD・テーブル追加は Sonnet で可（コスト最適化。CLAUDE.md Dynamic Workflows 方針）。

### 15.4 段階実装（Wave 分割案）【提案】

| **Wave 1** | ②寄合後半戦（出欠・コメント・決まったこと・宿題）＋④年輪。**timeline を触らない純・村ドメイン**で先行（リスク最小・試練が書きやすい） | なし |
