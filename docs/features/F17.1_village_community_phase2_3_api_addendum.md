#### 候補日の時刻対応（#2357 / DATE + 任意 TIME 分離）

寄合の候補日に**任意の時刻**を持たせられる（御裁可済の DATE + 任意 TIME 分離方式）。

- DB: `village_meetup_candidate_dates.candidate_time TIME NULL`（終日 = NULL）／
  `village_meetups.confirmed_time TIME NULL`（確定時刻）。移行は `V159.__meetup_candidate_time.sql`。
  既存の「日付のみ」候補は `candidate_time = NULL` で**無損失移行**。
- UNIQUE を `(meetup_id, candidate_date)` → `(meetup_id, candidate_date, candidate_time)` に張り替え、
  **同日別時刻の候補**を共存できる。⚠️ MySQL の UNIQUE は `TIME NULL` の重複を許容するため、
  終日候補の重複は**アプリ層でも `(date, time)` ペアで重複検査**する（`VillageMeetupService`）。
- 作成リクエスト `MeetupCreateRequest.candidateDates` は素の日付配列（`List<LocalDate>`）から
  **object 配列 `{date（必須）, time（任意・終日=省略）}`**（`MeetupCandidateDateInput`）へ拡張。
- 候補日追加 `MeetupCandidateDateAddRequest` に `candidateTime`（任意）を追加。
- レスポンス（候補日 DTO・寄合詳細・投票集計候補）に `candidateTime` / `confirmedTime` を追加。
- 確定（`confirm`）時は採用候補の `date` と `time` を `confirmed_date` / `confirmed_time` へ転記。
- FE: 作成ダイアログに任意の時刻入力（`type="time"`）、詳細は date + time 突合で確定候補を判定し
  `HH:mm`／終日ラベルを表示。

| 状態 | メソッド | パス | Controller | 説明 |
|---|---|---|---|---|
| 🟢 | GET | `/api/v1/villages/{villageId}/chronicles` | `VillageChronicleController#list` | 村史一覧（年月降順） |
| 🟢 | GET | `/api/v1/villages/{villageId}/chronicles/{yearMonth}` | `VillageChronicleController#get` | 村史詳細（指定月） |

> 設計補足: 村史は F09.8 コルクボードの村スコープ版として `village_chronicles` を別エンティティ化。
> 参照系（一覧・詳細）はいずれも実装済み。**生成は月初バッチ
> （`VillageChronicleBatchService`）専用**であり、作成/更新/削除の API は意図的に提供しない
> （村史はユーザーが編集する対象ではなく、集計結果のスナップショットであるため）。

#### レスポンス契約

- **一覧**: `ApiResponse<List<ChronicleResponse>>` — `{"data":[...]}` の**素の配列**。
  `{items, total}` エンベロープではなく、ページングも未対応（村史は月次のため件数が少ない）。
- **`yearMonth`**: `LocalDate` / OpenAPI `format: date`（`"2026-05-01"`）。
  当該月の 1 日に正規化済み。詳細取得のパス変数も**この ISO `YYYY-MM-DD` を渡す**
  （村史の ID(UUID) ではない点に注意）。
- **`topics`**: `TopicItem`（`{name, count}`）の配列で TOP3 トピックを返す。
  集計対象が 3 件未満なら実在する件数のみ格納する（`string[]` ではない）。

#### 認可（2026-07-15 根治）

村史の TOP3 トピックは**村掲示板スレッドのタイトルを集計したもの**であるため、
参照系（一覧・詳細）はいずれも**掲示板本体と同一の閲覧認可**（村の `bulletin_visibility`）に従う。
判定は `VillageBulletinAccessService#checkVillageBulletinViewAccess` に一元化する
（独自の可視性述語を書かない）。

| 村の `bulletin_visibility` | 非メンバー | 村メンバー / SYSTEM_ADMIN |
|---|---|---|
| `PUBLIC` | 200（ログイン済なら誰でも） | 200 |
| `MEMBERS_ONLY`（既定値） | **403 `VILLAGE_081`** | 200 |

- 村が存在しない／削除済／凍結済 → 404 `VILLAGE_001`（IDOR 対策で統一）
- 認可は村史の存在確認**より先**に効く。非メンバーには「その月の村史が有るか無いか」も秘匿する
- 村史 0 件の村は 200 で空配列を返す（例外にしない）

> 根治前は `bulletin_visibility` を一切参照しておらず、掲示板 API が `MEMBERS_ONLY` で
> 守っているスレッドタイトルが村史経由で非メンバーに漏れていた（全村が `MEMBERS_ONLY` 既定）。

## 3. 設計補足

### 3.1 スコープ汎用 Controller を村に適用した経緯

`/api/v1/{scopeType}/{scopeId}/...` 形式の汎用 Controller は元々 organizations / teams 用に
作られた共通機能（掲示板・フォーム・アンケート・物件履歴・修繕計画・ワークフロー）である。
F17.1 Phase 2/3 にて、村もこれらの共通機能を再利用すべく、`scopeType` の許容値に `villages` を
追加した。これにより 1 Controller で 3 スコープ（organizations / teams / villages）対応となり、
コードの重複を排除している。

### 3.2 PostingIdentityController（投稿主体切替）

`PostingIdentityController` は本書記載の 122 件には含まれないが、村関連の補助 Controller として
`village/controller/` 配下に同居しており、`/api/v1/me/posting-identities` 系で投稿主体（個人 /
チーム代表 / 組織代表）を切り替える機能を提供する。F17.1 §4.6 の対応実装。

### 3.3 VillageMonshoController / VillageSearchController

`village/controller/` 配下に存在する `VillageMonshoController` / `VillageSearchController` は
それぞれ村紋（`villages.monsho_r2_key`）と村横断検索を担うが、本 addendum 対象（122 件）には
集計上含まれていない（既に `/api/v1/villages/{_}/...` 配下の他検出に吸収済み）。
