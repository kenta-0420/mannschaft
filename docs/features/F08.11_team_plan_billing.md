> **マスター確定の課金モデル（不変・本設計で逸脱禁止）**:
> 予約する側（会員・利用者）は**完全無料**。負担者は導入チームのみ。

> 既存チームには**猶予期間つき適用**（30日）。価格はマスタ化（SYSTEM_ADMIN 管理・初期値 1000/500・JPY・将来変更可能）。

## 1. 概要

整骨院・美容室・飲食店等のサービス業チームが使う予約機能（F03.4 系）の**ライン数を課金軸**とするチーム向けサブスクリプションを導入する。予約ライン（席・ベッド・施術台）はチームの事業規模に比例する自然な従量軸であり、「1ラインまで無料 → 3ラインまで月額 → 4本目以降は1本ごとに追加課金」の段階制で、小規模チームの無料利用を守りつつ事業利用から対価を得る。

既存の `TeamPlanService.hasPaidPlan()` / `team_subscriptions`（V9.055）は**器だけ存在し、書き込み実装が一切ない**（`TeamSubscriptionRepository` への save 呼び出しは main 全体でゼロ・実測 2026-07-08）。本設計はこの器を活性化し、チーム課金の**最初の実体**を与える。

### 1.1 非ゴール（明示）

| 非ゴール | 理由 |
|---|---|
| **予約する側（会員・利用者・一般ユーザー）への課金** | マスター確定モデル。予約の申込・キャンセル・履歴閲覧は誰でも完全無料。本設計のいかなる変更もこの原則を破ってはならない |
| Stripe **Connect / エスクロー / destination charge** の使用 | 本課金は「チーム → Mannschaft（platform）」の直課金。F22.1/F08.9 の Connect レール（受領者が第三者）とは資金の向きが異なる |
| **F18（ポイント・ウォレット・残高）** との連携 | F18 は資金決済法対応で凍結中。本設計は Stripe サブスク一本で残高概念を持たない |
| ライン数以外の**機能制限**（無料チームの機能劣化） | 無料枠は「ライン数のみ」の制限。予約メニュー・テンプレート・通知等の機能自体は全プランで同一 |
| 組織（Organization）単位のプラン | 予約ラインはチーム単位の資産（F03.4 §2）。組織課金は将来の別設計 |
| 年額プラン・トライアル | 初期リリースは月額のみ（§11 要裁可論点にトライアル有無を残置） |
| 既存 `PlanType.MODULE/PACKAGE/ORGANIZATION` の実装 | V9.055 の構想値。本設計では使用せず温存（§3.2） |

### 3.1 全体像

購入履歴テーブルは**新設しない**。サブスクの請求実績は Stripe が正本（invoice）であり、FE の請求履歴は Stripe Billing Portal（§6.6）へ委譲する。アプリ側の監査は `audit_logs`（購入・数量変更・解約の操作記録）と `stripe_webhook_events`（受信記録）で足りる — F09.13 が purchases テーブルを持つのは「一回払いでクレジット残高を自前管理する」ためであり、サブスクには残高がないため器を増やさない（設計判断）。

### 3.2 `team_subscriptions` の活性化（既存テーブル改修）

**既存テーブルを捨てずに改修して使う**（設計判断）。理由: (1) `TeamPlanService.hasPaidPlan` → `hasActivePaidPlan` の参照系がすでに 3 ドメイン（reservation/template/analytics）から結線済みで、テーブルを替えると参照系全部の付け替えになる。(2) V9.055 のカラム構成（plan_type/status/stripe_subscription_id/period）はサブスク管理の素直な骨格で、不足分の追加で足りる。

**主キーは BIGINT のまま**（既存テーブルの ID 変更はしない — CLAUDE.md 原則6は「新規テーブル」対象。既存 BIGINT は変更しない）。

#### 3.2.1 PlanType の扱い

既存 enum `FREE / MODULE / PACKAGE / ORGANIZATION` に **`BASIC` を追加**する（Java enum 追加のみ。DDL は `VARCHAR(30)` のため変更不要）。

- `BASIC` = 本設計の基本プラン（¥1,000/月・3ライン込み・addon 加算可）
- `MODULE / PACKAGE / ORGANIZATION` は V9.055 時点の構想値で**未使用のまま温存**（削除しない — enum 値の削除は既存行が無くとも逆コンパチ配慮で避ける。将来のプラン多層化の器として残す）
- `isPaidPlan()` の判定（`planType != FREE && status == ACTIVE`）は `BASIC` を自然に有料と判定する

#### 3.2.1a SubscriptionStatus に `PENDING` を追加（二重サブスク防止・精査2パス指摘b 根治）

既存 enum `ACTIVE / CANCELLED / EXPIRED / PAST_DUE` に **`PENDING` を追加**する（`VARCHAR(20)` のため DDL 変更不要）。

- `PENDING` = Checkout Session 発行済み・未完了の中間状態。**Checkout 起票時にこの状態で行を作る**（§6.2 改訂）。UNIQUE(team_id) で「1チーム1行」を保ち、二重 Checkout・二重サブスクを入口で遮断する
- `isPaidPlan()` は `PENDING` を**有料と判定しない**（`ACTIVE` のみ有料）。PENDING 中はまだ無料枠のエンティトルメント
- `checkout.session.completed` で `PENDING → ACTIVE`、`checkout.session.expired` で `PENDING → 行削除`（掃除・§6.4.4）。会費（`MemberPaymentEntity` の PENDING→CANCELLED パターン・実測）と同型
- 初稿（§6.2-3）の「PENDING 中間状態を DB に持たない」方針は**二重サブスクを防げないため撤回**（精査2パスで露見・§6.2 に理由）

#### 3.2.3 `hasActivePaidPlan` の既存欠陥の修正【根治・必須】

現行クエリ（`TeamSubscriptionRepository:25`）:

```java
@Query("SELECT COUNT(s) > 0 FROM TeamSubscriptionEntity s " +
        "WHERE s.teamId = :teamId AND s.status = 'ACTIVE' AND s.planType <> 'FREE'")
```

**欠陥**: `current_period_end` を一切見ない。webhook が取りこぼされて status が ACTIVE のまま残ると、期限が過ぎても永久に有料扱いになる。書き込み実装ゼロの現状では顕在化していないが、本設計で実体化した瞬間に実害化する。修正:

```java
@Query("SELECT COUNT(s) > 0 FROM TeamSubscriptionEntity s " +
        "WHERE s.teamId = :teamId AND s.status = 'ACTIVE' AND s.planType <> 'FREE' " +
        "AND (s.currentPeriodEnd IS NULL OR s.currentPeriodEnd >= :today)")
boolean hasActivePaidPlan(@Param("teamId") Long teamId, @Param("today") LocalDate today);
```

- `today` は Service 層で注入 `Clock` から算出して渡す（`CURRENT_DATE` 直書きにしない — date-pin テスト可能にする。F08.9 §OVERDUE バッチと同じ流儀）
- `currentPeriodEnd IS NULL` を許すのは**手動付与プラン**（SYSTEM_ADMIN が営業対応で無期限有料化するケース）の器。通常の Stripe 同期行では必ず値が入る
- **期限跨ぎの正常系は webhook（`invoice.paid` → period 延長）が担い、本条件は webhook 欠落時の安全弁**（fail-closed: 課金が確認できなければ無料扱い）
- `Entity.isPaidPlan()` も同一意味論に揃える（`isPaidPlan(LocalDate today)` へシグネチャ変更。判定ロジックの二重定義ズレを残さない）
- `DailyAggregationBatchService.countActivePaidSubscriptions()`（analytics）も同条件へ揃える

### 3.3 価格マスタ `team_plan_pricing`（新規・SYSTEM_ADMIN 管理）

F13 ストレージプラン（`StoragePlanEntity` ＋ `pages/admin/storage-plans.vue`）の型を写経する。**金額の権威は常にこのマスタ**であり、FE から金額を受けるエンドポイントは一切作らない（§9）。

```sql

-- 初期データ（マスター確定値）

     free_line_limit, included_line_limit, currency, is_active)
VALUES
    ('基本プラン', 1000.00, 500.00, 1, 3, 'JPY', 1);
```

- **主キーは BIGINT AUTO_INCREMENT（UUIDv7 ではない・精査2パス指摘d 根治）**。理由は2つ: (1) 本テーブルは CLAUDE.md 原則6の**「マスタテーブル例外」に明確に該当**する（全テナント共通の参照データ・書き込みは SYSTEM_ADMIN の運用操作のみ・シャーディング時は全シャードへ複製）。(2) **既存 `StripePaymentProvider.createProduct(String name, Long paymentItemId)` の第2引数が `Long`**（`putMetadata("paymentItemId", id.toString())`・実測）であり、UUID(BINARY16) 主キーだと**型が渡せず**遅延生成の写経が破綻する。BIGINT なら既存メソッドをそのまま流用できる（初稿の「迷ったら原則6で UUIDv7」判断を、マスタ例外の明示適用＋既存 I/F 整合のため BIGINT へ撤回する）。**Entity は `UuidV7Entity` を継承せず** `@GeneratedValue(strategy = IDENTITY)` の BIGINT id を持つ（`StoragePlanEntity` と同型・写経元も BIGINT IDENTITY・実測）
- **価格改定は「新行 INSERT ＋ 旧行 is_active=0」**（行の上書きではなくバージョン切替）。Stripe の Price は immutable（金額変更＝新 Price 作成）なので、マスタ行と Stripe Price を 1:1 に保つにはこの方式が構造的に正しい。旧価格で契約中の既存サブスクは**旧 Price のまま継続**（グランドファザリング）し、新規契約のみ新価格を使う — 既存契約の価格改定強制は初期スコープ外（§11 要裁可論点）
- `free_line_limit` / `included_line_limit` もマスタ化する（ゲートのハードコードを排し、SYSTEM_ADMIN が将来「無料2本」等へ緩和できる）。**厳格化方向（例: 込み3→2）の変更は既存契約チームに不利益変更となるため、管理画面で警告表示**（§8.4）
- `is_active=1` は常に1行のみ（Service 層で切替をトランザクション内一括更新・アプリ層保証）

### 3.4 ドメイン境界

- `team_plan_pricing` / `team_subscriptions` は **payment ドメイン**（`com.mannschaft.app.payment`）に置く（既存 `TeamSubscriptionEntity` の現在地に揃える）
- reservation ドメインからは `TeamPlanService`（payment）の**サービスメソッド呼び出しのみ**で参照する（既存 `ReservationNotificationRecipientService` と同型・Entity 直参照禁止）
- `purchased_by_user_id` / `team_id` にクロスドメイン FK は張らない（インデックスのみ・整合はアプリ層）

## 4. エンティトルメント解決（entitledLines の一元化）

### 4.1 解決式（正本）

```
entitledLines(teamId) =
    有料（BASIC ACTIVE・期限内）    → included_line_limit(3) + addon_line_qty
    猶予中（grace_until >= today）  → 無制限（物理上限20のみ）
    無料（上記以外すべて）           → free_line_limit(1)
```

- **PAST_DUE の扱い（指摘5・要裁可 §16-6）**: 初期設計は「無料扱い（fail-closed）」だが、Stripe の Smart Retries 中の正規顧客が決済一時失敗の瞬間から即 402 になるのは体験が悪い。そこで **PAST_DUE 中は `current_period_end + N日`（推奨 N=7）まで有料扱いを維持する短猶予**を §16-6 の要裁可論点として提示する（採用時は `entitlement()` の PAST_DUE 分岐に「period_end + N >= today なら有料値を維持」を追加）。**いずれにせよゲートは新規作成のみに効く**ため、既存ライン・既存予約は PAST_DUE でも一切影響を受けない（§5.3）
- **CANCELLED（期末解約後）/ EXPIRED も無料扱い**。期末解約予約中（`cancel_at_period_end=1` かつ期限内 ACTIVE）は**期末まで有料扱い**（Stripe の意味論と一致）

### 4.2 実装: `TeamPlanService` の拡張（判定の一元化）

新しい Resolver クラスは作らず、既存 `TeamPlanService` に集約する（既に3ドメインが依存する判定一元化ポイントであり、第二の判定器を作ると F00 可視性の教訓〔独自述語は漏洩源〕を繰り返す）。

### 4.3 キャッシュ設計

|---|---|
| キャッシュ名 | 既存 `teamPlan`（boolean）＋新設 `teamPlan:entitlement`（record） |
| ストア | Redis（Valkey）— `RedisConfig.cacheManager` 管轄。既定 TTL 30分のまま（個別 TTL 設定は不要。evict が正で TTL は安全網） |
| **evict 契機（必須・全列挙）** | ① webhook 同期（`checkout.session.completed` / `customer.subscription.updated` / `customer.subscription.deleted` / `invoice.paid` / `invoice.payment_failed` の**すべての team_subscriptions 書き込み後**） ② 数量変更 API 成功後 ③ 期末解約予約/取り消し後 ④ SYSTEM_ADMIN 手動プラン付与/剥奪後 |
| evict 漏れの安全網 | TTL 30分 ＋ `hasActivePaidPlan` の期限条件（§3.2.3）。最悪でも30分で自己修復 |
| 直列化注意 | record は Redis JSON 直列化のため、enum フィールドは name() 文字列で持つ（`feedback_cacheable_enum_key_redis` の教訓） |

> **注意（トランザクション境界）**: evict は team_subscriptions 更新トランザクションの**コミット後**に行う（`@TransactionalEventListener(AFTER_COMMIT)` または webhook サービスの tx 完了後呼び出し）。tx 内で evict → ロールバックすると「DB は旧値・キャッシュは消えて次読み込みで旧値再充填」で実害はないが、tx 内 evict → コミット前に別リクエストが旧値を再充填する競合窓は残る。TTL とゲートの fail-closed 性でこの窓は許容する（厳密化は過剰設計）。

| 事象 | 挙動 |
|---|---|
| 有料→無料（解約・期限切れ・PAST_DUE） | **既存ライン・既存予約・既存枠・既存宛先はすべて無傷**。予約受付も従来通り継続する |

### 6.1 Product / Price 管理（遅延生成）

F09.13 `NotificationCreditCheckoutService.createCheckout` の遅延生成パターンを写経する:

- 初回 Checkout 時に `team_plan_pricing.stripe_product_id` が NULL なら `createProduct(name, pricingId)` → `createRecurringPrice`（**既存メソッド**・MONTHLY）を基本/addon の2本発行し、マスタ行へ保存。`createProduct` の第2引数 `Long paymentItemId` には **pricing 行の BIGINT id を渡す**（§3.3 で BIGINT 主キーにしたため既存 I/F がそのまま通る・metadata キー名 `paymentItemId` は流用でよい）

- 価格改定（新マスタ行）時は新しい Price を新規発行（旧 Price はアーカイブせず旧契約が使い続ける）
- Product 名は「チームプラン: {name}」/「追加ライン: {name}」

購入フロー（PENDING 起票 → webhook 確定・**精査2パス指摘b 根治で PENDING 行を作る方式に改める**）:

1. `POST /api/v1/teams/{teamId}/plan/checkout`（body: `{ addonQty: 0..17 }` — **金額は受けない**）
2. 認可: チーム ADMIN（§9）。既に **ACTIVE** な BASIC 契約があれば 409（`TEAM_PLAN_ALREADY_SUBSCRIBED` — 数量変更 API を使わせる）

4. 操作者の Stripe Customer を取得 or 生成（`stripe_customers` 共用・F09.13 写経）→ `stripe_customer_id` を PENDING 行へ保存
5. Checkout Session を作成し、PENDING 行の `stripe_subscription_id` は**この時点では NULL**（Subscription は完了時に確定）。代わりに **Checkout Session ID を PENDING 行に保存**（未 expired 判定と `checkout.session.expired` 掃除の逆引きに使う。`session_id` 用カラムを §3.2.2 の ALTER に追加）
6. Checkout URL を返す → FE リダイレクト。success_url: `/teams/{slug}/settings/plan?payment=success` / cancel_url: 同 `?payment=cancelled`

> **二重サブスクの二段防御（精査2パス指摘b）**: (1) 入口＝PENDING 行 UNIQUE(team_id)＋未 expired Session 再利用（上記 3）。(2) 最終防御＝`checkout.session.completed` 時に「既に **ACTIVE** で**別の** `stripe_subscription_id` を持つ完了イベントが来た」場合、**後着 Subscription を即座に Stripe で `cancelSubscription`（新プロバイダメソッド・即時 cancel）して二重課金を止め、監査ログに記録**する（握り潰さず積極的に是正・§6.4.4）。この2段で「Checkout を2つ作らせない・万一2つ完了しても2本目を止める」を担保する。

### 6.4 Webhook 同期

#### 6.4.1 ルーティングと帰属解決（既存 dispatcher の実構造に即した具体手順・重大指摘2 根治）

**実測した既存構造の制約**（設計の前提・裏取り済み 2026-07-08）:

- `StripeWebhookService.handleWebhook` は冒頭で `constructEvent`（`WebhookEventInfo`）を1回呼び、`payment_intent.*` を escrow へ、`isSubscriptionEvent`（`invoice.*` / `customer.subscription.deleted`）を membership へ**無条件委譲**する。各委譲先は `constructInvoiceEvent`/`constructEscrowEvent` で**署名を再検証**する（＝既存構造がすでに二重署名検証）。
- **`constructEvent`（`WebhookEventInfo`）は invoice 系で `subscriptionId=NULL`**（`Session`/`PaymentIntent`/`Refund` の3型しか分岐せず・`StripePaymentProviderImpl:355-397` 実測）。したがって **dispatcher の `WebhookEventInfo.subscriptionId` では invoice 系の帰属解決ができない**（初稿 §6.4.1 の「subscriptionId をペイロードから解決」は現構造では不成立だった）。
- **`constructEvent` の Session 分岐は metadata から `memberPaymentId`/`notificationCreditPurchaseId` の2キーしか読まない**（`:359-371` 実測）。したがって **`WebhookEventInfo` record には `teamId`/`teamSubscriptionCheckout` が乗らず、dispatcher で `checkout.session.completed` を team と判定できない**（精査2パス指摘a・初稿 §6.4.1 の「constructEvent が Session.metadata を既に読める」は該当キーについては誤り）。**是正=`constructEvent` の Session 分岐を拡張**し metadata から `teamSubscriptionCheckout`/`teamId`/`teamSubscriptionId` を読んで `WebhookEventInfo` record に**新フィールド `teamId`（Long・nullable）を追加**する（既存 record の破壊を避け nullable 追加・F09.13 の `notificationCreditPurchaseId` 追加と同型）。
- **`constructInvoiceEvent`（`InvoiceWebhookEventInfo`）は `Invoice` と `Subscription` の両分岐を持ち subscriptionId を埋める**（`:969-983` 実測）。`customer.subscription.updated` も `Subscription` インスタンスなので `subscription.getId()`（`sub_xxx`）が取れる（`:980-982`）— ただし現 record に **quantity/cancel_at_period_end フィールドが無い**ため、数量は §6.3-4 の `Subscription.retrieve` で取り直す。

**帰属解決の具体手順**（dispatcher 改修・§6.4.2 と噛み合う3分岐に統一）:

```
handleWebhook(payload, sig):
  event = constructEvent(payload, sig)           # 1度目の署名検証（既存）
  if type startsWith "payment_intent."     → escrow へ委譲（既存・不変）
  if type == "checkout.session.completed":
      # ★constructEvent 拡張後は WebhookEventInfo.teamId が読める（上記 record 拡張）
      if event.teamId != null (= teamSubscriptionCheckout) → TeamPlanWebhookService  # 新規
      elif event.notificationCreditPurchaseId != null → 通知クレジット（既存・不変）
      else → 会員費（既存・不変）
  if type == "checkout.session.expired":
      if event.teamId != null → TeamPlanWebhookService（PENDING 掃除・§6.4.4）  # 新規
      else → 既存処理（会員費 markAsCancelled・不変）
  if isSubscriptionEvent(type) || type == "customer.subscription.updated":
      # ★invoice/subscription 系は constructInvoiceEvent で帰属解決（2度目の署名検証）
      iEvent = constructInvoiceEvent(payload, sig)          # subscriptionId を確実に取得
      subId  = iEvent.subscriptionId
      if teamSubscriptionRepository.existsByStripeSubscriptionId(subId)
                                       → TeamPlanWebhookService                 # 新規
      elif membershipSubscriptionRepository.existsByStripeSubscriptionId(subId)
                                       → MembershipSubscriptionWebhookService   # 既存
      else  # ★どちらにも未登録＝新規購読レース（§6.4.2）
          throw StripeWebhookRetryableException   # 500・Stripe 再送に委ねる（IGNORED 確定させない）
```

- **§6.4.2 との整合（自己矛盾の解消・精査2パス指摘c）**: 初稿は「team 無ければ membership へ委譲」（2分岐）と書き、§6.4.2 の「両方未登録なら再送」と噛み合わず、**未知 subscription が membership 経由で IGNORED 確定される握り潰し経路が残っていた**。上記のとおり **dispatcher を3分岐に統一**し「team・membership のどちらにも `existsByStripeSubscriptionId` しなければ委譲せず即 `StripeWebhookRetryableException`（500・再送）」に修正する。これで「未知 sub を確定させない」防御が dispatcher 段で効き、§6.4.2 と一貫する。
- **membership 既存挙動への影響（正直な記述）**: membership の継続課金は購読同期 API 内で `membership_subscriptions` 行を**先に起票**してから Subscription を作る（webhook 到着前に行が存在する）ため、実運用で「membership の未知 sub」はほぼ発生しない＝回帰は実質ゼロ。ただし万一 membership 側で同種の checkout 前 invoice 先着レースが起きた場合、旧挙動（IGNORED 確定→喪失）から新挙動（再送→救済）に変わる＝**membership 側にとっても改善方向の挙動変化**であり劣化はない。この点を AC-15 の検証範囲に含める。
- **二重署名検証のコスト注記（指摘12）**: 帰属解決のため dispatcher で `constructInvoiceEvent` を追加で1回呼ぶ（署名検証は HMAC-SHA256 の軽量演算・ペイロードは数 KB）。既存の membership/escrow 経路も委譲先で再検証しており本追加は既存流儀の踏襲でボトルネックにならない。委譲先が自前で再検証するため同一 payload に最大3回の検証になるが許容する（正しさ優先）。将来 dispatcher が解決済み record を委譲先へ引き渡す最適化は別 PR 候補として記録。
- `customer.subscription.updated` は現行 membership が購読していないイベント（`isSubscriptionEvent` は invoice.*/deleted のみ）。上記3分岐で team に該当すれば team、membership に該当すれば membership、どちらでもなければ再送。
- 帰属解決は `stripe_subscription_id` の UNIQUE インデックス1発（§3.2.2）。membership 側の `existsByStripeSubscriptionId` は既存 `MembershipSubscriptionRepository` に無ければ**読み取り専用メソッドを1本追加**（既存挙動不変の純粋追加）。

#### 6.4.2 misroute-swallow の防止（新規購読レース・重大指摘4 根治）

**問題**: `WebhookIdempotencyService` は `event_id` **単位のグローバル**な冪等ゲート。新規購読で `invoice.paid` が `checkout.session.completed` **より先着**すると、その時点で team 行が未作成のため §6.4.1 の `existsByStripeSubscriptionId` が false → membership へ誤配 → membership 側で「未知の subscription」として IGNORED → `markProcessed`。すると**同一 event_id は二度と再処理されず、team 側の period 延長が永久喪失**する（Stripe 再送も冪等ゲートで弾かれる）。

**是正**: ドメイン名前空間の分離＋「未知 subscription を確定させない」の二段:

- **冪等キーのドメイン名前空間分離**: `TeamPlanWebhookService` は `tryBegin("teamplan:" + eventId, ...)`、membership は現状のまま（`eventId`）。同一 Stripe イベントでも team 経路と membership 経路で**別の冪等行**になり、片方の早すぎる確定が他方の再処理を封じない。
- **未知 subscription の非確定化（核心）**: §6.4.1 で `existsByStripeSubscriptionId` が false **かつ** membership にも該当 subscription が存在しない（＝どちらにも未登録）場合、`markProcessed` せず **`StripeWebhookRetryableException` を投げて 500 を返し Stripe 再送に委ねる**（team 行が `checkout.session.completed` で作られた後の再送で正しく team へ届く）。「未知 subscription を IGNORED で確定させない」ことが核心（恒久 no-op の根治と同じ思想・症状を隠さない）。
- Stripe の invoice.paid リトライ間隔（数時間〜数日）内に `checkout.session.completed`（通常は先着）が team 行を作るためレースは自己解消する。レース到着の red テストを **AC-28** で観測する。

#### 6.4.3 状態機械（全遷移表・重大指摘3 根治）

`SubscriptionStatus` は `ACTIVE / CANCELLED / EXPIRED / PAST_DUE` の4値。**4状態 × 5イベントの全遷移を定義**する（初稿の3値表を廃し全セルを埋める）:

| 現在状態 ＼ イベント | `checkout.session.completed`※1 | `customer.subscription.updated`（retrieve 反映） | `invoice.paid` | `invoice.payment_failed` | `customer.subscription.deleted` |
|---|---|---|---|---|---|
| **（行なし）** | → **ACTIVE**（通常は PENDING を経るが、行が消えていれば upsert・BASIC・grace_until=NULL） | 帰属先なし＝§6.4.2 の再送待ち | 同左（再送待ち） | 同左 | 同左 |
| **PENDING**（Checkout 起票済・未完了・sub_id=NULL） | → **ACTIVE**（stripe_subscription_id/item ids/period 確定・§6.2 の二重防御適用） | sub_id 未確定のため通常マッチせず（`checkout.session.expired` で行削除 or completed で ACTIVE 化） | sub 未リンクで未登録扱い→§6.4.2 再送（completed 後に確定） | 同左 | 同左（PENDING のまま／completed 未達なら expired で掃除） |
| **ACTIVE** | 冪等 no-op（二重購入は §6.2-2 で 409 入口遮断＋別 sub 完了は §6.2 最終防御で新 sub を即 cancel） | retrieve で qty/period/cancel_at_period_end/status 上書き（Stripe が `past_due` → **PAST_DUE**） | period 延長・**ACTIVE 維持** | → **PAST_DUE** | → **CANCELLED**（cancelled_at=now） |
| **PAST_DUE** | 冪等 no-op（回収は invoice 経路） | retrieve 反映（Stripe が `active` → **ACTIVE**） | 回収成功 → **ACTIVE**・period 延長 | **PAST_DUE 維持**（Smart Retries 継続） | → **CANCELLED**（回収不能で Stripe 最終削除） |
| **CANCELLED** | → **ACTIVE**（同一チーム**再購入**・既存行を上書き活性化・新 sub id） | retrieve 反映（通常は終端で無変化） | **CANCELLED 維持**（解約後の遅延 invoice は period 延長しない） | **CANCELLED 維持** | 冪等 no-op |
| **EXPIRED**※2 | → **ACTIVE**（再購入） | retrieve 反映 | **EXPIRED 維持** | **EXPIRED 維持** | 冪等 no-op |

- ※1 `checkout.session.completed` は「PENDING/CANCELLED/EXPIRED からの新規・再購入」で ACTIVE を作る主経路。metadata の `teamId` と upsert 対象行の team_id を照合し不一致は FAILED（§9 IDOR）。**同一チームで別 sub の完了が来たら §6.2 の最終防御で後着 sub を即 cancel**（二重サブスク是正）。`checkout.session.expired` は表外の第6イベントで、PENDING 行を削除する（§6.4.4）。
- ※2 **EXPIRED の生成契機**: 本設計の webhook 経路は EXPIRED を**生成しない**（Stripe は期末解約を `deleted`、回収不能を `past_due→deleted` で表現し実運用の終端は CANCELLED に集約される）。EXPIRED は V9.055 由来の予約値であり**当面はレガシー扱い（到達しない・削除もしない）**。将来「手動付与プランの期限切れ」（`current_period_end < today` の手動 ACTIVE 行）をバッチで EXPIRED 化する余地を残すため enum は温存する。entitlement 判定（§4.1）は EXPIRED を無料扱いに含める（到達しても安全側）。
- すべての遷移は**同値冪等**（同一イベント再処理で結果不変）。`livemode` 不一致（test → 本番）は IGNORED（既存流儀）。遷移網羅を **AC-29** で検証。

#### 6.4.4 各イベントの処理詳細（`TeamPlanWebhookService`・新設）

冪等は既存 `WebhookIdempotencyService` を流用（§6.4.2 の名前空間分離キー `teamplan:{eventId}`。tryBegin → dispatch → markProcessed/markFailed。失敗は FAILED 記録＋再送出で Stripe 再送に委ねる）。処理は §6.4.3 の遷移表に従い、**`customer.subscription.updated` は必ず `Subscription.retrieve` で現況を取り直してから反映**する（§6.3-4 の順序逆転防御）。書き込み後は必ず evict。

| イベント | 処理 |
|---|---|
| `checkout.session.completed` | PENDING 行を検索（`teamId` で逆引き）→ **二重防御**: (1) 既に ACTIVE で**同一 sub_id** なら冪等 no-op。(2) 既に ACTIVE で**別 sub_id** なら**後着 sub を即 `cancelSubscription`（新プロバイダメソッド・即時 cancel）＋監査ログ**（二重サブスク是正・握り潰さない）。(3) PENDING なら → ACTIVE（sub_id/item ids/period/addon_line_qty 確定・grace_until=NULL）→ evict |
| `checkout.session.expired` | PENDING 行を `stripe_checkout_session_id` で逆引き → **PENDING なら物理削除**（掃除・§3.2.1a）。ACTIVE 済み（別経路で完了）なら no-op。会費の `markAsCancelled` パターンと同型 |
| `customer.subscription.updated` | **必ず `Subscription.retrieve(subId)` で現況取得** → qty/period/cancel_at_period_end/status を上書き（順序逆転防御・§6.3-4）→ evict |
| `customer.subscription.deleted` | status=CANCELLED / cancelled_at=now → evict |
| `invoice.payment_failed` | status=PAST_DUE → evict |
| `invoice.paid` | period_start/end を invoice 期間で延長・PAST_DUE なら ACTIVE 復帰 → evict |

新プロバイダメソッド（既存破壊なしの追加）:

```java
/** チームプランの Subscription を即時解約する（二重サブスク是正・§6.2 最終防御）。
 *  cancelSubscriptionAtPeriodEnd（期末）とは別に、後着二重 sub を即座に止めるため即時 cancel を用いる。 */
void cancelSubscription(String subscriptionId, String idempotencyKey);
```

### 6.5 解約フロー

- **期末解約のみ提供**（即時解約は提供しない — 設計判断。月額 ¥1,000 規模で日割り返金の実装・CS コストが見合わない。Stripe 既存メソッド `cancelSubscriptionAtPeriodEnd` を流用）

  - AFTER_COMMIT リスナのため失敗しても退会本体はロールバックしない（既存方針維持）。ただし**通知送出失敗を握り潰さず**ログ＋リトライキューに積む
  - この退会×有料チームの分岐を専用 **AC-30** で検証する

## 7. 猶予期間（既存チームの移行・30日）

### 7.1 対象と原則

**課金リリース時点で予約ラインを2本以上持つ既存チーム**が対象。原則: **告知 → 30日の猶予 → 期限後は新規ライン作成のみ制限**。既存ライン・既存予約・既存宛先は永久に剥奪しない（§5.3 と同一原則）。

### 7.2 実装: Flyway backfill（冪等）＋通知バッチ

**方式: リリースマイグレーションでの一括 backfill** を採る（初回アクセス時 lazy 判定は「判定コードが永住する」「テスト対象が増える」ため不採用 — 移行は一度きりの事象として一度きりのデータ操作で終わらせる）:

```sql
-- V146.{yyyyMMddHHmmss}__backfill_team_plan_grace_for_existing_teams.sql
-- 課金リリース時点でライン2本以上の既存チームに FREE 行＋猶予期限を付与する（冪等）。
-- 猶予日数 30 日（§11 要裁可論点の最終値確定後に定数を差し替えてからマージする）。
INSERT INTO team_subscriptions (team_id, plan_type, status, grace_until)
SELECT rl.team_id, 'FREE', 'ACTIVE', DATE_ADD(CURRENT_DATE, INTERVAL 30 DAY)
FROM (SELECT team_id, COUNT(*) AS cnt
      FROM reservation_lines
      WHERE deleted_at IS NULL
      GROUP BY team_id
      HAVING cnt >= 2) rl
WHERE NOT EXISTS (SELECT 1 FROM team_subscriptions ts WHERE ts.team_id = rl.team_id);
```

- **クロスドメイン SELECT**（payment → reservation テーブル）は移行 SQL に限り許容する（一度きりのデータ backfill であり実行時依存を作らない。設計書に理由明記 — 本注記がそれ）
- UNIQUE(team_id)（§3.2.2）より**前**の実行順にならないようタイムスタンプ採番順に注意（backfill は ALTER の後）
- 猶予期限は `team_subscriptions.grace_until`。`entitlement()` が `grace_until >= today` を「猶予中＝ゲート免除」と解釈（§4.1）
- **期限後の挙動**: `grace_until < today` になった瞬間、`createLine` のみ 402（自動・バッチ不要。判定は読み取り時に毎回評価）。行の掃除も不要（grace_until は過去日のまま残って歴史になる）
- 猶予中に購入 → `checkout.session.completed` で grace_until=NULL（§6.4.3 遷移表）

### 7.3 告知

1. **FE 常時バナー**: 猶予中チームのライン管理タブ・プラン画面に「⏳ {date} まで移行期間（ライン{n}本を継続するには基本プランが必要です）」（`graceUntil` は §5.2 の一覧 API 同梱で FE へ届く — 追加 API 不要）
2. **通知1回**: 既存 notification 基盤で猶予対象チームの ADMIN へリリース時に1回送出。`@BatchEndpoint` の手動トリガーバッチ（SYSTEM_ADMIN 実行・送出済みチームはスキップの冪等設計。送出記録は notification 側の既存 dedup で担保）

| 8.1 | `ReservationNotificationRecipientService`（F03.4 機能D） | 宛先4件目で常に 402 | 有料チームは 10 件まで登録可に**解放** | ✅ プラス方向のみ（機能が増える。既存データ・既存挙動の破壊なし） |
| 8.2 | `ModuleService.enableModule`（`requiresPaidPlan` モジュール） | 有料要求モジュールは常に有効化不可 | 有料チームは有効化可に**解放** | ✅ プラス方向のみ。**ただし注意**: 現 main で `requiresPaidPlan=true` のモジュールがシードに存在するか実装時に確認し、存在する場合「解放されるモジュール一覧」を検分でマスターへ報告する（意図しない機能の突然解放を裁可対象にする） |

| 8.5 | `DailyAggregationBatchService.countActivePaidSubscriptions`（analytics） | 恒常 0 | 有料チーム数を正しく集計 | ✅ 集計の正直化（ダッシュボードの時系列に段差が出るのは事実の反映） |
