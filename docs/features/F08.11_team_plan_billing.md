# F08.11: チームプラン課金（予約ライン従量サブスクリプション）

> **ステータス**: 🟡 精査待ち（設計初稿・6観点2度精査は未実施）
> **実装フェーズ**: Phase 3 拡張（予約 v2 完了後の課金化第一弾）
> **最終更新**: 2026-07-08
> **関連ドキュメント**: F03.4 予約管理（ライン上限20・`TeamPlanService` フリーミアム判定）、F03.4.2 枠ライン軸（ライン上限 5→20 拡張）、F08.9 会費・ペイウォール（会員→チーム/組織の課金。**本設計とは受益方向が逆**）、F09.13 通知プリペイドクレジット（Checkout→webhook付与の完成形・写経元）、F13 ストレージプラン（SYSTEM_ADMIN プランマスタの型・写経元）、F01.3 テンプレート・モジュール（`requiresPaidPlan` モジュール）

> **マスター確定の課金モデル（不変・本設計で逸脱禁止）**:
> 予約する側（会員・利用者）は**完全無料**。負担者は導入チームのみ。
> **無料枠=予約ライン1本**（機能制限なし・ライン数のみ）／**基本プラン ¥1,000/月=3ラインまで**／**追加ライン ¥500/月/本**（4本目以降・物理上限20の内側）。
> チームごとに Stripe サブスクリプション **1契約**（platform 直課金・Connect 不使用）＝基本プランの Price ＋ 追加ラインの Price（quantity=N・licensed）。数量変更は Stripe の proration に任せる。
> 既存チームには**猶予期間つき適用**（30日）。価格はマスタ化（SYSTEM_ADMIN 管理・初期値 1000/500・JPY・将来変更可能）。

## 1. 概要

整骨院・美容室・飲食店等のサービス業チームが使う予約機能（F03.4 系）の**ライン数を課金軸**とするチーム向けサブスクリプションを導入する。予約ライン（席・ベッド・施術台）はチームの事業規模に比例する自然な従量軸であり、「1ラインまで無料 → 3ラインまで月額 → 4本目以降は1本ごとに追加課金」の段階制で、小規模チームの無料利用を守りつつ事業利用から対価を得る。

既存の `TeamPlanService.hasPaidPlan()` / `team_subscriptions`（V9.055）は**器だけ存在し、書き込み実装が一切ない**（`TeamSubscriptionRepository` への save 呼び出しは main 全体でゼロ・実測 2026-07-08）。本設計はこの器を活性化し、チーム課金の**最初の実体**を与える。

### 1.1 非ゴール（明示）

| 非ゴール | 理由 |
|---|---|
| **予約する側（会員・利用者・一般ユーザー）への課金** | マスター確定モデル。予約の申込・キャンセル・履歴閲覧は誰でも完全無料。本設計のいかなる変更もこの原則を破ってはならない |
| Stripe **Connect / エスクロー / destination charge** の使用 | 本課金は「チーム → Mannschaft（platform）」の直課金。F22.1/F08.9 の Connect レール（受領者が第三者）とは資金の向きが異なる |
| **F18（ポイント・ウォレット・残高）** との連携 | F18 は資金決済法対応で凍結中。本設計は Stripe サブスク一本で残高概念を持たない |
| ライン数以外の**機能制限**（無料チームの機能劣化） | 無料枠は「ライン数のみ」の制限。予約メニュー・テンプレート・通知等の機能自体は全プランで同一 |
| 組織（Organization）単位のプラン | 予約ラインはチーム単位の資産（F03.4 §2）。組織課金は将来の別設計 |
| 年額プラン・トライアル | 初期リリースは月額のみ（§11 要裁可論点にトライアル有無を残置） |
| 既存 `PlanType.MODULE/PACKAGE/ORGANIZATION` の実装 | V9.055 の構想値。本設計では使用せず温存（§3.2） |

## 3. データモデル

### 3.1 全体像

```
team_plan_pricing (新規・価格マスタ・SYSTEM_ADMIN管理)
  └─ 基本料/ライン単価/無料ライン数/込みライン数/Stripe Product・Price ID（遅延生成）

team_subscriptions (既存 V9.055 を改修・活性化)
  └─ チームの契約状態の正本。PlanType に BASIC を追加、addon 数量・Stripe item ID・猶予期限を追加

stripe_webhook_events (既存) … webhook 冪等（WebhookIdempotencyService 流用・変更なし)
stripe_customers (既存)      … 購入操作者ユーザーの Stripe Customer（F09.13 と共用・変更なし)
```

購入履歴テーブルは**新設しない**。サブスクの請求実績は Stripe が正本（invoice）であり、FE の請求履歴は Stripe Billing Portal（§6.6）へ委譲する。アプリ側の監査は `audit_logs`（購入・数量変更・解約の操作記録）と `stripe_webhook_events`（受信記録）で足りる — F09.13 が purchases テーブルを持つのは「一回払いでクレジット残高を自前管理する」ためであり、サブスクには残高がないため器を増やさない（設計判断）。

### 3.2 `team_subscriptions` の活性化（既存テーブル改修）

**既存テーブルを捨てずに改修して使う**（設計判断）。理由: (1) `TeamPlanService.hasPaidPlan` → `hasActivePaidPlan` の参照系がすでに 3 ドメイン（reservation/template/analytics）から結線済みで、テーブルを替えると参照系全部の付け替えになる。(2) V9.055 のカラム構成（plan_type/status/stripe_subscription_id/period）はサブスク管理の素直な骨格で、不足分の追加で足りる。

**主キーは BIGINT のまま**（既存テーブルの ID 変更はしない — CLAUDE.md 原則6は「新規テーブル」対象。既存 BIGINT は変更しない）。

#### 3.2.1 PlanType の扱い

既存 enum `FREE / MODULE / PACKAGE / ORGANIZATION` に **`BASIC` を追加**する（Java enum 追加のみ。DDL は `VARCHAR(30)` のため変更不要）。

- `BASIC` = 本設計の基本プラン（¥1,000/月・3ライン込み・addon 加算可）
- `MODULE / PACKAGE / ORGANIZATION` は V9.055 時点の構想値で**未使用のまま温存**（削除しない — enum 値の削除は既存行が無くとも逆コンパチ配慮で避ける。将来のプラン多層化の器として残す）
- `isPaidPlan()` の判定（`planType != FREE && status == ACTIVE`）は `BASIC` を自然に有料と判定する

#### 3.2.3 `hasActivePaidPlan` の既存欠陥の修正【根治・必須】

現行クエリ（`TeamSubscriptionRepository:25`）:

```java
@Query("SELECT COUNT(s) > 0 FROM TeamSubscriptionEntity s " +
        "WHERE s.teamId = :teamId AND s.status = 'ACTIVE' AND s.planType <> 'FREE'")
```

**欠陥**: `current_period_end` を一切見ない。webhook が取りこぼされて status が ACTIVE のまま残ると、期限が過ぎても永久に有料扱いになる。書き込み実装ゼロの現状では顕在化していないが、本設計で実体化した瞬間に実害化する。修正:

```java
@Query("SELECT COUNT(s) > 0 FROM TeamSubscriptionEntity s " +
        "WHERE s.teamId = :teamId AND s.status = 'ACTIVE' AND s.planType <> 'FREE' " +
        "AND (s.currentPeriodEnd IS NULL OR s.currentPeriodEnd >= :today)")
boolean hasActivePaidPlan(@Param("teamId") Long teamId, @Param("today") LocalDate today);
```

- `today` は Service 層で注入 `Clock` から算出して渡す（`CURRENT_DATE` 直書きにしない — date-pin テスト可能にする。F08.9 §OVERDUE バッチと同じ流儀）
- `currentPeriodEnd IS NULL` を許すのは**手動付与プラン**（SYSTEM_ADMIN が営業対応で無期限有料化するケース）の器。通常の Stripe 同期行では必ず値が入る
- **期限跨ぎの正常系は webhook（`invoice.paid` → period 延長）が担い、本条件は webhook 欠落時の安全弁**（fail-closed: 課金が確認できなければ無料扱い）
- `Entity.isPaidPlan()` も同一意味論に揃える（`isPaidPlan(LocalDate today)` へシグネチャ変更。判定ロジックの二重定義ズレを残さない）
- `DailyAggregationBatchService.countActivePaidSubscriptions()`（analytics）も同条件へ揃える

- `team_plan_pricing` / `team_subscriptions` は **payment ドメイン**（`com.mannschaft.app.payment`）に置く（既存 `TeamSubscriptionEntity` の現在地に揃える）
- reservation ドメインからは `TeamPlanService`（payment）の**サービスメソッド呼び出しのみ**で参照する（既存 `ReservationNotificationRecipientService` と同型・Entity 直参照禁止）
- `purchased_by_user_id` / `team_id` にクロスドメイン FK は張らない（インデックスのみ・整合はアプリ層）

## 4. エンティトルメント解決（entitledLines の一元化）

### 4.1 解決式（正本）

```
entitledLines(teamId) =
    有料（BASIC ACTIVE・期限内）    → included_line_limit(3) + addon_line_qty
    猶予中（grace_until >= today）  → 無制限（物理上限20のみ）
    無料（上記以外すべて）           → free_line_limit(1)
```

- **PAST_DUE は「無料扱い」**（fail-closed）。ただしゲートは新規作成のみに効くため、既存ライン・既存予約は一切影響を受けない（§5.3）
- **CANCELLED（期末解約後）/ EXPIRED も無料扱い**。期末解約予約中（`cancel_at_period_end=1` かつ期限内 ACTIVE）は**期末まで有料扱い**（Stripe の意味論と一致）

### 4.2 実装: `TeamPlanService` の拡張（判定の一元化）

新しい Resolver クラスは作らず、既存 `TeamPlanService` に集約する（既に3ドメインが依存する判定一元化ポイントであり、第二の判定器を作ると F00 可視性の教訓〔独自述語は漏洩源〕を繰り返す）。

```java
@Service
public class TeamPlanService {

    /** 既存（維持・実装は entitlement() へ委譲に変更） */
    @Cacheable(value = "teamPlan", key = "#teamId")
    public boolean hasPaidPlan(Long teamId) { ... }

    /** 新設: エンティトルメントのスナップショット（FE 表示・ゲート判定の共通ソース） */
    @Cacheable(value = "teamPlan:entitlement", key = "#teamId")
    public TeamPlanEntitlement entitlement(Long teamId) { ... }

    /** 新設: 判定キャッシュの evict（webhook 同期・数量変更・手動付与のすべてが呼ぶ） */
    @Caching(evict = {
        @CacheEvict(value = "teamPlan", key = "#teamId"),
        @CacheEvict(value = "teamPlan:entitlement", key = "#teamId")
    })
    public void evictPlanCache(Long teamId) { /* no-op body */ }
}

/** record: planType / status / entitledLines / currentLineIncluded / addonQty /
    freeLineLimit / includedLineLimit / graceUntil / currentPeriodEnd / cancelAtPeriodEnd */
```

### 4.3 キャッシュ設計

| 項目 | 設計 |
|---|---|
| キャッシュ名 | 既存 `teamPlan`（boolean）＋新設 `teamPlan:entitlement`（record） |
| ストア | Redis（Valkey）— `RedisConfig.cacheManager` 管轄。既定 TTL 30分のまま（個別 TTL 設定は不要。evict が正で TTL は安全網） |
| **evict 契機（必須・全列挙）** | ① webhook 同期（`checkout.session.completed` / `customer.subscription.updated` / `customer.subscription.deleted` / `invoice.paid` / `invoice.payment_failed` の**すべての team_subscriptions 書き込み後**） ② 数量変更 API 成功後 ③ 期末解約予約/取り消し後 ④ SYSTEM_ADMIN 手動プラン付与/剥奪後 |
| evict 漏れの安全網 | TTL 30分 ＋ `hasActivePaidPlan` の期限条件（§3.2.3）。最悪でも30分で自己修復 |
| 直列化注意 | record は Redis JSON 直列化のため、enum フィールドは name() 文字列で持つ（`feedback_cacheable_enum_key_redis` の教訓） |

> **注意（トランザクション境界）**: evict は team_subscriptions 更新トランザクションの**コミット後**に行う（`@TransactionalEventListener(AFTER_COMMIT)` または webhook サービスの tx 完了後呼び出し）。tx 内で evict → ロールバックすると「DB は旧値・キャッシュは消えて次読み込みで旧値再充填」で実害はないが、tx 内 evict → コミット前に別リクエストが旧値を再充填する競合窓は残る。TTL とゲートの fail-closed 性でこの窓は許容する（厳密化は過剰設計）。

## 5. BE 強制ゲート（予約ライン作成）

### 5.1 挿入点: `ReservationLineService.createLine`

既存の RESERVATION_029 ゲート（`ReservationNotificationRecipientService.addRecipient`）の写経。判定順は**物理上限 → エンティトルメント**:

```java
@Transactional
public ReservationLineResponse createLine(Long teamId, CreateReservationLineRequest request) {
    long count = lineRepository.countByTeamId(teamId);
    // (1) 物理上限 20 本（既存・有料でも超過不可）→ 400
    if (count >= MAX_LINES_PER_TEAM) {
        throw new BusinessException(ReservationErrorCode.LINE_LIMIT_EXCEEDED);
    }
    // (2) エンティトルメント超過 → 402（新設）
    TeamPlanEntitlement ent = teamPlanService.entitlement(teamId);
    if (!ent.isInGrace() && count >= ent.entitledLines()) {
        throw new BusinessException(ReservationErrorCode.LINE_PLAN_ENTITLEMENT_EXCEEDED);
    }
    ...（既存処理）
}
```

- 件数は `countByTeamId`（論理削除済みは `@SQLRestriction` で除外＝**削除すれば枠が空く**。通知宛先ゲートと同じ「登録行数」意味論）
- エラーコードは **`RESERVATION_046`（仮置き）** — 現 main の最終番号は 045（実 enum 確認済み 2026-07-08）。**マージ直前に採番の空きを再確認すること**（並行設計 F03.4.5 W2 が 046 以降を使う可能性がある）
- `GlobalExceptionHandler` に `Map.entry("RESERVATION_046", HttpStatus.PAYMENT_REQUIRED)` を追加（029 と同型）

### 5.2 一覧 API へのエンティトルメント同梱（FE ロック表示駆動）

通知宛先（`NotificationRecipientListResponse`）と同型で、ライン一覧をラッパーレスポンス化する:

```
GET /api/v1/teams/{teamId}/reservation-lines
→ {
     lines: ReservationLineResponse[],   // 既存の配列
     currentCount: number,               // 登録済みライン数
     entitledLines: number,              // 権利数（無料1 / 基本3+addon）
     maxLimit: 20,                       // 物理上限
     hasPaidPlan: boolean,
     graceUntil: string | null           // 猶予中なら期限日（FE バナー表示用）
   }
```

- **破壊的変更**（現行は素の配列）のため、**BE 変更と FE 追随（ロックバッジ・トースト）を同一弾・同一 PR 群で実施**し、`docs/openapi.json` 再生成＋`generate:types` を同 PR に含める（`project_openapi_json_chronic_drift`）
- `listActiveLines`（予約者側・公開グリッド用）は**変更しない**（予約者に課金情報を見せる必要がない・回帰面を最小化）

### 5.3 ダウングレード時の方針（剥奪しない）

通知宛先ゲートの方針（§F03.4.D「登録済みは剥奪しない」）を踏襲する:

| 事象 | 挙動 |
|---|---|
| 有料→無料（解約・期限切れ・PAST_DUE） | **既存ライン・既存予約・既存枠・既存宛先はすべて無傷**。予約受付も従来通り継続する |
| 同上 | 制限されるのは**新規ライン作成のみ**（`createLine` の 402） |
| addon 削減（5本契約→3本へ） | 既存の5本はそのまま。新規作成のみ entitled(3+3=6→3+0... ではなく基本3+addon0=3) 超過分が 402 |
| ラインの update / activate / deactivate / delete | **ゲート対象外**（既存資産の操作は常に可能） |

> **なぜ剥奪しないか**: 予約は将来日付の顧客との約束であり、課金状態の変化で既存予約を壊すとチームの顧客（無関係の第三者）に実害が及ぶ。課金は「これ以上広げる」ことだけを堰き止める。

## 6. Stripe 設計

### 6.1 Product / Price 管理（遅延生成）

F09.13 `NotificationCreditCheckoutService.createCheckout` の遅延生成パターンを写経する:

- 初回 Checkout 時に `team_plan_pricing.stripe_product_id` が NULL なら `createProduct` → `createRecurringPrice`（**既存メソッド**・MONTHLY）を基本/addon の2本発行し、マスタ行へ保存
- 価格改定（新マスタ行）時は新しい Price を新規発行（旧 Price はアーカイブせず旧契約が使い続ける）
- Product 名は「チームプラン: {name}」/「追加ライン: {name}」

### 6.2 Checkout Session（mode=subscription・2 line items）

`StripePaymentProvider` に新メソッドを追加する（既存メソッドは破壊しない・インターフェース追記の流儀）:

```java
/**
 * チームプラン購読用 Checkout Session を作成する（mode=subscription）。
 * line_items: [基本 Price × 1] ＋ [addon Price × addonQty（0なら省略）]
 * subscription_data.metadata: { teamSubscriptionId, teamId }
 */
CheckoutSessionInfo createTeamPlanCheckoutSession(
        String basePriceId, String addonPriceId, int addonQty,
        String stripeCustomerId, Long teamSubscriptionId, Long teamId,
        String successUrl, String cancelUrl);
```

購入フロー（F09.13 と同型・PENDING 起票 → webhook 確定）:

1. `POST /api/v1/teams/{teamId}/plan/checkout`（body: `{ addonQty: 0..17 }` — **金額は受けない**）
2. 認可: チーム ADMIN（§9）。既に ACTIVE な BASIC 契約があれば 409（`TEAM_PLAN_ALREADY_SUBSCRIBED` — 数量変更 API を使わせる）
3. `team_subscriptions` を upsert（planType=BASIC・status は新設 `PENDING` を**追加しない**。既存 enum を汚さず、**契約成立まで既存行を書き換えない**方式を採る: Checkout 時点では行を作らず metadata に `teamId` を焼き、`checkout.session.completed` で初めて upsert する。PENDING 中間状態を DB に持たないことで「Checkout 離脱行の掃除」問題を構造的に消す — F09.13 との差異は設計判断として明記）
4. 操作者の Stripe Customer を取得 or 生成（`stripe_customers` 共用・F09.13 写経）
5. Checkout URL を返す → FE リダイレクト
6. success_url: `/teams/{slug}/settings/plan?payment=success` / cancel_url: 同 `?payment=cancelled`

> **addonQty の上限 = 17**（included 3 + addon 17 = 物理上限 20）。範囲外は 400（`TEAM_PLAN_ADDON_QTY_INVALID`）。

### 6.3 数量変更 API（追加ライン購入・削減 → proration は Stripe 任せ）

```
PATCH /api/v1/teams/{teamId}/plan/addon-quantity   body: { addonQty: 0..17 }
```

1. 認可: チーム ADMIN。ACTIVE な BASIC 契約が無ければ 409（`TEAM_PLAN_NO_ACTIVE_SUBSCRIPTION`）
2. Stripe Subscription の addon item quantity を更新（新プロバイダメソッド）:

```java
/**
 * addon subscription item の quantity を更新する。
 * - 増量: proration_behavior=create_prorations（差額即時請求は always_invoice にしない —
 *   次回請求に按分合算。少額都度決済の手数料負けを避ける）
 * - qty 0→N: addon item を追加（SubscriptionItem.create）
 * - qty N→0: addon item を削除（SubscriptionItem.delete・proration あり）
 * - idempotencyKey で再送二重適用を Stripe 側でも拒否
 */
SubscriptionInfo updateTeamPlanAddonQuantity(String subscriptionId, String addonPriceId,
                                             int newQty, String idempotencyKey);
```

3. DB 反映は **API 応答で先行更新＋webhook（`customer.subscription.updated`）で確定同期**の二段。API 成功時に `addon_line_qty` と `stripe_addon_item_id` を更新して即時 evict（UX: 画面が即座に新権利数を映す）。webhook は同じ値の冪等上書き（真実の最終同期）
4. **削減時も既存ラインは剥奪しない**（§5.3）。FE は「現在のライン数より権利数が小さくなる」場合に警告モーダルで影響（新規作成ロック）を明示してから実行

### 6.4 Webhook 同期

#### 6.4.1 ルーティング（既存 dispatcher との共存・重要）

現行 `StripeWebhookService.handleWebhook` は `invoice.*` / `customer.subscription.deleted` を**無条件で `MembershipSubscriptionWebhookService` へ委譲**している（`isSubscriptionEvent`・実測）。チームプランのサブスクイベントも同じ型で届くため、**subscriptionId の帰属による振り分け**を dispatcher に追加する:

```
if (isSubscriptionEvent(type) || type == "customer.subscription.updated") {
    subscriptionId をペイロードから解決
    → team_subscriptions.stripe_subscription_id にヒット → TeamPlanWebhookService
    → それ以外（membership_subscriptions ヒット含む）      → 既存 MembershipSubscriptionWebhookService
}
```

- `customer.subscription.updated` は現行 membership が**購読していない**イベント（`isSubscriptionEvent` は invoice.*/deleted のみ）。team plan で新規購読するが、membership 側に流れても既存 default 分岐（IGNORED ログ）に落ちるだけで無害
- 帰属解決は `stripe_subscription_id` の UNIQUE インデックス1発（§3.2.2）。**membership 側の既存挙動は一切変えない**（回帰面ゼロが受け入れ条件 §13）
- `checkout.session.completed` は metadata（`teamSubscriptionCheckout=true` / `teamId`）で振り分ける（F09.13 の `notificationCreditPurchaseId` 分岐と同型。`WebhookEventInfo` record に `teamId` 系フィールドを追加）

#### 6.4.2 イベント別処理（`TeamPlanWebhookService`・新設）

冪等は既存 `WebhookIdempotencyService` を**そのまま流用**（tryBegin → dispatch → markProcessed/markFailed。`MembershipSubscriptionWebhookService.handleWebhook` の構造を写経。失敗は FAILED 記録＋再送出で Stripe 再送に委ねる）。

| イベント | 処理 |
|---|---|
| `checkout.session.completed`（teamId metadata あり） | `team_subscriptions` を upsert: planType=BASIC / status=ACTIVE / stripe_subscription_id / base・addon item id / addon_line_qty / period / purchased_by / **grace_until=NULL（猶予チームが購入したら猶予は役目を終える）** → evict |
| `customer.subscription.updated` | quantity・period・cancel_at_period_end・status を DB へ同期（数量変更 API の確定同期・Stripe ダッシュボード直操作の取り込み） → evict |
| `customer.subscription.deleted` | status=CANCELLED / cancelled_at=now → evict（期末解約の期日到来・即時削除の双方をこれで受ける） |
| `invoice.payment_failed` | status=PAST_DUE → evict（Stripe の Smart Retries は既定のまま利用。再試行成功は invoice.paid で復帰） |
| `invoice.paid` | period_start/end を invoice の期間で延長・status=PAST_DUE なら ACTIVE へ復帰 → evict |

- すべての書き込みは**同値冪等**（同じイベント再処理で結果が変わらない）
- `livemode` 不一致（test イベントが本番へ）は IGNORED（既存流儀）

### 6.5 解約フロー

- **期末解約のみ提供**（即時解約は提供しない — 設計判断。月額 ¥1,000 規模で日割り返金の実装・CS コストが見合わない。Stripe 既存メソッド `cancelSubscriptionAtPeriodEnd` を流用）
  - `POST /api/v1/teams/{teamId}/plan/cancel` → `cancel_at_period_end=true`・DB フラグ更新・応答に「{period_end} まで利用可」
  - `POST /api/v1/teams/{teamId}/plan/reactivate` → 期末前の解約取り消し（`cancel_at_period_end=false` へ戻す新プロバイダメソッド `resumeCancelledSubscription`）
- 期日到来で Stripe が `customer.subscription.deleted` を送出 → §6.4.2 で CANCELLED 化
- **購入者ユーザーの退会**: サブスクは購入者の Stripe Customer に紐づくため、購入者退会時は当該チームのサブスクを**期末解約予約し、チームの全 ADMIN へ通知**（別 ADMIN が自分のカードで再購入する導線）。既存 `WithdrawalStripeHandler`（現状スタブ・「未実装」ログのみ）に本処理を実装する — 未実装は未実装として対処する原則

### 6.6 請求履歴・支払い方法変更（Stripe Billing Portal）

自前の請求履歴画面は作らず、**Stripe Billing Portal**（customer portal session）へリンクする:

## 7. 猶予期間（既存チームの移行・30日）

### 7.1 対象と原則

**課金リリース時点で予約ラインを2本以上持つ既存チーム**が対象。原則: **告知 → 30日の猶予 → 期限後は新規ライン作成のみ制限**。既存ライン・既存予約・既存宛先は永久に剥奪しない（§5.3 と同一原則）。

### 7.2 実装: Flyway backfill（冪等）＋通知バッチ

**方式: リリースマイグレーションでの一括 backfill** を採る（初回アクセス時 lazy 判定は「判定コードが永住する」「テスト対象が増える」ため不採用 — 移行は一度きりの事象として一度きりのデータ操作で終わらせる）:

```sql
-- V146.{yyyyMMddHHmmss}__backfill_team_plan_grace_for_existing_teams.sql
-- 課金リリース時点でライン2本以上の既存チームに FREE 行＋猶予期限を付与する（冪等）。
-- 猶予日数 30 日（§11 要裁可論点の最終値確定後に定数を差し替えてからマージする）。
INSERT INTO team_subscriptions (team_id, plan_type, status, grace_until)
SELECT rl.team_id, 'FREE', 'ACTIVE', DATE_ADD(CURRENT_DATE, INTERVAL 30 DAY)
FROM (SELECT team_id, COUNT(*) AS cnt
      FROM reservation_lines
      WHERE deleted_at IS NULL
      GROUP BY team_id
      HAVING cnt >= 2) rl
WHERE NOT EXISTS (SELECT 1 FROM team_subscriptions ts WHERE ts.team_id = rl.team_id);
```

- **クロスドメイン SELECT**（payment → reservation テーブル）は移行 SQL に限り許容する（一度きりのデータ backfill であり実行時依存を作らない。設計書に理由明記 — 本注記がそれ）
- UNIQUE(team_id)（§3.2.2）より**前**の実行順にならないようタイムスタンプ採番順に注意（backfill は ALTER の後）
- 猶予期限は `team_subscriptions.grace_until`。`entitlement()` が `grace_until >= today` を「猶予中＝ゲート免除」と解釈（§4.1）
- **期限後の挙動**: `grace_until < today` になった瞬間、`createLine` のみ 402（自動・バッチ不要。判定は読み取り時に毎回評価）。行の掃除も不要（grace_until は過去日のまま残って歴史になる）
- 猶予中に購入 → `checkout.session.completed` で grace_until=NULL（§6.4.2）

### 7.3 告知

1. **FE 常時バナー**: 猶予中チームのライン管理タブ・プラン画面に「⏳ {date} まで移行期間（ライン{n}本を継続するには基本プランが必要です）」（`graceUntil` は §5.2 の一覧 API 同梱で FE へ届く — 追加 API 不要）
2. **通知1回**: 既存 notification 基盤で猶予対象チームの ADMIN へリリース時に1回送出。`@BatchEndpoint` の手動トリガーバッチ（SYSTEM_ADMIN 実行・送出済みチームはスキップの冪等設計。送出記録は notification 側の既存 dedup で担保）

| # | 消費箇所 | 現在の挙動（恒常 false） | 実体化後（有料チーム） | 方向 |
|---|---|---|---|---|
| 8.1 | `ReservationNotificationRecipientService`（F03.4 機能D） | 宛先4件目で常に 402 | 有料チームは 10 件まで登録可に**解放** | ✅ プラス方向のみ（機能が増える。既存データ・既存挙動の破壊なし） |
| 8.2 | `ModuleService.enableModule`（`requiresPaidPlan` モジュール） | 有料要求モジュールは常に有効化不可 | 有料チームは有効化可に**解放** | ✅ プラス方向のみ。**ただし注意**: 現 main で `requiresPaidPlan=true` のモジュールがシードに存在するか実装時に確認し、存在する場合「解放されるモジュール一覧」を検分でマスターへ報告する（意図しない機能の突然解放を裁可対象にする） |
| 8.3 | `ModuleService` カタログ応答（`TeamModuleCatalogResponse.hasPaidPlan` / Org 側は常時 false のまま） | FE 表示が常に「無料」 | 有料チームは「有料プラン加入中」表示 | ✅ 表示の正直化のみ |
| 8.4 | `NotificationRecipientListResponse.hasPaidPlan`（FE ロック表示） | 常にロック表示 | 有料チームはロック解除表示 | ✅ プラス方向のみ |
| 8.5 | `DailyAggregationBatchService.countActivePaidSubscriptions`（analytics） | 恒常 0 | 有料チーム数を正しく集計 | ✅ 集計の正直化（ダッシュボードの時系列に段差が出るのは事実の反映） |
