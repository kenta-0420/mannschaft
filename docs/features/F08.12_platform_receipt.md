## 1. 概要

Mannschaft **運営（プラットフォーム事業者）自身が発行者**となる領収書および適格請求書（インボイス）を発行する機能。

F08.4 が扱うのは「チーム・組織の ADMIN が、会費・イベント参加費に対して**自分の団体名義で**発行する領収書」である。本書が扱うのはその逆で、「**Mannschaft 運営が、運営の収入に対して支払者（広告主・組織）へ発行する証憑**」である。発行者が違うだけで文書としての性質・法的要件（インボイス制度・電子帳簿保存法）は同じであるため、**テーブル・エンティティ・PDF 生成基盤を F08.4 と共有し、スコープ種別（`PLATFORM`）で分離する**。

### 対象となる運営の収入 3 系統

| 系統 | 実装状況（2026-09-02 実測） | 本戦役での扱い |
|------|--------------------------|---------------|
| 広告費（`ad_invoices`） | 稼働形。月次バッチ + Stripe Invoice + 手動 markPaid。**後払い（請求書方式）は本戦役で廃止し、Stripe 一本にする（§5.0）** | **第1段で対応** |
| 通知プリペイドクレジット（`notification_credit_purchases`） | 稼働形。Stripe Checkout → Webhook → 残高加算 | **第1段で対応** |
| 月謝サブスク（`billing_invoices`） | **DDL のみ実在。Java エンティティが 1 つも無く投影実装が空** | **第2段（後追い）** — §10 |

### 本ドキュメントのスコープ

| 機能 | 説明 |
|------|------|
| PLATFORM 発行者設定 | 運営の発行者名・住所・登録番号（インボイス）を 1 行だけ保持する |
| 運営領収書の発行 | 広告費入金・クレジット購入完了を契機に自動発行 |
| 広告費の後払い廃止 | `BillingMethod.INVOICE` を選択不可にし、決済を Stripe 一本にする（§5.0。御裁可済み） |
| 請求書 PDF の是正 | `InvoicePdfService`（日本語不可・宛名なし）を PDF 基盤へ寄せ、「決済前の内訳確認用」に性格を変える |
| 支払者向け閲覧 | 広告主・組織が自分宛の領収書／請求書を一覧・PDF 取得 |
| 運営コンソール | SYSTEM_ADMIN による一覧・詳細・無効化・再発行 |
| 電子帳簿保存法の原本保存 | PDF 原本を保存し改ざん・削除を防止する共通基盤（**団体側 F08.4 と共用**） |

- 団体（TEAM / ORGANIZATION）が発行する領収書 → F08.4
- Stripe が自動送付するレシート（`receipt_url`）→ 正式な証憑ではないため本書の対象外
- 運営の支出側（仕入・外注費）の証憑受領・保存 → 将来検討
- 会計ソフト（freee / MF）との API 連携 → 将来検討（CSV エクスポートまでを本書の範囲とする）

### 2.1 認可の前提（実コードで裏取り済み・当初の想定は誤りだった）

`AccessControlService.resolveEffectiveRole()` は **`isSystemAdmin(userId)` を最初に評価して priority 1 で即 return する**（`AccessControlService.java`:236-239）。したがって `checkAdminOrAbove(userId, 0L, "PLATFORM")` は SYSTEM_ADMIN に対しては 403 にならず**通る**。

実際の問題はそこではなく、**非 SYSTEM_ADMIN が `ScopeType.valueOf(scopeType)`（同 :256）に到達して `IllegalArgumentException` を投げ、500 になる**ことである。`ScopeType` enum に `PLATFORM` は存在しない。

```
非SYSTEM_ADMIN → resolveEffectiveRole(userId, 0, "PLATFORM")
  → isSystemAdmin=false
  → ScopeType.valueOf("PLATFORM") → IllegalArgumentException → 500
```

**設計方針**: `AccessControlService` に PLATFORM 用の分岐を先に置く。

```java
// AccessControlService（新設ガード。全 check 系の入口）
public void checkPlatformAdmin(Long userId, ReceiptScopeType scopeType) { ... }

// resolveEffectiveRole の冒頭（isSystemAdmin 判定の直後）
if (PLATFORM_SCOPE_TYPE.equals(scopeType)) {
    // SYSTEM_ADMIN は上の分岐で解決済み。ここに来る = 非 SYSTEM_ADMIN
    return Optional.empty();   // → 403（500 にしない）
}
```

これにより、団体 ADMIN が PLATFORM スコープの管理 API を叩いた場合の応答は **403（`COMMON_002`）** に確定する。ただし本設計では**運営領収書の管理 API はそもそも `/api/v1/system-admin/**` 配下に置く**ため、`SecurityConfig.java`:527 の `.requestMatchers("/api/v1/system-admin/**").hasRole("SYSTEM_ADMIN")` によりフィルタチェーンで先に 403 になる。上記のガードは、Service 層が別経路（バッチ・イベントリスナー）から呼ばれた場合の二重防御である。

Controller には `@AuthorizedByPathConfig("/api/v1/system-admin/**")` をクラス付与する。これで `AuthzControllerGuardArchTest` を満たす（既存の `SystemActivityPresetController` と同じ型）。

## 3. DB設計

### 3.0 器の再利用（案A採用。運営専用テーブルは作らない）

マスターの裁可により、**既存 receipt ドメインに `PLATFORM` スコープを足して再利用する**。実測で以下を確認済み。

| 確認項目 | 実測結果 | 帰結 |
|---|---|---|
| `receipts.scope_type` / `receipt_issuer_settings.scope_type` の型 | `VARCHAR(20)`（ENUM ではない）。`V8.023__create_receipts.sql`:4 / `V8.022`:4 | 値の追加に **DDL 変更・マイグレーション不要** |
| JPA マッピング | `@Enumerated(EnumType.STRING)`（`ReceiptEntity.java`:34-36） | Java enum に定数を足すだけ |
| `scope_id` への FK | **無い**（FK は `recipient_user_id` / `issued_by` / `voided_by` の 3 本のみ） | センチネル値でも FK 違反が起きない |
| UNIQUE 制約 | `uq_ris_scope (scope_type, scope_id)` / `uq_r_receipt_number (scope_type, scope_id, receipt_number)` | `scope_type='PLATFORM'` で他スコープと衝突しない |
| `member_payment_id` | **NULL 許容・FK 無し**、単独インデックス | NULL のまま運営領収書を作れる |

したがって `ReceiptScopeType` に定数を 1 つ足す。

```java
public enum ReceiptScopeType {
    ORGANIZATION,
    TEAM,
    /** 運営（Mannschaft 自身）。scope_id は常に PLATFORM_SCOPE_ID。 */
    PLATFORM
}
```

**センチネル `scope_id`**: `scope_id` は `BIGINT UNSIGNED NOT NULL` のため NULL を置けない。`0` を運営スコープの固定値とし、**定数 1 箇所に閉じ込める**。

```java
public final class ReceiptScopes {
    /** PLATFORM スコープの scope_id。実在する team/organization の id は 1 以上のため衝突しない。 */
    public static final Long PLATFORM_SCOPE_ID = 0L;
    private ReceiptScopes() {}
}
```

> **番人（要実装）**: `scope_type = 'PLATFORM'` の行で `scope_id <> 0` のものが作られないことを保証するテスト、および `0L` リテラルが `ReceiptScopes` 以外に散らないことを検査する ArchUnit テストを置く。

### 3.1 既存テーブルの変更

#### `receipts` — 元データ参照の汎用化

現状 `member_payment_id` しか元データを指せない。運営領収書の元データは `ad_invoices` / `notification_credit_purchases` /（将来）`billing_invoices` であるため、汎用列を**追加**する。`member_payment_id` は既存互換のため**残す**（Java 側の参照 74 箇所を無改修にするため）。

| カラム名 | 型 | NULL | デフォルト | 説明 |
|---------|---|------|-----------|------|
| `source_type` | VARCHAR(30) | YES | NULL | 元データ種別（`MEMBER_PAYMENT` / `AD_INVOICE` / `NOTIFICATION_CREDIT_PURCHASE` / `BILLING_INVOICE` / `MANUAL`） |
| `source_ref` | VARCHAR(64) | YES | NULL | 元データ ID の**文字列表現**（FK は張らない。クロスドメイン FK 禁止原則1） |

```sql
ALTER TABLE receipts
  ADD COLUMN source_type VARCHAR(30) NULL COMMENT '元データ種別',
  ADD COLUMN source_ref  VARCHAR(64) NULL COMMENT '元データIDの文字列表現（FK なし・アプリ層で整合性保証）',
  ADD INDEX idx_r_source (source_type, source_ref);
```

##### なぜ ID 列を `BIGINT` ではなく `VARCHAR(64)` にするのか（実測に基づく判断）

収入 3 系統の主キー型を実測したところ、**揃っていない**。

| 元データ | 主キー型 | 出典 |
|---|---|---|
| `member_payments` | `BIGINT UNSIGNED` | 既存 `receipts.member_payment_id` が `BIGINT UNSIGNED`（`V8.023`:7） |
| `ad_invoices` | `BIGINT UNSIGNED AUTO_INCREMENT` | `V10.062__create_ad_invoices.sql`:2 |
| `notification_credit_purchases` | `BIGINT UNSIGNED AUTO_INCREMENT` | `V9.118__create_notification_credit_purchases.sql`:6 |
| **`billing_invoices`** | **`BINARY(16)`（UUIDv7）** | `V196.20260831142049__expand_billing_center.sql`:494 |

`source_id BIGINT UNSIGNED` で定義すると、**第2段（サブスク）で `billing_invoices.id` を保存も返却もできない**。法的文書であり行数も増える表の列型を後から変えるのは避けたいため、**最初から両方入る型で切る**。

**型と命名の根拠（このリポの既存流儀に合わせた）**:
- **「種別 + ID」の持ち方**は `seal_stamp_logs` に倣う — `target_type VARCHAR(30)` / `target_id` + `INDEX idx_seal_stamp_logs_target (target_type, target_id)`（`V5.013__create_seal_stamp_logs_table.sql`:7-8, 16）。列の並びと複合索引の形はこの流儀どおりにする。
- **「FK を張らない論理参照を文字列で持つ」**場合の命名は billing ドメインの `_ref VARCHAR(...)` に倣う（`psp_invoice_ref` / `psp_subscription_ref` 等。`V151.20260710123257__expand_billing_contracts_psp.sql`:22 のコメントに「論理参照」と明記されている）。
- 両者を合わせて **`source_type` + `source_ref VARCHAR(64)`** とする。`seal_stamp_logs` の `target_id BIGINT` をそのまま真似ると UUID が入らないため、**ID の型だけ billing 流儀に寄せた**。

**格納形式（アプリ層の規約。ぶれると照合が壊れるため厳密に定める）**:
- `BIGINT` 系: 10 進数の文字列。**ゼロ埋めしない**（`"12345"`）
- `UUIDv7` 系: `java.util.UUID#toString()` の**小文字ハイフン付き 36 文字**
- 変換は値オブジェクト `ReceiptSourceRef` の 1 箇所に閉じ込め、`Long` / `UUID` からの生成と復元だけを公開する。**呼び出し側に `String.valueOf(id)` を書かせない**
- `VARCHAR(64)` は UUID 36 文字・`BIGINT UNSIGNED` 最大 20 桁のいずれにも足り、複合索引 `(source_type, source_ref)` も `utf8mb4` の索引長上限に収まる

> **番人（要実装）**: `source_ref` が上記の格納形式（`^\d+$` または小文字 UUID）に一致することを検証するテストを置く。`source_type` ごとに期待する形式が違うため、`ReceiptSourceRef` の生成経路以外から値が入らないことも合わせて検査する。

##### 発行の重複防止 — 生成列による「部分 UNIQUE」で原子的に防ぐ

**要件**: 同一の `(source_type, source_ref)` に対して、**有効な領収書は 1 通まで**。
ただし**無効化されたものは何通あってもよい**（無効化 → 再発行を繰り返せる必要がある）。

**当初案（アプリ層の存在確認のみ）は不十分だった。**
「発行前に `exists` を検査して、無ければ作る」は **TOCTOU（検査と実行の間の競合）**であり、
webhook の重複配送、あるいは webhook と手動補填（§4.1 の `backfill`）の並行実行で、
**両方が「未発行」と判定して領収書を 2 通作れてしまう**。金銭の証憑が二重に出る事故になる。
アプリ層の検査は**補助**であって、防止の主体にしてはならない。

**採用方式: STORED 生成列 + UNIQUE（MySQL に部分インデックスが無いことへの定石）**

```sql
ALTER TABLE receipts
  ADD COLUMN active_platform_source_key VARCHAR(110)
    GENERATED ALWAYS AS (
      CASE WHEN scope_type = 'PLATFORM'
                AND voided_at IS NULL
                AND source_type IS NOT NULL
                AND source_ref IS NOT NULL
           THEN CONCAT(source_type, 0x1F, source_ref)
           ELSE NULL END
    ) STORED
    COMMENT '有効なPLATFORM領収書の重複防止キー。無効化・非PLATFORM・source未設定はNULL',
  ADD UNIQUE KEY uq_r_active_platform_source (active_platform_source_key);
```

**なぜこれで要件が表現できるか**: MySQL の UNIQUE 索引は **NULL を重複とみなさない**。
- 有効な PLATFORM 行 … キーが値を持つ → **同一 source では 1 行しか入らない**
- 無効化された行 … `voided_at` が入った瞬間にキーが `NULL` に**再計算される** → **何通でも並ぶ**
- 団体（TEAM / ORGANIZATION）の行 … 常に `NULL` → **一切影響を受けない**

区切りに `0x1F`（ASCII の Unit Separator）を使うのは、`source_type` と `source_ref` の
境界が値の中身と衝突しないようにするため（`CONCAT` の素朴な連結だと
`"AD" + "1_2"` と `"AD_1" + "2"` が同じ文字列になりうる）。

**この MySQL で実現可能であることを実機で確認した**（憶測ではない）

検証環境: `mannschaft-mysql` コンテナ（`docker-compose.yml`:3 の `mysql:8.0`）、
実バージョン **8.0.46**。使い捨てスキーマ上で `receipts` と同型の表を作り、以下を実測した。

| 検証項目 | 結果 |
|---|---|
| 有効な行が既にある状態で同一 source を INSERT | **`ERROR 1062 Duplicate entry ... for key 'uq_r_active_platform_source'` で拒否** |
| 1 通目を `UPDATE ... SET voided_at = NOW()` | 生成列が `NULL` に**再計算された**（`STORED` でも UPDATE 時に再評価される） |
| 無効化後に同一 source を再発行 | **成功** |
| 再発行分も無効化して 3 通目 | **成功**（無効な行は何通でも並ぶ） |
| `scope_type='TEAM'` で同一 source を 2 行 INSERT | **両方成功**（F08.4 の分割領収書を壊さない） |
| FK を持つ表への生成列 + UNIQUE の後付け `ALTER` | **成功** |

**`V60.004__add_membership_partial_unique.sql` の前例との違い（重要）**

このリポは**過去に同じ手法を試して断念している**。同ファイルの NOTE は
「MySQL 8.0 の制限により、`ON DELETE SET NULL` / `CASCADE` FK が設定されたカラムは
`GENERATED ALWAYS AS` 列の式に使用できない。このため `active_key` の生成列アプローチは廃止し、
一意制約はアプリ層で担保する」と記録している。

**この制限が `receipts` には当たらないことを確認した。**

- 制限の再現も実機で確認した。`ON DELETE SET NULL` 付きの FK 列を生成列の式に使うと
  **`ERROR 1215 Cannot add foreign key constraint`** になる。一方、
  `ON DELETE` 指定の無い素の FK 列を式に使う場合は**成功する**。
  つまり制限は「FK 列すべて」ではなく「参照アクションを伴う FK 列」に対するものである。
- `receipts` の FK は `recipient_user_id` / `issued_by` / `voided_by` の 3 本だけで、
  いずれも `REFERENCES users (id)` のみ（**`ON DELETE` 指定なし**。`V8.023`:43-45）。
- しかも本方式の式が参照するのは `scope_type` / `voided_at` / `source_type` / `source_ref` の
  4 列で、**そのどれも FK 列ではない**。

**つまり `memberships` で成立しなかった理由は `receipts` には存在しない。**
前例をもって「この手法は使えない」と早合点しないよう、ここに理由を残す。

##### 【実装前必読・罠】Flyway に書くだけでは統合テストのスキーマに現れない — `ReceiptEntity` 側にも宣言が要る

**事実（試練の過程で摘出・殿が実ファイルで裏取り済み）**: 本リポジトリの統合テストのスキーマは
**Flyway ではなく Entity（JPA）から生成される**。

- `backend/src/test/resources/application-test.yml`:4 が `hibernate.ddl-auto: create`、
  :21-22 が `flyway.enabled: false`。
- `backend/src/main/resources/application-test.yml`:1-9 の警告コメントが、同名ファイルが
  `src/main` と `src/test` の両方に存在し、Gradle の test ランタイムクラスパスでは
  `build/resources/test` が `build/resources/main` より前に来るため
  **`./gradlew test` では `src/test/resources` 側が本ファイルを完全に隠蔽する**旨を自ら明記している
  （実測: `ddl-auto=create` も `flyway.enabled=false` も test 側の値が採用される）。

**したがって**、上記の生成列 `active_platform_source_key` と
`UNIQUE KEY uq_r_active_platform_source` を Flyway の `ALTER TABLE` に書くだけでは、
統合テスト（`ddl-auto=create` が Entity から素の DDL を組み立てる）のスキーマには
**一切現れない**。AC-78〜AC-85（重複防止・冪等の検証）は Flyway 側だけの実装では
**永久に赤のまま**になるか、あるいは Entity 側のマッピングが偶然 NOT NULL 等を
満たしてしまい**別の理由で見かけ上パスする**（後述）。

**逆側の事故がより重い**: Flyway と Entity の宣言が食い違うと、
**「CI は緑（Entity 由来のテストスキーマでは重複防止が効かないことに気付けない）だが
本番（Flyway 由来の本物のスキーマ）では `active_platform_source_key` の UNIQUE が効いている」**
という組み合わせ自体は安全側だが、**逆向き**——Entity 側だけ UNIQUE 制約を宣言して
Flyway 側の生成列定義を書き忘れる、あるいは式の条件（`scope_type='PLATFORM' AND voided_at IS NULL AND ...`）
がずれる——が起きると、**本番の実 DDL には重複防止の制約が存在しないまま、
テストは Entity 由来の（正しい）制約で走るため CI は緑になり、
本番でだけ運営領収書が二重に発行される**。金銭の証憑が二重に出る事故を、
テストが構造的に見逃す形になる。**Flyway と Entity は必ず両方を同じ内容で更新し、
どちらか一方だけの変更で「対応済み」としてはならない。**

**JPA 側の宣言方法（このリポジトリの前例に倣う）**: DB 生成カラムを Entity にマッピングする
前例が既に 2 件ある。

- `RecruitmentParticipantEntity.java`（`backend/src/main/java/com/mannschaft/app/recruitment/entity/`）
  の `activeSubjectKey` フィールド（:92）:
  `@Column(name = "active_subject_key", insertable = false, updatable = false, length = 100)`
  という形で、**`nullable` 属性は明示的に書かない**。同フィールドの Javadoc（:77-91）に
  理由が詳しく残されている——DB 生成カラムに `nullable=false` を付けても Hibernate は
  INSERT/UPDATE 文自体にこの列を含めないため実質無意味であり、しかも
  `ddl-auto=create` のテストスキーマでは生成式が再現されず**素の `NOT NULL` 列として
  作られてしまう**ため、`nullable=false` を付けると INSERT が全滅する
  （`RecruitmentScopeContractIT` で実測: 29 件中 29 件失敗）。
- `TicketBookEntity.java`（`backend/src/main/java/com/mannschaft/app/ticket/entity/`）の
  `remaining_tickets` も同型（:45 のコメント）。

`active_platform_source_key` も同じ形——
`@Column(name = "active_platform_source_key", insertable = false, updatable = false, length = 110)`
（`nullable` は書かない）——で `ReceiptEntity` に追加する。**式（`CASE WHEN ... THEN CONCAT(...) ELSE NULL END`）
自体を Java 側で再現する必要はない**（`insertable=false, updatable=false` なので Hibernate は
この列に値を書き込まず、DB 側の生成式のみが効く）。

**UNIQUE 制約側**は `@Table(uniqueConstraints = @UniqueConstraint(...))` で
`ReceiptEntity` のクラスレベルアノテーションに追加する。**これが無いと、
`ddl-auto=create` が組み立てるテストスキーマには `uq_r_active_platform_source` 自体が
存在せず、AC-78（直接 INSERT で `DataIntegrityViolationException` が起きることの確認）・
AC-79（並行 20 スレッドで 1 通しか作られないことの確認）は、
テスト環境では制約が無いにもかかわらず、たまたまアプリ層の存在確認
（`issueFor()` の「先に軽い存在確認」）が先に効いて見かけ上パスしうる**。
これは「制約が効いている」ことの証明にならない偽陽性であり、
**本番でだけ制約が効かない**という前項の事故に直結する。実装時は
生成列・UNIQUE 制約の両方を Entity 側に必ず反映すること。

**既存の番人テストは "NULL 許容の食い違い" しか見ていない**: 本リポジトリには
`MigrationEntityNullableConsistencyReportTest`
（`backend/src/test/java/com/mannschaft/app/common/architecture/`）という、
Flyway の最終状態（NULL 許容 / NOT NULL）と Entity 側 `@Column(nullable=...)` の
食い違いを検出する既存の番人（`assertThat(mismatches).isEmpty()` で fail する、
CMP-021 由来の実害を踏まえて番人へ昇格済み）が存在する。ただし
**この番人が突き合わせるのは nullable の一致のみであり、UNIQUE 制約や生成列の
存在・式の一致までは検証していない**。したがって本設計が導入する
`uq_r_active_platform_source` の Flyway↔Entity 一致は、**この既存番人ではカバーされない**。
AC-89（後述）で新設を提案する。

**同種の罠は他の DDL 要素にも及ぶ**: 生成列・UNIQUE に限らず、本書が Flyway で定義する
他の列・表——`receipt_number_sequences`（§3.2）、`source_type` / `source_ref`（本節）、
`pdf_status` / `pdf_attempt_count` / `pdf_failed_at` / `pdf_failure_reason`（次項）、
`receipt_pdf_archives`（§3.3）の `UNIQUE (receipt_id, archive_kind)` を含む全列——も、
**Flyway だけでなく対応する Entity（`ReceiptEntity` / `ReceiptNumberSequenceEntity`
（新設）/ `ReceiptPdfArchiveEntity`）側にも反映しない限り、統合テストでは一切検証できない**。
出陣時はテーブル単位ではなく**列単位**で Flyway → Entity の反映漏れが無いか確認すること。

##### 冪等をどの層で担保するか — 領収書の発行サービスに一元化する

発行契機は 3 系統（広告費の `markPaid()`、通知クレジットの `handlePurchaseCompleted()`、
将来のサブスク）にまたがり、さらに手動補填（`POST /system-admin/receipts/backfill`）もある。
**各ドメインの webhook 側で個別に冪等を書くと、収入源が増えるたびに書き漏れる。**

**方針: すべての発行経路を `PlatformReceiptIssueService.issueFor(sourceType, sourceRef, ...)`
という単一のメソッドに通し、そこで冪等を担保する。**
手動補填も**この同じメソッドを通る**（別経路を作らない）。

```java
// 全経路が通る唯一の入口
public IssueResult issueFor(SourceType type, ReceiptSourceRef ref, ...) {
    // 1) 先に軽い存在確認（正常系で例外を投げないため。防止の主体ではない）
    //    → 既にあればそれを返す（RECEIPT_026 ではなく「既存を返す」= 冪等な成功）
    // 2) INSERT を試みる
    // 3) DataIntegrityViolationException（uq_r_active_platform_source 違反）を捕捉し、
    //    読み直して既存の領収書を返す。握りつぶさず INFO ログに残す
}
```

**このリポの既存パターンに倣った**（新しい流儀を持ち込まない）:

- `WebhookIdempotencyService.tryBegin()`（`backend/.../payment/WebhookIdempotencyService.java`:50-73）が
  まさにこの形である。「先に検索 → 無ければ INSERT → `DataIntegrityViolationException` を捕捉して
  読み直し、勝者の状態で再判定」。:65-67 のコメントは
  「並行受信で UNIQUE 競合 → 勝者の確定状態を読み直して再判定（**症状を隠さず情報ログに残す**）」
  と明記しており、**DB の一意制約を主・アプリ層の検査を従とする**構えである。**これに倣う。**
- 対照的に `BillingIdempotencyService`（`billing/api/BillingIdempotencyService.java`）は
  Valkey に冪等キーを置く方式で、自身の Javadoc に
  「**時間差リトライ（ネットワーク再送・再押下）の吸収に限定**する。完全同時の再送に対する
  厳密な原子性は `active_contract_pointers.uk_acp_slot` が backstop する」（:17-18）と書いている。
  **このリポは既に「アプリ層の冪等は best-effort、DB 制約が最終 backstop」という立場を取っている。**
  本設計もその立場に揃える。

**`WebhookIdempotencyService` だけでは足りない理由**: あれは `event_id`（Stripe の配送単位）で
ゲートするため、**同じ webhook の重複配送は防げるが、「webhook と手動補填」「別々の
event_id で届いた同一請求書への 2 回の paid」は防げない**。
重複の単位が違うので、**source 単位の制約が別途要る**。両者は排他ではなく重ねて使う。

**アプリ層の存在確認を残す理由**: 正常系（既に発行済みの source への再要求）で
毎回 DB 例外を発生させるとログが汚れ、トランザクションのロールバックも起きる。
**先に読むのは速度と可読性のため**であり、**正しさは UNIQUE 制約が保証する**。
この役割分担を実装コメントにも明記すること。

##### F08.4（団体側）との関係 — 覆さない

F08.4 は `ReceiptService.checkDuplicateWarnings()`（`ReceiptService.java`:609-625）で
`findActiveByMemberPaymentId` を引き、既発行があれば `DUPLICATE_PAYMENT` の
**警告を返すだけでブロックしない**。「分割領収書のユースケースがあるため UNIQUE 制約は設けない」
という**意図的な設計判断**（F08.4 §8）である。

**この判断は覆さない。** 本方式の生成列は `scope_type = 'PLATFORM'` を条件に含めるため、
団体側の行は常に `NULL` になり、**制約の対象外**である（上の実機検証で確認済み）。

| | 団体（F08.4） | 運営（本書） |
|---|---|---|
| 重複の扱い | 警告のみ・発行は通る | **DB 制約でブロック** |
| 理由 | 1 回の支払いを複数人・複数枚に分けて発行する実務がある | 運営の収入は「1 決済 = 1 領収書」であり、分割の実務が無い。二重発行は事故でしかない |
| キー | `member_payment_id` | `source_type` + `source_ref` |

**運営側だけ厳格にする**。同じ表を共有しつつ、スコープごとに要件が違うことを
生成列の条件式で表現できるのが、案A（器の再利用）の利点でもある。

> **注意（`source_type` の埋め戻しを禁じる理由）**: §7 のとおり既存の団体領収書に
> `MEMBER_PAYMENT` を埋め戻さない方針だが、仮に将来埋め戻しても、
> 生成列の条件に `scope_type = 'PLATFORM'` が入っているため**分割領収書は壊れない**。
> 条件から `scope_type` を外してはならない。

#### `receipts` — PDF の生成・保存状態

**現状の問題（実測）**: `ReceiptService.java`:661 は
`String pdfStatus = receipt.getPdfStorageKey() != null ? "READY" : "GENERATING";`
と書かれており、状態は `pdf_storage_key` の NULL 判定から**導出**されている。しかも
`ReceiptEntity.updatePdfStorageKey()`（:172）の呼び出し元は **0 件**であるため、
**`pdfStatus` は常に `GENERATING` を返す**。失敗を記録する場所が無く、
「失敗したのか、まだ生成中なのか」を区別できないため、再試行の判断もできない。

`receipt_pdf_archives`（§3.3）は `storage_key` / `content_sha256` が `NOT NULL` の
**成功した原本だけを載せる表**である。失敗は原本ではないので、そこには置けない。
したがって **PDF の生成・保存状態は `receipts` 側に持つ**。この配置を設計上の確定事項とする。

| カラム名 | 型 | NULL | デフォルト | 説明 |
|---------|---|------|-----------|------|
| `pdf_status` | VARCHAR(20) | NO | `'GENERATING'` | `GENERATING` / `READY` / `FAILED` |
| `pdf_attempt_count` | INT UNSIGNED | NO | 0 | 生成・保存の試行回数 |
| `pdf_failed_at` | DATETIME | YES | NULL | 直近の失敗時刻 |
| `pdf_failure_reason` | VARCHAR(500) | YES | NULL | 直近の失敗理由（エラーコード + 要約。**スタックトレースは入れない**） |

```sql
ALTER TABLE receipts
  ADD COLUMN pdf_status         VARCHAR(20)  NOT NULL DEFAULT 'GENERATING' COMMENT 'PDF生成状態（GENERATING/READY/FAILED）',
  ADD COLUMN pdf_attempt_count  INT UNSIGNED NOT NULL DEFAULT 0            COMMENT 'PDF生成・保存の試行回数',
  ADD COLUMN pdf_failed_at      DATETIME     NULL                          COMMENT '直近の失敗時刻',
  ADD COLUMN pdf_failure_reason VARCHAR(500) NULL                          COMMENT '直近の失敗理由',
  ADD INDEX idx_r_pdf_status (pdf_status, updated_at);
```

**既存行への影響**: `DEFAULT 'GENERATING'` が入る。既存の団体領収書は
`pdf_storage_key` が 1 行も書かれていないため、これは**現状の導出結果と同じ値**であり、
挙動は変わらない（後方互換）。

**状態遷移**:

```
   [発行時]  pdf_status = GENERATING, attempt_count = 0
        │
        ├─ @Async 生成 → 原本保存 成功
        │      → receipt_pdf_archives に ORIGINAL 行を INSERT
        │      → pdf_status = READY, pdf_failed_at = NULL, pdf_failure_reason = NULL
        │
        └─ 生成 or 保存 失敗
               → pdf_status = FAILED, attempt_count += 1,
                 pdf_failed_at = now, pdf_failure_reason = <ErrorCode + 要約>
               → 監査ログ PLATFORM_RECEIPT_PDF_FAILED
                      │
                      └─ 次に PDF 取得 API が呼ばれたとき、FAILED なら再試行する
                         （再試行するのは pdf_attempt_count < 5 のときだけ。
                           pdf_attempt_count >= 5 なら再試行せず RECEIPT_031 を返す。
                           無限リトライで外部ストレージを叩き続けない）
```

**`receipts` のデータ項目 UPDATE 禁止（§9.3）との関係**: 禁止対象は
`description` / `amount` / `tax_rate` / `recipient_name` 等の**証憑の内容**であり、
`pdf_status` 系は**内容ではなく生成の進行状態**である。`voided_at` と同じ扱いで
UPDATE を許可する。Service 層の UPDATE 許可列ホワイトリストに明記する。

**再試行上限の境界（`MAX_PDF_ATTEMPTS = 5`）**: 判定は **`pdf_attempt_count >= 5` で打ち切り**とする。
「5 回失敗したらもう試さない」であって「6 回目を実行する」ではない。
`attempt_count` は**試行の直前ではなく失敗時に加算**するため、
値 5 は「5 回失敗済み」を意味する。AC-51 の観測点もこの境界に揃える。

**`ReceiptService.java`:661 は是正対象**とする。導出をやめ、`pdf_status` 列を読む。

### 3.2 新規テーブル `receipt_number_sequences`（採番の直列化解消）

**現状の問題（実測）**: 採番は 3 箇所（`ReceiptService.java`:81-83 / :192-197 / :355-361）で `findByScopeTypeAndScopeIdForUpdate`（`PESSIMISTIC_WRITE`、`ReceiptIssuerSettingsRepository.java`:26-31）により**発行者設定行そのものをロック**して行う。団体スコープでは行がテナントごとに分かれるため実害が小さいが、**PLATFORM は全プラットフォームで 1 行**であり、月次一括発行が全件直列化する。

さらに `bulkCreateReceipts`（:183-259）は :194 でロックを取り :258 まで保持したまま、ループ内で 1 件あたり `memberPaymentRepository.findById` + `resolveUserDisplayName` + `save` の N+1 を最大 50 件回す。PLATFORM で同じ形を使うと、ロック保持時間が件数に比例する。

**反面教師**: `MonthlyInvoiceBatchService.java`:241-244 の `generateInvoiceNumber` は `adInvoiceRepository.count() + 1` で採番している。並行実行すればほぼ確実に重複し `uk_invoice_number` で INSERT が落ちる。**同じ轍を踏まない。**

| カラム名 | 型 | NULL | デフォルト | 説明 |
|---------|---|------|-----------|------|
| `id` | BINARY(16) | NO | — | PK（UUIDv7。`UuidV7Entity` 継承） |
| `scope_type` | VARCHAR(20) | NO | — | `PLATFORM` / `TEAM` / `ORGANIZATION` |
| `scope_id` | BIGINT UNSIGNED | NO | — | スコープ ID（PLATFORM は 0） |
| `period_key` | VARCHAR(8) | NO | — | 期間キー（`YYYYMM`。将来 `YYYY` も許容できる長さ） |
| `next_number` | INT UNSIGNED | NO | 1 | 次に払い出す番号 |
| `created_at` / `updated_at` | DATETIME | NO | — | |

```sql
UNIQUE KEY uq_rns_scope_period (scope_type, scope_id, period_key)
```

**採番方式（3点セット）**:
1. **発行者設定行のロックから切り離す** — 採番は本表の行だけをロックする。発行者設定の読み取りはロックなし（`findByScopeTypeAndScopeId`）。
2. **`period_key` で分割** — `YYYYMM` 単位で行が分かれるため、別月の発行が競合しない。番号も可読になる（例: `PLAT-202609-00001`）。既存 UNIQUE は `receipt_number` の**文字列**に対するものなので、フォーマットを変えても DDL 変更は不要。
3. **短命トランザクションで分離** — 「番号レンジを取る」処理を `REQUIRES_NEW` の独立トランザクションにし、レコード本体を書く親トランザクションのロック保持時間から切り離す。

```java
@Transactional(propagation = Propagation.REQUIRES_NEW)
public int reserveRange(ReceiptScopeType scopeType, Long scopeId, String periodKey, int count) {
    // 行が無ければ INSERT（uq 違反は 1 回だけリトライ）、あれば SELECT ... FOR UPDATE
    // next_number を count 進めて開始番号を返す。呼び出し元はここでコミット済み。
}
```

> **番号の欠番を許容する**: レンジ確保後に本体トランザクションがロールバックすると番号が飛ぶ。**インボイス制度・電子帳簿保存法とも連番の連続性は要件ではない**（重複禁止・改ざん禁止が要件）ため、欠番を許容する。この判断は設計書上の明示的な選択である。

**移行**: 本表の導入は PLATFORM スコープに**先行適用**し、団体スコープは `next_receipt_number` 方式のまま据え置く（後方互換。§8）。団体側の移行は別戦役とする。

### 3.3 新規テーブル `receipt_pdf_archives`（電子帳簿保存法の原本保存）— §9

| カラム名 | 型 | NULL | デフォルト | 説明 |
|---------|---|------|-----------|------|
| `id` | BINARY(16) | NO | — | PK（UUIDv7） |
| `receipt_id` | BIGINT UNSIGNED | NO | — | 対象領収書（`receipts.id`。同一ドメイン内のため FK 可） |
| `archive_kind` | VARCHAR(20) | NO | — | 原本の種別（`ORIGINAL` / `VOIDED`） |
| `storage_key` | VARCHAR(500) | NO | — | オブジェクトストレージ上のキー |
| `content_sha256` | CHAR(64) | NO | — | PDF 原本の SHA-256（改ざん検知） |
| `byte_size` | BIGINT UNSIGNED | NO | — | バイト数 |
| `archived_at` | DATETIME | NO | CURRENT_TIMESTAMP | 保存日時 |
| `retention_until` | DATE | NO | — | 保存期限（`archived_at` + 7年。§9） |
| `retention_backend` | VARCHAR(30) | NO | — | 実際に効いた不変性の担保手段（`S3_OBJECT_LOCK` / `R2_BUCKET_LOCK` / `APP_ONLY`） |
| `created_at` / `updated_at` | DATETIME | NO | — | |

```sql
UNIQUE KEY uq_rpa_receipt_kind (receipt_id, archive_kind)  -- 1 領収書につき種別ごとに 1 原本
INDEX idx_rpa_receipt (receipt_id)
INDEX idx_rpa_retention (retention_until)
CONSTRAINT fk_rpa_receipt FOREIGN KEY (receipt_id) REFERENCES receipts (id)
```

**一意制約を `(receipt_id, archive_kind)` にした理由**: 当初案の `UNIQUE (receipt_id)` は
「1 領収書 = 原本 1 つ」を意図したものだったが、**§3.4 の状態遷移と矛盾していた**。
無効化（void）時には無効化 PDF を**同じ領収書の新しいアーカイブ行として追加**するため、
`receipt_id` 単独の一意制約では void が制約違反で失敗し、AC-42 を満たせない。

電子帳簿保存法の観点でも、**元の原本を上書きせず両方を残すことが要件**である
（無効化は元データの改ざんではなく状態の追加。§3.4）。したがって
「1 領収書に複数のアーカイブ行が並ぶ」ことを前提にした制約へ改める。

- `ORIGINAL` … 発行時に生成した原本。**1 領収書に 1 つだけ。以後どんな操作でも書き換えない**
- `VOIDED` … 無効化時に生成した「無効」表示の PDF。**1 領収書に高々 1 つ**

種別を複合キーに含めることで、「原本の二重登録」と「無効化 PDF の二重登録」の
**両方を DB 制約で防ぎつつ、両者の共存を許す**。

**再発行（reissue）との整合**: 再発行は§3.4 のとおり**新しい `receipts` 行を起こす**
（元の行を書き換えない）。新しい行は自分の `receipt_id` を持つため、
自分の `ORIGINAL` 行を新規に作れる。既存の制約と衝突しない。

**`retention_backend` を列として持つ理由**: R2 と S3 で担保できる強度が違う（§9）。「どの手段で守られた原本か」を行として残さないと、監査時にどの文書が Compliance 相当で守られているか説明できない。

**UUIDv7 / テナント原則との整合**（`docs/architecture/domain_db_design_principles.md`）:
- 原則6（新規テーブルは `UuidV7Entity` 継承）に**従う**。`receipt_number_sequences` / `receipt_pdf_archives` はいずれも UUIDv7 主キー。
- 原則1（クロスドメイン FK 禁止）に**従う**。`receipt_id` は同一 receipt ドメイン内なので FK 可。`source_ref` はクロスドメインなので FK なし。
- 原則7（テナントスコープ Repository は `AbstractTenantAwareRepository` 継承）は、**PLATFORM スコープにはテナントが無い**ため該当しない。既存 receipt ドメインの Repository も `AbstractTenantAwareRepository` を使っていない（`scope_type` + `scope_id` の明示条件で絞る方式）ので、既存パターンを踏襲する。

### 3.4 状態遷移

運営領収書は F08.4 の状態機械をそのまま使う。ただし **PLATFORM では `DRAFT` を使わない**（承認者が SYSTEM_ADMIN しかおらず、承認ワークフローの意味がないため）。

```
[発行契機イベント]
      │  (入金確定: AdInvoiceEntity.markPaid / purchase.markAsPaid)
      ▼
   ISSUED ──(SYSTEM_ADMIN が void)──▶ ISSUED + voided_at ≠ NULL
      │                                        │
      │                                        │ (reissue)
      │                                        ▼
      │                                  新しい ISSUED 行
      │                                  (source_type/source_ref は同じ、
      │                                   description に元番号を記載)
      ▼
  PDF 原本を receipt_pdf_archives に保存（不可逆）
```

**無効化は原本を消さない**。`voided_at` を立て、無効化用 PDF（`pdf/receipt-voided`）を
**`archive_kind = 'VOIDED'` の新しいアーカイブ行として追加**する（§3.3）。
元の `ORIGINAL` 行は書き換えも削除もされず、保持期限まで残る。
`receipt_pdf_archives` の一意制約は `(receipt_id, archive_kind)` であり、この追加を許す。

**PDF の生成・保存状態**は `receipts.pdf_status`（`GENERATING` → `READY` / `FAILED`）で
別途追跡する（§3.1）。証憑の状態機械（`ISSUED` / `voided_at`）とは独立した軸である。

#### 3.4.1 アーカイブ種別ごとの PDF 参照方法（`pdf_storage_key` の扱いを確定する）

void 後は同一領収書に `ORIGINAL` と `VOIDED` の **2 行**が並ぶ。一方
`receipts.pdf_storage_key` は**単一値の列**であり、どちらか一方しか指せない。
無効化 PDF のキーで上書きすれば原本が取得できなくなり（電子帳簿保存法の
原本保存要件に反する）、原本のキーを保持したままだと無効化 PDF を取得できない。
**この列を PDF 取得の参照経路に使うことはできない。**

**確定事項**:

1. **参照は `receipt_pdf_archives` を `(receipt_id, archive_kind)` で引く**。
   一意制約がこの組であるため、必ず 0 件か 1 件に定まる。
   ```java
   Optional<ReceiptPdfArchiveEntity> findByReceiptIdAndArchiveKind(Long receiptId, ArchiveKind kind);
   ```
2. **`receipts.pdf_storage_key` は廃止せず、`ORIGINAL` のキーのキャッシュとして残す**。
   - 意味を「**原本（`ORIGINAL`）の `storage_key`**」に**確定**し、DDL コメントを更新する。
     `VOIDED` のキーは**絶対に書き込まない**（上書き事故を設計で塞ぐ）。
   - 既存の `ReceiptEntity.updatePdfStorageKey()`（現状 呼び出し 0 件）は
     `ORIGINAL` アーカイブ作成時にのみ呼ぶ。
   - **列を落とさない理由**: 既存の団体領収書（F08.4）と共用の列であり、
     落とすと F08.4 側の後方互換を壊す。値は常に `ORIGINAL` に対応するため
     曖昧さは残らない。**取得の正は常にアーカイブ表**であり、この列は
     一覧表示で「原本があるか」を JOIN なしに判定するための冗長キャッシュに留める。

**API 契約（PDF 取得エンドポイント）**:

`GET /api/v1/system-admin/receipts/{id}/pdf` および支払者向けの各 PDF 取得に、
任意クエリパラメータ `kind` を追加する。

| `kind` | 返すもの | 該当が無いとき |
|---|---|---|
| 省略（既定） | **その領収書の現在の状態に対応する PDF**。`voided_at` が NULL なら `ORIGINAL`、NULL でなければ `VOIDED` | `RECEIPT_030`（404） |
| `original` | 常に `ORIGINAL` | `RECEIPT_030`（404） |
| `voided` | 常に `VOIDED`。`voided_at` が NULL の領収書に指定した場合も `RECEIPT_030`（404） | `RECEIPT_030`（404） |

**既定を「現在の状態に対応する PDF」にした理由**:
- **電子帳簿保存法の観点**: 要件は「原本を消さず残すこと」であって
  「既定で原本を出すこと」ではない。`ORIGINAL` はアーカイブ表に不変で残り、
  `kind=original` でいつでも取り出せるため、要件は満たされる。
- **ユーザー体験の観点**: 無効化済みの領収書をダウンロードして、
  「無効」表示のない原本がそのまま出てくるのは**危険**である。
  受領者がそれを有効な証憑として使ってしまう。既定は必ず現在の状態を反映させる。
- 監査・税務調査で原本そのものが要る場面は `kind=original` の明示指定に寄せる。
  **明示した人にだけ原本を渡す**のが、事故の起きにくい既定である。

**FE の扱い**: 一覧・詳細のダウンロードボタンは `kind` を付けずに呼ぶ。
無効化済み行には「無効」バッジを出し、詳細画面にのみ
「原本（無効化前）をダウンロード」の副次リンク（`kind=original`）を置く。

#### 【決定済み】取引先での検索は収入源テーブルへの JOIN で解く

**採用方式**: `recipient_name` を検索対象にせず、**`source_type` + `source_ref` から
収入源テーブルを引いて絞り込む**。暗号化列を検索対象にしない。

| `source_type` | 引く先 | 検索対象の列 |
|---|---|---|
| `AD_INVOICE` | `ad_invoices.advertiser_account_id` → `advertiser_accounts` | `company_name`（`VARCHAR(200) NOT NULL`。平文） |
| `NOTIFICATION_CREDIT_PURCHASE` | `notification_credit_purchases.organization_id` → `organizations` | `name`（平文） |
| `BILLING_INVOICE`（第2段） | `billing_invoices` | `billing_name_snapshot`（平文。`V196`:513） |

実装は 2 段階にする（クロスドメイン JOIN を 1 本の SQL に書かない。原則1）。

```
1. recipient_name（検索語）で該当する収入源の ID 群を各ドメインの Service 経由で引く
2. その ID 群を source_ref に変換し、receipts を (source_type, source_ref) の IN で絞る
   → idx_r_source が効く
```

**新たな平文列を足さない**（`recipient_name_search` 案は不採用）。運営の取引先は法人であり、
その名称は収入源テーブルに**既に平文で存在する**。同じ情報を receipts 側に複製すると、
二重管理になるうえ個人情報の平文コピーを増やすことになる。

**電子帳簿保存法の検索 3 要件を満たせるか — 正直に書く**

| 要件 | PLATFORM（本書） | 判定 |
|---|---|---|
| 日付 | `issued_from` / `issued_to`（`receipts.issued_at`） | **満たす** |
| 金額 | `amount_min` / `amount_max`（`receipts.amount`） | **満たす** |
| 取引先 | 上記の JOIN 方式 | **満たす**（ただし下記の限界あり） |

**満たせない部分（握りつぶさない）**:

1. **`source_type` / `source_ref` が NULL の運営領収書は取引先で検索できない。**
   手動発行（`source_type = 'MANUAL'` で `source_ref` を持たない場合）が該当する。
   → **対策**: PLATFORM の領収書は `source_ref` を必須とする。手動補填でも
   収入源の ID を必ず指定させる（§4.1 の `backfill` は `source_type` + `source_ref` 必須）。
   これにより NULL の運営領収書が生まれない。**AC-86 で検証する。**
2. **収入源の名称が後から変更されると、過去の領収書の検索結果が変わる。**
   `advertiser_accounts.company_name` を改称すると、旧名では引けなくなる。
   領収書の `recipient_name`（スナップショット）は旧名のままなので、**帳簿上の表示と
   検索キーが食い違う**。
   → 電子帳簿保存法は「取引先で検索できること」を求めており、
   *どの時点の名称で* とまでは規定していないため要件自体は満たすが、
   **この挙動は設計上の既知の限界として記録する**。実務で問題になれば、
   収入源側に改称履歴を持たせるのが筋（本書では扱わない）。
3. **団体（F08.4）側の取引先検索は本方式の対象外**であり、**現在も機能していない**（§15-11）。

## 5. ビジネスロジック

### 5.0 【御裁可済み】広告費の後払い（請求書方式）を廃止する — 本戦役の範囲に含む

#### 判断

**広告主の決済方式はクレジット（Stripe）一本とし、`BillingMethod.INVOICE` を廃止する。**

#### 判断理由

現状の後払いを実コードで調べたところ、**回収の裏づけが何も無い**ことが分かった。

| 論点 | 実態 |
|---|---|
| 与信審査 | **無い**。`AdvertiserAccountService.java`:67 は `request.billingMethod()` を検証せず entity にそのまま入れる。**誰でも選べる** |
| 延滞時の制裁 | **無い**。`OverdueInvoiceBatchService`（`@Scheduled(cron="0 0 6 * * *")`）が `ISSUED` かつ `due_date < today` を `OVERDUE` に印を付け、`OverdueInvoiceNotificationListener` が通知とメールを送るだけ。**配信停止も回収手段も無い** |
| 取消 | **無い**。`InvoiceStatus` は `DRAFT / ISSUED / PAID / OVERDUE` の 4 値のみで `VOID` / `CANCELLED` が無い |
| `credit_limit` | `advertiser_accounts.credit_limit DECIMAL(12,2) DEFAULT 100000`（`V10.060`:9）は**列があるだけ**で、与信枠として評価している箇所が無い |

つまり「払わない広告主に、通知を送り続ける」以外に何もできない。

- **与信・督促・貸倒れの運用負担を負わない。** 与信審査も債権回収も、片手間で持てる機能ではない。
- **大手の標準に合わせる。** 主要な SNS 広告はいずれもカード登録済みの事後課金が標準であり、銀行振込の請求書払いは**与信審査つきの大口限定の例外**として運用されている。審査の仕組みを持たないまま例外だけ真似ている状態になっている。
- **本番データがまだ無い今のうちに畳む。** 実データが入ってからでは移行が要る。
- **将来の余地は残す。** 大口向けに与信審査つきで復活させる可能性はあるため、下記のとおり **enum 値と DB の列自体は残し、選択できなくする**方式を採る。

#### 「値を消す」のではなく「選択不可にする」— その理由

**`advertiser_accounts.billing_method` は MySQL の `ENUM('STRIPE','INVOICE')`**（`V10.060__create_advertiser_accounts.sql`:7。実測。VARCHAR ではない）。値を消すには `MODIFY COLUMN` の DDL 変更が要り、既存行に `'INVOICE'` があれば変換で落ちる。

**採用方針**: Java の `BillingMethod` enum からも DB の ENUM 定義からも **`INVOICE` を消さない**。代わりに **入口を塞ぐ**。

| 層 | 対応 |
|---|---|
| DB (`V10.060`:7 の ENUM) | **変更しない**。マイグレーションを増やさない |
| `BillingMethod` enum | **`INVOICE` を残す**。`@Deprecated` を付け、Javadoc に「廃止済み。新規選択不可。将来の与信つき復活のために値のみ保持」と明記 |
| `AdvertiserAccountService`:67 | **`INVOICE` を指定されたら拒否**する（400）。既定は既に `STRIPE`（`AdvertiserAccountEntity`:55-58）なので既定値の変更は不要 |
| `RegisterAdvertiserRequest` | `billingMethod` フィールドを**残す**（API 互換のため）が、`INVOICE` はバリデーションで弾く。省略時は `STRIPE` |
| `MonthlyInvoiceBatchService`:186-191 | **INVOICE 分岐を削除**（下記の付け替えと同時に行う） |
| FE 登録画面 2 本 | **選択肢から `INVOICE` を外す**。方式が 1 つになるので入力欄ごと消し、固定表示にする |

**enum 値を残す判断の理由**: 値を消すと (a) MySQL ENUM の `MODIFY COLUMN` が要る、(b) `billing_method` を生 SQL で INSERT している既存 IT が多数あり全滅する、(c) 将来の復活時に再び DDL が要る。**入口を塞げば目的（新規に後払いを選ばせない）は達成できる**ため、DDL を触らない方を採る。

#### 【重要】STRIPE 経路には `issue()` が無い — 廃止と同時に必ず直す

実コードを追って**既存の重大な欠陥**を見つけた。`AdInvoiceEntity.issue()`（DRAFT → ISSUED）の呼び出し元は **`MonthlyInvoiceBatchService.java`:189 の INVOICE 分岐ただ 1 箇所**である。

```
STRIPE 方式の請求書は issue() が呼ばれず DRAFT のまま
        ↓
Stripe の invoice.paid webhook が markPaid() を呼ぶ
        ↓
markPaid() は「ISSUED または OVERDUE のみ」を要求（AdInvoiceEntity:88-91）
        ↓
IllegalStateException
```

**つまり現状、Stripe 経路の入金確定は成立していない。** 本書の運営領収書は `markPaid()` を発行契機にしている（§5.2）ため、**ここを直さない限り領収書は 1 通も発行されない。**

**是正**: `MonthlyInvoiceBatchService` の INVOICE 分岐を消すのと同時に、**`issue()` を STRIPE 経路（Stripe Invoice の finalize 成功時）へ付け替える**。Stripe への送信が失敗した場合は DRAFT のまま残し、次回リトライに委ねる（現行 :191-197 の catch と同じ方針）。

#### 書類は「領収書」1 本になる — 請求書 PDF の扱い

#### 広告費の丸め不一致（構造的な 1 円ズレ。本戦役で解く）

| 箇所 | 丸め |
|---|---|
| 自社 DB の税額計算 `MonthlyInvoiceBatchService.java`:180 | `RoundingMode.FLOOR` |
| Stripe へ送る金額 同 :217 | `RoundingMode.HALF_UP` |

同一請求内で丸めが食い違うため、**Stripe から実際に引き落とされた額と `ad_invoices.total_with_tax` が 1 円ズレうる**。領収書は「実際に受け取った金額」を書く文書なので、ここがズレると領収書が事実と異なる。

**方針**:
1. **丸めを `HALF_UP` に統一**する（`MonthlyInvoiceBatchService.java`:180 を修正）。日本の消費税の実務慣行としても切り捨て・四捨五入いずれも可だが、**2 箇所で違うことが問題**。
2. その上で、**領収書の金額は「請求書の額」ではなく「実際の入金額」を正とする**。後払い廃止（§5.0）により決済は Stripe 一本になったので、**入金額は常に Stripe webhook の `amount_paid` から取れる**。`ad_invoices.total_with_tax` と差があれば領収書は入金額で発行しつつ差額を監査ログに残す。
3. 既発行の `ad_invoices` に遡及修正は**しない**（過去の請求書を書き換えることこそ改ざんであるため）。

- 宛名が決まるのは **Checkout セッション作成時**（購入レコードを `PENDING` で作る時点。
  `NotificationCreditCheckoutService`:107-118）であり、領収書が生まれるのは
  **その後の webhook**（同 :190）である。**領収書行がまだ存在しない時点の入力**なので、
  領収書側には置けない。
- `receipts.recipient_name` は**発行時のスナップショット**（暗号化列）であり、
  発行時に購入行の値をコピーして入れる。二重管理ではなく、**入力の置き場と
  スナップショットの置き場**という役割の違いである。

#### 既定値と解決順序

発行時の宛名は次の順で解決する。

```
1. purchase.receipt_recipient_name が非 NULL・非空白  → それを使う
2. それ以外                                          → organizations.name（組織名）
3. 組織名も取れない（論理的には起きない）              → RECEIPT_017（受領者名は必須）
```

**FE の入力欄の初期値は「組織名」を prefill する**。多くの購入者はそのまま進めばよく、
必要な人だけ書き換える形にする（空欄にして必須入力を強いると離脱が増える）。

#### Stripe レシートとの宛名不一致（許容する）

Stripe Customer は購入操作者個人の email で作られているため、
**Stripe が自動送付するレシートの宛先と、運営が発行する領収書の宛名は食い違いうる**。

- **この不一致は許容する。** 既存購入者の Stripe Customer を組織単位に作り直すのは
  影響が大きく（既存の支払い方法・課金履歴が紐づいている）、本戦役の範囲を超える。
- **正式な証憑は本機能が発行する領収書**である。Stripe のレシートは
  決済事業者が発行する取引通知であって、適格請求書ではない（F08.4 §1 と同じ整理）。
- FE の購入画面と領収書画面に、この関係を短く注記する（i18n キー
  `platform.purchase.stripeReceiptNotice`）。
- **Stripe Customer を組織単位に作り直すかどうかは別戦役の課題**とし、本書では扱わない。

#### FE への影響

`frontend/app/pages/organizations/[slug]/settings/notification-credits.vue`
（クレジット購入画面。実在を確認済み）に宛名入力欄を追加する。

- ラベル「領収書の宛名」、初期値に組織名を prefill、最大 200 文字
- 「購入後は変更できません（変更には無効化と再発行が必要です）」の注記
- Checkout セッション作成リクエストに `receiptRecipientName` を追加

### 5.5 発行者情報のスナップショット

`receipts` の `issuer_name` / `issuer_address` / `invoice_registration_number` / `is_qualified_invoice` は**発行時点のスナップショット列**（`ReceiptEntity.java`:66-84、DDL `V8.023`:12-18）。運営の登録番号を後から設定しても、**既発行文書は遡って書き換わらない**。§11 の移行はこの性質だけで成立する。

宛名（`recipient_name`）も同じくスナップショットである。§5.4 の購入時入力は
発行時にこの列へコピーされ、以後は購入行を書き換えても領収書は変わらない。

## 7. Flywayマイグレーション

**採番規約**（`backend/.claudecode.md` §18）: `V{origin/main 全体の最大 major + 1}.{yyyyMMddHHmmss}__{説明}.sql`。minor はタイムスタンプ必須（連番禁止。`FlywayTimestampNamingGuardTest` が拒否）。

2026-09-02 時点の本 worktree（origin/main ベース）での最大 major は **198**（実測）。したがって本戦役は **major = 199** を予約する。

> **major はマージ時に再確認して確定する。** 並行セッションが 199 を先に取っている可能性があるため、着地直前に `origin/main` を取り直して最大 major を数え直す。

```
V199.{yyyyMMddHHmmss}__add_source_ref_to_receipts.sql
    -- receipts に source_type / source_ref + idx_r_source を追加

V199.{yyyyMMddHHmmss}__add_active_source_unique_to_receipts.sql
    -- receipts に active_platform_source_key（STORED 生成列）+
    --   UNIQUE uq_r_active_platform_source を追加（§3.1「発行の重複防止」）
    -- 既存行は全件 scope_type <> 'PLATFORM' のためキーは NULL。既存データと衝突しない
    -- ※ source_type / source_ref を追加するマイグレーションより後に置くこと（式が参照するため）

V199.{yyyyMMddHHmmss}__add_pdf_status_to_receipts.sql
    -- receipts に pdf_status / pdf_attempt_count / pdf_failed_at /
    --   pdf_failure_reason + idx_r_pdf_status を追加（§3.1）
    -- pdf_status は DEFAULT 'GENERATING'。既存行は現状の導出結果と同値のため挙動不変

V199.{yyyyMMddHHmmss}__create_receipt_number_sequences.sql
    -- 採番テーブル（UUIDv7 主キー）

V199.{yyyyMMddHHmmss}__create_receipt_pdf_archives.sql
    -- 原本保存テーブル（UUIDv7 主キー）

V199.{yyyyMMddHHmmss}__seed_platform_receipt_issuer.sql
    -- receipt_issuer_settings に PLATFORM 行を 1 行投入
    -- scope_type='PLATFORM', scope_id=0, is_qualified_invoicer=FALSE,
    -- invoice_registration_number=NULL（§11）
    -- INSERT ... ON DUPLICATE KEY UPDATE id=id で冪等にする
```

**マイグレーション上の注意点**:
- `receipts` への列追加のうち `source_type` / `source_ref` / `pdf_failed_at` / `pdf_failure_reason` は **NULL 許容の ADD COLUMN** であり、既存行への影響は無い。`pdf_status` / `pdf_attempt_count` は `NOT NULL DEFAULT` 付きだが、既定値が**現状の導出結果と同値**（既存行は `pdf_storage_key` が全件 NULL のため `GENERATING`）なので挙動は変わらない。既存の団体領収書は `source_type` / `source_ref` とも `NULL` のまま残る（`MEMBER_PAYMENT` への埋め戻しは行わない。行数が多く、`member_payment_id` から一意に導出できるため不要）。
- `scope_type` は `VARCHAR(20)` なので `PLATFORM` を入れるための DDL 変更は不要（§3.0）。
- **`test` プロファイルは Entity 由来の DDL を使い Flyway シードが走らない**（既知の罠）。したがって PLATFORM 発行者行のシードに依存する統合テストは、**テスト側でフィクスチャとして自分で 1 行入れる**こと。Flyway シードに依存したテストは CI で偽陰性になる。

## 9. 電子帳簿保存法の原本保存基盤

### 9.1 現状 — 規定はあるがコードが 1 行も無い

F08.4 §5「電子帳簿保存法への対応」および §6 は「S3 Object Lock（Compliance モード、Retention 7年）」「専用バケット `mannschaft-receipts`」を規定している。**実装は存在しない**（実測）:

- `pdf_storage_key` 列と `ReceiptEntity.updatePdfStorageKey()` は**定義だけで呼び出し 0 件**
- PDF はリクエストのたびにオンデマンド生成しており、原本という概念が無い
- `mannschaft-receipts` バケットの定義も無い（`StorageProperties` はバケット 1 つ）

したがって「7 年保存・改ざん防止」は**紙の上だけの規定**である。本戦役で団体側・運営側**共通の保存基盤**として実装する。

### 9.2 重大な検証結果 — Cloudflare R2 は S3 Object Lock に対応していない

現在の既定ストレージ実装は **`R2StorageService`（Cloudflare R2）** である。`S3StorageService` は `@ConditionalOnProperty(prefix="storage", name="provider", havingValue="s3")` が付いており、`R2StorageService` は**無条件 `@Service`**（実測）。`application.yml`:196-202 も R2 の設定のみで、`storage.provider` の記述が無い。**つまり本番は R2 で動く。**

Cloudflare 公式ドキュメントを確認した結果:

| 機能 | R2 の対応 |
|---|---|
| `PutObjectLockConfiguration` / `GetObjectLockConfiguration` | **未実装** |
| `PutObjectRetention` / `PutObjectLegalHold` | **未実装** |
| `x-amz-object-lock-mode`（COMPLIANCE / GOVERNANCE） | **未実装** |
| バケットのバージョニング（`PutBucketVersioning`） | **未実装** |
| **Bucket Lock**（Cloudflare 独自） | **対応**。プレフィックス単位の保持ルール（期間指定・日付指定・無期限）。複数ルールが重なる場合は最も長い保持が優先。ルールが 1 つでもあるとバケットを空にできない |

**つまり F08.4 が規定する「S3 Object Lock Compliance モード」は R2 上では実現できない。** これは設計書に書かれていた前提の誤りであり、本書で是正する。

出典:
- https://developers.cloudflare.com/r2/api/s3/api/
- https://developers.cloudflare.com/r2/buckets/bucket-locks/

### 9.3 設計 — 3 層の不変性担保

`StorageService` インターフェースに保存操作を足すのではなく、**保持ポリシーの適用は実装ごとに違う**ため、専用の抽象を切る。

```java
public interface ImmutableArchiveService {
    /** 原本を書き込み、保持期限を適用する。既存キーへの上書きは拒否する。 */
    ArchiveResult archive(String key, byte[] content, String contentType, LocalDate retentionUntil);
    byte[] read(String key);
    /** どの手段で不変性を担保したか（receipt_pdf_archives.retention_backend に入る） */
    RetentionBackend backend();
}
```

| 実装 | 環境 | 担保手段 | 強度 |
|---|---|---|---|
| `S3ObjectLockArchiveService` | AWS S3 を使う場合（`storage.provider=s3`） | `PutObject` に `ObjectLockMode=COMPLIANCE` + `ObjectLockRetainUntilDate` | **最強**。ルート権限でも期限内は削除不可 |
| `R2BucketLockArchiveService` | **現行の本番（R2）** | バケットの `receipts/` プレフィックスに Bucket Lock（7年）を Terraform / Wrangler で事前設定。アプリは「上書きしない」規律を守る | **中**。プレフィックス単位の保持。個別オブジェクトの retain-until は持てない |
| `LocalArchiveService` | ローカル開発（MinIO） | 保持ルールは適用しない。**代わりに `content_sha256` の一致検証を必須にする** | **弱**（開発用） |

**3 層で守る**:
1. **ストレージ層** — 上記の保持ルール
2. **キー設計で上書きを起こさない** — `receipts/{scope_type}/{yyyy}/{receipt_id}/{sha256の先頭16桁}.pdf`。内容が変われば必ず別キーになるため、同一キーへの上書きが原理的に発生しない
3. **アプリ層のハッシュ検証** — 読み出しのたびに `content_sha256` を照合し、不一致なら `RECEIPT_032`（改ざんの疑い）で拒否 + 監査ログ。**R2 の担保が S3 より弱い分をここで埋める**

さらに、`receipts` の `description` / `amount` / `tax_rate` / `recipient_name` 等の
**証憑の内容にあたるデータ項目は発行後 UPDATE 禁止**（Service 層でホワイトリスト制約）。
UPDATE を許可するのは `voided_at` / `voided_by` / `voided_reason` と
`pdf_status` / `pdf_attempt_count` / `pdf_failed_at` / `pdf_failure_reason` /
`pdf_storage_key` に限る。無効化も PDF 状態も**状態の追加であり内容の改ざんではない**。

**アーカイブ行自体は不変**とする。`receipt_pdf_archives` の行は INSERT のみで、
`storage_key` / `content_sha256` の UPDATE と行の DELETE を Service 層で禁止する。
生成の失敗はこの表に行を作らず、`receipts.pdf_status = FAILED` として記録する（§3.1）。

### 9.3.1 【御裁可済み】R2 Bucket Lock は手作業で設定し、手順を本書に残す

IaC（Terraform）での管理が本来は筋だが、**現状このリポにインフラのコード管理は整備されていない**
（CMP-013 の課題）。本戦役でそこまで抱えると範囲が崩壊するため、
**本番バケットへの Bucket Lock 設定は手作業で行い、手順を本書に記録する**。
**IaC 化は CMP-013 に委ねる**（本戦役では扱わない）。

**設定手順（本番。1 回だけ実施する）**

```sh
# 1) 現在のロックルールを確認（初回は空のはず）
npx wrangler r2 bucket lock list mannschaft-storage

# 2) receipts/ プレフィックスに 7 年の保持ルールを追加
#    2557 日 = 220,924,800 秒（7年 + うるう日2回ぶん。7年を下回らないよう切り上げる）
npx wrangler r2 bucket lock add mannschaft-storage     --name receipts-7y     --prefix "receipts/"     --max-age-seconds 220924800

# 3) 反映を確認（receipts-7y が enabled で並ぶこと）
npx wrangler r2 bucket lock list mannschaft-storage
```

| 項目 | 値 | 備考 |
|---|---|---|
| バケット | `mannschaft-storage` | 既存の単一バケット。**専用バケットは作らない**（F08.4 が書いていた `mannschaft-receipts` は実在しない） |
| ルール名 | `receipts-7y` | |
| プレフィックス | `receipts/` | §9.3 のキー設計の先頭と一致させること |
| 条件 | `Age` / `maxAgeSeconds = 220924800` | オブジェクトが 7 年経つまで削除・上書き不可 |

**注意点（Cloudflare のドキュメントで確認済み）**:
- ルールは**新規オブジェクトだけでなく既存オブジェクトにも適用される**。
- プレフィックスを指定しないルールは**バケット全体**に効く。`receipts/` を必ず指定すること
  （指定を忘れると画像等も 7 年消せなくなる）。
- 同一プレフィックスに複数ルールがある場合は**最も長い保持が優先**される。
- **ロックルールが 1 つでもあるとバケットを空にできない。**
- 設定は S3 API ではなく Cloudflare 独自の API / Wrangler / ダッシュボードで行う。
  **アプリケーションコードからは設定しない**（アプリに消せる権限を持たせない方が安全）。

**確認方法**: 設定後、`receipts/` 配下のテストオブジェクトに対して
`DeleteObject` が拒否されることを 1 度だけ手で確かめ、結果を運用記録に残す。

### 9.4 ローカル開発（MinIO）

`docker-compose.yml` の `minio` サービス（profile: `storage`、バケット `mannschaft-storage`）を使う。

**【御裁可済み】ローカル開発ではロックをかけない。**

- 既定は `LocalArchiveService`（**保持ルールなし + ハッシュ検証のみ**）。
  MinIO の Object Lock はバケット作成時にしか有効化できず、有効化すると
  開発者が作ったオブジェクトを 7 年間消せなくなる。開発環境で
  `docker compose down -v` すら詰まる状態を作るのは割に合わない。
- 選択は `mannschaft.storage.archive.backend` プロパティ
  （`s3-object-lock` / `r2-bucket-lock` / `local`。**既定 `local`**）で行う。

**この差異が実機E2E で意味すること（重要）**

| 検証内容 | ローカル / CI | 本番 |
|---|---|---|
| アーカイブ行が作られる（AC-38） | **検証できる** | — |
| ハッシュ不一致を検知して拒否（AC-40） | **検証できる**（`LocalArchiveService` でもハッシュ検証は動く） | — |
| `ORIGINAL` / `VOIDED` の共存（AC-42） | **検証できる** | — |
| **ストレージ層が削除を物理的に拒否する** | **検証できない**（ロックをかけないため） | 本番のみ |

つまり **3 層防御（§9.3）のうち第 1 層だけがローカルで検証できない**。
これを黙って「テスト済み」と扱わないために、代替の検証手段を定める:

1. **第 2 層・第 3 層は自動テストで担保する** — キー設計により同一キーへの上書きが
   起きないこと、読み出し時のハッシュ照合が効くことを AC-40 / AC-59 で検証する。
   ロックが無くても原本の差し替えは検知できる。
2. **アプリ層に削除経路を作らない** — `ImmutableArchiveService` に delete を生やさない。
   これは**ローカルでも検証できる**（ArchUnit で「アーカイブのキーに対して
   `StorageService.delete` / `deleteAll` を呼ぶコードが存在しない」ことを禁止する。AC-60）。
3. **第 1 層は本番で 1 度だけ手動確認する** — §9.3.1 の「確認方法」。
   **自動テストで緑になったことをもって第 1 層の担保とは言わない。**

### 9.5 保持期限

- **7 年**（法人税法の帳簿書類保存期間）
- `retention_until = archived_at + 7年`

**【御裁可済み】保存期間 7 年経過後の PDF は自動削除しない。**

- **理由**: 欠損金が生じた事業年度は帳簿書類の保存期間が **10 年**に延びるなど、
  7 年で切れない例外がある。どの年度が該当するかは決算が確定してから決まるため、
  `retention_until` だけを見て機械的に消すと**消してはいけない証憑を消す**。
  削除は取り返しがつかない一方、保持し続けるコストは PDF 数十 KB × 件数で軽微である。
  **非対称なリスクなので、安全側（消さない）に倒す。**
- **実装しないもの**: 期限到来分を削除するバッチ。**作らない。**
- **実装するもの**: `retention_until <= today` の一覧を返す運用向け API
  （`GET /api/v1/system-admin/receipts/retention-expired`）。**一覧のみで削除はしない。**
- **削除が必要になった場合**: 運用担当が対象を確認したうえで**手動**で行う。
  ストレージ側のロック（§9.3）も別途解除が要るため、誤操作だけでは消せない。
  この二重の手間は意図的なものである。

## 10. 段階リリースの方針

**広告費・通知クレジットを第1段、サブスクを第2段とする 2 段構えを採用する。**

**理由**:
- サブスク系（F20.1 課金センター）は `V196.20260831142049__expand_billing_center.sql` が `billing_invoices`(:494) / `billing_invoice_adjustments`(:536) / `billing_invoice_lines`(:568) を CREATE しているが、**対応する Java エンティティが 1 つも存在しない**（`billing_invoices` を参照する Java コードは 0 件。実測）。`BillingSubscriptionWebhookService` の `invoice.paid` ハンドラは請求書行を 1 件も作っていない。
- **書かれていない表から領収書は作れない。** ここに手を出すと本戦役が「課金センターの投影実装」を含む別の戦役になり、範囲が崩壊する。
- 一方で広告費・通知クレジットは**発行契機が単一地点に収束しており**（§5.2）、器（receipt ドメイン）を共有する形が素直に成立する。

**第2段の前提条件**（満たされたら着手）:
1. `billing_invoices` / `billing_invoice_lines` の Java エンティティと投影処理が実装されていること
2. `tax_behavior` / `tax_rate_basis_points` / `tax_master_snapshot` が実際に書き込まれていること（**税率別内訳を出せる唯一の系統**であり、複数税率の領収書はここでしか作れない）
3. `billing_name_snapshot` 等の宛名列が書き込まれていること

第2段では `receipt_line_items`（F08.4 の複数税率対応）を PLATFORM でも使う。第1段は単一税率（10%）で足りるため使わない。

### 返金・取消の扱い

| 系統 | 現状 | 第1段での扱い |
|---|---|---|
| 広告費 | **返金経路が無い。** `InvoiceStatus` は `DRAFT / ISSUED / PAID / OVERDUE` の 4 値のみで `VOID` / `CANCELLED` が無い（実測）。なお `OVERDUE` は後払い廃止後も Stripe の `invoice.payment_failed` で使われ続けるため残す（§5.0） | 領収書の `void` + 再発行のみ提供。返金そのものは未実装であり、**実装したふりをしない** |
| 通知クレジット | enum に `REFUNDED` はあるが**遷移コードが 0 件** | 同上 |
| サブスク | `billing_invoice_adjustments` が `REFUND` / `CREDIT_NOTE` / `DISPUTE` を持つ（設計済み・未実装） | 第2段 |

**返金時の適格返還請求書（返還インボイス）は本戦役では未対応**とする。返金経路自体が存在しないため。これは正直に未実装として記載する。

## 11. 運営の登録番号未取得からの移行

運営はまだ適格請求書発行事業者の登録番号（T + 13桁）を取得していない可能性がある。**取得を待たずに機能を出せる**設計とする。

1. **開始時**: `receipt_issuer_settings` の PLATFORM 行を `is_qualified_invoicer = FALSE`、`invoice_registration_number = NULL` で作る（§7 のシード）。
   - PDF には登録番号を印字せず、「適格請求書発行事業者以外の者からの領収書」である旨を明記する（F08.4 §1 の非登録事業者対応と同じ扱い）。
2. **取得後**: `PUT /api/v1/system-admin/receipt-settings` で `is_qualified_invoicer = TRUE` + `invoice_registration_number` を設定するだけ。**コード変更もマイグレーションも不要。**
3. **遡及しない**: `receipts.is_qualified_invoice` / `invoice_registration_number` は**発行時点のスナップショット列**（§5.5）。取得前に発行済みの文書は `FALSE` / `NULL` のまま残り、**遡って適格請求書に化けない**。これは電子帳簿保存法の改ざん防止要件から見ても正しい挙動である。
4. **バリデーション**: `is_qualified_invoicer = TRUE` にするとき `invoice_registration_number` が `/^T\d{13}$/` に一致しなければ `RECEIPT_006` / `RECEIPT_007`（既存コードを再利用）。

## 15. 実装しない／未実装であることの明記

本設計書は以下を「未実装である」と正直に記録する。設計上そう見えるだけで動いていない、という誤解を避けるためである。

1. **F08.4 が規定する S3 Object Lock による原本保存は 1 行も実装されていない。** `pdf_storage_key` は書かれたことがなく、PDF は毎回オンデマンド再生成されている。
2. **PDF 用の日本語フォントがリポジトリに存在しない。** `fonts/` には `.gitkeep` しか無く、`PdfFontConfig` は黙ってスキップする。Flying Saucer 経由の PDF すべてに影響する。
3. **`pdf/receipt` テンプレートは現行エンティティと不整合で、生成すれば必ず失敗する。**
4. **`InvoicePdfService` は適格請求書として成立していない**（日本語不可・宛名なし・登録番号なし）。
5. **F20.1 課金センターの `billing_invoices` 系 3 表は DDL のみで Java エンティティが存在しない。**
6. **広告費・通知クレジットに返金／取消の遷移コードが存在しない。** よって返還インボイスも未対応。
7. **STRIPE 方式の請求書は `issue()` が呼ばれず DRAFT のままである。** `issue()` の呼び出し元は `MonthlyInvoiceBatchService.java`:189 の INVOICE 分岐 1 箇所のみ。そのため `invoice.paid` webhook の `markPaid()` は `IllegalStateException` で落ちる。**Stripe 経路の入金確定は現状成立していない**（§5.0 で是正する）。
8. **広告費の後払いには与信審査も回収手段も無い。** 延滞は `OVERDUE` の印と通知だけで、配信停止も取消も存在しない（§5.0 で廃止する）。
9. **`GlobalExceptionHandler` の status マップに `RECEIPT_*` は 10 件しか登録されておらず、`RECEIPT_020` を含む 14 件が既定ステータスに落ちている。**
10. **`Cloudflare R2` は S3 Object Lock・バージョニングのいずれにも対応していない。** F08.4 の「S3 Object Lock Compliance モード」という規定は、現行の本番ストレージでは実現不可能である。
11. **団体側（F08.4）の「取引先での検索」は機能していない。** `receipts.recipient_name` は `EncryptedStringConverter` によるアプリ層暗号化（`ReceiptEntity.java`:52-55）であり、**DB に入っているのは暗号文**である。F08.4 が電子帳簿保存法の取引先検索要件のために張った `FULLTEXT INDEX ft_r_recipient (recipient_name)`（`V8.023`:41）は**暗号文に対する索引**であり、平文の検索語では 1 件も引けない。`LIKE` の部分一致も原理的に効かない。**つまり団体領収書は電子帳簿保存法の検索 3 要件のうち「取引先」を現在満たしていない。**
    - **本戦役の範囲外**（団体側の是正は F08.4 の課題）。
    - **運営側（本書）は §4.1 の JOIN 方式でこの問題を回避する**（暗号化列を検索対象にしない）。
    - 団体側の是正には、暗号化しない検索用列を持つか、検索可能暗号を導入するか、
      あるいは `member_payment_id` 経由で `users` を JOIN するかの判断が要る。
      **「索引を張ったから要件を満たしている」と誤解されたまま残さないよう、ここに記録する。**
