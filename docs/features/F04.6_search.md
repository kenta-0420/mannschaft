## 1. 概要

プラットフォーム内のコンテンツを横断的に検索するグローバル検索機能。タイムライン投稿・チャットメッセージ・掲示板スレッド・ブログ記事・ファイル・ユーザー・チーム・組織・活動記録の9種別を統一的な検索 API で一括検索し、種別フィルタ・日付範囲・スコープ絞り込み・キーワードハイライトを提供する。MySQL 8.0 の FULLTEXT インデックス（N-gram パーサー + BOOLEAN MODE）と LIKE を使い、外部検索エンジンは導入しない。

各フィーチャーが個別に持つ検索 API（`GET /timeline/search`、`GET /chat/channels/{id}/messages/search` 等）は機能内の詳細検索として残し、本機能はそれらを**横断的に統合する入口**として位置づける。

### アーキテクチャ（SearchContributor 契約）

- `search` ドメインは **集約のみ**を担い、`SearchContributor` 契約（種別 `type`・可視件数 `count`・ページ取得）を定義する。
- 各ドメイン（timeline / chat / bulletin / cms / filesharing / activity / auth / team / organization）が **自ドメイン内で** `SearchContributor` を実装する。
- `search` は他ドメインの Repository を直接 DI しない（`CrossDomainRepositoryDependencyArchTest` の凍結を増やさない。旧 `GlobalSearchService` の凍結分は撤去で減らす）。
- 可視性は各ドメインの正準判定を再利用し、検索側で独自述語を作らない。**件数と結果は同一の可視性述語から出す**（取得後フィルタだけで件数を出さない）。
- 所属スコープの解決・名前や slug の解決はバッチで行い、所属スコープ数に比例した SQL（ループ内クエリ）を発行しない。
- **結果に載せる本文・メタ情報（題名・本文・作成者・作成日時・スコープ）は、可視性を判定した同じ SQL の SELECT 列から取る**。可視性判定で ID だけを取り、ID で行を読み直す（JPQL・エンティティ取得）形は禁止（トランザクションの無い 2 本の間に「権限範囲外への移動＋本文更新」が同時にコミットされると、判定外の状態を返すため。CMP-261116-0722 PR-6 検分 P1）。作成日時は DB の UTC 格納値を `DATE_FORMAT` で文字列として読み、`SearchHit#createdAtOfStoredUtc` で瞬間へ直す。番人 `SearchContributorSingleQueryFetchTest`。名前・slug・アバターの解決は可視性に関わらない表示名の解決なので、判定済み SQL が返したスコープ ID・作成者 ID に対してだけ行う。

## 2. スコープ

### 対象ロール

ロールは**スコープ（チーム／組織）単位**で判定する。全所属先のロールの和集合では判定しない（スコープ X で ADMIN・スコープ Y で SUPPORTER の者に、Y の管理者限定コンテンツを見せない）。

| ロール | 操作可能な範囲 |
|--------|--------------|
| SYSTEM_ADMIN | 通常ユーザーと同じ判定（バイパスなし。通常のテナントアカウントではない前提。モデレーション用全件検索は §10 の別行で扱う） |
| ADMIN / DEPUTY_ADMIN | 自スコープの全可視レベルのコンテンツ |
| MEMBER | 自スコープの MEMBERS_ONLY 以下のコンテンツ・公開コンテンツ |
| SUPPORTER | 各ドメインの可視レベル判定に委ねる（MEMBERS_ONLY 等は出ない） |
| GUEST | GUEST ロールしか持たないスコープは**検索母集団から除外**する（403 にはしない。ロールはスコープ単位のため） |

### 対象レベル
- [x] 組織 (Organization) — 組織内コンテンツの横断検索
- [x] チーム (Team) — チーム内コンテンツの横断検索
- [x] 個人 (Personal) — 本人が閲覧可能なコンテンツの横断検索

### 今回対象外とする範囲

次は件数と結果を同じ述語で一致させられない、または別設計が要るため本戦役では検索対象に含めない。扱いは台帳 **CMP-261117-1854** で決める。

- SYSTEM_ADMIN のモデレーション用全件検索（監査ログ付き）
- 特殊公開範囲の記事（CUSTOM / CUSTOM_TEMPLATE / FOLLOWERS_ONLY / PRIVATE）と個人ブログ
- 村（VILLAGE）投稿、大会（TOURNAMENT*）・イベント（EVENT_CHAT）チャット、村ロビー（VILLAGE_LOBBY）、委員会（COMMITTEE）活動記録
- 暗号化されたユーザー氏名（`last_name` / `first_name`）による検索

- `type` は大文字の列挙値（`POST` / `MESSAGE` / `THREAD` / `ARTICLE` / `FILE` / `USER` / `TEAM` / `ORGANIZATION` / `ACTIVITY`）。未定義値は 400。
- 旧 9 業務種別（schedules / events 等）は応答に含めない。

## 4. API設計

### エンドポイント一覧
| メソッド | パス | 認証 | レート制限 | 説明 |
|---------|-----|------|-----------|------|
| GET | `/api/v1/search` | 必要 | 30回/分/ユーザー | グローバル横断検索 |
| GET | `/api/v1/search/suggestions` | 必要 | 60回/分/ユーザー | 検索サジェスト |
| GET | `/api/v1/search/recent` | 必要 | — | 最近の検索キーワード履歴（最新20件） |
| DELETE | `/api/v1/search/recent` | 必要 | — | 検索履歴の全削除 |
| DELETE | `/api/v1/search/recent/{id}` | 必要 | — | 検索履歴の個別削除（本人分のみ。他人の id は 404） |
| GET | `/api/v1/search/saved` | 必要 | — | 保存済み検索一覧 |

JSON のキーはすべて **camelCase**。ページは **0 始まり** の `page` + `size`。

### `GET /api/v1/search`

認証済みユーザーなら誰でも呼べる（可視範囲はユーザーごとに各種別の述語が決める）。

**クエリパラメータ**
| パラメータ | 型 | 必須 | 説明 |
|-----------|---|------|------|
| `q` | String | Yes | 検索キーワード（trim 後 2〜100文字） |
| `type` | String | No | 種別。カンマ区切りで複数指定可（例 `POST,FILE`）。未指定: 全種別 |
| `scopeType` | String | No | `TEAM` / `ORGANIZATION`。指定時は `scopeId` 必須 |
| `scopeId` | Long | No | スコープ ID（`scopeType` と併用） |
| `dateFrom` | String | No | 期間開始日（YYYY-MM-DD） |
| `dateTo` | String | No | 期間終了日（YYYY-MM-DD） |
| `authorId` | Long | No | 投稿者・作成者 ID |
| `page` | int | No | 0 始まり（既定 0）。詳細ビューのみ有効 |
| `size` | int | No | 既定 20、1〜50。詳細ビューのみ有効 |

`dateFrom` / `dateTo` / `authorId` は USER / TEAM / ORGANIZATION には適用しない（投稿日時・作成者の概念がないため無視する）。

`dateFrom` / `dateTo` は**閲覧者の TZ（`users.timezone`。未解決なら `Asia/Tokyo`）の暦日**として解釈し、その TZ の 0 時を日付境界にする（`dateTo` は翌日 0 時未満）。閲覧者 TZ はリクエストスレッドで `UserZoneLocalDateTimeParser#requestZone()` により解決し、`SearchCriteria#viewerZone` に載せて種別ごとの別スレッドへ渡す。結果の `createdAt` は作成の瞬間をオフセット付き ISO 8601 で返す（アプリ層の JST 壁時計を `SearchHit#createdAtOf` で瞬間へ変換）。

**ビュー**
- **概要ビュー**（`type` 未指定、または複数指定）: `meta.viewMode = OVERVIEW`。対象種別ごとに関連度（FULLTEXT 種別）→ 新しい順で最大5件を混在して返す。`page` / `size` は無視。`typeCounts` は9種別すべてのキーを持ち、複数指定時は指定種別のみ実数・それ以外は 0。
- **詳細ビュー**（`type` 単一）: `meta.viewMode = DETAIL`。該当種別の単一テーブルを `OFFSET + LIMIT` で正確にページング。`meta.total` / `page` / `size` / `totalPages` を返す。最終ページを超える `page` は空配列で 200。`meta.total` と `typeCounts[type]` は一致する。

**レスポンス（200 OK）**
```json
{
  "data": {
    "results": [
      {
        "type": "POST",
        "id": 42,
        "title": null,
        "snippet": "今日の練習は<mark>グラウンド</mark>で行います。集合時間は...",
        "highlights": {},
        "relevance": 1.85,
        "author": { "id": 10, "displayName": "田中太郎", "avatarUrl": "https://..." },
        "scope": { "type": "TEAM", "id": 5, "name": "サッカー部" },
        "createdAt": "2026-03-18T09:00:00",
        "url": "/timeline/42",
        "actions": ["LIKE", "BOOKMARK"]
      }
    ],
    "typeCounts": {
      "POST": 12, "THREAD": 3, "MESSAGE": 25, "ARTICLE": 1, "FILE": 2,
      "USER": 1, "TEAM": 0, "ORGANIZATION": 0, "ACTIVITY": 0
    },
    "query": "グラウンド",
    "timedOutTypes": []
  },
  "meta": { "viewMode": "DETAIL", "total": 12, "page": 0, "size": 20, "totalPages": 1 }
}
```

概要ビューの `meta` は `viewMode` を必須とし、`total` / `page` / `size` / `totalPages` は種別をまたぐ意味を持たないため値に依存しない（FE は概要ビューで Paginator を出さない）。

**補足**
- **`typeCounts` は真の可視件数**: 上限で頭打ちにしない（可視11件・不可視3件なら 11）。結果と同一の可視性述語から数える。不可視データを増やしても件数は変わらない。
- **`snippet`**: コンテンツを HTML エスケープしてからキーワード周辺を抜粋し、一致箇所のみ `<mark>` で囲む。**最大200文字**（`<mark>` タグ分を除いた本文基準）。元本文の `<script>` 等は生のまま返らない。FE は `v-html` で表示する。
- **`title`**: プレーンテキスト（`<mark>` なし）。`highlights.title` に `[start, end]`（プレーンテキスト基準）を返す。`snippet` 側の位置は返さない。
- **`relevance`**: FULLTEXT 種別のみのソート用内部値。LIKE 種別（USER / TEAM / ORGANIZATION / ACTIVITY）は `null`。
- **`actions`**: `POST`: LIKE / BOOKMARK、`THREAD`: MARK_READ / BOOKMARK、`FILE`: DOWNLOAD / BOOKMARK、`USER`: SEND_DM、`ARTICLE`: BOOKMARK、`MESSAGE` / `TEAM` / `ORGANIZATION` / `ACTIVITY`: 空配列。実行は各フィーチャーの既存 API を呼ぶ。
- **`timedOutTypes`**: 種別ごとの取得が3秒を超えた、または例外になった種別。**その種別だけ**をスキップし、全体は 200 で他種別の結果と件数を返す（例外で他種別の件数を欠けさせない）。FE は該当タブに警告を出す。
- **FULLTEXT / LIKE の入力処理**: BOOLEAN 演算子（`+ - * " ( ) ~ < > @`）は演算子として解釈させず文字として検索する（各語を `+"語"` の必須フレーズにし、語中の `"` は除く）。LIKE 系は `%` `_` `\` を `\` でエスケープし、値はバインドパラメータで渡す（エスケープ文字 `\` は `ESCAPE` 句にもバインドパラメータで渡す）。いずれも 500 にしない。複数語（スペース区切り、全角スペース含む）は AND 条件。共通処理は `SearchQueryText` / `SearchLikeConditions`。
- **`zeroResultsHelp`**（`typeCounts` が全 0 のとき付与。500 にしない）:
  ```json
  "zeroResultsHelp": { "didYouMean": "グランド", "broaderQuery": "グラウンド" }
  ```
  - `didYouMean`: **本人の検索履歴のみ**から Levenshtein 距離2以内の語を出す。他人の検索語は出さない。候補なしは `null`。
  - `broaderQuery`: 複数語検索で語数を1つ減らした機械的な候補。単一語は `null`。
- **履歴の自動保存**: 入力検証を通った検索のみを、正規化（trim・連続スペースと全角スペースの畳み込み）して UPSERT する。400 になった検索は残さない。
- **FE のプリセットボタン**（API 変更なし）: 「今週」「自分の投稿」「このチーム」等は FE がクエリパラメータを付け替える。

**結果の遷移 URL（`url`）**: BE が実在する FE ルートを返す。
| 種別 | `url` |
|------|-------|
| POST | `/timeline/{id}` |
| MESSAGE | `/chat?channel={channelId}` |
| THREAD | `/teams/{slug}/bulletin?threadId={id}`（組織は組織版ルート） |
| ARTICLE | `blogPostRoute.ts` 準拠（slug） |
| FILE | スコープのファイル一覧（`/teams/{slug}/files` 等） |
| TEAM | `/teams/{slug}` |
| ORGANIZATION | `/organizations/{slug}` |
| ACTIVITY | 現役ルートを ACTIVITY の実装 PR で確認して確定 |
| USER | `/social/{handle}`（有効なソーシャルプロフィールの handle。無いユーザーはリンクなし＝`url: null`） |

**エラーレスポンス**
| ステータス | 条件 |
|-----------|------|
| 400 | `q` が空・空白のみ・2文字未満・100文字超 / `type` に未定義の値 / `scopeType` 指定で `scopeId` 無し / `scopeId` が数値でない / `size` が 1〜50 の範囲外 / `page` が負 / 日付形式不正（エラーコードは `SearchErrorCode`） |
| 401 | 未認証 |
| 429 | レート制限超過（`Retry-After` 付き。検索 30回/分、サジェスト 60回/分。別ユーザーは影響を受けない） |

**scope 指定時の応答**: 本人が所属しないスコープを指定した場合と、存在しない `scopeId` を指定した場合は**同一応答**（200・結果0・件数0）にし、存在を明かさない。

### `GET /api/v1/search/suggestions`

**クエリパラメータ**: `q`（最小1文字）、`limit`（既定5、最大10）。

**レスポンス（200 OK）**
```json
{
  "data": {
    "suggestions": [
      { "text": "グラウンド利用", "type": "KEYWORD", "userId": null, "teamId": null, "organizationId": null, "url": null },
      { "text": "田中太郎", "type": "USER", "userId": 10, "teamId": null, "organizationId": null, "url": "/social/tanaka" },
      { "text": "サッカー部", "type": "TEAM", "userId": null, "teamId": 5, "organizationId": null, "url": "/teams/soccer" }
    ]
  }
}
```

- `KEYWORD`: 本人の `search_histories` の前方一致（上位3件。他人の検索語は出さない）。
- `USER` / `TEAM` / `ORGANIZATION`: 検索本体と**同じ SearchContributor（同一の可視性述語）**を通ったもののみ。照合は検索本体と同じ部分一致（各種別最大2件）。
- `q` が空・空白のみは 400、`limit` が 1〜10 の範囲外は 400。
- FE は debounce 300ms。

### `GET /api/v1/search/recent`

最新20件（`searchedAt DESC`）を返す。同一キーワードの再検索は既存行の `searchedAt` を更新する。

```json
{ "data": [ { "id": 1, "query": "グラウンド", "searchedAt": "2026-03-18T10:30:00" } ] }
```

### 保存済み検索

`POST /search/saved` は `name`（最大50文字）と `queryParams`（`GET /search` のパラメータを JSON で保存）を受ける。**`queryParams` は JSON として検証**し、不正は 400。1ユーザー最大10件で、11件目は 409。`DELETE /search/saved/{id}` は本人のものだけ削除でき、他人の id は 404（存在を明かさない）。

## 5. DB設計

### テーブル一覧
| テーブル名 | 役割 | 論理削除 |
|-----------|------|---------|
| `search_histories` | ユーザーの検索キーワード履歴 | なし |
| `search_saved_queries` | ユーザーの保存済み検索条件 | なし |

### `search_histories`

| カラム名 | 型 | NULL | 説明 |
|---------|---|------|------|
| `id` | BIGINT UNSIGNED | NO | PK |
| `user_id` | BIGINT UNSIGNED | NO | ユーザー |
| `query` | VARCHAR(100) | NO | 正規化済み検索キーワード |
| `searched_at` | DATETIME | NO | 最終検索日時 |

- `UNIQUE (user_id, query)`、`INDEX (user_id, searched_at DESC)`。
- 1ユーザー最大50件。超過時は `searched_at` 最古を物理削除（51件目で最古が消える）。同一キーワードは UPSERT。物理削除（論理削除不要）。

### `search_saved_queries`

| カラム名 | 型 | NULL | 説明 |

## 6. ビジネスロジック

### 検索実行フロー

```
1. 入力検証（q の trim 後 2〜100文字、type/scope/size/page）。不正は 400（履歴に残さない）
2. 履歴を正規化して UPSERT
3. 本人の所属スコープとスコープ別ロールを一括解決（GUEST のみのスコープは除外）
4. 対象種別の SearchContributor を並列実行（各3秒タイムアウト。例外・タイムアウトは種別単位で timedOutTypes へ）
5. 各 Contributor が「同一の可視性述語」で count と page 取得を行う
6. 概要ビュー: 種別ごと上位5件 / 詳細ビュー: OFFSET + LIMIT
7. snippet / title / highlights を生成（HTML エスケープ後に <mark>）
8. 名前・slug を NameResolverService で一括解決しレスポンス返却
```

### 認可（種別ごとの述語）

共通: 論理削除済み（コンテンツ・スコープ双方）は出ない。可視レベルは**スコープごと**に判定する（`resolveVisibleLevels` はスコープ単位）。SYSTEM_ADMIN のバイパスはない。GUEST のみのスコープは母集団から除外する。

**閲覧者の母集団（実装: `SearchViewerResolver`、PR-1 で確定）**:
- 所属の列挙は `AccessControlService#findAffiliatedScopeIds`（`user_roles` ∪ `memberships`）、ロールは `MembershipBatchQueryService#snapshotForUser` の `roleByScope`（スコープごとに権限ロールと所属ロールの最強）。
- SUPPORTER 以上のロールを持つスコープだけを母集団に入れる（GUEST のみ・JOBBER 等の並行ロールのみのスコープは除外）。
- ACTIVE（承諾済み）かつ未アーカイブ・未削除のスコープだけを残す（論理削除済み・アーカイブ済みスコープ経由では仲間もコンテンツも見えない）。
- スナップショットが SYSTEM_ADMIN 扱いになった場合はスコープ別ロールが得られないため、所属スコープを母集団に入れない（安全側。公開のチーム・組織だけが見える）。
- SQL 数は所属スコープ数に依らない定数回。
- `scopeType` / `scopeId` 指定時、そのスコープが母集団に無ければ（非所属・GUEST のみ・存在しない ID）Contributor を呼ばずに全種別 0 件の同一応答を返す。母集団にあれば各 Contributor がそのスコープに絞る（TEAM 種別は `scopeType=TEAM` のときそのチーム自身のみ・`ORGANIZATION` 指定時は 0 件、ORGANIZATION 種別はその逆、USER 種別は共有スコープをそのスコープだけにする）。

| 種別 | 述語 |
|------|------|
| POST | `TimelinePostVisibilityAccessGuard` / `TimelinePostRepository#SEARCH_QUERY` と同じ scope 述語を SQL 化（`TimelinePostSearchContributor` → `TimelinePostKeywordSearchRepository`、件数と取得は同一 WHERE）: PUBLIC、所属 TEAM/ORG（`SearchViewer` の母集団）、配信祖先組織（`TimelineDeliveryScopeResolver` の距離1は CHILDREN/DESCENDANTS・距離2以上は DESCENDANTS。到達先のうち削除・アーカイブ済み組織は除外）、本人の PERSONAL。かつ `deleted_at IS NULL`・`status = PUBLISHED`（投稿者本人の下書き・予約・非表示も出さない）。VILLAGE・FRIEND_*・他人の PERSONAL は対象外。公開済み返信は親のスコープを継承した独立投稿として出す。スコープ指定時はそのスコープの投稿だけ（PUBLIC・PERSONAL・配信到達は含めない）。`authorId` は個人として投稿したもの（`posted_as_type = USER`）の `user_id` に一致させる（チーム/組織名義の投稿から個人を推定させない）。期間は閲覧者 TZ の日付を SQL の `CONVERT_TZ` で UTC 格納基準に変換して比較。author はチーム/組織名義の投稿では null |
| MESSAGE | `ChatMessageSearchContributor` → `ChatMessageKeywordSearchRepository`（件数と取得は同一 WHERE）。次をすべて満たすものだけ: 閲覧者本人の `chat_channel_members` 行がある（EXISTS。未参加の公開チャンネルは対象外、退出・除名＝メンバー行の物理削除の後は出ない）／チャンネル種別が `ChannelType#isScopeChannel` の4種で、種別とスコープ列が対応（`TEAM_PUBLIC`/`TEAM_PRIVATE` は `team_id`、`ORG_PUBLIC`/`ORG_PRIVATE` は `organization_id`）し、そのスコープが `SearchViewer` の母集団（スコープ指定時は `narrowTo` 後）に含まれる（チャンネルのメンバー行が残っていてもスコープ所属が無ければ出ない。DM / GROUP_DM・VILLAGE_LOBBY / EVENT_CHAT / TOURNAMENT* は `team_id` が付いていても対象外）／チャンネルが未削除・未アーカイブ／メッセージが未削除・`is_system = FALSE`・`message_type = 'TEXT'`（INVITE_CARD 除外）・予約未送信（`scheduled_at IS NOT NULL AND scheduled_sent_at IS NULL`）でない。スレッド返信は親と同じチャンネルの可視性に従って対象にする（チャンネル画面のメッセージ一覧は返信も表示するため遷移先から辿れる）。`authorId` は `sender_id`。期間は閲覧者 TZ の日付を `CONVERT_TZ` で UTC 格納基準に変換して比較。scope はチャンネルのチーム／組織。`ChatMessageVisibilityResolver` はチャンネルメンバーシップを見ないため単独ゲートに使わない |
| THREAD | 所属 TEAM/ORG scope の IN（`BulletinThreadVisibilityResolver` の SCOPE_AFFILIATED と同義）。削除・アーカイブ済み除外。PERSONAL / VILLAGE / TOURNAMENT は対象外。種別と scope_id は必ずペアで照合する。**返信（`bulletin_replies`）は対象外**（`BulletinThreadKeywordSearchRepository`） |
| ARTICLE | `status = PUBLISHED` かつ `published_at <= now`、所属または公開を粗く絞り、`MembershipBatchQueryService.resolveVisibleLevels` 相当の可視レベル IN を SQL に入れる（スコープごとのロールで判定: PUBLIC / SCOPE_AFFILIATED / SUPPORTERS_AND_ABOVE は SUPPORTER 以上、MEMBERS_ONLY / MEMBERS_AND_ABOVE は MEMBER 以上、ADMINS_AND_ABOVE は ADMIN のみ）。DRAFT・PENDING_*・REJECTED・ARCHIVED・公開日時前は作成者本人にも出ない。CUSTOM / CUSTOM_TEMPLATE / FOLLOWERS_ONLY / PRIVATE と個人ブログは対象外。非所属者への公開記事は `visibility = PUBLIC` かつ `public_visible = TRUE` かつスコープが PUBLIC・ACTIVE・未アーカイブ・未削除のものに限る（F19.1 公開ページ・sitemap と同条件）。課金ゲート（`content_payment_gates`）付きの記事は、閲覧者が支払い条件を満たすときだけ結果にも件数にも出す。判定は記事を開くときと同じ正準判定（`PaymentGateService#checkAccessBatch` の scope 束縛版）で、ゲートの全支払い項目について（AND）閲覧者本人が受益者（`member_payments.user_id`。払い手 `payer_user_id` は問わない）の `PAID` 記録が `valid_until IS NULL OR valid_until >= CURRENT_DATE - grace_period_days` で存在すること。支払い項目の消失・論理削除・DONATION 型や記事と別スコープの項目のゲートは誰にも解錠しない。SYSTEM_ADMIN・スコープ ADMIN もバイパスしない。`is_title_hidden = FALSE` の「鍵付きタイトルだけ見せる」表示は検索では行わず、未充足なら出さない。payment の `ContentGateAccessService#findUnsatisfiedGatedContentIds`（閲覧者が満たさないゲート付き ID を一括で返す。クエリ数は ID 数に比例しない）の集合を件数と取得の同じ WHERE の `NOT IN` に渡す。実装は `BlogPostSearchContributor` → `BlogPostKeywordSearchRepository`（件数と取得は同一 WHERE、公開日時は `UTC_TIMESTAMP()` と比較、公開スコープ判定は `TeamQueryService` / `OrganizationQueryService#findPublicIds`）（`GlobalSearchArticleVisibilityIT`） |

### 検索サジェスト生成

```
1. q 前方一致で本人の search_histories（上位3件。他人の履歴は使わない）
2. q 前方一致で USER / TEAM / ORGANIZATION を、検索本体と同じ可視性述語を通して取得
3. マージして limit 件に制限
```

### パフォーマンス戦略

- FULLTEXT + ngram（`ngram_token_size = 2`）、BOOLEAN MODE。1文字検索は 400 で拒否。関連度 DESC → `created_at DESC`。
- 並列実行は種別単位・各3秒。1回の検索で発行する SQL 数は所属スコープ数（1件でも30件でも）で変わらない。
- 検索結果はユーザーごとに可視範囲が異なるためキャッシュしない。`typeCounts` を別途キャッシュする場合も、キーにユーザーを含め、可視範囲変更を跨いで古い件数を返さない短い TTL に限る。
- 構造化ログに `query_hash`（SHA-256。生のキーワードは出さない）・種別ごとの所要時間・`timedOutTypes`・`viewMode` を出す。
- FULLTEXT 付きテーブルは月次バッチ等でメンテナンス（OPTIMIZE TABLE）を検討する。
- `chat_messages` は日付条件と併用して範囲を限定する。

## 7. セキュリティ考慮事項

- **認可フィルタリング**: 全クエリに種別ごとの述語（§6）を付加。権限範囲外のデータは結果にも件数にも出さない。存在しない ID と非所属スコープの応答を同一にして存在オラクルを作らない。
- **`is_searchable`**: FALSE のユーザーは USER 種別に出ない。
- **FULLTEXT / LIKE インジェクション防止**: パラメータバインド。BOOLEAN 演算子と `%` `_` `\` をエスケープして文字として検索。
- **snippet の XSS 防止**: HTML エスケープ後に `<mark>` を挿入。
- **履歴のプライバシー**: 履歴・保存済み検索は本人のみ閲覧・削除可能。サジェストと `didYouMean` に他人の検索語を出さない。
- **レート制限**: 検索 30回/分、サジェスト 60回/分（ユーザー単位。超過は 429 + `Retry-After`）。
- **クエリ長制限**: 最大100文字。
- **監査ログ**: 通常の検索は記録しない。SYSTEM_ADMIN のモデレーション検索を導入する場合（§10）に監査ログを設計する。
