## 1. 概要

ログイン後の個人ダッシュボードに、ユーザー登録時に必須入力させている**郵便番号から導出した居住地点**の **今日・明日の天気** を表示するウィジェット。表示項目は天気（アイコン＋テキスト）・最高/最低気温・湿度・降水確率の4つ。

### 本機能が解決する課題

| 課題 | 解決策 |
|------|--------|
| 朝のチーム活動・通学・通勤前にダッシュボードを開いた際、天気アプリへの切替が摩擦になっている | ダッシュボード上で完結 |
| 雨天時に屋外イベント（部活・地域行事）を中止判断したいが、現状アプリ内に判断材料がない | 今日・明日の予報を1ウィジェットに集約 |
| 高齢ケア対象者の見守り（F03.12）で、家族が「明日の最低気温・湿度」を踏まえた服装助言を判断したい | 湿度・最低気温まで明示 |

### 本ドキュメントのスコープ

| 機能 | 説明 |
|------|------|
| 天気ウィジェット | 個人ダッシュボードに今日・明日の予報を表示 |
| 居住地点導出 | 郵便番号 → 緯度経度（GeoNames データから引き当て） |
| 外部 API 連携 | WeatherAPI.com から予報取得（商用無料枠 1M/月） |
| キャッシュ戦略 | Valkey による地点共有キャッシュ（TTL 1 時間） |
| GeoNames 取り込みバッチ | 月次の郵便番号 → 緯度経度マスタ更新 |

**スコープ外**:
- 任意地点（旅行先・職場）の天気 → 将来拡張（後述 §13.5）
- 警報・注意報 → スコープ外。緊急時はプッシュ通知（F04.3）で別途
- 雨雲レーダー・週間予報（3 日以上先）
- 花粉・PM2.5・紫外線 → スコープ外
- チーム/組織ダッシュボードでの集計表示 → 個人スコープのみ

## 3. 外部 API 選定

### 採用: WeatherAPI.com

| 項目 | 内容 |
|------|------|
| エンドポイント | `https://api.weatherapi.com/v1/forecast.json` |
| 認証 | API キー（クエリパラメータ `key`） |
| 料金 | **Free プラン: 1,000,000 calls/月、商用利用可** |
| カバレッジ | 全世界 |
| 取得可能 | 天気状態（コード+テキスト）/ 最高・最低気温 / 平均湿度 / 降水確率 / アイコン URL |
| 予報日数 | Free で 3 日 |
| 多言語 | `lang` パラメータで ja/en/zh/ko/es/de に対応 |
| SLA | 99.9% 公称（無料枠も同等） |
| 入力形式 | 緯度経度 (`q=35.68,139.69`) / 都市名 / 一部国の郵便番号 |

### 比較で落とした候補

| 候補 | 理由 |
|------|------|
| Open-Meteo | 商用は €29/mo 必須。世界対応 + 湿度予報あるが有料 |
| 気象庁 (JMA) | 日本限定 + **湿度の予報値を提供しない**（実況値のみ）。本機能の必須要件「湿度」を満たせない |
| Tomorrow.io | 無料枠 500 calls/日。1 万ユーザー想定では即枯渇 |
| OpenWeatherMap | 無料枠商用利用は不明瞭、湿度は時間別のみ |
| Visual Crossing | 無料枠 1,000 calls/日 |

### API 呼び出し仕様

**リクエスト例:**
```
GET https://api.weatherapi.com/v1/forecast.json
  ?key={WEATHER_API_KEY}
  &q={lat_rounded},{lon_rounded}    # 例: 35.5,139.5（0.5 度丸め後の値）
  &days=2
  &aqi=no
  &alerts=no
  &lang={ja|en|zh|ko|es|de}          # users.locale から決定。未対応言語は en へフォールバック
```

**WeatherAPI.com のタイムゾーン挙動**: 緯度経度から自動判定したローカルタイムゾーンで `today` / `tomorrow` を返す。例えば `q=35.5,139.5` なら JST 基準で「今日」を返却する。サーバー時刻（UTC）に依存せず、ユーザーの実居住地時刻に整合する設計。

**ベース URL の固定**: `application.yml` で `weather.api.base-url=https://api.weatherapi.com/v1` を**ハードコード相当の固定値**として記述する。環境変数で上書き可能にしない（SSRF 経路を作らない）。テスト時のみ `@TestPropertySource` で WireMock URL に差し替える。

**レスポンスから利用するフィールド** （`forecast.forecastday[].day` 配下）:

| フィールド | 用途 |
|------------|------|
| `maxtemp_c` | 最高気温（℃） |
| `mintemp_c` | 最低気温（℃） |
| `avghumidity` | 平均湿度（%） |
| `daily_chance_of_rain` | 降水確率（%） |
| `condition.code` | 天気コード（自前 SVG にマッピング） |
| `condition.text` | 天気テキスト（lang=ja で「曇り」「晴れ」等） |

`forecast.forecastday[0]` = 今日、`forecast.forecastday[1]` = 明日。

### コール量見積もり

```
想定アクティブユーザー: 50,000 人
Valkey キャッシュ: 同一 (lat_rounded, lon_rounded) 単位で 1 時間共有
都道府県レベル粒度（0.1 度丸め）の地点クラスタ: 約 3,000 種
1 時間に 1 地点 1 コール × 3,000 地点 × 24 時間 × 30 日 = 約 2.16M/月
```

→ 1M/月を超過するリスクあり。**0.5 度丸め**（約 55km 四方）に切り替えて約 600 地点に圧縮する案を採用：

```
600 地点 × 24 × 30 = 約 432K/月（1M に対し約 43%）
```

55km の精度低下は天気予報としては実害なし（近隣 1 県内は概ね同じ予報傾向）。詳細は §7 プライバシーで再論。

## 4. DB 設計

### 4.0 新原則（CLAUDE.md 原則 6/7）への準拠

| テーブル名 | 区分 | 主キー方針 | 原則 6 適用 | 原則 7 適用 |
|---|---|---|:---:|:---:|
| `postal_codes` | **マスタ** | 自然複合キー `(country_code, postal_code)` | ❌ マスタ例外 | ❌ 組織非依存 |
| `user_weather_locations` | トランザクション | **UUIDv7（`UuidV7Entity` 継承）** | ✅ 適用 | ❌ 組織非依存（個人帰属） |
| `geonames_metadata` | **シングルトン** | `TINYINT UNSIGNED CHECK (id = 1)` | ❌ シングルトン例外 | ❌ 組織非依存 |
| `weather_location_bootstrap_jobs` | **シングルトン** | `TINYINT UNSIGNED CHECK (id = 1)` | ❌ シングルトン例外 | ❌ 組織非依存 |

**例外根拠**:
- `postal_codes` は全テナント共通の参照データ（CC BY 4.0 の GeoNames 公開データを取り込んだもの）で、将来シャーディング時は全シャードに同一データを複製する運用となる。CLAUDE.md §アーキテクチャ思想 原則 6 のマスタ例外条項に該当
- `geonames_metadata` / `weather_location_bootstrap_jobs` は `CHECK (id = 1)` で行数 1 を強制するシングルトン。UUIDv7 化の利点が完全にゼロ。CLAUDE.md §アーキテクチャ思想 原則 6 のシングルトン例外条項に該当
- `user_weather_locations` は **ユーザーごとに 1 行**増えていく純粋なトランザクションテーブルなので原則 6 を適用。ただし `organization_id` を持たない個人帰属データのため原則 7（TenantAwareRepository）は対象外

### テーブル一覧

| テーブル名 | 役割 | 論理削除 |
|-----------|------|----------|
| `postal_codes` | GeoNames 郵便番号→緯度経度マスタ | なし（バッチで全置換 or upsert） |
| `user_weather_locations` | ユーザーごとの導出済み地点（粒度を丸めた緯度経度） | なし（user 削除時に物理削除） |
| `geonames_metadata` | GeoNames 取り込みのバージョン管理 | なし |
| `weather_location_bootstrap_jobs` | 既存ユーザー初回導出ジョブの冪等フラグ | なし |

### 4.1 `postal_codes`

GeoNames Postal Codes（CC BY 4.0）の TSV を月次でバッチ取り込みするマスタ。

**主キー方針**: マスタ例外（§4.0 参照）。自然複合キー `(country_code, postal_code)` を PK として採用。理由は (1) 引き当ては必ず `(country_code, postal_code)` で行うため自然キーが最も効率的 (2) 全テナント共通の参照データでシャーディング非対象 (3) UUIDv7 を追加しても 150 万行 × 16 バイト = 24MB の単純オーバーヘッドで利点ゼロ。

| カラム名 | 型 | NULL | デフォルト | 説明 |
|---------|---|------|-----------|------|
| `country_code` | CHAR(2) | NO | — | ISO 3166-1 alpha-2 |
| `postal_code` | VARCHAR(20) | NO | — | 国別フォーマット（JP は半角ハイフン除去後の 7 桁） |
| `place_name` | VARCHAR(180) | NO | — | 地名（表示用、GeoNames の生値） |
| `admin1_name` | VARCHAR(100) | YES | NULL | 第1行政区画（都道府県・州） |
| `admin2_name` | VARCHAR(100) | YES | NULL | 第2行政区画（市区町村） |
| `latitude` | DECIMAL(8,5) | NO | — | 緯度（生値、丸め前） |
| `longitude` | DECIMAL(8,5) | NO | — | 経度（生値、丸め前） |
| `accuracy` | TINYINT UNSIGNED | YES | NULL | GeoNames の精度コード（1-6） |
| `updated_at` | DATETIME | NO | CURRENT_TIMESTAMP ON UPDATE | |

**インデックス**
```sql
PRIMARY KEY (country_code, postal_code)  -- 引き当てキー
INDEX idx_pc_country_admin1 (country_code, admin1_name)  -- 行政区画別の集計用（将来）
```

**運用方針**:
- バッチで `INSERT ... ON DUPLICATE KEY UPDATE` 方式の upsert
- 削除済み郵便番号は残置（参照され続ける可能性のため明示削除しない）
- 行数: JP のみ約 12 万、世界全体で約 150 万。MySQL InnoDB で問題なし

### 4.2 `user_weather_locations`

ユーザーの居住地点キャッシュ。郵便番号変更時に `postal_codes` を引いて自動更新する。

**主キー方針**: 新原則 6 を適用し `UuidV7Entity` を継承。`id BINARY(16)` で UUIDv7 を採用。

| カラム名 | 型 | NULL | デフォルト | 説明 |
|---------|---|------|-----------|------|
| `id` | BINARY(16) | NO | UUIDv7（アプリ側生成）| PK（`UuidV7Entity` 継承） |
| `user_id` | BIGINT UNSIGNED | NO | — | FK → users（既存 `users.id` は BIGINT で変更不可。原則「既存テーブルの BIGINT ID は変更しない」に従う）|
| `label` | VARCHAR(50) | NO | `'home'` | 地点ラベル（将来複数地点拡張用、本機能では `home` 固定で運用） |
| `country_code` | CHAR(2) | NO | — | ユーザーの `users.country_code` |
| `postal_code_hash` | CHAR(64) | NO | — | 平文郵便番号の HMAC-SHA256（暗号化された郵便番号と比較不可なため、検索時の照合用に別途ハッシュを保持） |
| `latitude_rounded` | DECIMAL(4,1) | NO | — | 0.5 度丸めの緯度（キャッシュキー兼）|
| `longitude_rounded` | DECIMAL(4,1) | NO | — | 0.5 度丸めの経度 |
| `place_name_snapshot` | VARCHAR(180) | NO | — | UI 表示用の地名スナップショット（例: 「東京都千代田区」） |
| `derived_at` | DATETIME | NO | CURRENT_TIMESTAMP | 導出日時 |
| `created_at` | DATETIME | NO | CURRENT_TIMESTAMP | |
| `updated_at` | DATETIME | NO | CURRENT_TIMESTAMP ON UPDATE | |

**インデックス**
```sql
PRIMARY KEY (id)                                -- UUIDv7（時刻順ソート可能、B-Tree フラグメント耐性）
UNIQUE KEY uq_uwl_user_label (user_id, label)   -- 将来の複数地点拡張に備え、最初から (user_id, label) 複合キー
INDEX idx_uwl_grid (latitude_rounded, longitude_rounded)  -- 集計・キャッシュ統計用
```

**Entity 継承**
```java
@Entity
@Table(name = "user_weather_locations")
public class UserWeatherLocationEntity extends UuidV7Entity {
    // id (UUID) は UuidV7Entity が提供
    private Long userId;
    private String label;
    // ...
}
```

**Repository**: `JpaRepository<UserWeatherLocationEntity, UUID>` を直接継承。`organization_id` を持たない個人帰属データのため `AbstractTenantAwareRepository`（原則 7）は適用対象外。

**HMAC キー**: 既存の `HmacSignatureUtil` / `EncryptionService` で使われている共通シークレット `app.security.hmac-secret`（環境変数 `APP_HMAC_SECRET`）を流用。新規キーは作らない（鍵管理点を増やさないため）。

**ER 図（テキスト）**
```
users (1) ──── (1) user_weather_locations（user_id, FK 同一 auth ドメイン内）
postal_codes ──── (lookup, FK なし) ──── user_weather_locations
```

**FK 方針**: CLAUDE.md「クロスドメイン FK は作らない」原則に厳密に従い、`user_weather_locations.user_id → users.id` の FK は**張らない**。auth ドメイン内であってもドメイン境界を最小化する設計に統一し、INDEX `idx_uwl_user_id` のみで検索性能を担保する。参照整合性は `UserAnonymizedEvent` リスナーによりアプリケーション層で保証する（§7.8）。`postal_codes` への FK も同様に張らない（マスタ更新時の一時的な不整合を許容するため）。

**論理削除/物理削除**:
- ユーザー退会時 (`UserService#anonymize`) に物理削除（個人特定可能な地理情報のため保持しない）
- `users.deleted_at` セット時に `UserAnonymizedEvent` リスナーが削除

### 4.4 `weather_location_bootstrap_jobs`

既存ユーザー初回導出ジョブ（§8.3 `WeatherLocationBootstrapJob`）の冪等フラグ用シングルトンテーブル。

**主キー方針**: シングルトン例外（§4.0 参照）。`CHECK (id = 1)` で行数 1 を強制。

| カラム名 | 型 | NULL | 説明 |
|---------|---|------|------|
| `id` | TINYINT UNSIGNED | NO | 固定値 1（PK、シングルトン制約） |
| `completed_at` | DATETIME | YES | ジョブ完了日時。NULL のときは未完了 |
| `processed_user_count` | INT UNSIGNED | YES | 処理済みユーザー数 |
| `skipped_user_count` | INT UNSIGNED | YES | スキップユーザー数（郵便番号未ヒット等） |

### 4.5 GDPR 連携

`user_weather_locations` は `@PersonalData(category = "location_preference")` を付与し、`PersonalDataCollector` に登録する。

- **エクスポート**: `country_code` / `postal_code_hash` を除く `latitude_rounded` / `longitude_rounded` / `place_name_snapshot` / `derived_at` を JSON にダンプ
- **削除**: ユーザー削除時に物理削除（前述）
- **エクスポート時の `id` 表示**: UUID 文字列形式（`xxxxxxxx-xxxx-7xxx-...`）でダンプ。ユーザー識別に使われない補助フィールドのため通常はマスク不要

## 5. API 設計

### エンドポイント一覧

| メソッド | パス | 認証 | 説明 |
|---------|-----|------|------|
| GET | `/api/v1/dashboard/weather` | 必要 | 今日・明日の天気予報を返す |
| POST | `/api/v1/users/me/weather-location/refresh` | 必要 | 郵便番号から地点を再導出（手動再試行） |

### 5.1 GET `/api/v1/dashboard/weather`

**処理フロー**:
1. 認証ユーザーの `user_weather_locations` を取得
2. レコードが無ければ `WeatherLocationDeriver` を呼び出して導出（同期）
3. 導出失敗 → 422 + 失敗理由別のエラーコード（下記）
4. 緯度経度をキーに Valkey キャッシュ参照（`weather:{country}:{lat_r}:{lon_r}:{lang}`）
5. キャッシュヒット → 返却。ミス → WeatherAPI.com 呼出 → Valkey に TTL 1h で保存 → 返却
6. WeatherAPI.com エラー → §8 障害時動作に従い stale データ or エラー応答

**レスポンス例（200）**:
```json
{
  "location": {
    "place_name": "東京都千代田区",
    "country_code": "JP"
  },
  "today": {
    "date": "2026-05-09",
    "condition_code": 1003,
    "condition_text": "曇り時々晴れ",
    "icon_key": "partly_cloudy",
    "max_temp_c": 22.4,
    "min_temp_c": 14.1,
    "avg_humidity": 58,
    "chance_of_rain": 10
  },
  "tomorrow": {
    "date": "2026-05-10",
    "condition_code": 1063,
    "condition_text": "雨",
    "icon_key": "rain",
    "max_temp_c": 18.0,
    "min_temp_c": 13.5,
    "avg_humidity": 82,
    "chance_of_rain": 80
  },
  "data_source": "WeatherAPI.com",
  "fetched_at": "2026-05-09T07:00:12Z",
  "is_stale": false
}
```

**フィールド注記**:
- `today.date` / `tomorrow.date` は WeatherAPI.com が緯度経度から自動判定したローカルタイムゾーン基準の日付（YYYY-MM-DD）
- `fetched_at` は ISO 8601 UTC（`Z` 終端）。フロントエンドで `users.timezone` に変換して相対時刻表示する
- `condition_text` は WeatherAPI.com 提供の翻訳済み文字列。表示時は **必ず `v-text` / mustache でエスケープ**（XSS 対策、後述 §7.7）
- `icon_key` は `weatherIconMap.ts` 経由で自前 SVG にマッピング済みのキー。フロント側で再マッピング不要
- WeatherAPI.com が将来未知の `condition.code` を返した場合、サーバー側で `cloudy` にフォールバックする（後述 §13.5）

**エラーレスポンス**:

レスポンスボディは `{ "error_code": "...", "message": "..." }` 形式。`error_code` は §6.4 のサブコードと 1:1 で対応する。

| HTTP | error_code | 条件 |
|------|------------|------|
| 401 | — | 未認証 |
| 422 | `POSTAL_CODE_MISSING` | 郵便番号が `users.postal_code` に未登録（理論上発生せずデータ不整合のみ）|
| 422 | `POSTAL_CODE_NOT_FOUND` | 郵便番号は登録済みだが `postal_codes` マスタに該当なし（私書箱・新設地域・誤入力等） |
| 422 | `COUNTRY_NOT_SUPPORTED` | `users.country_code` が `postal_codes` に 1 件も収録されていない（GeoNames 未対応国） |
| 503 | `WEATHER_PROVIDER_UNAVAILABLE` | WeatherAPI.com 5xx/タイムアウト + stale キャッシュなし |

`is_stale` フィールド: 通常レスポンス（200）に含まれる boolean。`true` のとき直近の WeatherAPI.com 取得から **§8.1 通常 TTL 3600 秒を超過しているが §8.2 障害時 TTL 21600 秒以内** で返却された延命応答。フロントは amber 警告を出す（§6.4）。

**レートリミット**: ユーザー単位 60 req/h（Bucket4j。手動連打防止）。Valkey キャッシュ前提なので通常運用では到達しない。

### 5.2 POST `/api/v1/users/me/weather-location/refresh`

ユーザーが郵便番号を更新した直後、または「天気が表示されない」とき手動で再導出を要求する。

**リクエストボディ**: なし

**処理**: `WeatherLocationDeriver.deriveAndPersist(userId)` を同期実行。

**レスポンス例（200）**:
```json
{
  "place_name": "東京都千代田区",
  "country_code": "JP",
  "derived_at": "2026-05-09T07:05:32Z"
}
```

**エラー**: GET と同じ体系（`POSTAL_CODE_MISSING` / `POSTAL_CODE_NOT_FOUND` / `COUNTRY_NOT_SUPPORTED`）。

> **方針転換（2026-06-24・§5.3.1 郵便番号検証基盤の導入に伴う）**:
> かつては「フォーマット不正も `POSTAL_CODE_NOT_FOUND` に集約（マスタにヒットしない時点でフォーマット問題と切り分け不要）」としていた。
> しかしこれでは誤入力（例: JP の `111`）が「お住まいの郵便番号が見つかりません」という分かりにくいメッセージになり、入力直後に誤りを通知できなかった。
> そこで **入力受付の時点（登録・プロフィール更新）で国別レジストリによるフォーマット検証を行い、不正なら `AUTH_072` を 400 で即時に返す**方針へ改めた（§5.3.1）。
> 地点導出（本エンドポイント）まで到達した郵便番号は既にフォーマット検証済みであり、ここで残る失敗はマスタ未ヒット系のみとなる。

| HTTP | error_code | 条件 |
|------|------------|------|
| 422 | 上記 GET と同じ | 導出失敗（理由はマスタ未ヒット系） |
| 429 | — | 1 ユーザー 5 req/h 超過 |

> **AC-15 古い地点キャッシュの無効化（2026-06-24）**:
> 郵便番号起因の決定的失敗（`POSTAL_CODE_MISSING` / `POSTAL_CODE_NOT_FOUND` / `COUNTRY_NOT_SUPPORTED`）で導出に失敗した場合、`WeatherLocationDeriver.deriveAndPersist` は再 throw する前に既存の `user_weather_locations(userId, label="home")` 行を削除する。
> これを残すとダッシュボード GET（行が存在すれば再導出しない実装）が旧郵便番号の天気を出し続けてしまう（§458 違反）。`@Transactional(noRollbackFor = WeatherLocationDeriveException.class)` 済みのため削除はコミットされる。一時障害（`WeatherProviderException`）はこの無効化の対象外。

### 5.3 内部連携

**郵便番号更新時の自動再導出**:

`UserService#updateProfile` で `postalCode` または `countryCode` が変化した場合、`UserPostalCodeUpdatedEvent` を発火。`WeatherLocationEventListener` が `@TransactionalEventListener(phase = AFTER_COMMIT)` で `WeatherLocationDeriver` を非同期実行。失敗時は WARN ログのみ（次回ダッシュボード GET 時に同期再導出される）。

**ユーザー登録時**:

`AuthService#register` 完了直後に同様のイベントを発火。新規登録ユーザーは初回ダッシュボードアクセス時に天気が即表示される。

### 5.3.1 郵便番号検証基盤（国別レジストリ駆動・2026-06-24 追加）

天気導出の前段として、**入力受付時点で郵便番号フォーマットを国別に検証する単一真実源の基盤**を導入する（Phase 1。対応国は現状 JP のみ）。

**目的**: 誤入力（例: JP の `111`）を「お住まいの郵便番号が見つかりません」(`POSTAL_CODE_NOT_FOUND`) に丸める従来方針をやめ、登録・プロフィール更新の時点で `AUTH_072`（400）として即時にユーザーへ通知する。対応国では郵便番号を必須とし、未対応国は検証をスキップする（フロントエンドは「未対応」を表示）。

**構成（共有 `com.mannschaft.app.postal` パッケージ）**:

| クラス | 役割 |
|---|---|
| `PostalCodePolicy`（record） | 1 国分の規則（`countryCode` / `pattern`（正規表現）/ `example`）|
| `PostalCodePolicyRegistry`（@Component） | **単一真実源**。対応国ポリシーを `Map` で保持。`isSupported` / `getPolicy` / `isValidFormat`（生入力 regex・正規化しない）/ `all`。対応国の追加は `Map` に 1 行足すだけ |
| `CountryResolver`（@Component） | ユーザーの実効国コードを解決（明示 `countryCode` 優先・なければ locale プレフィックス ja→JP/en→US/zh→CN/ko→KR/es→ES/de→DE）。weather 地点導出（`WeatherLocationDeriver`）も本クラスへ委譲し locale→国 マップを一元化 |

> **正規化との違い**: `PostalCodePolicyRegistry.isValidFormat` は**生入力**を正規表現で評価する（正規化しない）。`PostalCodeNormalizer`（JP=ハイフン除去+7桁ゼロパディング）はマスタ引き当て用の正規化であり目的が異なる。例えば JP の `111` は normalizer ではゼロパディングされ得るが、検証では桁不足として弾く。

**JP のポリシー**: `pattern = ^\d{3}-?\d{4}$`（7桁・ハイフン任意。`123-4567` / `1234567` 可、`111` 不可）、`example = "123-4567"`。

**検証配線（サービス層手動チェック。国依存のクロスフィールド検証ゆえ Bean Validation 注釈では不可）**:

- `AuthRegistrationService.register`: `req.getLocale()`（既定 `ja`）から実効国を解決。対応国なら郵便番号 blank → `AUTH_071`、フォーマット不正 → `AUTH_072`。未対応国はスキップ。
- `UserService.updateProfile`: 実効国（更新適用後の `countryCode` / `locale`）を解決し、対応国のときのみ検証。`req.getPostalCode()` が **null（欄据置・未変更）** は既存値維持で検証スキップ、**空文字 ""（明示クリア）** は対応国では `AUTH_071`（空に戻せない）、**非空** はフォーマット不正なら `AUTH_072`。

**公開 API（FE 単一真実源・未認証可）**:

`GET /api/v1/postal-code/policies` → `{ "data": [{ "countryCode", "pattern", "example" }] }`（対応国一覧）。register 画面（未ログイン）からも使うため `permitAll`（フォーマット規則のみで機微情報なし）。フロントエンドはこのレスポンスを単一真実源として対応国判定・フォーマット検証・入力例表示に用いる。

**エラーコード**:

| error_code | HTTP | 条件 |
|---|---|---|
| `AUTH_071` | 400 | 対応国で郵便番号が未入力（必須違反） |
| `AUTH_072` | 400 | 郵便番号フォーマット不正 |

## 7. セキュリティ・プライバシー

### 7.1 緯度経度の粒度（PII 性低下）

| 粒度 | 精度 | 識別性 | 採用 |
|------|------|--------|------|
| 生値（DECIMAL(8,5)） | 約 1m | 個人特定可能（住所相当） | ❌ |
| 0.1 度丸め | 約 11km 四方 | 都市レベル | ❌（コール量超過） |
| **0.5 度丸め** | **約 55km 四方** | **都道府県レベル** | ✅ |
| 1 度丸め | 約 110km 四方 | 県またぎ精度低下 | ❌ |

`user_weather_locations.latitude_rounded` / `longitude_rounded` は **0.5 度丸め**で保存。GDPR 上は識別性が大幅に低下するため `@PersonalData("location_preference")` カテゴリ（嗜好情報レベル）として扱う。

導出処理では `postal_codes` の生値（DECIMAL(8,5)）を `WeatherLocationDeriver` 内で読み取り、丸め後のみを永続化する。生値はサービス層を出ない。

### 7.2 暗号化された郵便番号の取扱

- `users.postalCode` は `EncryptedStringConverter` で AES-256-GCM 暗号化済み（V9.053）
- `WeatherLocationDeriver` は `UserEntity#getPostalCode()` 経由で復号値を取得 → `postal_codes` 引き当て → 丸め座標を保存 → メソッドのローカル変数を抜けた時点でスコープ外（GC 対象）
- ログ出力には平文郵便番号を**絶対に含めない**（`log.info` は `country_code + place_name_snapshot` のみ）。SLF4J の MDC に郵便番号を入れることも禁止
- `postal_code_hash` カラムは平文郵便番号の HMAC-SHA256（既存共通シークレット `APP_HMAC_SECRET` を使用）。「ユーザーの郵便番号変更を検知して再導出が必要か判定する」目的のみ。元の郵便番号を復元できない一方向ハッシュ
- **String の即時破棄について**: Java の `String` はイミュータブルで GC 任せのため明示的破棄は不可。`char[]` 化までは要件として過剰と判断（既存の `EncryptedStringConverter` 利用箇所も同水準）。本機能ではメソッドローカル変数に閉じ込めることで実質的なリスク低減で足りるとする

### 7.3 API キーの管理

| 観点 | 対策 |
|------|------|
| 保管 | `application.yml` の `${WEATHER_API_KEY}` で環境変数経由のみ。リポジトリにコミットしない |
| 露出 | バックエンドのみ保持。**フロントエンドからは絶対に露出させない**（フロントが直接 WeatherAPI.com を叩かない） |
| ログ出力 | `WeatherApiClient` 内でリクエスト URL をログ出力する場合、`key=***` でマスク |
| ローテーション | 年 1 回 + 漏洩疑い時。手順を `docs/operations/weather_api_key_rotation.md` に記載 |
| 不正利用検知 | WeatherAPI.com 管理画面の使用量を週次でチェック（運用ドキュメント化） |

### 7.3.1 SSRF（Server-Side Request Forgery）対策

- ベース URL `https://api.weatherapi.com/v1` は `application.yml` で固定。環境変数で上書き可能にしない（テスト環境のみ `@TestPropertySource` で WireMock URL に切替）
- ユーザー入力からホスト名を組み立てない。クエリパラメータ（`q`、`lang`）はサーバー側で内部状態（丸め済み座標 + ユーザーロケール）から構築
- WebClient は `https://api.weatherapi.com/v1` の prefix 一致でしかリクエストできないよう、ベース URL を Bean としてシングルトン注入する

### 7.4 認可

- `GET /api/v1/dashboard/weather` は認証ユーザー自身の地点のみ返す（`SecurityContext#getCurrentUserId` を使用、ID パラメータを受け取らない → IDOR 不可能）
- `POST /weather-location/refresh` 同様

### 7.5 監査ログ

天気の閲覧・取得は監査ログ非対象（個人の利便性情報、改竄リスクなし）。郵便番号変更による地点再導出も非対象（郵便番号変更自体が `users` の監査対象）。

### 7.6 レートリミット

| エンドポイント | 制限 | 理由 |
|----------------|------|------|
| `GET /dashboard/weather` | 60 req/h/user | キャッシュ前提なので通常未到達。連打バグ・DoS 防御 |
| `POST /weather-location/refresh` | 5 req/h/user | 手動再試行は最大 5 回で十分 |

外部 API の使用量保護は §8 でキャッシュ層により対応。

### 7.7 入力バリデーション

- 認証ユーザーの内部 ID のみ使用、外部入力なし → SQL インジェクション・XSS リスクなし
- WeatherAPI.com への問い合わせ値（lat/lon/lang）はサーバーが構築する固定形式 → 注入リスクなし
- レスポンス JSON の `condition.text` は HTML エスケープ後に表示（Vue の `v-text` または mustache、`v-html` 禁止）

### 7.8 GDPR・退会時動作

- `UserAnonymizedEvent`（既存）リスナー `WeatherLocationCleanupListener` で `user_weather_locations` を物理削除
- データエクスポート時 `PersonalDataCollector#collect` に `user_weather_locations` を含める（`location_preference` カテゴリ）
- `PersonalDataCoverageValidator` 起動時チェックを通過させる

## 8. キャッシュ・障害時動作

### 8.1 Valkey キャッシュ

| 項目 | 値 |
|------|-----|
| キー | `weather:{country_code}:{lat_r}:{lon_r}:{lang}` |
| 値 | API レスポンス JSON（自前 DTO に整形済み） |
| TTL | 通常 3600 秒（1 時間） |
| 障害時 TTL | 21600 秒（6 時間。stale 延命用） |
| エビクション | LRU（既存 Valkey 設定準拠） |

`lat_r` / `lon_r` はユーザーごとではなく丸め座標単位なので、同一エリアのユーザー全員でキャッシュを共有する → 外部 API コール削減。

### 8.2 障害時動作（fallback）

| 障害 | 動作 |
|------|------|
| WeatherAPI.com 5xx | 直近の Valkey 値があれば `is_stale = true` で返却（TTL 6 時間延長）。なければ 503 |
| WeatherAPI.com 4xx（キー無効/無料枠超過） | 503 + `WEATHER_PROVIDER_UNAVAILABLE`、Slack/メールでオペレーション通知（§10） |
| WeatherAPI.com タイムアウト（3 秒超） | 直近キャッシュ返却。なければ 503 |
| Valkey ダウン | 毎回 WeatherAPI.com 直接呼出に縮退（§3 で見積もった 432K/月 + 通常コール）+ レートリミット強化 |

リトライ: 5xx およびタイムアウトに対して指数バックオフ（200ms / 600ms / 2s）で最大 3 回。**Spring Retry**（`@Retryable`、既存依存）で実装。サーキットブレーカーは F12.5 のエラーレポート系と同水準にしない（外部 API 1 つの天気機能のため過剰）。

### 8.3 既存ユーザーへの初期データ

Flyway は SQL のみで Java 処理（暗号化郵便番号の復号）を伴わないため、既存ユーザーへの座標導出は **`WeatherLocationBootstrapJob`（Spring Bean、`@PostConstruct` + 冪等フラグ）** で行う。

処理フロー:
1. アプリ起動時 `@PostConstruct` で実行
2. `geonames_metadata.last_imported_at` を確認、未取り込みなら処理スキップ（GeoNames バッチ完了待ち）
3. 専用フラグテーブル `weather_location_bootstrap_jobs (id=1, completed_at)` を確認、既に completed_at があればスキップ
4. 全既存ユーザー（`deleted_at IS NULL`）を 1,000 件チャンクでループし `WeatherLocationDeriver.deriveAndPersist(userId)` を呼出（既に `user_weather_locations` がある場合はスキップ）
5. 完了後フラグテーブルに completed_at を記録

- 既存ユーザー数: 設計時点では数百〜数千規模を想定
- 失敗ユーザー（`postal_codes` 未ヒット）はスキップしてレポート出力。ダッシュボード初回アクセス時に同期再試行される
- 起動時負荷: 1,000 件チャンクなので起動 SLA に影響しない（非同期実行 `@Async`）

### 10.3 GeoNames 取り込みバッチ

- Gradle タスク: `./gradlew importPostalCodes`（手動実行用）
- 引数: `--country=ALL` / `--country=JP` 指定可
- 自動実行: `@Scheduled(cron = "0 0 2 5 * ?")` で月 1 回 02:00 JST 実行（既存の `MemberInfoUpdateReminderBatchService` 等と同じスケジューリング基盤）
- ソースファイル: `https://download.geonames.org/export/zip/allCountries.zip`（または国別 zip）
- 取り込みは **JDBC バルクインサート** + `INSERT ... ON DUPLICATE KEY UPDATE`、5,000 行/バッチで chunk
- 取り込み行数・所要時間を `geonames_metadata` に記録。完了時 INFO ログ + Slack 通知
- 失敗時はリトライせず WARN（手動 Gradle タスクで再開）。途中失敗でも既存データは破壊しない（upsert 方式）
- ダウンロードファイル検証: HTTP レスポンスサイズ + 行数下限（`allCountries` は 100 万行以上を期待。下回ったら破損疑いで取り込み中止）

## 13. 既存設計への影響

### 13.1 F02.2 ウィジェット一覧への追記

F02.2 §3「ウィジェット一覧」§3.個人ダッシュボードに以下を追加する。**本設計書の確定と同 PR で F02.2 を改訂する**（F02.2 の変更履歴にも 2026-05-09 のエントリを追加）。

| widget_key | ウィジェット名 | デフォルト表示 | 依存モジュール | 説明 |
|-----------|-------------|:---:|-------------|------|
| `WEATHER` | 天気 | ○ | — | 登録郵便番号から導出した居住地点の今日・明日の予報。F02.10 参照 |

**配置の優先度**: `sort_order` 既定値は `NOTICES`(0)・`UPCOMING_EVENTS`(1)・`PERSONAL_TODO`(2) の次の `3` を割り当てる。理由は朝の利用導線として「お知らせ → 直近イベント → TODO → 天気」の順が自然なため。広告ウィジェットより上位。

**条件付き表示の有無**: `WidgetFamilyHub` のような条件分岐（家族チーム所属時のみ表示）は不要。全ユーザーがデフォルトで表示対象。

### 13.2 F02.2 GET `/api/v1/dashboard` への影響

`GET /api/v1/dashboard` の集約レスポンスに `weather` キーを追加するか、独立 API（`GET /dashboard/weather`）のままにするかの判断:

- **独立 API のままにする**を採用
- 理由: WeatherAPI.com のレイテンシ（200-800ms）を集約 API のクリティカルパスに乗せたくない。ダッシュボード初期表示は他ウィジェットを優先し、`WEATHER` は `useLazyAsyncData` で第 2 段階フェッチする（F02.2 の遅延ロード方針と整合）

### 13.3 F12.3 GDPR への影響

`PersonalDataCollector` に新カテゴリ `location_preference` を登録し、`user_weather_locations` をエクスポート対象に追加。テストで `PersonalDataCoverageValidator` が新カテゴリを検出することを確認。

### 13.4 F01.1 認証・登録への影響

- 郵便番号必須化は既存仕様（V9.053 + register.vue regex）に乗る
