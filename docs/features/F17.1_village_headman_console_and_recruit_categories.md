## 1. 背景と課題

### 1.1 課題A — 募集カテゴリがスポーツに固着している

【確認済み】`backend/src/main/java/com/mannschaft/app/village/entity/enums/VillageMatchRecruitCategory.java:13-18`:

```java
public enum VillageMatchRecruitCategory {
    PRACTICE_MATCH,
    REFEREE,
    VENUE,
    OTHER
}
```

各値の意味は同ファイルの Javadoc（`:7-10`）にある — `PRACTICE_MATCH` 練習試合の対戦相手募集 / `REFEREE` 審判募集 / `VENUE` 会場提供募集 / `OTHER` その他（マネージャー等）。

問題の本質は**ラベルの文言ではなく、カテゴリの型そのものがスポーツを前提としている**ことにある。
`REFEREE`（審判）は F17.1 §1.4 が想定する村（【確認済み】`F17.1_village_community.md:55` 「マンション管理組合村」/ `:57` 「新米管理職村」）では意味を成さない。ラベルを差し替えても enum の値域がスポーツ語彙のままである以上、非スポーツ村は `OTHER` に全部を押し込むことになり、カテゴリ機能が死ぬ。

これは i18n では解けない。**村ごとに値域そのものを定義できる必要がある**。

【確認済み】固着は enum に留まらず DB・DTO・FE の全層に及ぶ:

### 1.4 なぜ今まとめて設計するか

課題A（カテゴリマスタ）は**村長が管理する対象**であり、課題B（村長ページ）は**その管理画面の置き場**である。カテゴリマスタだけ作っても村長が触れる画面が無く、村長ページだけ作っても載せる中身が薄い。両者は同一の設計単位として扱うのが自然である。

一方、課題C は**本設計の土台**である。**カテゴリマスタは「壊れた募集一覧」の上に建つ**ため、C-1 を直さずに移行すると「マスタは正しいのに画面は相変わらずゴミバッジ」という状態になり、**移行が成功したのか失敗したのかを実機で判定できない**（AC-35 が検証不能になる）。したがって §10 で**依存関係として明示**する。

## 3. 村長ページの構成

### 3.1 金型 — チーム管理コンソールのカードグリッド

【確認済み】`frontend/app/pages/teams/[slug]/admin/index.vue` を金型とする（同ファイル `:5-6` が設計書 [`F10.1.1_team_org_admin_console/01_console_routes.md`](F10.1.1_team_org_admin_console/01_console_routes.md) §2 を参照している）。要点:

- `definePageMeta({ layout: 'team', middleware: ['auth', 'admin-console'] })`（`:17-20`）
- `cards` computed 配列（`:72-110`）で `{ key, titleKey, descKey, icon, to }` を定義し、`to: null` は「近日公開」プレースホルダ（`:27`）
- **タブではなくカードグリッド**（`:125` `grid gap-4 sm:grid-cols-2 lg:grid-cols-3`）
- 権限ガードは `isAdminOrDeputy` による表示制御。二重防御の意図は `:9`（「ページ本体では二重防御として `useRoleAccess` の `isAdminOrDeputy` でカード表示を制御する」）と `:63-64`（「ミドルウェアが本丸・ここは表示制御」）にコメントされ、実際の適用は `:115` の `<template v-if="isAdminOrDeputy">`
- i18n 名前空間は `adminConsole.*`

村長コンソールもこの**カードグリッド方式**を踏襲する。

### 3.2 【重要】admin-console ミドルウェアは村に流用できない

【確認済み】`frontend/app/middleware/admin-console.ts`:

```ts
const slug = String(to.params.slug ?? '')          // :23  村は params.id
if (!slug) return
const scopeType = to.path.startsWith('/organizations/') ? 'organization' : 'team'  // :26
```

【確認済み】`frontend/app/composables/useRoleAccess.ts:8`:

```ts
export function useRoleAccess(scopeType: 'team' | 'organization', scopeId: Ref<string> | string)
```

村は `params.id`（`slug` ではない）を使い、`useRoleAccess` の型は `'team' | 'organization'` のみで **village を受け付けない**。したがって `admin-console` ミドルウェアの流用も、`useRoleAccess('village', ...)` への拡張も、そのままでは成立しない。

さらに村の権限は既に**別経路で解決済み**である。【確認済み】`pages/villages/[id].vue:163-171`:

```ts
const perms = computed(() => {
  const role = village.value?.myRole ?? null
  return {
    isMember: !!village.value?.isMember,
    isAdmin: role === 'HEADMAN' || role === 'ELDER',
    isHeadman: role === 'HEADMAN',
    myRole: role,
  }
})
```

これは親シェルが `useAsyncData` で1回だけ取得した村データ（`:79-88`）から導出され、`provideVillageContext` で子へ渡される（`:294-300`）。

**【提案】村長コンソールの権限ガードは `useVillageContext().perms` を使い、専用ミドルウェアは作らない。**

根拠:
1. ミドルウェアを作ると、シェルが既に取得している村データを**もう一度フェッチする**ことになる（ミドルウェアは provide/inject の外側で走るため context を読めない）。永続シェル方式（`[id].vue:7-24` の設計意図）に真っ向から反する
2. `admin-console.ts:14-15` 自身が「これは UX のための表示制御であり、認可の最終判断ではない。BE は各 API で必ず認可チェックを通す」と明記している。**認可の本丸は BE**（§6.3）であり、FE ミドルウェアの有無はセキュリティ強度を変えない
3. 既存の村の設定画面（`newsletter-settings.vue:128-132`）も同じくミドルウェア無しの `v-if="!isHeadman"` 表示制御で実装されており、村ドメインの既存作法と一致する

> **【提案】トレードオフの明示**: ミドルウェアが無いため「権限不足で誤遷移 → リダイレクト＋トースト」は起きず、代わりに「権限不足の案内をページ内に表示」となる。これは `newsletter-settings.vue` と同じ挙動であり、村ドメイン内で一貫する。チーム/組織コンソールとは挙動が異なるが、権限の解決経路（`useRoleAccess` vs シェル inject）が構造的に違う以上、無理に揃えるとシェル設計を壊す。

### 3.3 タブに載せるか、独立画面か —— 既存方針との整合

【確認済み】`pages/villages/[id]/newsletter-settings.vue:13-14`（コメントブロック `:12-15` 内）に既存の設計判断が明記されている:

```
注意: VillageHeader の `activeTab` に新タブ追加は最小化のため、
設定タブとしては独立画面で動作させる（ヘッダーは付けず情報のみ）。
```

【確認済み・重要】このコメントは**現在のコードと部分的に食い違っている**。同ファイル `:7-8` は「上段: `<VillageHeader activeTab="newsletter-settings" />`」と書いているが、**テンプレート（`:110-201`）に `VillageHeader` は無い**。実際には親シェル `[id].vue:351-362` が VillageHeader を常駐描画しているため、newsletter-settings を開くと**ヘッダーは出る**。コメントは永続シェル化以前の記述が残った stale なものと判断する（【要確認】: 実装時に当該コメントも是正すること）。

したがって既存方針の生きている部分は「**9タブ列に新タブを追加しない**」の一点である。

**【提案】村長コンソールは `/villages/[id]/admin` に置き、シェルの子ルートとする。9タブ列には追加しない。**

| 選択肢 | 評価 |
|---|---|
| A. 9タブ列に「運営」タブを追加 | ✗ 既存方針に反する。村人（VISITOR/VILLAGER）にも見えるタブ列に村長専用タブを出すと、押せないタブが並ぶか、ロールでタブ数が変わって不安定になる |
| B. シェルの子 `/villages/[id]/admin`（**推奨**） | ✓ 既存方針（タブ列に追加しない）を守る。シェルの `perms` を inject できる。VillageHeader が常駐するので村の文脈（村名・紋）を保ったまま運営画面に入れる。newsletter-settings と同じ構造 |

> **【提案】整合性の注意**: 論理削除されたカテゴリ（`deleted_at IS NOT NULL`）を参照する募集は**正常系として残り得る**。削除ガード（AC-10）は「生きている募集」だけを数えるため、**論理削除済みの募集しか参照していないカテゴリは削除できる**（そうしないとカテゴリが永久に消せなくなる）。この状態でも FK は RESTRICT のまま整合し、表示も壊れない — ただし**募集取得時のカテゴリ join を `deleted_at` で絞らないこと**が前提。詳細は §6.2 の `recruitCount` の注を参照。

### 4.4 Flyway 採番

CLAUDE.md の採番規約に従う: `V{major}.{yyyyMMddHHmmss}__{説明}.sql`。

- **major** = 「origin/main 全体の最大 major + 1」
- **minor はタイムスタンプ必須**（連番 `.001` 等は禁止。番人テスト `FlywayTimestampNamingGuardTest` が機械的に拒否）
- タイムスタンプは `date -u '+%Y%m%d%H%M%S'` で採る

【確認済み】2026-07-15 時点の `origin/main`（`255cc9cde`）の最大 major は **152**。したがって見込みは `V153.{yyyyMMddHHmmss}__*.sql` となる。

> **実際の版番号は実装時に採番すること。** マージ時衝突を避けるため、**着手直前に `origin/main` を再取得して最大 major を再確認**する（memory `feedback_migration_version_collision`）。本書に版番号を確定記載しない。

【提案】マイグレーションは §5.4 の Expand / Contract に対応して**2本に分ける**（1本目=Expand、2本目=Contract）。

## 5. 既存 enum からの移行方針

### 5.1 前提 — 既存データの所在

`village_match_recruits.category` は `VARCHAR(30) NOT NULL`（【確認済み】`V9.147:17`）で、`PRACTICE_MATCH` / `REFEREE` / `VENUE` / `OTHER` のいずれかが入っている。【要確認】本番の実データ件数・村ごとの分布は未計測（実装時に `SELECT village_id, category, COUNT(*) ... GROUP BY 1,2` で確認すること）。

### 5.2 案の比較

#### 案A: enum 併用（既定プリセット enum + カスタム追加）

`category`（enum）を残し、カスタム時のみ `custom_category_id` を参照する二本立て。

| | 内容 |
|---|---|
| ✅ | 既存データ・既存 API 契約を一切変更しない。移行コストが最小 |
| ✅ | 段階導入が容易（カスタムを使わない村は現状のまま） |
| ❌ | **「どちらが正か」が曖昧な二重表現**になる。`category` と `custom_category_id` の両方が埋まった行の解釈が未定義になり、将来の障害の温床 |
| ❌ | **`category` が `NOT NULL` なので、カスタム使用時に何を入れるか**が破綻する。`OTHER` を詰めると「カスタムなのに OTHER」という意味の腐敗が起き、集計・フィルタが壊れる |
| ❌ | **スポーツ固着 enum が永久に残る**。マンション管理組合村のカテゴリ選択肢に `REFEREE` が居座り続け、§1.1 の課題が解決しない |
| ❌ | FE がカテゴリ描画のたびに二分岐（enum なら `$t()`、カスタムなら生文字列）。`match-recruits.vue` の二重定義（§1.1）も残存 |

#### 案B: 全面マスタ移行（**推奨**）

`category_id` をマスタ参照の単一の正とし、既定プリセットも**データとして**マスタに投入する。

| | 内容 |
|---|---|
| ✅ | **単一の正**。カテゴリの表現が `category_id` 一本に収束し、二重表現の曖昧さが無い |
| ✅ | **スポーツ固着が構造的に消える**。既定プリセットもただの1行であり、村長が改名・削除できる（§4.2） |
| ✅ | FE の描画が `category.name` 一本になり、二重定義・i18n 分岐が消滅 |
| ❌ | マイグレーションが重い（村ごとにプリセット行を seed + 既存行のバックフィル） |
| ❌ | DTO / 生成型 / FE の破壊的変更を伴う（§5.4 の段階移行で緩和する） |

### 5.3 推奨案 — **案B（全面マスタ移行）**

**理由**: マスターの不満の根は「カテゴリの型自体がスポーツ前提」であること（§1.1）。案A では enum が残るため、**問題の症状（ラベル）を覆うだけで原因（値域の固着）が残る**。これは CLAUDE.md「障害対応の原則 — 根治治療」が禁じる対処療法に該当する。案B は移行コストを払う代わりに原因を除去する。

### 5.4 移行手順 — Expand / Migrate / Contract

既存データを一切壊さないため、**3段階**に分ける。各段階は独立して main にマージ可能（＝いつ止めても壊れない）。

#### Stage 1: Expand（DDL 追加のみ・後方互換）

1. `village_recruit_categories` を作成（§4.2）
2. `village_match_recruits.category_id BINARY(16) **NULL**` を追加（§4.3）。**この時点では NULL 可**。既存行は `category`（enum）が正のまま
3. **プリセットの seed**（§5.5）
4. **既存行のバックフィル** — `category` 文字列 → 同一村の `preset_key` が一致する行の `id` へ:

```sql
UPDATE village_match_recruits r
JOIN village_recruit_categories c
  ON c.village_id = r.village_id
 AND c.preset_key = r.category
 AND c.deleted_at IS NULL
SET r.category_id = c.id
WHERE r.category_id IS NULL;
```

5. **番人検証**（同マイグレーション内）— 取りこぼしがあれば**マイグレーションを失敗させる**:

```sql
-- category_id が埋まらなかった行が1件でもあれば移行は不完全。
-- 黙って進めると Stage 3 の NOT NULL 化が失敗する（＝時限爆弾）ため、ここで止める。
-- 【重要】deleted_at で絞らない（下記「論理削除の罠」参照）。
SELECT COUNT(*) INTO @orphans
  FROM village_match_recruits
 WHERE category_id IS NULL;
-- @orphans > 0 なら SIGNAL SQLSTATE '45000' で abort
```

> ### 【重要】論理削除の罠 — バックフィルは「生きている行」だけでは足りない
>
> 本設計の初稿では seed 導出・バックフィル・番人のいずれも `deleted_at IS NULL` で絞っていたが、**これは Stage 3 で破綻する**。理由:
>
> 1. Stage 3 は `category_id` を **`NOT NULL` 化**する。`NOT NULL` 制約は**論理削除済みの行にも適用される**（DB は `deleted_at` を知らない）
> 2. したがって「論理削除済みの募集」の `category_id` が NULL のまま残ると、**Stage 3 の `ALTER TABLE ... MODIFY ... NOT NULL` が失敗する**
> 3. 同様に、**論理削除済みの村**（`villages.deleted_at IS NOT NULL`）が持つ募集も対象。CASCADE FK は物理削除でしか発火しないため、ソフト削除された村の募集行は生き残っている
>
> **したがって Stage 1 では以下を徹底する:**
>
> | 処理 | 絞り込み |
> |---|---|
> | seed の導出（`SELECT DISTINCT category ...`） | **`deleted_at` で絞らない**（論理削除済みの募集が使っていた値も seed する） |
> | 対象の村 | **論理削除済みの村も含む**（募集行を1件でも持つ村すべて） |
> | バックフィル `UPDATE` | **`deleted_at` で絞らない**（全行） |
> | 番人の COUNT | **`deleted_at` で絞らない**（全行が `category_id IS NOT NULL` であること） |
>
> **トレードオフ**: 「論理削除済みの募集でしか使われていないカテゴリ」も seed されるため、村長の画面に一見不要なカテゴリが出ることがある。これは**許容する**（村長が消せばよい。§4.2 のとおりプリセットは可変）。逆に seed しないと Stage 3 が確実に失敗するため、参照完全性を優先する。

> 【提案】`SIGNAL` による abort は Flyway の SQL マイグレーションで機能する。【要確認】プロジェクトで `SIGNAL` を使った先例の有無は実装時に確認し、無ければ番人を**テスト側**（`@SpringBootTest` + Testcontainers で移行後の `category_id IS NULL` 件数が 0 であることを検証）に置く。**いずれにせよ「取りこぼしを黙って許す」ことはしない。**

この段階で BE/FE は**まだ `category`（enum）を使い続ける**。DDL だけ先行させる。

#### Stage 2: Migrate（BE/FE を `category_id` 主体へ切替）

1. Entity に `categoryId` を追加。**読み取りは `category_id` 一本に切り替える**。`category`（enum）は**書き込みのみ継続**（対応する `preset_key` があればその値、カスタムなら `OTHER`）
2. API: リクエストは `categoryId` を受ける（`category` は非推奨として当面受理）。レスポンスは `categoryId` / `categoryName` / `categoryColor` を返し、`category`（enum）も**当面併記**
3. `generate:types` 再生成 → FE を `categoryId` 主体へ。`match-recruits.vue:53-59` / `:101-108` の**ハードコード2箇所をマスタ取得に置換**（二重定義の解消）
4. Repository の `findByVillageIdAndCategoryAndStatusAndDeletedAtIsNull`（`:28-29`）を `...AndCategoryIdAnd...` へ

> **【提案】`category` 二重書きの正当化 — 案A への批判と矛盾しないか**
>
> §5.2 で案A を「`OTHER` を詰めると意味が腐敗する」と批判しておきながら、Stage 2 で `OTHER` を詰めるのは一見矛盾する。矛盾しない理由は3点:
>
> 1. **書く理由が「制約」であって「設計」ではない** — `category` は `NOT NULL`（`V9.147:17`）なので、Stage 3 で DROP するまで**何かを入れざるを得ない**。設計上の意味を持たせているのではなく、DDL に強制されているだけである
> 2. **読み手がいない** — Stage 2 で**読み取りは `category_id` 一本に切り替わる**。`category` は write-only のレガシー列となり、集計・フィルタ・表示のいずれも参照しない。案A で腐敗が問題になるのは `category` が**正として読まれ続ける**からであって、読み手がゼロなら腐敗しようがない
> 3. **期限が切られている** — 案A は恒久、Stage 2 は Stage 3 までの一時措置
>
> 唯一の存在意義は **Stage 2 のロールバック余地**（Stage 2 のコードを revert しても旧コードが `category` を読んで動く）である。Stage 3 を同一キャンペーン内で完了させることを条件とする。**Stage 2 で止めて放置することは禁止**（それは案A に堕ちる）。

#### Stage 3: Contract（旧表現の撤去）

1. `category_id` を `NOT NULL` 化（バックフィル完了が Stage 1 の番人で保証済み）
2. `village_match_recruits.category` カラムを DROP、`idx_vmr_category` を DROP
3. `VillageMatchRecruitCategory` enum クラスを削除
4. DTO から `category` を除去 → `generate:types` 再生成 → FE の残存参照を除去
5. i18n `village.matchRecruit.category.*`（`village.json:421-426`）を6言語から削除
6. §3.3 の `activeTab` null 許容化（小改善）

### 5.5 プリセットの seed 方針 —— 【重要な設計判断】

「既定プリセット4件（練習試合/審判/会場/その他）を全村に配る」のは**課題A を再生産する**。マンション管理組合村に「審判」が自動で生えるのは、まさにマスターが不満に思っている状態そのものである。

**【提案】村の状態で seed 内容を分ける:**

| 対象 | seed 内容 | 根拠 |
|---|---|---|
| **募集行を1件でも持つ村**（村・募集の**論理削除を問わない**） | その村で**実際に使われている `category` の値のみ**。名称は現行 ja ラベル（【確認済み】`village.json:421-426` の「練習試合」「審判」「会場」「その他」）、`preset_key` に旧 enum 値、`is_preset = TRUE` | データ保存と参照完全性が最優先。使っていないカテゴリまで配らない |
| **募集行が1件も無い村**（論理削除済みの村は**対象外**） | 汎用プリセット（下記） | スポーツ語彙を配らない。消えた村にゴミを作らない |
| **新規村（村作成時）** | 汎用プリセット（下記） | 同上 |

seed 導出クエリ（**`deleted_at` で絞らないこと**。§5.4「論理削除の罠」）:

```sql
-- 募集行を持つ村 × 使われている category 値。村・募集の deleted_at は問わない。
SELECT DISTINCT village_id, category FROM village_match_recruits;
```

> **【提案】非対称性の理由**: 「募集を持つ村」は論理削除済みでも seed する（さもないとバックフィルが漏れて Stage 3 の `NOT NULL` 化が失敗する＝§5.4 の罠）。一方「募集を持たない村」は論理削除済みなら seed しない（バックフィル対象が無いので参照完全性に影響せず、消えた村に汎用プリセット3行を作る意味が無い）。**この非対称は意図的**である。

**【提案】汎用プリセット（スポーツ語彙を含まない3件）:**

| preset_key | ja 名称 | display_order |
|---|---|---|
| `PARTICIPANT` | 参加者募集 | 10 |
| `HELPER` | 協力者募集 | 20 |
| `OTHER` | その他 | 30 |

**【提案】スポーツ村向けテンプレの一括適用**: スポーツ系村の村長が毎回4件を手入力するのは退行なので、カテゴリ管理画面に「**スポーツ村テンプレを追加**」ボタンを置き、押すと練習試合/審判/会場を一括追加できるようにする（Phase 2 の任意項目）。**押さない限り生えない**ことが重要。

> ### 🔷 マスター御裁可（2026-07-15）— 汎用プリセットは上表の3件で**確定**
>
> `PARTICIPANT`「参加者募集」/ `HELPER`「協力者募集」/ `OTHER`「その他」の3件で確定。**実装はこの語彙・この `preset_key`・この `display_order` をそのまま用いること**（勝手に増やさない・言い換えない）。スポーツ語彙（練習試合・審判・会場）は**汎用プリセットに含めない**という点が本裁可の要旨である。

### 5.6 付随課題 — `match_date NOT NULL` のスポーツ固着

【確認済み】`V9.147:20` — `match_date DATE NOT NULL COMMENT '試合予定日'`、`VillageMatchRecruitEntity.java:63-64` も `nullable = false`。

カテゴリを汎用化しても**日付が必須のまま**では、「マネージャー募集」「引っ越し手伝い募集」のような**日付を持たない募集が登録できない**。これは §1.1 と同根のスポーツ固着である。

**【提案】`match_date` を NULL 許容に緩和する。** `NOT NULL → NULL` は制約の**緩和方向**であり、既存データを一切壊さない（既存行は全て値を持つ）。Stage 1 の Expand に含めてよい。

【提案・任意】さらに踏み込むなら、カテゴリマスタに `requires_date BOOLEAN NOT NULL DEFAULT FALSE` を持たせ、村長が「このカテゴリは日付必須」と定義できるようにする。ただしスコープが膨らむため **Phase 2 の任意拡張**とし、Phase 1 では単純に NULL 許容とする。

> **【要確認】** FE の `MatchRecruitForm` が `matchDate` を必須バリデーションしているかは未確認。実装時に確認し、緩和に追随させること。

### 6.3 認可の実装 — 金型は `requireModerator`（BAN 安全な系統）

村ドメインの認可ヘルパーは §3.4 の注のとおり **5つの別名・6実装に分裂**しており、**そのうち `bannedAt` を検査するのは `requireModerator` という名前の2実装だけ**である。

Q1 の御裁可により本設計は **HEADMAN + ELDER** となった。これは `requireModerator` の意味論（「モデレーター＝村長または長老」）と**完全に一致**する。したがって:

> **【提案】金型は `requireModerator` を採る**（`requireHeadmanOrElder` ではない）。理由は3点:
> 1. **意味論が一致** — Q1 裁可後の要件「HEADMAN or ELDER」はまさに「モデレーター」である
> 2. **BAN 安全** — 長老に CRUD を開ける以上 `bannedAt` 検査は必須（後述）。`requireModerator` は最初から持っている
> 3. **membership を返す** — 監査ログに操作者の membership を残せる（`VillageReportService` が `handler_membership_id` に使っている形）

【確認済み】`VillageReportService.java:249-261` を**そのまま引用**（`VillageCalendarService.java:261` も同名・同型。**この2つが `requireModerator` の全て**）。以下はコードの原文であり、本書による注釈は加えていない:

```java
private VillageMembershipEntity requireModerator(UUID villageId, Long actorUserId) {
    VillageMembershipEntity m = membershipRepository
            .findByVillageIdAndSubjectTypeAndSubjectIdAndLeftAtIsNull(
                    villageId, VillageSubjectType.USER, actorUserId)
            .orElseThrow(() -> new BusinessException(VillageErrorCode.MODERATION_FORBIDDEN));
    if (m.getBannedAt() != null) {
        throw new BusinessException(VillageErrorCode.MODERATION_FORBIDDEN);
    }
    if (m.getRole() != VillageRole.HEADMAN && m.getRole() != VillageRole.ELDER) {
        throw new BusinessException(VillageErrorCode.MODERATION_FORBIDDEN);
    }
    return m;
}
```

上記のうち **`m.getBannedAt() != null` の3行（原文 `:254-256`）が、この系統だけが持つ BAN 検査**である（他4実装には無い）。

> **メンバーシップ解決の作法**: 実行者は `subjectType = USER` + `subjectId = actorUserId` + `leftAt IS NULL` で引く。【確認済み】`VillageMembershipEntity.java:44-50` のとおり村メンバーシップは `subjectType`（`VillageSubjectType`）+ `subjectId`（Long）の多態設計であり、**ユーザー個人としての参加は必ず `USER` で絞る**必要がある（絞らないと同じ `subjectId` を持つ TEAM/ORGANIZATION の行を誤って掴む）。memory `project_matching_authz_userid_as_teamid_idor` と同型の事故を避けるため、新規 Service でもこの3条件を必ず揃えること。

**【提案】実装方針**: `VillageRecruitCategoryService` に上記と**同型の `requireModerator(UUID villageId, Long actorUserId)`** を private で持ち、`create` / `update` / `delete` / `reorder` の先頭で呼ぶ。役職違反時は `VillageErrorCode.MODERATION_FORBIDDEN`（= `VILLAGE_024` / 403）。**新しい 403 コードは作らない**（既存体系に合わせる）。

> **【重要・御裁可に伴う必須要件】BAN 検査は省略不可**
>
> Q1 の裁可で**長老に CRUD を開けた**以上、`bannedAt` 検査は**必須**である。村長は事実上 BAN されない（BAN を実行するのが村長自身）が、**長老は村長に BAN され得る**。BAN された長老が募集カテゴリを作り替え・削除できる状態は、BAN の意味を失わせる。
>
> - **必ず `m.getBannedAt() != null` を弾く**こと
> - **【提案】エラーコードは `MEMBER_BANNED`（`VILLAGE_031` / 403）を使う** — 【確認済み】`VillageErrorCode.java:105-106` に定義済みでありながら**村ドメイン全体で未使用**（§3.4）。金型の `requireModerator` は BAN 時も `MODERATION_FORBIDDEN` を投げるが、本設計では**「権限が無い」と「BAN されている」を区別する**方が利用者に正直である（症状を隠さない原則）。

**IDOR 対策**: 【確認済み】`TodoStatusLabelService.java:118-121` の先例に従う（**引用元は Todo ドメイン**。村の親設計書 §6.6（`:1090`）も「IDOR 対策」の節だが、内容は `@PreAuthorize("@villageAccessGuard.canRead(#villageId)")` によるスコープ絞り込みの話で、**404-vs-403 の方針には触れていない**）:

### 7.1 原則 — 村長の自由入力は i18n 対象外

**【提案】**
- カテゴリ名は `{{ category.name }}` で**そのまま描画**する。`$t()` を通さない
- 一方、**画面の枠**（見出し・ボタン・バリデーションメッセージ・空状態）は従来どおり `$t()` 必須。【確認済み】ロケールは6言語（`locales/{ja,en,zh,ko,es,de}/village.json` が全て存在）
