> **ステータス**: 🟢 設計完了

> **最終更新**: 2026-05-25
> **関連ドキュメント**: F05.3 電子印鑑（押印連携なし・将来検討）、F04.3 プッシュ通知（重要度別通知）、F15.3 マイスコープフォルダ（ScopeFolder のネスト・色・アイコン設計を踏襲）

## 1. 概要

組織・チーム内のメンバーが目的別カテゴリのもとでスレッド形式の情報共有を行う掲示板機能。ネスト返信（ツリー構造）により文脈を保った議論ができ、5段階の重要度設定と既読トラッキングにより、重要な連絡の見落とし防止と確認状況の可視化を実現する。ピン留め・ロック・アーカイブ機能で運用上の情報整理をサポートし、リアクション（絵文字スタンプ）で軽量なフィードバックを可能にする。アーカイブしたスレッドは**保管庫（アーカイブ）**へ集約され、**ネスト（多階層）フォルダ**でスコープ（チーム/組織）全員が共有する形に整理できる。カテゴリ別の投稿権限制御、下書き自動保存、一括既読、画像サムネイルプレビューなどの利便性機能も備える。

**インデックス**
```sql
INDEX idx_bulletin_categories_scope (scope_type, scope_id, display_order)  -- スコープ別カテゴリ一覧
```

**制約・備考**
- `scope_type` によって `scope_id` の参照先が異なるため DB レベルの FK 制約は設けない（アプリ層で検証）
- カテゴリ名の重複防止は DB UNIQUE 制約ではなく **Service 層で `deleted_at IS NULL` の既存レコードと照合**して制御する（論理削除レコードと同名のカテゴリを再作成可能にするため。DB UNIQUE はソフトデリートと競合する）
- カテゴリ削除時: 配下のスレッドは「未分類」として残す（カテゴリとの紐付けを NULL にセット）
- 初期カテゴリ: チーム/組織作成時に「連絡事項」「相談」「雑談」の3件を自動作成

##### スコープ種別の拡張（`TOURNAMENT` / `TOURNAMENT_DIVISION`）— F08.7.1 連携

- F08.7.1 トーナメント連絡スペースのため、`scope_type` に **`TOURNAMENT`**（大会全体）/ **`TOURNAMENT_DIVISION`**（ディビジョン単位）を追加する。`scope_id` には `tournaments.id` / `tournament_divisions.id` を直接格納する（クロスドメイン FK なし）。
- 大会/ディビジョン作成時に `BulletinCategoryService.provisionForScope(...)` でデフォルトカテゴリ（「お知らせ」「連絡」）を自動生成する（自動付帯）。
- read/write 認可は本書の TEAM/ORGANIZATION とは別系統で、F08.7.1 の `TournamentContactAccessService`（参加チーム＝`tournament_participants` の REGISTERED/ACTIVE メンバー＝閲覧、各チーム代表＋主催組織 ADMIN＝投稿）が担う。詳細は [F08.7.1/01_communication.md](F08.7.1_tournament_extensions/01_communication.md)。
- 値追加方法: 実装が ENUM なら `ALTER TABLE ... MODIFY COLUMN scope_type ENUM(...)`、VARCHAR なら DDL 不要。実装時に実スキーマを確認する。

| カラム名 | 型 | NULL | デフォルト | 説明 |
|---------|---|------|-----------|------|
| `id` | BIGINT UNSIGNED | NO | AUTO_INCREMENT | PK |
| `category_id` | BIGINT UNSIGNED | YES | NULL | FK → bulletin_categories。ON DELETE SET NULL（カテゴリ削除時に未分類へ移行）。NULL = 未分類 |
| `scope_type` | ENUM('TEAM', 'ORGANIZATION', 'TOURNAMENT', 'TOURNAMENT_DIVISION') | NO | — | スコープ種別（`TOURNAMENT` / `TOURNAMENT_DIVISION` は F08.7.1 連絡スペース） |
| `scope_id` | BIGINT UNSIGNED | NO | — | FK → teams / organizations / tournaments / tournament_divisions（クロスドメインのため DB FK は設けない） |
| `author_id` | BIGINT UNSIGNED | NO | — | FK → users（投稿者）。ON DELETE RESTRICT |
| `title` | VARCHAR(200) | NO | — | スレッドタイトル |
| `body` | TEXT | NO | — | 本文（Markdown 対応） |
| `priority` | ENUM('CRITICAL', 'IMPORTANT', 'WARNING', 'INFO', 'LOW') | NO | 'INFO' | 重要度（5段階） |
| `read_tracking_mode` | ENUM('NONE', 'COUNT_ONLY', 'SHOW_READERS') | NO | 'COUNT_ONLY' | 既読表示モード |
| `is_pinned` | BOOLEAN | NO | FALSE | ピン留め状態 |
| `is_locked` | BOOLEAN | NO | FALSE | ロック状態（TRUE = 返信不可） |
| `is_archived` | BOOLEAN | NO | FALSE | アーカイブ状態（TRUE = 一覧のデフォルト表示から除外 = 保管庫に格納） |
| `archive_folder_id` | BINARY(16) | YES | NULL | 保管庫フォルダ（`bulletin_archive_folders.id`）。NULL かつ `is_archived=TRUE` ＝ 保管庫直下（未分類）。`is_archived=FALSE` のときは無視（NULL 運用）。スレッドは 1 フォルダのみ所属 |
| `reply_count` | INT UNSIGNED | NO | 0 | 返信数（denormalized。返信追加/削除時にアトミック更新） |
| `read_count` | INT UNSIGNED | NO | 0 | 既読者数（denormalized。既読記録時に +1、ユーザー退会時の減算はバッチで補正） |
| `last_replied_at` | DATETIME | YES | NULL | 最終返信日時（スレッド一覧のソート用） |
| `source_type` | VARCHAR(50) | YES | NULL | 自動生成元の機能種別（例: `SAFETY_CHECK`）。手動投稿の場合は NULL |
| `source_id` | BIGINT UNSIGNED | YES | NULL | 自動生成元のレコード ID |
| `created_at` | DATETIME | NO | CURRENT_TIMESTAMP | |
| `updated_at` | DATETIME | NO | CURRENT_TIMESTAMP ON UPDATE | |
| `deleted_at` | DATETIME | YES | NULL | 論理削除日時（SoftDeletableEntity 適用） |

**インデックス**
```sql
INDEX idx_bulletin_threads_scope_pinned (scope_type, scope_id, is_pinned DESC, last_replied_at DESC)  -- スコープ別スレッド一覧（ピン留め優先 + 新着順）
INDEX idx_bulletin_threads_category (category_id, last_replied_at DESC)                                -- カテゴリ別スレッド一覧
INDEX idx_bulletin_threads_author (author_id)                                                          -- 投稿者別の検索
INDEX idx_bulletin_threads_source (source_type, source_id)                                             -- 自動生成元の逆引き
INDEX idx_bulletin_threads_archive_folder (archive_folder_id)                                          -- 保管庫フォルダ別スレッド一覧
FULLTEXT INDEX ft_bulletin_threads_title (title)                                                       -- タイトル全文検索
```

**制約・備考**
- `reply_count` は denormalized カウンターキャッシュ。返信の INSERT/DELETE 時に `UPDATE bulletin_threads SET reply_count = reply_count ± 1` でアトミック更新（COUNT クエリ廃止）
- `read_count` は denormalized カウンターキャッシュ。既読記録時に +1。ユーザー退会による既読データ CASCADE 削除時は即時減算せず、90日バッチの実行時に COUNT で補正する（退会は低頻度のため許容）
- `last_replied_at` も返信追加時に更新。返信が論理削除された場合は直前の返信の `created_at` で再計算する（`SELECT MAX(created_at) FROM bulletin_replies WHERE thread_id = ? AND deleted_at IS NULL`）。返信が全て削除された場合は NULL に戻る。スレッド一覧の「最近の活動順」ソートでは `COALESCE(last_replied_at, created_at)` を使用し、返信なしスレッドも正しくソートする
- `source_type` + `source_id`: 他機能からの自動生成スレッドを識別
  - `SAFETY_CHECK`: 安否確認（`safety_checks.id`）— 従来通り（`safety_checks.bulletin_thread_id` からの逆引きにも対応）
  - `SURVEY`: アンケート（`surveys.id`）— アンケート作成時に自動生成、CLOSED 時に `is_locked = TRUE`（F05.4 連携）
  自動生成スレッドは `category_id = NULL`（「未分類」扱い）で作成される
- `archive_folder_id`: 同一 bulletin ドメイン内の `bulletin_archive_folders` を参照するが、bulletin 系の慣習（FK 制約は最小限・参照整合性はアプリ層で保証。例: `bulletin_replies.parent_reply_id`、`category_id` も同方針）に揃え **DB レベルの FK 制約は設けない**。スレッドのアーカイブ解除（`is_archived=FALSE`）時に Service 層で `archive_folder_id` を NULL にリセットする。フォルダ削除時は配下スレッドの `archive_folder_id` を NULL（保管庫直下）に退避（§5 参照）。スレッドとフォルダの `scope_type`/`scope_id` は一致していること（不一致は 409。アプリ層検証）
- `FULLTEXT` インデックスは MySQL FULLTEXT を使用し `MATCH(title) AGAINST(? IN BOOLEAN MODE)` で検索。将来的に本文検索が必要になった場合は `FULLTEXT(title, body)` への拡張で対応可能（検索ロジックは Service 層に集約し、インデックス変更のみで移行できる設計とする）
- 論理削除時: 配下の返信・既読データはそのまま保持（スレッド復元時に復活）。ただし既読データは90日バッチで物理削除される
- `category_id` が NULL のスレッドは「未分類」として扱う（カテゴリ削除時のフォールバック）

#### `bulletin_replies`

| カラム名 | 型 | NULL | デフォルト | 説明 |
|---------|---|------|-----------|------|
| `id` | BIGINT UNSIGNED | NO | AUTO_INCREMENT | PK |
| `thread_id` | BIGINT UNSIGNED | NO | — | FK → bulletin_threads。ON DELETE CASCADE |
| `parent_reply_id` | BIGINT UNSIGNED | YES | NULL | FK → bulletin_replies（自己参照）。ON DELETE SET NULL（親返信が物理削除された場合、子返信はスレッド直下に昇格）。NULL = スレッド直下の返信 |
| `author_id` | BIGINT UNSIGNED | NO | — | FK → users（投稿者）。ON DELETE RESTRICT |
| `body` | TEXT | NO | — | 返信本文（Markdown 対応） |
| `depth` | TINYINT UNSIGNED | NO | 0 | ネストの深さ（0 = スレッド直下、1 = 返信の返信、...）。最大5 |
| `created_at` | DATETIME | NO | CURRENT_TIMESTAMP | |
| `updated_at` | DATETIME | NO | CURRENT_TIMESTAMP ON UPDATE | |
| `deleted_at` | DATETIME | YES | NULL | 論理削除日時（SoftDeletableEntity 適用） |

**インデックス**
```sql
INDEX idx_bulletin_replies_thread (thread_id, created_at ASC)           -- スレッド内の返信一覧（時系列）
INDEX idx_bulletin_replies_parent (parent_reply_id, created_at ASC)     -- 特定返信への子返信一覧
INDEX idx_bulletin_replies_author (author_id)                           -- 投稿者別の検索
```

**制約・備考**
- **ツリー構造**: `parent_reply_id` による自己参照で再帰的なネストを実現。`depth` カラムで深さを追跡し、最大5階層に制限（それ以上のネストは 400 エラー）
- **表示順**: ツリー構造の描画はフロントエンド側で `parent_reply_id` を元に再構築。API は `created_at ASC` のフラットリストで返却し、クライアントがネスト表示を組み立てる
- `thread_id` に ON DELETE CASCADE を設定 — スレッドの物理削除時に返信も連動削除（論理削除では CASCADE しない。論理削除は Service 層で個別制御）
- 論理削除された返信は「この返信は削除されました」として表示し、子返信のツリーは保持する（子返信が孤立しない設計）
- 返信追加時に `bulletin_threads.reply_count` を +1、論理削除時に -1（deleted_at をセットした時点でカウントから除外）

#### `bulletin_read_status`

| カラム名 | 型 | NULL | デフォルト | 説明 |
|---------|---|------|-----------|------|
| `id` | BIGINT UNSIGNED | NO | AUTO_INCREMENT | PK |
| `thread_id` | BIGINT UNSIGNED | NO | — | FK → bulletin_threads。ON DELETE CASCADE |
| `user_id` | BIGINT UNSIGNED | NO | — | FK → users。ON DELETE CASCADE |
| `read_at` | DATETIME | NO | CURRENT_TIMESTAMP | 既読日時 |

**インデックス**
```sql
UNIQUE KEY uq_bulletin_read_status_thread_user (thread_id, user_id)  -- 同一ユーザーの重複既読防止
INDEX idx_bulletin_read_status_user (user_id, read_at DESC)          -- ユーザー別の既読履歴
```

**制約・備考**
- `read_tracking_mode = 'NONE'` のスレッドでも既読レコードは INSERT する（未読/既読のフィルタリング用。表示モードは「既読UIをどう見せるか」の制御であり、記録自体は常に行う）
- ON DELETE CASCADE: スレッド削除時に既読データも連動削除
- **データ保持期限**: 既読データは投稿（`bulletin_threads.created_at`）から **90日後** にバッチで物理削除する（蓄積量削減）
- ON DELETE CASCADE（users）: ユーザー退会時に既読データも削除（既読カウントの正確性より、退会ユーザーのデータクリーンアップを優先）

**制約・備考**
- 1スレッド/返信あたり最大5ファイル（アプリ層で制御）
- 1ファイル最大6MB（S3 Pre-signed URL のアップロード時にサイズ制限を適用）
- ポリモーフィック参照（`target_type` + `target_id`）のため DB 制約の FK は設けない
- スレッド/返信の論理削除時に添付ファイルはそのまま保持（復元時にファイルが失われないため）。物理削除時に S3 オブジェクトも削除（バッチまたはイベントリスナー）
- `remove_attachment_ids` で個別削除された添付ファイルは `bulletin_attachments` から物理削除し、S3 オブジェクトも非同期で削除する（`@Async` + `S3Client.deleteObject`）
- 大容量ファイルの共有は F05.5 ファイル共有を利用する想定。掲示板の添付は軽量な資料共有（PDF、写真、Officeドキュメント等）用途

**制約・備考**
- プリセット絵文字のみ許可（👍👏🙏😊❤️の5種）。カスタム絵文字は不可（アプリ層でバリデーション）
- ポリモーフィック参照（`target_type` + `target_id`）のため DB 制約の FK は設けない
- 同一ユーザーが同一対象に異なる絵文字を複数付与可能（1つの投稿に👍と❤️の両方を付けられる）
- リアクション追加/削除時に通知は発行しない（ノイズ防止）
- スレッド/返信の論理削除時にリアクションはそのまま保持（復元時に復活）。物理削除時に CASCADE で連動削除

#### `bulletin_archive_folders`

保管庫（アーカイブ）をフォルダ分けして整理するためのテーブル。**スコープ（チーム/組織）全員で共有**し、管理者（ADMIN / DEPUTY_ADMIN）が整理する（個人別フォルダではない）。**ネスト（多階層）**に対応する。

| カラム名 | 型 | NULL | デフォルト | 説明 |
|---------|---|------|-----------|------|
| `id` | BINARY(16) | NO | UUIDv7（アプリ生成） | PK（`UuidV7Entity` 継承） |
| `scope_type` | ENUM('TEAM', 'ORGANIZATION') | NO | — | スコープ種別（既存 bulletin と統一） |
| `scope_id` | BIGINT UNSIGNED | NO | — | チーム/組織の ID（アプリ層で整合保証、FK なし） |
| `scope_village_id` | BINARY(16) | YES | NULL | 村スコープ時の村 ID（将来対応用。当面 UI は team/org のみ。§5「村スコープの扱い」参照） |
| `parent_folder_id` | BINARY(16) | YES | NULL | 親フォルダ（自己参照ネスト）。NULL = 保管庫直下のルートフォルダ |
| `name` | VARCHAR(100) | NO | — | フォルダ名 |
| `color` | VARCHAR(7) | YES | NULL | フォルダカラー（HEX 形式: #FF5733。視覚識別。ScopeFolder 流用） |
| `icon` | VARCHAR(40) | YES | NULL | アイコン（PrimeIcons 名。例: `pi-folder`） |
| `depth` | TINYINT UNSIGNED | NO | 0 | 階層の深さ。ルート = 0、最大4（= 5 階層） |
| `display_order` | INT UNSIGNED | NO | 0 | 同一親の中での表示順 |
| `created_by` | BIGINT UNSIGNED | YES | NULL | FK → users（作成者）。ON DELETE SET NULL（退会時にフォルダは残す） |
| `created_at` | DATETIME | NO | CURRENT_TIMESTAMP | |
| `updated_at` | DATETIME | NO | CURRENT_TIMESTAMP ON UPDATE | |
| `deleted_at` | DATETIME | YES | NULL | 論理削除日時（`SoftDeletableEntity` 適用） |

**インデックス**
```sql
INDEX idx_bulletin_archive_folders_scope_parent (scope_type, scope_id, parent_folder_id, display_order)  -- スコープ別・親別の子フォルダ一覧（ツリー構築の主クエリ）
INDEX idx_bulletin_archive_folders_parent (parent_folder_id)                                              -- 親フォルダ単独の逆引き（移動・削除時の子取得）
```

**制約・備考**
- **主キーは UUIDv7**（`UuidV7Entity` 継承）。CLAUDE.md 原則6 準拠（新規テーブル）。`bulletin_archive_folders` はテナント（スコープ）ごとに行が増えていくテーブルであり、マスタ例外・シングルトン例外には該当しないため原則6 を適用する
- `scope_type` によって `scope_id` の参照先が異なるため DB レベルの FK 制約は設けない（アプリ層で検証）。既存 bulletin 系テーブルの慣習と一致
- **本テーブルの Repository は `AbstractTenantAwareRepository` を継承しない**。既存 bulletin の Repository が `scope_type`/`scope_id` を明示引数で扱う multi-scope 方式（`AbstractTenantAwareRepository` は `organization_id` 単一カラム前提のため不適合）を採用しており、保管庫フォルダもそれに揃える
- **ネスト方式は隣接リスト + `depth` カラム**を採用。深さ上限が 5 階層（depth ≤ 4）と浅く、クロージャテーブルは保守・書き込みコストの面で過剰なため採用しない。祖先・子孫の取得は depth と `parent_folder_id` を辿る再帰（最大5段で打ち止め）で十分。深さ上限があるため再帰コストは定数で抑えられる
- 自己参照 `parent_folder_id` は**同一ドメイン内**のため CLAUDE.md 原則1（クロスドメイン FK 禁止）には抵触しないが、既存の自己参照（`bulletin_replies.parent_reply_id`）が「FK 制約なし・アプリ層整合」方針のためそれに揃え **FK 制約は設けない**
- フォルダ名の重複は DB UNIQUE 制約で縛らない（同一親内でも同名フォルダを許容。視覚識別は color/icon で補い、UI 上は重複時に注意喚起する程度）。`bulletin_categories` と同様にソフトデリートと UNIQUE の競合を避ける方針
- スコープあたりのフォルダ数上限は **200**（§5「フォルダ数上限」参照。スパム・UI ツリー肥大防止）
- 論理削除（`deleted_at`）時: 配下スレッドの `archive_folder_id` を NULL（保管庫直下）に退避し、直下の子フォルダは削除フォルダの親（なければルート）へ繰り上げ・depth 再計算する（§5「フォルダ削除時の退避ロジック」参照）

#### `POST /api/v1/{scopeType}/{scopeId}/bulletin/threads/{threadId}/archive`

アーカイブ状態を設定する。アーカイブされたスレッドはスレッド一覧のデフォルト表示から除外され、保管庫に格納される。**保管庫フォルダへの振り分けも同時に行える**（任意）。

**リクエストボディ**

```json
{

}
```

- `is_archived`: 必須。`true` でアーカイブ（保管庫へ格納）、`false` でアーカイブ解除（保管庫から戻す）

- `archive_folder_id` を指定する場合: 当該フォルダがスレッドと同一スコープ（`scope_type`/`scope_id` 一致）に存在し、論理削除されていないことを検証

**レスポンス（200 OK）**
```json
{
  "data": {
    "id": 42,
    "is_archived": true,
    "archive_folder_id": "0190e4b2-7c3a-7f9a-8b21-2f6c8d4a9e10"
  }
}
```

**エラーレスポンス**
| ステータス | 条件 |
|-----------|------|
| 400 | バリデーションエラー（`is_archived` 欠落等） |
| 403 | ADMIN / DEPUTY_ADMIN（MANAGE_CONTENT）ではない |
| 404 | スレッドが存在しない / `archive_folder_id` のフォルダが存在しない |
| 409 | `archive_folder_id` のフォルダがスレッドと別スコープ（scope 越境） |

```json
  "color": "#3498DB",
  "icon": "pi-folder"
}
```

- `name`: 必須・1〜100文字
- `parentFolderId`: 任意（NULL = 保管庫直下のルートフォルダ）。指定時は同一スコープに存在する有効フォルダであること。`depth` は親の `depth + 1` で計算し、4 を超える場合は 400
- `color`: 任意・HEX 形式（`#` + 6桁）
- `icon`: 任意・PrimeIcons 名（最大40文字）
- `display_order`: 同一親内の末尾に自動採番（明示指定は PUT で変更）

**レスポンス（201 Created）**
```json
{
  "data": {
    "id": "0190e4b2-7c3a-7f9a-8b21-2f6c8d4a9e10",
    "parentId": null,
    "name": "2025年度",
    "color": "#3498DB",
    "icon": "pi-folder",
    "depth": 0,
    "displayOrder": 0,
    "childCount": 0,
    "threadCount": 0
  }
}
```

**エラーレスポンス**
| ステータス | 条件 |
|-----------|------|
| 400 | バリデーションエラー（名前が空文字等） / 親フォルダ指定により深さ上限（5階層 = depth ≤ 4）を超過 |
| 403 | ADMIN / DEPUTY_ADMIN（MANAGE_CONTENT）ではない |
| 404 | `parentFolderId` のフォルダが存在しない |
| 409 | `parentFolderId` がスレッドと別スコープ（scope 越境） / フォルダ数が上限（200）に達している |

#### `PUT /api/v1/{scopeType}/{scopeId}/bulletin/archive/folders/{folderId}`

フォルダの名前・色・アイコン・表示順を編集する。`parentFolderId` を変更すると**フォルダ移動**になる（サブツリーごと移動）。

**リクエストボディ**
```json
{
  "name": "2025年度（確定）",
  "color": "#2ECC71",
  "icon": "pi-folder-open",
  "displayOrder": 1,
  "parentFolderId": "0190e4b2-aaaa-7c2b-9a44-000000000000"
}
```

- `parentFolderId`: 任意。指定時は移動。以下を検証:
  - **循環参照防止**: 移動先が自分自身または自分の子孫の場合は 400
  - **深さ超過防止**: 移動対象サブツリー全体の最大 `depth` が上限（4）を超えないか検証。超過時は 400
  - 移動後は対象フォルダ + サブツリー全体の `depth` を再計算（新しい親の `depth + 1` を起点に再採番）
- `name`/`color`/`icon`/`displayOrder`: いずれも任意（指定されたフィールドのみ更新）

**レスポンス（200 OK）**: POST と同一形式（移動の場合は更新後の `parentId`/`depth` を反映）

**エラーレスポンス**
| ステータス | 条件 |
|-----------|------|
| 400 | バリデーションエラー / 循環参照（自分自身・子孫への移動） / 移動後の深さが上限超過 |
| 403 | ADMIN / DEPUTY_ADMIN（MANAGE_CONTENT）ではない |
| 404 | フォルダまたは `parentFolderId` のフォルダが存在しない |
| 409 | `parentFolderId` が別スコープ（scope 越境） |

#### `DELETE /api/v1/{scopeType}/{scopeId}/bulletin/archive/folders/{folderId}`

フォルダを論理削除する。配下のデータは失わずに退避する（Service 層トランザクション内で実施）。

**処理（退避ロジック）**
1. 削除対象フォルダ直下のスレッドの `archive_folder_id` を **NULL（保管庫直下 = 未分類）** に退避（`is_archived = TRUE` は維持。スレッド自体は削除しない）
2. 削除対象フォルダ直下の子フォルダを、削除フォルダの **親フォルダ**（親が NULL ＝ 削除対象がルートなら、子フォルダもルート）へ繰り上げ、繰り上げたサブツリー全体の `depth` を再計算
3. 削除対象フォルダに `deleted_at` をセット（論理削除）

**レスポンス（200 OK）**
```json
{
  "data": {
    "id": "0190e4b2-7c3a-7f9a-8b21-2f6c8d4a9e10",
    "deleted_at": "2026-05-25T15:00:00+09:00",
    "moved_thread_count": 5,
    "promoted_folder_count": 2,
    "message": "フォルダを削除しました。5件のスレッドを保管庫直下に移動し、2件の子フォルダを繰り上げました"
  }
}
```

**エラーレスポンス**
| ステータス | 条件 |
|-----------|------|
| 403 | ADMIN / DEPUTY_ADMIN（MANAGE_CONTENT）ではない |
| 404 | フォルダが存在しない |

## 5. ビジネスロジック

### スレッド投稿フロー

```
1. ユーザーがスレッドを投稿
2. バリデーション:
   a. title: 1〜200文字
   b. body: 1〜10,000文字
   c. category_id: 指定時は同一スコープ（scope_type + scope_id が一致）内に存在するか検証
   d. SUPPORTER はスレッド作成不可（返信のみ）。さらにカテゴリの `post_min_role` でロール制限を検証
   d2. カテゴリ指定時: ユーザーのロールが `post_min_role` 以上であるか検証（例: `post_min_role = 'ADMIN'` のカテゴリには MEMBER は投稿不可）
   e. 添付ファイル: ファイル数 ≤ 5、各サイズ ≤ 6MB、content_type ホワイトリスト + ファイルヘッダ（マジックバイト）の二重検証
3. bulletin_threads へ INSERT
3a. 添付ファイルがある場合: S3 へアップロード → bulletin_attachments へ INSERT
4. 重要度に応じた通知を発行（ApplicationEvent: BulletinThreadCreatedEvent）:
   - CRITICAL: プッシュ通知 + LINE通知 + お知らせ欄 + ポップアップ
   - IMPORTANT: プッシュ通知 + お知らせ欄
   - WARNING: お知らせ欄
   - INFO: お知らせ欄（通常）
   - LOW: 通知なし（掲示板内でのみ閲覧可能）
5. メンション解析 → メンションされたユーザーへ個別通知
```

### 返信投稿フロー

```
1. ユーザーが返信を投稿（スレッド直下 or 既存返信への返信）
2. バリデーション:
   a. body: 1〜5,000文字
   b. スレッドがロック中でないことを確認（is_locked = false）
   c. ネスト返信の場合: 親返信の depth + 1 ≤ 5 を確認
3. bulletin_replies へ INSERT（depth = 親の depth + 1。スレッド直下は 0）
3a. 添付ファイルがある場合: S3 へアップロード → bulletin_attachments へ INSERT
4. bulletin_threads の reply_count を +1、last_replied_at を更新（アトミック UPDATE）
5. 通知対象を収集（スレッド作成者 + 親返信の作成者）し、重複を排除してから通知（ApplicationEvent: BulletinReplyCreatedEvent）。自分自身への通知はスキップ
6. メンション解析 → メンションされたユーザーへ個別通知（ステップ5と重複するユーザーは除外）
```

### 既読記録フロー

```
1. ユーザーがスレッド詳細を開く（GET /threads/{id}）→ サーバー側で暗黙的に既読を記録
   ※ GET の副作用を避けたい場合はフロントエンドから明示的に POST /threads/{id}/read を呼び出す方式も可。
     現設計では GET 詳細時に Service 層で自動記録する方式を採用（ユーザーの手間を省くため）
2. bulletin_read_status へ UPSERT（存在チェック後に INSERT。既存の場合はスキップ）
2a. 新規 INSERT の場合: bulletin_threads.read_count を +1（アトミック UPDATE）
3. read_tracking_mode に関わらず記録する:
   - NONE: 記録するが UI に表示しない
   - COUNT_ONLY: 「既読 N」の数字を表示
   - SHOW_READERS: アイコン一覧 + クリックでアカウント名表示
```

### 安否確認連携フロー

```
1. 安否確認が実行される → SafetyCheckCreatedEvent
2. BulletinService が購読:
   a. 対象スコープの掲示板に専用スレッドを自動生成
      - author_id: 安否確認を実行したユーザー（safety_checks.created_by）
      - タイトル: 「【安否確認】{実行日時 yyyy/MM/dd HH:mm}」
      - 優先度: CRITICAL
      - read_tracking_mode: SHOW_READERS
      - source_type: SAFETY_CHECK, source_id: safety_check.id
      - is_pinned: true（自動ピン留め）
   b. safety_checks.bulletin_thread_id に生成したスレッドの ID を保存
3. メンバーが安否回答 → SafetyCheckResponseEvent
   a. 専用スレッドに自動返信を追加（author_id = 回答したユーザー。本文: 「{ユーザー名}: {ステータス} — {メッセージ}」）
   b. BulletinReplyCreatedEvent を発行 → ポーリング経由でフロントエンドに反映（将来 WebSocket 導入時はリアルタイム配信に切り替え）
4. 安否確認クローズ → スレッドを自動ロック（is_locked = true）
```

### お知らせ掲示板への伝搬フロー（カスケード通知連携）

```
上位組織からのお知らせ（announcement）が掲示板に表示される仕組み:

1. 上位組織の ADMIN がお知らせを発行（announcement_scope を指定）
2. 各チーム/組織の掲示板ロード時にプルモデルで判定:
   a. 自組織の直接スレッド → 表示
   b. 上位組織からのお知らせで announcement_scope が自スコープを含む → 表示
3. 表示判定ルール:
   - SELF: 送信元組織の掲示板のみ
   - ORGANIZATIONS: 送信元 + サブツリー内の全子組織の掲示板
   - TEAMS: 送信元 + サブツリー内の全組織 + 全チームの掲示板

※ 伝搬ロジックの詳細は F01.2 組織・チーム設計書を参照

**パフォーマンス戦略**:
- 祖先組織の取得は再帰 CTE ではなく `group_hierarchy`（クロージャテーブル）の JOIN で O(1) 取得
- 祖先一覧は組織階層の変更頻度が低いため Valkey に TTL 1時間でキャッシュ（組織移動時にキャッシュ無効化）
- お知らせ自体もスコープ別に Valkey キャッシュ（お知らせ作成/削除時に無効化）
- 階層の深さに依存しないクエリ構造のため、大規模組織でも安定したレスポンスタイムを維持
```

### リアルタイム更新戦略

```
■ 初期リリース（Phase 5）: ポーリング方式（Twitter/タイムライン型）
- スレッド一覧: 画面上部に「新しいスレッドがあります」バナーを表示（30秒間隔のポーリング）
- スレッド詳細: 「新しい返信があります」バナーを表示（同上）
- ユーザーがバナーをタップして手動リロード（プルリフレッシュ）
- ポーリングエンドポイント: GET /bulletin/threads/updates?scope_type=TEAM&scope_id=5&since={ISO8601}
  → 指定日時以降の新規スレッド数・更新スレッド数を返却（軽量レスポンス）

■ 将来（WebSocket 導入時）: イベント駆動に切り替え
- 以下の ApplicationEvent を発行する設計は Phase 5 で組み込み済み:
  - BulletinThreadCreatedEvent（新スレッド作成）
  - BulletinReplyCreatedEvent（返信追加）
  - BulletinThreadUpdatedEvent（ピン留め/ロック/重要度変更）
- WebSocket 導入時はこれらのイベントを STOMP + Valkey メッセージブローカー経由で配信するリスナーを追加するだけで移行可能
- フロントエンドはポーリング → WebSocket への切り替えをフィーチャーフラグで制御
```

### コルクボード連携

```
掲示板スレッドはコルクボードの参照カード（ref_type = 'BULLETIN_THREAD'）として保存可能。

1. ユーザーがスレッドをコルクボードに保存
2. corkboard_cards に INSERT（ref_type='BULLETIN_THREAD', ref_id=thread_id, content_snapshot=本文先頭5,000文字）
3. 元スレッドが削除されても content_snapshot で内容を保持
4. GET /bulletin-threads/{id}/context で前後のスレッドコンテキストを取得可能
```

### 既読データのバッチ削除

```
1. 日次バッチ（深夜帯に実行）
2. bulletin_read_status のうち、紐付く bulletin_threads が以下の条件を全て満たすレコードを物理削除:
   a. bulletin_threads.created_at が90日以上前
   b. bulletin_threads.is_pinned = false（ピン留めスレッドは除外）
   ※ ピン留め解除後は通常通り90日カウントダウンが始まる
3. バッチサイズ: 1,000件ずつ DELETE（ロック時間を最小化）
4. 削除対象: 全 read_tracking_mode のスレッドの既読データ（モードに関わらず一律削除）
5. 削除後: 対象スレッドの read_count を COUNT で再計算して補正
```

### 下書き保存（フロントエンド）

```
■ 自動保存（localStorage）
- スレッド作成・編集フォームで10秒間隔のデバウンス付き自動保存
- キー: `bulletin_draft_{scope_type}_{scope_id}_{thread_id || 'new'}`
- 保存内容: { title, body, category_id, priority, files（ファイル名のみ） }
- 復元: フォーム表示時に localStorage を確認し、下書きが存在する場合は復元ダイアログを表示
  - 「復元する」→ フォームに反映
  - 「破棄する」→ localStorage から削除
- 投稿成功時: 対応する下書きを localStorage から削除
- サーバーサイドの DB 保存は不要（コスト0、オフラインでも動作）
```

### リアクション集計

```
1. リアクション追加/削除時:
   a. bulletin_reactions へ INSERT / DELETE
   b. レスポンスに最新の reaction_counts を返却（GROUP BY emoji で集計）
2. スレッド一覧/詳細取得時:
   a. reaction_counts: 対象の全リアクションを GROUP BY emoji で集計（LEFT JOIN + サブクエリ）
   b. my_reactions: リクエストユーザー自身のリアクション絵文字の配列（詳細画面のみ）
3. 通知: リアクションの追加/削除では通知を発行しない（返信のノイズ代替のため、通知まで出すと本末転倒）
```

### 画像サムネイル生成

```
1. 添付ファイルのアップロード時に content_type が image/* の場合:
   a. is_image = true をセット
   b. S3 アップロード後、CloudFront Functions（または Lambda@Edge）で サムネイル（幅200px）を自動生成
   c. サムネイルは S3 の別プレフィックス（`thumbnails/`）に保存
2. 画像添付のレスポンスに thumbnail_url を含める（Pre-signed URL）
3. 非画像ファイルの場合: thumbnail_url = null
4. スレッド一覧では attachment_count + 最初の画像のサムネイルを返却（プレビュー表示用）
```

### 保管庫（アーカイブ）フォルダ整理フロー

```
■ ユーザビリティ方針（ADHD 配慮）
- アーカイブはスレッド一覧から「ワンクリック」で実行できる（フォルダ指定は任意）。
  →「今すぐ片付けたい」を最優先し、入力摩擦をゼロに保つ。フォルダ振り分けは後からいつでも整理可能。
- フォルダ未指定でアーカイブしたスレッドは保管庫直下（未分類）に溜まり、保管庫ビューで後からまとめて振り分けられる。
- フォルダはネスト（多階層・最大5階層）で整理でき、色とアイコンで視覚識別する。

■ フォルダ作成・移動の深さ計算と上限
1. フォルダの depth = 親フォルダの depth + 1（ルートフォルダ = 0）
2. 上限は depth ≤ 4（= 5 階層）。作成・移動で超過する場合は 400
3. 移動（PUT で parentFolderId 変更）時は、移動対象フォルダのサブツリー全体について
   「(移動先 depth + 1) + サブツリー内の相対最大深さ」が 4 を超えないか検証してから実行する
4. 移動を確定したら対象フォルダ + サブツリー全体の depth を再計算（新しい親基準で再採番）

■ 循環参照防止
- 移動先 parentFolderId が「自分自身」または「自分の子孫」の場合は 400
- 判定は移動対象フォルダから parent_folder_id を辿って祖先集合を作る代わりに、
  移動対象のサブツリー（子孫集合）を depth 上限 5 段の範囲で展開し、その中に移動先が含まれるかで判定する
  （深さ上限があるため再帰は最大5段で打ち止め＝スタックオーバーフロー/無限ループのリスクなし）

■ フォルダ削除時の退避ロジック（Service 層トランザクション）
1. 削除対象フォルダ直下のスレッドの archive_folder_id を NULL（保管庫直下）へ退避（is_archived は TRUE のまま）
2. 削除対象フォルダ直下の子フォルダを、削除フォルダの親（親が NULL なら子もルート）へ繰り上げ、
   繰り上げたサブツリー全体の depth を再計算
3. 削除対象フォルダに deleted_at をセット（論理削除）
   ※ 孫フォルダ・空フォルダも上記ルールで一貫処理（孫は親フォルダ繰り上げに追従、空フォルダは退避対象なしで論理削除のみ）

■ 並行性制御（複数管理者の同時操作対策）
- フォルダの移動・削除は、対象フォルダとそのサブツリー（子孫フォルダ群）に悲観ロック（SELECT ... FOR UPDATE）を取得した上で
  循環参照判定・depth 再計算・退避を 1 トランザクション内で実行する。2 人の管理者が同時に移動して循環を作る／depth が不整合になる／
  退避漏れが起きる、といったレースを構造的に防ぐ（リトライで症状を隠さず根治）
- フォルダ作成時のフォルダ数上限（200）チェックも、同一スコープのフォルダ行をロックして計数し上限の同時すり抜けを防ぐ

■ scope 越境防止
- スレッドのフォルダ振り分け（archive 拡張 / PATCH .../folder）・フォルダ移動時、
  スレッドとフォルダ・親フォルダの scope_type/scope_id が一致しない場合は 409

■ フォルダ数上限
- スコープ（チーム/組織）あたり最大 200 フォルダ（deleted_at IS NULL のアクティブフォルダで計数）。
  上限はスパム的な大量作成と保管庫ツリー UI の肥大化を防ぐための値。超過時は 409
- 一般的なチーム/組織の年度・カテゴリ別整理（年度 × 用途で数十フォルダ程度）には十分な余裕がある

■ アーカイブ済みスレッドの扱い
- 保管庫内でも返信・既読記録・リアクションは引き続き可能（既存のアーカイブ仕様を維持）
- 保管庫スレッドは通常一覧のデフォルト表示から除外され、GET .../bulletin/threads?include_archived=true でのみ通常一覧に混ざる。
  保管庫ビュー（GET .../bulletin/archive/threads）はフォルダ単位で保管庫スレッドを閲覧する専用導線
- source_type = 'SAFETY_CHECK'（安否確認自動生成）スレッドもアーカイブ・フォルダ振り分けは可能
  （アーカイブは「一覧から片付ける」操作であり、§6 で禁止しているのは手動「削除」のみ。整理目的のアーカイブ/振り分けは許容する）
```

### 保管庫ビュー（フロントエンド構想）

```
■ 画面構成
- 掲示板に「保管庫」タブ（または別ページ）を設け、未アーカイブの通常一覧と切り替える。
- 保管庫ビューは「フォルダツリー（サイドバー）+ 選択フォルダのスレッド一覧（メイン）」の2ペイン構成。
- サイドバー: bulletin/archive/folders のツリーをアイコン + 色で表示。各フォルダに threadCount バッジ。
  「未分類」（保管庫直下）を常に先頭に固定表示。
- メイン: 選択フォルダのスレッド一覧（GET bulletin/archive/threads?folder_id=...）。folder_id=all で全件横断表示も可能。
- パンくず: ネストの現在位置（例: 保管庫 > 2025年度 > 総会議事録）を表示し、階層を見失わない。

■ 操作
- アーカイブ: 通常スレッド一覧の各スレッドのメニューから「保管庫へ」ワンクリック（フォルダ選択は任意で後回し可能）。
- 振り分け: 保管庫ビューでスレッドをドラッグ＆ドロップ、またはメニューの「フォルダへ移動」で PATCH .../folder を呼ぶ。
- フォルダ作成/編集: ADMIN/DEPUTY_ADMIN のみ表示される「+ フォルダ作成」ボタン・編集メニュー。色/アイコン選択 UI は F15.3 ScopeFolder のコンポーネントを流用。
- MEMBER/SUPPORTER には作成・移動・振り分け UI を出さず、閲覧専用で表示する。
```

### 重要な判定ロジック
- **スレッド作成権限**: MEMBER 以上（SUPPORTER はスレッド作成不可、返信のみ可能）。さらにカテゴリの `post_min_role` による制限あり
- **スレッド削除権限**: 投稿者本人 or ADMIN。DEPUTY_ADMIN はコンテンツ削除権限が権限グループで明示的に付与されている場合のみ
- **返信削除権限**: 投稿者本人 or ADMIN（同上）
- **ピン留め・ロック権限**: ADMIN or DEPUTY_ADMIN（MANAGE_CONTENT 権限）
- **重要度変更権限**: 投稿者本人 or ADMIN
- **ロック中の制限**: 返信の投稿・編集が不可。スレッドのタイトル・本文の編集は ADMIN のみ可
- **ネスト深さ制限**: 最大5階層。超過時は 400 エラー
- **カテゴリ削除時**: 配下スレッドの `category_id` を NULL に更新（未分類に移行）。スレッドは削除しない
- **アーカイブ権限**: ADMIN or DEPUTY_ADMIN（MANAGE_CONTENT 権限）。アーカイブされたスレッドは一覧のデフォルト表示から除外（`include_archived=true` で表示可能）し、保管庫に格納する。返信・既読記録は引き続き可能
- **保管庫フォルダ管理権限**: フォルダの作成・編集・移動・削除、スレッドのフォルダ振り分けは ADMIN or DEPUTY_ADMIN（MANAGE_CONTENT 権限）。MEMBER / SUPPORTER は保管庫・フォルダの**閲覧のみ**可能（スコープ共有のため全員が同じ整理結果を見る）
- **保管庫フォルダのネスト深さ**: 最大5階層（depth ≤ 4）。作成・移動で超過時は 400。隣接リスト + depth カラムで管理し、再帰は深さ上限により最大5段で打ち止め
- **保管庫フォルダの循環参照**: フォルダ移動で移動先が自分自身または子孫の場合は 400（無限ループ・スタックオーバーフロー防止）
- **保管庫フォルダ削除時**: 配下スレッドは保管庫直下（`archive_folder_id = NULL`）へ退避、子フォルダは親へ繰り上げ・depth 再計算。スレッド・子孫データは失わない
- **保管庫フォルダ数上限**: スコープあたり最大 200 フォルダ（超過時 409）
- **アーカイブとフォルダ振り分けの分離**: アーカイブはワンクリック（フォルダ任意）。後から保管庫ビューで振り分け可能。アーカイブ解除時は `archive_folder_id` を自動 NULL リセット
- **ソート**: `last_activity`（デフォルト）= `COALESCE(last_replied_at, created_at) DESC`、`created_at` = `created_at DESC`、`reply_count` = `reply_count DESC`。ピン留めスレッドは全ソートで常に先頭
- **リアクション**: 全ロール（GUEST 除く）がリアクション可能。プリセット絵文字のみ（👍👏🙏😊❤️）。通知なし
- **引用表示**: 返信レスポンスの `parent_reply_id` が非 NULL の場合、フロントエンドで親返信の `body` 先頭200文字を引用ブロックとして表示（DB 変更不要、表示ロジックのみ）
- **カテゴリ別投稿権限**: `post_min_role` でカテゴリごとにスレッド投稿可能な最低ロールを設定。デフォルトは MEMBER。例: 「連絡事項」を ADMIN 専用にする場合は `post_min_role = 'ADMIN'` に設定
- **重要度変更時の通知範囲**: 重要度の引き上げ時のみ通知を発行し、引き下げ時は通知しない

| 変更パターン | 通知範囲 |
|------------|---------|
| → CRITICAL | 全スコープメンバー（既読者含む。安全性に関わる見落とし防止） |
| → IMPORTANT / WARNING | 未読者のみ（既読者への再通知はノイズになるため） |
| → INFO / LOW | 通知なし（重要度を下げる変更で通知は不要） |

## 6. セキュリティ考慮事項

- **認可チェック**: 全 API エンドポイントで `scope_type` + `scope_id` に対するユーザーの所属・ロールを検証
- **XSS 防止**: 本文の Markdown レンダリング時に HTML サニタイズ（`<script>`, `<iframe>`, `onerror` 等を除去）。サーバーサイドでは生の Markdown を保存し、レンダリングはフロントエンドで実施
- **コンテンツ削除の監査**: 他者のスレッド/返信を削除した場合は監査ログに記録（`BULLETIN_THREAD_DELETED`, `BULLETIN_REPLY_DELETED`）
- **レートリミット**: スレッド作成に `Bucket4j` で 1分間5件の制限を適用（スパム防止）。返信は1分間10件。ポーリングエンドポイント（`/threads/updates`）はユーザーあたり1分間20リクエスト（30秒間隔の正常利用の約10倍をバッファ）
- **FULLTEXT 検索の入力制限**: 検索クエリは最大100文字に制限。特殊文字（`+`, `-`, `*`, `~`）をエスケープして MySQL FULLTEXT のインジェクションを防止
- **安否確認スレッドの保護**: `source_type = 'SAFETY_CHECK'` のスレッドは手動削除不可（安否確認機能のクローズ時にのみロック可能）
- **既読データのプライバシー**: `read_tracking_mode = 'COUNT_ONLY'` のスレッドでは readers API が個人情報を返さない（カウントのみ）
- **添付ファイルのバリデーション**: アップロード時に `content_type` をホワイトリスト検証（`image/*`, `application/pdf`, `application/msword`, `application/vnd.openxmlformats-officedocument.*`, `text/plain`, `text/csv`）+ ファイルヘッダ（マジックバイト）の二重検証で `content_type` 偽装を防止。実行可能ファイル（`.exe`, `.sh`, `.bat` 等）は拒否。ファイルサイズは S3 Pre-signed URL の生成時に6MB上限を設定
- **添付ファイルのアクセス制御**: S3 Pre-signed URL の有効期限は15分。URL 生成時にスコープへの所属を検証
- **保管庫フォルダ API の認可**: フォルダ系 API（一覧/作成/更新/削除/スレッド振り分け）も全件で `scope_type` + `scope_id` への所属・ロールを検証。フォルダ・親フォルダ・対象スレッドの scope が一致しない操作は 409（scope 越境拒否）。作成・編集・移動・削除・振り分けは ADMIN / DEPUTY_ADMIN（MANAGE_CONTENT）のみ。MEMBER / SUPPORTER は閲覧のみ
- **フォルダ名の XSS 防止**: フォルダ名はサーバーサイドで生のまま保存し、表示時にフロントエンドでサニタイズ（本文 Markdown と同方針）。`color` は HEX 形式（`#` + 6桁）バリデーション、`icon` は PrimeIcons 名のホワイトリスト/形式検証で任意スクリプト混入を防止
- **循環参照・深さ超過による DoS 防止**: フォルダ移動時の循環参照（自分自身・子孫への移動）と深さ上限超過（depth > 4）をアプリ層で必ず検証し、無限ループ・スタックオーバーフロー・無制限ネストによる再帰コスト爆発を防ぐ。再帰探索は深さ上限5段で必ず打ち止め
- **保管庫操作の監査ログ**: フォルダ削除・スレッドのフォルダ移動を監査ログに記録（`BULLETIN_ARCHIVE_FOLDER_DELETED`, `BULLETIN_THREAD_ARCHIVE_FOLDER_CHANGED`。フォルダ作成・更新も必要に応じて `BULLETIN_ARCHIVE_FOLDER_CREATED` / `BULLETIN_ARCHIVE_FOLDER_UPDATED` を記録）。スコープ共有のため、誰がどの整理操作を行ったか追跡可能にする

- **保管庫フォルダの番号採番【重要】**: 既存 bulletin は V5.x 帯だが、本番 DB は既に高い番号（V68.x 等）まで適用済みのため、V5.x の隙間に挿入すると Flyway の out-of-order 適用になる。**保管庫フォルダの 2 本は V5.x ではなく、実装 PR 時点での最新の空き番号帯を採番する**こと（上記は仮に `Vxx.yyy` と表記。具体的な V 番号は実装 PR で確定）。連番で 2 本（テーブル作成 → カラム追加）を採番し、テーブル作成を先に実行する
- `bulletin_archive_folders` は新規テーブルのため主キーは UUIDv7（BINARY(16)）。`scope_type`/`scope_id` への FK は設けない（アプリ層整合）。`parent_folder_id` は同テーブル内の自己参照だが FK 制約なし（bulletin 慣習）。`created_by` のみ `users` への FK（ON DELETE SET NULL）
- `bulletin_threads.archive_folder_id`（BINARY(16)）は `bulletin_archive_folders.id` を参照するが **FK 制約は設けない**（bulletin 慣習・アプリ層整合）。インデックス `idx_bulletin_threads_archive_folder` のみ追加。カラム追加マイグレーションはテーブル作成マイグレーションの後に実行されること

## 7.1 お知らせウィジェット連携（F02.6）

掲示板スレッドは、作成・編集画面で「お知らせウィジェットに表示する」チェックを入れることで、ダッシュボード上部の横断お知らせウィジェット（F02.6）に表示できる。

### 表示フラグの扱い

- `bulletin_threads` テーブルには **専用カラムを追加しない**（F02.6 案B採用）
- フロントエンドは編集画面を開いた際に `GET /api/v1/teams/{teamId}/announcements?source_type=BULLETIN_THREAD` で既存登録を確認し、チェック状態を復元
- `is_archived = TRUE` のスレッドはお知らせ化不可（400）。アーカイブ時に `announcement_feeds` も自動削除

### 優先度のマッピング

| bulletin_threads.priority | announcement_feeds.priority |
|---|---|
| `CRITICAL` | `URGENT` |
| `IMPORTANT` | `IMPORTANT` |
| `WARNING` | `NORMAL` |
| `INFO` | `NORMAL` |
| `LOW` | `NORMAL` |

### 連動削除・同期

- スレッドの論理削除時、`BulletinThreadDeletedEvent` を発行 → `AnnouncementSyncEventListener` が `announcement_feeds.source_deleted_at` をセット
- タイトル・優先度変更時に `BulletinThreadUpdatedEvent` を発行 → `title_cache` / `priority` を同期
- カテゴリ削除（未分類化）は announcement_feeds に影響しない

### UI 配置

`BulletinThreadForm.vue` の重要度セレクタの下に `AnnouncementToggle.vue` を配置。

### ソースタイプ自動生成からの除外

`source_type = SAFETY_CHECK`（安否確認から自動生成されたスレッド）はお知らせウィジェット化の**対象外**（F02.6 側で弾く）。安否確認は独自の UI フローで目立たせる責務があるため、お知らせウィジェットとの重複を避ける。

`source_type = 'SURVEY'`（アンケートから自動生成されたスレッド）はお知らせウィジェット化の対象外（安否確認と同様の理由：アンケート詳細ページでの表示に特化するため）。

### 保管庫フォルダ機能との整合

- 既存仕様どおり `is_archived = TRUE`（保管庫格納）のスレッドはお知らせ化不可（400）であり、アーカイブ時に `announcement_feeds` も自動削除される。保管庫フォルダへの振り分け（`archive_folder_id` の付与・変更）は **`is_archived = TRUE` を維持したまま**行うため、お知らせウィジェットの挙動には影響しない（保管庫内のスレッドは一貫してお知らせ化対象外）。
- スレッドのアーカイブ解除（`is_archived = false`）後は再びお知らせ化が可能になる（既存仕様どおり。`archive_folder_id` は解除時に自動 NULL リセット）。

## 7.2 i18n（多言語対応）方針

保管庫フォルダ機能で追加する UI 文字列（例: 「保管庫」「フォルダを作成」「フォルダへ移動」「未分類」「2025年度」等のラベル・操作名・空状態メッセージ・確認ダイアログ）は **直書き禁止**。`frontend/app/locales/{ja,en,zh,ko,es,de}/` 配下の該当ファイル（`common.json` 等）に 6 言語すべてへキーを追加し、`$t('key')` で参照する。

- デフォルトロケールは `ja`。未翻訳の言語はとりあえず日本語と同じ値で追加し、後で翻訳する。
- 実際の翻訳作業は実装フェーズで行う（本設計書では方針記載のみ）。
- フォルダ名・スレッドタイトル等のユーザー入力データは i18n 対象外（そのまま表示）。
