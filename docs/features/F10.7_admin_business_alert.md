# F10.7: 業務アラート（ADMIN ダッシュボードウィジェット）

> **ステータス**: 🟢 設計完了
> **実装フェーズ**: Phase 10
> **最終更新**: 2026-05-25
> **モジュール種別**: デフォルト機能（ダッシュボード）管理者向け拡張
> **関連ドキュメント**: F10.1 管理者ダッシュボード、F04.3 プッシュ通知（通知種別追加）、F03.4 予約管理（予約受付通知）、F04.2 チャット（問い合わせチャンネル）

---

## 1. 概要

整骨院・美容室・飲食店等のサービス業チームを運営する ADMIN/DEPUTY_ADMIN が、予約受付・承認待ち・問い合わせ着信をリアルタイムで把握できるよう、個人ダッシュボードに「業務アラート」ウィジェット（`WidgetAdminBusinessAlert`）を追加する。

新着イベント発生時は以下の2経路で通知する:
1. **通知ベル（IN_APP/PUSH）**: 既存の F04.3 通知基盤に新規通知種別を追加して配信
2. **業務アラートウィジェット**: 個人ダッシュボードに要対応件数をチーム別サマリーで表示

ウィジェットは `GET /api/v1/admin/business-alerts/summary` で件数を取得し、既存 WebSocket（NotificationBell の購読ストア）で通知受信時にリアルタイム更新する。

## 2. スコープ

### 対象ロール
| ロール | 操作可能な範囲 |
|--------|--------------|
| ADMIN | 自分が ADMIN を持つ全チームのアラートサマリー閲覧 |
| DEPUTY_ADMIN | 自分が DEPUTY_ADMIN を持つ全チームのアラートサマリー閲覧（予約系は `MANAGE_RESERVATIONS` 権限保有時のみ件数が表示） |
| MEMBER / SUPPORTER / GUEST | 対象外 |
| SYSTEM_ADMIN | 対象外（SYSTEM_ADMIN 用のダッシュボードは F10.1 §AB） |

### 対象レベル
- [ ] 組織 (Organization) — 対象外（予約・問い合わせはチーム単位）
- [x] チーム (Team) — アラートを集計・表示する単位
- [x] 個人 (Personal) — 個人ダッシュボード上にウィジェットを配置

### アラート種別
| アラート | 内容 | モジュール依存 |
|---------|------|--------------|
| 新規予約 | 本日以降の未対応予約件数（`reservations.status IN ('PENDING', 'CONFIRMED')` かつ未来日程） | 予約モジュール有効時のみ |
| 承認待ち | 手動承認モードで `PENDING` 状態の予約件数 | 同上 |
| 問い合わせ未読 | 問い合わせチャンネル（`is_inquiry_channel = TRUE`）の当日分未読メッセージ件数 | チャットモジュール（コア） |

## 3. DB 設計

### 新規テーブルなし

本設計書固有の新規 DB テーブルは作成しない。以下の既存テーブルを利用する:

| テーブル | 利用内容 | 定義場所 |
|---------|---------|---------|
| `notifications` | ADMIN 宛て通知の記録（F04.3 の新規種別を追加） | F04.3 |
| `reservations` | 予約ステータス・件数集計 | F03.4 |
| `chat_channels` | `is_inquiry_channel` フラグ（追加カラム） | F04.2 §3 および本ドキュメント §3.1 |
| `chat_messages` | 問い合わせチャンネルの未読メッセージ集計 | F04.2 |
| `user_roles` | ADMIN/DEPUTY_ADMIN ロール判定 | F01.1 |
| `permission_group_permissions` | `MANAGE_RESERVATIONS` 権限判定 | F01.1 |

### 3.1 chat_channels テーブルへの追加カラム

`chat_channels` テーブルに以下のカラムを追加する（Flyway は F04.2 で管理）:

| カラム名 | 型 | NULL | デフォルト | 説明 |
|---------|---|------|-----------|------|
| `is_inquiry_channel` | BOOLEAN | NO | FALSE | 問い合わせチャンネルフラグ。TRUE の場合、非 ADMIN メンバーがメッセージを投稿すると ADMIN/DEPUTY_ADMIN 全員に `INQUIRY_RECEIVED` 通知を送信する |

**制約**:
- `is_inquiry_channel = TRUE` に設定できるのは `channel_type = 'TEAM'` のチャンネルのみ（Service 層でバリデーション。`ORGANIZATION` / `CROSS_TEAM` / `DIRECT` は対象外）
- 1 チームあたり問い合わせチャンネルは **最大 1 本**。2 本目を設定しようとした場合は 409 エラー
- アーカイブ済みチャンネル（`is_archived = TRUE`）への設定不可

**インデックス（F04.2 Flyway に含める）**:
```sql
CREATE INDEX idx_cc_team_inquiry ON chat_channels (team_id, is_inquiry_channel);
```

### 3.2 Valkey キャッシュ設計

| キー | TTL | 内容 |
|-----|-----|------|
| `admin_alert_summary:{userId}` | 60 秒 | `GET /api/v1/admin/business-alerts/summary` のレスポンスを JSON でキャッシュ |
| `inquiry_notified:{channelId}` | 300 秒 | 同一問い合わせチャンネルへの重複通知抑制フラグ（5 分以内の連続投稿は 1 通のみ通知） |

**キャッシュ invalidate のタイミング**:
- `RESERVATION_RECEIVED` / `RESERVATION_PENDING_APPROVAL` / `INQUIRY_RECEIVED` 通知生成時（新着イベント）
- ADMIN が予約を確定（confirm）/ キャンセル / 完了したとき（`pending_approval` カウント変動）
- 60 秒 TTL を超えた場合（自動失効）

上記以外（問い合わせチャンネルの既読化等）は TTL 失効まで最大 60 秒のラグを許容する（summary ウィジェットは精密カウンターではなく「要対応概況」の提供を目的とするため）。

## 4. API 設計

### エンドポイント一覧

| メソッド | パス | 認証 | 説明 |
|---------|-----|------|------|
| GET | `/api/v1/admin/business-alerts/summary` | 必要（ADMIN or DEPUTY_ADMIN） | 自分が管理するチームの業務アラートサマリー |

### `GET /api/v1/admin/business-alerts/summary`

**認可**: 認証済み、かつ少なくとも 1 チームで ADMIN または DEPUTY_ADMIN ロールを持つこと。条件を満たさない場合は 403。

**クエリパラメータ**: なし

**レスポンス（200 OK）**

```json
          "new_reservations": 2,

        },
        "links": {
          "reservations_url": "/teams/1/reservations",
          "inquiry_channel_url": "/teams/1/chat"

      {
        "team_id": 2,
        "team_name": "美容室チーム B",
        "reservation_module_enabled": true,
        "alerts": {
          "new_reservations": 5,
          "pending_approval": 0,
          "unread_inquiries": 0
        },
        "links": {
          "reservations_url": "/teams/2/reservations",
          "inquiry_channel_url": null
        }
      }

    "total_pending": 11

```

**フィールド定義**
| フィールド | 型 | 説明 |
|-----------|---|------|
| `teams[].team_id` | Long | チーム ID |
| `teams[].team_name` | String | チーム名 |
| `teams[].reservation_module_enabled` | Boolean | 予約モジュールが有効かどうか。`false` の場合、予約系アラートは 0 固定 |
| `teams[].alerts.new_reservations` | Int | 本日以降の未対応予約件数（`CONFIRMED` かつ来院日が未来のもの） |
| `teams[].alerts.pending_approval` | Int | 手動承認モードで `PENDING` の予約件数 |
| `teams[].alerts.unread_inquiries` | Int | 問い合わせチャンネルの当日分未読件数（問い合わせチャンネル未設定の場合は 0） |
| `teams[].links.reservations_url` | String | 予約管理ページへのディープリンク |
| `teams[].links.inquiry_channel_url` | String \| null | 問い合わせチャンネルページへのリンク（設定なし = null） |
| `total_pending` | Int | 全チームの全アラート件数の合計 |

**エラーレスポンス**
| ステータス | 条件 |
|-----------|------|
| 401 | 未認証 |
| 403 | ADMIN/DEPUTY_ADMIN ロールを 1 件も持たない |

**パフォーマンス考慮**:
- Valkey `admin_alert_summary:{userId}` に 60 秒キャッシュ
- 新規通知（`RESERVATION_RECEIVED` / `RESERVATION_PENDING_APPROVAL` / `INQUIRY_RECEIVED`）が生成された時点でキャッシュ invalidate（`NotificationService.createNotification()` の事後処理として実装）
- 管理チーム数が多い場合（> 10 チーム）でも DB クエリは集約 SQL 1 本で処理

## 5. ビジネスロジック

### 5.1 サマリー集計ロジック

`AdminBusinessAlertService.getSummary(userId)` の処理フロー:

1. `UserRoleRepository.findAdminAndDeputyAdminTeamIds(userId)` でユーザーが ADMIN/DEPUTY_ADMIN を持つチーム ID 一覧を取得
2. `TeamModuleService.getEnabledModules(teamIds)` で各チームの予約モジュール有効状態を取得
3. 予約モジュール有効なチームに対し、`ReservationRepository.countPendingByTeamIds()` で新規予約数・承認待ち数を一括集計
4. `ChatChannelRepository.findInquiryChannelsByTeamIds()` で問い合わせチャンネルを取得し、未読件数を集計
5. `links` を組み立てて `AdminBusinessAlertSummaryResponse` を返す
6. Valkey にキャッシュ（TTL=60 秒）

### 5.2 通知ディスパッチ（F03.4・F04.2 との連携）

本設計書では通知の **受取人解決と dispatch** を規定する。イベント発行は F03.4（予約系）・F04.2（問い合わせ系）で規定する。

#### 予約系通知（F03.4 §5 参照）

| 通知種別 | 受取人解決クエリ |
|---------|--------------|
| `RESERVATION_RECEIVED` | `UserRoleRepository.findAdminUserIdsByTeamId(teamId)` + `findDeputyAdminUserIdsByTeamIdAndPermission(teamId, "MANAGE_RESERVATIONS")` |
| `RESERVATION_PENDING_APPROVAL` | 同上 |
| `RESERVATION_CANCELLED_BY_MEMBER` | 同上 |

- **自己除外**: `actor_id = user_id` の通知は生成しない（F04.3 §3 の既存ルールが自動適用）
- **モジュールガード**: 予約モジュール無効時はイベント自体を発行しない

#### 問い合わせ系通知（F04.2 §5 参照）

| 通知種別 | 受取人解決クエリ |
|---------|--------------|
| `INQUIRY_RECEIVED` | `UserRoleRepository.findAdminUserIdsByTeamId(teamId)` + `findAllDeputyAdminUserIdsByTeamId(teamId)` |

- **重複抑制**: Valkey `inquiry_notified:{channelId}` (TTL=300 秒) で 5 分以内の連続通知を抑制
- **送信者ガード**: ADMIN/DEPUTY_ADMIN からのメッセージは通知しない

### 6.4 リアルタイム更新

既存の WebSocket 通知ストアを流用する:

```typescript
// WidgetAdminBusinessAlert.vue（抜粋）
const notificationStore = useNotificationStore()

const ALERT_TYPES = [
  'RESERVATION_RECEIVED',
  'RESERVATION_PENDING_APPROVAL',
  'RESERVATION_CANCELLED_BY_MEMBER',
  'INQUIRY_RECEIVED',
]

watch(
  () => notificationStore.latestNotification,
  (notification) => {
    if (notification && ALERT_TYPES.includes(notification.notificationType)) {
      fetchSummary()
    }
  }
)

onMounted(() => {
  fetchSummary()
})
```

## 7. セキュリティ設計

### 7.1 認可

| 対象 | 実装 |
|------|------|
| `GET /api/v1/admin/business-alerts/summary` | `@PreAuthorize("@adminRoleChecker.hasAnyAdminRoleInAnyTeam(authentication)")` |
| チームデータの絞り込み | `UserRoleRepository.findAdminAndDeputyAdminTeamIds(userId)` で自チームのみに絞る（他チームのデータ混入を防ぐ） |

### 7.2 情報漏洩防止

- サマリー API は **件数のみ** 返す（予約者氏名・チャットメッセージ本文等の個人情報を含めない）
- 予約詳細・チャット詳細は既存の認可済み API（`/teams/{id}/reservations` 等）で取得
- Valkey キャッシュキーはユーザー ID スコープ（`admin_alert_summary:{userId}`）のため他ユーザーと共有されない

### 7.3 通知のプライバシー

- `RESERVATION_RECEIVED` 通知には予約者名とスロットタイトルのみを含める（連絡先・住所・カルテ情報は含めない）
- `INQUIRY_RECEIVED` 通知には送信者名とチャンネル名のみを含める（メッセージ本文は含めない）
- `F00 Content Visibility Resolver` の二重ガードが既存の通知ディスパッチに組み込まれているため、受信者が対象コンテンツを閲覧不可な場合は自動スキップ

### 7.4 CSRF / レート制限

- API は既存の Spring Security CSRF 設定で保護済み（stateless JWT のため CSRF トークン不要）
- 業務アラートウィジェットは 60 秒 Valkey キャッシュでリクエスト数を抑制。通知受信時のみキャッシュ invalidate するため、悪意ある連続クリックでも DB 負荷を防止

---

## 8. 保守性

- **通知種別の追加**: `ALERT_TYPES` 配列と `alerts` フィールドに追加するだけ。ウィジェットは `alerts` を動的レンダリングするため変更最小
- **新規モジュール対応**: `module_enabled` フラグをチームオブジェクトに追加し、フロントエンドで `v-if` 制御
- **通知頻度の調整**: 問い合わせの重複抑制 TTL（Valkey `inquiry_notified:{channelId}` の 300 秒）はアプリケーション設定（`application.yml`）で変更可能にする

## 9. 検証シナリオ

### シナリオ 1: 予約受付通知（自動確定モード）
1. 予約モジュール有効なチームで MEMBER がスロットを予約申込
2. ADMINの通知ベルに `RESERVATION_RECEIVED` 通知が届く
3. ADMINの個人ダッシュボードの「業務アラート」ウィジェットの「新規予約」カウントが +1
4. カウントをクリックすると `/teams/{id}/reservations` に遷移

### シナリオ 2: 承認待ち通知（手動承認モード）
1. チーム設定の `approval_mode = MANUAL` に変更
2. MEMBER が予約申込 → `RESERVATION_PENDING_APPROVAL` 通知が ADMIN に届く
3. ウィジェットの「承認待ち」カウントが +1
4. ADMIN が `/confirm` API を呼ぶと通知が既読になり、カウントが減少

### シナリオ 3: 問い合わせ通知
1. ADMIN があるチャンネルに `is_inquiry_channel = TRUE` を設定
2. MEMBER がそのチャンネルにメッセージを投稿
3. ADMIN の通知ベルに `INQUIRY_RECEIVED` 通知が届く
4. ウィジェットの「問い合わせ」カウントが +1
5. 5 分以内に同じ MEMBER が追加メッセージを投稿 → 追加通知は来ない（重複抑制）
6. 別の MEMBER が投稿 → この場合は通知が届く（チャンネル単位の抑制のため同一チャンネルでも抑制）

> ※ 重複抑制は「同一チャンネルへの連続投稿」を対象とする。投稿者が変わっても同じチャンネルなら 5 分間は 1 通のみ。これにより複数患者の同時問い合わせでも過剰通知を防ぐ。

### シナリオ 4: セキュリティ検証
1. MEMBER アカウントで `GET /api/v1/admin/business-alerts/summary` を叩く → 403
2. ADMIN A が ADMIN B のチームのアラートを取得できないことを確認（レスポンスに含まれない）
3. 予約モジュールが無効なチームの `new_reservations` が 0 であることを確認

### シナリオ 5: 予約モジュール無効時
1. チームの予約モジュールを無効化
2. MEMBER が予約申込 → 通知が届かない
3. ウィジェットに「新規予約」行が表示されない（`reservation_module_enabled = false`）
