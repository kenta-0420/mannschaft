## 1. 概要

整骨院・美容室・飲食店・ジム・マンション共用施設等のサービス業チームが、時間枠（スロット）を定義し、メンバーやサポーターが予約を申し込む機能。チームは最大5本の予約ライン（席・ベッド・施術台等）を定義し、ユーザーは空きラインを選んで予約する。ADMIN はスタッフ別・日付別の予約枠を30分単位で作成・管理し、メンバーは空き枠を確認して予約・キャンセルを行う。予約時間が近づいたらプッシュ通知でリマインドし、来店後はサービス履歴（F07.1）やカルテ（F07.4）と連携する。

**役割分離**: チームアカウント = 枠管理（提供側）、個人アカウント = 予約のみ（利用側）。

### テーブル定義

#### `reservation_lines`

チームが保有する予約ライン（席・ベッド・施術台・テーブル等）。1チームあたり最大5ラインまで定義可能。各ラインは独立して予約可能で、ユーザーが予約時にどのラインを使うかを選択する。

| カラム名 | 型 | NULL | デフォルト | 説明 |
|---------|---|------|-----------|------|
| `id` | BIGINT UNSIGNED | NO | AUTO_INCREMENT | PK |
| `team_id` | BIGINT UNSIGNED | NO | — | FK → teams。ON DELETE CASCADE |
| `name` | VARCHAR(50) | NO | — | ライン名（例: 「ベッドA」「席1」「テーブル2」） |
| `description` | VARCHAR(200) | YES | NULL | ライン説明（例: 「窓際の席」「個室」） |
| `display_order` | INT UNSIGNED | NO | 1 | 表示順（1〜5） |
| `is_active` | BOOLEAN | NO | TRUE | 有効/無効フラグ（一時的にラインを閉鎖する場合に FALSE） |
| `default_staff_user_id` | BIGINT UNSIGNED | YES | NULL | FK → users。ON DELETE SET NULL（このラインのデフォルト担当スタッフ。NULL = 未指定） |
| `created_at` | DATETIME | NO | CURRENT_TIMESTAMP | |
| `updated_at` | DATETIME | NO | CURRENT_TIMESTAMP ON UPDATE | |
| `deleted_at` | DATETIME | YES | NULL | 論理削除（SoftDeletableEntity 適用） |

**インデックス**
```sql
INDEX idx_rl_team (team_id, display_order)           -- チーム別ライン一覧（表示順）
INDEX idx_rl_team_active (team_id, is_active)        -- 有効ライン検索
```

**制約・備考**
- 1チームあたり最大5ラインまで。6ライン目の作成は 400 エラー
- `display_order` はチーム内で 1〜5 の範囲。Service 層で一意性を保証（DB UNIQUE 制約は不要。論理削除との組み合わせが複雑になるため）
- `is_active = FALSE` のラインは新規予約の対象外。既存予約は維持される
- `default_staff_user_id`: 予約枠作成時に `staff_user_id` を省略した場合、このラインのデフォルトスタッフが適用される（省略可能な便利機能）
- ライン削除: 未来の予約が存在する場合は論理削除不可（409 エラー）。先に予約をキャンセルする運用
- **ライン名の例**: 整骨院 →「ベッド1」「ベッド2」「ベッド3」、飲食店 →「テーブルA」「テーブルB」「カウンター」、美容室 →「席1」「席2」、マンション共用施設 →「会議室」「多目的ホール」

#### `reservation_slots`

チーム ADMIN が作成する予約枠。1枠 = 特定日時の特定スタッフ（または指名なし共通枠）の予約可能枠。予約時間は **30分単位** で設定。

| カラム名 | 型 | NULL | デフォルト | 説明 |
|---------|---|------|-----------|------|
| `id` | BIGINT UNSIGNED | NO | AUTO_INCREMENT | PK |
| `team_id` | BIGINT UNSIGNED | NO | — | FK → teams。ON DELETE CASCADE |
| `staff_user_id` | BIGINT UNSIGNED | YES | NULL | FK → users。ON DELETE SET NULL（担当スタッフ。NULL = 指名なし共通枠） |
| `title` | VARCHAR(200) | YES | NULL | 枠タイトル（例: 「整体60分コース」「ランチ予約」。NULL の場合はスタッフ名 + 時間帯で自動表示） |
| `slot_date` | DATE | NO | — | 予約枠の日付 |
| `start_time` | TIME | NO | — | 開始時刻（30分単位: 00分 or 30分） |
| `end_time` | TIME | NO | — | 終了時刻（30分単位: 00分 or 30分） |
| `booked_count` | INT UNSIGNED | NO | 0 | 現在の予約確定数（denormalize。チームの有効ライン数と比較して FULL 判定） |
| `slot_status` | ENUM('AVAILABLE', 'FULL', 'CLOSED') | NO | 'AVAILABLE' | 枠ステータス |
| `recurrence_rule` | JSON | YES | NULL | 繰り返しルール（後述）。NULL = 単発枠 |
| `parent_slot_id` | BIGINT UNSIGNED | YES | NULL | FK → reservation_slots（繰り返し親枠。自己参照）。ON DELETE RESTRICT |
| `is_exception` | BOOLEAN | NO | FALSE | 繰り返し展開後に個別編集された枠か |
| `price` | DECIMAL(10,2) | YES | NULL | 予約料金（表示用。決済は F08 会費・決済モジュール連携。NULL = 無料 or 料金表示なし） |
| `closed_reason` | VARCHAR(20) | YES | NULL | CLOSE 原因（`MANUAL` / `BUSINESS_HOURS` / `BLOCKED`）。NULL = 非CLOSED。※ **`BLOCKED` は将来形の dead value でセットされない**（機能B は予約不可枠を runtime overlap で判定し slot を CLOSED 永続化しない。§3.B/§5.B が正）|
| `note` | TEXT | YES | NULL | ADMIN 向け枠メモ（予約者には非公開） |
| `approval_mode` | ENUM('AUTO', 'MANUAL') | YES | NULL | **枠単位の承認モード上書き**。`NULL` = チーム既定（`reservation_policies`）に従う。値あり = この枠だけ上書き。承認モードの最終解決は `ReservationPolicyService.resolveApprovalMode(teamId, slot)` で「枠値 → チーム設定 → AUTO」の順に解決する（V112.001 で `NOT NULL DEFAULT 'AUTO'` から NULL 許容化＋既存行を全て NULL へ backfill） |
| `created_by` | BIGINT UNSIGNED | YES | NULL | FK → users。ON DELETE SET NULL |
| `created_at` | DATETIME | NO | CURRENT_TIMESTAMP | |
| `updated_at` | DATETIME | NO | CURRENT_TIMESTAMP ON UPDATE | |
| `deleted_at` | DATETIME | YES | NULL | 論理削除（SoftDeletableEntity 適用） |

**インデックス**
```sql
INDEX idx_rs_team_date (team_id, slot_date, start_time)            -- チーム別日付順の枠一覧
INDEX idx_rs_staff_date (staff_user_id, slot_date, start_time)     -- スタッフ別の枠一覧
INDEX idx_rs_status (team_id, slot_status, slot_date)              -- 空き枠検索
INDEX idx_rs_parent (parent_slot_id)                                -- 繰り返し親枠からの子枠検索
UNIQUE KEY uq_rs_parent_date (parent_slot_id, slot_date, start_time) -- 繰り返し展開時の重複防止
```

**制約・備考**
- 論理削除: `deleted_at DATETIME nullable`（SoftDeletableEntity 適用）
- **30分単位バリデーション**: `start_time` と `end_time` の分は `00` または `30` のみ許可。それ以外は 400 エラー（例: 10:00, 10:30, 11:00 は OK、10:15 は NG）。最小枠は30分（`end_time - start_time >= 30分`）
- `start_time < end_time` のバリデーション（Service 層で検証。日をまたぐ枠は非対応）
- `slot_status` の自動遷移:
  - `booked_count` がチームの有効ライン数（`reservation_lines` で `is_active = TRUE` の件数）に達したら `FULL` に自動更新
  - キャンセルで `booked_count` が有効ライン数未満に戻ったら `AVAILABLE` に自動復帰
  - ADMIN が手動で `CLOSED` に設定可能（`closed_reason = 'MANUAL'`）。`CLOSED` の枠は新規予約不可
  - 営業時間変更による自動 CLOSE: `closed_reason = 'BUSINESS_HOURS'`
  - ~~ブロック時間帯設定による自動 CLOSE: `closed_reason = 'BLOCKED'`~~ → **将来形・未実装（機能B で不採用）**。予約不可枠は slot を CLOSED にせず **runtime overlap（§5.B）で判定**する。`closed_reason = 'BLOCKED'` は**セットされない dead value**
  - REOPEN / 営業時間復帰時: `closed_reason` を NULL に戻す。復帰対象は `closed_reason` の値で判別し、他の原因で CLOSE された枠は復帰しない（**ブロック由来の自動 CLOSE/復帰は行わない**＝上記のとおり）
  - ライン無効化時: 有効ライン数が減少した結果 `booked_count >= 有効ライン数` になった場合は `FULL` に自動更新
- `staff_user_id` は `memberships`（scope_type='TEAM' AND scope_id=チームID AND left_at IS NULL）で当該チームに所属する MEMBER を参照（権限ロール ADMIN/DEPUTY_ADMIN の確認は user_roles 経由）。退職等でチーム脱退（left_at セット）した場合、既存予約枠は保持するが新規作成は不可（Service 層で所属チェック）
- `slot_date` は当日以降のみ作成可能。過去日の枠作成は 400 エラー
- **同一スタッフの枠重複チェック**: 同一 `staff_user_id` × `slot_date` で時間が重複する枠の作成を禁止（Service 層で検証）。共通枠（`staff_user_id = NULL`）同士の重複は許可（異なるメニューの並行予約を想定）
- **`booked_count` の並行更新**: 予約申込時は `UPDATE reservation_slots SET booked_count = booked_count + 1, slot_status = IF(booked_count + 1 >= :activeLineCount, 'FULL', slot_status) WHERE id = :slotId AND slot_status = 'AVAILABLE' AND deleted_at IS NULL` の1 SQL で実行。`affected rows = 0` の場合は 409 エラー（他ユーザーが先に予約済み or CLOSED）。キャンセル時は `booked_count = booked_count - 1` + `FULL → AVAILABLE` 復帰を同様にアトミック更新。`SELECT FOR UPDATE` によるペシミスティックロックは不要（単一行のアトミック更新で十分）

#### 繰り返しルール（`recurrence_rule`）

F03.1 スケジュールの繰り返しルールと同一フォーマット。

```json
{
  "type": "WEEKLY",
  "interval": 1,
  "days_of_week": ["MON", "WED", "FRI"],
  "end_type": "DATE",
  "end_date": "2026-06-30"
}
```

| フィールド | 型 | 説明 |
|-----------|---|------|
| `type` | String | `DAILY` / `WEEKLY` / `MONTHLY` |
| `interval` | Integer | 繰り返し間隔（1 = 毎週、2 = 隔週） |
| `days_of_week` | String[] | `WEEKLY` 時の対象曜日 |
| `end_type` | String | `DATE`（日付指定）/ `COUNT`（回数指定） |
| `end_date` | String | `end_type = DATE` の場合の終了日 |
| `end_count` | Integer | `end_type = COUNT` の場合の回数 |

- 繰り返し展開は最大90日先まで。日次バッチ（AM 0:00 JST）で7日分を先行展開
- 展開された子枠は `parent_slot_id` で親枠を参照。`is_exception = FALSE` の状態で生成
- 個別枠の変更は `is_exception = TRUE` に設定。親枠の変更は `is_exception = FALSE` の子枠に伝播
- 親枠を削除した場合: `ON DELETE RESTRICT` のため、未予約の子枠を先に削除する必要がある。予約が入っている子枠がある場合は 409 エラー
- **営業時間・定休日との連携**:
  - 繰り返し枠作成時: `recurrence_rule.days_of_week` に定休日（`reservation_business_hours.is_open = FALSE`）が含まれている場合は 400 エラー（「{曜日}は定休日です」）
  - 繰り返し展開バッチ: 子枠生成時に営業時間と `reservation_blocked_times` を再チェックし、定休日やブロック時間帯に該当する日の子枠は生成しない（スキップ）
  - 営業時間の後変更（定休日追加等）: 既存の繰り返し親枠の `recurrence_rule` は変更しない。未展開の子枠がバッチで生成される際に自動スキップされる。既に展開済みの子枠は営業時間変更時の自動 CLOSE ロジック（`closed_reason = 'BUSINESS_HOURS'`）で対応

**制約・備考**
- 論理削除: `deleted_at DATETIME nullable`（SoftDeletableEntity 適用）
- `uq_rv_slot_line_active`: 同一枠・同一ラインに対する有効予約の重複を防止。MySQL では NULL 同士は UNIQUE 比較で distinct 扱い（= 重複とみなされない）のため、`deleted_at` を直接 UNIQUE に含める方式では機能しない。代わりに生成カラム `active_unique_key`（有効時 = 1、削除時 = NULL）を使用することで、有効な予約のみで一意性を保証し、論理削除済みの行は制約をすり抜ける
- 同一ユーザーが同一枠の**異なるライン**を予約することは可能（例: 飲食店で2テーブル予約）。`max_active_reservations` 設定で全体の予約数上限を制御
- `status` のライフサイクル:
  - **自動確定モード**（デフォルト）: 予約申込時に即座に `CONFIRMED`（PENDING をスキップ）
  - **手動承認モード**: `PENDING` → ADMIN が承認 → `CONFIRMED` / ADMIN が拒否 → `CANCELLED`
  - `CONFIRMED` → 来店 → `COMPLETED` / 来店なし → `NO_SHOW`
  - `PENDING` / `CONFIRMED` → ユーザーまたは ADMIN がキャンセル → `CANCELLED`
- **承認モード設定**: チーム単位で設定（`reservation_settings` は `teams` テーブルの拡張カラムではなく、`team_settings` JSON カラムまたは専用設定テーブルで管理。詳細は Section 5 の予約管理設定を参照）
- `service_record_id` は来店完了後に ADMIN がサービス履歴を作成した際にリンク（NULL の場合はサービス履歴未作成）
- **キャンセルポリシー**: チーム設定で `cancel_deadline_hours`（予約開始 N 時間前までキャンセル可能）を設定可能。デフォルト: 24時間前。期限後のユーザーキャンセルは 400 エラー（ADMIN はいつでもキャンセル可能）

#### `reservation_blocked_times` 機能B 拡張（予約不可枠・resource 軸）— §3.B

機能B は既存 `reservation_blocked_times` を **CRUD 専用テーブルから「実際に予約をブロックする予約不可枠」へ格上げ**する。従来 §3 で宣言されていた `OUTSIDE_BUSINESS_HOURS`（RESERVATION_008）/ `BLOCKED_TIME_CONFLICT`（RESERVATION_009）は、コードに enum が存在するのみで **どこからも throw されていなかった**（＝予約不可時間帯が予約判定に一切効いていない潜在バグ）。機能B でこれを配線し根治する。

**対象軸（`resource_type`）の根拠**:
- `reservation_slots` は `staff_user_id` のみを持ち、`line_id` を持たない（実コード裏取り済み）。したがって「per-対象の予約不可」として MVP で実 enforce できる軸は **TEAM（全 slot）/ STAFF（`slot.staff_user_id == resource_id`）の2軸のみ**。
- `LINE` / `RESOURCE` は enum 拡張点として確保するだけで MVP では enforce しない（slot にライン軸が入る将来に有効化）。
- UI 上「予約対象」（=ライン等）から予約不可を設定する導線に入った場合は、そのラインの `default_staff_user_id` を解決して **STAFF の `resource_id` として保存**する（ラインには紐付けない）。`default_staff_user_id` 未設定のラインは対象選択不可であることを UI で明示する。

**enforcement（BE 防御が主・時間帯 overlap 対応）** — 判定は §5.B の**単一 overlap ユーティリティ**を3箇所（空き枠除外・予約作成拒否・機能C グリッド）で共有する（別実装厳禁）:
1. **空き枠除外（`listAvailableSlots`）**: `blocked_date == slot_date` ∧ `resourceMatch`（TEAM→常に真 / STAFF→`resource_id == slot.staff_user_id`）∧ `timeOverlap`（全日=両 NULL→真、部分=`slot.start < 枠.end && 枠.start < slot.end`。境界 `slot.start == 枠.end` は非重複＝**半開区間**）に該当する slot を一覧から落とす。
2. **予約作成拒否（`createReservation`）**: 上記 overlap に該当する場合、**`BLOCKED_TIME_CONFLICT`（RESERVATION_009）を実 throw（400）**。
3. **予約不可枠の作成/更新の 409 ガード**: 登録しようとする予約不可枠と時間帯 overlap する active 予約（`PENDING` / `CONFIRMED`）が既に存在する場合、**`UNAVAILABILITY_HAS_ACTIVE_RESERVATIONS`（RESERVATION_027・409）**で拒否する。

**既存予約の扱い（確定方針）**: 予約不可枠の登録は既存予約を強制キャンセルしない。まず impact API（§4.B）で overlap する既存 active 予約の件数＋一覧を返して管理者に警告し、管理者が振替/キャンセルしてから登録する運用。競合したまま登録しようとした場合は上記 3 の 409 が最終防御となる。

> **⚠ enforcement は runtime overlap 一本（slot を CLOSED 永続化しない）**: 上記 §3「`reservation_blocked_times` 制約・備考」の「ブロック設定後に該当時間帯の既存枠は `CLOSED` に自動更新」という記述は**将来形（aspirational）で、既存実装は行っていない**（`createBlockedTime`/`updateBlockedTime` は `reservation_blocked_times` 行を書くだけ）。機能B もこれを踏襲し、**slot を `CLOSED` に永続化せず、実行時の overlap ユーティリティ（§5.B）で判定する**。永続 `slot_status='CLOSED'`（スタッフ操作/営業時間由来）と、overlap 由来で実行時導出する機能C グリッドの `UNAVAILABLE` は**別物**（§5.B の是正注記参照）。

**テンプレート（FE 固定プリセット・BE は具体時刻のみ保存）**: FE は営業時間（`getBusinessHours`）を基準に相対算出した固定プリセットと手入力を提供する。**BE は「テンプレート」概念を持たず、常に具体時刻（または全日=NULL）のみを保存する**。

| プリセット | 意味 | 算出（営業時間基準） |
|---|---|---|
| 全休 | 終日不可 | `start_time` / `end_time` = NULL |
| 遅出 | 午前を不可 | `[openTime, 昼(12:00)]` |
| 早上がり | 夕方を不可 | `[昼(12:00), closeTime]` |
| 中抜け | 昼休憩を不可 | `[12:00, 13:00]`（既定） |
| 手入力 | 任意の開始〜終了 | ユーザー入力（空=全日） |

> プリセット算出後もユーザーが時刻を編集できる。BE に送られるのは編集後の具体時刻（30分単位・§3 既存制約を踏襲）。

**承認モードの解決ルール（マスター御裁可）**

承認モードは「チーム既定 ＋ 枠で上書き」の二段構成で解決する。解決は `ReservationPolicyService.resolveApprovalMode(teamId, slot)` に一本化する:

1. `reservation_slots.approval_mode` に値があればそれを使う（**枠単位の上書き**）
2. なければ `reservation_policies.approval_mode`（チーム既定）を使う
3. チーム既定レコードも無ければ `AUTO`（最終フォールバック。`getOrDefault` が既定値の未永続エンティティを返す）

`reservation_slots.approval_mode` は V112.001 で `NOT NULL DEFAULT 'AUTO'` から NULL 許容化し、既存行（死蔵の初期値 AUTO・一度も自動確定に使われていない）を全て NULL へ backfill した（`NULL` = チーム設定に従う・挙動後退ゼロ）。既存データ環境での backfill 破綻は `FlywayExistingDataReservationSlotApprovalModeMigrationTest`（既存 slot 行シード番人テスト）で恒久的に検知する。

> **注**: 承認モードに基づく**自動確定の実フロー配線は実装済み**（下記「AUTO 自動確定の配線」参照）。**CONFIRMED 時のリマインド自動生成も実装済み**（下記「CONFIRMED 時リマインド自動生成」参照。`remind_before_hours` を反映）。**キャンセル締切（`cancel_deadline_hours`）の実適用も実装済み**（段階拡張 ⑤・`ReservationService.cancelByUser`。注入 `Clock` 基準で枠開始の `cancel_deadline_hours` 時間前を過ぎた会員キャンセルを `CANCEL_DEADLINE_PASSED`（RESERVATION_026・400）で拒否。ADMIN は対象外）。

**AUTO 自動確定の配線（実装済み・F03.4 残ギャップ MVP ①）**

予約作成（`ReservationService.createReservation`）で、枠の保存後に `ReservationPolicyService.resolveApprovalMode(teamId, slot)` で実効承認モードを解決し、以下のとおり分岐する:

- **AUTO**: 同一トランザクション内で `ReservationEntity.confirm()` を呼び CONFIRMED へ即時遷移（PENDING をスキップ）→ 再 save → `ReservationConfirmedEvent` を発行。作成レスポンスは確定済み status を即返す。
- **MANUAL**: PENDING のまま維持。`ReservationConfirmedEvent` は発行しない（管理者の手動承認を待つ）。

既存の `ReservationCreatedEvent`（管理者通知用）は維持するが、渡す承認モードは生の `slot.approval_mode`（nullable）ではなく **`resolveApprovalMode` の解決結果（必ず非 null）** に差し替える。これにより、枠値 NULL かつチーム設定が MANUAL のケースでも管理者通知が「承認待ち（RESERVATION_PENDING_APPROVAL）」を正しく出し分ける。

**`ReservationConfirmedEvent`**（`reservation/event/`・純データイベント）:

| フィールド | 型 | 説明 |
|---|---|---|
| `teamId` | `Long` | チームID |
| `reservationId` | `Long` | 予約ID |
| `actorUserId` | `Long` | 確定を引き起こした操作者（AUTO 時=予約者本人 / 手動時=承認者） |
| `slotStartAt` | `LocalDateTime` | スロット開始日時（`slotDate` + `startTime` を合成）。リマインド基準時刻 |
| `slotTitle` | `String` | スロットのタイトル |

本イベントは **AUTO 自動確定時（`createReservation`）と手動承認成功時（`confirmReservation`）の両方**で発行される（設計書 §3「CONFIRMED 時にリマインド生成」＝手動承認時もリマインド対象）。確定が実際に起きた経路でのみ発行し、既に CONFIRMED の予約に対する再確定では発行しない（`isConfirmable()` ガードにより二重発行は起きない）。リマインド生成（`reservation_reminders`）のトリガとして下記リスナーで消費する。

**CONFIRMED 時リマインド自動生成（実装済み・F03.4 残ギャップ MVP ⑥）**

`ReservationConfirmedEvent` を購読する専用リスナー **`ReservationReminderEventListener`**（`reservation/event/`・管理者通知用 `ReservationAdminNotificationEventListener` とは**別クラス・別 Bean**＝同名ハンドラ衝突回避）が、チームの予約ポリシー（`reservation_policies.remind_before_hours`・既定 `"24,1"`）に従ってリマインドを生成する。

- **トランザクション設計（必須）**: ハンドラに `@TransactionalEventListener(phase = AFTER_COMMIT)` ＋ **`@Transactional(propagation = REQUIRES_NEW)`** を付与する。AFTER_COMMIT は確定 TX のコミット後に発火し実行中の TX が存在しないため、リマインドの DB 書き込みには新規トランザクションが必須。素の `@Transactional`（=REQUIRED）を付けると `TransactionalEventListenerFactory` の起動時バリデーションで ApplicationContext がロード不能になり全 `@SpringBootTest` が巻き添えで落ちる（既知の重大地雷）。この設計は `ReservationReminderEventListenerContextTest`（最小 context 実起動の番人テスト）で恒久検証する。
- **逆算ロジック**: `remind_before_hours` の CSV（不正トークン・0 以下は無視）の各時間 h について `remindAt = slotStartAt.minusHours(h)` を算出し、**現在時刻（注入 `Clock` で取得）より未来のもののみ**を採用する（直近確定で 24h 前が既に過ぎている等の過去時刻はスキップ）。1 予約あたり最大 3 件（`ReservationReminderService.MAX_REMINDERS_PER_RESERVATION`）の上限内で `reservation_reminders` に INSERT する（`ReservationReminderService.generateReminders`）。
- **安全弁**: 生成は AFTER_COMMIT の副作用であり、その失敗を既にコミット済みの確定 TX へ波及させない。例外は握りつぶさず `log.error` に正直に記録する（症状隠蔽ではなく AFTER_COMMIT 副作用失敗の正規記録）。
- **実送信（実装済み・段階拡張 ⑥）**: リマインドの実送信は **`ReservationReminderDispatchBatchService`**（`reservation/service/`）が担う。`@Scheduled(fixedDelay = 60_000)`（1 分間隔）＋ `@SchedulerLock`（多重起動防止）＋素の `@Transactional`（スケジューラ起点の新規 TX＝AFTER_COMMIT 副作用の REQUIRES_NEW とは別物）で、`ReservationReminderService.findDueReminders()`（`remind_at <= now(clock)` の PENDING）を拾う。`reservation_reminders` は `reservationId` のみ保持するため、reservation（受信者 `userId`・`teamId`・`reservationSlotId`）→ slot（`title`・`slotDate`+`startTime`）を**一括取得（N+1 回避）して辿り**、`NotificationHelper.notify(userId, "RESERVATION_REMINDER", title, body, "RESERVATION", reservationId, TEAM, teamId, "/teams/{teamId}/reservations", null)` で予約者本人へ送出する（アプリ内通知＋WebPush・チャネル非依存。メールは設計書に無いため送らない）。**二重送信回避**: 送出に成功した行のみ `markSent()` で `SENT`＋`sentAt` を立てる（送信 → マークの順序を厳守）。送出失敗は握りつぶさず `log.error` で記録し、`SENT` にせず次回ポーリングで再送する。行単位 try/catch で一件の失敗が他行を巻き込まない。`@Scheduled`＋`@Transactional` 境界は `ReservationReminderDispatchBatchServiceContextTest`（`@EnableScheduling` 最小 context 実起動の番人テスト）で恒久検証する。

#### `reservation_notification_recipients`（機能D）— §3.D

チーム単位で登録する「予約通知メール宛先」。メンバーの予約が成立するたびに、ここに登録された**任意のメールアドレス**（非ユーザー＝店の代表アドレス等でも可）へ「日時＋メニュー＋予約者名」をメール送信する（§5.D）。**フリーミアム**（無料は最大3件、有料で最大10件・§5.D）で件数をゲートする。**新規テーブルのため主キーは UUIDv7（アーキ原則6）。`team_id` / `created_by` は teams / users ドメインへのクロスドメイン参照のため FK なし・インデックスのみ（アーキ原則1）。**

> **枠単位の承認モード上書き（`approvalMode`）**
> - 実装フィールド名は `approvalMode`（camelCase。Jackson 既定）。値は `"AUTO" | "MANUAL"`。
> - **`null` / 未指定 = チーム既定（`reservation_policies`）に従う（継承）**。値を指定するとこの枠だけチーム既定を上書きする。
> - 不正な enum 値は Jackson のデシリアライズ段階で 400。

|-----------|------|
| 400 | 現在の予約が `PENDING` / `CONFIRMED` 以外 / 移動先ラインが無効 / 移動先枠の日時が過去 / キャンセル期限超過（ユーザーの場合）/ 当日予約不可 / 事前予約時間不足 |

2. 新枠の `booked_count` を +1 アトミック更新。有効ライン数に達した場合は `FULL` に遷移
3. `reservations` の `reservation_slot_id`、`line_id` を更新。`status` は変更なし（CONFIRMED のまま）
4. 旧リマインドを `CANCELLED` → 新しい日時でリマインドを再生成
5. 予約者に `RESERVATION_RESCHEDULED` 通知を送信（旧→新の日時を含む）
6. 担当スタッフにも変更通知を送信
7. **予約チャット連携**: `chat_channel_id` が非 NULL の場合、チャットにシステムメッセージを投稿:
   「予約日時が変更されました 📋
    変更前: {旧slot_date} {旧start_time}〜{旧end_time}（{旧staff_name}）
    変更後: {新slot_date} {新start_time}〜{新end_time}（{新staff_name}）」
8. 担当スタッフが変更された場合（旧 staff_user_id ≠ 新 staff_user_id）:
   a. 旧スタッフをチャットメンバーから削除
   b. 新スタッフをチャットメンバーに追加
   c. システムメッセージ:「担当が {旧staff_name} → {新staff_name} に変更されました」

※ キャンセル期限は**旧枠**の `start_time` 基準で判定（旧枠の直前に変更されるのを防ぐため）。
※ 手動承認モードの場合、`PENDING` 予約のリスケジュールは再承認不要（PENDING のまま移動）。

### 4.C 空きグリッド API（機能C）

#### `GET /api/v1/teams/{teamId}/reservation-slots/grid`

複数の予約対象（スタッフ）を列に並べた空きグリッド。read-only 専用 Service `ReservationGridService`（`ReservationSlotService` 肥大化回避）。

**認可（`@PreAuthorize` では表現しない）**: 予約閲覧可否は「会員 or `allow_public_reservation`」で、これは `@accessGuard.isScopeAdmin` のような単純ロール式では表現できない。よって grid エンドポイントには **`@PreAuthorize` を付けず（`isScopeAdmin` は付けない＝会員/公開ユーザーが使うため）**、**Service 層で予約作成と同じ view ゲート**（`isMember` or `allow_public_reservation`。非許可は **403 = `RESERVATION_PERMISSION_DENIED`（RESERVATION_021）**）を適用する。未認証は認証層で 401。

**MVP は単日のみ**: grid API は **単日 `?date=` のみ**（レスポンス DTO を2次元＝列×時間帯セルに保つため）。**週タブは FE が単日 API を7日分クライアントから取得（7リクエスト）**して構成する。`from`/`to` レンジ拡張は将来枠（§8 将来拡張）。

**クエリパラメータ**
| パラメータ | 型 | 必須 | 説明 |
|-----------|---|------|------|
| `date` | String(date) | Yes | 対象日（`YYYY-MM-DD`）。**単日のみ**（週タブは FE が7回呼ぶ） |
| `staffUserIds` | String(CSV) | No | 列に並べる予約対象（`1,2,3`）。未指定なら当日 slot を持つ全スタッフ＋共通列 |

**レスポンス（200 OK）** — 列=予約対象、各セル=時間帯 state:
```json
{
  "data": {
    "date": "2026-04-01",
    "columns": [
      {
        "staffUserId": 456,
        "staffName": "田中スタッフ",
        "lineIds": [1, 2],
        "cells": [
          { "slotId": 1, "startTime": "10:00", "endTime": "11:00", "state": "AVAILABLE", "price": 5000.00 },
          { "slotId": 2, "startTime": "11:00", "endTime": "12:00", "state": "BOOKED" },
          { "slotId": 3, "startTime": "12:00", "endTime": "13:00", "state": "UNAVAILABLE" },
          { "slotId": 4, "startTime": "13:00", "endTime": "14:00", "state": "CLOSED" }
        ]
      },
      { "staffUserId": null, "staffName": "共通", "lineIds": [], "cells": [ /* staff_user_id=null の店共通 slot を集約 */ ] }
    ]
  }
}
```

- **セル state**（**セル単位**・列単位ではない）:
  - `AVAILABLE` — 予約可能
  - `BOOKED`（=FULL） — 埋まっている（**予約者氏名/userId は DTO に構造的に含めない**。管理用 enrich とは別 DTO・BE で担保しFEフィルタ任せにしない）
  - `CLOSED` — クローズ枠（`slot_status=CLOSED`）
  - `UNAVAILABLE` — 機能B の予約不可枠に該当（**セル＝時間帯単位**。前回案の列単位 `DAY_OFF` は廃止）
- **state 決定順**: `FULL → BOOKED` / `CLOSED → CLOSED` より優先で、機能B の overlap に該当するセルは **`UNAVAILABLE` で上書き**（判定は §5.B の同一 overlap ユーティリティを共有）。
- `staff_user_id = null` の店共通 slot は「共通」列に集約（MVP）。
- 氏名は `NameResolverService` で一括解決（N+1回避）。
- **`columns[].lineIds` の導出元**: `reservation_slots` は `line_id` を持たないため、列（staff）の `lineIds` は **その列の `staffUserId` を `default_staff_user_id` に持つ active（`is_active = TRUE` かつ `deleted_at IS NULL`）な `reservation_lines` の ID 集合**とする。共通列（`staffUserId = null`）の `lineIds` は空配列（`[]`）。
  - **空集合になり得る**: 当該スタッフを既定担当に持つラインが1本も無いと `lineIds = []` になる。その場合の**予約時のライン選択**は §5.B の予約作成フロー同様、空きセル click → `ReservationForm` で**ユーザーがチームの有効ライン一覧から明示選択**する（`lineIds` は「そのスタッフの推奨ライン」プリセットに過ぎず、予約可能ラインを制限しない）。`lineIds` が1本以上あればそれを既定選択のフォールバックにできる。
- **slotId 露出と IDOR**: grid が返す `slotId` から `GET /reservation-slots/{slotId}` を引いても**予約者 PII は露出しない**。`getSlot` は枠情報（時間帯・スタッフ・空き状況）のみを返し、予約本体（予約者氏名等）は `GET /reservations/{id}` にあり、そちらは #2099 で admin-or-owner ゲート済み。よって slotId の露出は IDOR にならない。

| ステータス | 条件 |
|-----------|------|
| 400 | `date` 不正 / `staffUserIds` 形式不正 |
| 401 | 未認証 |
| 403 | 予約閲覧不可（非会員かつ非公開）= RESERVATION_021 |

`/api/v1/teams/{teamId}/reservation-notification-recipients`。全操作は `@PreAuthorize("@accessGuard.isScopeAdmin(authentication, #teamId, 'TEAM')")`（実シグネチャ3引数）。最終ゲートは BE。

#### `GET`（一覧＋フリーミアム状態）

```json

  }

```

> `freeLimit`/`maxLimit`/`hasPaidPlan`/件数 は FE のロック表示（3件超4件目の有料ロック・10件で追加不可）を駆動するために含める。**FE 表示はあくまで補助で、実ゲートは BE（POST）で強制**。

#### `POST`（追加）

```json
{ "email": "reserve@example.com", "label": "予約担当", "isEnabled": true }
```

| フィールド | 型 | 必須 | バリデーション |
|-----------|---|------|-------------|
| `email` | String | Yes | `@Email`（形式不正は 400） |
| `label` | String | No | 最大100文字 |

**フリーミアム件数ゲート（BE 強制・登録時ゲート方針）**: `TeamPlanService.hasPaidPlan(teamId)` で判定。件数は**有効・無効を問わず全登録行**で数える。
- `count >= MAX_RECIPIENT_LIMIT(10)` → **RESERVATION_028（上限超過・400）**
- `count >= FREE_RECIPIENT_LIMIT(3)` かつ `!hasPaidPlan` → **RESERVATION_029（有料プラン必須・402 Payment Required）**
- 同一チームで `email` 重複 → **RESERVATION_030（409 Conflict）**（DB `UNIQUE(team_id,email)` が最終防御）
- email 形式不正 → `@Email` の 400

> **RESERVATION_029 の HTTP は 402 に確定**（Payment Required＝有料課金で解放される意味論に一致。403 ではない）。**FE 導線**: この 402 は AD 課金の前例（`AD_CAMPAIGN_CREDIT_EXCEEDED` を `GlobalExceptionHandler` が **PAYMENT_REQUIRED(402)** にマップ）と同じ扱いとし、FE は**同じ 402 ハンドラ／アップグレード導線を流用**する（新規ハンドラを作らない）。
> **有料→無料ダウングレードでも登録済み宛先は剥奪しない**（登録時ゲート方針。既に登録済みの4件目以降もそのまま全件送出される）。モジュール on/off ではなく件数ゲートで表現する（module 基盤は「機能まるごと」ゲートのため4件目という粒度を表現できない）。

```json
{ "label": "旧・予約担当", "isEnabled": false }
```

`label` / `isEnabled` の部分更新。`isEnabled=false` にしても件数ゲートのカウント対象からは外れない（登録行として数える）。

物理削除。削除すると件数ゲートのカウントも減る（＝空いた枠に再登録可能）。

## 5. ビジネスロジック

### 主要フロー

#### 予約枠作成フロー
```
1. ADMIN が予約枠を作成（単発 or 繰り返し）
   ※ チームに reservation_lines が1件以上存在していることが前提。0件の場合は「先にラインを作成してください」で 400 エラー
2. バリデーション:
   a. staff_user_id がチームに所属しているか
   b. start_time < end_time か
   c. start_time / end_time が30分単位か（分が 00 or 30）
   d. slot_date が今日以降か
   e. 同一スタッフの同日同時間帯に重複枠がないか
   f. slot_date の曜日が営業日（reservation_business_hours.is_open = TRUE）か
   g. start_time >= open_time かつ end_time <= close_time（営業時間内か）
   h. slot_date + start_time 〜 end_time が reservation_blocked_times に該当しないか
3. 繰り返しの場合:
   a. recurrence_rule に基づいて最大90日先までの子枠を一括生成
   b. 各子枠に parent_slot_id を設定
   c. 繰り返し展開バッチ（日次 AM 0:00 JST）で7日分を先行展開
4. reservation_slots に INSERT
```

#### 予約申込フロー
```
1. メンバーが空き枠を選択し、利用するラインを選んで予約申込
2. バリデーション:
   a. 予約枠が AVAILABLE か（CLOSED でないか）
   b. 指定 line_id がチームの有効ライン（is_active = TRUE）か
   c. 指定ラインがこの枠で未予約か（uq_rv_slot_line_active で保証）
   d. 予約枠の日時が未来か
   e. allow_same_day_booking = FALSE の場合、slot_date が明日以降か
   f. min_advance_hours > 0 の場合、予約枠開始時刻まで min_advance_hours 時間以上あるか
   g. ユーザーの同時有効予約数が max_active_reservations 以下か
3. reservations に INSERT（line_id を含む）
   a. 自動確定モード: status = CONFIRMED、confirmed_at = NOW()
   b. 手動承認モード: status = PENDING
4. reservation_slots.booked_count を +1 アトミック更新
   a. booked_count がチームの有効ライン数に達した場合、slot_status = FULL に自動更新
5. 自動確定モードの場合:
   a. reservation_reminders にデフォルトリマインドを INSERT
   b. ユーザーに予約確定通知を送信（notification_type = RESERVATION_CONFIRMED）
   c. 担当スタッフにも予約通知を送信
   d. **予約チャットの自動開設**（後述「予約チャット連携」参照）
6. 手動承認モードの場合:
   a. ADMIN に承認リクエスト通知を送信（notification_type = RESERVATION_PENDING）
   b. ADMIN が承認 → CONFIRMED に遷移、リマインド生成、ユーザーに確定通知
   c. **予約チャットの自動開設**（CONFIRMED 遷移時に実行。後述「予約チャット連携」参照）
   d. ADMIN が拒否 → CANCELLED に遷移、booked_count -1、ユーザーに拒否通知
```

#### 予約キャンセルフロー
```
1. ユーザーまたは ADMIN がキャンセル実行
2. バリデーション:
   a. status が PENDING or CONFIRMED か
   b. ユーザーの場合: キャンセル期限（cancel_deadline_hours）を超過していないか
3. reservations.status = CANCELLED、cancelled_at/cancel_reason/cancelled_by を更新
4. reservation_slots.booked_count を -1 アトミック更新
   a. slot_status が FULL だった場合、AVAILABLE に復帰
5. 未送信の reservation_reminders.status を CANCELLED に一括更新
6. 通知:
   a. ユーザーキャンセルの場合: 担当スタッフ・ADMIN に通知
   b. ADMIN キャンセルの場合: ユーザーに通知（cancel_reason 付き）
7. 予約チャット連携:
   a. chat_channel_id が非 NULL の場合、チャットにシステムメッセージを投稿:
      「予約がキャンセルされました。再予約をご希望の場合はこちらからご相談ください。」
   b. チャット自体は削除・アーカイブしない（再予約の相談に引き続き利用可能）
```

#### 予約チャット連携

予約が `CONFIRMED` に遷移した時点で、予約者と担当スタッフ（または ADMIN）の間にチャットスレッドを自動開設する。予約の詳細確認・変更依頼・到着連絡等のコミュニケーションに使用。

```
■ 予約確定時の自動チャット開設フロー:

1. reservations.status → CONFIRMED に遷移（自動確定 or ADMIN 承認）
2. ReservationConfirmedEvent を発行
3. ReservationChatListener がイベントを受信:
   a. chat_channels に DM チャンネルを作成:
      - channel_type = 'DIRECT'
      - source_type = 'RESERVATION'
      - source_id = reservation.id
      - UNIQUE KEY (source_type, source_id) で同一予約の重複作成を防止
   b. chat_channel_members に2人を追加:
      - 予約者（reservation.user_id）
      - 担当スタッフ（reservation_slots.staff_user_id）
        ※ staff_user_id が NULL（指名なし共通枠）の場合:
          `reservation_settings.default_chat_admin_id` が設定されていればその ADMIN を追加。
          未設定の場合はチームの ADMIN ロールのうち `created_at` 最古のユーザーを追加
   c. システムメッセージを自動投稿（is_system = TRUE）:
      「予約が確定しました 📋
       日時: {slot_date} {start_time}〜{end_time}
       メニュー: {title}
       担当: {staff_name}
       こちらのチャットで予約に関するご連絡が可能です。」
   d. 予約者にプッシュ通知:
      「{チーム名} との予約チャットが開設されました」
   e. **SUPPORTER の投稿権限**: F04.2 では SUPPORTER はチャット閲覧のみだが、
      予約チャット（`source_type = 'RESERVATION'`）に限り投稿を許可する。
      F04.2 の認可チェックで `source_type = 'RESERVATION'` の DIRECT チャンネルは
      SUPPORTER の送信を例外的に許可するホワイトリスト判定を追加

■ チャットの利用シーン:
  - 予約者: 「少し遅れます」「持ち物の確認」「日時変更の相談」
  - スタッフ: 「ご来店お待ちしています」「当日の注意事項」「空き状況の案内」

■ チャットのライフサイクル:
  - 予約 CONFIRMED: チャット開設
  - 予約 COMPLETED: チャットは自動アーカイブしない（次回予約の相談等に引き続き利用可能）
  - 予約 CANCELLED: チャットに「予約がキャンセルされました」のシステムメッセージを投稿。
    チャット自体は残す（キャンセル理由の確認・再予約の相談に利用可能）
  - 同一の予約者×スタッフの組み合わせで再予約: 既存の DM チャンネルを再利用（新規作成しない）。
    新しい予約のシステムメッセージを追加投稿

■ 同一ペアの DM 再利用ロジック:
  1. 予約確定時、予約者×スタッフの既存 DIRECT チャンネルを検索
  2. 既存あり → source_type/source_id を最新の予約に更新 + 新しいシステムメッセージを投稿
  3. 既存なし → 新規 DIRECT チャンネルを作成
  ※ 同一ペアで複数の DIRECT チャンネルが存在しない設計（F04.2 の既存制約に準拠）

■ 複数予約の識別（同一ペア DM 再利用時）:
  - システムメッセージに予約ID + ディープリンクを含めて区別:
    「予約 #123 が確定しました 📋 [詳細を見る](/teams/{teamId}/reservations/123)
     日時: 4/1 10:00〜11:00 / メニュー: 整体60分 / 担当: 田中スタッフ」
  - チャット内の予約リンクをタップ → 予約詳細画面に遷移
  - 同月に複数予約がある場合でも、各予約の確定・キャンセル・完了のシステムメッセージに
    予約番号が含まれるため「どの予約の話か」が明確
```

### 重要な判定ロジック

#### 予約管理設定

チーム単位の設定。`teams` テーブルの `reservation_settings` JSON カラム、または `team_feature_settings` テーブルで管理。

| 設定キー | 型 | デフォルト | 説明 |
|---------|---|-----------|------|
| `approval_mode` | String | `AUTO` | `AUTO`（自動確定）/ `MANUAL`（手動承認） |
| `pending_expiry_hours` | Integer | 48 | 手動承認モード時、PENDING 予約が未承認のまま N 時間経過で自動キャンセル（0 = 無効） |
| `cancel_deadline_hours` | Integer | 24 | ユーザーキャンセル可能な期限（予約開始 N 時間前まで） |
| `remind_before_hours` | Integer[] | `[24, 1]` | リマインド送信タイミング（予約開始 N 時間前。複数指定可） |
| `max_active_reservations` | Integer | 5 | 1ユーザーあたりの同時有効予約数上限 |
| `allow_same_day_booking` | Boolean | TRUE | 当日予約を許可するか |
| `min_advance_hours` | Integer | 0 | 予約可能な最短時間（予約開始時刻の N 時間前まで。0 = 制限なし） |
| `default_slot_duration_minutes` | Integer | 30 | 枠作成時のデフォルト時間（分。30分単位） |
| `auto_no_show_hours` | Integer | 2 | 予約枠終了時刻から N 時間後に自動で NO_SHOW にする（0 = 無効、ADMIN 手動のみ） |
| `no_show_threshold` | Integer | 3 | 直近90日間の NO_SHOW 回数がこの値以上のユーザーに予約時に警告表示（0 = 無効） |

#### ノーショー警告の挙動

`no_show_threshold` を超えたユーザーが予約申込する際の警告は**ソフト警告**（予約自体はブロックしない）。

**ユーザー側（フロントエンド）**:
- 予約申込確認画面に「直近の予約で無断キャンセルが複数回記録されています。当日のご来店をお願いいたします。」と警告メッセージを表示
- 予約申込 API 自体は 201 で成功する（ブロックしない）
- ユーザーには具体的な NO_SHOW 回数は表示しない（プライバシー配慮）

**ADMIN 側**:
- 予約一覧・詳細に「このユーザーは直近90日間で N 回ノーショーです」と表示
- ADMIN が手動承認モードに切り替える判断材料にする
- 統計 API の `no_show_rate` でチーム全体のノーショー率を把握

**判定タイミング**: `POST /reservations` の処理中に `reservations` テーブルから `user_id` の直近90日間 `status = NO_SHOW` 件数を COUNT。閾値超過の場合、レスポンスに `no_show_warning: true` を付与（フロントエンドが警告表示に利用）。

**ハード制限にしない理由**: 正当なユーザーが体調不良等のやむを得ない事情で NO_SHOW になるケースがあり、自動ブロックは過剰制裁になる。ADMIN が状況を見て手動承認モードに切り替えるのが適切。

#### リマインドバッチ

- **実行タイミング**: Spring `@Scheduled(fixedRate = 60000)` で1分間隔ポーリング
- **対象**: `reservation_reminders.status = PENDING AND remind_at <= NOW()`
- **処理**: F04.3 通知基盤に `notification_type = RESERVATION_REMINDER` として送信。送信後に `status = SENT`、`sent_at = NOW()`、`notification_id` を更新
- **内容**: 「明日 10:00〜11:00 に〇〇整骨院の予約があります（田中スタッフ / 整体60分コース）」

#### ノーショー自動検出バッチ

- **実行タイミング**: 毎時実行（`@Scheduled(cron = "0 0 * * * *")`）
- **対象**: `reservations.status = CONFIRMED` かつ `reservation_slots.slot_date + end_time` から `auto_no_show_hours` 時間以上経過したレコード
- **処理**: 対象の `reservations.status` を `NO_SHOW` に更新。`completed_at` は設定しない
- **設定**: チーム設定 `auto_no_show_hours`（デフォルト: 2、0 = 無効）で調整可能
- **注意**: ADMIN が先に `COMPLETED` をマークした予約はバッチ対象外（`status = CONFIRMED` のみ対象）

#### PENDING 予約自動期限切れバッチ

- **実行タイミング**: 毎時実行（`@Scheduled(cron = "0 0 * * * *")`）— ノーショーバッチと同じタイミングで実行可能
- **対象**: `reservations.status = PENDING` かつ `booked_at` から `pending_expiry_hours` 時間以上経過したレコード（チーム設定の `pending_expiry_hours` を参照。0 = 無効）
- **処理**: 対象の `reservations.status` を `CANCELLED` に更新。`cancelled_by = 'SYSTEM'`、`cancel_reason = '承認期限切れによる自動キャンセル'`
- **副作用**:
  - `reservation_slots.booked_count` を -1 アトミック更新
  - 予約者に `RESERVATION_EXPIRED` 通知を送信（「予約リクエストが承認期限切れにより自動キャンセルされました。再度予約をお試しください。」）
  - ADMIN に「N件の予約リクエストが期限切れになりました」と通知（承認漏れへの気づきを促す）

#### 繰り返し枠展開バッチ

- **実行タイミング**: 日次 AM 0:00 JST（`@Scheduled(cron = "0 0 0 * * *")`）
- **処理**: `parent_slot_id IS NULL AND recurrence_rule IS NOT NULL` の親枠について、未展開の7日先までの子枠を生成
- **重複防止**: `UNIQUE KEY uq_rs_parent_date` で保証
- **例外枠**: `is_exception = TRUE` の既存子枠は上書きしない

#### F03.5 シフト管理との連携

- 予約枠作成時に `staff_user_id` を指定する場合、当該スタッフの確定シフト（`shift_slots` で `PUBLISHED` 状態のシフトスケジュール）と照合可能（将来機能）
- Phase 3 初期は参照のみ（シフト外の予約枠作成は警告表示するがブロックしない）
- 将来: シフト確定時に自動で予約枠を生成する機能を検討

#### F07.1 サービス履歴との連携

- 予約 `COMPLETED` 時に `service_record_id` をリンク可能
- F07.1 のサービス履歴作成画面に「紐付ける予約」ドロップダウンを表示（CONFIRMED/COMPLETED の予約を候補に表示）
- カルテ（F07.4）の「次回推奨メモ」からの自動予約リマインド連携は将来検討

### フロントエンド表示仕様

#### 月間カレンダービュー

予約の空き状況を1ヶ月単位のカレンダーで一覧表示する。MEMBER+ が予約を検討する際の起点画面。

**カレンダー表示仕様**

| 表示要素 | MEMBER+ 向け | ADMIN+ 向け |
|---------|-------------|-------------|
| 日付セル | 「空」「満」「休」のバッジ表示 | 「空」「満」「休」+ 予約件数バッジ |
| 月切り替え | 当月〜3ヶ月先まで | 過去月も閲覧可能（統計用） |
| 曜日ヘッダー | 定休日の曜日はグレーアウト | 同左 |

**日付セルの状態バッジ**

| バッジ | 条件 | 色 |
|-------|------|-----|
| 「空」 | その日に `AVAILABLE` の枠が1件以上ある | 緑（`#22C55E`） |
| 「満」 | その日の全枠が `FULL` | 赤（`#EF4444`） |
| 「休」 | 定休日（`is_open = FALSE`）またはブロック（終日） | グレー（`#9CA3AF`） |
| 「閉」 | 全枠が `CLOSED`（臨時休業等） | グレー（`#9CA3AF`） |
| なし | その日に枠が存在しない | — |

※ `AVAILABLE` と `FULL` が混在する日は「空」を優先表示（予約可能であることを強調）。

**ホバー / 長押しプレビュー（ツールチップ）**

日付セルにカーソルを合わせる（PC）または長押し（モバイル）すると、詳細ページに遷移せずにその日の予約状況サマリーをツールチップで表示する。

```
┌─────────────────────────────┐
│ 4月1日（火）  9:00 - 19:00   │
│─────────────────────────────│
│ 空き枠: 5 / 8               │
│ 10:00  整体60分 田中   [空]  │
│ 10:30  整体60分 佐藤   [満]  │
│ 11:00  整体60分 田中   [空]  │
│ ...他 5件                    │
│─────────────────────────────│
│ タップして予約枠を表示 →      │
└─────────────────────────────┘
```

| 表示項目 | 説明 |
|---------|------|
| 営業時間 | 当該曜日の `open_time` 〜 `close_time` |
| 空き枠数 / 総枠数 | `AVAILABLE` 枠数 / 全枠数（`CLOSED` 除く） |
| 枠リスト（最大5件） | 開始時刻、タイトル、スタッフ名、空き状況 |
| 「...他 N件」 | 6件以上の場合に表示 |

**ツールチップの取得API**: `GET /api/v1/teams/{teamId}/reservation-slots/available` をプレビュー用にも使用。フロントエンドが月間データをバッチ取得し、ツールチップ表示はクライアント側でレンダリングする（日付ごとのAPIコールは不要）。

### 5.B 予約不可枠の判定ロジック（機能B）

**単一 overlap ユーティリティ（別実装厳禁）**: 予約不可枠の時間帯重複判定は BE の**単一ユーティリティメソッド**に集約し、以下の3箇所が**同一実装を共有**する:

1. `listAvailableSlots`（空き枠一覧からの除外）
2. `createReservation`（予約作成の拒否 = RESERVATION_009）
3. `ReservationGridService`（機能C グリッドのセル `UNAVAILABLE` 判定）

```
boolean isBlocked(slot, blockedTime):
    if slot.slotDate != blockedTime.blockedDate: return false
    # 対象軸マッチ
    if blockedTime.resourceType == TEAM:            resourceMatch = true
    elif blockedTime.resourceType == STAFF:         resourceMatch = (blockedTime.resourceId == slot.staffUserId)
    else:                                            resourceMatch = false   # LINE/RESOURCE は MVP 未 enforce
    if not resourceMatch: return false
    # 時間帯 overlap（半開区間）
    if blockedTime.startTime == null and blockedTime.endTime == null: return true   # 全日
    return slot.startTime < blockedTime.endTime and blockedTime.startTime < slot.endTime
```

- **半開区間**: `slot.startTime == blockedTime.endTime`（隣接）は**非重複**として扱う（境界を潰さない）。
- 予約不可枠が複数ある日は、いずれか1件でも `isBlocked` が真なら「ブロック」。

**enforcement の source-of-truth は「runtime overlap ユーティリティ1本」**。予約不可枠は **`reservation_blocked_times` に行を書くだけ**で、slot を永続的に `CLOSED` へは**しない**。上記3箇所（`listAvailableSlots` 除外・`createReservation` 拒否・機能C グリッド `UNAVAILABLE`）が実行時に `isBlocked` を評価して判定する。これが唯一の enforcement 経路である。

> **⚠ 誤解の是正（精査第1パス）**: 「予約不可枠の登録で該当既存枠を `CLOSED(closed_reason='BLOCKED')` に自動更新する」は**事実誤認**。既存 `ReservationBlockedTimeService.createBlockedTime` / `updateBlockedTime` は `reservation_blocked_times` 行を書き込むだけで、`reservation_slots` を CLOSE しない（実コード裏取り済み）。機能B もこの挙動を**変えない**（slot を CLOSED 永続化しない）。
>
> **`CLOSED` と `UNAVAILABLE` は別物**: `slot_status='CLOSED'`（`closed_reason` 付き）は**既存のスタッフ操作用の永続ステータス**（管理者の手動クローズ／営業時間・繰り返しバッチ由来）。機能C グリッドの `UNAVAILABLE` は**予約不可枠との overlap 由来で実行時に導出**するセル状態であり、DB に永続化しない。両者を混同しないこと。

**予約不可枠 作成/更新時の 409 ガード + impact（副作用は blocked_times 行のみ）**:
```
1. リクエストの (date, resourceType, resourceId, startTime, endTime) から対象枠を構成
2. その枠と overlap する active 予約（PENDING/CONFIRMED）を専用リポジトリクエリで検索（下記「observ点」）
   - overlap 判定は上記ユーティリティを reservation の slot に対して適用
3a. impact API（GET .../impact）: 件数 + 一覧（管理画面ゆえ氏名可）を返すだけ（完全に副作用なし）
3b. POST/PATCH（登録）: overlap する active 予約が 1 件以上 → RESERVATION_027（409）で拒否
    overlap 0 件 → reservation_blocked_times に INSERT/UPDATE のみ（slot テーブルは触らない）
```

**overlap 予約の観測点（新規リポジトリクエリが必要）**: 「当該 `team_id` × `blocked_date` の slot（`resourceType='STAFF'` のときは `staff_user_id = resource_id` に絞る）に紐づき、時間帯が overlap する `status IN (PENDING, CONFIRMED)` の予約」を引く新規クエリ（`ReservationRepository`）が要る。既存に該当クエリは無いため新設する。impact のレスポンス件数・027 の発火はこのクエリ結果を観測点とする。

- 既存予約は**強制キャンセルしない**。管理者が impact で確認 → 振替/キャンセル後に登録するのが正規運用。競合したまま登録した場合は 409 が最終防御。

**根治対象の潜在バグ**: 従来 `OUTSIDE_BUSINESS_HOURS`（RESERVATION_008）/ `BLOCKED_TIME_CONFLICT`（RESERVATION_009）は enum 宣言のみで throw されず、予約不可時間帯が予約判定に効いていなかった。機能B の上記配線により RESERVATION_009 を実 throw して根治する（§8 残ギャップ表も更新）。

### 5.D 予約通知メール送出フロー（機能D）

メンバーの予約成立（`ReservationCreatedEvent`）ごとに、`reservation_notification_recipients` に登録された有効宛先へ「日時＋メニュー＋予約者名」をメール送出する。

**イベント購読リスナー（既存 ADMIN 通知とは役割分離・別クラス/別 Bean）**:
- 新リスナー **`ReservationRecipientEmailEventListener`**（`reservation/event/`）を新設。既存 `ReservationAdminNotificationEventListener`（アプリ内/Push で ADMIN ユーザーへ `RESERVATION_RECEIVED`）を**写経**するが、責務を分離する（Dはメールで任意アドレスへ）。同一 `ReservationCreatedEvent` を**別リスナー**が購読するだけで、二重通知・混同はしない。
- **トランザクション設計（必須）**: `@TransactionalEventListener(phase = AFTER_COMMIT)` ＋ **`@Transactional(propagation = REQUIRES_NEW)`**（enqueue が DB 書込のため）＋ `@Async`。素の `@Transactional`（=REQUIRED）は `TransactionalEventListenerFactory` の起動時バリデーションで ApplicationContext がロード不能になり全 `@SpringBootTest` が巻き添えで落ちる**既知の重大地雷**（リマインドリスナーと同じ轍）。最小 context 実起動の番人テストで恒久検証する。

**`ReservationCreatedEvent`（純データイベント・運ぶ値）**:

| フィールド | 型 | 説明 |
|---|---|---|
| `teamId` | `Long` | チームID |
| `reservationId` | `Long` | 予約ID（**リスナーはこれを起点に reservation→slot を解決する**） |
| `actorUserId` | `Long` | 予約者本人 |
| `approvalMode` | `ApprovalMode`（enum）| AUTO / MANUAL（解決後。実体は enum） |

> **⚠ 「日時」はイベントに載せず、リスナーが解決する（N-1 是正）**: 本文の「日時」は**来店予定日時（`slot_date` + `start_time`）**であって、申込時刻（`reservations.booked_at`）**ではない**。`ReservationCreatedEvent` には slot の日時が無いため、**リスナーが `reservationId → reservation → slot` を辿って来店日時を組み立てる**（`ReservationReminderDispatchBatchService` と同じ辿り方・slot 一括取得で N+1 回避）。メニュー（`slot.title`）も同経路で解決する。
> - **採用は (b) リスナー解決**（共有 `ReservationCreatedEvent` を改変しない＝blast radius 小）。代替案 (a)「`ReservationCreatedEvent` に `slotStartAt`/`slotTitle` を足す」も可能だが、既存購読者（ADMIN 通知）への影響を避けるため本設計では**不採用**。
> - 申込日時（`booked_at`）は補助情報として本文の別項に添えてよい（必須ではない）。

**送出処理（EmailOutbox 実仕様に準拠）**:
```
1. reservationId → reservation を解決し、reservation.reservationSlotId → slot を解決（slot は一括取得で N+1 回避）
   - 来店日時 arrivalAt = slot.slotDate + slot.startTime、メニュー menuTitle = slot.title
2. findByTeamIdAndIsEnabledTrue(teamId) で有効宛先を取得
3. 予約者氏名を NameResolverService.resolveUserFullName(actorUserId) で解決（common 経由＝ArchUnit 安全）
4. 各 email について EmailOutboxService.enqueue(new EmailOutboxRequest(...)) を呼ぶ（1 record = 1 宛先）:
   - templateKind = "RESERVATION_RECEIVED_NOTIFY"   # EmailTemplateKind enum に新規追加（下記(a)〜(c)）
   - locale       = "ja"                              # MVP は 'ja' 固定（必須項目）
   - toAddress    = recipient.email                   # 宛先メール（必須・enqueue 内で暗号化＋HMAC 保存）
   - sourceDomain = "reservation"                     # 必須
   - sourceEventId= "reservation-notify:" + reservationId + ":" + email   # 冪等キーの nonce（下記）
   - userId       = null                              # 非ユーザー宛先を許可（userId 未指定→合成キーで "0" になる）
   - payloadVars  = { "subject": <件名>, "body": <本文> }   # スルー方式は subject/body 両方必須
       subject 例: "予約が入りました"
       body    例: 来店日時(arrivalAt = slot_date + start_time) + メニュー(menuTitle = slot.title) + 予約者名(resolveUserFullName)
                   ※ 必要なら申込日時(booked_at) を補助として併記可
4. 1 宛先の送出失敗は他宛先を巻き込まない（行単位 try/catch + log.error。握りつぶさない）
```

> **`EmailOutboxRequest` の実仕様（`EmailOutboxRequest.java` / `EmailOutboxServiceImpl.validateRequest`）**:
> - **必須**: `templateKind` / `locale` / `toAddress`（email 正規表現）/ `sourceDomain`。
> - **任意**: `idempotencyKey` / `userId` / `organizationId` / `sourceEventId`。
> - `vars` の実フィールド名は **`payloadVars`**（`Map<String,String>`）。スルー方式（pass-through）の分岐は `payloadVars.get("subject")` と `payloadVars.get("body")` を読み、**どちらか欠けると `EMAIL_OUTBOX_002` を throw**する。ゆえに**本文だけでなく件名（subject）も必ず定義**する。

**`RESERVATION_RECEIVED_NOTIFY` を通す3点セット（EmailOutbox の規約・実装前提）**:
1. **(a) `EmailTemplateKind` enum に定数追加**（既存の `RESERVATION_EMERGENCY_CLOSURE` 等と同じ命名系統）。
2. **(b) `EmailOutboxServiceImpl.renderTemplate` の switch に case 追加**（スルー方式ブランチに載せる。**未登録のまま送信時に到達すると `default` 分岐が `IllegalStateException("Unsupported templateKind…")` を throw → `SesExceptionClassifier` 経由で backoff / DEAD_LETTER 化**する。enqueue 時ではなく送信処理時に落ちる点に注意）。
3. **(c) F09.18 §11「既存 14 箇所の移行マトリクス」に行追加**（`docs/features/F09.18_email_delivery_infrastructure.md` §11・line 868 付近）。F09.18 の規約で **enum ＋ §11 マトリクス ＋ 移行 Phase は3点同時更新が必須**。
   - **⚠ enum/switch ドリフト注意**: 既存 `GUARDIANSHIP_PROGRESSION_NOTICE` は **switch に case はあるが enum・§11 に無い**という三重ドリフトの前例がある。機能D は逆（enum だけ足して switch を忘れる）を避けるため、**enum＋switch＋§11 の3点を必ず揃える**こと。
   - **F09.18 側設計書の更新要否**: 上記(c)により **F09.18 の §11 マトリクスへの1行追加が必要**。機能D の実装 PR で F09.18 設計書も同時更新する（別 PR に切り出さない）。

**冪等（二重送出防止）の実体**:
- `enqueue` は `idempotencyKey` が渡されればそれを、無ければ **`IdempotencyKeyGenerator.generate(userId, templateKind, sourceEventId)` = `sha256(userId + ":" + templateKind + ":" + sourceEventId)` を先頭32桁**で合成する（`userId=null → "0"`、`sourceEventId=null → ランダム UUID フォールバック＝実質非冪等）。機能D は `userId=null` かつ `sourceEventId="reservation-notify:{reservationId}:{email}"` を必ず渡すので、**同一予約×同一 email は同一キー**になる。
- **観測点**: `email_outbox.idempotency_key`（`CHAR(32)` **UNIQUE** = `uk_email_outbox_idempotency`）。重複 enqueue は `DataIntegrityViolationException → EMAIL_OUTBOX_004` で弾かれる（＝二重送出防止の最終防御）。D-9 の受け入れ条件はこの UNIQUE 行を観測点とする。

- **送信タイミング**: AUTO / MANUAL の両方で**予約作成時**に送出（承認待ちでも「予約が入った」ことを店側に伝える）。
- **既存 ADMIN 通知フローとの関係**: §8「ADMIN 通知フロー」はアプリ内/Push で **ADMIN ユーザー**へ（`RESERVATION_RECEIVED` 等）。機能D は**メールで任意アドレス**へ。両者は同一イベントを**別リスナー**が購読する役割分離であり、二重・混同しない。

**PII 注意**: 予約者氏名が外部アドレスに載る。`email_outbox` は `to_address`（AES-256-GCM 暗号化）＋ `payload_json`（暗号化）で保存するが、**`to_address_hash`（HMAC-SHA-256・indexed）で宛先は検索可能＝完全秘匿ではない**（リスク受容）。加えて**送信そのものの注意喚起を UI に出す**（「登録アドレスに予約者氏名が送信されます」）。将来はマスク/オプトアウトを検討（§8 将来拡張）。

**ネストトランザクションの健全性（番人必須）**: 本リスナーは `REQUIRES_NEW` で新規 TX を開き、その中で `EmailOutboxService.enqueue`（それ自体 `@Transactional`）を呼ぶ＝**ネスト書込**になる。ReplicaRouting 環境で readOnly コンテキストのネスト書込が 500 になった前例（#2096）を踏まえ、**実 DB 統合テストで「1 宛先 = 1 outbox 行が生成される」ことと、ネスト TX が readOnly ルーティングに巻き込まれず正常コミットすること**を番人化する（D-10・`/試練` 観点）。純 Mockito UT では routing を踏まないため見逃す。

**ArchUnit（reservation → payment 越境の確認）**: フリーミアム判定 `TeamPlanService.hasPaidPlan(teamId)` は payment ドメインの直参照になる。**reservation → payment の ArchUnit 越境許可が既に通っているか**を実装前に確認する（既存 `ModuleService` も `TeamPlanService` を呼んでおり許可済みの可能性が高い）。**もし不許可なら common ポート経由（例: `PlanQueryPort`）に寄せる**。この確認を D の実装前提リスクとして明記する。

## 6. セキュリティ考慮事項

- **認可チェック**: ReservationSlotService / ReservationService の入り口で `teamId` と `currentUser` の所属・ロールを必ず検証。他チームの予約枠・予約へのアクセスは 403 で拒否
- **予約者本人チェック**: 予約詳細・更新・キャンセルは `reservation.user_id == currentUser.id` または ADMIN+ であることを検証
- **レートリミット**: 予約申込 API（`POST /reservations`）は `Bucket4j` で1ユーザー1分間に5回まで — 予約枠の買い占め防止。空き枠検索 API は1分間に30回まで
- **入力サニタイズ**: `user_note`・`admin_note`・`cancel_reason`・`reservation_blocked_times.reason` は XSS 対策として HTML タグを除去
- **ノーショーデータの保護**: ノーショー回数はユーザー本人には直接表示しない（ADMIN ダッシュボードでのみ参照可能）。ユーザーには「予約時に警告」として間接的にフィードバック
- **監査ログ**: 予約枠の作成・変更・削除、予約の申込・承認・拒否・キャンセル・完了・ノーショー、営業時間変更、ブロック時間帯の追加・削除のすべてを `audit_logs` に記録
- **個人情報**: `user_note`（症状等のセンシティブ情報を含む可能性あり）はスコープ内 ADMIN+ のみアクセス可能。API レスポンスでも権限に応じてフィルタ
- **認可強制の是正（2026-07-03・実装漏れ是正）**: §2 で規定済みだった「予約枠 CRUD・予約管理・予約設定・予約不可枠・予約通知メール宛先は ADMIN+ 限定」「予約詳細/更新/キャンセルは本人 or ADMIN+」を、**実装が機械的に強制し忘れていた**。PR #2097（FE 表示切替）/ PR #2099（BE `@PreAuthorize("@accessGuard.isScopeAdmin(authentication, #teamId, 'TEAM')")` を管理系 26 箇所＋1 箇所に付与、`getReservation` に本人 or ADMIN+ の所有権ゲート追加）で設計どおりに強制化した。**これは設計変更ではなく実装漏れの是正**である。機能B/D の新規エンドポイントも同ゲート（`isScopeAdmin`＝副管理者可・**実シグネチャ3引数**）を最初から適用する。機能C グリッドは `@PreAuthorize` では表現せず**Service 層で予約閲覧 view ゲート**（会員/公開 `canBook`。項6・§4.C 参照）。
- **機能C の個人情報保護（機能C）**: 空きグリッドの `BOOKED` セルは「埋まっている」ことのみを返し、**予約者氏名/userId を DTO に構造的に含めない**（管理用 enrich とは別 DTO）。BE で担保し、FE のフィルタ任せにしない。
- **機能B impact の氏名開示（機能B）**: impact API は ADMIN+ 限定の管理用途のため、overlap する既存予約の予約者氏名を返してよい（振替判断のため）。一般会員向け API では返さない。
- **機能D の外部送信 PII（機能D）**: 予約者氏名が外部メールアドレスへ送信される。`email_outbox` は宛先・payload を暗号化保存するが、送信の事実を UI で注意喚起する（「登録アドレスに予約者氏名が送信されます」）。宛先の登録は ADMIN+ 限定。将来はマスク/オプトアウトを検討。

### ADMIN 通知フロー（F10.7 業務アラート連携）

F10.7 業務アラートウィジェットは、以下の予約イベントを起点にして ADMIN / DEPUTY_ADMIN へリアルタイム通知を発報する。通知の技術基盤は F04.3 を使用し、`ApplicationEventPublisher` + `@TransactionalEventListener(phase = AFTER_COMMIT)` + `@Async` パターンで実装する。

| 予約イベント | 発火通知タイプ | 送信先 | 実装メモ |
|-------------|--------------|--------|---------|
| 新規予約申込・**自動確定モード**（`approval_mode = AUTO`、`CONFIRMED` で着地） | `RESERVATION_RECEIVED`（HIGH） | ADMIN + `MANAGE_RESERVATIONS` 権限を持つ DEPUTY_ADMIN | 申込者本人（actor）は除外。手動承認モードでは発火しない |
| 新規予約申込・**手動承認モード**（`approval_mode = MANUAL`、`PENDING` で着地） | `RESERVATION_PENDING_APPROVAL`（HIGH） | 同上 | `RESERVATION_RECEIVED` とはモード排他で**二重発火しない**。承認/拒否で解消 |
| メンバーによる予約キャンセル（`CANCELLED` 遷移、実行者が予約者本人） | `RESERVATION_CANCELLED_BY_MEMBER`（NORMAL） | 同上 | ADMIN 自身がキャンセルした場合は送信しない |

> **受取人の統一**: 予約系通知の受取人は「ADMIN + `MANAGE_RESERVATIONS` 権限を持つ DEPUTY_ADMIN」で F10.7 §5.2 と一致させる。F03.4 §2 で予約操作権限を `MANAGE_RESERVATIONS` と定義しているため、その権限を持たない DEPUTY_ADMIN には予約通知を送らない。
>
> **モード排他の根拠**: 1 回の予約申込で `RESERVATION_RECEIVED` と `RESERVATION_PENDING_APPROVAL` が同時に飛ぶと二重通知になる。`approval_mode` で着地ステータスが `CONFIRMED`（AUTO）か `PENDING`（MANUAL）かが一意に決まるため、発火する通知種別も排他に決まる。

**実装方式**:

```java
// ReservationService 内でイベント発行
@Transactional
public ReservationResponse createReservation(...) {
    // ...予約作成ロジック...
    eventPublisher.publishEvent(new ReservationReceivedEvent(reservation));
    return response;
}

// ReservationNotificationEventListener（別クラス）
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
@Async("notificationTaskExecutor")
public void handleReservationReceived(ReservationReceivedEvent event) {
    // ADMIN / DEPUTY_ADMIN ユーザーを取得し NotificationService 経由で通知
}
```

**Flyway 参照**: 本フローに必要な `notification_type` 拡張（`RESERVATION_RECEIVED` 等）は F04.3 の Flyway マイグレーションで管理する（F03.4 側に DDL 変更なし）。
