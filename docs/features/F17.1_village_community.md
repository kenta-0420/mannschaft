## 1. 概要・コンセプト

### 1.1 コンセプト

「**袖振り合うも他生の縁**」。

Mannschaft における「村（Village）」は、組織・チーム・個人の垣根を越えて、共通の関心・職種・地域・趣味で人が集う、**自由参加型の横断コミュニティ**である。

既存の組織（Organization）・チーム（Team）は「所属する」「招かれる」関係であるのに対し、村は「**誰でも自由に出入りできる**」点が決定的に異なる。村は所属実態（リアル組織や雇用契約）を反映しない、**緩い縁（縁戚）でつながる場**として設計する。

> 「縁あって寄り合った者同士が、ニックネームでゆるりと語らう。役職も格式も置いてくる。それが村である。」

### 1.2 「公式村」と「任意村」

| 種別 | 説明 | 作成権限 | 例 |
|---|---|---|---|
| **公式村 (OFFICIAL)** | プラットフォーム運営が認定した由緒ある村。バッジ表示・トップ検索優遇 | 運営のみ作成可、または申請承認制 | 「マンション管理組合村」「整骨院村」「公式ブログ村」 |
| **任意村 (COMMUNITY)** | ユーザーが申請して作成する自由な村 | 申請承認制（運営審査） | 「○○市民村」「△△アニメ村」「夜更かし村」 |

公式村は **`villages.type = 'OFFICIAL'`** のフラグで区別し、UIで公式バッジを表示する（Q14 で決着）。

### 1.3 参加主体の混在

村への参加主体は次の 3 種とする（Q2 で決着）:

- **個人 (USER)**: 自分自身が村人として参加
- **チーム (TEAM)**: チームの代表として参加（ADMIN 等が代理参加・代理投稿）
- **組織 (ORGANIZATION)**: 組織の代表として参加（同上）

UI 上は **Phase 1 では 1 タブ混在表示**とし、`subject_type` バッジで識別できるようにする（Q3 で決着）。将来需要があれば「個人タブ / 法人タブ」のような分割も検討するが、Phase 1 は混在のままシンプルに走る。

| 種別 | 村の例 |
|---|---|
| 業種・職種 | 整骨院村、美容室村、塾講師村、士業村、保育士村 |
| 趣味・関心 | アニメ村、釣り村、家庭菜園村、ボードゲーム村 |

## 3. DB設計

### 3.1 設計原則の遵守

| CLAUDE.md 原則 | 本設計での扱い |
|---|---|
| 原則1: クロスドメイン FK 禁止 | `village_memberships.subject_id` は USER/TEAM/ORGANIZATION の ID を保持するが FK は張らない |
| 原則2: CASCADE は同一ドメイン内のみ | villages → village_memberships は CASCADE OK。users との連動は SET NULL + アプリ層 |
| 原則3: コアエンティティは論理削除 | villages は `deleted_at` + `archived_at` の二段構え |
| 原則4: 退会時は匿名化 | 投稿は保持、`user_village_nicknames` のみ物理削除、村内発言は「元村人A」化 |
| 原則5: @Transactional はドメイン内 | village ドメイン内に閉じる。Audit Log への記録は非同期 |
| 原則6: 新規テーブル PK = UUIDv7 | 9 テーブルすべて `BINARY(16)` UUIDv7 |
| 原則7: テナント絞り込み | 村は全テナント横断のため `AbstractTenantAwareRepository` は **使わない**。標準 `JpaRepository` を使う |

### 3.2 新規テーブル一覧

すべてのテーブルが **原則7 適用外（organization_id を持たない・全テナント横断ドメイン）** である点に留意。Repository は標準 `JpaRepository` を継承する。

| テーブル名 | 役割 | 論理削除 |
|---|---|---|
| `villages` | 村本体（※原則7非適用・全テナント横断） | あり（deleted_at + archived_at） |
| `village_memberships` | 村への参加（個人/チーム/組織） | あり |
| `user_village_nicknames` | ユーザーの村ニックネーム（Phase 1: 全村共通 1 件／Phase 2: 村ごと上書き行を追加可） | なし（退会時物理削除） |
| `village_creation_requests` | 村作成申請 | なし（履歴保持） |
| `village_join_requests` | 承認制村への参加申請 | なし |
| `village_reports` | 通報 | なし |
| `village_lobby_daily_threads` | 井戸端の日次スレッド（リアルタイム発言の日付集約） | あり（管理者削除時） |
| `user_village_pins` | お気に入り村ピン止め | なし（退会時物理削除） |
| `village_representatives` *(Phase 2)* | 代表権限の専用委任 | あり |

### 3.3 villages

```sql
CREATE TABLE villages (
    id                  BINARY(16)    NOT NULL                       COMMENT 'UUIDv7 PK',
    slug                VARCHAR(64)   NOT NULL                       COMMENT 'URL スラッグ（半角英数ハイフン）',
    name                VARCHAR(100)  NOT NULL                       COMMENT '村名（表示用）',
    description         TEXT          NULL                           COMMENT '村の紹介文',
    type                ENUM('OFFICIAL','COMMUNITY') NOT NULL DEFAULT 'COMMUNITY' COMMENT '公式村 / 任意村',
    join_policy         ENUM('FREE','APPROVAL') NOT NULL DEFAULT 'FREE' COMMENT '参加方式',
    visibility          ENUM('PUBLIC','UNLISTED') NOT NULL DEFAULT 'PUBLIC' COMMENT '検索可否',
    category            VARCHAR(64)   NULL                           COMMENT 'カテゴリ（業種/地域/趣味 等）',
    icon_r2_key         VARCHAR(255)  NULL                           COMMENT 'R2 上のアイコンキー',
    cover_r2_key        VARCHAR(255)  NULL                           COMMENT 'カバー画像 R2 キー',
    monsho_r2_key       VARCHAR(255)  NULL                           COMMENT 'Phase 2: 村紋 R2 キー',
    guideline_md        MEDIUMTEXT    NULL                           COMMENT '村ガイドライン Markdown',
    member_count_cache  INT UNSIGNED  NOT NULL DEFAULT 0              COMMENT 'メンバー数キャッシュ',
    created_by_user_id  BIGINT UNSIGNED NULL                          COMMENT '作成者（FK 張らない / 退会時 NULL 化）',
    created_at          DATETIME(3)   NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    updated_at          DATETIME(3)   NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
    deleted_at          DATETIME(3)   NULL                           COMMENT '論理削除（村長判断）',
    archived_at         DATETIME(3)   NULL                           COMMENT '永久凍結（運営判断・違反村）',
    version             BIGINT        NOT NULL DEFAULT 0              COMMENT '楽観ロック',
    PRIMARY KEY (id),
    UNIQUE KEY uk_villages_slug (slug),
    UNIQUE KEY uk_villages_name (name),
    KEY idx_villages_type (type),
    KEY idx_villages_visibility_deleted (visibility, deleted_at),
    KEY idx_villages_category (category),
    KEY idx_villages_created_at (created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT='村本体';
```

- `slug` は人間可読 URL 用（`/villages/integral-clinic` など）
- `archived_at` は `deleted_at` と独立で、運営が「ガイドライン違反で永久凍結」した村を表す
- `created_by_user_id` は FK を張らず、アプリ層でユーザー存在を検証。退会時は SET NULL 相当（バッチで処理）

### 3.4 village_memberships

```sql
CREATE TABLE village_memberships (
    id              BINARY(16)    NOT NULL                            COMMENT 'UUIDv7 PK',
    village_id      BINARY(16)    NOT NULL                            COMMENT 'FK → villages.id（同一ドメイン）',
    subject_type    ENUM('USER','TEAM','ORGANIZATION') NOT NULL       COMMENT '参加主体',
    subject_id      BIGINT UNSIGNED NOT NULL                          COMMENT '参加主体ID（FK 張らない / 原則1）',
    role            ENUM('HEADMAN','ELDER','VILLAGER','VISITOR') NOT NULL DEFAULT 'VILLAGER' COMMENT '村内ロール',
    joined_at       DATETIME(3)   NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    left_at         DATETIME(3)   NULL                                COMMENT '退村日（論理削除）',
    banned_at       DATETIME(3)   NULL                                COMMENT 'BAN日（モデレーション）',
    banned_reason   VARCHAR(500)  NULL,
    invited_by_membership_id BINARY(16) NULL                          COMMENT '招待元メンバーシップ（オプション）',
    created_at      DATETIME(3)   NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    updated_at      DATETIME(3)   NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
    version         BIGINT        NOT NULL DEFAULT 0,
    PRIMARY KEY (id),
    UNIQUE KEY uk_vm_village_subject (village_id, subject_type, subject_id, left_at) COMMENT '退村（left_at IS NOT NULL）は履歴として並存、現役（left_at IS NULL）は1主体1件のみ。MySQL の NULL は UNIQUE で別値扱いになるため複数履歴の保持と現役の一意性を両立',
    KEY idx_vm_village_role (village_id, role),
    KEY idx_vm_subject (subject_type, subject_id),
    KEY idx_vm_joined_at (joined_at),
    CONSTRAINT fk_vm_village FOREIGN KEY (village_id) REFERENCES villages(id) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT='村メンバーシップ';
```

- `subject_id` は USER の場合は users.id、TEAM なら teams.id、ORGANIZATION なら organizations.id。**FK は張らない**（原則1）
- 退村は `left_at` で論理削除。同一主体の再参加は新規レコード追加で表現
- UNIQUE は `left_at` を含めることで「現役 1 件 + 過去履歴」を許容

### 3.5 user_village_nicknames

```sql
CREATE TABLE user_village_nicknames (
    id              BINARY(16)    NOT NULL                            COMMENT 'UUIDv7 PK',
    user_id         BIGINT UNSIGNED NOT NULL                          COMMENT 'ユーザーID（FK 張らない）',
    village_id      BINARY(16)    NULL                                COMMENT 'NULL = 全村共通（Phase 1 デフォルト）/ 特定 ID = その村専用の上書き（Phase 2 で導入予定の村ごと別名機能）。FK は張らない（NULL 許容のため／原則1 にも準拠）',
    nickname        VARCHAR(40)   NOT NULL                            COMMENT '村ニックネーム（プラットフォーム全体で一意）',
    avatar_r2_key   VARCHAR(255)  NULL                                COMMENT 'アバター（NULL なら共通アバター）',
    bio             VARCHAR(500)  NULL                                COMMENT '村内プロフィール一言',
    last_changed_at DATETIME(3)   NOT NULL DEFAULT CURRENT_TIMESTAMP(3) COMMENT 'スロットリング用',
    change_count_this_month INT UNSIGNED NOT NULL DEFAULT 0           COMMENT '月内変更回数（ロールバック式）',
    created_at      DATETIME(3)   NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    updated_at      DATETIME(3)   NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
    PRIMARY KEY (id),
    UNIQUE KEY uk_uvn_user_village (user_id, village_id) COMMENT '1 ユーザーにつき (NULL=共通) は 1 件、(村ID 上書き) も村ごと 1 件。Phase 1 は NULL 行のみ運用',
    UNIQUE KEY uk_uvn_nickname (nickname) COMMENT 'プラットフォーム全体でニックネーム一意。同名による別人混同（攻撃シナリオC）を防ぐ',
    KEY idx_uvn_user (user_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT='ユーザーの村ニックネーム（Phase 1 は全村共通1つ／Phase 2 で村ごと上書き拡張）';
```

- **Phase 1**: 1 ユーザー = 1 ニックネーム（`village_id IS NULL` の行を 1 件のみ持つ）。**どの村でも同じ名前を表示**（Q4 マスター確定: 全村共通1つ）
- **Phase 2 拡張**: 特定の村だけ別名を使いたい場合に `village_id` を入れた上書き行を追加可能。アプリ層で「特定の village_id 行があればそれを優先、なければ NULL 行を使用」のロジックで解決
- **ニックネームはプラットフォーム全体でユニーク**（先着優先）。これにより「同一ニックネーム + 同一アバター」による別人なりすまし／村を跨いだ混同を本質的に防ぐ
- `village_id` に FK を張らない理由: NULL 許容と原則1（クロスドメイン FK 回避を可能な限り徹底）の両立。村削除時の整合性はアプリ層 + バッチで担保
- 退会時は **物理削除**（個人特定可能情報の最たるもの。原則4 で「投稿は保持・氏名のみ匿名化」とした方針に沿う）
- `last_changed_at` + `change_count_this_month` でレートリミット（月 3 回まで）

### 3.8 village_reports

```
Response 200: { "data": [ { "id": "...", "status": "PENDING", "message": "...", "createdAt": "..." } ] }
```

上記の審査者向け一覧（`GET .../join-requests`）は HEADMAN/ELDER 限定である。
一方**申請者は承認されるまで定義上「非メンバー」**であり、審査者一覧を開放するわけにはいかない。
そのため申請者が自分の申請状態を確認し、取下げに必要な `id` を復元するための専用 EP を設ける。
（これが無かったため、FE は画面をリロードすると取下げ導線を出せなかった。）

| 論点 | 決定 | 根拠 |
|---|---|---|
| URL 形 | 村スコープ + `/me` サフィックス | 参加申請は村に属するリソース。村スコープ `/me` の前例に `GET /api/v1/villages/{villageId}/serendipity-scores/me` がある |
| 戻り値 | `ApiResponse<List<JoinRequestResponse>>`（`createdAt` 降順） | (village, user) に対し申請は**時系列で複数**あり得る（PENDING は同時に 1 件だが、APPROVED/REJECTED/WITHDRAWN の履歴が残る）。「自分の申請一覧」の前例 `GET /api/v1/me/village-creation-requests`（`listMine`）も素の `List` を返す |
| 申請が 0 件のとき | **空配列 + 200**（404 にしない） | 「申請が無い」は「リソースが見つからない」ではない。`listMine` の前例と一致させ、FE の 404 分岐を不要にする |
| 認可 | **パス・クエリで対象ユーザーを一切受け取らず、`SecurityUtils.getCurrentUserId()` だけで解決**。リポジトリで `requesterUserId` を絞り込む | 他人の行を読んでから弾く方式は検証漏れがそのまま漏洩になる。**そもそも他人の行を読まない**ため、IDOR の余地が構造的に存在しない（403/404 の判定自体が不要）。絞り込みキーは取下げの認可条件（`requesterUserId == actor`）と同一で、独自の認可述語を新設しない |
| メンバーシップ判定 | **行わない** | 申請者は承認まで非メンバー。ここでメンバーシップを要求すると「申請中は自分の申請を見られない」矛盾が生じる |
| 村の状態 | `loadActiveVillage`（不存在/削除は `VILLAGE_001`、凍結は `VILLAGE_027`） | 本 Service の他メソッドと同一の流儀に揃える |

## 5. 権限モデル

### 5.1 村内ロール

| ロール | 役割 |
|---|---|
| **HEADMAN** (村長) | 村の最高責任者。村設定変更・ロール任命・全モデレーション権限 |
| **ELDER** (長老) | モデレーション・参加申請審査 |
| **VILLAGER** (村人) | 通常メンバー。投稿・閲覧・通報 |
| **VISITOR** (旅人) | 閲覧のみ（PUBLIC 村に対する未参加ユーザー） |

### 5.2 パーミッション

| パーミッション | 説明 |
|---|---|
| `VILLAGE.MANAGE` | 村設定編集・削除・凍結・ロール任命 |
| `VILLAGE.MODERATE` | 投稿削除・BAN・参加申請審査・通報処理 |
| `VILLAGE.POST` | 投稿・チャット発言 |
| `VILLAGE.READ` | 閲覧・検索 |

### 5.3 ロール × パーミッション

| | HEADMAN | ELDER | VILLAGER | VISITOR |
|---|---|---|---|---|
| VILLAGE.MANAGE | ✅ | ❌ | ❌ | ❌ |
| VILLAGE.MODERATE | ✅ | ✅ | ❌ | ❌ |
| VILLAGE.POST | ✅ | ✅ | ✅ | ❌ |
| VILLAGE.READ | ✅ | ✅ | ✅ | ✅ (PUBLIC 村のみ) |

加えて、SYSTEM_ADMIN は全村に対して MANAGE/MODERATE を持つ（運営権限）。

### 5.4 投稿主体代表権限の検証

`postedAs.subjectType` が `TEAM` または `ORGANIZATION` の場合、サーバーは以下を順に検証する:

1. 呼び出しユーザーがその村のメンバーであること
2. 呼び出しユーザーが指定したチーム/組織のメンバーであること
3. **Phase 1**: 呼び出しユーザーがそのチーム/組織で `ADMIN` ロールであること
4. **Phase 2**: 上記または `village_representatives` で委任を受けていること
5. 指定したチーム/組織が当該村のメンバーであること（village_memberships に subject 一致行があり left_at IS NULL）

いずれか失格なら `403 REPRESENT_FORBIDDEN` を返す。

### 5.5 村長の引き継ぎ

- HEADMAN は退村する前に他のメンバーを HEADMAN に任命する必要がある（`409 HEADMAN_CANNOT_LEAVE`）
- 例外: HEADMAN が退会した場合、最古参の ELDER が自動昇格する（バッチ）。ELDER がいなければ最古参 VILLAGER。0 人なら村は自動 archive

## 6. セキュリティ

### 6.1 個人特定情報の分離

村スコープのレスポンスでは、個人投稿者の `displayName` (実名) と `userId` を **絶対に返さない**。返却すべきは `nickname` と `avatarUrl` のみ。

#### 攻撃シナリオ A: ID 逆引き

攻撃者が `userId` を取得し、`GET /api/v1/users/{id}` で実名を引く。

**対策**: 村スコープのレスポンスから `userId` を完全除外する。村内の他ユーザー参照は `village_memberships.id` (UUIDv7) のみ。

```java
// VillagePostResponse (Phase 1)
record VillagePostResponse(
    UUID id,
    String body,
    PostedAsDto postedAs,
    Instant postedAt
) {}

sealed interface PostedAsDto permits PostedAsUserDto, PostedAsTeamDto, PostedAsOrgDto {}

record PostedAsUserDto(
    UUID villageMembershipId,  // ← village_memberships.id（村内固有 UUID）
    String nickname,
    String avatarUrl
    // userId は **絶対に持たない**
) implements PostedAsDto {}
```

#### 攻撃シナリオ B: チーム経由の名寄せ

攻撃者がチーム代表投稿の `teamId` から `GET /api/v1/teams/{id}/members` で個人を特定。

**対策**: チーム/組織の代表投稿では `teamId`/`organizationId` を返してよい（公的主体のため）が、そのチーム/組織の **メンバー一覧 API は当該ユーザーが該当チーム/組織のメンバーである場合のみ** 返却する。これは F01.2 既存ルールどおり。

#### 攻撃シナリオ C: 所属チーム逆引き

「山田太郎」名義の個人投稿者が、所属するチームの掲示板で「山田太郎（本名）」名義で投稿していた場合、検索で名寄せされる。

**対策**: ニックネーム重複は許容するが、村内で「同一ニックネーム + 同一アバター」だと別人と勘違いされうる。
- **ニックネームはプラットフォーム全体で UNIQUE**（`user_village_nicknames.nickname` をグローバルユニーク制約）。これにより「同一ニックネーム + 同一アバター」での別人混同・なりすましを **根本から不可能** にする
- 個人投稿時の `postedAs` から `userId` を排除
- 個人投稿のレスポンスに「所属チーム情報」を含めない（既存タイムラインで返している `teamBadges` 等は village スコープでは抑止）

**この対策の限界（明示）**: 上記でニックネームの**字面の衝突**は完全に防げるが、以下は別途モデレーションで対応する：
- **口調・文体での識別**: 同一人物が複数アカウント（複数ニックネーム）で似た口調を使う場合（既存の Sock Puppet 検出と同じ課題）。運営によるモデレーション + 通報フローで対応
- **アバター画像が他人と類似**: 著作権絡みの著名キャラクター流用などはガイドライン違反として処理
- **Phase 2 で村ごと上書き名を導入する場合**: 同じユーザーが村ごとに別の名前を使えるようになるが、これは「文脈で人格を分けたいニーズ」への解放であり、悪用検出は通報＋運営の役割になる

### 6.2 通報者非開示

`village_reports.reporter_user_id` は村長・長老向け一覧 API でも返さない。`reportedBy: "ANONYMOUS_VILLAGER"` 固定で返す。被報告者が報復するのを防ぐ。

例外: SYSTEM_ADMIN は監査目的で参照可能（admin API 別エンドポイント）。

### 6.3 なりすまし防止

`postedAs` ヘッダの値はクライアントから自由に指定できるため、§5.4 の検証を **必ずサーバー側で実行する**。テスト規約上、`PostingIdentityValidationServiceTest` の専用テストクラスで以下を全件カバーする:

- `postedAs.subjectType=TEAM` で当該チーム ADMIN でない場合 → 403
- `postedAs.subjectType=ORGANIZATION` で組織 ADMIN でない場合 → 403
- 指定したチームが村のメンバーでない場合 → 403
- ニックネーム改竄（リクエストに nickname を含めても無視）→ サーバー側で `user_id` をキーに `user_village_nicknames` から引き直し（Phase 2 で村ごと上書き行が存在する場合はそれを優先）

### 6.4 レートリミット

| 操作 | 上限 |
|---|---|
| 通報 | 10 件 / 時 / ユーザー |
| 村作成申請 | 3 件 / 日 / ユーザー |
| ニックネーム変更 | 3 回 / 月 / ユーザー（Phase 1 は全村共通 1 つのため）。Phase 2 で村ごと上書きが導入されれば 3 回/月/村 に粒度変更 |
| 参加 / 退出の繰り返し | 5 回 / 日 / 村 / ユーザー（DoS 対策） |
| 投稿（チャット含む） | 既存のグローバル制限を流用 |

実装は既存の RateLimitInterceptor + Redis (Valkey) スライディングウィンドウ方式。

### 6.5 スパム対策

- ガイドライン同意必須（参加時 `agreedGuideline:true` を強制）
- 参加直後 24 時間は VISITOR と同等の投稿制限（任意設定、村長が ON/OFF）
- 新規アカウント（登録 7 日以内）は村作成申請を出せない

### 6.6 IDOR 対策

すべての村スコープ API で、`{villageId}` の path variable に対して以下を必須化する:

```java
@PreAuthorize("@villageAccessGuard.canRead(#villageId)")
public ResponseEntity<X> get(@PathVariable UUID villageId, ...)
```

`VillageAccessGuard` は内部で:
1. 村が存在し deleted_at IS NULL AND archived_at IS NULL
2. PUBLIC ならスルー、UNLISTED なら村人であることを確認
3. 投稿・更新系は villager 以上、モデレ系は ELDER 以上

### 6.7 監査ログでの実投稿者記録

村スコープレスポンスから `userId` を排除しても、監査ログには **必ず実 user_id を記録する**。これは F10.3 監査ログの責務（運営の調査用）。投稿削除イベント `BULLETIN_POST_DELETED` の metadata に `posted_by_user_id` を含める。

## 7. GDPR / 退会時の扱い

CLAUDE.md 原則4「ユーザー退会時は匿名化」に準拠する。

### 7.1 退会時の処理

```java
// AuthAnonymizationService 拡張（F09.14 の前例どおり）
public void anonymizeForVillage(Long userId) {
    // 1. user_village_nicknames: 物理削除
    nicknameRepository.deleteAllByUserId(userId);

    // 2. user_village_pins: 物理削除
    pinRepository.deleteAllByUserId(userId);

    // 3. village_memberships: subject_type=USER のものを LEFT 状態に
    memberships.markLeft(userId, "ANONYMIZED");

    // 4. village_creation_requests: requester_user_id を 0 化（運営履歴は残す）
    creationRequests.anonymizeRequester(userId);

    // 5. 投稿（bulletin_posts / timeline_posts / chat_messages）:
    //    本テーブルは村ドメイン外。各機能の anonymizer が呼ばれる。
    //    村スコープ投稿の表示は「元村人A」「元村人B」…とインクリメンタル番号でマスクされる
    //    (※posted_as_subject_type=USER の場合のみ。TEAM/ORG 名義は保持)
}
```

### 7.2 元村人マスク

退会者の `userId` を `users` テーブル側で `display_name = "元村人 #ANON12345"` に置換する処理は **既存 anonymizer** が行う（F09.14 の例）。
村スコープ表示では `nickname` フィールドが削除済みなので、表示時に下記ルールで補完する:

```
if (user_village_nicknames に該当行なし AND users.deleted_at IS NOT NULL) {
    nickname = "元村人 #" + abs(userId.hashCode() % 100000)   // 安定的に同一人物は同一表示
}
```

### 7.3 投稿は保持

掲示板投稿・タイムライン投稿・井戸端発言はすべて保持する。

ただし `posted_as_subject_id` が user で当該 user_id が退会済みの場合は「元村人」表示。
`posted_as_subject_id` が team/organization の場合は、そのチーム/組織自身の deleted_at に従う（既存ロジック）。

### 7.4 監査ログ

監査ログの `user_id` 列は F10.3 既存ルール「SET NULL on delete」相当ではなく、本機能では `metadata` 内に `actor_user_id` を平文で記録するため、退会時バッチで `metadata.actor_user_id` を `null` に置換する処理を `AuthAnonymizationService` に追加する。

### 7.5 削除請求（Right to Erasure）

GDPR の削除請求があった場合、村スコープでは:

- 個人投稿の本文を `[削除されました]` に置換
- ニックネームを「元村人 #X」に置換
- 同一 user が複数の村に投稿していた場合、すべての村で同一処理

## 14. アーキテクチャ原則チェックリスト

| 原則 | 遵守状況 | 根拠 |
|---|---|---|
| **原則1** クロスドメイン FK 禁止 | ✅ | `village_memberships.subject_id`, `village_lobby_daily_threads.chat_channel_id`, `bulletin/timeline.scope_village_id`, `chat_channels.village_id` すべて FK なし |
| **原則2** CASCADE は同一ドメイン内のみ | ✅ | villages → village_memberships/nicknames/pins/reports/join_requests/lobby_daily_threads CASCADE は全て village ドメイン内。クロスドメインの CASCADE なし |
| **原則3** コアエンティティは論理削除 | ✅ | villages は deleted_at + archived_at の二段。village_memberships は left_at |
| **原則4** 退会時は匿名化 | ✅ | §7 で詳細。投稿維持・nickname 物理削除・元村人マスク |
| **原則5** @Transactional はドメイン内 | ✅ | village サービスは village ドメイン内に閉じる。投稿系は呼出先（bulletin/timeline/chat）の Transactional に委譲。監査ログは非同期イベント |
| **原則6** 新規テーブル PK = UUIDv7 | ✅ | 9 テーブル全て `BINARY(16)` UUIDv7 |
| **原則7** テナント絞り込み | ✅（適用外） | 村は全テナント横断のため `AbstractTenantAwareRepository` は **使わない**。標準 `JpaRepository` を使用。原則 7 の意図（テナント絞り込み統一）に該当しない設計判断を明記 |

### 14.1 原則7 適用外の根拠

CLAUDE.md 原則7 は「`organization_id` で絞り込む Repository は `AbstractTenantAwareRepository` を継承する」と定めるが、村は **全テナントを横断する横断機能** であり、`organization_id` カラム自体を持たない。
原則7 の意図は「将来シャーディング時に `organization_id` をシャードキーとして使う」ことだが、村は全テナント横断のため別のシャーディング戦略（村 ID シャードまたはレプリカ運用）が必要となる。Phase 1 では標準 `JpaRepository` を使い、Phase 5 以降のスケール段階で別途検討する。

## 付録 A: 設計の哲学

> 「村」は近代的な「コミュニティ」ではない。
> 「会員」も「役員」も「規約」もない、ただ縁あって寄り合った者同士が、
> ニックネームでゆるりと語らう場である。
>
> だからこそ、この機能は派手な装飾よりも、
> **個人の素性が漏れない安全**と、
> **誰でも気軽に出入りできる軽さ**と、
> **村人同士の距離感**を最優先に設計する。
>
> 公式村が権威を、任意村が多様性を、それぞれ担い、
> 1000 を超える村が、1000 万のユーザーの「他生の縁」を支える。

— F17.1 設計者註
