## 1. 背景・目的

### 1.1 背景

Mannschaft は現状、ランディングページ（`/`）以外のすべてのコンテンツがログイン必須である。未ログインユーザーが「このチームはどんな雰囲気か」「この組織はどんな投稿をしているか」を覗き見できる手段が一切なく、登録モチベーションを供給できない構造になっている。F15.4 Phase 5 で「店舗詳細の未ログイン公開」が個別に立ち上がっているが、横断的な公開導線・投稿者識別ルール・SEO 戦略は未整備であり、機能ごとに公開判断がブレるリスクがある。

### 1.2 目的

1. **新規ユーザー獲得障壁の撤去**: PUBLIC 設定のチーム・組織について、紹介ページ・公開投稿・公開イベントを未ログインで閲覧可能にする
2. **プライバシー保護の横断統一**: 投稿者識別情報（氏名・アバター・所属）を閲覧者立場（未ログイン / 非メンバー / サポーター / メンバー / 本人）別に段階開示する基盤を提供する
3. **法令遵守**: GDPR・改正個人情報保護法・CCPA に対応した「拡散済み情報の不可逆性」への警告 UI と削除フローを整備する
4. **SEO 流入の獲得**: OGP・sitemap・構造化データを整備し、検索エンジン経由の新規流入を成立させる
5. **F15.4 Phase 5 の上位概念化**: 単一テーブル（teams）の単一ページ（店舗詳細）向け設計を、組織・複数投稿・複数イベントを含む汎用基盤に昇格させる

### 1.3 価値マトリクス

| 価値 | 解決される課題 |
|---|---|
| 公開導線 | 「中身が見えない」問題による登録離脱を解消 |
| 段階開示 | 「公開設定にした瞬間に全員が本名で晒される」恐怖を解消（サポーター/メンバーで段階分け） |
| 非対称切替 | 「過去投稿の本名遡及公開」というユーザー裏切りを構造的に防ぐ |
| GDPR 完全対応 | snapshot を退会時に匿名化することで、退会後も過去投稿が本名で残るリスクを除去 |
| SEO 基盤 | 検索流入経路を構築（モダンランディングと年代別テーマだけでは流入経路が貧弱） |

### 2.2 含まないもの（明示的な Out of Scope）

| 除外項目 | 理由 / 代替方針 |

| チャット内容の公開 | チャットは常時プライベート（F04.2.1 と整合） |
| ファイル添付・写真の本体公開 | 情報漏洩リスク大。投稿本文のテキストのみ公開、添付は「ログインして閲覧」CTA に置換 |

| スケジュール（個人時間割）の公開 | F03.15 個人時間割は常時プライベート |

| 18 歳未満アカウントの投稿の公開 | §11.3 で常時 display_name 固定（本人投稿は公開可、ただし本名表示は無効化） |
| 半径検索 / 地図一覧 | F15.4 Phase 5 と整合し、別 Phase（v2）で扱う |

### 2.3 F15.4 Phase 5 との関係

F15.4 Phase 5 で提案された `/api/v1/public/teams/{id}` と `/public/teams/[id]` ページは、本設計の §6.1 に **そのまま包含** する。本設計では以下を追加する:

- F15.4 Phase 5 が扱わない「組織 (organizations) の公開ページ」
- F15.4 Phase 5 が扱わない「投稿一覧・投稿詳細・イベント一覧」
- F15.4 Phase 5 が扱わない「投稿者識別段階開示」
- F15.4 Phase 5 が扱わない「公開チーム / 組織の検索・列挙ページ」

F15.4 Phase 5 の `TeamPublicDetailResponse` 抑制 DTO・`PublicTeamApiRateLimitFilter`・`map_embed_url` カラムは本設計でも踏襲する。実装着手時に F15.4 Phase 5 と本設計を統合 PR として進めるか、Phase 5 を先行 PR としてマージしてから本設計の Phase 2 以降を積むかは §15 で判断する。

## 3. 用語定義

| 用語 | 定義 |
|---|---|
| **未ログイン閲覧者 (UnauthenticatedViewer)** | `Authentication` が anonymous または認証情報なし |
| **非メンバー (NonMember)** | ログイン済みだが対象チーム / 組織の `memberships` に `left_at IS NULL` 行を持たない |
| **サポーター (Supporter)** | 対象チーム / 組織の `memberships.role_kind = 'SUPPORTER'` かつ `left_at IS NULL` の行を持つ。他組織の SUPPORTER は対象組織から見れば「非メンバー」扱い |
| **メンバー (Member)** | 対象チーム / 組織の `memberships.role_kind = 'MEMBER'` かつ `left_at IS NULL` の行を持つ |
| **本人 (Self)** | 投稿の `author_id` が viewer の `userId` と一致 |
| **公開チーム (PublicTeam)** | `teams.visibility = 'PUBLIC'` かつ `archived_at IS NULL` かつ `deleted_at IS NULL` |
| **公開組織 (PublicOrganization)** | `organizations.visibility = 'PUBLIC'` かつ `archived_at IS NULL` かつ `deleted_at IS NULL` |
| **表示名 (display_name)** | `users.display_name`（NULL / 空時はフォールバック §4.6.4） |
| **本名 (real_name)** | `users.last_name + ' ' + users.first_name`（locale により語順変動 §8.4） |
| **名前開示モード (NameDisclosureMode)** | サポーター向け表示の切替フラグ。ENUM('DISPLAY_NAME', 'REAL_NAME') |
| **本名スナップショット (RealNameSnapshot)** | 投稿時に `author_real_name_snapshot` カラムに保存される本名文字列。REAL_NAME モード時のみ記録 |
| **ViewerContext** | バックエンドが投稿表示時に組み立てる「閲覧者の立場 + メンバーシップ情報」DTO |
| **DisplayIdentity** | IdentityVisibilityResolver が返す表示用識別情報 { name, avatarUrl, teamAffiliationVisible } |
| **汎用ラベル (GenericLabel)** | 未ログイン / 非メンバーに見せる匿名ラベル（例: 「投稿者」「メンバー」） |
| **汎用アバター (AnonymousAvatar)** | 未ログイン / 非メンバーに見せるデフォルトアイコン（個人特定不能） |

## 4. 機能要件

### 4.1 公開チーム / 組織ページの閲覧

- `teams.visibility = 'PUBLIC'` のチーム、`organizations.visibility = 'PUBLIC'` の組織のみ未ログインで閲覧可能
- アーカイブ済み（`archived_at IS NOT NULL`）・削除済み（`deleted_at IS NOT NULL`）は対象外（404）
- 表示要素: 名称・愛称・テンプレート・所在地（市区町村まで）・設立日・公式 HP・理念（`organization_profile_visibility` の `philosophy` 公開フラグが ON のときのみ）・アイコン・バナー・地図埋め込み（`map_embed_url` がある場合）
- 段階開示ルール（§4.6）に従う

### 4.2 公開投稿一覧の閲覧

- 対象: `announcement_feeds` のうち以下条件全てを満たす行
  - `scope_type = 'TEAM'` または `'ORGANIZATION'`
  - `scope_id` が PUBLIC エンティティ
  - `visibility = 'PUBLIC'`（announcement_feeds の visibility は元コンテンツから継承・同期されている前提。F02.6 と整合）
  - `source_deleted_at IS NULL`
  - `starts_at IS NULL OR starts_at <= NOW()`
  - `expires_at IS NULL OR expires_at > NOW()`
  - `posts.public_visible = TRUE`（§5.2.3 新規カラム）

> **軍議追補（2026-05-18）**: 偵察により `announcement_feeds.visibility` の事後同期機構が未実装（作成時継承のみで、ソース側の visibility 変更が feed に反映されない）と判明。Phase 1 では安全側に倒し、`announcement_feeds.visibility` ではなく **ソーステーブル直 JOIN**（`blog_posts` / `timeline_posts` / `events` 等の `visibility` カラムを直接結合）で PUBLIC 絞り込みを実装する。`announcement_feeds.visibility` は補助情報として参照可だが、PUBLIC 判定の権威ソースにはしない。事後同期 listener は本設計と切り離し、別軍議（F02.6 改修）で扱う。§5.2.3 / §7.6 / §17.10 の SQL 詳細は Phase 1 実装軍議の Foundation 部隊で本方針を反映して確定する。
- ページネーション: カーソル方式（`(created_at, id)` 複合カーソル）。20 件 / ページ。最大 1000 件まで（深いページネーション抑止）
- 各投稿はタイトル・本文抜粋（excerpt_cache）・投稿者識別（段階開示）・投稿日時を表示
- 添付ファイル・画像は本文中の参照のみテキスト表示（プレースホルダ「[添付ファイル — ログインして閲覧]」）

### 4.3 個別投稿詳細・OGP

- URL: `/public/teams/{teamId}/posts/{postId}` / `/public/organizations/{orgId}/posts/{postId}`
- 表示要素: タイトル・本文全文・投稿者識別（段階開示）・投稿日時・所属チーム / 組織情報リンク
- OGP メタタグ: `og:title` = 投稿タイトル、`og:description` = 抜粋（最大 200 文字）、`og:image` = 組織 / チームバナー、`og:type` = `article`
- 構造化データ: `schema.org/Article`（headline / datePublished / author（汎用ラベル または display_name）/ publisher）
- canonical URL: `https://{host}/public/{teams|organizations}/{id}/posts/{postId}`

### 4.4 公開イベント・タイムライン投稿一覧

**公開イベント（events）**:
- チームのイベント: チームが PUBLIC かつ `teams.public_events_enabled = TRUE`（§5.1.1）かつイベントの visibility = PUBLIC の場合のみ公開
- 組織のイベント: 組織が PUBLIC かつ `organizations.public_events_enabled = TRUE`（§5.1.2 改訂）かつイベントの visibility = PUBLIC の場合のみ公開
- 両者ともデフォルト非公開（DEFAULT FALSE）。管理者が明示的に有効化する

**タイムライン投稿（timeline_posts）**:
- チーム: `teams.timeline_posts_public = TRUE`（§5.1.1）かつ投稿の `public_visible = TRUE` の場合のみ公開
- 組織: `organizations.timeline_posts_public = TRUE`（§5.1.2）かつ投稿の `public_visible = TRUE` の場合のみ公開
- 両者ともデフォルト非公開（DEFAULT FALSE）

- 表示要素: タイトル・日時・場所（公開可フラグが ON の場合のみ）・主催者識別（段階開示）
- 参加申込ボタンは「ログインして申し込む」CTA に置換

### 4.5 メンバー総数表示

- `teams.member_count` / `organizations.member_count`（F15.4 Phase 4 で導入済み）を表示
- 個別メンバー名は段階開示ルール（§4.6）に従う。未ログインには **常時非表示**
- F15.4 Phase 5 §3.2 の禁則フィールド（members 一覧）を踏襲

### 4.6 投稿者識別段階的開示ルール

#### 4.6.1 開示マトリクス

| 閲覧者 | 投稿者名 | アバター | チーム所属表示 |
|---|---|---|---|
| 未ログイン / 非メンバー | 汎用ラベル（「投稿者」/「メンバー」/「主催者」） | 汎用アバター | **非表示** |
| サポーター（対象チーム / 組織の SUPPORTER） | 設定に従う（DISPLAY_NAME or REAL_NAME） | ユーザーアバター | 表示 |
| メンバー（対象チーム / 組織の MEMBER） | 本名 | ユーザーアバター | 表示 |
| 本人 | 本名 | ユーザーアバター | 表示 |
| ADMIN / DEPUTY_ADMIN / SYSTEM_ADMIN | メンバーと同じ（本名） | ユーザーアバター | 表示 |

「チーム所属表示」は「このメンバーは XX チームに所属しています」というラベル。未ログインビューで非表示にする理由は「チーム名 + 顔写真 + イニシャル」の組み合わせで個人特定されるのを防ぐため。

#### 4.6.2 サポーターの厳格定義

- viewer のメンバーシップ取得は **対象スコープ単位** で実施: `SELECT role_kind FROM memberships WHERE user_id = :viewerId AND scope_type = :scopeType AND scope_id = :scopeId AND left_at IS NULL LIMIT 1`
- 別組織 / 別チームの SUPPORTER は viewer 立場として「非メンバー」扱い
- 投稿の `team_id` / `organization_id` を取得し、その scope に対するメンバーシップで判定

#### 4.6.3 本人判定

- 投稿の `author_id == viewer.userId` の場合のみ「本人」
- 退会済みユーザーの過去投稿は `author_id IS NULL` または `author_id = 0`（センチネル）になる。この場合「本人」扱いは発生しない

#### 4.6.4 display_name フォールバック規約

`users.display_name` が NULL または空文字の場合、表示時は以下のフォールバック文字列を用いる。投稿自体はブロックしない（プロフィール設定で後から変更可能）。

- 日本語ロケール: `匿名のユーザー#${shortHash}`
- その他ロケール（en / zh / ko / es / de）: `Anonymous#${shortHash}`
- `shortHash` は `users.id` から決定論的に生成する 4〜6 文字の英数字（例: SHA-256(`users.id` の文字列表現) を Base36 エンコードして先頭 5 文字、ハイフンは含めない）。同一ユーザーであれば常に同じ値が得られるため、同一スレッド内で「同じ匿名ユーザー」と区別可能になる
- 上記をフォールバックする helper として、`IdentityVisibilityResolver` 内に static メソッド `IdentityVisibilityResolver.fallbackDisplayName(User user)` を実装する。各 Resolver / DTO 組み立て箇所はこの helper を経由して取得する（重複実装禁止）
- 本フォールバック文字列は §4.6.1 開示マトリクスの「未ログイン / 非メンバー」が見る汎用ラベル（「投稿者」「メンバー」「主催者」）とは異なる用途で、サポーター以上の閲覧者に対して「display_name 表示の代替」として使われる点に注意

### 4.7 表示名→本名 / 本名→表示名 の非対称切替ルール

#### 4.7.1 DISPLAY_NAME → REAL_NAME（本名表示に切替）

- **切替以降の投稿のみ** 本名で表示
- 切替時点で既に存在する投稿は `author_real_name_snapshot IS NULL` のままで、表示時は viewer 立場別に **display_name** で表示し続ける
- 切替以降に作成された投稿は `author_real_name_snapshot` に投稿時の本名がスナップショットされ、サポーター以上の viewer には本名で表示
- 理由: 過去に「display_name 前提で投稿した」ユーザーの期待を裏切らない

#### 4.7.2 REAL_NAME → DISPLAY_NAME（表示名表示に戻す）

- **過去投稿も含め全て** display_name に切替
- 表示ロジック: 「現在の設定が DISPLAY_NAME なら snapshot を無視」（§7.6）
- スナップショットは DB に残るが表示には使われない。再度 REAL_NAME に切り替えた場合は snapshot が再び表示に使われる
- 理由: ユーザーがプライバシーを取り戻せるようにする（GDPR的にも適切）

#### 4.7.3 切替の真実の源 (Source of Truth)

- 現在の `teams.supporter_name_disclosure` / `organizations.supporter_name_disclosure` が表示モードの権威ソース
- `author_real_name_snapshot` はあくまで「投稿時点の本名スナップショット」であり、現在の display_name と乖離していても問題ない（ユーザーが改名した場合の歴史的真実を保持）
- 切替操作は `team_name_disclosure_change_logs` / `organization_name_disclosure_change_logs` テーブル（§5.3）に監査記録される

### 4.8 管理者向け切替警告 UI

- REAL_NAME に切り替える際、確認ダイアログを表示
- 警告文（ja サンプル）:
  > 「サポーター向けに本名表示モードに切り替えます。切替以降の新規投稿は、サポーター以上の閲覧者に投稿者の本名が表示されます。
  >
  > 公開ページ（未ログイン閲覧者を含む）でも、サポーター登録すれば本名が見えるようになります。**外部にスクレイピング・SNS 拡散された情報は後から取り戻せません。**
  >
  > 本変更を実施してよろしいですか?」
- 確認チェックボックス「上記リスクを理解しました」を ON にしないと「変更する」ボタンが活性化しない
- 切替操作は監査ログ（`audit_logs`）と専用切替履歴テーブル（§5.3）に二重記録
- REAL_NAME → DISPLAY_NAME に戻す方向は警告不要（プライバシー強化方向のため）

### 4.9 ランディングからの導線・公開検索

- ランディング (`/`) の CTA エリアに「公開チームを探す」「公開組織を探す」ボタンを追加
- 検索ページ: `/discover/teams` / `/discover/organizations`
- キーワード（name / nickname1 / nickname2 部分一致）+ 都道府県 + テンプレート絞り込み
- 結果はカーソル方式ページネーション
- F15.4 既存の `OrganizationTeamSearchRateLimitFilter` を流用（F15.4 Phase 5 §4.4 と整合）

### 7.1 IdentityVisibilityResolver（新規）

```java
@Component
public class IdentityVisibilityResolver {
    public DisplayIdentity resolve(
        ViewerContext viewer,
        AuthorRef author,           // { userId, currentDisplayName, currentRealName, currentAvatarUrl }
        PostRef post,               // { realNameSnapshot, teamId, organizationId }
        ScopeSettings scopeSettings // { supporterNameDisclosure }
    );
}

public enum ViewerStatus {
    UNAUTHENTICATED, NON_MEMBER, SUPPORTER, MEMBER, SELF
}

public record DisplayIdentity(
    String name,
    String avatarUrl,
    boolean teamAffiliationVisible
) {}
```

判定アルゴリズム:

```
1. viewer.status == UNAUTHENTICATED または NON_MEMBER:
     return DisplayIdentity(汎用ラベル, 汎用アバター, false)
2. viewer.status == SELF:
     return DisplayIdentity(本人本名, 本人アバター, true)
3. viewer.status == MEMBER または ADMIN系:
     return DisplayIdentity(本名, 実アバター, true)
4. viewer.status == SUPPORTER:
     if (scopeSettings.supporterNameDisclosure == DISPLAY_NAME):
         return DisplayIdentity(現在のdisplay_name (フォールバック §4.6.4), 実アバター, true)
     if (scopeSettings.supporterNameDisclosure == REAL_NAME):
         if (post.realNameSnapshot != null):
             return DisplayIdentity(post.realNameSnapshot, 実アバター, true)
         else:
             return DisplayIdentity(現在のdisplay_name (フォールバック), 実アバター, true)
              // ★ Snapshot がない場合は切替前投稿 → display_name にフォールバック
```

「未成年フラグ」を持つ投稿者は §11.3 のロジックで強制的に DISPLAY_NAME 系にフォールバック。

### 7.5 PostAuthorSnapshotService（投稿時 snapshot 記録）

```java
@Service
@RequiredArgsConstructor
public class PostAuthorSnapshotService {

    private final TeamRepository teamRepository;
    private final OrganizationRepository organizationRepository;
    private final UserRepository userRepository;

    /**
     * 投稿作成時に呼ばれ、scope の現在のモードに応じて real_name_snapshot を返す。
     */
    public String resolveSnapshotForPost(Long authorId, ScopeRef scope) {
        var mode = lookupMode(scope);
        if (mode == NameDisclosureMode.DISPLAY_NAME) {
            return null;
        }
        // REAL_NAME の場合は現在の本名をスナップショット
        UserEntity author = userRepository.findById(authorId).orElseThrow();
        if (author.isMinor()) {            // §11.3
            return null;
        }
        return formatRealName(author);
    }
}
```

呼び出し元: `BlogPostService.create`, `TimelinePostService.create`, `EventService.create` 等の各投稿系 Service。投稿 Entity を save する直前に snapshot を埋める。

`@Transactional` はドメイン内（blog ドメイン等）に閉じる。`PostAuthorSnapshotService` は user / team / organization Repository を読み取り専用で参照する横断 Service として位置付け、書き込みは行わない（CLAUDE.md 原則 5）。

## 10. セキュリティ

### 10.1 認証・認可

- 公開エンドポイントは認証不要だが、ハンドラ冒頭で `teams.visibility == PUBLIC` を厳格チェック
- `PRIVATE` チームの ID が指定された場合は **404**（403 ではない、存在自体を隠す。F15.4 Phase 5 §4.3 と整合）
- 認証済みユーザーが認証必須エンドポイントを叩いたときの挙動は不変

### 10.2 レート制限

- 公開エンドポイントは IP ごとにレート制限
- F15.4 Phase 5 §4.4 の `PublicTeamApiRateLimitFilter` を流用し、対象パスを `/api/v1/public/**` 全体に拡張（リネーム: `PublicApiRateLimitFilter`）
- 未ログイン: 60 req/min/IP
- ログイン: 200 req/min/user
- 検索エンドポイント（`/api/v1/public/teams`）は 30 req/min/IP（列挙攻撃抑制）
- レート超過時は 429 + `Retry-After` ヘッダ

### 10.3 IDOR 対策

- `teamId` / `postId` / `orgId` が PUBLIC でないスコープを指していたら **404**（403 ではない）
- 投稿 ID と URL 上の teamId / orgId が一致しない場合も **404**（クロススコープ参照防止）

### 10.4 PII 漏洩防止

- 公開 DTO は認証済み DTO と完全分離（§6.3）
- CI で「禁則ワード検出テスト」を必須化:
  ```java
  @Test
  void publicResponseMustNotContainPii() {
      String json = mockMvc.perform(get("/api/v1/public/teams/1")).andReturn();
      assertThat(json).doesNotContain("email", "phone", "lastName", "firstName",
          "lastNameKana", "firstNameKana", "birthday", "address", "passwordHash",
          "refreshToken", "version", "archivedAt", "deletedAt");
  }
  ```
- レビュー時のチェックリストに「公開 DTO に新規フィールドを追加するときは禁則ワードリストを更新する」を追加

### 10.5 監査ログ

- 認証必須操作（モード切替・public_visible 切替）は既存 `audit_logs` に記録
- 公開エンドポイントの正常アクセスは **access log のみ**（既存 Nginx / Spring の標準ログで十分、`audit_logs` は使わない）
- レート超過時のみ `audit_logs` に `PUBLIC_API_RATE_LIMIT_EXCEEDED` で記録（IP ハッシュ + パス）

### 10.6 スクレイピング / Bot 対策

- 上記レート制限
- カーソルベースページネーション（offset 攻撃の効率を落とす）
- 大量列挙が観測された場合は CDN レベルで User-Agent ベースのチャレンジ（v2 で CAPTCHA 検討）

### 10.7 XSS / CSP

- 投稿本文 HTML は既存サニタイザ（HTML Sanitizer ライブラリ）でホワイトリスト方式
- CSP に `frame-src https://www.google.com`（map_embed_url 用）を追加（F15.4 Phase 5 §5.2 と整合）
- 公開ページの URL クエリパラメータ反映時は `v-text` / `{{ }}` のみ、`v-html` 禁止

### 10.8 CSRF

- 公開 GET エンドポイントは CSRF トークン不要（読み取り専用 + 副作用なし）
- PATCH 系（モード切替）は既存 CSRF 保護対象

### 10.9 SQL インジェクション

- すべて Spring Data JPA / 名前付きパラメータ。検索キーワードも JPA Specification で安全に組み立て
- LIKE 句のワイルドカード（`%`, `_`）はエスケープ

### 10.10 クリックジャッキング

- 公開ページに `X-Frame-Options: SAMEORIGIN` を維持（外部 iframe 埋め込み禁止）
- v2 で「埋め込み許可ホワイトリスト」を導入する場合は別軍議

### 10.11 robots.txt と認可の分離

- robots.txt は紳士協定。Bot がこれを無視してアクセスしてくる前提で認可は §10.1〜10.4 のサーバーサイド検証に依存

## 11. プライバシー・GDPR

### 11.1 ユーザー退会時のスナップショット匿名化

F12.3 `AccountPurgeService` の Phase 2 に以下を追加:

```
Phase 2 (extended): snapshot 匿名化
  ├─ blog_posts          → author_real_name_snapshot を「退会済みユーザー」に上書き
  ├─ timeline_posts      → 同上
  ├─ events              → 同上
  └─ team/organization_name_disclosure_change_logs → changed_by を NULL に
```

実装:

```java
@Modifying
@Query(value = "UPDATE blog_posts SET author_real_name_snapshot = '退会済みユーザー' WHERE author_id = :userId AND author_real_name_snapshot IS NOT NULL", nativeQuery = true)
int anonymizeBlogPostSnapshots(@Param("userId") Long userId);
```

これにより退会後も snapshot 由来の本名漏洩はゼロになる（投稿テキスト本文中に本名が書かれていた場合は別問題で、対処は §11.4 個別非表示フラグ）。

### 11.2 表示名→本名切替の警告

§4.8 参照。第三者拡散の不可逆性を必ず警告し、確認チェックボックスを必須とする。

### 11.3 子供アカウント保護

- 18 歳未満ユーザーの投稿は **常時 display_name**
- `IdentityVisibilityResolver.resolve()` 内で `author.isMinor()` を判定し、REAL_NAME モードでも snapshot を無視
- **軍議裁定（2026-05-19 / PR-1 Foundation）**: `users.is_minor` カラムは**追加しない**。代わりに F03.12 で既存の `users.care_category = 'MINOR'` を MINOR 判定の **SoT（Source of Truth）** として使用する。これにより新規カラム追加（V9.172）が不要となり、既存の care_category フィールドを活用した実装が可能になる。
- `IdentityVisibilityResolver.isMinor(author)` の実装では `author.getCareCategory() == CareCategory.MINOR` で判定する（Phase 2 で活性化）
- Phase 1 では `isMinor()` を **常に false 返却**の暫定実装（no-op）にしておく

> **経緯**: 当初は Phase 2 で `users.is_minor` BOOLEAN カラム（V9.172）を追加する計画だったが、F03.12 で既に `users.care_category` ENUM カラムが存在し `'MINOR'` 値が定義されているため、重複追加は設計重複となる。`care_category = 'MINOR'` を MINOR 判定の SoT として採用することで、V9.172 マイグレーションが不要となり DB 変更コストも削減できる。

### 11.4 削除要求への対応（個別非表示フラグ）

- 投稿テーブルに `public_visible BOOLEAN DEFAULT TRUE` カラム（§5.2.2）
- 投稿者本人が `PATCH /api/v1/posts/{postId}/public-visible` で `false` に変更可能
- `false` の投稿は公開ページ・sitemap・OGP すべてから除外（ログイン後の通常ビューには変化なし）
- 「過去の投稿で本名公開時代のものを引っ込めたい」要求への第一防衛線

### 11.5 国別法規対応

| 法規 | 対応 |
|---|---|
| GDPR（EU）第 17 条「忘れられる権利」 | 退会 → 30 日後 snapshot 匿名化 + 個別非表示フラグ |
| GDPR 第 7 条「同意撤回権」 | 切替警告ダイアログでオプトイン的に「同意」を取る |

## 13. 保守性

### 13.1 既存 Resolver パターンとの統合

- F00 ContentVisibilityResolver の Strategy + Registry パターンに乗る

### 13.7 CLAUDE.md 原則 7（AbstractTenantAwareRepository）の適用外注記

本設計の Repository（`PublicTeamQueryService` / `PublicOrganizationQueryService` の配下 Repository 等）は「未認証ユーザーによる横断公開検索」が主用途であり、特定 `organization_id` への絞り込みを前提としない。そのため CLAUDE.md アーキテクチャ思想原則 7（テナントスコープは `AbstractTenantAwareRepository` を継承）の適用対象外とし、`JpaRepository<T, ID>` を直接継承する。`teams.visibility = 'PUBLIC'` / `organizations.visibility = 'PUBLIC'` での絞り込みはアプリ層で明示し、テナント境界は「PUBLIC ⇔ それ以外」という縦の境界線で実現する。

将来テナント横断キャッシュ層を導入する場合は、原則 7 とは別系統の `AbstractPublicCachingRepository` 等を新設する想定（v2 別軍議）。Phase 1 〜 Phase 5 ではキャッシュは Service 層（`PublicPostQueryService` 等）で per-scope に保持し、Repository 層に持ち込まない。

- 緩和策: `<meta name="robots" content="noindex">` を以下に付与
  - 投稿数 0 件のチーム / 組織
  - 最終投稿から 1 年以上経過
  - メンバー数 1 名のチーム
- canonical URL で重複コンテンツ対策

### 16.4 サーバー負荷増（未認証アクセス激増の可能性）

- 緩和策: レート制限 / CDN キャッシュ（Cloudflare 1 時間 TTL）/ 投稿一覧は per-scope キャッシュ
- 負荷急増時はサーキットブレーカで認証必須に強制フォールバック（運用切替）

### 16.5 法的リスク（地域別の個人情報保護法）

- §11.5 で対応済みだが、施行細則の変更を年次でレビュー
- プライバシーポリシーに「公開ページ表示項目」を明記

### 16.6 子供アカウント保護の網羅性

- `users.birthday` / `users.is_minor` の運用品質に依存
- 18 歳未満が誤って成人として登録した場合のリスク → 保護者通報フロー（F03.12 ケア対象者見守りと連携）

### 16.7 切替監査ログの肥大化
