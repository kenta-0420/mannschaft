## 1. 背景・目的

### 1.1 SEO から GEO へ

これまでの公開ページ最適化は **SEO（Search Engine Optimization / 検索エンジン最適化）** を前提にしてきた。SEO は「Google などの検索エンジンの結果一覧で上位に表示され、ユーザーにクリックしてもらう」ための施策である。

しかし 2024〜2026 年にかけて、ユーザーの情報取得行動が大きく変わった。ChatGPT・Perplexity・Google AI Overviews（旧 SGE）といった **生成 AI が「答えそのもの」を返す** 形式が一般化し、ユーザーは検索結果のリンクを踏まずに AI の回答だけで完結する（＝ **ゼロクリック**）ケースが急増している。

このため「検索結果で上位に出る」だけでは不十分で、**AI が回答を生成するときに自社のコンテンツを引用・参照してくれる** ことを狙う最適化が必要になった。これを **GEO（Generative Engine Optimization / 生成エンジン最適化）** と呼ぶ。

### 1.2 SEO と GEO の違い（初心者向け）

| 観点 | SEO（従来） | GEO（本設計の対象） |
|---|---|---|
| 最適化の相手 | 検索エンジンのランキングアルゴリズム | 生成 AI（LLM）の回答生成プロセス |
| ゴール | 検索結果で上位表示 → クリックされる | AI の回答に **引用・要約・出典リンク** として採用される |
| ユーザー行動 | 検索 → リンクをクリック → サイト訪問 | 検索 → AI が答えを生成 → サイトを踏まないことが多い（ゼロクリック） |
| 効く施策 | キーワード・被リンク・表示速度・モバイル対応 | **構造化データ（JSON-LD）**・明確な定義文・事実の機械可読化・信頼できる出典提示 |
| 評価される文章 | クリックを誘うタイトル・キャッチ | 「○○とは△△である」と **そのまま引用できる簡潔な定義文** |

要するに GEO では「AI が安心して引用できるよう、**誰が・どこで・何をしている組織か** を機械可読な形で明示し、引用しやすい定義文を置く」ことが重要になる。SEO の施策は GEO の土台でもあるため捨てるのではなく、その上に GEO 特有の施策を重ねる。

### 1.3 本設計のゴール

Mannschaft の公開ページ（公開チーム / 公開組織）を、ChatGPT・Perplexity・Google AI Overviews に **引用されやすい状態** にする。具体的には:

1. 組織の所在地・公式サイト・定義文を **構造化データ（JSON-LD）** として明示する。
2. パンくず（階層構造）を機械可読にして、AI がページの文脈を理解しやすくする。
3. philosophy（理念）が未設定でも **引用に耐える定義文** を自動生成する。

### 2.3 重要な発見

公開 DTO `PublicTeamResponse` / `PublicOrganizationResponse` には既に以下のフィールドが含まれている:

```
prefecture / city / philosophy / homepageUrl / iconUrl / bannerUrl
```

したがって §2.2 の **Phase 1 候補（PostalAddress / BreadcrumbList / 定義文 / sameAs）はフロントエンドの JSON-LD 拡張だけで実現でき、バックエンド・DB の変更は一切不要** である。これが Phase 1 を「即対応」と位置づける根拠。

## 3. スコープと非スコープ

### 3.1 スコープ（Phase 1）

- 公開チームページ（`/public/teams/[id]`）と公開組織ページ（`/public/organizations/[id]`）の JSON-LD を `@graph` 化し、`Organization`（address + sameAs + description）と `BreadcrumbList` を出力する。
- philosophy 未設定時に地理情報入りの定義文を i18n で動的生成する。
- 6 言語（ja / en / zh / ko / es / de）の i18n キー追加。
- E2E テスト（`public-seo.spec.ts`）の拡張。

### 3.2 非スコープ

- バックエンド・DB の変更（Phase 1 では一切行わない）。
- 投稿詳細ページ（`Article`）への `@graph` 化（既存のままで十分に GEO 適合済のため対象外）。
- 緯度経度・電話番号・営業時間など DB に存在しないデータを要する構造化（Phase 2 以降）。
- 都道府県別ハブページの新規作成（Phase 2 以降）。

### 4.1 Organization スキーマの拡張

- `address`: `prefecture` または `city` が存在する場合のみ `PostalAddress`（`addressCountry: 'JP'`, `addressRegion: prefecture`, `addressLocality: city`）を出力。両方 null なら `address` 自体を `undefined`。
- `sameAs`: `homepageUrl` があれば `[homepageUrl]`、なければ `undefined`。
- `description`: §7 の `seoDescription`。

### 4.2 BreadcrumbList スキーマ

3 階層:

1. position 1 = ホーム（item = `baseUrl`）
2. position 2 = チームを探す / 組織を探す（item = `baseUrl + /discover/teams` または `/discover/organizations`）
3. position 3 = チーム名 / 組織名（item なし＝末端）

`undefined` のフィールドは `JSON.stringify` が自動的に省くため、出力はクリーンになる。

### 4.3 i18n（直書き禁止）

UI / 構造化データに出す文字列はすべて i18n キー経由（CLAUDE.md i18n ルール）。en には英訳、zh / ko / es / de はとりあえず日本語値（後で翻訳）。

- `og:locale:alternate`（6 言語分）。
- 画像 `alt` の i18n 化。

## 6. JSON-LD スキーマ定義（Phase 1 / @graph）

### 6.1 公開チームページの出力例

prefecture / city / homepageUrl がすべて揃う場合:

```json
{
  "@context": "https://schema.org",
  "@graph": [
    {
      "@type": "Organization",
      "name": "FC サンプル",
      "url": "https://mannschaft.example.com/public/teams/123",
      "logo": "https://cdn.example.com/icons/team-123.png",
      "description": "東京都渋谷区を拠点に活動する FC サンプルの公開ページです。",
      "address": {
        "@type": "PostalAddress",
        "addressCountry": "JP",
        "addressRegion": "東京都",
        "addressLocality": "渋谷区"
      },
      "sameAs": ["https://fc-sample.example.com"]
    },
    {
      "@type": "BreadcrumbList",
      "itemListElement": [
        { "@type": "ListItem", "position": 1, "name": "ホーム", "item": "https://mannschaft.example.com" },
        { "@type": "ListItem", "position": 2, "name": "チームを探す", "item": "https://mannschaft.example.com/discover/teams" },
        { "@type": "ListItem", "position": 3, "name": "FC サンプル" }
      ]
    }
  ]
}
```

### 6.2 prefecture / city / homepageUrl が無い場合

`address` と `sameAs` は出力されず（`JSON.stringify` が `undefined` を省く）、`description` は §7 の名前のみフォールバック文になる:

```json
{
  "@context": "https://schema.org",
  "@graph": [
    {
      "@type": "Organization",
      "name": "FC サンプル",
      "url": "https://mannschaft.example.com/public/teams/123",
      "description": "FC サンプルの公開ページです。"
    },
    {
      "@type": "BreadcrumbList",
      "itemListElement": [
        { "@type": "ListItem", "position": 1, "name": "ホーム", "item": "https://mannschaft.example.com" },
        { "@type": "ListItem", "position": 2, "name": "チームを探す", "item": "https://mannschaft.example.com/discover/teams" },
        { "@type": "ListItem", "position": 3, "name": "FC サンプル" }
      ]
    }
  ]
}
```

### 6.3 公開組織ページ

構造は §6.1 と同じ。BreadcrumbList の position 2 が「組織を探す」（item = `/discover/organizations`）になる点のみ異なる。

## 7. 定義文（description）生成ロジック

`seoDescription` computed を各ページに定義し、`useSeoMeta` の description / ogDescription / twitterDescription、`useSeoPublicPage` の description、Organization の description で **共有**（重複定義を避ける）。

優先順位:

1. `philosophy`（理念）が空白でなければそれをそのまま使う。
2. philosophy が無く、`prefecture` または `city` があれば
   → `{prefecture}{city}を拠点に活動する{name}の公開ページです。`（`public.{team,organization}.geoDescription`）
3. philosophy も地理情報も無ければ
   → `{name}の公開ページです。`（`public.{team,organization}.geoDescriptionNoLocation`）

> 補足: 計画では philosophy 無し時に常に geoDescription を使う想定だったが、prefecture / city が両方空だと「を拠点に活動する…」という不自然な文になるため、地理情報ゼロ時専用の `geoDescriptionNoLocation` キーにフォールバックする設計に変更した（§10 変更履歴参照）。

## 9. リスク・トレードオフ

| リスク | 評価 | 対応 |
|---|---|---|
| `@graph` 化で既存 JSON-LD の形が変わり、過去のクローラ前提が壊れる | 低 | schema.org の `@graph` は標準。トップレベル単体から `@graph` 配列への移行は Google も推奨形。E2E で形を固定。 |
| philosophy 自動生成文が不自然・誇大に見える | 低 | 「公開ページです」という事実ベースの控えめな文に留め、活動内容の断定を避けた。 |
| prefecture / city が荒い（市区まで）ため `GeoCoordinates` 相当の精度は出ない | 中 | Phase 1 では `PostalAddress` の `addressRegion` / `addressLocality` まで。緯度経度は Phase 2。 |
| AI 引用は外部要因（各社アルゴリズム）に依存し効果測定が難しい | 中 | 構造化データの正しさは Rich Results Test で検証可能。引用率自体は将来の分析対象。 |
| バックエンド変更ゼロのため `sameAs` 等は既存データの充足率に依存 | 低 | データが無いフィールドは `undefined` で自然に省略され、出力は常に妥当。 |
