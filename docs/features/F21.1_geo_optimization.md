## 1. 背景・目的

### 1.1 SEO から GEO へ

これまでの公開ページ最適化は **SEO（Search Engine Optimization / 検索エンジン最適化）** を前提にしてきた。SEO は「Google などの検索エンジンの結果一覧で上位に表示され、ユーザーにクリックしてもらう」ための施策である。

しかし 2024〜2026 年にかけて、ユーザーの情報取得行動が大きく変わった。ChatGPT・Perplexity・Google AI Overviews（旧 SGE）といった **生成 AI が「答えそのもの」を返す** 形式が一般化し、ユーザーは検索結果のリンクを踏まずに AI の回答だけで完結する（＝ **ゼロクリック**）ケースが急増している。

このため「検索結果で上位に出る」だけでは不十分で、**AI が回答を生成するときに自社のコンテンツを引用・参照してくれる** ことを狙う最適化が必要になった。これを **GEO（Generative Engine Optimization / 生成エンジン最適化）** と呼ぶ。

### 1.2 SEO と GEO の違い（初心者向け）

| 観点 | SEO（従来） | GEO（本設計の対象） |
|---|---|---|
| 最適化の相手 | 検索エンジンのランキングアルゴリズム | 生成 AI（LLM）の回答生成プロセス |
| ゴール | 検索結果で上位表示 → クリックされる | AI の回答に **引用・要約・出典リンク** として採用される |
| ユーザー行動 | 検索 → リンクをクリック → サイト訪問 | 検索 → AI が答えを生成 → サイトを踏まないことが多い（ゼロクリック） |
| 効く施策 | キーワード・被リンク・表示速度・モバイル対応 | **構造化データ（JSON-LD）**・明確な定義文・事実の機械可読化・信頼できる出典提示 |
| 評価される文章 | クリックを誘うタイトル・キャッチ | 「○○とは△△である」と **そのまま引用できる簡潔な定義文** |

要するに GEO では「AI が安心して引用できるよう、**誰が・どこで・何をしている組織か** を機械可読な形で明示し、引用しやすい定義文を置く」ことが重要になる。SEO の施策は GEO の土台でもあるため捨てるのではなく、その上に GEO 特有の施策を重ねる。

### 1.3 本設計のゴール

Mannschaft の公開ページ（公開チーム / 公開組織）を、ChatGPT・Perplexity・Google AI Overviews に **引用されやすい状態** にする。具体的には:

1. 組織の所在地・公式サイト・定義文を **構造化データ（JSON-LD）** として明示する。
2. パンくず（階層構造）を機械可読にして、AI がページの文脈を理解しやすくする。
3. philosophy（理念）が未設定でも **引用に耐える定義文** を自動生成する。

### 4.1 Organization スキーマの拡張

- `@id`: `ctx.canonicalUrl + '#organization'`。`@graph` 内ノードの一意識別子で、AI / クローラがノード間参照を解決しやすくする。
- `url`: `ctx.canonicalUrl`（単一ソース。§4.4 参照）。
- `address`: `prefecture` または `city` が存在する場合のみ `PostalAddress`（`addressCountry: 'JP'`, `addressRegion: prefecture`, `addressLocality: city`）を出力。両方 null なら `address` 自体を `undefined`。
- `sameAs`: `homepageUrl` があれば `[homepageUrl]`、なければ `undefined`。
- `description`: §7 の `seoDescription`。

### 4.2 BreadcrumbList スキーマ

- `@id`: `ctx.canonicalUrl + '#breadcrumb'`。
- 3 階層:
  1. position 1 = ホーム（item = `ctx.baseUrl`）
  2. position 2 = チームを探す / 組織を探す（item = `ctx.baseUrl + /discover/teams` または `/discover/organizations`）
  3. position 3 = チーム名 / 組織名（item なし＝末端）

`undefined` のフィールドは `JSON.stringify` が自動的に省くため、出力はクリーンになる。

### 4.4 canonical / baseUrl の単一ソース化（重要）

canonical URL とフロントエンドの baseUrl は **`useSeoPublicPage` が唯一の算出元**とする。

- 以前は各ページが独自に `useRuntimeConfig().public.apiBase` からホストを組み立てる一方、`useSeoPublicPage` は `NUXT_PUBLIC_BASE_URL` を優先していたため、当該環境変数を設定するとホストが不整合になる潜在バグがあった。
- これを解消するため、ページ側のローカル `canonicalUrl` 計算と `useRuntimeConfig` 参照を**廃止**し、`useSeoPublicPage` の戻り値 `canonicalUrl` を `useSeoMeta` の `ogUrl` に流用する。JSON-LD は `jsonLd` 関数の引数 `ctx`（`{ canonicalUrl, baseUrl }`）から受け取る。
- 呼び出し順序: **`seoDescription` 定義 → `useSeoPublicPage`（先）→ `useSeoMeta`（後）**。`useSeoMeta` が `useSeoPublicPage` の戻り値に依存するため順序を固定する。
- `useSeoPublicPage` の `jsonLd` は「オブジェクト直渡し」または「`ctx?` を受け取る関数」の union で受ける。既存の引数なし `jsonLd` 関数（users / posts ページ）は追加された optional 引数を無視するだけで動作するため後方互換。

### 4.3 i18n（直書き禁止）

UI / 構造化データに出す文字列はすべて i18n キー経由（CLAUDE.md i18n ルール）。en には英訳、zh / ko / es / de はとりあえず日本語値（後で翻訳）。

### 5.5 FAQ駆動GEO（Phase 2）

> ステータス: 🟡 設計のみ（本節は基盤＝DB・Entity・Repository・enum を先行実装。API / Service / FE は後続フェーズ）

#### 5.5.1 背景：なぜ FAQ が GEO で最重要か

生成 AI（ChatGPT / Perplexity / Google AI Overviews）は、ユーザーの**質問文**に対して「答えそのもの」を生成する。`FAQPage` 構造化データは「**質問（Question）と回答（acceptedAnswer）のペア**」をそのまま機械可読で提供するため、AI にとって最も引用しやすい形式である（質問文がユーザーの検索クエリと一致しやすく、回答文をそのまま要約・引用に転用できる）。

実際、`Organization` / `BreadcrumbList`（Phase 1 で実装済）が「誰が・どこで・何をしている組織か」を示すのに対し、`FAQPage` は「**よくある具体的な疑問への明確な答え**」を提供し、AI 回答への採用率を直接押し上げる。Mannschaft の公開チーム/組織ページにとって、見込み参加者の典型的な疑問（活動内容・場所・参加方法・費用・対象・初心者可否）を構造化して置くことは GEO の費用対効果が最も高い施策である。

#### 5.5.2 方針：カテゴリ別固定質問（7カテゴリ×6問）+ 自由質問

団体の業種・種別はさまざま（スポーツクラブ・クリニック・教室・企業・自治会・マンション管理組合 等）であり、全団体一律の固定6問では「クリニックなのに『活動場所』」のように噛み合わない質問が出る。そこで固定質問を**カテゴリ別**に出し分ける。

- **固定6問（カテゴリ別・編集不可の質問）**: 団体の**カテゴリ**（後述 §5.5.2.1）ごとに、その業種で見込み利用者が必ず知りたい定番質問を 6 問固定で用意し、団体は**回答のみ**を入力する。質問文は編集できない（同カテゴリの全団体で表記が揃い、AI から見て一貫性が高い）。固定質問は全 7 カテゴリ × 6 問 = **42 問**を `FixedFaqQuestion` enum に定義する。

- **自由質問**: 団体が独自に質問文・回答文の両方を入力できる任意の Q&A。固定6問では拾えない団体固有の疑問（例「楽器の貸し出しはあるか」）に対応する。カテゴリに依存しない。

##### 5.5.2.1 FaqCategory（7カテゴリ）と種別→カテゴリ正規化

##### 5.5.2.3 カテゴリ変更時の挙動

団体がカテゴリ（template / orgType）を変更すると、旧カテゴリの固定質問への回答が `public_faqs` に残骸として残る場合がある。**管理 GET・公開 GET いずれも「現カテゴリの固定質問のみ」を返し、旧カテゴリの question_key は出力に含めない**（DB レコードは論理削除せず温存するため、カテゴリを戻せば回答も復活する）。固定質問の回答 PUT も、現カテゴリに属さない question_key は不正キー（`FAQ_002`）として 400 を返す。

#### 5.5.3 義務付けは緩い推奨（公開ブロックなし）

FAQ の入力は**任意**とし、回答が無くても公開ページの表示はブロックしない（参加障壁を上げない方針）。

- **回答済み（answer_text が非空）の項目のみ** `FAQPage` JSON-LD として出力する。未回答の固定質問は JSON-LD に含めない（空回答を AI に拾わせない）。
- FAQ が1件も無い団体は `FAQPage` ノード自体を出力しない（Phase 1 の `Organization` / `BreadcrumbList` はそのまま）。

#### 5.5.4 データモデル（`public_faqs` 1表）

固定質問・自由質問を**1表で管理**し、`question_key` の有無で区別する。

- 固定質問: `question_key` = `FixedFaqQuestion` の enum名（カテゴリ別。例 `SPORTS_ACTIVITY`）／`question_text` = NULL（文言は i18n 描画）
- 自由質問: `question_key` = NULL／`question_text` = 質問文（自由入力）

> テーブル DDL は変更不要。カテゴリ別化に伴い `question_key`（VARCHAR40）に保存される値が増える（`ACTIVITY` 等の旧6値 → `SPORTS_ACTIVITY` 等の42値）だけで、スキーマは不変。

```sql
CREATE TABLE public_faqs (
  id            BINARY(16)      NOT NULL COMMENT 'UUIDv7',
  scope_type    VARCHAR(20)     NOT NULL COMMENT 'TEAM / ORGANIZATION',
  scope_id      BIGINT UNSIGNED NOT NULL COMMENT 'チーム/組織ID（FKなし・アプリ層整合）',
  question_key  VARCHAR(40)     NULL COMMENT '固定質問キー。自由質問はNULL',
  question_text VARCHAR(255)    NULL COMMENT '自由質問の質問文。固定はNULL（i18n描画）',
  answer_text   TEXT            NOT NULL COMMENT '回答本文',
  display_order INT UNSIGNED    NOT NULL DEFAULT 0,
  created_by    BIGINT UNSIGNED NULL COMMENT 'users.id（FKなし・indexのみ）',
  created_at    DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at    DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  deleted_at    DATETIME        NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uq_public_faqs_fixed (scope_type, scope_id, question_key),
  INDEX idx_public_faqs_scope (scope_type, scope_id, deleted_at, display_order),
  INDEX idx_public_faqs_created_by (created_by)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='公開FAQ（チーム/組織）';
```

Flyway: `V70.019__create_public_faqs.sql`。

- `uq_public_faqs_fixed (scope_type, scope_id, question_key)`: 同一スコープ内で同じ固定質問が二重登録されないことを保証（UPSERT のキー）。MySQL では NULL は UNIQUE 制約の重複対象外のため、`question_key` が NULL の自由質問は任意件数登録できる。

**CLAUDE.md アーキテクチャ原則への準拠:**

- **原則6（UUIDv7）**: 新規テーブルのため主キーは `BINARY(16)` の UUIDv7。Entity は `UuidV7Entity` を継承。
- **原則1（クロスドメインFK禁止）**: `created_by`（users.id）は **FK を張らず index のみ**。FAQ ドメインと user ドメインは別ドメインであり、クロスドメインFKを作ると将来の水平シャーディング（シャード分割）が不能になるため。参照整合性はアプリケーション層で保証する。同様に `scope_id`（teams/organizations.id）も FK なし。
- **論理削除**: `deleted_at` による soft delete に対応。

#### 5.5.5 Repository が原則7（テナント基底クラス）非適用の理由

`FaqRepository` は `AbstractTenantAwareRepository` を**継承しない**。原則7のテナント基底クラスは `organization_id` カラムで直接絞り込むテーブル専用だが、FAQ は `scope_type`（TEAM / ORGANIZATION）+ `scope_id` の**複合スコープ**で管理する。チームFAQでは `scope_id` がチームIDになるため `organization_id` 単独では絞り込めず、原則7の意図（`organization_id` をシャードキーとする統一）に合致しない。よって `JpaRepository<FaqEntity, UUID>` を直接継承し、scope ベースのカスタムクエリメソッドを提供する。

#### 5.5.6 API 契約（後続フェーズで実装）

| 種別 | メソッド・パス（案） | 認可 | 用途 |
|---|---|---|---|
| 管理（取得） | `GET /api/v1/{teams\|organizations}/{id}/faqs` | 当該スコープの管理権限 | `category` + 解決カテゴリの固定6問（未回答含む）+ 自由質問を編集画面に表示 |
| 管理（一括更新） | `PUT /api/v1/{teams\|organizations}/{id}/faqs` | 当該スコープの管理権限 | 回答の入力/更新・自由質問の追加/削除・表示順変更（固定質問は回答 UPSERT、自由質問は差分適用）。カテゴリ外の固定 question_key は `FAQ_002`（400） |
| 公開（取得） | `GET /api/v1/public/{teams\|organizations}/{id}/faqs` | `permitAll`（未認証可） | 回答済みのみ返す。FAQPage JSON-LD 構築のソース |

**認可（実装）:** 管理 API（GET/PUT 双方）の per-scope 認可は **`FaqAdminService` 内で `AccessControlService.checkAdminOrAbove(userId, scopeId, scopeType)` により強制**する（SYSTEM_ADMIN は全スコープ短絡許可）。`AdminFaqController` の `@PreAuthorize("hasRole('ADMIN') ...")` は本アプリで `@EnableMethodSecurity` 未有効のため実機では効かず、宣言・防御多重に留まる（hasRole は JWT に ADMIN が乗らず per-scope 判定にもならないため）。これにより他団体管理者による他団体 FAQ の編集・閲覧を遮断する。

管理 GET レスポンス `FaqEditorResponse` は団体のカテゴリ（`category` = `FaqCategory` 名）と、そのカテゴリの固定6問（`fixedQuestions`・displayOrder 昇順・全件、未回答は `answer=null`）、自由質問（`customFaqs`）を返す。

```json
{
  "category": "SPORTS",
  "fixedQuestions": [
    { "questionKey": "SPORTS_ACTIVITY", "displayOrder": 1, "answer": "少年サッカーをしています" },
    { "questionKey": "SPORTS_LOCATION", "displayOrder": 2, "answer": null }
  ],
  "customFaqs": [
    { "id": "0190...uuid", "questionText": "用具の貸し出しはありますか", "answer": "あります", "displayOrder": 0 }
  ]
}
```

公開 GET は **回答済み（answer_text 非空）の項目のみ**を「現カテゴリの固定質問（displayOrder 昇順）→ 自由質問（displayOrder 昇順）」で返す。固定質問は `question_key` を含めて返し、FE 側が i18n で質問文を描画する。自由質問は `question_text` をそのまま返す。現カテゴリに属さない固定 question_key（カテゴリ変更後の残骸）は公開出力に含めない。

#### 5.5.7 FAQPage を `@graph` へ追加する方針

公開ページの JSON-LD（Phase 1 で `@graph`: `Organization` + `BreadcrumbList`）に、回答済み FAQ が1件以上ある場合のみ `FAQPage` ノードを追加する。質問文（`name`）は固定質問なら FE の i18n、自由質問なら `question_text` を用いる。回答文（`acceptedAnswer.text`）は `answer_text`。XSS 対策は Phase 1 同様 `escapeJsonLdForHtml`（§11）を経由して注入する。`@id` は `canonicalUrl + '#faq'`。

#### 5.5.8 検索連携（§5.5-B・後続フェーズ）

回答済み FAQ を `/discover` の検索インデックスに反映し、「初心者歓迎の団体」「費用無料の団体」等で見つけやすくする連携は**後続フェーズ**とする（本節の公開・JSON-LD 出力が先）。

#### 5.5.9 固定質問文言の6言語 i18n

固定42問の質問文は `frontend/app/locales/{ja,en,zh,ko,es,de}/faq.json` に `faq.fixed.{enum名小文字}`（§5.5.2.2 の i18nキー全42。例 `faq.fixed.sports_activity`）として6言語追加する（後続 FE 足軽が担当）。デフォルトロケールは ja。未翻訳言語はとりあえず日本語値で可（CLAUDE.md i18n ルール）。FE は管理 GET の `category` で表示する固定質問群を切り替える。

## 7. 定義文（description）生成ロジック

`seoDescription` computed を各ページに定義し、`useSeoMeta` の description / ogDescription / twitterDescription、`useSeoPublicPage` の description、Organization の description で **共有**（重複定義を避ける）。

優先順位:

1. `philosophy`（理念）が空白でなければそれをそのまま使う。
2. philosophy が無く、`prefecture` または `city` があれば
   → `{prefecture}{city}を拠点に活動する{name}の公開ページです。`（`public.{team,organization}.geoDescription`）
3. philosophy も地理情報も無ければ
   → `{name}の公開ページです。`（`public.{team,organization}.geoDescriptionNoLocation`）

> 補足: 計画では philosophy 無し時に常に geoDescription を使う想定だったが、prefecture / city が両方空だと「を拠点に活動する…」という不自然な文になるため、地理情報ゼロ時専用の `geoDescriptionNoLocation` キーにフォールバックする設計に変更した（§10 変更履歴参照）。

> 注記（meta description の長さ）: `seoDescription` は meta description / OGP / JSON-LD の `description` で共有している。philosophy 全文が長い場合、meta description は検索結果（SERP）で途中切れする可能性がある（JSON-LD の `description` は長文を許容するため問題ない）。Phase 2 で meta description 用の要約生成（先頭 N 文字 or 要約）を検討する。Phase 1 では共有のままとする（事実ベースの短いフォールバック文が大半のため実害は小さい）。

## 11. セキュリティ

### 11.1 JSON-LD の XSS 対策（スクリプトブレイクアウト防止）

JSON-LD は `<script type="application/ld+json">` の中身として HTML に埋め込まれる。`JSON.stringify(ld)` の結果をそのままタグの中身に流し込むと、`philosophy` / `name` / `city` などの**自由入力**に閉じスクリプトタグ文字列（小なり記号 + `/script` + 大なり記号）が混入した場合、HTML パーサが script を閉じてしまい、続く文字列が新しいスクリプトとして実行される（**スクリプトブレイクアウト = XSS**）。

公開ページ（`/public/teams/[id]` / `/public/organizations/[id]`）は**未認証アクセス可**であり、攻撃者が組織名・理念等を細工して任意の閲覧者に対し XSS を成立させられるため、影響が大きい。`unhead` は script の中身（children / innerHTML）を**自動エスケープしない**ため、アプリ側で必ずエスケープする。

**対策**: 純粋関数 `escapeJsonLdForHtml(json: string): string`（`frontend/app/utils/escapeJsonLdForHtml.ts`）で、JSON 文字列中の**小なり記号（U+003C `<`）を `<`（Unicode エスケープ）に置換**してから注入する。

- 小なり記号さえ無効化すれば HTML パーサは `</script>` 等の閉じタグを検出できず、ブレイクアウトを完全に防げる。
- `<` は JSON 文字列リテラルとして妥当なため、結果は引き続き `JSON.parse` 可能で、クローラ / Rich Results Test での構造化データの意味は変わらない。

**一元実施**: `useSeoPublicPage` の JSON-LD 注入で本関数を適用する。加えて、本 composable を経由せず独自に JSON-LD を出力している箇所（`pages/index.vue` の `SoftwareApplication`、`pages/help/qa.vue` の `FAQPage`）にも同関数を適用し、JSON-LD 注入を**一律にエスケープ**する方針とした（現状静的・i18n 由来でも、将来の動的化に備える防御）。

関連: `docs/security/README.md`（A03 インジェクション / XSS 横断方針）。

## 12. 保守の観点

- `teams/[id].vue` と `organizations/[id].vue` は JSON-LD（`@graph`: Organization + BreadcrumbList）の構築ロジックがほぼ同一で**2 箇所に重複**している。現状は許容するが、**同種の公開ページが 3 箇所目に増えた時点で composable（例: `usePublicEntityJsonLd`）への共通化を検討**する。重複が 2 箇所のうちは、共通化による間接化コストの方が大きいと判断した。
