## 0. 本書の読み方 — 事実と提案の区別

本書は TimeTree 比較④「統合カレンダーはあるが UI が薄い」（マスター評）を受け、既存の横断カレンダー
`GET /api/v1/my/calendar` と `/calendar` ページを **実用に耐えるレイヤー型カレンダー** へ引き上げる設計である。

| 記法 | 意味 |
|---|---|
| 【確認済み】 | `origin/main`（= `0a933be1c`, 2026-08-06）の実ファイルを開いて確認した事実。クラス名・パス・行番号は実物と一致する |
| 【提案】 | 本書で新規に提案する設計。実装は未着手 |
| 【御裁可済み】 | マスターが決定済みの事項（本書では変更しない） |
| 【既定】 | 家老が既定値として置く判断。PR レビューで変更可 |

本書の目標は **未決事項ゼロ**（§11）である。

### 0.1 設計原則 — ADHD フレンドリー方針（CMP-005）

本書のすべての設計判断は、以下4原則に従う。個別仕様の根拠として §2 以降から参照する。

| # | 原則 | 本書での具体化 |
|---|---|---|
| **P1** | **ゼロ設定で機能する既定** | 色設定を一度もしなくてもレイヤーごとに色が分かれる（スコープキーからの決定的ハッシュ自動色・§3.3）。設定は「気に入らなければ変える」ための上書きに過ぎない |
| **P2** | **意図しない状態変化の排除** | 作成スコープ Select を触ると表示フィルタが勝手に書き換わる現行挙動を廃止（§2.2 (d)・§5.4）。ユーザーが明示的に操作した対象だけが変わる |
| **P3** | **黙って消える情報の排除** | 4件目以降が無言で切り捨てられる現行を廃し「+N件」を必ず出す（§6.2）。複数日バーの MAX_LANES 超も同様に件数として可視化する |
| **P4** | **状態の一貫性** | ダッシュボードウィジェットと `/calendar` でフィルタ状態が分裂している現行を統一（§5.3）。同じ「レイヤーの見え方」がアプリ全体で一つ |
| **P5** | **入力摩擦の削減** | 予定を入れるのに日付と時刻を**手で入力させない**。バーチカル週ビューの時間グリッドを**なぞるだけ**で開始・終了時刻が決まる（§6.6）。ADHD 傾向のユーザーにとって「フォームの空欄を埋める」工程そのものが着手の障壁であり、**見えている枠を指でなぞる**という身体的な操作へ置き換えることで、予定入力の開始コストをほぼゼロにする |

## 1. 概要・背景

### 1.1 TimeTree 比較で見えた課題

TimeTree の中核体験は「**カレンダーを複数持ち、色で束ねて1面に重ねる**」ことにある。Mannschaft は
**統合の実体（API）は既に持っているが、UI がそれを見せていない**。マスター評「統合カレンダーはあるが UI が薄い」の内訳は以下。

| # | 現状【確認済み】 | 何が薄いか |
|---|---|---|
| 1 | フィルタの選択肢は **取得済みイベントから動的抽出**（`useMyCalendarData.ts` `availableScopes`。`extendedEvents` を走査して `scopeType:scopeId` を集める） | 予定が0件のチーム・組織は選択肢に**現れない**。月を移動すると選択肢が増減し、順序も取得順まかせで不安定。「レイヤーが並んでいる」感覚が成立しない |
| 2 | 共有イベントの色が **`color: null` 固定**（`useMyCalendarData.ts` の `sharedEvents` マッピング。`color: null,` とハードコード） | 全チーム・全組織の予定が同一色で描かれる。どのレイヤーの予定か色で判別できない。なお BE 側は `ScheduleEntity.color`（:140）と `ScheduleEventCategoryEntity.color`（:32, 既定 `#3B82F6`）を**既に持っている**が、`CalendarEntryResponse` に色フィールドが無いため API 境界で落ちている |
| 3 | 単日イベントは **先頭3件で `slice(0, 3)` 切り捨て**（`CalendarGrid.vue:245`）、複数日バーは **`MAX_LANES = 3`**（:43）超が `filter(s => s.lane < MAX_LANES)`（:276）で**無言非描画** | 4件目以降が存在の痕跡すら残さず消える。予定の見落としが構造的に発生する（P3 違反） |
| 4 | `/calendar` は **月表示のみ**（`pages/calendar.vue`） | 「今週何があるか」「今日この後何があるか」に答えられない。TimeTree の週/日/リストに相当するものが無い |
| 5 | **「今日」ボタンが無い**（`pages/calendar.vue` に `today` 相当の実装なし【確認済み】） | 数か月先を見た後、今月へ戻る手段が矢印連打しかない |
| 6 | スコープ切替が **全画面スピナー**（`withScopeLoading()` `pages/calendar.vue:318-325`。`calendarLoading=true` → `nextTick` → `setTimeout(0)` → フィルタ適用 → `false`） | 実体は**クライアント側フィルタのみ**で通信は発生しない。存在しない待ちを演出しているだけで、体感が重い |
| 7 | 作成スコープ Select の変更が **表示フィルタを強制上書き**（`pages/calendar.vue:227-234`。`watch(createScopeKey, ...)` が `selectedScopes` を `[PERSONAL_KEY]` ないし `[PERSONAL_KEY, key]` に置換） | 「予定を作る先を選んだ」だけで「今見ている面」が崩れる。P2 違反の典型 |
| 8 | モバイルのリストビューは **`teams/[slug]/schedule.vue` にしか存在しない**（`md:hidden` ブロック :105-。`ScheduleListRow.vue` は既に独立コンポーネント化済み） | 統合カレンダー `/calendar` はスマホでも月グリッドのままで、狭幅では時刻もタイトルも読めない |
| 9 | フィルタ永続化キーが **2系統に分裂**【確認済み】: `/calendar` は `mannschaft:calendar:scopeFilter`（`useMyCalendarData.ts` の既定 `SCOPE_FILTER_KEY`）、ダッシュボードウィジェットは `mannschaft:widget:calendar:scopeFilter`（`WidgetMyCalendar.vue:42` が `storageKey` で上書き） | 同じユーザーの同じレイヤー選択が2箇所で食い違う（P4 違反） |

### 1.2 既に持っているもの（土台）【確認済み】

本書は**ゼロから作らない**。以下は実装済みで、本書はこの上に UI レイヤーを積む。

| 資産 | 実体 | 役割 |

### 1.2b 予定を「入れる」側の摩擦【確認済み】

閲覧側だけでなく**入力側**にも薄さがある。現行の予定作成は以下の一本道しかない。

- `/calendar` の月グリッドで日付セルをクリック → `onDateClick(date)`（`pages/calendar.vue:89-95`）が `selectedDate` に**日付文字列のみ**を入れて `ScheduleEventForm` を開く。
- `ScheduleEventForm` の props は `initialDate?: string`（`ScheduleEventForm.vue:17`）で、受け取った日付を `form.startDate` / `form.endDate` の**両方に同じ Date として代入**する（:294-297）。**時刻は一切プリセットされない。**
- 結果、ユーザーは毎回ダイアログ内で開始時刻と終了時刻を手入力（ピッカー操作）する。

TimeTree では**バーチカル週ビュー上のドラッグ作成がプレミアム機能相当**として提供されており、ここは比較上の明確な差である。かつ、時刻の手入力は ADHD 傾向のユーザーにとって着手の障壁そのものである（P5）。本書は **(e) バーチカル週ビュー** と **(h) グリッド選択作成** を対にして、この摩擦を根から取り除くことを目玉と位置づける。

### 1.3 本書のゴール

**レイヤー（＝所属スコープ）が、予定の有無に関わらず常にそこに在り、色で識別でき、任意に重ね外しでき、月／週／リストの3面から同じ状態で見える。**
**そして、週ビューの空いている時間帯をなぞれば、時刻を一文字も打たずに予定が入る。**

## 3. DB 設計

### 3.1 新テーブル `user_calendar_layer_settings`【提案】

ユーザー×レイヤー（`scope_type` + `scope_id`）の表示設定を保持する。現時点で保持するのは色と表示可否のみ。

**設計判断**:

- **主キーは UUIDv7**（CLAUDE.md アーキテクチャ思想 原則6）。`UuidV7Entity`（`common/entity/UuidV7Entity.java`）を継承する【確認済み・存在する】。`id` は `BINARY(16)`。
- **クロスドメイン FK は張らない**（原則1）。`user_id` / `scope_id` はいずれも論理参照でインデックスのみ。schedule ドメインから user / team / organization ドメインへの FK を作らない。
- **`scope_id` は多型参照**。`scope_type = 'PERSONAL'` の行は `scope_id = 0`（センチネル）とし、NULL 混在によるユニーク制約の破綻を避ける（`notification_fanout_jobs` の `scope_ref` VARCHAR 一本化と同趣旨の判断）。チーム／組織はいずれも `BIGINT` 主キーであるため VARCHAR 化は不要。
- **論理削除は持たない**。設定行は「削除＝自動色に戻す」であり、ユーザーの意思そのもの。物理削除でよい（原則3 の対象はコアエンティティであり、本表は該当しない）。
- **テナント列は持たない**。ユーザーの個人設定であり組織を跨る（所属組織Aと組織Bの色を同一ユーザーが持つ）ため、`AbstractTenantAwareRepository`（原則7）の適用対象外。
- **照合順序は親と同じ `utf8mb4_unicode_ci`**。


### 3.2 Flyway 採番・rollback 方針

- ファイル名: `V{major}.{yyyyMMddHHmmss}__create_user_calendar_layer_settings.sql`
- **major はマージ時に `origin/main` 全体の最大 major + 1 で確定する**。本書執筆時点（2026-08-06 / `0a933be1c`）の最大 major は **175**【確認済み】であり、素朴には 176 だが、**並行 PR が着地すると陳腐化するため、実装時に `git ls-files` で再測して確定すること**（CLAUDE.md Git 運用ルール §Flyway 採番）。
- minor は**タイムスタンプ必須**（連番禁止。`FlywayTimestampNamingGuardTest` が拒否する）。採番は `date -u '+%Y%m%d%H%M%S'`。
- **rollback 方針**: 本マイグレーションは**新規テーブル作成のみで既存テーブルへの ALTER を含まない**ため、ロールバックは `DROP TABLE user_calendar_layer_settings;` で完結し、既存データへの影響はゼロ。アプリ側も「設定行が無い＝自動色」で正常動作する（P1）ため、**テーブルが消えても機能は劣化するだけで壊れない**。この性質を保つため、`user_calendar_layer_settings` を **NOT NULL 前提で参照するコードを書かないこと**（AC-15 で検証）。

### 3.3 自動色（決定的ハッシュ）— P1 の中核【提案】

設定行が無いレイヤーには、**スコープキーから決定的に導出した色**を割り当てる。

- **入力キー**: `"{scopeType}:{scopeId}"`（例 `"TEAM:42"`）。`PERSONAL` は `"PERSONAL:0"`。
- **アルゴリズム【既定】**: キーの UTF-8 バイト列に対する 32bit FNV-1a ハッシュ → `hash % PALETTE.length` でパレットから1色選ぶ。
- **パレット【既定】**: ライト／ダーク双方で白文字が読める彩度・明度に揃えた 12 色固定配列。個人予定の既定色 `#22C55E`（`useMyCalendarData.ts` の personal fallback と一致）とリフレクションの `#F59E0B` / `#6366F1` は**パレットから除外**し、意味を持つ色との衝突を避ける。
- **算出場所**: **BE と FE の両方で同じ関数を実装する**のではなく、**BE の `/my/calendar` 応答と `/me/calendar-layers` 応答に解決済みの色を載せる**（§4）。FE 側にハッシュ実装を持たない。これにより「グリッドとレイヤー一覧で色が違う」事故を構造的に排除する。
- **決定性の要件**: 同じ `scopeType:scopeId` は**いつ・どのユーザーが見ても同じ自動色**になる（AC-06）。ユーザーIDは入力に含めない（含めると同じチームがユーザーごとに違う色になり、スクリーンショット共有時に会話が噛み合わない）。

### 3.4 色の優先順位【提案】

1つの予定がどの色で描かれるかは、以下の優先順位で決まる。**上ほど強い。**

| 優先 | 由来 | 出所 | 意図 |
|---|---|---|---|
| 1 | **ユーザーのレイヤー色設定** | `user_calendar_layer_settings.color` | 「このチームは赤で見たい」というユーザーの明示的意思が最優先 |
| 2 | **予定自身の色** | `schedules.color`（`ScheduleEntity#color` :140）【確認済み】 | 予定作成者が個別に付けた色 |
| 3 | **カテゴリ色** | `schedule_event_categories.color`（`ScheduleEventCategoryEntity#color` :32、既定 `#3B82F6`）【確認済み】 | チームが定義した行事カテゴリの色 |
| 4 | **自動色** | §3.3 のハッシュ | 何も設定していなくても色が分かれる（P1） |

> **設計上の注意**: 優先1（レイヤー色）が優先2（予定色）より強いのは意図的である。レイヤーで色分けする体験を選んだ以上、「レイヤーを赤にしたのに一部の予定だけ青い」は一貫性を壊す。ただし**優先1が設定されていないレイヤーでは 2→3→4 が効く**ため、既存の予定色・カテゴリ色の投資は無駄にならない。

## 4. API 契約

### 4.1 共通

- ベースパス `/api/v1`、応答は既存 `ApiResponse<T>` ラッパー（`{ "data": ... }`）。
- 日時は `LocalDateTime`（既存 `/my/calendar` の `from`/`to` と同形式）。
- **本人限定 API は `/me/` 配下に置き、パスに `userId` を含めない**。ユーザー識別は `SecurityUtils.getCurrentUserId()` 固定とする（`docs/security/README.md` の IDOR 防止方針。パスに他人の ID を書ける形にしない＝到達不能にする）。
- 新規エンドポイントは **ArchUnit の認可番人と `addFilters=false` の契約 IT の両方**に登録すること（§9 AC-16）。

### 4.2 レイヤー一覧の取得 — 既存 API を使う【確認済み・新 API 不要】

タスク指示の「所属スコープ一覧を返す既存 API の有無を実コードで確認」に対する結論:

**既存 API で賄える。新規の「所属一覧 API」は作らない。**

| API | 実体 | 返すもの |
|---|---|---|
| `GET /api/v1/me/teams` | `MyTeamResponse`（`role/dto/MyTeamResponse.java`）【確認済み】。FE は `useTeamStore#fetchMyTeams`（:27-40）が既に呼んでいる | 自分の所属チーム一覧 |
| `GET /api/v1/me/organizations` | `MyOrganizationResponse`（`role/dto/MyOrganizationResponse.java`）【確認済み】。FE は `useOrganizationStore`（:31）が既に呼んでいる | 自分の所属組織一覧 |

ただし **FE が「レイヤー一覧」を組み立てるのに 3 回叩く（teams / organizations / layer-settings）のは無駄**であり、かつ「所属はあるが色設定が無い」レイヤーの自動色を FE 側で算出させることになり §3.3 の方針（BE が解決済みの色を返す）に反する。そこで **合成ビュー API を1本置く**。

### 4.3 `GET /api/v1/me/calendar-layers` — レイヤー一覧（合成ビュー）【提案】

**所属スコープ一覧 ＋ 解決済み色 ＋ 表示可否** を1レスポンスで返す。(a)(b)(g) の土台。

- **認可**: 認証必須。返るのは常に**呼び出し本人の所属のみ**（`/me/teams` `/me/organizations` と同じ可視性。他人の所属は一切露出しない）。クエリパラメータで対象ユーザーを指定する口は**設けない**。
- **副作用なし**（GET）。設定行が無いレイヤーも `color` に自動色が入って返る（P1）。
- **並び順は安定**（AC-04）: `PERSONAL` → `ORGANIZATION`（`sortOrder` 昇順 NULLS LAST → `scopeId` 昇順）→ `TEAM`（同）。**予定の有無に依存しない**。

```jsonc
// 200 OK
{
  "data": [
    {
      "scopeType": "PERSONAL",     // string, non-null, "PERSONAL"|"TEAM"|"ORGANIZATION"
      "scopeId": null,             // number|null — PERSONAL は null（DB のセンチネル 0 は API 境界で null に正規化）
      "scopeName": "個人",          // string, non-null — PERSONAL はサーバー側の表示名ではなくキーを返し FE が i18n する（§8 参照）

      "scopeIconUrl": null,        // string|null
      "color": "#22C55E",          // string, non-null — 常に #RRGGBB（解決済み。§3.4 の優先1 or 4）
      "colorSource": "AUTO",       // string, non-null, "USER"|"AUTO" — ユーザー設定由来か自動色か
      "hidden": false,             // boolean, non-null — 既定で非表示にするか
      "sortOrder": null            // number|null
    },
    {
      "scopeType": "TEAM",
      "scopeId": 42,
      "scopeName": "青葉FC",
      "scopeNameKey": null,
```

### 4.4 `PUT /api/v1/me/calendar-layers/{scopeType}/{scopeId}` — 色設定の upsert【提案】

- **認可**: 認証必須・本人のみ。**`scopeType`/`scopeId` が呼び出し本人の所属レイヤーであることを検証**する（所属していないチームの設定行を作らせない。ゴミ行の防止＋「どのチームIDが存在するか」の探索を許さない）。非所属なら `SCHEDULE_101`（403）。
- **冪等**: 同一キーの再呼び出しは上書き。`uk_user_calendar_layer` に対する upsert。
- `PUT` を選ぶ理由: リソースは `(user, scopeType, scopeId)` で一意に定まり、クライアントが URL を決められる。POST + 採番は不要。

```jsonc
// リクエスト
{
  "color": "#EF4444",  // string|null — null で「自動色に戻す」（行は残り colorSource=AUTO になる）
  "hidden": false      // boolean|null — null は「変更しない」ではなく「既定 false を適用」。部分更新は行わない（PUT の意味論を守る）
}

// 200 OK — 更新後のレイヤー1件（§4.3 と同一スキーマ）
{ "data": { "scopeType": "TEAM", "scopeId": 42, "scopeName": "青葉FC", "scopeNameKey": null,
            "scopeIconUrl": "https://.../signed", "color": "#EF4444", "colorSource": "USER",
            "hidden": false, "sortOrder": null } }
```

**バリデーション**:

| 対象 | 規則 | 違反時 |
|---|---|---|
| `color` | `^#[0-9A-Fa-f]{6}$` または `null`。保存時は**大文字へ正規化**（`#ef4444` → `#EF4444`。比較・重複判定を安定させる） | `SCHEDULE_102`（422） |
| `scopeType` | `PERSONAL` / `TEAM` / `ORGANIZATION` のいずれか | `SCHEDULE_103`（422） |
| `scopeId` | `TEAM`/`ORGANIZATION` は必須かつ正の整数。`PERSONAL` はパス上 `0` 固定（それ以外は 422） | `SCHEDULE_103`（422） |
| 所属 | 呼び出し本人が当該スコープに所属していること | `SCHEDULE_101`（403） |

### 4.5 `DELETE /api/v1/me/calendar-layers/{scopeType}/{scopeId}` — 設定の削除（自動色へ戻す）【提案】

- 設定行を物理削除する。以後そのレイヤーは自動色・`hidden=false` に戻る。
- **冪等**: 行が存在しなくても `204 No Content`（「設定が無い状態にする」という要求は既に満たされている）。404 は返さない。

## 5. 状態・データフロー（FE）

### 5.1 レイヤー状態の単一の出所

現行はイベントから逆算していた選択肢を、**レイヤー一覧 API を単一の出所**に切り替える。

```
GET /me/calendar-layers ──▶ layers: LayerView[]   （レイヤーの「実体」。予定0件でも存在する）
                                   │
                                   ├─ 色マップ  Map<"TYPE:ID", color>  ──┐
                                   └─ フィルタ選択肢（順序安定）          │
                                                                        ▼
GET /my/calendar (+ 個人 + TODO) ─▶ events: CalEvent[] ──── filteredEvents（クライアント側フィルタ・通信なし）
                                                                        │
                                              月グリッド / 週グリッド / アジェンダ（同じ配列を描く）
```

**要点**:

1. `layers` と `events` は**独立に取得**する。`layers` は月移動で再取得しない（所属は月に依存しない）。これにより「月を移動すると選択肢が変わる」現行の欠陥（§1.1 #1）が構造的に消える（AC-03）。
2. `events` 側の色は **API が既に解決済みの `content.color` を使う**（§4.6）。FE でハッシュを計算しない。ただし `layers` 由来の色マップは**凡例とフィルタチップの描画にのみ**使う（同じ BE 解決値なので必ず一致する）。
3. フィルタは**純粋なクライアント側の絞り込み**。ゆえに **(c) スピナー廃止**が成立する（§5.4）。
4. **グリッド選択作成（(h)）は既存の作成フローに合流する**。週ビューが `rangeSelect` を emit → `pages/calendar.vue` が `selectedStartAt`/`selectedEndAt` をセット → `ScheduleEventForm` が開く → 保存で既存の `@saved="refresh"`【確認済み・`pages/calendar.vue:577`】が走り `events` が再取得される。**新しいデータ経路を1本も増やさない**（§6.6.5）。

### 5.2 `useMyCalendarData` の変更点

| 現行【確認済み】 | 変更後【提案】 |
|---|---|
| `availableScopes` = `extendedEvents` を走査して抽出 | `availableScopes` = レイヤー一覧 API の結果（`hidden` なレイヤーも**選択肢には出す**。初期選択から外れるだけ＝P3） |
| `allScopeOptions` が `label: '個人'` を日本語直書き | `scopeNameKey` があれば `$t()`、無ければ `scopeName` をそのまま使う（§8） |
| `sharedEvents` が `color: null` 固定 | `color: e.content?.color ?? null` — API 由来の解決済み色を使う。`?? null` のフォールバックは**残す**（BE 未デプロイ時に描画が壊れないため。ただし null 時の見た目は現行と同じ単色にフォールバックし、握りつぶしではなく明示的な劣化とする） |
| `watch(allScopeOptions, ...)` で「初回のみ全選択」 | 初期選択は `layers` の `hidden=false` なもの全部（§5.3 の移行を経た後） |

### 5.3 localStorage スキーマと移行【(g)】

**新キー（統一）**: `mannschaft:calendar:layerState`

**移行手順**（初回読み込み時に1度だけ実行）:

| 3 | それも無ければ旧キー `mannschaft:widget:calendar:scopeFilter`（ウィジェット側）を読む |
| 4 | どちらか読めたら `{ version: 2, selected: <旧配列>, view: "month" }` として新キーへ書き、**旧キーは削除する**（両系統が残って再分裂するのを防ぐ） |
| 5 | どれも無ければ「`hidden=false` のレイヤーを全選択」で初期化（P1: 初回起動でも全部見える） |

**ウィジェット（`WidgetMyCalendar.vue`）は `storageKey` 上書きを廃止**し、既定キーを使う。これで `/calendar` とウィジェットのレイヤー選択が常に一致する（P4・AC-13）。

> **注**: `view` はウィジェットには適用しない（ウィジェットは常に月グリッドの縮約）。ウィジェットは `selected` のみを読む。

### 5.4 作成スコープと表示フィルタの分離【(d)】

**現行**（`pages/calendar.vue:227-234`）【確認済み】:

```ts
watch(createScopeKey, (key) => {
  withScopeLoading(() => {
    if (key === 'personal') { selectedScopes.value = [PERSONAL_KEY] }
    else { selectedScopes.value = [PERSONAL_KEY, key] }
  })
  ...
})
```

**変更後**【提案】:

- **`selectedScopes` への代入を削除する。** 作成スコープの変更は、作成フォームの初期スコープにのみ影響する。
- ガントビューのキャッシュ破棄（`ganttCache.clear()` 以下）は**残す**。これは表示フィルタではなくデータ取得対象の変更であり、正当な副作用である。
- **表示フィルタが空（全レイヤー非選択）のまま予定を作成しても、作成した予定が見えない**という状況が起こりうる。これに対しては**「作成したレイヤーが非表示です」の一行案内＋そのレイヤーを表示にするボタン**を作成完了時に出す（P2 を守りつつ P3 の「黙って消える」も避ける・AC-11）。勝手にフィルタを書き換えない点が現行との本質的な違い。

### 5.5 スピナー廃止【(c)】

`withScopeLoading()`（`pages/calendar.vue:318-325`）を**削除**し、`onToggleScope` / `onMultiSelectChange` は `toggleScope(value)` / `selectedScopes.value = vals` を**同期的に呼ぶだけ**にする。

- 根拠: フィルタ適用は `filteredEvents` の `computed` 再評価のみで、**ネットワーク I/O は一切発生しない**【確認済み・`useMyCalendarData.ts` の `filteredEvents`】。`calendarLoading` を立てて `setTimeout(0)` を挟む現行は、存在しない待ちを演出しているだけ。
- `calendarLoading` 自体は**月移動時のデータ取得には引き続き使う**（そちらは本物の通信）。廃止するのはフィルタ操作経路のみ。

#### 6.5.2 重なりの解決（横並び分割）

同じ日の時間帯が重なる予定は、**列を等分して横に並べる**。

1. その日の時刻付き予定を開始時刻昇順に整列する。
2. 時間的に重なる予定同士を**クラスタ**（推移的に重なりが繋がる集合）にまとめる。
3. クラスタ内で**同時に重なっている最大本数 = `width` の分母**とし、各予定に空いている最小の列インデックスを割り当てる。
4. 描画幅 = `列幅 / 分母`、左オフセット = `列幅 × 列インデックス / 分母`。

- **上限は設けない**（月ビューの `MAX_LANES` に相当する切り捨てを持ち込まない）。10 本重なれば 1/10 幅になり文字は読めないが、**存在は必ず見える**（P3）。読めない場合はタップして詳細を開く導線がある。
- **極短時間の予定**（15分未満など）は、計算上の高さが 12px を下回っても **最低高さ 20px を確保**する。潰れて消えるのを防ぐ（P3）。この場合わずかに下へはみ出すが、重なり計算は実時刻ベースのまま行う。
- 各予定バーの背景色は §3.4 で解決済みの `content.color`。左端に濃いめの縦アクセント線を置き、淡い背景でも所属レイヤーが判別できるようにする。

#### 6.5.3 ナビゲーションと状態

- 週の起点は**日曜**（月ビュー `daysOfWeek = ['日','月',...]`【確認済み】と揃える）。
- `◀ ▶` で前週・翌週。`今日` ボタン（§6.3）で今週へ。
- **月/週/アジェンダの切替でレイヤー選択は保持される**（§5.1・AC-13）。週ビューは `filteredEvents` を日付で束ね直すだけで、再取得しない。
- 週の表示範囲が月をまたぐ場合、`useCalendarEvents` の取得範囲は**表示中の週を包含する月**を必ず含むように拡張する（またいだ側の予定が空になるのを防ぐ）。

### 6.6 グリッド選択による予定作成【(h)・御裁可済み・本書の目玉】

**バーチカル週ビューの時間グリッドをなぞると、その範囲の開始・終了時刻がプリセットされた作成ダイアログが開く。** P5（入力摩擦の削減）の中核であり、TimeTree のプレミアム機能相当にあたる。

#### 6.6.1 一連の流れ

| 段 | PC（マウス） | モバイル／タッチ |
|---|---|---|
| **開始** | 時間グリッドの空き領域で `pointerdown` | 時間グリッドの空き領域を **500ms 長押し**（§6.6.4） |
| **選択中** | ドラッグに追従して**半透明のハイライト矩形**を描き、矩形内に**「9:00 – 10:30」の時刻ラベル**をリアルタイム表示（§6.6.3） | 同左。長押し成立時に**触覚フィードバック**（`navigator.vibrate?.(10)`・非対応環境では何も起きない） |
| **確定** | `pointerup` | `touchend` |
| **ダイアログ** | 既存 `ScheduleEventForm` が**開始日時・終了日時をプリセットされた状態で**開く（§6.6.5） | 同左 |
| **保存後** | `@saved="refresh"` で再取得し、**作成した予定が今いる週ビュー上のなぞった位置にそのまま現れる**（AC-21） | 同左 |
| **キャンセル** | ダイアログを閉じるとハイライトは消える。カレンダーの状態は選択前と完全に同一に戻る | 同左 |

#### 6.6.2 「選択の開始」と見なす条件

以下の**いずれかに該当する場合は選択を開始しない**（誤爆防止）。

| 条件 | 理由 |
|---|---|
| ドラッグが**既存の予定バーの上**で開始された | その予定を開きたいのか新規作成なのか判別できない。予定バー上の操作は従来どおり `eventClick`。**将来のドラッグ移動・リサイズはここに差し込む**（§2.3） |
| ドラッグが**終日帯**の上で開始された | 終日帯は時刻を持たない。終日予定の作成は日付セルクリック（既存導線）で行う |
| ドラッグが**時刻ラベル列**の上で開始された | スクロール操作と衝突する |
| 移動距離が **閾値未満**（PC: 4px 未満、モバイル: 長押し不成立） | 単なるクリック／タップ。この場合は**その位置の時刻から既定 60 分**の予定として扱い、ダイアログを開く（クリック1発でも作れる。P5） |
| **月ビュー／アジェンダビューを表示中** | **ドラッグ選択は週ビュー限定**。月ビューの日付セルのドラッグは何も起こさない（従来どおりクリックで `onDateClick`）。アジェンダは一次元リストであり時間軸を持たないため対象外。誤って別ビューにジェスチャを実装しないこと（AC-22b で検証） |

#### 6.6.3 ビジュアルフィードバックとスナップ

- **ハイライト矩形**: 選択中の時間帯を、そのとき選択されている**作成スコープのレイヤー色**（§6.6.6）の半透明（`opacity: 0.35`）＋破線枠で描く。「これから何色の予定がここに入るか」が選択中に分かる。
- **時刻ラベル**: 矩形の中央に `9:00 – 10:30` を常時表示。ドラッグに追従して更新する。**これが「時刻を手入力しない」ことの視覚的な保証**であり、ユーザーは数字を確認しながら指を離せる。
- **スナップ単位**【御裁可事項の具体化・既定】:

| 表示密度 | スナップ | 理由 |
|---|---|---|
| 既定（1時間 = 48px） | **15分**（= 12px） | 12px は指でも十分に狙える最小単位。15分刻みは実用上ほぼすべての予定を表現できる |
| 将来ズームアウトを入れた場合（1時間 < 32px） | **30分** | 物理ピクセルが 15分あたり 8px を切ると狙えない。密度に応じて粗くする |

- スナップは**開始・終了の両端に独立して適用**する。丸めは**最も近い境界へ**（`Math.round`）。切り捨てにすると 9:59 から下へなぞったとき 9:45 開始になり直感に反する。
- **最小選択長は 15分**。上へ逆方向にドラッグした場合は開始と終了を入れ替えて正の範囲にする（`start > end` を作らない）。逆方向に 0 まで戻したら最小 15分を維持する。
- **日をまたぐ選択はしない**。ドラッグが横方向に別の列へ移っても、**選択は開始した列（＝日）に固定**する。週ビューで斜めに引いて 3 日間の予定が生まれるのは事故であり、複数日予定は終日帯／既存フォームから作る。
- 上端・下端を越えるドラッグでは**時間グリッドを自動スクロール**する（端から 40px 以内で毎フレーム 8px）。24:00 を超えたら 24:00 で止める。

#### 6.6.4 モバイル: スクロールとドラッグの競合回避

時間グリッドは縦にスクロールする。**タッチ開始を即座に選択と解釈すると、縦スクロールが一切できなくなる。** これを避けるため：

1. `touchstart` の時点では**何もしない**。`preventDefault()` も呼ばない（＝ブラウザの慣性スクロールは生きたまま）。
2. **500ms** のタイマーを張る。この間に **10px 以上の移動** または `touchend` が起きたら**タイマーを破棄**し、通常のスクロール／タップとして扱う。
3. 500ms 経過して指が留まっていたら**長押し成立**。この瞬間に触覚フィードバックを出し、ハイライトを表示し、以降の `touchmove` で `preventDefault()` を呼んでスクロールを止め、選択モードへ入る。
4. 選択モード中はコンテナに `touch-action: none` を当てる（成立前は当てない。ここを常時 `none` にするとスクロールが死ぬ）。
5. `touchcancel`（着信・システムジェスチャ等）では**選択を破棄**する。中途半端な時刻でダイアログを開かない。

> **設計上の要点**: 「長押しで初めて選択が始まる」ため、**モバイルではスクロールが常に最優先**である。ユーザーが週を眺めている限り誤って予定作成が始まることはない（P2）。

#### 6.6.5 既存作成ダイアログとの整合

現行の `ScheduleEventForm` は **`initialDate?: string`（日付のみ）** を受け取り、`form.startDate` と `form.endDate` の両方に同じ `Date` を入れる（:294-297）【確認済み】。時刻をプリセットする口が無い。

**変更方針**【提案】:

- `ScheduleEventForm` に **`initialStartAt?: string` / `initialEndAt?: string`**（いずれも ISO 8601・ユーザー TZ のオフセット付き）を追加する。
- 適用の優先順位: **`initialStartAt`/`initialEndAt` があればそれを使い、無ければ従来どおり `initialDate` を使う**。`initialDate` の既存挙動は一切変更しない（月ビューの日付クリック導線＝現行の唯一の作成経路が壊れないこと。AC-22c）。
- 時刻の解釈は**必ずユーザー TZ 基準**とする。ピッカーが扱う `Date` は「瞬間」ではなく「壁時計」であり、`tz()` で投影し直すと日がずれる既知の罠があるため、`localDate.ts` の既存原則に従って組み立てる。ナイーブ文字列の連結はしない。
- `pages/calendar.vue` 側は `selectedDate` に加えて `selectedStartAt` / `selectedEndAt` を持ち、週ビューの `@rangeSelect` を受けてセットしてから `showCreateDialog = true` にする。**日付クリック経路（`onDateClick`）では `selectedStartAt`/`selectedEndAt` を `undefined` にリセットする**（前回のドラッグ値が残って日付クリックに時刻が付く事故を防ぐ）。
- `CalendarWeekGrid.vue` の emit に `rangeSelect: [startAt: string, endAt: string]` を追加する。**コンポーネント自身はダイアログを知らない**（既存 `dateClick` / `eventClick` と同じく、親が組み立てる責務分離を保つ）。

#### 6.6.6 作成スコープの既定値 —(d) との整合

ドラッグで開いたダイアログの**作成先スコープは、画面上部の作成スコープ Select の現在値をそのまま使う**（`selectedCreateScope`【確認済み・`pages/calendar.vue:223`】）。これは既存の「＋予定追加」ボタン経由と完全に同じ挙動であり、導線によって作成先が変わることはない。

- **表示フィルタ（`selectedScopes`）は参照しない。** (d) の裁定（§5.4）どおり、作成スコープと表示フィルタは独立である。「今そのレイヤーだけ表示しているから、そこに作る」といった**推測を一切しない**（P2）。
- ハイライト矩形の色は**作成スコープのレイヤー色**（§3.4 の優先1 or 4 で解決済みの値）を使う。これは「どこに作られるか」の予告であって、表示フィルタとは無関係。
- 作成先レイヤーが表示フィルタで非表示の場合、保存後に §5.4 の「作成先のレイヤーが非表示です／表示する」案内が出る（AC-11b と同じ経路）。**ここでも勝手にフィルタを書き換えない。**

| 観点 | 見積り |
|---|---|
| 1ユーザーあたりの行数 | 所属チーム数＋所属組織数＋1（PERSONAL）**を上限とし、かつ色を変更したものだけ**。実際には大半のユーザーが 0〜数行（P1 により設定しなくても機能するため） |
| 1000万ユーザー時の最大行数 | 仮に平均5レイヤー × 20% のユーザーが色を設定 → 約 1000万行。**単一テーブルで問題ない規模**（`notifications` 等と比べて桁が2つ小さい） |
| 主クエリ | `SELECT * FROM user_calendar_layer_settings WHERE user_id = ?` — `idx_user_calendar_layer_user` で数行を引く。`/my/calendar` あたり **1回**（§4.7） |
| 書き込み | ユーザーが色を変えたときのみ。書き込み頻度は極めて低い |
| キャッシュ | **導入しない**。1ユーザー数行の主キー引きにキャッシュを噛ませる利益は薄く、色変更直後に反映されない不整合（P2 違反）の方が害が大きい |

### 10.2 レスポンスサイズ

`/my/calendar` へ `content` に3フィールド（`color` 7文字 / `colorSource` 最大12文字 / `categoryColor` 7文字 or null）を追加する。1エントリあたり約 60 バイト増。1か月分 300 件で約 18KB 増。**gzip 後は色文字列の重複が高圧縮されるため実質的な増加は僅少。** 許容する。

### 10.3 後方互換・段階リリース

| 段階 | 内容 | この時点で壊れないこと |
|---|---|---|
| **Wave 1** | Flyway + Entity + レイヤー API 3本 + `/my/calendar` の色フィールド追加 | FE は新フィールドを読まないため**現行 UI は無変更で動く**（追加のみ＝AC-18） |
| **Wave 2** | FE のレイヤー実体化・色反映・localStorage 移行 | BE が Wave 1 で先行デプロイ済み。仮に BE が古くても `content.color` が `undefined` になるだけで、`?? null` フォールバックで現行の単色描画に劣化する（§5.2） |
| **Wave 3** | バーチカル週／アジェンダビュー・グリッド選択作成・モバイル共通化 | 既定ビューは `month` のままなので、新ビューに不具合があっても既存の月ビュー体験は無傷。**グリッド選択作成は週ビュー内に閉じており**（§6.6.2）、月ビューの日付クリック作成経路には一切触れない（AC-22c）ため、既存の唯一の作成導線が壊れるリスクを構造的に断っている |

**旧 localStorage キーからの移行**は §5.3 のとおり Wave 2 で1度だけ実行し、**旧キーを削除**する。移行に失敗した場合（JSON パース不能等）は「全レイヤー選択」へフォールバックする — ここは**エラー握りつぶしではなく意図した劣化**であり、「全部見える」方向へ倒すことで情報欠落（P3）を避ける。ログには warn を残す。

### 10.4 セキュリティ

- **IDOR 防止**: 色設定 API はパスに `userId` を取らない（§4.1）。`SecurityUtils.getCurrentUserId()` 以外のユーザーの設定へ到達する経路が**存在しない**。
- **所属検証**: `PUT`/`DELETE` は所属を検証する（AC-10）。これは「どのチーム ID が存在するか」の総当たり探索を防ぐ意味も持つ（非所属は一律 403 で、存在/非存在を区別しない）。
- **可視性の非露出**: レイヤー一覧が返すのは本人の所属のみ。`/my/calendar` 側の予定は既存の `filterAccessible`（F00）を通っており【確認済み】、本改修は**可視性判定に一切手を触れない**（色を後付けするだけ）。
- **公開リポジトリ**: 本書は認可の穴を記述していない（新規 API の認可を最初から定義している）ため、PR 本文のサニタイズは不要。ただし「所属検証を後から足す」ような実装順は取らないこと。
