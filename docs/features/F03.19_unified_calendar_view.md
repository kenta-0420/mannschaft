## 0. 本書の読み方 — 事実と提案の区別

本書は TimeTree 比較④「統合カレンダーはあるが UI が薄い」（マスター評）を受け、既存の横断カレンダー
`GET /api/v1/my/calendar` と `/calendar` ページを **実用に耐えるレイヤー型カレンダー** へ引き上げる設計である。

| 記法 | 意味 |
|---|---|
| 【確認済み】 | `origin/main`（= `0a933be1c`, 2026-08-06）の実ファイルを開いて確認した事実。クラス名・パス・行番号は実物と一致する |
| 【提案】 | 本書で新規に提案する設計。実装は未着手 |
| 【御裁可済み】 | マスターが決定済みの事項（本書では変更しない） |
| 【既定】 | 家老が既定値として置く判断。PR レビューで変更可 |

本書の目標は **未決事項ゼロ**（§11）である。

### 0.1 設計原則 — ADHD フレンドリー方針（CMP-005）

本書のすべての設計判断は、以下4原則に従う。個別仕様の根拠として §2 以降から参照する。

| # | 原則 | 本書での具体化 |
|---|---|---|
| **P1** | **ゼロ設定で機能する既定** | 色設定を一度もしなくてもレイヤーごとに色が分かれる（スコープキーからの決定的ハッシュ自動色・§3.3）。設定は「気に入らなければ変える」ための上書きに過ぎない |
| **P2** | **意図しない状態変化の排除** | 作成スコープ Select を触ると表示フィルタが勝手に書き換わる現行挙動を廃止（§2.2 (d)・§5.4）。ユーザーが明示的に操作した対象だけが変わる |
| **P3** | **黙って消える情報の排除** | 4件目以降が無言で切り捨てられる現行を廃し「+N件」を必ず出す（§6.2）。複数日バーの MAX_LANES 超も同様に件数として可視化する |
| **P4** | **状態の一貫性** | ダッシュボードウィジェットと `/calendar` でフィルタ状態が分裂している現行を統一（§5.3）。同じ「レイヤーの見え方」がアプリ全体で一つ。**なお「色＝サーバー保存・選択状態＝端末ローカル（localStorage）」の非対称は意図的である** — 色は「このチームは赤」という長期的な意味づけで端末を跨いで持ち歩きたいのに対し、選択状態は「今この端末で何を見ているか」という一時的な作業文脈であり、スマホで絞り込んだらPCも絞り込まれるのはむしろ不便だからである |
| **P5** | **入力摩擦の削減** | 予定を入れるのに日付と時刻を**手で入力させない**。バーチカル週ビューの時間グリッドを**なぞるだけ**で開始・終了時刻が決まる（§6.6）。ADHD 傾向のユーザーにとって「フォームの空欄を埋める」工程そのものが着手の障壁であり、**見えている枠を指でなぞる**という身体的な操作へ置き換えることで、予定入力の開始コストをほぼゼロにする |

## 1. 概要・背景

### 1.1 TimeTree 比較で見えた課題

TimeTree の中核体験は「**カレンダーを複数持ち、色で束ねて1面に重ねる**」ことにある。Mannschaft は
**統合の実体（API）は既に持っているが、UI がそれを見せていない**。マスター評「統合カレンダーはあるが UI が薄い」の内訳は以下。

| # | 現状【確認済み】 | 何が薄いか |
|---|---|---|
| 1 | フィルタの選択肢は **取得済みイベントから動的抽出**（`useMyCalendarData.ts` `availableScopes`。`extendedEvents` を走査して `scopeType:scopeId` を集める） | 予定が0件のチーム・組織は選択肢に**現れない**。月を移動すると選択肢が増減し、順序も取得順まかせで不安定。「レイヤーが並んでいる」感覚が成立しない |
| 2 | 共有イベントの色が **`color: null` 固定**（`useMyCalendarData.ts` の `sharedEvents` マッピング。`color: null,` とハードコード） | 全チーム・全組織の予定が同一色で描かれる。どのレイヤーの予定か色で判別できない。なお BE 側は `ScheduleEntity.color`（:140）と `ScheduleEventCategoryEntity.color`（:32, 既定 `#3B82F6`）を**既に持っている**が、`CalendarEntryResponse` に色フィールドが無いため API 境界で落ちている |
| 3 | 単日イベントは **先頭3件で `slice(0, 3)` 切り捨て**（`CalendarGrid.vue:245`）、複数日バーは **`MAX_LANES = 3`**（:43）超が `filter(s => s.lane < MAX_LANES)`（:276）で**無言非描画** | 4件目以降が存在の痕跡すら残さず消える。予定の見落としが構造的に発生する（P3 違反） |
| 4 | `/calendar` は **月表示のみ**（`pages/calendar.vue`） | 「今週何があるか」「今日この後何があるか」に答えられない。TimeTree の週/日/リストに相当するものが無い |
| 5 | **「今日」ボタンが無い**（`pages/calendar.vue` に `today` 相当の実装なし【確認済み】） | 数か月先を見た後、今月へ戻る手段が矢印連打しかない |
| 6 | スコープ切替が **全画面スピナー**（`withScopeLoading()` `pages/calendar.vue:318-325`。`calendarLoading=true` → `nextTick` → `setTimeout(0)` → フィルタ適用 → `false`） | 実体は**クライアント側フィルタのみ**で通信は発生しない。存在しない待ちを演出しているだけで、体感が重い |
| 7 | 作成スコープ Select の変更が **表示フィルタを強制上書き**（`pages/calendar.vue:227-234`。`watch(createScopeKey, ...)` が `selectedScopes` を `[PERSONAL_KEY]` ないし `[PERSONAL_KEY, key]` に置換） | 「予定を作る先を選んだ」だけで「今見ている面」が崩れる。P2 違反の典型 |
| 8 | モバイルのリストビューは **`teams/[slug]/schedule.vue` にしか存在しない**（`md:hidden` ブロック :105-。`ScheduleListRow.vue` は既に独立コンポーネント化済み） | 統合カレンダー `/calendar` はスマホでも月グリッドのままで、狭幅では時刻もタイトルも読めない |
| 9 | フィルタ永続化キーが **2系統に分裂**【確認済み】: `/calendar` は `mannschaft:calendar:scopeFilter`（`useMyCalendarData.ts` の既定 `SCOPE_FILTER_KEY`）、ダッシュボードウィジェットは `mannschaft:widget:calendar:scopeFilter`（`WidgetMyCalendar.vue:42` が `storageKey` で上書き） | 同じユーザーの同じレイヤー選択が2箇所で食い違う（P4 違反） |

### 1.2 既に持っているもの（土台）【確認済み】

本書は**ゼロから作らない**。以下は実装済みで、本書はこの上に UI レイヤーを積む。

| 資産 | 実体 | 役割 |

### 1.2b 予定を「入れる」側の摩擦【確認済み】

閲覧側だけでなく**入力側**にも薄さがある。現行の予定作成は以下の一本道しかない。

- `/calendar` の月グリッドで日付セルをクリック → `onDateClick(date)`（`pages/calendar.vue:89-95`）が `selectedDate` に**日付文字列のみ**を入れて `ScheduleEventForm` を開く。
- `ScheduleEventForm` の props は `initialDate?: string`（`ScheduleEventForm.vue:17`）で、受け取った日付を `form.startDate` / `form.endDate` の**両方に同じ Date として代入**する（:294-297）。**時刻は一切プリセットされない。**
- 結果、ユーザーは毎回ダイアログ内で開始時刻と終了時刻を手入力（ピッカー操作）する。

TimeTree では**バーチカル週ビュー上のドラッグ作成がプレミアム機能相当**として提供されており、ここは比較上の明確な差である。かつ、時刻の手入力は ADHD 傾向のユーザーにとって着手の障壁そのものである（P5）。本書は **(e) バーチカル週ビュー** と **(h) グリッド選択作成** を対にして、この摩擦を根から取り除くことを目玉と位置づける。

### 1.3 本書のゴール

**レイヤー（＝所属スコープ）が、予定の有無に関わらず常にそこに在り、色で識別でき、任意に重ね外しでき、月／週／リストの3面から同じ状態で見える。**
**そして、週ビューの空いている時間帯をなぞれば、時刻を一文字も打たずに予定が入る。**

## 3. DB 設計

### 3.1 新テーブル `user_calendar_layer_settings`【提案】

ユーザー×レイヤー（`scope_type` + `scope_id`）の表示設定を保持する。現時点で保持するのは色と表示可否のみ。

**設計判断**:

- **主キーは UUIDv7**（CLAUDE.md アーキテクチャ思想 原則6）。`UuidV7Entity`（`common/entity/UuidV7Entity.java`）を継承する【確認済み・存在する】。`id` は `BINARY(16)`。
- **クロスドメイン FK は張らない**（原則1）。`user_id` / `scope_id` はいずれも論理参照でインデックスのみ。schedule ドメインから user / team / organization ドメインへの FK を作らない。
- **`scope_id` は多型参照**。`scope_type = 'PERSONAL'` の行は `scope_id = 0`（センチネル）とし、NULL 混在によるユニーク制約の破綻を避ける（`notification_fanout_jobs` の `scope_ref` VARCHAR 一本化と同趣旨の判断）。チーム／組織はいずれも `BIGINT` 主キーであるため VARCHAR 化は不要。
- **論理削除は持たない**。設定行は「削除＝自動色に戻す」であり、ユーザーの意思そのもの。物理削除でよい（原則3 の対象はコアエンティティであり、本表は該当しない）。
- **索引は `uk_user_calendar_layer` のみ**。主クエリ `WHERE user_id = ?` は UNIQUE 制約の**左端プレフィックス**で賄えるため、`user_id` 単独の索引は張らない（重複索引は書き込みコストと容量の無駄）。
- **`sort_order` 列は持たない**。手動並べ替えは現時点で要件に無く、必要になった時点の `ALTER TABLE ADD COLUMN` は本表の規模（§10.1）では安価である。使われない列を先行確保しない（YAGNI）。
- **テナント列は持たない**。ユーザーの個人設定であり組織を跨る（所属組織Aと組織Bの色を同一ユーザーが持つ）ため、`AbstractTenantAwareRepository`（原則7）の適用対象外。
- **照合順序は親と同じ `utf8mb4_unicode_ci`**。

```sql
-- F03.19 統合カレンダービュー: ユーザー×レイヤーの表示設定（色・表示可否）
-- 設計書: docs/features/F03.19_unified_calendar_view.md §3
--
-- 採用方針（CLAUDE.md アーキテクチャ思想）:
--   - 主キーは UUIDv7（原則6）。id は BINARY(16)。

    scope_id       BIGINT       NOT NULL DEFAULT 0
                                                  COMMENT 'レイヤー対象ID（TEAM=teams.id / ORGANIZATION=organizations.id / PERSONAL=0 センチネル。論理参照・FK なし）',

    color          CHAR(7)      NULL              COMMENT 'ユーザー指定色（#RRGGBB 大文字。NULL=自動色にフォールバック）',
    hidden         BOOLEAN      NOT NULL DEFAULT FALSE
                                                  COMMENT '既定で非表示にするか（フィルタの初期状態。true でもレイヤー一覧には必ず出る＝P3）',

    created_at     DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    updated_at     DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3)
                                  ON UPDATE CURRENT_TIMESTAMP(3),

    PRIMARY KEY (id),
    UNIQUE KEY uk_user_calendar_layer (user_id, scope_type, scope_id)
        COMMENT '1ユーザー1レイヤーにつき1行（upsert キー・AC-05）。user_id が左端のため findByUserId の索引も兼ねる'

  DEFAULT CHARSET=utf8mb4
```

### 3.2 Flyway 採番・rollback 方針

- ファイル名: `V{major}.{yyyyMMddHHmmss}__create_user_calendar_layer_settings.sql`
- **major はマージ時に `origin/main` 全体の最大 major + 1 で確定する**。本書執筆時点（2026-08-06 / `0a933be1c`）の最大 major は **175**【確認済み】であり、素朴には 176 だが、**並行 PR が着地すると陳腐化するため、実装時に `git ls-files` で再測して確定すること**（CLAUDE.md Git 運用ルール §Flyway 採番）。
- minor は**タイムスタンプ必須**（連番禁止。`FlywayTimestampNamingGuardTest` が拒否する）。採番は `date -u '+%Y%m%d%H%M%S'`。
- **rollback 方針**: 本マイグレーションは**新規テーブル作成のみで既存テーブルへの ALTER を含まない**ため、ロールバックは `DROP TABLE user_calendar_layer_settings;` で完結し、既存データへの影響はゼロ。アプリ側も「設定行が無い＝自動色」で正常動作する（P1）ため、**テーブルが消えても機能は劣化するだけで壊れない**。この性質を保つため、`user_calendar_layer_settings` を **NOT NULL 前提で参照するコードを書かないこと**（AC-15d で検証）。

### 3.3 自動色（決定的ハッシュ）— P1 の中核【提案】

- **算出場所**: **BE と FE の両方で同じ関数を実装する**のではなく、**BE の `/my/calendar` 応答と `/me/calendar-layers` 応答に解決済みの色を載せる**（§4）。FE 側にハッシュ実装を持たない。これにより「グリッドとレイヤー一覧で色が違う」事故を構造的に排除する。
- **決定性の要件**: 同じ `scopeType:scopeId` は**いつ・どのユーザーが見ても同じ自動色**になる（AC-06）。ユーザーIDは入力に含めない（含めると同じチームがユーザーごとに違う色になり、スクリーンショット共有時に会話が噛み合わない）。

### 3.4 色の優先順位【提案】

1つの予定がどの色で描かれるかは、以下の優先順位で決まる。**上ほど強い。**

| 優先 | 由来 | 出所 | 意図 |
|---|---|---|---|
| 1 | **ユーザーのレイヤー色設定** | `user_calendar_layer_settings.color` | 「このチームは赤で見たい」というユーザーの明示的意思が最優先 |
| 2 | **予定自身の色** | `schedules.color`（`ScheduleEntity#color` :140）【確認済み】 | 予定作成者が個別に付けた色 |
| 3 | **カテゴリ色** | `schedule_event_categories.color`（`ScheduleEventCategoryEntity#color` :32、既定 `#3B82F6`）【確認済み】 | チームが定義した行事カテゴリの色 |
| 4 | **自動色** | §3.3 のハッシュ | 何も設定していなくても色が分かれる（P1） |

> **設計上の注意**: 優先1（レイヤー色）が優先2（予定色）より強いのは意図的である。レイヤーで色分けする体験を選んだ以上、「レイヤーを赤にしたのに一部の予定だけ青い」は一貫性を壊す。ただし**優先1が設定されていないレイヤーでは 2→3→4 が効く**ため、既存の予定色・カテゴリ色の投資は無駄にならない。

#### 3.4.1 この優先順位が適用される範囲【R1 裁定】

| 対象 | レイヤー色の適用 | 根拠 |
|---|---|---|
| チーム・組織のスケジュール（`/my/calendar` 由来） | ✅ 適用 | 本書の中心 |
| **個人スケジュール**（`GET /me/schedules` 由来・`listPersonalSchedules`） | ✅ **適用**（レイヤー色 > 予定色 `schedules.color` > 自動色） | **カレンダー面に並ぶ以上、個人だけ色体系の外にあるのは一貫性の破れである（P4）。FE の `personalEvents` が `'#22C55E'` へフォールバックしている現状【確認済み】を、BE 解決済みの色に置き換える。カテゴリ色は個人予定に紐づかないため 3 段（レイヤー色 > 予定色 > 自動色）** |
| **TODO**（ガント由来の期限印） | ❌ **対象外**（従来の固定色を維持: HIGH `#F97316` / LOW `#22C55E` / その他 `#3B82F6`） | TODO の色は**優先度**という別の意味軸を担っている。レイヤー色で塗ると優先度が読めなくなる。カレンダー上の TODO は「予定」ではなく「期限の印」であり、レイヤーの概念に属さない |
| **reflection**（`CalendarEnricher` 由来） | ❌ **対象外**（従来の固定色を維持: 想起 `#F59E0B` / 記入 `#6366F1`） | 橙／藍は「想起予定か記入か」という意味を担う。レイヤー色で塗り潰すと種別が読めなくなる（AC-19） |

> **凡例上の扱い**: TODO と reflection は**レイヤーチップの対象外**であり、フィルタは従来どおり `PERSONAL` レイヤーの選択に従う（現行の `isPersonal` 判定を維持）。ユーザーから見ると「個人レイヤーを消せば TODO も reflection も消える」で一貫する。

## 4. API 契約

### 4.1 共通

- ベースパス `/api/v1`、応答は既存 `ApiResponse<T>` ラッパー（`{ "data": ... }`）。
- 日時は `LocalDateTime`（既存 `/my/calendar` の `from`/`to` と同形式）。
- **本人限定 API は `/me/` 配下に置き、パスに `userId` を含めない**。ユーザー識別は `SecurityUtils.getCurrentUserId()` 固定とする（`docs/security/README.md` の IDOR 防止方針。パスに他人の ID を書ける形にしない＝到達不能にする）。
- 新規エンドポイントは **ArchUnit の認可番人と `addFilters=false` の契約 IT の両方**に登録すること（§9 AC-16）。

### 4.2 レイヤー一覧の取得 — 既存 API を使う【確認済み・新 API 不要】

タスク指示の「所属スコープ一覧を返す既存 API の有無を実コードで確認」に対する結論:

**既存 API で賄える。新規の「所属一覧 API」は作らない。**

| API | 実体 | 返すもの |
|---|---|---|
| `GET /api/v1/me/teams` | `MyTeamResponse`（`role/dto/MyTeamResponse.java`）【確認済み】。FE は `useTeamStore#fetchMyTeams`（:27-40）が既に呼んでいる | 自分の所属チーム一覧 |
| `GET /api/v1/me/organizations` | `MyOrganizationResponse`（`role/dto/MyOrganizationResponse.java`）【確認済み】。FE は `useOrganizationStore`（:31）が既に呼んでいる | 自分の所属組織一覧 |

ただし **FE が「レイヤー一覧」を組み立てるのに 3 回叩く（teams / organizations / layer-settings）のは無駄**であり、かつ「所属はあるが色設定が無い」レイヤーの自動色を FE 側で算出させることになり §3.3 の方針（BE が解決済みの色を返す）に反する。そこで **合成ビュー API を1本置く**。

**列挙ロジックの再利用【R12】**: `/me/calendar-layers` の所属列挙は、**`GET /me/teams` / `GET /me/organizations` が使っているサービスメソッドをそのまま呼ぶ**。独自の Repository クエリを書き起こしてはならない（「一覧に出るチームと色設定できるチームが違う」というズレを構造的に排除するため）。

- **ページングしない・上限を設けない。** レイヤーは「全部見えていること」自体が (a) の要件であり、途中で切れたら目的を果たさない。`CursorPagedResponse`（`backend/.../common/CursorPagedResponse.java`【確認済み・存在する】）は本 API では**使わない**。
- 所属数が極端に多いユーザー（数百チーム）では応答が膨らむが、1件あたり 200 バイト程度・実測上の所属数は数十が上限であり（§10.1）、ページングの複雑さに見合わない。**将来ページングが必要になったら、それはレイヤー UI 自体の再設計を要する規模**であり、その時点で改めて設計する。

### 4.3 `GET /api/v1/me/calendar-layers` — レイヤー一覧（合成ビュー）【提案】

**所属スコープ一覧 ＋ 解決済み色 ＋ 表示可否** を1レスポンスで返す。(a)(b)(g) の土台。

- **認可**: 認証必須。返るのは常に**呼び出し本人の所属のみ**（`/me/teams` `/me/organizations` と同じ可視性。他人の所属は一切露出しない）。クエリパラメータで対象ユーザーを指定する口は**設けない**。
- **副作用なし**（GET）。設定行が無いレイヤーも `color` に自動色が入って返る（P1）。
- **並び順は安定**（AC-04）: `PERSONAL` → `ORGANIZATION`（`scopeId` 昇順）→ `TEAM`（`scopeId` 昇順）。**予定の有無に依存しない**。

```jsonc
// 200 OK
{
  "data": [
    {
      "scopeType": "PERSONAL",     // string, non-null, "PERSONAL"|"TEAM"|"ORGANIZATION"
      "scopeId": 0,                // number, non-null — PERSONAL は常に 0（DB のセンチネルと同値。§4.3.1）
      "scopeName": "個人",          // string, non-null — PERSONAL はサーバー側の表示名ではなくキーを返し FE が i18n する（§8 参照）
      "scopeNameKey": "schedule.calendar.layer.personal", // string|null — PERSONAL のみ非 null。TEAM/ORG は null（実名を出す）
      "scopeIconUrl": null,        // string|null
      "color": "#059669",          // string, non-null — 常に #RRGGBB（解決済み。§3.4 の優先1 or 4）
      "colorSource": "LAYER_AUTO", // string, non-null — 本 API は "LAYER_USER"|"LAYER_AUTO" のみ返す（§4.3.2）
      "hidden": false              // boolean, non-null — 既定で非表示にするか
    },
    {
      "scopeType": "TEAM",
      "scopeId": 42,
      "scopeName": "青葉FC",
      "scopeNameKey": null,
      "scopeIconUrl": "https://.../signed",
      "color": "#DC2626",
      "colorSource": "LAYER_USER",
      "hidden": false
    }
  ]
}
```

#### 4.3.1 `PERSONAL` の `scopeId` は 0 で統一する【R7】

`PERSONAL` レイヤーの `scopeId` は、**DB・API 応答・URL パス・FE のレイヤーキーのすべてで `0`** とする。

- 応答で `null` に正規化して FE で `?? 0` に戻す、といった往復変換は**しない**。境界ごとに表現が変わると、片方だけ直したときに静かに壊れる。
- レイヤーキー（localStorage・`filteredEvents` の突合）は `"PERSONAL:0"` で統一する。現行 FE の `PERSONAL_KEY = 'PERSONAL'`（`useMyCalendarData.ts`【確認済み】）は `"PERSONAL:0"` へ移行する（§5.3 の localStorage 移行で旧値 `"PERSONAL"` を `"PERSONAL:0"` へ読み替える）。
- URL は `PATCH /me/calendar-layers/PERSONAL/0`。`scopeId` を省略できる別形の口は設けない（経路が2本あると認可の抜けを生む）。

#### 4.3.2 `colorSource` の値は全 API で共通の4値【R6】

`colorSource` は **`LAYER_USER` / `SCHEDULE` / `CATEGORY` / `LAYER_AUTO` の4値**とし、`/my/calendar`・個人予定一覧・`/me/calendar-layers` で**同一の enum を使う**。API ごとに `USER`/`AUTO` と `LAYER_USER`/`LAYER_AUTO` が混在すると、FE が API ごとに分岐する羽目になる。

- **`/me/calendar-layers` が返しうるのは `LAYER_USER` と `LAYER_AUTO` の2値のみ**（レイヤーには予定色もカテゴリ色も存在しないため）。値域が狭いだけで、**型は共通**である。
- 値の意味は §3.4 の優先順位 1/2/3/4 に一対一で対応する。

> **`scopeName` と `scopeNameKey` の二本立ての理由**: 現行 FE は `allScopeOptions` で `label: '個人'` を**日本語直書き**している【確認済み・`useMyCalendarData.ts`】。これは CLAUDE.md の i18n ルール違反である。BE が日本語を返すと違反が BE へ移るだけなので、**PERSONAL のみ i18n キーを返し FE が翻訳する**。チーム・組織名はユーザーが付けた実名なので翻訳対象外（`scopeNameKey = null`）。

### 4.4 `PATCH /api/v1/me/calendar-layers/{scopeType}/{scopeId}` — レイヤー設定の部分更新【提案・R2 裁定】

**メソッドは `PATCH`**（部分更新セマンティクス）。**`null` は「変更しない」を意味する。**

> **`PUT` を採らない理由【R2】**: 当初 `PUT`（全置換）で設計したが、これは**色を変えただけで `hidden` が既定値に巻き戻る**という欠陥を持つ。UI は「チップから色を選ぶ」と「チップを on/off する」を別々の操作として提供するため、片方の操作がもう片方の状態を破壊するのは P2（意図しない状態変化の排除）の直接的な違反である。**`PATCH` にして、送られなかった項目は現状を保つ。**

```jsonc
// リクエスト（両方とも省略可。省略 or null = 変更しない）
{
  "color": "#DC2626",  // string|null — 色を変更する。null または未指定なら現在の色設定を維持
  "hidden": true       // boolean|null — 表示可否を変更する。null または未指定なら現在値を維持
}

// 200 OK — 更新後のレイヤー1件（§4.3 と同一スキーマ）
{ "data": { "scopeType": "TEAM", "scopeId": 42, "scopeName": "青葉FC", "scopeNameKey": null,
            "scopeIconUrl": "https://.../signed", "color": "#DC2626", "colorSource": "LAYER_USER",
            "hidden": true } }
```

| 送った内容 | 結果 |
|---|---|
| `{"color": "#DC2626"}` | 色のみ変更。**`hidden` は現在値のまま**（AC-08b） |
| `{"hidden": true}` | 表示可否のみ変更。**色設定は保持される**（`colorSource` も変わらない） |
| `{"color": null, "hidden": null}` / `{}` | 何も変わらない。`200` で現在値を返す（冪等） |
| 設定行がまだ無い状態での `PATCH` | 行を作成し、送られた項目を設定・**送られなかった項目は既定値**（`color=NULL`＝自動色 / `hidden=false`）で埋める |

> **「色を自動色に戻す」は `PATCH` では表現しない。** `color: null` が「変更しない」を意味する以上、同じ `null` に「自動色へ戻す」も担わせると意味が二重になる。**自動色へ戻すのは `DELETE`**（§4.5）の役割である。`hidden` を保ったまま色だけ自動に戻したい場合も `DELETE` で行 ごと消す（`hidden=false` に戻る）— この組み合わせは UI 上「色をリセットしたうえで非表示のままにする」という要求であり、実運用でほぼ発生しない。将来必要になれば `"color": "AUTO"` のような明示的センチネルを足す。

**認可**:

- 認証必須・本人のみ。パスに `userId` は取らない（§4.1）。
- **所属の判定は `AccessControlService`（`backend/.../common/AccessControlService.java`【確認済み・存在する】）経由の和集合**とし、**`GET /me/teams` / `GET /me/organizations` が返す集合と完全に一致させる**【R3 裁定】。
  - Mannschaft の所属は `user_roles` 由来と membership 由来の**2系統**があり、片方だけを見ると「一覧には出るのに色を設定すると 403」という不整合が起きる。**レイヤー一覧に出るものは必ず設定できる**という不変条件を守る（AC-10b2）。
  - 判定ロジックを本 API 専用に書き起こしてはならない。§4.2 の列挙と**同じサービスメソッドの結果に対する所属判定**を使う。
- 非所属なら `SCHEDULE_101`（403）。**存在しないチーム ID も同じ 403** とし、存在／非存在を区別しない（ID 総当たり探索の防止）。

**バリデーション**:

| 対象 | 規則 | 違反時 |
|---|---|---|
| `color` | `^#[0-9A-Fa-f]{6}$` または `null`／未指定。保存時は**大文字へ正規化**（`#dc2626` → `#DC2626`。比較・重複判定を安定させる） | `SCHEDULE_102`（422） |
| `scopeType` | `PERSONAL` / `TEAM` / `ORGANIZATION` のいずれか | `SCHEDULE_103`（422） |
| `scopeId` | `TEAM`/`ORGANIZATION` は正の整数。`PERSONAL` はパス上 `0` 固定（それ以外は 422） | `SCHEDULE_103`（422） |
| 所属 | 呼び出し本人が当該スコープに所属していること（上記の和集合定義） | `SCHEDULE_101`（403） |
| 行数上限 | 当該ユーザーの設定行が **1000 件未満**であること（§10.1） | `SCHEDULE_104`（409） |

### 4.6 `GET /api/v1/my/calendar` の拡張【提案】

**既存フィールドは一切変更せず、`content` にフィールドを追加する**（追加のみ＝後方互換）。

```jsonc
{
  "data": [
    {
      "id": 1234,                    // number|null（既存・reflection 等は null）
      "content": {
        "title": "練習",              // 既存
        "eventType": "PRACTICE",     // 既存
        "status": "SCHEDULED",       // 既存
        "referenceUuid": null,       // 既存
        "referenceKind": null,       // 既存
        "color": "#DC2626",          // 【新規】string, non-null — §3.4 で解決済みの最終表示色
        "colorSource": "LAYER_USER", // 【新規】string, non-null — §4.3.2 の共通4値
                                     //   "LAYER_USER"|"SCHEDULE"|"CATEGORY"|"LAYER_AUTO"
                                     //   （§3.4 の優先1/2/3/4 のどれで決まったか。デバッグと凡例のため）
        "categoryColor": "#3B82F6"   // 【新規】string|null — カテゴリ色そのもの（未設定/カテゴリ無しは null）
      },
      "time":  { "startAt": "2026-08-06T19:00:00", "endAt": "2026-08-06T21:00:00", "allDay": false },
      "scope": { "scopeType": "TEAM", "scopeId": 42, "scopeName": "青葉FC", "scopeIconUrl": "https://.../signed" },
      "myAttendanceStatus": "ATTEND"
    }
  ]
}
```

**後方互換の担保【R8】**:

`CalendarContentDto` は **record** である【確認済み】。record は正準コンストラクタ（全フィールド）を自動生成するため、フィールドを3つ足すと**正準コンストラクタの引数は 5 → 8 に変わり、既存の 5 引数呼び出しはコンパイルエラーになる**。現状 record が持つ明示コンストラクタは **3 引数版のみ**であり、5 引数版は正準コンストラクタとして暗黙に存在しているにすぎない。

したがって以下を行う。

1. 正準コンストラクタを **8 引数**（`title, eventType, status, referenceUuid, referenceKind, color, colorSource, categoryColor`）にする。
2. **5 引数の後方互換コンストラクタを新規に追加する** — `this(title, eventType, status, referenceUuid, referenceKind, null, null, null)` へ委譲する明示コンストラクタを書く。これは「残す」のではなく**新しく書き足す**作業である（暗黙に存在していたものが正準でなくなるため、明示しないと消える）。
3. 既存の 3 引数コンストラクタは 5 引数版へ委譲する形のまま維持する。
4. **サービス層で色を必ず埋める。** 上記の後方互換コンストラクタは既存呼び出しをコンパイル可能に保つためのものであり、`/my/calendar` の応答経路では**色が `null` のまま返ってはならない**（null が漏れると FE が色無しで描く）。色を埋めない経路が残っていないことを AC-18b で検証する。

**`CalendarEnricher` の扱い【R14 裁定】**:

- **enricher は色を設定しない**（`color` / `colorSource` / `categoryColor` を `null` のまま返す）。reflection ドメイン側のコードは**一切改修しない**。
- **色の付与はすべてサービス層（`ScheduleQueryService`）が行う。** enricher が返したエントリについては、`content.referenceKind` を見て §3.4.1 の「レイヤー色対象外」ルールを適用し、**`REFLECTION_RECALL` → `#F59E0B` / それ以外の reflection → `#6366F1`** を `colorSource: "SCHEDULE"` として付与する。
- こうすることで「色を決める責務」が1箇所（サービス層）に閉じる。SPI の契約に色の責務を持ち込むと、将来 enricher を実装する各ドメインが色解決ロジックを再実装することになり、必ずズレる。
- SPI インターフェース `CalendarEnricher#enrich` のシグネチャは**変更しない**。

**個人スケジュール一覧の拡張【R1 裁定】**:

- `GET /me/schedules`（`listPersonalSchedules`）の応答 DTO（`PersonalScheduleResponse` 相当）の `content` にも **`color` / `colorSource` を追加**する。解決順は §3.4.1 のとおり **レイヤー色（`PERSONAL:0`）> 予定色 `schedules.color` > 自動色**（カテゴリは個人予定に紐づかないため無し）。
- これがないと「個人レイヤーだけ色設定が効かない」という穴が残る。個人予定は `/my/calendar` からは重複防止のため FE 側で除外されており【確認済み・`useMyCalendarData.ts` の `filter(... scopeType !== 'PERSONAL')`】、**個人予定の色は個人一覧 API 経由でしか届かない**。

**その他**:

- **`openapi.json` の再生成と `npm run generate:types` を同一 PR で行うこと**（CLAUDE.md 型定義の管理）。

## 5. 状態・データフロー（FE）

### 5.1 レイヤー状態の単一の出所

現行はイベントから逆算していた選択肢を、**レイヤー一覧 API を単一の出所**に切り替える。

```
GET /me/calendar-layers ──▶ layers: LayerView[]   （レイヤーの「実体」。予定0件でも存在する）
                                   │
                                   ├─ 色マップ  Map<"TYPE:ID", color>  ──┐
                                   └─ フィルタ選択肢（順序安定）          │
                                                                        ▼
GET /my/calendar (+ 個人 + TODO) ─▶ events: CalEvent[] ──── filteredEvents（クライアント側フィルタ・通信なし）
                                                                        │
                                              月グリッド / 週グリッド / アジェンダ（同じ配列を描く）
```

**要点**:

1. `layers` と `events` は**独立に取得**する。`layers` は月移動で再取得しない（所属は月に依存しない）。これにより「月を移動すると選択肢が変わる」現行の欠陥（§1.1 #1）が構造的に消える（AC-03）。
2. `events` 側の色は **API が既に解決済みの `content.color` を使う**（§4.6）。FE でハッシュを計算しない。ただし `layers` 由来の色マップは**凡例とフィルタチップの描画にのみ**使う（同じ BE 解決値なので必ず一致する）。
3. フィルタは**純粋なクライアント側の絞り込み**。ゆえに **(c) スピナー廃止**が成立する（§5.4）。
4. **グリッド選択作成（(h)）は既存の作成フローに合流する**。週ビューが `rangeSelect` を emit → `pages/calendar.vue` が `selectedStartAt`/`selectedEndAt` をセット → `ScheduleEventForm` が開く → 保存で既存の `@saved="refresh"`【確認済み・`pages/calendar.vue:577`】が走り `events` が再取得される。**新しいデータ経路を1本も増やさない**（§6.6.5）。

### 5.2 `useMyCalendarData` の変更点

| 現行【確認済み】 | 変更後【提案】 |
|---|---|
| `availableScopes` = `extendedEvents` を走査して抽出 | `availableScopes` = レイヤー一覧 API の結果（`hidden` なレイヤーも**選択肢には出す**。初期選択から外れるだけ＝P3） |

#### 5.2.1 レイヤー未掲載スコープのフォールバック【R4 裁定】

**レイヤー集合（`/me/calendar-layers` 由来）とイベント集合（`/my/calendar` 由来）は必ずしも一致しない。**

- `/my/calendar` は `user_roles` を辿って予定を集める【確認済み・`ScheduleQueryService:183-197`】。一方レイヤー一覧は §4.2 の所属列挙による。両者の定義が将来ズレる可能性に加え、**アーカイブ済み・論理削除済みのチームの過去予定**、**退会処理の途中状態**など、「予定は返るがレイヤー一覧には出ない」スコープが現実に生じうる。
- 現行実装は `selectedScopes.includes(...)` による**ホワイトリスト方式**であり【確認済み】、レイヤー一覧に無いスコープの予定は**選択肢が存在しないので永久に非表示**になる。これは P3（黙って消える情報の排除）の直接的な違反であり、しかもユーザーには消えた自覚すら生じない。

**裁定: 未知スコープ用のフォールバックチップを必ず出す。**

1. `filteredEvents` の評価時、イベントのレイヤーキーが `layers` に**存在しない**ものを集める。
2. 存在しないキーがひとつでもあれば、レイヤーチップ列の末尾に**フォールバックチップ**（表示名 = `scopeName`／`scopeName` も無ければ `schedule.calendar.layer.unknown` の翻訳、色 = §3.3 の自動色）を追加する。スコープごとに1チップ。
3. フォールバックチップは**既定で選択状態**（＝見える側に倒す）。ユーザーが明示的に外すまで表示され続ける。
4. 色設定 UI は出さない（設定しても `PATCH` が 403 になるスコープを含みうるため）。**表示／非表示だけができるチップ**とする。

これにより「**イベントが1件でも存在するスコープは、必ず対応するチップが画面上に存在する**」という不変条件が成立する（AC-23）。

### 5.3 localStorage スキーマと移行【(g)】

**新キー（統一）**: `mannschaft:calendar:layerState`

```jsonc
{
  "version": 2,
  "selected": ["PERSONAL:0", "TEAM:42", "ORGANIZATION:7"],  // 表示中のレイヤーキー（§4.3.1 の統一キー）
```

**移行の実行場所【R15】**: 移行は **`useMyCalendarData`（`/calendar` とウィジェットが共有する唯一の composable）の初期化 `initStorage()` 内で 1 度だけ**実行する。`pages/calendar.vue` と `WidgetMyCalendar.vue` の双方に移行コードを置いてはならない — ダッシュボードとカレンダーを同一セッションで開いた場合に二重実行され、**後から走った方が「旧キーが既に消えている」ため初期化フォールバックに落ちて選択状態を失う**。共有 composable の 1 箇所に閉じ、モジュールスコープの実行済みフラグで多重実行も防ぐ。

**移行手順**（初回読み込み時に1度だけ実行）:

| 順 | 処理 |
|---|---|
| 1 | 新キー `mannschaft:calendar:layerState` があればそれを使う。以降 2〜5 はスキップ |
| 2 | 無ければ旧キー **`mannschaft:calendar:scopeFilter`（`/calendar` 側）を読む** |
| 3 | それが無い場合に限り旧キー `mannschaft:widget:calendar:scopeFilter`（ウィジェット側）を読む |
| 4 | **両方が併存する場合は必ず `/calendar` 側（手順2）を採用する。** ウィジェット側は「ダッシュボードの小窓でざっと見るための一時的な絞り込み」であるのに対し、`/calendar` 側は「カレンダー画面でユーザーが意図して作った表示構成」であり、後者の方が意図が濃い。どちらを採るか非決定的にしてはならない |
| 5 | 読めた配列に対し **旧キー値 `"PERSONAL"` を `"PERSONAL:0"` へ読み替える**（§4.3.1）。そのうえで `{ version: 2, selected: <変換後>, view: "month" }` を新キーへ書き、**旧キーは両方とも削除する**（両系統が残って再分裂するのを防ぐ） |
| 6 | どれも無ければ「`hidden=false` のレイヤーを全選択」で初期化（P1: 初回起動でも全部見える） |

**ウィジェット（`WidgetMyCalendar.vue`）は `storageKey` 上書きを廃止**し、既定キーを使う。これで `/calendar` とウィジェットのレイヤー選択が常に一致する（P4・AC-13）。

> **注**: `view` はウィジェットには適用しない（ウィジェットは常に月グリッドの縮約）。ウィジェットは `selected` のみを読む。

### 5.4 作成スコープと表示フィルタの分離【(d)】

**現行**（`pages/calendar.vue:227-234`）【確認済み】:

```ts
watch(createScopeKey, (key) => {
  withScopeLoading(() => {
    if (key === 'personal') { selectedScopes.value = [PERSONAL_KEY] }
    else { selectedScopes.value = [PERSONAL_KEY, key] }
  })
  ...

```

**変更後**【提案】:

- **`selectedScopes` への代入を削除する。** 作成スコープの変更は、作成フォームの初期スコープにのみ影響する。
- ガントビューのキャッシュ破棄（`ganttCache.clear()` 以下）は**残す**。これは表示フィルタではなくデータ取得対象の変更であり、正当な副作用である。
- **表示フィルタが空（全レイヤー非選択）のまま予定を作成しても、作成した予定が見えない**という状況が起こりうる。これに対しては**「作成したレイヤーが非表示です」の一行案内＋そのレイヤーを表示にするボタン**を作成完了時に出す（P2 を守りつつ P3 の「黙って消える」も避ける・AC-11）。勝手にフィルタを書き換えない点が現行との本質的な違い。

### 5.5 スピナー廃止【(c)】

`withScopeLoading()`（`pages/calendar.vue:318-325`）を**削除**し、`onToggleScope` / `onMultiSelectChange` は `toggleScope(value)` / `selectedScopes.value = vals` を**同期的に呼ぶだけ**にする。

- 根拠: フィルタ適用は `filteredEvents` の `computed` 再評価のみで、**ネットワーク I/O は一切発生しない**【確認済み・`useMyCalendarData.ts` の `filteredEvents`】。`calendarLoading` を立てて `setTimeout(0)` を挟む現行は、存在しない待ちを演出しているだけ。
- `calendarLoading` 自体は**月移動時のデータ取得には引き続き使う**（そちらは本物の通信）。廃止するのはフィルタ操作経路のみ。

- 3ビューは**同一の `filteredEvents` を描く**。ビュー切替で再取得しない（切替もクライアント側・スピナー無し）。
- 選択中のビューは localStorage の `view`（§5.3）に永続化する。

### 6.2 「+N件」オーバーフロー表示【(c)・P3】

**単日イベント**（`CalendarGrid.vue:245` の `slice(0, 3)`）:

| 状況 | 表示 |
|---|---|
| セル内の単日イベントが 3件以下 | 全件表示（現行どおり） |
| 4件以上 | 先頭2件 ＋ **「+N件」行**（N = 総数 − 2）。**3件目を犠牲にして必ず「+N」を出す**。「3件表示して4件目から+N」にすると、4件のとき「+1件」が出て行数が増え、レイアウトが崩れるため |

**複数日バー**（`CalendarGrid.vue:276` の `filter(s => s.lane < MAX_LANES)`）:

| 状況 | 表示 |
|---|---|
| その週のレーン数が `MAX_LANES`(3) 以下 | 全バー表示（現行どおり） |
| 超過 | レーン 0,1 のバー ＋ **レーン2の位置に「+N件」行**（N = そのセルの日に掛かる非表示バー数。**日ごとに数える**。週で1つの数字にすると「この日には無いのに+3と出る」嘘になる） |

**展開挙動**【既定】:

- 「+N件」をクリック → **その日のイベント全件を出す日別ポップオーバー**を開く（月グリッドのセル高を可変にしない＝レイアウトが跳ねない。ADHD 配慮として「押した場所の近くに開く」）。
- ポップオーバー内の行は `ScheduleListRow.vue` を再利用し、時刻・タイトル・レイヤー色ドットを表示。行クリックで既存の `eventClick` / `reflectionClick` を親へ発火（現行の振り分けロジック `onEventClick`【確認済み】をそのまま使う）。
- **アジェンダビューには「+N件」は存在しない**（一次元リストなので切り捨てが起きない）。これが P3 に対する最も強い保証であり、「取りこぼしが心配なときはアジェンダを見ればよい」という逃げ道になる。

### 6.3 「今日」ボタン【(c)】

- 月ナビゲーション（`◀ 2026年8月 ▶`）の右に **「今日」ボタン**を常設。
- 押下時: 表示月を**ユーザータイムゾーン基準の今日**が属する月へ移動し、月グリッドでは今日のセルへフォーカスリング、週ビューでは今日を含む週へ、アジェンダでは今日の見出しへスクロールする。
- **既に今月を表示中でも無効化しない**（押しても何も起きないのではなく、今日のセルへフォーカスが移る）。「押したのに反応しない」は P2 の観点で不信を招く。
- ユーザータイムゾーンは既存 `useDatetime()` の `userTimezone`【確認済み・`CalendarGrid.vue:5`】に従う。ブラウザ TZ 直参照はしない。

### 6.4 レイヤー凡例・フィルタ UI

- レイヤーは**色ドット＋名前のチップ列**として月ナビの下に並べる。選択中は塗り、非選択は輪郭のみ（**色の情報を残したまま on/off が分かる**）。
- **予定0件のレイヤーもチップとして常に出す**（AC-02）。ここが (a) の可視的な成果である。
- チップ数が多い場合、既存の `FILTER_OVERFLOW = 5`【確認済み・`useMyCalendarData.ts`】に倣い 5 件超は MultiSelect へ畳む。**畳んだ場合も「N件のレイヤー」と件数を表示**し、存在を隠さない（P3）。
- 各チップの長押し／右クリック（モバイルは「…」）で**色変更ポップオーバー**（§4.4 の `PATCH` を呼ぶ）。§3.3 のパレット12色＋「自動に戻す」（§4.5 の `DELETE` を呼ぶ）。
- **チップは必ず「色ドット＋レイヤー名」を併記する**（色だけに識別を担わせない・§3.3 の色覚多様性配慮）。
- **フォールバックチップ**（§5.2.1）はチップ列の末尾に、通常のチップと同じ見た目で並べる。ただし色変更ポップオーバーは開かない（表示／非表示のみ）。

#### 6.5.1b 日をまたぐ時刻付き予定【R11】

`allDay=false` でありながら開始日と終了日が異なる予定（例 8/6 22:00 〜 8/7 02:00 の夜間行事）は、**終日帯に送らず、両日の列に分割して描画する**。

- 8/6 の列に **22:00〜24:00** のバー、8/7 の列に **00:00〜02:00** のバーを置く。
- 分割された各バーには**継続記号**を付ける — 翌日へ続く側の下端に `▼`、前日から続く側の上端に `▲`（月ビューの複数日バーが `continuesBefore` / `continuesAfter` を持つのと同じ考え方【確認済み・`MultiDaySlot`】）。記号が無いと「22時に始まって24時に終わる予定」と「翌朝まで続く予定」が区別できない。
- **分割片は1つの予定として扱う**。`uniqueKey` は共有し、どちらをクリックしても同じ予定詳細が開く。重なり解決（§6.5.2）は分割後の片ごとに、その日の中で行う。
- 3日以上にまたがる時刻付き予定は、中間日が **00:00〜24:00 のフルハイトバー**になる。この場合は例外的に**終日帯へ送る**（時間グリッドを丸ごと1本の予定が占有し、その日の他の予定が全部隠れるため）。判定は「その日における占有が 24 時間フル か否か」で行う。

#### 6.5.2 重なりの解決（横並び分割）

同じ日の時間帯が重なる予定は、**列を等分して横に並べる**。

1. その日の時刻付き予定を開始時刻昇順に整列する。
2. 時間的に重なる予定同士を**クラスタ**（推移的に重なりが繋がる集合）にまとめる。
3. クラスタ内で**同時に重なっている最大本数 = `width` の分母**とし、各予定に空いている最小の列インデックスを割り当てる。
4. 描画幅 = `列幅 / 分母`、左オフセット = `列幅 × 列インデックス / 分母`。

- **上限は設けない**（月ビューの `MAX_LANES` に相当する切り捨てを持ち込まない）。10 本重なれば 1/10 幅になり文字は読めないが、**存在は必ず見える**（P3）。読めない場合はタップして詳細を開く導線がある。
- **極短時間の予定**（15分未満など）は、計算上の高さが 12px を下回っても **最低高さ 20px を確保**する。潰れて消えるのを防ぐ（P3）。この場合わずかに下へはみ出すが、重なり計算は実時刻ベースのまま行う。
- 各予定バーの背景色は §3.4 で解決済みの `content.color`。左端に濃いめの縦アクセント線を置き、淡い背景でも所属レイヤーが判別できるようにする。

#### 6.5.3 ナビゲーションと状態

- 週の起点は**日曜**（月ビュー `daysOfWeek = ['日','月',...]`【確認済み】と揃える）。
- `◀ ▶` で前週・翌週。`今日` ボタン（§6.3）で今週へ。
- **月/週/アジェンダの切替でレイヤー選択は保持される**（§5.1・AC-13）。週ビューは `filteredEvents` を日付で束ね直すだけで、再取得しない。
- 週の表示範囲が月をまたぐ場合、`useCalendarEvents` の取得範囲は**表示中の週を包含する月**を必ず含むように拡張する（またいだ側の予定が空になるのを防ぐ）。

#### 6.5.4 テスト用の識別子規約【R19】

週ビューの時間グリッドは**ピクセル座標でしか指し示せない**ため、E2E から「9:00 のセル」を安定に掴む手段が無いと (h) のテストが書けない。以下を規約とする。

- 時間グリッドの各スロットに **`data-testid="week-slot-{dayIndex}-{hour}-{minute}"`** を付与する。
  - `dayIndex`: 0〜6（0 = 週の起点＝日曜）
  - `hour`: 0〜23（ゼロ埋めしない）
  - `minute`: スナップ単位の境界のみ（既定 15分刻みなら `0` / `15` / `30` / `45`）
  - 例: 月曜 9:00 → `week-slot-1-9-0`
- **E2E はこの要素の bounding box を基準に座標を算出する**（`boundingBox()` の中心へ `mouse.move` → `mouse.down` → 目標スロットの box へ `mouse.move` → `mouse.up`）。**画面高やスクロール位置から座標を計算してはならない** — 1時間 = 48px という実装定数（§6.5.1）を E2E が知っている状態は、定数を変えた瞬間にテストが嘘をつく。
- 予定バーには `data-testid="week-event-{uniqueKey}"`、終日帯には `data-testid="week-allday-lane"`、選択ハイライトには `data-testid="week-selection-highlight"` を付与する。
- 同様に、月ビューの「+N件」は `data-testid="day-overflow-{dateStr}"`、日別ポップオーバーは `data-testid="day-detail-popover"` とする（§6.2 の AC で使う）。

### 6.6 グリッド選択による予定作成【(h)・御裁可済み・本書の目玉】

**バーチカル週ビューの時間グリッドをなぞると、その範囲の開始・終了時刻がプリセットされた作成ダイアログが開く。** P5（入力摩擦の削減）の中核であり、TimeTree のプレミアム機能相当にあたる。

#### 6.6.1 一連の流れ

| 段 | PC（マウス） | モバイル／タッチ |
|---|---|---|
| **開始** | 時間グリッドの空き領域で `pointerdown` | 時間グリッドの空き領域を **500ms 長押し**（§6.6.4） |
| **選択中** | ドラッグに追従して**半透明のハイライト矩形**を描き、矩形内に**「9:00 – 10:30」の時刻ラベル**をリアルタイム表示（§6.6.3） | 同左。長押し成立時に**触覚フィードバック**（`navigator.vibrate?.(10)`・非対応環境では何も起きない） |
| **確定** | `pointerup` | `touchend` |
| **ダイアログ** | 既存 `ScheduleEventForm` が**開始日時・終了日時をプリセットされた状態で**開く（§6.6.5） | 同左 |
| **保存後** | `@saved="refresh"` で再取得し、**作成した予定が今いる週ビュー上のなぞった位置にそのまま現れる**（AC-21） | 同左 |
| **キャンセル** | ダイアログを閉じるとハイライトは消える。カレンダーの状態は選択前と完全に同一に戻る | 同左 |

#### 6.6.2 「選択の開始」と見なす条件

以下の**いずれかに該当する場合は選択を開始しない**（誤爆防止）。

| 条件 | 理由 |
|---|---|
| ドラッグが**既存の予定バーの上**で開始された | その予定を開きたいのか新規作成なのか判別できない。予定バー上の操作は従来どおり `eventClick`。**将来のドラッグ移動・リサイズはここに差し込む**（§2.3） |
| ドラッグが**終日帯**の上で開始された | 終日帯は時刻を持たない。終日予定の作成は日付セルクリック（既存導線）で行う |
| ドラッグが**時刻ラベル列**の上で開始された | スクロール操作と衝突する |
| 移動距離が **閾値未満**（PC: 4px 未満、モバイル: 長押し不成立） | 単なるクリック／タップ。この場合は**その位置の時刻から既定 60 分**の予定として扱い、ダイアログを開く（クリック1発でも作れる。P5） |
| **月ビュー／アジェンダビューを表示中** | **ドラッグ選択は週ビュー限定**。月ビューの日付セルのドラッグは何も起こさない（従来どおりクリックで `onDateClick`）。アジェンダは一次元リストであり時間軸を持たないため対象外。誤って別ビューにジェスチャを実装しないこと（AC-22b で検証） |

#### 6.6.3 ビジュアルフィードバックとスナップ

- **ハイライト矩形**: 選択中の時間帯を、そのとき選択されている**作成スコープのレイヤー色**（§6.6.6）の半透明（`opacity: 0.35`）＋破線枠で描く。「これから何色の予定がここに入るか」が選択中に分かる。
- **時刻ラベル**: 矩形の中央に `9:00 – 10:30` を常時表示。ドラッグに追従して更新する。**これが「時刻を手入力しない」ことの視覚的な保証**であり、ユーザーは数字を確認しながら指を離せる。
- **スナップ単位**【御裁可事項の具体化・既定】:

| 表示密度 | スナップ | 理由 |
|---|---|---|
| 既定（1時間 = 48px） | **15分**（= 12px） | 12px は指でも十分に狙える最小単位。15分刻みは実用上ほぼすべての予定を表現できる |
| 将来ズームアウトを入れた場合（1時間 < 32px） | **30分** | 物理ピクセルが 15分あたり 8px を切ると狙えない。密度に応じて粗くする |

- スナップは**開始・終了の両端に独立して適用**する。丸めは**最も近い境界へ**（`Math.round`）。切り捨てにすると 9:59 から下へなぞったとき 9:45 開始になり直感に反する。
- **最小選択長は 15分**。上へ逆方向にドラッグした場合は開始と終了を入れ替えて正の範囲にする（`start > end` を作らない）。逆方向に 0 まで戻したら最小 15分を維持する。
- **日をまたぐ選択はしない**。ドラッグが横方向に別の列へ移っても、**選択は開始した列（＝日）に固定**する。週ビューで斜めに引いて 3 日間の予定が生まれるのは事故であり、複数日予定は終日帯／既存フォームから作る。
- 上端・下端を越えるドラッグでは**時間グリッドを自動スクロール**する（端から 40px 以内で毎フレーム 8px）。24:00 を超えたら 24:00 で止める。

#### 6.6.4 モバイル: スクロールとドラッグの競合回避

時間グリッドは縦にスクロールする。**タッチ開始を即座に選択と解釈すると、縦スクロールが一切できなくなる。** これを避けるため：

1. `touchstart` の時点では**何もしない**。`preventDefault()` も呼ばない（＝ブラウザの慣性スクロールは生きたまま）。
2. **500ms** のタイマーを張る。この間に **10px 以上の移動** または `touchend` が起きたら**タイマーを破棄**し、通常のスクロール／タップとして扱う。
3. 500ms 経過して指が留まっていたら**長押し成立**。この瞬間に触覚フィードバックを出し、ハイライトを表示し、以降の `touchmove` で `preventDefault()` を呼んでスクロールを止め、選択モードへ入る。
4. 選択モード中はコンテナに `touch-action: none` を当てる（成立前は当てない。ここを常時 `none` にするとスクロールが死ぬ）。
5. `touchcancel`（着信・システムジェスチャ等）では**選択を破棄**する。中途半端な時刻でダイアログを開かない。

> **設計上の要点**: 「長押しで初めて選択が始まる」ため、**モバイルではスクロールが常に最優先**である。ユーザーが週を眺めている限り誤って予定作成が始まることはない（P2）。

#### 6.6.5 既存作成ダイアログとの整合

現行の `ScheduleEventForm` は **`initialDate?: string`（日付のみ）** を受け取り、`form.startDate` と `form.endDate` の両方に同じ `Date` を入れる（:294-297）【確認済み】。時刻をプリセットする口が無い。

**変更方針**【提案】:

- `ScheduleEventForm` に **`initialStartAt?: string` / `initialEndAt?: string`**（いずれも ISO 8601・ユーザー TZ のオフセット付き）を追加する。
- 適用の優先順位: **`initialStartAt`/`initialEndAt` があればそれを使い、無ければ従来どおり `initialDate` を使う**。`initialDate` の既存挙動は一切変更しない（月ビューの日付クリック導線＝現行の唯一の作成経路が壊れないこと。AC-22c）。
- **受け側の解釈【R16】**: `ScheduleEventForm` が `initialStartAt` / `initialEndAt` を受け取るとき、**`dayjs(value).tz(userTimezone.value)` で「ユーザー TZ における壁時計」として解釈**し、そこから年・月・日・時・分を取り出してフォームの `Date` を組み立てる。
  - **`new Date(value)` によるナイーブ生成は禁止**。これは実行端末のローカル TZ で解釈されるため、**端末 TZ とユーザー設定 TZ が異なる場合に時刻がずれる**（例: 端末 UTC・ユーザー設定 Asia/Tokyo で 9:00 を選ぶと 18:00 になる）。既存の `initialDate` 経路が `new Date(props.initialDate)` を使っている【確認済み・:295-296】のは、日付のみで時刻が 00:00 固定だったため被害が顕在化していなかっただけであり、時刻を載せた瞬間にバグになる。
  - 送り側（`CalendarWeekGrid` の `rangeSelect`）も同じ原則で、**ユーザー TZ のオフセットを明示した ISO 8601 文字列**（例 `2026-08-06T09:00:00+09:00`）を emit する。オフセット無しのナイーブ文字列は渡さない。
  - `userTimezone` は既存 `useDatetime()` から取る【確認済み】。`Intl.DateTimeFormat().resolvedOptions().timeZone`（端末 TZ）を直接参照してはならない。
- `pages/calendar.vue` 側は `selectedDate` に加えて `selectedStartAt` / `selectedEndAt` を持ち、週ビューの `@rangeSelect` を受けてセットしてから `showCreateDialog = true` にする。**日付クリック経路（`onDateClick`）では `selectedStartAt`/`selectedEndAt` を `undefined` にリセットする**（前回のドラッグ値が残って日付クリックに時刻が付く事故を防ぐ）。
- `CalendarWeekGrid.vue` の emit に `rangeSelect: [startAt: string, endAt: string]` を追加する。**コンポーネント自身はダイアログを知らない**（既存 `dateClick` / `eventClick` と同じく、親が組み立てる責務分離を保つ）。

#### 6.6.6 作成スコープの既定値 —(d) との整合

ドラッグで開いたダイアログの**作成先スコープは、画面上部の作成スコープ Select の現在値をそのまま使う**（`selectedCreateScope`【確認済み・`pages/calendar.vue:222`】）。これは既存の「＋予定追加」ボタン経由と完全に同じ挙動であり、導線によって作成先が変わることはない。

- **表示フィルタ（`selectedScopes`）は参照しない。** (d) の裁定（§5.4）どおり、作成スコープと表示フィルタは独立である。「今そのレイヤーだけ表示しているから、そこに作る」といった**推測を一切しない**（P2）。
- ハイライト矩形の色は**作成スコープのレイヤー色**（§3.4 の優先1 or 4 で解決済みの値）を使う。これは「どこに作られるか」の予告であって、表示フィルタとは無関係。
- 作成先レイヤーが表示フィルタで非表示の場合、保存後に §5.4 の「作成先のレイヤーが非表示です／表示する」案内が出る（AC-11b と同じ経路）。**ここでも勝手にフィルタを書き換えない。**

### 6.7 アクセシビリティ【R5・新設】

グリッド選択作成（§6.6）は**ポインタジェスチャに依存した機能**であり、そのままではキーボードのみの操作者・スクリーンリーダー利用者が予定を作れない。**代替経路を必ず用意する。**

#### 6.7.1 キーボード操作

| 操作 | 挙動 |
|---|---|
| `Tab` | 時間グリッドへフォーカスが入る。**グリッド全体で1つのタブストップ**とし（`tabindex="0"` をグリッドに1つだけ置く「ロービングフォーカス」方式）、42×96 個のセルを個別のタブストップにはしない — `Tab` を数千回押さないと次の要素へ抜けられない設計は、支援技術利用者にとって機能の追加ではなく妨害である |
| `↑` `↓` | フォーカスセルをスナップ単位（既定15分）で上下移動 |
| `←` `→` | フォーカスセルを前日・翌日へ移動（週の端で前週・翌週へ繰り上がる） |
| `Enter` / `Space` | **フォーカス位置から既定 60 分の予定として作成ダイアログを開く**（単クリックと同じ・§6.6.2） |
| `Shift` + `↓` | **選択範囲をスナップ単位で下へ延長**する。延長中はハイライトが伸び、時刻ラベルが更新される |
| `Shift` + `↑` | 選択範囲を縮める（最小15分で止まる） |
| `Enter`（範囲選択中） | その範囲で作成ダイアログを開く |
| `Escape` | 選択を破棄してフォーカスのみに戻す |

- キーボードによる範囲選択は**ドラッグと完全に同じ結果**を生む（同じ `rangeSelect` を emit する）。経路が違うだけで到達点は同一とする。

#### 6.7.2 ARIA と読み上げ

- 時間グリッドのコンテナに **`role="grid"`**、各日の列に `role="row"`、各スロットに `role="gridcell"` を付与する。
- 各 `gridcell` の **`aria-label` に時刻を含める** — 例 `"8月6日 水曜日 9時00分"`。空きスロットには加えて `"空き"`、予定が置かれているスロットには予定タイトルを含める。**時刻が読み上げられなければ、視覚に頼らない利用者はどこを選んでいるか分からない。**
- 選択範囲の変化は **`aria-live="polite"` の領域**で `"9時00分から10時30分を選択中"` としてアナウンスする（ハイライトという視覚表現の等価物）。
- 週ビューの `role="grid"` に `aria-label` として週の範囲（例 `"2026年8月2日から8月8日の週"`）を与える。
- 終日帯は `role="grid"` の外に置き、独立した `role="list"` とする（時間軸を持たないため grid の行列モデルに乗らない）。

#### 6.7.3 その他の配慮

- **ハイライトの識別を色だけに依存させない**（§3.3 の色覚多様性配慮と同趣旨）。選択矩形は半透明の塗りに加えて**破線枠**を持つ（§6.6.3）。
- `prefers-reduced-motion: reduce` が指定されている場合、ハイライトの追従アニメーションと自動スクロールの補間を無効化し、即座にジャンプさせる。
- 予定バーの文字色は §3.3 の表に従い、**背景色に対して 4.5:1 以上のコントラスト**を保つ。

## 10. 非機能

### 10.1 スケール — `user_calendar_layer_settings`

| 観点 | 見積り |
|---|---|
| 1ユーザーあたりの行数 | 所属チーム数＋所属組織数＋1（PERSONAL）**を上限とし、かつ色を変更したものだけ**。実際には大半のユーザーが 0〜数行（P1 により設定しなくても機能するため） |
| **行数の上限（ハード）** | **`user_id` あたり 1000 行**。**サービス層で担保**する（DB 制約では表現できない）。新規行の作成前に `countByUserId` で確認し、1000 以上なら `SCHEDULE_104`（409）で拒否する（AC-10d）。既存行の更新は上限に関係なく成功する。脱退後も行が残る仕様（§10.5）のため、長期利用者では所属数を超えて行が積み上がりうる。上限が無いと、API を機械的に叩いて1ユーザーが無制限に行を作れる（所属検証があるため大量所属が前提になるが、大規模組織では現実的に到達しうる） |
| 1000万ユーザー時の最大行数 | 仮に平均5レイヤー × 20% のユーザーが色を設定 → 約 1000万行。**単一テーブルで問題ない規模**（`notifications` 等と比べて桁が2つ小さい） |
| 主クエリ | `SELECT * FROM user_calendar_layer_settings WHERE user_id = ?` — `idx_user_calendar_layer_user` で数行を引く。`/my/calendar` あたり **1回**（§4.7） |
| 書き込み | ユーザーが色を変えたときのみ。書き込み頻度は極めて低い |
| キャッシュ | **導入しない**。1ユーザー数行の主キー引きにキャッシュを噛ませる利益は薄く、色変更直後に反映されない不整合（P2 違反）の方が害が大きい |

### 10.2 レスポンスサイズ

`/my/calendar` へ `content` に3フィールド（`color` 7文字 / `colorSource` 最大12文字 / `categoryColor` 7文字 or null）を追加する。1エントリあたり約 60 バイト増。1か月分 300 件で約 18KB 増。**gzip 後は色文字列の重複が高圧縮されるため実質的な増加は僅少。** 許容する。

### 10.3 後方互換・段階リリース

| 段階 | 内容 | この時点で壊れないこと |
|---|---|---|
| **Wave 1** | Flyway + Entity + レイヤー API 3本 + `/my/calendar` の色フィールド追加 | FE は新フィールドを読まないため**現行 UI は無変更で動く**（追加のみ＝AC-18） |
| **Wave 2** | FE のレイヤー実体化・色反映・localStorage 移行 | BE が Wave 1 で先行デプロイ済み。仮に BE が古くても `content.color` が `undefined` になるだけで、`?? null` フォールバックで現行の単色描画に劣化する（§5.2） |
| **Wave 3** | バーチカル週／アジェンダビュー・グリッド選択作成・モバイル共通化 | 既定ビューは `month` のままなので、新ビューに不具合があっても既存の月ビュー体験は無傷。**グリッド選択作成は週ビュー内に閉じており**（§6.6.2）、月ビューの日付クリック作成経路には一切触れない（AC-22c）ため、既存の唯一の作成導線が壊れるリスクを構造的に断っている |

**旧 localStorage キーからの移行**は §5.3 のとおり Wave 2 で1度だけ実行し、**旧キーを削除**する。移行に失敗した場合（JSON パース不能等）は「全レイヤー選択」へフォールバックする — ここは**エラー握りつぶしではなく意図した劣化**であり、「全部見える」方向へ倒すことで情報欠落（P3）を避ける。ログには warn を残す。

### 10.4 データのライフサイクル — 脱退・削除・退会【R9・新設】

`user_calendar_layer_settings` はクロスドメイン FK を持たない（原則1）ため、**参照先が消えても行は自動では消えない**。孤児行の扱いを明示する。

| イベント | 設定行の扱い | 理由 |
|---|---|---|
| **ユーザーがチーム／組織を脱退する** | **削除しない（残す）** | **再加入したときに、以前設定した色で復活する**のが望ましい（保存値優先）。「一度離れて戻ったら色が変わっていた」は、ユーザーが何もしていないのに状態が変わったことになり **P2（意図しない状態変化の排除）に反する**。脱退中は所属していないため `/me/calendar-layers` に現れず、実害は無い（行数は §10.1 の 1000 上限で頭打ち） |
| **チーム／組織が削除される** | **削除する（フック）** | 二度と復活しない参照先の設定を残す理由が無い。チーム削除・組織削除のドメインイベント受信時に `deleteByScopeTypeAndScopeId` を発行する。**クロスドメイン FK ではなくアプリ層のイベントで整合を取る**（原則1に沿う） |
| **ユーザーが退会する** | **削除する** | ユーザー退会フロー（PII 消去の即時＝弱匿名化の段）で本表の行も削除する。**退会処理の対象テーブル表に `user_calendar_layer_settings` を追加すること**。色設定は個人の嗜好情報であり、匿名化後のユーザーに紐づけて残す意味が無い |

- 削除フックは**同期・ベストエフォート**とする。削除に失敗しても親の操作（チーム削除等）をロールバックしない（孤児行は害が無く、上限でも頭打ちになるため）。ただし**握りつぶさず warn ログを残す**。
- チーム削除が論理削除の場合、レイヤー一覧からは所属列挙経由で自動的に消えるため、行削除は「掃除」であって機能要件ではない。
- 定期バッチによる孤児行の一括掃除は**設けない**（規模が小さく、上限で頭打ちになるため）。

### 10.5 セキュリティ

- **IDOR 防止**: 色設定 API はパスに `userId` を取らない（§4.1）。`SecurityUtils.getCurrentUserId()` 以外のユーザーの設定へ到達する経路が**存在しない**。
- **所属検証**: `PATCH`/`DELETE` は所属を検証する（AC-10・AC-10b2）。これは「どのチーム ID が存在するか」の総当たり探索を防ぐ意味も持つ（非所属は一律 403 で、存在/非存在を区別しない）。
- **可視性の非露出**: レイヤー一覧が返すのは本人の所属のみ。`/my/calendar` 側の予定は既存の `filterAccessible`（F00）を通っており【確認済み】、本改修は**可視性判定に一切手を触れない**（色を後付けするだけ）。
- **公開リポジトリ**: 本書は認可の穴を記述していない（新規 API の認可を最初から定義している）ため、PR 本文のサニタイズは不要。ただし「所属検証を後から足す」ような実装順は取らないこと。
