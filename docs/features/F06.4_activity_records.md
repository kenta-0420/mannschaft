## 1. 概要

チーム/組織の活動内容を構造化データとして記録・蓄積する機能。試合結果・練習記録・イベント報告・会議議事録など、業種に応じた記録項目をカスタムフィールドで自由に定義し、統計・集計機能で活動傾向を可視化する。

CMS のブログ・お知らせ（F06.1）が「エディトリアルコンテンツ（自由記述の記事）」であるのに対し、活動記録は「構造化データ（定義済みフィールドに値を記録）」として管理する。

**主要ユースケース**:
- スポーツチーム: 試合結果（スコア・対戦相手・会場）、練習記録（メニュー・参加者・時間）
- 学校・PTA: 授業記録、行事報告、PTA 活動報告
- マンション管理組合: 理事会議事録、定期点検記録、修繕工事記録
- 整骨院・美容室: 日報・業務記録（施術件数・売上等の集計用）
- コミュニティ: イベント報告、ボランティア活動記録

### 本ドキュメントのスコープ

| 機能 | 説明 |
|------|------|
| 活動テンプレート | チームごとにカスタムフィールドを定義した記録テンプレート |
| 活動記録 CRUD | テンプレートに基づいた活動記録の作成・編集・削除 |
| 参加者管理 | 活動への参加メンバーの記録（メンバー番号での選択対応） |
| 統計・集計 | 期間別・テンプレート別・フィールド別の集計・グラフ表示 |
| 公開設定 | 公開記録は SSR で SEO 対応。メンバー限定記録は SPA |

**スコープ外**:
- ブログ・お知らせ（自由記述の記事） → F06.1
- パフォーマンスデータの個人統計ダッシュボード → F07.2
- サービス履歴（施術記録・来店記録） → F07.1
- カルテ（問診票・身体チャート） → F07.4

### テーブル定義

#### `activity_templates`

活動記録のテンプレート。チームごとにカスタムフィールドを定義した記録フォーマット。

| カラム名 | 型 | NULL | デフォルト | 説明 |
|---------|---|------|-----------|------|
| `id` | BIGINT UNSIGNED | NO | AUTO_INCREMENT | PK |
| `scope_type` | VARCHAR(20) | NO | — | スコープ（`TEAM` / `ORGANIZATION`） |
| `scope_id` | BIGINT UNSIGNED | NO | — | スコープ ID |
| `name` | VARCHAR(100) | NO | — | テンプレート名（例: 「試合結果」「練習記録」「理事会議事録」） |
| `description` | VARCHAR(500) | YES | NULL | テンプレートの説明 |
| `icon` | VARCHAR(30) | YES | NULL | アイコン（emoji or アイコン名。例: `⚽`, `📋`） |
| `color` | VARCHAR(7) | YES | NULL | テーマカラー（hex。例: `#3B82F6`） |
| `is_participant_required` | BOOLEAN | NO | TRUE | 参加者の記録が必須か |
| `default_visibility` | VARCHAR(20) | NO | 'MEMBERS_ONLY' | デフォルトの公開設定（`PUBLIC` / `MEMBERS_ONLY`） |
| `sort_order` | INT | NO | 0 | 表示順 |
| `created_by` | BIGINT UNSIGNED | NO | — | FK → users。作成した ADMIN |
| `created_at` | DATETIME | NO | CURRENT_TIMESTAMP | |
| `updated_at` | DATETIME | NO | CURRENT_TIMESTAMP ON UPDATE | |
| `deleted_at` | DATETIME | YES | NULL | 論理削除日時 |

**インデックス**
```sql
INDEX idx_at_scope (scope_type, scope_id, sort_order)  -- スコープ別のテンプレート一覧
```

**制約・備考**
- 1スコープあたり最大 **20 テンプレート**
- テンプレートを論理削除しても、既存の活動記録は閲覧可能（テンプレート名はスナップショットされない。JOIN で取得）
- `default_visibility = 'PUBLIC'`: SSR でインデックスされる。ゲストも閲覧可能
- テンプレートごとにカスタムフィールドを `activity_template_fields` で定義

#### `activity_template_fields`

テンプレートのカスタムフィールド定義。チームが記録したい項目を自由に追加。

| カラム名 | 型 | NULL | デフォルト | 説明 |
|---------|---|------|-----------|------|
| `id` | BIGINT UNSIGNED | NO | AUTO_INCREMENT | PK |
| `template_id` | BIGINT UNSIGNED | NO | — | FK → activity_templates。ON DELETE CASCADE |
| `field_key` | VARCHAR(50) | NO | — | フィールドキー（英数字・アンダースコア。例: `score`, `opponent`, `location`） |
| `field_label` | VARCHAR(100) | NO | — | 表示ラベル（例: 「スコア」「対戦相手」「会場」） |
| `field_type` | VARCHAR(20) | NO | — | フィールド型（`TEXT` / `NUMBER` / `DATE` / `DATETIME` / `SELECT` / `CHECKBOX` / `TEXTAREA`） |
| `is_required` | BOOLEAN | NO | FALSE | 必須フィールドか |
| `options_json` | JSON | YES | NULL | `SELECT` 型の選択肢（例: `["勝ち", "負け", "引き分け"]`） |
| `placeholder` | VARCHAR(200) | YES | NULL | プレースホルダーテキスト |
| `unit` | VARCHAR(20) | YES | NULL | 単位（例: 「点」「km」「時間」。`NUMBER` 型の場合に表示） |
| `is_aggregatable` | BOOLEAN | NO | FALSE | 統計集計の対象か（`NUMBER` 型のみ TRUE 可能。合計・平均・最大・最小の集計対象） |
| `sort_order` | INT | NO | 0 | 表示順 |

**インデックス**
```sql
INDEX idx_atf_template (template_id, sort_order)                -- テンプレート別のフィールド一覧
UNIQUE KEY uq_atf_key (template_id, field_key)                   -- テンプレート内でフィールドキー一意
```

**制約・備考**
- 1テンプレートあたり最大 **15 フィールド**
- `field_type` ごとの保存形式:
  - `TEXT`: 文字列（最大 200 文字）
  - `NUMBER`: 数値（DECIMAL(10,2)）
  - `DATE`: 日付（YYYY-MM-DD）
  - `DATETIME`: 日時（YYYY-MM-DDTHH:mm。F04.10 議事録標準テンプレートの「開催日時」で使用）
  - `SELECT`: 選択肢の値（`options_json` から選択）
  - `CHECKBOX`: 真偽値（true/false）
  - `TEXTAREA`: 長文（最大 2,000 文字）
- `is_aggregatable = TRUE` は `NUMBER` 型のみ。統計 API で合計・平均・最大・最小を算出
- フィールド定義の変更ルール:
  - **追加**: 許可。既存記録には新フィールドの値がない → 表示時に「未記録」と表示
  - **削除**: 許可。既存記録に旧フィールドの値が残る → 表示時に「（削除済みフィールド）」として値を表示（データは消さない）
  - **`field_type` 変更**: 禁止（既存 JSON の値が新しい型と不整合になるため。型を変えたい場合は旧フィールド削除 + 新フィールド追加）
  - **`field_key` 変更**: 禁止（JSON のキーと一致しなくなるため）
  - **`field_label` 変更**: 許可（表示名のみの変更で既存データに影響なし）
  - **`is_required` 変更**: 許可（新規記録のみ影響。既存記録は再バリデーション対象外）
  - **`options_json` 変更**: 許可（新規記録のみ新しい選択肢を適用。既存記録の値が新選択肢に含まれなくてもエラーにしない）

#### `activity_results`

活動記録の実データ。テンプレートに基づいて記録される。

| カラム名 | 型 | NULL | デフォルト | 説明 |
|---------|---|------|-----------|------|
| `id` | BIGINT UNSIGNED | NO | AUTO_INCREMENT | PK |
| `scope_type` | VARCHAR(20) | NO | — | スコープ（`TEAM` / `ORGANIZATION`） |
| `scope_id` | BIGINT UNSIGNED | NO | — | スコープ ID |
| `template_id` | BIGINT UNSIGNED | NO | — | FK → activity_templates。使用テンプレート |
| `title` | VARCHAR(200) | NO | — | 活動タイトル（例: 「第15節 vs ○○チーム」「2026年4月度 練習記録」） |
| `activity_date` | DATE | NO | — | 活動日 |
| `activity_time_start` | TIME | YES | NULL | 開始時刻（任意） |
| `activity_time_end` | TIME | YES | NULL | 終了時刻（任意） |
| `description` | TEXT | YES | NULL | 活動の詳細説明（Markdown 対応。任意） |
| `field_values` | JSON | NO | '{}' | カスタムフィールドの値（`{ "score": "3-1", "opponent": "○○チーム", "location": "○○スタジアム" }`。フィールドなし or 全て任意で未入力の場合は `{}`） |
| `attachments` | JSON | YES | NULL | 添付ファイル ID 配列（`{ "file_ids": [101, 102, 103] }`。F05.5 の `shared_files` を参照。最大10件） |
| `visibility` | VARCHAR(20) | NO | 'MEMBERS_ONLY' | 公開設定（`PUBLIC` / `MEMBERS_ONLY`） |
| `schedule_id` | BIGINT UNSIGNED | YES | NULL | FK → schedules。スケジュールから自動作成した場合 |
| `created_by` | BIGINT UNSIGNED | YES | — | FK → users（ON DELETE SET NULL）。作成者。退会時は NULL に遷移 |
| `created_at` | DATETIME | NO | CURRENT_TIMESTAMP | |
| `updated_at` | DATETIME | NO | CURRENT_TIMESTAMP ON UPDATE | |
| `deleted_at` | DATETIME | YES | NULL | 論理削除日時 |

**インデックス**
```sql
INDEX idx_ar_scope (scope_type, scope_id, activity_date DESC)           -- スコープ別の活動記録一覧
INDEX idx_ar_template (template_id, activity_date DESC)                  -- テンプレート別の記録一覧
INDEX idx_ar_schedule (schedule_id)                                      -- スケジュールからの逆引き
INDEX idx_ar_visibility (scope_type, scope_id, visibility, activity_date DESC)  -- 公開記録の一覧（SSR 用）
```

**制約・備考**
- `field_values`: `activity_template_fields` で定義されたフィールドの値を JSON で保存。キーは `field_key`、値は `field_type` に応じた形式
- `field_values` のバリデーション: Service 層で `activity_template_fields` の定義に基づき型チェック・必須チェックを実行
- `visibility = 'PUBLIC'`: ゲストも閲覧可能。SSR でレンダリングし SEO 対象
- `schedule_id`: F03.1 のスケジュール完了時に「活動記録を作成しますか？」の導線で紐付け。イベントのタイトル・日付を初期値に使用
- アクセス解析: `page_view_logs` に `target_type = 'ACTIVITY_RECORD'`, `target_id = activity_results.id` で記録
- `attachments`: F05.5 の `shared_files.id` を参照する JSON 配列。1活動記録あたり最大10ファイル。F05.5 のストレージ容量管理がそのまま適用。表示時に `shared_files` から URL・サムネイルを IN 句で取得
- `description`（Markdown）: Markdown テキストをそのまま保存（HTML 変換はフロントエンドで実施）。サニタイズは DOMPurify で SSR 時含めてフロントエンドで実行。最大 10,000 文字
- `created_by` の ON DELETE: `SET NULL`。作成者がアーカイブ/退会しても活動記録は残る。`created_by IS NULL` の場合は「退会済みユーザー」と表示

#### `activity_participants`

活動への参加者。活動記録と users の多対多リレーション。

| カラム名 | 型 | NULL | デフォルト | 説明 |
|---------|---|------|-----------|------|
| `id` | BIGINT UNSIGNED | NO | AUTO_INCREMENT | PK |
| `activity_result_id` | BIGINT UNSIGNED | NO | — | FK → activity_results。ON DELETE CASCADE |
| `user_id` | BIGINT UNSIGNED | NO | — | FK → users（ON DELETE CASCADE）。参加者。退会時は参加記録も削除 |
| `role_label` | VARCHAR(50) | YES | NULL | 活動内での役割（例: 「GK」「司会」「記録係」） |
| `created_at` | DATETIME | NO | CURRENT_TIMESTAMP | |

**インデックス**
```sql
UNIQUE KEY uq_ap_activity_user (activity_result_id, user_id)  -- 同一活動の重複参加防止
INDEX idx_ap_user (user_id, created_at DESC)                    -- ユーザー別の参加履歴
```

**制約・備考**
- 参加者はスコープ内のメンバーであること（Service 層バリデーション）
- `role_label`: 任意。テンプレートの `is_participant_required = TRUE` の場合、最低1名の参加者が必須
- F06.2 のメンバー番号（背番号・社員番号等）でも参加者を検索・選択可能

| `updated_at` | DATETIME | NO | CURRENT_TIMESTAMP ON UPDATE | |
| `deleted_at` | DATETIME | YES | NULL | 論理削除日時 |

**インデックス**
```sql
INDEX idx_ac_activity (activity_result_id, created_at)  -- 活動記録別のコメント一覧
```

#### `system_activity_template_presets`

プラットフォーム標準テンプレート。SYSTEM_ADMIN がカテゴリ別の推奨テンプレートを管理し、チーム作成時のオンボーディングで提供。

| カラム名 | 型 | NULL | デフォルト | 説明 |
|---------|---|------|-----------|------|
| `id` | BIGINT UNSIGNED | NO | AUTO_INCREMENT | PK |
| `category` | VARCHAR(30) | NO | — | カテゴリ（`SPORTS` / `SCHOOL` / `COMMUNITY` / `BUSINESS` / `MANAGEMENT_ASSOCIATION`） |
| `name` | VARCHAR(100) | NO | — | プリセット名（例: 「試合結果（スポーツ）」「理事会議事録（管理組合）」） |
| `description` | VARCHAR(500) | YES | NULL | プリセットの説明 |
| `icon` | VARCHAR(30) | YES | NULL | アイコン |
| `color` | VARCHAR(7) | YES | NULL | テーマカラー |
| `is_participant_required` | BOOLEAN | NO | TRUE | 参加者必須設定 |
| `default_visibility` | VARCHAR(20) | NO | 'MEMBERS_ONLY' | デフォルト公開設定 |
| `fields_json` | JSON | NO | — | フィールド定義の JSON 配列（`activity_template_fields` と同形式） |
| `is_active` | BOOLEAN | NO | TRUE | 有効/無効 |
| `created_at` | DATETIME | NO | CURRENT_TIMESTAMP | |
| `updated_at` | DATETIME | NO | CURRENT_TIMESTAMP ON UPDATE | |
| `deleted_at` | DATETIME | YES | NULL | 論理削除日時 |

**インデックス**
```sql
INDEX idx_satp_category (category, is_active)  -- カテゴリ別のプリセット一覧
```

**制約・備考**
- `fields_json`: `[{"field_key": "opponent", "field_label": "対戦相手", "field_type": "TEXT", ...}]` 形式。`POST /activity-templates/import-preset` で `activity_template_fields` に展開
- `category` でチーム種別（テンプレートの `template_type`）に応じたフィルタリングが可能
- `system_activity_template_preset_fields` テーブルは設けない（`fields_json` で十分。プリセットのフィールドは DB に正規化する必要がない）

#### 公開活動記録 API（5 本共通仕様・匿名公開）

**認可**: 不要（`permitAll` の公開 API）。実装は `ActivityPublicController` → `PublicActivityQueryService`。

チーム/組織の公開活動記録を取得する。SSR でレンダリングし SEO 対象。

##### レスポンス項目（公開専用 DTO・8 項目のみ）

認証済み API の `ActivityRecordResponse` は**使わない**。公開経路は専用 DTO
（`publicview.dto.PublicActivityDetail` / `PublicActivitySummary`）で以下 **8 項目だけ**を返す。

| 項目 | 説明 |
|---|---|
| `id` | 活動記録 ID |
| `title` | タイトル |
| `activityDate` | 活動日 |
| `activityTimeStart` / `activityTimeEnd` | 開始・終了時刻（未設定は `null`。キーは常に存在する） |
| `description` | 説明（未設定は `null`） |
| `scopeRef` | 所属スコープ参照（`scopeType` / `scopeId` / `scopeName`） |
| `createdAt` | 作成日時 |

**禁則（絶対に含めない）**: `fieldValues` / `attachments` / `createdBy` / `visibility` / `status` /
`templateId` / `venueId` / `scheduleId` / `scopeId` 生値 / `updatedAt` / `deletedAt` / `publishable` / `location`。
`@JsonInclude(NON_NULL)` は**付けない**（キーごと消えると FE の型契約が崩れる）。

##### 200 を返す条件（すべて満たすこと）

1. **親スコープが公開**: チーム/組織が `visibility = PUBLIC` かつ `archived_at IS NULL` かつ `deleted_at IS NULL`
2. **記録が公開済み**: `visibility = 'PUBLIC'` かつ `status = 'PUBLISHED'`（`deleted_at IS NULL`）
3. **F00 可視性判定を通過**: `ContentVisibilityChecker`（未認証 `userId = null`）
4. **パス変数と実スコープが一致**: `teamId` / `orgId` が記録の `scope_type` / `scope_id` と一致（スコープ詐称拒否）

##### スコープ種別ごとの公開可否（COMMITTEE は fail-closed）

| `scope_type` | 公開 EP から見えるか | 実装 |
|---|---|---|
| `TEAM` | 親チームが `visibility=PUBLIC` かつ未凍結・未削除なら可 | `TeamService#findPublicTeamNameById` |
| `ORGANIZATION` | 親組織が `visibility=PUBLIC` かつ未凍結・未削除なら可 | `OrganizationService#findPublicOrganizationNameById` |
| **`COMMITTEE`** | **常に不可（一律 404）** | `resolvePublicScopeRefOrThrow` の `case COMMITTEE -> Optional.empty()` |

委員会は公開ページを持たないため fail-closed とする。記録自身が `visibility=PUBLIC` かつ `status=PUBLISHED` でも 404 であり、ボディも「存在しない ID」と同一（存在秘匿）。**将来 COMMITTEE を公開対象にする場合はこの分岐に追記することになるが、その瞬間に委員会の活動記録が匿名公開される**ため、契約テスト **AC-37** が現在の fail-closed を機械的に固定している。分岐を追加するなら AC-37 の改訂を伴う意思決定として扱うこと。

##### 認証済みユーザーが公開 EP を叩いた場合（応答は閲覧者に依存しない）

公開ページをログイン状態で閲覧する / SNS のシェアリンクをログイン中に踏む経路は必ず発生する。
`PublicActivityQueryService` は `canView(..., null)` / `filterAccessible(..., null)` と **`userId` を `null` 固定**で呼ぶため、認証状態にかかわらず応答は同一である。

- ログイン済みでも **200**（401/403 にしない）
- 返る項目は匿名時と**まったく同じ 8 項目**
- **当該チームの ACTIVE メンバーであっても**、公開 EP 経由では `MEMBERS_ONLY` / `DRAFT` / 論理削除済みは見えない
- 匿名時とレスポンスボディが **1 バイトも変わらない**

これは公開 EP が SSR / CDN / リバースプロキシでキャッシュされうるためで、閲覧者によって内容が変わる公開 URL は**キャッシュ汚染**と意図しない露出の温床になる。契約テスト **AC-39 / AC-39b** が固定しており、`null` 固定を `SecurityUtils.getCurrentUserIdOrNull()` に差し替えた瞬間に落ちる。

##### 失敗はすべて 404（存在秘匿）

不在 / 非公開 / 下書き / 削除済み / 親スコープ非公開・凍結・停止 / スコープ不一致 は
**すべて `PUBLIC_013` → 404** に倒し、ステータスコードもレスポンスボディも区別しない。
403 を返すと「存在するが権限がない」ことを漏らす**存在オラクル**になり、ID 総当りで実在 ID を列挙されるため。

##### 一覧の `limit` / `page`

`limit` は **上限 100・既定 20** に丸める（`0` 以下は 20、`100` 超は 100）。
無制限だと全件取得の DoS 経路になり、`limit=0` は `PageRequest.of(0, 0)` で 500 を誘発できた。

`page`（0始まり・既定 0）は **2026-08-09 の第三陣で新設**した。旧実装は
`ActivityPublicController` の一覧2本（チーム/組織）が `page` を受け取らず、
`PublicActivityQueryService.toPageable` が `PageRequest.of(0, size)` と第0ページを
直書きしていたため、公開一覧は 2 ページ目以降へ永久に到達できなかった
（公開ページに活動記録タブを新設する以上、ページ送りができないのは他タブとの不整合になる）。
先例 PR #2598（`ActivityController#listActivities` の同型改修）と同じ流儀を踏襲する:
`page` に負値を渡すと `PageRequest.of` が `IllegalArgumentException` を投げ 500 に化ける口が
新たに開くため `@Min(0)` で 400 に倒す。**`ActivityPublicController` に `@Validated` を
付けてはならない**（付けると Spring 6.1+ の組込みメソッド検証ではなく AOP プロキシ経由の
従来型検証に切り替わり、standalone 試験環境では `@Min` が素通りして 500 に戻る）。

##### 非数値パス変数は 400（404 に倒さない）

`/api/v1/public/activities/abc` のように **ID として成立しない値**は、Spring MVC の型変換（`String → Long`）がコントローラ到達**前**に失敗し `400` + `COMMON_001` を返す。ボディは `ErrorResponse.of(CommonErrorCode.COMMON_001)` の定数で、入力値・例外クラス名・パラメータ名・スタックトレースを一切含まない。

**これは「失敗はすべて 404」の例外ではなく、対象外である**。存在秘匿が封じるのは「ID として妥当な値を投げたとき、その記録が実在するかを学べてしまう」ことだが、非数値では activity_results への問い合わせが一度も発生しないため、攻撃者は記録の存在について何も学べない。400 と 404 の差は**入力領域の違い（ID か否か）**であって**リソースの存在有無の違いではない**。契約テスト **AC-38** がこの 400 と「ボディに内部情報を載せないこと」を固定する。

> なお `teamId` / `orgId` / `organizationId` のパス変数だけは `ScopeSlugIdConverter` による slug 解決の対象で、非数値でも slug として解決を試み、解決できなければ 404 `COMMON_005` になる（`GlobalExceptionHandler#isUnresolvedScopeSlug`）。この結果、`/public/teams/{不在slug}/activities`（404 `COMMON_005`）と `/public/teams/{実在するが非公開なチームのslug}/activities`（404 `PUBLIC_013`）でボディが異なり、**slug の実在が判別できる**。activity 固有ではなく `ScopeSlugIdConverter` を通す全 `/public/teams/**` 系に共通する挙動のため、本設計書の範囲では是正せず横断課題として記録する。

##### 一覧における条件 2（門2）と条件 3（門3）の適用層（2026-07-30 改訂・ページング歯抜けの根治）

**症状**: 旧実装の `ActivityResultService#listPublicActivities` は、スコープ配下の全行から 1 ページ分（= `limit` 件）を SQL で取得し、**取得後にメモリ上で** `ContentVisibilityChecker#filterAccessible` を掛けていた。`Pageable` は既に `size=limit` で切られているため落ちた分は補充されず、非公開が混ざると `limit=20` でも 20 件返らない（**ページング歯抜け**）。総件数も「全行数 − このページで落ちた件数」という**上界近似**にしかならなかった。

**根治**: 一覧は条件 2 を **SQL の WHERE 句**で解く。

```java
// ActivityResultRepository#findPublicByScopeTypeAndScopeId
@Query("SELECT ar FROM ActivityResultEntity ar "
        + "WHERE ar.scopeType = :scopeType AND ar.scopeId = :scopeId "
        + "AND ar.visibility = com.mannschaft.app.activity.ActivityVisibility.PUBLIC "
        + "AND ar.status = com.mannschaft.app.activity.ActivityStatus.PUBLISHED "
        + "ORDER BY ar.activityDate DESC, ar.id DESC")
```

論理削除は `@SQLRestriction("deleted_at IS NULL")` が自動除外する。索引は既存の
`idx_ar_visibility (scope_type, scope_id, visibility, activity_date DESC)` がそのまま効く。

| 門 | 詳細（単件） | 一覧 |
|---|---|---|
| 条件 2（`PUBLIC` × `PUBLISHED`） | `findByIdAndVisibilityAndStatus`（SQL） | **`findPublicByScopeTypeAndScopeId`（SQL 述語）** |
| 条件 3（F00 `ContentVisibilityChecker`） | 判定の主体 | **第二の門**。SQL が通した行を匿名 (`userId=null`) で再確認し、落ちた行は返さない（fail-closed）うえで `log.warn` に乖離を記録する（本番での不整合検知） |

これは **F00 一本化方針に反しない**。禁じられているのは「二つ目の判定器を作ること／手書きのロール階層を書くこと」であり、SQL に書くこと自体ではない（`docs/features/F02.6_announcement_widget.md` は逆に「検証は Repository 層の `@Query` レベルで WHERE 句に入れる」と規定している）。匿名では `MembershipBatchQueryService#snapshotForUser(null, …)` が `UserScopeRoleSnapshot.empty()` を返してラダーが縮退し、`StandardVisibility.PUBLIC` の Javadoc が「未認証時は PUBLIC かつ PUBLISHED のときのみ true、それ以外はすべて fail-closed」と明文で宣言しているため、上記述語は **F00 自身の宣言の機械的転写**である。金型は F19.1 `BlogPostRepository#findPublicPostsByTeamId`（`PublicActivityQueryService` が「金型」と明記する `PublicPostQueryService` の実体）。

契約は `ActivityPublicContractIT`（実 Security フィルタチェーン経由）が機械的に検証する。とくに **AC-32（等価性番人）** が「SQL 述語の集合 S」と「F00 `filterAccessible` の集合 F」の **`S == F`** を `visibility × status × deleted` の全 8 組合せで固定しており、片方だけを変更すると必ず落ちる。ページング系 AC（AC-30 / AC-30b / AC-31 / AC-31b / AC-35）は (a) 公開 / (b) `MEMBERS_ONLY` / (c) `PUBLIC`+`DRAFT` / (d) 論理削除 の 4 種を**交互に投入**した混在フィクスチャを用い、非公開行が先頭ページに食い込むことを自己検査する。

##### 認証済み一覧（`GET /api/v1/activities`）の既知の残務

`ActivityResultService#listActivities` の総件数は 2026-07-30 に是正した（旧: `new PageImpl<>(filtered, pageable, filtered.size())` でページ内件数へ化けていた → 新: `TournamentService` と同じく「DB 総件数 − このページで落ちた件数」）。
ただし **歯抜けそのものは認証済み経路に残っている**。認証済みでは F00 のラダーが縮退しない（閲覧者のロールに応じて `MEMBERS_AND_ABOVE` 等が通る）ため、SQL 述語化すると本物の独自述語になり F00 一本化方針に正面から反する。
厳密化の道筋: **F00 側に「単一スコープに対する閲覧者の可視レベル解決 API」を新設**し、その結果（閲覧可能な `StandardVisibility` 集合）を SQL の `IN` 述語へ翻訳する。これにより判定器は F00 のまま一つで、SQL は F00 の出力を機械的に写すだけになる。後続戦役として起票する。

##### sitemap.xml への収録（2026-07-30 新設）

公開活動記録は `GET /sitemap.xml` に `/activity/{id}` として収録する。
これが無いと「公開したのに検索エンジンから発見されない」状態が続く（リンクを辿る経路が無いため）。

収録してよいのは**次の 4 条件をすべて満たすものだけ**である:

1. `visibility = PUBLIC`
2. `status = PUBLISHED`
3. 論理削除されていない
4. **親スコープ（チーム / 組織）も公開である**

条件 4 が sitemap 固有の勘所である。単票 API なら「非公開なら 404」で守れるが、
sitemap は **URL をこちらから検索エンジンへ差し出す**ため、親が非公開のまま載せると
「非公開チームが存在すること」と「その配下の記録 ID」を能動的に開示してしまう
（後から 404 を返しても手遅れ）。`COMMITTEE` は公開ページを持たないため常に除外（fail-closed）。

実装と検査:

| 層 | 実体 |
|---|---|
| SQL | `ActivityResultRepository#findPublicForSitemap`（4 条件を WHERE 句で解く） |
| ドメイン境界 | `ActivityResultService#findPublicActivitiesForSitemap` が JDK 型だけの `PublicActivitySitemapRow` を返す（publicview へ Entity を渡さない＝番人 D-1 / D-5 回避） |
| 組み立て | `SitemapQueryService#findPublicActivityEntries` が公開スコープ ID 集合を作って渡す |
| 検査 | `ActivityResultSitemapQueryTest`（実 MySQL）— 非公開 / DRAFT / 論理削除 / 親非公開 / COMMITTEE が載らないことを固定 |

詳細は `docs/features/F19.1_public_pages_identity_disclosure.md` §9.2 / §9.2.1。

##### 公開ページの SSR 要件（2026-07-30 是正・仕様からの乖離を根治）

本設計書は当初から「公開記録は SSR で SEO 対応」（§1 本ドキュメントのスコープ / §5「重要な判定ロジック」）と規定していたが、
**`/activity/{id}` の実装は CSR 専用に乖離していた**。実測（稼働中 FE に対する SSR HTML の取得）:

| 対象 | SSR HTML の中身 |
|---|---|
| `/activity/1`（是正前） | `<title>` なし・OGP なし・本文なし。`#__nuxt` 直下はスピナーのみ |
| `/public/organizations/1`（比較対象・既存の公開ページ） | `<title>` あり・`og:title` あり・本文あり |

原因は 2 つあり、**両方**を直さないと SSR にならない:

1. `layouts/default.vue` が `v-if="!isMounted"` でマウント前はスピナーだけを描画する
   （＝ default レイアウトを使うページは、どのページでも SSR 出力が空になる）
2. データ取得が `onMounted`（サーバー側では実行されない）

**是正**: 他の公開ページ（`pages/public/**`）と同じ流儀に揃えた。
`definePageMeta({ layout: 'public' })` + `await useAsyncData` + `useSeoMeta` / `useSeoPublicPage`。

これは SEO だけの都合ではない。**SNS のクローラ（LINE / X / Facebook）は JavaScript を実行しない**ため、
CSR のままでは OGP タグが永久に読まれない。本ページは SNS シェアを主目的とするのに、
**その OGP が丸ごと死んでいた**（`ActivitySharePanel` が配る URL を踏んでもカードが出ない）。
sitemap 収録（F19.1 §9.2）はこの SSR 化とセットで初めて意味を持つ。

##### ID の連番性による列挙耐性 — 検討した結果、追加の検知機構は実装しない（2026-07-30 判断）

**論点**: `activity_results.id` は `BIGINT AUTO_INCREMENT` の連番で、
`GET /api/v1/public/activities/{id}` は ID 直引きできる。抑止は `PublicApiRateLimitFilter` の
**60 req/分/IP** のみのため、分散 IP なら列挙は理論上可能である。

**結論: (b) 監査ログの充実にとどめ、連続 404 の検知アラートは新設しない。**

判断の根拠:

1. **得られるものが小さい**。列挙で取れるのは御裁可済み 8 項目
   （`id` / `title` / `activityDate` / `activityTimeStart` / `activityTimeEnd` / `description` / `scopeRef` / `createdAt`）
   だけで、これは**そもそも匿名公開してよいと決めた項目**である。非公開 / DRAFT / 削除済み / 親スコープ非公開は
   すべて 404 に倒れる（上記「失敗はすべて 404」）。つまり列挙の成果は「公開情報を機械的に集める」ことに留まり、
   秘密が漏れる経路にはなっていない。
2. **404 は正常系で構造的に連続する**。sitemap でクローラに URL を配り、SNS でシェアリンクが拡散する設計である以上、
   記録を非公開に戻す / 下書きに戻す / 削除する、あるいは**親チーム・組織を非公開化すると、
   それまで 200 だった URL 群が一斉に 404 化する**（親スコープ判定が先に走るため、チーム 1 件の非公開化で
   配下の全公開記録が同時に 404 になる）。「404 が連続したら攻撃」という閾値は誤検知の塊になり、
   運用を疲弊させるだけで検知能力を持たない。
3. **アラートを受け取る土台が本番に存在しない**。調査時点で:
   - `application-prod.yml` の actuator は `include: health` のみで、**本番に Prometheus のスクレイプ経路が無い**
   - Terraform に `aws_cloudwatch_metric_alarm` / `aws_cloudwatch_log_metric_filter` は **1 件も無い**
     （存在するのは月額コストの `aws_budgets_budget` と SES バウンス用 SNS のみ）
   - `infra/grafana/` はローカル専用資産で、既存のアラートルール 3 本はいずれも `"_disabled": true`
   - `audit_logs` を**読んで通知する仕組みは存在しない**（アーカイブ / GDPR エクスポート用の読み取りのみ）

   したがって今アラートを定義しても**鳴る先が無い**。先に必要なのは個別アラート 1 本ではなく
   本番メトリクス基盤の敷設であり（`FUTURE_CONSIDERATIONS.md` の未チェック項目）、本件の範囲を超える。

**将来この検知を入れるときの指針**（前提が変わったとき用）:

- 新規メトリクスの実装は不要。`PublicApiRateLimitFilter` が既に
  `public.api.requests{path,method,status}` を出しており、`status="404"` で数えられる。
- ただし `path` タグは ID を `*` に潰しているため、**現状のメトリクスだけでは「ID の分散度」を判定できない**。
  総当り性を見たいなら「同一 `ip_hash` あたりの distinct ID 数」または「404/200 比率」が要る。
- **より鋭い signal は `public.api.rate_limit.exceeded`**（60/min/IP を突破した未認証アクセス）である。
  正常系のシェアリンク流入はこの閾値に届かないため誤検知が少なく、実装量もゼロ（既存メトリクス）。
  連続 404 アラートより先にこちらを Slack（`ErrorReportNotifier` の配管が既存）へ繋ぐのが費用対効果で勝る。

**UUIDv7 への移行は検討対象外**。`CLAUDE.md` 原則 6 は「**新規テーブル**は UUIDv7」であり、
既存テーブルの ID は変更しない方針。`activity_results` は既存テーブルのため該当しない。

なお ID 直引き経路の監査ログに `activityId` を載せる改善は **PR #2548** で別途実施済み（本 PR では重複して触らない）。

## 5. ビジネスロジック

### 活動記録の作成フロー

```
1. ADMIN / MEMBER がテンプレートを選択
   a. テンプレート一覧から記録フォーマットを選択
   b. カスタムフィールドの入力フォームが動的に生成

2. フィールド値の入力
   a. field_type に応じた入力 UI を表示
      - TEXT: テキスト入力
      - NUMBER: 数値入力（unit 表示付き）
      - DATE: デートピッカー
      - SELECT: ドロップダウン（options_json から選択肢生成）
      - CHECKBOX: チェックボックス
      - TEXTAREA: テキストエリア
   b. is_required = TRUE のフィールドはバリデーション必須

3. 参加者の選択
   a. スコープ内のメンバー一覧から選択（チェックボックス）
   b. メンバー番号（F06.2 の背番号等）での検索・フィルタ対応
   c. 前回の参加者をデフォルト選択（同一テンプレートの直近記録から引き継ぎ）

4. 保存
   a. field_values を JSON として activity_results に INSERT
   b. participant_user_ids を activity_participants に INSERT
   c. visibility = 'PUBLIC' の場合: SSR キャッシュを無効化
```

### スケジュールからの活動記録作成

```
1. F03.1 のスケジュール完了時（status = 'COMPLETED'）
   a. 「活動記録を作成しますか？」のプロンプトを表示
   b. 「はい」→ 活動記録作成画面に遷移
      - title: schedules.title をプリフィル
      - activity_date: schedules.starts_at の DATE 部分をプリフィル
      - activity_time_start / end: schedules.starts_at / ends_at の TIME 部分をプリフィル
      - participant_user_ids: schedule_attendances で status = 'ATTENDING' のユーザーをプリフィル
      - schedule_id: 該当スケジュールの ID
   c. 「いいえ」→ スキップ
```

### カスタムフィールドの集計ロジック

```
1. GET /activities/stats/fields で is_aggregatable = TRUE の NUMBER フィールドを集計
2. 集計対象: activity_results.field_values の JSON から該当 field_key の値を抽出
3. SQL:
   SELECT
     COUNT(*) as count,
     SUM(CAST(JSON_EXTRACT(field_values, CONCAT('$.', :fieldKey)) AS DECIMAL(10,2))) as sum,
     AVG(CAST(JSON_EXTRACT(field_values, CONCAT('$.', :fieldKey)) AS DECIMAL(10,2))) as avg,
     MAX(CAST(JSON_EXTRACT(field_values, CONCAT('$.', :fieldKey)) AS DECIMAL(10,2))) as max,
     MIN(CAST(JSON_EXTRACT(field_values, CONCAT('$.', :fieldKey)) AS DECIMAL(10,2))) as min
   FROM activity_results
   WHERE template_id = :templateId
     AND scope_type = :scopeType AND scope_id = :scopeId
     AND deleted_at IS NULL
     AND activity_date BETWEEN :dateFrom AND :dateTo
4. MySQL 8.0 の JSON_EXTRACT で JSON 内の値を直接集計
5. セキュリティ: :fieldKey は CONCAT でJSON パスに組み込まれるため、
   field_key のバリデーション（/^[a-zA-Z0-9_]+$/）を Service 層 + DB の
   UNIQUE KEY uq_atf_key で二重に保証。SQL インジェクションリスクを排除
6. パフォーマンス: template_id + activity_date のインデックスで絞り込み後に JSON_EXTRACT
   → 大量データ（1万件超）の場合はマテリアライズドビュー or 日次バッチ集計を検討
```

### 活動記録の複製フロー

```
1. ユーザーが活動記録詳細画面で「この記録をコピー」ボタンをクリック
2. POST /activities/{id}/duplicate を呼び出し
3. バックエンド:
   a. 元の記録の field_values / visibility / description をコピー
   b. 元の activity_participants を全員コピー
   c. file_ids はコピーしない（添付ファイルは元の記録と共有すると
      削除時に影響するため。必要なら手動で再添付）
   d. activity_date を今日の日付でプリフィル（リクエストで上書き可能）
   e. title は元のタイトルをそのままコピー（リクエストで上書き可能）
4. フロントエンド: 複製結果の編集画面を開く（即座に保存ではなく編集→保存の2ステップ）
```

### タイムラインへの自動投稿

```
1. POST /activities で post_to_timeline = true の場合
2. 活動記録の INSERT 完了後に ApplicationEvent を発行
3. TimelineAutoPostListener が非同期で受信:
   a. タイムライン投稿のテキストを自動生成:
      「📋 活動記録: {title}
       {field_values_summary の必須フィールドを箇条書き}
       👥 参加者 {participant_count} 名」
   b. POST /timeline（内部呼び出し）でタイムライン投稿を作成
   c. 投稿に活動記録へのリンクを含める
   d. 投稿の visibility は活動記録の visibility に合わせる
4. 失敗時: 活動記録の作成はロールバックしない（タイムライン投稿は副作用）
5. 注意: 編集時（PUT /activities）には自動投稿しない（初回作成時のみ）
```

### コメントフロー

```
1. メンバーが活動記録詳細画面でコメントを投稿
2. POST /activities/{id}/comments で activity_comments に INSERT
3. 活動記録の created_by（作成者）にプッシュ通知:
   「{commenter_name} が活動記録「{title}」にコメントしました」
4. コメントの body は Markdown 対応（description と同一のサニタイズ方針）
5. コメント一覧は created_at ASC でソート（時系列順）
```

### プリセットテンプレートのインポートフロー

```
1. チーム作成直後のオンボーディング画面 or テンプレート管理画面で
   「おすすめテンプレートをインポート」ボタンを表示
2. GET /system-admin/activity-template-presets?category={チームのカテゴリ}
   でカテゴリに合ったプリセット一覧を取得
3. ユーザーがプリセットを選択 → POST /activity-templates/import-preset で
   スコープにインポート
4. インポート後のテンプレートは通常のテンプレートと同一に扱える
   （フィールド追加・削除・名前変更等すべて可能）
5. 1プリセットを複数チームにインポート可能（各チームに独立したコピーが作成される）
```

### JSON 集計のパフォーマンス戦略

```
1. Phase 6 初期実装: JSON_EXTRACT のまま
   a. 大半のチームは年間 100-500 件。JSON_EXTRACT で十分
   b. stats API にクエリタイムアウト（3秒）を設定
   c. タイムアウト時: 部分結果を返却 + warnings に "集計がタイムアウトしました" を含める
   d. レスポンスに query_time_ms を含めて監視指標にする

2. Phase 11 負荷テストで 1万件超のケースを検証
   a. 超過した場合の対策: activity_field_aggregates テーブル（日次バッチ集計）
      - template_id × field_key × date → sum / avg / max / min / count
      - 日次バッチ（AM 3:00）で前日分を集計して UPSERT
      - stats API はバッチ集計テーブルから読み取り（JSON_EXTRACT を回避）
   b. このテーブルは Phase 6 では作成しない（YAGNI 原則）
```

### Markdown サニタイズ方針

```
1. 保存: activity_results.description には Markdown テキストをそのまま保存
   - バックエンドでは HTML 変換しない
   - 最大 10,000 文字のバリデーションのみ

2. 表示（フロントエンド）:
   a. marked.js で Markdown → HTML に変換
   b. DOMPurify で sanitize（SSR 時は isomorphic-dompurify を使用）
   c. 許可タグ（ホワイトリスト）:
      p, h1-h6, ul, ol, li, a, strong, em, code, pre, blockquote,
      img, br, hr, table, thead, tbody, tr, th, td
   d. 禁止: script, iframe, form, input, style, on* イベントハンドラ
   e. a タグの href: http / https のみ許可。javascript: スキーム禁止
   f. img タグの src: https のみ許可（http 禁止。mixed content 防止）

3. 本方針の適用範囲:
   - activity_results.description（本機能）
   - blog_posts.body（F06.1）
   - bulletin_threads.body / bulletin_replies.body（F05.1）
   - 他の Markdown 対応フィールド全般
   → FRONTEND_CODING_CONVENTION.md に共通方針として追記すべき
```

### 重要な判定ロジック

- **Cursor ページネーション**: `cursor` は `{activity_date}_{id}` の複合キー。SQL: `WHERE (activity_date, id) < (:cursorDate, :cursorId) ORDER BY activity_date DESC, id DESC`。activity_date 順のソートと ID 順の作成が異なるケース（「昨日の活動を今日登録」等）で重複・スキップを防止
- **カスタムフィールドのバリデーション**: `POST /activities` 時に `activity_template_fields` の定義に基づき、`field_values` の各フィールドの型・必須・選択肢を検証。未定義の `field_key` は無視（将来のフィールド削除に対応）
- **テンプレート削除の影響**: 論理削除された `activity_templates` のフィールド定義は `activity_results` の `field_values` を表示する際に引き続き参照可能（JOIN で取得）。テンプレート削除後も既存記録の閲覧・編集は可能
- **JSON フィールドの検索**: `field_values` の JSON 内容での検索は `JSON_EXTRACT` + `WHERE` で可能だが、大量データではパフォーマンスに注意。全文検索が必要な場合は `description` カラムの FULLTEXT インデックスを活用
- **参加者のプリフィル**: 同一テンプレートの直近の活動記録から `activity_participants` を取得し、デフォルト選択として提示。レギュラーメンバーの入力手間を削減
- **SSR と公開記録**: `visibility = 'PUBLIC'` の記録は `/public/teams/{teamId}/activities` で認証不要のアクセスを提供。Nuxt 3 の SSR で `useFetch` を使用し SEO 対象に。LCP < 2.5s を維持
- **MEMBER の作成権限**: MEMBER は活動記録を作成可能（ただし自分が `created_by` の記録のみ編集・削除可能）。ADMIN / DEPUTY_ADMIN は全記録の編集・削除が可能
- **アクセス解析連携**: `page_view_logs` に `target_type = 'ACTIVITY_RECORD'` で自動記録。ダッシュボードの `TEAM_PAGE_VIEWS` ウィジェットに反映
- **テンプレートフィールド変更の安全性**: `field_type` / `field_key` の変更は禁止（既存 JSON データとの不整合防止）。`field_label` / `is_required` / `options_json` の変更は許可（新規記録のみ影響）。削除済みフィールドの値は「（削除済みフィールド）」として表示継続
- **添付ファイル**: `attachments.file_ids` で F05.5 の `shared_files` を参照。最大10ファイル。F05.5 のストレージ容量管理がそのまま適用
- **CSV エクスポート**: `template_id` 指定時はカスタムフィールドを個別カラムに展開。BOM 付き UTF-8。最大 5,000 件
- **JSON 集計パフォーマンス**: Phase 6 は JSON_EXTRACT で対応（クエリタイムアウト 3秒）。1万件超は Phase 11 で日次サマリーテーブルを検討（YAGNI 原則）
- **Markdown サニタイズ**: description は Markdown テキストで保存。HTML 変換 + サニタイズはフロントエンド（marked.js + DOMPurify）。バックエンドは最大文字数バリデーションのみ
- **活動記録の複製**: `POST /activities/{id}/duplicate` で前回の `field_values` / `participant_user_ids` / `visibility` / `description` をコピー。`file_ids` はコピーしない（共有ファイルの削除連鎖を防止）。複製結果は編集画面で確認後に保存
- **タイムライン自動投稿**: `post_to_timeline = true` で活動記録作成時に F04.1 タイムラインにサマリーを自動投稿。ApplicationEvent + 非同期 Listener で実装。PUT（編集）時は自動投稿しない
- **コメント機能**: `activity_comments` テーブルで活動記録への補足情報・フィードバックを管理。投稿者本人のみ編集可能、削除は投稿者 or ADMIN。作成者にプッシュ通知
- **テンプレート共有**: `POST /activity-templates/{id}/duplicate` で組織内の別チームにテンプレートをコピー。コピー元/先の両方の ADMIN 権限が必要
- **プリセットテンプレート**: `system_activity_template_presets` で SYSTEM_ADMIN がカテゴリ別の標準テンプレートを管理。`POST /activity-templates/import-preset` でチームにインポート。インポート後は通常のテンプレートとして自由に編集可能

## 6. セキュリティ考慮事項

- **認可チェック**: テンプレート管理は ADMIN / DEPUTY_ADMIN（`ACTIVITY_MANAGE`）。活動記録の作成は MEMBER 以上。編集・削除は作成者 or ADMIN。公開記録の閲覧は認証不要
- **スコープメンバーシップ検証**: 活動記録の作成・閲覧はスコープメンバーであること。非メンバーは 403（公開記録を除く）
- **参加者の検証**: `participant_user_ids` に含まれるユーザーがスコープメンバーであること
- **JSON Injection 防止**: `field_values` の JSON 入力は Service 層で構造を検証し、予期しないキーや深いネストを拒否
- **XSS 対策**: `description`（Markdown）はバックエンドでは Markdown テキストのまま保存（HTML 変換しない）。フロントエンドで marked.js → DOMPurify のパイプラインでサニタイズ。`field_values` の TEXT / TEXTAREA は API レスポンス時に HTML エスケープ
- **添付ファイルの検証**: `file_ids` に含まれる `shared_files` がスコープ内のファイルであること。他チームのファイルを添付不可（403）
- **レートリミット**: `Bucket4j` で以下の制限を適用
  - 活動記録作成: 1分間10件/ユーザー
  - テンプレート作成: 1分間5件/ユーザー
  - 統計 API: 1分間30件/ユーザー
  - CSV エクスポート: 1分間3件/ユーザー
  - コメント投稿: 1分間10件/ユーザー
  - テンプレート複製: 1分間5件/ユーザー
  - プリセットインポート: 1分間5件/ユーザー
  - 公開 API: 1分間60件/IP（認証不要のため IP ベース）
- **監査ログ**: 以下のイベントを記録
  - `ACTIVITY_TEMPLATE_CREATED`: テンプレート作成
  - `ACTIVITY_TEMPLATE_DELETED`: テンプレート削除
  - `ACTIVITY_CREATED`: 活動記録作成
  - `ACTIVITY_UPDATED`: 活動記録更新
  - `ACTIVITY_DELETED`: 活動記録削除
  - `ACTIVITY_EXPORTED`: CSV エクスポート（scope, template, 件数, 期間）
  - `ACTIVITY_DUPLICATED`: 活動記録の複製（source_id, new_id）
  - `ACTIVITY_TEMPLATE_DUPLICATED`: テンプレートのスコープ間コピー（source_id, target_scope）
  - `ACTIVITY_TEMPLATE_PRESET_IMPORTED`: プリセットのインポート（preset_id, target_scope）

## 13. 認証付き詳細と予定連携（CMP-261007-1510）

> 2026-10-07 御裁可済み。設計・実装検証中。以下は今回追加する契約の正本であり、旧章の設計例（snake_caseのJSON、予定完了時だけの作成、クロスドメインFK等）を今回の実装へ転用しない。実装・検証の完了状態とテスト証拠は `docs/task-list.md` のCMP-261007-1510、および戦役台帳を正本とする。

### 13.1 範囲・導線

対象はTEAM/ORGANIZATIONの認証付き活動記録。個人予定・COMMITTEE・出欠の継続同期は追加しない。チーム/組織一覧のカード・タイトル、下書き保存直後、予定詳細の関連記録から `/activities/{id}` へ進む。公開SSR `/activity/{id}` は公開APIだけを利用する既存ページとして維持し、認証情報・同期情報を渡さない。

活動詳細では本文、日時、テンプレート項目、参加者、添付、元予定を表示する。閲覧と編集・公開の可否を別に扱い、読取専用ユーザーには編集ボタンを出さない。取得中・正常な空欄・取得失敗を区別し、失敗時は再試行を表示する。一覧へ戻る導線は活動のtop-level scopePublicIdを用い、`/teams/{scopePublicId}/activities` または `/organizations/{scopePublicId}/activities` へ戻る。スコープ単票画面はslug専用のためraw numeric scopeIdからUI URLを組み立てない。元予定がない記録にもこの公開識別子を返す。元予定リンクは `/teams/{scopePublicId}/schedule?eventId={id}` または `/organizations/{scopePublicId}/schedule?eventId={id}` へ接続し、スコープ予定画面がqueryの予定IDを独立認可付きで取得して既存詳細パネルを開く。活動記録を予定として再作成・再登録せず、カレンダー件数を増やさない。

新詳細UIは編集・公開時に取得したversionを送る。DRAFTでtemplateId=nullの場合だけテンプレートを一度設定でき、設定後の変更は拒否する。省略/nullは維持であり既存テンプレートの解除ではない。公開時には設定済みテンプレートの必須項目と日時などの公開可能性をサーバーで再検証する。旧クライアントへversion必須化等の破壊的変更を加えるかはBEの既存契約と照合し、今回の新UIの必須送信と区別する。

### 13.2 詳細DTOと値の保全

`GET /api/v1/activities/{id}` の `ActivityDetailResponse` は既存 `ActivityRecordResponse` のcamelCaseキー・raw形式を維持し、以下の詳細項目を加算する。`fieldValues` はJSON文字列、`attachments` はJSON文字列またはnull（既存 `{ "file_ids": [101] }` 形式）。オブジェクト型への置換や公開DTOの拡張は行わない。予定参照DTOは `ActivitySourceScheduleResponse`。一覧取得に詳細の参加者・項目定義を混在させない。

| キー | 型・null | 意味 |
|---|---|---|
| `activityEndDate` | ISO日付文字列またはnull | 跨日終了日。同日または終了未指定はnullで、表示・比較時は開始日を基準に解釈 |
| `scopePublicId` | string、非null（今回のTEAM/ORGANIZATION） | 活動の実scopeのslug。NameResolverService.resolveScopeSlugで解決し、元予定なしの一覧戻り先にも使用 |
| `version` | number、非null | 活動の楽観ロック値 |
| `canEdit` | boolean、非null | 現在の利用者の実効活動編集権 |
| `canPublish` | boolean、非null | 実効公開権かつDRAFT |
| `sourceSchedule` | 認可済み予定参照またはnull | 状態はAVAILABLE/CANCELLED/UNAVAILABLE。元予定の閲覧権を独立確認。可視時だけscopePublicIdで公開識別子を返す |
| `participants` | `ActivityParticipantResponse[]` | 正常な0名は空配列 |
| `templateFields` | `ActivityTemplateResponse.TemplateFieldResponse[]` | 定義なし/テンプレート消失/活動とテンプレートの実scope不一致は空配列 |

活動更新のfieldValuesは省略/nullで既存値を保持し、明示オブジェクトで更新する。fileIdsも省略/nullで既存添付を保持し、明示 `[]` は添付解除とする。未送信と削除を混同して既存結果/添付を消さない。

跨日活動の複製では、元の開始日から終了日までの日数差を複製先のactivityDateへ加算し、activityEndDateを移す。例えば15日23時から16日1時の活動を20日に複製した場合は21日1時までとし、終了時刻が同日開始前になる欠損を防ぐ。終了日nullはnullを維持する。複製先には元予定のscheduleIdとscheduleSyncStateを引き継がない。

raw値のJSON解析は正常な空値と解析失敗を区別する。`0` と `false` を空欄へ変換せず、null・空文字・空配列・空オブジェクトは各値の意味を維持する。テンプレートが削除された/項目定義が失われた場合も、保存済みフィールドキーと値を表示し、未知の型でクラッシュしない。本文Markdownは既存のサニタイズ部品を利用し、raw HTMLを直接描画しない。添付IDは既存ファイル閲覧認可を通し、別スコープのIDを渡してURLを取得できないことを検証する。参加者の名前解決は詳細DTOでまとめて取得し、人数分のAPI/SQL呼び出しを作らない。添付は最大10件の既存ファイル単体認可APIを利用し、今回bulk APIを新設しない。

### 13.3 予定からの下書き作成

`POST /api/v1/activities/draft-from-schedule?scope_type=TEAM|ORGANIZATION&scope_id={numericId}`、`CreateDraftFromScheduleRequest` のbodyは `{ "scheduleId": 10 }` のみ。クライアントがタイトル・日時・参加者の値や更新日時を送ってコピー元を偽装できない形にする。

サーバーは元予定の閲覧権、path/queryスコープとの一致、活動作成権を確認し、予定行をロックして最新値を取得する。同じ予定に紐づく生存記録を再照合し、既存の閲覧可能記録があれば再利用する。不可視記録の存在を利用者へ漏らすID・本文・件数を返さず、opaqueな競合とする。連打・同時要求は予定行で直列化し、新規記録を二重作成しない。既存のscheduleId指定通常POST作成経路も同じ予定ロック・重複照合を経由させ、別APIからの競合を防ぐ。ただし本文/fieldValues等の入力を伴う通常POSTは既存記録を200で再利用せず409を返し、未保存入力とローカル下書きを保全する。scheduleIdのみのdraft-from-scheduleだけが可視既存記録を200で再利用する。無関係な既存記録の削除・統合・一意制約追加を行わない。

新規時は `status=DRAFT`、`visibility=MEMBERS_ONLY`、`templateId=null` とし、タイトル、開始日、開始時刻、終了日、終了時刻をサーバーでコピーする。終日予定は時刻null。`endAt=null` は終了日・終了時刻null。跨日予定は `activityEndDate` で日付を保持し、終了時刻だけ切り出して同日扱いにしない。日時変換は既存予定のJST保持基準に従い、ブラウザTZ依存のISO文字列切り出しを行わない。

出席予定者は作成時点の `ATTENDING` を重複なしで既存 `activity_participants` へ初期投入する。PARTIAL/ABSENT/UNDECIDEDは含めず、未回答・0名でも作成できる。以後の出欠回答変更は参加者へ追従させない。本文・結果・添付は予定からコピーしない。

実参加者は活動編集権を持つ編集者が詳細画面で明示編集できる。予定との自動同期では変更しない。参加者必須テンプレートのDRAFTは参加者を選択・保存してから公開できる導線を持ち、参加者未指定の公開を許可して制約を回避しない。既存参加者のroleLabelは参加者集合の更新で失わない。

### 13.4 同期基準とDDL

新テーブル、クロスドメインFK、参加予定者専用JSONは作らない。既存 `schedule_id` と `idx_ar_schedule` を再利用する。追加DDLは以下の既存表ALTERのみとする。migration名は規約に従う `V236.20261007094759__activity_schedule_sync_state.sql` に確定した。

```sql
ALTER TABLE activity_results
  ADD COLUMN activity_end_date DATE NULL,
  ADD COLUMN schedule_sync_state JSON NULL,
  ADD COLUMN version BIGINT NOT NULL DEFAULT 0;
```

`ActivityResultEntity.version` はJPA `@Version`。本文編集、公開、参加者の追加削除を含む活動変更は同一親versionを進める。子行だけ変更して親versionが据え置きになる経路を残さない。新詳細UIは取得したversionを必ず送信して比較し、既存APIのversion未指定互換はBE契約に従う。既存呼出元、DTOコンストラクタ、テストfixtureを同じ変更で対応する。公開APIはversionを返さない。

同期stateはJSONオブジェクトに固定項目の `baseline` と `manualFields` を保持する。baselineのキーは `title/activityDate/activityEndDate/activityTimeStart/activityTimeEnd`、manualFieldsは手動変更済みキーの集合（JSON配列）とし、汎用フィールド同期機構へ拡張しない。既存レコードはstate=nullを維持して由来不明として扱い、自動同期へ誤移行しない。stateは内部管理情報で、公開DTO/通常一覧に含めない。

手動編集は保存前の値との差で該当キーをmanualFieldsへ記録する。一度変更後に元へ戻しても手動変更済みを維持する。同じ値を送っただけで手動変更済みにしない。同期適用は手動編集の業務メソッドと分離し、自動適用自身がmanualFieldsを増やさない。baselineは反映したキーだけ新しい予定値へ更新し、据え置いたキーの基準値と活動値は保持する。差分を手動選択で反映しても既存manualFieldsを解除せず、次回も選択確認を必要とする。state=nullの旧記録を選択同期しても、未選択項目を自動同期可能へ転換しない。

同期対象はこの5具体フィールドだけ（要件上の「タイトル・日付・開始終了時刻」を跨日終了日を含めて保持する）。location、本文description、結果fieldValues、attachments、実参加者、visibility、templateIdは対象外。汎用の `updateActivity` にnullの本文・添付を渡して消す経路を使わず、Entityの専用同期メソッドで選択項目だけ変更する。

| 状態 | 予定変更の扱い |
|---|---|
| DRAFT、stateあり、manualFieldsにない、現在値もbaselineと一致 | 予定由来の未編集項目として自動反映 |
| DRAFT、手動変更済み/現在値がbaselineと不一致 | 差分選択確認。現在の活動値を既定で維持 |
| PUBLISHED | 全差分を選択確認。自動反映しない |
| state=nullの既存リンク記録 | 由来不明。差分選択確認で扱う |
| 閲覧権または活動編集権なし | 活動を変更しない。不可視記録の差分・ID・件数を返さない |

`expectedScheduleState` は `{updatedAt,title,startAt,endAt,allDay,status,schedules:[{id,updatedAt,title,startAt,endAt,allDay,status}]}`。schedulesは更新対象全予定の状態・ID集合を保持し、単発でも1件配列を返す。updatedAtだけでは秒精度の同時更新を検出できないため、同一日時基準・DB精度に正規化した全状態を予定行ロック下で完全比較する。選択予定のみ比較して兄弟予定のpreview後変更を見落とさない。ExpectedScheduleState/ExpectedScheduleEntryのupdatedAt/startAt/endAtと内部ScheduleActivitySourceはOffsetDateTimeを境界型とし、既存SERVER_ZONE（Asia/Tokyo）へ明示投影した+09:00のdate-time文字列を返す。確認tokenは異なるoffsetでも同一instantへ正規化してDBの秒精度で比較し、活動の暦日・時刻と終日の排他的終了日はJST基準で解釈する。クライアントはtokenを不透明な値として返送し、ブラウザ表示文字列そのものを比較しない。予定全体への@Version移行は今回行わない。activity側は各versionを比較し、対象記録ID集合の追加・削除も再検証する。previewで見ていない差分が増えた場合は409とし、確認していない値を追加適用しない。未知フィールド・重複ID・他予定IDの選択は入力不正として拒否する。

繰返し `THIS_ONLY/THIS_AND_FOLLOWING/ALL` は既存 `ScheduleRecurrenceService` が求める更新予定ID集合と同じ範囲を扱う。選択元の1件だけ同期して兄弟記録を取り残さない。プレビューと保存の対象予定集合/活動集合が変化した場合も409。終了日・開始終了時刻の選択を合成した後に、終了日時が開始日時を下回らないことを検証する。null終了・終日切替・日付変更で古い終了日が残るケースを検証する。

予定保存と活動同期は単一のユーザー操作として同じDBトランザクションで確定し、途中のDB/変換/検証失敗では全体をrollbackする。認可・プレビューの段取りは非TXファサード、原子的書込みは共通orchestrationの専用Beanに分離し、既存Serviceの書込みが同じTXへ参加する構成を用いる。ドメインRepositoryへの直接依存を追加せずService経由とし、D3/D3T等のアーキテクチャ番人に適合させる。凍結例外の追加で通さない。原子的TXの理由をコードと本節に明記する: **利用者が確認した予定変更と活動差分を一体で保存し、片側だけ成功する状態を許さないため**。この処理をAFTER_COMMITの非同期活動同期へ置換するとAC-15を満たさない。通知・外部カレンダー連携等の副作用は既存のAFTER_COMMIT境界を維持する。

取消・論理削除・繰返し系列削除では活動記録とscheduleIdを保持し、活動本文・参加者を変更しない。元予定が削除済み/未認可なら参照先を利用できない表示とし、秘匿すべきID・scopeId・本文・取消理由を返さない。元予定の閲覧権を持つ場合だけ取消状態を表示する。

### 13.6 認可・HTTP契約

新規APIは認証必須。予定閲覧/管理は既存Scheduleのscope・F00可視性判定、活動閲覧は既存Activityのscope membershipと記録の可視性判定、活動編集は作成者または当該scope管理者という既存境界へ委譲する。予定管理権だけで活動編集を許可しない。DRAFTはscope membershipを満たす作成者またはscopeのADMIN/DEPUTY_ADMINに限り閲覧でき、SYSTEM_ADMINだけを理由に非所属scopeのDRAFTを表示しない。FEのボタン非表示だけで認可を代替しない。

既存の予定PATCHは互換性を維持し、URLのscopeではなく予定の実scopeに対する管理認可を先に行う。認可後に実scopeのDTOを取得し、TEAM/ORGANIZATIONの予定だけをその実scopeで活動同期へ投影する。PERSONAL予定は従来の所有者認可（SYSTEM_ADMINの既存例外を含む）を経て、従来の予定writerへ委譲し活動同期を行わない。この既存PATCHの契約を、新規のdraft-from-schedule・linked活動一覧・activity-sync-previewへ適用しない。これらの新入口はURLのscopeと予定の実scopeの一致および予定の可視性を厳格に確認し、既存の不一致時404等の秘匿契約を維持する。

成功はApiResponseの `data` ラップ。未知applyField/重複applyField/重複選択ID等の入力不正は `COMMON_001`（400）、未認証401、権限不足403、対象不在/参照スコープ不一致/存在秘匿404。不可視の既存リンクとの作成競合は `ACTIVITY_009`（409）、同期確認が必要な場合は `ACTIVITY_022`（409）、古い予定state・予定/活動の対象集合不一致は `ACTIVITY_023`（409）、activity version不一致は既存 `COMMON_003`（409）とする。クライアント起因ErrorCodeは `Severity.WARN` とし、必要な404/409だけGlobalExceptionHandlerへ明示登録する。DB障害等は500で伝播させ、正常な空配列や参照なしへ握り潰さない。新ErrorCode採番は既存enumの最大番号と同一概念の兄弟コードを調べて重複を避ける。

活動の更新・公開・参加者追加削除はcommonの外側TXで既存getActivityのmembership/閲覧認可、作者/adminの編集認可、version検証、writerの順に実行する。同scopeでも非作者かつ非adminの他者DRAFTは存在秘匿404とし、誤ったversionでも409を先に返さない。閲覧可能なPUBLISHEDを同利用者が編集する場合は403とする。

### 13.7 移行・性能・画面実装

Flywayは `V{origin/mainの最大major+1}.{UTC yyyyMMddHHmmss}__{説明}.sql` で採番し、既存migrationを書き換えない。既存行に終了日NULL・stateNULL・version0を追加し、本文/添付/参加者/scheduleIdを変更しない。全件JSON構築・予定とのクロスドメインJOINによる履歴推定・既存重複リンクの自動削除を行わない。実Flyway/MySQLで新旧行のCRUD、@Version409、跨日終了日、NULL移行を検証し、ddl-auto=createのみの自己整合を合格証拠にしない。

一覧は既存page/limit方式と公開一覧の契約を維持する。詳細の定義取得・参加者取得は記録単位でまとめ、名簿の人数分N+1を追加しない。予定リンク逆引きは既存idx_ar_scheduleを使い、全活動スキャンを行わない。繰返し複数予定を取得するときもID集合でまとめて取得する。操作件数・SQL/API本数を小規模/複数記録/参加者増加の条件で比較し、既存ページングの既知問題を今回の無関係な変更へ広げない。

表示文言はactivity/scheduleの6言語ja/en/zh/ko/es/deへ追加し、直書きしない。エラー・再試行・空欄・取消済み・参照利用不可・差分選択・競合文言も対象とする。既存共通フォーム/ダイアログ/Markdown/ファイル部品を利用する。OpenAPIはBEから再生成、生成型はnpm generate:typesで再生成し、手編集しない。

### 14.2 状態遷移と原子性

- 予定作成とauto記録作成は共通orchestrationの単一TX。具体予定一件を単位にする。繰返し親に記録を作らず、生成された各具体子予定で同じ入口を通す。繰返し生成側の既存rollback契約は弱めない。
- 同じschedule lockでauto/manual全作成入口を直列化する。既存リンクを尊重し、manualをautoへ再分類しない。削除済みauto履歴が同予定・同実scopeにあれば自動生成を行わない。通常POSTの重複409、入力を持たないdraft-from-scheduleの既存可視記録再利用という互換契約を維持する。
- バッチは毎分、ShedLockで多重起動を抑止。候補はSCHEDULED、endAt非nullかつ厳密にendAt<now、未削除、繰返し親でないもの。既存SERVER_ZONEとClockを使い、端末時刻を正本にしない。
- 候補取得後、行lock下で最新status/endAt/deletedAt/繰返し親条件を再確認。同一TXでCOMPLETEDとauto記録isPlanned=falseを保存。本文・結果・添付・実参加者・公開状態は変更しない。削除済み活動を復元しない。
- endAt==nowは対象外、直後は対象。終了nullは予定のまま（終了時刻を設定するまで自動完了しない）。終日exclusive終了・JST跨日・秒精度を維持する。
- 未完了の延期は最新endAtを参照。COMPLETED予定を未来へ延期する更新ではSCHEDULEDへ戻し、未削除auto記録isPlanned=true。PUBLISHED実績の値・本文は自動上書きせず既存同期選択規則を適用する。

metadataOnly=trueではcanEdit/canPublish/canDelete=false、description/fieldValues/attachments/templateId/createdBy/location/venue=null、participants/templateFields=[]。作成者名等のPIIも返さない。title/activityDate/activityEndDate/activityTimeStart/activityTimeEndは認可済み元予定projection、会場を未公開actualから流用しない。autoGeneratedFromSchedule/isPlanned/metadataOnlyはraw/list/detailにnon-null booleanで追加し、canDeleteは詳細だけ。既存raw型のcreatedBy等はmetadata projectionのnull許容をOpenAPIで明示し、0や偽名で代替しない。full DTOの既存JSON文字列・manual内容は維持する。BE exact契約を生成OpenAPIと照合し、nullを異常扱いする旧FE実装が残らないことを確認する。

DDL案は is_auto_generated_from_schedule BOOLEAN NOT NULL DEFAULT FALSE、is_planned BOOLEAN NOT NULL DEFAULT FALSE。既存schedule_id/index/version/sync_stateを利用し新テーブル・FKを作らない。wire名はautoGeneratedFromSchedule/isPlanned。server-onlyで更新DTOから書き換えない。具体migration filenameはBE隊がorigin/main最大major+1とUTC yyyyMMddHHmmssで採番し、設計と実ファイルを照合する。

| 新規具体予定 | SCHEDULED | true | DRAFTを作成、本文等を自動生成しない |

#### 実在する統計・CSV・コメントの関連認可（AC36）

origin/main ActivityStatsControllerは/stats、/stats/fields、/exportを実装済み。ActivityStatsServiceはcountByScope/countByTemplate、findForExportから参加者を取得し、CSVは日付・タイトル・参加者数・作成者IDを出力する。これらを未実装扱いしてauto認可対象から外さない。auto actual非可視を同じpredicateで件数・集計・CSV候補から除外する。既存manualを一律に再認可する機能拡張は行わず対照を保持する。

### 14.9 採用構成と実装照合

作成入口は具体予定の同期保存イベントをcommon orchestrationで処理し、呼出TXへの参加（MANDATORY）でpure activity writerへ委譲する案を採用する。予定ドメインから活動Repositoryへ直依存せず、非同期/AFTER_COMMITでauto本体を作らない。各具体子一件が原子的であり、共通lock順序を維持する。イベント/handlerの具体名称と実アーキテクチャ番人結果はBE隊成果へ照合する。
