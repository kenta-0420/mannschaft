## 1. 概要

Mannschaft はマンション管理組合のチーム機能を実装済だが、住民・理事に対する **長期視点の可視化** が未整備である。「いつ積立金が枯渇するか」「過去20年で何にいくら使ったか」「今いくつ修繕案件が走っているか」「次の理事に何を引き継ぐか」が散在しており、総会での合意形成・歴史の継承（輪番制で失われる課題）に支障が出ていた。

本機能は既存基盤 **F08.6 budget_accounting**（修繕積立金収支）と **F09.13 property_history**（修繕履歴台帳）にデータが既に蓄積されている事実を前提に、**新規ドメインは作らず、既存の上に「可視化・シミュレーション・引き継ぎ」レイヤーを薄く乗せる** 統合ダッシュボードを提供する。

### 採用機能（5機能）

| # | 機能 | 概要 | 流用基盤 |
|---|---|---|---|
| 案1 | 積立金枯渇シミュレーター + 世代別メーター | 月額・物価上昇率・延期年数・徴収額・借入金元利のスライダーで `balance(t)` を再計算し、世代帯別の信号機メーターを表示 | F08.6 拡張 |
| 案3 | 修繕履歴の地層タイムライン | chart.js stacked bar で年度×部位×金額を地層化、当時の理事長・議事録IDをレイヤートグル | F09.13 拡張 |
| 案4 | 相見積もりカンバン | F12.5 Kanban基盤を流用し業者見積を `REQUESTED→RECEIVED→UNDER_REVIEW→SHORTLISTED→SELECTED` の6stage で管理 | F12.5 Kanban |
| 案5 | 修繕計画項目リスト ★追加 | 30年長期修繕計画の予定項目テーブル。シミュレーターの予定支出ソース＋案4 カンバンの親案件 | 新規 |
| 案7 | 次の理事への申し送りパック | 任期終了月 cron で当年度の決定/未解決/進行中/シナリオを集約 → PDF → R2 PUT → 後任通知 | 新規 |

### 対象外機能

| 案 | 機能 | 不採用理由 |
|---|---|---|
| 案2 | 健康診断マップ（マンション部位別リスク可視化） | **対象外**。マンションごとに構造・部位データが過大に異なり、汎用化困難。各マンション固有の構造図・劣化診断はスコープ外（外部の建物診断サービスを推奨） |

### 設計方針

- **新規ドメインは作らず可視化レイヤーのみ追加**: 既存 F08.6 / F09.13 を改変せず、ビュー（read-only view）と新規9テーブルで統合
- **クロスドメインFK禁止**: F08.6 / F09.13 / **users** / teams への ID 参照のみ。FK 制約は本ドメイン内に閉じる
- **3スコープモデル踏襲**: SYSTEM テンプレ → ORG → TEAM の3層オーバーライド（修繕周期マスタ）
- **マンション管理組合専用テンプレート**: 一般テンプレート化は非目標

### 住民閲覧時の3段階 visibility

業者名・金額の機密性レベルを管理組合が設定可能：

| レベル | 業者名 | 金額 | 用途 |
|---|---|---|---|
| `HIDDEN` | 非表示 | 非表示 | 入札期間中・極秘案件 |
| `ANONYMIZED` (デフォルト) | 「業者A/B/C」匿名化 | 100万円単位レンジ（例: 「200〜300万円台」） | 通常運用（住民信頼の透明性 vs 業者保護のバランス） |
| `FULL` | 業者名フル開示 | 円単位フル表示 | 総会承認後・履歴公開時 |

#### 相見積もりカンバン読み取りの認可（実装仕様・2026-06 セキュリティ根治）

業者見積カンバンの読み取り（`GET /quote-kanbans` 一覧 / `GET /quote-kanbans/{kanbanId}` 詳細）は、**メンバーシップ検証 → ロール別マスキング** の二段で認可する。実装は `RepairPlanQuoteKanbanController#checkReadAccess` と `RepairPlanQuoteKanbanService#resolveIsAdmin`。

| 閲覧者の立場 | アクセス | 業者名・金額 |
|---|---|---|
| **SYSTEM_ADMIN** | 全スコープ横断で許可 | FULL（マスクなし） |
| **当該 scope の ADMIN / DEPUTY_ADMIN**（理事長・理事 MANAGE 相当） | 許可 | FULL（マスクなし） |
| **一般メンバー（MEMBER）** | 許可 | `visibility_to_member` と入札締切に従いマスク（HIDDEN=非表示 / ANONYMIZED=匿名ラベル＋レンジ / 締切前は visibility に関わらず業者名・金額を非表示） |
| **非メンバー（当該 scope 未所属の認証ユーザー）** | **遮断（`COMMON_002` / 403 相当）** | — |

- 認可ヘルパは標準認可基盤 `common.AccessControlService`（`checkMembership` / `isSystemAdmin` / `isAdminOrAbove`）に委譲する。書き込み系（作成・更新・カード追加・stage 遷移）が用いる `checkAdminOrAbove` と同一基盤。
- マスキングの管理者判定は **カンバンごとの実 scope（`scope_type` / `scope_id`）** に対して評価する。「認証済みなら一律フル表示」「Service は全件返して呼び出し元でフィルタ」という前提は採らない（非メンバー・一般メンバーへの業者名・金額漏洩の根本原因であったため撤廃）。

> 根治前は Service の `isAdminRole()` が認証さえあれば無条件 `true` を返し、read Controller にメンバーシップ検証が無かったため、非メンバーを含む任意の認証ユーザーが HIDDEN/匿名化/締切前の業者名・金額を素通しで取得できる漏洩があった。本仕様でこれを遮断する。

### 退会済元理事のフィルタリング

退会済元理事は **在任期間内データのみ閲覧** 可能。`viewer_active_term` ビューで `term_start ≤ data.created_at ≤ term_end` の条件で絞り込む（区分所有法 42 条の議事録閲覧権の延長として実装）。

### 対象テンプレート

`apartment` テンプレートを選択した組織・チームに `repair_longterm_plan` モジュールが推奨自動有効化される。`apartment` 以外では UI を非表示。

#### 非 apartment テンプレート組織での扱い

本機能はマンション管理組合（`apartment` テンプレ）固有の業務概念（区分所有法・修繕積立金・理事会任期制）に依存するため、**非 apartment 組織では `repair_longterm_plan` モジュールを有効化できない**。仮にオプトイン有効化 API を叩いた場合は **HTTP 422** で拒否する（エラーコード `REPAIR_PLAN_013: TEMPLATE_NOT_APARTMENT`）。修繕周期マスタ（`repair_plan_templates` SYSTEM seed）は国交省マンション標準長期修繕計画ガイドライン準拠であり、他業種（自治会・社宅管理・一般企業）では意味を成さないため、誤適用を物理的に阻止する。

**インデックス**
```sql
INDEX idx_rss_scope (scope_type, scope_id, deleted_at, created_at DESC)
INDEX idx_rss_locked (scope_type, scope_id, locked_at)
INDEX idx_rss_published (published_announcement_id)
```

**制約**

- `content_sha256` は `SHA-256(params_json || computed_summary_json || engine_version)` で算出

### 読み取り専用ビュー

```sql
-- v_repair_fund_balance: 積立金現在残高（F08.6 を改変せず参照）
CREATE OR REPLACE VIEW v_repair_fund_balance AS
SELECT
  bt.scope_type,
  bt.scope_id,
  SUM(CASE WHEN bt.transaction_type = 'INCOME' THEN bt.amount ELSE -bt.amount END) AS balance,
  MAX(bt.transaction_date) AS as_of_date
FROM budget_transactions bt
INNER JOIN budget_categories bc ON bt.category_id = bc.id
WHERE bt.deleted_at IS NULL
  AND bt.approval_status = 'APPROVED'
  AND bc.name LIKE '%修繕積立金%' -- カテゴリ命名規約
GROUP BY bt.scope_type, bt.scope_id;

-- v_repair_fund_yearly_summary: 年度別収支サマリ
CREATE OR REPLACE VIEW v_repair_fund_yearly_summary AS
SELECT
  bt.scope_type,
  bt.scope_id,
  bfy.id AS fiscal_year_id,
  bfy.name AS fiscal_year_name,
  SUM(CASE WHEN bt.transaction_type = 'INCOME' THEN bt.amount ELSE 0 END) AS total_income,
  SUM(CASE WHEN bt.transaction_type = 'EXPENSE' THEN bt.amount ELSE 0 END) AS total_expense
FROM budget_transactions bt
INNER JOIN budget_fiscal_years bfy ON bt.fiscal_year_id = bfy.id
WHERE bt.deleted_at IS NULL AND bt.approval_status = 'APPROVED'
GROUP BY bt.scope_type, bt.scope_id, bfy.id, bfy.name;

-- v_repair_plan_summary: F09.14 重説書からの参照用
CREATE OR REPLACE VIEW v_repair_plan_summary AS
SELECT
  rpi.scope_type,
  rpi.scope_id,
  rpi.planned_year,
  rpi.category,
  COUNT(*) AS planned_count,
  SUM(rpi.estimated_amount) AS total_estimated
FROM repair_plan_items rpi
WHERE rpi.deleted_at IS NULL AND rpi.status IN ('PLANNED','IN_PROGRESS','DEFERRED')
GROUP BY rpi.scope_type, rpi.scope_id, rpi.planned_year, rpi.category;
```

### 5.1 シミュレーション計算式

```
balance(t+1) = balance(t)
             + monthly_fee × dwelling_units × 12 × (1 + reserve_inflation_rate)^t
             - Σ planned_repair(t) × (1 + cpi_inflation_rate)^t × deferral_factor(t)
             - fixed_management_cost(t)
             ± loan_repayment(t)
```

| 変数 | 説明 |
|---|---|
| `monthly_fee` | 戸あたり月額修繕積立金（円） |
| `dwelling_units` | 戸数（F09.1 ResidentRegistry または手入力） |
| `reserve_inflation_rate` | 月額の年率上昇率（自動値上げシナリオ） |
| `planned_repair(t)` | repair_plan_items の年度別予定支出 |
| `cpi_inflation_rate` | 物価上昇率（デフォルト 1.5%、国交省R5） |
| `deferral_factor(t)` | 延期年数による調整係数 |
| `fixed_management_cost(t)` | 管理費等の固定費 |
| `loan_repayment(t)` | 借入金元利返済（任意・災害特別修繕積立金等） |

スライダー5本: 月額・物価上昇率・延期年数・徴収額・借入金元利。`engine_version` は計算式変更時にインクリメント、過去シナリオは旧 engine で再現可能。

### 5.2 世代別メーター

居住者の年代帯（20s〜70s+）×枯渇予測年で SEVERE/MODERATE/SAFE を判定。

| 年代帯 | 判定基準 |
|---|---|
| `20s`/`30s` | 枯渇予測年が居住予想期間（30〜40年）内なら SEVERE |
| `40s`/`50s` | 枯渇予測年が10〜20年以内なら SEVERE、20〜30年以内なら MODERATE |
| `60s`/`70s_plus` | 枯渇予測年が10年以内なら MODERATE、それ以降なら SAFE |

**`computed_summary_json` の世代別構造例**:

```json
{
  "depletion_year": 2041,
  "generation_meters": {
    "20s":   { "current_avg_age": 28, "age_at_depletion": 43, "impact": "MODERATE" },
    "30s":   { "current_avg_age": 35, "age_at_depletion": 50, "impact": "MODERATE" },
    "40s":   { "current_avg_age": 45, "age_at_depletion": 60, "impact": "SAFE" },
    "50s":   { "current_avg_age": 55, "age_at_depletion": 70, "impact": "MODERATE" },
    "60s":   { "current_avg_age": 65, "age_at_depletion": 80, "impact": "SEVERE" },
    "70s+":  { "current_avg_age": 75, "age_at_depletion": 90, "impact": "SEVERE" }
  }
}
```

**プライバシー保護**: 生年そのものは保存せず**年代帯と平均年齢のみ**を保存。GDPR 観点で個人特定リスクを排除（k-匿名性 k≥5 を年代帯バケット化で確保）。

### 5.3 Kanban 状態遷移

```
REQUESTED → RECEIVED → UNDER_REVIEW → SHORTLISTED → SELECTED
                                    ↘
                                     → REJECTED（任意）
```

- 前進のみ可（後戻りは取り消しモーダル経由）
- `SELECTED` 確定時に Service 層経由で `property_work_packages.selected_vendor_id` を更新（クロスドメイン更新は Service 経由のみ）
- `bid_deadline_at` 後でないと業者間比較ビューは解放されない（Repository 共通フィルタで `vendor_id != requester.vendor_id` の見積行 SELECT 不能）

### 5.4 申し送りパック生成フロー

```
1. cron が毎月実行: term_end - 30 日のレコードを抽出 → 理事長に「申し送り作成依頼」通知
2. 理事長が POST /handover-packs を呼ぶ（または cron で自動キック）
3. 非同期ジョブ（@Async("repair-plan-pdf-pool")、Bulkhead 組織同時3並列）:
   a. 当年度の決定/未解決/進行中/シナリオを集約（v_repair_fund_yearly_summary + repair_plan_items + scenarios + property_work_packages）
   b. OpenPDF で PDF 生成（NotoSansJP・パスワード保護）
   c. SHA-256 算出 → repair_plan/{scope}/{id}/packs/{packId}/{sha256}.pdf として R2 PUT
   d. board_handover_packs を UPDATE（pdf_r2_key, pdf_sha256, status=COMPLETED）
   e. 後任理事に通知（パスワードは別経路: SMS/メール別経路）
4. cron が term_end + 90日経過した team_member_terms.is_active を FALSE に更新（demote）
```

**透かし**: ダウンロード時に動的に「閲覧者ロール透かし」（`for: 田中理事 / 2026-05-09 14:32`）を埋め込む。同じパックでも閲覧者ごとに別ファイルとして配布。

### 5.5 退会済元理事の閲覧フィルタ

```sql
-- viewer_active_term ビュー（実装はサービス層 + Specification）
SELECT *
FROM repair_plan_items rpi
INNER JOIN team_member_terms tmt
  ON tmt.scope_type = rpi.scope_type AND tmt.scope_id = rpi.scope_id AND tmt.user_id = :viewer_id
WHERE rpi.created_at BETWEEN tmt.term_start AND tmt.term_end
  AND rpi.deleted_at IS NULL;
```

退会済元理事は `users.deleted_at IS NOT NULL` でも上記ビューでアクセス可能（区分所有法 42 条準拠）。

### 5.6 GDPR 退会者対応

ユーザー退会時:
1. `users` テーブルは F12.3 の方針に従い匿名化（氏名→「元理事A」）
2. 既発行の `board_handover_packs.pdf_r2_key` には旧氏名が PDF 内に焼き付けられている
3. 再生成 API: `POST /handover-packs/{packId}/regenerate-anonymized` で `pii_level=ANONYMIZED` 版を生成し、旧 PDF は R2 削除
4. F12.3 GDPR バッチが本機能の `external_agent_delegations.agent_user_id` 等も匿名化対象に含める

### 5.7 シナリオ → 告知変換（議案変換）

```
1. 理事長が POST /scenarios/{id}/publish-as-announcement を呼ぶ
2. Service 層:
   a. scenario の content_sha256 を再計算して整合性チェック
   b. repair_simulation_scenario_versions に INSERT（version_no = MAX+1, locked_at=NOW）
   c. repair_simulation_scenarios.locked_at をセット（以降 UPDATE 禁止・DBトリガで保証）
   d. F02.8 dashboard_announcements に DRAFT で INSERT（content に scenario サマリ + 議案番号）
   e. 監査ログ SCENARIO_LOCKED_FOR_PROPOSAL / SCENARIO_PROPOSAL_CONVERTED 記録
3. F02.8 側で理事長が告知を最終確定 → 住民配信
```

### 5.8 計算基準日ドリフト警告

`baseline_at` から30日以上経過したシナリオを再計算試行する場合、UI に警告バナーを表示し、再計算を促す。再計算しない場合は閲覧専用とする（編集は新シナリオ作成）。

### 5.9 修繕積立金値上げ決議要件の自動判定

区分所有法に基づき:
- **過半数決議**: 通常の積立金変更
- **4分の3決議**: 規約変更を伴う大幅変更（例: 戸あたり月額が現行の 1.5 倍超）

UI 上で値上げシナリオに対して必要決議要件を自動表示（参考情報として、最終判断は管理組合）。

### 5.10 災害特別修繕積立金シナリオ

シミュレーターに「災害シナリオ」テンプレ（地震・台風被害想定の臨時支出）をプリセット。`loan_repayment(t)` を活用し復旧借入金返済をシミュレート可能。

### 5.11 建替え決議成立時の処理

区分所有法 62 条建替え決議が成立した場合:
1. `migration_handover_pack` 一括生成（全任期分の handover_pack を集約した PDF）
2. 旧データは10年凍結保存（物理削除しない・読み取り専用化）
3. 新管理組合のための引継ぎパックとして R2 に保管

## 6. セキュリティ考慮事項

| 観点 | 対策 |
|---|---|
| **IDOR** | 全 API 入口で `scope_type+scope_id × currentUser` 所属検証（既存 `MembershipResolver` 流用）。`/quote-cards/{id}/move` は card → kanban → package → scope を辿る `RepairScopeGuard` を新設 |
| **業者間漏洩** | 入札締切（`bid_deadline_at`）後のみ比較ビュー解放。Repository 共通フィルタで `vendor_id != requester.vendor_id` の見積行は SELECT 不能。`bid_token_hash` で外部業者の見積投函を一意化 |
| **シミュレーション DoS** | Bucket4j 20req/min/user・100req/min/scope。同一 input ハッシュ60秒キャッシュ（Valkey）。`Bulkhead` で `simulation-pool` 隔離（同時実行 4） |
| **PDF 漏洩追跡** | 「閲覧者ロール透かし」（`for: 田中理事 / 2026-05-09 14:32`）埋込・SHA-256 でバージョン管理。ダウンロードごとに `audit_logs.PACK_DOWNLOADED` 記録 |
| **GDPR** | 退会者氏名 → 「元理事A」匿名化置換、決定記録は区分所有法 42 条で法定保持。F12.3 GDPR バッチに本機能の対象テーブルを登録 |
| **改ざん検出（F09.14準拠）** | `scenarios.content_sha256` + `scenario_versions` 不変＋DBトリガ `BEFORE UPDATE WHEN locked_at IS NOT NULL` で UPDATE 拒否 |
| **R2 命名（F13 Phase 5準拠）** | `repair_plan/{scopeType}/{scopeId}/{scenarios|bids|packs}/...`。業者見積は業者プレフィックスで Cloudflare Worker 認可（業者間アクセス分離） |
| **simulate API 監査ログ抑制** | 保存系（CREATE/UPDATE/DELETE）のみ記録。`/simulate` は記録しない（爆発防止） |
| **反社チェック** | `vendors.compliance_check_status` が `EXPIRED` の業者へのカード投函は 403。期限切れ業者は新規見積依頼自体不可 |
| **レートリミット並列** | user/scope 二重レートリミット（同一マンション複数理事の同時シミュ 429 連発防止）|
| **入力バリデーション** | `monthly_fee`/`dwelling_units` は `>= 0`、`scenario_horizon_years` は `1〜50`、CPI率は `-0.10〜+0.20` |

### 13.5 マスタ・シングルトン例外への該当判定（CLAUDE.md 原則6 例外規定）

CLAUDE.md（2026-05-11 追記）に「マスタテーブル」「シングルトン表」は UUIDv7 例外と規定された。
本機能の 9 テーブルを判定した結果、**いずれも例外区分に該当せず**、全テーブル UUIDv7 を維持する。

| テーブル | 性質 | 判定根拠 |
|---|---|---|
| `repair_plan_templates` | SYSTEM seed + ORG/TEAM オーバーライド混在 | テナント側で行が増殖するため原則6適用。混在テーブルは UUIDv7 が安全 |
| `repair_plan_items` | テナント増殖 | 原則6適用 |
| `repair_simulation_scenarios` | テナント増殖 | 原則6適用 |
| `repair_simulation_scenario_versions` | シナリオ毎増殖 | 原則6適用 |
| `repair_quote_kanbans` | 案件毎増殖 | 原則6適用 |
| `repair_quote_cards` | 業者見積毎増殖 | 原則6適用 |
| `team_member_terms` | 任期毎増殖 | 原則6適用 |
| `board_handover_packs` | 任期終了毎増殖 | 原則6適用 |
| `external_agent_delegations` | 委任契約毎増殖 | 原則6適用。同時1委任のみだが過去履歴行が残るためシングルトンではない |

**判断原則**: CLAUDE.md「迷ったら原則6を適用しておけば後悔しない（24バイト/行のオーバーヘッドだけで済む）」に従う。
