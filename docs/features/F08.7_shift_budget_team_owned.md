## 1. 概要

### 1.1 マスターの意図（2026-09-30、確定）

1. **シフトを作るのはチームだけ。** 組織がシフトを作ることはない。
2. **予算はチームが持つ。** チームの予算は、シフトの人件費だけでなく備品代なども含めた**チーム全体の予算**である（＝F08.6 のチーム予算・会計と一体）。
3. **組織は組織で、別に自分の予算を持ってよい。**（F08.6 の組織スコープ。従来どおり）
4. **組織から所属チームへ予算を割り振って反映させる機能はあってよい。** 例: サッカー協会 → 社会人委員会・高校委員会へ予算を割り振る。

### 1.2 現状の何が食い違っているか

現行の F08.7（v1.4）は「予算の持ち主は組織」で組んである。組織がシフト人件費の月次予算（`shift_budget_allocations`）を作り、チームは組織の予算の細分（任意の `team_id`）にすぎない。これがマスターの意図と逆で、次の症状を生んでいる（§2 に根拠）。

- チーム管理者が**自分のチームのシフト予算を作れない**（作成 API は組織スコープ＋組織の `BUDGET_ADMIN` 専用）。
- **組織に加盟していない独立チームは、シフト予算を使えない**（消化記録の入口で組織を解決できずスキップされる）。
- 1チームが複数の組織に加盟できるようになる（F01.2.1）と、「消化をどの組織の予算に計上するか」が曖昧になる。F01.2.1 §9.2 #14 は「その期間に割当を持つ組織へ計上し、重なる割当は 409 で禁止」という**継ぎ足しの安全策**で凌いでいるが、所有がチームにあれば曖昧さ自体が生じない。
- シフト人件費の予算が F08.6 のチーム予算と**別系統**で、チームの全体予算の中での位置づけが無い（月次締めで初めて F08.6 の仕訳に現れる）。

### 1.3 本書の解決方針（骨子）

| # | 決定 |
|---|---|
| D1 | **シフト予算の持ち主はチーム。** `shift_budget_allocations` は `team_id` 必須・`organization_id` を廃止する。組織はシフト予算を作らない。 |
| D2 | **シフト人件費は F08.6 チーム予算の一費目の「月次内訳」。** 別枠にしない。月次割当の合計は、その費目の実効予算（年額）を超えられない。 |
| D3 | **組織→チームの予算割り振り（`org_budget_grants`）を新設する。** 組織の予算配分から金額を切り出し、チームの指定費目の予算に上乗せする。組織側は「配賦済み」、チーム側は「割り振り由来の予算」として両方に見える。仕訳（実績）は作らない。 |
| D4 | **独立チームも同じ仕組みで使える。** 加盟の有無に依らず、チームが自分の予算を持つ。 |
| D5 | **複数組織加盟でも曖昧さが生じない。** 計上先はチーム自身の割当で一意。割り振りは組織ごとに独立の行として記録される。F01.2.1 §9.2 #11〜#16 の安全策は不要になる（§18）。 |

### 1.4 非目標

- 組織のシフト予算・組織横断のシフト集計。組織自身の予算管理は F08.6 の組織スコープが担う（変更なし）。
- 実際の資金移動・送金・会費精算。割り振りは「予算枠」の移転であって、金銭の移動ではない。
- F08.7 v1.4 の逆算式・消化計算・按分・閾値・時給漏洩防止・TODO 紐付の計算規則の変更（所有先がチームになるだけで規則は不変。§8.7）。
- 多通貨・給与計算（v1.4 §1.3 のとおり）。

## 3. 用語

| 用語 | 意味 |
|---|---|
| チーム予算 | F08.6 の TEAM スコープの年度・費目・配分・取引の総体。シフト人件費も備品代も含む、チーム全体の予算 |
| 自己設定分 | チームが F08.6 の `budget_allocations` に自分で設定した費目の年額 |
| 割り振り（grant） | 組織がチームの費目へ上乗せした予算枠。`org_budget_grants` の 1 行。「組織の予算配分の一部を切り出してチームに渡した」ことの記録 |
| 実効予算 | 費目の予算 = 自己設定分 + その費目宛ての有効な割り振りの合計。消化率・警告はこの値で判定する |
| 配賦済み | 組織の費目の配分額のうち、割り振りとして既に切り出された額（有効な割り振りの合計） |
| 未配賦残 | 組織の費目の配分額 − 配賦済み − その費目の承認済み支出。割り振れる上限 |
| 月次割当 | `shift_budget_allocations` の 1 行。チームの費目の月次内訳（シフト人件費の月予算） |
| 予算管理者（チーム） | チームの ADMIN、および `TEAM_BUDGET_MANAGE` を持つ DEPUTY_ADMIN |
| 割り振り元組織 | チームに ACTIVE 加盟している組織のうち、割り振りを行う組織 |

「割当」（allocation）は既存の用語のまま **`shift_budget_allocations`（月次割当）** を指す。組織→チームの受け渡しは混同を避けて **「割り振り（grant）」** と呼び、テーブル・クラス・API とも `grant` で統一する。

## 4. 所有モデル（決定の詳細）

```
組織 X（サッカー協会）                        チーム T1（社会人委員会）
 F08.6 ORGANIZATION スコープ                   F08.6 TEAM スコープ（チーム全体の予算）
  年度 / 費目 / 配分 / 取引  ──割り振り──▶     年度 / 費目 / 配分（自己設定分）
  （組織自身の予算。従来どおり）  org_budget_grants   ＋ 割り振り由来分  ＝ 実効予算
   配賦済み ↑                     (X→T1, 100万円)          │
                                                            ├─ 費目「備品費」  実効予算
                                                            └─ 費目「人件費」  実効予算
                                                                  └─ 月次割当 shift_budget_allocations（シフト人件費の月予算）
                                                                        └─ 消化 shift_budget_consumptions（シフト公開で PLANNED、月次締めで CONFIRMED）
                                                                              └─ 月次締めで F08.6 TEAM 取引（EXPENSE）を1件作成
独立チーム I（組織未加盟）: 割り振りを受けないだけで、上の右側の構造は同じ
チーム M（X と Y に加盟）  : X からの割り振りと Y からの割り振りが別行で並ぶ。計上先の曖昧さは無い
```

### 4.1 決定表

| # | 論点 | 決定 | 理由 |
|---|---|---|---|
| Q1 | シフト予算の持ち主 | チーム。`organization_id` 列を廃止し `team_id NOT NULL` | マスター意図 1・2。組織がシフトを作らないため、組織を経由する意味が無い |
| Q2 | シフト人件費は F08.6 の費目に載せるか、別枠か | **F08.6 の費目に載せる**。月次割当は「チーム所有の年度に属する EXPENSE 費目」を必須とし、月次割当の合計はその費目の実効予算以下 | マスター意図 2（チーム全体予算と一体）。別枠だと備品代と人件費を足した全体像が作れない。月次締めのスコープ不整合（§2 #8）も同時に消える |
| Q3 | 組織の予算とシフト予算 | 無関係。組織予算は F08.6 組織スコープのまま。組織→チームは割り振りだけが橋渡し | マスター意図 3 |
| Q4 | 割り振りは「予算枠」か「実資金（収入仕訳）」か | **予算枠**。F08.6 の収入・支出取引は作らず、実効予算の計算に足す | 予算と実績を混ぜない。実際の資金が動くなら、チーム・組織が各自の取引として記録すればよい（F08.6 の既存機能）。**§17 裁可 U1** |

| Q6 | 独立チーム | 使える。割り振りだけ受けられない | D4 |

## 5. F08.6 との接続

### 5.1 月次割当の親子関係

月次割当（`shift_budget_allocations`）の `fiscal_year_id` と `budget_category_id` は、次を**すべて**満たさなければならない（作成・更新時に検証し、違反は 400 `SHIFT_BUDGET_ALLOCATION_CATEGORY_SCOPE_MISMATCH`）。

1. `budget_fiscal_years.scope_type = 'TEAM' AND scope_id = :teamId`（他チーム・組織所有の年度は不可）
2. 費目が上記の年度に属し（`budget_categories.fiscal_year_id`）、`category_type = 'EXPENSE'`、論理削除されていない
3. 年度が `OPEN`
4. 期間 `[period_start, period_end]` が年度の `[start_date, end_date]` に収まる（年度をまたぐ月次割当は不可。年度の切れ目で月を分けて 2 本作る）

### 5.2 月次割当の合計と実効予算

同一（`team_id`、`fiscal_year_id`、`budget_category_id`）の**生存する月次割当の `allocated_amount` の合計は、その費目の実効予算（自己設定分 + 有効な割り振りの合計）を超えられない**。超える作成・増額は 409 `SHIFT_BUDGET_ALLOCATION_EXCEEDS_CATEGORY_BUDGET`。実効予算が未設定（0）の費目には月次割当を作れない（同じ 409。応答に「先に費目の予算を設定してください」を示すコード付き詳細 `category_budget_zero` を含め、FE は F08.6 の予算配分画面へ誘導する）。

> **費目行ロック規約（全経路共通）**: 費目の予算に影響する次の操作は、すべて**対象費目の `budget_categories` 行を `SELECT ... FOR UPDATE` でロックしてから**検証・更新する。①F08.6 の予算配分（`BudgetAllocationService` の作成・更新。既存は無ロックなので改修対象。自己設定分を「必要額（§7.5 の式）」未満へ下げる更新は拒否する）②割り振りの作成・増減・取消（切り出し元・上乗せ先の両費目）③月次割当の作成・増額④費目の論理削除（有効な割り振り・月次割当が残る費目は削除不可）。**複数費目をロックする操作（割り振りは元と先の 2 費目）は費目 ID の昇順でロックする**（デッドロック回避）。月次割当行のロックは費目行ロックの後に取る。組織側も同じ規約で、切り出し元費目の配分額を既存の割り振り合計未満へ下げる更新は拒否する。

### 5.3 F08.6 の消化率・報告書は実効予算を使う

F08.6 §5「予算消化率の計算ロジック」の `budget` を次のとおり改める（F08.6 へ追従）。

```
budget = budget_allocations.amount（自己設定分。行が無ければ 0）
       + SUM(org_budget_grants.amount WHERE dest_category_id = ? AND status = 'ACTIVE')
■ 割り振りだけがあり自己設定分の行が無い費目は「予算未設定」ではなく、実効予算あり
■ 内訳（自己設定分 / 各組織からの割り振り）を年度サマリー・費目別サマリーの応答に含める（§7.6）
```

組織側の費目は、逆に `consumed = SUM(承認済み EXPENSE 取引) + 配賦済み`（割り振りは組織の予算枠を消費する）として消化率を出す。

### 5.4 月次締めの F08.6 仕訳（スコープ不整合の根治）

月次締めは、F08.6 の TEAM 取引を 1 件作る（従来どおり）が、`scopeType='TEAM'`、`scopeId=team_id`、`fiscalYearId`・`categoryId` は §5.1 で検証済みの**チーム所有のもの**になる。組織スコープの取引を作る分岐（`team_id IS NULL`）は廃止する。仕訳の他の属性（`source_type='SHIFT_BUDGET_MONTHLY'`、`source_id=allocation_id`、`is_auto_recorded=TRUE`、二重締め防止の 409 `MONTHLY_ALREADY_CLOSED`、割当行ロックによる直列化）は変えない。

### 5.5 シフト見込みの見え方（月次締めまでの空白）

F08.6 の消化は承認済み取引だけを数えるので、シフト人件費は月次締め（翌月 1 日）まで F08.6 に現れない。チームの予算画面で全体像を欠かさないよう、費目別サマリーに **「シフト見込み（未確定）」** を別行で出す（`planned_shift_amount` = その費目の月次割当に紐づく PLANNED 消化の合計）。F08.6 の消化率そのものは変えず（確定分のみ）、見込みを足した「見込み込み消化率」を併記する。

### 6.3 消化記録（シフト公開 hook）の変更

`ShiftBudgetConsumptionRecordListener.onShiftPublished` の解決順を次に変える。

1. **組織の解決をやめる**（`findOrganizationIdByTeamId` を削除。F01.2.1 §9.2 #11）。
2. 機能フラグ判定は**チームの設定**で行う（§6.5）。
3. スロットごとに、計上先の月次割当を**一意に**決める（下記の一意性規則）。組織全体割当へのフォールバックは廃止。該当が無ければ従来どおり警告ログ＋スキップ（割当の事前作成が前提。v1.4 UC-2）。

**計上先の一意性規則（新設）**: シフト人件費の月次割当は、**同一チーム・同一 `project_id`（NULL 同士を含む）で、期間が 1 日でも重なる生存割当を作れない**（費目が違っても不可。作成・更新時に 409 `ALLOCATION_ALREADY_EXISTS`。重なり検査は、そのチームの月次割当の集合を `SELECT ... FOR UPDATE` で取ってから行う）。よって 1 チームが同時に持つ通常の月次割当は日付ごとに高々 1 件で、シフトのスロットは (a) スケジュールの `linked_project_id` に専用割当（`project_id` 一致）があればそれ、(b) 無ければ `project_id IS NULL` の割当、の順で 1 件に決まる。現行の `findContainingPeriod` は費目・プロジェクトを条件に含まず `Optional` を返すため、`project_id` を条件に含む形に改め、複数候補が返る状況が起きないことを IT で固定する。1 チームで複数費目（例: ホール・キッチン）に分けたい場合は、当面費目を分けず 1 割当にまとめる（段階拡張。§19）。
4. 以降（時給スナップショット・PLANNED 記録・閾値判定・時給未設定の通知・失敗イベント）は変更なし。

`ShiftBudgetConsumptionCancelListener`・`ShiftBudgetConsumptionReconcileBatchService` は、消化行が指す割当の `team_id` を使う（組織 ID の再解決をしない。F01.2.1 §9.2 #15・#16 は「消化行に組織 ID を記録」ではなく「割当のチーム」で足りるため不要になる）。

### 6.4 月次締め・バッチ

- 手動起動（API #9）はパスのチームが対象。cron バッチ `MonthlyShiftBudgetCloseBatchJob`（`closeAll`。現状は組織を走査し、`@BatchEndpoint` の説明も「全組織横断」）は、**機能が有効なチーム**を走査して各チームの割当を締める形に改める（結果型 `AllOrgsCloseResult` の `processedOrganizationIds`/`failedOrganizationIds` はチーム ID 版に改名し、失敗は従来どおり failed_events に記録して続行）。cron は `feature.shift-budget.monthly-close-cron-enabled` が true のときだけ生成される既存の仕組み（既定では無効で、手動再実行経路が主）を維持する。
- 締め処理の中身は §5.4 のとおり。1 割当 = 1 トランザクション（`REQUIRES_NEW`）と自己プロキシ経由の呼び出し（CMP-260910-1556）は維持する。

### 6.5 機能フラグ・超過承認ワークフローの所在

`budget_configs` の `scope_type='TEAM'` の行に置く（列 `shift_budget_enabled`・`over_limit_workflow_id` は既存。F08.6 はチームの `budget_configs` を既に持てる）。判定は従来の三値論理のまま（グローバル `feature.shift-budget.enabled` が OFF なら強制無効、チーム行が NULL/無しならグローバル既定を継承、明示 FALSE でオプトアウト）。**超過承認ワークフロー**（100% 到達時。`ThresholdAlertEvaluationService` が `createRequest`/`submitRequest` を `"ORGANIZATION", allocation.getOrganizationId()` で呼んでいる箇所を含む）も TEAM スコープに改める: `createRequest`/`submitRequest` は `"TEAM", allocation.getTeamId()` で行い、`over_limit_workflow_id` に指定できるテンプレートは**同じチーム所有**のものに限る（他チーム・組織所有のテンプレート ID は設定時に 400 `SHIFT_BUDGET_WORKFLOW_TEMPLATE_INVALID`、実行時も所有を再検証して不一致なら `WORKFLOW_NOT_CONFIGURED` 扱いで監査ログに残す）。失敗イベントの再実行（`ShiftBudgetRetryExecutor`）も TEAM スコープで行う。

組織の `budget_configs` 行にある同名の列は**読まなくなる**（列の物理削除は行わず、段階拡張で扱う。§19）。

### 6.6 警告・通知の宛先

閾値警告（80/100/120%）・時給未設定・月次締め失敗の通知先は、v1.4 の「組織の ADMIN/DEPUTY_ADMIN ∪ `BUDGET_ADMIN`」から**チームの予算管理者**（チーム ADMIN ∪ `TEAM_BUDGET_MANAGE` を持つ DEPUTY_ADMIN）に改める。宛先の解決は `RoleService` 経由で行い、`role` ドメインの Repository を直接掴まない（既存作法）。通知のアクション URL は `/teams/{slug}/budget`（シフト予算タブ。時給未設定は従来どおり `/teams/{slug}/settings/hourly-rate`）。

### 6.7 不変の規則

次は所有先が変わるだけで、v1.4 の規則をそのまま適用する: 逆算式と `MEMBER_AVG` / `POSITION_AVG` / `EXPLICIT`（§4.1）、消化の同時刻・按分なし・深夜跨ぎ・月跨ぎの計上月（§4.2・§4.6・§11）、TODO/プロジェクトの直接経路と TODO 経由の二重計上防止（§4.3。**ただし紐付先の範囲は §8.3**）、閾値 80/100/120% と `UNIQUE(allocation_id, threshold_percent)`（§4.5）、`consumption-summary` の `by_user`/`flags` 形状（§6.2.3・§9.3）、CANCELLED による取消・改竄防止（§5.3・§9.4）、監査ログ名（§9.1。`organization_id` 欄に代えて `team_id` を記録）。

## 7. 組織からチームへの予算割り振り（新設）

### 7.1 何をするか

組織 X の ADMIN が、X の予算のある費目（例: 「委員会配賦金」）から金額を切り出し、所属チーム T1 の費目（例: 「人件費」）の予算に上乗せする。T1 の予算管理者は、自分のチームの予算画面で「組織 X から 100 万円」を含む実効予算と内訳を見る。X の予算画面では、その費目の「配賦済み」が増え、未配賦残が減る。

### 7.2 DDL（新規 `org_budget_grants`）

新規テーブルなので `UuidV7Entity` 継承（主キー UUIDv7、`BINARY(16)`）。所属ドメインは `budget`（F08.6 と同じ。実効予算の計算に直結するため）。

| カラム | 型 | NULL | 説明 |
|---|---|---|---|
| `id` | BINARY(16) | NO | PK（UUIDv7） |
| `organization_id` | BIGINT UNSIGNED | NO | 割り振り元の組織。**FK なし**（クロスドメイン原則 1。索引のみ。整合はアプリ層） |
| `team_id` | BIGINT UNSIGNED | NO | 割り振り先のチーム。FK なし（同上） |
| `source_fiscal_year_id` | BIGINT UNSIGNED | NO | 組織の年度（`budget_fiscal_years`。scope=ORGANIZATION・`organization_id` と一致） |
| `source_category_id` | BIGINT UNSIGNED | NO | 組織の EXPENSE 費目（切り出し元） |
| `dest_fiscal_year_id` | BIGINT UNSIGNED | NO | チームの年度（scope=TEAM・`team_id` と一致・OPEN） |
| `dest_category_id` | BIGINT UNSIGNED | NO | チームの EXPENSE 費目（上乗せ先） |
| `amount` | DECIMAL(12,0) | NO | 割り振り額（円。1 以上） |
| `currency` | CHAR(3) | NO | 既定 `'JPY'`（v1.4 と同じ拡張ポイント） |
| `status` | VARCHAR(20) | NO | `ACTIVE` / `REVOKED` |
| `client_request_id` | VARCHAR(64) | NO | 冪等キー（`Idempotency-Key`）。`UNIQUE (organization_id, client_request_id)` |
| `organization_name_snapshot` / `team_name_snapshot` | VARCHAR(200) | NO | 作成時点の組織名・チーム名。組織・チームが削除／アーカイブされても表示できるようにする（Entity は `deleted_at IS NULL` 制限付きで、削除後は引けない）。G1・G6 の表示は生存していれば現在名、引けなければスナップショットを使う |
| `note` | VARCHAR(500) | YES | 用途メモ |
| `granted_by` | BIGINT UNSIGNED | NO | 割り振った組織 ADMIN（`users.id`。FK なし） |
| `revoked_at` / `revoked_by` / `revoke_reason` | DATETIME / BIGINT / VARCHAR(200) | YES | 取消の記録 |
| `version` | BIGINT | NO | 楽観ロック |
| `created_at` / `updated_at` | DATETIME | NO | |

```sql
INDEX idx_obg_org_status  (organization_id, status, source_category_id)   -- 組織側: 配賦済みの集計
INDEX idx_obg_team_dest   (team_id, dest_category_id, status)              -- チーム側: 実効予算・受領一覧
INDEX idx_obg_source_cat  (source_category_id, status)                     -- 未配賦残の集計
UNIQUE KEY uq_obg_org_request (organization_id, client_request_id)
CONSTRAINT chk_obg_amount CHECK (amount >= 1)
CONSTRAINT chk_obg_status CHECK (status IN ('ACTIVE','REVOKED'))
```

`REVOKED` の行は物理削除しない（会計証跡。F08.6 の取引と同じ扱い）。金額の変更は既存行の `amount` の更新（`version` 楽観ロック）＋監査ログで記録する（履歴は監査ログが担う）。

**Repository**: `AbstractTenantAwareRepository` は `findByOrganizationIdAndDeletedAtIsNull` を導出するため、`deleted_at` を持たない本テーブルの Entity に継承させると起動時に `PropertyReferenceException` になる（`REVOKED` の行は物理削除せず `status` で表すため `deleted_at` は不要）。よって**素の `JpaRepository` を使い**、組織側は `findByOrganizationId...`、チーム側は `findByTeamId...` を明示メソッドで持つ。組織 ID・チーム ID による絞り込みはサービス層で必須引数にし、番人（テナント絞り込み系）の許可リストへ「`deleted_at` を持たない財務台帳のため」という理由付きで登録する。

### 7.3 割り振り可能な条件（作成時の検証、すべて満たすこと）

| # | 条件 | 違反時 |
|---|---|---|
| 1 | 操作者が割り振り元組織の予算権限を持つ（F08.6 組織スコープの管理権限。§9） | 403 |
| 2 | チームが割り振り元組織に **ACTIVE で加盟**している（`team_org_memberships`。PENDING・非加盟・アーカイブ済みは不可） | 404 `BUDGET_GRANT_TARGET_NOT_FOUND`（存在オラクルを作らない） |
| 3 | 切り出し元は、その組織の OPEN 年度の EXPENSE 費目 | 400 `BUDGET_GRANT_CATEGORY_INVALID` |
| 4 | 上乗せ先は、そのチームの OPEN 年度の EXPENSE 費目 | 400 `BUDGET_GRANT_CATEGORY_INVALID`（チームに OPEN 年度が無い・予算モジュールが無効なら 409 `BUDGET_GRANT_TARGET_NOT_READY`） |
| 5 | `amount ≤ 未配賦残`（切り出し元費目の配分額 − 既存の有効な割り振り − 当該費目の承認済み支出）。**切り出し元の費目行を `SELECT ... FOR UPDATE` でロックしてから再計算**（並行作成の超過防止） | 409 `BUDGET_GRANT_EXCEEDS_SOURCE` |
| 6 | 年度が CLOSED でない（切り出し元・上乗せ先とも） | 409 `BUDGET_004`（既存） |

`{grantId}` は UUID。パスの `orgId` と行の `organization_id` が一致しなければ 404（他組織の割り振りを存在ごと隠す）。

### 7.5 変更・取消の制約（チームの既存支出を守る）

割り振りを減額・取消して上乗せ先費目の実効予算が下がるとき、**下がった後の実効予算 ≥ 「シフト以外の承認済み支出の合計」＋ max(「月次締め済みのシフト仕訳（`source_type='SHIFT_BUDGET_MONTHLY'`）の合計」, 「その費目の月次割当の合計」)** でなければならない（備品などの通常支出とシフト計画は別用途なので足し、シフトの確定分は月次割当の内数なので二重に数えない）。違反は 409 `BUDGET_GRANT_BELOW_COMMITMENT`（応答に不足額を含める）。増額は §7.3 #5（未配賦残）だけが制約。`REVOKED` の再取消は 409 `BUDGET_GRANT_ALREADY_REVOKED`。チーム側は割り振りを編集・取消できない（G6 は参照のみ）。

### 7.6 チーム・組織それぞれの見え方

- **チーム**（F08.6 チーム予算画面）: 費目ごとに「実効予算 = 自己設定 + 組織 X から + 組織 Y から」の内訳を表示。割り振り由来の行には組織名を付ける。複数の組織から受け取っていても、他の組織が出した金額・存在は、**受け取った側であるチーム自身**には全て見える（自チームの予算の内訳であるため）。
- **組織**（F08.6 組織予算画面）: 費目ごとに「配分額 / 配賦済み / 承認済み支出 / 未配賦残」。「チームへ割り振る」導線と、割り振りの一覧（G1）。**他の組織が同じチームへ出した割り振りは見えない**（G1 は `organization_id` で絞る）。
- **複数組織に加盟するチーム**: 各組織は自分の割り振りだけを操作でき、チームは全部を合算した実効予算を見る。組織 X の取消が組織 Y の割り振りに影響することはない。

### 7.7 加盟の離脱・チームのアーカイブとの関係

- チームが組織から離脱・除名されても、既存の割り振りは**そのまま有効**（既に渡した予算枠であり、遡って消すとチームの進行中の予算が壊れる）。新規の割り振りは条件 #2 で不可。組織 ADMIN は §7.5 の制約の範囲で取消できる。**§17 裁可 U4**
- チームのアーカイブ: 割り振りは残す（会計証跡）。一覧は組織側に残り、チーム側は F08.6 のアーカイブ済みスコープの扱いに従う。
- 組織の停止・削除: F01.2.1 §4.5 の片付けに従い、割り振りには触れない（財務記録）。

### 7.8 通知・監査

- 通知（F04.3、宛先＝上乗せ先チームの予算管理者）: `BUDGET_GRANT_RECEIVED`（作成）、`BUDGET_GRANT_CHANGED`（増減）、`BUDGET_GRANT_REVOKED`（取消）。組織 ADMIN 本人には通知しない。
- 監査ログ（F10.3）: `BUDGET_GRANT_CREATED` / `BUDGET_GRANT_UPDATED`（`before/after` の金額）/ `BUDGET_GRANT_REVOKED`。`organization_id` と `team_id` の両方を記録する。
- 通知の配送失敗で割り振りの操作をロールバックしない（F01.2.1 裁可 #35 と同じ作法。操作と同一トランザクションで enqueue のみ）。

## 8. 独立チーム・複数組織・TODO 紐付

### 8.1 独立チーム

### 8.3 TODO・プロジェクトの紐付先

`todo_budget_links` は「チームの月次割当」に紐付ける。TODO／プロジェクトのスコープが**そのチーム**（`TodoScopeType.TEAM` かつ `scope_id = 割当の team_id`）であることを検証する（`TodoBudgetLinkService.isScopeInOrganization` を `isScopeOfTeam` に置き換え、組織 ID との等値比較を廃止）。組織スコープのプロジェクト・個人 TODO は紐付不可（400 `SHIFT_BUDGET_INVALID_LINK_TARGET`）。組織のプロジェクトの予算は、組織自身の F08.6 の費目で管理する。**§17 裁可 U5**（組織プロジェクトに、加盟チームの月次割当を紐付けたい要望が出た場合の扱い）。

## 12. Flyway と移行

### 12.1 マイグレーション（設計）

major は**マージ時に origin/main 全体の最大 major ＋ 1 で確定**（`date -u '+%Y%m%d%H%M%S'` の minor、連番禁止、`FlywayTimestampNamingGuardTest` が拒否）。1 本の移行に責務を混ぜず、次の 3 本に分ける（適用順は major の昇順）。

| 順 | 名前（説明部） | 内容 |
|---|---|---|
| 1 | `shift_budget_team_owned_cleanup` | 非本番データの片付け（§12.2）。F08.7 の全テーブルの全行と、`SHIFT_BUDGET_MONTHLY` の仕訳を削除 |
| 2 | `shift_budget_allocations_team_owned` | `organization_id` 列・FK・索引の削除、`team_id NOT NULL` 化、関数インデックスの作り直し（§6.1）。`shift_budget_failed_events` の `organization_id` → `team_id NOT NULL` |
| 3 | `create_org_budget_grants` | `org_budget_grants` 新設（§7.2） |

- **FK/索引の削除順**: MySQL は FK が使っている索引を先に落とせない。`organization_id` の FK 制約を先に DROP し、次に依存する索引、最後に列を DROP する。関数インデックスの作り直しは DROP INDEX → CREATE UNIQUE INDEX。
- **Entity と DDL の一致**: `ShiftBudgetAllocationEntity`・`ShiftBudgetFailedEventEntity` から組織列を除く。`FlywayFromScratchMigrationTest`（実 MySQL に実 Flyway を適用して Entity の全列を突き合わせる番人）と `関数インデックスの存在検査` を、新しい索引定義に合わせて更新する。テスト用プロファイルは `ddl-auto=create` で Flyway を実行しないため、この番人でしか Entity と DDL の乖離は検出できない（v1.4 §5.2 の教訓）。
- **既存データ番人テストの要否**: 要（`ShiftBudgetTeamOwnedMigrationTest`）。移行前スキーマを再現し、`team_id` あり／なしの割当・消化・警告・紐付・失敗イベント・月次集計仕訳を投入してから移行を適用し、①全て消えている、②移行後に §5.1 違反の行が無い、を確かめる。
- **`budget_configs`**: 変更しない（TEAM 行の `shift_budget_enabled` / `over_limit_workflow_id` を新たに読むだけ）。

### 12.2 既存データの扱い（本番に実データは無い前提）

- 本番: `feature.shift-budget.enabled` は既定 false で一度も有効化されておらず（v1.4 §5.2 の 2026-09-09 の記述）、`shift_budget_*` に実データは無い。
- 開発・検証環境に残るテストデータ: **`shift_budget_*`・`todo_budget_links`・`budget_threshold_alerts`・`shift_budget_failed_events` の全行を削除する**。`team_id` のある既存割当も、組織所有の年度・費目を指しており §5.1（チーム所有）の制約を満たさない（§2 #8 の不整合そのもの）ため、そのまま引き継げない。チーム所有の年度・費目への対応表を作って再作成する案は、本番実データが無い以上コストに見合わないので採らない。会計証跡の物理削除だが、本番実データが無いことを根拠とし、削除行数を移行 SQL 冒頭のコメントと PR 本文に書く。あわせて、F08.7 が作った F08.6 の月次集計仕訳（`source_type='SHIFT_BUDGET_MONTHLY'`）も、開発・検証環境では同じ移行で削除する（孤児の仕訳を残さない）。
- **旧 API・旧 FE ルートの扱い（main の既存資産）**: 旧 `/api/v1/shift-budget/**`・`/api/v1/todo-budget/**` は削除、FE の `/admin/shift-budget/*` は削除（互換層・リダイレクトは置かない。理由は §6.2）。`docs/openapi.json` は再生成する（手編集禁止。**8082 汚染に注意**し、生成ポートの確認手順は `/伝令` に従う）。`frontend/app/types/shiftBudget.ts` は生成型へ寄せる。
- **ブランチ横断の整合**: 並行中の PR #3531（「計上先の組織が曖昧なら計上しない」の安全策）は、本書の実装が入ると不要になる。#3531 が先にマージされた場合、本書の実装 PR がその分岐（`findOrganizationIdByTeamId` 周辺・曖昧時スキップの分岐）を**削除する**。後にマージされる場合は本書側の実装に吸収されるため、#3531 は閉じてよい（実装着手時に状態を再確認）。

## 14. 非機能

- **スケール**: 月次割当・消化はチーム単位で完結し、組織を跨ぐ集計は割り振り（`org_budget_grants`）だけ。実効予算の計算（自己設定＋割り振り合計）は `idx_obg_team_dest` の 1 クエリ。1000 万ユーザー・シャーディング前提でもチーム ID を分割キーにできる（従来は組織 ID と team_org_memberships の JOIN が要った）。
- **整合性の保証**: 割り振りの未配賦残・月次割当の合計は、それぞれ「親の行を `FOR UPDATE`」で直列化する（§5.2・§7.3 #5）。アプリ層の保証であり、クロスドメイン FK は張らない（原則 1）。`@Transactional` は budget ドメイン内で閉じる。割り振りが `team` ドメイン（加盟の存在確認）を読むのはサービス経由の読み取りのみ。
- **後方互換**: 旧 API・旧画面は廃止（§12.2）。F08.7 v1.4 の不変部分（§6.7）の API 形状（`consumption-summary` 等）はパスだけが変わる。
- **段階拡張として残す範囲**: §19。

## 17. 裁可事項（2026-10-01 マスター裁可済み）

**裁可の結果**: **U1 は推奨どおり確定**（割り振りは予算の枠だけを増やし、仕訳は作らない）。**U2 も推奨どおり確定**（チームの承諾は要らず、通知のみ）。**U3〜U6 は既定の推奨案で確定し、後から拡張できる**。以下の表の「推奨」列が確定内容。

推奨案を既定にして本書を組んでいる。マスターの意図から一意に決まらない判断のみ、選択肢と推奨を示す。

| # | 論点 | 選択肢 | 推奨と理由 |
|---|---|---|---|
| U1 | 割り振りの実体は「予算枠」か「実資金」か（§4.1 Q4） | (a) **予算枠のみ**。F08.6 に仕訳は作らず、実効予算に足す (b) 実資金として組織に EXPENSE 仕訳・チームに INCOME 仕訳を自動作成する | **(a)**。予算と実績を混ぜず、資金が実際に動く場合は各自が取引として記録できる。(b) は組織・チームの帳簿を自動で書き換えるため、監査・取消の設計が重くなる |
| U2 | チーム側の受け入れ工程（§4.1 Q5） | (a) **承諾不要**。通知のみ (b) チーム ADMIN の承諾で成立（PENDING 状態を新設） | **(a)**。予算枠が増えるだけで実害が無く、承諾工程は入力摩擦。減額・取消はチームの支出を守る制約で保護する。(b) は F01.2.1 の加盟の PENDING と紛らわしくなる |
| U3 | 組織から、割り振り先チームの消化状況をどこまで見せるか（§7.4 G1） | (a) **割り振り額と、割り振り先費目の消化率（集計）のみ** (b) 額だけ（消化率なし） (c) 取引明細まで | **(a)**。資金を出した側が使われ方の概況を知れるが、取引明細・個人別時給は組織に見せない。組織が予算を出していても、チームの経理内訳はチームのもの |
| U4 | チームが組織から離脱・除名された後の既存の割り振り（§7.7） | (a) **そのまま有効**（組織が取消可） (b) 離脱時に自動で取消 (c) 離脱後は無効化（実効予算から除く） | **(a)**。進行中のチーム予算を後から壊さない。(b)(c) はチームの予算が離脱の一操作で突然減り、実支出との整合が崩れる |
| U5 | 組織スコープのプロジェクトに、加盟チームの月次割当を紐付けたい場合（§8.3） | (a) **不可**（TODO・プロジェクトはそのチームのものだけ紐付可。組織のプロジェクトは組織の F08.6 費目で管理） (b) 組織プロジェクトから、加盟チームの割当へ紐付可能にする | **(a)**。所有の境界が単純で、権限（チーム予算管理者）とも整合する。要望が出たら (b) を段階拡張で検討 |
| U6 | 組織が「自分の予算配分（F08.6）の一部」から割り振る以外に、**組織の予算配分を持たずに** チームへ予算を出すことを認めるか | (a) **認めない**。切り出し元は必ず組織の予算のある費目（配分額が根拠） (b) 認める（配分額の裏付け不要。青天井で割り振り可） | **(a)**。「組織から所属チームへ割り振る」という意図（原資は組織の予算）に沿い、未配賦残で過大な割り振りを防げる |

> U1・U2 は後から変更すると DDL・API・通知の全部に響く（仕訳の有無・PENDING 状態）ため、裁可済みの内容を前提に実装する。U3〜U6 は既定案で確定しており、後から拡張できる。
