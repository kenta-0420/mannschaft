## 1. 概要

個人ダッシュボード（`DashboardPersonalPanel.vue`）は現在、約24個のウィジェットを 1〜3 カラムのグリッドへ**横並びで全件展開**している。ウィジェット数が増えるほど縦に長大化し、「今すぐ必要な情報」が下方へ押し流される。本機能はこれを **「フォルダ＝タブ」** の二層構造に再構成する。

- **上層（今すぐ層）**: フォルダに属さないウィジェットを従来どおり生のカードとして常時表示する。`dashboard_widget_settings.folder_id IS NULL` のウィジェットが該当する。
- **下層（フォルダ層）**: フォルダカードが常設グリッドとして並ぶ。カードには内包ウィジェットのラベル一覧と新着件数バッジを表示し、選択するとタブのように選択状態になって、グリッド直下の**内容パネル**へ中身のウィジェット群が展開される。

ユーザーは任意のウィジェットを今すぐ層⇔フォルダ間で自由に移動でき、フォルダ自体も作成・改名・削除・並べ替えできる。「今日の時間割を常に一番上に置きたい」「募集フィードは普段畳んでおきたい」といった個人差を、ウィジェットの ON/OFF ではなく**配置**で吸収する。

> **本ドキュメントとの参照規約**: ウィジェット一覧（key・名称・データソース）の正本は F02.2 が保持する。本ドキュメントは「フォルダ構造」と「既定の振り分け」のみを定義する。新ウィジェットを追加する際は F02.2 のウィジェット一覧と本ドキュメント §3.5 の既定振り分け表の**両方**を更新すること。

### 本ドキュメントのスコープ

| 機能 | 説明 |
|------|------|
| フォルダカード常設グリッド | 個人パネル下段を、ウィジェット横並びからフォルダカード一覧へ置き換える |
| タブ的展開 | フォルダカード選択で内容パネルが開く（同時に開くのは1つ・再クリックで閉） |
| 今すぐ層 | `folder_id IS NULL` のウィジェットをフォルダ外に生表示 |
| ユーザー定義フォルダ | 作成・改名・削除・並べ替え（上限20・名称50文字） |
| ウィジェット割り当て | 任意ウィジェットの今すぐ層⇔フォルダ間の移動 |
| 新着件数バッジ（Phase1） | 3ウィジェット限定の件数集約 API を新設しフォルダカードへ集計表示 |
| 永続化欠落4ウィジェットの是正 | `recruitment-feed` / `my-recruitments` / `village-lobby-digest` / `my-corkboard` のキー整備（§9） |

**スコープ外**:
- チーム／組織ダッシュボード（`scope_type = TEAM / ORGANIZATION`）。DDL に `scope_type` / `scope_id` の両列を持たせ、Phase3 で DDL 変更なしに拡張できる形だけ用意する（§3.2）
- フォルダのアイコン・カラー設定（`chat_contact_folders` は持つが、本機能 Phase1 では持たない）
- フォルダの入れ子（サブフォルダ）
- 全ウィジェットのバッジ対応（Phase1 は3種のみ。§5.5）
- ウィジェットの ON/OFF・並び順そのものの仕様変更（F02.2 の既存仕様を踏襲。フォルダ内の並び順は既存 `sort_order` を流用する）
- F02.2.1 の `min_role` 制御（個人スコープは対象外＝自分のデータしか出ないため）

## 3. DB設計

### 3.1 テーブル一覧

| テーブル名 | 役割 | 論理削除 |
|-----------|------|---------|
| `dashboard_widget_folders`（新規） | ユーザー単位のウィジェットフォルダ（既定6＋ユーザー定義） | なし（物理削除） |

### 3.2 テーブル定義

#### `dashboard_widget_folders`（新規）

| カラム名 | 型 | NULL | デフォルト | 説明 |
|---------|---|------|-----------|------|
| `id` | BINARY(16) | NO | — | PK。UUIDv7（`UuidV7Entity` 継承） |
| `user_id` | BIGINT UNSIGNED | NO | — | 所有ユーザー。FK は張らずアプリ層で整合（クロスドメインFK禁止） |
| `scope_type` | VARCHAR(20) | NO | `'PERSONAL'` | スコープ種別。Phase1 は `PERSONAL` のみ。将来の TEAM / ORGANIZATION 拡張余地 |
| `scope_id` | BIGINT UNSIGNED | NO | 0 | スコープ ID。`PERSONAL` は `0`（`dashboard_widget_settings` と同一表現） |
| `folder_key` | VARCHAR(50) | YES | NULL | システム既定フォルダの識別子（§3.5）。ユーザー作成フォルダは NULL |
| `name` | VARCHAR(50) | YES | NULL | 表示名。NULL の場合は `folder_key` の i18n 名を使う（既定フォルダの未改名状態） |
| `sort_order` | INT | NO | 0 | フォルダカードの並び順（昇順） |
| `created_at` | DATETIME(6) | NO | CURRENT_TIMESTAMP(6) | |
| `updated_at` | DATETIME(6) | NO | CURRENT_TIMESTAMP(6) ON UPDATE | |

**インデックス**

```sql
UNIQUE KEY uq_dwf_user_scope_key  (user_id, scope_type, scope_id, folder_key)  -- 既定フォルダの重複作成防止
KEY          idx_dwf_user_scope_sort (user_id, scope_type, scope_id, sort_order) -- 一覧取得（user_id で閉じる）
```

**制約・備考**

- **`scope_id` を持つ理由**: `dashboard_widget_settings` は既に `(user_id, scope_type, scope_id)` の3点でスコープを表現し、個人は `scope_id = 0` としている。本テーブルだけ `scope_id` を欠くと、両表の結合条件が非対称になり、Phase3 の team/org 拡張時に UNIQUE 制約の作り直しを伴う DDL が必要になる。既存表と同じ3点セットで揃える（2026-08-22 裁定）。
- `organization_id` は**持たない**。本テーブルは「ユーザー個人の画面設定」であり、テナント境界（`AbstractTenantAwareRepository`）の対象外である（`dashboard_widget_settings` と同じ扱い）。
- FK は張らない。`user_id` はクロスドメイン参照のためアプリ層で整合を保証し、インデックスのみ張る（[domain_db_design_principles.md](../architecture/domain_db_design_principles.md) 原則1）。
- `folder_key` が NULL の行が同一ユーザーに複数存在しうる（ユーザー作成フォルダ）。MySQL の UNIQUE は NULL を重複と見なさないため、この UNIQUE 制約はユーザー作成フォルダを妨げない。
- 名称の重複はユーザー作成フォルダ間で**アプリ層検証**する（`chat_contact_folders` と同じ流儀。DB の UNIQUE では NULL 混在のため表現できない）。
- 照合順序は `utf8mb4_0900_ai_ci`（プロジェクト統一。V173 以前の混在を持ち込まない）。
- ユーザー退会時: `AccountPurgeService` で明示削除する（§3.4）。CASCADE は張らない。

##### JPA マッピング注記【重要・基底クラスの選択が型を決める】

本プロジェクトには UUIDv7 の基底クラスが**2種類**あり、**どちらを継承するかで DDL の列型が決まる**。

| 基底クラス | `id` のマッピング | 対応する DDL 列型 | 採用例 |
|---|---|---|---|
| `UuidV7Entity` | `@JdbcTypeCode` **なし**（Hibernate 既定の UUID マッピング） | **`BINARY(16)`** | `ReturnStayPlanEntity`（V188 `return_stay_plans`） |
| `UuidV7CharEntity` | `@JdbcTypeCode(SqlTypes.CHAR)` | `CHAR(36)` | CHAR(36) 系の表 |

`BINARY(16)` を採る本テーブルは **`UuidV7Entity` をそのまま継承し、`id` に `@JdbcTypeCode` を付けない**。Hibernate の UUID 既定マッピングが MySQL 方言で `binary(16)` になるため、これで DDL と一致する。**`UuidV7CharEntity` を継承してはならない**（CHAR(36) 側の基底であり、継承すると Flyway の `BINARY(16)` と噛み合わず実 MySQL でのみ落ちる）。

```java
@Entity
@Table(name = "dashboard_widget_folders")
@Getter
@NoArgsConstructor(access = AccessLevel.PROTECTED)
@SuperBuilder(toBuilder = true)
public class DashboardWidgetFolderEntity extends UuidV7Entity {
    // id は UuidV7Entity が保持。@JdbcTypeCode は付けない（既定マッピング = BINARY(16)）。

    @Column(nullable = false)
    private Long userId;

    @Enumerated(EnumType.STRING)
    @Column(nullable = false, length = 20)
    private ScopeType scopeType;

    @Column(nullable = false)
    private Long scopeId;

    @Column(length = 50)
    private String folderKey;

    @Column(length = 50)
    private String name;

    @Column(nullable = false)
    private Integer sortOrder;
}
```

`dashboard_widget_settings.folder_id` は**主キーではない** UUID 列である。こちらも素の `UUID` 型フィールドとして宣言し、`@JdbcTypeCode` を付けない（同じ既定マッピングで `BINARY(16)` になる）。

```java
@Column(name = "folder_id")
private UUID folderId;   // null = 今すぐ層
```

**実装時の必須確認**: Testcontainers の統合テスト（実 MySQL・Flyway DDL）で 1 件でも INSERT / SELECT を通し、型が噛み合っていることを確かめること。`test` プロファイルは Entity 由来の DDL を生成するため、**Entity 側だけで完結する検証はこの不整合を絶対に検出しない**（Entity が CHAR を要求すれば DDL も CHAR で作られ、両者は永遠に一致する）。

##### `updated_at` の流儀

本テーブルは `UuidV7Entity` を継承する。`ChatContactFolderEntity` / `DashboardWidgetSettingEntity` は `@PrePersist` / `@PreUpdate` で Java 側から時刻を入れているが、**本テーブルは V188 流儀（DDL 側の `DEFAULT CURRENT_TIMESTAMP(6)` / `ON UPDATE CURRENT_TIMESTAMP(6)`）に統一する**。理由は、`UuidV7Entity` 継承の新規テーブル（V188 `return_stay_plans` 等）が既にこの流儀であり、同じ基底クラスを継承する表の間で時刻の出所が分かれるのを避けるため。Java 側に `@PrePersist` / `@PreUpdate` を**書かない**（両方あると、DB の壁時計と JVM の壁時計という2つの真実が混在する）。

#### `dashboard_widget_settings`（既存・列追加）

| カラム名 | 型 | NULL | デフォルト | 説明 |
|---------|---|------|-----------|------|
| `folder_id` | BINARY(16) | YES | NULL | 所属フォルダ。**NULL = 今すぐ層**（フォルダ外の生表示） |

```sql
KEY idx_dws_user_folder (user_id, folder_id)   -- フォルダ削除時の一括 NULL 化・フォルダ内ウィジェット取得
```

- **索引を `(user_id, folder_id)` の複合にする理由**: 単独の `(folder_id)` 索引は、全ユーザー分の同一フォルダ行が混在する索引を引いた上で `user_id` を後段フィルタすることになる。更新系 SQL は必ず `user_id = :me` を条件に含める規則（§7.1）であり、索引の先頭を `user_id` にすることで**索引だけで自分の行に閉じる**。1000万ユーザー規模でこの差は効く。
- FK は張らない（同一ドメイン内だがアプリ層整合の既存流儀を維持し、フォルダ削除時の挙動を Service で明示制御するため。§5.3）。
- 既存行の `folder_id` は NULL で追加される。**移行方針が「全員リセット」のため、既存行はマイグレーション後に初回アクセス時点で既定構成へ置き換わる**（§5.4）。

### 3.4 退会・匿名化時の扱い【既存の穴を継承しないこと】

`origin/main` を実地確認した結果、**退会・匿名化の経路は `dashboard_widget_settings` を削除していない**。

| クラス | 役割 | ダッシュボード設定の扱い |
|---|---|---|
| `com.mannschaft.app.auth.service.UserService`（`requestWithdrawal` / `withdrawUser`） | 即時（弱）匿名化 | **触れていない** |
| `com.mannschaft.app.gdpr.service.AccountPurgeService`（`purgeExpiredAccounts` / `purgeUser`） | 30日後の強匿名化・物理パージ | **触れていない** |

両クラスが扱うのはトークン・OAuth・MFA/2FA・S3 失敗記録等の認証／GDPR 系リポジトリのみで、`dashboard_widget_settings` は**孤児レコードとして残り続ける**。

本機能で `dashboard_widget_folders` を足すと、**同じ穴がもう1つ増える**。よって本 PR では:

1. `AccountPurgeService.purgeUser` に `dashboard_widget_folders` と `dashboard_widget_settings` の**両方**の削除を追加する（フォルダだけ消して設定を残すと、`folder_id` が孤児を指す）。削除順序は §5.3 と同じく「設定 → フォルダ」。
2. 「退会処理後に当該 `user_id` の `dashboard_widget_folders` / `dashboard_widget_settings` が 0 件になる」テストを追加する（§11.2）。

> **設計判断**: 既存の `dashboard_widget_settings` の取りこぼしも本 PR で併せて塞ぐ。「自分が足す表だけ塞いで既存の穴は別課題」とすると、同じ削除処理を2度書くことになり、片方だけ直る典型形になる。これらは PII ではないが、退会ユーザーの画面設定を保持し続ける理由が無い（GDPR Art.17 の消去範囲としても保持根拠が説明できない）。

### 4.3 `POST /api/v1/dashboard/widget-folders`

新規フォルダの作成と、**未実体化の既定フォルダの実体化**の両方を担う。

**リクエスト（A: 新規ユーザー作成フォルダ）**

```jsonc
{
  "scopeType": "personal",   // string | NOT NULL
  "name": "受験対策",         // string | NOT NULL / 1〜50文字 / 前後空白トリム後に空は不可
  "sortOrder": 6             // integer | nullable。未指定なら末尾（既存最大+1）
}
```

**リクエスト（B: 既定フォルダの実体化。`name` を同時指定すると「実体化＋改名」を原子的に行う）**

```jsonc
{
  "scopeType": "personal",   // string | NOT NULL
  "folderKey": "SCHEDULE",   // string | NOT NULL（B の場合）。§3.5 の6値のいずれか
  "name": "テストの予定"      // string | nullable。指定時は実体化と同一トランザクションで改名まで行う
}
```

**レスポンス**

| 状況 | ステータス | 本体 |
|---|---|---|
| A: 新規作成 | `201 Created` | §4.2 の `folders[]` 要素 1 件（`folderKey: null` / `isSystem: false` / `widgetKeys: []`） |
| B: `folderKey` 指定で**未実体化** | `201 Created` | 作成された既定フォルダ 1 件（`id` 非 null / `isSystem: true`。`name` 同時指定時はその名前が入った状態） |
| B: `folderKey` 指定で**既に実体化済み** | `200 OK` | 既存行を返す（**冪等**。`name` 同時指定時は改名を適用した結果を返す） |

- **B が冪等である理由**: 実体化は FE がユーザー操作の裏で透過的に行う（§6.4）。ネットワーク再送や並行タブで二重に飛ぶことが普通に起きるため、2 回目を 409 にすると**ユーザーには何もしていないのにエラートーストが出る**。既に在るなら在るものを返すのが正しい。
- **`folderKey` + `name` を同時に受け付ける理由（2026-08-22 第2パス是正）**: 初版は「FE が実体化 → 改名の 2 回呼び、失敗したら作成済みフォルダを削除して戻す」としていたが、**この補償処理は成立しない**。実体化された行は `folder_key != null` であるため、`DELETE /widget-folders/{id}` は `DASHBOARD_024`（既定フォルダは削除不可）で拒否される。すなわち改名だけ失敗すると、**ユーザーから見れば何も起きていないのに、既定フォルダが旧名のまま実体化された状態が残る**（元に戻す手段が API に存在しない）。FE 側の補償で辻褄を合わせるのをやめ、**BE の単一トランザクションで実体化と改名を原子的に行う**契約へ変更する。FE の 2 段呼び出しは廃止する。
- `name` と `folderKey` の**両方が無い**リクエストは `DASHBOARD_022` 400（A でも B でもない）。A は `name` のみ、B は `folderKey`（＋任意で `name`）で識別する。
- B は**フォルダ数上限（20）の判定対象外**とする。既定 6 フォルダは常に存在するものとして扱われており、実体化は「新しく増やす」操作ではないため。上限判定はユーザー作成フォルダ（`folder_key IS NULL` の行）の件数で行う。

#### 並行実体化の原子性（同時 POST の衝突処理）

同一ユーザーの `folderKey` 実体化 POST が並行して 2 本走ると、両方が「実体行なし」を観測してから両方が INSERT を試み、**片方が `uq_dwf_user_scope_key` の重複キー違反で落ちる**。ここで 500 を返すと、ユーザーには何の操作もしていないのにエラーが出る。

**契約**: 重複キー例外（`DataIntegrityViolationException`）を捕捉し、**既存行を再取得して `200 OK` で返す**（原子的 upsert）。

```
INSERT を試みる
  ├ 成功                     → 201 Created
  └ 重複キー違反を捕捉
       └ 同じ (user_id, scope_type, scope_id, folder_key) で SELECT し直す
            ├ 見つかった → 200 OK（他方のリクエストが作った行を返す）
            └ 見つからない → 本物の異常として再スロー（握りつぶさない）
```

- 例外を捕捉して**握りつぶすのではなく、再取得して正しい結果を返す**（見つからなければ再スローする）。捕捉して `null` を返す・空を返すのは禁止。
- `name` 同時指定の場合、再取得した既存行に対して改名を適用してから返す（同一トランザクション内）。
- 呼び出し側から見て、並行実体化は「両方成功（片方が 201、片方が 200）」に収束し、**重複行は 1 行も作られない**。

**エラー**

| 状況 | コード | HTTP |
|---|---|---|
| ユーザー作成フォルダが 20 件に到達（A のみ） | `DASHBOARD_020` | 409 |
| 同名フォルダが既に存在（A のみ） | `DASHBOARD_021` | 409 |
| `name` が 50 文字超・空 | `DASHBOARD_022` | 400 |
| `name` と `folderKey` の**両方が無い** | `DASHBOARD_022` | 400 |
| `folderKey` が §3.5 の6値以外 | `DASHBOARD_022` | 400 |

#### フォルダ上限の並行突破を防ぐ（計数と INSERT の直列化）

「件数を数える → 20 未満なら INSERT する」は **check-then-act** であり、そのままでは並行リクエストで上限を突破する。19 件の状態で POST が 2 本同時に来ると、両方が「19 件（20 未満）」を観測して両方が INSERT し、**21 件になる**。上限は `chat_contact_folders` と違い DB 制約で表現できない（行数の上限は UNIQUE では書けない）ため、アプリ層で直列化するしかない。

**実装規則**: 計数と INSERT を**同一トランザクション内で、ユーザー単位に悲観ロックを取ってから**行う。

```java
@Transactional
public WidgetFolderResponse createFolder(Long userId, CreateWidgetFolderRequest req) {
    // ① 該当ユーザーのフォルダ行を FOR UPDATE でロックしてから数える。
    //    ロックの粒度は (user_id, scope_type, scope_id) に閉じるため、他ユーザーは待たされない。
    long count = folderRepository.countUserCreatedForUpdate(userId, scopeType, scopeId);
    if (count >= MAX_USER_FOLDERS) {
        throw new BusinessException(DashboardErrorCode.DASHBOARD_020);
    }
    // ② ①のロックを保持したまま INSERT する
    return toResponse(folderRepository.save(...));
}
```

```java
@Query(value = "SELECT * FROM dashboard_widget_folders "
             + "WHERE user_id = :userId AND scope_type = :scopeType AND scope_id = :scopeId "
             + "AND folder_key IS NULL FOR UPDATE", nativeQuery = true)
List<DashboardWidgetFolderEntity> lockUserCreatedFolders(...);
```

- ロック対象は `folder_key IS NULL`（ユーザー作成フォルダ）の行のみ。上限判定の母数と一致させる。
- **0 行のときもロックが効くことに注意**: MySQL の `FOR UPDATE` は該当行が 0 件だと行ロックを取れない（ギャップロックの挙動は分離レベル依存）。フォルダが 1 件も無い状態からの並行 POST も直列化するには、`users` 行（`SELECT ... FROM users WHERE id = :userId FOR UPDATE`）を先に取る方が確実である。**どちらを採るかは実装時に実 MySQL で並行テストして決めること**（モックでは分離レベルを再現できず、この種の欠陥はモック緑のまま残る）。
- ロックは同一ユーザーの同一スコープに閉じるため、他ユーザーの作成は待たされない。個人設定の作成頻度から見て競合はまれであり、悲観ロックのコストは問題にならない。
- 同じ規則は**フォルダ数上限に関わる経路すべて**に適用する（`POST` 形式 A のみ。形式 B の実体化は上限判定の対象外なのでロック不要）。

| 不整合 | 例 |

```jsonc
}
```

- **Phase1 の対象は 3 種のみ**: `UNREAD_THREADS`（未読チャットスレッド数）/ `NOTICES`（未読お知らせ数）/ `PERSONAL_TODO`（期限内の未完了 TODO 数）。`RECRUITMENT_FEED` は Phase1 から**除外**した（根拠は §5.5）。
- **対象外のウィジェットはキーごと返さない**（`0` を返さない）。「集計対象外」と「0件」を FE が区別できるようにするため。後続フェーズで対象を広げる際に、既に 0 が返っていると「増えていない」のか「未対応」なのか判別できなくなる。
- 実装は `ScopeWidgetSummaryService` の前例（各ドメインの既存 Repository を流用して集約する dashboard ドメインのサマリ Service）に倣い、`PersonalWidgetBadgeService` を新設する。
- フォルダカードのバッジは、そのフォルダに属するウィジェットの badge 値の**合計**を FE 側で算出する（BE はウィジェット粒度の生値のみ返す。ユーザーがウィジェットをフォルダ間で移動しても BE を変えずに追随できる）。

**取得タイミング**: FE は**個人パネルのマウント時に 1 回**取得し、加えて `document.visibilitychange` で `visible` へ戻ったときに再取得する。**ポーリングはしない**（24 ウィジェット分のバッジのために定期的に BE を叩くのは、得られる鮮度に見合わない。タブに戻った瞬間が実質的に最も鮮度を求められる瞬間である）。WebSocket による push も Phase1 では行わない。

### 4.9 `DELETE /api/v1/dashboard/widgets`（既存拡張）

既存のリセット API は `dashboard_widget_settings` の該当行を削除するだけだが、本機能では**同一トランザクションで `dashboard_widget_folders` の該当行も削除**する。結果として、次回の GET で §5.1 の既定構成が合成される＝フォルダ構成も出荷時状態へ戻る。削除順序は §5.3 と同じく「設定 → フォルダ」。

> **F02.2 本体の更新タスク**: `docs/features/F02.2_dashboard.md` の `DELETE /api/v1/dashboard/widgets` 節（**処理**の手順1〜2）は「`dashboard_widget_settings` から全レコードを DELETE」としか書いていない。本機能で挙動が変わるため、同節へ「個人スコープでは `dashboard_widget_folders` も併せて削除しフォルダ構成も既定へ戻す（F02.2.2）」の1行を追記する。**本 PR で実施済み**。

### 5.1 既定フォルダ構成の解決（合成マージ方式）

`GET /api/v1/dashboard/widget-folders` は、**DB の実体行と既定 6 フォルダを常にマージして返す**。「行が無ければ全合成／あれば DB のみ」という二分岐にはしない。

1. `dashboard_widget_folders` を `(user_id, scope_type, scope_id)` で検索する。
2. §3.5 の既定 6 フォルダを基準リストとし、**同じ `folder_key` の実体行があればそれで置き換え、無ければ `id: null` の合成行として残す**。
3. ユーザー作成フォルダ（`folder_key IS NULL` の実体行）を、`sort_order` に従って同じリストへ差し込む。
4. `dashboard_widget_settings` を `(user_id, scope_type, scope_id)` で引き、`folder_id` でグルーピングして `widgetKeys` / `unfiledWidgetKeys` を組み立てる。**設定行が無いウィジェットは §3.6 の既定振り分けに従って配置**する（F02.2 の既存「レコード無し＝既定値」の流儀と一致）。

> **なぜ二分岐をやめたか（2026-08-22 是正）**: 初版は「実体行が1件でもあれば合成で補わない」としていた。これだと、ユーザーが 1 つのフォルダを触った瞬間に**残り5つの既定フォルダが画面から消える**。実体化は §5.2 の「触られたフォルダだけ」という部分的な操作なので、二分岐は必ずこの状態を通る。合成マージなら、実体化が何件進んでいても `folders` は常に「既定6＋ユーザー作成分」を返し、`id` が非 null か否かだけが変わる。**`folders` の件数は常に 6 以上**であることが不変条件になる（AC-01/13 で固定する）。

**既定フォルダの「復活」について**: 既定フォルダは削除できない（§5.3）ため、実体行が消えるのは `DELETE /widgets`（全リセット）の場合のみである。その場合は既定構成へ戻るのが正しい挙動であり、合成マージはそれと一致する。

### 5.2 ウィジェット割り当ての変更と実体化

`PUT /api/v1/dashboard/widgets` の UPSERT 時に `folder_id` を書き込む。未実体化（`id: null`）の既定フォルダへ割り当てる場合、`widgets[].folderId` の代わりに `widgets[].folderKey` を送れる。Service は `folderKey` に対応する実体行が無ければ**先に作ってから**割り当てる（初回操作で 6 行が一斉に作られるのではなく、**触られたフォルダだけが実体化する**）。`folderId` と `folderKey` の同時指定は `DASHBOARD_026`（割り当て指定の競合）400。

#### `folderId` の名義解決は 1 クエリで一括（N+1 禁止・部分適用禁止）

`PUT /widgets` のリクエストには複数の `folderId` が混在しうる。**ウィジェット1件ごとに所有チェックの SELECT を撃ってはならない**（24 件送れば 24 回引く）。

```sql
-- リクエスト中の distinct な folderId をまとめて 1 回で名義解決する
SELECT id FROM dashboard_widget_folders
 WHERE user_id = :me AND scope_type = :scopeType AND scope_id = :scopeId
   AND id IN (:folderIds)
```

- 返ってきた件数が `distinct(folderIds)` の件数と**一致しない**場合、1 件でも不明・他人・スコープ不一致の ID が混ざっている。この場合は**リクエスト全体を 404 `DASHBOARD_023` で拒否し、ロールバックする**。
- **部分適用を認めない**。「正当な 23 件だけ保存して不正な 1 件を無視する」実装にすると、クライアントは自分の保存が通ったのか一部落ちたのかを知る手段がなく、画面と DB が静かに乖離する。
- `scope_type` / `scope_id` も名義解決の条件に含める。`user_id` だけで絞ると、将来 team/org へ拡張したときに「自分の別スコープのフォルダ ID」を個人スコープのウィジェットへ代入できてしまう。
- この一括解決は `folderKey` 指定分にも同様に適用する（`folder_key IN (:keys)` で 1 回引き、無いものだけを INSERT する）。

### 5.3 フォルダ削除時の挙動

```
DELETE /widget-folders/{id}
  ├ 既定フォルダ（folder_key != null） → DASHBOARD_024 で拒否（400）
  └ ユーザー作成フォルダ
      ├ UPDATE dashboard_widget_settings SET folder_id = NULL WHERE folder_id = {id} AND user_id = :me
      └ DELETE FROM dashboard_widget_folders WHERE id = {id} AND user_id = :me
```

**同一トランザクション（`@Transactional`・dashboard ドメイン内に閉じる）で実行する。** 順序は「先に中身を今すぐ層へ戻す → 後でフォルダを消す」。逆順にすると、フォルダ削除後に UPDATE が失敗した場合に**どのフォルダにも属さないが NULL でもない孤児 `folder_id`** が残る。FK を張らないため DB は止めてくれない。

削除されたフォルダの中身は**消えない**。今すぐ層に現れる。ユーザーには削除確認ダイアログで「中のウィジェットは『今すぐ』に戻ります」と明示する（§6.4）。

### 5.4 移行方針: 全員リセット【裁可済み】

新 UI のリリース時、**既存ユーザーの個人ダッシュボードの並び順・表示 ON/OFF 設定はすべて破棄し、既定構成へリセットする**（§3.3 のマイグレーション内 `DELETE`）。

- **理由**: 旧 UI の `sort_order` はフラットな 24 件の通し番号であり、二層構造（フォルダ内順序＋フォルダ順序）へ機械的に写像する自然な規則が存在しない。無理に写像すると「ユーザーが意図して上に上げたウィジェットが、フォルダの奥深くの 1 番目」という結果になり、設定を保った意味がない。
- **実害が無い根拠**: 本番環境に実データが未投入であること（マスター裁可・2026-08-22）。ステージング／開発環境のユーザーは再設定で足りる。
- リリースノート・お知らせでの周知は不要（対象ユーザーが実質存在しないため）。将来この前提が変わったら、本節は**再裁可が必要**である。

### 5.5 バッジ集計（Phase1）

| `WidgetKey` | 集計内容 | データソース |
|---|---|---|
| `UNREAD_THREADS` | **未読掲示板スレッド数 ＋ 未読チャット数の合計**（下記注） | 既存 `DashboardController.getUnreadThreads` と同源（`BulletinThreadRepository` + `BulletinReadStatusRepository` + `ChatChannelMemberRepository`） |
| `NOTICES` | 未読お知らせ件数 | 既存 `GET /api/v1/dashboard/notices` の未読集計と同源 |
| `PERSONAL_TODO` | 期限内の未完了 TODO 件数 | F02.3 TODO Repository |

> **`UNREAD_THREADS` は掲示板とチャットの合算である（2026-08-22 第2パス是正）**: 初版は「未読チャットスレッド数」とだけ書いていたが、対応するウィジェット `WidgetUnreadThreads` の実体である `GET /api/v1/dashboard/unread-threads` は、**`total_unread_bulletin`（所属チームの未読掲示板スレッド数）と `total_unread_chat`（チャンネル `unreadCount` の合計）の 2 値を返している**（`DashboardController.java:365-396`）。バッジをチャットのみで数えると、ウィジェットを開けば未読掲示板が並んでいるのにバッジは 0、という**過少集計**になる。バッジは**ウィジェットが見せる内容と同じ母数**を数えなければ意味がない。よって `total_unread_bulletin + total_unread_chat` を返す。

- すべて `user_id` を必須条件とするクエリで、他人の件数は原理的に混入しない。
- **クエリ本数の注意**: 既存 `getUnreadThreads` の掲示板側は「所属チームごとに 100 件取得して未読を数える」ループになっており、**所属チーム数に比例した N+1** を含む。バッジ API でこの実装をそのまま呼ぶと、所属チームが多いユーザーでダッシュボード描画のたびにクエリが膨らむ。バッジ用には**未読件数を 1 本の集計クエリで数える専用メソッド**（`COUNT(*)` と `NOT EXISTS` の結合）を `PersonalWidgetBadgeService` 側に用意すること。既存エンドポイントの N+1 は本 PR のスコープ外だが、**それを新経路へコピーしてはならない**。
- 1 リクエストで 3 クエリ（掲示板未読 1 本・チャット未読 1 本・お知らせ 1 本・TODO 1 本の計 4 本になる場合は、`UNREAD_THREADS` が 2 本を要する旨をテストの期待値に明記する）。いずれにせよ**所属チーム数・ウィジェット数に比例して増えない**ことが要件である（§11.1）。
- **後続フェーズ**: 残る 21 ウィジェットのバッジ化は本機能のスコープ外。追加時は本表と §4.8 のレスポンス例を同時更新する。

#### `RECRUITMENT_FEED` を Phase1 から除外した根拠【U-06 決着】

`origin/main` を実地確認した結果、**募集ドメインに「ユーザーが募集を閲覧済みか」を記録する仕組みが存在しない**。

- `backend/src/main/java/com/mannschaft/app/recruitment/` 配下の全 Entity・Controller・Service に `viewed` / `read` / `seen` / `last_viewed_at` 相当のフィールドは無い（`RecruitmentListingEntity` にも無い）。
- `db/migration` の recruitment 系 SQL（`V3.116`〜`V3.131` 等）にも該当カラムは無い。

したがって「未閲覧の新着募集件数」は現状**算出できない**。代替として「最終ログイン以降に作成された募集数」を当てる案があったが、これは*閲覧*の代理指標として正しくない（ログインしていてもフィードを見ていないことは普通にある。バッジが「見たのに消えない／見ていないのに消える」の両方向で嘘をつく）。**代理指標でバッジを出すくらいなら出さない**。

→ **F03.11 が閲覧トラッキング（`recruitment_listing_views` 相当）を持った時点で Phase2 として追加する。** 追加時は本表・§4.8・AC-33 を同時更新すること。

### 5.6 `folderId` の三値（省略／null／値）

`PUT /api/v1/dashboard/widgets` の BE 側の契約は**差分更新**である（F02.2 §4「リクエストに含まれないウィジェットの設定は変更しない」／`DashboardWidgetService.updateWidgetSettings` は受け取った `widgets[]` のみを UPSERT する）。現行 FE の `persist()` がたまたま全件を送っているだけであり、**「FE は全量送るから未指定は起きない」という前提に寄りかかってはならない**。差分更新の契約下では「フィールド未指定」は日常的に起きる。DTO では次を区別する。

| 送信内容 | 意味 |
|---|---|
| `folderId` フィールド自体が無い | 現在の所属を維持 |
| `"folderId": null` | 今すぐ層へ移動 |
| `"folderId": "018f..."` | そのフォルダへ移動 |

Jackson の素の `String` フィールドでは「未指定」と「明示 null」が両方 `null` になり区別できない。**`JsonNullable<String>`（または `Optional` を包んだ専用ラッパー）で受ける**こと。ここを素の `String` で実装すると、`folderId` を送らないクライアントが全ウィジェットを今すぐ層へ吹き飛ばす。

## 6. UI・UX

### 6.1 フォルダカード（常設グリッド）

```
┌──────────────────────────────┐
│ 📅 予定・時間            (3) │  ← 名前 ＋ 新着件数バッジ
│ 今後の予定 / 参加予定 /       │  ← 内包ウィジェットのラベル一覧
│ 帰省・滞在予定 / 今日の時間割 │     ($t(labelKey) を ' / ' で join)
└──────────────────────────────┘
```

- レイアウトは既存グリッドを踏襲（`grid-cols-1 md:grid-cols-2 lg:grid-cols-3`）。
- ラベル一覧は `widgetKeys` を FE ケバブキーへ逆引きし、`$t(w.labelKey)` を `join(' / ')` で連結する。**直書き文字列は使わない**（i18n ルール）。長い場合は 2 行でクランプし `line-clamp-2` で省略する。
- バッジは、そのフォルダ内ウィジェットの badge 値の合計。**合計が 0 のときはバッジ自体を描画しない**（0 のバッジは視覚ノイズであり、「未対応」との区別もつかない）。
- 空フォルダ（`widgetKeys` が空）はラベル一覧の代わりに `dashboard.folder.empty_hint`（「ウィジェットを追加できます」）を表示する。カードは消さない（そこにドロップ／割り当てできる的が必要なため）。

### 6.2 選択とタブ的展開

- カードクリックで選択状態（`aria-selected="true"`・枠線とアクセント背景）になり、**フォルダカードのグリッド直下**に内容パネルが開く。
- **同時に開けるのは 1 つ**。別のカードをクリックすると前のパネルは閉じ、新しいパネルが開く。
- 選択中のカードを再クリックすると閉じる（トグル）。
- 内容パネルは既存のウィジェット描画をそのまま流用する（`isDataWidget` 分岐・`DashboardWidgetCard` 包み・`col-span` 規則は変更しない）。
- 内容パネルの開閉は既存の `PageTransition` を使わず、`max-height` + `opacity` のトランジションとする（単一ルート要素の制約を持ち込まない）。
- 選択状態は**永続化しない**（リロードで全閉じ）。永続化すると「前回開いた状態」が復元されて今すぐ層が押し下げられ、二層構造の狙いが崩れる。`localStorage` / `sessionStorage` / URL クエリ / ハッシュのいずれにも書かない（AC-40）。

#### アクセシビリティ（WAI-ARIA Tabs パターン準拠）

カード群を `role="tablist"`、各カードを `role="tab"`、内容パネルを `role="tabpanel"` とし、`aria-controls` / `aria-labelledby` で結ぶ。キーボード操作は WAI-ARIA Authoring Practices の Tabs パターンに準拠する。

| キー | 挙動 |
|---|---|
| `←` / `→` | 前後のタブへフォーカス移動（端で折り返す） |
| `↑` / `↓` | 同上（カードが縦積みになるモバイル幅でも操作できるようにする） |
| `Home` | 先頭タブへフォーカス |
| `End` | 末尾タブへフォーカス |
| `Enter` / `Space` | フォーカス中のタブを選択（開く／閉じる） |
| `Tab` | tablist から抜けて次の要素へ（tablist 内の個々のカードは Tab で辿らない） |

**roving tabindex** を用いる（tablist 内でちょうど 1 枚のカードだけが `tabindex="0"`、他は `tabindex="-1"`）。これにより Tab キー 1 回で tablist 全体を通過でき、24 個のカードを Tab で延々と辿らされることがない。

> **roving focus は「選択状態」から分離すること（2026-08-22 第2パス是正）**: 初版は「**選択中の**カードのみ `tabindex="0"`」と書いていたが、本機能は**全フォルダが閉じている状態が初期状態であり、かつ通常状態**である（§6.2 のトグル・リロードで全閉じ）。選択中カードを基準にすると、全閉時に `tabindex="0"` のカードが 1 枚も存在せず、**キーボードユーザーは tablist に入ることすらできない**（Tab で丸ごと飛ばされ、フォルダ機能へ到達する手段が無くなる）。
>
> **正しい規則**: `tabindex="0"` を持つのは「**最後にフォーカスしたカード**」であり、選択（開いているか）とは独立に管理する。初期値は**先頭カード**。全フォルダが閉じていても、いずれか 1 枚は必ず `tabindex="0"` を保つ。

| 状態 | `tabindex="0"` を持つカード |
|---|---|
| 初期表示（全閉） | 先頭カード |
| 矢印で移動中（未選択） | フォーカス中のカード |
| いずれかを選択中 | フォーカス中のカード（選択中のカードとは限らない） |
| 選択を解除して全閉に戻った | 直前にフォーカスしていたカード（`tabindex="0"` は移動しない） |

**選択（activation）は手動方式**（矢印キーはフォーカスのみ動かし、`Enter`/`Space` で初めて開く）とする。自動方式にすると、矢印で通り過ぎるだけで内容パネルが次々に開閉し、内容ウィジェットの API が矢印キーの回数だけ叩かれる。手動方式であることも、roving focus を選択から分離すべき理由の一つである（矢印移動中は「フォーカスはあるが選択はされていない」状態が常に存在する）。

### 6.3 モバイル（カルーセル内での動作）

個人パネルは F22.1 のスワイプ式スコープカルーセルの 1 スライドとして描画される。

- フォルダカードは 1 カラム（`grid-cols-1`）で縦積みになる。
- **横スワイプはカルーセルのスコープ切替に予約されている**。フォルダカードは横スクロールコンテナにしない（カルーセルとジェスチャが競合する）。常設グリッドを縦に積む。
- 内容パネルは開いたカードの直下にインライン展開する（モーダルにしない）。開いたとき、選択カードが画面上端付近に来るよう `scrollIntoView({ block: 'start' })` する。
- 既存の「モバイルでは全ウィジェットを既定で折り畳む」挙動（`collapsedKeys`）は、**内容パネル内のウィジェットに対してのみ**維持する。フォルダカード自体は折り畳み対象ではない。

### 6.4 設定ダイアログ（`DashboardConfigDialog` 拡張）

既存の「表示/非表示トグル＋ドラッグ並べ替え」に、フォルダ操作を加える。

- ウィジェット一覧を**フォルダ単位のセクション**に分け、先頭セクションを「今すぐ」（`dashboard.folder.unfiled`）とする。
- ウィジェット行に「移動先フォルダ」のセレクトを置く（ドラッグ&ドロップでのフォルダ間移動も可能とするが、セレクトを必ず併設する — ドラッグのみだとタッチ環境で詰む）。
- フォルダ操作 UI: 「＋ フォルダを追加」ボタン、各フォルダヘッダに改名（鉛筆）と削除（ゴミ箱）、フォルダ自体のドラッグ並べ替え。
- 削除は確認ダイアログを挟み、`dashboard.folder.delete_confirm`（「『{name}』を削除します。中のウィジェットは『今すぐ』に戻ります。」）を表示する。
- 既定フォルダの削除ボタンは**描画しない**（押せてから 400 で断られるのは悪い体験）。改名・並べ替えは可能。
- ユーザー作成フォルダが 20 に達したら「＋ フォルダを追加」を `disabled` にし、`dashboard.folder.limit_reached` を添える。
- 保存は既存の楽観更新＋失敗ロールバック方式（`optimisticPersist`）を踏襲する。失敗時のトーストは既存 `dashboard.widget_settings.save_error_*` を流用する。

#### 実体化は FE が透過的に行う（入力摩擦ゼロ）

既定フォルダの「未実体化（`id: null`）」は**純粋に BE 側の内部状態**であり、ユーザーに見せてはならない。「まずフォルダを作成してください」のような前置きステップを挟まない。

| ユーザーの1アクション | FE が内部で行うこと | リクエスト数 |
|---|---|---|
| 既定フォルダを改名して確定 | `POST /widget-folders {folderKey, name}` の**1本のみ**（BE が実体化＋改名を単一トランザクションで実施・§4.3） | 1 |
| 既定フォルダを並べ替えて確定 | 並べ替えに関与する未実体化フォルダを `POST {folderKey}` で実体化 → `PUT /reorder` | 1〜N+1 |
| ウィジェットを既定フォルダへ移動 | `PUT /widgets` に `folderKey` を載せる（BE が実体化・§5.2）。追加リクエスト不要 | 1 |

- ユーザーから見た操作は**常に 1 アクションで完結**する。中間状態のダイアログ・確認・スピナーの二段重ねを出さない。
- **改名は FE の2段呼び出しを廃止した（2026-08-22 第2パス是正）**。初版は「実体化 → 改名」の2本立てとし、改名が失敗したら FE が実体化済みフォルダを削除して戻す補償処理を想定していたが、**この補償は実行不可能**である。実体化された行は `folder_key != null` であり、`DELETE /widget-folders/{id}` は `DASHBOARD_024`（既定フォルダは削除不可）で拒否される。元に戻す API が存在しない以上、FE 側の補償では原子性を作れない。**原子性は BE の単一トランザクションで担保する**（§4.3 形式 B の `name` 同時指定）。
- 並べ替えは実体化と `reorder` の2段が残るが、**実体化は冪等**（§4.3）であり、`reorder` が失敗しても「既定フォルダが実体化されただけ」の状態に留まる。この状態は**ユーザーから見て何も変わっていない**（§5.1 の合成マージにより、実体化の有無は表示に影響しない）。よって補償処理は不要であり、失敗時は楽観更新をロールバックしてエラートーストを 1 回出すだけでよい。
- この方針は ADHD-UX 戦役の「入力摩擦を増やさない」に沿う。設定変更のたびに手順が増えると、そもそも設定されなくなる。

### 6.5 初回ヒント（全員リセット移行に伴う一回性の案内）

§5.4 の全員リセットにより、既存ユーザーは**次回ログイン時に画面構成が変わって見える**。何の説明もないと「設定が消えた」と受け取られる。

- 新 UI で初めて個人ダッシュボードを描画したとき、**一度だけ**コーチマーク（フォルダカードのグリッドを指す吹き出し）を表示する。文言は `dashboard.folder.intro_title` / `dashboard.folder.intro_body` / `dashboard.folder.intro_dismiss`。
- 表示済みフラグは `localStorage`（キー: `dashboard.folderIntroSeen`）に持つ。**サーバーには持たない**（一回性の案内のためにテーブルや API を足すのは過剰。端末を変えてもう一度出るのは許容範囲であり、実害がない）。
- 「閉じる」を押す、またはいずれかのフォルダカードを開くと消える（操作できた時点で説明は役目を終える）。
- コーチマークが出せない文脈（SSR 初回描画・モーダルが既に開いている）ではトーストへフォールバックし、`life: 8000` で自動的に消す。
- **モーダルにはしない**。ログイン直後にダッシュボードを塞ぐ全画面モーダルは、目的があって来たユーザーの動線を止める。

### 6.6 `settings/dashboard-widgets.vue` の追従

設定ページ（`/settings/dashboard-widgets`）も同じフォルダ構造を扱えるようにする。ダイアログと設定ページで**同一のフォルダ編集コンポーネント**（`DashboardFolderEditor`）を共有し、二重実装しない（同じ機能が 2 箇所に別実装で存在すると、片方だけ直る）。個人スコープ以外のタブ（チーム／組織）ではフォルダ UI を出さない。

## 7. セキュリティ

### 7.1 認可

すべてのエンドポイントで、対象は**認証ユーザー自身**に固定する。

- `user_id` はリクエストから受け取らず、`SecurityUtils.getCurrentUserId()` で確定する。
- 更新・削除系の SQL は**必ず `user_id = :currentUserId` を条件に含める**（`WHERE id = ? AND user_id = ?`）。`id` だけを条件にした更新・削除を書かない。ID が UUIDv7 で推測困難であることを防御に数えない。
- Controller には `@SelfScopedEndpoint` を付し、「削除・更新対象が `(currentUserId, ...)` の複合条件に閉じている」根拠を注記する（既存 `DELETE /api/v1/dashboard/widgets` と同じ流儀）。この注記があると認可番人 ArchUnit の対象から外れるため、**注記の内容が実装と一致していることをテストで裏取りする**（AC-20 / AC-20b の他人 ID 混入テスト。§11.0 の対応表では BE 統合テストに配置）。

### 7.2 F00 `ContentVisibilityResolver` を通さない根拠

F00 の可視性解決は「あるコンテンツを、閲覧者がスコープのロール／可視性設定に照らして見てよいか」を判定する仕組みである。本機能が扱うのは:

1. **ユーザー自身の画面レイアウト設定**（フォルダ名・並び順・所属）であり、他者に配信されるコンテンツではない。
2. フォルダは**ウィジェットの中身を含まない**。フォルダカードに出るのはウィジェットの i18n ラベルと件数だけであり、件数の元になる各ウィジェットのデータは、既存の各ウィジェット API が**それぞれ自前の可視性判定を通した上で**返している。

したがってフォルダ API に可視性解決は不要。ただし **§5.5 のバッジ集計は例外的に注意が必要**で、集計クエリは各ドメインの既存 Repository を直接叩くため、**元の API が課していた可視性フィルタを迂回しうる**。バッジ集計は「自分宛て／自分が作成した」行のみを数える集計に限定し、他者コンテンツの可視性判定を要する集計は Phase1 の対象に入れない（4 種はいずれもこの条件を満たす）。

### 7.3 入力検証

| 項目 | 規則 |
|---|---|
| `name` | トリム後 1〜50 文字。制御文字を拒否。HTML エスケープは描画時（Vue の既定）に委ねる |
| `folderIds`（reorder） | 全要素が自分のフォルダ、かつ自分の全フォルダを漏れなく含む |
| フォルダ数 | 1 ユーザー 20 件（`chat_contact_folders` の `MAX_FOLDERS_PER_USER` と同値） |

### 7.4 存在秘匿 — 既存 `DASHBOARD_007`（403）と意図的に異なる

他人のフォルダ ID を指定した操作は、すべて**不在時と同じ 404 `DASHBOARD_023`** を返す。403 との出し分けは「その ID は存在する」を漏らす（存在オラクル）。

**根拠**: 本プロジェクトは越境アクセスを 404 で秘匿する方針を採っており、`backend/src/test/java/**/**ScopeContractIT.java`（129 クラス以上）が各ドメインでこれを機械的に固定している。例: `MemberScopeContractIT`（`backend/src/test/java/com/mannschaft/app/member/MemberScopeContractIT.java:263-267`）

```java
@DisplayName("別チームADMIN（越境IDでpageAを直指定）は404（BOLA存在秘匿）")
void 越境IDは404() throws Exception {
    setAuth(adminBId);
    mockMvc.perform(get("/api/v1/team/pages/{id}", pageAId))
            .andExpect(status().isNotFound());
```

**同一ドメイン内の既存挙動との差異**: チャットフォルダ（`ChatFolderController`）は他人のフォルダに対して `DASHBOARD_007` = **403 FORBIDDEN** を返す（`GlobalExceptionHandler.java:1866-1867` の写像表に `Map.entry("DASHBOARD_007", HttpStatus.FORBIDDEN)  // FOLDER_NOT_OWNED（存在は隠さず権限拒否）` と明示。`ChatFolderController.java:80` 付近の `updateFolder` が経路）。

本機能はこれと**意図的に異なる 404 を採る**。理由:

| | `chat_contact_folders`（既存・403） | `dashboard_widget_folders`（本機能・404） |
|---|---|---|
| 性質 | 連絡先・DM の分類。**共有・招待の文脈**があり、他人のフォルダ ID を正当に知りうる場面が想定されている | **純粋に個人の画面設定**。他人がその ID を正当に知る経路が存在しない |
| ID を知っている＝ | 正当な経緯がありうる | 総当たりか漏洩のいずれか |
| 適切な応答 | 「あなたのものではない」と伝える方が親切 | 存在すら教えない |

他人の ID を正当に知る経路が無い以上、403 は「当たりの ID を引いた」というシグナルにしかならない。よって 404 を採る。

> **実装時の注意**: この差異は**同じ `DashboardErrorCode` enum の中に 403 と 404 が同居する**ことを意味する。`GlobalExceptionHandler` の写像表に `DASHBOARD_023 → NOT_FOUND` を追加する際、隣の `DASHBOARD_007 → FORBIDDEN` を「揃っていない」と見て直さないこと（揃えると chat 側の既存契約が壊れる）。写像表にこの意図をコメントで残す。

### 7.5 エラーコード（予約）

`DashboardErrorCode` の現在の最大は `DASHBOARD_019` のため、`DASHBOARD_020` から予約する。**確定は本 PR のマージ時に再確認すること**（並行戦役が同域を使う可能性がある）。

> **`DASHBOARD_006`〜`DASHBOARD_009` の流用は禁止**。これらは名前が「フォルダ」で紛らわしいが、**チャット・連絡先フォルダ（`chat_contact_folders`）専用**である（`DASHBOARD_006` FOLDER_NOT_FOUND / `007` FOLDER_NOT_OWNED / `008` FOLDER_NAME_DUPLICATE / `009` 作成上限20件）。メッセージ文言も HTTP 写像も chat 側の契約として `GlobalExceptionHandler` と `*IT` に固定済みであり、本機能が相乗りすると chat 側のテストを巻き込んで壊す。**ウィジェットフォルダは 020 番台の独自コードを使う**。

| コード | メッセージ | HTTP |
|---|---|---|
| `DASHBOARD_020` | ウィジェットフォルダの作成上限（20件）に達しています | 409 |
| `DASHBOARD_021` | 同じ名前のウィジェットフォルダが既に存在します | 409 |
| `DASHBOARD_022` | フォルダ名は1〜50文字で指定してください | 400 |
| `DASHBOARD_023` | 指定されたウィジェットフォルダが存在しません | 404 |
| `DASHBOARD_024` | 既定フォルダは削除できません | 400 |
| `DASHBOARD_025` | 並べ替え対象のフォルダ一覧が不正です | 400 |
| `DASHBOARD_026` | folderId と folderKey は同時に指定できません | 400 |

#### エンドポイント × エラーコード マトリクス

| エンドポイント | 200/201/204 | 400 | 401 | 404 | 409 |
|---|---|---|---|---|---|
| `GET /widget-folders` | 200 | `DASHBOARD_014`（scopeType 不正） | 未認証 | — | — |
| `POST /widget-folders` | 201（新規）/ 200（`folderKey` 実体化で既存あり） | `DASHBOARD_022`, `DASHBOARD_014`, `DASHBOARD_026` | 未認証 | — | `DASHBOARD_020`, `DASHBOARD_021` |
| `PUT /widget-folders/{id}` | 200 | `DASHBOARD_022` | 未認証 | `DASHBOARD_023` | `DASHBOARD_021` |
| `DELETE /widget-folders/{id}` | 204 | `DASHBOARD_024`（既定フォルダ） | 未認証 | `DASHBOARD_023` | — |
| `PUT /widget-folders/reorder` | 200 | `DASHBOARD_025`, `DASHBOARD_014` | 未認証 | — | — |
| `PUT /widgets` | 200 | `DASHBOARD_001`, `DASHBOARD_002`, `DASHBOARD_015`, `DASHBOARD_026` | 未認証 | `DASHBOARD_023`（folderId 名義解決失敗） | — |
| `DELETE /widgets` | 204 | `DASHBOARD_014` | 未認証 | — | — |
| `GET /widgets/badges` | 200 | `DASHBOARD_014` | 未認証 | — | — |

401 はすべて Spring Security のフィルタ段で返るため `DashboardErrorCode` を経由しない（`ErrorResponse` の形は共通）。`reorder` が 404 を持たないのは、不正 ID を「不整合な配列」として `DASHBOARD_025` の 400 に畳むため（配列全体の妥当性検証であり、個別 ID の存在照会ではない）。

## 9. 既知課題の是正: 永続化欠落 4 ウィジェット【前提作業・同梱】

現状、personal スコープの 24 ウィジェットのうち **4 つが `WidgetKeyMap`（FE）に登録されておらず、並び順・表示設定が DB に一切保存されていない**。`useDashboardWidgets.persist()` は `backendKey()` が `undefined` のウィジェットを `continue` でスキップするため、これらはドラッグしても保存されず、リロードで元に戻る（症状が出ているのに誰も直していない）。

フォルダ割り当ても `dashboard_widget_settings` の行に載る以上、**キーが無いウィジェットはフォルダにも入れられない**。よって本機能の前提として同梱で是正する。

| FE key | 現状 | 是正内容 |
|---|---|---|
| `recruitment-feed` | BE キー無し・FE マップ無し | BE `WidgetKey.RECRUITMENT_FEED(PERSONAL, true, 27)` 新設 ＋ FE `WidgetKeyMap` 登録 ＋ `DashboardWidgetService.WIDGET_NAMES` へ「新着募集」追加 |
| `my-recruitments` | BE キー無し・FE マップ無し | BE `WidgetKey.MY_RECRUITMENTS(PERSONAL, true, 28)` 新設 ＋ FE マップ登録 ＋ `WIDGET_NAMES` へ「参加予定」追加 |
| `village-lobby-digest` | BE キー無し・FE マップ無し | BE `WidgetKey.VILLAGE_LOBBY_DIGEST(PERSONAL, true, 29)` 新設 ＋ FE マップ登録 ＋ `WIDGET_NAMES` へ「井戸端ダイジェスト」追加 |
| `my-corkboard` | BE `MY_CORKBOARD` は**既存**・FE マップのみ欠落 | FE `WidgetKeyMap` に `'my-corkboard': { personal: 'MY_CORKBOARD' }` を追加するのみ（BE 変更不要） |

> **`defaultSortOrder` の 27〜29 は暫定値**。`WidgetKey` の personal スコープの現在の最大 `defaultSortOrder` は `RETURN_STAY_PLAN` の 26 だが、**本 PR のマージ時点で並行戦役が新ウィジェットを足していれば衝突する**（`WidgetKey` は enum 定数の追加が競合しにくく、squash merge で静かに重複しうる）。実装時に `origin/main` の最新を引いて personal スコープの最大値を数え直し、+1 から採番すること。番号自体は「レコード未作成時の既定並び順」にしか使われないため機能は壊れないが、重複すると既定順が不定になる。

> **`SwipeWidgetKey` への追随は不要**。`SwipeWidgetKey`（F22.1 の横スワイプ用 8 ウィジェット）は `WidgetKey` と**名前空間を意図的に分離**しており（同 enum の Javadoc: 「F02.2 の可視性設定と共有すると片方の非表示がもう片方に波及するため」）、かつ定義されているのは `SWIPE_TEAM_*` / `SWIPE_ORG_*` のみで **personal スコープの値を1つも持たない**。本機能は personal スコープ限定のため、`SwipeWidgetKey` への追加は発生しない。フォルダ機能も同様に `SwipeWidgetKey` を対象外とする（対象にすると分離した名前空間を再び混ぜることになる）。

**再発防止**: FE `ALL_WIDGETS` の personal ウィジェットが全件 `WidgetKeyMap` に登録されていることを検証する FE ユニットテストを追加する。これが無い限り、次にウィジェットを足した人が同じ穴を開ける（4 件開いた実績がある）。

### 11.1 バックエンド 単体テスト

- 既定フォルダ合成ロジック（`DashboardWidgetFolderService`）: 設定 0 件 → 6 フォルダ＋4 今すぐ、**部分実体化 → 実体行と合成行が混在して 6 件返る**（実体行があっても合成を打ち切らない・§5.1）。
- フォルダ削除の順序（中身 NULL 化 → フォルダ削除）が同一 `@Transactional` 内で行われること。**`TransactionTemplate` でテスト自身を包まない**（自分の透過性を測ってしまう）。
- `folderId` 三値（未指定／null／値）の解釈（§5.6）。素の `String` 実装だと未指定で全件が今すぐ層へ落ちることを、退行テストで固定する。
- 上限 20（**ユーザー作成フォルダのみ計数**）・名称 50（**コードポイント数**）・トリム・重複判定（`name IS NOT NULL` の行のみ比較）。
- `POST` 形式 B の `folderKey` + `name` 同時指定で、実体化と改名が**同一トランザクション**で行われること（改名側の失敗でフォルダ行も残らない）。
- **クエリ本数の検証**: バッジ集計が 3 本、`PUT /widgets` の folderId 名義解決が 1 本であること。

> **クエリ本数検証の実装方針**: `ScopeWidgetSummaryServiceTest`（`backend/src/test/java/com/mannschaft/app/dashboard/service/ScopeWidgetSummaryServiceTest.java`）を前例として挙げたが、**実地確認したところ同テストは `verify()` を1件も使っておらず**、`@Mock` + `given()` によるスタブと戻り値の `assertThat` のみで構成されている。つまり**このプロジェクトにクエリ本数を固定する前例は無い**。本機能で新たに `verify(repository, times(1)).findXxx(...)` の形で導入する。前例が無いことを承知の上で入れる理由は、バッジ対象が Phase2 で増える予定であり、そのとき「キーを 1 つ足したらクエリが 1 本増える」構造になっていないことを機械的に守る必要があるため。

### 11.2 バックエンド 統合テスト（Testcontainers）

- Flyway マイグレーションが実 MySQL で通ること、`DELETE FROM dashboard_widget_settings WHERE scope_type='PERSONAL'` が既存行を消すこと。
- **`test` プロファイルは Entity 由来の DDL であり Flyway シードを踏まない**ため、マイグレーション自体の検証は Testcontainers（実 DDL）側で行う。Entity にだけ `folder_id` を足して DDL を忘れる事故は、この経路でしか捕まらない。
- **`BINARY(16)` の噛み合わせ**: フォルダを INSERT → その `id` を `folder_id` に入れて設定を INSERT → GET で読み戻す、を実 MySQL で 1 往復させる。Entity 側が `CHAR` を要求していれば `test` プロファイルでは通り、ここで初めて落ちる（§3.2 JPA マッピング注記）。
- **退会・匿名化の後始末**: `AccountPurgeService.purgeUser` 実行後に、当該 `user_id` の `dashboard_widget_folders` および `dashboard_widget_settings` が**ともに 0 件**になること（§3.4）。フォルダだけ消えて設定が残る／その逆の半端な状態にならないことを両方 assert する。
- **並行実体化（AC-13e/13f）**: `CountDownLatch` で 2 スレッドから同一 `folderKey` の `POST` を同時に放ち、片方 201・片方 200・DB 上は 1 行、を検証する。重複キー例外が握りつぶされて 0 行になる／500 が返る、のいずれもここで落ちる。
- **上限の並行突破（AC-15c/15d）**: 19 件の状態から 2 スレッド同時 `POST` で 20 件に収まること、および 0 件の状態から 2 スレッド同時 `POST` で 2 件になること。**悲観ロックの粒度（folders 行ロック vs users 行ロック）は、この 2 本を実 MySQL で走らせて決める**（§4.3）。モック緑のまま並行で壊れている、という形の欠陥はこの経路でしか捕まらない。
- **`UNREAD_THREADS` の母数一致（AC-33/33b）**: 未読掲示板のみ・未読チャットのみ・両方、の 3 パターンで、バッジ値が既存 `GET /api/v1/dashboard/unread-threads` の `total_unread_bulletin + total_unread_chat` と一致すること。
- **バッジのクエリ本数が所属チーム数に依存しない（AC-35b）**: 所属チーム 1 件と 20 件のユーザーで発行 SQL 本数が同一であること（既存実装の N+1 を新経路へコピーしていない）。
- 他ユーザーのフォルダ ID を用いた全操作（AC-20/21/23/35）を `@AutoConfigureMockMvc(addFilters = false)` **ではない**実 SecurityFilterChain 経路でも検証する（`@SelfScopedEndpoint` により ArchUnit の認可番人から外れるため、IT が唯一の防御になる）。
- 論理削除・キャッシュの一次キャッシュ干渉を避けるため、更新後の検証は `flush` + `clear` を挟む。

### 11.3 フロントエンド

- `useDashboardWidgets` のフォルダ対応: 既定合成レスポンスからの状態組み立て、フォルダ間移動の楽観更新とロールバック。
- `WidgetKeyMap` 網羅テスト（AC-48）。
- コンポーネントテスト: 単一展開（AC-38/39）、バッジ 0 の非描画（AC-36）、ラベル `join(' / ')`（AC-41）。
- **キーボード到達性（AC-46e/46f）**: 全フォルダ閉状態で `tabindex="0"` の要素がちょうど 1 つ存在すること、選択解除後も `tabindex="0"` が直前のフォーカス位置に留まること。**「選択中のカードに `tabindex=0`」という実装だと全閉で 0 個になり、このテストが落ちる**。
- 既定フォルダの改名が `POST` 1 本で完結すること（`PUT /widget-folders/{id}` が呼ばれていないことを fetch モックで検証。2 段呼び出しへの退行を防ぐ）。
- i18n: 追加キーが 6 言語すべてに存在すること（既存の locale 網羅テストがあればそれに乗せる）。

### 11.4 E2E（実機）

- 実 UI でフォルダを作成 → ウィジェットを移動 → リロード → 保持されている、までの CRUD 一気通貫。**モックなし・実 BE**。
- 375px 幅でのスワイプ競合確認（AC-46）。
- 「保存されたように見えるが実は保存されていない」を捕まえるため、**必ずリロードを挟んで検証**する（§9 の欠落 4 件はまさにこの検証が無くて 4 件も溜まった）。

## 12. 非機能

### 12.1 クエリ特性（1000万ユーザー前提）

- フォルダ一覧・ウィジェット設定・バッジ集計のすべてのクエリは、**`user_id` を先頭に持つ索引で閉じる**。
  - `idx_dwf_user_scope_sort (user_id, scope_type, scope_id, sort_order)` — フォルダ一覧はこの索引だけでソート済みに取れる（filesort なし）。
  - `uq_dwf_user_scope_key (user_id, scope_type, scope_id, folder_key)` — `folderKey` 指定の実体化時の存在判定。
  - `dashboard_widget_settings` の既存 `(user_id, scope_type, scope_id)` 索引 — ウィジェット設定取得。
  - `idx_dws_user_folder (user_id, folder_id)` — フォルダ削除時の一括 NULL 化。**先頭が `user_id` のため索引だけで自分の行に閉じる**。1 ユーザーのフォルダ 1 個分（最大 24 行）に限定される。
- `BINARY(16)` を採ったことで、`folder_id` の索引エントリは `CHAR(36)`（`utf8mb4` で最大 144 バイト）比で大幅に小さい。1000万ユーザー × 最大 24 行の設定表において、この差は索引がバッファプールに載るか否かに効く。
- 全ユーザー横断のスキャンを要するクエリは**存在しない**。テーブルはユーザー数に比例して伸びるが、1 リクエストの読み取り件数はユーザーあたり定数（フォルダ ≤20、設定 ≤ ウィジェット数）に収まる。
- 個人ダッシュボード 1 描画あたりの追加リクエストは **2 本**（`widget-folders` と `widgets/badges`）。ウィジェット設定は既存の 1 本を流用する。フォルダ数・ウィジェット数が増えてもリクエスト本数は増えない。

### 12.2 段階拡張の範囲

| フェーズ | 範囲 |
|---|---|
| **Phase 1（本設計）** | personal スコープ。既定 6 フォルダ＋ユーザー定義。バッジ 3 種。 |
| Phase 2 | バッジ対象の拡大（残り 21 ウィジェット。`RECRUITMENT_FEED` は F03.11 が閲覧トラッキングを持ち次第ここで追加）。集計コストが上がるため、Valkey キャッシュ（TTL 数十秒）の導入をここで検討する。 |
| Phase 3 | チーム／組織スコープへの拡張。**`scope_type` / `scope_id` の両列を Phase1 で用意済みのため、テーブル定義の変更なしで拡張できる**（Service とエンドポイントの `scopeType` 受理範囲を広げるのみ）。 |

### 12.3 キャッシュ

Phase1 ではキャッシュを入れない。フォルダ構成は変更頻度が低いが、変更直後に古い構成が見える不整合の方が体験上悪い。バッジは「新着件数」であり鮮度が価値そのもののため、キャッシュするなら TTL は数十秒が上限（Phase2 で検討）。
