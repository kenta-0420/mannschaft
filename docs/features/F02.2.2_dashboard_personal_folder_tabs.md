## 1. 概要

個人ダッシュボード（`DashboardPersonalPanel.vue`）は現在、約24個のウィジェットを 1〜3 カラムのグリッドへ**横並びで全件展開**している。ウィジェット数が増えるほど縦に長大化し、「今すぐ必要な情報」が下方へ押し流される。本機能はこれを **「フォルダ＝タブ」** の二層構造に再構成する。

- **上層（今すぐ層）**: フォルダに属さないウィジェットを従来どおり生のカードとして常時表示する。`dashboard_widget_settings.folder_id IS NULL` のウィジェットが該当する。
- **下層（フォルダ層）**: フォルダカードが常設グリッドとして並ぶ。カードには内包ウィジェットのラベル一覧と新着件数バッジを表示し、選択するとタブのように選択状態になって、グリッド直下の**内容パネル**へ中身のウィジェット群が展開される。

ユーザーは任意のウィジェットを今すぐ層⇔フォルダ間で自由に移動でき、フォルダ自体も作成・改名・削除・並べ替えできる。「今日の時間割を常に一番上に置きたい」「募集フィードは普段畳んでおきたい」といった個人差を、ウィジェットの ON/OFF ではなく**配置**で吸収する。

> **本ドキュメントとの参照規約**: ウィジェット一覧（key・名称・データソース）の正本は F02.2 が保持する。本ドキュメントは「フォルダ構造」と「既定の振り分け」のみを定義する。新ウィジェットを追加する際は F02.2 のウィジェット一覧と本ドキュメント §3.5 の既定振り分け表の**両方**を更新すること。

### 本ドキュメントのスコープ

| 機能 | 説明 |
|------|------|
| フォルダカード常設グリッド | 個人パネル下段を、ウィジェット横並びからフォルダカード一覧へ置き換える |
| タブ的展開 | フォルダカード選択で内容パネルが開く（同時に開くのは1つ・再クリックで閉） |
| 今すぐ層 | `folder_id IS NULL` のウィジェットをフォルダ外に生表示 |
| ユーザー定義フォルダ | 作成・改名・削除・並べ替え（上限20・名称50文字） |
| ウィジェット割り当て | 任意ウィジェットの今すぐ層⇔フォルダ間の移動 |
| 新着件数バッジ（Phase1） | 4ウィジェット限定の件数集約 API を新設しフォルダカードへ集計表示 |
| 永続化欠落4ウィジェットの是正 | `recruitment-feed` / `my-recruitments` / `village-lobby-digest` / `my-corkboard` のキー整備（§9） |

**スコープ外**:
- チーム／組織ダッシュボード（`scope_type = TEAM / ORGANIZATION`）。DDL に `scope_type` 列を持たせて将来拡張の余地のみ残す（§3.2）
- フォルダのアイコン・カラー設定（`chat_contact_folders` は持つが、本機能 Phase1 では持たない）
- フォルダの入れ子（サブフォルダ）
- 全ウィジェットのバッジ対応（Phase1 は4種のみ。§5.5）
- ウィジェットの ON/OFF・並び順そのものの仕様変更（F02.2 の既存仕様を踏襲。フォルダ内の並び順は既存 `sort_order` を流用する）
- F02.2.1 の `min_role` 制御（個人スコープは対象外＝自分のデータしか出ないため）

### 対象レベル

### 対象ロール

| ロール | 説明 |
|--------|------|
| 認証済みユーザー（全ロール） | 自分の個人ダッシュボードのフォルダ構成を作成・変更できる |
| 未認証 | 対象外（個人ダッシュボード自体が認証必須） |

個人スコープのため、閲覧者ロールによる出し分け（F02.2.1）も、F00 の `ContentVisibilityResolver` による可視性判定も走らない（根拠は §7.2）。

### 二層モデル

```
┌─ 挨拶ヘッダー ──────────────────────────────┐
│ WidgetCommandCenter（固定・移動不可）        │
│ WidgetFamilyHub（v-if・固定・移動不可）      │
├─ 今すぐ層（folder_id IS NULL）──────────────┤
│ [お知らせ] [マイカレンダー]                  │
│ [天気] [TODOカウントダウン]                  │
├─ フォルダ層（フォルダカード常設グリッド）────┤
│ [予定・時間割 ③] [やること ①] [連絡・お知らせ ⑤] │
│ [フィード] [マイコンテンツ] [所属]           │
├─ 内容パネル（選択中フォルダのみ展開）────────┤
│ 「予定・時間割」の中身ウィジェット群          │
├─ 末尾固定 ──────────────────────────────────┤
│ WidgetAdminBusinessAlert（v-if）/ Spotlight  │
└──────────────────────────────────────────────┘
```

### 固定パネル（本機能でも移動不可）

以下は従来どおり `v-if` による固定描画であり、フォルダにも今すぐ層にも「割り当て」の対象としない（`dashboard_widget_settings` の行を持たないため `folder_id` も持ちえない）。

| コンポーネント | 位置 | 条件 |
|---|---|---|
| `WidgetCommandCenter` | 挨拶ヘッダー直下 | 常時 |
| `WidgetFamilyHub` | 司令塔の直下 | `hasFamilyTeam` |
| `WidgetAdminBusinessAlert` | 末尾 | `hasAdminOrDeputyRole` |
| `WidgetSpotlightPrimary` / `Secondary` | 最末尾 | 掲載候補あり |

**これらは「今すぐ層に見える」が、今すぐ層のメンバーではない**（DB 上の概念ではなくテンプレート固定描画）。UI 上の連続性のためこの順序で描画するが、設定ダイアログの一覧には出さない。

## 3. DB設計

### 3.1 テーブル一覧

| テーブル名 | 役割 | 論理削除 |
|-----------|------|---------|
| `dashboard_widget_folders`（新規） | ユーザー単位のウィジェットフォルダ（既定6＋ユーザー定義） | なし（物理削除） |
| `dashboard_widget_settings`（既存・列追加） | `folder_id` 列を追加し、ウィジェットの所属フォルダを保持 | なし |

### 3.2 テーブル定義

#### `dashboard_widget_folders`（新規）

| カラム名 | 型 | NULL | デフォルト | 説明 |
|---------|---|------|-----------|------|
| `id` | CHAR(36) | NO | — | PK。UUIDv7（`UuidV7Entity` 継承） |
| `user_id` | BIGINT UNSIGNED | NO | — | 所有ユーザー。FK は張らずアプリ層で整合（クロスドメインFK禁止） |
| `scope_type` | VARCHAR(20) | NO | `'PERSONAL'` | スコープ種別。Phase1 は `PERSONAL` のみ。将来の TEAM / ORGANIZATION 拡張余地 |
| `folder_key` | VARCHAR(50) | YES | NULL | システム既定フォルダの識別子（§3.4）。ユーザー作成フォルダは NULL |
| `name` | VARCHAR(50) | YES | NULL | 表示名。NULL の場合は `folder_key` の i18n 名を使う（既定フォルダの未改名状態） |
| `sort_order` | INT | NO | 0 | フォルダカードの並び順（昇順） |
| `created_at` | DATETIME(6) | NO | CURRENT_TIMESTAMP(6) | |
| `updated_at` | DATETIME(6) | NO | CURRENT_TIMESTAMP(6) ON UPDATE | |

**インデックス**

```sql
UNIQUE KEY uq_dwf_user_scope_key (user_id, scope_type, folder_key)  -- 既定フォルダの重複作成防止
KEY idx_dwf_user_scope_sort (user_id, scope_type, sort_order)       -- 一覧取得（user_id で閉じる）
```

**制約・備考**

- `organization_id` は**持たない**。本テーブルは「ユーザー個人の画面設定」であり、テナント境界（`AbstractTenantAwareRepository`）の対象外である（`dashboard_widget_settings` と同じ扱い）。
- FK は張らない。`user_id` はクロスドメイン参照のためアプリ層で整合を保証し、インデックスのみ張る（[domain_db_design_principles.md](../architecture/domain_db_design_principles.md) 原則1）。
- `folder_key` が NULL の行が同一ユーザーに複数存在しうる（ユーザー作成フォルダ）。MySQL の UNIQUE は NULL を重複と見なさないため、この UNIQUE 制約はユーザー作成フォルダを妨げない。
- 名称の重複はユーザー作成フォルダ間で**アプリ層検証**する（`chat_contact_folders` と同じ流儀。DB の UNIQUE では NULL 混在のため表現できない）。
- 照合順序は `utf8mb4_0900_ai_ci`（プロジェクト統一。V173 以前の混在を持ち込まない）。
- ユーザー退会時: `dashboard_widget_settings` と同じ運用（退会時匿名化バッチで併せて削除）。CASCADE は張らない。

#### `dashboard_widget_settings`（既存・列追加）

| カラム名 | 型 | NULL | デフォルト | 説明 |
|---------|---|------|-----------|------|
| `folder_id` | CHAR(36) | YES | NULL | 所属フォルダ。**NULL = 今すぐ層**（フォルダ外の生表示） |

```sql
KEY idx_dws_folder (folder_id)   -- フォルダ削除時の一括 NULL 化・フォルダ内ウィジェット取得
```

- FK は張らない（同一ドメイン内だがアプリ層整合の既存流儀を維持し、フォルダ削除時の挙動を Service で明示制御するため。§5.3）。
- 既存行の `folder_id` は NULL で追加される。**移行方針が「全員リセット」のため、既存行はマイグレーション後に初回アクセス時点で既定構成へ置き換わる**（§5.4）。

### 3.3 Flyway マイグレーション

```
V189.{yyyyMMddHHmmss}__create_dashboard_widget_folders.sql
```

> **採番注**: `major` は本 PR マージ時点の `origin/main` 全体の最大 major + 1 で**再確認して確定**すること。本設計書執筆時点（2026-08-22）の最大 major は 188 のため `V189` を想定するが、並行戦役のマージで前後しうる。`minor` は `date -u '+%Y%m%d%H%M%S'` のタイムスタンプ必須（連番禁止・`FlywayTimestampNamingGuardTest` が拒否）。

```sql
CREATE TABLE dashboard_widget_folders (
    id          CHAR(36)        NOT NULL,
    user_id     BIGINT UNSIGNED NOT NULL,
    scope_type  VARCHAR(20)     NOT NULL DEFAULT 'PERSONAL',
    folder_key  VARCHAR(50)     NULL,
    name        VARCHAR(50)     NULL,
    sort_order  INT             NOT NULL DEFAULT 0,
    created_at  DATETIME(6)     NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
    updated_at  DATETIME(6)     NOT NULL DEFAULT CURRENT_TIMESTAMP(6) ON UPDATE CURRENT_TIMESTAMP(6),
    PRIMARY KEY (id),
    UNIQUE KEY uq_dwf_user_scope_key (user_id, scope_type, folder_key),
    KEY idx_dwf_user_scope_sort (user_id, scope_type, sort_order)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;

ALTER TABLE dashboard_widget_settings
    ADD COLUMN folder_id CHAR(36) NULL AFTER widget_key,
    ADD KEY idx_dws_folder (folder_id);

-- 移行方針「全員リセット」: 既存の並び順・表示設定を破棄し、初回アクセス時の既定合成に委ねる。
-- 本番実データが未投入であること（殿の裁可・2026-08-22）を前提とする。
DELETE FROM dashboard_widget_settings WHERE scope_type = 'PERSONAL';
```

既定フォルダ行の **INSERT は行わない**。F02.2 既存の遅延作成方式を踏襲し、レコードが無いユーザーには API 側で既定構成を合成して返す（§5.1）。

## 4. API設計

### 4.1 エンドポイント一覧

| メソッド | パス | 説明 | 認可 |
|---|---|---|---|
| GET | `/api/v1/dashboard/widget-folders` | フォルダ一覧＋各フォルダの widgetKey 配列 | 本人のみ |
| POST | `/api/v1/dashboard/widget-folders` | フォルダ作成 | 本人のみ |
| PUT | `/api/v1/dashboard/widget-folders/{id}` | フォルダ改名 | 本人のみ |
| DELETE | `/api/v1/dashboard/widget-folders/{id}` | フォルダ削除（中身は今すぐ層へ戻す） | 本人のみ |
| PUT | `/api/v1/dashboard/widget-folders/reorder` | フォルダ並べ替え | 本人のみ |
| PUT | `/api/v1/dashboard/widgets` | **既存**。`items[].folderId` を追加 | 本人のみ |

すべて `ApiResponse<T>` ラッパーを返す（F02.2 既存流儀）。`scopeType` は `personal` のみ受理し、それ以外は `DASHBOARD_014`（無効なスコープタイプ）で 400 とする。

### 4.2 `GET /api/v1/dashboard/widget-folders`

**クエリパラメータ**

| 名前 | 型 | 必須 | 説明 |
|---|---|---|---|
| `scopeType` | string | YES | `personal` 固定（Phase1） |

**レスポンス** `200 OK`

```jsonc
{
  "data": {
    "folders": [
      {
        "id": "018f2c...",              // string(UUID) / NOT NULL。既定フォルダ未作成時も合成 UUID ではなく null を返す（下記注）
        "folderKey": "SCHEDULE",         // string | null。ユーザー作成フォルダは null
        "name": "予定・時間",             // string | NOT NULL。既定フォルダ未改名時は folderKey の i18n 名を BE が解決せず、FE が labelKey から描画（下記注）
        "nameKey": "dashboard.folder.schedule", // string | null。folderKey 由来の i18n キー。ユーザー作成フォルダは null
        "sortOrder": 0,                  // integer | NOT NULL
        "isSystem": true,                // boolean | NOT NULL。folderKey != null と等価。削除不可の判定に使う
        "widgetKeys": ["UPCOMING_EVENTS", "MY_RECRUITMENTS", "RETURN_STAY_PLAN", "TIMETABLE_TODAY"]
                                         // string[] | NOT NULL（空配列あり）。sort_order 昇順
      }
    ],
    "unfiledWidgetKeys": ["NOTICES", "PERSONAL_CALENDAR", "PERSONAL_WEATHER", "PERSONAL_TODO_COUNTDOWN"]
                                         // string[] | NOT NULL。今すぐ層（folder_id IS NULL）
  }
}
```

> **`id` と `name` の null 許容についての設計判断**: 遅延作成方式のため、一度も設定を保存していないユーザーには DB 行が存在しない。この場合 **`id` は `null`** を返し、`folderKey` / `nameKey` / `widgetKeys` のみで既定構成を表現する。FE は `id === null` のフォルダに対する改名・削除・並べ替えを行う前に、まず `PUT /api/v1/dashboard/widgets`（フォルダ込みの一括保存）を通して実体化させる。`name` は `folderKey` があれば BE では NULL のまま返し、FE が `nameKey` を `$t()` して描画する（多言語をサーバー側で決め打たない）。ユーザー作成フォルダおよび改名済み既定フォルダは `name` に実値が入り `nameKey` は `null` になる。

### 4.3 `POST /api/v1/dashboard/widget-folders`

**リクエスト**

```jsonc
{
  "scopeType": "personal",   // string | NOT NULL
  "name": "受験対策",         // string | NOT NULL / 1〜50文字 / 前後空白トリム後に空は不可
  "sortOrder": 6             // integer | nullable。未指定なら末尾（既存最大+1）
}
```

**レスポンス** `201 Created` — §4.2 の `folders[]` 要素 1 件（`folderKey: null` / `isSystem: false` / `widgetKeys: []`）。

**エラー**

| 状況 | コード | HTTP |
|---|---|---|
| フォルダ数が 20 に到達 | `DASHBOARD_020` | 409 |
| 同名フォルダが既に存在 | `DASHBOARD_021` | 409 |
| `name` が 50 文字超・空 | `DASHBOARD_022` | 400 |

### 4.4 `PUT /api/v1/dashboard/widget-folders/{id}`（改名）

**リクエスト**: `{ "name": "新しい名前" }`（`string | NOT NULL / 1〜50文字`）

**レスポンス** `200 OK` — 更新後のフォルダ 1 件。既定フォルダも改名可能（`name` に値が入り、`nameKey` は `null` になる）。

**エラー**: `DASHBOARD_023`（フォルダ不存在）404 / `DASHBOARD_021`（名称重複）409 / `DASHBOARD_022`（長さ違反）400。

> **他人のフォルダ ID を指定した場合も `DASHBOARD_023` の 404** を返す（不在側と同一ステータス）。403 を返すと「その ID のフォルダは存在する」という存在オラクルになる（`docs/security/README.md` の存在秘匿方針）。

### 4.5 `DELETE /api/v1/dashboard/widget-folders/{id}`

**レスポンス** `204 No Content`。削除と同時に、そのフォルダに属していたウィジェットの `folder_id` を **`NULL`（今すぐ層）へ戻す**（§5.3）。

**エラー**: `DASHBOARD_023`（不存在）404 / `DASHBOARD_024`（既定フォルダは削除不可）400。

### 4.6 `PUT /api/v1/dashboard/widget-folders/reorder`

**リクエスト**

```jsonc
{
  "scopeType": "personal",
  "folderIds": ["018f2c...", "018f2d...", "..."]   // string[] | NOT NULL。全フォルダを漏れなく含む配列。先頭が sortOrder=0
}
```

**レスポンス** `200 OK` — 並べ替え後のフォルダ一覧（§4.2 と同形）。

**エラー**: 自分のフォルダでない ID が混ざる／自分のフォルダで配列に含まれない ID がある → `DASHBOARD_025`（並べ替え対象の不整合）400。

### 4.7 `PUT /api/v1/dashboard/widgets`（既存拡張）

既存の一括保存リクエストの `widgets[]` 要素へ `folderId` を追加する。

```jsonc
{
  "scopeType": "personal",
  "scopeId": null,
  "widgets": [
    {
      "widgetKey": "UPCOMING_EVENTS",  // string | NOT NULL（既存）
      "isVisible": true,               // boolean | NOT NULL（既存）
      "sortOrder": 0,                  // integer | NOT NULL / >= 0（既存）
      "folderId": "018f2c..."          // string(UUID) | nullable（新規）。null = 今すぐ層
    }
  ]
}
```

- `folderId` を**省略した場合は現在値を維持**、明示的に `null` を送った場合は今すぐ層へ移動する（省略と null の区別が必要なため、DTO は `JsonNullable` 相当の三値表現を用いる。詳細は §5.6）。
- 存在しない／他人の `folderId` を指定 → `DASHBOARD_023` 404。
- `sortOrder` は**フォルダ内での並び順**として解釈する（フォルダをまたいで一意である必要はない）。今すぐ層は `folder_id IS NULL` のグループ内で並ぶ。

### 4.8 `GET /api/v1/dashboard/widgets/badges`

**クエリパラメータ**: `scopeType`（`personal` 固定）

**レスポンス** `200 OK`

```jsonc
{
  "data": {
    "badges": {
      "UNREAD_THREADS": 3,     // integer | NOT NULL / >= 0
      "NOTICES": 1,
      "PERSONAL_TODO": 5,
      "RECRUITMENT_FEED": 0
    },
    "generatedAt": "2026-08-22T09:00:00Z"   // string(date-time) | NOT NULL
  }
}
```

- **Phase1 の対象は 4 種のみ**: `UNREAD_THREADS`（未読チャットスレッド数）/ `NOTICES`（未読お知らせ数）/ `PERSONAL_TODO`（期限内の未完了 TODO 数）/ `RECRUITMENT_FEED`（未閲覧の新着募集数）。
- **対象外のウィジェットはキーごと返さない**（`0` を返さない）。「集計対象外」と「0件」を FE が区別できるようにするため。後続フェーズで対象を広げる際に、既に 0 が返っていると「増えていない」のか「未対応」なのか判別できなくなる。
- 実装は `ScopeWidgetSummaryService` の前例（各ドメインの既存 Repository を流用して集約する dashboard ドメインのサマリ Service）に倣い、`PersonalWidgetBadgeService` を新設する。
- フォルダカードのバッジは、そのフォルダに属するウィジェットの badge 値の**合計**を FE 側で算出する（BE はウィジェット粒度の生値のみ返す。ユーザーがウィジェットをフォルダ間で移動しても BE を変えずに追随できる）。

### 4.9 `DELETE /api/v1/dashboard/widgets`（既存拡張）

既存のリセット API は `dashboard_widget_settings` の該当行を削除するだけだが、本機能では**同一トランザクションで `dashboard_widget_folders` の該当行も削除**する。結果として、次回の GET で §5.1 の既定構成が合成される＝フォルダ構成も出荷時状態へ戻る。

## 5. ビジネスロジック

### 5.1 既定フォルダ構成の解決（遅延作成方式）

`GET /api/v1/dashboard/widget-folders` の処理:

1. `dashboard_widget_folders` を `(user_id, scope_type)` で検索する。
2. **1件も無い場合**: §3.4 の既定 6 フォルダと §3.5 の既定振り分けから、DB を書かずにレスポンスを合成する（`id: null`）。
3. **1件以上ある場合**: DB の行をそのまま返す。既定フォルダのうち DB に無いものは**合成で補わない**（ユーザーが削除…は既定フォルダではできないが、将来の仕様変更やデータ欠損時に「勝手に復活する」挙動を避けるため）。
4. `dashboard_widget_settings` を `(user_id, PERSONAL, 0)` で引き、`folder_id` でグルーピングして `widgetKeys` / `unfiledWidgetKeys` を組み立てる。**設定行が無いウィジェットは §3.5 の既定振り分けに従って配置**する（F02.2 の既存「レコード無し＝既定値」の流儀と一致）。

### 5.2 ウィジェット割り当ての変更

`PUT /api/v1/dashboard/widgets` の UPSERT 時に `folder_id` を書き込む。フォルダが DB 上に未実体化（`id: null` で返していた既定フォルダ）の場合、FE は先に `POST` ではなく、**BE が `folderKey` 指定での実体化を受け付ける**。すなわち `widgets[].folderId` に加えて `widgets[].folderKey` を受け付け、`folderKey` が指定され対応行が無ければ Service が既定フォルダ行を作ってから割り当てる（初回操作で 6 行が一斉に作られるのではなく、**触られたフォルダだけが実体化する**）。`folderId` と `folderKey` の同時指定は `DASHBOARD_026`（割り当て指定の競合）400。

### 5.3 フォルダ削除時の挙動

```
DELETE /widget-folders/{id}
  ├ 既定フォルダ（folder_key != null） → DASHBOARD_024 で拒否（400）
  └ ユーザー作成フォルダ
      ├ UPDATE dashboard_widget_settings SET folder_id = NULL WHERE folder_id = {id} AND user_id = :me
      └ DELETE FROM dashboard_widget_folders WHERE id = {id} AND user_id = :me
```

**同一トランザクション（`@Transactional`・dashboard ドメイン内に閉じる）で実行する。** 順序は「先に中身を今すぐ層へ戻す → 後でフォルダを消す」。逆順にすると、フォルダ削除後に UPDATE が失敗した場合に**どのフォルダにも属さないが NULL でもない孤児 `folder_id`** が残る。FK を張らないため DB は止めてくれない。

削除されたフォルダの中身は**消えない**。今すぐ層に現れる。ユーザーには削除確認ダイアログで「中のウィジェットは『今すぐ』に戻ります」と明示する（§6.4）。

### 5.4 移行方針: 全員リセット【裁可済み】

新 UI のリリース時、**既存ユーザーの個人ダッシュボードの並び順・表示 ON/OFF 設定はすべて破棄し、既定構成へリセットする**（§3.3 のマイグレーション内 `DELETE`）。

- **理由**: 旧 UI の `sort_order` はフラットな 24 件の通し番号であり、二層構造（フォルダ内順序＋フォルダ順序）へ機械的に写像する自然な規則が存在しない。無理に写像すると「ユーザーが意図して上に上げたウィジェットが、フォルダの奥深くの 1 番目」という結果になり、設定を保った意味がない。
- **実害が無い根拠**: 本番環境に実データが未投入であること（マスター裁可・2026-08-22）。ステージング／開発環境のユーザーは再設定で足りる。
- リリースノート・お知らせでの周知は不要（対象ユーザーが実質存在しないため）。将来この前提が変わったら、本節は**再裁可が必要**である。

### 5.5 バッジ集計（Phase1）

| `WidgetKey` | 集計内容 | データソース |
|---|---|---|
| `UNREAD_THREADS` | 未読チャットスレッド数 | `ChatChannelMemberRepository` の未読集計（既存 `getUnreadThreads` と同源） |
| `NOTICES` | 未読お知らせ件数 | 既存 `GET /api/v1/dashboard/notices` の未読集計と同源 |
| `PERSONAL_TODO` | 期限内の未完了 TODO 件数 | F02.3 TODO Repository |
| `RECRUITMENT_FEED` | 未閲覧の新着募集件数 | F03.11 募集 Repository |

- すべて `user_id` を必須条件とするクエリで、他人の件数は原理的に混入しない。
- 1 リクエストで 4 クエリ。N+1 にならないよう Service 内で並列ではなく逐次 4 本に固定する（本数がキーの数で増えないことをテストで固定する。§10）。
- **後続フェーズ**: 残る 20 ウィジェットのバッジ化は本機能のスコープ外。追加時は本表と §4.8 のレスポンス例を同時更新する。

### 5.6 `folderId` の三値（省略／null／値）

`PUT /api/v1/dashboard/widgets` は既存の全量 PUT であり、FE は毎回全ウィジェットを送る。しかし将来の部分更新や他クライアントを考慮し、DTO では次を区別する。

| 送信内容 | 意味 |
|---|---|
| `folderId` フィールド自体が無い | 現在の所属を維持 |
| `"folderId": null` | 今すぐ層へ移動 |
| `"folderId": "018f..."` | そのフォルダへ移動 |

Jackson の素の `String` フィールドでは「未指定」と「明示 null」が両方 `null` になり区別できない。**`JsonNullable<String>`（または `Optional` を包んだ専用ラッパー）で受ける**こと。ここを素の `String` で実装すると、`folderId` を送らないクライアントが全ウィジェットを今すぐ層へ吹き飛ばす。

## 6. UI・UX

### 6.1 フォルダカード（常設グリッド）

```
┌──────────────────────────────┐
│ 📅 予定・時間            (3) │  ← 名前 ＋ 新着件数バッジ
│ 今後の予定 / 参加予定 /       │  ← 内包ウィジェットのラベル一覧
│ 帰省・滞在予定 / 今日の時間割 │     ($t(labelKey) を ' / ' で join)
└──────────────────────────────┘
```

- レイアウトは既存グリッドを踏襲（`grid-cols-1 md:grid-cols-2 lg:grid-cols-3`）。
- ラベル一覧は `widgetKeys` を FE ケバブキーへ逆引きし、`$t(w.labelKey)` を `join(' / ')` で連結する。**直書き文字列は使わない**（i18n ルール）。長い場合は 2 行でクランプし `line-clamp-2` で省略する。
- バッジは、そのフォルダ内ウィジェットの badge 値の合計。**合計が 0 のときはバッジ自体を描画しない**（0 のバッジは視覚ノイズであり、「未対応」との区別もつかない）。
- 空フォルダ（`widgetKeys` が空）はラベル一覧の代わりに `dashboard.folder.empty_hint`（「ウィジェットを追加できます」）を表示する。カードは消さない（そこにドロップ／割り当てできる的が必要なため）。

### 6.2 選択とタブ的展開

- カードクリックで選択状態（`aria-selected="true"`・枠線とアクセント背景）になり、**フォルダカードのグリッド直下**に内容パネルが開く。
- **同時に開けるのは 1 つ**。別のカードをクリックすると前のパネルは閉じ、新しいパネルが開く。
- 選択中のカードを再クリックすると閉じる（トグル）。
- 内容パネルは既存のウィジェット描画をそのまま流用する（`isDataWidget` 分岐・`DashboardWidgetCard` 包み・`col-span` 規則は変更しない）。
- 内容パネルの開閉は既存の `PageTransition` を使わず、`max-height` + `opacity` のトランジションとする（単一ルート要素の制約を持ち込まない）。
- **アクセシビリティ**: カード群を `role="tablist"`、各カードを `role="tab"`、内容パネルを `role="tabpanel"` とし、`aria-controls` / `aria-labelledby` で結ぶ。左右矢印キーでカード間を移動できる。
- 選択状態は**永続化しない**（リロードで全閉じ）。永続化すると「前回開いた状態」が復元されて今すぐ層が押し下げられ、二層構造の狙いが崩れる。

### 6.3 モバイル（カルーセル内での動作）

個人パネルは F22.1 のスワイプ式スコープカルーセルの 1 スライドとして描画される。

- フォルダカードは 1 カラム（`grid-cols-1`）で縦積みになる。
- **横スワイプはカルーセルのスコープ切替に予約されている**。フォルダカードは横スクロールコンテナにしない（カルーセルとジェスチャが競合する）。常設グリッドを縦に積む。
- 内容パネルは開いたカードの直下にインライン展開する（モーダルにしない）。開いたとき、選択カードが画面上端付近に来るよう `scrollIntoView({ block: 'start' })` する。
- 既存の「モバイルでは全ウィジェットを既定で折り畳む」挙動（`collapsedKeys`）は、**内容パネル内のウィジェットに対してのみ**維持する。フォルダカード自体は折り畳み対象ではない。

### 6.4 設定ダイアログ（`DashboardConfigDialog` 拡張）

既存の「表示/非表示トグル＋ドラッグ並べ替え」に、フォルダ操作を加える。

- ウィジェット一覧を**フォルダ単位のセクション**に分け、先頭セクションを「今すぐ」（`dashboard.folder.unfiled`）とする。
- ウィジェット行に「移動先フォルダ」のセレクトを置く（ドラッグ&ドロップでのフォルダ間移動も可能とするが、セレクトを必ず併設する — ドラッグのみだとタッチ環境で詰む）。
- フォルダ操作 UI: 「＋ フォルダを追加」ボタン、各フォルダヘッダに改名（鉛筆）と削除（ゴミ箱）、フォルダ自体のドラッグ並べ替え。
- 削除は確認ダイアログを挟み、`dashboard.folder.delete_confirm`（「『{name}』を削除します。中のウィジェットは『今すぐ』に戻ります。」）を表示する。
- 既定フォルダの削除ボタンは**描画しない**（押せてから 400 で断られるのは悪い体験）。改名・並べ替えは可能。
- フォルダ数が 20 に達したら「＋ フォルダを追加」を `disabled` にし、`dashboard.folder.limit_reached` を添える。
- 保存は既存の楽観更新＋失敗ロールバック方式（`optimisticPersist`）を踏襲する。失敗時のトーストは既存 `dashboard.widget_settings.save_error_*` を流用する。

### 6.5 `settings/dashboard-widgets.vue` の追従

設定ページ（`/settings/dashboard-widgets`）も同じフォルダ構造を扱えるようにする。ダイアログと設定ページで**同一のフォルダ編集コンポーネント**（`DashboardFolderEditor`）を共有し、二重実装しない（同じ機能が 2 箇所に別実装で存在すると、片方だけ直る）。個人スコープ以外のタブ（チーム／組織）ではフォルダ UI を出さない。

## 7. セキュリティ

### 7.1 認可

すべてのエンドポイントで、対象は**認証ユーザー自身**に固定する。

- `user_id` はリクエストから受け取らず、`SecurityUtils.getCurrentUserId()` で確定する。
- 更新・削除系の SQL は**必ず `user_id = :currentUserId` を条件に含める**（`WHERE id = ? AND user_id = ?`）。`id` だけを条件にした更新・削除を書かない。ID が UUIDv7 で推測困難であることを防御に数えない。
- Controller には `@SelfScopedEndpoint` を付し、「削除・更新対象が `(currentUserId, ...)` の複合条件に閉じている」根拠を注記する（既存 `DELETE /api/v1/dashboard/widgets` と同じ流儀）。この注記があると認可番人 ArchUnit の対象から外れるため、**注記の内容が実装と一致していることをテストで裏取りする**（§10 の「他人の folder_id 混入テスト」）。

### 7.2 F00 `ContentVisibilityResolver` を通さない根拠

F00 の可視性解決は「あるコンテンツを、閲覧者がスコープのロール／可視性設定に照らして見てよいか」を判定する仕組みである。本機能が扱うのは:

1. **ユーザー自身の画面レイアウト設定**（フォルダ名・並び順・所属）であり、他者に配信されるコンテンツではない。
2. フォルダは**ウィジェットの中身を含まない**。フォルダカードに出るのはウィジェットの i18n ラベルと件数だけであり、件数の元になる各ウィジェットのデータは、既存の各ウィジェット API が**それぞれ自前の可視性判定を通した上で**返している。

したがってフォルダ API に可視性解決は不要。ただし **§5.5 のバッジ集計は例外的に注意が必要**で、集計クエリは各ドメインの既存 Repository を直接叩くため、**元の API が課していた可視性フィルタを迂回しうる**。バッジ集計は「自分宛て／自分が作成した」行のみを数える集計に限定し、他者コンテンツの可視性判定を要する集計は Phase1 の対象に入れない（4 種はいずれもこの条件を満たす）。

### 7.3 入力検証

| 項目 | 規則 |
|---|---|
| `name` | トリム後 1〜50 文字。制御文字を拒否。HTML エスケープは描画時（Vue の既定）に委ねる |
| `folderIds`（reorder） | 全要素が自分のフォルダ、かつ自分の全フォルダを漏れなく含む |
| フォルダ数 | 1 ユーザー 20 件（`chat_contact_folders` の `MAX_FOLDERS_PER_USER` と同値） |
| `scopeType` | `personal` のみ。他は 400 |

### 7.4 存在秘匿

他人のフォルダ ID を指定した操作は、すべて**不在時と同じ 404 `DASHBOARD_023`** を返す。403 との出し分けは「その ID は存在する」を漏らす（存在オラクル）。

### 7.5 エラーコード（予約）

## 11. テスト観点

### 11.1 バックエンド 単体テスト

- 既定フォルダ合成ロジック（`PersonalWidgetFolderResolver`）: 設定 0 件 → 6 フォルダ＋4 今すぐ、部分実体化 → DB 行優先。
- フォルダ削除の順序（中身 NULL 化 → フォルダ削除）が同一 `@Transactional` 内で行われること。**`TransactionTemplate` でテスト自身を包まない**（自分の透過性を測ってしまう）。

- バッジ集計の SQL 本数がキー数に対して固定（4 本）であること。

### 11.2 バックエンド 統合テスト（Testcontainers）

- Flyway マイグレーションが実 MySQL で通ること、`DELETE FROM dashboard_widget_settings WHERE scope_type='PERSONAL'` が既存行を消すこと。
- **`test` プロファイルは Entity 由来の DDL であり Flyway シードを踏まない**ため、マイグレーション自体の検証は Testcontainers（実 DDL）側で行う。Entity にだけ `folder_id` を足して DDL を忘れる事故は、この経路でしか捕まらない。

## 12. 非機能

### 12.1 クエリ特性（1000万ユーザー前提）

- フォルダ一覧・ウィジェット設定・バッジ集計のすべてのクエリは、**`user_id` を先頭に持つ索引で閉じる**。
  - `idx_dwf_user_scope_sort (user_id, scope_type, sort_order)` — フォルダ一覧はこの索引だけでソート済みに取れる（filesort なし）。
  - `dashboard_widget_settings` の既存 `(user_id, scope_type, scope_id)` 索引 — ウィジェット設定取得。
  - `idx_dws_folder (folder_id)` — フォルダ削除時の一括 NULL 化。1 ユーザーのフォルダ 1 個分（最大 24 行）に限定される。
- 全ユーザー横断のスキャンを要するクエリは**存在しない**。テーブルはユーザー数に比例して伸びるが、1 リクエストの読み取り件数はユーザーあたり定数（フォルダ ≤20、設定 ≤ ウィジェット数）に収まる。
- 個人ダッシュボード 1 描画あたりの追加リクエストは **2 本**（`widget-folders` と `widgets/badges`）。ウィジェット設定は既存の 1 本を流用する。フォルダ数・ウィジェット数が増えてもリクエスト本数は増えない。

### 12.2 段階拡張の範囲

| フェーズ | 範囲 |
|---|---|
| **Phase 1（本設計）** | personal スコープ。既定 6 フォルダ＋ユーザー定義。バッジ 4 種。 |
| Phase 2 | バッジ対象の拡大（残り 20 ウィジェット）。集計コストが上がるため、Valkey キャッシュ（TTL 数十秒）の導入をここで検討する。 |
| Phase 3 | チーム／組織スコープへの拡張。`scope_type` 列は用意済みだが、**`scope_id` 列が無いため追加 DDL が必要**（§13）。 |

### 12.3 キャッシュ

Phase1 ではキャッシュを入れない。フォルダ構成は変更頻度が低いが、変更直後に古い構成が見える不整合の方が体験上悪い。バッジは「新着件数」であり鮮度が価値そのもののため、キャッシュするなら TTL は数十秒が上限（Phase2 で検討）。
