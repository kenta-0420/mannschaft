## 1. 目的と採用方針

個人ダッシュボードは24個の設定対象ウィジェットを一続きのグリッドへ全件展開しており、必要な情報へ到達するまでの縦スクロールが長い。案Cでは次の二層へ再構成する。

- **今すぐ層**: <code>WidgetCommandCenter</code>、<code>my-calendar</code>、<code>notices</code>を生のカードで先に表示する。
- **整理層**: 残る22個の設定対象ウィジェットを、固定5カテゴリのアコーディオンへ分類する。

カテゴリはユーザーが作る「フォルダ」ではない。カテゴリ名・順序・所属は製品側の固定定義であり、ユーザーが編集、追加、削除、並べ替え、カテゴリ間移動する機能は設けない。ユーザー設定として維持するのは、既存のウィジェット単位の表示/非表示と並び順だけである。

### 1.1 元モック案Cから採用する仕様

- 今すぐ層を常時展開し、その下へカテゴリ見出しを縦に積む。
- 初期状態は全カテゴリを閉じる。
- 各カテゴリは独立して開閉し、**複数カテゴリを同時に開ける**。
- 閉じた見出しにも1行プレビューと件数バッジを出す。
- カテゴリ内はカードグリッドとし、狭幅では1列へ落とす。
- カテゴリアイコンは順に 📆、✅、💬、📰、🗂️ とする。

### 1.2 元モックから意図的に補完・変更する仕様

元モックは説明用の静的HTMLであり、カテゴリ内には14個の表示項目しかなかった。また「所属」はチームと組織を1枚にまとめ、プレビューとバッジは固定文言だった。現行実装との整合のため、次を補完する。

| 論点 | 元モック | 本仕様 |
|---|---|---|
| 設定対象 | カテゴリ内14表示項目。「所属」は1表示 | 現行24ウィジェットを欠落なく扱う。「所属」は <code>my-teams</code> と <code>my-organizations</code> に分ける |
| モック未掲載 | 7ウィジェットの所属が未定義 | §3の固定表へ補完する |
| 見出しプレビュー | 日付・未読数等を含む固定例文 | 表示中ウィジェットの先頭2ラベルからクライアントで算出する |
| バッジ | 固定数値 | カテゴリ内の表示中ウィジェット数をクライアントで算出する |
| 内容カード | 短いダミーのミニカード | 現行ウィジェット本体を描画する |
| 開閉状態 | 非永続 | 非永続を維持する。再読込時は全閉 |

この補完により、カテゴリ専用APIや複数ドメインを横断する件数集約APIを作らず、現行の表示設定だけで見出しを確定できる。

## 4. アコーディオンUI

### 4.1 見出し

各見出しは左から、カテゴリ絵文字、カテゴリ名、1行プレビュー、件数バッジ、開閉シェブロンの順に並べる。

プレビューは、そのカテゴリで<code>visible=true</code>のウィジェットを表示順に並べ、i18nラベルから次のように算出する。

| 表示中件数 | プレビュー |
|---:|---|
| 0 | 「表示するウィジェットはありません」 |
| 1 | 「ラベル1」 |
| 2 | 「ラベル1 / ラベル2」 |
| 3以上 | 「ラベル1 / ラベル2 ほかN件」。「N」は表示中件数 - 2 |

- プレビューはデータ内容、未読数、API成功状態には依存しない。
- 1行、省略記号付きとし、見出し全体を横スクロールさせない。
- ラベルと空状態文言は全対応ロケールのi18nから取得し、文字列をテンプレートへ直書きしない。

バッジは、そのカテゴリで<code>visible=true</code>のウィジェット数を整数表示する。

- 非表示ウィジェットはプレビュー、バッジ、展開内容のすべてから除外する。
- 0でもバッジを隠さず、灰色のzeroスタイルで「0」を表示する。
- 件数はローカルの設定状態からO(24)以内で算出し、バッジ専用APIを呼ばない。

### 4.2 開閉状態

- 初回表示、再読込、再訪問では5カテゴリすべて閉じる。
- 見出しを押すと対象カテゴリだけを開閉する。他カテゴリの状態は変えない。
- 同時に0〜5カテゴリを開ける。
- 開閉状態をDB、<code>localStorage</code>、<code>sessionStorage</code>、URL query/hashへ保存しない。
- 開閉に伴って自動スクロールやフォーカス移動を行わない。

### 4.3 lazy first mountと再展開

- 閉じたカテゴリのウィジェット本体は初期mountしない。
- カテゴリを初めて開いた時だけ、そのカテゴリの表示中ウィジェットをmountする。
- 一度mountしたカテゴリは、閉じてもコンポーネントインスタンスを破棄しない。DOMは非表示にし、再展開時に内部状態、入力途中の値、個別ウィジェットの取得結果を保つ。
- 「閉じて開き直した」ことだけを理由にデータAPIを再取得しない。各ウィジェット固有の更新、TTL、手動更新は従来仕様を維持する。
- 非表示へ変更されたウィジェットは内容DOMから除外する。再表示時のmountは通常の初回mountとして扱う。

実装上はカテゴリごとに<code>hasEverOpened</code>を持ち、初回までは条件描画、初回以後は可視性切替を使う。開閉状態そのものはページコンポーネントのメモリだけに置く。

### 4.4 アクセシビリティ

- 見出し全体をネイティブ<code>button type="button"</code>とする。クリック可能な<code>div</code>を使わない。
- ボタンは一意な内容領域IDを<code>aria-controls</code>で参照し、状態を<code>aria-expanded</code>で公開する。
- 内容領域は<code>role="region"</code>とし、見出しIDを<code>aria-labelledby</code>で参照する。
- 閉じた内容領域は<code>hidden</code>相当で支援技術とTab順から除外する。
- バッジには「表示中N件」と分かるアクセシブル名を付ける。装飾絵文字とシェブロンは重複読上げを避ける。
- Tab / Shift+Tabは通常の文書順で5見出しを移動する。Enter / Spaceはフォーカス中のカテゴリだけを開閉する。
- タブUIではないため、<code>tablist</code>、<code>tab</code>、<code>tabpanel</code>、<code>aria-selected</code>、roving tabindex、矢印キーによる専用移動を実装しない。
- <code>:focus-visible</code>の輪郭をライト・ダーク両テーマで識別可能にする。
- シェブロン回転を含む遷移は<code>prefers-reduced-motion: reduce</code>で無効化する。

### 4.5 レスポンシブとジェスチャ

- 今すぐ層は<code>repeat(auto-fit, minmax(230px, 1fr))</code>相当とし、狭幅では1列にする。760px以上では<code>WidgetCommandCenter</code>を2列相当にできる。
- カテゴリ内容は<code>repeat(auto-fit, minmax(220px, 1fr))</code>相当とし、360px・390pxでは必ず1列にする。
- 見出しの最小操作高は44pxとする。
- 360px・390pxで本文、見出し、プレビュー、バッジがビューポートを越えない。長い翻訳ラベルは省略表示する。
- アコーディオン領域自身は横スクロールコンテナにしない。
- <code>touchstart</code>、<code>touchmove</code>へ一律<code>preventDefault</code>を掛けず、F22.1の親スコープカルーセルへ横スワイプを透過する。
- 展開時の高さ変化で親カルーセルの現在スコープを変えない。

### 4.6 視覚仕様

元モックの意味をプロジェクトの既存surface/accentトークンへ対応させる。

- アコーディオン外枠: surface背景、1px line、角丸12px、軽いshadow、項目間10px。
- 見出し: padding 13px 16px、gap 10px、太字。シェブロンは <code>▸</code> 相当で、開時に90度回転。
- 内容領域: 見出しとの間に上罫線、左右16px、上12px、下14px。
- バッジ: 高さ20px、最小幅20px、pill形、11px太字、tabular numerals。1以上はbadge色、0はsurface2背景とmuted文字色。
- 元モックのライト基準色は ground <code>#F4F6F8</code>、surface <code>#FFFFFF</code>、surface2 <code>#EDF0F4</code>、ink <code>#1C2430</code>、muted <code>#5B6675</code>、line <code>#DCE2E9</code>、accent <code>#35618E</code>、badge <code>#C25E1F</code>。
- ダーク基準色は ground <code>#13171D</code>、surface <code>#1C2129</code>、surface2 <code>#242B35</code>、ink <code>#E6EAEF</code>、muted <code>#98A3B0</code>、line <code>#333B47</code>、accent <code>#7FA8CF</code>、badge <code>#E08A4C</code>。
- 実装では同等コントラストの既存PrimeVue/Tailwindテーマトークンを使い、テーマ切替を壊す固定色の直書きは避ける。

## 5. 設定、DB、API

### 5.1 維持するデータ

既存<code>dashboard_widget_settings</code>だけを使う。

| 既存項目 | 用途 |
|---|---|
| <code>user_id</code> / <code>scope_type</code> / <code>scope_id</code> | 本人のPERSONAL設定の識別 |
| <code>widget_key</code> | 24ウィジェットの識別 |
| <code>is_visible</code> | 今すぐ層・プレビュー・バッジ・展開内容への表示可否 |
| <code>sort_order</code> | 同一固定カテゴリ内または今すぐ層内の相対順 |

カテゴリ所属、カテゴリ順、開閉状態は保存しない。

### 5.2 使用する既存API

| メソッド | パス | 用途 |
|---|---|---|
| GET | <code>/api/v1/dashboard/widgets?scopeType=personal</code> | 表示/非表示・並び順の取得 |
| PUT | <code>/api/v1/dashboard/widgets</code> | 24件の表示/非表示・並び順を全量保存 |
| DELETE | <code>/api/v1/dashboard/widgets?scope_type=PERSONAL</code> | 個人設定を削除し既定表示・既定順へ戻す |

- リクエスト・レスポンス形はF02.2から変更しない。
- カテゴリ取得、カテゴリCRUD、カテゴリ並べ替え、ウィジェットのカテゴリ移動、バッジ集計のAPIは追加しない。
- <code>folderId</code>、<code>folderKey</code>等を設定APIへ追加しない。
- PUTは既存どおり本人のPERSONAL設定だけを更新し、途中失敗時に部分適用しない。
- DELETEは<code>dashboard_widget_settings</code>だけを削除する。カテゴリは静的定義なので削除対象がない。

### 5.3 撤回する旧案E

次の設計・実装は行わない。

- <code>dashboard_widget_folders</code>テーブル
- <code>dashboard_widget_settings.folder_id</code>列と関連インデックス
- フォルダ用Flyway DDL、既存設定の全員リセット
- フォルダの作成、改名、削除、並べ替え、実体化
- 今すぐ層とフォルダ間、フォルダ間のウィジェット移動
- <code>/api/v1/dashboard/widget-folders</code>配下のAPI
- <code>/api/v1/dashboard/widgets/badges</code>

チャットの連絡先フォルダ等、他機能が持つ<code>folder_id</code>やフォルダAPIは本撤回の対象外である。

### 5.4 既存設定との互換性

- 既存ユーザーの<code>is_visible</code>をそのまま適用し、非表示設定を勝手に戻さない。
- 既存<code>sort_order</code>を各固定グループ内の相対順として利用し、既存行を書き換える移行は行わない。
- カテゴリが静的であるため、既存設定にカテゴリ情報がなくても追加取得なしで描画できる。
- GETが<code>200 []</code>の場合は24個を既定表示・§3の既定順とする。
- GETが失敗した場合もローディングのまま固めず、同じ既定構成へフォールバックする。ただし失敗を成功扱いにして自動PUTはしない。
- 未知のBEキーは描画せず、開発時に検知できる警告を1キー1回に抑えて出す。既知24キーを欠落させることはテスト失敗とする。
- <code>sortOrder</code>がnull、重複、負数、または極端な値でも、数値で並べた後に§3の既定順をタイブレークとして安定描画する。保存時は24件を0〜23の重複なし連番へ正規化する。

## 6. ロード、失敗、空状態

### 6.1 初期ロード

- 既存設定は従来どおりSSR対応の<code>useAsyncData</code>で取得し、表示順確定前のフラット旧レイアウトを描画しない。
- 設定解決後の最初の描画から、今すぐ層と閉じた5見出しを表示する。
- 閉じたカテゴリのデータウィジェットを初期mountしないため、それらの個別データ取得も走らない。
- プレビューとバッジは設定とi18nラベルだけで先に描画できる。

### 6.2 空状態

- あるカテゴリの22対象がすべて非表示でも、そのカテゴリ見出しは消さない。
- その見出しは空状態プレビューと灰色の「0」バッジを表示する。
- 0件カテゴリを開いた場合、内容領域に「表示するウィジェットはありません」と設定を開く導線を表示する。
- 24ウィジェットすべてが非表示でも、<code>WidgetCommandCenter</code>、5カテゴリ見出し、条件を満たす固定パネルは残り、設定画面へ復帰できる。
- 各ウィジェット自身の0件/nullデータは、そのウィジェット既存の空状態を使う。カテゴリ件数を0へ減らす理由にはしない。

### 6.3 途中失敗

- カテゴリ内の1ウィジェットが取得失敗しても、カテゴリ全体や他ウィジェットを閉じない。失敗したカードだけ既存エラー表示と再試行導線を出す。
- あるカテゴリを開いている間に個別取得が失敗しても、他の開いているカテゴリの状態を変えない。
- 設定PUT失敗時は楽観更新前の表示/非表示・並び順へ戻し、既存エラートーストを表示する。カテゴリ固定マップは変化しない。
- 開閉操作はローカルUI状態なので、設定APIやデータAPIの成否により拒否しない。
- 素早い開閉を繰り返しても二重mount・重複リクエスト・古い非同期応答による開閉状態の逆転を起こさない。

## 7. 性能条件

- 本改修による追加HTTPリクエストは0本とする。
- 初期表示時に発生する設定リクエストは既存1本だけで、カテゴリ数やウィジェット数に比例させない。
- プレビューとバッジ算出はメモリ上の24件を1回分類するO(24)処理とし、renderごとに多重フィルタを繰り返さない。
- 初期状態では今すぐ層の表示中2ウィジェットだけを通常mountし、整理層の22ウィジェットは開かれるまでmountしない。
- 初回open後は再openによる再mount・再取得を避ける。
- レイアウトシフトを抑えるため、設定確定前に旧フラットグリッドを一瞬描画しない。

## 9. テスト方針

### 9.1 フロントエンドunit/component

- 静的分類マップが24キーを重複・欠落なく網羅すること。
- 各カテゴリの既定順、元モック14項目、補完7項目をスナップショットではなく配列比較で固定すること。
- 0/1/2/3件のプレビュー、0を含むバッジ、非表示除外を境界値テストすること。
- 初期全閉、複数open、個別close、再open時の子インスタンス保持を検証すること。
- 子のmount回数とfetch mock呼出回数によりlazy first mountと再open非再取得を検証すること。
- GETの空配列・reject、PUT reject、null/重複/負数sortOrderを検証すること。
- native button、ARIA参照整合、キーボード、閉領域の非到達性を検証すること。
- 360px・390px相当viewportで1列、overflowなし、親スワイプ透過を検証すること。

### 9.2 バックエンド

- 追加する3 enumを含む24キーについて、PERSONALのGET/PUT/DELETE既存契約を検証すること。
- 24件全量PUTが原子的で、無効キーを1件混ぜた場合に0件も更新されないこと。
- 未認証401と本人スコープ固定を既存SecurityFilterChain経路で検証すること。
- 新規フォルダRepository、Service、Controller、DDLを作らない。旧案E由来の成果物が残っていないことを検索で確認すること。

### 9.3 E2E

- 既存設定を持つユーザーで、表示/非表示とカテゴリ内順序が改修前後で保持されること。
- 5カテゴリを任意に複数openし、再読込で全閉へ戻ること。
- 全非表示から設定画面で1件を戻し、対応カテゴリのプレビュー・バッジ・内容へ即時反映されること。
- 360pxおよび390pxの実ブラウザで、縦スクロール、横スワイプ、キーボード操作を確認すること。
