## 1. 概要・背景

### 1.1 課題 — 予定について「話す場所」がない

【確認済み】現在、共有スケジュール（`schedules`）に紐づけて会話できる場所は存在しない。

| 現状の選択肢 | 何が起きるか |
|---|---|
| 出欠コメント（`schedule_attendances.comment`） | 1人1件・500文字・返信不可。「持ち物は？」に誰も答えられない。ADMIN の出欠一覧を開かないと読めない |
| チャット（F04.2）のチームチャンネル | 予定と紐づかない。他の話題に流れて、当日に遡って探せない |
| 掲示板（F04.x） | 予定と紐づかない。単発の予定に対して重すぎる |

結果として、**予定に関する Q&A・連絡調整がアプリ外（LINE 等）へ流出**している。

### 1.2 TimeTree 比較 — 採用の根拠【御裁可済】

競合の **TimeTree** は、共有カレンダーの各予定に**予定単位のコメント欄**を標準装備しており、これが同アプリの中核的な差別化要素になっている（「予定を立てる」だけでなく「予定について話す」までを1画面に閉じる）。Mannschaft は予定管理・出欠管理では上回るが、**この「予定に紐づく会話」だけが欠けている**。

比較の結果、マスターが**採用を決定**した【御裁可済】。

| 軸 | TimeTree | Mannschaft 現状 | 本書適用後 |
|---|---|---|---|
| 予定単位のコメント | ✅ 標準装備 | ❌ 無し | ✅ `schedule_comments` |
| 返信スレッド | △（フラット） | ❌ | ✅ 1段返信（§3.3） |
| メンション通知 | ✅ | ❌ | ✅（F04.3/F04.11・§6） |
| 出欠との一体運用 | △（出欠は簡易） | ✅ 強い | ✅ 両立（§0.1 で棲み分け） |
| 可視性の細粒度制御 | ❌（カレンダー単位） | ✅ 強い（F00） | ✅ 親の可視性を継承（§4.5） |

### 1.3 御裁可済み方針【御裁可済・変更禁止】

以下はマスター決定済みであり、本書はこれを前提に設計する。設計中に矛盾が生じても**この決定を動かさない**。

1. **専用テーブル `schedule_comments` を新設する**。**チャット基盤（`chat_messages`/`chat_channels`）の流用はしない**。ただし返信ツリー構造（`parent_id`/`root_id`/`depth`）のカラム設計は【確認済み】`ChatMessageEntity`（`backend/src/main/java/com/mannschaft/app/chat/entity/ChatMessageEntity.java`）を踏襲する。
2. **対象は共有 `schedules` のみ**。個人予定（F03.2・`schedules.user_id IS NOT NULL`）は**対象外**（閲覧者が本人しかいないためコメント需要がない）。イベント（F03.8）は `events.schedule_id` 経由で載るが、**この列は NULL 許容である**ため無条件ではない（§1.5）。

   なお **F03.17（キープ／日付未定予定）でキープから変換されて生まれた予定にもコメントは付く**。変換後は通常の `schedules` レコードになるため、本書の設計がそのまま適用され、F03.17 側・本書側とも追加実装は不要。
3. **可視性は親スケジュールの可視性を継承する**。先例は【確認済み】`CirculationCommentVisibilityResolver`（回覧コメント）。F00 `ContentVisibilityResolver` 準拠で**参照時に判定**する（コメント自身は visibility 列を持たない）。ただし**「親の可視性」は `canView` だけでは不足**であり、`min_view_role` を併せた「予定実効閲覧述語」を用いる（§4.5・重大な設計上の要点）。
4. **既存の出欠コメント（`schedule_attendances.comment` / `comment_option`）とは別物**として併存させる（§0.1）。
5. **メンションは通知（F04.3 プッシュ通知基盤）へ連携する**。

### 1.5 【訂正】イベント（F03.8）は「1:1 で自動的に載る」わけではない

> ⚠️ 初版は「イベントは `events.schedule_id` で `schedules` に 1:1 紐づくため自動的に本機能が載る」と書いていたが、**これは誤りである**。

【確認済み】`V3.100__create_events_table.sql` の実 DDL:

```sql
schedule_id  BIGINT UNSIGNED,                                   -- ← NOT NULL ではない（NULL 許容）
UNIQUE KEY uq_events_schedule (schedule_id),
FOREIGN KEY (schedule_id) REFERENCES schedules (id) ON DELETE RESTRICT,
```

- `schedule_id` は **NULL 許容**。したがって関係は **1:1 ではなく「0 または 1 : 1」**（`UNIQUE` 制約は NULL 行を対象外にするため、`schedule_id IS NULL` のイベントは何件でも存在できる）。
- **`schedule_id` が NULL のイベントには親スケジュールが存在しないため、コメントスレッドは成立しない**。

**確定方針**【提案】:

| イベントの状態 | コメントスレッド |
|---|---|
| `events.schedule_id` が**非 NULL** | 親スケジュールのスレッドがそのまま載る。イベント側の追加実装は不要 |
| `events.schedule_id` が **NULL** | **コメント欄を表示しない**。FE は `scheduleId` が null ならコメントセクション自体を `v-if` でレンダリングしない（「コメントできません」のエラー表示すら出さない＝存在しない機能として扱う） |

**FE へ `scheduleId` を通すための実装**【提案・Wave 3 の作業項目】:

> ⚠️ 【確認済み】現状、**カレンダー API の応答にも FE のイベント型にも `scheduleId` は無い**。`CalendarEntryResponse`（`schedule/dto/`）は `id` / `content(title, eventType, status, referenceUuid, referenceKind)` / `time` / `scope` / `myAttendanceStatus` を持ち、`FE` 側の `CalendarEventItem`・`CalEvent`・`CalendarMonthView.events` にも `scheduleId` フィールドは存在しない。**このままでは FE がコメント API を呼ぶ ID を持てない。**

1. **BE**: `CalendarEntryResponse` に **`scheduleId: Long`（null 許容）** を追加する。schedule 由来の行は予定 ID を入れ、**それ以外の行（活動記録などの reflection 行）は `null`**。
2. **FE 型**: `CalendarEventItem`（`composables/useCalendarEvents`）と `calendar.vue` のローカル型 `EventDetail` に **`scheduleId: number | null`** を追加する。
3. **`EventDetailPanel`**: `defineProps` の `event` インライン型に **`scheduleId: number | null`** を追加し、`calendar.vue` が組み立てる `:event` オブジェクトリテラルに `scheduleId` を含めて渡す。
4. **描画ガード**: コメントセクションは **`v-if="event.scheduleId !== null"`** で囲む。

> **なぜ `event.id` を流用しないのか**: 【確認済み】`EventDetailPanel` は現状 `event.id` を予定 ID として子に渡している（`:schedule-id="event.id"`）が、`CalendarEntryResponse.id` は **reflection 行では `null`**（識別子は `content.referenceUuid` / `referenceKind`）。**「id が常に予定 ID」という前提は成り立たない**ため、コメント機能は専用の `scheduleId` フィールドを見る。既存の流用箇所の是正は本書のスコープ外（別途起票）。

- BE 側に「イベント ID からコメントを引く」API は**作らない**。コメント API のパスは常に `{scheduleId}` を取るため、`schedule_id` が NULL のイベントからは**そもそも呼びようがない**（構造的に安全）。
- **AC-07 で両ケースを検証する**（非 NULL は表示・NULL は非表示）。

### 1.6 【裁定変更】主キーは UUIDv7（`UuidV7Entity` 継承）

> ⚠️ **初版の「`UuidV7Entity` は存在しないので使わない・`BaseEntity`/BIGINT を採る」は誤りである。** 偵察時の事実誤認であり、**マスターの裁定により UUIDv7 へ変更する**【御裁可済】。

**訂正の根拠**【確認済み】:

1. **`UuidV7Entity` は実在する** — `backend/src/main/java/com/mannschaft/app/common/entity/UuidV7Entity.java`。`@MappedSuperclass` ＋ `@Id @GeneratedValue @UuidGenerator(style = TIME)` の `UUID id`。Javadoc に「新規テーブル作成時に適用」「DDL の id 列は `CHAR(36)` または `BINARY(16)` を推奨」と明記されている。
2. **ArchUnit 番人が新規 `@Entity` に継承を強制している** — `EntityUuidV7ConventionArchTest`（`backend/src/test/java/com/mannschaft/app/common/architecture/`）が `classes().that().areAnnotatedWith(Entity.class).should().beAssignableTo(UuidV7Entity.class)` を **FreezingArchRule** で課している。凍結ストア（`backend/src/test/resources/archunit_store/`）は既存違反を登録済みだが、**ストアに無い新規違反は fail する**。
3. **凍結ストアは緩めてはならない** — 同テストの Javadoc に「本エントリは『違反隠蔽』ではなく『設計是認例外の正規登録』であり、**他 Entity へ緩めてはならない**（新規 Entity は原則どおり `UuidV7Entity` を継承すること）」と明記。【確認済み】`archunit.properties` は `freeze.refreeze=false`（自動再凍結を禁止）。
4. よって **`BaseEntity` のまま実装すると Wave 1 の初日に ArchUnit が赤で止まる**。凍結ストアへの追記で通すことは上記3により禁止されている。CLAUDE.md 原則6 のとおり **UUIDv7 が正しい**。

**採用する ID 体系**【御裁可済】:

| 列 | 型 | 理由 |
|---|---|---|
| `id`（主キー） | **`BINARY(16)`** / Java は `UUID`（`UuidV7Entity` から継承） | 原則6・ArchUnit 番人 |
| `parent_id` / `root_id`（**自表参照**） | **`BINARY(16)`** / Java は `UUID` | 同一テーブルの `id` を指すので当然 UUID |
| `schedule_id`（**`schedules` への参照**） | **`BIGINT UNSIGNED`** / Java は `Long` | **外部参照列の型は参照先（親）に合わせる**。`schedules.id` が BIGINT である以上ここは BIGINT。**親子で ID 体系が違っても問題ない** |
| `user_id`（`users` への参照） | **`BIGINT UNSIGNED`** / Java は `Long` | 同上 |

- **前例**【確認済み】: `V173.20260730033806__create_notification_fanout_jobs.sql` — `id BINARY(16) NOT NULL COMMENT 'UUIDv7 主キー'` を持ちつつ、他ドメイン参照は `organization_id BIGINT NULL` / `source_id BIGINT NULL` / `actor_id BIGINT NULL`。対応する `NotificationFanoutJob` は `extends UuidV7Entity` ＋ `@SuperBuilder(toBuilder = true)` で、**BIGINT 参照は `Long` のまま**・UUID 参照は `UUID` に `columnDefinition = "BINARY(16)"` を明示。本書はこの構成をそのまま踏襲する。
- **自己参照 FK の前例**【確認済み】: `V69.001__create_village_categories.sql` — `id BINARY(16)` / `parent_id BINARY(16) NULL` ＋ `FOREIGN KEY (parent_id) REFERENCES village_categories(id)`。冒頭コメントに「自己参照 FK は同一ドメイン内のため許可（原則2）」。**DDL の形はこれに倣う。**

**UUID フィールドのマッピングは明示指定で確定する**【御裁可済】:

```java
@Column(name = "parent_id", columnDefinition = "BINARY(16)")
@JdbcTypeCode(SqlTypes.BINARY)
private UUID parentId;
```

- **`VillageCategoryEntity` 方式（`@Column(name=...)` のみで `columnDefinition` も `@JdbcTypeCode` も付けない）は採らない**【裁定】。Hibernate 6 は `UUID` を既定で `BINARY`/`UUID` いずれにも解決しうるため、**方言・設定・テストプロファイル（`ddl-auto=create`）ごとに列型が揺れる**。実 DDL は `BINARY(16)`、テストの自動生成スキーマは別型、という不一致は「本番だけ落ちる」類の事故になる（memory `feedback_test_schema_column_type_differs_from_prod_ddl` と同じ構図）。
- **`id`（`UuidV7Entity` から継承）にはこの指定を書けない**ため、DDL 側で `BINARY(16)` を明示し、必要なら `application.yml` / 方言設定で UUID の既定 JDBC 型が `BINARY` になっていることを Wave 1 で実測確認する（`NotificationFanoutJob` が実運用で `BINARY(16)` に収まっている事実が根拠になる）。
- **`@SuperBuilder(toBuilder = true)` が必須**（`UuidV7Entity` が `@SuperBuilder` のため、サブクラスも付けないとビルダーが繋がらない）。`@EqualsAndHashCode` は基底の ID ベース実装を継承する。

**API・ソート契約への影響**（§4・§10）:

- **API の `id` / `parentId` / `rootId` は UUID 文字列**（`"018f2c...-..."`）になる。`scheduleId` は**数値のまま**。§4 の JSON 例・型表は本裁定に合わせて更新済み。
- **ソート・カーソルは `created_at` を基準とする**【確定】。UUIDv7 は時刻順に単調増加するため `id` 順でも実用上は時系列になるが、**ソート契約を `id` に依存させない**（生成タイミングと `created_at` の微小なズレ、将来の ID 方式変更、同一ミリ秒内の順序保証の無さが契約を壊す）。同順位の tie-break にのみ `id` を用いる（§4.3）。

## 2. スコープ

### 2.1 対象ロール

コメントの**閲覧可否は親スケジュールの可視性判定に完全に一致する**（§4.5）。以下は「親スケジュールを閲覧できる」ことを前提とした、コメント固有の操作権限である。

| ロール | 操作可能な範囲 |
|---|---|
| SYSTEM_ADMIN | 全コメントの参照・強制削除（モデレーション）。スレッド開閉の強制変更 |
| ADMIN | 親スケジュールを閲覧できる場合: 投稿・返信・**自分のコメントの編集**・**任意のコメントの削除**（モデレーション）・**スレッド開閉（`comments_enabled`）の変更** |
| DEPUTY_ADMIN | 投稿・返信・自分のコメントの編集/削除。他者コメントの削除は `DELETE_OTHERS_CONTENT` 権限が必要。**スレッド開閉は不可**（予定作成者である場合を除く） |
| MEMBER | 投稿・返信・**自分のコメントのみ**編集/削除。他者コメントの削除は `DELETE_OTHERS_CONTENT` 権限が必要。**スレッド開閉は不可**（予定作成者である場合を除く） |
| SUPPORTER | 親スケジュールを閲覧できる場合（`min_view_role IN (ANYONE, SUPPORTER_PLUS)`）: **投稿・返信・自分のコメントの編集/削除が可能**【既定】 |
| GUEST（**＝未ログインの閲覧者**） | `min_view_role = ANYONE` の予定に限り **`GET` 一覧のみ認証不要で閲覧できる**。**投稿・返信・編集・削除は不可**（未認証なら 401、認証済みで権限不足なら 403 `SCHEDULE_COMMENT_004`） |

> **【定義の確定】本書の「GUEST」は未ログインの閲覧者を指す**。初版は「GUEST は認証済みの最低ロール」と「未ログインは 401」の2つの記述が混在し矛盾していた。本書では次で統一する:
>
> - **GUEST = 未ログイン**。`min_view_role = ANYONE` の予定の **`GET` 一覧のみ**が認証不要（§4.1 の認証列）。
> - **それ以外の全エンドポイント（`meta`・`replies`・`mention-candidates`・POST・PATCH・DELETE・settings）は認証必須**。未ログインで叩けば **401**。
> - 認証済みだが投稿要件（§4.4 の `postableRole`）を満たさないユーザーは **403 `SCHEDULE_COMMENT_004`**。
> - **401 と 403 を混同しない**: 「誰か分からない」が 401、「誰か分かるが許可されない」が 403。

**書き込み権限を `min_response_role` に結びつけない理由**【既定】: `min_response_role` は**出欠回答**の最小ロールであり、「出欠は答えなくてよいが質問はしたい」保護者・応援者を締め出してしまう。コメントは会話であって回答ではないため、**「読める人は書ける（GUEST を除く）」**を既定とする。より厳しく閉じたい予定は §3.2 の `comments_enabled = FALSE` でスレッドごと閉じる。

#### 2.1.1 【訂正】スレッド開閉の権限に `MANAGE_SCHEDULES` を使わない

> ⚠️ 初版は「スレッド開閉には `MANAGE_SCHEDULES` が必要」としていたが、**これでは事実上ほぼ全員が開閉できてしまう**ため不採用とする。

【確認済み】`V2.016__seed_role_permissions.sql:17-22` は **MEMBER × `MANAGE_SCHEDULES` を `is_default = 1`（既定付与）** で seed している（F03.1 §2 の「MEMBER はデフォルトで `MANAGE_SCHEDULES` 権限を持つ」という記述と一致）。したがって `MANAGE_SCHEDULES` を条件にすると **一般 MEMBER が誰の予定のスレッドでも閉じられる**。荒れた議論を当事者が一方的に封じる運用事故につながる。

**確定方針**【御裁可済】: **スレッド開閉は次の3者に限定する。**

1. `SYSTEM_ADMIN`
2. 当該スコープの `ADMIN`
3. **予定の作成者**（`schedules.created_by = 操作者の userId`）

- `MANAGE_SCHEDULES` も `DELETE_OTHERS_CONTENT` も条件に使わない。判定は「ロール ＋ 作成者一致」のみで、権限テーブルを引かない（§4.4）。
- 【確認済み】`created_by` は `ScheduleVisibilityProjection.createdBy` として既に射影されており、追加クエリなしで判定できる。
- §4.4 の `PATCH .../comments/settings` もこの規則で統一する（初版は §2.1 と §4.4 で条件が食い違っていた。本項で一本化）。

#### 2.1.2 権限の scope は TEAM のみ — 組織予定でのフォールバック規則

【確認済み】`V2.015__seed_permissions.sql` で **`MANAGE_SCHEDULES`・`DELETE_OTHERS_CONTENT` はいずれも `scope = 'TEAM'` としてのみ seed されている**（`ORGANIZATION` スコープの行が存在しない）。【確認済み】権限判定は `RoleService#hasPermission(userId, scopeId, scopeType, permissionName)` で `scopeType` を取るため、**組織スケジュール（`schedules.organization_id IS NOT NULL`）に対して `scopeType = "ORGANIZATION"` で `DELETE_OTHERS_CONTENT` を問い合わせても常に false になる**。

**確定する解決規則**【提案】: 他者コメントの削除可否は、親スケジュールのスコープに応じて次のように判定する。

| 親スケジュールのスコープ | 他者コメント削除の判定 |
|---|---|
| **TEAM**（`team_id IS NOT NULL`） | `RoleService#hasPermission(userId, teamId, "TEAM", "DELETE_OTHERS_CONTENT")` |
| **ORGANIZATION**（`organization_id IS NOT NULL`） | **権限テーブルを引かず、組織 ADMIN（`resolveEffectiveRoleName` が `ADMIN`）であることを条件とする**（TEAM スコープ権限へのフォールバックはしない） |

- **なぜ「組織 ADMIN へフォールバック」なのか**: `DELETE_OTHERS_CONTENT` に ORGANIZATION 行が存在しない以上、組織予定で権限ベース判定を試みると**必ず false ＝ 組織予定のコメントを誰もモデレートできない**という詰みになる。かといって権限テーブルに ORGANIZATION 行を足すのは本書のスコープ（コメント機能）を超える権限モデルの変更なので採らない。**組織 ADMIN であればモデレートできる**という単純な規則で埋める。
- 判定は必ず**単一のヘルパ**（§4.5 の `ScheduleCommentPermissionEvaluator` 相当）に集約し、Controller/Service の各所で条件を書き分けない（分岐が散ると片方だけ直る事故になる）。

**制約・備考**

- `parent_id IS NULL` ⇔ `root_id IS NULL` ⇔ `depth = 0`（トップレベル）。`parent_id IS NOT NULL` ⇔ `root_id IS NOT NULL` ⇔ `depth = 1`。**アプリ層で必ず検証**する（不整合は 400 `SCHEDULE_COMMENT_006`）。
- 返信の `schedule_id` は**親コメントの `schedule_id` と一致しなければならない**（他予定のコメントへの返信を作らせない＝IDOR 経路の遮断・§4.5）。不一致は 400 `SCHEDULE_COMMENT_006`。
- `reply_count` は**トップレベル行のみ**が意味を持つ（返信行は常に 0）。返信の作成/削除時に根の行を増減する。**減算は 0 を下限とするガードを必ず入れる**（【確認済み】`ChatMessageEntity.decrementReplyCount()` が `if (this.replyCount > 0)` で同じガードを持つ。二重削除・再試行でカウンタが負に落ちると「生存返信 > 0」判定〔§5.3〕が壊れ、トゥームストーン表示が破綻する）。
- **`reply_count` は「生存返信数」を表す**（削除済み返信を含まない）。返信を論理削除したら親の `reply_count` をデクリメントする。この定義は §5.3 のトゥームストーン判定と一体であり、**片方だけ変更してはならない**。
- **CASCADE の適用範囲**（CLAUDE.md 原則2「CASCADE DELETE は同一ドメイン内のみ」）:
  - `schedule_id` → `schedules`: **同一 schedule ドメイン内**なので `ON DELETE CASCADE` 可。ただし `schedules` は論理削除（`deleted_at`）が主で物理削除は稀。
  - `parent_id` → 自己参照: 同一テーブル内なので `ON DELETE CASCADE` 可（親コメントの物理削除で返信も消える）。**通常運用は論理削除**なので発火しない（§5.3）。
  - `user_id` → `users`: **クロスドメインのため FK を張らない**（原則1）。整合はアプリ層＋退会匿名化（§10.4）で保証する。
- **FK の非対称について**【実装者向けの一言】: 同じテーブルに「FK を張る列（`schedule_id`・`parent_id`）」と「張らない列（`user_id`）」が同居する。これは書き忘れではなく**原則1（クロスドメイン FK 禁止）の意図的な適用**である。DDL レビュー時に「`user_id` にも FK を付けよう」と直さないこと（付けると users のシャード分離・退会物理削除の際に `schedule_comments` が巻き添えで壊れる）。
  - ⚠️ **親 `schedules` には `fk_sch_created_by`（`created_by` → `users`）が実在する**が、これは原則1 が定まる前の既存資産である。**本表は新方針に従い `user_id` に FK を張らない**（既存に倣わない）。「親が張っているのだから子も張るべき」という指摘に対する回答をここに置く。

**GDPR / 個人データ注釈**【提案】:

- エンティティに **`@PersonalData(category = "scheduleComments")`** を付与する（【確認済み】`ChatMessageEntity:25` の `@PersonalData(category = "chatMessages")` に倣う）。
- **あわせて `PersonalDataCollector` 側へ収集処理を実装する**。【確認済み】`PersonalDataCoverageValidator` はクラスパスを走査して annotation の `category()` を集め、`PersonalDataCollector#getCategoryKeys()` に無ければ **ERROR ログを出す（起動は止まらない）**。つまり**注釈だけ付けて収集を実装しないと、静かにエクスポート漏れになる**。
- ⚠️ **既存の命名不整合に巻き込まれないこと**: 【確認済み】`ChatMessageEntity` の注釈は `"chatMessages"`（キャメル）だが、`PersonalDataCollector.CATEGORY_FILES` のキーは `"chat_messages"`（スネーク）で、`collectChatMessages` は `log.warn("リポジトリ未実装...")` して `"[]"` を返す**スタブ**である。**本書は同じ轍を踏まない** — 注釈の `category` と `PersonalDataCollector` の登録キー・`switch` の case を**必ず同一文字列で揃え**、実際に本文を返す収集処理を実装する。既存の chat 側の不整合の是正は本書のスコープ外（別途起票）。
- エクスポート内容: 自分が投稿したコメントの `id` / `scheduleId` / `body` / `createdAt` / `updatedAt` / `isEdited`（**削除済みも含める** — 本人のデータなので）。**AC-35 で検証する**。
- **【裁定】`@SQLRestriction("deleted_at IS NULL")` は付けない**【御裁可済】。`deleted_at IS NULL` を**各クエリの明示条件として書く**方式を採る。

  **理由**: 本機能は**トゥームストーン（削除済みだが表示する行）が一覧の本流**である（§5.3）。`@SQLRestriction` はエンティティに対する全クエリへ問答無用で `deleted_at IS NULL` を差し込むため、「一覧に削除済みトップレベルを含めたい」という主要ユースケースが**注釈と正面衝突**する。回避するには native クエリで注釈を迂回することになり、**「主要な読み取り経路だけが注釈を裏切る」**という最も危険な構成になる（実装者が注釈を見て『削除済みは来ない』と誤解する）。
  先例の `CirculationCommentEntity` は `@SQLRestriction` を付けているが、**あちらは返信ツリーもトゥームストーンも持たない**ため同じ問題が起きない。金型をここだけ意図的に外す。

  **原則3（論理削除）との整合**: 原則3 が要求するのは「物理削除せず `deleted_at` で消す」ことであって、「`@SQLRestriction` を使うこと」ではない。本書は `deleted_at` 列を持ち物理削除しないため**原則3 を満たしている**。除外条件の実装手段が注釈か明示条件かは原則の範囲外である。

  **代わりに守る規律**:
  - リポジトリの**全メソッドが `deleted_at` を明示的に扱う**こと（`AND c.deletedAt IS NULL` を書くか、意図的に含めるかを必ずどちらか明示）。「条件を書き忘れたら削除済みが漏れる」ため、**リポジトリのテストで削除済み行を1件混ぜて各メソッドの挙動を固定する**（AC-34）。
  - API 応答へ削除済みを載せるのは §5.3 の条件を満たすトゥームストーンのみ。それ以外の経路（検索・エクスポート・通知）は必ず `deleted_at IS NULL` で絞る。

#### 3.3.1 深さの上限は 1（2階層）【既定・PR レビューで変更可】

- **トップレベル（depth=0）とその返信（depth=1）の2階層のみ**。`depth = 1` のコメントへの返信要求は **400 `SCHEDULE_COMMENT_007`** で拒否し、**返信先を自動的に根へ付け替える暗黙処理はしない**（ユーザーが意図した相手と表示上の親がずれる事故を防ぐ＝症状を隠さない）。
- **カラムは 3 本とも先に持つ**（`parent_id`/`root_id`/`depth`）。将来 2 段以上へ広げるときに**マイグレーション不要**で上限値の定数だけ変えれば済む（`ChatMessageEntity` が既に同じ形を持っており、実装者が読み替えやすい）。
- FE は「返信」ボタンを depth=1 のコメントには出さない（BE 400 は防御の二層目）。

### 3.4 ER 図（テキスト形式）

```
schedules (1) ──── (N) schedule_comments        [FK: schedule_id, ON DELETE CASCADE, 同一ドメイン]
schedule_comments (1) ──── (N) schedule_comments [FK: parent_id (自己参照), ON DELETE CASCADE]
schedule_comments (N) ──── (1) users             [ID参照のみ・FKなし（原則1・クロスドメイン）]

events (0..1) ──── (1) schedules                  [既存: events.schedule_id は NULL 許容 + UNIQUE, ON DELETE RESTRICT]
   ├─ schedule_id 非 NULL → 親 schedules のコメントスレッドがそのまま載る
   └─ schedule_id が NULL → 親スケジュール不在。コメント欄は表示しない（§1.5・AC-07(b)）

schedule_attendances (N) ──── (1) schedules      [既存: 出欠コメント（別物・§0.1）]
```

> **`events` の多重度に注意**: `UNIQUE KEY uq_events_schedule (schedule_id)` は NULL 行を制約対象外にするため、**`schedule_id IS NULL` のイベントは何件でも存在できる**。「1 対 1」ではなく「0 または 1 対 1」であり、コメント機能から見ると**親を持たないイベントが常に存在しうる**前提で設計する。

#### 3.6.1 ロールバック方針

Flyway Community 版は `undo` を持たないため、**巻き戻しは「打ち消しマイグレーションを前方に足す」方式**とする（`flyway repair` で誤魔化さない＝根治治療の原則）。

| 対象 | 前方打ち消し SQL | 注意 |
|---|---|---|
| `schedule_comments` の新設 | `DROP TABLE IF EXISTS schedule_comments;` | **新規テーブルなので既存データを一切失わない**（安全）。ただし投稿済みコメントは消える |
| `schedules.comments_enabled` の追加 | `ALTER TABLE schedules DROP COLUMN comments_enabled;` | 追加列のみの削除。既存列・既存行に影響なし（Expand の逆＝Contract） |

- **本番環境で一度でもコメントが投稿された後の `DROP TABLE` は UGC の消失**にあたるため、実行前に必ずマスターの承認を取ること（CLAUDE.md 自動実行ポリシーの例外「本番環境への変更」）。
- ステージング／ローカルでの巻き戻しは上記2文で完結する（`schedules` 本体・`schedule_attendances` には触らないので、出欠機能への波及はゼロ）。

### 4.1 エンドポイント一覧

すべて `CirculationCommentController` の作法（`/api/v1/{親リソース}/{親ID}/comments`・`PagedResponse` / `ApiResponse` エンベロープ）に揃える。

| メソッド | パス | 認証 | 説明 |
|---|---|---|---|
| GET | `/api/v1/schedules/{scheduleId}/comments` | **GET 一覧のみ任意**（下記） | コメント一覧（トップレベル＋返信の階層構造） |
| GET | `/api/v1/schedules/{scheduleId}/comments/meta` | 必要 | **スレッド状態**（`commentsEnabled` / `canPost` / `canPostReason`） |
| GET | `/api/v1/schedules/{scheduleId}/comments/{commentId}/replies` | 必要 | 指定トップレベルコメントの**全返信**（一覧の同梱3件で足りない場合） |
| GET | `/api/v1/schedules/{scheduleId}/comments/mention-candidates` | 必要 | **メンション候補ユーザー一覧**（可視性フィルタ済み） |
| POST | `/api/v1/schedules/{scheduleId}/comments` | 必要 | コメント投稿／返信 |
| PATCH | `/api/v1/schedules/{scheduleId}/comments/{commentId}` | 必要 | 本文編集（自分のコメントのみ） |
| DELETE | `/api/v1/schedules/{scheduleId}/comments/{commentId}` | 必要 | 論理削除 |
| PATCH | `/api/v1/schedules/{scheduleId}/comments/settings` | 必要 | スレッド開閉（`commentsEnabled`）の変更 |

> **認証列の但し書き**（§2.1 の GUEST 定義と整合）: **`min_view_role = ANYONE` の予定に限り、`GET` 一覧のみ認証不要**（未ログインでも読める）。それ以外の予定では 401。**書き込み系（POST/PATCH/DELETE）と `meta`・`replies`・`mention-candidates` は常に認証必須**。

> **`meta` を別エンドポイントにした理由**【訂正】: 初版はスレッド状態を一覧応答の `meta` に載せていたが、【確認済み】`PagedResponse.PageMeta` は `total`/`page`/`size`/`totalPages` の**4フィールド固定のクラス**で、任意フィールドを足せない（`PagedResponse` を継承・改造すると全 API に波及する）。**スレッド状態は専用の 8 本目のエンドポイントで返す**。FE は予定詳細を開いたときに一覧と `meta` を並行取得する（1往復増えるが、既存の共通エンベロープを壊さない方が安全）。

> **`mention-candidates` を設ける理由**: FE がメンション候補を出すために既存の「チームメンバー一覧 API」を流用すると、**その予定を閲覧できないメンバーまで候補に並ぶ**（＝名簿の漏洩、かつ選んでも §6.3 で黙って除外されるので「送ったのに届かない」体験になる）。**予定ごとの専用エンドポイントで、§4.5 の「予定実効閲覧述語」を通したユーザーだけを返す**。契約は §4.4 を参照。

> **`{scheduleId}` を必ずパスに含める理由**: `commentId` だけで操作させると、他予定のコメント ID を渡す IDOR 経路が生まれる。**すべての操作で「`commentId` が `scheduleId` に属すること」を検証**し、属さなければ **404**（403 ではなく 404＝他予定のコメントの存在を漏らさない）。

### 4.3 `GET /api/v1/schedules/{scheduleId}/comments`

**クエリパラメータ**

| パラメータ | 型 | 任意 | 既定 | 説明 |
|---|---|---|---|---|
| `page` | integer | ✅ | 0 | ページ番号（**0 始まり**・`CirculationCommentController` の `PagedResponse` 作法に合わせる） |
| `size` | integer | ✅ | 20 | 1ページ件数（最大 50。超過は 50 にクランプ） |
| `sort` | string | ✅ | `createdAt,asc` | `createdAt,asc`（会話は古い順）／`createdAt,desc` のみ許可 |

- **ページングの単位は「トップレベルコメント」**。各トップレベルに紐づく返信は、**1件あたり最新 3 件までを同梱**し、残りは `replyCount` との差分で FE が「他 N 件の返信を表示」を出す（全返信の取得は §4.4）。
- **全件返しは禁止**（`size` 上限 50・§10.1）。
- **ページング・`meta.total` にもトゥームストーン述語を適用する**【確定】: 一覧が返す「トップレベル」の集合は §5.3 の表示述語（`deleted_at IS NULL OR reply_count > 0`）を通したものであり、**`meta.total`・`meta.totalPages` もこの述語適用後の件数で計算する**。
  - **削除済みで生存返信 0 のトップレベルを件数に数えない**（数えると「20件と言われたのに19件しか表示されない」空席が生まれる）。
  - **トゥームストーンは件数に数える**（画面に1枚のカードとして出るため）。
  - 実装上は `WHERE schedule_id = ? AND (deleted_at IS NULL OR reply_count > 0)` を**一覧クエリと件数クエリの両方に同一条件で**書く。**片方だけに書くと件数と中身がずれる**（§3.3 で `@SQLRestriction` を使わない方針にした以上、この二重記述は明示的に管理する）。境界は **AC-26b** で検証する。
- **並びの tie-break**: 既定ソートは `created_at`。**同一 `created_at` の同着は `id` 昇順で解消する**（UUIDv7 は時刻順のため実質的な作成順になる）。`ORDER BY` に一意列を含めないとページ間で行が重複・欠落するため必須（§1.6 の「ソート契約は `created_at` 基準」と整合）。
- **`sort` は「トップレベルの並び順」だけを変える。同梱返信の規則は `sort` に依存しない**【確定】: 同梱するのは常に **`createdAt` 昇順で最も新しい 3 件**（＝末尾3件）を取り、**配列内は `createdAt` 昇順で並べる**。`sort=createdAt,desc` を指定してもこの規則は変わらない。
  - **なぜ固定するか**: 「新しい順」を返信にも波及させると、会話の途中3件が逆順で並び**文意が読めなくなる**。トップレベルの並び（どの話題を先に見せるか）と、返信の並び（会話の流れ）は別の軸である。
  - 同梱するのが「最新3件」なのは、続きの会話が見えた方が文脈を追いやすいため（古い3件だと会話が止まって見える）。

##### `canPost` の定義（肯定形で確定）

初版は「GUEST は `false`」という否定形の例示しか無く、**GUEST 以外の誰が投稿できるのかが未定義**だった。次のとおり肯定形で確定する。

```
canPost := writable(schedule)                        -- §5.2 の述語（comments_enabled AND status != CANCELLED）
           AND canEffectivelyView(schedule, viewer)  -- §4.5.0 の述語（ここまでは一覧が返っている時点で真）
           AND postableRole(viewer)

postableRole(viewer) :=
       role != null
   AND ( RolePriority.isAtLeast(role, "MEMBER")                       -- MEMBER 以上は常に投稿可
         OR ( role == "SUPPORTER"
              AND schedule.min_view_role IN (ANYONE, SUPPORTER_PLUS) ) )  -- SUPPORTER は閲覧できる予定にのみ投稿可
```

- **`role == null` は投稿不可**【明文化】。ロール解決に失敗した／スコープに所属していないユーザーは `false`（fail-closed。null を「制限なし」と解釈しない）。
- **GUEST は `postableRole` を満たさない**ため `false`（`RolePriority` 上 MEMBER 未満であり、SUPPORTER でもない）。結果は初版の記述と一致するが、**根拠が「GUEST を名指しで弾く」から「投稿可能な条件を満たさない」に変わった**。将来ロールが増えても既定で投稿不可になる（deny-by-default）。
- `SUPPORTER` に条件が付くのは §2.1 の「読める人は書ける」を素直に実装した結果である（`min_view_role = MEMBER_PLUS` の予定は SUPPORTER には見えないので、そもそもこの分岐に到達しない。冗長だが**述語単体でも安全**であるよう明示的に書く）。

##### `canPostReason` の判定順序

`canPost = false` のとき、**次の順序で最初に該当したものを1つだけ返す**（複数該当時に FE が表示を迷わないよう順序を固定する）:

| 順 | 値 | 条件 | FE の表示（§8） |
|---|---|---|---|
| 1 | `CANCELLED` | `schedules.status == CANCELLED` | `schedule.comment.cancelled` |
| 2 | `CLOSED` | `comments_enabled == FALSE` | `schedule.comment.closed` |
| 3 | `ROLE` | `postableRole(viewer)` が false | GUEST は `schedule.comment.guestReadOnly` ＋ `guestSignInPrompt`、それ以外は `schedule.comment.error.forbidden` |

- **`CANCELLED` を `CLOSED` より先に判定する**理由: 両方に該当する場合、ユーザーにとって重要な情報は「予定が中止になった」ことであり、「スレッドが閉じている」は副次的。
- **`canPostReason` は表示用であり認可ではない**。BE は POST 時に §5.2 の述語と権限判定を**独立に**再評価する（`canPost` を信じて認可を省略しない・§4.2 の `canEdit`/`canDelete` と同じ二層防御）。

|---|---|---|---|---|

**レスポンス（200 OK）**: **`ApiResponse<List<...>>`**（`PagedResponse` ではない。§4.4 の「件数を漏らさない」方針によりページメタを返さないため）。

```json
{
  "data": [
    { "userId": 102, "displayName": "鈴木 花子", "avatarUrl": null }
  ]
}
```

**母集団と絞り込みの順序**【確定】:

| 順 | 処理 | 詳細 |
|---|---|---|
| 1 | **母集団の取得** | 親スケジュールのスコープに応じて分岐する。**TEAM**（`team_id IS NOT NULL`）→ `TeamMembershipRepository` から当該チームの有効メンバーの `user_id`。**ORGANIZATION**（`organization_id IS NOT NULL`）→ `OrganizationMembershipRepository` から当該組織の有効メンバー（配下チーム経由の所属を含む解決規則は既存の出欠配信母集団と同じものを使う）。**退会・BAN・無効化されたメンバーは含めない** |
| 2 | **`q` による絞り込み** | 表示名の部分一致（大文字小文字・全半角は既存の検索規約に従う）。`q` 未指定なら母集団のまま |
| 3 | **可視性フィルタ** | **§4.5.0 の `filterViewers`** を適用（`canView` ＋ `min_view_role`）。**必ずこの段階で行う** |
| 4 | **並び替え** | 下記の tie-break 規則 |
| 5 | **`size` で切る** | 既定 20・最大 50 |

> ⚠️ **順序が重要**: **可視性フィルタ（3）は `size` で切る（5）より前に行う。** 逆にすると「上位 50 件を取ってから可視性で除外」となり、**除外された分だけ候補が減って 50 件に満たなくなる**（見えるはずの人が候補に出てこない）。フィルタ後に切ることで、返る件数が常に「見える人の中の上位 N 件」になる。

**並びの tie-break（完全順序を規定）**:

1. **前方一致を優先**（`q` が表示名の先頭に一致するものを先に）
2. **表示名の昇順**（照合順序はテーブルの `utf8mb4_unicode_ci` に従う）
3. **`user_id` の昇順**（最終的な同着解消。**これにより順序が一意に定まる**）

- 3 段目まで規定するのは、**同名ユーザーがいると順序が不定になりページングとテストが揺れる**ため（`ORDER BY` に一意列を含めるのは一覧 API 共通の作法）。

**契約上の要点**:

- **返す集合は「この予定を §4.5 の述語で閲覧できるユーザー」に限定する**。上記の順序で母集団を絞り、**`canView` ＋ `min_view_role` の両方**を通したユーザーだけを返す。
- **`min_view_role` によるフィルタを省略しない**。省略すると `MEMBER_PLUS` の予定で SUPPORTER が候補に並び、§6.3 で通知は届かないという不整合になる（かつ SUPPORTER の名簿が MEMBER に漏れる）。
- **閲覧できないユーザーの存在を数でも漏らさない**（**`PagedResponse` を使わず `ApiResponse<List<...>>` で配列のみ返す**。`meta.total` を返すと件数から母集団を推測されるため）。
- 権限なし／個人予定は **404 `SCHEDULE_COMMENT_002`**。GUEST は投稿できないため **403 `SCHEDULE_COMMENT_004`**。
- レート制限は一覧 GET と同じ共通制限に従う（名簿の総当り取得を抑止）。

### 4.5 認可 — 親スケジュールの可視性を Resolver 経由で継承する【提案・必須】

> ⚠️ **コメント側で独自の可視性述語（`team_id` 突き合わせ等）を書いてはならない。** 独自述語は F00 の可視性ラダー（`ORGANIZATION` / `CUSTOM_TEMPLATE` / F01.7 テンプレート）と必ずずれ、漏洩源になる。**判定は必ず `ContentVisibilityChecker` 経由**で行う。

#### 4.5.0 【重大】`canView` だけでは `min_view_role` が効かない — 「予定実効閲覧述語」を定義する【御裁可済】

> ⚠️ **初版の「`canView(SCHEDULE, scheduleId, viewerUserId)` を呼べば親の可視性を継承できる」は誤りである。** そのまま実装すると **`min_view_role = MEMBER_PLUS` の予定のコメントが SUPPORTER に見える**（情報漏洩）。

**根拠**【確認済み】:

- `ScheduleVisibilityProjection`（`schedule/visibility/ScheduleVisibilityProjection.java`）のレコード成分は `id` / `teamId` / `organizationId` / `userId` / `createdBy` / `scheduleVisibility` / `visibilityTemplateId` / `scheduleStatus` の8つで、**`minViewRole` を含まない**。
- したがって `ScheduleVisibilityResolver` は `min_view_role` を一切評価しない。`canView(SCHEDULE, ...)` が見ているのは `ScheduleVisibility`（`MEMBERS_ONLY` / `ORGANIZATION` / `CUSTOM_TEMPLATE`）と所属だけである。
- 実際、【確認済み】`GoogleCalendarService#isSchedulePushableToUser`（`schedule/service/GoogleCalendarService.java:547`）は**この不足を知っていて自前で補っている**:
  1. `contentVisibilityChecker.canView(ReferenceType.SCHEDULE, schedule.getId(), userId)`
  2. `accessControlService.resolveEffectiveRoleName(userId, scopeId, scopeType)`
  3. `satisfiesMinViewRole(roleName, minViewRole)` — `RolePriority.isAtLeast` によるロール閾値比較
  つまり **`canView` ＋ `min_view_role` の二段構えが既存コードの実態**である。
- ⚠️ ただし `satisfiesMinViewRole` は **`private`** であり、`isSchedulePushableToUser` も Google push 専用（個人スコープを無条件 true にする）ため、**どちらもそのままでは再利用できない**。

**確定方針【御裁可済】: 「予定実効閲覧述語（`ScheduleEffectiveViewPredicate`）」を1つ定義し、コメント機能の全経路がこれだけを使う。**

```java
// backend/src/main/java/com/mannschaft/app/schedule/visibility/ScheduleEffectiveViewPredicate.java【提案】
// 単一の公開述語。コメント機能はこれ以外の可視性判定を持たない。
public boolean canEffectivelyView(Long scheduleId, Long viewerUserId);
// 複数件版（メンション通知・メンション候補用。SQL 本数を定数に保つ）
public Set<Long> filterViewers(Long scheduleId, Collection<Long> candidateUserIds);
```

##### `filterViewers` の実現手段（N+1 を作らない）

**単一スケジュールに対して複数ユーザーを判定する**という向きなので、素朴に `canEffectivelyView` をユーザー数だけ回すと**候補数に比例して SQL が増える**。【確認済み】`GoogleCalendarService#filterBackfillSchedules`（`:654-667`）が「1ユーザー × 複数スケジュール」の逆向きで同じ問題を既に解いており、**その最適化と同型**に実装する。

| ステップ | 実現手段 | SQL 本数 |
|---|---|---|
| 1. スケジュールの射影取得 | `scheduleRepository` から `scopeType` / `scopeId` / `minViewRole` を1回引く | **1** |
| 2. **ロール解決** | 【重要】**スコープは全候補で同一**（同じ予定なので `scopeId`/`scopeType` は1つ）。よって **`resolveEffectiveRoleName` をユーザーごとに呼ばず、スコープ単位の一括解決を1回**行い `Map<userId, roleName>` を得る。`filterBackfillSchedules` が `resolveEffectiveRoleName` を**ループ外で1回だけ**呼んで `roleName` を保持しメモリ比較しているのと同じ発想（あちらは1ユーザー固定、こちらは1スコープ固定） | **1** |
| 3. `min_view_role` 閾値比較 | 2 で得た `Map` に対し**メモリ上で** `RolePriority.isAtLeast` を適用（DB アクセスなし） | 0 |
| 4. `canView` | `ContentVisibilityChecker` の**単一コンテンツ × 複数ビューアー**に一括の口が無い場合は候補ごとの呼び出しになる。**この段は候補数に比例しうる**ため、**先に 2〜3 でロール足切りを済ませて候補を減らしてから呼ぶ** | 候補数依存（ただし 3 で削減後） |

- **`canView` を先に回さない**こと。ロール足切り（メモリ比較・0 クエリ）を先に通す方が、`canView` の呼び出し回数が減る。**順序が性能を決める**ため実装順を固定する。
- **候補数の上限を設ける**: `filterViewers` に渡す候補は **メンション上限 20 件（§4.2）／メンション候補の母集団は §4.4 の取得時点で上限**。無制限のコレクションを渡さない。
- **SQL 本数を AC-39 で固定する**（ステップ1・2 が候補数に依存しないこと＝候補 3 人と 20 人で同数であることを実測）。

判定の順序（**すべて満たしたときのみ true**）:

1. `contentVisibilityChecker.canView(ReferenceType.SCHEDULE, scheduleId, viewerUserId)` — F00 のラダー（所属・`ORGANIZATION` 昇格・`CUSTOM_TEMPLATE`）
2. `accessControlService.resolveEffectiveRoleName(viewerUserId, scopeId, scopeType)` でロール解決
3. `RolePriority.isAtLeast(roleName, required)` で `min_view_role` 閾値比較。対応は【確認済み】既存実装に合わせ `ANYONE → 閾値なし` / `SUPPORTER_PLUS → "SUPPORTER"` / `MEMBER_PLUS → "MEMBER"` / `ADMIN_ONLY → "ADMIN"`

- **fail-closed**: `viewerUserId` が null、スケジュールが見つからない、`minViewRole` が null、ロール解決に失敗 — いずれも **false**。

##### ⚠️ 抽出時の意味変更に注意 — 既存は `minViewRole == null` で fail-open

【確認済み】`GoogleCalendarService#satisfiesMinViewRole`（`:634-645`）の実装は次のとおりで、**本書の述語とは null の扱いが異なる**:

| 入力 | 既存 `satisfiesMinViewRole` | 本書の述語 | 差異の有無 |
|---|---|---|---|
| `minViewRole == null` | **`true`（fail-open）**（`:635-636` が `null` と `ANYONE` を同列に扱い早期 return） | **`false`（fail-closed）** | **あり** |
| `roleName == null` | **`false`**（`RolePriority.priority(null)` が `Integer.MAX_VALUE` を返すため `isAtLeast` が false。`ANYONE` 指定時のみ true） | `false` | なし |

**確定方針**【御裁可済】:

## 5. 状態遷移

### 5.1 コメントの状態遷移

```
        POST /comments
             │
             ▼
       ┌───────────┐   PATCH（本人のみ）    ┌───────────┐
       │  ACTIVE   │ ────────────────────▶ │  EDITED   │
       │(is_edited │ ◀──────────────────── │(is_edited │
       │  =FALSE)  │   （再編集で留まる）    │  =TRUE)   │
       └─────┬─────┘                       └─────┬─────┘
             │                                   │
             │  DELETE（本人 / 権限者 / ADMIN）    │
             ▼                                   ▼
       ┌─────────────────────────────────────────────┐
       │              DELETED（deleted_at 非NULL）     │
       │  ・body は API 応答で null                    │
       │  ・返信を持つ場合はトゥームストーン表示（§5.3） │
       │  ・以後 PATCH/DELETE は 404                   │
       └─────────────────────────────────────────────┘
```

- **`DELETED` からの復活はしない**（`deleted_at` を戻す API を作らない）。誤削除は再投稿で対応する。復活 API は「削除したはずの発言が復活する」という信頼を損なう挙動になりうるため設けない。
- `ACTIVE → EDITED` は不可逆（一度編集したら `is_edited` は `FALSE` に戻らない）。

### 5.2 スレッド開閉（`comments_enabled`）の遷移

```
  schedules 作成時
       │
       ▼
  ┌──────────┐   PATCH settings {false}   ┌──────────┐
  │  OPEN    │ ─────────────────────────▶ │  CLOSED  │
  │ (=TRUE)  │ ◀───────────────────────── │ (=FALSE) │
  └──────────┘   PATCH settings {true}    └──────────┘
```

#### 投稿可否は単一の述語に一本化する【提案・確定】

初版は「スレッドが閉じている」（§3.2）と「親が `CANCELLED`」（§5.4）を別々の文で書き、後者を「409 `SCHEDULE_COMMENT_005` **相当**」と曖昧に濁していた。**「相当」は実装者に解釈を委ねる表現であり、片方だけ実装される温床になる**ため排除する。

**書き込み可否は次の単一述語で判定する**（Service の1箇所で評価し、POST / PATCH がこれを呼ぶ）:

```
writable(schedule) := schedule.comments_enabled == TRUE
                      AND schedule.status != CANCELLED
```

- **false のときは常に 409 `SCHEDULE_COMMENT_005`**（理由が「閉じた」でも「中止」でも**同一のコードとステータス**）。呼び分けない。
- **DELETE はこの述語の対象外**（下表のとおり常に許可）。
- 【確認済み】`ScheduleVisibilityResolver.toContentStatus` は `CANCELLED` も `ContentStatus.PUBLISHED` として扱う（「メンバーにはキャンセル済みも表示する運用」）。よって**閲覧は F00 側で通り、書き込みだけを本述語で止める**という役割分担になる。

#### 状態 × 操作の一覧（3軸）

| `comments_enabled` | `schedules.status` | GET 一覧 | POST 投稿 | PATCH 編集 | DELETE 削除 |
|---|---|---|---|---|---|
| `TRUE` | `SCHEDULED` | ✅ | ✅ | ✅ | ✅ |
| `TRUE` | `COMPLETED` | ✅ | ✅（振り返り・お礼に需要あり） | ✅ | ✅ |
| `TRUE` | `CANCELLED` | ✅（読める） | ❌ 409 | ❌ 409 | ✅ |
| `FALSE` | `SCHEDULED` | ✅（読める） | ❌ 409 | ❌ 409 | ✅ |
| `FALSE` | `COMPLETED` | ✅（読める） | ❌ 409 | ❌ 409 | ✅ |
| `FALSE` | `CANCELLED` | ✅（読める） | ❌ 409 | ❌ 409 | ✅ |

> **CLOSED / CANCELLED でも DELETE を許す理由**: スレッドを閉じる・予定が中止になるのは新しい会話を止める事由であって、既に書かれた不適切な発言を消せなくする（モデレーション不能にする）ためではない。「閉じたら消せない」は運用上の詰みを生む。
>
> **スレッド開閉（`PATCH .../settings`）自体は `CANCELLED` でも可能**（中止後に議論を締める運用があるため）。開閉操作は上記述語の対象外。

### 5.3 削除済みコメントの表示 — トゥームストーン【既定】

**判定基準は「生存返信数 > 0」に統一する**【御裁可済】。初版は §3.3 で「`reply_count` は生存返信数」としながら §5.3 で「全返信が削除されてもトゥームストーンは残す」と書いており、**同じ状態に対して2つの答えを持っていた**。次のとおり一本化する。

```
表示する(comment) := comment.deleted_at IS NULL          -- 生存コメントは当然表示
                     OR (comment.depth == 0 AND comment.reply_count > 0)  -- トゥームストーン
```

| ケース | 挙動 |
|---|---|
| 削除された**返信**（`depth = 1`） | 一覧から**完全に消える**。返信にトゥームストーンは無い |
| 削除されたトップレベルで**生存返信が 0 件** | 一覧から**完全に消える** |
| 削除されたトップレベルで**生存返信が 1 件以上**（`reply_count > 0`） | **トゥームストーンとして残す**。`isDeleted = true` / `body = null` / `author = null` で返し、FE は i18n キー `schedule.comment.deleted`（「このコメントは削除されました」）を表示する |

- **なぜ残すか**: 親を消して返信だけ浮かせると、返信が何に対する発言か分からなくなり会話の文脈が壊れる。**親を消しても子の文脈は保つ**。
- **【裁定】全返信が削除されたらトップレベルも一覧から消える**。残す理由（子の文脈の保護）が消滅した以上、残す必要がない。「表示が揺れる」ことは**むしろ正しい挙動**（会話が丸ごと無くなったのだから跡形も残さない）。`reply_count` の増減に応じて自然にそうなるため、**追加の状態管理は不要**。
- トゥームストーンの `body` は **API 応答で `null`**（削除された本文を BE から一切送らない＝「FE で隠す」対処療法にしない）。
- **`reply_count` の整合が表示の正しさを直接決める**ため、§3.3 の 0 下限ガードと「生存返信数」の定義を必ず守ること。カウンタがずれると、消えるべき行が残る／残すべき行が消える。
- **削除しても本文は復元できない**: 論理削除では `body` 列に本文が残るが、**API・エクスポートのいずれも他人へ返さない**。管理者向けの「削除済み本文の閲覧」機能は設けない（§11 スコープ外）。

### 5.4 親スケジュールの状態との関係

| 親 `schedules.status` | コメントスレッド |
|---|---|
| `SCHEDULED` | 通常どおり（投稿可） |
| `CANCELLED` | **読めるが投稿不可**。§5.2 の `writable()` 述語が false になり **409 `SCHEDULE_COMMENT_005`**（「相当」ではなく同一のコード）【既定】 |
| `COMPLETED` | **投稿可**（振り返り・お礼のコメントに需要がある）【既定】 |
| `deleted_at` 非 NULL（論理削除） | コメント API は **404 `SCHEDULE_COMMENT_002`**（親が消えた予定は存在しないものとして扱う。§10.5） |

## 6. 通知連携（F04.3 / F04.11）

### 6.1 通知が発火する契機

| 契機 | 通知先 | 種別（文字列） | 既定 |
|---|---|---|---|
| **メンションされた** | `mentionedUserIds` のうち**親スケジュールを閲覧できる**ユーザー | `SCHEDULE_COMMENT_MENTIONED` | ✅ 送る |
| **自分のコメントに返信が付いた** | トップレベルコメントの投稿者（`user_id`） | `SCHEDULE_COMMENT_REPLIED` | ✅ 送る |
| 予定に誰かがコメントした（メンション無し） | — | — | ❌ **送らない**【既定】 |

> **「誰かがコメントした」を全員に送らない理由**【既定】: 出欠が必要な予定は数十人規模になる。1コメントごとに全員へ通知すると**通知疲れで通知自体が読まれなくなる**（ADHD 傾向のユーザーには特に有害）。**名指し（メンション）と自分への返信だけ**を通知の既定とし、それ以外は予定詳細画面のコメント件数バッジで受動的に気づかせる。全体通知の opt-in はスコープ外（§11）。

### 6.2 メンション対象の受け渡し【既定】

**リクエストの `mentionedUserIds` で明示的に受け取り、本文からのパースはしない。**

- **本文パースにしない理由**: 表示名は変わる・同名ユーザーがいる・多言語で区切りが違う。「`@山田` が誰か」を BE が本文から推測すると、**別人に通知が飛ぶ**（プライバシー事故）。FE のメンション UI が選択したユーザー ID をそのまま送るのが確実。
- **永続化しない**【既定】: `schedule_comment_mentions` テーブルは作らず、**投稿時に通知を発火して終わり**とする。メンションの装飾表示は FE が本文中の `@表示名` をハイライトするに留める。テーブルを持つのは「誰にメンションされたか一覧」機能を作るときで、本書のスコープ外（§2.3）。
- **上限 20 件**（それ以上は 400 `SCHEDULE_COMMENT_008`）。一斉通知の代用としてメンションを乱用させない。

### 6.3 【最重要】通知は可視性でフィルタしてから送る

> ⚠️ **メンションは「その予定を見られない人」への情報漏洩経路になりうる。** 通知のタイトル・本文にはコメント本文の冒頭が載るため、**閲覧権限のないユーザーへ送ると本文が漏れる**。

- `mentionedUserIds` は **§4.5.0 の「予定実効閲覧述語」（`ScheduleEffectiveViewPredicate.filterViewers`）でフィルタしてから**通知する。閲覧できないユーザーは**黙って除外**する（「その人は見られません」とエラーを返すと、逆に**その予定の可視性を探る手段**になるため、エラーにはしない）。
- ⚠️ **`canView` 単体でフィルタしてはならない**。`canView` は `min_view_role` を評価しないため（§4.5.0）、それだけで絞ると **`min_view_role = MEMBER_PLUS` の予定のコメント本文が SUPPORTER の通知に載って漏れる**。参照経路（§4.5）と通知経路（本節）が**同一の述語**を使うことが、この漏洩を構造的に塞ぐ唯一の担保である。**AC-18 で機械的に検証する。**
- **返信通知（`SCHEDULE_COMMENT_REPLIED`）も同じ述語を通す**。親コメントの投稿者が、その後にロール降格・チーム離脱で予定を閲覧できなくなっている可能性があるため、**通知の発火時点で再評価**する（投稿時点の権限をキャッシュしない）。
- 通知本文に載せるのは **コメント本文の先頭 100 文字まで**（`NotificationEntity` の上限に収める・タイトル 200／本文 1000）。
- ⚠️ **通知本文も XSS の経路である**: コメント本文はユーザー入力そのままなので、**通知一覧（F04.11 のインボックス UI）・プッシュ通知の描画側でもエスケープが必要**。コメント画面だけを守っても、同じ文字列が通知に載って別画面で描画される。**本文は保存・配信の全経路でプレーンテキストとして扱い、`v-html` 相当を使わない**（§10.6 と同一方針）。抜粋の切り出しでも HTML タグを組み立てない。
- **自分自身へのメンション通知は送らない**（`mentionedUserIds` に投稿者本人が含まれていても除外）。
- **同一コメントで「メンション」と「返信」の両方に該当するユーザーには 1 通のみ**送る（メンションを優先）。

- 上記の通知は **F04.11 の通知インボックス（`docs/features/F04.11_notification_inbox/`）に自動的に載る**（既存の通知基盤にレコードを作るため、インボックス側の追加実装は不要）。

### 6.6 トランザクション分離（原則5）

> ⚠️ **通知の失敗でコメント投稿が巻き戻ってはならない。**

- コメントの INSERT（schedule ドメインのトランザクション）と、通知の発火（notification ドメインへの越境）は**分離する**。
- 実装は **`TransactionSynchronizationManager.registerSynchronization(...)` の `afterCommit()`**（または `@TransactionalEventListener(AFTER_COMMIT)` + `REQUIRES_NEW`）に載せ、**コメントのコミット後に通知を発火**する。
- 通知は **best-effort**（1件失敗しても他の宛先へ継続。ループ内 try/catch）。ただし**握りつぶさずログに残す**（`.catch(() => {})` 相当の沈黙は禁止）。
- **同一 Bean 内の自己呼び出しで `@Transactional(REQUIRES_NEW)` を期待しない**（Spring AOP プロキシを経由せず no-op になる）。別 Bean に切り出すか `TransactionTemplate` を使う。

### 7.3 存在秘匿の方針

- **閲覧権限がない予定へのアクセスは 403 ではなく 404**（`SCHEDULE_COMMENT_002`）。403 を返すと「その ID の予定は存在する」ことが漏れ、ID 総当たりで組織の予定数・活動状況を推測できてしまう。
- 同様に、**別予定のコメント ID を渡した場合も 404**（`SCHEDULE_COMMENT_003`）。
- `docs/security/README.md` §4「deny-by-default」に整合。

**`commentId` は `String` で受けて自前で UUID パースする**【提案・確定】:

```java
@GetMapping("/{commentId}/replies")
public ResponseEntity<PagedResponse<CommentResponse>> listReplies(
        @PathVariable Long scheduleId,
        @PathVariable String commentId,   // ← UUID ではなく String で受ける
        ...) {
    UUID id = parseCommentId(commentId);  // 失敗時は 404 SCHEDULE_COMMENT_003 を投げる
    ...
}
```

- **`@PathVariable UUID commentId` と書いてはならない**。Spring の型変換が失敗すると `MethodArgumentTypeMismatchException` → **400 Bad Request** になり、「UUID として不正」と「存在しない」が**外から区別できてしまう**。攻撃者は 400 と 404 の差から「この形式の ID は実在しうる」と学習できる。
- **不正な形式も存在しない ID も、等しく 404 `SCHEDULE_COMMENT_003`** を返す（存在秘匿の一貫性）。
- パース処理は**共通ヘルパ1つ**に集約し、全エンドポイントがそれを通す（各所で `UUID.fromString` を直接呼ぶと 500 が漏れる箇所ができる）。
- **AC-41 で検証する**（`commentId=not-a-uuid` で 400 でも 500 でもなく 404 が返ること）。

## 9. 受け入れ条件（AC）

> **BE 契約テストは MockMvc 経由必須**（`TEST_CONVENTION.md`・Bean 直呼び禁止）。**実 MySQL Testcontainers**・**日時は `LocalDateTime` を bind**（文字列リテラル禁止・TZ 境界事故回避）。各 AC は `/試練` でそのまま red に落とせる粒度で、**実機 E2E（Playwright）でも観測可能**な「誰が・何をしたら・どうなる」で書く。

**検証層タグ**（各 AC の末尾に付す。どの層で緑にするかを試練の時点で確定させ、「BE は通ったが画面は壊れている」を防ぐ）:

| タグ | 意味 | 実体 |
|---|---|---|
| `[BE-IT]` | BE 統合テスト | MockMvc ＋ 実 MySQL Testcontainers（`*ScopeContractIT` / `*IT`） |
| `[BE-UT]` | BE 単体テスト | Resolver・述語・カウンタ等のロジック単体 |
| `[FE]` | FE 単体テスト | vitest（コンポーネント・分岐の描画） |
| `[E2E]` | 実機 E2E | Playwright（実サーバー・実 DB・実 UI） |

複数タグが付く AC は**そのすべての層で検証する**（片方だけでは不足という判断を明示したもの）。

### 9.3 境界

- **AC-21**（本文長）: `body` が **2000 文字ちょうどは 201 で成功**し、**2001 文字は 400 `SCHEDULE_COMMENT_001`**。空文字および空白のみ（トリム後に空）も **400**。`[BE-IT]`
- **AC-22**（深さ上限）: `depth=1` のコメントへ返信すると **400 `SCHEDULE_COMMENT_007`**。**返信先を自動で根に付け替えない**（応答にコメントが作られていないことを DB で確認）。`[BE-IT]`
- **AC-23**（メンション件数）: `mentionedUserIds` が **20 件ちょうどは成功**、**21 件で 400 `SCHEDULE_COMMENT_008`**。`[BE-IT]`
- **AC-24**（自己メンション）: `mentionedUserIds` に投稿者自身を含めて投稿すると **201 で成功するが、自分宛の通知は生成されない**。`[BE-IT]`
- **AC-25**（メンション＋返信の重複）: A のコメントに B が「A をメンションしつつ返信」すると、**A への通知は 1 通のみ**（メンション種別）。`[BE-IT]`
- **AC-26**（ページング境界）: トップレベルが 21 件あるとき、`page=0&size=20` で 20 件＋`hasNext=true`、`page=1` で 1 件＋`hasNext=false`。**`size=100` を指定しても 50 件にクランプされる**。`[BE-IT]`
- **AC-26b**（トゥームストーン述語とページングの整合・§4.3）: トップレベル 21 件のうち **1 件を「削除済み・生存返信0」**、**別の 1 件を「削除済み・生存返信1（トゥームストーン）」**にすると、`totalElements` は **20**（前者を除外し後者を算入）になり、`page=0&size=20` で 20 件返って `hasNext=false` になる。**返る件数と `totalElements` が一致し、空席が生じない**。`[BE-IT]`
- **AC-26c**（同着の順序安定・§4.3）: `created_at` が**完全に同一**のトップレベルを 3 件作り、`page=0&size=2` と `page=1&size=2` を取得すると、**同じ行が二重に現れず、取りこぼしも無い**（`id` 昇順の tie-break が効いている）。`[BE-IT]`
- **AC-27**（返信の同梱境界）: 返信が 5 件あるトップレベルの一覧応答では **`replies` が 3 件・`replyCount=5`** で返り、FE が「他 2 件の返信を表示」を出す。`GET .../{commentId}/replies` で全 5 件が取得できる。`[BE-IT]` `[FE]`
- **AC-27b**（`reply_count` の 0 下限ガード・§3.3）: 同一の返信に対して削除処理が**2回**走っても（再試行・二重クリック）、親の `reply_count` は **0 未満にならない**。カウンタが 0 の状態でデクリメントを呼んでも 0 のままである。`[BE-UT]`
- **AC-27c**（`replyCount` と実データの一致・§3.3）: 返信を 5 件作成 → 2 件削除 した後、一覧応答の **`replyCount` が 3** であり、`GET .../{commentId}/replies` の **`totalElements` も 3** で、**両者が一致する**。さらに返信を 1 件追加すると両方 4 になる。**非正規化カウンタが実データから乖離していないことの検証**であり、乖離すると §5.3 のトゥームストーン表示が壊れる。`[BE-IT]`
- **AC-28**（退会ユーザー）: 投稿者が退会（匿名化）した後もコメント本文は残り、**`author` が `null`** で返って FE が「退会したユーザー」（`schedule.comment.deletedAuthor`）を表示する（**空欄・NPE にならない**）。`[BE-IT]` `[FE]`

### 9.4 非機能・トランザクション・データ保護

- **AC-29**（N+1 なし）: トップレベル 20 件＋各 3 返信を含む一覧応答の SQL 発行数を **Hibernate `Statistics#getPrepareStatementCount()` で実測**し、**5 本以下**であること。**同じ測定を「トップレベル 5 件」でも行い、両者の発行数が一致する**こと（件数に比例しない＝ N+1 でないことの実証。SQL ログの目視や「速いから OK」は不可）。`[BE-IT]`
- **AC-30**（可視性判定の SQL 数）: `ScheduleCommentVisibilityResolver.filterAccessible` の SQL 発行数が **≦2**（F00 の要件）。同じく `getPrepareStatementCount()` の差分で測る。`[BE-IT]`
- **AC-31**（通知失敗の分離）: 通知サービスを**例外を投げるようスタブ化**した状態でコメントを投稿すると、**コメントは `schedule_comments` に保存されている**（201 が返る）一方で通知は 0 件。**投稿が巻き戻らない**（§6.6 の分離が機能）。`[BE-IT]`
- **AC-32**（レート制限）: **テスト用プロファイルで閾値を縮小し（例: 1分あたり 30 → 3 回）、時刻を注入可能な `Clock`（テストでは固定 `Clock`）で窓を制御する**。3 回投稿後の 4 回目が **429 `SCHEDULE_COMMENT_012`** となり、`Clock` を 61 秒進めると再び投稿できることを検証する。**実時間の `sleep` に依存しない**（CI の flaky 化を防ぐ。本番閾値のまま 31 回叩くテストは書かない）。`[BE-IT]`
- **AC-33**（認可契約テスト）: `ScheduleCommentScopeContractIT` が、**全 7 エンドポイント**（一覧・返信一覧・メンション候補・POST・PATCH・DELETE・settings）について「非メンバー 404／未認証 401／正当ユーザー 2xx」を実 MySQL Testcontainers で検証して緑になる。`[BE-IT]`
- **AC-34**（`deleted_at` の明示条件・§3.3）: `@SQLRestriction` を使わない方針の担保として、**削除済み行を1件混ぜた状態で `ScheduleCommentRepository` の全メソッドを呼び**、各メソッドが削除済みを「含む／含まない」のどちらであるべきかを固定する。**新しいメソッドを追加したときにこのテストに行を足し忘れると気づける**形にする（メソッド一覧との突合）。`[BE-IT]`
- **AC-35**（GDPR エクスポート・§3.3）: `@PersonalData(category="scheduleComments")` に対応する `PersonalDataCollector` の収集処理が、**自分が投稿したコメント（削除済みを含む）を実際に JSON で返す**。`PersonalDataCoverageValidator` の起動時突合で**当該カテゴリが missing にならない**（注釈の `category` と収集キーの文字列が一致している）。**`"[]"` を返すスタブでは AC を満たさない。** `[BE-IT]`
- **AC-36**（fail-closed・§4.5.0）: 予定実効閲覧述語が、**`viewerUserId = null` / スケジュール不存在 / `minViewRole = null` / ロール解決失敗**のいずれの入力でも **false** を返す（例外を投げて 500 にしたり、true に倒したりしない）。`[BE-UT]`
- **AC-37**（Resolver の一意性・§4.5.1）: アプリケーション起動時に、`referenceType()` が重複する `ContentVisibilityResolver` が存在しない（`SCHEDULE_COMMENT` と `COMMENT` が別々に解決される）。`[BE-UT]`
- **AC-38**（Google 側の挙動保存・§4.5.0）: `satisfiesMinViewRole` を述語へ抽出する**前に**特性テストを追加し、`minViewRole`（`null`/`ANYONE`/`SUPPORTER_PLUS`/`MEMBER_PLUS`/`ADMIN_ONLY`）× `roleName`（`null`/`SUPPORTER`/`MEMBER`/`ADMIN`）の全組み合わせの戻り値と、`isSchedulePushableToUser` の「個人スコープは無条件 true」「`canView` false なら false」を固定する。**抽出後も同じ特性テストが緑のまま**であること（特に **`minViewRole == null` で Google 側は `true` を返し続ける**こと＝コメント側の fail-closed 化が Google の挙動を変えていないこと）。**現状 `GoogleCalendarServiceTest` にはこれらのテストが1件も無い**ため、新規に書き起こす。`[BE-UT]`
- **AC-39**（`filterViewers` の SQL 本数・§4.5.0）: `filterViewers` に候補 **3 人**を渡した場合と **20 人**を渡した場合で、**ステップ1（射影取得）とステップ2（ロール一括解決）の SQL 本数が同一**であること（候補数に比例して増えない）。`getPrepareStatementCount()` の差分で実測する。`[BE-IT]`
- **AC-40**（メンション候補のフィルタ順序・§4.4）: 母集団 60 人のうち **10 人が `min_view_role` で閲覧不可**という状況で `size=50` を指定すると、**返る件数は 50 件**（可視な 50 人）であり、**閲覧不可の 10 人が1人も含まれない**。「先に 50 件で切ってから可視性で除外して 40 件になる」実装では失敗する。`[BE-IT]`

## 10. 非機能

### 10.1 N+1 の回避

コメント一覧は **「投稿者情報」「返信」「可視性判定」の3方向で N+1 になりやすい**。以下を必須とする。

| 箇所 | 危険 | 対策 |
|---|---|---|
| 投稿者情報の付加 | コメント 20 件 → users を 20 回引く | `user_id` を**一括収集して 1 クエリ**で引く（`IN (...)`）。既存の enrich パターンに倣う |
| 返信の取得 | トップレベル 20 件 → 返信を 20 回引く | **`root_id IN (...)` の 1 クエリ**で全返信を取り、アプリ側で `root_id` 別にグループ化して各3件に切る（`idx_sc_root_created` を使用） |
| 返信数 | 毎回 `COUNT(*)` | **`reply_count` の非正規化カウンタ**（§3.3）で 0 クエリ |
| 可視性判定 | コメントごとに `canView` | **`filterAccessible` で一括判定（SQL ≦2）**。コメント単位ではなく**親 `scheduleId` 単位で 1 回判定**すれば足りる（一覧は単一予定なので実質 1 回） |

- **`@OneToMany` で返信をマッピングしない**【既定】。JPA の関連にすると `FetchType` の設定ミスで容易に N+1 に落ちる。**`parent_id`/`root_id` は素の `Long` フィールド**として持ち（`ChatMessageEntity` と同じ）、取得はリポジトリの明示クエリで行う。
- **AC-29 / AC-30 で SQL 本数を機械的に検証**する（「速そう」で終わらせない）。

### 10.2 レート制限

| 対象 | 上限 | 根拠 |
|---|---|---|
| コメント投稿（POST） | **1ユーザーあたり 30 回/分**【既定】 | 連投荒らし・ボットの抑止。人間の会話速度では到達しない |
| コメント編集（PATCH） | 60 回/分 | 誤字修正の連打を許容 |
| 一覧取得（GET） | 既存の共通レート制限に従う | — |

- 実装は既存の `Bucket4j` 方式に揃える（F03.14 のアップロード URL 発行が前例）。
- 超過は **429 `SCHEDULE_COMMENT_012`**。

### 10.3 1000万ユーザー・シャーディング耐性

- **シャードキーは親スケジュールのスコープに従う**。`schedule_comments` は `schedule_id` でしか引かれない設計（全インデックスの先頭が `schedule_id` または `root_id`）なので、**`schedules` と同じシャードに同居させれば全クエリが単一シャードで閉じる**。
- **クロスシャードのクエリを作らない**: 「あるユーザーの全コメント」を横断で引く API は本書では作らない（`idx_sc_user` は退会匿名化バッチ・モデレーション用であり、ユーザー向け機能ではない）。
- **`user_id` に FK を張らないこと自体がシャーディング前提**（原則1）。users が別シャード／別サービスへ分離しても `schedule_comments` は壊れない。
- **`reply_count` の非正規化**は、シャード分割後に `COUNT(*)` がクロスシャードにならないための保険でもある。
- **想定行数**: 1予定あたり平均 5 コメント・予定が年間 1000万件なら年 5000万行。`schedule_id` 先頭の複合インデックスで単一予定の取得は常に定数時間。**将来の水平分割はスコープ（team/organization）単位**を想定し、予定とコメントを同じ単位に置く。
- **主キー UUIDv7 の効き方**（§1.6）: `id` が `BINARY(16)` の UUIDv7 であることで、**シャード間で ID を独立発番できる**（AUTO_INCREMENT のような採番調整が不要）。かつ時刻順に単調増加するため、`UUIDv4` と違って**主キーインデックスの page split が起きにくく INSERT 性能が保たれる**（`UuidV7Entity` の Javadoc が挙げる採用理由そのもの）。1予定あたり数件〜数十件の追記が続くコメント表とは相性がよい。
- **ただしソート契約は `created_at`**（§1.6）。UUIDv7 が時刻順であることに**クエリの正しさを依存させない**（同一ミリ秒内の順序は保証されず、`id` 順と `created_at` 順が微妙にずれうる）。`id` は tie-break にのみ使う。
- **`BINARY(16)` はストレージ上も BIGINT より 8 バイト大きい**が、`schedule_id` 先頭の複合インデックスで引く設計なので**主キーの走査は起きない**（セカンダリインデックスに主キーが載る分の増加のみ）。この程度の増加は独立発番・page split 回避の利得に見合うと判断する。

### 10.4 退会・匿名化（原則4・GDPR Art.17）

- コメント本文は **UGC として残す**が、**投稿者の同定情報は消す**。退会時に `schedule_comments.user_id` を **NULL 化**し、API は `author = null` で返す（FE は「退会したユーザー」表示・AC-28）。
- **本文中の PII**: 自由記述であるため実名・連絡先が混入しうる。**強匿名化（退会 30 日後）のフェーズで、当該ユーザーが書いたコメント本文を匿名化プレースホルダへ置換する**【既定】（F17.2 §13.4 の村コメントと同じ扱い。表示解決の匿名化では本文中の PII は消えないため物理置換が必要）。
- 実装は既存の退会クリーナ（`AFTER_COMMIT` + `REQUIRES_NEW` の前例）にメソッドを1本足す形。

### 10.5 削除された予定のコメントの扱い

| 親の状態 | コメントの扱い |
|---|---|
| **論理削除**（`schedules.deleted_at` 非 NULL） | コメント行は**物理的に残る**（`ON DELETE CASCADE` は物理削除にしか反応しない）。API は 404（AC-20）。**予定を復活させればコメントも復活する**（論理削除の意味を保つ） |
| **物理削除**（稀・システム管理者による強制削除） | `ON DELETE CASCADE` でコメントも消える（同一ドメイン内なので原則2に適合） |
| 親が `CANCELLED` | 読めるが投稿不可（§5.4） |

- **孤児コメントの定期掃除は不要**（親が論理削除されているだけなら復活可能性があるため掃除してはならない）。物理削除は CASCADE が面倒を見る。
- **ストレージ**: コメントは TEXT のみで添付を持たない（§2.3）ため、R2 等の外部ストレージのクリーンアップは発生しない。

### 10.6 その他

- **XSS**: `body` は **プレーンテキストとして保存**し、HTML/Markdown を解釈しない【既定】。FE は必ずテキストとして描画する（`v-html` 禁止）。URL の自動リンク化を将来入れる場合は、**サニタイズ済みの限定的なリンク化のみ**とする。
- **監査**: コメントの削除（特に他者コメントのモデレーション削除）とスレッド開閉は **`AuditEventType` に記録する**【提案】（`SCHEDULE_COMMENT_DELETED_BY_MODERATOR` / `SCHEDULE_COMMENT_THREAD_TOGGLED`）。投稿そのものは件数が多いため監査対象外。
- **後方互換**: 本書の DB 変更は**すべて Expand**（新規テーブル＋列1本追加）であり、既存行・既存クライアントを一切壊さない。既存の出欠コメント機能には**一切触らない**（§0.1）。
