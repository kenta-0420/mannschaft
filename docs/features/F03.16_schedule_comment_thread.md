本書は、共有スケジュール（`schedules`）の各予定に紐づく**汎用コメントスレッド**を新設するための設計である。既存の「出欠に添える一言コメント」（`schedule_attendances.comment`）とは**別物**であり、両者の棲み分けは §0.1 に置く。

| 記法 | 意味 |
|---|---|
| 【確認済み】 | `origin/main`（= `b27eee07c`, 2026-08-05）の実ファイルを開いて確認した事実。クラス名・テーブル名・カラム名・enum 値は実物と一致する |
| 【提案】 | 本書で新規に提案する設計。実装は未着手 |

本書の目標は **未決事項ゼロ** である（§11 に残余があれば「要裁可」として明示）。

### 0.1 【最重要】既存「出欠コメント」との棲み分け

> ⚠️ **本機能は出欠コメントの置き換えではない。両者は併存する。** 実装・レビュー時にこの表を最初に確認すること。

| 観点 | **出欠コメント**（既存・F03.1） | **予定コメントスレッド**（本書・F03.16） |
|---|---|---|
| 実体 | 【確認済み】`schedule_attendances.comment VARCHAR(500)`（`V3.041__create_schedule_attendances_table.sql`）。出欠回答行の1カラム | 【提案】新規テーブル `schedule_comments`（1予定に N 行） |
| 表示制御 | 【確認済み】`schedules.comment_option`（`HIDDEN`/`OPTIONAL`/`REQUIRED`・enum は `com.mannschaft.app.schedule.CommentOption`） | `comment_option` とは**無関係**。スレッドの開閉は §3.2 の `comments_enabled` で独立制御 |

## 1. 概要・背景

### 1.1 課題 — 予定について「話す場所」がない

【確認済み】現在、共有スケジュール（`schedules`）に紐づけて会話できる場所は存在しない。

| 現状の選択肢 | 何が起きるか |
|---|---|
| 出欠コメント（`schedule_attendances.comment`） | 1人1件・500文字・返信不可。「持ち物は？」に誰も答えられない。ADMIN の出欠一覧を開かないと読めない |
| チャット（F04.2）のチームチャンネル | 予定と紐づかない。他の話題に流れて、当日に遡って探せない |
| 掲示板（F04.x） | 予定と紐づかない。単発の予定に対して重すぎる |

結果として、**予定に関する Q&A・連絡調整がアプリ外（LINE 等）へ流出**している。

### 1.2 TimeTree 比較 — 採用の根拠【御裁可済】

競合の **TimeTree** は、共有カレンダーの各予定に**予定単位のコメント欄**を標準装備しており、これが同アプリの中核的な差別化要素になっている（「予定を立てる」だけでなく「予定について話す」までを1画面に閉じる）。Mannschaft は予定管理・出欠管理では上回るが、**この「予定に紐づく会話」だけが欠けている**。

比較の結果、マスターが**採用を決定**した【御裁可済】。

| 軸 | TimeTree | Mannschaft 現状 | 本書適用後 |
|---|---|---|---|
| 予定単位のコメント | ✅ 標準装備 | ❌ 無し | ✅ `schedule_comments` |
| 返信スレッド | △（フラット） | ❌ | ✅ 1段返信（§3.3） |
| メンション通知 | ✅ | ❌ | ✅（F04.3/F04.11・§6） |
| 出欠との一体運用 | △（出欠は簡易） | ✅ 強い | ✅ 両立（§0.1 で棲み分け） |
| 可視性の細粒度制御 | ❌（カレンダー単位） | ✅ 強い（F00） | ✅ 親の可視性を継承（§4.5） |

### 1.3 御裁可済み方針【御裁可済・変更禁止】

以下はマスター決定済みであり、本書はこれを前提に設計する。設計中に矛盾が生じても**この決定を動かさない**。

1. **専用テーブル `schedule_comments` を新設する**。**チャット基盤（`chat_messages`/`chat_channels`）の流用はしない**。ただし返信ツリー構造（`parent_id`/`root_id`/`depth`）のカラム設計は【確認済み】`ChatMessageEntity`（`backend/src/main/java/com/mannschaft/app/chat/entity/ChatMessageEntity.java`）を踏襲する。
2. **対象は共有 `schedules` のみ**。個人予定（F03.2・`schedules.user_id IS NOT NULL`）は**対象外**（閲覧者が本人しかいないためコメント需要がない）。イベント（F03.8）は【確認済み】`events.schedule_id`（`V3.100__create_events_table.sql`・`UNIQUE KEY uq_events_schedule`・`FOREIGN KEY ... REFERENCES schedules(id) ON DELETE RESTRICT`）で `schedules` に紐づくため、**自動的に本機能が載る**（本書で events 側の追加実装は行わない）。
3. **可視性は親スケジュールの可視性を継承する**。先例は【確認済み】`CirculationCommentVisibilityResolver`（回覧コメント）。F00 `ContentVisibilityResolver` 準拠で**参照時に判定**する（コメント自身は visibility 列を持たない）。
4. **既存の出欠コメント（`schedule_attendances.comment` / `comment_option`）とは別物**として併存させる（§0.1）。
5. **メンションは通知（F04.3 プッシュ通知基盤）へ連携する**。

## 2. スコープ

### 2.1 対象ロール

コメントの**閲覧可否は親スケジュールの可視性判定に完全に一致する**（§4.5）。以下は「親スケジュールを閲覧できる」ことを前提とした、コメント固有の操作権限である。

| ロール | 操作可能な範囲 |
|---|---|
| SYSTEM_ADMIN | 全コメントの参照・強制削除（モデレーション）。スレッド開閉の強制変更 |
| ADMIN | 親スケジュールを閲覧できる場合: 投稿・返信・**自分のコメントの編集**・**任意のコメントの削除**（モデレーション）・スレッド開閉（`comments_enabled`）の変更 |
| DEPUTY_ADMIN | 投稿・返信・自分のコメントの編集/削除。他者コメントの削除は `DELETE_OTHERS_CONTENT` 権限が必要。スレッド開閉の変更は `MANAGE_SCHEDULES` が必要 |
| MEMBER | 投稿・返信・**自分のコメントのみ**編集/削除。他者コメントの削除は `DELETE_OTHERS_CONTENT` 権限が必要 |
| SUPPORTER | 親スケジュールを閲覧できる場合（`min_view_role IN ('ANYONE','SUPPORTER+')`）: **投稿・返信・自分のコメントの編集/削除が可能**【既定】 |
| GUEST | 親スケジュールを閲覧できる場合（`min_view_role = 'ANYONE'`）: **閲覧のみ。投稿不可**【既定】（403 `SCHEDULE_COMMENT_004`） |

**書き込み権限を `min_response_role` に結びつけない理由**【既定】: `min_response_role` は**出欠回答**の最小ロールであり、「出欠は答えなくてよいが質問はしたい」保護者・応援者を締め出してしまう。コメントは会話であって回答ではないため、**「読める人は書ける（GUEST を除く）」**を既定とする。より厳しく閉じたい予定は §3.2 の `comments_enabled = FALSE` でスレッドごと閉じる。

### 2.2 対象レベル

- [x] 組織 (Organization) — `schedules.organization_id IS NOT NULL`
- [x] チーム (Team) — `schedules.team_id IS NOT NULL`
- [ ] 個人 (Personal) — **対象外**【御裁可済】。`schedules.user_id IS NOT NULL` の予定に対する全コメント API は **404 `SCHEDULE_COMMENT_002`** を返す（存在秘匿。403 ではなく 404 なのは「個人予定の存在自体を伏せる」ため）

### 2.3 スコープ外（本書では実装しない）

以下は**未決事項ではなく、明示的な後回し**である。

- リアクション（絵文字スタンプ）— 将来 `schedule_comment_reactions` として追加余地を残す（§3.5）
- コメントへのファイル・画像添付 — F03.14（`schedule_media_uploads`）は予定に紐づくためコメント単位の添付は別設計
- 2段以上の深い返信ツリー（`depth >= 2`）— §3.3 で構造だけ用意し、当面は 1 段に制限
- コメントの既読管理・未読バッジ
- メンション対象の永続化（`schedule_comment_mentions` テーブル）— §6.2 の理由により本書では持たない

## 3. DB 設計

### 3.1 テーブル一覧

| テーブル名 | 役割 | 論理削除 |
|---|---|---|
| `schedule_comments` | 予定に紐づくコメント・返信 | **あり**（`deleted_at`） |
| `schedules`（既存・ALTER） | `comments_enabled` 列を1本追加（§3.2） | 既存どおりあり |

### 3.2 `schedules` への ALTER【提案】

```sql
-- 【提案】schedules にスレッド開閉フラグを1列追加（Expand のみ・既存行を壊さない）
ALTER TABLE schedules
  ADD COLUMN comments_enabled BOOLEAN NOT NULL DEFAULT TRUE
    COMMENT '予定コメントスレッドの開閉（FALSE = 新規投稿・返信・編集を拒否。既存コメントの閲覧は可）';
```

- **既定 TRUE**（開いている）。「コメントできるのが普通」を既定にし、荒れた予定・確定した予定だけ閉じる運用。
- `FALSE` にしても**既存コメントは読める**（消さない）。閉じるのは書き込み（POST/PATCH/DELETE の新規操作）のみ。
- **JPA 注釈も対で追加する**: `ScheduleEntity` に `@Column(nullable = false) @Builder.Default private Boolean commentsEnabled = true;` を追加する（DDL だけ足して注釈を忘れると `ddl-auto` 検証・スキーマ生成で齟齬が出る）。
- **`comment_option` とは無関係**（§0.1）。`comment_option = 'HIDDEN'` でも `comments_enabled = TRUE` ならスレッドは動く。

### 3.3 `schedule_comments`（新規）【提案】

| カラム名 | 型 | NULL | デフォルト | 説明 |
|---|---|---|---|---|
| `id` | BIGINT UNSIGNED | NO | AUTO_INCREMENT | PK |
| `schedule_id` | BIGINT UNSIGNED | NO | — | FK → `schedules`（**同一ドメイン内**なので FK 可。ON DELETE CASCADE） |
| `user_id` | BIGINT UNSIGNED | YES | NULL | 投稿者。**FK は張らない**（users は別ドメイン＝原則1）。退会匿名化で NULL 化されうるため NULL 許容 |
| `parent_id` | BIGINT UNSIGNED | YES | NULL | 返信先コメント ID（NULL = トップレベル）。自己参照 FK・ON DELETE CASCADE |
| `root_id` | BIGINT UNSIGNED | YES | NULL | スレッド根の ID（トップレベルは NULL、返信は根の `id`）。`ChatMessageEntity.rootId` 踏襲 |
| `depth` | INT | NO | 0 | 階層。トップレベル=0、返信=1。**当面 1 を上限**とする（§3.3.1） |
| `body` | TEXT | NO | — | 本文。アプリ層で 1〜2000 文字を検証（§4.2） |
| `is_edited` | BOOLEAN | NO | FALSE | 編集済みフラグ（`ChatMessageEntity.isEdited` 踏襲） |
| `reply_count` | INT | NO | 0 | 返信数の非正規化カウンタ【既定】（一覧の N+1 回避・§10.1） |
| `created_at` | DATETIME | NO | CURRENT_TIMESTAMP | `BaseEntity` |
| `updated_at` | DATETIME | NO | CURRENT_TIMESTAMP ON UPDATE | `BaseEntity` |
| `deleted_at` | DATETIME | YES | NULL | 論理削除（`@SQLRestriction("deleted_at IS NULL")`） |

**インデックス**

```sql
INDEX idx_sc_schedule_created (schedule_id, created_at)          -- 予定別コメント一覧（既定ソート）
INDEX idx_sc_root_created     (root_id, created_at)              -- スレッド内の返信取得
INDEX idx_sc_parent           (parent_id)                        -- 返信の親引き・整合チェック
INDEX idx_sc_user             (user_id)                          -- 退会匿名化・本人コメント検索
INDEX idx_sc_schedule_alive   (schedule_id, deleted_at)          -- 生存コメント件数の高速集計
```

**制約・備考**

- `parent_id IS NULL` ⇔ `root_id IS NULL` ⇔ `depth = 0`（トップレベル）。`parent_id IS NOT NULL` ⇔ `root_id IS NOT NULL` ⇔ `depth = 1`。**アプリ層で必ず検証**する（不整合は 400 `SCHEDULE_COMMENT_006`）。
- 返信の `schedule_id` は**親コメントの `schedule_id` と一致しなければならない**（他予定のコメントへの返信を作らせない＝IDOR 経路の遮断・§4.5）。不一致は 400 `SCHEDULE_COMMENT_006`。
- `reply_count` は**トップレベル行のみ**が意味を持つ（返信行は常に 0）。返信の作成/削除時に根の行を増減する。
- **CASCADE の適用範囲**（CLAUDE.md 原則2「CASCADE DELETE は同一ドメイン内のみ」）:
  - `schedule_id` → `schedules`: **同一 schedule ドメイン内**なので `ON DELETE CASCADE` 可。ただし `schedules` は論理削除（`deleted_at`）が主で物理削除は稀。
  - `parent_id` → 自己参照: 同一テーブル内なので `ON DELETE CASCADE` 可（親コメントの物理削除で返信も消える）。**通常運用は論理削除**なので発火しない（§5.3）。
  - `user_id` → `users`: **クロスドメインのため FK を張らない**（原則1）。整合はアプリ層＋退会匿名化（§10.4）で保証する。
- **`SQLRestriction` の副作用に注意**【実装者向け】: `@SQLRestriction("deleted_at IS NULL")` を付けると、論理削除された親コメントは JPA から見えなくなる。返信の親引き・`reply_count` 補正は**削除済みも含めて扱う必要がある**ため、該当箇所は native / `@Query` で明示的に取得すること（`CirculationCommentEntity` と同じ注釈を使うが、あちらは返信ツリーを持たないので同じ落とし穴がない）。

#### 3.3.1 深さの上限は 1（2階層）【既定・PR レビューで変更可】

- **トップレベル（depth=0）とその返信（depth=1）の2階層のみ**。`depth = 1` のコメントへの返信要求は **400 `SCHEDULE_COMMENT_007`** で拒否し、**返信先を自動的に根へ付け替える暗黙処理はしない**（ユーザーが意図した相手と表示上の親がずれる事故を防ぐ＝症状を隠さない）。
- **カラムは 3 本とも先に持つ**（`parent_id`/`root_id`/`depth`）。将来 2 段以上へ広げるときに**マイグレーション不要**で上限値の定数だけ変えれば済む（`ChatMessageEntity` が既に同じ形を持っており、実装者が読み替えやすい）。
- FE は「返信」ボタンを depth=1 のコメントには出さない（BE 400 は防御の二層目）。

### 3.4 ER 図（テキスト形式）

```
schedules (1) ──── (N) schedule_comments        [FK: schedule_id, ON DELETE CASCADE, 同一ドメイン]
schedule_comments (1) ──── (N) schedule_comments [FK: parent_id (自己参照), ON DELETE CASCADE]
schedule_comments (N) ──── (1) users             [ID参照のみ・FKなし（原則1・クロスドメイン）]

events (1) ──── (1) schedules                    [既存: events.schedule_id UNIQUE, ON DELETE RESTRICT]
   └─ イベント（F03.8）は schedules 経由で自動的にコメントスレッドを持つ

schedule_attendances (N) ──── (1) schedules      [既存: 出欠コメント（別物・§0.1）]
```

### 3.5 将来拡張の余地（本書では作らない）

#### 3.6.1 ロールバック方針

Flyway Community 版は `undo` を持たないため、**巻き戻しは「打ち消しマイグレーションを前方に足す」方式**とする（`flyway repair` で誤魔化さない＝根治治療の原則）。

| 対象 | 前方打ち消し SQL | 注意 |
|---|---|---|
| `schedule_comments` の新設 | `DROP TABLE IF EXISTS schedule_comments;` | **新規テーブルなので既存データを一切失わない**（安全）。ただし投稿済みコメントは消える |
| `schedules.comments_enabled` の追加 | `ALTER TABLE schedules DROP COLUMN comments_enabled;` | 追加列のみの削除。既存列・既存行に影響なし（Expand の逆＝Contract） |

- **本番環境で一度でもコメントが投稿された後の `DROP TABLE` は UGC の消失**にあたるため、実行前に必ずマスターの承認を取ること（CLAUDE.md 自動実行ポリシーの例外「本番環境への変更」）。
- ステージング／ローカルでの巻き戻しは上記2文で完結する（`schedules` 本体・`schedule_attendances` には触らないので、出欠機能への波及はゼロ）。

## 4. API 契約

### 4.1 エンドポイント一覧

すべて `CirculationCommentController` の作法（`/api/v1/{親リソース}/{親ID}/comments`・`PagedResponse` / `ApiResponse` エンベロープ）に揃える。

| メソッド | パス | 認証 | 説明 |
|---|---|---|---|
| GET | `/api/v1/schedules/{scheduleId}/comments` | 必要 | コメント一覧（トップレベル＋返信の階層構造） |
| POST | `/api/v1/schedules/{scheduleId}/comments` | 必要 | コメント投稿／返信 |
| PATCH | `/api/v1/schedules/{scheduleId}/comments/{commentId}` | 必要 | 本文編集（自分のコメントのみ） |
| DELETE | `/api/v1/schedules/{scheduleId}/comments/{commentId}` | 必要 | 論理削除 |

### 4.5 認可 — 親スケジュールの可視性を Resolver 経由で継承する【提案・必須】

> ⚠️ **コメント側で独自の可視性述語（`team_id` 突き合わせ等）を書いてはならない。** 独自述語は F00 の可視性ラダー（`ORGANIZATION` / `CUSTOM_TEMPLATE` / `min_view_role` / F01.7 テンプレート）と必ずずれ、漏洩源になる。**判定は必ず `ContentVisibilityChecker` 経由**で行う。

**新設する Resolver**【提案】

```java
// backend/src/main/java/com/mannschaft/app/schedule/visibility/ScheduleCommentVisibilityResolver.java
@Component
public class ScheduleCommentVisibilityResolver
        extends AbstractContentVisibilityResolver<StandardVisibility, ScheduleCommentVisibilityProjection> {
    // referenceType()   → ReferenceType.SCHEDULE_COMMENT（§4.5.1 で新設）
    // loadProjections() → scheduleCommentRepository.findVisibilityProjectionsByIdIn(ids)
    // toStandard()      → 恒等（Projection は常に CUSTOM を返す）
    // toContentStatus() → 常に ContentStatus.PUBLISHED
    // customSubType()   → "PARENT_DELEGATION"
    // evaluateCustom()  → contentVisibilityChecker.canView(ReferenceType.SCHEDULE, row.scheduleId(), viewerUserId)
}
```

- 【確認済み】`CirculationCommentVisibilityResolver` と**同じ形**（`@Lazy ContentVisibilityChecker` で循環依存回避・`RecursionDepthCounter.enter()` / `finally exit()` で深度上限 3・`MembershipBatchQueryService`・`VisibilityTemplateEvaluator`・`VisibilityMetrics`）。実装者はこのクラスをそのまま金型にできる。
- **fail-closed**: `viewerUserId` が null／`row` が null／`row.scheduleId()` が null のいずれかで **`false`**（読めない側に倒す）。
- `filterAccessible(...)` の SQL 数は **≦2**（F00 の要件）。コメント一覧は「1回で全 `scheduleId` を引く → 1回で可視判定」の2段で済ませる（§10.1）。
- **Projection**: `ScheduleCommentVisibilityProjection`（`id`, `scheduleId`）を新設。`schedule_comments` からこの2列だけを引く軽量 Projection。

#### 4.5.1 `ReferenceType` への値追加が必要【提案・重要】

【確認済み】`ReferenceType`（`backend/src/main/java/com/mannschaft/app/common/visibility/ReferenceType.java`）には `COMMENT`（「コメント (Phase C / 親コンテンツの可視性に従属)」）が既にあるが、**この値は `CirculationCommentVisibilityResolver` が既に `referenceType()` で専有している**。同じ値を2つの Resolver が返すと Resolver 解決が一意に定まらない。

したがって **`SCHEDULE_COMMENT` を新規追加する**【提案】。

- 【確認済み】同 enum の Javadoc は「**値の削除を禁止・deprecated 化のみ許可**」（設計書 §15 D-12）としており、**追加は許可されている**。新 referenceType の追加手順は `docs/features/F00_content_visibility_resolver.md` §6.3 に従う。
- 【確認済み】`corkboard_card_reference.reference_type`（VARCHAR(30)）と値を一致させる要件がある。`SCHEDULE_COMMENT` は **16 文字**で 30 以内に収まる。
- **既存の `COMMENT` を流用しない理由**を Javadoc に明記する（将来「なぜ2つあるのか」で誤って統合されるのを防ぐ）。

#### 4.5.2 認可の実施箇所と番人対応

- **書き込み系（POST/PATCH/DELETE）も、まず親スケジュールの `canView` を通す**。「読めない予定にコメントを書ける」経路を作らない。
- **認可ガードは public な入口（Controller から呼ばれる Service メソッド）に置く**。内部共有ヘルパに置くと、将来のバッチ処理が巻き添えで 403 になる（memory `feedback_authz_gate_on_public_entry_not_shared_method`）。
- **`userId` を引数に取るだけで本体で使っていない「死んだ引数」を作らない**。ArchUnit 認可番人は引数の存在ではなく**到達**を検証する必要がある（memory `feedback_dead_authz_param_deceives_guard`）。
- 新規エンドポイントは **ArchUnit 認可番人（`AuthzControllerGuardArchTest`）と `addFilters=false` の契約 IT の両方に対応**させる（`docs/security/README.md` §4.1）。契約 IT は `@WithMockUser` 必須。
- **`*ScopeContractIT` に `ScheduleCommentScopeContractIT` を追加**する（非メンバー 403／越境 404／正当成功を実 MySQL Testcontainers で検証）。これが認可回帰の一次防御となる。
- **正常系も必ず契約テストに書く**（異常系だけだと「常に 500 を返す実装」でも緑になる。memory `feedback_native_count_gt_zero_boolean_classcast`）。

## 5. 状態遷移

### 5.1 コメントの状態遷移

```
        POST /comments
             │
             ▼
       ┌───────────┐   PATCH（本人のみ）    ┌───────────┐
       │  ACTIVE   │ ────────────────────▶ │  EDITED   │
       │(is_edited │ ◀──────────────────── │(is_edited │
       │  =FALSE)  │   （再編集で留まる）    │  =TRUE)   │
       └─────┬─────┘                       └─────┬─────┘
             │                                   │
             │  DELETE（本人 / 権限者 / ADMIN）    │
             ▼                                   ▼
       ┌─────────────────────────────────────────────┐
       │              DELETED（deleted_at 非NULL）     │
       │  ・body は API 応答で null                    │
       │  ・返信を持つ場合はトゥームストーン表示（§5.3） │
       │  ・以後 PATCH/DELETE は 404                   │
       └─────────────────────────────────────────────┘
```

- **`DELETED` からの復活はしない**（`deleted_at` を戻す API を作らない）。誤削除は再投稿で対応する。復活 API は「削除したはずの発言が復活する」という信頼を損なう挙動になりうるため設けない。
- `ACTIVE → EDITED` は不可逆（一度編集したら `is_edited` は `FALSE` に戻らない）。

### 5.2 スレッド開閉（`comments_enabled`）の遷移

```
  schedules 作成時
       │
       ▼
  ┌──────────┐   PATCH settings {false}   ┌──────────┐
  │  OPEN    │ ─────────────────────────▶ │  CLOSED  │
  │ (=TRUE)  │ ◀───────────────────────── │ (=FALSE) │
  └──────────┘   PATCH settings {true}    └──────────┘
```

| 状態 | GET 一覧 | POST 投稿 | PATCH 編集 | DELETE 削除 |
|---|---|---|---|---|
| `OPEN` | ✅ | ✅ | ✅ | ✅ |
| `CLOSED` | ✅（読める） | ❌ 409 | ❌ 409 | ✅ **削除は許可** |

> **CLOSED でも DELETE を許す理由**: スレッドを閉じるのは新しい会話を止めるためであって、既に書かれた不適切な発言を消せなくする（モデレーション不能にする）ためではない。「閉じたら消せない」は運用上の詰みを生む。

### 5.3 削除済みコメントの表示 — トゥームストーン【既定】

| ケース | 挙動 |
|---|---|
| **返信を持たない**トップレベル、または返信そのもの | 一覧から**完全に消える**（`@SQLRestriction` により JPA から見えない） |
| **返信を持つ**トップレベル（`reply_count > 0`） | **トゥームストーンとして残す**。`isDeleted = true` / `body = null` / `author = null` で返し、FE は i18n キー `schedule.comment.deleted`（「このコメントは削除されました」）を表示する |

- **なぜ残すか**: 親を消して返信だけ浮かせると、返信が何に対する発言か分からなくなり会話の文脈が壊れる。**親を消しても子の文脈は保つ**。
- トゥームストーンの `body` は **API 応答で `null`**（削除された本文を BE から一切送らない＝「FE で隠す」対処療法にしない）。
- 返信がすべて削除されて `reply_count` が 0 になっても、**トゥームストーンは残したまま**にする（毎回再評価すると表示が揺れる）。

### 5.4 親スケジュールの状態との関係

| 親 `schedules.status` | コメントスレッド |
|---|---|
| `SCHEDULED` | 通常どおり（投稿可） |
| `CANCELLED` | **読めるが投稿不可**（409 `SCHEDULE_COMMENT_005` 相当）。中止になった予定への新規会話は止める【既定】 |
| `COMPLETED` | **投稿可**（振り返り・お礼のコメントに需要がある）【既定】 |
| `deleted_at` 非 NULL（論理削除） | コメント API は **404 `SCHEDULE_COMMENT_002`**（親が消えた予定は存在しないものとして扱う。§10.5） |

## 6. 通知連携（F04.3 / F04.11）

### 6.1 通知が発火する契機

| 契機 | 通知先 | 種別（文字列） | 既定 |
|---|---|---|---|
| **メンションされた** | `mentionedUserIds` のうち**親スケジュールを閲覧できる**ユーザー | `SCHEDULE_COMMENT_MENTIONED` | ✅ 送る |
| **自分のコメントに返信が付いた** | トップレベルコメントの投稿者（`user_id`） | `SCHEDULE_COMMENT_REPLIED` | ✅ 送る |
| 予定に誰かがコメントした（メンション無し） | — | — | ❌ **送らない**【既定】 |

> **「誰かがコメントした」を全員に送らない理由**【既定】: 出欠が必要な予定は数十人規模になる。1コメントごとに全員へ通知すると**通知疲れで通知自体が読まれなくなる**（ADHD 傾向のユーザーには特に有害）。**名指し（メンション）と自分への返信だけ**を通知の既定とし、それ以外は予定詳細画面のコメント件数バッジで受動的に気づかせる。全体通知の opt-in はスコープ外（§11）。

### 6.2 メンション対象の受け渡し【既定】

**リクエストの `mentionedUserIds` で明示的に受け取り、本文からのパースはしない。**

- **本文パースにしない理由**: 表示名は変わる・同名ユーザーがいる・多言語で区切りが違う。「`@山田` が誰か」を BE が本文から推測すると、**別人に通知が飛ぶ**（プライバシー事故）。FE のメンション UI が選択したユーザー ID をそのまま送るのが確実。
- **永続化しない**【既定】: `schedule_comment_mentions` テーブルは作らず、**投稿時に通知を発火して終わり**とする。メンションの装飾表示は FE が本文中の `@表示名` をハイライトするに留める。テーブルを持つのは「誰にメンションされたか一覧」機能を作るときで、本書のスコープ外（§2.3）。
- **上限 20 件**（それ以上は 400 `SCHEDULE_COMMENT_008`）。一斉通知の代用としてメンションを乱用させない。

### 6.3 【最重要】通知は可視性でフィルタしてから送る

> ⚠️ **メンションは「その予定を見られない人」への情報漏洩経路になりうる。** 通知のタイトル・本文にはコメント本文の冒頭が載るため、**閲覧権限のないユーザーへ送ると本文が漏れる**。

- `mentionedUserIds` は **`ScheduleVisibilityResolver`（`ReferenceType.SCHEDULE`）でフィルタしてから**通知する。閲覧できないユーザーは**黙って除外**する（「その人は見られません」とエラーを返すと、逆に**その予定の可視性を探る手段**になるため、エラーにはしない）。
- 通知本文に載せるのは **コメント本文の先頭 100 文字まで**（`NotificationEntity` の上限に収める・タイトル 200／本文 1000）。
- **自分自身へのメンション通知は送らない**（`mentionedUserIds` に投稿者本人が含まれていても除外）。
- **同一コメントで「メンション」と「返信」の両方に該当するユーザーには 1 通のみ**送る（メンションを優先）。

### 6.4 通知の配線

| 通知フィールド | 設定値 | 理由 |
|---|---|---|
| `notificationType` | `"SCHEDULE_COMMENT_MENTIONED"` / `"SCHEDULE_COMMENT_REPLIED"`（String） | **核 `NotificationType` enum は改変しない**（横断 enum への波及回避。F17.2 §3.4 と同方針） |
| `sourceType` | `"SCHEDULE_COMMENT"`（String） | — |
| `sourceId` | コメント ID（Long） | **BIGINT なのでそのまま載る**（村ドメインの UUID 問題は起きない） |
| `scopeType` | 親スケジュールのスコープ（`TEAM` / `ORGANIZATION`） | `schedules.team_id` / `organization_id` から解決 |
| `scopeId` | 同上の ID | — |
| `actionUrl` | `/schedules/{scheduleId}?commentId={commentId}` | タップでコメントへ直接ジャンプ |
| `title` / `body` | i18n 由来（§8）＋本文冒頭 100 文字 | `NotificationEntity` の上限（200/1000）に収める |
| `actorId` | コメント投稿者の `user_id` | 「誰が」を通知に出す |

### 6.5 F04.11（通知インボックス）との連携

- 上記の通知は **F04.11 の通知インボックス（`docs/features/F04.11_notification_inbox/`）に自動的に載る**（既存の通知基盤にレコードを作るため、インボックス側の追加実装は不要）。
- **既読化**: 通知インボックスから `actionUrl` を開くと既存の既読フローで既読になる。コメント側に独自の既読管理は持たない（§2.3）。
- **プッシュ配信**: F04.3 のプッシュ通知基盤に乗る。ユーザーの通知設定（種別ごとの on/off）に従う。**種別が文字列なので、既存の設定 UI に新種別を足すだけで opt-out が効く**。

### 6.6 トランザクション分離（原則5）

> ⚠️ **通知の失敗でコメント投稿が巻き戻ってはならない。**

- コメントの INSERT（schedule ドメインのトランザクション）と、通知の発火（notification ドメインへの越境）は**分離する**。
- 実装は **`TransactionSynchronizationManager.registerSynchronization(...)` の `afterCommit()`**（または `@TransactionalEventListener(AFTER_COMMIT)` + `REQUIRES_NEW`）に載せ、**コメントのコミット後に通知を発火**する。
- 通知は **best-effort**（1件失敗しても他の宛先へ継続。ループ内 try/catch）。ただし**握りつぶさずログに残す**（`.catch(() => {})` 相当の沈黙は禁止）。
- **同一 Bean 内の自己呼び出しで `@Transactional(REQUIRES_NEW)` を期待しない**（Spring AOP プロキシを経由せず no-op になる）。別 Bean に切り出すか `TransactionTemplate` を使う。

- 同様に、**別予定のコメント ID を渡した場合も 404**（`SCHEDULE_COMMENT_003`）。
- `docs/security/README.md` §4「deny-by-default」に整合。

## 9. 受け入れ条件（AC）

> **BE 契約テストは MockMvc 経由必須**（`TEST_CONVENTION.md`・Bean 直呼び禁止）。**実 MySQL Testcontainers**・**日時は `LocalDateTime` を bind**（文字列リテラル禁止・TZ 境界事故回避）。各 AC は `/試練` でそのまま red に落とせる粒度で、**実機 E2E（Playwright）でも観測可能**な「誰が・何をしたら・どうなる」で書く。

### 9.1 正常系

- **AC-01**（投稿）: **チームの MEMBER が**、閲覧できるチーム予定の詳細画面で本文「集合場所は駅前でよいですか？」を入力し投稿すると、**コメントが一覧の末尾に自分の表示名・アバター付きで即座に現れ**、`schedule_comments` に `schedule_id=当該予定` / `user_id=自分` / `parent_id IS NULL` / `root_id IS NULL` / `depth=0` / `is_edited=FALSE` / `reply_count=0` の行が1件生成される。
- **AC-02**（返信）: **別の MEMBER が** AC-01 のコメントの「返信」ボタンを押して投稿すると、**そのコメントの直下にインデントされて表示され**、新しい行が `parent_id=親のid` / `root_id=親のid` / `depth=1` で生成され、**親行の `reply_count` が 1 になる**。
- **AC-03**（一覧・階層）: `GET /api/v1/schedules/{id}/comments` は、トップレベルを `createdAt` 昇順で `size=20` 件返し、各トップレベルに**最新3件までの返信を `replies` 配列で同梱**する。**返信行の `replies` は常に `null`**（無限ネストしない）。`meta.commentsEnabled` / `meta.canPost` が含まれる。
- **AC-04**（編集）: 投稿者本人が自分のコメントを編集すると、本文が更新され **`is_edited=TRUE`** になり、UI に「（編集済み）」（`schedule.comment.edited`）が表示される。
- **AC-05**（削除・返信なし）: 返信のないコメントを投稿者本人が削除すると **204** が返り、**一覧から完全に消える**（`deleted_at` が打たれ `@SQLRestriction` で除外される）。
- **AC-06**（削除・返信あり／トゥームストーン）: `reply_count > 0` のトップレベルを削除すると、**一覧には「このコメントは削除されました」（`schedule.comment.deleted`）のカードが残り、その返信は消えずにぶら下がったまま**になる。API 応答は `isDeleted=true` / **`body` が `null`** / `author` が `null`。
- **AC-07**（イベント経由）: F03.8 のイベント（`events.schedule_id` で紐づく）の詳細画面からも、**同じ `schedules` のコメントスレッドが同じ内容で表示・投稿できる**（events 側に別実装を持たない）。
- **AC-08**（スレッド開閉）: ADMIN が「コメントを締め切る」を押すと `schedules.comments_enabled=FALSE` になり、**全ユーザーの入力欄が無効化され「この予定のコメントは締め切られています」が表示される**。**既存コメントは引き続き読める**。
- **AC-09**（メンション通知）: A がコメント本文で B をメンションして投稿すると、**B の通知インボックス（F04.11）に「A さんがあなたをメンションしました」が届き**、タップすると `/schedules/{scheduleId}?commentId={commentId}` へ遷移して該当コメントが表示される。
- **AC-10**（返信通知）: A のコメントに B が返信すると、**A の通知インボックスに「B さんがあなたのコメントに返信しました」が届く**。
- **AC-11**（`canEdit`/`canDelete`）: 一覧応答で、**自分のコメントは `canEdit=true`/`canDelete=true`、他人のコメント（権限なし MEMBER 視点）は両方 `false`** で返り、FE の編集/削除ボタンの表示がこれに一致する。

### 9.2 異常系

- **AC-12**（越境・存在秘匿）: **別チームのユーザーが**他チーム予定のコメント一覧を叩くと **404 `SCHEDULE_COMMENT_002`**（403 ではない）。コメント件数・予定タイトルなど一切の情報が応答に含まれない。
- **AC-13**（コメント ID の越境）: 予定 X のコメント ID を予定 Y のパスに混ぜて `PATCH /schedules/{Y}/comments/{Xのコメント}` を叩くと **404 `SCHEDULE_COMMENT_003`**（本文は更新されない）。
- **AC-14**（他人のコメントの編集）: **ADMIN であっても**他人のコメント本文を PATCH すると **403 `SCHEDULE_COMMENT_009`**（改竄不可）。ただし**同じ ADMIN が DELETE すれば 204 で削除できる**（モデレーションは可・編集は不可）。
- **AC-15**（GUEST）: `min_view_role='ANYONE'` の予定で、**GUEST はコメントを閲覧できるが投稿すると 403 `SCHEDULE_COMMENT_004`**。UI では入力欄が出ず「コメントの閲覧のみ可能です」が表示される。
- **AC-16**（閉じたスレッドへの投稿）: `comments_enabled=FALSE` の予定へ POST すると **409 `SCHEDULE_COMMENT_005`**。**同じ状態で DELETE は 204 で成功する**（§5.2）。
- **AC-17**（個人予定）: 個人予定（`schedules.user_id IS NOT NULL`）に対する**全コメント API が 404 `SCHEDULE_COMMENT_002`**（本人が叩いても 404。個人予定はスコープ外）。
- **AC-18**（メンションの可視性フィルタ）: A が、**その予定を閲覧できない C** を `mentionedUserIds` に含めて投稿すると、**投稿自体は 201 で成功**し（エラーにしない＝可視性の探索を許さない）、**C には通知が届かない**。同時に指定した閲覧可能な B には届く。
- **AC-19**（削除済みへの操作）: 既に削除済みのコメントへ PATCH／DELETE すると **404 `SCHEDULE_COMMENT_003`**。
- **AC-20**（親が論理削除済み）: 親スケジュールが論理削除された後にコメント API を叩くと **404 `SCHEDULE_COMMENT_002`**。

### 9.3 境界

- **AC-21**（本文長）: `body` が **2000 文字ちょうどは 201 で成功**し、**2001 文字は 400 `SCHEDULE_COMMENT_001`**。空文字および空白のみ（トリム後に空）も **400**。
- **AC-22**（深さ上限）: `depth=1` のコメントへ返信すると **400 `SCHEDULE_COMMENT_007`**。**返信先を自動で根に付け替えない**（応答にコメントが作られていないことを DB で確認）。
- **AC-23**（メンション件数）: `mentionedUserIds` が **20 件ちょうどは成功**、**21 件で 400 `SCHEDULE_COMMENT_008`**。
- **AC-24**（自己メンション）: `mentionedUserIds` に投稿者自身を含めて投稿すると **201 で成功するが、自分宛の通知は生成されない**。
- **AC-25**（メンション＋返信の重複）: A のコメントに B が「A をメンションしつつ返信」すると、**A への通知は 1 通のみ**（メンション種別）。
- **AC-26**（ページング境界）: トップレベルが 21 件あるとき、`page=0&size=20` で 20 件＋`hasNext=true`、`page=1` で 1 件＋`hasNext=false`。**`size=100` を指定しても 50 件にクランプされる**。
- **AC-27**（返信の同梱境界）: 返信が 5 件あるトップレベルの一覧応答では **`replies` が 3 件・`replyCount=5`** で返り、FE が「他 2 件の返信を表示」を出す。`GET .../{commentId}/replies` で全 5 件が取得できる。
- **AC-28**（退会ユーザー）: 投稿者が退会（匿名化）した後もコメント本文は残り、**`author` が `null`** で返って FE が「退会したユーザー」（`schedule.comment.deletedAuthor`）を表示する（**空欄・NPE にならない**）。

### 9.4 非機能・トランザクション

- **AC-29**（N+1 なし）: トップレベル 20 件＋各 3 返信を含む一覧応答の SQL 発行数が **定数本数（≦5 本）**であること（Hibernate statistics または SQL ログで実測。件数に比例して増えないこと）。
- **AC-30**（可視性判定の SQL 数）: `ScheduleCommentVisibilityResolver.filterAccessible` の SQL 発行数が **≦2**（F00 の要件）。
- **AC-31**（通知失敗の分離）: 通知サービスを**例外を投げるようスタブ化**した状態でコメントを投稿すると、**コメントは `schedule_comments` に保存されている**（201 が返る）一方で通知は 0 件。**投稿が巻き戻らない**（§6.6 の分離が機能）。
- **AC-32**（レート制限）: 同一ユーザーが 1 分間に 31 回投稿しようとすると **31 回目が 429**（§10.2）。
- **AC-33**（認可契約テスト）: `ScheduleCommentScopeContractIT` が、全エンドポイントについて「非メンバー 404／未認証 401／正当ユーザー 2xx」を実 MySQL Testcontainers で検証して緑になる。

## 10. 非機能

### 10.1 N+1 の回避

コメント一覧は **「投稿者情報」「返信」「可視性判定」の3方向で N+1 になりやすい**。以下を必須とする。

| 箇所 | 危険 | 対策 |
|---|---|---|
| 投稿者情報の付加 | コメント 20 件 → users を 20 回引く | `user_id` を**一括収集して 1 クエリ**で引く（`IN (...)`）。既存の enrich パターンに倣う |
| 返信の取得 | トップレベル 20 件 → 返信を 20 回引く | **`root_id IN (...)` の 1 クエリ**で全返信を取り、アプリ側で `root_id` 別にグループ化して各3件に切る（`idx_sc_root_created` を使用） |
| 返信数 | 毎回 `COUNT(*)` | **`reply_count` の非正規化カウンタ**（§3.3）で 0 クエリ |
| 可視性判定 | コメントごとに `canView` | **`filterAccessible` で一括判定（SQL ≦2）**。コメント単位ではなく**親 `scheduleId` 単位で 1 回判定**すれば足りる（一覧は単一予定なので実質 1 回） |

- **`@OneToMany` で返信をマッピングしない**【既定】。JPA の関連にすると `FetchType` の設定ミスで容易に N+1 に落ちる。**`parent_id`/`root_id` は素の `Long` フィールド**として持ち（`ChatMessageEntity` と同じ）、取得はリポジトリの明示クエリで行う。
- **AC-29 / AC-30 で SQL 本数を機械的に検証**する（「速そう」で終わらせない）。

### 10.2 レート制限

| 対象 | 上限 | 根拠 |
|---|---|---|
| コメント投稿（POST） | **1ユーザーあたり 30 回/分**【既定】 | 連投荒らし・ボットの抑止。人間の会話速度では到達しない |
| コメント編集（PATCH） | 60 回/分 | 誤字修正の連打を許容 |
| 一覧取得（GET） | 既存の共通レート制限に従う | — |

- 実装は既存の `Bucket4j` 方式に揃える（F03.14 のアップロード URL 発行が前例）。
- 超過は **429 `SCHEDULE_COMMENT_012`**。

### 10.3 1000万ユーザー・シャーディング耐性

- **シャードキーは親スケジュールのスコープに従う**。`schedule_comments` は `schedule_id` でしか引かれない設計（全インデックスの先頭が `schedule_id` または `root_id`）なので、**`schedules` と同じシャードに同居させれば全クエリが単一シャードで閉じる**。
- **クロスシャードのクエリを作らない**: 「あるユーザーの全コメント」を横断で引く API は本書では作らない（`idx_sc_user` は退会匿名化バッチ・モデレーション用であり、ユーザー向け機能ではない）。
- **`user_id` に FK を張らないこと自体がシャーディング前提**（原則1）。users が別シャード／別サービスへ分離しても `schedule_comments` は壊れない。
- **`reply_count` の非正規化**は、シャード分割後に `COUNT(*)` がクロスシャードにならないための保険でもある。
- **想定行数**: 1予定あたり平均 5 コメント・予定が年間 1000万件なら年 5000万行。`schedule_id` 先頭の複合インデックスで単一予定の取得は常に定数時間。**将来の水平分割はスコープ（team/organization）単位**を想定し、予定とコメントを同じ単位に置く。

### 10.4 退会・匿名化（原則4・GDPR Art.17）

- コメント本文は **UGC として残す**が、**投稿者の同定情報は消す**。退会時に `schedule_comments.user_id` を **NULL 化**し、API は `author = null` で返す（FE は「退会したユーザー」表示・AC-28）。
- **本文中の PII**: 自由記述であるため実名・連絡先が混入しうる。**強匿名化（退会 30 日後）のフェーズで、当該ユーザーが書いたコメント本文を匿名化プレースホルダへ置換する**【既定】（F17.2 §13.4 の村コメントと同じ扱い。表示解決の匿名化では本文中の PII は消えないため物理置換が必要）。
- 実装は既存の退会クリーナ（`AFTER_COMMIT` + `REQUIRES_NEW` の前例）にメソッドを1本足す形。

### 10.5 削除された予定のコメントの扱い

| 親の状態 | コメントの扱い |
|---|---|
| **論理削除**（`schedules.deleted_at` 非 NULL） | コメント行は**物理的に残る**（`ON DELETE CASCADE` は物理削除にしか反応しない）。API は 404（AC-20）。**予定を復活させればコメントも復活する**（論理削除の意味を保つ） |
| **物理削除**（稀・システム管理者による強制削除） | `ON DELETE CASCADE` でコメントも消える（同一ドメイン内なので原則2に適合） |
| 親が `CANCELLED` | 読めるが投稿不可（§5.4） |

- **孤児コメントの定期掃除は不要**（親が論理削除されているだけなら復活可能性があるため掃除してはならない）。物理削除は CASCADE が面倒を見る。
- **ストレージ**: コメントは TEXT のみで添付を持たない（§2.3）ため、R2 等の外部ストレージのクリーンアップは発生しない。

### 10.6 その他

- **XSS**: `body` は **プレーンテキストとして保存**し、HTML/Markdown を解釈しない【既定】。FE は必ずテキストとして描画する（`v-html` 禁止）。URL の自動リンク化を将来入れる場合は、**サニタイズ済みの限定的なリンク化のみ**とする。
- **監査**: コメントの削除（特に他者コメントのモデレーション削除）とスレッド開閉は **`AuditEventType` に記録する**【提案】（`SCHEDULE_COMMENT_DELETED_BY_MODERATOR` / `SCHEDULE_COMMENT_THREAD_TOGGLED`）。投稿そのものは件数が多いため監査対象外。
- **後方互換**: 本書の DB 変更は**すべて Expand**（新規テーブル＋列1本追加）であり、既存行・既存クライアントを一切壊さない。既存の出欠コメント機能には**一切触らない**（§0.1）。
