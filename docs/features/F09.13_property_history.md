## 1. 概要

マンション管理組合をはじめとする「物件」を管理する組織が、改修工事・修繕・点検・事故・打合せ等のイベントを **時系列の履歴台帳**として一元管理し、関連文書（議事録・見積書・契約書・写真・報告書）を **1工事 = 1パッケージ** として集約する機能。

本機能は**汎用基盤**として設計されており、F09.14 の重要事項説明書出力機能を上位で支える。マンション以外の業種（保育園の事故台帳・店舗の改装履歴・町内会の修繕履歴・自治会の備品補修記録など）にも転用できるよう、`property_history` という抽象化された名称とモジュール構造を採る。

### 主要ユースケース

| ユースケース | 流れ |
|---|---|
| 改修工事記録 | 理事会で大規模修繕承認 → 業者選定 → 見積書アップロード → 契約書アップロード → 施工 → 完了報告書 → 1パッケージで履歴化 |
| 事故記録 | F07.6 で漏水事故を報告 → 自動で履歴パッケージ生成 → 復旧工事の文書を追加 → クローズ |
| 重要事項説明書作成 | 物件売買時に F09.14 から本台帳を参照し、過去工事・事故履歴を自動引用 |
| 定期点検記録 | F07.6 の `MaintenanceSchedule` から自動生成された点検記録に、報告書を添付 |
| 監査・引継ぎ | 理事改選時に過去5年の履歴を PDF/Excel で出力し新理事に引継ぎ |

### 設計方針

- **2層アーキテクチャ**: 汎用基盤（本F09.13） + 特化レイヤー（F09.14）
- **既存資産の徹底活用**: 文書実体は F05.5 SharedFile、金額は F08.6 BudgetTransaction、事故は F07.6 Incident に委譲。本機能は「集約ルート」として接続のみ担う
- **単一情報源**: 金額は BudgetTransaction、文書は SharedFile、事故は Incident。本機能のテーブルでは ID 参照のみ持ち、データの二重管理を避ける
- **段階導入**: Phase 1 で MVP、Phase 2 で重説書（F09.14）、Phase 3 で Word出力・電子印鑑承認

## 2. スコープ

### 対象ロール

| ロール | 操作可能な範囲 |
|---|---|
| SYSTEM_ADMIN | 全組織・チームの履歴台帳閲覧（監査用、書込不可） |
| ADMIN | パッケージ・業者マスタの CRUD・全件閲覧・エクスポート・他ロールへの閲覧権限委譲 |
| DEPUTY_ADMIN | 権限グループに `PROPERTY_HISTORY_MANAGE` が含まれる場合: パッケージ CRUD・業者マスタ CRUD・エクスポート。`PROPERTY_HISTORY_VIEW` のみの場合: 閲覧・エクスポートのみ（金額マスク版） |
| MEMBER | 公開設定された履歴の閲覧（金額・契約詳細はマスクされる）・自分が報告者のパッケージへのコメント |
| SUPPORTER | 公開設定された履歴の閲覧のみ（金額・業者連絡先はマスク） |
| GUEST | 対象外 |

**重要**: 工事金額・契約金額は機密性が高い（管理組合の総会前に未承認工事金額が漏れると問題化する）ため、`MEMBER`/`SUPPORTER` には金額をマスクして表示する。`DEPUTY_ADMIN` も権限グループの設定により金額マスク有無を切り替える。

### 対象レベル

- [x] 組織 (Organization) — 主たる対象（マンション管理組合）
- [x] チーム (Team) — 副次対象（小規模な物件・施設管理）
- [ ] 個人 (Personal) — 対象外（個人レベルの工事履歴は需要なし）

### 対象テンプレート（推奨モジュールとして自動有効化）

`apartment` テンプレートを選択した組織・チームでは、`property_history` モジュールが自動で推奨有効化される。`community`（町内会）/`company`（企業の社宅管理）/`custom` でもオプション有効化可能。

## 3. DB設計

### テーブル一覧

| テーブル名 | 役割 | 論理削除 |
|---|---|---|
| `vendors` | 業者マスタ（施工業者・点検業者・コンサル等） | あり |
| `property_work_packages` | 集約ルート。1工事/1事故/1点検 = 1レコード | あり |
| `property_work_documents` | パッケージ ↔ SharedFile 中間テーブル（種別タグ付き） | なし（パッケージ削除時カスケード） |
| `property_work_history_views` | 閲覧履歴（監査用） | なし（`retention_days` で TTL 削除） |

### テーブル定義

| `name_kana` | VARCHAR(200) | YES | NULL | フリガナ（検索用） |
| `category` | VARCHAR(30) | YES | NULL | 業者分類（`CONSTRUCTION`/`INSPECTION`/`CONSULTING`/`CLEANING`/`SECURITY`/`OTHER`） |
| `phone` | VARCHAR(30) | YES | NULL | 代表電話 |
| `email` | VARCHAR(255) | YES | NULL | メールアドレス |
| `website` | VARCHAR(500) | YES | NULL | URL |
| `postal_code` | VARCHAR(10) | YES | NULL | 郵便番号 |

**インデックス**
```sql
INDEX idx_vendors_scope (scope_type, scope_id, is_active, name_kana)
UNIQUE KEY uq_vendors_scope_name (scope_type, scope_id, name, deleted_at)
INDEX idx_vendors_category (scope_type, scope_id, category, is_active)
```

**制約**
- `scope_type` CHECK: `IN ('TEAM','ORGANIZATION')`
- `category` CHECK: `IN ('CONSTRUCTION','INSPECTION','CONSULTING','CLEANING','SECURITY','OTHER') OR NULL`
- 1スコープあたり業者数: 上限なし（運用上は数百件想定）
- 業者を論理削除しても、既存パッケージの `vendor_name_snapshot` で表示は維持

| `created_by` | BIGINT UNSIGNED | NO | — | FK → users。ON DELETE RESTRICT |
| `updated_by` | BIGINT UNSIGNED | YES | NULL | FK → users。ON DELETE SET NULL |
| `version` | BIGINT | NO | 0 | 楽観的ロック |
| `created_at` | DATETIME | NO | CURRENT_TIMESTAMP | |
| `updated_at` | DATETIME | NO | CURRENT_TIMESTAMP ON UPDATE | |
| `deleted_at` | DATETIME | YES | NULL | 論理削除 |

**インデックス**
```sql
INDEX idx_pwp_scope_status (scope_type, scope_id, status, deleted_at)
INDEX idx_pwp_scope_type (scope_type, scope_id, work_type, deleted_at)
INDEX idx_pwp_dwelling (dwelling_unit_id) -- 居室別履歴
INDEX idx_pwp_incident (incident_id) -- 事故起点パッケージ検索
INDEX idx_pwp_vendor (vendor_id) -- 業者別履歴
INDEX idx_pwp_planned_dates (scope_type, scope_id, planned_start_date) -- ガントビュー用
INDEX idx_pwp_actual_dates (scope_type, scope_id, actual_end_date) -- 完了履歴ソート
INDEX idx_pwp_disclosable (scope_type, scope_id, is_disclosable, actual_end_date) -- 重説書用
```

**制約**
- `work_type` CHECK: `IN ('RENOVATION','REPAIR','INCIDENT','INSPECTION','DISASTER','MEETING','OTHER')`
- `status` CHECK: `IN ('PLANNED','IN_PROGRESS','COMPLETED','CLOSED','CANCELLED')`
- `visibility` CHECK: `IN ('ADMINS_ONLY','MEMBERS_ONLY','MEMBERS_MASKED','PUBLIC_MASKED')`
- `currency` CHECK: 3文字の大文字（`^[A-Z]{3}$`）
- アプリ層検証: `actual_start_date <= actual_end_date`、`planned_start_date <= planned_end_date`
- アプリ層検証: `work_type IN ('INCIDENT','DISASTER')` の場合 `incident_date IS NOT NULL`
- アプリ層検証: 金額カラムは `>= 0`
- 非正規化カラム（`attachment_count`/`comment_count`）はサービス層で更新

#### `property_work_documents`

パッケージと SharedFile を結ぶ中間テーブル。文書種別タグを保持する。

| カラム名 | 型 | NULL | デフォルト | 説明 |
|---|---|---|---|---|

| `shared_file_id` | BIGINT UNSIGNED | NO | — | FK → shared_files.id。ON DELETE CASCADE |
| `document_kind` | VARCHAR(30) | NO | — | `MINUTES`(議事録)/`QUOTE`(見積書)/`CONTRACT`(契約書)/`REPORT`(報告書)/`PHOTO`(写真)/`DRAWING`(図面)/`INVOICE`(請求書)/`RECEIPT`(領収書)/`OTHER` |
| `display_order` | INT | NO | 0 | 表示順 |
| `note` | VARCHAR(500) | YES | NULL | 補足メモ |
| `created_by` | BIGINT UNSIGNED | NO | — | FK → users。ON DELETE RESTRICT |

**インデックス**
```sql
UNIQUE KEY uq_pwd_pkg_file (package_id, shared_file_id) -- 同じファイルを同パッケージで重複登録不可
```

## 4. API設計

> 📝 **実装注記（2026-05-17）**: 本セクションの `{scope}` 表記は実装の
> `@PathVariable("scopeType")` / `@PathVariable("scopeId")` に対応。
> 組織版 `/api/v1/organizations/{orgId}/property-history/...` および
> `/api/v1/organizations/{orgId}/vendors/...` は
> `PropertyWorkPackageController` (11 件) / `VendorController` (4 件) で実装済。
> API drift baseline は `{scope}` の突合精度が低いため「実装あり・設計なし」として
> 誤検出するが、本設計書の `{scope}` 表記が正であり実装と設計に齟齬は無い。

## 5. ビジネスロジック

### 5.1 パッケージ作成フロー

1. ADMIN が「新規工事」ボタンをクリック
2. 必須項目: `workType`, `title`, `scope`
3. 業者選択: `VendorPicker` でオートコンプリート、新規業者の場合はモーダル内で即作成可能
4. 文書添付: F05.5 のファイル選択モーダルから既存ファイルを紐付け、または新規アップロード
5. 金額: F08.6 BudgetTransaction を選択して連携、または手入力
6. 保存時に F04.1 TimelinePostEntity に自動投稿（status=PUBLISHED, scopeType, scopeId, contentType=PROPERTY_WORK_PACKAGE）

### 5.2 F07.6 Incident との連携

- F07.6 で `IncidentEntity` が `RESOLVED` → `CONFIRMED` に遷移する際、`IncidentService.confirmIncident()` から `PropertyWorkPackageEventListener.onIncidentConfirmed()` がイベント駆動で発火
- 自動で `PropertyWorkPackageEntity` を `workType=INCIDENT`, `incidentId={id}`, `incidentDate=incident.reportedAt`, `incidentNarrative=incident.summary` で作成
- 既に手動でパッケージが作成済みの場合（`incident_id` が一致するレコードあり）はスキップ
- 双方向参照: パッケージ詳細から Incident 詳細へリンク、Incident 詳細から関連パッケージへリンク

### 5.3 F08.6 BudgetTransaction との連携

- パッケージに `budget_transaction_id` を設定すると、F08.6 で該当取引の `sourceType='WORK_PACKAGE'`, `sourceId={packageId}` が自動セット
- BudgetTransaction の金額が変更された場合、パッケージの金額表示も連動（金額の単一情報源は BudgetTransaction）
- 1工事 = 複数支払い（着手金・中間金・完了金）の場合は複数 BudgetTransaction を `sourceId={packageId}` で紐付け、合計金額をパッケージの `actualAmount` として集計表示

### 5.4 F04.1 TimelinePost との連携

- 新規作成時: 自動投稿（テキスト本文に「【物件履歴】タイトル / 工事種別 / 業者名」を整形、本文末尾にパッケージへのディープリンクを埋め込む）。`TimelinePostEntity` に `contentType` カラムは無いため、本機能専用の enum 拡張は行わず、純粋なテキスト投稿として記録する
- 状態遷移時（`PLANNED → IN_PROGRESS`, `IN_PROGRESS → COMPLETED`, etc.）: 投稿を編集（`TimelinePostEditEntity` に履歴記録）
- 完了時: 完了通知投稿
- 添付ファイル追加時: 投稿のコメントとして追記
- TimelinePost の `scopeType`/`scopeId` はパッケージと一致させる。`status` は WorkPackage の `visibility` から導出（ADMINS_ONLY → DRAFT、それ以外 → PUBLISHED）。これにより既存タイムラインの可視性ガード（F00 ContentVisibilityResolver）と整合

### 5.5 マスキング処理（金額・連絡先）

`PropertyWorkPackageMaskingService` が `visibility` と現在のユーザーロールから判定:

| visibility | ADMIN | DEPUTY_ADMIN(MANAGE) | DEPUTY_ADMIN(VIEW) | MEMBER | SUPPORTER |
|---|---|---|---|---|---|
| ADMINS_ONLY | 全表示 | 全表示 | 金額マスク | 不可視 | 不可視 |
| MEMBERS_ONLY | 全表示 | 全表示 | 金額マスク | 全表示 | 不可視 |
| MEMBERS_MASKED | 全表示 | 全表示 | 金額マスク | 金額マスク | 不可視 |
| PUBLIC_MASKED | 全表示 | 全表示 | 金額マスク | 金額マスク | 金額マスク |

マスク対象: `estimatedAmount`/`contractAmount`/`actualAmount`/`vendor.phone`/`vendor.email`/`vendor.address`/`vendor.contactPerson`/`budgetTransaction.amount`。
マスク後は UI で「●●●円」と表示。

> **⚠️ 可視性の正準対応と移行ステータス注記（2026-06-05・F00 W0 設計統一）**:
> 本機能の feature-local enum 値 `ADMINS_ONLY`/`MEMBERS_ONLY`（+ マスキング派生 `MEMBERS_MASKED`/`PUBLIC_MASKED`）は **本機能固有のため据え置く**。
> ただし可視レベルとしては、`MEMBERS_ONLY`（MEMBER 全表示・**SUPPORTER 不可視**）が F00 正準ラダーの **`MEMBERS_AND_ABOVE`**（応援者除外）に、`ADMINS_ONLY` が **`ADMINS_AND_ABOVE`** に対応する。
> property は CHECK 制約で visibility 値を列挙しているため、F00 §5.1.6 で「**破壊的 DB 値移行が要る 2 系統**」の 1 系統（もう 1 系統は announcement）と位置づけられている。enum 値・CHECK 制約・マスキング派生をどう正準ラダーへ寄せるか（あるいは派生値を CUSTOM 扱いにするか）は後続 wave で別途検討する。本設計書時点では現行 enum 値のまま稼働する。

### 5.6 エクスポート（PDF / Excel）

#### PDF (Phase 1)
- 既存 `PdfGeneratorService` + `templates/pdf/property-work-history.html`
- 1パッケージ単独 PDF または 一覧 PDF（履歴台帳形式）
- マスキング適用後のデータでレンダリング

#### Excel (Phase 1)
- 新規 `ExcelGeneratorService`（Apache POI 5.2.x SXSSFWorkbook ストリーミング）
- ファイル名: `{yyyyMMdd}_物件履歴台帳_{組織名}.xlsx`
- シート構成:
  - シート1: サマリ（件数集計・年度別グラフ用データ）
  - シート2: 履歴一覧（フィルタ・ソート可能、ヘッダー固定）
  - シート3: 業者別集計
  - シート4: カテゴリ別集計
- 日本語フォント: NotoSansJP（`ExcelFontConfig` で統一）
- 金額カラムは `#,##0` 書式

#### 頻度制限
- 1ユーザー 1分10回まで（F10.3 audit_logs に記録）
- 大量データのレコード数閾値: 同期処理は 5,000 件まで（PDF）、20,000 件まで（Excel SXSSF ストリーミング）。これを超える運用が発生した時点で非同期ジョブ基盤導入を別軍議で検討（Phase 1 範囲外）

### 5.7 添付ファイル上限

- 1パッケージあたり: 最大50ファイル
- 1ファイルサイズ: F13 ストレージクォータ + F05.5 制限に従う
- 拡張子制限: F05.5 の許可リストに従う（PDF/Word/Excel/画像のみ）
- ストレージ消費は scope の F13 クォータに加算（既存基盤）

### 5.8 削除ポリシー

- 論理削除のみ（`deleted_at` 設定）
- 削除されたパッケージは ADMIN のみ復元可能（30日以内）
- 30日経過後の物理削除は F12.3 GDPR バッチに委譲
- 関連する `property_work_documents` は CASCADE 削除（紐付けのみ、SharedFile 本体は残る）
- 関連する F08.6 BudgetTransaction は **削除しない**（会計記録は別ライフサイクル）

## 6. セキュリティ考慮事項

### 6.1 アクセス制御

- 全 API は `@RequiresScopeRole` で保護
- パッケージごとの `visibility` でロール × アクション × 金額閲覧可否を判定（F00 ContentVisibilityResolver パターンに準拠）
- `PropertyWorkPackageVisibilityResolver` を新規作成し、`AbstractContentVisibilityResolver<PropertyWorkPackageView, ?>` を実装

### 6.2 データ機密性

- **工事金額**: マンション管理組合の総会前に未承認工事金額が漏洩すると組合員間トラブルに発展。`MEMBERS_MASKED` をデフォルトとし、必要に応じて `MEMBERS_ONLY` に開放
- **業者連絡先**: 個人情報（担当者氏名・電話・メール）。MEMBER には常にマスク
- **事故詳細**: 事故いきさつは F09.14 重説書で利用するため、保管は厳格。ADMIN のみ全文閲覧、MEMBER は要約のみ
- **居住者情報**: F09.1 ResidentRegistry と紐づく場合、ResidentRegistry のアクセス制御を継承

### 6.3 SQL インジェクション対策

- すべてのクエリは Spring Data JPA + パラメータバインドで実装。動的検索は `Specification<T>` 使用
- フィルタの `tags` JSON 検索は MySQL の `JSON_CONTAINS` をパラメータ化して実行

### 6.4 ファイルアップロード

- F05.5 SharedFile 経由のため、既存のウイルススキャン・拡張子チェック・サイズ制限を継承
- 直接アップロード経路は持たない（紐付けのみ）

### 6.5 監査ログ

- すべての CRUD 操作を `F10.3 audit_logs` に記録: `eventType=PROPERTY_HISTORY_*`, `actorUserId`, `targetType=property_work_packages`, `targetId`, `action=CREATE/UPDATE/DELETE/VIEW/EXPORT/DOWNLOAD`
- 金額閲覧・エクスポートは `property_work_history_views` でも追跡（重要事項説明書作成のために誰が何を見たかを記録）
- 監査ログ保持期間: F10.3 のデフォルト（180日）

### 6.6 入力バリデーション

- `title`: 1-200 文字、HTML エスケープ
- `description`: 0-10,000 文字、Markdown のみ許可（XSS は既存 `common/security/HtmlSanitizer.java` で処理）
- `tags`: 配列上限20件、各要素 1-30 文字
- `incident_narrative`: 0-5,000 文字、Markdown許可
- 金額: `0 <= amount <= 999_999_999_999`（約1兆円上限）
- 日付: ISO 8601 形式、未来日チェック（`incident_date <= today`）

### 6.7 レート制限

- パッケージ作成: 1ユーザー 1分10回
- エクスポート: 1ユーザー 1分10回
- 検索 API: 1ユーザー 1分100回
- 既存 `RateLimitingFilter` を流用

### 6.8 CSRF / XSS

- 既存 SecurityConfig の CSRF トークン制御に従う
- レスポンスは UTF-8 JSON、`X-Content-Type-Options: nosniff` 既定適用

### 6.9 個人情報保護法 / GDPR

- 業者の `representative`/`contact_person` は個人情報。F12.3 GDPR 削除リクエスト対象に含める（業者削除時に snapshot もマスキング）
- 居住者の住所・電話は F09.1 ResidentRegistry 側で管理し、本機能では参照のみ
