## 1. 概要

個人ダッシュボードには **お知らせ・TODO期限・メンション・チーム/組織の新着・確認必須通知** が複数の別々のウィジェットに散在しており、「これは後で対応する」と退避できる一元的な受け皿が存在しない。本機能は、これら全ストリームを **1 画面の「通知インボックス」** に集約し、各通知を **スヌーズ（時間で受信箱へ自動復帰）／アーカイブ（保管庫へ退避）／軽量ラベル付与** で仕分けできるようにする。緊急度（priority）と種類（sourceType）による分類は **手作業ゼロで自動** に行われる。

本機能のユーザーは ADHD 傾向を含み、**入力摩擦ゼロ・必須項目最小・「自動で整理される」体験** を必須要件とする（`user_adhd_tendency` 方針）。したがって「全件を手で仕分ける」運用は採らず、自動グルーピングを主・手動ラベルを任意の補助とする。

### 1.1 背景

- 現状、通知系ウィジェット（`WidgetNotices` / `WidgetPersonalTodo` / `WidgetTodoCountdown` / `WidgetUnreadThreads` / `WidgetTeamAnnouncements` / `WidgetOrgAnnouncements`）はダッシュボード上に並列配置され、横断的な「未対応の山」を一覧・退避する手段がない。
- `notifications` テーブルには `snoozed_until` カラムが既に存在するが、**フロントに UI が露出しておらず、かつフロント/バックエンドの DTO が不整合で現状疎通していない**（§後述・[03_business_logic.md](./03_business_logic.md) §6）。スヌーズ機能の「正しい開通」も本機能のスコープに含む。
- 「フォルダで仕分けたい」要望は F15.2/F15.3 のスコープフォルダ（チーム/組織の分類）と概念が近いが、対象が異なる（あちらは所属スコープの分類、本機能は通知 1 件単位の仕分け）。

### 1.2 目的 / コンセプト

| 観点 | 内容 |
|------|------|
| 集約 | 5 ソース（通知 / お知らせ / メンション / 確認必須 / TODO 期限）を統一 DTO `InboxItem` に正規化し 1 画面に集約 |
| 自動分類 | 緊急度（priority）・種類（sourceType）でクエリ時に自動グルーピング。**永続テーブルを持たない（導出のみ）** |
| あとで見る | スヌーズ（`snoozed_until > now` の間だけ受信箱から隠れ、時刻到来で自動復帰）＋アーカイブ（保管庫へ退避、時間復帰なし） |
| 軽量ラベル | 「要件別」の任意ラベルを 1 タップ付与。未分類でも破綻しない |
| 非侵襲 | 発生源テーブルを一切変更しない。triage 状態は per-user オーバーレイ表のみに保持（採用アーキ §6） |
| 摩擦ゼロ | スヌーズはプリセット選択のみ（日時入力なし）。デフォルト（未読・未アーカイブ・非スヌーズ）は行を作らない遅延生成 |

### 1.3 UI 概観（テキスト図）

```
┌────────────────────────────────────────────────────────────┐
│ 受信箱                                                         │
│ [ 受信箱 12 ] [ スヌーズ中 3 ] [ 保管庫 ]      ← 状態タブ(主軸) │
├────────────────────────────────────────────────────────────┤
│ 緊急度: (●緊急2) (●重要5) (通常)   種類: (お知らせ) (TODO) (…) │ ← サブフィルタ(チップ)
│ ラベル: #要返信 #経理 #あとで読む                              │
├────────────────────────────────────────────────────────────┤
│ ● [緊急] TODO「決算提出」期限切れ      🕒 ⌛ 🏷  ← 1タップ操作   │
│ ● [重要] お知らせ「総会のご案内」(組織) 🕒 ⌛ 🏷               │
│   [通常] メンション @you がコメント     🕒 ⌛ 🏷               │
│   …                                                         │
└────────────────────────────────────────────────────────────┘
  🕒=スヌーズ(プリセット)  ⌛=アーカイブ  🏷=ラベル付与
```

## 2. スコープ

### 2.1 対象ロール

通知インボックスは **ログインユーザー本人の通知のみ** を扱う個人機能であり、ロールによる機能差はない（自分宛て通知の集約・仕分けは全ロール共通）。表示される通知の内容自体は各ソースの可視性ルール（F02.2.1 / 各ドメインの認可）に従う。

| ロール | インボックス利用 | 備考 |
|--------|:--------------:|------|
| SYSTEM_ADMIN | ✅ 本人宛て通知 | 全ユーザー通知の閲覧は不可（あくまで本人分） |
| ADMIN | ✅ | |
| DEPUTY_ADMIN | ✅ | |
| MEMBER | ✅ | |
| SUPPORTER | ✅ | サポーター可視範囲の通知のみ流入 |
| GUEST / 未ログイン | ❌ | ログイン必須 |

### 2.2 対象レベル

- [ ] 組織 (Organization)
- [ ] チーム (Team)
- [x] **個人 (Personal)** — 本人の全スコープ横断通知を個人の受信箱に集約

### 2.3 スコープ外

| 項目 | 理由・参照先 |
|------|------------|
| 通知の **発生・配信** ロジック | 各ソースドメイン（F04.3 通知 / F04.9 確認通知 / announcement / mention / todo）が担当。本機能は読み取り集約と triage のみ |
| 通知の **既読化ロジックそのもの** | 各ソースの既読 API を流用（§後述）。インボックスは既読書き込みを新設しない |
| プッシュ配信チャネル（PWA Push / メール等） | F04.3 が担当 |
| チーム/組織の **スコープ分類フォルダ** | F15.2/F15.3 が担当（対象が異なる） |
| スコープ別「要対応」抽出ウィジェット | F22.1（§7 で棲み分けを定義） |
| 通知の長期保管・アーカイブの自動エクスポート | 将来 Phase 4（GDPR 連携、§6 ロードマップ） |

### 2.4 関連機能との境界

| 機能 | 関係 |
|------|------|
| F02.2 マイダッシュボード | **母体**。インボックスは通知系ウィジェットの「受け皿」。`WidgetInbox` を新設し既存通知ウィジェットの遷移先を `/inbox` に集約（[F02.2 追記](../F02.2_dashboard.md)） |

## 4. 採用アーキテクチャ — A 案 / B 案 比較（**採用＝B 案**）

通知インボックスの実装方式として 2 案を比較検討した。**採用は B 案（仮想インボックス＋オーバーレイ表）**。

### 4.1 概要

| | **A 案：実体化（notifications 拡張）** | **B 案：仮想インボックス（採用）** |
|---|---|---|
| 集約方式 | 全ソースが `notifications` 行を生成し、それを「背骨」とする | 発生源は不変。`GET /api/v1/inbox` が読み取り時に各ソースを集約 |
| triage 状態の保持 | `notifications` 行に `archived_at` 等を追加 | per-user オーバーレイ表 `inbox_item_states` のみに保持 |
| 未配線ソース | メンション・お知らせは notifications 行を作っておらず**配線が必要** | 配線不要（既存リポジトリを読むだけ） |

### 4.2 比較表

| 観点 | A 案 | B 案（採用） |
|------|------|------|
| 既存機能への影響 | △ 発生源への配線が必要（回帰リスク） | ◎ 発生源不可侵・回帰リスクほぼゼロ |
| お知らせの集約 | ✗ 購読者×フィードで notifications 行が**爆発**（fan-out スケール問題） | ◎ `announcement_feeds` を読み取り集約（行を増やさない） |
| 既読/状態の整合 | △ confirmable は recipient 表と二重持ち | ○ ソース既読はソースのまま、triage のみオーバーレイ |
| スヌーズ自動復帰 | △ 復帰バッチが必要 | ◎ `snoozed_until > now` を集約時判定でバッチ不要 |
| cleanup バッチ衝突 | ✗ `NotificationCleanupBatchService`（既読90日物理削除）が**アーカイブを誤削除**するリスク | ◎ notifications 行を触らないため衝突しない |
| 実装着手コスト | △ 発生源配線が前提 | ◎ `DashboardService` の集約パターン拡張＋オーバーレイ表の写経 |
| 読み取り性能 | ◎ 単一表クエリで高速 | △ 複数ソース集約で N+1/ページングに配慮要（§後述で対策） |
| ページング | ◎ 単一表で容易 | △ 複数ソースマージで真のカーソル不可（ハードリミット運用） |

### 4.3 採用判断

**B 案を採用する。** 決め手は ①発生源不可侵による回帰リスク最小、②お知らせ fan-out の行爆発と cleanup バッチ誤削除という A 案固有の重大リスクの回避、③スヌーズ自動復帰のバッチ不要、④「整理不要なものは行を作らない」遅延生成が ADHD 要件と合致、の 4 点。B 案の弱点（読み取り集約の N+1・ページング難）は、(a) オーバーレイ/ラベルを `IN` 句 1 クエリでまとめ取り、(b) ソース毎ハードリミット、(c)「インボックス＝直近の仕分け場」と割り切るオフセットページング、で許容範囲に抑える（[03_business_logic.md](./03_business_logic.md) §4・[04_security_operations.md](./04_security_operations.md) §5）。

> **A 案を将来採る余地**: 通知量が極端に増えマテリアライズドビューが必要になった場合、オーバーレイ表（B 案）をそのまま「実体化インボックス」のキャッシュ表に昇格させる移行が可能（オーバーレイ表に title/excerpt 等のスナップショット列を足すだけ）。B 案は A 案への上位互換的な移行パスを持つ。

## 7. F22.1「要対応」ウィジェットとの棲み分け（重複解消）

F22.1（横スワイプダッシュボード）は、チーム/組織パネルに **「要対応」ウィジェット**（回覧板・アンケート・出席確認をスコープ単位で集約）を持つ。本機能（通知インボックス）と目的が一部重なるため、以下のとおり**明確に棲み分ける**。

| | F04.11 通知インボックス | F22.1 「要対応」ウィジェット |
|---|---|---|
| 主体 | **個人**（本人宛て全通知の受け皿） | **スコープ**（特定チーム/組織の未対応アクション） |
| 範囲 | 5 ソース横断・全スコープ | 回覧/アンケート/出席確認に限定・単一スコープ |
| 目的 | 「後で見る」退避・仕分け（スヌーズ/アーカイブ/ラベル） | 「今このスコープで対応すべきもの」の即時把握 |
| 設置 | 専用ページ `/inbox` ＋ `WidgetInbox` | F22.1 チーム/組織パネル内ウィジェット |

両者は競合せず補完関係にある。**重複実装を避けるため**、F22.1「要対応」の集計ロジックと本機能のソースアダプタ（confirmable / survey 等）は将来的に共通のクエリ層を共有する余地を残す（Phase 3 以降の整理対象として [04_security_operations.md](./04_security_operations.md) §8 に記録）。本フェーズでは両者を独立実装とし、データ重複は発生しない（インボックスは triage オーバーレイのみ、要対応は読み取り集計のみ）。
