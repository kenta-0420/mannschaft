## Z1–Z8と五類型

| AC | 正常・空/0/null・境界・途中失敗・認可/性能への対応 | 残る検証・制約 |
|---|---|---|
| Z1 暗号化の実体 | ZIP実bytesの全entryでAES-256/AE-2/CRC 0、正password復号、無・誤password拒否、改ざん拒否を検査。空byte、Unicode、JSON文字列null・0・空配列を含む。Java nullは従来どおり失敗させ、空文字へ変換しない | 別実装による製品ZIP復号は最終実機工程 |
| Z2 通常/fallback・資源 | 小さい同一mapで通常/fallback両writerの暗号化を確認。ByteArrayOutputStreamの既存メモリ経路を維持し、平文tempは作らない | 500MB実体生成・負荷測定は未実施。既存fallbackは同じmapを再出力するため縮小不成立を今回解消したとはしない |
| Z3 秘密保持 | 実DB ITで保存bcryptと、実outboxの暗号化payloadから得たpasswordと、実アップロードZIPの復号結果を対応確認。APIにpasswordを追加せず、失敗ログは原因classのみ。writer入力char[]はfinally消去 | 不変Stringやライブラリ内部cloneを含む全heap消去は保証しない |
| Z4 完了/失敗の整合 | 実collector・実MySQL・実outboxで、COMPLETEDとREADYの同一TX、READY失敗時のrollback後FAILED永続化、アップロード済み対象objectの削除を検証。失敗通知も失敗する場合にFAILEDが維持される追加green境界を確認 | 外部storageは境界stub。実外部配送は行わない |
| Z5 配送再試行 | 既存processOne 3件とbackoff 9件が成功。生成処理は既存暗号化outboxへ一度投入し、配送処理は既存payloadを再送する構成を維持 | 実メール配送の再送は未実施。outboxの30日cleanup呼出元は今回確認・修正したとしない |
| Z6 旧ZIP・24時間 | requestExport/getDownloadUrlの処理本体を保持。既存の直近COMPLETED拒否、状態・期限切れHTTP対応を含むService/Controller試験が成功。旧COMPLETEDの再暗号化・一括失効・再生成を追加しない | 厳密24時間の両端、既存plain ZIPの実Downloadはこの局所runでは未実施 |
| Z7 本人scope | Controller既存7件の正常・制限・prefetch失敗・状態エラーが成功。認証・本人取得経路は変更しない | 匿名・他actorの実BE拒否は最終実機/CIへ対応し、この7件だけで合格とはしない |
| Z8 案内・互換性 | 既存6言語descriptionだけを更新しJSON parseと他key/value不変を確認。AES対応アプリ、Windows標準非対応、macOS標準非保証、旧ZIP形式/期限保持をREADME/F12.3にも明記 | 実UI表示・独立展開・住民探索は最終統合後 |

## Redからの対応とテスト境界

修正前commit `37e69a29a9949b1dbd2cbbb8d212d07e8f546ad9` では、暗号header不成立、無passwordで本文読取可能、誤passwordで本文読取可能、実outbox故障後にFAILEDではなくPENDINGへ戻る、の4件が実assertionでredになった。同runの正常IT 1件は試験SQL列名の誤りであり、製品のredへ数えない。前phaseのSpring構成不一致も環境準備失敗として分離した。

ZIP単体試験のrepo/collector/outbox mockはbyte検査用harnessに限定する。最終状態とpassword整合は、実DataExportService・PersonalDataCollector・MySQL・EmailOutboxServiceImplを使うITで担保する。storageのみ外部境界stub、job-poolは完了観測用に同期化し、実EncryptionServiceへの故障注入spyでoutbox失敗を再現した。試験外側のTXには依存しない。

## 呼出元とTX境界

唯一の製品呼出元GdprControllerは非TXで、requestExportのcommit後に既存job-poolの非同期処理を呼ぶ。処理の正常完了とREADY投入を局所REQUIRES_NEWでまとめ、rollback後に別TXでFAILEDを保存し、さらに独立TXで失敗通知を試みる。既存AccountPurgeServiceと同じTransactionTemplateの慣習を用い、新しいイベント基盤やexecutorは追加しない。
