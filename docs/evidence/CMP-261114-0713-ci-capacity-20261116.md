# CMP-261114-0713 Backend CI 容量調整の証拠

## 今回の設定変更

通常profileの設定test-step 95分/job 110分を維持する。この95分設定を実適用した通常profileの完走は未検証である。今回の変更はmigration込みprofileだけで、test-step上限を105分から110分へ延長し、job上限120分を維持する。非test時間の目安は通常profileで15分、full profileで10分。いずれも完走や終了artifact回収を保証しない。

6 shard、2 fork、forkEvery 180、profile選別、テスト重み、必須gateは変更しない。通常profileの95分を今回のfull-profile結果から不足または合格と推論しない。今回の全CIはfull profileにおける機能回帰確認であり、normal95の再確認ではない。

## PR 4529 baseline（HEAD `49769226182ca8441769d0a68fc561acca15cf6c`）

[Backend CI run 43739112159](https://github.com/kenta-0420/mannschaft/actions/runs/43739112159) は6 shardでmigrationを含むfull profile（`excludeMigrationTests=false`、test/job timeout 105/120分）を実行した。shard 0/2/3/5は成功、shard 1は実際のguard失敗、shard 4は105分timeout。したがってこのrunは全greenではない。

shard 4の保存済みraw progressを再集計すると、`:test` の1,408 start/endイベントは全て対応し、endは全件SUCCESSだった。nested class名を外側のtop-levelクラスへまとめると537件で、未開始・未終端クラスは0件。`AuthRegisterPrivacyPolicyTest` のstatic nested 2件もtop-levelクラス1件として数える。最後のクラス `VillageSerendipityServiceTest` は18:59:52.418ZにSUCCESS、timeoutは18:59:52.944Zで、差は0.526秒。クラス単位の処理後にGradleの最終集計・終了処理を完了できず、test stepの正常終端を確認できなかった。設定値105分は使い切られた。元artifactのhashと再集計の根拠はローカル証跡に保全し、原本を保持した。

shard 4の診断artifactでは `completed=false`、`cacheHit=false`、`testStepOutcome=failure`。`testStepExitCode`、`commandExitCode`、`shellExitCode`、`finishedAt` はnullで、最終集計も得られない。これは正常終端を得られなかったという観測限界であり、成功とは扱わない。別にartifactの上限値欄もnullで、finalize stepへenvが渡らないため、適用上限は実Run tests stepの設定とログで確認する。今回その計測実装は変更しない。artifactの回収保証もない。

全537件SUCCESS・未終端0件と最後のクラス終了直後のtimeoutを踏まえ、full-profile test-stepに5分の有限余白を足して110分とする。jobは120分のままなのでtest step後の余白は10分。advisorのrun観測ではjobのtest以外に約2分30秒を要しているが、回収・後処理が常にその範囲に収まる保証はない。新しいfull110設定の正常終端は、次のfixed-head全CIで未検証項目として確認する。

shard 1はtimeoutではなく、`TaskListCmpIdDuplicateGuardTest` がCMP-ID `CMP-261115-2145` の状態セル `実装中` にpriorityが無いとして失敗した。後続main `4f01ee8ba98c9b591a8e3e2308b2fa7d9e546240` では同じ行に `P3` が付与されたことを別事実として記録する。統合時は最新mainの修正を追従し、このCIの失敗をtimeoutやparser不具合とは扱わない。

## 先行する通常profile設定の根拠

[run 43720702097 / attempt 1](https://github.com/kenta-0420/mannschaft/actions/runs/43720702097/attempts/1)、source `2f78df04cc9afb69484769e234e5ea938382d323` では旧85分上限が使い切られた。shard 4は割当523クラス中514開始、513 SUCCESS、失敗0で終了し、未終端・未開始の計10クラスの歴史重み合計は419.644秒だった。この観測をもとに通常profileをtest85→95分、job100→110分へ設定した。

通常profileの95分容量は、normal profileが実適用されたrunで確認する。migration込み105/120分枝または今回のfull profileの結果で代用しない。`BlogPostServiceTest.GetBySlug` のstub未使用によるfixture失敗は、この先行runの独立した失敗であり、製品assertionの失敗とは区別する。

## 検証範囲

- workflowのYAML parse、旧新構造比較、`git diff --check` を実施する。
- workflowの実行、Gradleテスト、CI再実行は行わない。full110の実完走確認は次のfixed-head全CIで行う。
- workflowのmigration-sensitive判定、profile選別、shard matrix、weights、fork設定、必須gateは変更しない。

[個別4クラスの重み追加](CMP-261114-0713-shard-weights-delta-20261115.md)の3218行prefixと4件deltaを維持する。失敗runから全表重みを再生成せず、正常nightly全6freshというupdater条件も変更しない。
