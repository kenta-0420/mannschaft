## 実装とACの対応

| AC | 実装境界・検証対象 |
| --- | --- |
| AC0 | ErrorReportIsolationGuardが実プール接続のRRを起動時検査。業務処理のないopenapi-gen専用H2だけ除外 |
| AC1 / AC1h | IngestService NOT_SUPPORTED → IngestTx REQUIRED。非IGNORED最小idのLIMIT1 FOR UPDATE、空hash gap lock、rollback後最大5試行 |
| AC2 / AC3 | FE/BACKEND/HEALTHの再発・SLA・人数・昇格・通知/AIの差をIngestTxで維持 |
| AC4 | 実Async/Health入口を同じTX境界へ接続。bufferはcomputeとkeyごとのremove |
| AC5 | 最優先commit trackerを各試行の業務callback前に登録。save/flush hookは実境界。commit後失敗は再試行しない |
| AC7 / AC7h | ManagementService NOT_SUPPORTED → ManagementTx REQUIRED。hash全行id順→対象行lock、bulk hash/id順、rollback後最大3試行、013/409・014/503 |
| AC8 | Entity DynamicUpdateと共通管理lockをstatus/Timeline工程・担当/Health復旧へ適用。HealthのIGNORED保持 |
| AC9 | 既存Securityフィルタ・SYSTEM_ADMIN認可境界を維持 |

既存HTTP契約のstrict contention assertに公開JSON `$.error.code = ERROR_REPORT_014` を追加した。
通知因果試験は公開updateStatusを通し、実lock hookからbeforeCommit失敗を登録する。
実TX内のRESOLVED到達後rollback→DB NEW/通知0と、外側TXだけrollback→独立管理commit/通知1を別々に検証する。
純UTは分割した実業務Beanへ接続し、既存の外部mockと期待値を維持する。
Async小contextは実no-op Hook・実ingest境界・実H2 TX managerを読み込み、外部Repository/Redis/集約bufferだけを従来のstub境界として扱う。

FEのHIGH以上の新規/再発だけが `ErrorReportAiAnalysisRequestedEvent(reportId)` を発行する。
既存AI DispatcherがAFTER_COMMITで受信し、既存の機能有効性・予算判定を経て別BeanのAsyncRunnerへ渡す。
commit済みの受信時にsynchronizationを再登録しない。Runner側の重複排除・例外処理・非同期性は変更しない。
AC3の既存実ITはFE新規/再発を各1回、BE/HEALTHを0回、AC5はrollback時0回で照合する。
TestSupportも新eventの実commitだけを観測し、FE実ITではevent数1/2と実分析DB行数1/2・外部provider呼出数1/2を対応付ける。
既存Dispatcherの予算内/予算超過/disabledの3条件を、従来入口とcommit済みevent入口の双方へparameterizedで適用する。
event入口はsynchronization active下でも再登録0で、予算内だけrunner1、予算超過/disabledはrunner0を検証する。
