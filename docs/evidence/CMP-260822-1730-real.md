# 実機E2E CMP-260822-1730（実装PR #4248 チームTZ対応・日跨ぎ予約枠の仮予約失効バッチ）— 合格（再実機で欠陥解消）

実施 2026-11-03（1回目）と 2026-11-04（再実機）。BE 8081（WSL の Linux JVM）。BE の再起動を挟んで実施した。画面の変更は無く（バッチが対象）、UI の E2E は対象外とした。資格情報は本書に記載しない。

## 前提
- DB の時刻は UTC 格納（DATETIME は UTC、TIME は壁時計から -9h、DATE は不変）。SQL のシードはこの規則で入れた。
- チームのタイムゾーン: 予約チーム A は Pacific/Auckland（+13）、予約チーム B は America/New_York。サーバー既定の JST と異なるゾーンで、誤抽出を弁別した。ポリシー: A は24時間、B は168時間、承認モードは MANUAL。

## 1回目（2026-11-03）受入条件の実測（予約8件）

失効は各1回で、枠の booked_count は有効予約数と常に一致した（不一致 0 件）。通知 RESERVATION_PENDING_EXPIRED は失効した3件に各1通のみ。

## 再起動を挟む確認
予約・枠を仕込んだ状態で BE を停止し、停止中に失効対象にして再起動した。再起動後の最初のバッチで正しく処理され、scan_state の周回は 1 周のみ、retry の主キーは再起動をまたいで保持された。二重失効・二重通知は無い。

## 承認と失効の競合
- 承認が先: 12件を失効バッチの直前〜直後に confirm すると、全て 200 CONFIRMED で枠は不変、バッチは 0 行。
- バッチが先: 12件は先に失効され、後から confirm すると 409 RESERVATION_006、CANCELLED のまま・booked_count 0・通知各1通。
- 真の同時（同一ミリ秒）の取り合いは、5分周期のバッチのため狙って再現できず未実施。統合テスト（ConcurrencyIT）が担保する。

## 実行計画（B18）
実バッチの SQL を general_log で採取し、実 DB（595行）で PRIMARY の range と eq_ref による索引利用を確認した。使い捨て DB（50万行）では status に先頭を持つ索引が無く、PRIMARY を全走査（336ms）した。これは欠陥ではなく性能所見として記録した。使い捨て DB は削除済み。

## 1回目の欠陥候補 D-1730-1 と再実機（PR #4275）
- 論理削除済みの枠に紐づく PENDING 予約（開発 DB の既存の残骸 3 件）が、永続 retry に残って毎周期 ERROR を出し続け、失効もされない。
- PR #4275 を反映した再実機で、BE 起動直後の初回バッチで残骸 3 件が CANCELLED/SYSTEM に遷移し、retry は空になり、以降の周期で ERROR は出ない。通知は各1通。
- 制御データ: 論理削除枠で経過時間条件を満たす 2 件は 1 周期で失効、経過前の 1 件は PENDING のまま retry にも載らない、枠が物理欠損の 1 件は従来どおり ERROR と retry 保持（2周期連続）。次周期で再処理なし・二重通知なし。欠損の予約を削除すると retry が空に戻る。

## 合否
合格。D-1730-1 は #4275 で解消。未実施は、真の同時競合（統合テストが担保）。
