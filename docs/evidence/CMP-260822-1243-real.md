# 実機E2E CMP-260822-1243（実装PR #4251 退会時の個人設定の消去）— 合格（再実機）

実施 2026-11-03（1回目）と 2026-11-04（再実機）。系統は、退会 API → 猶予 → 時刻を進める → 夜間バッチ `gdpr-account-purge-daily` を system-admin API で直接起動。資格情報は本書に記載しない。

## 1回目（2026-11-03、不合格 → 欠陥判明）
- 退会対象と対照（他人・退会しない）を用意し、各ユーザーに個人設定7表（shift の既定希望・parking のウォッチ・reflection のリマインダー・advertising の広告設定・property の閲覧履歴・village の pin とニックネーム）を投入した。
- 強匿名化の 1 回目は失敗した。`AccountPurgeService.purgeUser` が `refresh_tokens` の FK 違反でトランザクション全体をロールバックし、対象1・成功0・失敗1。原因は Phase 1 が「失効していない」トークンだけを削除し、退会受付で失効済みになったトークンが残って最後のユーザー削除が FK 違反になること（欠陥 D-1243-1）。
- 失効済みトークンを検証用に手で消すと完走し、7表は村 pin・ニックネームを含め 0 件、対照は残存。ただし完了条件を実環境のユーザーで満たせないため、この時点の戦役の判定は不合格とした。

## 再実機（2026-11-04、D-1243-1 を PR #4272 の V256 で解消した main）
BE を再ビルドして WSL ネイティブ jar で再起動し、Flyway が V256 を適用した。回避の SQL は使っていない。

### 手順
- 退会対象2名（1名は画面から、1名は API から退会）、対照1名（ログイン中・退会しない）。強匿名化の起動条件のため、退会者2名の `users.deleted_at` だけを UTC で31日前へ更新した。refresh_tokens は一切手で消していない。失効済みトークン5行を保持した状態で起動した。
- 起動は system-admin API の trigger（202）。

### 結果
- ログ: 物理削除バッチ完了 対象=2件・成功=2件・失敗=0件。FK 違反なし。D-1243-1 は根治。
- `users` は物理削除のため行ごと消え、`purged_at` 列の行は残らない（メールなどの個人情報の行は 0 件）。
- 7表は退会者2名とも 0 件（村 pin・ニックネーム含む）、refresh_tokens も 0 件。
- 対照: 7表は元の件数のまま、refresh_tokens も残存、API は 200。
- 旧トークン: 退会直後のアクセストークンでの `GET /users/me` は 401。退会後のログイン試行は AUTH_001。

### ロール横断
退会済み ID への `GET /users/{id}`・`/profile`・`/public-profile` を、本人（消滅）・他ユーザー・システム管理者・未認証で直打ちして、404 または 401 で個人情報なし。画面でも、他ユーザーから退会者の URL を直打ちすると 404 ページのみ。

### 所見
退会受付後に同ユーザーでログインすると `deleted_at` が NULL に戻る（猶予内ログインによる退会取消。仕様と思われる）。確認ログインで退会が取消されたため、API で退会し直した。

## 合否
合格。強匿名化は完走し、7表は 0 件、対照は残存する。
