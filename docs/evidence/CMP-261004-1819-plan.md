# CMP-261004-1819 実装計画・受け入れ条件

対象scopeは`app`。この文書は実装前の計画であり、試験・実機・独立探索の完了証拠ではない。登録基準は`origin/main`の`b0262b7b62eca70b1490983333f7d8c53e46900e`。Codex司令塔による軍議の最終ACレビュー済み。登録PRの採用後に試練へ進む。

## 原受け入れ条件

存在しない teamId でのシフトスケジュール作成が、SYSTEM_ADMIN でも不在として拒否される。契約テストで固定する。

台帳の完了条件セルは一字も変更しない。以下は原条件の試験可能な分解と、既存動作を保つ回帰条件である。

## 原因と採用方針

`ShiftScheduleController#createSchedule`は`POST /api/v1/shifts/schedules?teamId=`をFacadeへ渡す。`ShiftScheduleFacade#createSchedule`はSYSTEM_ADMINのチーム認可を短絡し、`ShiftScheduleService#createSchedule`は親チームを確認せずscalarの`teamId`を保存する。`V62.004__phase1a_drop_cross_domain_fk_wave4.sql`で`fk_ss_team`は撤廃済みである。

Facadeの既存明示契約に合わせ、不在も`403 COMMON_002`で拒否する。順序は「既存SYSTEM_ADMIN/通常ADMIN認可→`TeamService.findTeamSummary`で未削除チームの存在確認→既存書込Service」とする。認可に失敗した利用者には存在照会を行わない。親チーム不在を識別して書込みを止めるが、404・新エラー型・新権限は導入しない。

`TeamService.findTeamSummary`は未削除チームの存在をOptionalで返す公開窓口で、他ドメインのEntity/Repositoryを直接参照しない。`assertActiveTeamExists`はPROVISIONEDも拒否するため採用しない。公開範囲・アーカイブ・ACTIVE限定の新条件は加えない。
