## 実ロック先行CIのredとschema・監査観測の是正

head `065a7dd7583d6aa953d4145491953d9add6c55a3` の実MySQL試験は、承諾の加盟ロック先行で承諾200・取消500となった。取消の実Repository delegateから `CannotAcquireLockException` → MySQL SQLState `40001` / vendor `1213` が返り、承諾TXはcommit、取消TXはrollbackした。同期callback障害は空、承諾outboxは1行だった。取消先行と同時start10試行の成功で、このredを取り消さない。

テストは `src/test/resources/application-test.yml` の `ddl-auto: create` / `flyway.enabled: false` を使う。一方、本番共通設定は `application.yml` の `ddl-auto: none` / Flyway有効であり、`application-prod.yml` はこれらを上書きしない。正本 `V2.011__create_team_org_memberships_table.sql` は `uq_team_org UNIQUE (team_id, organization_id)` を作り、後続の当該表migrationにその削除・置換はない。`V62.008` も同一uniqueが存続する前提を明記している。しかしEntityの `@Table` にはこのunique宣言がなく、Hibernate生成schemaにはstatusを含む二次indexだけが宣言されていた。既存の同ドメインEntityと同じ `@UniqueConstraint` で正本に同期する。新しいmigrationや制約仕様は追加しない。

承諾はチーム行→PRIMARYの加盟行をロックしてstatusを更新する。取消は `(team_id, organization_id)` で加盟行をロックするため、uniqueを欠くテストschemaではstatusを含む二次indexを先に取ってPRIMARY待ちとなり、status更新側との循環待ちになった可能性がある。ただし実EXPLAIN・InnoDBのdeadlock graphは未採取で、使用indexと循環の詳細は未確定である。team/org/userへの外部キーは後続 `V62.006` / `.008` / `.009` で削除され、Entityにも関連付けはないため、親FKロック説の根拠はない。probeは実delegate後の有限待機だけで追加SQL・独自DBロックを取得しない。先行interleavingは保持し、probe・製品Commandのロック順・応答・retry/catchは変更しない。

別に、承諾監査のカウンタが通知種別 `TEAM_ORG_INVITE_ACCEPTED` と監査種別を混同していた。正本仕様 §4.1 と製品 `TeamOrgInviteService` / `AuditLogTeamAffiliationAuditRecorder` は `TEAM_ORG_MEMBERSHIP_CREATED`（`metadata.via=ORG_INVITE`）を書く。team/orgに加えmembership IDとviaで絞って実監査1件・敗者0件を数えるよう是正する。旧実測のacceptedAudits=0を製品監査欠落へ再解釈しない。取消監査にも同じmembership IDの絞り込みを加え、副作用保証を弱めない。OB14 rollback時の承諾監査0カウンタも同じ正本イベント・via・membership IDへ合わせ、存在しない監査種別を数えて常に0になる誤った検証を残さない。
