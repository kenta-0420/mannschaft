# 公開 API（permitAll）追加チェックリスト

`SecurityConfig` に `permitAll()` エンドポイントを新規追加する（または既存の `authenticated()` を
`permitAll()` に変更する）際に、レート制限の要否判断と実装確認を機械的に行うためのチェックリスト。

背景: 過去に「`SecurityConfig` のコメントには『レート制限あり』と書かれているのに、
参照先フィルタの正規表現がそのパスに実際にはマッチせず素通りしていた」事例が複数発見された
（本チェックリストの起票理由）。**コメントは実装を保証しない。** 必ず実測すること。

---

## 1. permitAll を足す前に

新しい未認証エンドポイントを追加する前に、以下を自問する。

1. **このエンドポイントは連打されると何が起きるか？**
   - DB に重い集計クエリを投げる（JOIN・集約・全表スキャン系）→ 高リスク
   - トークン / ID を含み、総当りで別人のデータや権限に到達しうる（IDOR・招待トークン等）→ 高リスク
   - メール送信・外部 API 呼び出し等のコストを伴う副作用がある → 高リスク
   - 静的・準静的な値を返すだけ（設定値・ポリシー等） → 低リスクだが無制限は禁止
2. **署名検証や capability トークンなど「認証以外の保護」があるか？**
   - Webhook の署名検証、ワンタイムトークンの単回使用等。あっても検証コスト自体を消費させる
     連打は起こりうるため、**レート制限の代替にはならない**（緩めの上限で共存させる）。
3. リスクが「低リスクだが無制限は禁止」以上なら、原則としてレート制限を実装してから
   `permitAll()` をマージする（後回しにしない）。

## 2. どのレート制限方式を使うか

| ケース | 方式 |
|---|---|
| GET が中心の公開参照 API（一覧・詳細） | `PublicApiRateLimitFilter`（`publicview/filter/`）に zone を足す |
| 性質が大きく異なる（重い集計・メール送信トリガー等） | 同ファイル内に**別 zone** を追加（新しい `Target` enum 値）。フィルタクラス自体は乱立させない |
| 特定ドメインに強く紐づく POST（例: 広告クリック） | そのドメインの既存フィルタ（例: `AdPublicEndpointRateLimitFilter`）に zone を足す |
| サービス層の一操作のみ（Controller 経由でなく Service 内で完結する副作用） | `AuthTokenService.checkRateLimit(key, maxAttempts, window)` を先頭で呼ぶ
  （`register` / `password-reset` / `parental-consent` 系と同じ作法。IP または対象ID をキーにする） |

新しいフィルタクラスを追加する前に、既存フィルタへの zone 追加で足りないか必ず検討する
（`docs/security/06 §4.1` のとおり、フィルタが乱立するとレビュー・監査コストが増える）。

## 3. コメントに「レート制限あり」と書く前に必ず確認すること

**これが今回の是正戦役の核心。** `SecurityConfig` にコメントを書く前に、以下を実際に確認する。

1. 対象フィルタのパスパターン（正規表現）を開き、**追加したパスが実際にマッチするか**を
   目視で確認する。特に注意すべき食い違い:
   - フィルタのパターンが `(teams|organizations)` のようにプレフィックスを限定している場合、
     新しいプレフィックス（`users` / `blog-posts` 等）は**別パターンとして追加しないと絶対にマッチしない**。
   - 選択肢のグループ（`(/posts|/events|...)`）に新しいサブパスを足し忘れると、
     末尾が一致しないため `matches()` は false になる。
2. 可能なら実際に `PublicApiRateLimitFilterTest` 等のユニットテストで「1 回叩いて
   `ValkeyRateLimiter.tryConsume` が呼ばれたこと」を検証する行を追加する
   （`shouldNotFilter` で弾かれていないことの直接証拠になる）。
3. `git grep` で対象パスのリテラルを検索し、フィルタ側とコントローラー側の両方に
   同じ文字列が存在することを確認する（typo・末尾スラッシュの有無のズレを防ぐ）。

## 4. `/**`（再帰）と `[^/]+`（1 階層）の落とし穴

- Mannschaft の公開 API 規約は **`/**` 再帰マッチを使わない**（`docs/features/F19.1... §7.4`）。
  IDOR 防止のため、各階層を `[^/]+` で 1 階層ずつ明示的に捕捉する。
- この規約はレート制限フィルタの正規表現にも同じ理由で適用される。ただし
  **「IDOR 防止のために厳格にした結果、新しいサブパスが未マッチになる」事故が起きやすい**
  （今回の timeline-posts / users / blog-posts 未マッチはこのパターン）。
  新しいサブパスを追加したら、必ず §3 の確認を行うこと。
- capture グループ番号に依存する監査ログコード（`recordRateLimitAudit` 等）がある場合、
  **既存グループの番号を変えないこと**。新しい選択肢は既存グループの `(...)` の内側
  （選択肢を増やす形）で追加する。

## 5. 新規公開 API に書くべきテスト

1. **red**: 対象パスが `shouldNotFilter` で弾かれず `resolveRule` が non-null を返すことを
   1 回のリクエストで検証する（`tryConsume` が呼ばれたことの verify で十分）。
2. **green**: 上限回数までは 200、上限+1 回目は 429 になることを検証する
   （`Retry-After` / `X-RateLimit-*` ヘッダー・JSON ボディも確認）。
3. **正常系（見落としがちだが必須）**: 上限内のリクエストが正しく通ること。
   「全部 429 になっていても気づけない」実装ミス（zone やキーの取り違え）を防ぐため。
4. 既存 zone と独立していることの確認（別 zone を使い切っても対象パスは影響を受けない）。
5. サービス層で `AuthTokenService.checkRateLimit` を使う場合は、モック化した
   `AuthTokenService` 経由でレート超過時に `BusinessException(AUTH_044)` が飛ぶことを確認する
   （429 へのマッピングは `GlobalExceptionHandler` の責務）。

## 6. 実装後の最終確認

- `SecurityConfig` のコメントを実態に合わせて更新する（「レート制限あり」と書くなら本当に
  効いている状態にする。効かせない判断をしたなら、その理由をコメントに残す）。
- 変更した正規表現が既存の保護対象パスを壊していないか、既存テストを再実行して確認する。
- ArchUnit の凍結ストア（`--tests` 絞り込みで壊れる既知の罠がある）に意図しない差分が
  出ていないか `git status` で確認する。
