## 0. 背景・目的

マスターが 3 領域（組織→チーム出欠/アンケート伝播・予約管理ダッシュボード・予約会員フロー＋休業一斉通知＋既読）の実機 E2E を別エージェントに依頼したところ、**未実装・エラーが複数発見**された。
AWS 本番投入前に、**設計書全体にわたって「設計に書いてあるのに UI/導線が無い／壊れている」箇所を体系的に炙り出す**ことが本法案の目的。

当初は上記 3 領域（F03.1/F03.4/F03.5/F03.6/F05.4）を除外していたが、**マスター指示により最終確認として全機能を対象に含めた**（P8/P9 で監査）。

## 1. 設計-実装トレーサビリティの判定凡例

| 記号 | 意味 | E2E 上の扱い |
|---|---|---|
| 🟢 **実在** | BE API・FE 画面・到達導線がすべて揃う | happy-path を実機で踏む |
| 🟡 **API のみ** | BE は実装済みだが FE の UI が無い／薄い | 「UI 欠落」として記録。API は契約テストで検証 |
| 🔴 **設計のみ** | 設計書に記載があるが実装が見当たらない | **未実装確定**。AWS 投入前に実装要否を判断 |
| ⚫ **到達不能** | FE 画面はあるが、人間が辿り着く導線が無い | UX 欠陥。導線追加が必要 |
| 🔵 **将来 Phase** | 設計上「次 Phase」と明記され先送りが正規 | 今回はテスト対象外（記録のみ） |

### テスト層（各フェーズ共通）
1. **Reachability（到達導線）** — ログイン後、当該機能まで画面遷移で辿り着けるか。**ここで詰まれば「設計あるが UI/導線欠落」を確定。**
2. **API Functional** / 3. **Realtime Delivery**（WS/STOMP・該当のみ）/ 4. **Integration**（クロスドメイン）/ 5. **Authorization**（ロール・IDOR・スコープ）

### 疑義の決着（思い込みを排した裏取り結果）
- **予約の「二重実装」疑義は誤り**: `emergency_closure_*`(予約ドメインロジック) と `confirmable_notification_*`(F04.3 汎用通知基盤) は**関心の分離による二層構造**であり設計違反ではない（P9 が原典逐語で確認）。
- **リアルタイム既読**: 通知/チャットの WebSocket は実装あり（P2）。予約固有の既読は F04.2/F04.3 管轄で現状 poll。「WS か poll か」の最終確定は実機 T-RT008 で。
- **「組織で修正したら反映されるか」**: アンケート/安否は**公開・実行後は編集不可が正しい設計**（P8 裏取り）。「修正の伝播」ではなく「公開前に確定」が仕様。

## 4. 重要な前提・注意（殿の戒め反映）

- **家老の机上判定は「疑義の提起」であって結論ではない。** 即修正に走らず、実機 E2E または原典精読で裏取りしてから確定する（二重実装疑義が好例：原典精読で否定された）。
- **机上インベントリ（地図隊）の実装ラベルは誤りを含む**（F01.9/F03.6 を「未実装」と誤判定 → 実際は実装済）。各フェーズ家老に実ファイルで裏取りさせた。
- **UI 入口の設置場所は迷ったら殿に質問する**（マスター指示 2026-06-17）。欠落 UI の導線をサイドバー/ダッシュボード/専用URL/設定のどこに置くかは情報設計判断。

## 5. E2E 実機実行のフェーズ計画（法案確定・御裁可後に着手）
- **実行環境**: ローカル実機（WSL2 backend :8080 / Nuxt :3000-3001 / MySQL・Valkey Docker）。既知の罠（CORS ブリッジ・幽霊ポート・3001 退避）を踏まえる。
- **Stripe 決済**: 実決済不可。テストカード(4242…)＋`stripe listen` で Webhook 到達確認まで。
- **並列可否**: 読み取り・UI・i18n は並列可。書き込み・状態遷移・決済・通知は DB 競合回避で直列推奨。
- **実行の推奨順**: P1(基盤認証で全テストの前提) → P8/P9/P2/P3(🔴 高リスク・書込/状態遷移/通知/決済) → P4 → P5/P6/P7(🟡 reachability で UI 欠落確定)。
