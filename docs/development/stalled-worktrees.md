開発途中で止まっている worktree を「消す」のではなく、1つの戦役 ID の下で別表管理し、開発を再開させるための台帳である。消してよいと確認できたものだけを撤去し、少しでも迷ったものはここに残している。

## 未 push の固有 commit がある worktree（優先して push または PR 化すべき）

**97 本**の worktree に、リモートに存在しない固有 commit がある（ブランチ単位の延べ 6282 件。積み上げ型のブランチは共通の履歴を重複して数えている）。worktree ディレクトリが消えるとローカル参照が失われ、この commit は復元できなくなる恐れがある。**優先して push または PR 化すべき**である（本別表の作成では push していない。push は担当者が判断して行う）。

判定は「`git ls-remote` のリモート先頭、または GitHub PR の head と HEAD が一致するか」で行った。squash merge 済みで内容が main に反映済みの可能性は個別には照合していないため、推奨は「まず push して退避し、その後に要否を判断」である。表の「push」列が「未push」「一部未push」の行が対象。

## 運用ルール

1. **着手するときは、その行の「状態」を「再開中」に更新する。** 同じ行を並行セッションが二重に再開しないための宣言である（横展開型の戦役の担当重複防止と同じ作法）。
2. **決着したら worktree を撤去する。** 決着とは「再開して PR マージ」「既存 PR へ統合」「破棄（理由を添えてマスター承認）」のいずれかで、状態を「決着」にし、証拠（PR 番号または破棄理由と承認）を「次の一手」列に書き添える。
3. **新たに止まった worktree はこの表に足す。** 黙って放置しない。未 push の固有 commit があれば先に push する。
4. 破棄は、固有 commit が main に入っていること（squash は PR の採用内容と照合）と、未コミット成果物が正本に取り込まれていることを確かめ、マスターの承認を得てから行う。lock の pid が生きているもの、PR が OPEN のものは撤去しない。
5. 機微情報は書かない。記載はパスとブランチ名までにとどめる。
