# 永続化enumの二段階展開

`@Enumerated(EnumType.STRING)` の定数名はDBの値として残る。定義の順序変更は値の意味を変えないが、
定数追加とその書込み開始を同時に配ると、旧バイナリが未知の値を読んで例外になり、APIが500を返し得る。
書込み済みの行はアプリのrollbackでは消えない。この作法は `BatchJobStatus.RESUMED` に限らず、
すべてのSTRING永続化enum（継承・埋め込み・enumコレクションを含む）に適用する。

## リリースの順序

1. **第1段階（読取り互換性の配布）**: 定数だけを追加する。新定数を書き始める変更は含めない。
   API、管理操作、バッチ、ジョブ、イベント処理、初期値、migration／backfillなど、全書込み経路で
   既存値を維持する。PRに対象enum・追加定数・対応するテーブル／列・書込み経路の調査結果を記録する。
   CHECK制約や列長の変更が必要なら、書込み前に互換性を確認する。
2. 第1段階を、同じDBを読む**すべてのタスク**へ配布する。API以外のワーカーやバッチも含め、
   旧versionの実行数が0で、遅れて動く旧タスクも再起動しないことを確認する。
   リリース記録へ対象環境・第1段階のversion／image digest・対象タスク・旧タスク退場の確認時刻と証拠を残す。
   確認できない場合、第2段階へ進めない。
3. **第2段階（書込み開始）**: 第1段階の完了記録を参照する別のリリースで、新定数を書き始める。
   書込み経路と新しい行の再読込みを検証する。単に別PRへ分けただけでは、第1段階を展開済みとは扱わない。
4. **rollbackの下限は第1段階**とする。新定数を知らない第1段階より前のバイナリへ戻してはならない。
   第2段階の機能を止めても既存の新定数行は残るため、停止だけでは下限を下げられない。
   より古いversionへ戻す必要がある場合は、全新値の意味・変換先・並行書込み停止・読取り互換性を
   個別に設計、承認、検証する。行削除や一律置換を通常のrollback手順にしない。

定数の削除・改名も、DB残存値の読取りとrollbackへ影響する。追加の二段階手順だけで安全とは判断せず、
値の移行と全読取りversionの互換性を別途確認する。

## 定数追加を検知する番人

`PersistedEnumCompatibilityArchTest` が、既存のArchUnitで全本番classのfield／propertyにある
`@Enumerated(STRING)` を読み、定数の `完全修飾型名#定数名` 集合を
`backend/src/test/resources/persisted_enum_guard/string_enum_compatibility.txt` と完全一致で照合する。
通常のBackend CIのテストに含まれ、追加・削除・改名・新規永続化enumで失敗する。
非永続enum、ORDINAL、注釈既定値、コメント／文字列内の偽装は対象外で、import／型名はコンパイラが解決する。
STRING注釈の型を解決できない場合は失敗させ、黙って走査対象から外さない。

赤くなったら、検出された定数と実装差分を確認し、上のリリース計画をPRへ記載してレビューを受ける。
計画と読取り互換性を確認した定数だけを、同じPRで互換性台帳へ明示的に追加する。
台帳の自動更新や「CIを緑にするためだけ」の更新を行わない。台帳は一般のアーキテクチャ違反の免除表ではない。

**台帳との一致は二段階デプロイの実施を証明しない。** 番人は書込み開始や旧タスク退場を証明できないため、
PRレビューとリリース記録で確認する。台帳更新済みでも、第1段階の展開が完了するまで書込みを始めない。
全注釈を保守的に収集するので、実際には使われないマッピング宣言もレビュー対象になる。
`AttributeConverter`、native SQLの文字列、JSON内部のenum、XMLマッピングは検出範囲外であり、
それらの永続化値を変えるときも読取り互換性を手動で確認する。

初期台帳は本番未構築の時点の定義を記録したもので、既存定数（`RESUMED` を含む）が二段階で
本番展開済みだという証跡ではない。初回本番展開前に本書を運用手順へ組み込み、以後の追加へ適用する。

## 検証

`PersistedEnumInventoryTest` が、追加定数、非永続enum／ORDINAL／既定値の除外、propertyアクセス、
MappedSuperclass／Embeddable、enumコレクション、新fieldによる永続化、static／Transientの除外、
コメント／文字列偽装、解決不能型を実バイトコードで検証する。
本番全量と台帳の照合は `PersistedEnumCompatibilityArchTest` が担う。
ローカルで全テストを実行する場合は `backend/scripts/gradle-turnstile.sh` を使い、
ArchUnitを `--tests` で絞らない（既存凍結ストアの保全規則）。同等の検証を公式CIで行ってよい。
