## A. 4 分類の判定基準

### 🔴 真の漏れ（実装追加要）

| 条件 | 内容 |
|---|---|
| 検出区分 | 設計あり・実装なし |
| 状態 | 設計書の **現フェーズが「実装済み」とされているのに実装が無い** |
| 例 | F02.9 Phase 1 で `/api/v1/me/favorites/check` を実装するはずだったが Controller に存在しない |
| 対処 | バックエンド実装追加 PR を作成し、不足しているエンドポイントを実装する |
| 担当 | バックエンド系足軽 |
| PR 命名 | `修正: [機能] [メソッド] [パス] を追加（Phase X 漏れ補完）` |

**判定の手順**:
1. 設計書ファイルの該当行を Read で開く
2. その章のフェーズ表記を確認（「Phase 1 実装済み」「v1.0 リリース済」など）
3. 該当 Controller を Glob/Grep で探し、確実に該当エンドポイントが無いことを確認
4. **Service / Repository は存在するが Controller のみ漏れ** のケースもあるため、ロジック有無も併せて確認

### 🟡 設計書更新要

| 条件 | 内容 |
|---|---|
| 検出区分 | 実装あり・設計なし / 実装あり・設計が古い |
| 状態 | **実装が正であり、設計書の更新で整合させる** |
| 例 | 機能改修で URL prefix が `/api/v1/circulation/*` → `/api/v1/organizations/{orgId}/circulations/*` に変わったが、設計書が旧記述のまま |
| 対処 | 該当設計書の §4 系（API 仕様）セクションに追記または書き換え |
| 担当 | 設計書精通の足軽（機能ドメイン担当） |
| PR 命名 | `設計書更新: [F**.md] [機能] §4 API 仕様 整合（乖離 N 件解消）` |

**判定の手順**:
1. 該当 Controller の docstring・ JavaDoc・メソッド名から意図を把握
2. 関連する `F*.md` を Grep で探す（コントローラ名 / 関数名 / リソース名で）
3. 設計書側にどう書かれているか確認 → 古ければ実装に合わせて改稿
4. 設計書自体が存在しない新機能であれば 🔴 と区別するため必ず実装側の意図・ユースケースを確認した上で 🟡 化（実装が「将来へ向けた仕掛け」なら 🔵 候補）

**設計書なし新エンドポイントの取り扱い**:
- 1 機能に集中している（例: `/api/v1/villages/*` 122件）→ **新規設計書を 1 本起こす**
- 既存設計書の追補で済む（例: `/api/v1/feedbacks` を F10.1 に追記）→ **既存 §4 に追記**

### 🔵 将来機能（明示残課題）

| 条件 | 内容 |
|---|---|
| 検出区分 | 設計あり・実装なし |
| 状態 | 設計書側で意図的に「未実装」とされているが、**明示ステータスが無くて漏れに見える** |
| 例 | F03.5 Phase 5 の API 群。Phase 5 自体が未着工で、設計書にはエンドポイント記載のみ |
| 対処 | 設計書に **🔵 ステータスバッジ** を追加して明示し、ベースライン報告書から自動除外できるようにする |
| 担当 | 設計書精通の足軽 |
| PR 命名 | `設計書更新: [F**.md] [機能] 未実装エンドポイントに 🔵 マーカ付与（Phase X）` |

**判定の手順**:
1. 設計書の該当フェーズ章の冒頭を読み「Phase X は未着工」「Phase X 計画」などの記述があるか確認
2. 該当エンドポイントを実装する PR が存在しないこと（git log / GitHub PR で検索）
3. **🔵 マーカ仕様**（後述）に従い、設計書側を更新

### ⚪ 除外（設計書対象外）

| 条件 | 内容 |
|---|---|
| 検出区分 | 実装あり・設計なし（主） |
| 状態 | 設計書化が **不要** な internal / admin / debug / actuator / 互換用エンドポイント |
| 例 | `/actuator/*`, `/api/internal/*`, `/api/v1/admin/system-flag/*`, `/v3/api-docs/*` |
| 対処 | `docs/internal/api_drift_exclusions.yml` にパターン追加 → スキャナ次回実行で除外 |
| 担当 | 軍議参謀 / 殿 |
| PR 命名 | `除外パターン追加: [パターン] - [理由]` |

**判定の手順**:
1. パスから内部用 / 監視用 / 旧版互換のいずれかであることを確認
2. Controller の package（`com.mannschaft.app.admin.system` / `actuator` 等）を確認
3. exclusions.yml にパターン追記 → コミット

## B. 🔵 将来機能タグ仕様

設計書内で未実装エンドポイントを明示する記法。次の 3 案を検討した。

### 案 A: ステータスアイコン列追加（既存 API 仕様表に追加）

```markdown
| 状態 | メソッド | パス | 説明 |
|---|---|---|---|
| 🟢 | GET | `/api/v1/foo` | 実装済み |
| 🔵 | POST | `/api/v1/foo/v2` | Phase 5 で実装予定 |
```

- 利点: 一覧性が高く、未実装が一目瞭然
- 欠点: 既存 API 仕様表のフォーマットを全機能で書き換える必要あり（影響大）

### 案 B: ステータス専用テーブル（独立セクション）

```markdown
#### 実装ステータス（自動分類用マーカ）

- 🟢 実装済み（v1.0〜）: GET /api/v1/foo
- 🔵 未着工（Phase 5）: POST /api/v1/foo/v2
```

- 利点: 既存表を弄らず追記のみで完結。スキャナでセクション全文を読み取りやすい
- 欠点: 表とリストの二重管理が発生し得る

### 案 C: 各エンドポイント table に新規列 `実装`（Phase X）

```markdown
| メソッド | パス | 実装 | 説明 |
|---|---|---|---|
| GET | `/api/v1/foo` | Phase 1 | ... |
| POST | `/api/v1/foo/v2` | Phase 5 (未着工) | ... |
```

- 利点: フェーズ情報も保持でき、進捗が table 内で読める
- 欠点: 全 §4 系テーブルの書き換えが必要、列幅が広くなり可読性が落ちる

### **足軽2 のお薦め: 案 A（採用推奨）**

**理由**:
1. **スキャナ側で正規表現一発判定が可能**（先頭列が `🔵` なら除外）— 案 B は section 全体読みが必要、案 C は列位置の解析が必要
2. **既存表の改修が局所的**（先頭に `| 状態 |` を 1 列追加するだけ、内容は `| 🟢 |` 一律で機械置換可能）
3. **エンドポイント単位で粒度を持てる** — 同じ章内で Phase 1 実装済み・Phase 5 未着工が混在しても表現できる
4. 案 B はリストと表の二重管理になりがちで、ドリフトが発生しやすい
5. 案 C はテーブル列数が増えて、ページ幅の狭い設計書でレイアウト崩れリスク

**運用ルール**:
- 既存 API 仕様表に `状態` 列を先頭追加（実装済みは `🟢`、未着工は `🔵`、廃止予定は `⚫`）
- Stage 2 着手時にドメインごとに表を機械置換でマイグレーション
- スキャナ v3 で `🔵` 行を除外対象とする（v2 改修で対応）

## E. PR 単位と粒度

### 原則

- **1 ドメイン = 1 PR** が基本
- ただし **100 件超ドメイン** はサブドメインで分割
  - `/organizations/*` 例: `/members/*`, `/facilities/*`, `/parking/*`, `/repair-plan/*`, `/promotions/*`, `/property-history/*`, `/tournaments/*`, `/workflows/*`, `/residence-status/*` 等
  - `/teams/*` 例: `/members/*`, `/schedules/*`, `/shifts/*`, `/chat/*`, `/circulations/*`, `/announcements/*`, `/todos/*` 等
- 1 PR あたり **50 件以内** を目安にする（レビュー負荷上限）

### コミットメッセージ規約

```
Stage2 [ドメイン名]: triage N件 → 漏れX件修正 / 設計書更新Y件 / 将来Z件 / 除外W件
```

例:
```
Stage2 /me/: triage 67件 → 漏れ3件修正 / 設計書更新58件 / 将来5件 / 除外1件
```

### PR 本文テンプレート

```markdown
## ドメイン: /api/v1/[ドメイン]/*

### triage 結果サマリ
- 🔴 真の漏れ（実装追加）: N 件
- 🟡 設計書更新: M 件
- 🔵 将来機能（🔵 マーカ付与）: K 件
- ⚪ 除外（exclusions.yml 追加）: L 件

### 🔴 実装追加分

| メソッド | パス | Controller | 設計書 |
|---|---|---|---|
...

### 🟡 設計書更新分

| 設計書 | セクション | 追加/書き換えエンドポイント数 |
|---|---|---|
...

### 検証

- [ ] バックエンド単体テスト追加（実装追加分）
- [ ] `scan_api_drift.py` 再実行で当該ドメインの乖離件数が想定どおり減ったことを確認
- [ ] 設計書のレンダリング崩れがないことを確認
```

## F. 留意事項

### F.1 スキャナの既知制約（v2 時点）

triage 時に「スキャナが拾えていない」ケースに遭遇したら以下を疑う:

1. **インライン記法のみのエンドポイント**: F17.1 のように `POST /api/v1/villages` がコードブロック外の本文行で書かれているケース。v2 で部分的に対応しているが、`POST /api/v1/foo` 単独行などは漏れる
2. **URL prefix `/api/v1/` を持たないコントローラ**: `IncidentController` (`/api/incidents`)、`SignageScreenController` (`/api/signage/screens`) など。**スキャナは `/api/v1/` 始まりしか追跡しない**ため、URL prefix を `/api/v1/` に揃える / 設計書側を `/api/incidents` に合わせる、のいずれかで根治
3. **`/api/v1/{_}/{_}` 表記揺れ**: 設計書側で `/api/v1/{scope}/{scopeId}/foo` と書かれ、スキャナは `/api/v1/{_}/{_}/foo` として展開。実装側 `/api/v1/teams/{teamId}/foo` との突合は v2 のスコープ展開で部分対応済みだが、ドメイン名がパラメータ化されている場合は不可能。triage 時は人間判断

### F.2 「設計書なし」かつ「実装に意図不明」な場合

- 過去の PR / commit log を `git log -p --follow` で追って、なぜ追加されたかを確認
- それでも不明であれば **殿に上申** し、設計書整備か削除かを判定してもらう

### F.3 削除候補（コントローラごと使われていないケース）

- フロントエンドからの呼び出しが Grep で 0 件 → 殿に削除可否を上申
- 安易に削除コミットを作らず、必ず軍議経由で判定

### F.4 進捗トラッキング

各 PR マージ時に `docs/internal/api_drift_baseline.md` を再生成し、`サマリ` セクションの 3 数値が減っていくのを定量モニタリング。

理想ゴール:
- 設計あり・実装なし: 0 件
- 実装あり・設計なし: 0 件
- 一致: 2,421 件以上

## 付録: 用語集

| 用語 | 意味 |
|---|---|
| 乖離 (drift) | 設計と実装の不一致 |
| triage | 乖離を 4 分類のいずれかに振り分けること |
| Stage 0 | スキャナ・ルール整備期 (現在進行中) |
| Stage 1 | スキャナ改善 + ベースライン生成（足軽1 完了） |
| Stage 2 | ドメイン別 triage 並列実施期（次フェーズ） |
| Stage 3 | スキャナを CI に組み込み、乖離発生時に即座にブロック |
